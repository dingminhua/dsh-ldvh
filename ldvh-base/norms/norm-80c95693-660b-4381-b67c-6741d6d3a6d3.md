# dsh-ldvh 发布规范

## 方向定位与适用范围

**管什么**：本方向管 dsh-ldvh 发布的完整纪律：版本门面、发布门禁、分支载体与产物边界。

**何时查阅**：准备发布、打 release tag、改版本号或推送 main 分支前查阅本规范。

## 核心规则体系

**管辖边界声明**：本规范是 dsh-ldvh「发布」方向的唯一权威依据，由三块合并而成——① 发布门面（版本号双轨、分发渠道、README/CHANGELOG 等发布规则，原元规范 specs/10 §7.1–§7.4；版本声明点核对规则与受保护文档路径登记仍留元规范 §7，本规范只引用）；② 发布门禁（发布前须过的硬门槛）；③ 分支载体纪律（dev/main 两条线各自可承载的内容）。三者主语同为「这个仓库怎么发布」，合并后不再分散定义。本规范不定义提交契约（元规范 specs/09）、代码与测试实现纪律（元规范 specs/06）、日常开发验证（dsh-ldvh-dev-workflow），也不承载 Output Envelope 的宿主机制（元规范 specs/10 §7.7，留元规范）。

**不管什么**：

- 提交契约与 Git Gate 的门禁规则归元规范 `specs/09`；本规范只引用其结论作为发布前置。
- 测试与构建的实现纪律归元规范 `specs/06`；日常开发验证（依赖安装、单元测试、打包核对、UI 验收、开发红线）归本项目 `dsh-ldvh-dev-workflow`；发布复用其结果，不重复定义。
- Output Envelope 的宿主承载（存储位置、生成职责、Web 投影）归元规范 `specs/10 §7.7`，本规范不纳入。
- 其他项目或其他仓库的发布流程与分支策略；各项目按自身实际自建方向。

**来源合并说明**（不是规则，记录去向）：本规范由 `norm-773cc0bc`（发布门槛）、`norm-d95bbb45`（分支载体纪律）与元规范 specs/10 §7.1–§7.4 合并而来（§7.5/§7.6 的路径登记位留元规范，本规范曾误搬已撤回，见「登记位归属说明」）；两份旧 Norm 以 `superseded` 退役，正文写明承接的本对象 uid。合并后原三份中「发布门面归 specs/10 §7」「本规范不构成第二权威」等划界句一并失效——因为门面规则已进入本规范自身。

### 第一部分：发布门面

**版本号双轨制**：对外发布版本 `MAJOR.MINOR.PATCH`（纯 SemVer，仅正式发布递增）；开发迭代版本同主版本 + `-dev.N`。二者共享主版本、互不污染；发布时封存干净版本，之后 dev 进入下一轮。`-dev.N` 的递增时机：`N` 只在已存在可区别的上一轮开发版本时递增；首次正式发布之前 `N` 恒为 `1`，不随开发迭代递增；首次正式发布后按需递增（如 `1.1.0-dev.1` → `1.1.0-dev.2`）。不要求为尚无对外版本的开发过程建立迭代计数。

**分发渠道**：DSH 插件市场（主要渠道，接受开源公共契约）／本地 asar 加载（开发测试与离线使用）／源码安装（社区贡献与自定义构建）。

**两类 README 及其分工**：仓库 README（`README.md`）是仓库首页，面向源码访客，说明仓库定位、版本号双轨规则与当前里程碑；插件 README（`plugin/README.md`）是 DSH 插件市场的用户第一眼界面，遵循行业通用格式（项目名与一句话定位、安装说明、使用指引、配置项、开源协议 MIT、版本号），内容须与当前版本实际能力一致，不得超前宣传。两者职责不得互相替代或整体搬入另一方；允许两处复述同一事实（许可证名、项目名），禁止职责混同。英文衍生件 `plugin/README.en.md` 是插件 README 的英文机械衍生物，不属受保护文档，可不经受保护流程重写，与中文版不一致时以中文版为准，不得承载中文版没有的实质要求。

**CHANGELOG**：遵循 Keep a Changelog——条目 `## [版本] - YYYY-MM-DD`，分区 Added/Changed/Fixed/Removed/Known。每次发布对应一条；条目内容必须由实际已提交变更支撑，不得为未提交内容记录；与受控提交契约对齐（message 与 diff 共同支撑条目）。

**版本声明点与受保护文档**：CHANGELOG 版本条目、manifest 版本字段、两类 README 版本行共同构成版本声明点，四处必须一致，漂移按停止条件处理；00 §3.3 五类受保护内容的精确路径清单与版本声明点登记，其唯一权威登记位在元规范「DSH 环境接入规范」§7（原 specs/10 §7.5/§7.6，改名后保留）。本规范**只引用该登记，不复制其路径表、不另建第二登记权威**（01 §14.1、00 §3.3）；本规范自身的门禁 4、门禁 5 与「代码不引用事实对象内容」规则按该登记执行核对，路径清单的变更须经 Human Gate 并走元规范。

**登记位归属说明**（本规范与元规范的分工）：受保护文档路径清单与版本声明点登记属**元规范层**职责（00 §3.3「下位规范承接」、01 §14.1），由元规范「DSH 环境接入规范」§7 承载，对全部受管辖项目生效。本规范在建立草稿时曾把这两张表复制进自身，属"两处定义"错误（本规范反模式明禁），已撤回——本规范只路由引用，不承载路径表。

### 第二部分：发布前门禁

执行发布前，以下各项全部必须满足；任一项不满足即不得发布：

1. **工作区与 release commit 洁净**——`git status --porcelain` 无输出，拟发布的 commit 不含未提交改动。
2. **依赖可复现安装**——`npm --prefix plugin ci` 通过（依 `package-lock.json`，非 `install`）。
3. **机械规则测试全绿**——`npm --prefix plugin test` 通过，无跳过项替代通过结论；须在有事实源的工作树（dev）执行，发布树无 `ldvh-base/` 会因缺事实源产生假失败。
4. **打包内容核对**——在 `plugin/` 目录执行 `npm pack --dry-run`（`npm --prefix plugin pack --dry-run` 在 npm 11.x 上以 ENOENT 失败），核对清单：`lib`、`icons`、`plugin/docs/assets`、`screenshots.json`、`plugin-specs`、`cordis.patch.yml`、`web/dist`、`web/api-js`、`web/shared-js`、`LICENSE`、`README.md`、`README.en.md`、`CHANGELOG.md`（以 `plugin/package.json` 的 `files` 字段为权威）。清单与 `files` 字段不一致时先查清再发布。
5. **宣传与能力一致**——README 与 CHANGELOG 不得超前宣传未实现功能（本规范「发布门面」部分已给出两类 README 与 CHANGELOG 规则）。
6. **市场产物一致**——市场登记 YAML 与 package 元数据一致；`plugin/screenshots.json` 截图可访问且对应当前版本。**以对象存在且消费形态已确认为前提**：市场登记 YAML 当前仍不存在，截图清单消费格式尚未取得市场侧确认，故本项仍不可执行；产物就位前不得声称已核对通过，亦不得因此反向放松其余各项；若最终不采用某产物，须走受控更新修订本项。

**建立时剔除项（非规则）**：`RELEASING.md` 原要求核对「Python 核心」进包——本仓已无 Python 源文件、`files` 亦不含 Python 产物，纳入会携带失实规则。

### 第三部分：发布操作与发布后核对

- 发布动作在 `plugin/` 目录执行 `npm publish`。
- Git tag 必须指向包含实际发布代码的提交，否则该次发布不可追溯。
- npm 2FA 按 CLI 提示在浏览器确认，不得绕过。
- 发布后核对：`npm view dsh-ldvh version` 与 `npm view dsh-ldvh dist-tags.latest`，确认线上版本与本次一致；registry 与镜像可能有 staged 延迟，按官方源时间线判断。

### 第四部分：分支载体纪律

1. **日常推送只进 dev**——开发提交只进 `dev` 并推 `origin/dev`；`main` 不接收日常开发的推送。检查：推送前 `git rev-parse --abbrev-ref HEAD` 为 `dev`。
2. **main 仅由发布动作推进**——`main` 每次前进对应一次发布或发布准备，不是日常合并。检查：`main` 上每个提交可对应发布记录、tag 或当次发布的受控提交。
3. **main 的树不含事实对象**——`main` 树中不出现 `ldvh-base/` 整个目录。检查（机械可判）：`git ls-tree -r --name-only <ref> -- ldvh-base` 输出为空即成立。
4. **发布产物不含事实对象**——`npm pack` 清单中不出现 `ldvh-base/` 下任何路径。检查：`npm pack --dry-run` 输出检索 `ldvh-base/`，零命中即成立。
5. **规则本体在 main 上不可读**——本规范以事实对象形态存于 `ldvh-base/norms/`，该目录不在 `main` 上，故从 main 单取树时本规范不可召回、不可读取；该情形靠 CI 检查兑现，不靠读取兑现。检查：CI 或发布流程须存在对第 3、4 条的机械检查；缺失时须如实登记为无机械保障。

6. **临时发布工作树位置固定、本地依赖隔离**——发布准备可在专用工作树中进行，检出源为发布线最新提交（`origin/main`；本地 `main` 可能落后，不得直接作为检出源）。位置以项目登记根 `project.path` 为锚：其父目录下、目录名为项目 id 加 `-main-release`（本项目为 `dsh-ldvh-main-release`，相对项目根为 `../dsh-ldvh-main-release`）；不得建在项目根内部，也不得使用 `/private/tmp` 等临时目录。该类工作树从发布线检出，不含开发树根 `.gitignore`（发布树内 `plugin/web/.gitignore` 已含 `node_modules`，但 `plugin/.gitignore` 未含），故 `npm --prefix plugin ci` 产生的 `plugin/node_modules` 会成为未跟踪文件。处置优先在发布线的 `plugin/.gitignore` 补 `node_modules/`（受版本控制、跨机持续）；不改发布线时，才在 common git-dir 的 `.git/info/exclude` 补 `node_modules/`（按 common-dir 解析，per-worktree 私有 `info/exclude` 不生效）——该本地配置属机器状态，不入库，换机或新克隆须重做。依赖目录不得进入 main 树的提交，发布产物边界另见第五部分。发布完成后，该工作树的保留或清理由 Human 决定，不因发布已推送自行删除；既存于 `/private/tmp` 的工作树由 Human 决定迁移或清理，迁移完成前不按本条追溯判定。检查：在该工作树执行 `git status --porcelain -uall`，输出中不出现 `node_modules/` 路径；在发布树执行门禁 1 时，以本条 ignore/exclude 已就位为前提；本条检查由能读取本规范的主控（dev 侧）发起，不以发布树内可读本规范为前提。

无机械强制面（核对：Human）

### 第五部分：发布内容纪律（代码与产物）

**规则：LDVH 代码不得引用具体事实对象内容**——随版本发布的插件实现代码（`plugin/lib/`、`plugin/web/` 等源码与产物）不得把任何具体事实对象的内容（`object_uid`、标题、正文片段或指向 `ldvh-base/` 具体载体的路径）作为实现依赖或逻辑依据；代码对事实源的访问须走类型契约与通用机制。理由：随版本发布的代码一旦绑定某项目事实内容，该内容即随包进入所有安装该版本的管辖项目。发布前以代码审查核对，当前无机械检查。

无机械强制面（核对：Human）

**规则：发布包须运行时完整**——随版本发布的包必须同时具备三层：`web/dist`（前端静态资源）、`web/api-js` 与 `web/shared-js`（后端编译产物，由 `scripts/build-api.mjs` 从 TS 源码预编译）、后端运行时依赖在 `plugin/package.json` 的 `dependencies` 中声明（名单以 `scripts/require-web-dist.mjs` 的 `WEB_RUNTIME_DEPS` 为准，当前 express／cors／compression／dotenv／js-yaml，**不得含 tsx**——带入 esbuild 构建脚本触发 pnpm 11 审批门）。理由：#1（缺 web/dist）、#2（缺后端运行物与依赖）、#3（tsx 触发审批门）是同一根因的三层——只核可见层、漏运行时层。`scripts/require-web-dist.mjs` 经 prepack 对存在性、声明与 `web/.npmignore` 在场做硬校验；CI 独立 install-smoke job（`scripts/smoke-install.mjs`）在 pnpm 11、allowBuilds 空的干净 workspace 安装并用有限重试探 health（不用 pid 当就绪信号，避 pitfall-8dbcd708）。两层互补，均不替代门禁 4 的 pack 输出人工比对。prepack 门禁不在 23 §6.1 的 gate 解析面内，按 §13.1 如实披露「声明无法用该闭集表达」。

无机械强制面（核对：Human）

**产物边界汇总**：发布产物须包含 `plugin-specs`（运行时机制载体，核对见门禁 4）；不得包含 `ldvh-base/` 下任何事实对象路径（依据见本规范「分支载体纪律」第 4 条）；连同上述两条规则，共同构成发布内容边界，不另立第二权威。

### 双源声明（唯一权威依据）

本规范自成立之日起为本项目「发布」方向的唯一权威依据。仓库根目录的 `RELEASING.md`、`DEVELOPMENT.md` 降为历史草稿——保留为过程记录，不再具规范效力；两者内容不一致时以本规范为准。历史草稿的收敛处置（删除、改为指针或继续保留）须由 Human 决定并走受控更新；本轮合并只完成归属与规则承载，不执行草稿收敛。

## 约束与反模式

**禁止项**：

1. 禁止在门禁任一项未满足（或不可执行而不自知）的情况下执行发布。
2. 禁止在 README/CHANGELOG 中超前宣传未实现的能力。
3. 禁止绕过 npm 2FA 认证。
4. 禁止发布不含实际发布代码的 Git tag。
5. 禁止声称已核对不存在的产物（如尚不存在的市场登记 YAML），亦不得把「截图清单已就位」读作「门禁第 6 项已通过」。
6. 禁止在随版本发布的 LDVH 代码中把具体事实对象内容作为实现依赖或逻辑依据。
7. 禁止以「main 落后很多」为由把 dev 整体合入 main（会把事实对象当产品内容发布）。
8. 禁止以「产物侧已满足」为由跳过分支侧检查。
9. 禁止声称本规范已被机械保障，除非分支纪律第 3、4 条的 CI 检查确实存在且实际运行。
10. 禁止删除 `main`（`origin/HEAD` 指向它）；禁止在 `main` 上读取本规范并据以判断「本项目没有这条规则」。
11. 禁止在发布已推送后自行删除临时发布工作树；禁止把 `node_modules/` 等本地依赖目录提交进 main 树。

**反模式**：

- **门禁空转**：清单写在文档里但从未逐项执行，发布凭印象放行——每一门禁项须有当次实际执行证据。
- **对象漂移不自知**：门禁项所核对的产物已被删除或尚未建立却仍按「已核对」对待——每次发布前先确认对象真实存在。
- **两处定义**：把已并入本规范的门面规则（版本语义、渠道、README/CHANGELOG 格式）再写进别的载体，或把留在元规范 §7 的受保护文档路径表复制到本规范，制造第二权威。
- **可见层偏食**：只核看得见的层（dist）、漏运行时层（api/shared/依赖）——#1/#2/#3 三次事故的根因。

**违规后果**：违反禁止项致发布条件不成立时，该次发布不成立，须撤回已发布版本或补做缺失门禁后重新发布；已据其作出的「已发布/可用」声明应予撤回（00 §4.6 据实声明）。违反分支纪律第 3 条时，发布线内容与项目事实源不可区分，须回退该次合并并重做树。
