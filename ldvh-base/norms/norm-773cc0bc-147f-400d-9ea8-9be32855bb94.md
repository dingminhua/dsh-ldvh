# 发布门槛

## 方向定位与适用范围

**管什么**：本方向管 dsh-ldvh 仓库执行发布动作的硬性前置门禁与发布过程纪律。

**何时查阅**：准备执行发布、打 release tag 或推进 main 分支前查阅本规范。

## 核心规则体系

**管辖边界声明**（原载于定位段，2026-11-15 按 27 §8 新契约迁入本节，内容逐句迁入、无删除——其中句首措辞随段落接续调整，详见本条 change_log）：本规范回答「这个仓库什么时候允许执行发布」，不回答「LDVH 插件作为产品应如何发布」。

**不管什么**：

- **LDVH 插件的发布门面**（版本号双轨语义、分发渠道、README 与 CHANGELOG 的格式要求、版本声明点三者一致性、受保护文档）归元规范 `specs/10 §7`。本规范**不复制、不改写**其中任何一条，也不构成其第二权威；凡涉该类问题一律回溯 `specs/10`。
- **提交契约与提交检查语义**（含 Git Gate 的门禁规则）归元规范 `specs/09`；本规范只引用其结论作为发布前置，不重新定义。
- **日常开发验证**（依赖安装、单元测试、打包核对、真实 UI 验收、开发红线）归本项目 `local-dev-workflow` 方向规范；发布**复用**其结果，不重复定义。
- **其他项目的发布流程**。

**与相邻规范的分工**：本规范与 `local-dev-workflow` 的主语不同——后者管**开发期**的动作，本规范管**发布点**的门禁条件。开发期验证通过是发布的**必要不充分**条件：本规范在开发验证之上追加发布专属检查（工作区洁净、包内容核对、真实安装验收、市场产物一致、发布后核对）。

**建立时的两处剔除**（均为**剔除**事项，不是本规范的规则）：

1. `RELEASING.md` 原「发布前门禁」第 4 项要求核对「**Python 核心**」进入包——本仓库**已无任何 Python 源文件**，`plugin/package.json` 的 `files` 字段亦不含 Python 产物。该核对项已无对象，纳入会使规范携带失实规则。
2. 该文件 `plugin/screenshots.json` 相关核对项，其**对象在建立时不存在**（该对象已于 2026-11-19 建立，见「尚未就位的发布产物」）。

保留一条已失效的规则会使规范携带错误结构（`01 §11.3`）。

### 发布前门禁

执行发布前，以下各项**全部**必须满足；任一项不满足即不得发布：

1. **工作区与 release commit 洁净**——`git status --porcelain` 无输出，且拟发布的 commit 不含未提交改动。
2. **依赖可复现安装**——`npm --prefix plugin ci` 通过（依 `package-lock.json`，非 `install`）。
3. **机械规则测试全绿**——`npm --prefix plugin test` 通过，无跳过项替代通过结论。
4. **打包内容核对**——在 `plugin/` 目录下执行 `npm pack --dry-run`（注：`npm --prefix plugin pack --dry-run` 在 npm 11.12.1 上不生效——`pack` 不接受 `--prefix`，会以 ENOENT 去找仓库根的 `package.json`），核对输出文件清单与实际预期一致：`lib`、`icons`、`plugin/docs/assets`（发布用截图）、`screenshots.json`（截图清单）、`specs`（打包时由 `prepack` 的 specs-bundle 脚本从仓库根复制生成的包内副本，`postpack` 清理；仓库工作树中它不存在属正常形态，核对对象是 pack 输出而非工作树）、`cordis.patch.yml`、`web/dist`、`LICENSE`、`README.md`、`README.en.md`、`CHANGELOG.md`（以 `plugin/package.json` 的 `files` 字段为权威；2026-11-16 勘误：本清单此前漏列 `specs`，与 `files` 字段漂移；2026-11-19 勘误：`files` 字段新增截图目录与截图清单两项后本清单同步补列，并改正 pack 命令形式）。**清单与 `files` 字段不一致时，先查清差异再发布。**
5. **真实安装验收**——在目标 DSH Desktop 上完成真实安装、重启、升级、停用、卸载全项验证。此为人工验收，不得以测试通过替代。
6. **宣传与能力一致**——README 与 CHANGELOG 的内容不得超前宣传尚未实现的功能（该要求的规范依据是 `specs/10 §7.3`/§7.4，本规范只将其列为发布前置，不改写其内容）。
7. **市场产物一致**——市场登记 YAML 与 package 元数据一致；`plugin/screenshots.json` 的截图可访问且对应当前版本。**该项以其对象存在且消费形态已确认为前提**，见下节。

### 尚未就位的发布产物

市场登记 YAML **当前仍不存在**（建立时实读核对）。`plugin/screenshots.json` **已于 2026-11-19 就位**（列出 `plugin/docs/assets/` 下三张发布用截图），但**其消费格式尚未取得消费方确认**——该文件是存包内相对路径还是须为可访问 URL、市场登记 YAML 如何引用它，均未取得市场侧确认；故门禁第 7 项**仍不可执行**。因此：

- 门禁第 7 项**尚不可执行**（截图清单虽在，消费形态未确认；市场登记 YAML 仍缺）；
- 这两份产物就位前，**不得声称它们已被核对通过**；亦不得因它们缺失而反向放松其余各项；
- 截图清单的消费形态取得确认、且市场登记 YAML 就位后，第 7 项自然生效；
- 若最终决定不采用某一产物（如放弃市场登记），须走受控更新修订本节与第 7 项。

**2026-11-19 勘误（本节随发布产物就位而改写）**：本节原文记载「`plugin/screenshots.json` 与市场登记 YAML 当前均不存在」，该陈述随 `plugin/screenshots.json` 建立而失真，按「对象漂移不自知」反模式核对后改写；direction_key、七项门禁、禁止项与验证表其余各条未动。

### 发布操作与发布后核对

- 发布动作在 `plugin` 目录执行 `npm publish`。
- **Git tag 必须指向包含实际发布代码的提交**——tag 指向的提交若不含发布内容，该次发布不可追溯。
- **npm 2FA 按 npm CLI 提示在浏览器确认，不得绕过认证**。
- 发布后核对：`npm view dsh-ldvh version` 与 `npm view dsh-ldvh dist-tags.latest`，确认线上版本与本次发布一致。

### 双源声明（唯一权威依据）

本规范自建立之日起为「发布门槛」方向的**唯一权威依据**。仓库根目录的 `RELEASING.md` 同时降为**历史草稿**——它保留为操作记录，不再具规范效力；两者内容不一致时以本规范为准。源文件暂不删除的理由：事实召回系统尚未建成，双源可互为补充；待召回系统就绪后再行收敛。

**2026-11-15 订正（前句理由已失真）**：上文「事实召回系统尚未建成、待就绪后收敛」的前提**已不成立**——双源召回与常驻枚举已建成并运行（`specs/34`；Norm 定位摘录每回合随 F1 常驻枚举注入，见 `specs/27 §10`）。故收敛 `RELEASING.md` 与 `DEVELOPMENT.md` 现在是一项**可决事项**（不再是未来的事），其处置（删除、改为指针、或继续保留为操作记录）须由 Human 决定并走受控更新；本轮按 Human 2026-11-15 决定只做订正登记，不执行收敛。唯一权威依据的结论本身不变。

## 约束与反模式

**禁止项**：

1. 禁止在门禁任一项未满足（或不可执行而不自知）的情况下执行发布。
2. 禁止以「测试通过」替代第 5 项真实安装验收。
3. 禁止在 README/CHANGELOG 中超前宣传未实现的能力。
4. 禁止绕过 npm 2FA 认证。
5. 禁止发布不含实际发布代码的 Git tag。
6. 禁止把本规范当作 LDVH 发布门面的第二权威使用——版本语义、渠道、README/CHANGELOG 格式一律回溯 `specs/10`。
7. 禁止声称已核对不存在的产物（如当前尚不存在的市场登记 YAML），亦不得把「截图清单已就位」读作「门禁第 7 项已通过」——其消费格式尚未取得市场侧确认。

**反模式**：

- **门禁空转**：清单写在文档里但从未逐项执行，发布时凭印象放行。每一门禁项都须有当次的实际执行证据。
- **对象漂移不自知**：门禁项所核对的产物已被删除或尚未建立，却仍按「已核对」对待。每次发布前须先确认各项的对象是否真实存在。
- **越界复制**：把 `specs/10` 的版本号语义或 CHANGELOG 格式抄进本规范，制造两处权威。

**违规后果**：违反禁止项 1–5、7 时，该次发布不成立，须撤回已发布的版本或补做缺失门禁后重新发布；已据其作出的「已发布/可用」声明应予撤回（`00 §5.6` 防自欺）。违反禁止项 6 时，该判断不成立，须回溯元规范原文重新判定。

## 验证与遵从性检查

逐条检查方式：

| 门禁项 | 检查方式 | 可否机械核查 |
|---|---|---|
| 1 工作区洁净 | `git status --porcelain` 无输出；核对 release commit 内容 | ✅ |
| 2 依赖安装 | `npm --prefix plugin ci` 退出码为 0 | ✅ |
| 3 测试全绿 | `npm --prefix plugin test` 退出码为 0，且无 skip 取代 | ✅ |
| 4 打包内容 | 在 `plugin/` 目录执行 `npm pack --dry-run`，输出清单与 `files` 字段逐项比对 | ✅ |
| 5 真实安装验收 | 在目标 DSH Desktop 实操安装/重启/升级/停用/卸载并留记录 | ⚠️ 人工 |
| 6 宣传一致 | 对照 README/CHANGELOG 与实际能力逐条审核 | ⚠️ 人工 |
| 7 市场产物一致 | 先确认 `screenshots.json` 与市场登记 YAML 存在；截图清单的消费形态须先取得消费方确认，再核对一致性与可达性 | ⚠️ 依赖对象存在 |
| tag 与发布内容 | 核对 tag 指向的提交确实包含发布代码 | ✅ |
| 发布后核对 | `npm view dsh-ldvh version` / `dist-tags.latest` 与本次发布比对 | ✅ |
| 2FA | 确认未绕过认证流程 | ⚠️ 人工 |

**遵从性边界**：本规范验证「发布动作是否按规定执行」，**不证明**产品能力完整、不证明价值兑现、不证明市场就绪，也不替代 `specs/10` 的发布门面要求与 `specs/06` 的测试基线。发布完成只证明当次交付动作的机械范围。
