# 发布门槛

## 方向定位与适用范围

**管什么**：dsh-ldvh 这一份仓库**发布前必须通过的检查清单**——发布这个动作在本仓库的硬性前置条件，以及发布过程中的操作纪律。它回答「这个仓库什么时候允许执行发布」，不回答「LDVH 插件作为产品应如何发布」。

**不管什么**：

- **LDVH 插件的发布门面**（版本号双轨语义、分发渠道、README 与 CHANGELOG 的格式要求、版本声明点三者一致性、受保护文档）归元规范 `specs/08 §7`。本规范**不复制、不改写**其中任何一条，也不构成其第二权威；凡涉该类问题一律回溯 `specs/08`。
- **提交契约与提交检查语义**（含 Git Gate 的门禁规则）归元规范 `specs/06`；本规范只引用其结论作为发布前置，不重新定义。
- **日常开发验证**（依赖安装、单元测试、打包核对、真实 UI 验收、开发红线）归本项目 `local-dev-workflow` 方向规范；发布**复用**其结果，不重复定义。
- **其他项目的发布流程**。

**与相邻规范的分工**：本规范与 `local-dev-workflow` 的主语不同——后者管**开发期**的动作，本规范管**发布点**的门禁条件。开发期验证通过是发布的**必要不充分**条件：本规范在开发验证之上追加发布专属检查（工作区洁净、包内容核对、真实安装验收、市场产物一致、发布后核对）。

**双源声明**：本规范自建立之日起为「发布门槛」方向的**唯一权威依据**。仓库根目录的 `RELEASING.md` 同时降为**历史草稿**——它保留为操作记录，不再具规范效力；两者内容不一致时以本规范为准。源文件暂不删除的理由：事实召回系统尚未建成，双源可互为补充；待召回系统就绪后再行收敛。

**建立时的两处剔除**（均为**剔除**事项，不是本规范的规则）：

1. `RELEASING.md` 原「发布前门禁」第 4 项要求核对「**Python 核心**」进入包——本仓库**已无任何 Python 源文件**，`plugin/package.json` 的 `files` 字段亦不含 Python 产物。该核对项已无对象，纳入会使规范携带失实规则。
2. 该文件 `plugin/screenshots.json` 相关核对项，其**对象当前不存在**（见「尚未就位的发布产物」）。

保留一条已失效的规则会使规范携带错误结构（`01 §11.3`）。

## 核心规则体系

### 发布前门禁

执行发布前，以下各项**全部**必须满足；任一项不满足即不得发布：

1. **工作区与 release commit 洁净**——`git status --porcelain` 无输出，且拟发布的 commit 不含未提交改动。
2. **依赖可复现安装**——`npm --prefix plugin ci` 通过（依 `package-lock.json`，非 `install`）。
3. **机械规则测试全绿**——`npm --prefix plugin test` 通过，无跳过项替代通过结论。
4. **打包内容核对**——`npm --prefix plugin pack --dry-run`，核对输出文件清单与实际预期一致：`lib`、`icons`、`cordis.patch.yml`、`web/dist`、`LICENSE`、`README.md`、`README.en.md`、`CHANGELOG.md`（以 `plugin/package.json` 的 `files` 字段为权威）。**清单与 `files` 字段不一致时，先查清差异再发布。**
5. **真实安装验收**——在目标 DSH Desktop 上完成真实安装、重启、升级、停用、卸载全项验证。此为人工验收，不得以测试通过替代。
6. **宣传与能力一致**——README 与 CHANGELOG 的内容不得超前宣传尚未实现的功能（该要求的规范依据是 `specs/08 §7.3`/§7.4，本规范只将其列为发布前置，不改写其内容）。
7. **市场产物一致**——市场登记 YAML 与 package 元数据一致；`plugin/screenshots.json` 的截图 URL 可访问且对应当前版本。**该项以其对象存在为前提**，见下节。

### 尚未就位的发布产物

`plugin/screenshots.json` 与市场登记 YAML **当前均不存在**（建立时实读核对）。因此：

- 在本规范订立时，门禁第 7 项**尚不可执行**；
- 这两份产物就位前，**不得声称它们已被核对通过**；亦不得因它们缺失而反向放松其余各项；
- 二者就位后，第 7 项自然生效，无需修改本规范；
- 若最终决定不采用某一产物（如放弃市场登记），须走受控更新修订本节与第 7 项。

### 发布操作与发布后核对

- 发布动作在 `plugin` 目录执行 `npm publish`。
- **Git tag 必须指向包含实际发布代码的提交**——tag 指向的提交若不含发布内容，该次发布不可追溯。
- **npm 2FA 按 npm CLI 提示在浏览器确认，不得绕过认证**。
- 发布后核对：`npm view dsh-ldvh version` 与 `npm view dsh-ldvh dist-tags.latest`，确认线上版本与本次发布一致。

## 约束与反模式

**禁止项**：

1. 禁止在门禁任一项未满足（或不可执行而不自知）的情况下执行发布。
2. 禁止以「测试通过」替代第 5 项真实安装验收。
3. 禁止在 README/CHANGELOG 中超前宣传未实现的能力。
4. 禁止绕过 npm 2FA 认证。
5. 禁止发布不含实际发布代码的 Git tag。
6. 禁止把本规范当作 LDVH 发布门面的第二权威使用——版本语义、渠道、README/CHANGELOG 格式一律回溯 `specs/08`。
7. 禁止声称已核对不存在的产物（如当前尚不存在的 `screenshots.json` 与市场登记 YAML）。

**反模式**：

- **门禁空转**：清单写在文档里但从未逐项执行，发布时凭印象放行。每一门禁项都须有当次的实际执行证据。
- **对象漂移不自知**：门禁项所核对的产物已被删除或尚未建立，却仍按「已核对」对待。每次发布前须先确认各项的对象是否真实存在。
- **越界复制**：把 `specs/08` 的版本号语义或 CHANGELOG 格式抄进本规范，制造两处权威。

**违规后果**：违反禁止项 1–5、7 时，该次发布不成立，须撤回已发布的版本或补做缺失门禁后重新发布；已据其作出的「已发布/可用」声明应予撤回（`00 §7.1` 防自欺）。违反禁止项 6 时，该判断不成立，须回溯元规范原文重新判定。

## 验证与遵从性检查

逐条检查方式：

| 门禁项 | 检查方式 | 可否机械核查 |
|---|---|---|
| 1 工作区洁净 | `git status --porcelain` 无输出；核对 release commit 内容 | ✅ |
| 2 依赖安装 | `npm --prefix plugin ci` 退出码为 0 | ✅ |
| 3 测试全绿 | `npm --prefix plugin test` 退出码为 0，且无 skip 取代 | ✅ |
| 4 打包内容 | `npm --prefix plugin pack --dry-run` 输出清单与 `files` 字段逐项比对 | ✅ |
| 5 真实安装验收 | 在目标 DSH Desktop 实操安装/重启/升级/停用/卸载并留记录 | ⚠️ 人工 |
| 6 宣传一致 | 对照 README/CHANGELOG 与实际能力逐条审核 | ⚠️ 人工 |
| 7 市场产物一致 | 先确认 `screenshots.json` 与市场登记 YAML 存在；存在则核对一致性与 URL 可达 | ⚠️ 依赖对象存在 |
| tag 与发布内容 | 核对 tag 指向的提交确实包含发布代码 | ✅ |
| 发布后核对 | `npm view dsh-ldvh version` / `dist-tags.latest` 与本次发布比对 | ✅ |
| 2FA | 确认未绕过认证流程 | ⚠️ 人工 |

**遵从性边界**：本规范验证「发布动作是否按规定执行」，**不证明**产品能力完整、不证明价值兑现、不证明市场就绪，也不替代 `specs/08` 的发布门面要求与 `specs/09` 的测试基线。发布完成只证明当次交付动作的机械范围。
