# dsh-ldvh 开发规范

## 方向定位与适用范围

**管什么**：本方向管 dsh-ldvh 开发期的规则与约束：目标环境、安装、验证、验收与开发红线。

**何时查阅**：在本机安装、验证插件、评估平台影响或开始前查阅本规范。

## 核心规则体系

**管辖边界声明**：本规范只定义 dsh-ldvh 单一仓库开发期**必须遵守的规则与约束**，不承载历史证据、升级差分或实测记录（此类过程材料随退役的历史对象留存，不进入当前规则）。本规范不定义构建与发布契约（发布规范 `norm-80c95693`）、LDVH Code 通用工程纪律（元规范 `specs/06`）、提交契约（元规范 `specs/09`），也不约束其他受管辖项目的开发方式。

**不管什么**：

- **发布契约**（版本号语义、分发渠道、README/CHANGELOG、发布门禁）归本项目发布规范 `norm-80c95693`；本规范不复制、不改写，也不构成其第二权威。
- **LDVH Code 通用工程纪律**（目录结构、命名、测试基线、lint 与工具链）归元规范 `specs/06`；本规范只承载本项目专属事实。
- **其他受管辖项目的开发方式**；各项目按自身环境自建方向。

**环境版本时效性**：本规范登记的环境版本号是**某一时点的观察值**，不是永久承诺。环境升级（DSH Desktop、`@deepseek-ai/dsh`、Node.js）后须走受控更新修订本文，并逐项核对消费面契约是否受影响；本文不因版本演进自动失效，但其版本行为须显式核对，不继承历史指认。

### 目标环境

开发以 DSH Desktop 为目标宿主，当前登记观察值（2026-11-19）：

- DSH Desktop `0.2.2-rc.5`（`/Applications/DeepSeek Harness.app`）；
- `@deepseek-ai/dsh` `0.2.2-rc.5`；
- desktop profile：`~/.dsh/profiles/desktop`；
- Node.js `>=22.15.0`——下界由 `plugin/lib/zstd-compat.js` 依赖的 `node:zlib` zstd API 决定；宿主 `dsh-plugin-desktop` 要求 `^22.19.0 || >=24.0.0`，故持续集成取 `22.19`。

**支持基线（Human 决定）**：本仓库对准的宿主版本为 `0.2.2-rc.5`，须按「开发红线」第 5 条的四项实证独立取得，不继承历史指认。

### 首次安装

插件以本地 `link:` 加入 desktop profile，不复制文件：

```bash
dsh plugin --profile desktop add /Users/dmh2002/DshProject/dsh-ldvh/plugin
```

Host、Client 与 bundle patch 均在进程启动时加载——安装或修改插件后必须退出并重新打开 DSH Desktop，改动才生效。

### 日常验证

每次变更后按序执行：

```bash
npm --prefix plugin ci
npm --prefix plugin test
```

第三条为打包核对：在 `plugin/` 目录执行 `npm pack --dry-run`（**不能用** `npm --prefix plugin pack --dry-run`，后者在 npm 11.x 上以 ENOENT 失败），核对输出文件清单与 `plugin/package.json` 的 `files` 字段一致。

### 真实 UI 验收

范围收为两项（Human 决定），二者须有本机实证：

- `/ldvh` 路由；
- `/ldvh/api/health` 健康检查。

单元测试通过不替代本项验收（见开发红线第 3 条）。

### 开发红线

1. **不手工复制插件文件进 profile 的 `node_modules`**——一律走统一安装入口，手工复制会使 profile 与源目录漂移且不可追溯。
2. **不在 DSH 安装目录内修改官方包以「修好」兼容**——宿主能力缺口须按 `specs/10` 接入契约处理或登记为缺口，不得就地篡改官方包。
3. **不因单元测试通过就声明支持当前 DSH**——支持声明须以「真实 UI 验收」两项完成为前提。
4. **不省略 Windows 影响评估**——每个变更的收口结论须显式回答「对 Windows 有何影响」；触及路径语义、Git Hook 的 shell 载体、文件权限模型、进程与终端调用、换行与编码时，须给出 win32 分支实现或如实登记未覆盖；能力缺口按 fail-closed 处置并登记为已知限制。未在 Windows 上运行不构成跳过评估的理由；未真机验证的范围须与已验证范围分开登记。
5. **宿主指认不得凭目录名或安装历史**——承载插件的宿主须以**四项实证**指认：进程正在运行、GUI 端口持有者、运行产物内核版本、profile 安装形态；四项一致方可写入「目标环境」，每次独立取得，不继承历史指认。

## 约束与反模式

**双源声明（唯一权威依据）**：本规范自成立之日起为「dsh-ldvh 开发」方向的唯一权威依据。仓库根目录的 `DEVELOPMENT.md` 降为历史草稿，保留为过程记录，不再具规范效力；两者内容不一致时以本规范为准。历史草稿的收敛处置（删除、改为指针或继续保留）须由 Human 决定并走受控更新；本规范只完成规则承载，不执行草稿收敛。

**禁止项**：

1. 禁止以手工复制文件的方式把插件装进 profile——安装必须经 `dsh plugin --profile desktop add` 一类统一入口。
2. 禁止在 DSH 安装目录内修改官方包来消除兼容问题。
3. 禁止以「单元测试通过」单独作为「支持当前 DSH」的声明依据。
4. 禁止跳过真实 UI 验收（当前两项：`/ldvh` 与 `/ldvh/api/health`）直接声明插件可用。
5. 禁止把本规范当作发布契约或通用 Code 纪律的第二权威——该类问题一律回溯 `norm-80c95693` 与 `specs/06`。
6. 禁止在变更收口时省略 Windows 影响评估（红线 4）。
7. 禁止以「同名 app 目录存在」推定「该宿主正在运行」——须以红线 5 四项实证指认。

**反模式**：

- **版本清单腐烂**：把环境版本号当作永久事实长期不核对——版本行为须随环境升级显式复核。
- **双源双读**：有本规范仍以 `DEVELOPMENT.md` 为规则依据——该文件已降为历史草稿，不一致时以本规范为准。
- **默认平台即开发机**：以开发机是 macOS 代替平台范围判断，把 Windows 影响留到「以后再说」——Windows 真机未验收前状态如实为 `unverified`。
- **按目录名指认宿主**：以「本机装过哪个 app」代替「此刻哪个进程在承载插件」——只有正在运行且经 profile 加载本插件的才是当前基线。

**违规后果**：违反禁止项 1–4、6、7 时，当次开发结论不成立，须回到合规路径重做；已据其作出的「支持当前 DSH」类声明应予撤回（00 §4.6 据实声明）。违反禁止项 5 时，该判断不成立，须回溯权威原文重新判定。

## 验证与遵从性检查

| 规则 | 检查方式 |
|---|---|
| 目标环境 | 核对 `node -v`、`plugin/package.json` 与 profile 配置是否与登记值一致；不一致时按「环境版本时效性」走受控更新 |
| 首次安装 | 检查 profile 中插件引用方式为 `link:`；检查 `plugin/` 下无被复制进 profile 的痕迹 |
| 日常验证 | `npm ci`、`npm test` 通过；`plugin/` 目录 `npm pack --dry-run` 清单与 `files` 字段一致 |
| 真实 UI 验收 | `/ldvh`、`/ldvh/api/health` 两项逐项实操；任一项未做即验收未完成 |
| 红线 1 | 审查 profile 的 `node_modules` 中该插件为链接而非副本 |
| 红线 2 | 检查 DSH 安装目录未被本仓库的工作修改 |
| 红线 3 | 审查「支持声明」是否附有真实 UI 验收两项记录；无记录则不成立 |
| 红线 4（平台影响） | 审查收口结论是否显式回答 Windows 影响；触及平台层时核对 win32 分支或未覆盖登记 |
| 红线 5（宿主指认） | 以四项实证独立指认：`pgrep` 进程、`lsof` GUI 端口持有者、运行产物内核版本与 asar 内包版本分布、profile 的 `link:` 指向；四项一致且不继承历史指认 |

**遵从性边界**：本规范的检查项验证「开发过程是否按规定执行」，不证明插件功能完整、不证明价值兑现，也不替代 `specs/06` 的测试基线与发布规范 `norm-80c95693` 的发布门禁。
