# 本地开发工作流

## 方向定位与适用范围

**管什么**：dsh-ldvh 这一份仓库的本地开发工作流——开发者在本机把插件跑起来、验证它、以及不可逾越的开发红线。具体含四类：目标环境锁定、首次安装方式、日常验证动作、真实 UI 验收范围，外加固化的开发红线。

**不管什么**：

- **LDVH 插件的构建与发布契约**（版本号语义、分发渠道、README/CHANGELOG 要求、发布门禁的产品面）归元规范 `specs/08`；本规范不复制、不改写，也不构成其第二权威。
- **LDVH Code 的通用工程纪律**（目录结构、命名约定、测试基线、lint 与工具链）归元规范 `specs/09`；本规范只承载 dsh-ldvh 作为单一项目的本地事实，不重新定义通用纪律。
- **其他受管辖项目的开发方式**；各项目按自身环境自建方向。

**双源声明**：本规范自建立之日起为「本地开发工作流」方向的**唯一权威依据**。仓库根目录的 `DEVELOPMENT.md` 同时降为**历史草稿**——它保留为过程记录，不再具规范效力；两者内容不一致时以本规范为准。源文件暂不删除的理由：事实召回系统尚未建成，双源可互为补充；待召回系统就绪后再行收敛。

**建立时剔除项**：`DEVELOPMENT.md` 原「红线」第 4 条「管辖/Git Gate 实现先按 v4 迁移清单吸收成熟代码」**未纳入本规范**。理由：其对象（v4 迁移清单批次 B/C/D/E/F）已于 `docs/ldvh-plugin-implementation-plan.md` 记载完成，该条已无适用对象；保留一条已失效的规则会使规范携带错误结构（`01 §11.3`）。此项为**建立时的剔除**，不是本规范的规则。

**环境版本时效性**：本规范「核心规则体系」中登记的环境版本号是**某一时点的观察值**，不是永久承诺。环境升级（DSH Desktop、`@deepseek-ai/dsh`、Node.js）后须走受控更新修订本文；本文不因版本演进自动失效，但其版本行为须显式核对。

## 核心规则体系

### 目标环境

开发以 DSH Desktop 为目标宿主环境，登记如下观察值（观察时点：2026-09-20）：

- DSH Desktop `2.0.13`；
- `@deepseek-ai/dsh` `0.1.5-rc.2`；
- desktop profile：`~/.dsh/profiles/desktop`；
- Node.js `>=22.15.0`——下界由 `plugin/lib/zstd-compat.js` 决定，它依赖 `node:zlib` 自 v22.15.0 起提供的 zstd API；DSH 宿主 `dsh-plugin-desktop` 自身要求 `^22.19.0 || >=24.0.0`，因此持续集成取 `22.19`。

**支持基线（Human 决定，2026-09-20）**：本仓库对准的 DSH 宿主版本为 `0.1.5-rc.2`。机械依据：本机 `/Applications/DSH Desktop.app` 壳版本 `2.0.13`，其 `Resources/app/node_modules/@deepseek-ai` 下 234 个 `dsh*` 包版本全部为 `0.1.5-rc.2`；插件在该基座上实际加载运行——`/ldvh` 与 `/ldvh/api/health` 路由返回正常，管辖判定与 `ldvh_*` 工具逐回合正常。

**支持声明的未成立部分（如实登记）**：按本规范「开发红线」第 3 条与 `specs/08` §8 的验证表，正式的「兼容/支持」声明须以「真实 UI 验收」全项完成为前提。该六项中，`/ldvh` 路由与 `/ldvh/api/health` 健康检查已取得本机实证；设置卡片、LDVH 会话视图、停用与重启、卸载清理四项**尚未核对**。故本登记确立的是 Human 已决定的**目标基线**，不等于验收已完成，也不构成可对外声称的「已验证支持」。

### 首次安装

插件以本地 `link:` 方式加入 desktop profile，不复制文件：

```bash
dsh plugin --profile desktop add /Users/dmh2002/DshProject/dsh-ldvh/plugin
```

**Host、Client 与 bundle patch 均在进程启动时加载**，因此安装或修改插件后必须退出并重新打开 DSH Desktop，改动才生效。

### 日常验证

每次变更后按序执行：

```bash
npm --prefix plugin ci
npm --prefix plugin test
npm --prefix plugin pack --dry-run
```

三条命令覆盖依赖安装、机械规则测试与打包内容核对。

### 真实 UI 验收

单元测试通过**不足以**声明插件在当前 DSH 上可用；必须进行真实 UI 验收，覆盖：

- 设置卡片；
- LDVH 会话视图；
- `/ldvh` 路由；
- `/ldvh/api/health` 健康检查；
- 停用与重启；
- 卸载清理。

### 开发红线

1. **不手工复制插件文件进 profile 的 `node_modules`**——一律走统一的安装入口，手工复制会使 profile 与源目录漂移且不可追溯。
2. **不在 DSH 安装目录内修改官方包以「修好」兼容**——宿主能力缺口须按 `specs/08` 的接入契约处理或登记为缺口，不得就地篡改官方包。
3. **不因单元测试通过就声明支持当前 DSH**——支持声明须以「真实 UI 验收」全项完成为前提。

## 约束与反模式

**禁止项**：

1. 禁止以手工复制文件的方式把插件装进 profile——安装必须经 `dsh plugin --profile desktop add` 一类统一入口。
2. 禁止在 DSH 安装目录内修改官方包来消除兼容问题。
3. 禁止以「单元测试通过」单独作为「支持当前 DSH」的声明依据。
4. 禁止跳过真实 UI 验收直接声明插件可用。
5. 禁止把本规范当作 LDVH 构建/发布契约的第二权威使用——该类问题一律回溯 `specs/08`。

**反模式**：

- **版本清单腐烂**：把本文的环境版本号当作永久事实长期不核对。版本行为须随环境升级显式复核。
- **双源双读**：在有本规范的情况下仍以 `DEVELOPMENT.md` 作为规则依据。该文件已降为历史草稿，不一致时以本规范为准。

**违规后果**：违反禁止项 1–4 时，当次开发结论不成立，须回到合规路径重做；已据其作出的「支持当前 DSH」类声明应予撤回（`00 §7.1` 防自欺：不得声明超出机械证据范围的成立结论）。违反禁止项 5 时，该判断不成立，须回溯元规范原文重新判定。

## 验证与遵从性检查

逐条检查方式：

| 规则 | 检查方式 |
|---|---|
| 目标环境 | 执行 `node -v`、读取 `plugin/package.json` 与 profile 配置，核对与本文登记值是否一致；不一致时按「环境版本时效性」走受控更新，而非默认本文仍成立 |
| 首次安装 | 检查 profile 中插件的引用方式为 `link:`；检查 `plugin/` 下无被复制进 profile 的痕迹 |
| 日常验证 | 三条命令全部通过；`pack --dry-run` 输出的文件清单与预期一致 |
| 真实 UI 验收 | 逐项实操并记录：设置卡片、会话视图、`/ldvh`、`/ldvh/api/health`、停用/重启、卸载清理；任一项未做即验收未完成 |
| 红线 1 | 审查 profile 的 `node_modules` 中该插件是否为链接而非副本 |
| 红线 2 | 检查 DSH 安装目录未被本仓库的工作修改 |
| 红线 3 | 审查「支持声明」是否附有完整真实 UI 验收记录；无记录则不成立 |

**遵从性边界**：本规范的检查项验证「开发过程是否按规定执行」，不证明插件功能完整、不证明价值兑现，也不替代 `specs/09` 的测试基线与 `specs/08` 的发布门禁。
