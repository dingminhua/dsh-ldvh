# 本地开发工作流

## 方向定位与适用范围

**管什么**：本方向管 dsh-ldvh 仓库的本地开发工作流：目标环境、安装验证、UI 验收、平台影响与开发红线。

**何时查阅**：在本机安装、验证插件、推进基线 tag 或评估平台影响前查阅本规范。

## 核心规则体系

**管辖边界声明**（原载于定位段，2026-11-15 按 27 §8 新契约迁入本节，内容逐句迁入、无删除——其中句首据本段主语补「本方向管的是 」，详见本条 change_log）：本方向管的是 dsh-ldvh 这一份仓库的本地开发工作流——开发者在本机把插件跑起来、验证它、以及不可逾越的开发红线；具体含五类：目标环境锁定、首次安装方式、日常验证动作、真实 UI 验收范围、平台影响评估（每处变更须显式回答 Windows 影响），外加固化的开发红线。

**不管什么**：

- **LDVH 插件的构建与发布契约**（版本号语义、分发渠道、README/CHANGELOG 要求、发布门禁的产品面）归元规范 `specs/10`；本规范不复制、不改写，也不构成其第二权威。
- **LDVH Code 的通用工程纪律**（目录结构、命名约定、测试基线、lint 与工具链）归元规范 `specs/06`；本规范只承载 dsh-ldvh 作为单一项目的本地事实，不重新定义通用纪律。
- **其他受管辖项目的开发方式**；各项目按自身环境自建方向。

**建立时剔除项**：`DEVELOPMENT.md` 原「红线」第 4 条「管辖/Git Gate 实现先按 v4 迁移清单吸收成熟代码」**未纳入本规范**。理由：其对象（v4 迁移清单批次 B/C/D/E/F）已于 `ldvh-plugin-implementation-plan.md`（原 docs 目录，已随 `ec19ba6` 清除、可自该提交回取） 记载完成，该条已无适用对象；保留一条已失效的规则会使规范携带错误结构（`01 §11.3`）。此项为**建立时的剔除**，不是本规范的规则。

**环境版本时效性**：本规范「核心规则体系」中登记的环境版本号是**某一时点的观察值**，不是永久承诺。环境升级（DSH Desktop、`@deepseek-ai/dsh`、Node.js）后须走受控更新修订本文；本文不因版本演进自动失效，但其版本行为须显式核对。

### 目标环境

开发以 DSH Desktop 为目标宿主环境，登记如下观察值（观察时点：2026-11-19）：

- DSH Desktop `0.2.2-rc.5`（`/Applications/DeepSeek Harness.app`）；
- `@deepseek-ai/dsh` `0.2.2-rc.5`；

### 开发红线

1. **不手工复制插件文件进 profile 的 `node_modules`**——一律走统一的安装入口，手工复制会使 profile 与源目录漂移且不可追溯。
2. **不在 DSH 安装目录内修改官方包以「修好」兼容**——宿主能力缺口须按 `specs/10` 的接入契约处理或登记为缺口，不得就地篡改官方包。
3. **不因单元测试通过就声明支持当前 DSH**——支持声明须以「真实 UI 验收」全项（当前为 `/ldvh` 路由与 `/ldvh/api/health` 两项；另四项经 Human 决定 2026-11-19 移出）完成为前提。
4. **不省略 Windows 影响评估**——每个变更的收口结论须显式回答「对 Windows 有何影响」。触及路径语义、Git Hook 的 shell 载体、文件权限模型、进程与终端调用、换行与编码时，须同时给出 win32 分支实现，或如实登记为未覆盖；宿主或本实现无对应能力时（如 win32 无 ACL 核验器）按 fail-closed 处置并登记为已知限制。未在 Windows 上运行不构成跳过该评估的理由；未真机验证的范围须与已验证范围分开登记，不得以「运行成功」冒充「能力已具备」或「已验收」。
5. **宿主指认不得凭目录名或安装历史**——承载插件的宿主须以**四项实证**指认：进程正在运行、GUI 端口持有者、运行产物的内核版本、profile 的安装形态；四项一致方可写入「目标环境」，且每次核对须独立取得，不继承历史指认。（本条依据 2026-09-29 的指认更正与 2026-09-30 的宿主机代。）

## 约束与反模式

**双源声明（唯一权威依据）**（原载于定位段，2026-11-15 按 27 §8 新契约迁入本节，内容逐字未改）：本规范自建立之日起为「本地开发工作流」方向的**唯一权威依据**。仓库根目录的 `DEVELOPMENT.md` 同时降为**历史草稿**——它保留为过程记录，不再具规范效力；两者内容不一致时以本规范为准。源文件暂不删除的理由：事实召回系统尚未建成，双源可互为补充；待召回系统就绪后再行收敛。

**2026-11-15 订正（前句理由已失真）**：上文「事实召回系统尚未建成、待就绪后收敛」的前提**已不成立**——双源召回与常驻枚举已建成并运行（`specs/34`；Norm 定位摘录每回合随 F1 常驻枚举注入，见 `specs/27 §10`）。故收敛 `DEVELOPMENT.md` 与 `RELEASING.md` 现在是一项**可决事项**（不再是未来的事），其处置（删除、改为指针、或继续保留为过程记录）须由 Human 决定并走受控更新；本轮按 Human 2026-11-15 决定只做订正登记，不执行收敛。唯一权威依据的结论本身不变。

**禁止项**：

1. 禁止以手工复制文件的方式把插件装进 profile——安装必须经 `dsh plugin --profile desktop add` 一类统一入口。
2. 禁止在 DSH 安装目录内修改官方包来消除兼容问题。
3. 禁止以「单元测试通过」单独作为「支持当前 DSH」的声明依据。
4. 禁止跳过真实 UI 验收（当前两项：`/ldvh` 与 `/ldvh/api/health`）直接声明插件可用。
5. 禁止把本规范当作 LDVH 构建/发布契约的第二权威使用——该类问题一律回溯 `specs/10`。
6. 禁止在变更收口时省略 Windows 影响评估（红线 4）。
7. 禁止以「同名 app 目录存在」推定「该宿主正在运行」——承载插件的宿主须以红线 5 的四项实证指认（进程、GUI 端口持有者、运行产物内核版本、profile 安装形态），不以目录名或安装历史推定（本条依据 2026-09-29 的指认更正与 2026-09-30 的宿主机代）。

**反模式**：

- **版本清单腐烂**：把本文的环境版本号当作永久事实长期不核对。版本行为须随环境升级显式复核。
- **双源双读**：在有本规范的情况下仍以 `DEVELOPMENT.md` 作为规则依据。该文件已降为历史草稿，不一致时以本规范为准。
- **默认平台即开发机**：以开发机是 macOS 代替平台范围判断，把 Windows 影响留到「以后再说」。本规范声明的支持平台为 macOS 与 Windows；Windows 真机验收未完成前，其状态如实为 `unverified`，不因开发机跑得通而推定成立。
- **按目录名指认宿主**：以「本机装过哪个 app」代替「此刻哪个进程在承载插件」作答。本机可并存多个宿主产物，也可能在换代中整体移除（`DSH NEXT.app` 即于 2026-09-30 前被移除）；只有正在运行且经 profile 加载本插件的那个才是当前基线。

**违规后果**：违反禁止项 1–4、6、7 时，当次开发结论不成立，须回到合规路径重做；已据其作出的「支持当前 DSH」类声明应予撤回（`00 §5.6` 防自欺：不得声明超出机械证据范围的成立结论）。违反禁止项 5 时，该判断不成立，须回溯元规范原文重新判定。
