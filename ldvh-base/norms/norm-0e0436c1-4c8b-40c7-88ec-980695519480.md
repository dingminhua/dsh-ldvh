# 上游更新跟进规程

## 方向定位与适用范围

**管什么**：本方向管上游 DSH 更新后的跟进操作序列：从被告知到提请登记。

当 Human 告知「上游 DSH 已更新（到某版本/某 tag）」时，AI 无须另行请示即可按本规程跟进；适用于宿主基线推进、契约面差分、三态判定与后续分派的全过程。基线登记值本身的权威承载在 Norm「本地开发工作流」（`local-dev-workflow`，norm a1b559a6），本规程只定义「从被告知到提请登记」的操作序列，不改变其 Human 决定 Gate。本规程的建立依据是 Spark `76ee7b7b`（建立上游 DSH 能力变化的吸收与同步机制）的调研结论：上游仓库已把契约面以生成物形式提交在仓内（`api-catalog.ts` / `slot-catalog.ts` / upgrade-guide 目录——官方破坏性变更自述，指称不以路径字面出现，09 §5.3 第 5 项），差分可机械取数。

## 核心规则体系

runbook，按序执行：

1. **取数前提**：确认本地上游克隆（`/Users/dmh2002/DshProject/deepseek-harness`）已 `git fetch --tags`，且目标 tag 存在；克隆缺失或过期时如实报告，不得以记忆或旧 tag 代替。
2. **基线读取**：从 Norm `local-dev-workflow` 的目标环境条目读当前登记基线 tag（唯一权威登记点）。
3. **契约差分**：运行 `plugin/scripts/host-contract-diff.mjs <基线tag> <目标tag>`，取得三份产出——服务端三表（SERVICE_API/EVENT_API/TYPE_API）增删改、客户端槽位表增删改、区间内新增 upgrade-guide 清单（版本序在 (基线, 目标] 的目录及其 description）。脚本解析失败时报「不可判定」并停止，**不得降级为「零变更」**。
4. **提请/答复接缝专项检查**（Human 2026-11-14 决定增设，专项纪律）：契约差分之外**必做**的一步，不并入三态判定，也不因「上游没删 API、没改签名」而跳过。凡差分或 upgrade-guide 触及宿主提问/答复链的三个包（`dsh-client-ui-user-questions` 的提问卡、`dsh-tool-ask-user` 的答案透传、`dsh-user-questions` 的答复协议类型）或 `AskUserQuestionAnswerItem` 字段时，须逐项核对：① 上游答复协议里**所有**承载字段（除 `selected` 外还有 `custom` 等）在 LDVH 每个答复消费点（`host-seams.js` 的把关请示与 Spark／ADR／管辖登记三处 Human Gate 的答案解析）是否都被读取；② 真实答案形态（尤其是「自由输入框写字 + 点提交」这一支，其 `selected` 被置空、文字只落在 `custom`）是否仍能被消费点正确识别、文字是否仍逐字回给模型；③ 「点跳过按钮」与「自由输入提交」是否仍可区分、自由文本是否仍不冒充 `review|skip` 闭集答复或 Gate 授权。核对结论以报告形态交 Human；发现不一致即按第 5 步分派适配，**不得判为「无关」**。本项的强制做法由规范源承接，失效机制与识别信号见 Pitfall `ac6c8a91`。
5. **三态判定**：对照机器可读消费面清单（`plugin/lib/host-consumption.json` 或等价载体），把每条差分落为——**破坏**（消费面内条目被删/改名/签名变）、**须审**（消费面条目语义收窄、或 upgrade-guide 关键词命中消费面，须读该 guide 原文后归类）、**无关**（其余，含一切纯新增）。判定结果以报告形态交 Human，AI 给初值不代决。第 4 步的专项结论须一并列入报告，不受「无关」结论覆盖。
6. **分派**：「破坏」与「须审→确认破坏」的适配改造走工单路由（specs/21 §6.3）；第 4 步发现的不一致同样按「破坏」分派；「无关」区间可直接提请基线推进。
7. **登记提请**：基线推进的登记按其既有规程执行（四项实证独立取得 + Human 决定 + norm a1b559a6 受控更新），差分报告、三态结论与第 4 步专项结论作为登记的机械依据附入 change_log summary。
8. **留痕**：每次跟进结束按事实类型落档（通常 DevLog；发现新破坏模式时评估 Pitfall/Friction）。

## 约束与反模式

- 反模式：跳过差分直接改代码「试一试」；以 asar 解析承担契约差分（asar 只用于红线 5 的版本取证）；把「脚本报告无关」当作「能力已验证」；未经 Human 决定推进基线登记值；**以「上游答复协议 API 未删、签名未变」为由跳过第 4 步专项检查**（2026-11-14 实际失效形态：上游卡片早已把自由输入只放进 `custom`，消费侧零读取，而三态判定因「无 API 变化」判成无关，漏检持续到 Human 指认）。
- 约束：消费面清单与插件实际消费点的一致性由测试守护（清单漂移即三态漏判，属必修缺陷）；第 4 步的字段覆盖核对须以协议定义与消费点实际读取的逐字清单比对，不以「测试通过」代替（测试也可能沿用旧的答案形态）；本规程只针对 DSH 单一宿主，不建通用抽象（specs/10 §11 红线）；差分脚本是只读取数与初值判定，不构成任何授权。

## 验证与遵从性检查

- 差分脚本对已知区间可复现历史人工登记数字（如 `dsh-v0.2.1-rc.5`→`dsh-v0.2.2-rc.1` 的服务 98→107、槽位键 103→109）作为回归锚点；
- 消费面清单一致性测试通过（`host-seams.js`/`client.js` 的实际消费点与清单双向核对）；
- **第 4 步专项检查的执行留痕可回指**：每次跟进须能回答「本次是否触及答复协议三包/字段、核对了哪些消费点、结论是什么」，未触及也要如实写明「未触及」而非省略；回归用例须覆盖「自由输入提交（`selected:[]` + `custom`）」这一答案形态（见 `plugin/test/ask-custom-visibility.test.mjs`）；
- 每次跟进的产出（差分报告、三态结论、专项结论、去向）在 norm change_log 或 DevLog 中可回指。
