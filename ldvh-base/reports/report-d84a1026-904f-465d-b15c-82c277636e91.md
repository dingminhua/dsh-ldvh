## 研究问题

@changfenhuang/dsh-genui 的回合边界检查与同回合纠偏机制如何实现，这一形态对 LDVH 的检查机制是否构成可借鉴的增量？

本问题分两问：（一）该插件的「每次检查」机制在实现层是什么；（二）它相对 LDVH 既有检查机制是增量还是重复。之所以必须拆成两问，是因为存在一种可能——若 LDVH 已经在工具调用点上具备机械关卡与同回合纠偏，那么照搬该形态只是把已有机制换个位置放，并不产生新能力。

**本轮补充（2026-11-13 续）**：两问均已回答，且第二问的答案经实测被推翻——「回合边界自检 + 同回合纠偏」这一最小形态在既有语料上**误伤 100%、真实问题 0 例**，按 04 §6.3 的量测结论不应推进。替代落点见「建议」。

## 关键发现

### dsh-genui 的检查点设在宿主回合边界事件上，不依赖模型自觉调用

该插件在 `agent/turn-stopping` 事件上挂载检查：每回合结束边界触发，对该回合助手正文里的每个 ```dsh-ui 围栏重跑一次判定（`fenceFailures`）。这与它同时提供的 `validate_dsh_ui` 工具性质不同——后者是模型**可选**调用的前置校验（SKILL.md 第 11 条「先验后发」规定复杂围栏才需先验），前者是**必然执行**的关卡。插件配置项 `fenceFeedback` 只控制是否开启回合转向，默认开启。

溯源：https://github.com/omdsh-dev/dsh-genui（src/plugin/fence-feedback.ts#L662；src/plugin/index.ts#GenuiPluginConfig）

### 检查判定与实际渲染共用同一套守卫代码

回合边界的判定调用 `resolveFence` + `processGenuiSpec`，与浏览器端渲染器走的是同一个守卫模块（`src/client/guard.ts`）。因此「校验器说通过、渲染却不是那个结果」这一类分裂被结构性地排除。另有一处额外核对：`droppedNodeFailure` 比对「声明节点数」与「实际渲染节点数」，把被丢弃的节点逐个报出路径与类型。

溯源：https://github.com/omdsh-dev/dsh-genui（src/plugin/fence-feedback.ts#L117-L138；src/plugin/genui-diagnostic.ts#droppedNodeFailure）

### 不可渲染时的纠偏走同回合 steering，且受硬预算、指纹去重与竞态沉默三重约束

失败时调用 `agent.steer(message)`，把一条带 `fence=` / `fingerprint=` / `error=` 的修正请求送回**同一回合**，模型重发修正版围栏，而非等下一轮。约束写在实现注释里：每回合修正上限 2（渲染失败与「已验证却没交付正文」共用预算）；每个围栏在当回合最多修正一次，按正文指纹记账；**先记账后发送**，以防重入边界重复投递；有未决的 `render_ui` 结果在飞时保持沉默，等下一个边界用已结算的事实判断。子代理回合不触发，已中止的回合不 steer。判定只读正式事件（围栏正文、工具调用、已交付正文），不读 reasoning 块——思考中的草稿不算模型已选择交付。

溯源：https://github.com/omdsh-dev/dsh-genui（src/plugin/fence-feedback.ts#L280-L303；src/plugin/fence-feedback.ts#L44；src/plugin/fence-feedback.ts#L662-L699）

### 诊断以计数差额与字段级键值对暴露静默丢弃

诊断不是自然语言，而是可解析的键值对：`declared=N` / `rendered=M` / `dropped=K` 给出差额，逐节点给出 `node=items[0]` / `type=items` / `error=unknown_field` / `allowed=<合法字段列表>`；警告类另有 `warning=alias_ignored`、`warning=policy_truncated`、`warning=block_markdown … replacement=<替换节点>`。校验工具在可修复时直接产出 `repaired_json` 并给出 `next=emit_repaired_fence`，模型可原样照抄发出；不可修复时给 `next=fix_and_revalidate`。**差额本身就是结论**——它能说出「声明了 12 个节点，实际只渲染 10 个」。

溯源：https://github.com/omdsh-dev/dsh-genui（src/plugin/genui-diagnostic.ts#droppedNodeDiagnosis；src/plugin/tool.ts#L389-L432）

### LDVH 的受控写入已具备工具点机械关卡与同回合纠偏，且判定与执行同源

对 LDVH 本仓的核对结论：受控写入的校验发生在工具调用内部并零写入拒绝，模型在同一回合即收到拒绝理由并可当场改正——本轮实测即为此形态（两次写入分别因缺正文、字段为空串被当场拦下并当场改正通过）。校验器与写入器共用同一实现（提交预检与 Git Gate 共用 `commit-validation.js`；各类型 precheck 与 writer 共用同一 validator），不存在「校验通过、执行另判」的分裂。检查项的复杂度分级在 LDVH 亦非必需：受控写入只有工具一个通道，不存在「要不要检查」的选择题。

溯源：https://github.com/omdsh-dev/dsh-genui（对照对象为该插件的机制分层；LDVH 侧证据在本机 plugin/lib 与本轮工具调用记录，非外部 URL 来源）

### 宿主已公开 steering 与工具执行链事件接缝，LDVH 只用了其中两个

宿主安装体暴露的插件可挂事件包含：`agent/turn-stopping`、`agent/pre-step`、`agent/assistant-stream`、`agent/request`、`agent/status`、`llm/stream`、`tools/pre-execute`、`tools/execute`、`tools/result`、`tools/post-execute`、`system-prompt/assemble`、`session/*`。其中 `agent.steer(message)` 是 `dsh-agent` 公开接口，语义为「向最近一步提交 steering；空闲驱动会启动一个回合，运行中的驱动在下一步边界消费」。LDVH 当前挂载的是 `system-prompt/assemble`（最小规则引导注入）与 `agent/turn-stopping`（刷新活动时刻、重置安静期计时）——**回合边界接缝已挂着，但用途是计时而非检查**；`tools/*` 四个工具执行链事件全部未挂。

溯源：https://github.com/omdsh-dev/dsh-genui（宿主接口证据为 @deepseek-ai/dsh-agent runtime-types.ts 与本机 app.asar 事件定义，非该仓库来源）

### 候选判据在既有语料上误伤 100%，而它要拦的真实问题出现 0 次

误伤量测（04 §6.3 义务）：语料为本机 132 个会话日志，按事件类型过滤出 `tool/call` / `tool/result` 后取数（工具名取自 `tool/call` 的 `data.name`，outcome 取自 `tool/result` 事件文本首行标记「LDVH `<tool>`: `<outcome>`」——**未对全文跑正则**，遵守 pitfall-5cd02c62 的规避纪律）。

- 语料规模：132 会话、7016 条 `tool/result`；其中 LDVH 工具可解析出 outcome 的 522 条。
- 受控写入类（`ldvh_<type>_write|update|correct`）：167 次调用，其中硬失败（`rejected` / `invalid_request` / `execution_error`）74 次。
- 候选判据「本回合存在硬失败 ∧ 同 `fact_type_key` 无 `completed`」触发 **3 个回合**。
- 逐回合查证这 3 例的助手正文：**三例全部是模型向 Human 求证（路由询问／确认 seam 返回空答复）后改走合法替代路径**——例一识别出 ADR 创建被 22 §16 拒绝是因为确认答复为空并如实向 Human 说明；例二例三在 Human 选择「直接执行」后改建单为直接执行并完成工作。**没有一例是「硬失败后静默放弃」**。
- 结论：该判据在触发集合上的误伤率为 **3/3 = 100%**，而它要拦的形态在 132 会话中出现 **0 次**。

溯源：https://github.com/omdsh-dev/dsh-genui（对照对象为该插件的机制分层；量测证据为本机会话日志与本仓 plugin/lib，非外部 URL 来源）

### 写失败不留持久痕迹是真缺口，但它的正解不在回合边界而在写入那一刻

独立审查指出并经本仓核实的事实：`appendPendingEntry` 的调用方有四处（`friction-failure-registration.js`、`friction-observation-buffer.js`、`idle-checkpoint.js`、`lifecycle.js`），**但没有任何 `*-writer.js` 引入 `pending-queue`**——即受控写入失败后不产生待处置条目，下一任接管者看不见。这与量测结果并不矛盾：模型几乎总会向 Human 说明或改走替代路径，所以「静默放弃」罕见；罕见的是**留痕缺失**，不是行为缺失。

因此同一缺口有两个候选落点：回合边界纠偏（已被量测否掉）与**写入失败即入待处置队列**（只留痕、不干预、不依赖语义判断）。

溯源：https://github.com/omdsh-dev/dsh-genui（对照对象为该插件的机制分层；缺口证据为本仓 plugin/lib 与 plugin/lib/pending-queue.js，非外部 URL 来源）

### 纠偏消息的来源类型必须由插件自己声明，否则会被静默丢弃

宿主 `dsh-llm` 的 `MessageSourceMap` 定义逐字写明：「each producer declares its own `kind` in its own module; **there is no shared catch-all `plugin` kind**」，且 `user` 类型的 source 专供 Human 输入；会话格式 v4 在消息准入处拒绝未声明的来源类型。这意味着：若 LDVH 要用 `agent.steer()` 发纠偏消息，必须在自己的模块里 `declare module '@deepseek-ai/dsh-llm'` 扩展 `MessageSourceMap`；用 `{kind:'user'}` 冒充则与 Human 输入不可区分；沿用未声明形态则 steer 会在准入处被拒——表现是「监听、判定、记账都发生了，纠偏从未送达」。本仓当前**没有任何** `MessageSourceMap` 声明（`plugin/lib` 全量检索零命中）。

溯源：https://github.com/omdsh-dev/dsh-genui（宿主接口证据为 @deepseek-ai/dsh-llm src/message.ts，非该仓库来源）

## 未证实与缺口

**未证实（uncertain）**：

1. 「回合边界自检」在 LDVH 究竟属 04 §6.3 既有机械校验形态内的**新增判据**，还是 04 §6 开头所称需要「修改 00 并由 Human 明确决定」的**检查机制形态新增**。本轮已取得判断依据：新增一道判据不改变检查机制的数量、名称与职责（04 §11.1 第 1 项的三条均不触发），故**归类为既有机械校验形态内的新增判据，不需改 00**；但按 04 §6.3「机械校验只执行规范已经定义的确定性内容」，实施前仍须先在规范层定义该确定性内容。该归类属语义判断（04 §6.3 明说「是否同构仍属主控与独立审核的语义判断」），须 Human 确认。
2. 「受控写入失败入待处置队列」的承载位归属——该动作可视为 11 号待处置队列覆盖面扩展、02 号事实变更纪律、或 36 号摩擦销账的前置，三处皆有相近条款，本轮未取得归位判据。

**缺口（gaps）**：

1. 本轮取证于本机安装包 v0.16.0，未与上游仓库 HEAD 逐字比对，也未在其他宿主版本上验证（medium）。
2. 量测的 outcome 取自事件文本首行标记，属**呈现层解析**——522/7016 条可解析（其余为非 LDVH 工具或无该格式）。本仓既有纪律要求「以写入侧解析规则为准，不能以呈现层能显示为准」，故本量测的取数口径本身带已知限制（medium）。
3. 误伤量测的语料只覆盖本机 132 个会话，未覆盖其它工作区；结论只在此批语料上成立（medium）。
4. 未核实 DSH 上游是否已有等价于「回合边界机械自检」的官方机制可复用（low）。

## 建议

1. **不推进「回合边界自检 + 同回合纠偏」这一最小形态。** 理由是量测而非偏好：候选判据在既有语料上误伤 100%（3/3 触发全为合法回合），它要拦的形态出现 0 次；按 04 §6.3 的量测结论与「零增量／高误伤不得推进」的精神，这条路不成立。不得据此声称该问题已被防住。
2. **若仍要覆盖「写失败无人接手」这一缺口，落点改为写入那一刻**：受控写入硬失败即入待处置队列（`appendPendingEntry`）。它的优势是——接缝已存在（四处调用方在用）、判据纯事件型（不判语义）、只留痕不干预（无误伤风险）、且不改任何检查机制的数量与职责。代价与前置：须先定承载位归属（见未证实第 2 条）与队列条目的 `task`/`reason`/`residual` 取值口径。
3. **保留 genui 的两条可借鉴形态，与本次取舍无关**：① 诊断携带「声明数／实际数／差额」与「合法值集合」——可直接增强 LDVH 工具诊断，减少无效重试；② 「判定与执行同源」——LDVH 已做到，新增判据不得引入第二套判定实现。
4. **若将来仍要做同回合纠偏，三项前置不可省**：自声明 `MessageSourceMap` kind（否则纠偏静默丢弃）、纠偏约束补足「回合已中止不 steer」「子代理不 steer」「同一 turn 边界会重入」「steer 入队数与被消费数的差额诊断」、以及「失败事实从来源侧取（`tools/post-execute` 或包住自有写入执行器），不得解析渲染文本」。
5. **本报告不构成实施授权**：上述任何落点都须先定承载位、再走规范修订（01 §11.1 的顺序：先定义语义与成立条件，再由 Code 实现），最后受控提交。
