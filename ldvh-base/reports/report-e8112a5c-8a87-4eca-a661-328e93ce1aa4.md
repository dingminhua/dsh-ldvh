## 研究问题

DSH 宿主的会话级 Git worktree / 工作目录切换能力如何构成——能否据此隔离并行会话的工作树，其边界是什么。

本调研支撑一个面向**所有管辖项目**的方向判断：当多个会话并行在同一仓库工作时，是否可借宿主原生 worktree 能力把它们引导进各自独立的 checkout，以减少共享工作树 / 共享 Git Index 引发的摩擦（本仓 open 摩擦中 042b0196、68e6f33e、451c4a7d 等均属此类）。

## 输入与边界

方法：① 对运行中宿主做只读能力面取证（Cordis Inspect 的 Host Service / Tool 目录，读到的是运行实例真实注册的服务与工具签名）；② 读取宿主安装 asar 内 `@deepseek-ai/dsh-experimental-worktree` 与 `dsh-experimental-tool-worktree` 的 README；③ 以官方仓库原始文档交叉核对并作为来源锚点。观察时点 2026-11-19，宿主为 DeepSeek Harness.app。

**取回路径如实声明**：`web_fetch` 在当前 profile 报 provider 未注册（即 friction-d9a74b74），官方 URL 的正文经 shell `curl` 直取同一地址取得（HTTP 200 已核验）。来源文本仍是一手官方仓库内容，但取回方式经实现层，特此登记。

不覆盖：未实际创建 worktree 做任何副作用验证；未验证 worktree 内 `ldvh_*` 工具、管辖判定与 Git Gate 的行为；未设计多 worktree 事实源分叉后的合并规则。

## 关键发现

### F1 宿主提供完整的 worktree 服务与工具面

运行实例的 Host Service 目录列出 `worktrees` 服务（方法 `create` / `restore` / `cleanupOf`，另有 README 记载的 `enter` / `exit`）与 `workingDirectory`（`get` / `set(agent, path)`）；Tool 目录中 `create_worktree` 在当前会话可调用。

溯源：https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/worktrees.md（provides ctx.worktrees）

### F2 create 建独立 checkout 并切换会话目录

`ctx.worktrees.create(agent, {name?, from?})` 建一个新分支与 checkout，并经 `ctx.workingDirectory.set` 把调用会话的 cwd 切进去，返回 `path` / `branch` / `baseCommit` / `repositoryRoot`。这是会话级文件隔离的原生形态——不是普通 git branch（换 HEAD 不换目录），而是每个会话进入不同目录。

溯源：https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/experimental/worktree/README.md（creates a new branch and checkout, then enters）

### F3 不复制未提交改动

`from` 解析到本地 commit（默认 HEAD），staged / unstaged / untracked / ignored 源文件都不复制。这意味着在途改动留在原 checkout——恰好是当前那批并发摩擦的主要发生形态。方案的有效性取决于"在进入 worktree 之前是否已把在途改动处理掉"。

溯源：https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/worktrees.md（nor copies staged, unstaged, untracked, or ignored files）

### F4 worktree 内的 Git 写权限受限

官方 README 明确：仓库 Git 目录位于 linked worktree 之外，`workspace-write` 下在其中会话不能 `git add` / `git commit`，除非沙箱策略通过 `additionalWritableRoots` / `registerWritableRoot` 授予该目录，且 Windows 进程忽略此类授权。受控提交依赖 `git commit`，这是落地的硬前提。

溯源：https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/experimental/worktree/README.md（cannot run git add or git commit）

### F5 生命周期与边界

默认 checkout 目录 `<root>/.agents/worktrees/<name>`；archive 会话时对本人创建的首个 checkout 注册后台清理，有跟踪改动 / 未跟踪文件 / 锁 / 分支不符时保留 checkout。工具面只覆盖创建与进入（`creation only`），检查、合并、删分支不在工具内。

溯源：https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/experimental/worktree/README.md（default checkout directory）

## 未证实与缺口

本报告在能力面取证层面已充分（stopping_reason=round-cap），以下缺口需另做受控可行性实验，本报告不声称已消解：

- **未实跑**：能力"可调用"来自 Tool 目录签名，本轮未实际创建 worktree 验证一次成功调用。
- **高优先缺口**：worktree 内管辖判定（依赖 cwd）与 Git Gate / `ldvh_*` 工具是否照常工作未实测——cwd 变了，管辖判定仍绑原项目路径与否，直接决定方案能否成立。
- **高优先缺口**：多 worktree 各持一份 `ldvh-base/`，事实源分叉后的合并规则、销账归属与冲突消解未定义；且分支载体纪律要求 main 树不含事实对象，worktree 须从 dev 建才带事实源。
- **中优先缺口**：`create_worktree` 只管创建与进入，如何与受控提交契约、检查/合并/清理接回，未定。

## 建议

方向上可行：宿主原生能力足以支撑"并行会话引导进独立 worktree"，不必自造隔离机制。但**不宜直接进入实现**，应先做一次受控可行性实验堵住两个高优先缺口：① worktree 内管辖判定 / Git Gate / 事实源读写是否照常；② 沙箱 Git 目录授权路径能否让受控提交在 worktree 内跑通。实验通过后再判断方案边界与触发时机（必须早于在途改动产生）。
