## 研究问题

外部同类项目（AI 编码代理的规则/规范交付形态）把规范文档放在哪里、交付给 agent 的是原文还是构建期派生物、契约的单一来源怎么做、派生产物是否入库与漂移如何被机械拦截——为 LDVH 已裁定的「① specs 只作开发期材料不进发布包、② 由构建期从 ① 生成产品规则」提供外部对照。

研究目的：支撑「① 不进包＋② 构建时生成」是否与业界一致，并决定「生成物是否入库、漂移怎么防」与「①→② 生成清单怎么定」两项取舍。

## 输入与边界

## 关键发现

### 规则材料有三种形态并存：项目内随会话加载、随包分发、构建期派生

观察事实：Kiro steering 在项目内 `.kiro/steering/`，"apply only to that specific workspace"，随工作区会话加载；AGENTS.md 是跨工具标准的项目级指令文件；也有产品把规则文本作为**包内文件**随发布物分发（npm 包内自带 AGENTS.md）；构建期派生则有 Ruler（单一源 `.ruler/` → 各 agent 配置文件）、microsoft/apm（"routes one source file to every detected harness"，输出到 copilot/claude/cursor/opencode/gemini/windsurf 各自的目录）与代码生成器。

价值判断：**"业界主流是规则随项目走"这一判断过强，须更正**——三类形态都有先例，差别在"规则原文在谁手里"。

溯源：https://kiro.dev/docs/steering.md（Steering file scope）；https://raw.githubusercontent.com/7nohe/openapi-react-query-codegen/main/docs/src/content/docs/guides/ci-and-agents.mdx（Coding agents: AGENTS.md 第 1 条）

### 已有厂商级先例：开发文档留在仓库，构建期复制进产物目录，用指针引导 agent 去读

观察事实：Next.js PR #89850 明确"shipping version-matched documentation inside the `next` npm package and generating agent instruction files during create-next-app"：构建期新增 copy_docs 任务，把仓库根的 `docs/` 复制进 `dist/docs/`（因 `dist` 已在包的 `files` 数组内，故自动随包发布到 `node_modules/next/dist/docs/`）；`create-next-app` 新增 `--agents-md` 开关，生成 AGENTS.md 指示 agent 去读 `node_modules/next/dist/docs/` 而非依赖训练数据。

价值判断：**这是与 LDVH「① 开发文档不进包、② 生产期给得到的东西」最接近的厂商级先例**——开发文档不直接随包、构建期把需要的部分搬进产物、靠指针把 agent 引过去。差别在关键一点：Next.js 仍把文档原文带进了包（版本对齐的副本），而 LDVH 打算只交提炼物不带原文，后者更激进。

溯源：https://github.com/vercel/next.js/pull/89850（PR 描述）；https://app.semanticdiff.com/gh/vercel/next.js/pull/89850/overview（PR 概述）

### 规则文本编译成运行期派生物有先例，且代价被明确记录：转写本身是漂移面

观察事实：SubLang 编译器 DR-047 记：随包发布的 compile definitions 既是编译器遵循的规范规则，也是自举元流水线中"每个阶段被编译成可运行阶段包"的来源；因为定义不自带行动提示，元编译把整段规则文本视为隐含行为，**逐条转写进包内的提示**；由此 "Every definition edit … invalidates the bundle and cannot reach compiled runs until the bundle is rebuilt through a nondeterministic agent run and re-reviewed; **the transcription itself is a drift surface**"。

价值判断：**"规则文本 → 运行期派生物"有直接先例**，但它同时记录了两条对 LDVH 直接适用的警告——转写/编译**本身是新的漂移面**，且若编译过程非确定，重编译代价高昂（须经 agent 运行并重新评审）。故 LDVH 的生成步骤必须**确定性可重建**，这正是"入库＋CI 新鲜度门禁"能成立的前提；SubLang 的形态是"原文随包 ＋ 派生物随包，两者并存"。

溯源：https://raw.githubusercontent.com/sublang-ai/playbook/62d63752ab2ccc10001dc8ad148974ede69cecac/specs/decisions/047-compiled-execution-contract-in-definitions.md（Context 段）

### 文档进不进包是跨仓约定，且 allowlist 与 denylist 存在不对称

观察事实：gotgenes/pi-packages retro #484 记录一次真实事故："the package's `files` allowlist omits `docs/`, so no documentation ships to npm and every README `docs/...` link (and the logo) breaks on the CDN"，处置结果是把范围扩大为跨包约定——"ship user-facing docs, never ship internal working docs"；同篇指出设计上的不对称"A denylist (.npmignore) cannot add files an allowlist omits"。npm 官方规则同向：`files` 是 allowlist，根目录 `.npmignore` 不覆盖它，子目录的 `.npmignore` 才生效；safeguard.sh 的说明亦指出 allowlist 比 blocklist 安全（新文件默认留在包外）。

价值判断：**「哪些文档进包、哪些不进」在同类项目里是被明确写下的跨包约定**，措辞与 Human 的主张几乎同形（面向用户的文档随包、内部工作文档不随包）。同时得到一条机制结论：LDVH 若要把 `specs` 排除出包，**必须改 `package.json` 的 `files` 字段（allowlist），不能靠根 `.npmignore` 补救**——而改 `files` 本来就是发布规范门禁 4 那一项。

溯源：https://github.com/gotgenes/pi-packages/blob/8b34bd3174b18fcbc15568d1144b8fb86fb6993a/docs/retro/0484-publish-docs-in-distribution.md（Root cause 与 Inclusion vs. exclusion asymmetry 段）；https://docs.npmjs.com/cli/v9/commands/npm-publish（Files included in package）

### Spec Kit 的规范由指令要求 agent 自己去读，不是 harness 自动注入

观察事实：constitution 落在项目内 `.specify/memory/constitution.md`，特性规范落在 `specs/<特性>/`，模板在 `.specify/templates/`；constitution 指令模板明写"Dependent templates and commands read the constitution at runtime"，plan 模板把"Read FEATURE_SPEC and `/memory/constitution.md`"列为显式步骤；走查文档指出此前规范靠 README/.cursorrules 传递、问题是"没有被 agent 工作流主动读取"。

价值判断：**"主动读取"与"被动注入"是两条兑现路径**；若 LDVH 把「① 不进包」做成"运行时无从读到原文"，等于选了 Spec Kit 的路径却没保留它的指针。

溯源：https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/constitution.md（Scope Guard）；https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/plan.md（Outline 第 2 步）

### 生成方向的主流是规范到派生物的单向生成，规范为单一来源

观察事实：OpenAPI contract-first 模式写明"规范先于实现代码写就；规范是每个 API 契约的唯一来源；生成代码跟随规范，规范永不跟随代码"；oapi-codegen 同构——"turns OpenAPI 3.x specs into Go server stubs, clients, and types"。

价值判断：**LDVH「表格类契约编译进代码、规范为唯一来源」与该形态完全同构**，支持"分界线＝能不能机械判定"这一分界方式。

溯源：https://github.com/wahidyankf/ose-public/blob/main/repo-governance/development/pattern/openapi-contract-first.md（Principles and Conventions）；https://raw.githubusercontent.com/oapi-codegen/oapi-codegen/main/.greptile/rules.md（首段）

### 派生产物有两种主流处置：入库加 CI 新鲜度门禁，或不入库加消费前重生成

观察事实：入库形态——oapi-codegen"Files matching `*.gen.go` are produced by the code generator and committed to source control so CI can verify they are up-to-date"；ifc-lite 要求"每个已提交的生成文件必须与其源重新生成的结果逐字节一致"且 fail-closed；openapi-react-query-codegen 提供 `--check` 入口，"exits with `0` when everything matches, and with `1` when files differ"。不入库形态——ose-public"生成物不入库，漂移被做成不可表示，消费前从已提交规范重新生成"；Ruler 默认把生成文件"out of version control"。

价值判断：**入库＋CI 新鲜度门禁是主流形态之一**，其 fail-closed 细节与 `--check` 退出码形态可直接抄成 LDVH 的三方比对门禁要求。

溯源：https://raw.githubusercontent.com/oapi-codegen/oapi-codegen/main/.greptile/rules.md（「1. Generated files」）；https://github.com/LTplus-AG/ifc-lite/commit/94acccc997c985166270bbc9bd2eac2bb4e74246（commit 正文）

### 存在构建期派生的直接先例：单一源派生各工具的规则文本

观察事实：Ruler 定位是"providing a **single source of truth** for all your AI agent instructions, automatically distributing them to the right configuration files"，做法是把指令存在专用 `.ruler/` 目录（Markdown）再分发到各 agent 配置文件；派生物由生成器覆盖写入，工具方明示"Manual edits to Ruler-managed files will be overwritten"。

价值判断：**"单一源 → 构建期派生多份交付文本"已有成熟工具形态**，LDVH 的 ①→② 在机制层有先例；但 Ruler 的源位于**使用方仓库**，不是厂商的开发期规范目录。

溯源：https://raw.githubusercontent.com/intellectronica/ruler/main/README.md（Why Ruler?；Core Features 第 1 条；Managed files, not whole directories）

### 规范类文档被官方定位为开发期工件，不进入交付物

观察事实：Kiro 文档中 specs 的产物生成在 `.kiro/specs/<name>/`；OpenSpec 在用户项目内创建 `openspec/` 目录并写托管 AGENTS.md 交接。

价值判断：**"规范文档是开发期工件"这一定位在同类工具有官方表述**，与 LDVH 把 specs 定为开发文档一致；差别是 Kiro 的 specs 是功能级规格，LDVH 的 specs 是插件自身的机制规范。

溯源：https://kiro.dev/docs/specs.md（Getting Started CLI 第 3 步）

### 常驻规则被官方定性为非强制配置，强制须另建机制

观察事实：Claude Code 官方文档写明"Claude treats CLAUDE.md files and auto memory as context. They aren't enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead"；Kiro steering 提供四种 inclusion 模式，且**用 YAML front matter 声明**（`inclusion: always|fileMatch|manual|auto`，auto 模式另带 `name` 与 `description`）。

价值判断：**这是"规则无机械承载"最权威的一句外部表述**，并明确了行业分工——文本规则是上下文，强制靠钩子。LDVH 的 Git Gate 属强制面，与主流形态正交：**差异化不在"把规则写得更好"，而在"把可强制的部分真正强制"**。Kiro 用 front matter 标注每份规则的加载时机，正是 LDVH「①→② 区间用途标注」的现成形态参照。

溯源：https://code.claude.com/docs/en/memory.md（CLAUDE.md vs auto memory 末段）；https://kiro.dev/docs/steering.md（Inclusion modes）

### 常驻注入有被记录在案的衰减机制，超限后静默失效且复制即漂移

观察事实：Platinum Software 生产经验报告写明：写进 always-loaded 配置的指令能活更久，"直到该文件长过模型能可靠关注全部内容的规模，然后它就静默衰减：什么都不会报错，那条规则只是不再触发"；同一条指令给第二台机器就是第二份副本，而副本会漂移。Claude Code 给出官方量级："target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence"；skills 把文档过长命名为 Sprawl；context-rot 说明长会话中"会话早期的指令相对于不断增长的后文失去影响力"，表现为决策门与审批点被跳过；akitaonrails 写明"AGENTS.md 是一份稀缺且被共享的预算……遵从度崩塌，agent 会静默地变差"。

价值判断：**LDVH 靠"注入规则进上下文"兑现价值，这条外部证据说明该路径有已记录的衰减上限**，并给出量级参照（200 行/文件）；LDVH 现行 4096 字符预算方向一致，但需对照该量级复核。

溯源：https://zenodo.org/records/22694070（Description）；https://code.claude.com/docs/en/memory.md（Keep your files short… Size 条）

### 指针措辞弱被定性为方差缺陷，指引放在产物目录里实测读不到，悬空引用须显式标记

观察事实：writing-for-agents 写明"The pointer's _wording_, not its target, decides when the agent reaches the material, and how reliably. A must-have target behind a weakly worded pointer is a variance bug"；openapi-react-query-codegen 实测"The same guide placed inside the output directory made no difference: an agent that searches with `grep` never loads it"；Kiro 的文件引用机制则明写"If a reference cannot be resolved, Kiro leaves a visible unresolved-reference marker in the Steering content instead of silently dropping the document"，并支持 `#[[file:path:start-end]]` 的行级引用。

价值判断：**"把指引放在产物目录里"被实测为无效做法**（支持 LDVH 现有做法）；**"弱措辞指针＝方差缺陷"**是 LDVH 引导文本措辞纪律的外部依据；**"悬空引用显式标记、不静默丢弃"**正是 LDVH 建议 4「无原文时指针悬空须显式声明不可用」的现成实现范式。

溯源：https://raw.githubusercontent.com/mattpocock/skills/main/skills/productivity/writing-for-agents/SKILL.md（Context pointers）；https://raw.githubusercontent.com/7nohe/openapi-react-query-codegen/main/docs/src/content/docs/guides/ci-and-agents.mdx（a guide in your AGENTS.md 末段）；https://kiro.dev/docs/steering.md（File references）

### 机械覆盖写入会摧毁用户本地修改，初始化覆盖用户规范是已发生的真实缺陷

观察事实：Ruler 明示"Manual edits to Ruler-managed files will be overwritten"；spec-kit 提交 4afbd87 记录的真实缺陷是"Moves constitution template from `memory/` to `templates/` to prevent overwrites when spec-kit is reinitialized with a different AI agent"；oapi-codegen 记录双写代价——改配置结构体须同步改 JSON Schema，"an out-of-sync schema silently breaks downstream users' configs"，该一致性靠**人工评审**兜底。

价值判断：**"生成物覆盖用户修改"与"初始化覆盖用户规范"是两类已记录的真实失败**，直接约束 LDVH 的"② 入库"设计——入库就必须有"手改会被覆盖"的显式披露与用户修改保留位；双写靠评审兜底则提示：契约表与代码若双写，一致性必须机械化。

溯源：https://raw.githubusercontent.com/intellectronica/ruler/main/README.md（Limitations）；https://api.github.com/repos/github/spec-kit/commits/4afbd87abb45744966bbeaaa71d20742cf778c48（commit message 第 2 段）；https://raw.githubusercontent.com/oapi-codegen/oapi-codegen/main/.greptile/rules.md（「2. Configuration changes must update the JSON schema」）

## 未证实与缺口

- **未证实**：「规则随项目走／随包分发／构建期派生」三类形态的普遍性未确证——样本体量有限且以文档型 agent 工具为主，未覆盖把规则编译进二进制的形态类项目。
- **未证实**：契约"由 schema 生成规范（反向生成）"的项目选择与代价——只核到"规范→代码"与"双写＋校验"两向。
- **缺口（已收窄，high→medium）**：「厂商规范目录被排除出发布包」此前无机制级先例，现取得两个近同构先例：Next.js（开发文档不直接随包，构建期 `copy_docs` 复制进 `dist/docs/` 随包，并生成 AGENTS.md 指针指向产物目录）与 SubLang（shipped definitions 作为编译来源，派生物随包）。**仍未覆盖的是最激进的那一格：「不带原文、只交提炼物／派生物」**——即 LDVH 当前裁定的形态仍无直接先例；且两个近同构先例都**保留了原文/来源在包内或可及**，比 LDVH 的设定保守。
- **缺口（medium）**：未取得各 harness 在「注入 vs 按需读」上的可比量化数据（无 token 预算／遵从率对照）。
- **缺口（medium）**：缺"规范文本与代码契约不一致导致线上问题"的公开事故记录。
- **缺口（medium）**：缺"机械替换改坏产物"的独立失败案例——现有为"手改被覆盖"与"初始化覆盖用户文件"两类。
- **缺口（low）**：缺"常驻上下文超预算"的量化实验数据。
- **缺口（medium）**：项目事实源中 2026-09～11 的外部调研与本轮证据的时效一致性未重新核验；本轮样本偏向文档型 agent 工具，样本偏差未排除。

## 建议

1. **采纳"规范 → 派生物"的单向生成作为既定形态**（对应 OpenAPI contract-first 与 oapi-codegen），不引入反向生成。适用条件：契约必须是表格或闭集；风险：散文类契约无法编译，须走搬运路径。
2. **派生产物采用"入库＋CI 字节级新鲜度门禁＋fail-closed"**（对应 ifc-lite／oapi-codegen／`--check`），而非"不入库"；适用条件：**生成物可确定性重建**（SubLang DR-047 记录了非确定性编译的代价与转写漂移面）；风险：生成器不确定则门禁持续失败。理由：入库形态让漂移在提交时暴露，与 LDVH 的 Git Gate 时机一致，且不放弃逐字回读；并须配套披露"手改会被覆盖"（Ruler）与用户修改保留位。
3. **把 ② 拆成"常驻注入面"与"按需可查规则库"两层，采用现成形态**：用途标注可参照 Kiro 的 YAML front matter（`inclusion: always|fileMatch|manual|auto`）写在每份规则文件开头；前者设独立上限并对照官方量级（Claude Code 200 行预算）复核 LDVH 的 4096 字符预算。适用条件：规则可按"是否每轮都要"分类；风险：分类是语义判断，须 Human 逐条裁定。
4. **为"① specs 不进包"补一条指针通道**（对应 Spec Kit 指令模板、Next.js 的 AGENTS.md 指针与 writing-for-agents 的措辞纪律）：生产端保留"某条规则的原文在哪"的定位信息；离线不可达时**按 Kiro 的做法显式留悬空标记，不静默丢弃**。适用条件：原文可达（自举项目成立，端用户项目不成立）；风险：无原文时指针悬空，须显式声明不可用而非假装可用。注意实测教训：把指引放进可检索目录不生效（agent 用 grep 不读目录）。
5. **把"强制"与"上下文"分层**：外部主流明确把规则文件视为非强制上下文，强制靠钩子等机制。LDVH 的 Git Gate 属强制面，是差异化点，不应被"把规则写进常驻文本"这条路径稀释——①→② 生成清单须区分"可强制的部分（编译进代码）"与"只能作为上下文的规则（按需可查）"。
6. **若要在包内排除 `specs`，机制上必须改 `package.json` 的 `files` 字段（allowlist）**，根目录 `.npmignore` 不覆盖它（npm 官方规则）；并可采用跨包约定"面向用户的文档随包、内部工作文档不随包"（pi-packages retro #484）。适用条件：发布规范门禁 4 同步改；风险：`files` 改动会影响打包清单核对。
7. **对最激进那一格作显式风险登记**：「不带原文、只交派生物」无外部先例；若采纳，其可回读性缺口须在 `00 §2.4` 与 `00 §5.2` 层面显式承认，或改采 Next.js 式的保守形态（原文副本随包 ＋ 指针引导），两者须由 Human 裁定。
