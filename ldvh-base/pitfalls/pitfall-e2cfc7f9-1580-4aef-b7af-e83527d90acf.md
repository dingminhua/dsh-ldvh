# 重载窗口多实例致钩子重复且互相摘除

## 症状

同一个 agent 上出现多份等效钩子，表现为两类彼此相反的故障：

1. **重复产出**：一次行动前召回注入了 3 条内容完全相同、message id 各不相同的行；同一秒内静置检查点被并行触发 3 次。
2. **反向失效**：在重载窗口里加了「新实例接管旧实例」的互斥后，旧实例被宿主回收的那一瞬间，**新实例的钩子被一并摘掉**，召回与管辖判定双双归零。后者更隐蔽——它只在回收发生时显形，且症状是「什么都不出现」，容易被读成「本回合无需注入」。

## 触发条件

同时满足以下条件即触发：

1. 插件以**进程内模块状态**做实例识别或去重（如 `const agents = new Map()` 在 `createRegistry()` 内，每实例一份）；
2. 宿主重载插件时**新旧实例存在并存窗口**（先改 entry 再等待旧 fiber 释放）；
3. 钩子注册在**跨实例共享的上下文**上（此处是 agent 自己的 `ctx`，所有实例都往同一个对象上挂）。

条件 1、3 缺一不会重复；缺 2 则窗口不存在。

## 根因

去重表与钩子宿主不在同一层级：

- `agents` 是**每实例**一份 Map，`agents.has(agentId)` 只能拦住同一实例内的重复安装，拦不住两个实例各装一次；
- 而 `agent.ctx` 是**跨实例共享**的，所有实例的监听器都落在同一个对象上。

于是「单例语义」由两个不同作用域的事实拼成，两者在并存窗口内必然不一致。第二形态的根因是：`ctx.effect` 的清理函数与**注册它的那个 fiber** 绑定——手工调用一次不会解绑，该 fiber 真正释放时清理仍会再跑一遍，而它清理的正是共享 ctx 上的监听器，于是把后来者刚装好的钩子一起摘掉。

## 解决

**未解决。** 本轮改动已按 Human 决定撤下（代际守卫整体移除），只保留两处已验证的修复：行动前召回的取词判据（不把宿主 time-context 当查询词）与注入行的同内容去重。多实例并存的根因仍在。

已排除的做法（含各自的实测结论）：

- **新实例放弃安装**：旧实例随后被回收时该 agent 再无人挂钩子，召回与检查点永久静默。
- **接管时调用旧实例的 dispose**：见根因末段，旧 fiber 释放时会连带摘掉新实例钩子。
- **代际守卫（只让最新实例生效、旧监听器原样放行）**：重复产出确实消失（1／2／3 实例并存均只注入 1 条），但并存期结束、旧实例被回收时钩子全死——即本条的第二种症状。

**同类问题的现成做法（dsh-purge，2026-10-27 对照阅读所得）**：它在自己的 pre-step 装配处同时用了两道闸，注释里写明「旧版 late() + queueMicrotask + setTimeout 三连都成功时，同一个 wrap 会在 agent/pre-step 瀑布上叠 3 层」——与本案同一失效面，且它明确处理了这个叠加：

1. **幂等标记落在 `ctx` 自身**：`if (ctx.__dshPurgeMnemonStrip) return; ctx.__dshPurgeMnemonStrip = true;`。标记与钩子宿主（ctx）同层，所以同一 ctx 上的第二次装配会被挡住——而不是像本案那样把去重表放在每实例私有的 registry 里。
2. **mounted 闸**：`if (mounted) return;`，第一次成功挂上就不再重试，disposer 交给 `ctx.effect` 回收；清理时只 `dispose?.()` 自己那一份，不清别人的。

该做法对本条的适用性**未验证**：purge 的标记挂在插件自己的 ctx 上（每实例不同），而本案要在共享的 `agent.ctx` 上表达「谁有效」，两者不是同一层级的问题；且 purge 没有「旧实例回收后新实例须继续工作」这一需求（它不依赖跨实例移交）。故它给出的是**判据方向**（幂等标记与钩子同层），不是可直接照搬的实现。

## 规避

1. **不要把「每实例私有的表」当作跨实例的单例约束**。去重表的作用域必须与钩子宿主同层：钩子挂在共享 ctx 上，去重就必须落在该共享 ctx（如 `ctx.__dsh*` 标记）或进程级（模块外 / `globalThis`）；或者反过来把钩子挂到每实例私有的 ctx 上。
2. **不要跨实例手工调用 `ctx.effect` 的清理函数**。它与注册它的 fiber 绑定，不构成「转移所有权」；正确方向是引用计数 + 显式移交，或由宿主保证原子替换。
3. **验证互斥时必须验证「并存结束后」的状态**，而不只是「并存期间行数正确」。本条两种形态里，后者只有把旧实例回收掉才暴露；只测并存期会得到「修复有效」的错误结论。
4. **判断实例数不要靠工具清单或配置条目**：宿主会按工具名去重，`listConfigs` 也只返回一个 Loader 条目。可靠口径是**每实例各自产生的副作用**——如检查点运行痕迹里同一毫秒的 `silence-expiry` 条数、或注入行各自的 message id。

## 验证

**已观察**：

- 隔离实验（单变量）：修复前代码在 1／2／3 个实例下分别产生 1／2／3 条注入行；3 实例的落盘顺序（NOTICE／RECALL 交替三次、id 全不同）与真实会话日志逐位一致。
- 真实运行痕迹：`~/.dsh/ldvh/idle-checkpoint-runs.json` 中 `2026-10-26T19:33:45.581Z` 一秒内有 3 条 `silence-expiry`，`quietFor` 为 300004／300005／300006 ms，反推武装时刻是 `19:28:45.576–.577`（1 ms 内三次）；同秒另有 1 条 `friction-discovery:admitted` 与 2 条 `throttled(dispatch-in-flight)`。
- 反向失效：B 接管后注入正常（1 条），回收 A 后注入归零——2 实例与 3 实例两个场景均复现。
- 排除项：`dispose` 后再装、同一 agent 重复 emit `agent/created`、`start()` 的 enlist 与 `agent/created` 事件同时走一遍，三者均只产生 1 条。

**未覆盖**：

- **未直接观测到「谁在那个毫秒里连开了 3 个实例」的日志**——宿主不记录插件装载。现有最强解释是 `reconcileProfilePatches`（`packages/boot/app-boot/src/index.ts:279`）在 `entry.update()` 之后 `await` 旧 fiber 释放之间的窗口，但这条因果链只有时间吻合（提交 03:28:33、turn/end 03:28:45、三计时器 03:28:45.5），不是直接证据。
- 3 实例并行只出现过一次（11 个静置到期时刻中仅一次为 3 个），是否还有其它触发路径未知。
- 修复方向（引用计数 + 代际移交）未实现、未验证；dsh-purge 的 ctx 幂等标记方案未在本案实测。

## 影响与适用范围

适用于以「共享钩子 + 每实例私有去重表」实现单例语义的插件：重载窗口内新旧实例并存时，去重失效会各自安装一套钩子；而在共享上下文上手工调用旧实例的清理函数，又会在旧实例真正释放时连带摘掉新实例的钩子。已在 dsh-ldvh 的 agent 生命周期链路上观察到两种形态。
