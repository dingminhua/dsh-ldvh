# 未核机制即写入事实载体或据此建单

## 症状

同一会话内三次出现同一失败形态：观察到一个现象，推断出机制，**未核实即写入事实源或据此建单**。三次的下游代价依次升高。

第一次：把「共享 Index 并发污染」的实测，跨接成「LDVH 的 Git Gate 有缺陷」，并进一步给出「默认隔离 Index」的建议。实际 `LDVH_PREFLIGHT_INDEX` 是安装期预检专用的合成 index（`hook-manager.js:197-199` 注释原文「real commits never set this variable」），照做会把 Gate 指向一个只含假探针的合成 Index。该错误已随调研提交落盘，由两路独立审核纠正，产生两轮更正提交。

第二次：声称召回摘录「按词法命中位置截取」。实际 `excerptOf`（`source-recall.js:1438-1444`）只做空白压平与 120 字截断，与命中位置无关。该错误由建单后的自动审核在数秒内指出。

第三次：声称 `pitfall-bdae1a55` 的摘录位交付的是它的 `summary` 而取不到 `scope`。实际该对象**根本没有 summary 字段**，只有 scope；且本会话召回记录里 `↳` 位显示的**正是 scope 原文**。该错误由自查（回查召回记录原文）发现，但为时已晚——已据其建立 Spark 与 WorkCase 各一。

## 触发条件

任何「从观察推断机制」的环节，且满足下列任一条件时最易发生：① 现象与机制在措辞上高度相似（「摘录看起来像命中词回声」→「所以它是按命中位置截取的」）；② 被观察对象在多处出现，只看了其中一处就推广（只看 `bdae1a55` 的标题与印象，未打开它的 frontmatter，也未回查召回记录原文）；③ 结论会直接进入事实载体或作为建单依据，而在那里无人复核（写 Spark/WorkCase 的 frontmatter 时，机制断言以叙述形式出现，没有机械校验要求它必须与代码一致）。

## 根因

推断本身是必要能力，问题在于**推断结论与已验证事实之间缺少一道显式边界**。三个具体缺口：

1. **未区分「我看到了什么」与「我因此认为机制是什么」**。写作时两者用同一种语气表达，读回去看不出哪句有实证、哪句是猜测。
2. **核实的成本被低估**。三次中每一次的核实都只需一到两条命令（读注释、读函数、回查会话记录），但当时都跳过了——因为结论「看起来显然」。
3. **写入面没有拦截**。Spark/WorkCase 的 frontmatter 有大量机械校验（长度、结构、载体内聚），但**没有一条能发现「这段机制叙述与代码事实不符」**。语义正确性不在机械层射程内，这本身是对的（02 §9 明禁自动裁决），但意味着必须由作者自己承担。

## 解决

在任何机制断言写入事实载体或作为建单依据之前，逐条执行：

1. **给每条断言标来源**：写下来源是「我读到的代码原文（文件:行号）」「我看到的输出原文」还是「我的推断」。凡属第三者，不得作为建单依据。
2. **对推断类断言，用一条命令证伪它**，而不是找证据支持它。例：怀疑「摘录按命中位置截取」→ 直接读 `excerptOf`；怀疑「该对象给的是 summary」→ 直接读该对象的 frontmatter 与召回记录原文。
3. **回查原文而非回忆**：涉及「系统给我看了什么」的断言，回会话记录 grep 原文，不凭记忆复述。本会话第三次错误正是靠这一步发现——回查后发现显示的就是 scope。

## 规避

- 写「系统如何如何」「某字段取的是 X」这类机制句时，若无文件:行号，默认降级为「疑似」并另开一步核实，不写进 frontmatter 的 summary/gist（那是索引层，读不出限定语）。
- 建单（Spark 或 WorkCase）前的最后一步固定问一句：**本单的立论前提，我是读了原文还是推的**。若是推的，先去读。
- 已有的相近经验可作旁证但不能替代本步：`pitfall-9703ac07`（条款地址凭推测写入）限条款引用，`pitfall-574919e7`（未核读数来源路径）限读数分层，都不覆盖「机制断言」这一类。

## 验证

本条的验证形态是可指认的：本会话三次错误各自留下了发现路径——第一次由两路独立审核（取证到 `hook-manager.js:197-199`、`commit-validation.js:250-253`）；第二次由建单后自动审核（取证到 `source-recall.js:1438-1444` 与 `:2548-2562`）；第三次由自查回查召回记录原文。三次的纠正证据均可在对应提交与会话记录中回读。

反例边界：若某次机制断言**先**给出了文件:行号或原文引用，**再**写成结论，则不属本条——那已经是本条的合规形态，不是它的失败样本。

## 影响与适用范围

适用于任何 AI 从可观察现象推断系统机制、并把该推断作为事实载体的内容或行动依据的环节——包括但不限于写 Spark/WorkCase/ADR/Pitfall 的 frontmatter、调研报告的断言、以及据此决定是否实施改动。

不适用于：已有机械校验覆盖的断言（如长度、结构、载体内聚——那些会被直接拒绝）；也不适用于纯主观判断（如「这个方案更好」——那不是机制断言，无从靠读代码核实）。

边界：本条只要求「把推断与已核实事实分开、并对推断做一次证伪尝试」，不保证核实后结论一定正确；也不覆盖「核实了但仍读错」的情形（那是另一类失败）。
