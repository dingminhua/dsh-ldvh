# 复刻脚本正则提取拆错致分类读数与服务端口径背离

## 症状

一次性复刻脚本用于按服务层口径给真实日志做分类时，5 条本应命中 `spec_lookup_miss` 的记录被归入 `other`，读数与真实服务层分类结果不一致。逐字引证：

```
问题出在我复刻脚本里 `new RegExp` 的提取把正则拆错了
来源：主控会话 turn 3 的 assistant 正文段（「其他 5 条全是 `no public operation declares operation_key` …」一节，紧接「新分类表在真实日志上验证：other 从 68 降到 5」之后）
```

识别信号：`other` 桶里出现「no public operation declares operation_key」这类本应命中别的类别的记录；离线分类表与服务端实跑分类逐条比对出现稳定差异，且差异集中在同一个不敏感桶。

## 触发条件

同时满足：① 需要在服务端之外复刻其分类逻辑（一次性测量／复刻脚本）；② 复刻方式是从源码文本里提取分类正则字面量，再用 `new RegExp` 重建匹配；③ 提取后没有与服务端真实实现逐条对照，也没有把复刻口径与服务端实跑口径在真实日志上做差异校验；④ 结论直接取用了该分类读数。

## 根因

根在「从源码文本提取正则」这一复刻环节的保真度：提取把正则字面量拆错（拆散、截断或错配转义），重建出的 `new RegExp` 与服务端实际使用的并非同一条正则，于是差集系统性地落在分类不敏感的桶里（本次为 `other`）。偏差方向一致、可重复，看起来就像「这些记录确实属于 other」。服务端分类逻辑本身未变——变的是离线复刻；因此这是复刻口径与真实口径的背离，而不是被测实现的缺陷。

## 解决

已实际采用的处置是修正提取方式、改用新分类表并在真实日志上验证：「新分类表在真实日志上验证：other 从 68 降到 5」。成功信号是 `other` 桶由 68 降到 5，且分类结果与真实服务层分类一致。必要边界：材料未给出提取修正的具体实现方式与逐条对照记录，5 条原被归入 `other` 的记录未逐条留痕。

## 规避

1. 核对条件：任何从源码文本提取正则字面量的复刻动作，提取后逐条与源码中的原始正则比对（转义、字符类、分组与量词均在内），确认 `new RegExp` 重建结果与源码字面量等价后再用于分类。
2. 动作：复刻出的分类表须在真实日志上与服务端实跑结果做差异校验，差异非零即判「复刻口径未对齐」，该读数不得作为结论使用。
3. 动作：读数里出现「其它／未分类」桶时，先核该桶是否为复刻偏差的堆积处（本条即 5 条集中在 `other`）。
4. 例外：直接在服务端代码路径上调用同一分类逻辑（不经文本提取）时不受本条约束。

## 验证

已观察：新分类表在真实日志上验证，`other` 从 68 降到 5（引证见「症状」段）；修正前 `other` 中含 5 条应命中 `spec_lookup_miss` 的记录。逐字引证：

```
问题出在我复刻脚本里 `new RegExp` 的提取把正则拆错了
来源：主控会话 turn 3 的 assistant 正文段（「其他 5 条全是 `no public operation declares operation_key` …」一节，紧接「新分类表在真实日志上验证：other 从 68 降到 5」之后）
```

未覆盖：修正后的提取实现未逐字记录；其余各类别上是否仍存在未逐类核对；复刻口径在更长日志／更多失败类型上的稳定性未观测；`other` 从 68 降到 5 是否已与服务端实跑逐条一致，材料未给出该比对的逐条清单。

## 影响与适用范围

适用于用一次性脚本从服务层源码提取正则并重建匹配逻辑、以便离线分类真实日志或做测量的场合：提取失真时读数与真实服务层分类系统性背离，偏差集中落在分类不敏感的桶（本次 `other`）。何时可能踩到：需要「按服务端口径给历史日志重新分类」这类工作，而服务端逻辑只能从源码读取、只能离线复刻时（本条引证的 `new RegExp` 提取拆错即该形态）。何时可信：只要提取环节仍是从文本里重建正则、且没有与真实实现逐条对照，本条即适用；若复刻口径已在真实日志上与服务端实跑对齐，则该风险已被本条核对条件覆盖。本条不覆盖脚本把查询异常静默折算成零命中（见 pitfall-1b2934e9）、以不覆盖被测类型的入口测量（见 pitfall-97d65fb9）、读数来源路径未分层（见 pitfall-574919e7）与自写扫描器缺映射规则致假阳性（见 pitfall-fdeff12d）。
