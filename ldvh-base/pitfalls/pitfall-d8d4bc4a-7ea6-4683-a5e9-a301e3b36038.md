# Electron asar 头偏移误读致解析失败

## 症状

手工解析 app.asar 归档头时 `JSON.parse` 抛 SyntaxError 解析中断；或把头索引原文当作文本 dump 出巨量噪音（首次实测输出约 15KB 原始索引文本）。

识别信号：解析在第一步 `JSON.parse` 即失败；按假设读出的「JSON 长度」显著大于实际 JSON 长度；错误输出开头是 `{"files":{...` 形式的原始索引文本而非裸 JSON。

## 触发条件

不借助 asar 库、直接用 `fs.readSync` 手工解析 Electron 应用的 app.asar 归档头，并按直觉假设头部为「偏移 4 = JSON 长度、偏移 8 = JSON 起点」的双字段布局。

## 根因

asar 头是 Chromium Pickle 双层序列化结构，直觉布局的每个偏移语义都错位：偏移 4 并非 JSON 长度而是 headerSize，JSON 也不起始于偏移 8 而是偏移 16（头部块内另有 4 字节长度前缀）。

已观察：实测可用的读取路径为——自偏移 0 读 8 字节，偏移 4 处 UInt32LE 得到 headerSize；自偏移 8 起读 headerSize 字节作为头部块；头部块内偏移 4 处 UInt32LE 得到 JSON 长度；头部块内偏移 8 起为 UTF-8 JSON 文本。未知：偏移 0 与头部块内偏移 0 的精确语义未读取核对，本对象不对其下判断。

## 解决

按实测偏移修正读取顺序：`headerSize = sizeBuf.readUInt32LE(4)` → 自偏移 8 读 headerSize 字节得头部块 → `strLen = headerBuf.readUInt32LE(4)` → `JSON.parse(headerBuf.slice(8, 8 + strLen))`。

成功信号：`JSON.parse` 一次通过，直接得到完整 files 树并读出全部内嵌包版本（实测 DSH Desktop 2.0.6 → 217 个 `@deepseek-ai/dsh*` 包均为 0.1.2-rc.1）。

必要边界：仅对 Chromium Pickle 风格的 asar 头成立。

## 规避

需要读 asar 内容时优先用现成工具（`npx asar list` / `extract` 或 `@electron/asar` 库），不手工偏移；确需手工解析时按上述偏移模板书写，不按直觉猜布局，并在解析前 dump 前 32 字节 hex 核对前缀。

例外：归档头不是 Pickle 风格时本经验不适用，须重新实测布局。

## 验证

已观察：对 DSH Desktop 2.0.6 的 app.asar（约 199MB）一次解析成功，读出 217 个 `@deepseek-ai/dsh*` 包（0.1.2-rc.1）、`@deepseek-ai/cordis` 4.0.2 与 cosmokit 1.8.3，并与 Info.plist 的壳版本 2.0.6 交叉核对成立。

未覆盖：标 `unpacked:true` 的条目实体（位于 app.asar.unpacked 目录）未读取；integrity SHA256 校验块未验证；其他 Electron 应用或不同 asar 版本的归档头未测试。

## 影响与适用范围

适用于手工解析 Electron app.asar 归档头以检查内嵌包内容的活动（如确认 DSH Desktop 内核版本、核对打包内容）；asar 头部格式变更后经验可信度需重审。

何时可能踩到：任何绕过 asar 库、直接读归档头的行动（版本确认、升级 diff、兼容性排查、打包内容核对）都可能落入本机制的影响范围。

经验何时可信：仅在归档头仍为本次实测的 Pickle 布局时可信；Electron 升级或应用改用其他打包格式后，须重新实测布局再复用本经验。
