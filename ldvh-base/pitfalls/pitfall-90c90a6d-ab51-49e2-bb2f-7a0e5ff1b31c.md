# 插件 lib 改动需重启宿主才进运行实例

## 症状
把 `plugin/lib/` 的改动当成「已经生效」，据此下判断或向 Human 汇报「功能已可用」。实际运行中的宿主进程仍执行旧模块，行为与源码不一致；而本仓以源码为准的校验（预检、比对、指纹）会给出与运行实例不符的判定，并在回执里标为「比宿主进程新」「不可核对」。

## 触发条件
- 改动了 `plugin/lib/` 下的服务端模块代码（writer / tools / 生命周期 / 路由等）；
- 且期望在**当前正在运行的**真实会话中立即观察到新行为。

反例（不触发）：只改配置值且代码每次现读——配置重载即可生效。

## 根因
宿主进程在启动时加载并求值插件模块；此后磁盘上的文件改动不会使已加载的 ESM 模块重新求值。模块缓存按**路径**驻留，因此「重新安装/重新启用插件」这类只重建插件实例的动作也不会重新求值已加载模块。结果是「源码已改、运行实例未变」的双态并存：任何以源码为准的检查与以运行实例为准的观察会互相矛盾，且矛盾方向固定（源码新、实例旧）。

## 解决
1. 改动落盘后先做**离线验证**（单测、直调 writer、静态核对），确认代码本身正确——这一步不依赖运行实例；
2. 需要真机行为时，**重启宿主进程**，让新模块进入运行实例；
3. 重启后立即做一次**行为形态对比**（同一操作，重启前后返回形态应不同），以此作为「改动已生效」的证据，而不是凭「文件已保存」推断。

## 规避
核对条件——出现以下任一情形时：
- 改动了 `plugin/lib/` 下的文件；
- 准备在真实会话里验证这次改动；
- 预检/校验结果与离线结论不一致，且提示信息里出现「比宿主进程新」「STALE」「过期代码」之类字样。

动作：
1. 先跑离线验证，确认代码本身正确；
2. 需要真机行为时，**明确要求重启宿主**，并在重启后做一次行为形态对比；
3. 看到「判定由过期代码算出、标为不可核对」这类回执时，**不要**当作通过，也不要当作失败——它是「不知道」，须重启后重跑；
4. 反过来也成立：不要因为「离线跑通了」就宣称功能已在真实会话生效。

例外：若改动只涉及配置项（且代码读取该配置的方式是每次现读），配置重载即可生效，不必重启——判据是「改的是配置值还是模块代码」。

**实测无效的替代通道（2026-11-04 本仓验证，勿再尝试）**：用 `plugin_manager` 把插件「禁用 → 重新启用」**不能**使 `plugin/lib/` 的改动生效。两次调用均返回 `application: applied`，但行为探针仍走旧代码——ESM 模块按路径永久驻留，禁用/启用只重建插件实例、不重新求值已加载模块。判据：禁用启用后用行为探针比对（而非看返回码），本仓的探针是 `ldvh_adr_write action=correct`（旧版回 `action must be create|update`，新版回 `adr/invalid_uid`）。**唯一可靠通道仍是重启宿主进程。**

## 验证
已观察（2026-10-29，本仓）：
- `plugin/lib/ldvh-tools.js` 改了候选渲染后，重启前工具输出为「31 candidate(s) at L0」；重启后输出逐条 31 行清单——同一会话、同一命令，仅进程重载与否不同；
- 预检在重启前反复附 gap：「校验器模块比宿主进程新，判定由过期代码算出、标为不可核对」，重启后该 gap 消失；
- `plugin/lib/index.js` 中 `config-reload` 的注释明记只重协调 Profile patches、不携带 diff。

已观察（2026-11-04，本仓，另一主体另一场景）：
- `adr-tools.js` / `workcase-tools.js` 于 21:48 改动，宿主进程 19:37 启动。重启前 `ldvh_adr_write action=correct` 回 `action must be create|update`（旧枚举）；22:17 重启后同一调用回 `adr/invalid_uid`（已进入 correct 分支）——同一命令、同一文件，仅进程重载与否不同；
- 同一时段内 `record_review` 恒报「no captured conclusion」，重启后同一子代理的结论立即可读（90 / 559 / 859 字符等多例）——证明该现象并非任何代码缺陷，而是运行实例陈旧所致。

未覆盖：
1. 宿主其它模块级重载通道：2026-11-04 已实测排除 `plugin_manager` 的禁用/启用（见「规避」末尾），其余通道（如 HMR 对服务端模块的作用）仍未核；
2. 未量化「改动到重启」之间的验证空窗带来的实际损失；
3. 客户端 HMR 对浏览器端是否总生效未验（本仓主要坑在服务端）。

## 影响与适用范围
适用于改动 DSH 宿主插件的服务端代码（plugin/lib/）后需要真机验证的场合：运行中的宿主进程不会加载新模块，改动只在重启后进入运行实例；期间以本仓代码为准的校验会给出过期判定并被标为「不可核对」。可靠顺序是离线先验、明确声明需重启、重启后做一次新旧行为形态对比。边界：本条只覆盖服务端模块代码；配置项的效应不在此列（判据是改的是代码还是配置值）。
