# 消费侧漏读答复协议 custom 致输入被吞

## 症状

当前提请框里，Human 在自由输入框写了信息并点击「提交」后，被判为「跳过／未决策」，AI 看不到写入的任何内容。把关请示工具返回 `decision: null` 与 `human did not choose an option`，Spark／ADR／管辖登记三处 Human Gate 则返回 `granted: false`「未确认」。Human 写的字既不在 `decision` 里、也不在留痕里、也不在回给模型的信封里——整段文字凭空消失，且外观上与「点跳过按钮」无法区分。2026-11-14 用仓库真实模块端到端复现，为必现而非概率性。

## 触发条件

宿主提问卡 `QuestionComposer.tsx:385-395` 在「单选题 + 自由输入」提交时，把 `selected` 强制置空、把文字只放进 `custom`，产出 `{ id, selected: [], custom: "..." }`。LDVH 消费点 `host-seams.js` 的 `selectedLabelOf` 只读 `entry.selected ?? entry.answer`，从不读 `custom`。上游工具 `dsh-tool-ask-user`（legacy 与 timed 两个 `execute`）、服务类型 `AskUserQuestionAnswerItem`、Typert 网关 schema、投影 `answerSchema` 四处都逐字透传 `custom`——宿主这条链是通的，断点只在 LDVH 消费侧。叠加一层：Human 2026-11-13 定了「提请只留 ≤200 字短标题、不带 detail」，于是自由输入框成了 Human 补充说明的唯一通道，被封死且无任何报错。

## 根因

两层叠加。① **消费侧把答复协议当成只有 `selected` 一个承载字段**，对上游协议里长期存在的 `custom` 字段零读取；② **上游跟进规程的差分三态只盯「消费面内条目被删/改名/签名变」（破坏）与「语义收窄／upgrade-guide 命中」（须审）**，没有一项针对「答复协议的实际答案形态与消费点字段覆盖」——于是「上游没删 API、没改签名」被判成「无关／零变更」，而上游卡片的实际产出形态早已与消费侧假设不符，从未被察觉。

## 解决

`host-seams.js` 增 `customTextOf`，四处接缝（`requestReviewAsk` + 三处 Gate）把 `custom` 逐字取回为 `custom_note`，经工具信封与 `renderEnvelope` 回给模型；`decision` 仍守 32 §9.1 的 `review|skip` 闭集、Gate 仍 fail-closed，自由文本不冒充答复、不进留痕载体；`reason` 区分「点跳过按钮」(`{selected:[]}`) 与「自由输入提交」(`{selected:[],custom}`)。同时在 Norm「上游更新跟进规程」增设「提请/答复接缝专项检查纪律」，把答案形态与消费点字段覆盖列为上游跟进必查项（强制做法由规范源承接，本经验只记机制）。

## 规避

上游跟进时，凡差分触及 `dsh-client-ui-user-questions` / `dsh-tool-ask-user` / `dsh-user-questions` 三包或答复协议类型，**不得只按「API 增删／签名」判三态**；须额外用真实答案形态（含「自由输入 + 点提交」这一支）核对 LDVH 每个答复消费点是否覆盖了协议里所有承载字段。受控写入前对「消费点读哪些字段」逐字列清单比对协议定义，不以「上游没删东西」代替核对。

## 验证

端到端复现：把自由输入提交的真实答案形态 `{selected:[],custom:"老丁：请特别核对 X 模块"}` 喂给仓库真实 `host-seams.js` 模块，修复前得 `decision:null` 且文字全失；修复后 `ask-custom-visibility.test.mjs` 11 条 + 相关回归 147 条全绿（含三处 Gate 仍拒绝授权但 `custom_note` 可见、`custom` 不进留痕、`renderEnvelope` 逐字打出）。未覆盖：宿主真机 GUI 上人工点选复核；其它消费宿主答复的第三方插件不在本仓范围。

## 影响与适用范围

适用于 LDVH 一切消费宿主提问/答复协议（ctx.userQuestions.ask / ask_user_question）的接缝——把关请示与 Spark、ADR、管辖登记三处 Human Gate 的答案解析点，以及上游 DSH 跟进时对提问卡与答复协议消费点的专项核对；不适用于宿主侧答复协议本身的实现。

上游 `dsh-client-ui-user-questions` / `dsh-tool-ask-user` / `dsh-user-questions` 三包或 `AskUserQuestionAnswerItem` 字段变动时，本经验须按 `trigger_signal` 重审——那正是「上游没删 API 却改了答案形态」这一类漏检的高发入口。
