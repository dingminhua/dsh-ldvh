# 零受检对象被工具缺失前置阻断致Hook死锁

## 症状

bundle 安装 dsh-ldvh@1.1.5 后，Git Hook 的 preflight 必然失败，报：

> `validation/lint_failed: eslint is not installed in …/node_modules/dsh-ldvh/node_modules — run npm ci there before committing (the gate refuses rather than skipping lint)`

用户因此装不上、也用不了 Git Hook，形成死锁。识别信号：本次探测根本没有**任何一个** lint 面内文件（preflight 的合成 index 里唯一条目是 `.md`），门禁却因「工具不在」而拒绝——即「没有要检查的东西」被报成「检查工具缺失」。常见表象是「同一功能在有 eslint 的开发机上一切正常，换到 bundle 安装形态就必然红」。

## 触发条件

三条同时成立才会踩到：① 门禁实现**先探测工具可用性、后判本次受检对象是否为零**；② 工具在该安装形态下合法缺席——bundle 安装目录不含 `node_modules`；③ 本次调用确实零受检对象、本应跳过。本仓这一处三条全部满足：

- preflight 使用合成 index，唯一条目是纯文档：`plugin/lib/hook-manager.js:264` —— `const PREFLIGHT_PATH = "ldvh-base/preflight-probe.md";`
- workspaceRoot 直接由 runner 路径上溯两级，即插件自身目录：`plugin/lib/hook-manager.js:344` —— `await Promise.all(pending.map((entry) => preflight(entry.rendered, identity, entry.spec, dirname(dirname(resolve(runnerPath))))));`
- 发布包不含依赖树，eslint 只在 devDependencies：`plugin/package.json:39-55` 的 `files` 数组只有 `lib`、`icons`、`plugin-specs`、`web/*` 等，无 `node_modules`；`plugin/package.json:102-111` 的 `devDependencies` 含 `"eslint": "^10.10.0"`、`"@eslint/js"`、`"globals"`、`"acorn"`。

叠加条件：正常开发机上 eslint 存在，顺序缺陷被完全掩盖，只在 bundle 安装形态暴露。

## 根因

可用性判定与工作量判定的**次序颠倒**：「工具在不在」被当成门禁的第一性问题，而「这次有没有东西需要这个工具」被排在后面。零受检对象本应走跳过分支，却先被工具缺失前置阻断，于是契约里合法的「空集跳过」被替换成阻塞失败。

逐字定位修复前代码（`plugin/lib/git-gate-runner.js`:402-407）：`checkLint` 的第一步是 `const eslint = await resolveEslint(workspaceRoot)`，缺失即返回阻塞 `validation/lint_failed`；而 `if (files.length === 0) return { ok: true, skipped: "no-lint-files" }` 排在其后。也就是说零对象判断根本到不了。

这层顺序缺陷还把死锁闭合了：拒绝文案建议的 `run npm ci` 在无 lockfile 的插件目录不可执行（issue 实测 EUSAGE），于是形成「拒绝 → 按提示修不了 → 继续拒绝」的闭环。注意「有 lint 文件而缺 eslint 就拒绝」这一决定本身是对的（Human 2026-10-19 的 refuses-rather-than-skipping），本条的缺陷不是它，而是它被错误地应用到了零对象场景。

## 解决

commit `fd454a5d`（fix(gate): 修复 bundle 安装缺 eslint 致 Git Hook preflight 必然失败（issue #7））把零 lint 文件的跳过判断移到 eslint 存在性检查之前。修复后顺序可见于当前 `plugin/lib/git-gate-runner.js:403-404`：第 403 行 `if (files.length === 0) return { ok: true, issues: [], skipped: "no-lint-files" };` 先判空，第 404 行才 `const eslint = await resolveEslint(workspaceRoot);`。

效果：空场景直接跳过、Hook 可装；有 lint 文件而缺 eslint 仍拒绝，不改动既有决策。错误提示同步改为可执行的安装命令 `npm install --no-save --no-audit --no-fund --legacy-peer-deps eslint @eslint/js globals acorn`，取代不可用的 `npm ci` 建议。

## 规避

① 门禁里「本次有没有对象要检查」必须是最先的判据，早于任何工具/环境探测；② 只有确认存在工作对象之后，才允许把工具缺失升级为阻塞；③ 拒绝文案必须给出在**该安装形态下可执行**的补救命令，工具目录无 lockfile 时避开 `npm ci`；④ 对「工具可能合法缺席」的形态（bundle 安装、可选依赖、懒加载）专门实拍一次零对象路径，而不是只测开发机；⑤ 零对象跳过与真正通过要在输出里可区分（打印 `skipped` 原因与受检对象数），避免跳过被读成通过。

## 验证

受影响测试 26/26 通过；全量 2641 项 0 失败；eslint 干净。两条回归用例分别钉住两个方向，均位于 `plugin/test/git-gate-runner.test.mjs`：

- `:546` 「无 eslint 且本次无 lint 面文件时放行——bundle 安装 preflight 不再死锁（issue #7 / 空清单先于工具检查）」：断言退出码 0、输出 `LDVH Git Gate (pre-commit) passed`，且不含 `validation/lint_failed` 与 `npm ci`；
- `:562` 「无 eslint 但本次有 lint 面文件时仍拒绝——不削弱 refuses-rather-than-skipping 决策（issue #7 / 有文件须 lint）」：断言退出码 1、含 `validation/lint_failed` 与 `refuses rather than skipping lint`，且含 `npm install --no-save`、不含 `npm ci`。

变异检验：把顺序回退（把 eslint 探测移回零对象判断之前）后，`:546` 用例转红——说明该用例对本次顺序缺陷有分辨力，不是空转。修复前的顺序可由上述 `:402-407` 逐字引证对照确认。

未覆盖：材料未逐字给出 bundle 安装目录下真实的 `resolveEslint` 返回路径与 issue 正文的完整报错堆栈；「其它门禁是否存在同形的工具先行探测」未逐一排查。

## 影响与适用范围

一切「先探测工具可用性、后判零工作对象」的校验/门禁脚本，尤其是工具可能在当前安装形态下合法缺席（bundle 安装、可选依赖、懒加载）而该场景本无需该工具时；本仓的具体落点为 `plugin/lib/git-gate-runner.js` 的 `checkLint` 及其 preflight 调用链（`plugin/lib/hook-manager.js` 的合成探测 index）。经验可信边界：限于本条证据链所及的 checkLint/preflight 场景及同形空集分支。

展开：最易踩到的是那些「拒绝而非跳过」的强门禁（lint、类型检查、格式校验、许可证扫描、审计），因为它们的工具缺失分支被刻意写成阻塞；一旦该分支排在零对象判断之前，任何「本无需该工具」的调用都会被它误伤。与「路径算错致清单滤空而静默放行」是同一函数里的相反方向缺陷：那条让空清单被读成通过（漏检风险），本条让真空清单被读成工具缺失（可用性死锁），两者的根因（路径换算 / 判定次序）与修法都不同。当门禁已把零对象判断前置、或安装形态不再让工具合法缺席时，本条触发条件不再成立，应重审。
