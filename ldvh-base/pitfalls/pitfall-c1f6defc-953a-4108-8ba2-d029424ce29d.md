# 共享工作树整树切换做单变量对照致对照污染

## 症状

助手把「质量基线测试转红是本单造成」当作已经核实的结论报告出去，直到下一轮改用单一变量重做对照才推翻它。事后自陈：

```
把**别人正在进行的语料改动**也一起回滚了，因此那个对照被污染
来源：本次观察材料 turn 5 · assistant 段（自陈「上一轮我用 git stash 做前后对照时……因此那个对照被污染」）
```

识别信号：报告把某条基线测试的转红直接归给本单改动，但对照的两侧并非只差被测变量；把对照重做后，同一读数翻转为不支持该归因。

## 触发条件

- 多个执行体共享同一 Git 工作树，树上有别人正在进行的语料改动尚未提交；
- 需要判断「某条质量基线测试转红是不是本单造成」，于是用整树状态切换（如 `git stash`）把工作树切到「改前」量基线，再切回「改后」取读数；
- 测量流程没有先核对两侧的差异面，也没有在取值前断言「除被测变量外没有别的改动进出」。

三者同时成立时，stash 会把别人正在进行的语料改动一并移出，回填时再一并带回，那个对照被污染。

## 根因

整树状态切换操作的是工作树的全局状态，不是被测变量的集合。stash 保存与恢复的是整棵树（包含其他会话未提交的改动），因此「改前」与「改后」两次读数之间发生变动的文件不止被测变量；而测量流程只比较两次读数、不核对两次状态之间的差异清单，于是把别人正在进行的语料改动造成的读数变化归到了本单头上。已观察：助手自陈回滚了别人正在进行的语料改动，并承认因此那个对照被污染。未知：那次整树切换是否还带走了构建产物或缓存，材料未给出。

## 解决

实际采用：确认别人正在进行的语料改动也随整树切换被回滚、因此那个对照被污染后，下一轮改用单一变量重做对照，只让被测改动进出，重做后原先「质量基线测试转红是本单造成」的结论被推翻。成功信号是干净对照下的读数不再支持原归因，助手据此撤回结论。必要边界：材料只记录了「用单一变量重做」这一处置，未记录隔离手段是逐文件 stash、临时副本还是独立工作树，故不把某一种手段写成已验证做法；共享树上他人改动被移出后是否完整回填，本次也未核对。

## 规避

准备用整树状态切换（`git stash` 做前后对照、`git checkout`/`git reset` 回基线）来量单变量差异时：先列出工作树里全部未提交改动（含其他会话的），确认被测变量之外没有别人的改动会被移出或带回；优先在独立副本或独立 worktree 上做测量；取值后核对两侧 diff 只含被测变量。例外：已确认工作树独占且无并行改动时，整树切换才可作为对照手段，即便如此仍要在取值后核对差异清单。

## 验证

已观察：turn 5 的 assistant 段自陈「上一轮我用 git stash 做前后对照时……因此那个对照被污染」，明确回滚了别人正在进行的语料改动；基于该对照给出的「质量基线测试转红是本单造成」在下一轮单一变量重做后被推翻。未覆盖：未逐文件核对那次 stash 实际移出了哪些他人改动、回填是否完整；未在独立 worktree 上重跑同一对照以复现结论翻转。

## 影响与适用范围

适用于多执行体共享同一 Git 工作树、且以整树状态切换建立「改前」基线来做单变量对照或因果归因的测量流程，也包括先用 stash 制造干净树、再据读数给缺陷定性的场合。何时可能踩到：树上有并行未提交改动，而测量只以「同一工作树的前后两次读数」为对照时。经验何时可信：只要对照仍以工作树整体状态作基线、且无差异面断言，本条即适用；一旦把「那个对照被污染」设为测量前置断言并改用隔离副本，本条的约束即可撤除。
