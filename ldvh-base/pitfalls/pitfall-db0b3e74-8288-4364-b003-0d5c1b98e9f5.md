# force-exit 与管道竞态吞 TAP 汇总行

## 症状

CI 8 次红中 2 次（run 44811382702、44793724745）的形态是：TAP 流在中途截断（其中一次为 `ok 2124` 行之后无后续），没有「# tests N」汇总块，子进程退出码为 0，守卫判「条数不可得（不得读作零失败）」。即失败不在用例，而在「汇总行没读到」，守卫因此拒绝把这次运行读作全绿。

## 触发条件

同时满足三项：(1) 测试入口给内层 `node --test` 传了 `--test-force-exit`——该 flag 由 commit 4e02f9f 引入 npm test 脚本（省约 84s 收尾空等），run-tests.mjs 包装器由 f90d42f7 建立时带入非 win32 分支，affected-tests.mjs 由 15312b0c 建立时带入同一条件分支；f90d42f7 将其平台条件化的原因是 Windows 上该 flag 与 undici 收尾句柄相撞、触发 libuv 原生断言 `UV_HANDLE_CLOSING` 造成进程级 abort；(2) 入口以 stdio pipe 捕获子进程 stdout 并从中取汇总行，故下游依赖完整输出；(3) CI 非 TTY，输出为 TAP 方言（开发机 TTY 走 spec 方言），汇总行为「# tests N」而非「ℹ tests N」。

## 根因

`--test-force-exit` 让进程在测试完成后立即 `process.exit`，而此时管道里尚未 drain 的 TAP 输出（含汇总行）被丢弃；截断位置随机，于是表现为「退出码 0 + 输出中途断流 + 无汇总块」。这是竞态而非稳定缺陷，故 8 次中只出现 2 次，重跑可能转绿。开发机的 TTY/spec 方言或同步写场景不易复现，掩盖了该机制。

由此得出一条独立判据：退出码 0 不证明全绿——它只说明进程正常结束，不说明输出完整；「输出被截断」与「条数不可得」须由汇总行是否存在来判定，不能由退出码推断。

## 解决

两个入口一律去掉 `--test-force-exit`，让 `node --test` 自然退出（事件循环排空、stdout 完整 drain）。代价是收尾空等回归：全套件约 41s → 95–131s，但有界；Windows 行为不变（本就不传该 flag）。成功信号：本地多次全量（含管道 stdout）实测汇总行完整、守卫通过；模拟干净 CI 环境（空 HOME + 不存在的上游克隆路径）实测 0 fail / 33 skipped / exit 0。

## 规避

1. 不要用 `process.exit` 类强制退出给测试收尾提速；若必须强制退出，先确保 stdout 是文件，或消费端已读完并 drain，再退出。
2. 对账守卫须把「条数不可得」与「零失败」分成两个终态，并在判红时按判据分流提示——截断与 skip 超基线是两类失败，处置不同。
3. 出现「退出码 0 + 输出截断」时不得读作全绿，应按「条数不可得」拒绝给出结论并重跑/查因。
4. 保留平台条件化：Windows 不传该 flag（有 `UV_HANDLE_CLOSING` 原生断言的已知碰撞）；若要重新引入，须在非 win32 且 stdout 非记账通道时才考虑，并重测收尾耗时与输出完整性。

## 验证

已观察：CI 8 次红中 2 次呈现上述截断形态，run id 为 44811382702 与 44793724745，其中一次截断点在 `ok 2124` 之后；两次子进程退出码均为 0、均无汇总块。修复后本地多次全量（含管道 stdout）汇总行完整、守卫通过；模拟干净 CI 环境实测 0 fail / 33 skipped / exit 0。历史侧另有两处可核对：4e02f9f 引入该 flag（省约 84s），f90d42f7 因 Windows 的 `UV_HANDLE_CLOSING` abort 改为平台条件化。CI 侧回证（2026-11-21 补充）：修复提交 ab0cf945 推送后 run 44839044532 的 plugin job 在 TAP 方言下汇总行完整（2511 tests / 0 fail / 33 skipped）、守卫对账通过、job 绿——去掉强制退出时点后本次运行未再出现截断。

未覆盖：单次 CI 绿不足以统计意义上证明「2/8 的间歇形态已消除」，机制判断（不再有强制退出时点）加本地与模拟环境的完整输出仍是主要依据；也未穷举其他 stdio 模式（如 TTY 下 spec 方言配合管道、或缓存后重定向）是否同样存在未 drain 的窗口。截断位置随机这一点只有两次样本，不足以刻画分布。

## 影响与适用范围

凡以 stdio 管道捕获 node --test 子进程 stdout、并依赖汇总行（spec 方言「ℹ tests N」/ TAP 方言「# tests N」）对账条数的测试入口，尤其 plugin/scripts/run-tests.mjs 与 affected-tests.mjs；入口对内层 node --test 传 --test-force-exit 类强制退出时，测试完成后未 drain 的输出（含汇总行）可能被丢弃。本条可信范围限于非 win32 平台、管道 stdout、TAP 或 spec 输出方言下的对账路径；强制退出带来的收益随用例与句柄构成变化，复用前须重测。

展开：受影响的不只是「条数守卫」，凡下游需要完整子进程输出做判断的环节（失败行统计、签名比对、覆盖摘要）都在同一竞态下，因为被丢的是管道缓冲区而非某一类行。Windows 侧不受本条约束——该 flag 在 Windows 上已被证伪并撤下，那里的问题是另一个（`UV_HANDLE_CLOSING` 原生断言），不得用本条结论去解释 Windows 的 abort。本条经验成立的前提是「stdout 经管道交给父进程且父进程依赖完整输出」；若入口把输出直接写文件再由父进程读取，强制退出不会丢已落盘的内容，本条即不适用。
