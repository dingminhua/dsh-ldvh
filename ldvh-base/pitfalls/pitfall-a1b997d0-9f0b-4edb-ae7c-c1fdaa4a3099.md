# 无关未提交改动阻塞变基致推送延迟

## 症状

执行 `git rebase` 时被未提交的改动挡住，rebase 无法开始；工作区中存在并非本会话产生的改动（材料自述为后台 idle 进程写入的观察计数更新）。

## 触发条件

远端出现了新提交，需要把本地领先的 8 个提交变基到远端之上；同时工作区里存在由其它执行者（后台 idle 进程）留下的未提交改动，且这些改动与当前会话的工作无关。

## 根因

工作区是共享的：后台辅助进程会直接在同一工作树写入文件并留下未提交的改动，而这些改动不属于当前执行者，但 git 的 rebase 前置条件要求工作区干净，因此无关改动同样构成阻塞。

## 解决

先确认这些改动的归属（判定为非本会话工作），再只针对自己的改动做 `git stash`，使工作区干净后执行 rebase；rebase 成功并推送完成后，原样恢复 stash 的改动，不混入任何提交，并在对外交代中显式声明曾 stash 过非己方改动。

## 规避

在需要 rebase / 切换分支这类要求干净工作区的操作前，先确认工作区是否存在非本会话产生的改动；若有，先判定归属再决定 stash 范围，并在完成后按原样恢复，避免把自己的会话边界与共享工作区状态混为一谈。

## 验证

已观察到的结果：变基后 8 个提交完整重放到远端之上且无冲突，推送成功（f90d42f..ecf95b1），本地与远端同步为 0 / 0；plugin 测试 1544 个、1543 通过、0 失败（1 跳过），web 测试 499/499 通过，tsc -b 零错误。stash 的改动在推送后恢复。
未覆盖的部分：材料未说明 stash 是否干净应用（是否有冲突提示），也未包含恢复后是否再次跑测试的观察，故「恢复后代码仍全绿」这一点本次未被观察到。

## 影响与适用范围

影响与适用范围：适用于任何在共享工作树上需要保持工作区干净才能执行的操作（rebase、切换分支、部分 merge），且工作区可能同时存在本执行者与非本执行者（后台辅助进程、并行会话）产生的未提交改动的情形；不适用于独占工作树或无并发写入的场景。
