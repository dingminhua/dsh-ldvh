# 无关未提交改动阻塞变基致推送延迟

## 症状
执行 `git rebase` 时被未提交的改动挡住，rebase 无法开始；工作区中存在并非本会话产生的改动（材料自述为后台 idle 进程写入的观察计数更新）。

## 触发条件
远端出现了新提交，需要把本地领先的 8 个提交变基到远端之上；同时工作区里存在由其它执行者（后台 idle 进程）留下的未提交改动，且这些改动与当前会话的工作无关。

## 根因
工作区是共享的：后台辅助进程会直接在同一工作树写入文件并留下未提交的改动，而这些改动不属于当前执行者，但 git 的 rebase 前置条件要求工作区干净，因此无关改动同样构成阻塞。

## 解决
先确认这些改动的归属（判定为非本会话工作），再用**限定路径**的 `git stash push` 只把无关改动收起（实际命令：`git stash push -m "idle-process friction count updates (not mine)" -- <两处 friction 载体路径>`），使工作区干净后执行 rebase；rebase 与推送完成后 `git stash pop` 原样恢复，不混入任何提交，并在对外交代中显式声明曾 stash 过非己方改动。**关键点**：stash 的对象是**非本执行者**的改动、且必须限定路径，不是把自己的改动收起来；本会话自己的工作当时已提交，工作区内并无待 stash 的己方改动。

## 规避
在需要 rebase / 切换分支这类要求干净工作区的操作前，先确认工作区是否存在非本会话产生的改动；若有，先判定归属再决定 stash 范围，并在完成后按原样恢复，避免把自己的会话边界与共享工作区状态混为一谈。stash 无路径限定会把己方与他方改动一并收起，恢复时难以分辨，故必须按路径限定到已判明归属的无关文件。

## 验证
已观察到的结果：变基后 8 个提交完整重放到远端之上且无冲突，推送成功（f90d42f..ecf95b1），本地与远端同步为 0 / 0；plugin 测试 1544 个、1543 通过、0 失败（1 跳过），web 测试 499/499 通过，tsc -b 零错误。stash 的改动在推送后恢复（`Dropped refs/stash@{0}`，无冲突提示）。
