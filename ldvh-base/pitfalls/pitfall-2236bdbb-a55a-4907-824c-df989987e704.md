# 配置武装只挂装载路径致改设置不生效

## 症状

改设置后行为没变：要把「每 N 分钟」改成别的间隔，重启才生效——因为武装逻辑（按配置注册定时任务／监听器／缓存）只在装载时跑了一次，之后的配置重载事件没有对应的重新武装。

识别信号：配置被读到时一切正常，改动后只有重启才生效；且在代码里搜得到「读配置」的地方，却搜不到「配置变了要重新做一遍」的地方。

## 触发条件

武装动作（schedule.create、ctx.on、缓存初始化）挂在**装载路径**上（`apply` 一类的钩子只在首次装载或插件启用时调用一次），而配置更新的通知走的是另一条事件通道（如 `app-boot/config-reload`、`settings/document-updated`）。只要两件事成立即触发：①武装有副作用且不会自动跟随配置变化；②配置变更只发事件、不重新调用装载路径。

## 根因

把「配置已经读到内存」当成了「配置会自己生效」。装载钩子与配置变更事件是两条不同的通道：钩子只证明**装载那一刻**拿到了配置；要跟着变，必须在事件通道上也挂一次同样的武装动作。缺了这一步，武装就成了一次性的快照。

另有一个容易漏的一半：**只挂在新事件上、不摘掉旧的**，改一次配置就多出一套监听者／定时任务，越改越多。

## 解决

在配置变更事件上重新武装：①先撤销旧武装（clear 定时任务、解绑监听器、清缓存），②再按新配置重新武装。撤销与重建必须成对出现——只重建不撤销，就是「改一次多一份」的来源。

必要边界：武装若有外部副作用（建了会话、写了文件），撤销时要一并清理，否则重建会留下孤儿。

## 规避

写「配置 → 运行时状态」的转换时，先问一句：**这个配置改变时，谁负责把状态改过来？** 答案必须是某条具体的事件订阅，而不是「装载时会读」。另把撤销与重建写成一对，放在同一个函数里，避免只加不减。

## 验证

已观察（2026-11-02 独立复现）：`080b7eb^` 与 `080b7eb` 对照——只发热更事件 `app-boot/config-reload` / `settings/document-updated` 时，修复前 `schedule.create` 调用 0 次，修复后 2 次（每个事件一次，`every_seconds=120`）；把两处 `ctx.on` 摘掉又回到 0 次；不发事件时两版都是 0；修复前补发 `agent/created` 能建 1 会话 + 1 任务，故「0 次」不是夹具失灵。

### 独立复现验证（2026-11-02）

**复现主体与独立性边界**：主控委派的独立子代理（受管辖隔离子代理，上下文不外泄给本候选），模型与主控相同（deepseek-v4.1-flash），派生于同一会话但上下文隔离；按 01 §12.2 读作「同模型 + 上下文隔离」，不是异模型独立验证。

**复现做法**：取 `080b7eb` 与其父提交的插件代码到临时目录，构造最小宿主桩（记录 `schedule.create` 调用次数），分别只发 `app-boot/config-reload`、只发 `settings/document-updated`、两者都不发；再在修复版上摘掉两处 `ctx.on` 复跑；最后补发 `agent/created` 验证桩本身可用。

**观察结果**：修复前发事件 0 次建任务，修复后每个事件各 1 次（合计 2）；摘掉 `ctx.on` 回到 0；不发事件两版都 0；补发 `agent/created` 时修复前也能建出 1 会话 + 1 任务——故 0 次是真实缺陷而非夹具失灵。

**判定**：复现成功。**一处与候选不一致**：候选原「验证」段称「变异测试使『改设置即时生效』用例转红」，但仓库中并无该用例（`080b7eb` 及其测试对 `config-reload` 零引用），当时是基于自建 harness 观测的。

**未覆盖**：真实宿主里「先关后开」的 config 对象变更（Cordis 的 config 不可在运行中改写，只能用事件模拟）；跨进程。

## 影响与适用范围

适用于一切「配置 → 运行时状态」的转换：定时任务、监听器、阈值缓存、开关状态。不适用于纯读取型的配置（每次用都重新读，本来就没有需要更新的状态）。边界：本条只解决「改配置要重新武装」，不解决「多个事件同时触发导致重复武装」——后者是另一类机制，须另行串行化。
