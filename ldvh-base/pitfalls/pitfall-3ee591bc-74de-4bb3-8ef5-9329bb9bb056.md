# 假形状夹具致真缺陷在测试全绿下潜伏

## 症状
修复丢失检测缺陷后，新写的回归用例通过，原有一条旧用例失败。失败点正落在旧用例为 rewind 构造的场景上：它把注入行从批次里移除，期望实现重新注入；而按真实语义修好的实现认得这行仍被台账跟踪，不再重注。表现为「代码改对了、测试却变红」，容易把真缺陷修复误判为自己引入的回归。

## 触发条件
实现的判定依据是状态代理（当前批次里是否可见该行），而配套测试把同一代理固化进夹具：夹具中删掉一行即被当作语义事件发生。宿主真实运行里该形状并不会出现，于是缺陷在测试全绿状态下长期潜伏，直到按真实语义改实现才暴露。

## 根因
形式与语义未一一对应：把「批次里没有行」当成了「发生过 rewind」的证据。权威信号在别处——lifecycle 的 `agent/created` 事件，其 `source ∈ startup|resume|clear|compact` 才是 rewind 与清空的权威判定；批次里有无该行只是这一事件的下游表现，`prime()` 亦在 `agent/created` 时被重新置位。

## 解决
1. 判定主体由「本批次内可见」改为「会话内已跟踪」（台账），使跨轮可见的旧行不再被判为丢失；rewind 恢复路径保留。
2. 把重置挂到 lifecycle：`preStepResetVisibility` 挂到 lifecycle 记录上，`injectedIds` 按需懒初始化，不改动 `preStep` 这一普通对象的结构。
3. 新增一条模拟真实宿主行为的回归用例（上一回合注入的行不会出现在下一回合批次里），并更新旧用例的 rewind 段，改用真实信号而非「从批次里拿掉行」。

## 规避
写夹具前先问一句：这条用例构造的输入形状，真实宿主里真的会发生吗？若不会，绿灯没有意义。遇到「旧用例变红」时，先核对该用例的隐含假设在真实语义下是否成立——成立则问题在新代码，不成立则问题在夹具，改代码去迎合错误夹具只会把缺陷重新固化。凡是靠「某物缺席」推断事件发生过的判定，都应去找该事件的权威信号，而不是用下游表现反推。

## 验证
已观察：完成判定主体改写与夹具更新后，`node --test test/lifecycle.test.mjs` 实测 30 tests / 30 pass / 0 fail（原文所记「31 项」为口径错误，此处按实测更正）。未覆盖：材料在此处截断，全量测试与 lint 的结果未出现在材料中；真实宿主上的运行时行为、以及 clear/compact/resume 各分支的实际回归均无观察记录，故不能声称该缺陷在真实宿主中已被观察到消除。

本条与本批已入档的 pitfall-4f33d264（「以单回合批次近似跨轮可见性致重复注入」）共享同一缺陷与同一修复（提交 2c476bd），其根因段与该条重合，按 specs/23 §18「一个机制一条经验」不独立入档，合并去向为 pitfall-4f33d264-e773-4875-a6fc-d82484c27e33。需说明：「规避」段的测试纪律（夹具形状须符合真实宿主、旧用例变红时先核对其隐含假设）是可独立复用的判据，已在 4f33d264 的「规避」段以「新增此类用例前先确认替身的数据形状与真实宿主一致」承载，本条不另设载体。

## 影响与适用范围
修复以「当前批次里没有该行」为判据的丢失检测时，配套回归用例可能把同一错误判据固化进夹具；适用于任何用状态代理代替权威事件判定的实现及其测试。
