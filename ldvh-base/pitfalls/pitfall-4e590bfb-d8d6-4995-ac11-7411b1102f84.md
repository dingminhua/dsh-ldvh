# 共享工作树上先 add 后提交致稿件被他人提交卷走

## 症状

并行工作线的一笔提交（bf64380）把本会话暂存在索引里的规范改动一并带走了。更糟的是被带走的是**未经修订的 v1 稿**：`specs/24-Research-调研报告.md` §244 里那个后来被独立审核判为虚构的 `fact_type_keys` 参数就是这样进了 HEAD，事后必须再补一笔修正提交（be00f01）才纠正。当时 `git status` 只显示这三个文件「已暂存、未提交」，看不出它们已经随别人的提交落地——症状要等到事后查 `git show --stat` 或审自己的稿件才暴露。

## 触发条件

多个执行体共享同一工作树与同一 Index；本执行体 `git add` 之后**没有立即提交**——在等独立审核、等测试结果或等一个 Human 决定；另一个执行体在这段间隙内执行 `git commit`（按其索引提交，甚至 `git commit -a`）。两者之间没有任何互斥或预约机制。

## 根因

Git Index 是工作树的**单一共享状态**，没有「按执行体分区」的维度：谁执行提交，谁就提交全部已暂存内容。「我 add 了」与「我提交了」之间不存在归属标记，因此并发提交者在间隙里提交任何东西，都会把别人未定稿的暂存一起带走。

本次的具体形状是**吞并**：暂存内容被并入他人提交，而不是被清空。二者的区别很关键——`pitfall-249c129b`（2026-10-19 否决）的否决理由正是「共享索引上的普通提交会吞并他方暂存，不会留下『索引空而复现』」；本条是那条判断的正例，也说明「被清空」不是这类事故的默认形态。

## 解决

**不改写他人提交**：另起一笔修正提交，把被卷走的中间稿改到定稿（be00f01），并在提交消息里写明「上一笔并入的稿件是 v1」，让修正关系在历史里可读。同时核对被卷走的每个文件里是否还有别的未定稿段落——只修被审核指出的那一处，会留下同样性质的残留。

## 规避

在共享工作树上**不要把暂存当草稿区**：

- 要么 `git add` 之后立刻提交，不要跨过等待期；
- 要么在等审核／测试／决定期间，把候选放到独立 worktree 或分支，主工作树保持不暂存；
- `git add` 之前先问一句「这段时间里会有别人提交吗」；
- 提交前用 `git diff --cached --name-only` 逐项对照本笔范围，多出来的路径当场处理，而不是提交后再看。

## 验证

可复算链条，三处都在提交历史里：①`git show --stat bf64380` 列出了不属于该笔目标的 `specs/24-Research-调研报告.md` 与 `specs/26-Friction-摩擦账本.md`；②`git show HEAD:specs/24-Research-调研报告.md | grep fact_type_keys` 命中（虚构参数进了 HEAD）；③修正提交 be00f01 只含四个文件，`friction-writer` 与 `commit-validation` 共 170 项用例通过。另有一条独立旁证：`pitfall-249c129b` 的否决文本已把「吞并」写成正确机制，本条与之一致。

## 影响与适用范围

适用于多个执行体（会话、子代理、并行工作线）共享同一 Git 工作树与同一 Index、且存在「先 git add、后提交」间隙的场景；不适用于独占工作树，或 add 后立即由同一执行体提交且无并发提交者的场景。

边界（据实声明）：本条只解决「如何在共享工作树上避免自己的暂存被卷走」，不解决「已经被卷走的历史如何清理」——后者属提交历史处置，不在本条范围；也不主张给 Git 加锁或改造宿主，那超出本条的已验证范围。
