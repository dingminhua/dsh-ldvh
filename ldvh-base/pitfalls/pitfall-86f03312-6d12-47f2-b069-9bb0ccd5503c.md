# 字段改名后读取侧与契约断言未同步

## 症状
经验（Pitfall）终态卡片的处置说明位置恒显「处置说明缺失。」，而同一条账目在 API 的列表与详情接口都正常带回 `disposition`，字段值完整；同一张卡上「卡体写缺失、另一处状态说明条也写缺失」自相矛盾。

## 触发条件
字段在版本演进中改名——v4 的 `disposition_summary` 被移出字段闭集、v5 改用 `disposition`——而读取侧组件未跟随改名；同时旧键名仍留在 `ObjectItem` 的 v4 兼容声明里，类型检查因此不报错。缺陷只能靠肉眼看卡片发现，无法由任何静态检查拦下。

## 根因
`PitfallTerminalCardContent` 与状态说明条 `getNonActiveReason` 仍按 v4 键名 `disposition_summary` 取值，而写侧与 API 层早已改用 `disposition`，形成读侧与写侧的键名错配。更深一层：契约测试 `pitfall-card-contract.test.ts` 与 `adr-card-contract.test.ts` 用 `assert.match(source, /obj\.disposition_summary\?\.trim\(\)/)` 把「源码读废弃键」写成了断言要求，等于把 bug 钉成契约——谁按规范去修代码，就得先弄绿这条测试，从而被推回去读废弃字段；ADR 卡片本来正确读 `retirement_reason`，是测试断言了错的键。旁证：`doesNotMatch` 的检查窗口过宽，跨进了别的函数。

## 解决
把 `PitfallTerminalCardContent` 与 `getNonActiveReason` 两处的取字段径由 `disposition_summary` 改为 `disposition`；把两条契约测试改为断言 v5 真实字段并加反向守卫，同时把 `doesNotMatch` 的匹配窗口从跨函数收敛到本函数体内。

## 规避
字段改名时按「写入侧 → 读取侧 → 契约测试的源码文本断言」三处同时核对，不依赖类型检查兜底——`tsc` 干净不等于键名正确。契约测试若断言的是源码文本而非行为，须在断言旁标明该键名对应的字段版本，并配一条反向断言防止再钉回废弃键；`doesNotMatch` 类守卫须把匹配窗口限定在被测函数体内。

## 验证
已观察：509 / 509 测试通过，`tsc` 与 `eslint` 干净，产物已按 `/ldvh/` 前缀重建；8 条 discarded 经验在 API 层全部带回 `disposition`，2 条 voided 摩擦的处置原因原本就通；全库检索呈现层残留 v4 键引用为 0 处。未覆盖：刷新后浏览器端卡片的实际呈现未由本轮当场观测，仍待用户确认；`doesNotMatch` 窗口收敛后是否波及别的同类跨函数用例未再复测；ADR 卡片那条断言修正后未单独跑过端到端渲染。

**入档复核（2026-10-19）**：转正前对修复面做了机械核对——`plugin/web/tests/api/pitfall-card-contract.test.ts:20` 已改为 `assert.match(source, /obj\.disposition\?\.trim\(\) \|\| t\('objectList\.dispositionMissing'\)/)`，`:21` 有反向守卫 `assert.doesNotMatch(source, /disposition_summary\?\.trim/)`，与本条「解决」段所述「改为断言 v5 真实字段并加反向守卫」逐条对应；`ObjectList.tsx:735-745` 留有该处曾读 v4 键的说明注释。呈现层残留的 `disposition_summary` 仅见于 `utils/api.ts:183`（`ObjectItem` 的 v4 兼容声明，即本条触发条件所指的「类型检查不报错」来源）与 `i18n/locales.ts` 的文案键，无读值路径。原文「未覆盖」三项（浏览器端实际呈现、`doesNotMatch` 收敛后的波及、ADR 卡片端到端渲染）本轮未复测，维持原样。


**机械化承载（2026-10-28 盘点）**：`plugin/web/tests/api/pitfall-card-contract.test.ts:20-21/35-53`（终态卡与 `getNonActiveReason` 都读 v5 `disposition`、闭集不含 v4 键、全文件 `doesNotMatch(/obj\.disposition_summary/)`）与 `adr-card-contract.test.ts:16-21`（窗口收敛到 `AdrTerminalCardContent` 函数体）已把本条的规避实现为机械判据，它断言读取侧只能用 v5 字段且呈现层不得再消费 v4 键。覆盖边界：只覆盖 `ObjectList.tsx` 的 `disposition`/`disposition_summary` 这一对字段与 ADR 的 `retirement_reason`，未把「写入侧 → 读取侧 → 契约断言」串成一条检查；`plugin/web/src/utils/api.ts:187` 仍保留 v4 兼容声明，类型检查照旧兜不住，别的组件或别的改名没有对应反向断言。

## 影响与适用范围
对象字段跨版本改名而读取侧与契约断言未同步时，终态卡片与状态说明条的取字段径失配会恒显缺失，且类型检查不能兜底。
