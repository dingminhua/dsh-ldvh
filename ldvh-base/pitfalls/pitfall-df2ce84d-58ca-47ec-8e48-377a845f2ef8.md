# dsh-ui 表格 rows 逐行须为数组或对象

## 症状
宿主返回渲染失败（`status=render_failed`、`error=invalid_spec`），逐项指出表格行「must be an array or object」；或 JSON 层面的解析失败（少一个闭合括号）。表现特征是**失败与内容质量无关**：表格语义完全正确、文字无误，仍被判无效并要求整段重发。同一回复里因此反复出现「围栏修复回执 → 重发」的往返。

## 触发条件
向 dsh-ui 围栏写 table 节点时，以下任一情形即触发：
- rows 的某个元素被写成**字符串**（把整行当作一行文本），而非按列给值的数组；
- 行内元素个数与 columns 声明**不一致**（多给一段空串、或少给一列）；
- 围栏 JSON 本身括号/引号不闭合（结构错误在解析阶段就被拦，报的是解析错而非形状错）；
- 同类字段错位：text 节点缺 content、把本应给 table 的字段名写成别的名字。
只要提交动作经过宿主渲染器，上述形态会被逐条校验；不经渲染的纯文本不受影响。

## 根因
宿主渲染器对 table 节点做**形状校验**，判据是「每一行必须是数组或对象」＋「列数与声明一致」。而人在写长表格时容易把表格当成文本块处理——一行一个字符串，视觉上完全正确，语义上却是「一个单元格里塞了整行字」。机制判断属已观察（失败回执逐项列出了 must-be-an-array 的位置）；**未知**：渲染器是否还接受「对象形态的行」（回执写的是 array or object，但本仓只实际观察过数组形态被接受），以及列数不一致时是否一律失败（观察到 3 列给 4 个元素失败，未穷举其余组合）。

## 解决
实际采用的处置是**按错误回执逐项改形状并整段重发**：把每一行改写成数组、逐格填值、对齐列数。成功信号是宿主不再判 invalid_spec、围栏正常渲染。必要边界：这类修复必须是**整段重发**——只补括号或只改一行往往留下其它同型错误，于是再失败一次（本仓观察到连续多轮修复回执即此形态）。

## 规避
提交前按三步核对：
1. 每个 rows 元素是不是**数组**（看见 `"一整行文字"` 这种形态即违规）；
2. 每行元素个数是否等于 columns 的列数（多给的空串也算不一致）；
3. 围栏 JSON 括号与引号是否闭合。
例外：短小的两列表格不易错位，但「不容易错」不等于「不必核对」——本仓多次失败里就有 3 列给 4 个元素的短表。
更省事的做法：**表格优先走渲染前的机械校验**（若所用工具链提供 `validate_dsh_ui` 之类入口则先验一次），把形状错误挡在提交之前，而不是靠宿主回执发现。

## 验证
已观察：本仓多轮会话中，dsh-ui 围栏表格因上述形态被判无效并重发，回执逐项指出行位置与「must be an array or object」；把行改为数组后渲染通过。覆盖范围限于 dsh-ui 围栏的 table 节点与 text 节点字段错位两类。
**未覆盖**：宿主渲染器的完整校验规则（是否接受对象形态的行、列数不一致以外的组合、嵌套表格）；也未在非 dsh-ui 的其它围栏类型上验证过同类形状要求。

## 影响与适用范围
适用于一切向 dsh-ui 围栏提交表格节点的场合：每条 rows 元素必须自身是数组（或对象），按 columns 逐格给值；把整行写成字符串、或行内元素数与 columns 不一致，宿主渲染器即判 invalid_spec 并退回重发。已验证实例：本仓会话中 dsh-ui 围栏表格多次因此被判失败——rows 元素为字符串（items[0].rows[0] 至 rows[7] 全部「must be an array or object」）、行少一个闭合括号、3 列表格每条给 4 个元素、text 节点写成无 content 的形态。边界：渲染器与技能在本仓之外（宿主侧），本条只描述错误形态与识别信号，不描述其内部实现。

何时可能踩到：任何用围栏做结构化呈现、且表格行数或列数较多的回复；一次回复里写多张表时风险更高（同型错误容易在第二、三张表上重犯）。
何时可信：把本条用于**避免形状错误**是可靠的（判据来自宿主回执原文）；把它当作「渲染器规则的完整说明」则不可靠——规则全集不在本仓，本条只覆盖已观察形态。
