# dsh-ui 非白名单组件类型被静默丢弃

## 症状
dsh-ui 围栏里某个节点在交付面上凭空消失：围栏里写下的那个节点没有渲染出来，读者看到的结构比作者写的少一块，而作者收不到任何提示。逐字引证：`{"type":"items","items":[]}` 来源：主控会话 turn 98，assistant 正文第二段 dsh-ui 围栏（gap:12 的那一块）的第一个子节点。特征：失败与内容质量无关、且没有可见回执——机制对、JSON 合法、语义也通，唯一错处是组件名不在白名单里，于是既不报错也不渲染。2026-11-10 实测：前置校验 `validate_dsh_ui` 对同形态 spec 返回 `status=valid`，确实不产生任何类型相关诊断。

## 触发条件
向 dsh-ui 围栏写节点时，把**字段名**当成组件 `type` 写入，或凭印象自造一个不在白名单内的类型名。最常见形态就是把 `list`／`card`／`grid` 的 `items` 数组误写成 `{"type":"items","items":[]}`（写作时把「容器字段」当成了「容器类型」）。只要 `type` 的值不在渲染层白名单内即触发；与同族的行、列形状错误不同，后者会被宿主以 `invalid_spec` 明确拦下并回执，前者连回执都没有。

## 根因
从可观察的行为面看，渲染层对 `type` 按白名单查表：命中就渲染，未命中就把整个节点丢掉继续，不产生错误项（渲染器实现不在本仓，此处只作行为描述，不描述其内部实现）；而写入前的机械校验只校验 JSON 合法性与**已识别组件**的字段形态，遇到未识别的 `type` 时没有可校验的组件，于是按通过处理。两层都不报错，「`items` 被当成组件类型」这一处写作错误因此没有任何机械承载。2026-11-10 在同一宿主的 `validate_dsh_ui` 上实拍：`{"items":[{"type":"items","items":[]}]}` 返回 `status=valid, rendered=1`，与合法的 dsh-ui 围栏（gap:12 的那一块）无法区分；而同一入口对行形状错误返回 `status=invalid, error=invalid_spec, diagnostic="items[0].rows[0] must be an array or object"`。即形状错有回执、类型错无回执，`rendered` 计数也不能反证每个节点都被渲染（单写一个非法节点时同样报 1）。

## 解决
本条没有可修的渲染侧缺陷（白名单与丢弃行为都在宿主侧，本仓改不了），处置是把判据前移到写作侧：dsh-ui 节点的 `type` 只许取白名单里的组件名（text／row／col／grid／card／list／table／keyvalue 等），`items`／`rows`／`columns` 永远是**字段名**，不出现在 `type` 位。据 2026-11-10 实拍定下的口径：不得把 `validate_dsh_ui` 的 `status=valid` 当作「全树已渲染」的证据——未识别的 `type` 正是它放过的一类；见到 valid 之后仍须按正文第二段 dsh-ui 围栏的结构逐节点核对类型名。

## 规避
1. `type` 从白名单取词，不从字段名或自然语言里借词；写容器节点时先把「这里要放 3 条要点」翻译成 `list` + `items` 字段，而不是 `type: items`。
2. 每条围栏发出前回扫所有 `type` 值，重点查三类：`list`（要点在 `items` 里）、`grid`（子节点宽度用 `span`）、`table`（用 `columns` + `rows`）。本条的错误形态就是 `{"type":"items","items":[]}` 这种「字段名当类型」。
3. 不拿「宿主没报错」或 `rendered` 计数当作没丢节点的证据——本条要防的正是静默丢弃。
4. 若交付面上某段结构凭空少了，先查该节点的 `type` 拼写，再怀疑内容或权限。
例外：`text`／`row` 这类高频类型很少写错；但一旦错在容器节点上，丢的是整段结构，代价比形状错误高——形状错误至少会收到回执。

## 验证
已观察：主控会话 turn 98 的 dsh-ui 围栏（gap:12 的那一块）第一个子节点写作 `{"type":"items","items":[]}`，渲染层不认该类型，节点被丢弃；该条材料里没有任何来自宿主的拒绝或重发记录。逐字引证：`{"type":"items","items":[]}` 来源：主控会话 turn 98，assistant 正文第二段 dsh-ui 围栏（gap:12 的那一块）的第一个子节点。
2026-11-10 本仓复测（当前宿主工具面）：同形态 spec 交 `validate_dsh_ui` 得 `status=valid, rendered=1`，无任何类型相关诊断；同一入口对 `{"type":"table","columns":["a","b"],"rows":["整行文字",["1"]]}` 得 `status=invalid, error=invalid_spec, diagnostic="items[0].rows[0] must be an array or object"`。两者对照确认了「类型错无回执、形状错有回执」这一分工。
未覆盖：白名单的完整组件清单未逐项验证（本条只以 list／row／table 等已知项作参照）；宿主是否在日志或别的错误面留下该次丢弃的痕迹未查；同一会话中是否还有其它被丢弃的节点未统计。

## 影响与适用范围
适用于一切手写 dsh-ui 围栏（含 `render_ui`）的场合：节点的 `type` 必须是渲染层白名单内的组件名，`items`／`rows`／`columns` 这类字段名不得上移成类型名；已验证错误形态是 dsh-ui 围栏（gap:12 的那一块）里把 `items` 写成 `type`，该节点被静默丢弃。边界：白名单本体与渲染层的丢弃行为都在宿主侧（本仓之外），本条只描述错误形态、识别信号与可执行的自查步骤，不描述其内部实现。
何时可能踩到：一条回复里分段写多个容器节点、或从自然语言结构（「几条要点」「一个网格」）直接映射成节点时，最容易把字段名借成类型名。
何时可信：把本条用于**避免静默丢节点**是可靠的（判据来自缓冲引证与本次实拍）；把它当作「渲染层白名单的完整说明」则不可靠——清单不在本仓，本条只覆盖已观察形态。
