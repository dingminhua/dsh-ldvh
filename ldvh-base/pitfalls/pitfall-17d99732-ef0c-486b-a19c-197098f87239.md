# npm 2FA 回调 E403 发布未落地须重走确认

## 症状

执行 `npm publish` 发布 dsh-ldvh@2.0.1 时，CLI 先打印 2FA 认证链接（authId=04728580-8132-404c-af02-576f11833d50），浏览器完成确认后 CLI 报错：

```
npm error code E403
npm error 403 403 Forbidden - GET https://registry.npmjs.org/-/v1/done?authId=***
npm error 403 In most cases, you or one of your dependencies are requesting a package version that is forbidden by your security policy, or on a server you do not have access to.
```

表面像是「包被安全策略禁止/权限不足」，实际发生在 2FA 浏览器确认的回调阶段（`/-/v1/done`），发布事务并未落地。

## 触发条件

- 账号已启用浏览器 2FA 确认的 `npm publish` 流程。
- 浏览器侧的确认动作与 CLI 等待的回调之间出现时序/会话态不一致（确认页停留过久、页面被刷新或重新打开、回调令牌已失效等）。
- 出现于 2026-11-26 发布 dsh-ldvh 2.0.1 的现场，错误 URL 明确指向 `/-/v1/done?authId=...`。

## 根因

确切根因未证实，候选为「确认页超时」「浏览器会话态失效」「回调令牌失效」三者之一——素材未提供可判定的证据，不作确定断言。

可回指确认的只有边界事实：该 403 发生在 2FA 浏览器确认的回调阶段，早于发布事务落地。registry 侧三路查证均显示发布未发生。

## 解决

1. 先三路查证发布是否落地（不要凭错误文案判断）：
   - dist-tags 缓存穿透端点：`curl -s https://registry.npmjs.org/-/package/dsh-ldvh/dist-tags?a=<ts>`，`latest` 仍为 2.0.0。
   - 版本端点：`curl -s -o /dev/null -w '%{http_code}' https://registry.npmjs.org/dsh-ldvh/2.0.1`，返回 404。
   - packument 版本列表：`curl -s https://registry.npmjs.org/dsh-ldvh | jq -r '.versions|keys[]' | tail`，尾部止于 2.0.0，无 2.0.1。
2. 三态一致 → 判定发布未落地：registry 无该版本、无 dist-tags 变化，无需回滚，也无需 unpublish。
3. 重新完整走一遍 `npm publish`：生成新的 authId（本次为 0f8fd683-…）与新的浏览器确认页，打开后即时确认，输出 `+ dsh-ldvh@2.0.1` 即成功。
4. 旧确认链接一律不复用（旧 authId 的回调已被消费/失效，复用只会再次失败）。

## 规避

- 浏览器 2FA 确认页打开后立即确认，不要挂着等、不要刷新或重开确认页。
- 一次 publish 一次确认，失败后重新发起完整 publish 取新 authId，而不是反复点旧链接或重复点击原确认页。
- 见到 E403 不要先改包内容、权限或 2FA 设置——先做 registry 三态查证定位阶段。

## 验证

- 成功判据：CLI 输出 `+ dsh-ldvh@2.0.1`，且 registry `latest` dist-tag 与版本端点均指向 2.0.1。
- 未落地判据（本次现场）：dist-tags `latest` = 2.0.0、`/dsh-ldvh/2.0.1` 返回 404、packument 版本列表尾部为 2.0.0。
- 本地状态判据：发布树与 dev 树在事故全程零改动，E403 不污染本地状态，翻号/tag/门禁无需重做。

## 影响与适用范围

任何使用 npm publish 且账号启用浏览器 2FA 确认的发布流程，当 CLI 报 E403 且错误 URL 指向 /-/v1/done 回调端点时；不适用于 npm 422/402/404 等其他码、或错误来自包内容校验/依赖策略的场合（那些需另查）。
