# 版本门禁取首个数字标题与规范不同义

## 症状

主控按 Human 裁定为 1.1.5 补正式条目后，受控提交前的 dev 态门禁立即失败，`node plugin/scripts/require-version-consistency.mjs --release` 报 `版本不一致：1.1.5 / 1.1.5-dev.1`，exit=1；而五处声明点的版本号本身并无笔误，失败只随条目的位置出现与消失。逐字引证：

```
版本不一致：1.1.5 / 1.1.5-dev.1
来源：主控受控提交前实测 require-version-consistency.mjs --release 的 exit=1 输出
```

识别信号：CHANGELOG 中同时存在 dev 轮次条目与正式条目，且正式条目被放在 dev 条目之前（`## [Unreleased]` 之后）时 dev 门禁转红；把正式条目移回 dev 条目之下即恢复 exit=0，期间没有改动任何版本号。

## 触发条件

同时满足：① 处于 dev 态（`plugin/package.json` 的 `version` 含 `-dev.`）；② `plugin/CHANGELOG.md` 同时存在正式条目与 dev 轮次条目；③ 按规范文字「最新正式条目」的理解，把新正式条目插到 `## [Unreleased]` 之后、dev 条目之前这一看似更合理的位置；④ 用该脚本（或 prepack 挂载的同脚本）判定门禁结果。

## 根因

机械判据与所声称执行的规范判据不同义。脚本取的是**第一个匹配的数字标题**，且正则允许可选的预发布后缀，故 dev 条目同样命中；规范写的却是**最新正式条目**。逐字引证（源：`plugin/scripts/require-version-consistency.mjs:5`）：

```
const CHANGELOG_FIRST = /^## \[(\d+\.\d+\.\d+(?:-[\w.]+)?)\]/m;
```

配合 `plugin/scripts/require-version-consistency.mjs:28-30` 的 `text.match(CHANGELOG_FIRST)`——`match` 无 `g` 标志时返回文本中首个匹配，于是「CHANGELOG 的版本」实为首个数字标题，而非规范所说的最新正式条目。

逐字引证（源：`ldvh-base/norms/norm-80c95693-660b-4381-b67c-6741d6d3a6d3.md` 门禁 7 正文，第 108 行）：

```
发布前由 `node scripts/require-version-consistency.mjs --release`（或 pack 时 prepack 自动）核对五处：CHANGELOG 最新正式条目、`plugin/package.json`、`plugin/README.md`、根 `README.md`、根 `package.json` 版本全部存在且一致
```

独立审核代理亦指出该点，原话：「门禁 7 的机械面比规范文字窄——脚本只校验『首个数字标题』而非『最新正式条目』，与 norm 第 108 行文字不一致」，判为 MINOR 披露、非本轮引入。因此这是机械面与规范面的长期背离，而不是本轮新引入的缺陷；位置约束是脚本行为派生的隐含条件，规范读者不会预期。

## 解决

已采用的处置是调整条目位置而非改脚本：把 `## [1.1.5] — 2026-11-24` 移到 `## [1.1.5-dev.1] — 2026-11-24` 之下，使首个数字标题回到 dev 版本，dev 门禁恢复 exit=0（读数：4 处一致 — 1.1.5-dev.1）。未改脚本、未改规范。该处置与仓库既有惯例一致：`## [1.1.4-dev.1]` 本就位于 `## [1.1.4]` 之上。必要边界：本条只记录了「按位置迁就判据」这一路处置，机械面与规范文字的对齐未做，背离仍然存在。

## 规避

1. 核对条件：在 dev 工作树补正式条目时，先确认 `plugin/CHANGELOG.md` 的**首个数字标题**是否仍等于 `plugin/package.json` 的 dev 版本；dev 条目在上、正式条目在下的既有惯例即为此服务的排序约定。
2. 动作：门禁转红且报出形如「正式版本 / dev 版本」的两值不一致时，先核条目顺序与首个数字标题，再怀疑版本号写错——两值都正确而顺序不同正是本条形态。
3. 动作：若确实要按规范文字「最新正式条目」调整顺序（或删除 dev 条目），须先确认脚本判据，或同步修脚本／规范并经 Human Gate；仅按规范文字改 CHANGELOG 位置会触发假失败。
4. 例外：release 态下首个数字标题应为发布版本，此时「首个数字标题」与「最新正式条目」同义，本条的位置约束不生效。

## 验证

两次实测对照：错误位置（正式条目在 dev 条目之上）→ dev 门禁 exit=1，输出 `版本不一致：1.1.5 / 1.1.5-dev.1`；调整位置后 → exit=0，`4 处一致 — 1.1.5-dev.1`。判据来源经直接读取脚本核对：`plugin/scripts/require-version-consistency.mjs:5` 的正则允许 `(?:-[\w.]+)?` 预发布后缀，`:26-30` 的 `versionsIn` 对 `plugin/CHANGELOG.md` 走 `text.match(CHANGELOG_FIRST)`，即首个匹配。规范侧经直接读取 `ldvh-base/norms/norm-80c95693-660b-4381-b67c-6741d6d3a6d3.md:108` 核对「最新正式条目」文字。

未覆盖：release 态另因本工作树无根 `package.json` 而失败，属既有 dev 态允许缺失，不属本条机制；脚本与规范的对齐未做，故本条只证明背离存在与位置效应可复现，不证明任何一方是错的判据来源。

## 影响与适用范围

适用于在 dev 工作树中维护 `plugin/CHANGELOG.md` 正式条目与 dev 轮次条目顺序、或依据 `plugin/scripts/require-version-consistency.mjs` 的输出判断门禁结果的场合：脚本判据是「首个匹配的数字标题」（dev 条目亦命中），规范文字是「最新正式条目」，二者不同义，按规范文字补正式条目可能因插入位置触发门禁假失败。本条不覆盖 release 态根 `package.json` 缺失等其它门禁失败原因。

何时可能踩到：dev 期内既要为已发布版本补正式条目、又要在其之上维护新的 dev 轮次条目时（rc／热修／同日连续发版的 dev 工作树即该形态）；此时「按规范文字放到最新处」与「按脚本判据放到 dev 条目之下」指向相反的位置。何时可信：只要脚本仍以首个数字标题为 CHANGELOG 判据、而规范仍写「最新正式条目」，本条即适用；release 态下两者同义，位置风险消失。判断门禁失败原因时，本条与「版本号真的写错」「声明点缺失」并列，须先区分再处置。
