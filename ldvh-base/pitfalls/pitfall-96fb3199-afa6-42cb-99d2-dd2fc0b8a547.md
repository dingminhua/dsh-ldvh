# 首行比较式校验漏掉多余H1

## 症状

对 Markdown 正文做「首个标题行必须等于 `# <title>`」式的结构校验时，**只比较首个非空行**会把两件事同时判错：

1. **漏检（逃逸）**：正文里多出一个标题行时校验通过。实测三种形式——`# T` 紧跟首行之后、夹在正文小节中间、放在文件末尾——全部被放行，于是写入器再补一个 H1，载体落盘后出现**两个 H1**。
2. **误报（拒绝合法载体）**：合法但写法略有差异的单个 H1 反被拒绝。实测三种——H1 带尾随空格 `# T   `、H1 缩进 1–3 空格、正文含 CRLF 换行——全部被判为「首个标题不符」。

识别信号：校验函数里出现 `lines.find(...)` 取首个非空行后与模板字符串**完全相等**比较；或对标题行的判断使用 `startsWith("# ")` 这类固定前缀匹配。

## 触发条件

- 结构校验以「首个非空行 == 模板」代替「统计各级标题数量」时；
- 标题的合法写法存在多种等价形式（CommonMark 的 ATX 标题允许 0–3 个前导空格、可用 tab 作为分隔、允许尾随空格）时；
- 正文可能包含代码围栏，而围栏内部的 `#` 行是字面内容而非标题时；
- 载体经由不同平台/工具读写，行尾可能为 CRLF 时。

组合条件：**校验只看第一个匹配**，同时**被判定的对象存在多种合法写法**——两者同时成立即触发。

## 根因

校验的**判定单位选错了**：把「标题结构是否正确」这一**集合性质**（一级标题恰好一个、二级标题序列固定）降级为**单点性质**（第一行长什么样）。

单点比较隐含一个假设——「合法输入只有一种字面写法」。一旦输入存在等价变体（缩进、tab、尾随空格、行尾差异），该假设不成立，于是：

- 变体写法被判为不符 → **误报**；
- 而单点比较天然看不见「后面还有没有第二个标题」 → **漏检**。

`startsWith("# ")` 型匹配是同一根因的另一形态：它把「是 ATX 标题」近似为「以 `# ` 开头」，既不覆盖 `#\t`、缩进写法，也不排除代码围栏内的字面 `#`。

补充观察：`#标题`（井号后无空格）在 CommonMark 下**不是**标题，`startsWith("# ")` 恰好不把它计入——这是**碰巧正确**而非设计正确，不能据此认为该匹配方式可用。

## 解决

把判定单位从「首个非空行」改为「按语法统计目标层级的标题数量」，并对合法变体做归一化后再比较。

已实际采用（`plugin/lib/spark-writer.js` 与 `plugin/lib/pitfall-writer.js` 的 `validateSparkBodyStructure` / `validatePitfallBodyStructure`）：

1. 新增 `countAtxHeadings(body, level)`：行尾先归一（`\r\n?` → `\n`），逐行按 `^ {0,3}#{level}(?!#)[ \t]` 匹配（≤3 前导空格、井号后须有空格或 tab、容忍尾随空格），并**跳过 fenced code block**（``` 或 ~~~ 配对，围栏内的行不计）；
2. 校验条件改为 `countAtxHeadings(body, 1) === 1`，不再只比较首行；
3. 首行比较保留，但先归一化再比：`trimEnd()` + 去前导 ≤3 空格 + 把井号后的连续空白折叠为单个空格，从而容忍合法写法。

成功信号：9 种情形全部判定正确——正常单 H1 与三种合法变体（尾随空格/缩进/CRLF）通过；三种多余 H1 形式（连续/中间/末尾）与两种变体多余 H1（缩进、tab 分隔）以及标题不符被拒。

必要边界：该实现只覆盖 ATX 标题与 fenced code block；setext 标题（下划线式）与行内代码中的 `#` 未处理。若正文格式扩展到这些形态，需同步扩展而非假定已覆盖。

## 规避

**核对条件**（写结构校验时逐条自问）：

1. 被校验对象的合法写法是否**唯一**？存在等价变体（空白、缩进、行尾、大小写）时必须先归一化。
2. 要判定的是**集合性质**还是单点性质？集合性质（「恰好一个」「序列固定」）必须用计数或逐项比对，不得用「第一项长什么样」代替。
3. 被扫的文本中是否存在**该符号作为字面量**的语境（代码围栏、行内代码、HTML 注释）？存在时必须先排除。

**动作**：对「数量/唯一性」类约束，写一个显式的计数函数并在测试中列出**逃逸形式**（多余项的各种合法写法）与**误报形式**（单项的各种合法写法）两组反例。

**例外**：若载体格式由本仓库写入器独占生成、且生成逻辑保证只有一种写法（如本例中写入器固定输出 `# <title>`），则归一化可以简化；但**漏检方向（多余项）仍必须用计数覆盖**，因为它不依赖输入的写法差异。此例外须在代码注释中写明前提，前提变化时重审。

## 验证

已观察（2026-09-13，本仓库）：

- 修复前实测：`# T` 连续重复、夹在中间、置于末尾三种形式，`validateSparkBodyStructure` 与 `validatePitfallBodyStructure` 均返回 `ok: true`（漏检）；尾随空格、CRLF、围栏内的 `#` 均返回 `ok: false`（误报）；缩进与 tab 形式的多余 H1 返回 `ok: true`（漏检）。
- 修复后实测：9 种情形（4 通过 / 5 拒绝）全部符合预期，两个 writer 行为一致。
- 回归：`plugin/test/*.test.mjs` 726 项全部通过；新增 H1 唯一性与 CommonMark 边界测试 4 项。

未覆盖：setext 标题形态、行内代码中的 `#`、HTML 注释中的 `#`（代理审核时指出注释内 `#` 亦为误报，本次未处理——因当前载体不含该形态）；CRLF 采取「容忍」而非「改写」策略时的长期一致性未经实测。

## 影响与适用范围

对 Markdown 正文做结构校验的场合——特别是以「首个匹配项 == 模板」实现标题层级/数量或段落序列校验时的漏检与误报。已验证实例：plugin/lib/spark-writer.js 与 plugin/lib/pitfall-writer.js 的正文结构校验。

具体而言：任何以「首个匹配项 == 模板」实现的结构校验；任何用固定前缀（`startsWith("# ")`、正则 `^#\s`）近似判断 Markdown 语法结构的实现。

何时可能踩到：新增或修改事实类型的正文结构校验时；把校验从「规范载体」复制到「事实对象载体」时（前者写法受控、后者由多入口写入）；引入新的 Markdown 语法特性（围栏、表格、setext）时。

何时可信：本经验的机制判断（判定单位选错导致漏检+误报）在 Markdown 与 CommonMark 语义范围内稳定成立；但具体到其它实现，是否同样存在逃逸需按「规避」的三条核对条件逐条核对，不得仅凭症状相似即认定同因。
