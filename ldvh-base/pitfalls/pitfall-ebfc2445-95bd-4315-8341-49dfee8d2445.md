# 静默计时器按固定时长武装致过期即静默不派发

## 症状

闲时派发在宿主重启后表现为「不再派发」：一个会话沉默越久越不会触发，旧版出现「等满 300 秒之后仍无动静」；宿主启动后长时间无任何派发记录。

## 触发条件

宿主进程重启后已存在一段安静时长（例如宿主在会话沉默期间启动），此后该会话不再产生新活动，且派发触发依赖按固定 `idleMs` 武装的静默计时器。

## 根因

`armSilenceTimer` 用固定 `idleMs` 武装，不考虑启动前已经过去的安静时长，因此计时器到期时刻远早于真正的空闲阈值；计时器到期早退时既不重新武装、也不留痕。于是触发条件永不再被满足——沉默时长与不派发呈正相关，表现为「越沉默越不触发」。

## 解决

**仍成立的部分**：改为按**剩余量**武装（即 `idleMs` 减去已经过去的安静时长），并在到期早退分支逐一**留痕**。提交为 `8955e2a`（fix(triggers)）。

**关于「重新武装」的更正（2026-10-27，独立审核实测）**：本文原写「早退的四个分支中全部记录日志后重新武装」，**与代码不符**。逐一核对现状：`disposed`、`turn-in-flight`、`no-activity-anchor`、`not-governed` 四个早退分支**都只留痕、不重武装**；**只有** `not-quiet-enough`（时钟与事件的残余交错，起点未变、只是还没够静）会重武装。这个分工是正确的，不是遗漏：前四种情形要么对象已销毁、要么回合正在进行、要么本就无锚点、要么已不受管辖，对它们重武装会制造一个不该存在的计时。**故「留痕」是普遍要求，「重武装」只属于 `not-quiet-enough`**；其余情形由**下一回合结束**或**新活动**重新起算。

**已废止的部分（2026-10-27 纪律反转，Human 决定）**：同一次提交还让 `restoreActivityAt` 在恢复活动锚点后**立即武装**，即装载时按持久化活动时刻「重建」安静期。**该做法已整体废除**：`restoreActivityAt` 已删除，装载路径不再读回活动时刻、不再建计时器，**一次延迟形态的计时只有一个起点——回合结束**（specs/11 §6.1「重启使安静期作废」段）。

废除的理由（与原修复并不矛盾，而是原修复漏看了一半）：原修复只看到「不武装 → 永不触发」，没看到「武装后这段安静期**仍是同一段**」。旧锚点的剩余量恒为 0，于是每一次插件重载、每一次**重新打开一个旧对话**，都在**同一个已经结束的安静期**上再触发一次——直接违反 specs/11 §6.1「一次触发完成后该形态的本次计时即告结束，不得在同一目标时刻上反复触发」。实测（2026-10-26 23:44 与 2026-10-27 全天）运行痕迹里 `quietFor` 出现 44.3／46.4／66.1／69.7／153.2／165.9 小时（安静时长仅 5 分钟），单日派发执行体会话数十个，多数只产生 ≤1 次工具调用。**正确形态是：重启使该安静期作废，等新回合结束再起算**——代价（重启窗口内一次都不到期）按 §6.1 如实登记。

## 规避

以静默计时器判定空闲时，武装值必须由「阈值 − 已过安静时长」得出，而非固定阈值本身；任何到期早退分支都须留痕；`not-quiet-enough` 之外的重武装须有明确理由，否则沉默时长会与触发条件反向耦合。

**新增一条（2026-10-27）**：**不要用「恢复持久化状态」来补偿计时器随进程消失这件事**。进程内计时器的消失意味着那段时间**不存在**，不等于「应当补算」；把跨进程的安静期读回来重建，会使一个已花掉的时机变成待触发的时机，从而在原目标时刻上重复触发。若确需跨重启的语义，须重新论证它是否与「一次触发后计时即结束」相容，而不是直接读回时间戳。

**另注意「变通等价」**：不建计时器、只把持久化锚点**预置**进内存，在「宿主装载后报一次 idle」时会得到同样的重复触发——这种形态比恢复方法更隐蔽（没有第二个武装入口可查）。判据须落在「装载后有没有派发」上，不能只查「有没有计时器」。

## 验证

**原验证（记录历史，已被推翻的部分须一并读）**：宿主 13:35:02 启动 → 13:35:03 即派发；13:58:55 启动 → 13:58:56 即派发。**这两条当时被当作「修复生效」的证据，现在恰恰是缺陷的症状**——冷启动后秒级派发意味着装载时把旧安静期读回来并立即触发了。

**现验证（2026-10-27）**：`plugin/test/triggers-idle.test.mjs`「装载不重建计时」与「重启后只有新回合结束才能重新起算并派发」两例；`plugin/test/lifecycle-checkpoint-path.test.mjs`「装载后收到 idle **不得**用持久化旧锚点派发」一例（封「预置活动时刻」变通），另三条重启用例已改为由**回合结束**起算。独立审核对上述用例做过破坏性验证：把恢复方法同名加回 → 变红；删掉 `turn/end` 的武装 → 变红；**改名后只预置锚点不武装 → 首版全绿**，该缺口已由新增用例封住。已观察：相关文件各自全绿、全量回归零新增失败。未覆盖：真实宿主重启后的长时行为（须待下一次宿主重载后按运行痕迹复核 `quietFor` 分布是否不再出现小时级数值）。

独立复现验证（2026-10-28，入档前置）：复现主体为隔离子代理（独立上下文 session 59751938-eb68-42da-a4ee-f2102f9fd730），未参与本候选形成；独立性边界为与形成者同模型（dsh-opencode-go/deepseek-v4.1-flash）、上下文隔离。复现做法：核对提交 `8955e2a` 的 diff（剩余量武装 + 逐分支留痕）；逐分支读 HEAD `plugin/lib/triggers.js`；在 /tmp 副本删去 `turn/end` 的 `armSilenceTimer()` 后跑 `triggers-idle.test.mjs` 与 `lifecycle-checkpoint-path.test.mjs`；查运行痕迹中的 `quietFor` 分布。

观察结果：`triggers-idle` 34/34、`lifecycle-checkpoint-path` 7/7 通过；删去 `turn/end` 武装后 `triggers-idle` 变 32 通过 / 2 失败，红的正是「按结束时刻重新武装」与「重启后只有新回合结束才能起算」两例，用例具可分辨力；`plugin/lib/triggers.js` 已无 `restoreActivityAt`，装载路径不建计时；归档运行痕迹中确有 `quietFor` 32.3h／14.7h 的历史值，当前 runlog 最近 12 条 dispatching 的 `quietFor` 均为 300000±6ms。复现未覆盖：候选所引 44.3／46.4／66.1／69.7／153.2／165.9 小时未逐字复现（同族现象已见，原文数值在 specs/11 §6.1）；真实宿主重启后的长时行为本次窗口未发生；「把恢复方法同名加回」的破坏性验证未重做。


**机械化承载（2026-10-28 盘点）**：`plugin/test/triggers-idle.test.mjs` 与 `plugin/test/lifecycle-checkpoint-path.test.mjs` 已把本条的规避实现为机械判据：剩余量武装（改成固定时长即转红）、装载不重建计时（断言 `restoreActivityAt` 接口不存在）、重启后只有新回合结束才能起算（删掉 `turn/end` 武装即两例转红）、装载后收到 idle 不得用持久化旧锚点派发（封「预置活动时刻」变通）。覆盖边界：「任何到期早退分支都须留痕」只对 `not-quiet-enough` 一条分支有断言——把其余四条（`disposed` / `turn-in-flight` / `no-activity-anchor` / `not-governed`）的 trace 删掉后 41 例全绿；「其余四条不得重武装」同样无用例（把 `turn-in-flight` 分支改成重武装仍全绿）。

## 影响与适用范围

idle 派发链路（`armSilenceTimer` 武装与到期早退分支）与任何以「按固定时长武装的静默计时器 + 无重新武装」为结构的同类实现；不影响派发准入的原子性判定。（**2026-10-27 收窄**：原文范围含「`restoreActivityAt` 恢复锚点」，该函数已删除，见「解决」与「验证」段的纪律反转登记。）
