# 共享工作树全绿被读作提交绿致假绿

## 症状

提交前在共享工作树上跑全量测试，读数全绿，于是把该绿读作「这次提交是绿的」。事后在隔离检出（提交树）上复跑同一批测试，出现红色读数：工作树的绿与提交树的绿并不等价，全绿掩盖的恰是提交物本身的缺陷。

## 触发条件

- 多人共享同一 Git 工作树：工作树内容 = 本会话改动 + 他人会话尚未提交的改动；提交树只含本会话已提交的内容，二者不等价。
- 提交前的验证动作在共享工作树上执行（即默认在主工作树里跑测试），读数被直接赋予「提交可交付」的含义。
- 另一会话在工作树里留有一份未提交的修复：工作树会绿，提交树仍然红。

## 根因

验证动作的读数对象与读数的被赋予对象不是同一件事：跑测的是「工作树当前状态」，被验证的却是「这次提交的提交树状态」。在共享工作树下这两者之间存在他人在途的未提交改动，二者的差异不被任何环节检查，于是「工作树全量测试绿」被默认读作「提交树全量测试绿」，形成假绿。

同源关系：与 pitfall-70ad6ff5「验证命令沿用主仓工作目录致 worktree 改动漏检」同根——两者都是「命令从哪棵树跑」与「要验哪份代码」被当成一件事；与 pitfall-c1f6defc「共享工作树整树切换做单变量对照致对照污染」同根——共享工作树使对照两侧不可比。但上述两条的适用范围各自限死在自身场景（改动在 worktree 内／用整树切换做基线），不覆盖「被验对象是一次提交、验证跑在含他人在途未提交改动的共享工作树」这一形态，故另立一条。

## 解决

提交后用 `git worktree add --detach <临时目录> <提交标识>` 隔离检出该提交，在该检出内跑全量测试，使读数对应被验对象（提交树）。

成功信号：隔离检出的提交树上同一用例转红，且 HEAD~1 同样转红——据此判定为既有红、红因不在本次提交；主工作树绿不构成反证。

必要边界：本次只做到「发现红」，未做到「把修复并入提交」。

## 规避

- 共享工作树上「工作树全量测试绿」不得单独作为「提交可交付」的证据。
- 凡提交触及受管载体（ldvh-base/ 事实对象、specs/ 规范源），须在隔离检出的提交树上复核。
- 若不做隔离检出，至少核对「工作树与提交树的差异面」是否只含被验改动。

## 验证

2026-11-19 本轮实测：

1. 本轮完成一个受控提交（提交标识 afc61a95）后，为核实「提交树本身是绿的」，用 `git worktree add --detach /tmp/ldvh-verify HEAD` 隔离检出该提交，在其中跑 `node scripts/run-tests.mjs`：结果为 tests 2412 / fail 3，其中 `plugin/test/source-recall.test.mjs` 的用例「recallForAction：经验（Pitfall）能被召回到」报「经验应被召回到，实际 facts=5」。
2. 对照：在同一隔离检出里切到 HEAD~1（本次提交之前）跑同一测试文件，同样失败。故该失败先于本次提交存在，不是本次改动引入。
3. 同一时刻主工作树跑全量为 tests 2435 / fail 0，同一条召回用例通过。
4. 差异定位：另一会话未提交的 `plugin/test/source-recall.test.mjs` 改动给该次召回加了 `excludeTypes: INJECTION_EXCLUDED_TYPES`；把主工作树该文件同步进隔离检出后，该用例转绿。即：主树的绿来自这份未提交的修复，提交树本身是红的。
5. 未覆盖／未知：本次未在两个真实并发会话下复现；隔离检出的依赖是用符号链接补齐 node_modules 的；隔离检出中未跟踪文件不存在，故测试条数比主工作树少 23 项（未跟踪文件不在检出内），这一差异与该失败无关。

## 影响与适用范围

凡在多人共享同一 Git 工作树下，把「提交前在共享工作树上跑全量测试全绿」当作「该提交可交付」证据的提交与验证场景均适用；本条可信的边界是读数与被验对象（提交树）是否同一份代码，而非测试本身是否通过。

具体地说，凡涉及受管载体（ldvh-base/ 事实对象、specs/ 规范源）的受控提交、需要在提交后给出「本次提交是绿的」这一结论的验证与汇报，以及任何把工作树读数直接当作提交质量读数的场合，均落入本条范围。独占工作树、或验证确实跑在隔离检出的提交树上的场景，本条前提消失。
