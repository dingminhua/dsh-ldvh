# 受控操作拒绝路径先删Hook后校验

## 症状
unregisterProject 在三条校验尚未判定前就删除了该项目的 Git Gate Hook，于是被拒绝返回失败时，项目仍登记在册、仍被报告为受管辖，而实际提交已不再过门禁——一条缺关键变更节的非法提交直接通过。
识别信号：拒绝返回与「受管辖」状态报告彼此矛盾——被拒绝的操作却仍在册，却已无门禁，即失败操作留下了已生效的状态变更。
逐字引证（来源：主控会话材料 turn 6 的助手回复（2026-10-31T06:07:05+08:00 起的那一轮，关于 unregisterProject 注销链路的段落）；对应行为在 plugin 侧的 Git Gate 注销/校验路径上）：
这是个真实缺陷：拒绝路径先删 Hook、后校验，与工具层返回的 `completed: []` 契约直接矛盾。

## 触发条件
受控操作的拒绝路径上，副作用的发生早于准入校验的判定：注销类操作先执行状态性副作用（摘除该项目的 Git Gate Hook），再逐条做校验；校验拒绝时没有任何回滚补偿动作。
上下文条件：Git Gate Hook 是提交门禁的唯一挂载点，摘除本身即生效，不因后续校验结论回滚。

## 根因
副作用与准入校验的先后次序不由任何构造保证——「拒绝无副作用」只是期待，不是被构造出来的性质。
已观察：材料明确认定拒绝路径「先删 Hook、后校验」（见症状段逐字引证）。
已观察：该次序与工具层返回 `completed: []` 的契约直接矛盾——被拒绝的操作声称没有任何已完成项，而删除事实上已经发生。
已观察（2026-11-02 复现补充）：缺陷当时没有任何失败路径补偿回滚——被拒绝后 Hook 就是 absent，只有修正次序才能消除该状态。

## 解决
把准入校验置于副作用之前：三条校验全部通过之后才执行 Hook 注销与项目除名；校验拒绝时立即返回失败，不产生任何状态变更。
做法：由「先删 Hook、后校验」改为「先校验、后删 Hook」，使拒绝路径成为 `completed: []` 的构造性结果，而非靠失败路径回滚补偿出来的巧合。
成功信号：拒绝时返回失败、`completed: []`、Git Gate Hook 仍在、项目仍受管辖且提交仍过门禁；接受时项目除名与 Hook 注销各发生一次。
必要边界：修复已由提交 a2dafe7（2026-10-31 06:11）落地，并带守卫用例（见「验证」段）；本条能引用的是该次序修正本身，不是对全部受控操作的普查。

## 规避
核对条件：受控操作中凡同时具备「状态性副作用」（删除钩子、除名、登记变更）与「准入校验」者，核对副作用是否位于校验之后。
动作：校验前置；拒绝路径返回 `completed: []` 且不改动任何状态；不得以「拒绝路径再补偿回滚」替代次序上的构造。
例外：若副作用本身是校验判据的输入（例如必须先摘钩才能读到被校验的状态），须在该操作上显式标注例外并说明为何拒绝仍无实质副作用，否则按本段处理。

## 验证
已观察：来源材料明确认定「这是个真实缺陷」，并指出其与工具层返回的 `completed: []` 契约直接矛盾；已观察到一次实际后果——一条缺关键变更节的非法提交直接通过门禁。
已观察：被拒绝后项目仍登记在册、仍被报告为受管辖，与「已无门禁」的实况并存。
已观察：修复 a2dafe7 之后，拒绝后 `hook state after refusal: managed`，守卫用例 `plugin/test/governed-projects.test.mjs:537`「leaves the Hook installed when it refuses」常绿。
未覆盖：其它受控操作是否同属该次序问题未普查；该非法提交与该项目的登记状态事后是否已被修复未追溯。
逐字引证来源标识：主控会话材料 turn 6 的助手回复（2026-10-31T06:07:05+08:00 起的那一轮，关于 unregisterProject 注销链路的段落），会话 session-e3289243-ba23-4726-992f-9e021c0ee416。

### 独立复现验证（2026-11-02）

**复现主体与独立性边界**：主控委派的独立子代理（受管辖隔离子代理，上下文不外泄给本候选），模型与主控相同（deepseek-v4.1-flash），派生于同一会话但上下文隔离；按 01 §12.2 读作「同模型 + 上下文隔离」，不是异模型独立验证。

**复现做法**：取当前 HEAD 的 `plugin/lib` 到临时目录，另做一份**缺陷副本**——把 `removeManagedHook` 挪回 `unregisterProject` 函数开头以还原「先删 Hook、后校验」的次序；两副本都先登记一个受管辖项目并安装 Hook，再以缺少必要授权材料的注销请求触发拒绝，随后检查 Hook 状态、登记状态，并试提交一条缺关键变更节的非法提交。

**观察结果**：缺陷副本上拒绝返回 `default_required` 之后，`hook state: absent`、`still registered: beta,alpha default= beta`，非法提交被放行（`{"passed":true}`）；HEAD 副本同样的拒绝之后 `hook state after refusal: managed`，非法提交被挡。守卫用例 `plugin/test/governed-projects.test.mjs:537` 绿。

**判定**：机制复现成功（次序先于校验时，拒绝确实留下已生效的状态变更，且门禁就此失守）。与候选不一致一处：候选「解决」「验证」两段都写着「材料未记录修复已实施与复验通过」，而实测该修复已由 a2dafe7（2026-10-31 06:11）落地并带用例，本次已据此改写两段。

**未覆盖**：另两条拒绝路径（fingerprint 过期、not_registered）未手工重放；未普查其它受控操作的副作用次序。
