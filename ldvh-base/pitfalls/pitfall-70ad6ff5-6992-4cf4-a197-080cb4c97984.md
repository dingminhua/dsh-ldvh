# 验证命令沿用主仓工作目录致 worktree 改动漏检

## 症状

在 worktree 中完成 Web 改动后，从主仓执行 `tsc -b` 与 web API 测试，命令全部通过，但通过的并不是 worktree 中的改动：真实改动一行都没有被编译或加载。识别信号是「验证全绿」与「改动文件不在被测路径内」同时成立——把 worktree 的改动临时改坏，从主仓执行的同类命令仍然全绿。

## 触发条件

代码改动在 git worktree 里，验证命令却在主仓（或另一棵树）的工作目录下执行；命令本身按 cwd 解析被测源码与测试路径（`tsc -b`、`node --test`、包管理器脚本都用相对 cwd 的 tsconfig/测试入口），于是执行的是另一份代码。会话 cwd 继承自启动目录时尤其容易踩到。

## 根因

「命令从哪里跑」与「要验哪份代码」是两件独立的事，而多数工具默认前者决定后者。worktree 的存在恰恰是为了让同一仓库有多份代码，因此 `pwd` 与被改文件所在树不是同一棵树时，「验证通过」只证明主仓没坏，对 worktree 的改动零信息。

## 解决

把验证命令的工作目录显式切到改动所在的 worktree 根后再执行：先 `pwd` 与 `git rev-parse --show-toplevel` 确认被测树，再跑 `tsc -b` 与 web API 测试，不再依赖会话默认 cwd；成功信号是命令解析到的源码与测试路径落在该 worktree 内，worktree 改动若破坏类型或 API 会直接转红。

## 规避

凡在 worktree 里改了东西，验证前先问一句：**这条命令会在哪棵树里找源码？** 用 `git rev-parse --show-toplevel` 打印被测树并肉眼确认；不要依赖会话 cwd。反过来，把改动临时改坏、确认从正确目录跑会转红，是最省事的一次性核对。

## 验证

已观察（逐字引证，来源：本会话主控会话 turn 3 的 assistant 正文，材料 turn 3 段落，Web 验证一段）：

> 我前面跑的那次 `tsc -b` 和 web API 测试都是在**主仓**跑的，用的是主仓代码，根本没检查到我在 worktree 里的 Web 改动。
> 来源：本会话主控会话 turn 3 的 assistant 正文（材料 turn 3 段落，Web 验证一段）

### 独立复现验证（2026-11-02）

**复现主体与独立性边界**：主控委派的独立子代理（受管辖隔离子代理，上下文不外泄给本候选），模型与主控相同（deepseek-v4.1-flash），派生于同一会话但上下文隔离；按 01 §12.2 读作「同模型 + 上下文隔离」，不是异模型独立验证。

**复现做法**：建一个临时 worktree，在其中注入两类可判定的错误——一条 TS 类型错误（`src/main.tsx(15,7)` 处把 `number` 赋成 `string`）与一条必失败的断言；先回主仓跑 `tsc -b` 与 web 测试，再在该 worktree 内跑同样两条命令。

**观察结果**：主仓 `tsc -b` 全绿、web 测试通过；worktree 内 `tsc -b` 退出码 2，报 `src/main.tsx(15,7): error TS2322: Type 'string' is not assignable to type 'number'`，测试报 `AssertionError actual:1 expected:2`。即主仓的结果对 worktree 的改动完全无信息量。

**判定**：复现成功，机制与识别信号（验证全绿但改动未被测）吻合。

**未覆盖**：lint、vite build、e2e 是否同样受隐式 cwd 影响未逐一核对；worktree 无 `node_modules` 的情形未测（本次用符号链接补齐依赖）。

## 影响与适用范围

凡在 git worktree 中改动代码、却从主仓或其它工作树目录执行类型检查与测试的验证场景均适用；本次实际发生在 Web 端的 `tsc -b` 与 web API 测试，其它验证命令未覆盖。

展开：何时可能踩到——任何「worktree 内改动 + 从主仓或另一棵树执行验证」的组合，尤其当会话 cwd 继承自启动目录、命令又不显式声明被测树时。何时可信——本条针对「命令按 cwd 解析被测代码」的验证形态；显式传入绝对路径或 `--project` 的调用不在覆盖内，仍需核对实际解析结果。
