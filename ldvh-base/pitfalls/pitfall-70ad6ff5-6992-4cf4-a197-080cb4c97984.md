# 验证命令沿用主仓工作目录致 worktree 改动漏检

## 症状

在 worktree 中完成 Web 改动后，从主仓执行 `tsc -b` 与 web API 测试，命令全部通过，但通过的并不是 worktree 中的改动：真实改动一行都没有被编译或加载。识别信号是「验证全绿」与「改动文件不在被测路径内」同时成立——把 worktree 的改动临时改坏，从主仓执行的同类命令仍然全绿。

## 触发条件

改动位于独立的 git worktree，而验证命令在会话默认工作目录（主仓或无改动的另一棵树）中执行；命令通过相对路径或项目发现机制解析源码，不要求显式指定被测工作树。本次为 worktree 内的 Web 改动与主仓内执行的 `tsc -b`、web API 测试组合。

## 根因

`tsc -b` 与测试运行器按调用时的工作目录解析 `tsconfig`、源码入口与测试文件，不感知「改动实际写在哪个工作树」；会话默认 cwd 是主仓，于是命令编译、加载的是主仓代码。主仓代码本身是干净的，所以命令照常通过，结果被误读为「改动已验证」。根因是验证对象的定位依赖隐式 cwd，而「改动位置」与「cwd」之间没有任何机械绑定。已观察：主仓侧 `tsc -b` 与 web API 测试通过、worktree 内的 Web 改动未被检查；未知：在 worktree 内重跑的具体结果未留在材料中。

## 解决

把验证命令的工作目录显式切到改动所在的 worktree 根后再执行：先 `pwd` 与 `git rev-parse --show-toplevel` 确认被测树，再跑 `tsc -b` 与 web API 测试，不再依赖会话默认 cwd；成功信号是命令解析到的源码与测试路径落在该 worktree 内，worktree 改动若破坏类型或 API 会直接转红。

## 规避

跨 worktree 工作时，每条验证命令前先确认「被测树 = 改动树」：用 `git rev-parse --show-toplevel` 与改动文件路径比对，或以 `git -C <worktree> ...`、`cd <worktree> && ...` 显式定位；对关键改动做一次反向检查（临时改坏 worktree 中的文件，确认验证转红），以证明命令确实覆盖了目标树。例外：验证对象确实在主仓（如需验证主仓 HEAD）时不受此限，但应在交还中写明被测树是哪一个。

## 验证

已观察（逐字引证，来源：本会话主控会话 turn 3 的 assistant 正文，材料 turn 3 段落，Web 验证一段）：

> 我前面跑的那次 `tsc -b` 和 web API 测试都是在**主仓**跑的，用的是主仓代码，根本没检查到我在 worktree 里的 Web 改动。
> 来源：本会话主控会话 turn 3 的 assistant 正文（材料 turn 3 段落，Web 验证一段）

未覆盖：在 worktree 内重跑后的具体输出未留在材料中；其它验证命令（lint、构建、e2e）是否同样受隐式 cwd 影响未逐一核对。

## 影响与适用范围

凡在 git worktree 中改动代码、却从主仓或其它工作树目录执行类型检查与测试的验证场景均适用；本次实际发生在 Web 端的 `tsc -b` 与 web API 测试，其它验证命令未覆盖。

展开：何时可能踩到——任何「worktree 内改动 + 从主仓或另一棵树执行验证」的组合，尤其当会话 cwd 继承自启动目录、命令又不显式声明被测树时。何时可信——本条针对「命令按 cwd 解析被测代码」的验证形态；显式传入绝对路径或 `--project` 的调用不在覆盖内，仍需核对实际解析结果。
