# skip 基线登记口径错致干净 CI 恒红

## 症状

干净 CI runner 上 plugin job 连续 6 个 run 判红，判词固定为「skip 数高于基线，新增 N 条未执行（…新增 skip 须经评审，不随单次运行上移）」。失败不在任何用例断言上，而在收尾的条数守卫对账段。同一提交在开发机上全量实测 skip=19，低于基线 27，恒绿。识别信号是「本机绿、CI 红」且红的是 skip 对账而非用例；另有一重误导：守卫旧提示把一切守卫失败都指向「`--test-force-exit` 截断签名，重跑」，与 skip 超基线无关，会把归因引向错误方向。

## 触发条件

同时满足两项即触发：(1) skip 基线值是「评审登记值」，其数值来自某一环境的跳过面；(2) 后续变更给用例加了「环境缺失即注册期 `test.skip`」的守卫，使干净环境上的设计内跳过条数增加，而基线未在同一次变更内同步上移。

本案的具体组合：基线 27 由 commit 52fb79de（2026-11-19）建立，其构成是开发机全量实测的 19 条 + 登记时已预见的上游锚点 8 条（27 = 19 + 8）。开发机的 19 条为 Windows 生命周期验证记录 10 条（test/windows-lifecycle-verification.test.mjs，skip 理由「本文件是 Windows 验证记录」）、Windows ACL 8 条（test/windows-acl-verification.test.mjs，「仅 win32 可构造/可达」）、8.3 短名 1 条（test/web-mount.test.mjs，「the 8.3 short-name defect is Windows-only」）。随后 commit bd95583d 与 af1e1143（2026-11-20）为会话数据相关用例加「无数据时注册期 `test.skip`」守卫，新增 6 条设计内跳过，基线未同步。干净 runner 缺少开发机的两类前提——本机会话数据 `~/.dsh/sessions` 与上游克隆 `/Users/dmh2002/DshProject/deepseek-harness`（4 个锚点 tag 齐全）——故其跳过面比开发机多出上游锚点 8 条（test/host-contract-anchor.test.mjs，克隆缺席时 `t.skip`「上游克隆或锚点 tag 缺席」）与会话数据 6 条（test/recall-action-evidence.test.mjs，依赖 `~/.dsh/sessions` 真实数据），实测 skip=33。

## 根因

基线口径错位：把「评审登记值」按开发机的观察值登记，而本应取最干净环境（CI）的跳过面。开发机的跳过面天然缺 8 条上游锚点跳过与 6 条会话数据跳过，于是同一基线在两处含义不同——CI 侧 27 实际低于其真实跳过面 33，开发机侧 27 高于其 19。新增 6 条设计内跳过后，CI 的 skip 恒为 33 > 27，守卫每次必红；开发机 19 ≤ 27，永远看不出问题。机制判断是「基线的登记口径与校验对象的环境不一致」，不是用例本身出错，也不是守卫算术出错。

另一层根因是失败提示未按判据分流：旧提示对所有守卫失败都给出「`--test-force-exit` 截断签名，重跑」的处置，而本次失败码是 skip 超基线，两者处置相反（前者是重跑，后者是评审后受控上移基线），提示把排障引向无效方向。

## 解决

评审 33 条跳过的逐条构成后，把基线受控上移 27→33；同时加一条评审锚用例，钉住登记值与构成，使「基线值」与「跳过构成」的对应关系可被机械核对，后续再改构成必须同改登记值并留下评审痕迹。守卫的失败提示按失败码分流：`skip_above_baseline` 指向「评审后受控上移基线或修复用例」，不再误指截断签名。成功信号为守卫在干净环境按新的登记值对账通过。

## 规避

1. 给用例加「环境缺失即跳过」守卫时，skip 基线的评审与上移必须放进同一次变更；不得留到「下次 CI 红了再说」。
2. 登记口径取最干净环境（CI runner）的跳过面，不取开发机观察值；开发机的跳过面因本机数据与克隆存在而偏小，不能充当登记依据。
3. 登记基线时把「已预见但本机不可见」的跳过（如上游锚点缺席）显式计入并留出处，而不是等它第一次在 CI 出现。
4. 守卫判红时先读失败码再信提示：skip 超基线与输出截断是两类失败，处置相反。
5. 保留评审锚用例；改跳过构成与改基线值必须成对出现。

## 验证

已观察：开发机全量实测 skip=19（10 + 8 + 1，逐条见「触发条件」）；CI 干净 runner 实测 skip=33，由 run 44815096601 日志逐条核对（19 + 上游锚点 8 + 会话数据 6）；连续 6 个 run 判词相同，证明是稳定假红而非偶发。修复侧：基线由 27 受控上移至 33，评审锚用例钉住登记值与构成，守卫提示按失败码分流；模拟干净 CI 环境（空 HOME + 不存在上游克隆路径）实测 0 fail / 33 skipped / exit 0。CI 侧回证（2026-11-21 补充）：修复提交 ab0cf945 推送后 run 44839044532 三个 job 全绿，plugin job 实测 2511 tests / 2478 pass / 0 fail / 33 skipped，守卫取数方言 tap、对账通过——「恒红已解除」取得 CI 侧实证。

未覆盖：单次 CI 绿不证明后续每次运行都绿（间歇性竞态由另一条经验 pitfall-db0b3e74 承载，其消除同样只有单次回证）；也未验证处于「部分具备前提」的开发机（如有会话数据但无上游克隆）时 skip 数落在 19 与 33 之间的中间态是否会对账产生新的歧义。

## 影响与适用范围

凡以「上次全绿基线」对账测试条数与 skip 数的测试入口，尤其 plugin/scripts/run-tests.mjs 的条数守卫；设计内 skip 数随环境变化而基线按某个环境登记时，干净环境（CI runner）的 skip 数高于基线即判失败。本条可信范围限于 dsh-ldvh 的 plugin job、Node 22 内置 test runner 与材料已核对的 19/33 条跳过构成；新增环境依赖用例或 CI 环境变更后须重新核对跳过构成再复用。

展开：凡「基线的数值来自 A 环境、校验发生在 B 环境」的对账机制都在受影响面内，不限于 skip——条数下限、耗时阈值等同理。本条的经验可信边界是：19 与 33 两组读数已逐条核对并含出处，可直接引用；修复后 CI 转绿已有 run 44839044532 单次实证，不外推为长期稳定。上游锚点与会话数据两类跳过属本仓特定前提，换仓后构成需重新测定。
