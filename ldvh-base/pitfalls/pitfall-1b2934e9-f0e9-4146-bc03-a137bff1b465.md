# 测量脚本把失败静默折算成零命中

## 症状
自建 A/B 测量脚本首版对两侧查询都返回 0 命中，且正控制与负控制同时为 0，却被读成「两侧没有差异」的测量成功。逐字引证：「第一版脚本正控制与负控制同时为 0，结果无效，我判废重跑」。

## 触发条件
调用方按错误约定给 listSparkObjects 传 factSourceRoot，多拼了一层目录；同时脚本把查询 failure 与真实的 0 命中合并为同一计数，且读数前没有「正控制必须 >0」的装置自检。材料记为「根因是 listSparkObjects 内部自己会 join(factSourceRoot, "sparks")，我多拼了一层目录；脚本又把 failure 静默当成「0 命中」」。

## 根因
两层缺陷叠加：其一是入参契约错配——listSparkObjects 内部已自行 join(factSourceRoot, "sparks")，调用方再拼一层，两侧查询集构造性地为空；其二是错误取值——脚本又把 failure 静默当成「0 命中」，失败与「确实没有命中」在读数上同形。由于没有独立的正控制门槛，装置整体失效时读数反而更「干净」，于是「第一版脚本正控制与负控制同时为 0」仍被当作测量成功。

## 解决
已采用的处理是判废首版读数并重跑：材料逐字记为「结果无效，我判废重跑」。成功信号是该轮无效读数没有被当成测量结论使用；必要边界是材料未逐字给出重跑时对路径传参与 failure 分支的具体修正。

## 规避
测量前先读被调函数的入参形态（本例 listSparkObjects 内部自己会 join(factSourceRoot, "sparks")），不重复拼接路径层级；把查询异常与 0 命中分开计数，failure 必须显式失败而不是折算成零；读数前加装置自检：正控制必须 >0、负控制必须 =0，任一不满足即判「未测量」而非「无差异」。材料中的「第一版脚本正控制与负控制同时为 0」正是该门槛应拦下的形态。

## 验证
已观察：第一版「正控制与负控制同时为 0」被判无效，操作者「我判废重跑」；未覆盖：重跑后的两侧读数、修正后的脚本实现与失败分支处理，材料均未逐字给出，故不能声称装置已修好。

## 影响与适用范围
适用于自建的一次性测量／A/B 对比脚本，尤其是以召回或查询返回计数作为结论依据、且把查询异常与零命中合并统计的场合；当路径参数按被调函数内部再拼一层的形态传递、或读数前没有正负控制自检时最易踩到。经验可信边界：本条只覆盖 recall_digest 的 A/B 测量装置这一处，且以「正控制与负控制同时为 0」为识别信号；不覆盖被测召回实现本身，也不证明修正后的重跑结果。与「以不覆盖被测类型的召回入口测量致全未命中」的区别是：那条的根因是入口声明范围排除被测类型，本条的根因是脚本路径重复拼接与 failure 折算；两者症状同为全零，修法不同。与「路径重复拼接致受检清单滤空而门禁静默放行」的区别是：那条把空清单当成门禁通过，本条把空查询当成零命中测量，落点与修法不同。与「否定式守卫用例缺正控制致假通过」的区别是：那条的缺口在测试断言，本条的缺口在测量装置的入参与错误计数。
