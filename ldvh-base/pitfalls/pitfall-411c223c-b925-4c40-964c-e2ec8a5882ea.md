# object 锚点只在 reports 目录解析致跨类型拒写

## 症状

首次调用 `ldvh_report_write action=create` 创建 action 型报告，证据摘录 E7 用「来源：object（3ab9c84c-0ebd-45d5-983d-cec515ef623a）」引用一个真实存在的 SubGoal 对象，被写入器拒回、零写入，回执为：

「LDVH report-write-object: unavailable」
「gap: research/internal_source_anchor_invalid: internal source anchors failed mechanical checks」
「gap: internal-source: object locator does not resolve to an existing report object: 3ab9c84c-0ebd-45d5-983d-cec515ef623a (24 §10.2)」
「follow_up: fix the reported mechanical issues and retry; zero write has occurred」

而被引用的对象真实存在：`ldvh-base/subgoals/subgoal-3ab9c84c-0ebd-45d5-983d-cec515ef623a.md`，本轮 `subgoal_read` 可读、status=active。报错文案说「does not resolve to an existing report object」，但目标根本不是 report 对象，提示语本身掩盖了「只认 report」这一真实判据。

## 触发条件

同时满足以下条件即触发：

1. 报告 `report_form` 为 `summary`、`audit`、`action` 或 `reference`（研究型 report 不走该校验）；
2. 正文携带 `来源：object（<uuid>）` 锚点；
3. 该 uuid 指向的是 **非 report 类型** 的事实对象（subgoal、pitfall、norm、spark、friction 等）。

此时无论对象是否真实存在、是否可读，都会进入 `resolveInternalObjectLocators` 并 100% 判为不可解析。

## 根因

对象路径拼装写死了 report 目录。`objectFilePath` 只查 `reports/report-<uid>.md`：

```
第 705 行：export function reportFileName(uid) { return `report-${uid}.md`; }
第 707-708 行：
function objectFilePath(factSourceRoot, uid) {
  return join(factSourceRoot, REPORT_DIRECTORY, reportFileName(uid));
}
```

其中 `REPORT_DIRECTORY = "reports"`（第 17 行）。解析处只做一次 `access`：

```
第 510-521 行：
async function resolveInternalObjectLocators(factSourceRoot, anchors) {
  const issues = [];
  for (const { kind, locator } of anchors) {
    if (kind !== "object" || !UUID_PATTERN.test(locator)) continue;
    try {
      await access(objectFilePath(factSourceRoot, locator));
    } catch {
      issues.push(`internal-source: object locator does not resolve to an existing report object: ${locator} (24 §10.2)`);
    }
  }
  return issues;
}
```

create 路径在第 815-822 行调用它，任一 issue 即整体拒写：

```
  if (frontmatter.report_form === "summary" || frontmatter.report_form === "audit" || frontmatter.report_form === "action" || frontmatter.report_form === "reference") {
    const anchorCheck = validateInternalSourceAnchors(body, { requireAny: true });
    const resolved = await resolveInternalObjectLocators(factSourceRoot, anchorCheck.anchors);
    const allIssues = [...anchorCheck.issues, ...resolved];
    if (allIssues.length > 0) {
      return failure("research/internal_source_anchor_invalid", "internal source anchors failed mechanical checks", { issues: allIssues });
    }
  }
```

即：object 锚点解析只查 `reports/report-<uid>.md`，跨类型对象（subgoal/pitfall/norm/spark/friction 等）文件不在 `reports/` 下，`access` 必失败 → 判不可解析。

规范与实现不一致是根因的另一半。24 §10.2 对 `object` 锚点的契约是：

「| `object` | 该内容来自另一个事实对象 | 该对象 `object_uid` 的规范文本；**事实对象只相互引用**，这是唯一被允许的「引用其它事实对象」通道 |」

同条又要求：

「4. **禁止虚构 `locator`**：写了 `commit` 就必须真存在该提交、写了 `object` 就必须能解析到该对象。机械层校验 `commit` 的 40 位 hex 形态与 `object` 的可解析性」

规范层允许 object 引用任一事实对象（不限 report），写入器实现窄于规范：它把「可解析」实现成「在 reports/ 下存在同名文件」，于是合规的跨类型引用被当成虚构 locator 拦下。

## 解决

不修写入器时，用 `commit` 锚点承载跨类型对象内容即可绕开该窄实现。主控当次把 E7 的「来源：object（3ab9c84c-…）」改为「来源：commit（41e0c870cd1fd8e9bbae79f065b5a76053b66f5f）」（该提交下含 subgoal 文件）后重试，回执：

「LDVH report-write-object: completed」
「object: 6339f3dc」
「read_back: ok」

原因：commit 锚点只校验 40 位 hex 形态、不解析对象文件，故能承载跨类型内容。

## 规避

- 写 summary/audit/action/reference 报告且需引用非 report 事实对象时，**不要**用 `来源：object（<uuid>）`；改用含该对象文件的 commit 锚点 `来源：commit（<40 位 hex>）`，或改引一个真实的 report 对象。
- 写入前先确认被引对象类型：只有 report 对象才可走 object 锚点；subgoal/pitfall/norm/spark/friction 一律走 commit 或正文直述。
- 遇到 `object locator does not resolve` 而对象明明存在时，先怀疑本窄实现，不要反复换 uuid 重试、更不要伪造 locator。
- 若要真正修复，应让 `objectFilePath` 之类解析按对象类型分目录查找（或走统一对象索引），而不是继续在 `reports/` 下找。

## 验证

本会话一次真实往返：object 锚点引用真实存在的 subgoal → 被拒（零写入，回执含 `research/internal_source_anchor_invalid`）；改 commit 锚点 → 成功（`object: 6339f3dc`、`read_back: ok`）。

另经本代理核对代码，update 路径（第 1011-1018 行）调用同一个 `resolveInternalObjectLocators`，故同形态更新亦受影响。

未覆盖：未验证 summary/audit/reference 形态是否同样受影响（代码路径共用同一 `resolveInternalObjectLocators`，推断同受影响但未实测）；未验证修复后跨类型 object 解析是否正确（本行动未修写入器）。

## 影响与适用范围

所有经 report-writer 受控创建或更新、report_form 为 summary/audit/action/reference 的报告正文：用 object 锚点引用任何非 report 类型事实对象（subgoal、pitfall、norm、spark、friction 等）时，均会被判不可解析而整次拒写。

适用范围限于走该校验的四种 report_form 与 object 锚点；commit/路径/规范条文等其他锚点形态不受影响，研究型 report 亦不走该分支。触发信号：当 report-writer 的 object 锚点解析改为跨类型目录查找（或改走对象索引/注册表）、或 24 §10.2 条文把 object 引用收紧为仅允许 report 对象时重审本经验。
