# 校验假定形式与语义一一对应

## 症状

为一个「写法/命名/编号」类纪律设计了机械校验或守卫测试，它**看起来正在管这件事**，但实测出现两类同时发生的失效：

1. **漏检**——抓不到它声称要防的那个错误。识别信号：校验的**匹配形式**与目标错误的**实际形式**交集为空。实测本例：原错误写作纯「步骤 7」「步骤 8」，而校验只识别显式形式「计划步骤 N」——两者无交集，校验对目标错误完全无感。
2. **误报**——拒绝合法或诚实的输入。实测本例：该校验把本单**自身工单的摘要**判为违规，因为摘要引述了那个编号错误（「…曾把复核编为计划步骤 7–8…」）而超出本单 plan 长度。后果是该对象无法再写入任何进展。

守卫测试侧有同类症状的另一形态：**源码文本断言全绿，而语义等价的门禁仍被注入且实测生效**。实测本例：把被回退的校验改名改文案（`checkLedgerNumbers`）、接入写入路径，7 项守卫全部通过（`ℹ pass 7`），而该门禁确实会拒绝写入。识别信号：守卫实现里出现 `fs.readFileSync(...)` + 正则/`includes` 匹配源码，而非调用被守卫的行为。

## 触发条件

同时满足以下条件即触发（缺一通常不成立）：

1. **校验需要区分两个在目标语言里字形相同的东西**。本例要区分「本对象引用自己的计划步骤」与「引述他对象的编号（含描述他人的编号错误）」——二者在 Markdown 正文里完全同形。
2. **被判定的对象是自然语言正文**（而非结构化字段）。自然语言里同一语义有无数等价写法，同一写法可承载多种语义。
3. **守卫以源码文本断言代替行为断言**：断言「某标识符/字符串出现在某文件里」，而非「调用该实现会产生某结果」。

组合条件：**形式与语义之间既非单射亦非满射，而校验只看形式**——此时漏检与误报会同时出现。

## 根因

**形式到语义的映射不构成一一对应，而机械校验只能看见形式。**

- **非单射（同形异义）**：同一字形承载不同语义。本例「计划步骤 7–8」既可能是本对象的真实引用，也可能是对他人编号错误的引述。形式相同、语义相反。
- **非满射（异形同义）**：同一语义有多种字形。数字可有半角/全角，编号可有多种措辞，同一引用可加引号、加归属或直接陈述。

由此，任何「识别某形式即判定某语义」的校验都必然在两个方向失效：

- 目标错误的字形若不在识别集合内 → **漏检**（校验对其无感）；
- 合法书写的字形若落入识别集合 → **误报**（拒绝正确输入）。

而**误报方向会制造反向激励**：当校验惩罚的是「如实描述」（本例即引述编号错误），最省事的通过方式不是写对，而是**不写编号**——被校验的信息量反而下降。这一点与本类型既有的「首行比较式校验漏掉多余H1」（`96fb3199`）**根因不同**：后者是「判定单位选错」（单点代替集合）因而可修；本条是**形式-语义映射本身不可判定**，无法通过换一种匹配方式来修复。

源码文本断言的失效是同根因的守卫侧形态：它把「某形态存在」当作「某语义生效」。形态可删可改可绕——只要换一套命名与文案，语义完全相同的实现就能在守卫全绿下通过。**形态是语义的影子，不是语义本身。**

## 解决

已实际采用（2026-09-18，LDVH 仓库 `21 §8` 执行节记账纪律，本仓库 WC-1c6afa19）：**回退该机械校验**，改以不含任何拒绝规则的「弱约束」承担同一目标——

1. **规范给出唯一合法写法**（`specs/21` §8）：正文引用计划步骤须用显式形式「计划步骤 N」，N 以当前 `plan` 为界；非计划步骤的执行事项独立描述、不得编入计划序号。该段**明确声明自己是写法约定而非机械门禁，并写明不得据此新增校验及其理由**。
2. **工具层在写入时点给出权威清单**：`workcase-writer.js` 的 `planStepReference(plan)` 在 `approve`（授权时点）与 `execute`（实际写正文时点）**两处**返回当前 plan 的逐条序号与 step 文本，使作者不必回查 frontmatter 即可确定编号。

成功信号：回退后 web 测试 274/274、plugin 测试 824/824 全绿；**且不再误伤诚实记述**——本单工单（摘要含对该编号错误的引述）可正常写入。规范与实现按受控提交分离为两次提交，均由 Git Gate 通过。

必要边界（**必须随本经验一同复用，不得只取「加提示就好」的结论**）：

- 弱约束**没有强制力**，不能保证不复发；它只把「无从自创」变成「无必要自创」。
- 因此**不得据其声称该纪律已获机械保障**。该声明已写入守卫测试头部，并有一条守卫断言该声明存在。
- 本方案只适用于「目标可用『前置告知』达成」的场合；若某纪律离开强制就无人遵守，则**不是本经验适用对象**，须回到「形式是否可分」重新判断，而不是退回强校验。

## 规避

**核对条件**（设计任何写法/命名类校验前逐条自问）：

1. **要区分的两个东西在字形上可分吗？** 若不可分（如「引用自己」与「引述他人」），**不要加该校验**——它必然同时漏检与误报。本例已实测该不可分性：四种引述写法（直接陈述、加引号、加归属、正误混排）与真实引用在字形上无任何稳定区别。
2. **这是行为断言还是源码文本断言？** 源码文本断言只拦形态，必须在测试头部**如实声明保证边界**（写清「只拦形态、不拦语义」以及「不得据其全绿声称已获机械保障」），否则会形成新的自欺面。
3. **该校验误报时会惩罚什么样的输入？** 若惩罚的是「如实描述、如实引述、如实记录」——即诚实性行为——则设计存在反向激励，须重新设计而非调阈值。

**动作——加校验前做「变异三连」**（每次变异后必须还原）：

1. **目标错误形态能否被捕获**：把该校验声称要防的那个错误**按它的真实写法**注入，观察是否被拒。若原错误写法与校验识别形式不同形，此项必失败——这正是本例的发现方式。
2. **合法形态是否被误伤**：注入合法写法（含各种等价变体：全/半角、缩进、引号、CRLF），观察是否被误拒。
3. **语义等价改名是否逃逸**：把校验函数改名、错误文案改写、但保留全部语义，观察守卫是否仍能捕获。若守卫仍全绿而该门禁实测生效，则守卫只具备形态级保证——**如实登记该边界，不得宣称语义级防护。**

**例外**：当被校验对象是**结构化字段**（YAML/JSON 的枚举、类型、必填性、闭集）而非自然语言正文时，形式与语义通常一一对应（`status: open` 就是那个枚举值，不存在等价的另一种写法），机械校验在此**有效且应当使用**。本经验不构成「不要加校验」的通用主张——它只否定「形式与语义非一一对应的场合仍强行加校验」。

## 验证

已观察（2026-09-18，LDVH 仓库）：

- **漏检**：以 2 步 `plan` 的 WorkCase 载体实测，向「执行」节写入纯「步骤 7」「步骤 8」——现有 `validateCarrierCoherence`（`plugin/lib/workcase-writer.js`，只校验摘要/授权范围/计划三节）返回通过，错误正常落盘。该校验函数体内**从不出现「执行」**（实测计数 0）。
- **误报**：为同一载体加上「识别显式形式」的校验后，含「引述他对象编号错误」的摘要被拒（`超出当前 plan 长度 6`），导致该对象无法再写入——该误报发生时对象正是「记录该缺陷」的那张工单。
- **守卫形态级**：独立对抗审核实施变异 ⑥（语义等价、改名改文案的越界门禁 `checkLedgerNumbers` 接入写入路径），7 项守卫全部通过且该门禁实测确实拒绝写入；本次由实现者独立复现确认。
- **回退后**：web 测试 274/274、plugin 测试 824/824 全绿；本单工单（摘要含该引述）可正常写入。

未覆盖：

- **弱约束的实际降低复发率未验证**——只有本会话一例样本，且规范与工具层提示的真实遵守效果需跨会话观察。
- **同类校验未普查**——本仓库其它类型（20/22/24/26/27）的正文纪律是否存在同根因设计，本经验未逐项核对。
- **变异三连第 3 项的通用性未验证**——「语义等价改名逃逸」在本例由独立审核的变异 ⑥ 实证，但其它项目的源码文本断言是否同样脆弱，需按其实际实现核对，不得仅凭症状相似即认定同因。

## 影响与适用范围

为「写法/命名/编号」类纪律设计机械校验或守卫测试的场合——特别是校验需要区分「X 引用自己」与「X 引述他人」、或需要以源码文本断言代替行为断言时，校验必然同时漏检与误报。已验证实例：LDVH `specs/21` §8 执行节记账纪律的越界校验（已回退）及其 7 项守卫测试。

具体而言：

- **何时可能踩到**：为自然语言正文的写法纪律新增机械校验时；把结构化字段的校验经验平移到正文纪律时（前者形式-语义一一对应、后者不然，平移即引入本机制）；用源码文本断言守卫「某实现不得复活」时。本例的触发场景是：AI 在一次执行记录里自创编号、与 plan 的位置序号混同，修复者据此设计「越界即拒绝」的校验——设计动机完全正当，失效源于**形式不可分**而非动机错误。
- **经验何时可信**：本经验的机制判断（形式-语义非一一对应时，机械校验必然漏检+误报，且误报制造反激励）在自然语言正文范围内稳定成立，与具体语言、项目、实现无关。但**具体到其它校验，是否同样不可分须按「核对条件」第 1 条实测**——先做变异三连，不得仅凭症状相似即认定同因，也不得因本经验存在就放弃所有正文校验。
- **与既有经验的分界**：`96fb3199`（首行比较式校验漏掉多余H1）的根因是判定单位选错，**可修**；本条的根因是形式-语义映射不可判定，**不可修**，只能改为弱约束或不设校验。二者症状相似（都表现为校验失效），**根因不同，故各自成对象**（23 §6.2：不同机制的相似症状不合并）。
