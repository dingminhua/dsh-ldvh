# 分号链验证只打印不设闸致红门禁照样提交

## 症状

提交 e73da3b5（2026-11-25）在轮次翻号的长命令链中被提交并推送 origin/dev，该提交处于版本门禁红、CHANGELOG 轮次条目缺失的坏状态；dev CI run 对 e73da3b5 判 completed failure。

关键的症状位不是「失败未被发现」，而是「失败已知却照样提交」：当轮命令输出里 `GATE_DEV_EXIT=1` 被如实打印，RC 确实取到了门禁进程的真实退出码 1，但同一条链继续执行 git add / commit / push。坏状态直到依靠下一轮 dev CI 才暴露，随后由修复提交 81ae0752 恢复（该提交在同 run 中判 completed success）。

## 触发条件

- 把「验证 → 动作」序列写进同一条 shell 命令链；
- 验证步骤以分号（`;`）串联，或验证结果只经 `RC=$?; echo ...` 打印，后继动作不置于 `&&` 或显式 `if ... exit 1` 之后；
- 自动续跑 / 脚本化执行中尤其危险：没有人在读打印出来的值。

事发当轮的形态：`node scripts/require-version-consistency.mjs > /dev/null 2>&1; RC=$?; echo "GATE_DEV_EXIT=$RC" && if ... fi && ... && git add -A && git commit ...`——验证与 echo 之间是分号，`echo` 之后的 `&&` 只承接 echo 的成功（echo 恒成功），RC 的取值从未参与任何判断。

不适用于单步手工执行（人看到红会自己停下），或验证与动作天然分离成两道工序/两条命令的流程。

## 根因

缺陷位是「动作不设闸」，不是「退出码捕获不诚实」：

1. **捕获环节是诚实的**：`RC=$?` 取到的是门禁进程的真实退出码（无管道介入，不存在管道掩蔽），并打印为 `GATE_DEV_EXIT=1`。
2. **串联环节是断裂的**：验证与打印之间用分号，失败不阻断链；打印与其后的动作用 `&&`，但只承接打印的成功。于是打印被当成了闸——而打印只是信息，闸必须是控制流：非零退出码必须终止后继动作。
3. **与前坑 pitfall-2aebcfdf 同族但缺陷位不同**：前坑（全局 sed 翻锁 + 管道掩蔽退出码）是「退出码捕获不诚实」——被验证命令不在管道末位，`$?` 取到的是 tail/grep 的状态，失败被吞掉；本坑是「捕获诚实、动作不设闸」——`$?` 取对了也打出来了，却没有任何分支消费它。前坑的防复发口径（退出码不经管道取得）在本仓已执行，本坑说明只修捕获、不修闸并不够：捕获对而链不设闸，等同于不拦。

## 解决

已落地于 81ae0752：

- 先修复坏状态（补齐 CHANGELOG 轮次条目、使版本门禁转绿），再重新走门禁；
- 提交链改为门禁前置闸、fail-closed：

```sh
node scripts/require-version-consistency.mjs > /dev/null 2>&1
RC=$?
if [ "$RC" -ne 0 ]; then
  ...
  exit 1
fi
git commit ...
```

门禁不过则整条链终止，不再存在「打印红色、照常提交」的路径。

## 规避

防复发口径：任何「验证 → 提交 / 推送 / 发布」序列，验证必须以条件与（`&&`）或显式 `if ... exit 1` 串联，让非零退出码终止整链；禁止用分号串联验证与动作；验证输出可以打印，但打印不是闸。

两条补充：

- CI 是最后一道独立闸，不能作为唯一指望——它发现时坏提交已经推上 origin/dev，代价是修复提交与一段被污染的远端历史；
- 复核一条链时问的不是「失败会不会被看见」，而是「失败会不会让后续动作停下来」。

## 验证

- dev CI run：e73da3b5 判 completed failure（版本门禁红被提交），81ae0752 判 completed success（门禁前置闸修复）。
- git 历史 e73da3b5..81ae0752：修复提交说明与「门禁前置闸」的改法一致。
- 反推检验：事发链中 `GATE_DEV_EXIT=1` 被如实打印、RC 取值为 1，说明捕获无误；提交仍然发生，说明缺口在设闸而不在捕获。

## 影响与适用范围

任何「验证 → 动作」序列被写进同一条 shell 命令链，且验证步骤以分号串联或验证结果只 echo 不 if 的场合；自动续跑/脚本化执行中尤其危险（无人盯着打印值）。不适用于单步手工执行、或验证与动作天然分离的流程。

补充边界：本坑的破坏面是 origin/dev 上出现一个门禁红的提交、并占用一轮 CI 才被发现；不涉及已发布产物。与 pitfall-2aebcfdf 合起来说明「退出码诚实」与「动作受控」是两个独立的必须项，任一缺失都会把门禁退化成打印。
