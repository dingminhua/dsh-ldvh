# 以 pid 为就绪信号致启动窗口探活失败

## 症状

web-mount 用例在读到子进程的新 pid 之后立即发起一次 health fetch，返回 `ECONNREFUSED`，该条用例转红。该失败在机器负载高时**概率性**出现，单独运行该用例时全绿——同一用例、同一断言，结果取决于运行时的并发负载。

逐字引证（缓冲条目 87a1b3ad-ba73-4c20-9663-0bc58a550e36 的 evidence，原文复制）：

```
失败细节已经拿到：`ECONNREFUSED`，出在最后那次 health fetch。
来源：主控会话材料 turn 9 助手回复（关于「处理过程中发现并修复了一个缺陷」一段）
```

识别信号：探活请求报 `ECONNREFUSED`（连接被拒，而非超时或 404），且失败集中在「子进程刚启动、pid 刚可读」的时点；同一用例在低负载下通过。

## 触发条件

子进程刚被 spawn、pid 已写入（或已可被读到），而它的 HTTP server 尚未完成 bind／listen。探活方以「读到新 pid」作为就绪判据，读到后立即发起一次 health fetch，且这次 fetch 没有重试。负载高时 spawn 到 bind 之间的间隔被拉长，单次 fetch 落在窗口内的概率升高；单独运行时该间隔极短，fetch 到达时 listener 已就绪，故全绿。窗口拉长到足够宽时（本次复现为 1200ms）即成必现。

## 根因

「pid 已写入」被当成了「服务已就绪」，但两者之间隔着 HTTP bind／listen 这一段：pid 只证明进程被创建，不证明端口已有 listener。窗口内没有进程在监听该端口，内核直接拒绝连接，于是得到 `ECONNREFUSED`（不是超时，也不是业务错误）。单次 fetch 在该窗口内必然失败；轮询或重试会在窗口结束后成功，因此它掩盖了窗口，而不是消除了窗口。

## 解决

把探活从「读到 pid 后单次 fetch」改为「等到就绪再 fetch」：优先让服务端在 listen 成功后发出就绪信号（输出一行、写就绪文件，或由启动器在 bind 完成后通知），探活方等该信号；取不到就绪信号时，退化为对 health 端点的有限重试（固定间隔轮询，直到成功或超时），超时才判失败。成功信号：同一用例在高负载下不再因 `ECONNREFUSED` 转红，同时真实启动失败仍由超时或子进程退出码识别并报红。

必要边界：轮询是掩盖窗口，不是消除窗口；若要求「单次 fetch 必定成功」，须把就绪判据换成 listen 完成事件。

## 规避

写「启动子进程 + 探活」类用例时，不要用 pid 文件当就绪信号：① 核对条件——探活对象是刚 spawn、需要绑定端口的子进程，且探活在 pid 可读后立即发生；② 动作——改为等待 listen 就绪信号，或对 health 端点做有限重试（有上限、失败可判定）；③ 例外——真实启动失败（进程已退出、端口被占）不得被重试吞掉，须由超时、退出码或错误文本区分。另：负载相关的红（单跑绿、并发红）应优先怀疑启动时序，而不是断言或数据问题。

## 验证

已观察：`ECONNREFUSED` 出在最后那次 health fetch；该用例负载高时出现、单跑全绿；引证与来源见症状段。

### 独立复现验证（2026-11-02）

**复现主体与独立性边界**：主控委派的独立子代理（受管辖隔离子代理，上下文不外泄给本候选），模型与主控相同（deepseek-v4.1-flash），派生于同一会话但上下文隔离；按 01 §12.2 读作「同模型 + 上下文隔离」，不是异模型独立验证。

**复现做法**：先以自然负载跑 3 轮（每轮 32 个忙循环进程制造压力），观察该用例的通过情况；再改一份夹具副本，把子进程从「写 pid 后立即 listen」改为「写 pid 后延迟 1200ms 才 listen」，跑同一用例；最后在延迟夹具上换成当前的 `waitForServing`（100 次 × 50ms 轮询）。

**观察结果**：自然负载 3 轮中 1 轮有 1 例转红（约 1/10，**不是每个高负载都必现**）；延迟夹具上必现失败，报 `[TypeError: fetch failed] { [cause]: Error: connect ECONNREFUSED 127.0.0.1:40855 ... }`，失败点正是最后那次 `/api/health` fetch；同一延迟夹具改用 `waitForServing` 轮询后转绿。

**判定**：机制复现成功（pid 可读 ≠ listener 就绪，窗口内单次 fetch 必失败、轮询可消除）。与候选一处不一致：候选写「负载高时必现」，实测自然负载下约 1/10 概率，只有人为拉宽窗口才是必现；症状段已按此改写。

**未覆盖**：真实 CI 并发下的复现频次；自然负载下窗口的实际长度。

## 影响与适用范围

适用于以「子进程写出 pid」作为就绪信号、并在读到新 pid 后立即发起单次 health 请求的用例与探活逻辑：此时请求会落在 pid 已写入而 HTTP 尚未 bind 的窗口内并失败；不适用于有 listen 就绪信号、或请求本身带有限重试的场合。

展开——何时可能踩到：以 pid／端口文件／日志行作为子进程就绪判据，并在读到后立刻发起一次探活的用例与脚本，尤其在 CI 并发或本机高负载时。经验何时可信：失败是 `ECONNREFUSED`、发生在子进程刚启动的时点、且单跑可绿时，本条可信；若失败是超时、404 或断言值不符，或子进程已稳定运行一段时间，则不适用本条。
