# 夹具写旧格式致生产路径假绿

## 症状
改完数据格式后，测试**仍然全绿**，但真实数据完全读不出来——旧格式的数据经生产读取路径读出的条数是 **0**，`recent` 为空：

```text
entries: 0 | recent: []
```

比「读不出来」更难发现的是：它同时证明了「测试跑过了」和「生产路径没被覆盖」。

## 触发条件
被测代码的持久化格式发生变更（这里是从整文件改写改为追加事件折叠），而测试夹具仍在写**旧格式**。夹具不经过生产代码的写入路径，而是自己拼一份数据文件喂给被测函数。

## 根因
夹具与生产代码是两条独立的写入路径，却都声称产出「同一份数据」。格式一改，两条路径分叉——生产读取新格式，夹具喂旧格式，测试测的是「读取代码能否读懂夹具的旧格式」，不是「能否读懂生产的真格式」。测试守的不是它以为在守的东西。

当前解析器按 `event.kind` 分派：`kind` 不在折叠事件闭集内的行计入 `skippedLines` 后跳过（`plugin/web/api/services/runtimeDiagnostics.ts:676–760`），所以一条 9 字段的旧记录既不报错也不呈现，只是整体消失。

## 解决
夹具从「一行一条完整记录」改为生产写入的字节形态（`{kind:"entry", record:{...}}`），并新增一条用例（`plugin/web/tests/api/diagnostics-experience-buffer.test.ts:103–132`）固定住生产写入的字节形状。

**但这一环的绑定尚未真正建立**（2026-11-02 复现时核实）：该用例手写上述字节、**不调用** `appendBufferEntry`；`writeBuffer()` 夹具同样手拼字节（`entries.map((row) => JSON.stringify({ kind: 'entry', record: row }))`）。因此它固定住的是**字节形状**，而不是「与写入函数实际产出一致」——写入端改装时它不会自动转红（见验证段的变异结果）。要让「夹具与生产同格式」从假设变成被机械检查的事实，仍须让夹具调用生产写入函数。

## 规避
凡测试夹具自己构造持久化数据的地方，都要问一句：「这份数据生产代码会不会真的写出来？」若夹具绕过了生产者，就必须有一条测试把两者绑在一起，否则格式变更必然静默漂移。**优先让夹具调用生产写入函数**，而不是拼字符串——手写字节即使当下正确，也只是把「与生产同格式」这一次的快照固定下来，不会在生产者变更时报警。

## 验证
本项目实测：改造后诊断页测试出现读不出旧格式数据的症状；夹具改生产格式并加「格式用例」后症状消失。变异（把夹具改回旧格式 `JSON.stringify(row)`）实测 **7 pass / 3 fail**，失败项为「只呈现四项」「按项目分区」「待审核数与最老一条」——即 3 条既有呈现断言会转红，而不是候选所称「新用例转红」：那条「夹具与生产同格式」用例（`plugin/web/tests/api/diagnostics-experience-buffer.test.ts:103–132`）是手写 `{kind:"entry",record:{...}}` 字节、**不走** `writeBuffer`，故它在变异下仍绿。

### 独立复现验证（2026-11-02）

**复现主体与独立性边界**：主控委派的独立子代理（受管辖隔离子代理，上下文不外泄给本候选），模型与主控相同（deepseek-v4.1-flash），派生于同一会话但上下文隔离；按 01 §12.2 读作「同模型 + 上下文隔离」，不是异模型独立验证。

**复现做法**：读取 `plugin/web/tests/api/diagnostics-experience-buffer.test.ts` 的夹具，改用 9 字段旧格式记录喂 `buildExperienceBufferReport`，再反向把夹具改回旧格式跑整份用例文件。

**观察结果**：旧格式数据读出的不是候选「症状」段所写的 `entries: 1` 且四字段全 `null`，而是 `entries: 0`、`recent: []`——当前解析器按 `event.kind` 分派，未知 kind 计入 `skippedLines` 后跳过。变异回旧格式后是 7 pass / 3 fail，而「夹具与生产同格式」用例仍绿（它手写折叠事件字节、不经过 `writeBuffer`）。

**判定**：机制成立且可复现（夹具与生产两条写入路径确已分叉、旧格式一条也读不出），但候选的**症状描述与验收断言有两处与实测不符**：①症状是「读出 0 条」而非「读出 1 条、字段全 null」；②「变异使新用例转红」不成立，转红的是 3 条既有呈现断言。旁证：`plugin/web/api/services/runtimeDiagnostics.ts:630–636` 注释自述该症状是「本轮真实发生过的缺陷」。

**未覆盖**：2026-10-26 事故当时的中间态读取器未入库，无法重放当时的现场。

**入档前据实订正（2026-11-03）**：原「解决」段声称「新增一条专门守这一环的测试：断言夹具产出与生产写入产出一致」，经核对**该绑定并未建立**——用例存在，但它固定的是字节形状而非写入函数的实际产出；`writeBuffer()` 亦未改为调用生产写入函数。已按实际形态改写该段，并同步收紧「规避」段（手写字节不等于绑定生产写入端）。订正后「解决」段所述的是**实际采用并已生效的处理**（夹具改生产字节形态 + 该格式用例），四前提据实成立；而「让夹具调用生产写入函数」作为待完成项明示在本条内，不再冒充已完成的事实。

## 影响与适用范围
适用于一切「读取端有测试、写入端被夹具替代」的形态：状态文件、事件日志、缓存、索引。不适用于夹具与生产共用同一函数的情形（那种形态下分叉无从发生）。边界：本条只保证「夹具格式与生产一致」被检查，不保证生产格式本身的正确性——后者仍须另有测试。

展开——何时可能踩到：持久化格式发生变更（整文件改写改追加事件、字段增删、编码或分层变化）时，凡是「夹具自己拼数据文件喂被测函数」的测试都会同时具备假绿条件；同一形态的相邻载体（状态文件、缓存快照、索引、事件日志）一样算在内。经验何时可信：夹具确实绕过生产者、两条写入路径相互独立时，本条的因果与解法成立——此时「测试全绿」不能作为格式变更已被覆盖的证据。另须注意本条只覆盖「夹具与生产同格式」这一环：生产格式本身是否写对了仍需另有测试；而本例中该环的绑定尚未真正建立（见「解决」段），故在本项目内复用本条时，应把「夹具调用生产写入函数」当作待完成项而不是既有事实。
