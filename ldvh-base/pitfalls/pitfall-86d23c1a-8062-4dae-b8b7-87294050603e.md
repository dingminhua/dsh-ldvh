# Git Gate 双向路径覆盖拦截

## 症状

git commit 时 commit-msg 钩子拒绝提交，报错形如 `validation/staged_path_uncovered: staged path "plugin/package.json" is not covered by any 关键变更 item`。

**创建时点**：预检工具 ldvh_precheck_git_commit 可能先行通过（当时预检只校验「每个关键变更项匹配某个暂存路径」的半边，双向覆盖只在 Git Gate 一侧）。**2026-10-14 复核更正**：两个入口已收敛为同一实现——`checkKeyChangesAgainstDiff` 同时承载正向半边与反向半边，两入口共用它，故「预检先过、Gate 后拦」这一分身不再出现；被拦症状本身不变。

**同一机制的反向表现：Gate 通过 ≠ 暂存区干净。** 当暂存区混入了并行会话的文件、且自己的「关键变更」项恰好含这些文件所在目录的**路径段词**（如 `plugin`）时，反向半边会把外来路径判为「已被覆盖」而**静默放行**——提交成功，但提交内容含属于他人的文件。此时症状不是报错，而是**误提交**：唯一发现手段是提交后比对 `git show --stat --oneline <sha>` 与自己实际改动的文件清单。

## 触发条件

提交消息的「关键变更:」小节中存在未包含任何暂存路径词的条目，同时暂存区包含未被任何条目覆盖的文件——典型场景：按语义分组写变更项（如「工具链落地」）而未点名 package.json/package-lock.json 等具体文件；或新增了与既有条目路径无关的暂存文件。

**反向触发的两个附加条件（2026-10-03 实测）**：①「关键变更」项中含**与他人文件共享的目录段词**（如 `plugin`、`docs`），使外来路径在目录段回退分支下被判为「已覆盖」；②提交命令**漏写 pathspec**（写成 `git commit -F <msg>` 而非 `git commit -F <msg> -- <自己的路径>`），使并行会话已暂存的文件一并进入本次提交。两者**各自都不足以**造成误提交：只缺 ① 会报 `staged_path_uncovered` 被拦；只缺 ② 则暂存区只含自己的文件、反向半边无外来路径可放行。

## 根因

K1 双向覆盖校验（并行线落地于 commit 07b9c25）：specs/09 §5.1 的提交契约要求关键变更项与暂存 diff **互相**覆盖——不仅每项要能机械对应到路径，每个暂存路径也要被某项覆盖（反向半边的机械切片在 §5.3 第 3 项，2026-09-10 Human 批准）。**号位更正（2026-10-14）**：本处创建时点曾引「09 §5.2」，而 §5.2 只是 `precheck-git-commit` 的公开操作登记表（operation_key／summary／effect／两个契约回指五列），不承载覆盖规则本身；规则语义在 §5.1、机械切片在 §5.3 第 3 项。

匹配规则（commit-validation.js 的 itemMatchesPath）：项含完整路径、文件名、去扩展名 stem、或无数字路径段（如 plugin/lib/spark-tools 的段 spark-tools）。

该规则的既定代价（同一根因的后果，非独立机制）：**目录段回退是有意设计**——`commit-validation.js` 注释明写「Diffstat-style summaries name the touched area; accept directory words.」，并有测试固化（`plugin/test/commit-validation.test.mjs` 断言「消息项用目录词分组覆盖两文件」应通过）。因此它对「同目录的外来污染」**无防护**；源码注释亦自认这是 known limitation。反向半边拦截「异目录污染」有效，拦截「同目录词污染」无效。

## 解决

**正向（被拦时）**：在「关键变更:」对应条目中补入暂存路径的 stem 或路径段后重新提交；本例在工具链条目点名 package.json/package-lock.json 后通过。必要边界：只改提交消息不需重做代码工作；但补词必须真实对应实际变更内容，不得为过门而虚写无关路径（那会被项-路径对应性校验的语义抽查暴露）。

**反向（静默放行而误提交后）**：① 先确认该提交是否已推送到远端（`git branch -r --contains <sha>` 为空则可安全重写）；② 用 `git reset --soft <误提交前的 HEAD>` 撤销提交并**核验 Index 逐字节保留**（`git write-tree` 前后同值）；③ 以**显式 pathspec** 或**隔离提交**（见下）重新提交自己的文件；④ 事后审计同期各提交的 `--stat`，确认污染只此一次。本次误提交的修复即按此四步完成，另一会话的 Index 状态分毫未动。

## 规避

写提交消息时先 `git status --short` 列出全部暂存文件，逐文件核对是否已被某个「关键变更」项的路径词覆盖；多文件提交按文件域分组写条目并逐项点名 stem（如「spark-tools 与 adr-tools、pitfall-tools」），不写无路径词的纯语义条目。暂存无关文件混入时（并行会话同仓库操作易发生），先 `git restore --staged` 剥离再提交。

**两项新增措施（针对反向表现）**：

1. **提交一律显式限定 pathspec**：`git commit -F <msg> -- <自己的路径>`。这是防止误提交的**第一道也是唯一必需**的措施——它使并行会话的暂存内容无论是否含共享目录词都无法进入本次提交。
2. **需要完全隔离时用临时索引**：`export GIT_INDEX_FILE=/tmp/tmp-index-<用途>` → `git read-tree HEAD` → `git add -- <自己的文件>` → 核 `git diff --cached --name-status HEAD` 只剩预期路径 → `GIT_INDEX_FILE=… LDVH_PREFLIGHT_INDEX=… git commit -F <msg>`。**`LDVH_PREFLIGHT_INDEX` 必须同步指向同一临时索引**，否则 commit-msg 钩子读真实索引、预检看到的与提交的不是同一份内容（`plugin/lib/git-gate-runner.js` 读 `--index-file`，`commit-msg` 钩子在 `LDVH_PREFLIGHT_INDEX` 非空时追加该参数）。

**撰写纪律的边界（不变）**：不得为过门而在「关键变更」项中虚写无关路径——补词必须真实对应实际变更内容。反向表现的存在**不构成**放宽该纪律的理由。

## 验证

修复后本仓库全部受控提交（19dcd7f 之后十余次）均通过 Git Gate；「路径词缺失→拦截→补词→通过」因果链在 2026-09-09 当日两次复现确认。

**反向表现的验证（2026-10-03）**：以隔离实验复现了该盲区——构造含 `docs/mine.md` 与两个 `plugin/web/src/**` 的 diff，提交消息项含 `plugin` 一词时 `checkKeyChangesAgainstDiff` 返回**通过**（外来路径被静默接受）；把该项改为不含 `plugin` 一词的写法后返回 **`FAIL -> validation/staged_path_uncovered`**（两条，对应两个外来路径）。⇒ 放行与拦截的差别**仅取决于消息中是否出现共享目录词**，与暂存区是否干净无关。另有一次真实误提交（漏写 pathspec）与该盲区叠加发生，其修复已使一并提交的 32 个外来文件从历史中完全移除（提交未被任何 ref 包含、未推送），修复前后 Index 全量比对逐字节一致。

**后续复核（2026-10-14，本仓）**：触发信号未命中（K1 双向覆盖校验未移除、09 号路径覆盖规则未改），但「未覆盖」项中的两处不确定性已有结果——①**预检与 Git Gate 的半边／全边差异已收敛**：`plugin/lib/ldvh-tools.js` 的 precheck 入口与 `plugin/lib/git-gate-runner.js` 的 Gate 入口都调用同一个 `checkKeyChangesAgainstDiff`（正向与反向半边同在一函数内），且 `git-gate-runner.js` 注释明写「09 §5.1 requires both entries of the same check to agree」，两入口的 maxBuffer 上限亦已对齐为 8MB，故「预检先行通过」不再是本机制的症状。②目录段回退**未**被收紧：`itemMatchesPath` 的 `segments.some(...)` 分支与 known-limitation 注释原样在，反向条目仍然有效。

未验证范围：非本仓库的其他 Git Gate 部署；目录段回退若被收紧后本经验的反向条目是否随之失效（见 trigger_signal）。

**机械化承载（2026-10-28 盘点）**：`plugin/lib/commit-validation.js:179-221`（`checkKeyChangesAgainstDiff`，反向半边 `:204`，规则 `validation/staged_path_uncovered`）经 `plugin/lib/ldvh-tools.js:687` 与 `plugin/lib/git-gate-runner.js:482` 两入口共用，用例 `plugin/test/commit-validation.test.mjs:500/522`，它断言每个非豁免暂存路径都被某个「关键变更」项覆盖。覆盖边界：`itemMatchesPath` 的目录段回退（`:244-253`）使含共享目录词（如 `plugin`）的条目覆盖该目录下任意外来路径——实测同目录词污染 `ok:true`、去掉该词才 `ok:false`，故只咬住「异目录污染」；「显式限定 pathspec」与「临时索引 + LDVH_PREFLIGHT_INDEX 同步」两项规避无任何机械检查。

## 影响与适用范围

适用于本仓库全部经 Git Gate 的受控提交的提交消息撰写。何时可能踩到：任何多文件提交且变更项按语义分组而非按文件域点名时；暂存区混入并行会话文件时尤甚——正向被拦侧本会话发生过两次（docs 文件被并行线暂进索引致我的提交被拦），**反向静默放行侧于 2026-10-03 发生过一次（并行会话已暂存 32 个 `plugin/web/**` 文件，我的提交消息项含 `plugin` 一词、且漏写 pathspec，致其被一并提交，后经重写历史完全移除）**。经验何时可信：K1 双向覆盖校验在 Git Gate 中生效且 09 号提交契约的路径覆盖规则未变的期间；校验移除或契约改版后本经验过时（见 trigger_signal）。**特别提示**：本经验的「规避」第 1 项（显式 pathspec）在任何情况下都应执行——反向半边对同目录词污染**无防护**，不能指望 Gate 在提交前替你发现。
