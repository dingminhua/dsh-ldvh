# 共享Index被他方提交清空致暂存内容被挤出

## 症状

预检报 `git/index_empty`，本会话刚 `git add` 的两个事实载体不在暂存区；工作树内容仍在，但提交范围为空。

## 触发条件

两个会话在同一仓库的同一共享 Git Index 上交错操作：本会话先 `git add` 未提交，另一会话在 14:16:12 用同一个 Index 完成提交 `83e72a1`，该次提交把暂存区一并清空。

## 根因

Git Index 是仓库级共享单例文件，不是按会话隔离的。任一会话执行提交会清空整个暂存区，因此并发会话的提交动作会把他方已入暂存的改动一并挤出——改动本身不丢失，只是暂存状态被清空且无告警。

## 解决

在预检失败后重新 `git add` 两个载体再跑预检，第二次预检 `mechanical_outcome=passed`，随后提交 `60648f2` 成功（2 files changed, +70 / −0）。

## 规避

依赖暂存区状态判断提交范围前，先用 `git status --short` 核对暂存内容与预期一致；预检报 `index_empty` 时先排查是否存在并发的他方提交动作，而非直接判定为改动丢失或通道异常。

## 验证

已观察到：重新 add 后预检通过，`60648f2` 提交落地，`git status --short` 无输出（工作树清空）。未覆盖：同一时间窗内并发提交持续发生时的反复 re-add 行为未观察；也未观察是否存在其他会话同样处于被挤出暂存区的风险面。

## 影响与适用范围

影响与适用范围：作用域限于同一仓库内共享 Git Index 的多会话并发场景，影响的是暂存区状态而非文件内容本身；单会话独占仓库时无此现象。
