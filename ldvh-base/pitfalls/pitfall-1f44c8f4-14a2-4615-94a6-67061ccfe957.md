# 预检条目匹配规则无权威表述致反复打回

## 症状
同一轮受控提交里，提交预检连续三次拒绝：补齐 `关键变更:` 章节与签名尾注后仍拒；把描述改成贴代码原文、Provider 改成 workbuddy 后仍拒，报错称无法把条目匹配到字节级差异；直到每条列表项写入被改动的文件路径才通过。

## 触发条件
向预检提交 `关键变更:` 章节时，每条列表项只写改动语义描述、不写对应的被改动文件路径，且描述文字与暂存差异中的字面文本不一致；项目确实存在暂存差异。

## 根因
预检对 `关键变更:` 每个列表项的判定要求「条目文本与某个被改动路径存在匹配关系」，只写语义描述而不含路径即不通过。需更正原判断「这条规则没有权威声明」——按 specs/06 §6.1，条目与 diff 的逐条对应本来就属明文要求，实现侧亦有对应落点（`plugin/lib/commit-validation.js` 的 `itemMatchesPath` 与 `checkKeyChangesAgainstDiff`）。真正的缺陷不在「规则未声明」，而在**规则的机械可判定片过窄且未在报错中说明如何满足**：`itemMatchesPath` 只接受条目文本包含完整路径、包含去掉扩展名后长度大于 2 的文件名主干、或包含路径段词根；UUID 类主干因含数字被 `!/\d/` 过滤，因此「写 UUID 短号」这类看似命中的写法仍不通过，而报错只说「no staged change corresponds to …」，不说明可接受的匹配形态。

## 解决
在 `关键变更:` 每个列表项里直接写出对应的被改动文件路径，并在条目内贴上与暂存差异一致的代码原文，Provider 写权威记录中的 workbuddy；本次涉及的三个文件为 `plugin/lib/friction-watermark.js`、`plugin/lib/lifecycle.js`、`plugin/test/friction-watermark.test.mjs`。补齐后预检通过，随即完成提交 `6ae8cef`，Git Gate passed。

## 规避
起草提交消息前先确认预检的实际判定逻辑（读实现或先跑一次预检），不要从报错字面反推规则；`关键变更:` 每项先落**完整文件路径**（不要只写 UUID 短号或文件名主干，前者会被数字过滤规则排除），再补语义描述；描述贴代码原文而非概括；Provider 一律取权威记录值而非凭印象。

## 验证
已观察：43/43 测试通过；预检通过；提交 `6ae8cef` 成功且 Git Gate passed——即「条目含被改动文件路径即可通过」这一路径在本次提交形态上生效。未覆盖：同一次预检中 Provider 与签名尾注是否另有未声明规则、第二轮「贴代码原文」是否单独必要，均未单独验证；其它提交形态（如新增文件、纯删除）下是否复现同类打回未观察。

**处置（2026-10-19）**：判 discarded。原根因段的核心断言「匹配规则在调用侧可读到的规则里没有声明」经核对不成立——条目须与暂存差异逐条对应是 specs/06 §6.1 的明文要求；本条实际踩到的是既定规则的**机械可判定片**（`itemMatchesPath` 的三档匹配形态）在报错中未说明如何满足，这属于该判据的实现可用性问题，与同批 `1a1f2d8f`（块结构规则无权威源致预检反复打回）指向的「规则表述与机械判定之间的落差」是同一机制的不同侧面，本条的机制表述与结论方向均有误，不再作为独立经验留存。可复用的实操结论（每项写完整文件路径、不写 UUID 短号）已在本条「规避」段保留，供后续以正确机制表述重新提案时复用。

## 影响与适用范围
影响所有经 Git Gate 的受控提交起草环节——每次起草 `关键变更:` 的调用方都要靠失败反推规则，打回轮次随提交次数线性累积。
