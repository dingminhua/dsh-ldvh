# 裸 git 安装因仓库根无清单被判无组合包

## 症状

在 DSH 插件管理页填 GitHub 仓库地址 `https://github.com/dingminhua/dsh-ldvh` 安装 dsh-ldvh，报「插件安装失败：这个包没有声明组合包，无法作为插件管理」，安装中止。

排障时先出现一重误导：官方 npm 源与镜像上的 dsh-ldvh@1.0.3 manifest 都带完整的 `dsh.bundle`（`{"bundle":{"patch":"./cordis.patch.yml"}}`），包本身没坏。真正的差异在安装产物：pnpm 从裸 git URL 安装后把整仓 clone 进 `node_modules/dsh-ldvh/`，该目录根上没有 package.json，pnpm 于是把包版本标为 `0.0.0`；DSH 安装后检查 `node_modules/dsh-ldvh/package.json` 的 `dsh.bundle` 落空，才给出「没有声明组合包」。

## 触发条件

同时满足三项即触发：

1. 仓库为双目录布局——仓库根没有 package.json，真正的包清单与 `dsh.bundle` 在子目录（本案为 `plugin/package.json`）；
2. 安装入口接受裸 git 地址，并由 pnpm 以 git 依赖方式安装（DSH 插件管理页即此路径）；
3. DSH 安装后在安装目录根部检查 `dsh.bundle`，而 pnpm 的 git 依赖物化只认仓库根清单。

对照：同为 git 地址安装、可正常工作的 dsh-connect-workbuddy，其仓库根有 package.json。

## 根因

主因是**清单读取位置与物化位置不一致**。pnpm 对 git 依赖的处理是「clone 整个仓库 → 在仓库根读 package.json → 按该清单物化」。仓库根无 package.json 时，pnpm 不报致命错，而是当作物化一个无清单的目录（版本记为 `0.0.0`），把子目录的 `plugin/` 一并带进去。DSH 的组合包检查则是在安装目录根部找 `package.json` 的 `dsh.bundle`，两者对「包根在哪」的假设不同，于是清单明明存在、检查仍落空。

第二层是两条看似自然的旁路都不成立：

- **根加 package.json + prepare 脚本**（安装期把 `plugin/` 铺到根并构建）：pnpm 直接拒装，`ERR_PNPM_GIT_DEP_PREPARE_NOT_ALLOWED`——git 依赖的 prepare 构建脚本必须在 `onlyBuiltDependencies` 白名单里，而 DSH 安装器不会替用户配置该白名单。这与 issue #3（tsx/esbuild 的 postinstall 被 pnpm 11 审批门拒，见 commit bb3a0f8d 移除 tsx/esbuild）同源：任何依赖安装期构建脚本的路径都会撞上同一道审批门。
- **加 `#path:plugin` 片段**让 pnpm 只从子目录装：即使装上也是残包。`web/dist`、`web/api-js`、`web/shared-js` 是构建产物且被 gitignore——`plugin/web/.gitignore` 长期忽略 `dist`，1.0.3 起连 `api-js`/`shared-js` 也一并忽略（这三者靠 `.npmignore` 未排除才进入 npm 包）。只装子目录得到的树缺这些产物，装上了也跑不起来。故「加 #path:plugin」单独不成立。

## 解决

已实测成功并随 1.0.4 落地（commit 88bb6e59，发布树）：**仓库根放一份薄壳 manifest，并让构建产物在发布树入库**。

- 根 `package.json`：`dsh.bundle.patch` 指向 `./plugin/cordis.patch.yml`，`main`/`exports` 指向 `./plugin/lib/*`，`dependencies` 复制自 `plugin/package.json`（版本 1.0.4）。
- 构建产物强制入库：`plugin/web/.gitignore` 在发布树移除对 `dist`、`api-js`、`shared-js` 的忽略并注明「发布树（main）：三者需入库」；dev 分支仍保留忽略，避免日常构建弄脏工作区。git 安装 clone 下来即得可运行包，无需安装期 prepare。
- 运行时零改动：`plugin/lib/index.js:21` 的 `PACKAGE_ROOT = dirname(dirname(fileURLToPath(import.meta.url)))` 在 git 安装布局下仍解析为 `node_modules/dsh-ldvh/plugin`，`webRoot`（第 256 行，`join(PACKAGE_ROOT, "web")`）等路径全部沿用，不需要按根清单位置改代码。

成功信号：`pnpm add https://github.com/dingminhua/dsh-ldvh` 装出 1.0.4，安装目录根 manifest 的 `dsh.bundle` 齐全、`plugin/web` 产物完整，后端子进程 health 200。

## 规避

1. 双目录布局的仓库若要支持裸 git 地址安装，**必须在仓库根声明 `dsh.bundle`**；不要在子目录清单里假设 pnpm 会发现它。
2. 不要用 prepare/postinstall 类安装期脚本绕过——git 依赖的这些脚本会被 pnpm 审批门拒（`ERR_PNPM_GIT_DEP_PREPARE_NOT_ALLOWED`），DSH 安装器不代配白名单。
3. 不要只加 `#path:<subdir>` 就觉得解决了：先确认该子目录的构建产物是否入库，否则得到的是残包。
4. 产物入库要划发布树与 dev：发布树放开忽略、dev 保持忽略，避免日常构建把产物改脏工作区；这要求发布流程有白名单机制承接（本仓为 main 发布树）。
5. 排障顺序：报错文案「没有声明组合包 / declares no dsh.bundle」只带包名、不带安装源和版本，容易被误读成包坏了。先对比（a）官方源 packument 的 `dsh.bundle` 与（b）git 装出来的 `node_modules/<name>/` 结构——若（a）有、（b）根上无 package.json，即本条。

## 验证

实测确认（主控当次，材料所述）：裸 git 安装报「没有声明组合包」；官方 npm 源与镜像的 1.0.3 packument 带完整 `dsh.bundle`；git 装出的目录根无 package.json、版本 `0.0.0`；根加 prepare 的原型被 `ERR_PNPM_GIT_DEP_PREPARE_NOT_ALLOWED` 拒；1.0.4 落地后 `pnpm add https://github.com/dingminhua/dsh-ldvh` 成功，`dsh.bundle` 齐全、产物齐全、后端子进程 health 200；`npm pack --dry-run` 220 文件不受影响、`require-web-dist` 通过。

本代理对仓库侧的核对：commit 88bb6e59 的根 `package.json` 确为所述薄壳字段；`plugin/web/.gitignore` 在该提交中移除 `dist`/`api-js`/`shared-js` 忽略并加注释；`plugin/lib/index.js:21` 与第 256 行的 `PACKAGE_ROOT`/`webRoot` 计算与上文一致；当前 dev 分支仍无根 package.json、且仍忽略三者，即修复只存在于发布树——这正是「dev 保持忽略、发布树放开」的落地形态。

未覆盖：未复核 DSH 安装器检查 `dsh.bundle` 的具体代码行与报错文案来源（文案取自材料）；`#path:plugin` 未真正执行过一次安装、其残包结论依据「产物被 gitignore」这一事实推断；prepare 被拒只据材料的实测回执，未复现；未验证 https 远程 clone 与 file:// 本地路径之外的其他安装方式、Windows 平台、其他 pnpm 大版本，也未验证根薄壳未复制 `peerDependencies`/`icon`/`bin` 是否带来安装后的能力缺失；未验证 npm 源安装路径在新布局下是否受影响（推断不受影响，因 npm 包内容由 plugin/ 打包）。

## 影响与适用范围

适用于「包根在子目录（如 plugin/）、仓库根无 package.json」且以裸 git 地址（https://github.com/<owner>/<repo>）安装的 DSH 插件；此时 pnpm 把整仓 clone 到 node_modules/<name>/、读不到根清单，DSH 组合包检查落空而报「没有声明组合包」。若仓库根本就有 package.json（包根＝仓库根），本条不适用；「给 pnpm git 依赖加安装期构建脚本会被审批门拒」一节对任何场景的 git 依赖均适用。

展开：受影响的不只是 dsh-ldvh 一个仓库，凡 monorepo/双目录布局、发布物由子目录构建、又希望支持 `dsh plugin add <git URL>` 的插件都在同一机制下。npm 源安装不受本条约束——那里打包的是子目录清单，`dsh.bundle` 与产物由 `files`/`.npmignore` 决定，与仓库根布局无关。产物入库的要求另有代价：发布树与 dev 的分叉必须由发布白名单维持，否则要么 dev 工作区被构建产物污染，要么发布树缺产物重演残包。本条不解释 npm 安装失败或「包本身缺 dsh.bundle」的报错——那属于另一类问题，须回到 packument 核对，不能套用本条结论。
