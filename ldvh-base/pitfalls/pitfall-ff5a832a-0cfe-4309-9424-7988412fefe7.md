# 删除唯一生产者后幽灵形参残留致派生恒空

## 症状
`plugin/lib/friction-discovery-provider.js` 的 `existingPitfalls` 成为幽灵形参：`:332` 的调用点恒传空数组（`build({ threshold, candidates, existing: existingPitfalls ?? [] })`），`:348` 的 `existing_pitfalls` 恒记 0（`existing_pitfalls: existingPitfalls?.length ?? 0`），而 `:324-331` 的注释仍在讲「经验积累的查重前提为空与确实没有既有经验无从区分」——该前提已随生产者被删而不再存在，注释成了错误解释。

## 触发条件
删除 `idle-checkpoint.js` 的「既有 Pitfall 前提」段（使 B′ 捕获段不再查重）之后，未同步清理下游 provider 侧的形参、调用点、派生字段与注释；该形态与本仓库 2026-10-17 已清退过一次的 `sessionSignature` 幽灵形参同型。

## 根因
`existingPitfalls` 的唯一生产者被删除后，provider 侧仍按「有生产者」的结构保留该形参及其两处派生（调用点传参、onRun 痕迹计数），签名本身成了恒空来源；由于 provider 不在当轮其它任务的写范围内，静态检查与自测都不会因「参数无人传」而失败，问题只有在人工做存量残渣核查时才会暴露。

## 解决
已实际执行选项 A：删掉 provider 签名中的 `existingPitfalls` 形参；`:332` 改为只传 `{ threshold, candidates }`；`:348` 删除 `existing_pitfalls` 字段与相关注释；三个测试调用点去掉 `existingPitfalls: []` 空数组。

## 规避
凡删除某个值的唯一生产者，须在同一轮内沿「形参 → 调用点 → 派生字段 → 注释」四点逐点核查下游；对不在当轮写范围内的载体（如本例的 provider），保留一次存量残渣核查：按名搜形参 → 查调用方是否仍传值 → 查派生是否恒空/恒零。

## 验证
已观察：`provider + lifecycle + idle-checkpoint + registry` 四个测试文件 85 项全绿。未覆盖：task-6 尚未完成，全套回归（基线 1762）仍带两个与本次清理无关的 fail，故本次改动未在全量回归层面得到确认；仓库内是否还存在其它同类幽灵形参未做全量普查；旧提案文档 `docs/idle-experience-capture-proposal-2026-10-16.md` 仍为单段式旧设计，未据其核对是否残留同类陈旧前提。

## 影响与适用范围
仅限 friction-discovery-provider.js 的 existingPitfalls 形参与其派生点、注释；本仓库经验积累两段式改造（删除 idle-checkpoint.js 既有 Pitfall 前提段）引发的同类残留。
