# 候选入参凭印象拼装致预检缺字段失败

## 症状
受控提交预检被判定不通过；修正补上缺失字段后，同一份预检立刻通过，工作区内容本身并无问题。

## 触发条件
对尚未提交过的新增文件构造 workcase 候选对象，直接调用受控写入的预检通道，未先核对预检入参模式所要求的全部必填字段。

## 根因
候选对象的入参是按使用经验凭印象拼装的，凭印象认为已有的字段即全部字段，遗漏了预检模式中要求的 `summary`；预检按其模式校验，把缺失字段如实判为不通过，从而在写入发生前把缺口暴露出来。

## 解决
在写入任何候选对象之前先执行一次只读预检；预检不通过时不反复猜测，而是把预检指出的缺失字段补进入参后重跑预检，确认通过才执行实际写入。

## 规避
凡是通过受控写入通道创建对象，先跑同参数形态的只读预检；预检入参以预检模式自身列出的必填字段为准，不以「以往写过什么」为准。

## 验证
已观察到：预检拦下缺失字段、补齐后预检通过；同一动作在无此缺口的入参下不会触发该失败。未覆盖：预检未覆盖的字段缺失仍可能直到写入或更晚才暴露，未在本材料中被观察。

**机械化承载（2026-10-28 盘点）**：`plugin/lib/workcase-tools.js:673` 的 create 分支（先跑 `precheckWorkcaseCreate` 再取 Human 路由答复）＋ `plugin/test/workcase-precheck-create.test.mjs`（「候选机械不合格时宿主询问入口零调用」等 13 例）已把「先跑同参数形态的只读预检」实现为机械判据：删掉该闸后该例转红；工具参数 schema（`workcase-tools.js:1382` required: [title, summary, scope, plan]）在 handler 前经 DSH 的 `validateJsonSchemaValue` 拒绝缺字段的候选。覆盖边界：只覆盖 WorkCase 的 create 路径——spark/pitfall/adr/norm/friction/research 无只读预检入口，缺字段只能到写入时被同一 validator 拦下；schema 的 required 只管「字段在不在」，「非空」判据仍只在 writer 侧，且 schema-writer-agreement 用例只断言「writer 字段集 ⊆ schema 属性集」，不覆盖必填性。

**规范补写进展与遗留（2026-10-28）**：已在 `specs/02` §10.1「共同前提」新增「写入前的入参核对」——受控写入的对象入参须以该类型规范登记的必填面为准，不以「以往写过什么」为准，也不以工具的入参声明为准（工具声明是契约的实现，不是权威）；必填面分两处取：字段级取该类型规范 §12.1 第 4 项「字段契约」，入口参数取「受控操作」一节登记的请求项，两处都只约束**调用方提供、非托管**的字段；工具声明与类型规范不一致时以类型规范为准并报告漂移，比对面须写明；类型规范未登记必填面时按「未确认」处理并 fail closed；有预检入口的通道写入前须先跑与写入在对象内容上等价的预检并按指出的问题修正后重跑，预检结果不可判定时按未通过处理；无预检入口或未声明者在交还中登记为未兑现范围，登记不等于免除核对。§13 补「写入前的入参核对」验证行，§1 补负担 (e) 与风险 (e)。

该处经**三轮代理独立审核**（隔离子代理），**终审仍判 `needs_revision`**：
- 第 1 轮 4 blocking：① §1 风险清单**整段重复**（作者改负担段时把 (a)–(d) 又贴了一遍，(a)–(d) 各出现两次）；② 正文写「若提供只读预检」（条件义务）而 §13 行写「已跑过」（无条件）；③「以预检模式自己列出的字段为准」无指路、不可判定；④「预检不可用」未定义、以披露替代义务（与 00 §5.6 冲突）、未覆盖 `unverifiable` 三态。
- 第 2 轮：唯一 blocking——作者把依据定为「工具定义／模式」，而 `05 §3.3` 明写「实现、缓存、**工具描述**、测试与 Web 不得反向创造第二规则源」，且同一张 §13 表两行指向不同载体；「唯一依据」与「可由类型规范覆盖」自相矛盾；「更严的一侧」无判据（A 必填 vs B 必填时无法判定）。
- 第 3 轮（终审）：仍判 `needs_revision`——作者的修法（落回类型规范）方向正确，但「**入口契约**」一词全仓只在 02 出现 7 次且**从未定义**；20–27 真正登记必填面的是 §12.1 第 4 项「字段契约」（字段级、含托管方），不是入口参数面；05 §6.1 的 `arguments_contract` 在 20–27 一份都没有声明。故「据以判断一致/漂移」的比对面落空。作者随后按审核给的最小修法指名载体（字段契约 + 受控操作登记 + 排除托管字段 + 写明比对面）并修了 fail-closed 括号与 §1(e) 指针。

**遗留（按 01 §12.4 登记；终审 `needs_revision` 后的修法未再送审，不得据此声称本条已获充分验证）**：
1. **「入口契约」一词在 02 内有两义且无定义**（存量）：§10.5 末段与 §13「通道判定」行用它指「各类型**字段通道**的具体名称与形态」（如 `frontmatter_after`，实际登记在 21 §14 等受控操作条文），而本条用它指「必填面」。本轮只把本条的用法改为指名段落，**存量三处未动**——它们是既有体例，改动面超出本条范围。引用时须知二者不同指。
2. **§13 新行密度偏高**（约 1100 字符，原表最长行约 730），审核建议按「表格行宜短、细则留正文」的口径压缩。
3. **候选同一性在 WorkCase 通道上的口径**：工具把 `expected_candidate_fingerprint` 设为可选；未提供时，「写入内部对同一份 draft 复跑预检」是否算作同一性核对，21 未明写。
4. **`partial_scope` 是语义槽位而非已登记字段**：02 §10.8 明说该结构是交还语义示例，不是对 CLI envelope 的字段登记；当前实现不产出该名（用 `scope.not_completed` + `gaps`）。本条把它当承载位是可行的，但「登记」二字偏强。
5. **「有预检入口」目前靠条文与实现观察确定，而非声明**：21 §15.1 登记了 create 的只读预检，但未按 05 §6.1 的形状声明为 `operation_key`，能力发现会把它报成「已实现、未声明」。
