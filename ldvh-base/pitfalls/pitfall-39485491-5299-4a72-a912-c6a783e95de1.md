# 跨 worktree 候选对预检工具不可见

## 症状

会话工作目录为 dev 树 `/Users/dmh2002/DshProject/dsh-ldvh`，候选改动却已在另一个 linked worktree `/Users/dmh2002/DshProject/dsh-ldvh-main-release`（挂 main 分支）的 Index 中：在该树 `git add README.md` 后 `git -C ../dsh-ldvh-main-release diff --cached --stat` 显示 1 file changed、26 insertions。此时调用 `ldvh_precheck_git_commit`（会话工作目录 = dev 树），返回 `mechanical_outcome: failed`，逐字引证（工具返回）：

> `issue: git/index_empty — candidate Index is empty`

并同时给出两条 `key_change_unmatched`「本次提交没有任何已改路径」。识别信号是：同一候选在该树自身看已完整暂存（`diff --cached` 非空），而预检却断言候选 Index 为空——不是候选内容问题，而是预检读的那棵树不是候选所在的树。

## 触发条件

候选改动在 linked worktree（或任何与 `exec.agent.session.header.cwd` 不同的树）里暂存，而预检工具按会话工作目录解析受管辖仓库后读取其 Index；多 worktree（发布树/开发树并行）的项目里，「在 A 树改、在 B 树开会话」是常态，因此极易触发。

## 根因

预检取候选 diff 的方式是 `plugin/lib/ldvh-tools.js:438` 的 `execFileAsync("git", ["-C", governed.project.path, "diff", "--cached", "--binary", "--no-ext-diff"], …)`，其中 `governed` 由 `plugin/lib/ldvh-tools.js:425` 的 `resolveGovernanceScope(dshHomePath, exec?.agent?.session?.header?.cwd)` 得出——即**会话工作目录所属的那棵树**；随后 `plugin/lib/ldvh-tools.js:451` 在 `diff.length === 0` 时 push 规则 `git/index_empty`（`plugin/lib/commit-validation.js:33` 定义为 `candidate Index is empty`）。

Git 的 linked worktree 各有独立 Index（位于 `.git/worktrees/<name>/index`），`git -C <会话树> diff --cached` 在结构上只能看到会话树的 Index。候选在另一棵树里，于是 diff 为空 → 报 `git/index_empty`，连带所有「关键变更须点名已改路径」的对应性检查都因 diff 为空而整批落空。这不是候选违反 09 §5.1，而是工具面无法表达「候选在别的树」。

## 解决

跨 worktree 的受控提交改由**该 worktree 自身的 Git Hook**（pre-commit / commit-msg）终闸把关，不在别的树调用 precheck。本次即在 `git -C ../dsh-ldvh-main-release commit …` 时由该树 Hook 输出 `LDVH Git Gate (pre-commit) passed` / `(commit-msg) passed`，提交成功。

同时必须**如实声明这绕过了 precheck 这一步**：Hook 与 precheck 是两个入口，绕过 precheck 意味着「预检」这一环对该候选没有跑过，不是「预检也通过了」；不得把 Hook 的 passed 表述成 precheck 亦已通过。

## 规避

在跨树提交前先确认「候选在哪棵树」与「预检会读哪棵树」是否同一棵：`pwd`、`git rev-parse --show-toplevel`、以及 `git -C <目标树> diff --cached --stat` 三者对照。不一致时不要用会话树的预检结果给该候选定性（它既不能否决也不能通过该候选），直接把终闸交给目标树的 Hook，并在交还 Human 时写明「precheck 未覆盖该候选」。反向的一次性核对：在目标树故意暂存一处可判定的改动，看会话树预检是否仍然报 `index_empty`，即可确认两棵树确实被分开。

## 验证

已观察（本任务主控交付材料 ①）：
1. 预检在 dev 树（会话工作目录）报 `git/index_empty — candidate Index is empty`，附两条 `key_change_unmatched`；
2. 同一候选在 `../dsh-ldvh-main-release` 树内 `git -C … commit` 由该树 Git Hook 判 `LDVH Git Gate (pre-commit) passed` 与 `(commit-msg) passed`，提交成功；
3. 两棵树提交后各自状态干净。

机制侧另经本仓源码核对：`plugin/lib/ldvh-tools.js:425`、`:438`、`:451` 与 `plugin/lib/commit-validation.js:33` 逐行印证「预检读会话树 Index、空则判 `git/index_empty`」。

## 影响与适用范围

凡在 linked worktree 里准备受控提交、却调用会话工作目录所属树的 ldvh_precheck_git_commit 的情形均适用；单工作树仓库、或候选暂存与预检调用落在同一棵树时不在覆盖内。

展开：何时可能踩到——多 worktree 并行（发布树 / 开发树 / 特性树）、会话由某棵树启动而候选在另一棵树暂存、或把「在 A 树跑预检、在 B 树提交」当作一次连续流程时。何时可信——预检结果只对它解析到的那棵树的 Index 成立；候选不在那棵树时，`git/index_empty` 不构成对候选内容的任何判断（既不证明缺失，也不证明违规）。与`pitfall-70ad6ff5`（验证命令沿用主仓工作目录致 worktree 改动漏检）属同一「cwd 决定操作对象」族但不同源：那条讲验证命令的假绿漏检，本条讲受控提交预检入口的假红阻断与 Hook 终闸的替代处置，且带「绕过须如实声明」这一交付义务。
