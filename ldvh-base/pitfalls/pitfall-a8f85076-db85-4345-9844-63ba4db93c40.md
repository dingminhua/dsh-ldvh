# 待裁定议题未先纵向核对规范源

## 症状

一条议题被登记为"开放、待 Human 裁定"（Spark `open`，或 `docs/` 待办表的一行），但该议题在其登记时**已被现行规范源正面回答**。可观察表现有三：

1. 后续核查者按 `question` 逐条验证时，发现规范原文已经给出裁定，且该裁定写入时间早于登记时间；
2. 该伪开放议题在 `docs/` 中繁衍出多条下游记录（待裁定表、优先级分档表、审核处置表各自的"待 Human 裁定"行），关闭时一并失实；
3. 议题最终不是因为"Human 作出了裁定"而关闭，而是因为"前提从未成立"而关闭——此时 Spark 自列的候选处置（扩维／维持／明确不划分）全部落空，正确落点是 `20 §9.2` 的第一种终态路径（无承接目标的否定处置）。

本仓实例：Spark `bdb9623d`（dimensions 七元组表达力缺口）。其三条前提经核查全部不成立——`01.Att.02 §2` 已裁定 `dimensions` 为能力轴、非业务系统镜像；§4 定该字段为可选故不存在"阻断"；`spec-registry.js` 的 `required: true` 只对根规范生效。该裁定由 `80ea2e0` 于 2026-09-11 写入，**早于 Spark 创建（2026-09-13）两天**，且已是 HEAD 祖先。

## 触发条件

同时满足以下条件的组合会触发该机制：

- **上游写入以"补充说明"形态出现**：规范条文的语义裁定以 commit 落在附件或条文之间（本例 `01.Att.02 §2` 第 49 行），而 commit message 只写"补充/说明 X 的语义边界"，未声明它终结了某条待办；
- **下游登记依据的是更早的状态快照**：拆分或登记动作引用的是"待办清单当时怎么写的"，而非"当前规范源实际怎么定的"；
- **跨类型载体**：裁定住在规范源（`specs/`），待办住在过程文档（`docs/`）或事实源（`ldvh-base/sparks/`），三者之间**没有机械同步机制**；
- **处置权前置**：议题被标为"待 Human 裁定"，使 AI 在登记时倾向于"如实转述上游，不自行判死"。

最易发生的时点：一次较大的批次改造之后（本例 `77d3703`/`80ea2e0`/`80e9524` 相近期落地），此时规范源已更新而待办清单尚未复核。

## 根因

**规范源与待办登记之间缺少"签发时重查"的核对环节，且现行规范未给该环节指定归属。**

具体地：登记一条 Spark 或待办时，`20 §13` 要求"创建前必须查重"——但 §6.2 的查重口径是**对照既有同类对象**（同题已开 Spark → 不新建），它回答的是"有没有别的 Spark 在管这件事"，**不回答"这件事在规范源里是否已经有答案"**。也就是说，查重是**同层横向**的，缺少**向上纵向**的核对（对象面向其 `question` 所涉规范条文的核对）。

第二层根因是**效力分层造成的盲区**：规范源与过程文档效力不同（前者构成规则效力、进机械校验；后者不进），这是正确设计；但它同时意味着规范源的更新**不会**在过程文档侧触发任何机械告警，于是过时陈述可以长期静置，直到有人重跑一遍核查。

第三层根因是**commit message 未承担语义终结的声明义务**：`80ea2e0` 实际终结了 N-2，但 message 只描述"补充语义边界"。规范源没有条款要求"某次修改若终结了既有待办，须在 commit message 或某处声明"，故该信息只存在于 diff 里，需读者主动比对才能发现。

**已观察与未知的区分**：上述三层中，第一层（查重口径为同层横向）与第三层（commit message 无终结声明义务）经条文原文核对确认为现行规范的实际状态；第二层（无机械同步）同样是实际设计。**未确定**的是：本次是否应通过新增规范条款来补"签发时重查"环节，还是仅作为操作纪律要求 AI 在登记时先横向+纵向双查——这属规范修订判断，超出本经验范围。

## 解决

本次采用的处理方式：**在关闭该 Spark 时，先逐条回溯其前提并对规范源原文取证，再据此选择终态路径**。

具体做了三步：

1. **逐条核验前提，而非复核结论**——把 Spark 正文的断言拆成可机械复查的条目（"无法表达六系统"、"至少两份无维度可声明会阻断校验"、"04 只能全列"、"`spec-registry.js:24` 机械强制"），每条都回到规范原文与代码原行去证伪或证实；关键是读**代码实际分支**而非正文对代码的转述（本例发现 `required: true` 只在 `isRoot` 内）。
2. **对裁定取时间证据**——用 `git merge-base --is-ancestor <commit> HEAD` 与 `git show -s --format=%ad` 确认裁定的写入时间与是否已在主线，从而区分"登记时尚未有裁定"（真·待裁定）与"登记时已有裁定"（伪开放）。
3. **按 `20 §9.2` 选路径**——前提不成立且无残余责任时，选第一种终态路径（`discarded`、**不写关系、不设承接目标**），而不是 `implemented`（本议题既未"落实"也未"交给 WorkCase"）。写入时按 §9.1 一并清除 `priority`。

**成功信号**：`ldvh_spark_write` 返回 `read_back: ok`，且 `disposition` 如实说明"前提已由 `<commit>` 推翻"而非"经 Human 裁定"。

**必要边界**：本解决**不**修复过程文档的失实陈述——那是 `docs/` 的时效纪律问题（本仓由 Spark `afc45279` 另行承接），本次只在 Spark 正文中如实登记该账实不符，不做越界改写。

## 规避

登记或复核一条"待裁定"议题时，按以下顺序核对：

1. **纵向前置检查（本经验的主要增量）**——在写 `question`/`intent` 或把待办登记为 `open` 之前，先就议题所涉的规范条文检索当前原文与其近期改动（`git log -S "<关键词>" -- <载体>`），确认"这件事在规范源里还没有答案"。**只做同层查重不足以发现本机制**。
2. **区分待办出处**——若登记依据是"某份待办清单当时这么写"，须标注该清单的快照时点，并把"清单陈述"与"规范源现状"分别对待；不得把清单的历史陈述当作当前事实。
3. **commit message 承担终结声明**——修改规范条文若实际终结了某条既有待办/Spark，在 commit message 或变更说明中明写"本改动终结 X"，避免裁定只存在于 diff。
4. **关闭伪开放议题时选对路径**——不要因为它"曾被标为待裁定"就想象一个 Human 裁定；前提不成立即走 `20 §9.2` 的否定处置，并在 `disposition` 中写明推翻它的 commit，便于后人免于重跑核查。

**例外**：若议题的 `question` 本身是"要不要新增规范条款"（而非"规范现状是什么"），则规范源现状不能回答它，纵向检查不适用——此类议题应保持 `open` 直到 Human 裁定。

## 验证

**已观察**：本例完整走通——对 `bdb9623d` 的三条前提逐条证伪（含 `spec-registry.js` 的 `isRoot` 分支核对、`80ea2e0` 的祖先关系与日期核对、21/25 的现行 `dimensions` 实值核对），受控写入 `discarded` 并通过精确回读。登记时确实存在四条 `docs/` 下游失实记录，逐一确认其位置与现述。另一佐证：同一父对象拆出的 `3c20a739`（N-1）已 `implemented`，证明此类伪开放议题不止一例。

**未覆盖**：

- 未验证本机制在**其他类型**（ADR/Norm/Friction/Research）的登记中是否同样发生——本次仅观察到 Spark 一例；
- 未验证"纵向检查"若被制度化，其成本与漏检率如何——单人单例，无统计意义；
- 未验证过程文档的失实陈述在实际使用中是否真的误导过读者（未见错误决策归因于此）；
- `bdb9623d` 关闭后遗留的父对象 `split-into` 指向非 `open` 子议题的形态（`2916e3d5` → 已关闭的 `bdb9623d`），其规范归属未见条款定义，本次未处置。

## 影响与适用范围

适用于本仓（LDVH 自举仓库）中一切「待 Human 裁定」类条目的登记与复核：Spark 事实对象的创建与拆分、`docs/` 待办清单的登记与维护、以及关闭此类议题时的终态路径选择。凡议题的 `question` 是「规范现状/机制是否如此」而非「要不要新增规范」的活动，都可能落入本经验；经验可信复用的边界是——本经验只保证「先纵向核对规范源再登记」这一纪律的收益，对该纪律的制度化成本与跨类型普适性不作断言（见「验证」未覆盖项）。

经验来源为当次行动的实际失败观察与验证：对 `bdb9623d` 的核查与关闭过程，内部证据见「症状」「解决」「验证」三段所引 commit 与文件位置，不另附外部 HTTP(S) 来源。
