# 适配宿主 0.2.2-rc.2 的子代理派发形状

## 背景

宿主 0.2.2-rc.2 的上游提交 `575606a356`「refactor(subagent): flatten activation task options」把 `subagents.startActivation` 的激活任务选项由「带一层 `request`」改为「平铺在 spec 顶层」，实现随之由读 `spec.request.parent` 改读 `spec.parent`。本插件三处派发调用（建前自动审核、闲时摩擦发现、经验审核）仍按 rc.1 的内层形状传参，宿主读到 `spec.parent` 为 undefined 即抛 `Cannot read properties of undefined (reading 'id')`，三条子代理链路在第一跳全部失败。更有欺骗性的是：五处测试替身把旧内层形状写死并断言，其中一处还把它记成「SubagentActivationSpec 的形状，宿主 0.2.1-rc.1」，故测试全绿而缺陷不可见。摩擦账目 `friction-6e7421ce`「回归用例以虚构形状编码宿主语义致修复受阻」已于 2026-10-28 销账，其处置自陈「存量夹具的逐份核对无机械清单，靠后续修复时按 06 §5 逐次执行」——本次撞上的正是它声明的残留。

## 做法

按「上游更新跟进规程」七步执行：先取机器可读消费面清单与契约差分（`plugin/scripts/host-contract-diff.mjs dsh-v0.2.2-rc.1 dsh-v0.2.2-rc.2`），再逐条判定消费面，然后只改 startActivation 的调用点，最后按 `specs/06` §5「断言须以被测面的真实形状为准」同步测试替身并补形状守卫。三处调用点（`plugin/lib/workcase-auto-audit.js`、`plugin/lib/friction-discovery-provider.js`、`plugin/lib/experience-review-stage.js`）的 `request` 内层拆平为 spec 顶层的 `prompt`／`parent`／`outputSchema`；五处编码旧形状的测试替身（`friction-discovery-provider.test.mjs`、`experience-review-stage.test.mjs`、`aux-task-registry.test.mjs`、`lifecycle-checkpoint-path.test.mjs`，以及 `workcase-create-confirmation.test.mjs` 的审核体假件）改为断言平铺形状；另在三个文件各补一条形状守卫用例，断言 `spec.request` 不存在且 `prompt`／`outputSchema` 在顶层。摩擦发现处把旧形状记成权威的表述一并改正——独立复核查得该模块另有两处仍把旧内层形状当作当前形状（模块头注释写 `spec.request.outputSchema`、报错文案写 `spec.request.parent`），已分别改为 `spec.outputSchema` 与 `spec.parent`，并采纳复核提出的行宽建议把括号说明单独成行。

## 实测

- 契约差分：上游区间 1568 次提交、4645 个文件变更；服务面 107→108，事件面 88→94，客户端槽位键 109→114。
- 消费面三态判定：破坏面 1 条（`subagents.startActivation` 的 spec 形状）；须审面经逐条核对后判为对插件消费面无关——`agents` 变的是 `enter`／`isOwnedBy`／`roots`（插件只消费逐字未变的 `agents.get`），`tools` 变的是未消费的 `checkGuards` 返回类型（`tools.guard` 签名逐字未变，`ToolGuard` 返回类型扩为 `string | ToolGuardDenial | undefined`，插件返回值 `string | undefined` 仍在允许集合内），`userQuestions.ask` 签名未变仅描述变化，`subagent/end` 参数形状未变仅描述新增 `parentSessionId`；无关面为新增服务与事件、已删的 `officeToPdf`、未消费方法与槽位噪音字段。
- 测试：全量 3260 例通过（fail 0，skipped 19，todo 1）。
- 形状守卫检测力（单项变异，每项只改一个实现点，跑完即还原）：退回内层形状后 `friction-discovery-provider.test.mjs` 4 例转红、`workcase-create-confirmation.test.mjs` 1 例转红、`experience-review-stage.test.mjs` 7 例转红。
- 宿主四项实证（本次独立取得、不继承历史指认）：进程在跑（主进程 PID 27583）；GUI 与插件 web api 同在端口 `62525`，持有者为该 app 的 PID 27581，`/ldvh/api/health` 返回 HTTP 200；`CFBundleShortVersionString` 为 `0.2.2-rc.2`，asar 内 `@deepseek-ai` 下 339 个包中 328 个 `dsh*` 全部 `0.2.2-rc.2`；profile 为 `link:` 指向本仓库 `plugin/`（符号链接，非副本）。
- 独立复核（受管辖隔离子代理，全程只读）：三处调用点与上游 rc.2 契约一致（rc.2 `types.ts:29`、`manager.ts:312/401`、已装宿主实现 `:3024`），五处替身已改平铺；以三处同时退回内层形状的方式复验检测力，三条守卫用例全红、连带 8 条既有用例转红，还原后三文件 sha256 与 `git diff` 哈希逐字回到起始值；复核查得上述两处旧形状表述并经本轮改正，复查确认已清干净。

- 客户端槽位 occupant：`conversation.view` 的 `ldvh`（order=20）、`plugins.bundle.config` 的 `dsh-ldvh`、`plugins.row.config` 的 `dsh-ldvh#dsh-ldvh` 均在且 active。

## 结论与边界

宿主 0.2.2-rc.2 把 subagents 的激活任务选项拆平后，本插件三处派发调用已改为平铺 spec，五处编码旧形状的测试替身同步改写并补三条形状守卫用例（经单项变异检验确认可检出回退）；其余消费面经逐条核对无破坏，基线登记值已推进到 0.2.2-rc.2。适用边界：插件侧真机复验本次未取得——修复后的派发在运行中宿主上尚未发生（闲时检查点需静默 ≥300 秒且无回合在飞，建前自动审核需建单载体）；「运行实例是否已换码」不能由 mtime 推定，只能由实际派发结果判定。

本次已确认不成立的两项：一是「测试全绿即宿主契约无破」——测试替身可把旧形状锁死并误记为权威，全绿与真实形状无关；二是「本地开发工作流的基线登记停在 0.2.2-rc.1 即可」——该区间上游跟进规程从未执行过，规程本身是对的，漏的是执行。

未验证范围：三处调用点在运行中宿主上的端到端复验未做——修复后的派发一次都未发生（闲时检查点需静默 ≥300 秒且无回合在飞，本次会话的每次回合推进都把该计时取消；建前自动审核只在建单时派生，而本轮就此提请路由时 Human 选择直接执行）。上一轮据 `ldvh_inspect_loaded_modules` 的「mtime 晚于进程启动」断言「进程内仍是旧模块」，该断言本轮收窄：宿主启用了 `@deepseek-ai/dsh-hmr`（按 inode/size/mtime 热重载，监视范围含 `linkedRoots`），但其热重载对本插件的相对导入是否击穿原生 Node 的 ESM 缓存未得判定，故该工具输出只能读作「可能陈旧」，不能单独充当「进程内仍是旧码」的依据；`conversation.chat.node` 槽位的 `ldvh-notice` 键 occupant 本次因 Inspect 输出截断未取到；提问卡观感的真机样本最后取自 `0.2.1-rc.2`，在 `0.2.2-rc.2` 上仍未取得。

## 去向

本次跟进的两项产物各归其位：宿主适配结论汇入事实规范「本地开发工作流」（`norm-a1b559a6`）的目标环境与支持基线登记项；适配动作与其验证证据留在本条，不另立条目。本条服务于子目标「空闲积累与摩擦发现」。
