# B′ 留观缓冲方案独立审核：可行但需改动

## 背景

本条目承载一次独立审核的完整结论报告，报告原文落笔于 2026-10-20（13053 字符），是同日被审方向的**第二轮**审核，对象为收窄后的 B′ 方案；第一轮（observed 状态 + 宿主定时审核）的完整报告另有条目（见「去向」段）。迁移自未入库的本地工作目录过程文档（文件名 `review-plan-b-prime-plan-reviewer.md`）。**下列来源交代是普通叙述，不是可解析指针**（29 §10.2、§6.4 条件 4），源文档删除后仍可由 Human 复核出处。

- **被审候选**：经验积累方向的 B′ 方案六点——① 闲置增量捕获写本地留观缓冲（非事实源、非 fact_type）；② 审核动作以空闲锚触发，读 raw，证据够→建 23 knowledge draft（七段由证据写），不够→标 buffer discarded；③ 人只做 draft→active；④ 存量不动、缓冲从空开始；⑤ 改动清单（当时编号 36 §9bis/§10bis + 23 §13 + 02 边界 + 05 两工具 + 06 测试 + 代码 observation-buffer.js / observation-review.js）；⑥ 按 21 §6.3 走 WorkCase。该候选未进入规范源，也未建过工单。
- **属于哪一轴**：审核轴（规范变更／方案的独立审核，01 §12），不是复核轴（关闭前复核）。
- **审核者来源形态**：与候选形成方上下文隔离的只读审核执行体，报告末段自述「审核为只读：未修改任何规范、代码或事实对象，未调用任何 `ldvh_*` 写工具」。**这是 2026-10-20 的执行事实，不是 21 §8 `pre_reviews.auditor_origin` 的机械凭据**——分区覆盖闸与建前审核门禁彼时尚未建立（其落盘见 `devlog-bc4ba39a`），工单侧不存在与本报告对应的节点概要流水，故本条不与任何 WorkCase 互相援引（§6.4「两轴的形式权威不同，不得互相援引」）。
- **审核立场**：只判需求是否满足，现行规范冲突按「必要改动 / 可选收紧」分列，不做终审，不复述第一轮的 H1–H10 成本结论。

## 做法

审核体按「需求 7 条逐条判定 → 硬冲突（H-A 至 H-G，每条给 `spec:行` 与必须怎么改）→ 可选收紧（O-1 至 O-4）→ 缺口／未决（6 项）→ 数据／存量复核实测 → 最小改动集与顺序 → 必须 Human 决定的问题（H1–H8 表）→ 测试 → 风险（R1–R9）→ 最强反方论证（5 条）→ 报告文件」组织。全程只读。

报告正文**完整照录**于下一段（29 §6.4 条件 1；§18 红线 3 禁止同一结论同时留在普通文档与本类型里，故照录后源文档由 Human 另行决定删除）。照录保留原文措辞、编号、以及报告「报告文件」段里当时的本地过程文档路径——该路径属报告自述的一部分，不代为抹除，其性质由上文背景段声明（非可解析指针）。本段不复制审核的开销、轮次与工具流水（§6.4 条件 3）。原文层级下沉一级（原 H2 → 本段 H3，原 H3 → 本段 H4）以适配 29 §8 的五段骨架，内容与措辞未改。

## 实测

### 结论（报告原文首段）

**可行，但需改动（4 处必要改动 + 3 处可选收紧）。**

理由：B′ 在结构上是三条需求（捕获不打断主线、捕获/审核/采纳分离、人只采纳）的正解——它保留 Pitfall 三状态闭集、不引入宿主定时器、不新增事实类型，把「低门槛入口」放到事实源之外的本地缓冲；剩下的真实代价集中在**证据留存形态**与**缓冲定性**两件事上，它们必须写进规范正文（不能只写在模块注释里），且 23 §10 四前提的重定位不可省。

与上一版（observed 状态 + 宿主定时审核）相比，B′ 消掉了四个高成本项：新增 Pitfall 状态（23 §18 红线 1 直接冲突）、宿主无插件定时缝（10 §6 无该缝）、13 条存量 draft 与 45 个 Pitfall 的迁移、以及「留观库作为跨状态视图」的持久化归属难题。

### 需求 7 条逐条判定（任务 2 的第 ⑬ 问）

| # | 需求 | 判定 | 依据 / 缺口 |
|---|---|---|---|
| 1 | 捕获不打断主线 | **满足** | 捕获挂在既有 idle checkpoint 锚（36 §6.1 触发锚 + 二次确认空闲），复用现有增量窗口与派发节流；不新增 host timer，不新增同步调用点。 |
| 2 | 入口低不漏 | **部分满足** | 入口低：满足（准入放宽到 claim+scope+evidence+practice，四前提移到审核/采纳侧）。不漏：**部分**——增量窗口只覆盖上次成功水位之后的会话内容，跨多次会话才成形的大经验无法由单条 raw 承载；缓冲多条目 + 审核聚类能部分缓解，但审核方无对话上下文（只看捕获方挑过的材料），无法补跨会话因果链。 |
| 3 | 捕获/审核/采纳分离 | **满足** | 三段各有独立动作、独立失败处置；这是 B′ 的核心优势，原方案（定时审核）其实也是三段，B′ 的增量在于把审核锚从「日历」换成「空闲」，代价见风险 R1。 |
| 4 | 人只采纳 | **满足** | 唯一 Human Gate = draft→active（23 §16 第 1 项，前置独立复现）。捕获与审核均为自动动作，不产生需 Human 决定的结论（结论只是 draft 候选）。 |
| 5 | 知识质量据实 | **部分满足** | draft 七段由证据写、不凭记忆补、不读实时对话 —— 满足「据实」的方向。但**证据留存形态未定**：若缓冲只存「来源引用」而不存逐字引证，则审核与人采纳都无法核对，draft 的七段会退化为「捕获方的转述」，据实性无载体支撑（见 H-C）。另：active 前的独立复现仍依赖人安排，未安排时的处置须显式（23 §16.1）。 |
| 6 | 事实源不长新类型 | **满足** | 缓冲非事实源；Pitfall 状态闭集仍为 draft/active/discarded（23 §9 不动、23 §18 红线 1/4 不动）；F→P 走 body 溯源行而非 26 informs。前提：证据必须**逐字复制进 draft body**，否则权威对象的证据链挂在可淘汰的非权威载体上（见 H-D）。 |
| 7 | 改动量 / 风险 | **满足（明显改善）** | 无宿主定时缝依赖、无新状态、无存量迁移（45 Pitfall / 107 Friction 全不动）。剩余成本 = 36 §19.1 Gate + 23 §10/§15 修订 + 00 措辞判定 + 05 工具契约 + 3 个新模块。**唯一反向成本**：本方案落在「规范正在重做」的窗口内，可能与重做撞车返工（见 R7）。 |

### 硬冲突（须改，否则 B′ 在现行规范下不成立）

按 `spec:行` 列出。每条给出**必须怎么改**。

#### H-A（必要）buffer 存「对话片段 / 命令 / 输出 / 测试结果」触碰 36 §21 红线 5
- 规范：`36-闲时辅助系统规范.md` §21 第 5 条「不为证明任务已执行而保存完整消息、思考链、运行日志或第二状态账本」；§11「交付材料是运行状态，不进入事实源」。
- 冲突：方案把**原文对话片段、命令、工具输出**作为 raw 条目的 evidence 字段持久化。
- 必须怎么改：证据形态收窄为「**逐字引证片段 + 来源引用**（会话 id / 轮次 / 文件:行 / 测试报告路径）」，**不存完整消息、不存完整命令输出、不作为「证明任务已执行」的载体**。条目须声明用途是「供审核核对」，不是「留运行痕迹」。先例支持：`32-记忆存取系统规范.md.draft` §9.5 明确本地层**不保留原始对话**（不采纳 L0 归档），source 只需弱形式回指。

#### H-B（必要）缓冲的定性必须写进 36 正文，「工作产物 vs 运行状态」切法成立但现在只存在于口头
- 规范：`36` §6.4「当次作用范围限于观察区间与本次读取到的账目，运行结束即退出，**不设常驻状态**」；§11（水位不进事实源）；§12（待处置队列是宿主侧追加型登记载体、不进事实源、不构成事实对象）；§21 红线 5。
- 冲突：缓冲**跨运行持久**且承载语义内容（claim / evidence / dedup_key / status），超出现有承载的形态（水位 = 位置、待处置队列 = 异常登记、idle-checkpoint-runs = 环形结局）。这些都**不含语义内容**；缓冲含。这不是同一类东西，不能靠「同在 DSH home 下、同样不进事实源」一句带过。
- 必须怎么改：在 36 新增一节（建议 §12bis「跨运行工作产物」）**明文写**：载体路径、条目字段闭集、容量上限、保留期、唯一消费者、与水位/待处置队列的关系、以及禁止事项（不得作为稳定事实消费、不得承载运行状态、不得替代待处置队列）。模块注释里的理由段落不构成规范依据。

#### H-C（必要）23 §10 四前提与 draft 七段要求必须重定位，方案变更清单漏了 §10/§15
- 规范：`23-Pitfall-踩坑经验.md:172`（§10 四前提：失败已发生 / 根因已查明 / 解决已采用 / 验证已有观察，四项不齐**不创建**）；`23` §9（draft 必须满足与 active 相同的正文七段要求，不得占位符或「待查明」）；`23:254`（§17 必停第 2 项：以占位符或「待查明」标记冒充七段）；`23:227`（§15 验证表）。
- 冲突：B′ 让捕获不要求四前提、由审核「证据够」时创建 draft。若不改 §10，则审核建 draft 违反「四项不齐时不创建」；若不改 §15，则验证表「经验候选的七段完整」一行仍按旧口径取证。
- 必须怎么改：把四前提从**创建时**重定位到 **draft→active 前置**（写入 §16.1 与 §9.2），并在 §15 验证表区分「draft 七段按证据写、无占位符」与「active 满足四前提」。**注意**：不新增状态、不改 §9 状态闭集，因此 §18 红线 1（不设第二个中间态）保持不动 —— B′ 在这一点上是对的。
- 顺带核对：§4.3「未解决的问题（没查明/没解决/没验证）不该有 Pitfall」的措辞是否需加「以 draft 候选形态存在」的限定。

#### H-D（必要）draft 的证据必须逐字复制进 body，不能是指向缓冲的活指针
- 规范：`02` §7.2（每个对象只有一个当前权威载体；索引/缓存/Web 视图均为派生）；§16.3（不建立第二事实源）；`23` §8（正文固定 H2 七段 + 证据可选）、§6.1。
- 冲突：方案说「body 引用 buffer 条目/来源」。若 body 只写 `buffer:<id>`，则**权威事实对象的证据链依赖一个可淘汰的非权威载体** —— 这在效果上就是第二事实源，也使缓冲淘汰（容量/TTL）会静默削弱既有 draft/active。
- 必须怎么改：规则写成「**draft 七段内逐字复制所用证据与来源标识**；缓冲条目仅作来源指针，可随时淘汰而不影响 draft 完整性」。这条同时是需求 5「据实」与需求 6「不长新类型」的共同支点。

#### H-E（必要）05 的两个工具必须给逐字可寻址契约，否则等于未声明
- 规范：`05-LDVH CLI 确定性服务规范.md` §6.1（operation_key 为小写 ASCII kebab-case 全局唯一；`arguments_contract` / `result_contract` 必须回指 `<spec_key>::<H2 标题>` 或 `<H2 标题>/<H3 标题>`，**只写 H3 视为未声明**；解析失败须按 00 §5.7 暂停发现）；§6.2（五类 availability，**必须实际解析来源声明**，不得以常量代替）。
- 冲突：方案只说「05 list/review 两工具」，没给 operation_key 与两个契约锚点。
- 必须怎么改：至少两条：`observation-buffer-list`（read）、`observation-buffer-review`（may_change_state）；两条的 arguments/result 锚点必须是 H2 或 H2/H3 逐字标题；锚点写不全则按未声明处理，工具不得对外声称可用。

#### H-F（必要）「审核是否新增职责构成」须先判定，否则 00 是否要改悬空
- 规范：`00` §3.4（闲时辅助含反思摩擦、积累经验与记忆维护；**业务系统数量/名称/职责的增删改须修改 00 并由 Human 明确决定**）；§4.2（改变业务系统职责属根决定）；§4.3（00 为受保护内容：须展示现有内容与准确候选、说明差异与原因、经独立审核并取得 Human 明确同意、形成只含该文档的独立提交）；`36` §8（三项分工）、§19.1 第 1 项；`04` §237（闲时辅助的职责构成由 36 §19.1 第 1 项承接，不走 04 的根决定项）。

- 必须怎么改：把这条判定写进报告并列入 Human 决定清单 H1。若 Human 判为新职责，则 00 §3.4 走 §4.3 程序（独立提交）。

#### H-G（必要）36 的自动动作闭集确属变更，§19.1 第 4 项无法回避
- 规范：`36` §9（摩擦闭集 6 项，机械通道仅第 3、4 项）、§10（经验闭集 5 项，机械通道仅第 3 项「创建 draft 候选」）、§19.1 第 3/4 项（改变发起条件/机械校验范围/fail-closed 处置；改变闭集成员或机械通道范围）、§19.2（不得据某次决定主张范围已扩大）、§20.1 第 3 项（拟执行超出闭集即必停）。
- 冲突/确认：B′ 实际做的是「把 §10 第 3 项拆成『写缓冲条目』+『据缓冲建 draft』」，**闭集成员发生变化** → 触发 §19.1 第 4 项；若同时改了失败处置（水位推进、fail-closed、停点）再触发第 3 项。方案已声明「过 §19.1」，此处确认方向正确、不可省略。

### 可选收紧（非硬冲突，但建议一并做）

- **O-1 缓冲的载体不可写时必须 fail-closed**（照抄 `plugin/lib/pending-queue.js` 的既有纪律：队列不可写则该次任务不继续）。这是 36 §12 的既有要求平移。
- **O-2 缓冲与待处置队列解耦**：36 §6.3 规定「受影响对象有未完成核查队列登记时相关自动动作不得执行」；若缓冲与队列共用一个文件，这条会误伤正常捕获。两载体必须分开。
- **O-3 `pitfall-writer.js:385` 默认 active 必须先禁**：现状是 `frontmatter.status = requestedStatus ?? "active"`。捕获/审核通道一旦漏传 status，就会直接创建 **active** Pitfall —— 这同时违反 23 §9 与 23 §13「机械通道不得创建 active」。应改为「必须显式」+ 通道断言，作为**独立的第一笔改动**，先回归全绿再接新模块。
- **O-4 F→P 走 body 溯源行**：图边会同时撞 26 §11（informs 仅 resolved 写、目标类型 ADR/WorkCase）与 23 §11（Pitfall 不用 relations），即 02 §14.1 第 3 项「确定关系证据方案」的 Human Gate。走文本是**最小合法做法**，代价是失去图查询/反向索引能力；若要图边，须改两处类型来源并走 02 §14.1。溯源行须逐字可核并指向 Pitfall 的 object_uid（或标题+创建日期唯一化），由人在采纳时确认。

### 缺口 / 未决

1. **审核锚不是定时器，长期无会话即长期不审核**。需求里没有「定时」这一条，所以空闲锚够用；但必须补兜底触发（会话启动时清点 + 人工调用 `observation-buffer-review`），否则 raw 无限期堆积。
2. **缓冲无容量上限 / 保留期 / 淘汰规则**（方案未提）。无界增长的本地载体是实际风险；先例见 `32.draft` §9.3：容量上限 400 条、buffer TTL 30 天、importance=3 与 locked 保护淘汰。淘汰必须是机械的、可观测的，且淘汰动作要报数（否则又是「机制跑了但看不出」的老问题，见 `plugin/lib/idle-runlog.js` 头部说明）。
3. **buffer `discarded` 的可逆性与保留期未定**。它不是事实终态（无处置语义），但若审核误判（证据其实够），条目被丢即永久丢失。需要：保留期 + 可由人重开（重开属 Human 决定，走 pending-queue 或人工 review）。
4. **正面 / 成功经验仍无家**（任务第 ⑧ 问）。23 §4.3 只收失败机制；`32.draft` §7 明确「正面可复用模式确无家可归时按 01 §11 程序另议新类型，本规范不预留空位」（Human 决定 2026-09-10）。**这不是 B′ 的缺陷**：B′ 也没声称解决它。若 7 条需求里其实包含「成功经验要能沉淀」，则 B′ 不满足该条，须另走类型准入程序 —— 这一点必须回到需求侧确认，不要在方案里混着解决。
5. **首轮审核的 backlog 处理方式未定**：缓冲从空开始是对的，但首轮若手工喂入存量（尤其 13 条旧 draft 对应的原始材料并未进入缓冲），会出现「有 draft 无证据」的悬空。方案已定存量不动，建议明确写：旧 13 条 draft 的证据链保持现状，不补录、不回填。
6. **dedup_key 的可靠性**：由 AI 生成的弱去重键不能保证幂等。同一事实两次不同键 → 建两个 draft。可行做法是审核侧同时做 23 §6.2 的语义查重（对照既有 active **与 draft**，draft 必须纳入），并接受偶发重复、由人在采纳时合并。

### 最强反方论证（对 B′）

1. **「缓冲不是第二事实源」靠的是声明，不是结构。** 只要 draft 引用缓冲条目、且该条目可淘汰，它就在事实链上。唯一的结构性解法是证据逐字复制进 body —— B′ 目前只写了「body 引用 buffer 条目/来源」，这一句的两种读法（一律复制 vs 存指针）后果完全不同。若是后者，02 §16.3 实际被突破。
2. **质量下移且不可见。** 四前提门槛从「创建时」挪到「审核时」，而审核方的输入是捕获方筛过的材料 —— 缺的不是四前提，是**因果链**。捕获在一个窗口里记下「A 现象 + D 解法」，中间 B、C 两步没进缓冲，审核看不到，只能照着残缺的证据把七段写满。人看到的 draft 格式完整、内容半自造，而「据实」的判断依据（逐字引证）恰好被 H-A 收窄掉了。二者叠加是 B′ 最危险的组合。
3. **「人只采纳」把质量责任全部前移到无人负责的一侧。** 人只做 draft→active，且前置是「另一主体复现验证」—— 若无人安排独立复现，按 23 §16.1 属 Human 可决定处置，但默认路径容易变成「看到格式完整就签」。建议：draft body 强制列出「未覆盖 / 未观察」清单，人采纳界面必须逐项确认。
4. **捕获与审核共享同一执行体家族，独立性只在时间维度。** 23 §16.1 要求复现方「未参与候选形成」；若审核方与捕获方是同一套提示词 + 同一模型，跨时间不等于独立。B′ 应显式声明审核执行体的独立性判据（01 §12.2）。
5. **成本论证的反面。** 即便 B′ 改动远小于上一版，它仍要过两道 Gate、改 4 份规范、加 3 个模块。在「规范正在重做」的窗口内推进，返工概率不低。更稳的顺序可能是：先把 7 条需求写成可验收条目 → 等规范重做落地 → 一次性实现。
