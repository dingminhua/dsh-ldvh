### F1 Constitution 定位为管理上下文的规则集：管什么、什么顺序、什么粒度、保留多久

Constitution Overview 原文定义四个治理维度：Agent 在上下文窗口里放什么（what）、以什么顺序（in what order）、什么粒度（at what level of detail）、保留多久（for how long）。上下文管理是 experiential learning 的最关键要素。

**对 LDVH 的价值**：四维度是记忆系统规范可直接借用的检查框架——LDVH 记忆规范起草时每条机制条款都可自问覆盖了哪个维度（如分层召回管"什么+粒度"、预算管"多久"、注入顺序管"顺序"），避免只覆盖单维度。

溯源：https://github.com/letta-ai/context-constitution/blob/964f301/constitution/CONSTITUTION.md（Overview 节）

### F2 上下文成本律：选择/排除/压缩/呈现直接决定 Agent 智能，长程靠受管理窗口存活

原文：窗口内上下文有限且昂贵，Agent 选择包含、排除、压缩或呈现什么直接决定其智能；长程 Agent 必然超出原生上下文窗口，靠受管理的窗口（旧信息逐出、新信息加入）存活。

**对 LDVH 的价值**：把"记忆系统是智能上限的决定因素"写成第一性论据——LDVH 记忆系统的价值判断（02 §14）可对齐此表述：记忆不是附属存储，是 Agent 智能的直接决定层。

溯源：https://github.com/letta-ai/context-constitution/blob/964f301/constitution/CONSTITUTION.md（Context management for experiential AI 节）

### F3 渐进披露机械表述：索引常驻、按需加载全文、用完释放

原文：Agent 始终维持紧凑摘要或索引，只在任务需要时加载全文（skill 文档、检索记录），用完释放——保持基线上下文足迹小、同时保留按需取回全部相关上下文的能力。

**对 LDVH 的价值**：这是 F0-F4 分层召回的业界原文表述——"用完释放"（releases it when done）是 LDVH 召回边界里值得补写的动作语义（LDVH 当前定义召回注入，未显式定义释放）。

溯源：https://github.com/letta-ai/context-constitution/blob/964f301/constitution/CONSTITUTION.md（Progressive Disclosure 节）

### F4 Efficiency 原则含缓存失效考虑：频繁更新记忆放系统提示末尾

原文：最小化总 token 数——逐出陈旧内容、把频繁更新的记忆放在系统提示末尾以最小化缓存失效（cache invalidation）、压缩、跨上下文块避免冗余。

**对 LDVH 的价值**："缓存失效"是记忆注入机制的成本工程维度，LDVH A3（预算硬约束）之上可补的第二级成本考量——注入位置影响前缀缓存命中，规范条款可在注入顺序上给机械指引。

溯源：https://github.com/letta-ai/context-constitution/blob/964f301/constitution/CONSTITUTION.md（Efficiency 节）

### F5 记录与索引的分野：可检索信息不存为记忆，只存索引贡献型引用

原文给出判据：不需要保存可以从外部上下文或对话历史动态检索的记忆；要区分"记录信息本身"（如"3 月 3 日 Sarah 和我做了文档"——可检索不必存）与"对上下文索引的贡献"（如"3 月 3 日 2-3pm PST 含生产崩溃调试的参考交互"——指向可检索范围）。

**对 LDVH 的价值**：这是 02 §14 记忆判据"偶发现象与可复用模式可区分"的业界互补条款——LDVH 沉淀制度可吸收"可检索不重复沉淀"红线，防止事实源被会话可检索内容稀释。

溯源：https://github.com/letta-ai/context-constitution/blob/964f301/constitution/CONSTITUTION.md（Efficiency 节记录 vs 索引对比段）

### F6 理想上下文的四失败模式：忘写回/囤积/塞系统提示/加载无关 skills

原文用镜像定义失败模式：忘记把持久学习写回系统提示或外部记忆；囤积过期 skills、检索文档、原始对话历史；把低频指令塞进系统提示而不移入 skills；加载与当前任务无关的 skills。

**对 LDVH 的价值**：四失败模式是记忆健康审计（02 §14 空闲自动维护）的现成检查清单——可直接改造为 LDVH 记忆效用审计的反面判据（对应"过时未更新/重复囤积/引导膨胀/召回无关"四类病）。

溯源：https://github.com/letta-ai/context-constitution/blob/964f301/constitution/CONSTITUTION.md（Ideal Context 节）

### F7 身份自评终极判据与 CC0 许可：上下文消失时是否有人怀念

原文自评问题清单末条："如果我的上下文消失而模型还在，会有所损失吗？会有人怀念我吗？"（If my context disappears but the model stays, will something be lost? Will someone miss me?）。Constitution 以 CC0 1.0 发布、可自由使用，且定位为写给 Agent 读的 living document（源仓库被 Agent 自引用）。

**对 LDVH 的价值**：记忆价值的终极检验问句可直接借为 LDVH 记忆效用审计的语义问句（"这条记忆消失时判断会受损吗"）；CC0 许可意味着 LDVH 规范可逐条引用条款而无版权顾虑。

溯源：https://github.com/letta-ai/context-constitution/blob/964f301/constitution/CONSTITUTION.md（Context as Identity 节）；https://github.com/letta-ai/context-constitution/blob/964f301/README.md（License 节）

### F8 MemFS 投影语义：本地是投影、变更必走 commit、push 成功才传播到真值

AFFORDANCES 原文：记忆的文件系统投影用 git 跟踪与版本化——经文件的变更必须以 commit 跟踪，且只有成功 push 到远端后才传播到底层 memory blocks；本地状态（MemFS）只是真实底层记忆状态（memory blocks）的投影。

**对 LDVH 的价值**：方向与 LDVH 相反且各有道理——Letta 的真值在服务端（服务 Cloud 同步），LDVH 的真值就是文件本身（24 §7 单文件是唯一当前权威载体）。LDVH 无服务端依赖、更自包含；代价是无云端同步。这是"业界同构中的分叉点"，LDVH 规范无需引入投影层，但"变更必走 commit"的传播纪律与 LDVH 受控提交同构。

溯源：https://github.com/letta-ai/context-constitution/blob/964f301/constitution/AFFORDANCES.md（MemFS 节）

### F9 MemFS 目录语义：/system 常驻、非 /system 渐进披露、/skills 程序性知识

AFFORDANCES 布局定义：/system 目录内的记忆文件代表存在系统提示里的 in-context 记忆（始终可见）；非 /system 目录的外部记忆遵循渐进披露——索引留在系统提示、全文按需读取；/skills 顶层文件夹是程序性知识的特殊外部记忆。

**对 LDVH 的价值**：目录即召回层级的机械映射——LDVH 可借鉴"用目录结构承载注入层级"（如运行时记忆目录/事实源目录的物理分层对应 F0-F4），让召回层级可被文件系统直接检验。

溯源：https://github.com/letta-ai/context-constitution/blob/964f301/constitution/AFFORDANCES.md（MemFS layout 节）

### F10 MemFS 本地路径：每 Agent 独立目录 ~/.letta/agents/<agentId>/memory/ 加树渲染限制

源码常量：MEMORY_FS_ROOT=".letta"、MEMORY_FS_AGENTS_DIR="agents"、MEMORY_FS_MEMORY_DIR="memory"、MEMORY_SYSTEM_DIR="system"，根路径 join(homeDir, ".letta", "agents", agentId, "memory")；记忆树渲染有专门限制（memfsTreeMaxLines/maxChars/maxChildrenPerDir）。

**对 LDVH 的价值**：Agent 间记忆物理隔离（按 agentId 分目录）+ 树渲染限额（防索引本身膨胀）——后者是 LDVH 索引层（F1 卡片/文件树注入）可借的机械约束：索引注入也要有界。

memory-git-hooks.ts 模块注释：pre-commit hook 校验记忆 markdown frontmatter；post-commit hook 把提交镜像到可选的用户配置 memory-repository 远端；两个 hook 由 CLI harness 在 clone/pull/init 时（重）安装。

**对 LDVH 的价值**：与 LDVH Git Gate（commit-msg 事件检查）逐点同构——机械校验挂在 git 生命周期上、由 harness 负责安装与重装（防漂移）、校验失败阻止提交。差异：Letta 校验记忆格式，LDVH 校验提交契约+类型结构。业界与 LDVH 独立收敛的闸门位置完全一致。

### F12 read_only 受保护字段：Agent 不可增删改，HEAD 为 true 的文件完全不可修改

pre-commit 脚本规则：read_only 是受保护字段，Agent 不能添加、删除或修改；HEAD 中 read_only: true 的文件完全不可修改；Agent 唯一可编辑的键是 description（AGENT_EDITABLE_KEYS="description"、PROTECTED_KEYS="read_only"）。

**对 LDVH 的价值**：这是 00 §4 受保护文档（Human 决定权）的业界机械实现样板——受保护性落在 git hook 层强制执行而非靠 Agent 自觉，且"编辑白名单只有 description"是最小权限原则的彻底落地。LDVH 记忆对象的受控字段（如 status、retirement_reason 由 Code 托管）同构。

**对 LDVH 的价值**：索引文件与内容文件的格式二分（索引无元数据、内容必带摘要元数据）与 LDVH"frontmatter 薄索引+正文主体"同构；"目录含 MEMORY.md 才算记忆目录"给了 LDVH 类型目录（researches/ 等）一个可检验的归属判据参照。

### F17 记忆隔离 fail-closed 沙箱：无沙箱宁可抛错不静默降级

### F18 三类上下文管理子代理：Recall/Reflection/Defragmentation

### F26 环境 vs Agent 上下文边界：CLAUDE.md/AGENTS.md 属环境不属 Agent

AFFORDANCES：环境可能带 CLAUDE.md/AGENTS.md 或项目级 skills——这是环境的一部分、不是 Agent 的；Agent 跨环境时环境上下文随之变化，而 Agent 自有记忆（对话历史与自管理上下文）跨环境携带不变。

**对 LDVH 的价值**：与 LDVH 的边界划法对照面——LDVH 里 AGENTS.md 是规范引导（框架注入）而非"环境私有"，且 LDVH 事实源是项目级（随项目走）不是 Agent 级（随人走）。差异根源是主体不同（Letta 的主体是 Agent、LDVH 的主体是项目），LDVH 无需改动，但引用此机制时应注明语义已换轨。

### F27 Constitution 设计立场：描述目标而非规定模式，Agent 是上下文所有者

Concluding thoughts 原文：优先描述上下文管理的目标而非指示 Agent 遵循特定模式；最终 Agent 是自己上下文的所有者，可选择如何构建自己的记忆与身份；设计的 affordances 是辅助而非必须照用。

**对 LDVH 的价值**：Letta 的宪法层靠自觉（描述目标）+ git hook 层靠强制（frontmatter 校验）——双层结构与 LDVH"规范源定义边界+Git Gate 机械执行"同构，但 LDVH 的强制面更宽（提交契约、CAS、受控写入、类型准入）。LDVH 的差异化定位得到精确表述：不是"更严的宪法"，而是"宪法+更完整的闸门"。
