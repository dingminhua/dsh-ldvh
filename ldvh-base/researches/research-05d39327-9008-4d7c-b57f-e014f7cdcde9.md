## 研究问题

DSH 宿主的 schedule 自动化任务机制具备哪些形态、绑定语义与能力边界？它能否承载 LDVH 辅助机制的第二种触发（定时处理留观缓冲、验证经验能否从留观进入草稿）？

之所以需要这份调研：现行规范只定义了「闲置触发」一种辅助机制，而实际需要两种。若新增定时触发，必须先确认宿主侧实际提供的是什么能力，否则规范会写在假设之上。

## 输入与边界

**输入**：DSH 宿主 schedule 服务包（`@deepseek-ai/dsh-schedule`）与工具包（`@deepseek-ai/dsh-tool-schedule`）的包级实现文档——实际读取的是当前 DSH 安装内的副本（`dsh/node_modules/@deepseek-ai/`）；本会话运行时可直接观察的工具注册事实（`schedule_create` / `schedule_list` / `schedule_update` / `schedule_delete` 四个工具已注册于当前 preset）。

**边界**：

- 本调研**只覆盖宿主 schedule 机制**，不评估 LDVH 侧应如何设计该触发；
- 材料为包级文档与运行时观察，**未做代码级验证**，也未实测投递时延与失败恢复；
- 未查明是否存在与 schedule 并列的其它宿主自动化入口。

## 关键发现

### F1 宿主具备持久化定时任务能力

宿主提供 `@deepseek-ai/dsh-schedule` 服务，支持一次性、固定间隔、每日、每周与 cron 五种墙钟形态，任务在 Host 重启后仍然保留。它由 preset 挂载的 `@deepseek-ai/dsh-tool-schedule` 暴露为四个模型工具；`standard`、`cordis`、`ptc` 三个 preset 挂载，`minimal` 不挂载——即这项能力**由 preset 决定是否给予某个 Agent**。

创建时必须且只能给一个选择器：`after_seconds`（≥1 秒）、`at`（严格未来的绝对时刻）、`every_seconds`（固定间隔 ≥60 秒，创建时对齐）、`daily`（显式 IANA 时区的本地时刻）、`weekly`（时刻 + ISO 星期集合 + 时区）、`cron`（五段表达式 + 时区）。标题必填、裁剪后非空、不超过 120 字符。

溯源：https://www.npmjs.com/package/@deepseek-ai/dsh-schedule（README「Summary」段）

### F2 cron 方言边界

cron 采用标准五段 Vixie 式 `分 时 日 月 周`，因此**最小间隔为一分钟**，不支持秒级。以下写法被拒绝并返回 `invalid_rule`：`L`、`W`、`#`、月份或星期英文名、`@daily` 一类宏、六段式（含秒字段）、越界值、倒置区间、零步长。创建时存储规范化表达式，原始拼写不保留。

每日/每周/cron 的首次目标严格在未来；本地时刻不存在（夏令时跳变）时跳过该日；重复时刻（回拨）每个日期只取较早的一次。

溯源：https://www.npmjs.com/package/@deepseek-ai/dsh-schedule（README「cron wall-clock input」段）

### F3 任务绑定调用者的 Session

一条定时任务绑定**创建它的那个 Agent 的 Session**。模型的 `schedule_list` 只返回本 Session 的**活跃**任务；共享 `schedule` 命名空间的 `catalog` 可见全部 Host 任务及其原始 Session id，但 `list`/`history`/`update`/`delete` 均需显式 Session id。

**委托子代理会话被拒绝**：当 Agent 的委托深度大于 0 时，`create` 与 `update` 以 `subagent_session` 拒绝。原因是投递经由 Session 控制器解析绑定会话时会拒绝委托子代理的活 Agent，绑定在那里的任务永远无法投递。该限制由工具层实施：对委托调用者拒绝全部四个工具；但 `list`/`catalog`/`history`/`delete` 仍服务该 Session，使此前存入的任务可被移除。

溯源：https://www.npmjs.com/package/@deepseek-ai/dsh-schedule（README「catalog」段与「Known Limitations」第六项）

### F4 投递形态是向会话收件箱追加后续消息

宿主内由一个 `ScheduleService` 持有**单一 Host 定时器**，只有 active 任务驱动该定时器。到期时，宿主通过 `sessionController.resolveAgent` 解析原 Session，由插件来源的 `followup()` **同步追加该消息到 Session 收件箱**；`session/flush` 成功即确认持久化投递。

**投递路径的终点是收件箱，不是执行**。宿主不直接调用任何执行体或工具；收到消息后是否执行、执行什么，由该 Session 的 Agent 决定。

溯源：https://www.npmjs.com/package/@deepseek-ai/dsh-schedule（README「Delivery」段）

### F5 投递不等于模型执行

包文档明确：回执含该次发生的 `scheduledAt`、确认时间 `deliveredAt` 与 `messageId`，它们**确认的是收件箱投递，不是模型执行**；保存的投递记录**不确立模型执行结果**。「已投递」与「被执行」是两件事。

溯源：https://www.npmjs.com/package/@deepseek-ai/dsh-schedule（README「Delivery」段末与「Known Limitations」末项）

### F6 无自动重试与至少一次投递语义

- **Host 必须运行才能投递**。恢复、入队或持久化失败时任务仍保留并报告警告，**没有自动重试定时器**；后续的任务管理变更、另一次定时唤醒或 Host 重启可能重试待办任务。
- **入队与任务写入不是原子的**，因此崩溃恢复**不保证恰好一次投递**；关闭时也可能重复投递同一任务——同源兄弟纤程并发释放，存储设施可能在投递排空写入确认之前关闭。

溯源：https://www.npmjs.com/package/@deepseek-ai/dsh-schedule（README「Known Limitations」第一、二项）

### F7 定时任务不激活 Agent 也不读会话日志

`catalog`/`list`/`history`/`delete` 等操作**不激活 Agent，也不读取会话日志**。删除会移除任务行及其保存的投递记录：任务离开 `list` 与 `catalog`，不再调度，`history` 对同一 `(sessionId, id)` 返回 `schedule_not_found`。

另有三条相关约束：会话归档时若存在活跃定时任务会被拒绝，选择停止会删除全部活跃任务，取消归档不会恢复它们；管理编辑只限活跃任务，**不支持暂停、执行状态、投递到原 Session 之外、或每次运行新建会话**；跨会话中继工作流不受支持。

溯源：https://www.npmjs.com/package/@deepseek-ai/dsh-tool-schedule（README「The four tools」与「Known Limitations」）

## 未证实与缺口

1. **定时触发后的执行路径未展开**（中优先级）。宿主只负责「把消息投进收件箱」，谁读这条消息、读后按什么规则执行，属于 Session 控制器与 Agent 运行时职责，schedule 包文档未展开。
2. **是否存在与 schedule 并列的其它自动化入口**（高优先级）。例如不绑定会话、可直接派发执行体的 headless 通道，本次未查明。若有，「定时触发直接 spawn 子代理执行审核段」才有宿主承载。
3. **投递时延与失败恢复未实测**（低优先级）。材料陈述来自包文档，未做运行时验证。

## 建议

**对本次设计决定的直接含义**：宿主 schedule 提供的是「**定时向某个会话投递一条消息**」，不是「定时执行一段动作」。这一区分决定规范怎么写：

1. 若定时触发要按固定闭集跑审核段，规范须写明该闭集**由收到消息的一方执行**，而非由宿主执行——宿主不具备执行能力；
2. 规范不得据「任务已投递」主张审核段已执行——这是 F5 的硬边界，与 00 §5.6 据实声明同向；
3. 定时任务**绑定会话**这一事实，与「宿主发起的辅助任务无主控、不落入任何主控负责范围」的定性之间存在张力：消息进入某个会话收件箱后，那个会话若存在主控，主控将读到并处理它。**该触发属于哪种定性须在设计时明确**，不能默认套用无主控的表述；
4. 宿主**不保证恰好一次投递**，规范不得声称定时触发具有恰好一次语义；多次投递的后果须由审核段的幂等设计吸收（缓冲条目状态流转本身幂等：已 `consumed`/`discarded` 的条目不再被处理）；
5. 宿主**无自动重试**，与现行规范「不得自行重试」方向一致，两者可对齐；
6. 若「定时触发不读新对话材料、只消费留观缓冲」的设计成立，则 F7（不读会话日志）正好支持这一形态——定时触发不需要、也不应该读会话历史。

## 后续分流

本调研支持「辅助机制第二种触发」的**可行性判断**，但**不构成设计决定**。待该设计确定后：

- 若定时触发按「向会话投递提示、由该会话继续处理」实现，它**不是**无主控辅助任务，规范落点不在 11 号的无主控框架内，须另行定性；
- 若定时触发按「独立执行体按固定闭集运行」实现，需先查明比 schedule 更底层的派发入口（缺口 2）；
- 该设计若改变辅助任务的定性，须回溯 `00 §5.5` 的「无主控」定义。
