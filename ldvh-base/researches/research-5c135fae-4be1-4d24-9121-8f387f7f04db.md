## 研究问题

以 LDVH 这类「AI 长程工作治理」项目为参照系，业界同类项目在哪些内容上建立了独立可寻址的记录类别（对应 LDVH 的事实对象），LDVH 现行八类事实类型未覆盖的类别有哪些？

## 输入与边界

比对口径经 Human 澄清裁定为「职责覆盖为主」——不以寻求同名类型为准，而问该职责在 LDVH 已由谁承担（类型、规范源、实现层，或明确不承载）。取证语料限定为工程治理 artifact 传统与 AI 代理治理项目两族；交付要求为查漏清单加按 02 §6.2 准入六问的预判。服务对象归属按 33 §1.2 显式标明：本题属**机制需求**，结论服务于 LDVH 自身的类型闭集，而非管辖项目 dsh-ldvh 的工程选型。

本轮外部通道受限：宿主配置的 web_search provider（`ddg`）与 web_fetch provider（`fs-quality-fetch`）均未注册，两类调用全部返回 provider not registered；改用 shell 直接取回同一 canonical URL 的一手正文，来源文本仍为一手，但取回路径经由实现层，已如实记入「未证实与缺口」。既有 Research 对象按 33 §5.2 承认的「已确认存在的文档」计入合法来源，其引文沿用各对象已入库的逐字摘录。

## 关键发现

### 事件复盘在业界是独立书写类别，其定义要件比 LDVH Pitfall 多出事件维度

观察：Google SRE 对 postmortem 的定义是「A postmortem is a written record of an incident, its impact, the actions taken to mitigate or resolve it, the root cause(s), and the follow-up actions to prevent the incident from recurring.」要件含影响、缓解动作、根因、防复发四项，且以一次可编号的事件为对象。

对 LDVH 的判断：23 §6.1 的 Pitfall 要件是症状、触发条件、根因、解决、规避、验证、影响范围，缺「一次具体事件的影响与处置过程」这一维；Friction 承载的是反复出现的阻碍而非单次事件。该职责在 LDVH 由 Pitfall 与 Friction 两类的并集近似覆盖，单次事件的独立档案无处落。考虑本仓为单人主导、事件多由主控当场处置，判定为可接受现状而非必须补缺，并把「多主控或多项目并行」登记为重审触发。

溯源：https://sre.google/sre-book/postmortem-culture/（Chapter 15 章首 The postmortem concept is well known 段定义句）

### 前瞻性风险在业界是独立记录类别，LDVH 八类事实类型无对应承载

观察：风险登记册被定义为「A risk register is a document used as a risk management tool and to fulfill regulatory compliance, acting as a repository for all risks identified and includes additional information about each risk, e.g., nature of the risk, risk owner, and mitigation measures.」其对象是尚未发生但已识别的风险，要件含风险性质、风险属主、缓解措施。

对 LDVH 的判断：现行七类加 Goal 单例全部指向事后或进行中的记录（已验证失败＝Pitfall、待推进方向＝Spark、正在执行＝WorkCase、已终止调研＝Research、待修阻碍＝Friction、已定决定＝ADR、成体系规则＝Norm），无「已识别但尚未发生的风险」这一类。ADR 的 consequences 段与 Spark 的 intent 段各自局部触及，但都不是以风险为主体的可寻址记录。这是本轮最强的缺类候选；该来源只确立类别存在性（三级来源），不足以支撑「LDVH 应立此类」，准入须按 02 §6.2 呈 Human。

溯源：https://en.wikipedia.org/wiki/Risk_register（节首定义段）

### 对外宣告的版本变更在业界是独立记录类别，LDVH 无版本级宣告面承载

观察：Keep a Changelog 的定义为「A changelog is a file which contains a curated, chronologically ordered list of notable changes for each version of a project.」其同页自述纪律为「Don’t let your friends dump git logs into changelogs.」，即该类别成立的前提是相对 git 日志经过筛编、按版本组织。

对 LDVH 的判断：LDVH 的对象级 change_log 与 Git 提交链承担的是内部溯源，与对外宣告是两个方向；08 号涉及发布门面但只作规范方向而非记录类别。缺口真实存在，但按 02 §6.2 第 3 问，一份普通 Markdown 文件即可无损承载版本级宣告，且 10 号插件发布规范已在规则侧覆盖，判定为**不立对象类型**。

溯源：https://keepachangelog.com/en/1.1.0/（What Does This 节定义句与页面 description 元数据）

### 范围级所有权与审批权在业界是可机械触发的声明式名录，LDVH 无类型承载

观察：GitHub 对 code owners 的定义为「Code owners are automatically requested for review when someone opens a pull request that modifies code that they own.」其关键性质是名录按路径范围声明属主，并由机械入口（开 PR）自动触发。

对 LDVH 的判断：LDVH 的责任承载有两处——00 §5 的主控责任（按发起者而非按路径范围划分）与 WorkCase attempt.controller（按单次执行持有者）。二者都不回答「这块范围归谁」。在单人主导现状下该缺口实际代价低（02 §6.2 第 1 问不成立）；判定为不立类，登记重审触发：本仓出现需要按路径范围指派的独立复核者时。

溯源：https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners（About code owners 正文首段）

### 想法是否值得投入的评估在上游是独立工件，LDVH 落在 Spark 终态与对话中

观察：spec-kit 把能力面列为「Decide whether an idea deserves investment」，其产出形态写明为「An evidence-backed go, clarify, or stop decision」，即有证据支撑的三值决定。

对 LDVH 的判断：LDVH 的等价判断发生在 Spark 的终态转换（discarded 的 disposition）与 Human 对话裁夺中，没有一个先于执行、承载「值得投入与否的证据」的独立记录形态；三值中的 clarify 一档在 20 §8 的闭集里没有对应取值（open 只表示悬置，不表示待澄清）。本条与 spark-e92d4ebb 的归位义务议题耦合：若归位义务落成，「显式放弃」的记录形态与该三值评估指向同一处承载，应合并裁定而非两处权威。

溯源：https://raw.githubusercontent.com/github/spec-kit/main/README.md（README 能力表 Idea assessment 行）

### 同类 AI 治理工具明文禁止以 markdown 待办列表承载任务，并为跨会话事实另设一类

观察：beads 给接入代理的 AGENTS.md 最小段落写明「Use bd remember "insight" for durable project facts; keep per-operator preferences in your harness's own memory. - Do not use markdown TODO lists for task tracking.」

对 LDVH 的判断：同一工具把 durable project facts 与 per-operator preferences 分置两处，并明文拒绝 markdown 待办列表——这与 Human 2026-10-28 提出的「有价值信息不得滞留临时载体」是同一主张的一手外部先例。差别在 beads 用独立存储类承载，LDVH 用分流路由（35 §8.3）加受控写入承载，属同一职责的两种实现。本条不指示 LDVH 须新增类型，但为「滞留」的判定提供外部基准，直接供 spark-e92d4ebb 的措辞裁定引用。

溯源：https://raw.githubusercontent.com/steveyegge/beads/main/README.md（agent setup 节的 AGENTS.md 最小段落建议清单）

### 需求到交付物的可建立关系是专门子学科，LDVH 已由 WorkCase 判据与 serves 覆盖

观察：需求可追溯性被定义为「traceability is a sub-discipline of requirements management」，其一般术语按 IEEE 词汇表为「the degree to which a relationship can be established between two or more products of the development process」，并以双向（前向与后向）之分为学科要件。

对 LDVH 的判断：该职责在 LDVH 已被机械承载——WorkCase 的 plan 每项带 done_criteria、关闭时 result.criteria_checks 逐条对应（21 §8／§14），serves 回指 goal.md 的 SG-n 锚点，构成子目标到工单到验收的双向链。判定为**职责已覆盖，不构成缺类**；本对象作为该覆盖关系的检索入口，不重复展开判据。

溯源：https://en.wikipedia.org/wiki/Requirements_traceability（节首定义段与 IEEE 定义引用）

### 领域概念与关系的形式命名在业界是独立类别，LDVH 由规范源条文承载故不构成缺类

观察：信息科学中的本体被定义为「an ontology encompasses a representation, formal naming, and definitions of the categories, properties, and relations between the concepts, data, or entities that pertain to one, many, or all domains of discourse」，其操作形态是「a set of terms and relational expressions that represent the entities in that subject area」。

对 LDVH 的判断：同一职责由规范源承载——01 §5 基础术语与文件角色、各规范的「基础概念」章，加上 01 §5 第 7 项的「定义来源」制度（对概念含义、边界与相邻差异承担唯一定义责任的当前规范章节），与 02 §8.2 的关系承载形态闭集。LDVH 不缺该职责的承载位置，缺的是一张可查询的术语总表；后者按 F12 判据属派生视图而非第二事实源，判定为**不立对象类型**。

溯源：https://en.wikipedia.org/wiki/Ontology_(information_science)（In information science 段定义句）

### 证据充分性判定在业界明确依赖专业判断，LDVH 已由三态字段与 reviews 覆盖

观察：审计证据的定义为「Audit evidence is evidence obtained by auditors during a financial audit and recorded in the audit working papers」，其充分性判据写明为「sufficient and appropriate, which means it is reliable and relevant」，且「The auditor must use their own professional judgement when determining if the audit evidence is persuasive and sufficient.」

对 LDVH 的判断：该职责由 Research 三态字段加 33 §10 逐字摘录入库、WorkCase reviews 判据七要素、02 §8 来源与证据共同边界承载。外部原文另给出「充分性属专业判断、不可机械化」的一手佐证，与 ADR 2a521398「该判据没有机械可判定部分」的推理同向，可作其外部旁证。判定为**职责已覆盖，不构成缺类**。

溯源：https://en.wikipedia.org/wiki/Audit_evidence（节首定义段与 sufficient and appropriate 段）

### 事件处置中的职责与状态持有者在业界以具名角色显式分配，LDVH 以令牌持有承载

观察：SRE 对事件指挥官的描述为「commander holds the high-level state about the incident. They structure the incident response task force, assigning responsibilities according to need and priority. De facto, the commander holds all positions that they have not delegated.」

对 LDVH 的判断：外部形态是按需要显式分配角色并把未分配职责默认兜给指挥官；LDVH 的 attempt 形态是单调令牌加心跳加至多一个活跃持有者（21 §10.4）。二者解的是同一个「谁在持有这件事」，但 LDVH 无「未分配职责的默认归属」条款——工单关闭后未承接的残留由去向词承担归属，而非默认落到某角色。属承载差异而非缺类，判定为可接受现状。

溯源：https://sre.google/sre-book/managing-incidents/（Chapter 14 commander 职责段）

### 非异常终态在既有取证中已给出底表，LDVH 的差距在机器可读承载而非取值选择

观察：既有取证记录「Mozilla 的优先级闭集里明确保留 P5 Will not fix, but will accept a patch，即不修本身就是一档正式取值而非异常状态」，同族来源把关闭定义为需人工承担的责任动作并要求留下解释决定的评论。

对 LDVH 的判断：LDVH 的四词去向闭集在取值形态上与业界一致，差距在于这四个词是正文加粗文字而非机器可读字段，故不可按取值检索与统计。属既有类型承载形态的改进项，不属缺类；改进方向已由既有取证给出，本条仅作横切登记不重复展开。

溯源：https://github.com/dmh2002/dsh-ldvh/blob/dev/ldvh-base/researches/research-35afd456-10cc-4d3b-b7fc-8a088946b183.md（关键发现节第一条观察段）

### 职责分离落在工作项 schema 的显式身份字段，LDVH 的差距在判据来源字段选择

观察：既有取证记录同类规范「定义了 maker / checker / merge authority 三个必须互不相同的身份，并要求在工作项 schema 里落 maker_id、maker_model、checker_id、checker_model 字段，合并时若 maker_id == checker_id 即拒绝」。

对 LDVH 的判断：LDVH 用 reviews 的 session_id 与 implementer_session_id 比对做同一件事，且两值相等时 fail-closed，方向一致；差别在外部把判据落在该语义的权威承载字段，LDVH 落在 attempt 路径上可能不代表实际写入者的字段。属既有类型的判据字段问题，不构成缺类。

溯源：https://github.com/dmh2002/dsh-ldvh/blob/dev/ldvh-base/researches/research-be619451-c42c-46c6-be5d-952cf5af2767.md（F3 观察段）

### 单一事实源与记录系统是两个概念，其判据可直接用于检验新类别是否形成第二事实源

观察：既有取证记录 GitLab Handbook 明文区分「A system of record (SoR) is the authoritative data source for a given data element or piece of information. It's worth noting that while it is possible to have a system of record that is also a single source of truth, simply just being a system of record doesn't directly imply it is the single source of truth.」并把重复内容列为应避免之事。

对 LDVH 的判断：这条判据给 02 §16 红线 3「不建立第二事实源」一个可操作读法——只从事实源机械派生、不存副本的是视图，复制内容且各自可改的才是第二事实源。任何候选新类别在过 02 §6.2 第 3 问时可用此判据检验：若其内容能由既有类型派生，则立类会造出第二事实源，应判不承载。本轮的术语总表与版本级宣告两条即用此判据落定。

溯源：https://github.com/dmh2002/dsh-ldvh/blob/dev/ldvh-base/researches/research-ff512ede-1d29-45d2-89f5-42ab9b289426.md（F4 观察段）

### 双时态账本与 LDVH 的 change_log 加 retired 是同一思想的两种载体实现

观察：既有取证记录某企业世界模型「核心数据模型是双时态知识图谱：每条事实携带世界轴与认知轴两条时间线，账本 append-only、更正走 supersedes 链、删除是事件」。

对 LDVH 的判断：LDVH 的等价承载是对象级 change_log 流水加终态不删（retired／discarded／closed 各按类型），未记录世界轴有效时间。「某事实于何时在世界上为真」这一维不被承载；对治理用途而言当前态加流水已足够，双时态属可选增强而非缺类，引入它须另答 02 §6.2 第 5 问的成本。

溯源：https://github.com/dmh2002/dsh-ldvh/blob/dev/ldvh-base/researches/research-6ba53f52-ef89-4afa-9676-9d8a69aa58e4.md（F3 节 migrations 列设计）

### 既有方向覆盖标注盘的是规范方向轴，不能直接充当事实类型缺口的证据

观察：既有取证对覆盖的标注为「✓ 已覆盖（09 Code、10 Web 两份完整覆盖为工程方向）；◐ 部分覆盖（05 仅 API 契约的 CLI 自身契约、06 受控提交契约、08 发布/文档/版本门面、02 评审制度）；✗ 未覆盖（依赖/配置/安全/可观测性/架构/需求/验收/审计/合规/许可证/隐私/缺陷/复盘等约 35+ 个方向）」，并另记审计、缺陷、复盘等方向「在 LDVH 中已由事实类型提供能力」。

对 LDVH 的判断：该清单回答的是「规范方向是否漏」，不是「内容类别是否有可寻址记录形态」；其自身 high 优先级缺口为元层级与项目层级判据未由 Human 裁定。本轮据此只借用其「方向不等于类型」的方法论区分，**不**借用其覆盖计数作为缺类结论，也不以其为「已扫尽」的依据。

## 未证实与缺口

未证实三条：其一，本轮类别清单由一手来源与既有 Research 拼合而成，语料族限于 ADR/KEP/RFC/changelog、议题跟踪、agent 编排与持久化执行、记忆系统、知识图谱、SRE 与 spec-kit 类上游，未含 ITIL／PMI／ISO 类治理标准正文；零命中类别（如运维手册）既无已证实记录也无反证，不得声称业界类别已扫尽。其二，「一个内容类别在何种条件下才需要独立事实对象、而非由规范条文或实现层承载」未取得业界直接判据，只能引用邻近判据（SoR 之辨、重复内容代价）推导，属跨域类比，迁移到 LDVH 须声明为自建。其三，前瞻性风险、版本级宣告、范围级属主、想法评估四类在同类 AI 治理语料（beads、spec-kit、logplane、governed-autonomy-spec）中均无先例，其缺类判断由工程治理语料推得，只到「值得考虑」为止，不到「应新设类型」。

缺口四条：其一，运维手册类内容未取得可用一手来源（SRE 站对应两个路径均返回 404），本轮不覆盖。其二，同类 AI 治理语料对四个候选类别无先例，跨域类比须声明自建。其三，「类别何时应独立对象化」的业界判据未取得。其四，宿主 web_search 与 web_fetch provider 未注册属环境事实，本轮以 shell 直取 canonical URL 绕行完成取证，来源文本为一手但取回路径经由实现层，后续同类调研宜先修复该配置。

## 建议

按 02 §6.2 六问对四个缺类候选作预判（均为建议，不取得效力；类型准入属 Human Gate，见 33 §19.1 第 3 项）：

其一，**前瞻性风险**：第 1 问（须跨行动保留）与第 2 问（需身份、状态与关系管理）成立——风险须被持续跟踪至消解或成真，成真后应能转为 Friction 或 Spark；第 3 问部分成立——ADR consequences 段可承载一次决定的风险陈述但无「未消解」状态与到期语义，Spark 可承载待决方向但不以风险为主体。建议落点为扩 Friction 语义（纳入「已识别但尚未成为阻碍的风险」）或新立一类，倾向先扩 Friction：26 §9 的闭集扩展成本低于新类型的规范起草加 F1–F4 召回接入成本。**须 Human 裁定，本条不自行准入。**

其二，**版本级对外变更宣告**：第 3 问答「能」（普通 Markdown 即可无损承载，10 号已在规则侧覆盖发布门面），建议不立对象类型。

其三，**范围级所有权**：第 1 问在单人现状下不成立，建议不立类，登记重审触发：本仓出现需要按路径范围指派的独立复核者时。

其四，**想法评估三值决定**：与 spark-e92d4ebb 的归位义务耦合——若归位义务落成，「显式放弃」的记录形态与该三值评估指向同一处承载。建议不单独立类，并入 20 §8 的 disposition 形态扩值（补 clarify 一档），与 spark-e92d4ebb 合并裁定以免两处权威。

## 后续分流
