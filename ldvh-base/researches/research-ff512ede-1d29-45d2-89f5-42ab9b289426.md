implications:
  - finding_ref: F1 计划职能在业界被拆入既有类型，没有「项目级推进计划」的独立载体规范
    implication: LDVH 无法通过沿用某一种成熟载体解决规划承载问题：机制层可借鉴，类型层必须自建并显式声明为自建。
  - finding_ref: F2 确定性按时间地平线分级，而非按文档分级
    implication: 同一载体可同时承载不同承诺强度的内容，远期条目只需标出确定性档位并给近似值，不必拆成第二份文档。
  - finding_ref: F3 变动史靠「旧条目冻结 + 新条目承载现状 + 双向指针 + 版本控制兜底」
    implication: 改向不得通过改写原计划的正文来保存；LDVH 已有的 superseded-by（ADR）与 updates（Research）关系形状可直接复用于计划类对象。
  - finding_ref: F4 「单一事实源」与「记录系统」是两个概念，重复内容的代价被明写
    implication: 判定蓝图是否为第二事实源的标准是「派生还是复制」：只作查询的视图不是第二事实源，可各自修改的副本才是。
  - finding_ref: F5 计划视图由事实源机械派生，不存副本
    implication: 蓝图投影面的落地前提是查询面先存在；实测本仓 serves 无按 SG 聚合的服务或端点，查询面缺失先于呈现面缺失。该聚合缺口在本仓未被单独登记；相邻的 Friction bdbab9ab 登记的是「serves 归属缺少反查复核」，按 SG 聚合仅为其正文列举的候选修复形态之一，且该账目明确不预设修复形态。
  - finding_ref: F6 结构化字段的存在理由是「让自动化可校验」，不是给人看
    implication: 蓝图中可机械判定的部分（状态、阶段、指向、时间）应提到字段层，但字段数应保持个小量级，其余留给正文。
  - finding_ref: F7 意图层必须与方案层解耦，且两层变更频率被量化
    implication: goal.md 的目标陈述与 SG-n 属意图层，不应被写成步骤表；两层变更频率的量化同时给出了「意图层不稳定」的可观测审计口径。
  - finding_ref: F8 计划必须可被廉价重写，「当前有效」与「当时所想」是两个东西
    implication: 「当前计划可重写」与「变动史必须留存」不冲突，解法是分载给不同载体；本仓 docs/action-plan-2026-09-10.md 当前两者混在一起且都不受治理。
  - finding_ref: F9 未决项与已否决项都要留痕，且各有明确目的
    implication: 「下一步」与「悬而未决」两块可采用三条纪律：未决不构成承诺、已否决须记原因以防重提、远期只给近似值——恰好覆盖三个 open spark 的缺口。
  - finding_ref: F10 时间与身份元数据必须自足，否则「多久没动」无法回答
    implication: LDVH 受控对象不设 updated_at，变更史由 change_log 承载；change_log 末条的 at 可作等价物，但它记录任何写入（含格式治理），与「最后显著变更」不等价，需在自建类型里正面回答。
  - finding_ref: F11 机械一致性只有两条路：同一动作写两处，或索引可幂等重建
    implication: 投影面应当现算而非缓存；凡需要落盘的聚合物必须设计成可幂等重建，否则将引入「台账与事实不符」这一新的漂移类。
  - finding_ref: F13 唯一制度齐全的「到期」样本把「删除」与「墓碑」分开，并留了复活通道
    implication: 条目到期的可移植形状是四件套：硬阈值、到期移出活跃面（非删除）、不可失效的墓碑、正式复活通道。

## 研究问题
项目级「推进计划」（下一步做什么、现在做到哪、为何改向）应以什么载体承载与治理，才能在计划频繁变动时不丢失变动史、又不形成第二事实源？

调研对象为四类外部实践族：①决策与提案类文档体系（Nygard ADR、AWS ADR 流程、MADR、adr-tools、adr-log、Log4brains、Rust RFC、PEP 1、Kubernetes KEP、IETF I-D、RFC 7322）；②产品管理与计划方法（Shape Up、ProdPad Now-Next-Later、PMI Rolling Wave、Roman Pichler 的愿景/路线图分层、Google OKR、Amazon PR-FAQ、SVPG、Martin Fowler）；③平台内建的进度载体（GitHub Projects、Linear Updates）；④陈旧与到期机制（actions/stale、GOV.UK、Kanban Guide、Google SRE toil）。

本对象为该问题的正面调研，承载 `research_purpose`：为本仓「规划」承载的载体选型提供业界依据。

## 输入与边界
输入为本轮调研会话的四轮三态证据提交，全部 confirmed 条目均实际抓取并读过原文，逐条带 URL 与可重新定位的锚点。

**不覆盖范围**：①Atlassian Jira Plans / Advanced Roadmaps 官方正文（多处 404 或正文截断，疑需真实浏览器执行 JS）；②GitLab Epics/Roadmaps 产品文档（CAPTCHA 拦截）与 GitLab handbook 的 product direction 路径（404）；③PMBOK 正文对 progressive elaboration 的逐字定义；④Prow `lifecycle/stale` 与 `lifecycle/frozen` 文档（四个候选路径全部 404，以 GitHub API 列目录证明该路径下无对应文件）；⑤PyPI/npm 生态的弃用与陈旧标记阈值；⑥Notion、Airtable 的项目模板（无实际抓取来源）。

**与既有对象的关系**：本对象不重复 `research-0ca1ab2c`（Linear/GitHub Projects/Jira Plans 的项目级 update 机制）的结论——该对象回答「蓝图六区块在业界有无先例」，本对象回答「推进计划应以什么载体承载与治理」。两对象的交集仅在 GitHub/Linear 的少量引文，且各自服务于不同问题。

**方法边界**：全部证据为公开文档与产品文档的一手抓取。厂商自述文档（ProdPad、ProductPlan）与个人博客（Roman Pichler、Malte Ubl）已单独标注性质。跨语境迁移（产品管理实践 → 规格驱动的事实治理）属跳域类比，已在「未证实与缺口」中声明为 high 优先级缺口。

## 关键发现

### F1 计划职能在业界被拆入既有类型，没有「项目级推进计划」的独立载体规范

Kubernetes KEP 明写它的设计是把四种职能合并进一个文件——「A KEP attempts to combine aspects of — a feature, and effort-tracking document — a product requirements document — a design document into one file」——同时明确拒绝把版本控制系统当项目管理工具用：「While git is a fantastic version control system (VCS), it is neither a project management tool nor a cogent way of managing an architectural catalog or backlog.」并给出替代口径：「reserve GitHub issues for tracking work in flight」。四条相邻线各自只覆盖一段：Nygard ADR 只收「架构上重要」的决策；KEP 只管一个特性；Keep a Changelog 只管已发布的差异；Rust RFC 只管设计提案过程。

**对 LDVH 的价值**：这是本轮最强的负结果——业界不存在「项目级推进计划」这一文档类型的权威规范，因此 LDVH 无法通过「沿用一种成熟载体」解决规划承载问题。可直接采用的只有机制层（变动史、双向指针、到期、机械校验），类型层必须自建，并应在规范中显式声明为自建而非声称沿用先例。

溯源：https://raw.githubusercontent.com/kubernetes/enhancements/master/keps/sig-architecture/0000-kep-process/README.md（What is a KEP 与 Motivation 章节）

### F2 确定性按时间地平线分级，而非按文档分级

ProdPad 把 Now/Next/Later 三栏的确定性做成递减梯度——Now「clearly defined, much more detailed, and completely spec'd out ... broken down into more granular pieces of work」，Later「hazy; they're big boulder blocks that you can see in the distance but don't need to break down yet」——并给出机制原话：「Time horizons are powerful because they allow you to move forward with a broad plan, yet only make commitments to what lies directly ahead of you.」「certainty is portioned out over time horizons – which gives you the chance to become more certain, rather than commit too early.」PMI 的 Rolling Wave 是同一机制的另一表述：「The Rolling Wave approach ... suggests that the project planning effort "rolls out" detailed plans for the foreseeable future and, as the project evolves, periodically reevaluates the completion dates and costs.」，且刻意区分口径：「Note the term is approximate, not estimate.」

**对 LDVH 的价值**：一个载体可以同时承载不同承诺强度的内容，只要同一页面内的确定性呈可读出的梯度；把「远期只给近似」写成可识别的档位标记，比拆成两份文档便宜，也避免了「远期文档腐烂」这一整类问题。

溯源：https://www.prodpad.com/blog/invented-now-next-later-roadmap/（Now/Next/Later 三栏定义与 More human and flexible 章节）

### F3 变动史靠「旧条目冻结 + 新条目承载现状 + 双向指针 + 版本控制兜底」

AWS 的 ADR 最佳实践把完整动作写成一句：「When the ADR owner updates the ADR, they should change the status of the old ADR to Superseded, note their changes in the change history of the new ADR, and keep the old ADR in the decision log.」同页还要求「ADRs should have a change history, and each change should have an owner」。指针是双向绑定的：KEP 要求「replaces: A list of KEPs that this KEP replaces. Those KEPs should list this KEP in their superseded-by.」；PEP 1 要求「The newer PEP must have a Replaces header containing the number of the PEP that it rendered obsolete.」；Rust RFC 的规则是「once accepted, RFCs should not be substantially changed. Only very minor changes should be submitted as amendments. More substantial changes should be new RFCs, with a note added to the original RFC.」

**对 LDVH 的价值**：这是「不丢失变动史」的四家一致做法，且没有任何一家靠「改写原条目正文」保存历史。其形状（旧冻结 + 新承载 + 双向指针）与 LDVH 已有的 ADR `superseded-by` 关系、Research `updates` 关系同构；LDVH 缺的不是机制，而是把它推广到「计划」这一内容类别。

溯源：https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/best-practices.html（Preserve ADR history 与 Store ADRs in a central location 章节）

### F4 「单一事实源」与「记录系统」是两个概念，重复内容的代价被明写

GitLab Handbook 明写它自己就是单一事实源——「The GitLab Handbook is the single source of truth for how we operate at GitLab, including processes, policies, and product direction.」——并给出可执行的更新纪律：「Remember, the handbook is not what we hope to do, what we should formally do, or what we did months ago. It is what we do right now. Make sure you change the handbook in order to truly change a process.」重复内容被列为应避免的事：「Duplicate content leads to more work by having to update the content in multiple places as well as the need to remember where all of the out of date content lives.」同时它区分了两个常被混用的概念：「A system of record (SoR) is the authoritative data source for a given data element or piece of information. It's worth noting that while it is possible to have a system of record that is also a single source of truth, simply just being a system of record doesn't directly imply it is the single source of truth.」

**对 LDVH 的价值**：LDVH 的「第二事实源」担忧在业界被拆成两个不同的问题——重复内容（要避免）与多个记录系统（不是同一件事）。这给出一条可用判据：蓝图若只从事实源派生（不存副本），则它是视图而非第二事实源；若它复制事实源的内容且各自可改，才是第二事实源。

溯源：https://gitlab.com/gitlab-com/content-sites/handbook/-/raw/main/content/handbook/about/handbook-usage.md（Single source of truth 与 System of record 章节）

### F5 计划视图由事实源机械派生，不存副本

GitHub Projects 把这个属性写在功能第一段：「Your projects are built from the issues and pull requests you add, creating direct references between your project and your work. Information is synced automatically to your project as you make changes, updating your views and charts. This integration works both ways, so that when you change information about a pull request or issue in your project, the pull request or issue reflects that information.」工具层不做手动同步：内置工作流在条目变更时自动设置字段。

**对 LDVH 的价值**：这是「不形成第二事实源」在工程上被真正实现的唯一一手样本——凭的不是纪律，而是数据只存在一处、视图只是查询。蓝图投影部分若要照此实现，前提是 LDVH 具备等价的查询能力；实测本仓 `serves` 字段当前无按 SG 聚合的服务或端点，即查询面的缺失先于呈现面的缺失。需要区分的是：这一聚合缺口在本仓尚未被单独登记；相邻的 Friction `bdbab9ab` 登记的是「serves 归属缺少反查复核」（serves 只在写入时校验、无写入后的反查复核），其正文把「F1 投影按 serves 聚合」仅列为候选修复形态之一，并明确「本账目不预设修复形态」「修复形态与归属层级须经 Human 定案」，故不可将其等同于本缺口。

溯源：https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects（About projects 与 Staying up-to-date 章节）

### F6 结构化字段的存在理由是「让自动化可校验」，不是给人看

KEP 把这个设计意图逐字写出：「In some cases, the questions below should also have answers in kep.yaml. This is to enable automation to verify the presence of the review, and to reduce review burden and latency.」其元数据是闭集：`status` 七值 `provisional|implementable|implemented|deferred|rejected|withdrawn|replaced`、`stage` 三值、`latest-milestone` 与 `milestone: {alpha, beta, stable}` 的阶段映射、`replaces` 路径列表、`feature-gates`。PEP 1 的 Preamble 是同类做法的更早版本，并把「被否决的想法」也结构化：「Those rejected ideas should be recorded along with the reasoning as to why they were rejected. This both helps record the thought process ... as well as preventing people from bringing up the same rejected idea again」

**对 LDVH 的价值**：蓝图若只做自由文本，就放弃了这一类收益；把可机械判定的部分（状态、阶段、指向、时间）从正文提到字段，是业界被明写为设计意图的做法，而非过度设计。反过来，`kep.yaml` 的闭集规模也给出上界——KEP 只结构化了不到十个字段，其余全部留给正文。

溯源：https://raw.githubusercontent.com/kubernetes/enhancements/master/keps/NNNN-kep-template/README.md（Metadata 章节与 Production Readiness Review Questionnaire 引言）

### F7 意图层必须与方案层解耦，且两层变更频率被量化

Roman Pichler 给出两条可操作的频率线：「As a general rule, the product vision should be stable. It should offer guidance for an extended period—at least five years」，而「the roadmap is likely to change several times per year. Both plans therefore benefit from regular reviews.」混同两层被命名为反模式「Confusing vision with strategy」，其具体失败形态包括「Tying the vision to a product idea or business objective: This would make the vision unstable.」与「Changing the vision frequently: An unstable vision fails to provide a continuity of purpose.」解耦的手法亦写明：「keeping the product vision free from assumptions about the actual product or solution. This allows you to change the product while you stay grounded in the vision.」Google 的 OKR 指南是同构表述：「There are some objectives that will stay the same quarter after quarter…But the key results should evolve」，并且显式禁止意图层承担待办职能：「One thing OKRs are not is a checklist. They are not intended to be a master task list of all the things the teams will work on in a quarter.」

**对 LDVH 的价值**：LDVH 的 `goal.md`（目标陈述 + SG-n，编号冻结）与「下一步做什么」正是这两层；业界共识支持把两层分开承载，并支持「意图层不是待办清单」——即 SG-n 不应被写成步骤表。频率量化（至少五年 vs 每年数次）还给出一个可用的审计口径：意图层若在数月内被改动多次，按业界判据即为不稳定信号。

溯源：https://www.romanpichler.com/blog/ultimate-product-vision-faqs/（Does the product vision ever change? 与 What product vision mistakes should be avoided? 章节）

### F8 计划必须可被廉价重写，「当前有效」与「当时所想」是两个东西

Fried 把计划的时态问题写成一句判据：「All plans are rooted in the past — they're never what you think right now, they're what you thought back then. And at best, they're merely guesses about the future.」37signals 的官方立场是不做长期路线图，理由是承诺的复利成本：「It's why we've never committed to a product road map.」「Promises pile up like debt, and they accrue interest, too.」GitLab Handbook 给出「当前有效」的定义：「the handbook is not what we hope to do, what we should formally do, or what we did months ago. It is what we do right now.」Shape Up 的取舍最彻底——长期路线图不落盘：「Even if we have some kind of road map in our heads at the time scale above cycles, we keep it in our heads and in our side-channel discussions.」Kubespray 的 roadmap 文件把这一取舍做到极端：全文仅三行，指向一个 issue。

**对 LDVH 的价值**：「计划载体必须能被廉价重写」与「变动史必须留存」在业界并不冲突——解法是把两者分给不同载体：当前计划是可重写的活文档（GitLab Handbook 模式），变动史由版本控制与 change_log 兜底（ADR 模式）。本仓 `docs/action-plan-2026-09-10.md` 当前把两者混在一起且都不受治理，正是这条发现直接命中的形态。

溯源：https://world.hey.com/jason/what-i-think-not-what-i-thought-99cae1d0（全文）

### F9 未决项与已否决项都要留痕，且各有明确目的

Rust RFC 模板固定两个尾部章节——`Unresolved questions`（「What parts of the design do you expect to resolve through the RFC process before this gets merged?」）与 `Future possibilities`（「This is also a good place to "dump ideas", if they are out of scope for the RFC you are writing but otherwise related.」）——并且给后者加了一条反承诺声明：「having something written down in the future-possibilities section is not a reason to accept the current or a future RFC」。PEP 1 把「被否决的想法」单列一节并写明目的：「preventing people from bringing up the same rejected idea again」；又把「未决」单列：「Those ideas should be recorded so people know that they are being thought about but do not have a concrete resolution.」KEP 提供在制品争点的内联标记 `<<[UNRESOLVED optional short context or usernames]>>`，并允许带着未决项进入持久载体：「Merge early and iterate.」「Just because a KEP is merged does not mean it is complete or approved.」

**对 LDVH 的价值**：LDVH 蓝图的「下一步」与「悬而未决」两块当前无规范落点。业界给出的关键补充是两条纪律：①未决项的记录不构成承诺（Rust 的显式声明）；②已否决项必须记原因，目的不是留档而是防止重复讨论（PEP 1）。第二条与 LDVH 的 Spark 终态 `discarded` 必须写 `disposition` 同构，可作为该字段价值的旁证。

溯源：https://raw.githubusercontent.com/rust-lang/rfcs/master/0000-template.md（Unresolved questions 与 Future possibilities 章节）

### F10 时间与身份元数据必须自足，否则「多久没动」无法回答

KEP 对这个取舍给出了理由：「creation-date: The date that the KEP was first submitted in a PR. ... While this info will also be in source control, it is helpful to have the set of KEP files stand on their own.」同时定义了两个语义不同的日期：`creation-date` 与 `last-updated: The date that the KEP was last changed significantly.` MADR 把同一语义直接写进模板：`date: {YYYY-MM-DD when the decision was last updated}`——是最后更新日而非创建日。

**对 LDVH 的价值**：LDVH 的受控对象不设 `updated_at`，变更史由「每次修改恰好追加一条 `change_log`」承载。业界样本显示「最后显著更新日」是被独立登记的字段，其值本身即陈旧信号。LDVH 若需要判断「多久没动」，`change_log` 末条的 `at` 是等价物，但它记录任何写入（含以「格式治理：」开头的纯形态调整），与「最后显著变更」不等价——这是一个需要在自建类型里正面回答的差异。

溯源：https://raw.githubusercontent.com/kubernetes/enhancements/master/keps/NNNN-kep-template/kep.yaml（creation-date 与 last-updated 字段说明）

### F11 机械一致性只有两条路：同一动作写两处，或索引可幂等重建

adr-tools 是第一条路的样本：以 `adr new -s 9 Use Rust for performance-critical functionality` 为例，「This will create a new ADR file that is flagged as superceding ADR 9, and changes the status of ADR 9 to indicate that it is superceded by the new ADR.」即一个命令写两个文件，人工漏不掉。adr-log 是第二条路的样本：用 `<!-- adrlog -->` 与 `<!-- adrlogstop -->` 两个标记包裹生成的索引段，每次运行幂等重建该段——索引因此不是事实源，只是可重算的工件，「索引与实体不一致」这一整类问题被结构性消除。对照面是 adr.github.io（仅汇总链接，页首声明不对所列实践背书）与 adr-tools 本身没有 lint/validate 子命令。

**对 LDVH 的价值**：LDVH 的投影面（蓝图、聚焦页、卡面）若全部由事实源现算，则天然落在第二条路上，无需一致性校验；凡需要落盘的聚合物（如索引文件），必须设计成可幂等重建，否则会引入「台账与事实不符」这一新的漂移类。这条同时说明「按 SG 聚合的视图」应当现算而非缓存。

溯源：https://raw.githubusercontent.com/adr/adr-tools/master/README.md（Creating a new ADR that supersedes a previous one 章节）

### F12 陈旧与到期机制：权威给理由、拒绝给数值，且「到期动作」与「人做决策」分离

actions/stale 给出的是默认值而非规范值：「Add a label "Stale" on issues and pull requests after 60 days of inactivity and comment on them / Close the stale issues and pull requests after 7 days of inactivity」，计时口径为 `updated_at`，且「If an update/comment occur on stale issues or pull requests, the stale label will be removed and the timer will restart」。Google SRE 给出阈值理由的少见样本：「toil tends to expand if left unchecked and can quickly fill 100% of everyone's time」，并据此定 toil ≤50%。Kanban Guide 把 WIP 上限列为强制项却拒绝给数值。GOV.UK 的主机制是 review date → 逾期标记 → CSV 审计 → 人做二值决策，唯一具体阈值是「news articles and press releases that are over a year old」；其 history mode 更说明该机制可以绑定事实事件而非天数。

**对 LDVH 的价值**：LDVH 的 Spark 与 Friction 已有「悬置」「重审信号」概念，但无到期机制。业界共同做法是——阈值本身可由使用者自定，但机制必须存在，且到期只触发标记与提请，不自动做终态判定。GOV.UK 的「事实事件触发」为 LDVH 提供了一条比天数更稳的替代口径（例如某 SG-n 达成时复核其下属悬置项）。

溯源：https://raw.githubusercontent.com/actions/stale/main/README.md（Default Configuration 章节）

### F13 唯一制度齐全的「到期」样本把「删除」与「墓碑」分开，并留了复活通道

IETF 的 Internet-Draft 有硬性 185 天有效期：到期即从活跃目录删除，且明写它不属于归档序列——「I-Ds are not an archival document series」。但到期不意味着引用失效：系统保留永不失效的墓碑条目；若需继续推进，作者可通过 `Resurrect I-D` 复活该文档（保留原编号）。硬性阈值、到期自动动作、墓碑留痕、正式复活通道四件套齐备，是本轮全部样本中唯一四项兼具者。

**对 LDVH 的价值**：「计划条目到期后如何处置」在业界普遍缺失，IETF 给出了一套可移植形状：条目到期 → 移出活跃面（不是删除）→ 留下不可失效的墓碑（可引用、可反查）→ 需要时以正式动作复活。这可对应到 LDVH 已有的 Spark `deferred`（可逆悬置）与 WorkCase `rebatch`/`cancel`（须留因）两种机制的组合。

溯源：https://www.ietf.org/ietf-ftp/ietf/1id-guidelines.txt（I-D 有效期与到期处置章节）

## 未证实与缺口
- 缺口（high）：没有任何权威来源给出「项目级推进计划」这一内容类别的载体规范——ADR 管架构决策、KEP 管单个特性、changelog 管已发布差异、RFC 管设计提案，四者都不等于「项目下一步做什么」。本调研的肯定性结论只能由多个邻近类型的机制拼合而成，属跳域类比，迁移到 LDVH 时必须声明为自建而非沿用。
- 缺口（high）：没有任何权威来源正面讨论「计划文档与事实源／规格源之间的职责切分」——最接近的只有 PEP 1 的「退位为历史文档」句与 KEP 的「git 不是项目管理工具」，均为侧写而非正面论述。
- 缺口（high）：没有任何权威来源提供「计划/路线图文档与事实源脱节」的机械检测方案；现有机制全部是事件驱动的单向上游→计划同步，无反向一致性检查。
- 缺口（high）：全部证据来自产品管理与软件工程语境，无任何 AI 协作治理或规格驱动开发语境的直接论述；F1–F13 对 LDVH 的全部含义均为跳域推理，未经同类系统验证。
- 缺口（medium）：Jira Plans / Advanced Roadmaps 与 GitLab Epics/Roadmaps 的官方正文未取到（多处 404、正文截断或 CAPTCHA），此两类「项目级计划视图」产品的官方设计理由缺失。
- 缺口（medium）：「N 天无更新即复核」在文档/计划（非 issue）语境下的权威阈值不存在——actions/stale 与 GOV.UK 均只覆盖 issue 或网页内容，其数值不可直接移植到计划条目。
- 缺口（medium）：计划条目数量上限的权威建议值不存在，仅有 GitHub 的平台上限 50000 与 Kanban Guide「必须设上限但不规定数值」两条间接依据。
- 缺口（medium）：GitLab 自身的路线图载体形态证据缺失（handbook 的 product direction 路径 404，about.gitlab.com/direction 仅返导航壳）。
- 缺口（low）：PMBOK 正文对 progressive elaboration 的逐字定义未取到，滚动式规划的官方规范表述缺位。
- 缺口（low）：Docusaurus onBrokenLinks 默认值与 Sphinx linkcheck builder 各选项默认值未取到，构建期链接闸门的默认强度无法比较。
- 缺口（low）：PyPI/npm 生态的弃用与陈旧标记阈值未覆盖，包管理语境下的到期机制无样本。

## 建议
A1 为「推进计划」建立独立的事实类型，并把「当前计划」与「变动史」分给不同承载：当前计划作为受控对象（CAS + change_log），变动史由 Git 与 change_log 兜底；改向不通过改写原计划正文保存，而通过「旧版本冻结 + 新版本承载现状 + 双向指针」表达。判断依据：F3 的四家一致做法（AWS、KEP、PEP 1、Rust RFC 均不靠改写原文保存历史）+ F8 的分载解法；此形状与 LDVH 已有的 ADR `superseded-by`、Research `updates`、WorkCase `rebatch` 三套机制同构，可直接复用而非新造。

A2 蓝图的投影面直接现算，不落盘聚合物；authored 面（下一步、悬而未决）作为计划的受控正文承载。判断依据：F5（GitHub Projects 的投影不存副本是唯一在工程上真正实现「不形成第二事实源」的样本）+ F11（幂等重建说明落盘的聚合物会引入新漂移类）；落地前提是本仓 `serves` 的按 SG 聚合查询能力先于呈现面建立。该聚合缺口当前未被登记为任何账目；相邻的 Friction `bdbab9ab` 覆盖的是写入后反查复核通路，聚合仅为其正文列举的候选形态之一，不构成对本缺口的登记。

A3 「下一步」与「悬而未决」两块采用三条纪律：未决项的记录不构成承诺；已否决项须记原因以防重提；远期条目只给近似值并标出确定性档位。判断依据：F2（PMI 的 approximate 口径与 ProdPad 的地平线分级）+ F9（Rust RFC 的反承诺声明与 PEP 1 的防重提目的）；这三条恰好对应 LDVH 三个 open spark 所标记的缺口。

A4 陈旧与到期机制照 IETF I-D 的四件套设计，但阈值由 Human 定，不抄样本数值。判断依据：F12（权威给出阈值理由却普遍拒绝给数值，且到期只触发标记与提请，终态判定留给人）+ F13（硬阈值 + 自动移出活跃面 + 墓碑留痕 + 正式复活通道是唯一四项齐备的制度样本）。
