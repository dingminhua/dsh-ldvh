## 研究问题

本调研回答的问题是：

> 软件开发可分解为哪些「方向」（工程/产品/治理/团队/质量等），以及 LDVH 应如何按「一个方向至多由一份规范承载（反重复版）」组织项目自身的事实规范？

该问题由两个子目标构成：①枚举软件开发可能分解为哪些「方向」（工程/产品/治理/团队/质量五层）；②基于调研结论，给出 LDVH 应以何种规则组织项目自身的事实规范。调研内容来自 `docs/survey-software-directions.md`（已完成、已终止的一轮深度调研）。

**结论背景（已裁定，非本对象新论证）**：Human 已裁定「一方向一规范」为**反重复版**——同一方向至多由一份规范承载（反重复），但一份规范可聚合多个强相关方向（允许合并）；方向内子主题可拆文件但不得升格新方向；跨方向约束以主规范承载 + 他处引用实现，禁止重复定义。本对象正文据此如实呈现调研发现。

## 输入与边界

- **实际读取的外部来源分工**：调研使用 web 搜索核实了各方向的行业依据，代表性来源见本对象 `urls`：Google eng-practices（E1 代码风格）、WCAG 2.1（E2/E16 Web 与无障碍）、OpenAPI（E5 API 契约）、12-Factor config（E10 配置）、OWASP Top 10（E11 安全）、OpenTelemetry（E13 可观测性）、ADR 实践（E21 架构）、SemVer（G8 版本）、Keep a Changelog（G5 文档）、用户故事与验收准则（P1/Q1）、GitHub 分支（G10 分支策略）；以及 LDVH 既有元规范 09/10/08/05/06/02 作为「是否已被承载」的对照。
- **观察时点与版本**：来源为公开规范/文档的稳定 URL（2026-09 读取）；本对象为信息性分类，不绑定某一框架版本。
- **分析方法**：文档阅读 + 行业共识归类 + 对 LDVH 现状的覆盖比对（✓/◐/✗），非代码级静态分析或试运行。
- **不覆盖范围**：本对象不承载任何规范正文、不立项、不对具体被管辖项目写规范；调研原文中的「与 LDVH 现状落差」仅作事实记录。
- **来源冲突**：无实质冲突；少数方向（如安全 vs 隐私）存在法规边界独立但常合并处理的实践分歧，已在关键发现中按「必须分开」标注。

## 关键发现

### C1 软件开发方向可按五层罗列为约 42 个候选方向

调研将「方向」定义为「一个软件项目会产生的规范方向」，按工程（E1–E21，21 项）、产品（P1–P5，5 项）、治理（G1–G10，10 项）、团队与流程（T1–T4，4 项）、质量与验证（Q1–Q4，4 项）五层罗列，合计约 42 个候选方向。典型内容、必需性与依据见 `docs/survey-software-directions.md` 第一、二节。

**对 LDVH/管辖项目的价值判断**：方向总量远多于可行规范数，证明机械「一方向一文件」不可持续，必须引入合并/聚合策略。

溯源：https://google.github.io/eng-practices/review/reviewer/standard.html（代码评审准则→代码健康度作为 E1 必需方向的依据）

### C2 大多数候选方向在 LDVH 元规范中未被作为「方向」承载

调研对每项标注 LDVH 覆盖：✓ 已覆盖（09 Code、10 Web 两份完整覆盖为工程方向）；◐ 部分覆盖（05 仅 API 契约的 CLI 自身契约、06 受控提交契约、08 发布/文档/版本门面、02 评审制度）；✗ 未覆盖（依赖/配置/安全/可观测性/架构/需求/验收/审计/合规/许可证/隐私/缺陷/复盘等约 35+ 个方向）。

**对 LDVH/管辖项目的价值判断**：事实规范规划存在大面积盲区，需优先补齐必需且 ✗ 的方向；但补齐应以「15–20 份为健康上限」聚合推进，而非逐方向建规范。

溯源：https://github.com/dmh2002/dsh-ldvh/blob/dev/specs/09-Code实践与测试规范.md（09=Code 方向，完整覆盖 E1+E6 的说明）

### C3 「一个方向一个规范」须读作反重复版

调研复核 Human 给定实例（09 把「代码风格+测试」合并、10 把「呈现+交互」合并）后指出：严格字面「一份规范只承载一个方向」与 09/10 既成事实矛盾；实际意图更可能是「一个方向不被多份规范重复承载」（反重复）。建议精炼为「一方向至多一份规范、一份规范可聚合强相关方向」。

**对 LDVH/管辖项目的价值判断**：判据的正确读法直接决定规范数量与维护成本，应按反重复版执行，既成 09/10 合规定性。

溯源：https://github.com/dmh2002/dsh-ldvh/blob/dev/specs/10-Web呈现与交互规范.md（10=Web 方向，完整覆盖 E2+P2 交互的说明）

### C4 方向内子主题可拆文件但不得升格为新方向、跨方向约束以主规范承载+他处引用

调研指出单方向内容可能溢出单文件（如「安全」拆为应用/基础设施/数据安全），拆后仍是同一方向多份子文件；跨方向内容（如 API 的安全规则）须以主规范承载、他处引用，禁止重复定义。

**对 LDVH/管辖项目的价值判断**：规范撰写需建立显式引用纪律，LDVH 06/08/05/02 的局部覆盖项应据引用而非复制，避免规范漂移与重复。

溯源：https://github.com/dmh2002/dsh-ldvh/blob/dev/specs/06-事实源与提交契约.md（06 在受控提交契约局部触及分支策略等方向——据引用而非复制）

### C5 部分「方向」应由事实类型能力承载而非事实规范

调研指出审计（G1）、缺陷（Q3）、复盘（Q4）等「方向」在 LDVH 中已由事实类型（ADR/Pitfall/Friction/WorkCase 等）提供能力，未必需要独立「规范方向」；此边界需 Human 裁定。

**对 LDVH/管辖项目的价值判断**：事实规范规划前应区分「规范方向」与「事实类型能力」，避免为已承接的能力新建规范方向，减少规范爆炸。

溯源：https://github.com/dmh2002/dsh-ldvh/blob/dev/specs/24-Research-调研报告.md（24 本部类型规范；证明以 Research 事实类型落盘调研结论的正当性）

## 未证实与缺口

- **未证实（uncertain）**：
  1. 「方向」粒度未定（粗 5 / 细 42），导致判据不可机械执行——见上 uncertain[0]，原因：元层级与项目层级混谈。
  2. 供应商/第三方（G9）、知识管理（T3）等仅厂商综述或工具盘点来源，未达强 [源]——见 uncertain[1]。
  3. 可选方向是否计入「规范」总量未定——见 uncertain[2]。
- **缺口（gaps）**：
  - high：元/项目层级判据适用范围未裁定，阻塞全部事实规范立项决策（见 gaps[0]）。
  - medium：单方向溢出的子主题拆分边界未定义（gaps[1]）；跨方向引用纪律未成文（gaps[2]）。
- **对判断的阻塞范围**：high 缺口使「是否按本清单规划规范」无法闭环，须先由 Human 裁定适用范围与粒度锚点。

## 建议

- **建议 1（规范规划）**：以「反重复版」为准则，对 ✗ 未覆盖的必需方向（依赖与供应链、配置与安全基线、错误处理与可观测性、构建/发布/部署、需求与验收、文档与版本策略、评审与变更、协作与分支）规划约 15–20 份事实规范，强相关方向聚合（如 09/10 模式）。目标对象类型：norm（spec）；预期目标：补齐覆盖盲区且规范数 ≤20；验收条件：每个 ✓/◐/✗ 状态有明确的规划去向；创建/更新判断：由主控在事实规范规划立项时调用。
- **建议 2（引用纪律）**：跨方向约束一律以主规范承载 + 他处引用实现，禁止重复定义；06/08/05/02 的局部覆盖项据引用纳入。目标对象：norm；验收：存在跨方向引用且零重复定义；创建判断：新规范起草时。
- **建议 3（能力 vs 规范分流）**：审计/缺陷/复盘等先判为事实类型能力（ADR/Pitfall/Friction/WorkCase）而非规范方向。目标：norm 规划；验收：规划表中标注每项是「规范」还是「类型能力」；创建判断：规划评审时。
- **建议 4（判据精炼）**：将 Human 判据精炼为「一方向至多一份规范、一份可聚合强相关、子主题可拆不升格、跨方向主规范承载+引用」。目标：spec（元规范或规划文档）；验收：判据含粒度锚点与适用范围；创建判断：由 Human 在规范治理时裁定。

## 后续分流

- **分流 1（Human Gate 前置）**：当 Human 裁定「判据适用范围（元层级 vs 项目层级）+ 粒度锚点」后，方可据本对象规划事实规范清单；在此之前不得据此立项。信号：Human 给出适用范围/粒度判据 → 创建 norm 规划对象。
- **分流 2（规范创建）**：当某 ✗ 必需方向确定要立规范时，创建对应 norm 并据建议 1–3 执行；信号：主控发起事实规范规划 WorkCase → 创建/更新 norm。
- **分流 3（类型能力确认）**：当某关注面被判定为事实类型能力（非规范）时，不创建 norm，转而确认既有事实类型（ADR/Pitfall/Friction/WorkCase）是否充分；信号：规划评审判定为能力 → 检查事实类型覆盖，无需对象化。
- **分流 4（无需对象化监测）**：若后续 Human 明确「仅元层级适用，本 42 项目方向不进入项目事实规范」，则本对象作为「反重复版判据背景」留存、无需进一步分流；信号：Human 声明适用范围仅元层级 → 本对象保持 active 仅供参考，不触发规范规划。
