## 研究问题

在 AI 编码代理的长程工作治理领域，外部已有哪些项目在做同类事情？它们各解决 LDVH 工单执行系统所声称的哪一部分问题，用了什么机制，又在哪些地方做了不同取舍？

## 输入与边界

调研边界限定在四类对外可查的公开项目/规范：① 持久化执行（durable execution）与人类审批；② 面向 AI 代理的任务追踪（issue tracker）；③ 受治理自治（governed autonomy）与职责分离规范；④ 规格驱动开发（SDD）方法论的批评与实践反思。

不覆盖：商业闭源产品的内部实现；具体代码实现质量评估；性能基准。检索手段为公开网络检索与页面抓取，结论以公开文档自述为限，未做独立复现。

## 关键发现

### F1 持久化执行是独立且成熟的领域，LDVH 的 attempt 正处于其覆盖面内

Temporal、Restate、DBOS、Inngest、Prefect 3.0 构成 2025–2026 一代的持久化执行框架：工作流状态持久化、确定性重放、从失败点精确恢复。Temporal 的 LangGraph 插件把每个图节点作为 Activity 执行并在每个节点落检查点，明确区分「检查点保存状态」与「持久化执行让运行本身存活」——其说法是 checkpoints are not durable execution。该领域把「人机审批」重新定义为一个正确性问题而非 UX 问题：审批必须可持久化，否则进程崩溃后审批状态丢失。

对 LDVH 的意义：21 §10.4 的 attempt 令牌（单调 id、至多一个活跃、孤立 attempt 判定）在概念上与这一领域的「租约（lease）+ 尝试（attempt）」模型同构，但 LDVH 只有字段契约、没有运行期实现。这不是 LDVH 独有的落后——它是**选择了不自己实现运行时**，把这块留给宿主（10/06）。

溯源：https://temporal.io/blog/temporal-langgraph-plugin-durable-execution（LangGraph 插件：节点级检查点与持久化执行的区别）

### F2 logplane 提供了与 LDVH 最接近的「单机、事件溯源、租约」完整实现

logplane（原名 agent-bus，v0.13.3，MIT）是本地单用户代理编排控制面。其核心设计与 LDVH 高度可对照：以 append-only 事件日志为唯一真相，当前状态由重放派生，而非可变任务板；四个身份区分重试与重放（correlation_id / task_id / assignment_id / instance_id）；worker 持有租约，死掉的 worker 的尝试过期后被重新分配；只允许当前尝试推进任务，丢失 worker 的迟到结果被拒绝；外部副作用用 assignment.effect_id 作幂等键，使重试不会重复执行。

**这是 LDVH「孤立 attempt」问题的一个已落地答案**：判定不是靠字段形状，而是靠「租约过期」这一可观测的运行期事实。LDVH 当前无租约概念，故 `heartbeat_at` 只是一个时间戳，无法区分「还活着但慢」与「已经死了」。

同时 logplane 明确声明其信任边界：actor 自报、token 只认证客户端不认证身份、任何授权客户端可冒充任何 actor、非分布式、单机单用户。**这与 LDVH 在 DSH 单宿主上的处境几乎相同。**

溯源：https://pypi.org/project/logplane/（What you get 段：租约、单活跃持有者、迟到结果拒绝、effect_id 幂等）

### F3 「受治理自治」规范把职责分离写进了工作项 schema，而非仅写在文档里

modonome 的 governed-autonomy-spec（v0.1-draft，MIT）定义了 maker / checker / merge authority 三个必须互不相同的身份，并要求**在工作项 schema 里落 maker_id、maker_model、checker_id、checker_model 字段**，合并时若 maker_id == checker_id 即拒绝。它与 LDVH 的对应关系非常直接：maker ↔ 实施者（attempt 持有者）；checker（独立上下文）↔ `reviews` + 独立复核门禁；merge authority ↔ Gate 2 的 Human 终判；其 P5 owner-gated learning（代理不得自行改写治理自身行为的规则）↔ `pre_reviews` 的审核轴写权限隔离。

其 P2 明确一条 LDVH 也面对的判断：单会话不得同时对同一工作项持有 maker 与 checker 角色；若只有单一身份，实现**必须**关闭自治检查与合并、转为 principal 复核，**不得**在单身份下继续合并。

**这条外部规范恰好印证了 LDVH 发现 A 的方向正确性**：LDVH 用 `session_id != implementer_session_id` 做同一件事，且在两值相等时 fail-closed。但外部规范把判据落在「工作项 schema 里显式记录的两个身份」，而 LDVH 落在「attempt.session_id（一个可能在 heartbeat 路径上不代表实际写入者的字段）」——差异在**判据的来源字段是否就是该语义的权威承载**。

溯源：https://github.com/enumind/modonome/blob/HEAD/docs/specs/governed-autonomy-spec.md（§4.1 maker/checker/merger 契约与 P2 职责分离）

### F4 职责分离在人类工作流里同样会失效，且失效形态相同

两处独立证据表明「自审通过」不是 AI 特有缺陷：typeorm PR #12380 讨论的 `approve_pr_on_self_review = true` 直接削弱 independent-review／separation-of-duties 控制；NVIDIA NemoClaw issue #6222 指出 GitHub 阻断了「PR 发起人批准自己的 PR」，但没有阻断「评审者随后成为贡献者再提供唯一的人类批准」，四人审查模型被绕过。

后者与 LDVH 发现 A 的形态**同构**：不是判据写错了，而是**身份在流程中途发生了变化，判据仍按旧身份比对**。这提示修复方向应是「判据绑定的身份须随实际动作更新」，而非仅加强比对。

溯源：https://github.com/NVIDIA/NemoClaw/issues/6222（评审者转为贡献者后提供唯一批准，绕过四人审查）

### F5 SDD 的主要已记录代价是「建设阶段退化为文档工作」

InnoQ 的实践反思（2026-04）记录：SDD 在思考阶段确实降低复杂度（迫使模糊需求明确化、切分范围、暴露缺口），但在建设阶段会翻车——一个简单 story 膨胀到 1070 行 Markdown；接着 agent 从中生成庞大实现计划，最终**没人认真读**，反而破坏了 story 原本要保证的理解共享。其引用 Jeff Patton：「共享文档不是共享理解」，story 是对话的提示物而非交接文档。作者的核心结论是：保护措施应逐步从文档转移到 harness（测试、linter、架构规则、评审），而不是把所有东西前置写进规格。

**这条对 LDVH 是最直接的警示**：LDVH 的 27 份规范、36 份工单、118 条摩擦、1331 次提交，本身就在承担「文档是否已经过重」的风险。InnoQ 的判据可借用：当「写关于工作」超过「做工作」时即为过重。

溯源：https://www.innoq.com/en/blog/2026/04/versteckte-kosten-spec-driven-development/（When building devolves into documentation work；1070 行 story 实例）

## 未证实与缺口

- 未找到任何项目同时具备 LDVH 的四项组合：① 三值状态机 + Gate 两道人类关口；② 内容指纹钉扎授权；③ 双轴（审核轴/复核轴）分离且各有独立写路径隔离；④ 事实对象与规范源分离、对象类型闭集由规范定义。最接近的是 modonome（有 ①② 的骨架与 ③ 的思想）与 logplane（有 attempt 的运行期实现），但两者都没有 LDVH 的「规范源—事实源」双层结构。
- 未验证 logplane 的租约机制在 DSH 宿主上是否可移植（DSH 不提供进程级心跳服务，需另行确认）。
- 未评估各项目的实际采用规模与长期维护状况。
- 「规格驱动开发是否值得」缺少对照实验数据，仅有实践者自述。

## 建议

1. **attempt 的运行期实现可直接借鉴 logplane 的租约模型**（租约过期 + 单活跃持有者 + 迟到结果拒绝 + 幂等键），而非另设计一套。落地前须确认 DSH 宿主是否提供可用的进程存活信号。
2. **发现 A 的修复方向应按 F4 的证据调整为「判据身份须随实际动作更新」**，即 heartbeat 时若写入者身份与 attempt 持有者不同，应更新持有者基线（或强制 takeover），而不是维持旧基线。
3. **借用 modonome 的 conformance-level 做法**（Level 0–3 分层声明各自满足条件），为 LDVH 的七项机制给出类似的分层诚实声明，避免「全有或全无」的表述。
4. **采纳 InnoQ 的判据作为自重检查**：定期衡量「写文档/写规范的时间」与「实际推进工作的时间」的比例，作为是否过重的信号。

## 后续分流
