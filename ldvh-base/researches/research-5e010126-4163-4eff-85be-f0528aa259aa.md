## 研究问题

第三方 DSH 插件 DSH-Project-Initialization（「想法落地」，v1.1.0）的机制构成、确认绑定与操作分级如何工作，以及它对 LDVH「引导设定项目目标与计划」这一能力面的参考价值与边界在哪

**服务对象声明（30 §1.2）**：本调研属**机制需求**——服务对象是 **LDVH 自身机制**，而非当前管辖项目的外部业务问题。调研目的是判断该第三方做法能否被 LDVH 的引导/规范面吸收，故结论默认指向 LDVH 机制判断，不默认指向 DSH 社区生态盘点。

## 关键发现

### F1 定位是 agent preset 而非功能插件

DSH-Project-Initialization 的交付形态不是新增工具或业务能力，而是一个 **agent preset（「想法落地」）**：`cordis.patch.yml` 只注册一个插件壳（`id: project-alignment`），宿主启动时把包内 `core-library/presets/alignment` 幂等复制到 `<dshHome>/.agent-presets/`，用户在新会话的场景选择器里选「想法落地」即进入。价值判断：这条路径对 LDVH 有直接参照意义——「引导设定项目目标和计划」如果做成插件，最自然的形态不是再造一套工具，而是**一个专门的 agent preset 承载引导身份 + 一组按需加载的 skill 承载规范**；LDVH 若要吸收，应评估在现有管辖会话内以 skill/preset 分层承载，而非另建平行体系。

溯源：https://github.com/Lorvaste/DSH-Project-Initialization/blob/main/cordis.patch.yml（插件壳 insert）

### F2 无场景预设、按上下文加载 skill 的调度模型

v1.1 取消了 v1.0.3 的「三场景最小预设」，改为**无场景预设**：6 类主 skill（base/req/dev/mnt/common/rules）即入口，skill 按上下文线索（工作区状态 / 用户指令 / 自动触发）加载，每个 skill 可单独调用。`user-manual.md` 给出一张「上下文线索 → 加载哪些主 skill」的速查表（如「提交初稿/想法/白皮书 → req + common」「进入维护/发布/反馈 → mnt」）。价值判断：这与 LDVH 的 L0–L4 渐进披露思路同向——**不预先加载全量规范，而是按上下文把最小充分的那部分规范送到模型面前**。差异在于 LDVH 的分层是「规范披露深度」（L0 定位到 L4 全文），该插件的分层是「任务阶段」（需求/开发/维护），两者可互补：LDVH 可按阶段选择披露哪些规范段，而不止按深度。

溯源：https://github.com/Lorvaste/DSH-Project-Initialization/blob/main/user-manual.md（主 skill 速查）

### F3 确认绑定：明确拒绝「上下文表述/沉默」充当确认

`skills/item-confirm/SKILL.md` 定义了一条可机械判定的确认规则——**确认 = 用户对当前点名编号项的明确回应**；返回内容、上下文回复、沉默、陈述句、扮演假设均**不算确认**；未确认项不进下一阶段，驳回项重新澄清；确认后立即写入决策表（ID/决定/依据/状态/来源=用户确认）。并设「误认回退」：发现误把上下文当确认执行 → 复述实际执行内容 → 用户确认 → 修正记录。价值判断：这是本轮调研对 LDVH 价值最高的一条。LDVH 当前 Human Gate 依赖 AI 判断「Human 是否确认」，而该插件把「什么算确认」**文本化为一条可核对的判据**，并配了误判的回退路径。LDVH 的吸收方向是明确的：在需要 Human 确认的节点（如 Gate 1 批准、Goal 修订、受控写入确认）显式声明「确认的形式要件」，把「AI 觉得用户同意了」这一最脆弱的判断点收窄。

溯源：https://github.com/Lorvaste/DSH-Project-Initialization/blob/main/core-library/presets/alignment/skills/item-confirm/SKILL.md（确认绑定/误认回退）

### F4 操作分级 L0–L4 与禁区拒绝

README 与 user-manual 一致声明**操作分级 L0-L4**：执行前核对授权范围，**禁区拒绝、高风险单独请示、干跑先行**。价值判断：LDVH 已有的授权语义（scope、越权拒绝、受控写入）比该插件更机械、更严格（有 fingerprint/CAS/validator 支撑），故此条**不应被吸收为规则来源**，但其「执行前先核对该操作是否在本轮授权范围内」的操作习惯与 LDVH 的 scope 字段同构——可作为 LDVH 在向 Human 交代时的表述参考（即：把「越权拒绝」这一机制用一句人话前置说明）。属低优先级参照。

溯源：https://github.com/Lorvaste/DSH-Project-Initialization/blob/main/README.md（规则要点-操作分级）

### F5 扮演假设规则族：假设须声明且 ≠ 事实

该插件设「扮演假设」规则族：扮演角色前声明假设；**扮演假设 ≠ 事实**；尊重客观事实，明确**禁止讨好用户与迎合上下文**；另有「因果与逻辑事实验证」（回答/提问前验证因果与前提）。价值判断：与 LDVH 00 §7「防自欺」同向。差别在承载：LDVH 的防自欺靠机械锚点（validator、fingerprint、Git Gate）与 Stop Conditions，属**结构性防自欺**；该插件靠 agent 的规则自觉，属**提示词层防自欺**。本条的参考价值在于它把「禁讨好、禁迎合上下文」作为一条显式禁令写进 persona 与 skill——LDVH 的防自欺若要在提示词层补强，「AI 不得因 Human 期待而软化证据」是一条可直接表述的禁令。

溯源：https://github.com/Lorvaste/DSH-Project-Initialization/blob/main/core-library/presets/alignment/agent.cordis.yml（persona 原则段）

### F6 引导者立场：AI 是引导者不是决策者

persona 文本明确「AI 是引导者不是决策者，用户是唯一权威；阶段推进由用户决定，禁止自行『假定完成』；沉默≠同意，关键点必须显式确认」，并给出**优先级链：用户拍板 > 全局规则（AGENTS.md）> 域内规则 > 规则（skill 规则）**。价值判断：与 LDVH 00 §4「Human 决定权」同构，可作为 LDVH 在 Human 面向的**表述参照**（用一句人话讲清「AI 不替你拍板」）。优先级链本身不宜吸收——LDVH 的规则效力次序由规范源层级（元规范/事实规范）机械确定，不靠提示词里的软声明，此处若照搬会形成第二权威。

溯源：https://github.com/Lorvaste/DSH-Project-Initialization/blob/main/core-library/presets/alignment/agent.cordis.yml（persona 优先级链）

### F7 工具白名单按 preset 收窄

`agent.cordis.yml` 显式接线工具白名单：`tool-ask-user`、`tool-fs`、`tool-fs-search`、`tool-bash`/`tool-pwsh`（按平台二选一，`disabled: !!js process.platform === 'win32'`）、skill 加载、compaction，**并明确「砍掉 subagent 等」以省 token**，仅保留 web 检索工具作为「相似方案/竞品检索例外」。同时 `skill-filesystem` 配置 `includeDefaultRoots: false` + 自定义 `customSkillDirs`，**只扫描 preset 自身 skills/ 以隔离外部 skill**。价值判断：两条机制对 LDVH 都有现实参照。其一，「按 preset 收窄工具面」是控制引导型 agent 边界的具体手段；其二，**skill 根目录隔离**（不扫默认根）意味着同一个 DSH 里可并存多套互不干扰的 skill 体系——这对 LDVH 有直接意义：LVH 的引导规则若以 skill 承载，需明确它与其他 skill 体系的可见性边界，避免规则互相污染。

溯源：https://github.com/Lorvaste/DSH-Project-Initialization/blob/main/core-library/presets/alignment/agent.cordis.yml（工具白名单/skill-filesystem）

### F8 verify 作为唯一验证调度者

`skills/verify/SKILL.md` 定义 verify 为**唯一验证调度者**：任何验证请求经它调度，按目标选择验证单元组合（如「需求/规格检查 → verify-3layer + verify-7dim + verify-3check + verify-placeholder」），输出 verify-report 模板，**结果经用户确认后生效**，并与阶段推进联动（阶段推进前给出检查类型清单）。价值判断：这与 LDVH 的「复核制度」同向但层次不同——该插件的 verify 是**单会话内的检查清单调度**，LDVH 的复核是有独立会话身份、独立记录的机械+语义双层核验（且 WorkCase close 要求由执行者之外的会话记录复核）。故 LDVH 不应以它为参照改造复核；可吸收的是其「**按目标选择验证单元组合**」的表述清晰度——把「这次要检查什么、用哪几项」在检查前显式列出，与 LDVH 02 §15 复核判据七要素的「覆盖/未覆盖」栏同向。

溯源：https://github.com/Lorvaste/DSH-Project-Initialization/blob/main/core-library/presets/alignment/skills/verify/SKILL.md（调度规则）

## 建议

A1 【可被 LDVH 规范吸收】在 Human 确认节点引入「确认的形式要件」：借鉴 item-confirm 的确认绑定，对 LVH 中依赖 Human 确认的节点（Gate 1 批准、Goal 修订、受控写入确认等）显式声明「什么算确认、什么不算」，并把「上下文表述/沉默不算确认」写成可核对判据。判断依据：F3。目标对象类型：Norm（方向为「Human 确认的形式要件」）或 00/25/21 相应节的修订。验收条件：至少一个 Human Gate 节点的规范文本含可核对的确认形式判据，且该判据被 AI 在提请时引用。创建/更新判断：先在讨论或 Spark 中定「采用哪几个确认节点」，再按 27 号建 Norm；当前不宜直接改 00（根规范修订代价高、影响面大）。

A2 【可被 LDVH 规范吸收】补一条「AI 不得因 Human 期待而软化证据」的显式禁令：借鉴 F5 的「禁止讨好用户与迎合上下文」，在防自欺面（00 §7）或其下游规范中，把该禁令文本化。判断依据：F5。目标对象类型：Norm 或 00 §7 修订。验收条件：防御面规范含该禁令的明确表述，且能在复核判据中对应到「发现：是否因期待而软化证据」这一栏。创建/更新判断：与 A1 一并讨论，避免零散改根规范。

A3 【已明确不吸收】不复刻该插件的规则效力链（用户拍板 > 全局规则 > 域内规则 > skill 规则）：LDVH 的规则效力由规范源层级机械确定，不引入提示词层优先级链，以免形成第二权威。判断依据：F6。保留判断依据与后续监测条件：若 LDVH 未来需要向 Human 解释「谁的规则更大」，应以规范源层级原文作答，而非引入插件式优先级声明。此项建议即「无需对象化」的显式声明。

A4 【工程参照，可被 WorkCase 承接】skill 体系隔离与工具面收窄：借鉴 `includeDefaultRoots: false` + `customSkillDirs` 的 skill 根隔离做法，明确 LDVH 引导规则以 skill 承载时的可见性边界；同时评估按会话/场景收窄工具面的必要性。判断依据：F7。目标对象类型：WorkCase（LDVH 插件能力面）。验收条件：LDVH 若有 skill 承载，其隔离配置明确且实测不与其它 skill 体系互扰；工具面收窄必要性有结论。创建/更新判断：属 SG-3 dogfood 闭环范围内，出现实际互扰信号时建 WorkCase。

A5 【参考，不必对象化】「按目标列出验证单元组合」的表述清晰度：LDVH 复核判据七要素已覆盖覆盖/未覆盖栏，无需新建对象；若未来复核交付物出现「未说清检查哪几项」的实际摩擦，再按 26 号记 Friction 并触发改进。判断依据：F8。监测条件：复核交付物出现覆盖表述不清的实际摩擦。
