implications:
  - finding_ref: karpathy 明示该文档仅为抽象意图文件，实现形态全凭领域自定
    implication: 「LDVH 是否可以这样做」无法通过对齐该模式文本回答，只能比较实现层与既有设计——任何以「karpathy 说了」为由要求增设结构的主张在方法上不成立。
  - finding_ref: 公众号文章自认该模式不适用企业场景：规模、权限与溯源三重局限
    implication: 该模式自认的局限恰好命中 LDVH 的规模、受众分诊与溯源三关切，说明 LDVH 已有治理强度高于该实践样本，模式本身不构成增量。
  - finding_ref: 机械可校验性是实现成色的决定性轴，而非 schema 表达力
    implication: LDVH 把机械校验与语义判断严格分立是必要而非过度；同族规则在纯提示词实现中遵从率不可观测，在机械实现中成为恒真保证。
  - finding_ref: 全部实现均未做近重复检测、写前四操作比对或乐观锁
    implication: LDVH 的四操作比对与 CAS 受控写入属该模式生态中的少数派能力，是相对价值而非过度设计。
  - finding_ref: zissa 的引文逐字回验是全调研唯一可机检的溯源实现
    implication: LDVH 的溯源锚点机械校验可向「引文与来源一致」推进一段，但移植的是校验方法而非承载形态（LDVH 明确不把摘录复制进对象）。
  - finding_ref: cobusgreyling 把「矛盾必须显式登记」做成可 CI 的机械检查
    implication: 补上 LDVH 矛盾检测仅发生在写入时一次的空缺：词面信号作触发器、账本作承载、lint 作兜底，三者均无需 LLM 即可运行；因其存在误报，宜作警告而非门禁。
  - finding_ref: hangandrew 提供门 0 式分诊与攒熟阈值的完整可运行先例
    implication: LDVH 的门 0 与攒熟提议在纯 shell+prompt 环境已被证明可运行；须补的是防递归闸门（空闲代理触发的会话不得重新进入采集队列），35 号未登记该防护。
  - finding_ref: hangandrew 的高危操作两阶段授权与代价非对称纪律
    implication: LDVH 的晋升提议与受控创建宜拆为两个不同时机、不同证据要求的 pass；变更上限应分类型设置；「存疑即丢弃」应有明文代价理由。
  - finding_ref: cortexes 的静默丢失事故链确立记录 fail-open 与变更 fail-closed 的分治
    implication: LDVH 应对记录/观察路径与变更/提交路径显式分治失败语义；机械锚点不可用裸子串 grep 判定状态（处理记忆的流程本身会引用状态词）；去重与清理的失败模式必须是「重复留下」而非「内容丢失」。
  - finding_ref: 检索分数语义必须写死在规范层，否则产生假判决与静默漏判
    implication: LDVH 的 Jaccard ≥ 0.7 等阈值判断须在规范层写死分值用途，无法分值时输出「歧义」而非 0，非主通道命中须回填同尺度分数。
  - finding_ref: 调研范围内全部实现的核心检索层都不使用向量
    implication: LDVH「不上向量、永不上量化」的分量级选择在同生态内是收敛共识；另可借鉴页级+段级双层评分在不引入向量的前提下提升命中精度。
  - finding_ref: zissa 的认识论标记是唯一直接设防「AI 生成内容被当事实再消费」的机制
    implication: LDVH 缺一条「低置信来源不参与比对基准」的资格规则；「永不提升声明层级」应作为承载纪律——AI 综合内容流转时必须持续携带来源等级。
  - finding_ref: chobizzy 把 LLM 生成来源标为最低可信度并对枢纽页单独告警
    implication: 效用审计可按「高入链/高召回优先」排序，而非平均抽样——被引用越多的对象错误传播面越大；LLM 来源等级可进一步影响派生置信度而非仅作标签。
  - finding_ref: 三家独立收敛到「维护提议不自动执行」，反向佐证空闲代理保守纪律
    implication: LDVH 空闲维护的保守纪律是该领域踩坑后的共识而非过度设计；须补「不自动修复」与「必须报告」成对出现，并机械保证自动路径无法绕过约束。
  - finding_ref: DSH 生态已有 177 个记忆与知识库相关插件，生态并不空缺
    implication: 35 号 §16.1 独占记忆职责承诺的验证条件变得具体：LDVH 须证明现成插件为何不足以替代，而不只是证明自身机制自洽。
  - finding_ref: DSH 原生已有「记忆→wiki」提案制双向晋升实现，与 LDVH 晋升机制高度同构
    implication: LDVH 尚缺的服务端计算幂等键有现成解，可直接消除附录 A.3 登记的三路晋升竞争条件，优于当前的 Jaccard 兜底。
  - finding_ref: personal-wiki 的延迟审批闭环补上「批准晚于回合」这一未设计场景
    implication: Web 确认卡本质是异步的，LDVH 当前交还结构不覆盖跨回合结算；须补结算语义、幂等键墓碑化与 conflicted 终态，并区分闸门结算账本与记忆活动账本。
  - finding_ref: DSH 内 Karpathy 直译插件是 LDVH 红线的反面实现样本
    implication: 该模式在生态中的自然落地形态就是自动流水线（LLM 产出直接进入消费闭环、零溯源、失败静默），这解释了 LDVH 红线 4 的必要性；且插件取证必须以代码为准。
  - finding_ref: 成熟生态在检索侧过度投资、在写入治理侧留白
    implication: LDVH 重心位于生态空白侧（受控写入与治理）而非竞争激烈的检索侧，这是顺向定位信号，但相对价值须由治理能力兑现。
  - finding_ref: 向量与图谱的记忆增益数字均出自利益相关方自测，且已有第三方反证
    implication: 现有证据不支持把任何检索增强设为默认；LDVH 把此类升级列为远期非承诺候选的写法得到外部证据支持。
  - finding_ref: 生态取证纪律：热度与 scope 名不可作为影响力与官方性的证据
    implication: 后续生态调研须核对仓库创建时间与提交历史、以代码核对 README 宣称；该纪律可并入 30 号调研系统的来源甄别纪律。

## 研究问题

LLM Wiki 模式（karpathy 2026 提出的「由 LLM 增量维护结构化 wiki」知识库构建模式）的三层架构、运作机制与不变量是什么？现存有哪些成熟实现与同类可安装插件，其增量更新、去重与矛盾保留、索引与检索、溯源与防污染机制如何实际实现（含失败模式）？该模式对 LDVH 记忆与反思系统（specs/35：git 层严进严出 + 本地层宽进轻出 + 门 0 分诊 + 双路召回 + 三路晋升）的分工边界意味着什么——其中哪些机制可被吸收、哪些与既有设计相冲突或属须避开的路线？

展开：本轮调研的对象不是「LLM Wiki 好不好用」这一评价问题，而是三件可取证的事——(a) 该模式由原始作者定义的构成要素与不变量是什么（以一手 gist 为准，不以二手转述为准）；(b) 现存实现各自把哪些不变量做成了机械保证、哪些仍停留在提示词纪律，以及在此过程中暴露了哪些真实失败模式；(c) LDVH 记忆与反思系统当前设计中，哪些边界与该模式冲突、哪些机制属于可直接吸收的增量、哪些属于须避开的路线。调研支撑的项目判断是「LDVH 记忆系统是否引入 wiki 化知识编译子层」。

## 关键发现

### LLM Wiki 模式的三层架构与「一次编译、持续复用」核心主张

观察：一手定义把模式固定为三层——raw 源层（人负责收集，**不可变**，LLM 只读不写，是事实来源）、wiki 编译层（LLM 完全拥有：摘要页、实体页、概念页、比较、综合，负责创建、更新、维护交叉引用与一致性）、schema 层（`CLAUDE.md`/`AGENTS.md` 一类文档，规定 wiki 结构与 ingest/query/维护的工作流，作者称之为「关键配置文件——它使 LLM 成为有纪律的 wiki 维护者而非通用聊天机器人」）。模式的核心主张是知识被**编译一次并保持当前**，而不是每次查询重新推导：交叉引用已经存在、矛盾已经被标记、综合已经反映读过的一切。

对 LDVH 的价值判断：三层架构本身对 LDVH 不构成新知识——LDVH 已有更严格的三层（规范源、事实源 `ldvh-base/`、业务系统），且其 schema 层是受成立程序约束的规范源而非单个 markdown 文件。真正需要吸收的是该模式对「可累积性」的论证方向：它主张价值来自**持续维护产生的复合结构**，而非单次检索质量。这与 LDVH 的 V8 持续积累同向，但 LDVH 用类型化对象 + 受控写入 + Human Gate 达成同一目的，两者是**同目标的不同手段**，而非可叠加的两层。

溯源：https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f（Architecture 节三个 bullet；The core idea 节）

### 模式的三条操作与「矛盾并存不覆盖」要求

观察：一手定义给出三条操作。Ingest——把新源读入、与 Human 讨论要点、写摘要页、更新 index、更新受影响的实体页与概念页、追加 log，**单个源可能触及 10-15 个 wiki 页**，作者偏好一次一个源并保持参与。Query——检索相关页、读取、带引用综合回答，并明确「好答案应能被归档回 wiki 成为新页，这样探索也像源一样复利」。Lint——周期性健康检查：页间矛盾、被新源取代的陈旧断言、无入链的孤儿页、被提及但缺页的重要概念、缺失的交叉引用、可用检索填补的数据缺口。关于矛盾，定义要求的是**标记而非覆盖**：新资料与旧说法不一致时，同时保留来源、时间与适用范围并给出冲突提示。

对 LDVH 的价值判断：lint 的检查清单（矛盾/陈旧/孤儿/缺页/缺交叉引用）与 LDVH §10.5 的四失败模式体检是两套不同的问题域——前者查「知识库结构是否健康」，后者查「记忆机制是否失灵」。LDVH 缺的正是前者这一层，且它已在调研范围内被证明可机械实现（见 F12、F23）。「答案归档回库」这一主张对 LDVH 有直接代价警告：它等价于「把召回产物再写为记忆」，正是 LDVH 门 0 第 2 条与再消费污染风险的交汇处，不能无条件吸收。

溯源：https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f（Operations 节三段；The core idea 节末段）

### 模式的价值立论是维护成本转移而非检索质量提升

观察：作者的立论全部围绕维护成本：维护知识库最枯燥的部分不是阅读或思考，而是记账——更新交叉引用、保持摘要当前、记录新数据何时与旧声明矛盾、维持数十个页面间的一致性；人类放弃 wiki 是因为维护负担增长快于价值；LLM 不会厌烦、不会忘记更新交叉引用、一次可触及 15 个文件，因此维护成本接近零。作者把该模式在精神上接到 Vannevar Bush 的 Memex（1945），并指出 Bush 未能解决的那一环正是「谁来做维护」。

对 LDVH 的价值判断：这个立论对 LDVH 是**顺向且已内化**的——35 号规范 §10 的空闲维护代理（评审/容量/体检三任务）与 §11 反思机制处理的正是同一问题（谁来做维护）。但它同时构成一个反面判据：如果 LDVH 引入 wiki 编译层却不配套「谁维护编译产物」的机制，就会把一个维护成本转移问题变成维护成本转移**问题**——引入新的需要维护的结构而不引入维护者。这是评估任何吸收动作时的硬约束。

溯源：https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f（Why this works 节；The core idea 节首段）

### karpathy 明示该文档仅为抽象意图文件，实现形态全凭领域自定

观察：一手定义在 Note 节明确声明：本文有意保持抽象，描述的是想法而非具体实现；目录结构、schema 约定、页面格式、工具链全部取决于领域、偏好与所用 LLM；文中提到的一切都是可选和模块化的——甚至可以只要 index 文件而不需要搜索引擎，可以只输出 markdown 不接受幻灯片。该文档唯一的工作是传达模式。

对 LDVH 的价值判断：这条边界对本轮调研的定位有决定性影响。模式**本身不提供任何可直接对齐的规范条款**——没有字段闭集、没有状态机、没有准入判据、没有失败语义。因此「LDVH 是否可以这样做」不能通过对齐 karpathy 文本回答，只能通过比较**实现层**（F8–F21）与 **LDVH 既有设计**（F22–F26）回答。任何以「karpathy 说了」为由要求 LDVH 增设结构的主张，在方法上不成立。

溯源：https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f（Note 节全文）

### index.md 索引优先导航在约百源量级被验证足以支撑中等规模

观察：一手定义给出两个特殊文件分工：`index.md` 是内容导向的全库目录（每页一行链接 + 一句话摘要 + 可选元数据），每次 ingest 更新，查询时先读 index 定位再钻入——作者称「这在中规模（约 100 个源、数百个页面）表现得出人意料地好，且避免了嵌入式 RAG 基础设施的必要」；`log.md` 是时间导向的追加式记录，建议每条以一致前缀开头（如 `## [2026-04-02] ingest | Article Title`），使其可用简单 unix 工具解析。作者另指出规模增长后可选本地搜索引擎（qmd，混合 BM25/向量 + LLM 重排，全在设备本地，同时具备 CLI 与 MCP 形态）。

对 LDVH 的价值判断：这是对 LDVH「本地层不上向量」取态的**同量级外部印证**——两者面对的记忆量级接近（LDVH 本地层容量上限 400 条），且都选择索引/启发式而非嵌入。同时它给出一条 LDVH 尚未采纳的具体做法：log 的**前缀一致性使记录可被机械解析**，这与 LDVH 要求 change_log 由 Code 托管署名同向，可佐证 LDVH 把流水做成结构化而非自由文本是正确取向。qmd 作为可选升级路径的存在，也与 35 号把 sqlite-vec 列为远期非承诺候选的写法同构（都不在 V1 承诺）。

溯源：https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f（Indexing and logging 节；Optional: CLI tools 节）

### 公众号文章自认该模式不适用企业场景：规模、权限与溯源三重局限

观察：触发本次调研的文章在给出完整实践后，用独立一节自我设限，列出三条理由：**数据规模**——wiki 文档膨胀到成百上千时，每次编译或查询的 token 消耗显著上升，甚至 index.md 本身可能撑爆上下文窗口；**权限管理**——企业级知识库需要细粒度访问控制，该模式支持不完善，难以满足安全合规；**可溯源性**——RAG 方案能明确回答基于哪个文档的哪一段，而 wiki 内容依赖模型对原始知识的理解与重构，「极有可能出现幻觉，存在生成错误知识关联的风险。一旦这类偏差被写入 Wiki，就可能会误导后续所有查询结果」。结论是该模式适合个人知识库与学习研究等低风险场景，企业知识库需要按规模、权限、引用准确性评估。

对 LDVH 的价值判断：这三条限制**恰好命中 LDVH 的三个核心关切**——规模（本地层 400 条上限与 git 层对象规模）、权限/受众（受众主轴与双层架构）、溯源（严进严出与举证义务）。作者自己承认的第三条最关键：偏差一旦写入就会污染后续所有查询——这正是 LDVH 用「严进严出 + 受控写入 + Human Gate + 退休流程」处理的问题。因此该文章不是「LDVH 应该照做」的论据，而是**「LDVH 若要做，必须带着比它更严的治理做」的论据**；而 LDVH 已有的治理强度高于该实践样本，说明模式本身不构成 LDVH 的增量。

溯源：https://mp.weixin.qq.com/s/VlcgqGtKt6OpESkvfBG0Zw（「在企业场景中，LLM wiki 的局限」节）

### 公众号文章的实践增量在工具链与采集管道，不在模式本身

观察：该文章的实质贡献是降低上手门槛与补齐采集管道：用 WorkBuddy（而非 Claude Code）承担编译角色，Obsidian 承担编辑器与可视化（关系图谱、双向链接），Obsidian Web Clipper 负责网页转 markdown 入 raw，IMA 知识库作为移动端（尤其微信公众号内容）中转站再经定时任务同步进 raw；并强调 AGENTS.md 写在项目根目录、「这个文件的内容并不是一劳永逸或者一蹴而就的，需要我们持续的维护更新，直到表现稳定」，以及原始资料质量决定 wiki 质量（宁缺勿滥，否则垃圾进垃圾出）。

对 LDVH 的价值判断：文章对模式的描述与一手 gist 一致，未引入新机制；其增量在**采集侧工程**（Web Clipper + IMA + 定时同步）与**可读性侧**（Obsidian 图谱）。这两项对 LDVH 均不适用：LDVH 的采集面是对话流与事实对象生命周期事件，不是外部网页剪藏；其可视化面由 10 号规范的四层阅读器与关系图承载。唯一值得登记的是「schema 文件需持续维护直到稳定」这一经验——它印证了 LDVH 把 schema 做成受成立程序约束的规范源（而非单个可随手改的文件）是更稳的处置。

### 机械可校验性是实现成色的决定性轴，而非 schema 表达力

观察：把样本按「规则能否被机械执行」排序后，成色差距极大而 schema 表达力差距很小。zissa-wiki 把机器可校验的规则下沉到 `conventions.toml`（类型枚举、必填字段、目录↔类型双向绑定、篇幅阈值、陈旧阈值），由单一 `wiki.py check` 命令产生非零退出码，并接到三处闸门：git pre-commit hook、Claude Stop hook、CI（Python 3.9/3.13 双矩阵）。反例是 obsidian-wiki：560 行 AGENTS.md 含 10 类页面闭集、逐类创建触发条件、confidence 字段、修复审批流，规则密度最高，但**无任何一条可被机械执行**——frontmatter 漂移、word-count 失真、confidence 自评只能靠模型自觉与人工排障，且该仓库把 wiki 目录 gitignore 掉，连审计线索都不留。

对 LDVH 的价值判断：这是本轮调研对 LDVH 最强的一条**方法论确证**。LDVH 把机械校验与语义判断严格分立（机械结果与语义判断互不替代），并被证明是必要而非过度：同一族规则在纯提示词实现中的遵从率无法被观测，而在机械实现中变成恒真保证。zissa 的 `conventions.toml` 写法另给出一条可直接吸收的工程模式：**叙述性 schema 留在规范/引导文档，机器可校验子集下沉为配置并驱动单一校验入口**——但须注意 zissa 靠人工保持两处同步，LDVH 应避免引入需双写同步的第二份真值。

### zissa 的引文逐字回验是全调研唯一可机检的溯源实现

观察：zissa 的 `quotes` 子命令把 source-note 中以引号开头的 blockquote 与其链接的 raw 原文做机械比对，只比字母（忽略标点、大小写、重音、连字、脚注号），因此 OCR 噪声与排版差异不计；能区分三种失败——`quote-differs`（改写）、`quote-omits`（未标记的省略，注释指出「未标记的省略可能反转语义」）、`quote-missing`（原文中找不到）；并能从 PDF 自印页码推算印刷页偏移以核对引文页码。`check` 命令进一步把「引了原文却不链接 raw 文件」从警告升级为错误。该仓库的 CHANGELOG 记载此漏洞由一次实测发现（「Quotes could escape checking」）。

对 LDVH 的价值判断：这是全调研中唯一做到「摘要/引文可被机械验证回指原文」的实现，也是与 LDVH 严进严出最直接对照的机制。LDVH 的 Research 类型已经要求每个发现单元附溯源锚点，但机械校验只覆盖锚点的**存在性、格式与 ref 回指一致性**，不覆盖「锚点处内容是否仍一致」（后者被明确划归 AI 语义审核与 F4 展开）。zissa 证明这条边界可以往机械侧推进一段：在存在本地可读来源副本时，引文比对是廉价且高信噪比的校验。**边界提醒**：LDVH 的 Research 明确「摘录原文不复制进对象」（24 §10），与 zissa 的 source-note 承载引文不同，因此可直接移植的是**校验方法**，不是承载形态。

溯源：https://github.com/MetamusicX/zissa-wiki（scripts/wiki.py quotes 实现与 scripts/README.md quotes 说明；CHANGELOG 相应条目）

### 全部实现均未做近重复检测、写前四操作比对或乐观锁

观察：逐一核对后，11 个实现没有一个具备：独立的近重复检测器、写入前的「新增/修正/矛盾/重复」四操作判定、或写入侧的乐观锁。普遍做法是把「更新现有页而非新建重复页」写成提示词纪律（「Update existing pages rather than duplicating info」「Grep index.md first; merge into the existing page」），由模型自行判断。ddsyasas 的更新语义是**整页替换而非 diff**（其 JSON 契约原文为「Full new body for this page (entire replacement, not a diff)」），无 CAS；cortexes 与 personal-wiki 是仅有的两处例外方向——cortexes 用 `source_sha256` 做 plan 身份锁并在 git commit 后校验「唯一变更即预期变更」，personal-wiki 用整页 sha256 作 `expected_revision` 做真 CAS。

对 LDVH 的价值判断：这是本轮的**共同空白确证**。LDVH 35 号 §8.2 的四操作比对（含「矛盾时必须提示替换还是并存，不自动改」）与 03/06 的 CAS 受控写入，在这个模式生态中属于少数派能力而非过度设计。同时给出两条可吸收的具体做法：**(a)** 把「比对时冻结目标指纹、写后回读校验唯一变更即预期变更」落成机械动作（cortexes 的 plan 锁即此项的现成实现形态）；**(b)** 覆盖旧声明时要求同时逐字引用旧表述与新证据（hangandrew 的 ROT_FIX 通道做法），把「修正」从自由改写变为举证式操作。

### cobusgreyling 把「矛盾必须显式登记」做成可 CI 的机械检查

观察：该实现把矛盾做成一等公民：独立的 `wiki/contradictions.md` 账本（表格列 Claim A | Source/Page | Claim B | Source/Page | Status，附 Resolution notes 区）；ingest 协议强制在发现冲突时登记入账；更关键的是 lint 侧有一项机械检查 `contradiction-unfiled`——用正则扫描正文中的矛盾/陈旧语汇（contradict / conflict / disagree / supersede / outdated / stale / deprecated），若命中而该页未被账本引用，即报 warning。检查完全无 LLM 参与，因此可进 CI。示例数据中带一条真实矛盾条目（一方主张「约 100 源无需嵌入」，另一方主张「稀疏交叉链接时 hybrid 更早改善召回」，状态 open 并附处置建议）。

### hangandrew 提供门 0 式分诊与攒熟阈值的完整可运行先例

观察：该实现把最接近 LDVH 门 0 的判据写进 schema 的排除清单：「什么不进去：逐会话日记、时间形日志……瞬态状态（进行中的分支、今天的待办）……任何可从 `git log`、`git blame` 或目标仓库源文件轻易推导的内容」；写入判据是**持久性**——「未来会话在 6 个月后还会因此受益吗？如果对一切都答否，就**不做任何变更地退出**」。采集侧配三重分诊（≥3 条用户消息、≥120 秒时长、排除规则引擎 Python 可配），并有防递归闸门（headless 合成会话直接跳过）。攒熟触发为：队列 ≥5 条，或最老条目 ≥6 小时，另加每日定时保底；光标只在合成成功后推进并删除待处理项（at-least-once，不静默丢弃）。

对 LDVH 的价值判断：这是本轮最有分量的**可行性确证**——LDVH 35 号的门 0 三条（可重新发现、AI 自身断言、单会话临时状态）与攒熟提议，在纯 shell + prompt 环境中已有完整可运行先例，不依赖任何平台特性。可直接吸收的三点：**(a)** 「不做任何变更地退出」应作为空闲维护代理的显式正常出口（LDVH 已写「默认不变更」，此先例给出文案与判据形态）；**(b)** 攒熟的阈值应同时含数量、时长与定时保底三条，避免单一条件导致长期不触发；**(c)** **防递归闸门是必要项**——空闲代理触发的会话不得重新进入采集队列，否则形成自我增殖；LDVH 设计空闲评审代理时有同类风险，而 35 号未登记此防护。

### hangandrew 的高危操作两阶段授权与代价非对称纪律

观察：该实现把高危结构操作（SPLIT / DEDUP / RENAME）拆成两个不同时机的 pass：合成器当场**不允许**执行，只能向 `wiki/syntheses/refactor-intents.md` 写意图标记（要求逐字引用原文、精确到 `## <header>` 边界、附 confidence 分级）；由独立的每日复核 pass 消费，且须全部门槛命中（标记存在 + confidence=high + 每个 header 逐字存在于源页 + 目标 slug 不存在 + 划分干净）才执行；另有硬上限：每轮 ≤5 个动作、≤1 个 SPLIT、≤1 个 DEDUP。门槛不过即丢弃，并明确写下代价非对称纪律：「漏掉一个动作的代价是一周；做错一个动作的代价是一次 git revert 加信任损失。存疑时，丢弃。」改名操作另由独立脚本机械执行（移动文件、改写 slug 与 updated、别名只增不删、全库重写链接），而散文中的提及**只报告不改**，理由是「错误的替换是静默的」。

对 LDVH 的价值判断：这套设计与 LDVH 空闲维护代理的「默认不变更 + 每次至多一条变更提议 + fail-closed」是同构的，且把两处 LDVH 表述得较抽象的地方落成了具体形态：**(a)** 「提议」与「执行」应是两个不同上下文、不同时机、不同证据要求的 pass，而非同一轮的连续动作——这样提议时不必拥有执行权限，执行时不必依赖提议者的判断；**(b)** 变更数量上限应是**分类型**的（总量 + 每类各自上限），不只一个总数字；**(c)** 「存疑即丢弃」应配上代价非对称的明文理由，使丢弃成为正当的默认而非失职。第 (a) 点尤其值得注意：LDVH 的晋升提议与受控创建当前由同一主控在同一会话内先后完成，而先例证明拆成两个 pass 可显著降低误动概率。

溯源：https://github.com/hangandrew/llm-wiki（.system/prompts/wiki-refactor-review.md 门槛与纪律节；.system/scripts/rename-entity.py 文件头注释）

### cortexes 的静默丢失事故链确立记录 fail-open 与变更 fail-closed 的分治

观察：该仓库的 CHANGELOG 是一部可核查的失败模式实录，其中三起直接相关：**(1)** 会话结束过滤器因一次 payload 形状变更崩溃，一次性损坏 21 条会话记录且只留下 100 字节残桩——修复为：捕获 stderr、脱敏后写入 `filter-failures.log`（权限 0600）、原始记录先写 `.partial.$$` 临时文件再原子 rename（注释明言「目标路径永远只放完整记录」）、超时值非法时回退默认而非写出残桩；**(2)** 队列判重用 `grep -rL '<!-- distilled:'` 实现，被一次「元会话」（自己打印该标记的提炼流水线）污染，**静默漏掉 26 条真正未提炼的记录**——修复为位置锚定的专用判定命令，并在文档中写明「为什么 grep 不安全」；**(3)** 会话结束事件对同一会话多次触发（清屏、退出后恢复）导致前缀重复记录堆积并被重复提炼——修复为只清理「严格前缀」且跨仓库前缀对拒绝删除，失败模式明确为「重复留下」而非「内容丢失」。作者把教训总结为一句：自动捕获很容易，真正的系统是防止静默丢失、重复记忆、陈旧状态、误导性置信度与意外过度召回的一切。

对 LDVH 的价值判断：这是本轮对 LDVH **失败语义设计**最有价值的输入。LDVH 当前对写入/维护路径统一采用 fail-closed（正确），但对**记录与观察路径**未区分——按此先例应显式分治：记录/观察路径 fail-open（宁可留下重复也不丢数据，且失败必须留下可见痕迹），变更/提交路径 fail-closed（宁可不动也不写错）。第二条教训对 LDVH 有直接对应风险：**用子串 grep 判定对象状态是不可靠的**，因为处理记忆的流程本身会在文本中引用状态词，而 LDVH 的规范与事实对象正文大量出现状态语汇；机械锚点应做成结构/位置敏感的专用读取，并明文写出「为什么裸 grep 不安全」。第三条的「失败模式必须是重复留下而非内容丢失」可直接作为 LDVH 去重与清理动作的取舍准则。

溯源：https://github.com/XBlueSky/cortexes（hooks/scripts/session-end-record.sh 失败处理与原子写注释；CHANGELOG 前缀回收与判重条目；hooks/scripts/filter-transcript.py 脱敏规则）

### 检索分数语义必须写死在规范层，否则产生假判决与静默漏判

观察：同仓库有两次由分数语义不清引发的事故：**(1)** 图检索流曾以加性 boost 的方式叠加在 RRF 融合分数带上（该分数带只有 0.001–0.016 量级），导致 MRR 从 0.875 崩到 0.49，改为 rank-based 第三流后恢复中性；**(2)** BM25 或图流命中的页面，其向量余弦分报 `0.00`，与「真实零重叠」不可区分，使近重复被误判为全新条目——修复为由存储层统一回填真余弦值。该实现随后在查询技能文档中用整节规定分数语义：「分数是语义重叠带，不是判决」；相关性看返回顺序；**永远不要因为余弦分低而降级 BM25 或图命中**；并把 `0.0` 重新定义为歧义值，逐一列举其四种成因（无密钥、回填失败、真零、四舍五入），禁止仅凭 0.0 推断运行模式。另要求任何检索增强默认关闭，开启前必须先跑评测对比 P@5/R@5/MRR。

对 LDVH 的价值判断：LDVH 本地层用的是 tokenize + Jaccard + 加权评分，虽不上向量，但面临同一类问题——**分数会被用于阈值判断**（35 号的近重复合并阈值为 Jaccard ≥ 0.7），而阈值判断一旦建立在语义不清的分数上就会产生假判决（把近重复判为新增，或把不同条目误合并）。可吸收的三条纪律：**(a)** 在规范层明文写死每个分值的用途——是只用于排序，还是也用于阈值；**(b)** 无法计算分值时输出「歧义」而非 0，并禁止消费方据 0 做判断；**(c)** 非主算法通道命中的候选项必须回填同尺度分数。另：该实现要求「检索增强必须带评测关卡」这一点，为 LDVH 未来的任何检索升级提供了准入形态（尽管 LDVH 当前无检索增强计划）。

溯源：https://github.com/XBlueSky/cortexes（cortex-vec/src/cortex_vec/fusion.py 融合与分数回填；skills/cortex-query/SKILL.md 分数语义节；CHANGELOG 相应事故条目）

### 调研范围内全部实现的核心检索层都不使用向量

观察：逐项核对检索实现：zissa-wiki 无算法检索（靠 index 与链接导航，README 明言「无数据库、无嵌入、无插件」）；obsidian-wiki 无检索（靠 Obsidian 图谱与索引）；ddsyasas 用 SQLite FTS5（删除旧行插新行、`snippet()` 高亮、排名排序，并把向量检索明确列入远期路线）；cobusgreyling 用手写 BM25（k1=1.5、b=0.75，标题加权 3.0、次级标题 1.5）+ 可选外部 qmd 后端；hangandrew 完全无检索（靠索引注入与文件搜索工具）；samur 用关键词计数 + 图邻居扩展 + CJK 二元组滑窗；cortexes 具备完整混合检索（向量 + BM25 + 图三流 RRF + 可选重排）但**四个增强默认全部关闭**，且要求开启前必须评测。生态侧的 personal-wiki 用页级与段级双层 BM25（k1=1.2、b=0.75）加标题/别名/标签加权，CJK 用一元与二元分词；vesna 插件用子串计数。

对 LDVH 的价值判断：这是对 35 号「不上向量、永不上量化」的**强外部印证**——在被调研的全部实现中，只有两个用了向量，且一个把它列为未实现的远期项、另一个把全部向量相关增强默认关闭并要求先评测。更值得注意的是 personal-wiki 的 CJK 一元/二元分词与分层 BM25，与 LDVH 35 号 §8.3 引用的 agent-memory 先例在做法上一致，说明该技术选型在同生态内是收敛共识而非孤立判断。可吸收的具体点：页级与段级双层评分（先定位页、再定位段落）在不引入向量的前提下提升了命中精度，LDVH 本地侧启发式检索目前只有条目级，段级评分是可选增强。

### zissa 的认识论标记是唯一直接设防「AI 生成内容被当事实再消费」的机制

观察：该实现提供一套可选的认识论标记体系，用四个标记区分声明所属的认识论层级：无标记＝可直接归因于某个具名来源并附引用；`[W]`＝wiki 自身跨源综合；`[P]`＝研究者本人的立场（非任何来源所述）；`[?]`＝无法核实的归属、日期或声明。启用后（默认关闭，由配置开关）配套三条规则：对概念/作者/辩论/主题/综合类页面逐条标记；**永不提升声明的层级**——被标记为 `[W]` 或 `[P]` 的声明不得在别处不带标记地重现，仿佛某个来源说过它；用 `[?]` 而非猜测，并把未决问题记入 log。作者给出的理由很直接：在人文领域，「来源说了什么」「wiki 跨源得出的结论」「研究者本人主张什么」是三类不同的声明，页面绝不应模糊它们。

对 LDVH 的价值判断：这是本轮唯一**直接设防再消费污染**的机制。LDVH 的问题域与之同构：LDVH 的记忆条目、反思意见、空闲评审提议都可能是 AI 生成内容，而 35 号 §8.3 的双路召回会把它们重新注入上下文参与后续判断，§8.2 的四操作比对还会以既有条目集合为基准——即 AI 生成内容可以作为后续比对的基准。LDVH 现有的间接缓解是门 0 第 2 条（AI 自身断言不记）、空闲评审「只认真人明确断言」与 `origin` 字段（user/agent 区分），但**没有一条禁止「低置信来源参与比对基准」的资格规则**，也没有要求在承载形态上标记声明层级。可吸收的核心是那条「永不提升声明层级」纪律：AI 综合内容在被写入或引用时必须持续携带其来源等级，不得在流转中退化为「某来源所述」。

溯源：https://github.com/MetamusicX/zissa-wiki（AGENTS.md Epistemic Markers 节与 conventions.toml [markers] 段）

### chobizzy 把 LLM 生成来源标为最低可信度并对枢纽页单独告警

观察：该实现建立来源质量分桶（0.4–1.0），其中 `llm_generated` 取**最低值 0.3**，并以公式 `base_confidence = min(N/3, 1) × 0.5 + avg_quality × 0.5` 计算页面基础置信度（N 为来源数）。另有 provenance 漂移检查：lint 重算页面的 extracted/inferred/ambiguous 比例块并与文件内声明比对，超阈值即告警——ambiguous 占比 >15% 判为思辨过度；无来源的 inferred 占比 >40% 判为无源综合；**枢纽页（高入链）的 inferred 占比 >20% 则重点报告**，理由是高入链页面的错误传播面最大。其宪法式规则还包括「绝不把综合声明呈现为提取所得」（推断标 `^[inferred]`、有争议标 `^[ambiguous]`，未标记即等价于对真实来源的转述）。

对 LDVH 的价值判断：这里有两项可直接吸收的判据。**(a) 把 LLM 生成内容显式标为最低可信来源**，是 LDVH 门 0 第 2 条与「只认真人明确断言」的量化形态——LDVH 目前用布尔式的 origin 字段区分，而先例表明可进一步影响由来源派生的置信度而非仅作标签。**(b) 枢纽页的推断占比单独告警**对 LDVH 尤其有价值：LDVH 的 git 层对象通过 relations 形成引用网络，被引用越多的对象（如被多个 ADR 引用的 Research）错误传播面越大；同理，本地层条目中被反复召回的热集条目亦然。这条判据给出了「效用审计应优先审计谁」的一个可机械计算的答案——**先审计高入链/高召回的对象**，而不是平均抽样。

### 三家独立收敛到「维护提议不自动执行」，反向佐证空闲代理保守纪律

观察：三家实现在互不参照的情况下给出同一原则的不同表述。zissa 的维护工作流结尾明确：「**不要自动修复**——呈现发现，让研究者决定」。obsidian-wiki 把审批写进流程：「向用户呈现发现。询问要应用哪些修复。执行已批准的修复。记录操作。」cobusgreyling 的 lint 只报告不修复（其扩展命令也声明「不会修复或重建」）。personal-wiki 的 lint 同样「只报告不修复」。samur 的设计约束甚至写下硬规则：图层的边不得由断链自动创建页面，只能报告，理由是「LLM 摄取会产生幻觉性的 wikilink，自动创建会放大噪声」——而同一仓库的自动化脚本却违背了这一精神，其夜间无人值守流程会为被多页提及的缺失实体自动生成定义页并写盘，是同一原则的反面教材。

对 LDVH 的价值判断：多家独立实现收敛到同一原则，是对 LDVH 空闲维护代理「默认不变更、每次至多一条变更提议、fail-closed」的**强反向佐证**——该保守纪律不是 LDVH 的过度设计，而是该领域在踩过坑之后的共识。同时先例给出两条补强：**(a)** 「不自动修复」需要与「必须报告」成对出现，否则保守会退化为无信息；**(b)** 同一系统内若存在「只报告」与「自动执行」两条并存路径（samur 的情形），必须机械保证自动路径不能绕过约束——LDVH 的对应物是空闲任务产出必须 fail-closed 入队而非直接落盘。

### personal-wiki 的延迟审批闭环补上「批准晚于回合」这一未设计场景

观察：同家族的 `@dsh-enhanced/personal-wiki` 只提交提案绝不直写：模型的写工具只创建完整页面的创建/更新提案，更新必须携带 `page_id` 与 `expected_revision`；模型没有直接写页的方法，也不能自行指定审批主体、工作区、审批时限或页面权威等级（这些由可信配置决定）。其审批可能发生在原回合结束之后（例如几分钟后在某即时通讯卡片上点击），因此插件周期性调用结算流程：从审批账本读取提案的**终态**，只有账本给出终态才写盘；pending 仍是 pending，**不推断批准**。配套五条边界：幂等（重复结算不会重复写页或重复结算）、公平扫描（游标与每轮高水位持久化，重启不回第一页，老 pending 不饿死新提案）、不复活旧意图（策略尚未提交且期限已过时，在同一事务中把幂等键永久墓碑化，防止多进程竞争生成孤儿审批）、冲突不丢决定（修订号已变或结算字段不匹配时，提案持久化为 `conflicted` 终态，绝不覆盖文件或反复重试）。此外还有提案有效期（默认 15 分钟）与写后回读断言（写后重建并断言页面修订号等于目标修订号）。

对 LDVH 的价值判断：这补上了 LDVH 一个**具体且必然会遇到的缺口**。35 号 §8.5 规定晋升拍板走双入口（Web 确认卡为主面 + 会话内问询通道），但未设计「Human 在回合结束之后才点确认」这一情形——Web 确认卡的本质就是异步的，而 LDVH 当前的交还结构与一次性的会话流不覆盖跨回合结算。可吸收四项：**(a)** 结算只读终态、绝不推断批准；**(b)** 幂等键墓碑化防止孤儿审批；**(c)** 提案有效期与 `conflicted` 终态语义（冲突时保留决定痕迹而非重试覆盖）；**(d)** 结算游标持久化以保证公平扫描。另有一处需要 LDVH 对抗审核区分的张力：该实现保留了追加式的审批结算账本，而 35 号 §20 红线 11 声明「不为记忆活动建独立审计账本」——该账本审计的是**闸门结算**而非记忆活动，两类账本的边界值得在审核时明确。

溯源：https://www.npmjs.com/package/@dsh-enhanced/personal-wiki（README「工具和写入语义」「延迟审批的提交闭环」「配置上限」各节）

### DSH 内 Karpathy 直译插件是 LDVH 红线的反面实现样本

观察：`@vesna-strivozha-2026/dsh-llm-wiki` 把该模式直接实现为 DSH 插件的宿主引擎与面板，提供工作区创建、上传、自动摄取、知识图谱、lint 与查询工具。逐行核对代码后确认：摄取由插件驱动 LLM 生成页面后**直接写盘**，无提案、无审批、无修订号、无写后回读；wiki 页面无溯源 frontmatter、无内容哈希；去重仅按**文件名**记账，同名文件的新内容不会被重新摄取；检索为子串计数评分并把页面原文拼接后返回，不暴露分数、无去重；lint 只检查孤儿页与孤立页，**链接目标不存在时静默忽略**；摄取失败只计入错误计数后继续；文件读取失败被吞掉返回空串，导致不可读页面在检索中静默当作不存在。此外其 README 声称具备「标记矛盾」能力，**代码中不存在任何矛盾检测**。其面板与工作区选择、图谱现算不落库、查询预算截断（索引与命中页各有字节上限）是少数可参考的同向设计。

对 LDVH 的价值判断：这是 35 号 §20 红线 4（不上无人工闸门的自动提取流水线）与门 0 纪律的**具体反面样本**——它把「LLM 产出直接进入消费闭环、零溯源、失败静默继续」三者同时实现，正好演示了该红线要防的东西。它的存在也解释了为什么 LDVH 需要红线：该模式在生态中的自然落地形态就是自动流水线。另有一处方法论价值：README 声称与代码实际不一致，说明**插件取证必须以代码为准**，这与 LDVH「机械结果与语义判断互不替代」的纪律同向。

溯源：https://www.npmjs.com/package/@vesna-strivozha-2026/dsh-llm-wiki（包内 lib/index.js 摄取与检索实现、README 能力声明）

### 成熟生态在检索侧过度投资、在写入治理侧留白

观察：把生态扫描结果按能力分布看：检索侧的投资极重——多个成熟项目投入向量库、混合检索、重排、知识图谱（有的用 SQLite FTS5 加向量扩展与本地重排模型，有的用云向量库，有的用时序知识图谱）。写入治理侧则接近空白：被点名的成熟项目多数写入自由、无审批、无修订号、无矛盾检测；唯一同时做到「增量编译 + 审计 + 溯源 + 审批闸门」的公开实现是一个社区级项目（1348 stars），其治理能力包括：审批绑定到精确的计划哈希、精确资源允许清单、声明的读写效果、稳定幂等键、验证回执、lint 出口码闸门（可按 critical 或 warning 级别阻断）、检查点导出采用先试运行后确认并做只读验证、研究选择带版本与哈希溯源。此外企业侧只有商业产品把验证权收回人工（指定所有者审批出「已验证」徽章、请求验证触发审批流、陈旧与过期管理）。

对 LDVH 的价值判断：能力分布给出了 LDVH 的定位坐标——LDVH 的重心（受控写入、Human Gate、类型化对象、机械校验）恰在生态的空白侧，而不是竞争激烈的检索侧。这是**顺向信号**：它说明 LDVH 不必在检索能力上追赶（且 35 号已明确不上向量），但必须在治理能力上做出生态尚未做的东西，否则其相对价值不成立。可吸收的具体机制有四项：**(a)** 审批对象绑定到精确的内容指纹（比「人工拍板」更可复核，且与 LDVH 的 CAS 指纹天然契合）；**(b)** lint 出口码分级阻断（对 LDVH 的 Git Gate 预检有直接参照）；**(c)** 幂等键与验证回执（已在 F23 登记）；**(d)** 人工验证状态的可见化与过期追踪（对应 LDVH 的 locked 与退休流程在管理面上的呈现）。

溯源：https://github.com/nvk/llm-wiki（README Changelog 各版本条目：治理性远程写入、检查点导出、lint 出口闸门）；https://docs.glean.com/user-guide/knowledge/verification/how-verification-works（人工验证与过期管理）

### 向量与图谱的记忆增益数字均出自利益相关方自测，且已有第三方反证

观察：所有可查到的增益数字都来自利益相关方。本地检索工具的基准（BM25 约 0.50、向量约 0.70、混合约 1.00）出自作者自选样本的自测框架，无第三方复核；主流记忆产品的基准成绩出自其自身 README；时序图谱论文的超越结论出自厂商署名论文。同时存在一份第三方系统评测，报告基于知识图谱的检索方案在问答任务上**普遍逊于预期**，原因是实体与关系抽取不全导致检索缺口。另一方面，学术界的增量方案（面向静态语料的改进工作）本身即是对既有图谱流水线增量能力不足的旁证。

对 LDVH 的价值判断：这印证了 35 号「图记忆实测增益不支持其标配化」与「不上向量」的取向，且论证强度高于规范中现有的写法（规范引用的是单一实测数字，而本轮取证显示**全部正方向数字都出自利益相关方，并已有第三方反证**）。须同时保持诚实边界：这些反证针对的是通用问答场景，不能直接外推到 LDVH 的类型化事实源场景——因此本报告不主张「向量与图谱对 LDVH 无用」，只主张「其增益未被独立验证，且现有证据不支持把任何一路设为默认」。这与 LDVH 把此类升级列为远期非承诺候选的写法一致。

### 生态取证纪律：热度与 scope 名不可作为影响力与官方性的证据

观察：核对过程中发现两类误读风险。**(1)** 某一热门 LLM Wiki 实现仓库的 stars 数字（数千级）继承自 2023 年创建的旧仓库——其历史提交包含与本项目无关的鉴权代码，仓库内容本身仅有 33 个文件、单次提交，因此该热度不能反映该实现的实际影响力。**(2)** 社区插件目录中存在借用官方包名前缀（`@deepseek-ai/...`）的包，其仓库字段实际指向个人仓库，并非官方发布。此外注意到部分高热度项目正在转向托管付费服务，热度与开源可用性不是同一回事。

对 LDVH 的价值判断：这是对本轮调研自身的取证纪律修正，也是对 LDVH 后续任何生态调研的**方法条款**：热度数字必须核对仓库创建时间与提交历史，包名前缀不构成官方性证据，README 宣称必须以代码实现核对（本轮已检出至少一处能力虚标）。该纪律与 LDVH「机械结果与语义判断互不替代」「不以对象数量、工具成功或测试通过声称价值成立」的防自欺取向一致，可直接作为 30 号调研系统来源甄别纪律的补充输入。

## 未证实与缺口

**未证实（uncertain）**

1. **LDVH 记忆与反思系统当前处于「规范草案态 + 插件零实现态」**——specs/35 未完成独立对抗审核与成立程序、本仓 `plugin/` 下无任何记忆实现。属仓库内部状态，无外部可回指来源，作为分析背景而非已证实条目。
2. **LDVH 规范间存在可指认的条款张力与漂移**——调研规范要求证据「逐字摘录入库」且引用一个 `confidence` 字段，而 Research 类型规范明确「摘录原文不复制进对象」且其字段契约中不含 `confidence`。该比对基于本仓规范原文，无外部 URL 可回指，须经规范层面的独立复核与修正程序。
3. **LDVH 记忆系统存在可指认的设计缺口**——本地层无主题聚合承载、矛盾检测仅写入时一次无周期巡检、晋升只有逐条通道无批量主题级、召回质量无度量与反馈回路。属语义审核范围的推断，是否构成真实缺口及是否补设相应机制须经独立对抗审核与 Human 裁决。
4. **两份既有调研对象被列为设计依据但正文未消费**——该落差需逐行核对草案声明与正文才能认定，属本仓文本内部核对，是否为真缺口需规范起草者与复核者判断。
5. **公众号文章所述的定时任务与自动化配置的可运行性**——相关配置以图片形式呈现，文本层不可核验，故不主张其可用性或具体行为。

**缺口（gaps）**

1. **LLM Wiki 模式在 LDVH 自身规模下的成本与失败率未实测**（medium）——本报告关于规模与成本的所有论断均引自外部作者自述而非本仓实测；不阻塞方向性结论（分工边界与可吸收机制清单均从机制层面得出），仅阻塞「落地成本与 V1 范围」类判断，故本报告全程不对实际开销与失败率下任何断言。
2. **DSH 生态记忆/知识库插件的真实运行时可用性未实测**（medium）——只做 npm 元数据检索与 6 个重点包的代码精读，未逐个安装运行；影响「是否应复用某个现成插件」类选型结论，不影响机制层对照。
3. **35 号规范附录 A 六项开放问题的对抗审核结论未取证**（medium）——该审核尚未发生；决定建议 2、3、6 的最终承载形态，在审核发生前上述建议保持待裁状态。

## 建议

**建议 1：以 ADR 承接「知识编译子层是否进入记忆系统 V1 范围」的职责裁决。**
目标对象类型：ADR。预期目标：明确「外部原始资料 → 结构化知识」的编译能力在当前规范体系中由谁承接，消除三不管地带。本报告的证据支持两种可辩护处置，须由 Human 裁决其一：**(a) 维持现状并正面宣告边界**——记忆与反思系统不承接知识编译，跨行动的资料来源继续由 Research 类型与普通文件承载（推荐，依据是 F4/F6/F27：该模式的自认局限与生态证据均不支持在企业级/项目级场景引入第二记忆面，且 LDVH 已有更严格的承载）；**(b) 若确需引入**，则必须同时设计维护者机制（F3 的代价警告）与再消费污染防护（F19/F20），不得只引入结构不引入维护。验收条件：ADR 的「适用范围」段落明确写出该能力归属与排除理由，且与 24 号 Research 类型、30 号 §13 结论承载、35 号 §15.1 交集规则三者无冲突。创建判断：本建议即刻可创建——它裁决的是一个已被识别的边界模糊，且不依赖任何未完成的实测。

**建议 2：以 ADR 承接「晋升幂等键的服务端计算」。**
目标对象类型：ADR。预期目标：用机械方式消除三路晋升的竞争条件，替代当前的近重复合并兜底。具体机制取自先例——由代码根据「方向 + 源对象标识与版本/内容哈希 + 目标 + 规范化内容」派生稳定幂等键，同内容多次触发收敛为同一提案。验收条件：针对「即时检测与攒熟提议对同一内容同时触发」的场景，能用键相等断言二者为同一提案（而非依赖合并）；ADR 须说明该键与既有 CAS 指纹的关系（是同一指纹的派生还是独立标识）。创建判断：35 号附录 A.3 已把该竞争条件登记为对抗审查项，本建议为其提供现成解，可在 35 号审核时一并裁决——若 35 号的对抗审核先发生，则本 ADR 转为承接该审核结论。

**建议 3：以 ADR 承接「异步拍板的结算语义」。**
目标对象类型：ADR。预期目标：补齐「Human 在回合结束之后点确认」这一 35 号未设计的场景，使 Web 确认卡真能作为主面工作。机制取自先例四项：结算只读终态绝不推断批准、幂等键墓碑化防孤儿审批、提案有效期、冲突时落 `conflicted` 终态而非重试覆盖。验收条件：ADR 须逐条回答「Human 永远不回应会怎样」「同一提案被撤下后重提如何识别」「结算与受控创建的写入顺序」三个问题；并须明确区分「记忆活动账本」（红线 11 禁止）与「闸门结算账本」（先例证明其必要性）的边界。创建判断：该项阻塞 35 号 §8.5 双入口的完整性，应在 35 号进入成立程序前裁决。

**建议 4：以 WorkCase 承接「写入闸门机制的实现加固」。**
目标对象类型：WorkCase。预期目标：把 CAS、写后回读、`conflicted` 终态、提案有效期、原子写（临时文件 + fsync + 原子改名）落成可测试实现。验收条件：覆盖三类对抗性测试——(i) 写前目标已变更 → 零写入且落冲突终态；(ii) 写后回读不一致 → 拒绝声明成功；(iii) 并发两次同键提案 → 只产生一个页面。创建判断：当 LDVH 记忆系统进入实现阶段（35 号成立后）时创建；当前 35 号为草案，提前实现会造成规范与实现的顺序倒置。**明确不对象化当下**：现在创建会与 35 号的成立程序竞争。

**建议 5：以 WorkCase 承接「机械锚点补强」的一组校验。**
目标对象类型：WorkCase。预期目标：在既有 Git Gate 与本地层校验中增加三类廉价高信噪比的机械锚点：**(a)** 引文逐字回验（在存在本地可读来源副本时，校验对象中的引文与来源原文一致，区分改写/未标记省略/查无原文三态）；**(b)** 矛盾未入账检测（对象正文出现矛盾或陈旧语汇但未被登记为待处置状态即告警）；**(c)** 被修改对象的 `change_log`/`updated` 必须前进（脏文件时间戳漂移检测）。验收条件：三项各有一个阳性样本与一个阴性样本转绿，且阳性样本须包含误报案例并如实记录（声明为警告级、不阻断）。创建判断：该项不依赖 35 号成立（覆盖范围含既有 git 层对象），可独立创建；但若 35 号的对抗审核对「本地层是否建矛盾账本」另有结论，则须等该结论后再动 (b) 项。

**建议 6：以 Spark 承接 35 号设计缺口的议题化。**
目标对象类型：Spark。预期目标：把本报告识别但未获证的四项候选缺口（主题聚合承载、周期性矛盾巡检、批量/主题级晋升、召回质量度量与反馈回路）转为待裁决议题，交由 35 号的对抗审核裁量。验收条件：四条各自写明「当前规范原文如何规定」「候选缺口是什么」「外部先例如何做」三段，确保审核者可独立复读；不得写成已认定的缺陷。创建判断：**推荐暂缓创建**——35 号本身处于草案态且附录 A 已登记六项开放问题为待裁范围，此时新增议题会与既有审核面重叠，宜先完成 35 号既定审核；仅当审核结论认为需要扩展议题面时再创建。该判断提交 Human 复核。

**建议 7：不采用任何现有的 DSH 生态记忆或 wiki 插件。**
目标对象类型：无需对象化（属既有规范的适用判断，不是新决定）。判断依据：35 号 §16.1 独占记忆职责承诺要求不引入第二记忆系统，§18 第 4 项把「引入并存的其他记忆系统」列为架构级 Human Gate 事项；被调研的 wiki 类插件中，治理完整者自成记忆家族（安装即构成并存系统），Karpathy 直译插件则直接违反 §20 红线 4（无人工闸门的自动提取流水线）与门 0。后续监测条件：若某插件在机制上收敛到「文件即真值 + 零依赖 + 提案制 + CAS」且不与 LDVH 的对象类型竞争，可重新评估；监测信号为该类插件的写入闸门实现（是否提案制、是否有 CAS 与回读）。
