## 研究问题

DSH 从 0.1.7-rc.2 到 0.2.0-rc.1 有哪些变更，其中哪些影响 dsh-ldvh 的宿主对接与 LDVH 消费面？

本轮调研的对象是 DSH 内核仓 `deepseek-ai/deepseek-harness` 从 tag `dsh-v0.1.7-rc.2`（`477b4f4205`，2026-09-24）到 tag `dsh-v0.2.0-rc.1`（`4878cdabd8`，2026-09-28）的发布差量。选择这一区间有明确背景：`0.2.0-rc.1` 是 DSH 进入 `0.2` 主版本线后的首个候选版本，而 dsh-ldvh 的既有兼容基线（peer 声明与上一轮调研）都锚在 `0.1.7-rc.x`。按 semver 的默认语义，`0.x` 线的主版本进位是**允许破坏性变更**的边界，因此不能沿用上一区间「契约只增不改」的惯性判断，必须重新机械取证。

本轮调研支撑的项目判断是三条：dsh-ldvh 是否需要为 `0.2.0-rc.1` 做契约适配；其 peer、dependencies 与 devDependencies 声明在宿主**实际判定口径**下是否失配；同级源码仓升级到该版本后是否存在未被察觉的落差。

## 输入与边界

来源按四分法分工，全部为长期可复核的 HTTP(S) 资料，配合本地只读差分：

- **DSH 内核源码仓**（`https://github.com/deepseek-ai/deepseek-harness`）承担全部内核侧发现：两 tag 的只读差分，覆盖七张生成式目录、bundle 组合补丁、持久化目录、包集合、peer 依赖与兼容门禁源码。观察时点固定为两个 tag 的发布提交，不涉及 `master` 后续提交。
- **官方发布说明**（`https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.0-rc.1`）承担产品面变更的权威骨架，用于与机械差分交叉验证，而非取代差分。
- **npm registry 元数据**（`https://registry.npmjs.org/@deepseek-ai/dsh`）承担版本通道事实：`latest` 仍为 `0.1.7-rc.2`，`0.2.0-rc.1` 走 `next` 通道。
- **受辖项目仓**（`https://github.com/dingminhua/dsh-ldvh`）承担消费面核对：`plugin/package.json` 的 peer/dependencies/devDependencies 声明、`plugin/lib/host-seams.js` 声明的宿主缝合消费清单、各 fact writer 的实际调用点，以及本机运行宿主的进程与端口实证。

方法为静态差分与集合级机械比对：对**生成式目录**（服务/事件/类型/槽位/工具/配置/持久化）提取条目集合与签名字段做逐条对照；对包集合提取 `package.json` 的 `name` 字段求差集；对关键源文件取 blob hash 判等；对兼容门禁以宿主**自带**的 semver 7.8.5 实跑求值，不采信手写语义解读；对本机宿主的指认以进程（`pgrep`）、端口持有者（`lsof`）、运行产物内核版本（`CFBundleShortVersionString` 与 asar 内包版本分布）和 profile 安装形态四项实证支撑，不以目录名或安装历史推定。证据分三级并在发现单元中标注：机械（生成物集合/哈希比对，可逐字复现）、源码（git 差分与官方决策记录原文）、运行时（本机运行宿主的实读观察）。

不覆盖范围与来源限制：本轮未在 `0.2.0-rc.1` 上做完备的端到端 UI 验收（六项中仅前两项取得实证），因此「dsh-ldvh 在 0.2.0-rc.1 上全面可用」类结论不在本轮证据内；未逐字审阅全部 1070 个变更文件，覆盖依赖集合级机械比对与改动量前列文件的定向阅读；官方决策记录与实际装配可能不一致，凡判定「默认是否可用」一律以 bundle patch 的行状态为准，不采信决策记录的叙述。

## 关键发现

### F1 宿主公开契约面为本区间唯一自变量：服务 89→91、事件 81→81 零变化、模型可见工具零变化

对宿主公开契约的三张生成式目录做集合级机械比对，结果高度收敛：`SERVICE_API` 由 89 项增至 91 项，**新增 `otel` 与 `productAnalytics` 两项，零删除**；`EVENT_API` 保持 81 项，**增删改均为零**（该数组体逐字节相同）；`TYPE_API` 由 926 项增至 935 项（+10 / −1），增量为 `EventLogOptions`、`OTelEventRecord`、`ProductEvent`、`SessionLogRecord` 等遥测与产品分析类型，唯一删除项 `ProductTelemetryScalar` 为同族改名（`ProductTelemetryRecord` 改为其别名）。方法级另有一处增量：`deepseekAccount` 服务新增 `getDeviceIdentity()` 方法。模型可见工具面 `docs/tool-catalog.md` 在两 tag 之间 **blob 全等**（`d2c16e30…`，96902 字节，`cmp` 判定 IDENTICAL）。

对 LDVH 而言这意味着本区间的「宿主公开缝」整体仍是安全区：一个主版本候选版本在服务、事件、工具三个最关键的公开面上只做了加法，且加法全部落在 LDVH 未接入的遥测与产品分析域。风险因此不在这三张目录上，而必须转向 LDVH 实际消费的具体接缝与声明范围（见 F2、F9）。

溯源：https://github.com/deepseek-ai/deepseek-harness（tag dsh-v0.1.7-rc.2 的 477b4f4205 与 dsh-v0.2.0-rc.1 的 4878cdabd8：packages/extensions/tool-cordis/src/api-catalog.ts 的 SERVICE_API 段 89 对 91 项、EVENT_API 段 81 对 81 项且数组体逐字节相同、TYPE_API 段 926 对 935 项并已列全增删名单；两 tag 的 docs/tool-catalog.md 同为 blob d2c16e300660d2ea11cff02eb740974d3ced6bfd）

### F2 dsh-ldvh 消费的六条宿主服务接缝在 91 个服务中无一被改动

按 `plugin/lib/host-seams.js` 声明的消费清单（`ctx.tools.register`、`ctx.tools.guard`、`ctx.invariants.register`、`fs/observed`、`ctx.userQuestions.ask`），加上 `plugin/lib/index.js` 的 `inject` 声明（`["tools","systemPrompt"]`、`["webServer"]`、`["connection"]`），dsh-ldvh 消费的是**主机侧 11 个宿主服务**：`agents`、`commands`、`dshHomePath`、`fs`、`invariants`、`sessionPersistence`、`tools`、`userQuestions`、`systemPrompt`、`webServer`、`connection`（其中 8 个经 `ctx.get` 动态取、3 个经 inject 注入；另有 `remote.directoryPicker` 属客户端面不计入）。逐条与 91 个服务的完整变更集对照，**11 个全部落在「未改动」集合**：本区间唯一发生签名的服务是 `deepseekAccount`（新增 `getDeviceIdentity()` 方法），既不在 LDVH 的 inject 声明中，也不在其任何调用点；`dshHomePath` 经 `ctx.provide` 提供，其所在文件两版 blob 全等。

这是本轮最有价值的单条结论：它把「是否需要适配」从一个印象问题变成可判定问题——在 91 个服务中，需要改动的恰好是 LDVH 不消费的那一个。注意这不构成「宿主对 LDVH 的防护」：按 specs/08 §6，缝存在不等于已消费，缝未变也不等于 LDVH 行为正确；本发现只支持「无需为签名变更做适配」，不支持「升级后行为已验证」。

**未证实 3：全部 1070 个变更文件未逐字审阅。** 覆盖策略是集合级机械比对（七张生成式目录、包集合、peer 声明、关键文件哈希）加改动量前列文件的定向阅读。原因：区间体量与取证预算限制。阻塞范围：个别未进入集合比对视野的源码行为变化可能未被列出，残余风险主要落在遥测、产品分析与桌面壳层——这三处均不在 LDVH 消费面内。

**未证实 4：本区间被修改（非新增）的 11 篇既有决策记录的修订前后差异未逐篇阅读。** 已确认这些记录被本区间修订，但未取其逐条 diff。原因：决策记录是意图说明而非装配权威，本轮把预算优先给了可机械复现的生成物比对。阻塞范围：可能遗漏「某既有决策被反转」的官方叙述；但由于默认可用性一律以 patch 行状态判定，该遗漏不改变 F7 的结论。

**未证实 5：本对象已两次自我更正（F9 结论方向、F10 宿主指认），两次更正均未经第二个独立会话复核。** F9 的更正依据是独立复核者的 semver 实跑；F10 的更正由独立审核者发现、主控以进程与端口实证复核。按 specs/24 §17.3 的纪律，同一原因再次触发的更正不得自行恢复，须进入 Human Gate。

**缺口 1（medium）：真实 UI 验收其余四项未执行。** 设置卡片呈现、LVH 会话视图、停用与重启、卸载清理需在下一步补做，以完成 specs/08 §8 的支持声明前提。

**缺口 2（medium）：官方发布说明未覆盖 API 契约细节。** 该说明面向用户措辞，四节共约 3.7KB，不含方法签名级变更；本报告的契约结论全部来自源码差分，发布说明仅用于交叉验证产品面叙述。

**缺口 3（low）：仓库根目录仍无 CHANGELOG。** 与上一轮一致，变更语义须由 Release 说明与决策记录反推，缺失可直接对照的逐版本条目。

**缺口 4（low）：本区间删除的 14 个文件中，除 `apps/cli/tests/profiles/web/tests/fixtures/schedule.patch.yml`（已确认与 Schedule 转为可选包同步）之外的 13 个删除文件，其各自的替代关系未逐条核对。**

## 建议

1. **把「上游发布 0.2.0 正式版将触发门禁拒收」的前瞻风险按 Human 决定处置——本项已执行。** 目标对象类型：WorkCase 或规范修订。预期目标：在 `>=0.1.7-rc.1 <0.2.0` 这一上界因上游发正式版而失效之前完成推进。验收条件：声明范围覆盖 0.2.x 且有据可查。执行结果：经 Human 决定（2026-09-29）上界推进为 `<0.3.0`、devDependencies 升至 `0.2.0-rc.1`，经受控提交 `2ee90ce`（声明与 lock）、`c303c38`（Norm 基线）、`491e59d`（受保护文档）落盘。

2. **补齐真实 UI 验收其余四项——本次调研已具备执行条件。** 目标对象类型：WorkCase。预期目标：把 F10 的「两项路由实证」扩展为「六项全数通过」，使支持声明的前提成立。验收条件：设置卡片、LVH 会话视图、停用与重启、卸载清理四项在 `0.2.0-rc.1` 宿主上逐项实操并记录。创建/更新判断：本项是当前唯一阻塞「已验证支持」声明的缺口，建议优先承接。

3. **把本轮的判定口径固化为后续同类调研的固定纪律：兼容性结论必须以宿主实际调用的库与选项实跑，不得据 semver 字面语义推断；宿主指认必须以进程、端口、运行产物内核版本与安装形态四项实证，不得据目录名或安装历史推定。** 目标对象类型：规范（specs 中的调研方法条款）或 Pitfall。预期目标：不再重复「据默认语义断言失配」与「按目录名指认宿主」两类误判。验收条件：后续同类调研在给出兼容性判定与宿主指认时附实跑命令与实证清单。创建/更新判断：本对象 F9 与 F10 各提供一例直接证据，且后者已写入 `local-dev-workflow` 禁止项 7；此处不再另立对象。

4. **将 `uiWorkspace.forkSession` 的返回类型变更登记为客户端面的兼容性注意项。** 目标对象类型：Pitfall。预期目标：让后续任何引入客户端 fork 能力的判断（不限于 LDVH）先核对返回类型。验收条件：该变更被记录为可检索的失败机制条目，含签名前后对照。创建/更新判断：dsh-ldvh 当前不击中，故它是**预防性**条目而非事故记录；若判断为「无需对象化」，则后续监测条件为「任何 LVH 消费 `sessions.fork` 或 `uiWorkspace.forkSession` 的新增提案」。

5. **把两个宿主产物并存的部署事实登记为观察项。** 目标对象类型：Pitfall 或扩展既有部署约束条目。预期目标：避免后续会话把「装过哪个 app」误读为「此刻哪个在承载插件」。验收条件：该事实（`DeepSeek Harness.app` 运行中、`DSH NEXT.app` 未运行）被记录为可复核的观察。创建/更新判断：本条已写入 `local-dev-workflow` 禁止项 7 与验证表「红线 7（宿主指认）」，可无损承载，不再另立对象。
