## 研究问题

DSH 从 0.1.7-rc.2 到 0.2.0-rc.1 有哪些变更，其中哪些影响 dsh-ldvh 的宿主对接与 LDVH 消费面？

本轮调研的对象是 DSH 内核仓 `deepseek-ai/deepseek-harness` 从 tag `dsh-v0.1.7-rc.2`（`477b4f4205`，2026-09-24）到 tag `dsh-v0.2.0-rc.1`（`4878cdabd8`，2026-09-28）的发布差量。选择这一区间有明确背景：`0.2.0-rc.1` 是 DSH 进入 `0.2` 主版本线后的首个候选版本，而 dsh-ldvh 的既有兼容基线（peer 声明与上一轮调研）都锚在 `0.1.7-rc.x`。按 semver 的默认语义，`0.x` 线的主版本进位是**允许破坏性变更**的边界，因此不能沿用上一区间「契约只增不改」的惯性判断，必须重新机械取证。

本轮调研支撑的项目判断是三条：dsh-ldvh 是否需要为 `0.2.0-rc.1` 做契约适配；其 peer、dependencies 与 devDependencies 声明在宿主**实际判定口径**下是否失配；同级源码仓升级到该版本后是否存在未被察觉的落差。

## 输入与边界

来源按四分法分工，全部为长期可复核的 HTTP(S) 资料，配合本地只读差分：

- **DSH 内核源码仓**（`https://github.com/deepseek-ai/deepseek-harness`）承担全部内核侧发现：两 tag 的只读差分，覆盖七张生成式目录、bundle 组合补丁、持久化目录、包集合、peer 依赖与兼容门禁源码。观察时点固定为两个 tag 的发布提交，不涉及 `master` 后续提交。
- **官方发布说明**（`https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.0-rc.1`）承担产品面变更的权威骨架，用于与机械差分交叉验证，而非取代差分。
- **npm registry 元数据**（`https://registry.npmjs.org/@deepseek-ai/dsh`）承担版本通道事实：`latest` 仍为 `0.1.7-rc.2`，`0.2.0-rc.1` 走 `next` 通道。
- **受辖项目仓**（`https://github.com/dingminhua/dsh-ldvh`）承担消费面核对：`plugin/package.json` 的 peer/dependencies/devDependencies 声明、`plugin/lib/host-seams.js` 声明的宿主缝合消费清单、各 fact writer 的实际调用点。

方法为静态差分与集合级机械比对：对**生成式目录**（服务/事件/类型/槽位/工具/配置/持久化）提取条目集合与签名字段做逐条对照；对包集合提取 `package.json` 的 `name` 字段求差集；对关键源文件取 blob hash 判等；对兼容门禁则以宿主**自带**的 semver 7.8.5 实跑求值，不采信手写语义解读。证据分三级并在发现单元中标注：机械（生成物集合/哈希比对，可逐字复现）、源码（git 差分与官方决策记录原文）、运行时（本机安装产物实读）。

不覆盖范围与来源限制：本轮未在 `0.2.0-rc.1` 上做端到端启动复现，因此「dsh-ldvh 在 0.2.0-rc.1 运行时可正常挂载」类结论不在本轮证据内；未逐字审阅全部 1070 个变更文件，覆盖依赖集合级机械比对与改动量前列文件的定向阅读；官方决策记录与实际装配可能不一致，凡判定「默认是否可用」一律以 bundle patch 的行状态为准，不采信决策记录的叙述。

## 关键发现

### F1 宿主公开契约面为本区间唯一自变量：服务 89→91、事件 81→81 零变化、模型可见工具零变化

对宿主公开契约的三张生成式目录做集合级机械比对，结果高度收敛：`SERVICE_API` 由 89 项增至 91 项，**新增 `otel` 与 `productAnalytics` 两项，零删除**；`EVENT_API` 保持 81 项，**增删改均为零**（该数组体逐字节相同）；`TYPE_API` 由 926 项增至 935 项（+10 / −1），增量为 `EventLogOptions`、`OTelEventRecord`、`ProductEvent`、`SessionLogRecord` 等遥测与产品分析类型，唯一删除项 `ProductTelemetryScalar` 为同族改名（`ProductTelemetryRecord` 改为其别名）。方法级另有一处增量：`deepseekAccount` 服务新增 `getDeviceIdentity()` 方法。模型可见工具面 `docs/tool-catalog.md` 在两 tag 之间 **blob 全等**（`d2c16e30…`，96902 字节，`cmp` 判定 IDENTICAL）。

对 LDVH 而言这意味着本区间的「宿主公开缝」整体仍是安全区：一个主版本候选版本在服务、事件、工具三个最关键的公开面上只做了加法，且加法全部落在 LDVH 未接入的遥测与产品分析域。风险因此不在这三张目录上，而必须转向 LDVH 实际消费的具体接缝与声明范围（见 F2、F9）。

溯源：https://github.com/deepseek-ai/deepseek-harness（tag dsh-v0.1.7-rc.2 的 477b4f4205 与 dsh-v0.2.0-rc.1 的 4878cdabd8：packages/extensions/tool-cordis/src/api-catalog.ts 的 SERVICE_API 段 89 对 91 项、EVENT_API 段 81 对 81 项且数组体逐字节相同、TYPE_API 段 926 对 935 项并已列全增删名单；两 tag 的 docs/tool-catalog.md 同为 blob d2c16e300660d2ea11cff02eb740974d3ced6bfd）

### F2 dsh-ldvh 消费的六条宿主服务接缝在 91 个服务中无一被改动

按 `plugin/lib/host-seams.js` 声明的消费清单（`ctx.tools.register`、`ctx.tools.guard`、`ctx.invariants.register`、`fs/observed`、`ctx.userQuestions.ask`），加上 `plugin/lib/index.js` 的 `inject` 声明（`["tools","systemPrompt"]`、`["webServer"]`、`["connection"]`），dsh-ldvh 实际消费六条宿主服务：`tools`、`systemPrompt`、`webServer`、`connection`、`invariants`、`userQuestions`。逐条与 91 个服务的完整变更集对照，**六条全部落在「未改动」集合**：本区间唯一发生签名的服务是 `deepseekAccount`（新增 `getDeviceIdentity()` 方法），既不在 LDVH 的 inject 声明中，也不在其任何调用点。

这是本轮最有价值的单条结论：它把「是否需要适配」从一个印象问题变成可判定问题——在 91 个服务中，需要改动的恰好是 LDVH 不消费的那一个。注意这不构成「宿主对 LDVH 的防护」：按 specs/08 §6，缝存在不等于已消费，缝未变也不等于 LDVH 行为正确；本发现只支持「无需为签名变更做适配」，不支持「升级后行为已验证」。

溯源：https://github.com/deepseek-ai/deepseek-harness（tag dsh-v0.1.7-rc.2 与 dsh-v0.2.0-rc.1：packages/extensions/tool-cordis/src/api-catalog.ts 的 SERVICE_API 逐条签名比对，变更条目仅 deepseekAccount；消费侧见 https://github.com/dingminhua/dsh-ldvh 的 plugin/lib/host-seams.js 文件头 08 §6 消费清单与 plugin/lib/index.js L76/L348/L383 的 inject 声明）

### F3 dsh-ldvh 消费的八个事件在 mode 与签名上逐字未变

dsh-ldvh 在 `plugin/lib/` 下监听八个宿主事件：`agent/created`、`agent/pre-step`、`agent/turn-stopping`、`fs/edit-intent`、`fs/observed`、`fs/write-intent`、`session/event`、`system-prompt/assemble`。对每个事件提取 `mode` 与 `signature` 两字段在两 tag 之间逐字对照，**八条全部完全相同**：`agent/created` 与 `agent/turn-stopping` 为 `serial`，`agent/pre-step`、`fs/edit-intent`、`fs/write-intent`、`system-prompt/assemble` 为 `waterfall`，`fs/observed` 与 `session/event` 为 `emit`。

事件面是 LDVH 的写守卫与观察记录的实际承载（`fs/write-intent` 承担版本守卫、`fs/observed` 承担读观察、`system-prompt/assemble` 承担规则引导注入）。这八条的 mode 与签名全等，说明本区间没有改变 LDVH 的拦截时序与重入语义——`waterfall` 的短路链与 `emit` 的旁路观察职责划分未被扰动，这是比「事件名还在」强得多的保证。

### F4 会话持久化格式仍为 v4，持久化根零变化；区间内 −75,173 行的删减是生成器压缩而非语义删除

**缺口 2（medium）：官方发布说明未覆盖 API 契约细节。** 该说明面向用户措辞，四节共约 3.7KB，不含方法签名级变更；本报告的契约结论全部来自源码差分，发布说明仅用于交叉验证产品面叙述。

**缺口 3（low）：仓库根目录仍无 CHANGELOG。** 与上一轮一致，变更语义须由 Release 说明与决策记录反推，缺失可直接对照的逐版本条目。

**缺口 4（low）：本区间删除的 14 个文件中，除 `apps/cli/tests/profiles/web/tests/fixtures/schedule.patch.yml`（已确认与 Schedule 转为可选包同步）之外的 13 个删除文件，其各自的替代关系未逐条核对。**

## 建议

1. **把「上游发布 0.2.0 正式版将触发门禁拒收」作为一条前瞻约束提请 Human 决定。** 目标对象类型：WorkCase 或规范修订。预期目标：在 `>=0.1.7-rc.1 <0.2.0` 这一上界因上游发正式版而失效之前，就「是否推进到覆盖 0.2.x、以及是否同步处理 `devDependencies` 的 `0.1.7-rc.2` 精确锁与 README 的目标宿主记载」取得明确答复。验收条件：三项声明（peer、devDependencies、README 记载）是否推进均有据可查的结论，且理由说明依据为本报告的 F1–F6、F8、F9。创建/更新判断：**不应由 AI 直接改写**——该范围是既有兼容基线的一部分，按 specs/08 的「支持基线登记」纪律属 Human 决定，须先提请再动。

2. **在推进声明范围之前，先做一次 0.2.0-rc.1 的最小运行时复现。** 目标对象类型：WorkCase。预期目标：让宿主的实际升级与 dsh-ldvh 的挂载验证在同一动作内闭合，把 F9 的「门禁判定为兼容」升级为「运行时已验证」。验收条件：在 0.2.0-rc.1 宿主上完成四项真实 UI 验收（设置卡片、LVH 会话视图、停用与重启、卸载清理）并记录结果，同时确认 profile 装载无 compatibility 警告。创建/更新判断：与建议 1 有顺序依赖，建议 1 的评价应以本条的结论为输入。

3. **把本轮的判定口径固化为后续同类调研的固定纪律：兼容性结论必须以宿主实际调用的库与选项实跑，不得据 semver 字面语义推断。** 目标对象类型：规范（specs 中的调研方法条款）或 Pitfall。预期目标：不再重复「据默认语义断言失配、实际门禁用 includePrerelease 放行」这一误判。验收条件：后续同类调研在给出兼容性判定时附实跑命令与库版本。创建/更新判断：本区间 F9 的更正过程是该纪律的直接实例证据；若已有规范承载则更新，否则新建 Pitfall。

4. **将 `uiWorkspace.forkSession` 的返回类型变更登记为客户端面的兼容性注意项。** 目标对象类型：Pitfall。预期目标：让后续任何引入客户端 fork 能力的判断（不限于 LDVH）先核对返回类型。验收条件：该变更被记录为可检索的失败机制条目，含签名前后对照。创建/更新判断：dsh-ldvh 当前不击中，故它是**预防性**条目而非事故记录；若判断为「无需对象化」，则后续监测条件为「任何 LVH 消费 `sessions.fork` 或 `uiWorkspace.forkSession` 的新增提案」。

5. **把本机运行中宿主与源码仓的版本落差登记为部署事实。** 目标对象类型：Pitfall 或部署约束条目。预期目标：避免后续会话把「源码仓已升级」误读为「宿主已升级」。验收条件：该落差被记录为可复核的观察（含本机 app 版本与依赖版本分布）。创建/更新判断：本区间 F10 是直接依据；若上一轮的部署约束条目可无损扩展，则更新而非新建。

6. **本轮无需为 LVH 的内核对接做任何代码适配。** 依据为 F2（六条宿主服务接缝零改动）、F3（八个事件 mode 与签名逐字未变）、F6（客户端槽位条目零增删、插件管理与设置卡契约零字节改动）、F8（两个 dependencies 的 src 零改动）四条独立机械证据。此条不构成「已验证支持 0.2.0-rc.1」——该声明需要建议 2 的运行时复现才能成立。
