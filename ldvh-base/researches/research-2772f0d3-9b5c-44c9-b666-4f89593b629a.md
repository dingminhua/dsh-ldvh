## 研究问题

DSH 从 0.1.7-rc.2 到 0.2.0-rc.1 有哪些变更，其中哪些影响 dsh-ldvh 的宿主对接与 LDVH 消费面？

本轮调研的对象是 DSH 内核仓 `deepseek-ai/deepseek-harness` 从 tag `dsh-v0.1.7-rc.2`（`477b4f4205`，2026-09-24）到 tag `dsh-v0.2.0-rc.1`（`4878cdabd8`，2026-09-28）的发布差量。选择这一区间有明确背景：`0.2.0-rc.1` 是 DSH 进入 `0.2` 主版本线后的首个候选版本，而 dsh-ldvh 的既有兼容基线（peer 声明与上一轮调研）都锚在 `0.1.7-rc.x`。按 semver 语义，`0.x` 线的主版本进位是**允许破坏性变更**的边界，因此不能沿用上一区间「契约只增不改」的惯性判断，必须重新机械取证。

本轮调研支撑的项目判断是三条：dsh-ldvh 是否需要为 `0.2.0-rc.1` 做契约适配；其 peer 与 dependencies 声明是否需要随之推进；同级源码仓升级到该版本后是否存在未被察觉的失配。

## 输入与边界

来源按四分法分工，全部为长期可复核的 HTTP(S) 资料，配合本地只读差分：

- **DSH 内核源码仓**（`https://github.com/deepseek-ai/deepseek-harness`）承担全部内核侧发现：两 tag 的只读差分，覆盖七张生成式目录、bundle 组合补丁、持久化目录、包集合与 peer 依赖。观察时点固定为两个 tag 的发布提交，不涉及 `master` 后续提交。
- **官方发布说明**（`https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.0-rc.1`）承担产品面变更的权威骨架，用于与机械差分交叉验证，而非取代差分。
- **npm registry 元数据**（`https://registry.npmjs.org/@deepseek-ai/dsh`）承担版本通道事实：`latest` 仍为 `0.1.7-rc.2`，`0.2.0-rc.1` 走 `next` 通道。
- **受辖项目仓**（`https://github.com/dingminhua/dsh-ldvh`）承担消费面核对：`plugin/package.json` 的 peer 与依赖声明、`plugin/lib/host-seams.js` 声明的宿主缝合消费清单、各 fact writer 的实际调用点。

方法为静态差分与集合级机械比对：对**生成式目录**（服务/事件/类型/槽位/工具/配置/持久化）提取条目集合与签名字符串做逐条对照；对包集合提取 `package.json` 的 `name` 字段求差集；对关键源文件取 blob hash 判等。证据分三级并在发现单元中标注：机械（生成物集合/哈希比对，可逐字复现）、源码（git 差分与官方决策记录原文）、运行时（本机安装产物实读）。

不覆盖范围与来源限制：本轮未在 `0.2.0-rc.1` 上做端到端启动复现，因此「dsh-ldvh 在 0.2.0-rc.1 运行时可正常挂载」类结论不在本轮证据内；未逐字审阅全部 1070 个变更文件，覆盖依赖集合级机械比对与改动量前列文件的定向阅读；官方决策记录与实际装配可能不一致，凡判定「默认是否可用」一律以 bundle patch 的行状态为准，不采信决策记录的叙述。

## 关键发现

### F1 宿主公开契约面为本区间唯一自变量：服务 89→91、事件 81→81 零变化、模型可见工具零变化

对宿主公开契约的三张生成式目录做集合级机械比对，结果高度收敛：`SERVICE_API` 由 89 项增至 91 项，**新增 `otel` 与 `productAnalytics` 两项，零删除**；`EVENT_API` 保持 81 项，**增删改均为零**；`TYPE_API` 由 926 项增至 935 项（+10 / −1），增量为 `EventLogOptions`、`OTelEventRecord`、`ProductEvent`、`SessionLogRecord` 等遥测与产品分析类型，唯一删除项 `ProductTelemetryScalar` 为同族改名。模型可见工具面 `docs/tool-catalog.md` 在两 tag 之间**逐字零差异**（该文件 2719 行、101 个条目标题，两版全等）。

对 LDVH 而言这意味着本区间的「宿主公开缝」整体仍是安全区：一个主版本候选版本在服务、事件、工具三个最关键的公开面上只做了加法，且加法全部落在 LDVH 未接入的遥测与产品分析域。风险因此不在这三张目录上，而必须转向 LVH 实际消费的具体接缝与声明范围（见 F2、F9）。

溯源：https://github.com/deepseek-ai/deepseek-harness（tag dsh-v0.1.7-rc.2 的 477b4f4205 与 dsh-v0.2.0-rc.1 的 4878cdabd8：packages/extensions/tool-cordis/src/api-catalog.ts 的 SERVICE_API 段 89 对 91 项、EVENT_API 段 81 对 81 项、TYPE_API 段 926 对 935 项；两 tag 的 docs/tool-catalog.md 全文件比对无差异）

### F2 dsh-ldvh 消费的六条宿主服务接缝在 91 个服务中无一被改动

按 `plugin/lib/host-seams.js` 声明的消费清单（`ctx.tools.register`、`ctx.tools.guard`、`ctx.invariants.register`、`fs/observed`、`ctx.userQuestions.ask`），加上 `plugin/lib/index.js` 的 `inject` 声明（`["tools","systemPrompt"]`、`["webServer"]`、`["connection"]`），dsh-ldvh 实际消费六条宿主服务：`tools`、`systemPrompt`、`webServer`、`connection`、`invariants`、`userQuestions`。逐条与 91 个服务的完整变更集对照，**六条全部落在「未改动」集合**：本区间唯一发生签名的服务是 `deepseekAccount`（新增 `getDeviceIdentity()` 方法），既不在 LDVH 的 inject 声明中，也不在其任何调用点。

这是本轮最有价值的单条结论：它把「是否需要适配」从一个印象问题变成可判定问题——在 91 个服务中，需要改动的恰好是 LDVH 不消费的那一个。注意这不构成「宿主对 LDVH 的防护」：按 specs/08 §6，缝存在不等于已消费，缝未变也不等于 LDVH 行为正确；本发现只支持「无需为签名变更做适配」，不支持「升级后行为已验证」。

溯源：https://github.com/deepseek-ai/deepseek-harness（tag dsh-v0.1.7-rc.2 与 dsh-v0.2.0-rc.1：packages/extensions/tool-cordis/src/api-catalog.ts 的 SERVICE_API 逐条签名比对，变更条目仅 deepseekAccount；消费侧见 https://github.com/dingminhua/dsh-ldvh 的 plugin/lib/host-seams.js 文件头 08 §6 消费清单与 plugin/lib/index.js L76/L348/L383 的 inject 声明）

### F3 dsh-ldvh 消费的八个事件在 mode 与签名上逐字未变

dsh-ldvh 在 `plugin/lib/` 下监听八个宿主事件：`agent/created`、`agent/pre-step`、`agent/turn-stopping`、`fs/edit-intent`、`fs/observed`、`fs/write-intent`、`session/event`、`system-prompt/assemble`。对每个事件提取 `mode` 与 `signature` 两字段在两 tag 之间逐字对照，**八条全部完全相同**：`agent/created` 与 `agent/turn-stopping` 为 `serial`，`agent/pre-step`、`fs/edit-intent`、`fs/write-intent`、`system-prompt/assemble` 为 `waterfall`，`fs/observed` 与 `session/event` 为 `emit`。

事件面是 LDVH 的写守卫与观察记录的实际承载（`fs/write-intent` 承担版本守卫、`fs/observed` 承担读观察、`system-prompt/assemble` 承担规则引导注入）。这八条的 mode 与签名全等，说明本区间没有改变 LDVH 的拦截时序与重入语义——`waterfall` 的短路链与 `emit` 的旁路观察职责划分未被扰动，这是比「事件名还在」强得多的保证。

溯源：https://github.com/deepseek-ai/deepseek-harness（tag dsh-v0.1.7-rc.2 与 dsh-v0.2.0-rc.1：packages/extensions/tool-cordis/src/api-catalog.ts 的 EVENT_API 段，对上述八个 name 逐条比对 mode 与 signature 字段，结果全等；消费侧见 https://github.com/dingminhua/dsh-ldvh 的 plugin/lib/ 下 ctx.on 监听的八个事件名）

### F4 会话持久化格式仍为 v4，持久化根零变化；区间内 −75,173 行的删减是生成器压缩而非语义删除

`SESSION_FORMAT_VERSION` 在两 tag 均为 `4`（`packages/core/session/src/types.ts`），且该文件在本区间**无任何差分**；`docs/session-format-status.md` 与 `docs/persistence-catalog.md` 两 tag 内容零差异。对 `docs/persistence-schema.json` 做结构化比对：顶层 `formatVersion` 2、`roots` 62 项、`types` 587 项三项计数两版全等；`roots` 段在 JSON canonical 化后**逐字等价**；`types` 段 587 条 `digest` 序列**完全相同**。

该文件表面上的 `+3393 / −75173` 是本区间全仓最大单项删减（占全量删除的 96%）。根因在生成器：`scripts/gen-persistence-catalog.ts` 在 0.2.0 把输出改为 `JSON.stringify(persistenceSchemaSnapshot(schema), null, 2)`，而 `persistenceSchemaSnapshot`（`scripts/persistence-schema-model.ts`）**只保留根图可达的 type schema**——587 条 type 中仅 1 条（`{"kind":"literal","value":false}`）不与其他根图共享因而保留 `schema` 键，其余 586 条丢弃可从 `roots` 重建的冗余副本。新增的 `scripts/persistence-schema-snapshot.spec.ts` 用往返测试守住无损性：`expect(restored).toEqual(original)` 且两种渲染输出 `toBe` 相等。

结论：这不是又一次「单向门」。LDVH 不读该 JSON，且该压缩有测试保障的往返等价；把减行数误读为持久化面收缩会得出完全相反的风险判断，这正是机械化核对计数之外必须核对**语义**的理由。

### F9 dsh-ldvh 的声明范围在 semver 上显式排除 0.2.0-rc.1，升级后即失配
