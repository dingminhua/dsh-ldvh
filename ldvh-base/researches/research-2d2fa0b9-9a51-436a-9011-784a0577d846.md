## 研究问题

DSH 从 0.2.0-rc.1 到 0.2.0-rc.2 有哪些变更，其中哪些影响 dsh-ldvh 的宿主对接与 LDVH 消费面？

本轮调研的对象是 DSH 内核仓 `deepseek-ai/deepseek-harness` 从 tag `dsh-v0.2.0-rc.1`（`4878cdabd8`，2026-09-28）到 tag `dsh-v0.2.0-rc.2`（`639ed01539`，2026-09-29）的发布差量。选此区间的直接背景是宿主已实际跃迁：本机运行中的 `/Applications/DeepSeek Harness.app` 现为 `CFBundleShortVersionString` `0.2.0-rc.2`，其 asar 内 279 个 `dsh*` 包全部为该版本，插件仍经 profile 的 `link:` 指向本仓库。上一轮调研（`0.1.7-rc.2`→`0.2.0-rc.1`）刚把兼容声明上界推进到 `<0.3.0` 并停在 `0.2.0-rc.1` 基线，本轮要回答该基线与声明在 rc.2 上是否仍成立。

本轮调研支撑的项目判断有三条：dsh-ldvh 是否需要为 `0.2.0-rc.2` 做契约适配；其刚推进的声明范围在 rc.2 上是否仍然覆盖；支持基线登记值是否应从 `0.2.0-rc.1` 推进到 `0.2.0-rc.2`。

## 输入与边界

来源按四分法分工，全部为长期可复核的 HTTP(S) 资料，配合本地只读差分：

- **DSH 内核源码仓**（`https://github.com/deepseek-ai/deepseek-harness`）承担全部内核侧发现：两 tag 的只读差分，覆盖生成式契约目录、bundle 组合补丁、持久化 schema 与变更记录、包集合、peer 声明、配置目录与决策记录。
- **官方发布说明**（`https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.0-rc.2`）承担产品面变更的权威骨架，用于与机械差分交叉验证并暴露机械比对不易察觉的用户面变更（如模型目录）。
- **npm registry 元数据**（`https://registry.npmjs.org/@deepseek-ai/dsh`）承担版本通道事实：`latest` 与 `next` 均已指向 `0.2.0-rc.2`。
- **受辖项目仓**（`https://github.com/dingminhua/dsh-ldvh`）承担消费面核对：`plugin/package.json` 的声明、`plugin/lib/host-seams.js` 的宿主缝消费清单与 `ask` 调用形态。

方法为静态差分与集合级机械比对：以字符串感知的括号深度解析器从生成物中抽取条目集合与签名字段逐条对照；对包集合提取 `package.json` 的 `name` 字段求差集；对关键文件取 blob hash 判等；对声明与宿主的兼容性以宿主**自带**的 semver 7.8.5 实跑求值；对宿主指认按上一轮写入 `local-dev-workflow` 的**红线 7**取四项实证（进程、端口持有者、运行产物内核版本、profile 安装形态）。证据分三级：机械（生成物集合/哈希比对，可逐字复现）、源码（git 差分与官方决策记录原文）、运行时（本机运行宿主的实读观察）。

不覆盖范围与来源限制：本轮未做完备的端到端 UI 验收（六项中 `/ldvh` 与 `/ldvh/api/health` 两项有运行时实证，其余四项未核对）；未逐字审阅全部 1022 个变更文件，覆盖依赖集合级比对与改动量前列文件的定向阅读；官方决策记录可能与实际装配不一致，凡判定「默认是否可用」一律以 bundle patch 与 `package.json` 的**实际行状态**为准；模型目录的逐条 ID 增删未穷举（见未证实 4）。

## 关键发现

### F1 区间规模 187 commits；`docs/persistence-schema.json` 的 ±1,600 行与新增 11,405 行 schema 文件都不代表格式升级

区间为 **187 commits**（140 非 merge，47 merge），1022 files `+33,253/−6,141`；排除 `docs/` 后 982 files `+19,279/−4,388`，仅 `docs/` 为 40 files `+13,974/−1,753`。`docs/` 增量几乎全部来自两处：新增的 `docs/persistence-changes/2026-09-21-user-question-reply.schema.json`（**+11,405 行，rc.1 无此文件**）与 `persistence-schema.json` 的 `+1,670/−1,528` 改写。

`SESSION_FORMAT_VERSION` 在两 tag **仍为 `4`**（`packages/core/session/src/types.ts` L89），且该文件 **blob 全等**（`593c86d5…`，byte 级同一对象，强于「无差分」）；`docs/session-format-status.md` 亦 **blob 全等**（`9df313da…`）。因此本轮**不是又一次格式升级**：`persistence-schema.json` 的改动是既有 v4 格式内**根图内容**的变化（见 F6），而非版本号进位。把「新增一万行 schema」误读为 v5 会得出完全相反的数据面风险判断——`schema.json` 是**格式参考物**（新 root 的完整定义文档），不是会话日志本身。

对 LDVH 的意义：其作为会话消费者不读这两个文件，数据面无需备份或迁移动作。

溯源：https://github.com/deepseek-ai/deepseek-harness（tag dsh-v0.2.0-rc.1 的 4878cdabd8 与 dsh-v0.2.0-rc.2 的 639ed01539：git rev-list --count 187 与非 merge 140；git diff --shortstat 的三组口径自洽 982+40=1022、19279+13974=33253、4388+1753=6141；packages/core/session/src/types.ts L89 两版均 4 且 blob 593c86d52a5c26d531913ffaff9aac651732c2da 全等；docs/session-format-status.md blob 9df313da2fad277254f464a8bdf6a6c8b541aab1 全等）

### F2 宿主公开契约只增不改：服务 91→91 零增删、事件 81→81 零变化、工具名 65→65 零增删

对三张生成式契约目录做集合级比对：`SERVICE_API` **91→91**（新增与删除均为空），`EVENT_API` **81→81，条目级变化数为 0**，`TYPE_API` **935→936**（新增 `TimedUserQuestionResult` 一项）。模型可见工具面 `docs/tool-catalog.md` **有差异**（`+5/−5`，5 处描述改写），但**工具名集合零增删**——两个独立口径（`### \`name\`` 标题集合与摘要表首列工具名集合）均为 65→65 且顺序相同。

服务条目级的实质变化恰有 **2 条**：`typertGateway` 新增 `hasLiveClient(): boolean`（4→5 方法，零删除）；`userQuestions` 新增 3 个方法（1→4 方法，零删除，见 F3）。事件面为零变化，这比「事件名还在」强：mode 与 signature 逐字全等。

对 LDVH 的意义：一个候选版本在三个最关键的公开面上仍只做加法。风险因此不在「有没有删东西」，而在**唯一被改动的那一条是否恰好被 LDVH 消费**——见 F3、F4。

溯源：https://github.com/deepseek-ai/deepseek-harness（tag dsh-v0.2.0-rc.1 与 dsh-v0.2.0-rc.2：packages/extensions/tool-cordis/src/api-catalog.ts 的 SERVICE_API 段 91 对 91 且 added/removed 均为空、变更条目恰为 typertGateway 与 userQuestions、EVENT_API 段 81 对 81 条目级变化 0、TYPE_API 段 935 对 936；docs/tool-catalog.md 的 +5/−5 与工具名集合 65 对 65 零增删）

### F3 唯一被改动的服务恰是 LDVH 消费的 `userQuestions`，但既有 `ask` 方法签名逐字未变，新增三方法为并列增量

`userQuestions` 在 rc.2 由 1 个方法增至 4 个，新增 `answer(agent, callId, answer)`（`@Remote`）、`attachWait(agent, callId, signal)`（`@Remote({ mode: 'stream' })`）与 `askTimed(request & { agent }, callId, timeoutMs)`。**既有 `ask(request: AskUserQuestionRequest): Promise<AskUserQuestionAnswer>` 未被触碰**：源文件 `packages/interaction/user-questions/src/index.ts` 中该行 rc.1:86 与 rc.2:287 **逐字节相同**，其上方 JSDoc 8 行亦逐字相同；生成物侧更强的证据是——整个 `ask` 方法对象（signature + description + parameters + returns + throws，约 950 字符）在两 tag **全等**，新增三方法在数组中位于 `ask` **之前**，`ask` 自身块未被改动。

这是本轮对 LDVH 最关键的判定：**唯一发生变更的服务正是它消费的那一个，但变更方式是并列新增方法，而非修改既有签名**。LDVH 只调用 `ask`（`plugin/lib/host-seams.js` 的 `seams.ask`，典型形态 `ask({questions, signal?, agent?})`），不触及三个新方法。

须附一条实质保留（见 F4）：`ask` 的**入参类型**经别名链间接扩张了一个可选字段，故「该缝契约完全未动」是过度表述。

溯源：https://github.com/deepseek-ai/deepseek-harness（tag dsh-v0.2.0-rc.1 与 dsh-v0.2.0-rc.2：packages/interaction/user-questions/src/index.ts 的 ask 方法 rc.1 L86 与 rc.2 L287 逐字节相同；packages/extensions/tool-cordis/src/api-catalog.ts 的 userQuestions 条目由 1 方法增至 4，新增 answer/attachWait/askTimed，零删除；消费侧见 https://github.com/dingminhua/dsh-ldvh 的 plugin/lib/host-seams.js 中 seams.ask 的定义与 L386/L464 两处调用）

### F4 `ask` 的入参类型经 `AskUserQuestionRequestEvent` 新增可选 `wait?` 字段扩张——纯加法，对 LDVH 不构成破坏

`AskUserQuestionRequest` 是空派生别名（`export interface AskUserQuestionRequest extends AskUserQuestionRequestEvent {}`），而 `AskUserQuestionRequestEvent`（`packages/interaction/user-questions/src/types.ts`，rc.1:70 / rc.2:129）在 rc.2 **追加了第 4 个字段**：

    wait?: {
      callId: ToolCallId
      timed?: boolean
