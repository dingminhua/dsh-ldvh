## 研究问题

DSH 实验性 Agent Teams bundle（@deepseek-ai/dsh-experimental-agent-team-profile 0.1.7-rc.1，含领域服务/tool/Web UI 三个组件）是什么、其能力与边界如何构成、对 dsh-ldvh 有什么可吸收或需规避之处？

本轮调研支撑的项目判断是：dsh-ldvh 当前对 Agent Teams 零消费面（`specs/` 与 `plugin/lib/` 全文无 teammate / agentTeams 引用，仅两份 DSH 升级调研报告各有一处理名提及），因此需要在「宿主原生机制面」上判断——该 bundle 的团队协作能力与 LDVH 自有的 WorkCase 授权门禁制度是什么关系，以及它对本仓独立复核通道构成机会还是风险。

调研对象是外部对象（DSH 随附发布的实验性公开 bundle），不是本仓内部方案或架构比较；调研问题在进入本轮时即已单句可表述，未经历问题收敛阶段，故本对象按明确方向型承载，正文不含「调查阶段」H2。

## 输入与边界

观察时点：2026-09-25。版本基线：本机 DSH 0.1.7-rc.1；bundle 的四个包均为 0.1.7-rc.1。

来源分工：

- 四个包的官方 README.zh.md（`master` 分支 raw 路径）—— 能力、边界与已知限制的权威自述，是本轮主要事实来源；
- `agent-team-profile/cordis.patch.yml` —— 组合层在宿主上实际做什么的权威文本（该包运行时内容即此文件）；
- npm registry 元数据 —— 发布节奏、版本线与 dist-tags；
- npm 上四个包的 0.1.7-rc.1 publish tarball —— 字节级载体，用于核对本机安装件与公开产物是否一致；
- `@deepseek-ai/dsh-subagent` 的 registry 产物 —— 用于确认 teammate 的会话身份来源（该字段由上游定义，不由 Team 包定义）；
- 本机运行时只读查询（Cordis Inspect 的 Tool 与 Config provider）—— 确认当前工具面与活跃配置，属观察而非解释。

核对方法与可信度：本机 `node_modules` 中四个包的 `lib/index.js`、`cordis.patch.yml`、`README.zh.md` 与 npm 0.1.7-rc.1 tarball 逐 sha256 比对，结论为全部相同，故对安装件的读取等价于对公开产物的读取，本轮引用源码与产物可复核。分析主体是静态分析（源码、产物文本、registry 元数据）叠加只读运行时查询。

不覆盖范围：Team 事件在会话日志中的 schema 版本与迁移行为；0.1.7-rc.1 与已发布的 rc.2 之间的变更内容；LDVH 若采用该 bundle 后呈现层的信息架构设计；多 teammate 并发写入与 LDVH 受控提交（Git Gate 的 K1 双向路径覆盖）的交互。以上见「未证实与缺口」。

来源冲突（如实登记）：profile 包 README 自述「`subagent`、`subagent_fork` 工具和名称重叠的全局 child control 均被禁用」，但本机运行时两者仍可调用（与本会话的九个 Team 工具并存）。该冲突不是文档错误，其成因已在关键发现中定位为预设作用域，且该边界由 profile README 自己的「预设内的子代理控件」条如实声明。

## 关键发现

### F1 bundle 由领域服务、模型工具与 Web 投影三层构成

观察：该 bundle 由三个可独立运行的行组成——`dsh-experimental-agent-team`（领域服务：持久 roster、peer mailbox、共享任务板）、`dsh-experimental-tool-agent-team`（模型工具表层）、`dsh-experimental-client-ui-agent-team`（Web 成员列表与任务看板）。三者职责边界清晰：领域包显式声明「它本身不提供任何工具」，需与工具包一起挂载；Web 包只读共享投影，不注册面向模型的输入。

判断：这是 LDVH 插件分解可以参考的三层切法——领域语义、模型面、呈现面各自独立成行，任何一层缺席都可由其余层如实报告（而非静默降级）。LDVH 的 `webServer` 路由 + Sidebar + 设置面板目前集中在一个包内，该切法值得在 08 号接入规范中作为可选结构记录，但不构成本轮必须动作。

溯源：https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/experimental/agent-team/README.zh.md（README.zh.md §概述）

### F2 bundle 本体的运行时内容是 patch，而非代码

观察：profile 包 `lib/index.js` 仅 11 字节、内容为 `export {};`；其全部运行时语义落在 `cordis.patch.yml`：先以顶层 `disabled: true` 禁用四条标准子代理行，再以 `insert` 插入三条 Team 行并给定显式 provider 与限制。官方自述亦确认「UI 插件的 Host 入口不执行逻辑；只有 Web 客户端加载器会挂载其浏览器入口，因此 headless 无需启动 Web 服务」。

判断：这与 LDVH 当前的接入形态（Host 侧注册路由与工具、Client 侧注册 slot）是同一套 Cordis 组合模型，说明「bundle 即一层 patch」是宿主认可的正式形态，而非临时手法。对 LDVH 的意义是：把组合差异写成 patch 层而非塞进插件运行时代码，可以让同一插件在不同 profile 下组合出不同能力面。本轮不改动 08 号规范，仅作为已知形态登记。

溯源：https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/experimental/agent-team-profile/cordis.patch.yml（cordis.patch.yml 全文）

### F3 九个模型工具覆盖创建、消息、观察与任务板四类能力

观察：工具包恰好注册九个工具，分四类——创建（`spawn_teammate`，仅 Lead 可调用）、消息（`send_message`，在最近步骤边界 steering 运行中的成员，或启动／冷恢复非活动成员）、观察与等待（`list_agents`、`wait_agent`、`interrupt_agent`）、任务板（`team_task_create`、`team_task_list`、`team_task_get`、`team_task_update`）。工具名在产物中经核对确为上述九个。Lead 与 teammate 的九个 schema 完全相同，Lead 专属权限在执行时才校验。

判断：schema 同构、权限在执行时校验，是一个值得 LDVH 参照的接口设计——它让「同一套工具描述」在两种角色下保持请求前缀稳定（利于 KV cache），而把角色差异收敛到执行期的一个检查点。LDVH 的 `ldvh_*` 工具目前只注册在受管辖根会话，属于相反的取舍（按角色裁剪工具面），两者各有依据，本轮不作优劣判断。

溯源：https://registry.npmjs.org/@deepseek-ai/dsh-experimental-tool-agent-team/-/dsh-experimental-tool-agent-team-0.1.7-rc.1.tgz（lib/index.js 内九个工具的 name 注册）

### F4 失败以 28 个类型化错误码的闭集报告，而非静默破坏状态

观察：领域包实现中定义了 28 个 `TEAM_*` 错误码闭集，覆盖权限（`TEAM_LEAD_REQUIRED`、`TEAM_TASK_UNAUTHORIZED`、`TEAM_NOT_MEMBER`）、成员（`TEAM_MEMBER_LIMIT`、`TEAM_MEMBER_NAME_TAKEN`、`TEAM_MEMBER_NOT_FOUND`、`TEAM_PROVISIONING_CONFLICT`）、并发（`TEAM_TASK_STALE_REVISION`、`TEAM_TASK_ALREADY_CLAIMED`）、容量（`TEAM_MAILBOX_FULL`、`TEAM_MESSAGE_TOO_LARGE`、`TEAM_TASK_LIMIT`）、生命周期（`TEAM_DISPOSED`、`TEAM_WAIT_ABORTED`）等类别。设计理念第四条为「超出上限时明确失败——每个限制都是经过校验的部署值，耗尽时报告类型化错误，而不是复用 id 或名字」。

判断：为每类失败给出稳定的机器可判标识，而不是让调用方解析自然语言——这与 LDVH 受控写入返回统一 envelope（含 `outcome`、`scope`、`gaps`）的取向一致，可视为同类实践的独立印证。对 LDVH 的启示是：错误码闭集本身值得在 05 号 CLI 规范的返回契约中被显式枚举，使调用方可按码分支而非按文本匹配。

溯源：https://registry.npmjs.org/@deepseek-ai/dsh-experimental-agent-team/-/dsh-experimental-agent-team-0.1.7-rc.1.tgz（lib/index.js 内 TEAM_* 常量闭集）

### F5 持久模型以 Lead 会话日志为唯一真源，状态全部由日志回放派生

观察：设计理念首条为「持久日志，派生状态」——Lead 会话日志是唯一真源，roster、mailbox 与任务状态每次读取都从中回放。Team 事件只追加到精确的 live Lead 会话并在操作报告成功或唤醒等待者之前 flush；四类事件 `team/member`、`team/task`、`team/message/queued`、`team/message/delivered` 仅存在于日志，从不进入会话表面，因此派生模型历史不受协作记录影响。顺序与时间由会话事件的 `seq` 与 `time` 负责，快照不重复保存；伴生不变式插件在 append 前回放候选事件、拒绝非法转换。

判断：这是本轮调研中对 LDVH 最有参照价值的一条。它与 LDVH 自有的事实源纪律（单一权威载体 + 写后精确回读 + 派生视图不反向写入）同构，且给出了一个 LDVH 尚未采用的补充手段——把不变式校验做成 append 前的前置拒绝（LDVH 目前的校验主要落在受控写入入口）。这属可借鉴的工程模式，但引入与否涉及 03/06 的改动，不属本轮判断范围。

溯源：https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/experimental/agent-team/src/invariant.ts（src/invariant.ts 伴生插件入口）

### F6 teammate 的会话身份与普通子代理同源，走宿主原生 startContinuable 路径

观察：`spawnTeammate` 不自建会话创建机制，而是调用既有的子代理服务：`started = await this.ctx.subagents.startContinuable({ childId, provider, label, request: { prompt, parent: root }, signal })`。该调用在 `@deepseek-ai/dsh-subagent` 内最终经 `childSessionMeta()` 组装子会话元数据，其中显式写入 `origin: "subagent"` 与 `parentSession`。也就是说，宿主不为 Team 另立身份类别，teammate 在会话层面的身份标记与由 `subagent` 工具创建的子代理完全相同。

判断：这条对 LDVH 是决定性的。LDVH 的子代理分支判据是 `agent.session.header.origin === "subagent"`，命中即进入子代理路径（血缘校验 + 管辖范围沿委派链继承）而不注册 `ldvh_*` 工具。由于 teammate 携带同一标记，它会被 LDVH 如实认定为受管辖子代理并进入其子代理登记表。推论：LDVH 的独立复核回传通道（父会话以自己的会话身份代隔离子代理回传，身份与结论取自宿主子代理登记表）对 teammate 同样可用——即「用 teammate 做独立复核」在机械路径上是通的，无需 LDVH 改动。注意：本推论由静态因果链得出，未经实际 teammate 运行验证（见「未证实与缺口」）。

溯源：https://registry.npmjs.org/@deepseek-ai/dsh-subagent/-/dsh-subagent-0.1.7-rc.1.tgz（lib/index.js 的 startContinuable 与 childSessionMeta 定义）

### F7 任务板是 CAS 版本化的依赖图，且 owner 永不自动释放

观察：任务是完整版本化快照，每次变更携带 `expectedRevision`，陈旧调用方收到 `TEAM_TASK_STALE_REVISION` 而不是覆盖更新的值。任务可声明对其他任务的依赖，只有全部依赖完成后才可 claim。`writeScopes` 是规范化后的 workspace 相对前缀，视图对与 in-progress 任务的重叠发出警告，但绝不阻止 claim 或授予写权限。另外，成员不活动、interrupt、进程退出与工作失败都不会释放任务 owner。数字 id 空间耗尽时报告 `TEAM_TASK_LIMIT` 而不复用 id；已删除任务作为 tombstone 保留以供回放与维持 id 稳定。

判断：这套「乐观并发 + 显式就绪 + 显式 owner 释放」的形状，恰好是 LDVH 在引入任何并行执行之前应当先想清楚的三个问题。尤其「owner 不自动释放」是一个诚实的取舍：它把 stale owner 的处置责任交给协调者（Lead），而不是用超时假装解决。LDVH 的 WorkCase 的 attempt 令牌目前也明确不承载授权、需人工核对副作用后决定续跑或作废（`21 §10.4`），两者在「不假装自动解决」这一点上取向一致。

溯源：https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/experimental/agent-team/src/task-board.ts（src/task-board.ts 的 CAS 命令与 DAG 校验）

### F8 bundle 顶层禁用标准子代理行，但预设作用域可使其复活

观察：patch 顶层显式禁用四条标准子代理行（`tool-subagent-control`、`tool-subagent-list-agents`、`tool-subagent`、`tool-subagent-fork`），profile README 亦自述「`subagent`、`subagent_fork` 工具和名称重叠的全局 child control 均被禁用」。但在本机实际运行下，两者与九个 Team 工具同时可调用。成因由 profile README 自己的已知限制条给出：「Web 预设仍可在预设作用域挂载 continuable Subagent 控件；顶层组合包不会替换这些注册」。本仓 profile 选定的 `cordis` 预设即在预设作用域内声明了自己的 `tool-subagent` 与 `tool-subagent-fork` 行，故它们不在顶层 patch 的禁用范围内。

判断：这是一个容易误判的点——「启用 Agent Teams 后就没有 subagent 工具」的直觉在本机不成立。但对 LDVH 而言该差异不影响核心结论：两条通道最终都通向同一份宿主子代理登记表，故复核回传通道不受影响。真正需要注意的是工具面收窄：启用后模型同时看到两套同形委派工具（Team 的 `spawn_teammate` 与预设的 `subagent`），指令空间变宽，LDVH 若在引导文本中提及委派时应避免含混表述。

溯源：https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/experimental/agent-team-profile/README.zh.md（README.zh.md §已知限制与延期工作「预设内的子代理控件」条）

### F9 交付保证止于进程内重试加去重，明确不承诺跨进程共识

观察：设计理念第三条明写「进程内归属——所有协作都位于单一进程；保证是重试加去重，绝不是跨进程共识」。mailbox 的保证边界同样被如实声明：只有目标会话在 pending inbox 或已记录历史中持久持有消息身份后才确认投递，重试前会同时折叠 live 与持久目标 inbox／历史状态，因此 inbox 已接受但模型尚未 claim 时发生崩溃不会复制消息——但该保证是「进程内重试加 target 会话去重」，而非跨进程 exactly-once。已知限制另列「mailbox 不保证跨进程 exactly-once——不支持多个 harness 进程并发操作同一 Team」。

判断：这种把保证边界写进设计理念、并在已知限制中复述的做法，正是 LDVH 反复要求的「如实登记未验证范围」。它同时也是对本仓的直接提示：若未来出现多进程同时操作同一项目工作树的情形，Team 不提供任何可用于协调的保证，LDVH 也不能把 Team 当作并发控制的底座。

溯源：https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/experimental/agent-team/README.zh.md（README.zh.md §设计理念与 §已知限制与延期工作）

### F10 所有成员共享同一工作目录，写范围只是提示而非锁

观察：已知限制明确列出「单进程、共享 checkout——成员共享 cwd，修改立即可见；本包不提供 worktree、远端成员、merge 或文件锁」，以及「write scope 仅作提示——Bash、formatter、代码生成器与直接外部写入可以绕过文件版本检查；Lead 必须协调 owner 并检查最终 diff」。工具包 README 亦声明其固定策略「只负责协调，不负责 confinement——它无法阻止 Bash 或外部进程写入重叠文件」。

判断：这与 LDVH 已自述的同类边界（受控提交之外，Bash、formatter、codegen 与脚本不受文件版本保护）是同一条已知缺口，Team 没有把它变得更窄，也没有把它变得更宽。因此「引入 Team 会带来并发写保护」是不成立的预期；反过来，Team 也没有引入 LDVH 尚未知晓的新风险。真正的新增成本在协调纪律：多个成员写入同一工作树时，受控提交的 staged Index 可能被并发 stage 干扰（见缺口，优先级 high）。

溯源：https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/experimental/agent-team/README.zh.md（README.zh.md §已知限制与延期工作）

### F11 Web 面板是只读派生视图，不提供任务修改控件

观察：Web 包从共享 Session store 读取 Lead Session 的 `agentTeam` 投影，Host 投影 frame 使其保持最新；「面板不提供任务修改控件」，任务创建与更新一律由 Team agent 通过工具完成。已知限制列出「没有 mailbox timeline——投影视图只承载 roster 与任务；不显示 peer 消息」，以及「没有 lifecycle 或 workspace control——panel 不能 spawn、rename、delete 或 interrupt teammate，write scope 仍只是提示性 metadata」。该包不扩展稳定 API Proxy、不存储 Team 状态、不注册面向模型的输入。

判断：呈现层与写入面严格分离、面板只读，是 LDVH 在 10 号呈现规范中已有的同类取向（呈现是派生结果，不是第二事实源）。Team 的做法可以作为一个外部印证：即便是官方实验性实现，也选择让面板只读。此项对本轮无动作。

溯源：https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/experimental/client-ui-agent-team/README.zh.md（README.zh.md §概述与 §查看任务板）

### F12 bundle 默认关闭，且本机安装版本落后于已发布的 rc.2

观察：profile README 声明「仅显式启用——本包随安装提供但默认关闭；随附 CLI、Web、SDK、ACP 与 Python profile 都不会启用它」。本机 profile 的 `dsh.profile.bundles` 手工列入了 `@deepseek-ai/dsh-experimental-agent-team-profile`。版本上，四个包的发布线从 2026-09-09 的 0.1.5-alpha.2 起共 10 个版本；本机为 0.1.7-rc.1（2026-09-23），而 npm 的 `dist-tags.next` 已指向 0.1.7-rc.2（2026-09-24）。

判断：默认关闭 + 显式 opt-in 与 LDVH 对自身实验能力的处置一致。版本落后一项属运维事实而非缺陷——它意味着本轮的结论锚定在 rc.1；若后续升级到 rc.2 或更高，应以官方 README 与 patch 的当期文本重新核对本报告的能力与边界条目，而不是沿用本报告。

溯源：https://registry.npmjs.org/@deepseek-ai/dsh-experimental-agent-team-profile（registry JSON 的 dist-tags 与 time 字段）

## 未证实与缺口

未证实项一：本机是否本当以 rc.2 而非 rc.1 安装。本机为 rc.1，npm `dist-tags.next` 已为 rc.2，两版差异未比较。该疑点不阻塞本轮结论（本报告所有条目均锚定 rc.1 的产物与文本），但阻塞「本机版本是否最新」这一判断；版本选择属用户 profile 决定，不由本调研裁定。

未证实项二：以 teammate 充当独立复核者时，LDVH 的身份判据是否按 `host` 通道为其盖戳。本调研只建立了「teammate 走 `startContinuable` 且携带 `origin: "subagent"`」的静态因果链，未以实际 teammate 运行验证复核回传成功返回。原因是未取得 Human 授权不创建 teammate。静态证据链足以支撑「路径在机制上可用」，但不等价于已实测——按 LDVH 自己的纪律，前者不得当作后者使用。

缺口一（high）：多 teammate 并行写入与 LDVH 受控提交（Git Gate）的拾取行为未验证。teammate 与 Lead 共享同一工作树，而 LDVH 的 K1 双向路径覆盖校验在受控提交时读取 staged Index；多个成员并发 stage 时的行为既未实测也未在规范层面讨论过。该缺口阻塞「LDVH 在受管辖会话中引入 Team 是否安全」这一判断，故按 high 登记。

缺口二（medium）：Team 事件在会话日志中的 schema 版本与迁移行为未展开。已知投影缓存版本 4 会从 Session 日志重建较早缓存版本的 checkpoint，且 Session 格式版本保持不变；如需在生产中长期启用该 bundle，应补此项。

缺口三（medium）：LDVH 若采用该 bundle，呈现层的信息架构冲突未评估。Team UI 向会话页头添加自己的 action，与 LDVH 自有的 Sidebar／全屏面板共存时的层级与入口关系未做设计比对。

## 建议

建议一：为本报告「Team 任务板与 WorkCase 分层」这一结论建立一条 ADR。目标对象类型为 ADR（22 号）；预期目标是钉死一条边界——Agent Teams 的共享任务板（会话内协作调度，无 Human Gate、无授权钉扎、无关闭审计、owner 不过期）不得被当作 WorkCase 的替代承载，不得以任务板条目代替 C1 提案、Gate 1 批准或 Gate 2 关闭。验收条件是该 ADR 落盘且 21 号或 10 号有一处指针指向它，使后续会话在同时看到两套「任务」概念时有唯一裁决依据。创建判断：现在就建，因为缺口一（并发写入）尚未解决，而任务板与 WorkCase 的形状相似性已经在本次调研中被实际观察到存在误用空间。

建议二：把「独立复核可经受管辖 teammate 承接」作为一条待验证假设登记，而非现在写进规范。目标对象类型为本轮之后的定向调研或 WorkCase（当缺口一解决后）；预期目标是用一次实际运行验证：父会话以 `reviewer_child_agent_id` 代 teammate 回传复核结论时，身份与结论是否均按预期取自宿主登记表，且关闭侧独立性判据是否满足。验收条件是复核条目成功写入并能在对象中回读到该条。创建判断：现在不建，依据是未证实项二——机制上路径已通，但 LDVH 的身份判据是否按 `host` 通道盖戳未经实测；在实测前写进规范会把「未验证范围」误报为「已承接」。

建议三：缺口一（并发写入与 Git Gate 的交互）按高优先级对象化。目标对象类型为 WorkCase（21 号）或 Research（若需先取证）；预期目标是明确多成员并发 stage 时受控提交的行为，并据此决定 LDVH 是否需要在 06 号提交契约中增加串行化约束。验收条件是该行为被实测记录，并给出「允许并发」或「必须串行」的明确判据。创建判断：现在就建，因为它是本轮唯一被判为 high 的缺口，且它阻塞的是「是否可以在受管辖会话中启用 Team」这一有现实后果的决定。

## 后续分流

分流一（对应建议一）：当出现「有人以 Agent Teams 任务板条目替代 WorkCase 承载执行工作」的实际信号，或当 21 号与 10 号下次修订时，创建 ADR 并回填指针。在此之前可继续无需对象化——本轮结论已在本报告内可回查，且 LDVH 当前尚无任何 Team 消费面，误用尚不具备现实路径。

分流二（对应建议二）：当缺口一的实测完成、且确有一次真实需要独立复核的执行场景时，创建定向 Research 或将该验证并入当日 WorkCase。若信号是「teammate 已实际作为复核者写入过至少一条 reviews 条目」，则升级为 ADR（把已验证事实固化为规则）；若始终无此场景出现，可继续无需对象化——该能力只是候选，不构成 LDVH 的能力缺口。

分流三（对应建议三）：当出现「受管辖会话中实际启动了两个以上成员并各自写入文件」的信号，或当 06 号提交契约下次修订时，创建 WorkCase 并以此为验收对象。在此之前可继续无需对象化，但需保持监测：本报告未覆盖该项，若期间发生并发写入导致的提交异常，应按 26 号登记 Friction 而非在本报告上追加结论。

分流四（版本漂移）：当本机 bundle 版本发生变化（升级到 rc.2 或更高）时，更新本对象或新建 Research——判断标准是该变化是否触及本轮的关键发现条目（尤其补丁禁用段、`origin` 身份来源、交付保证边界三处）。若仅是小版本修复且三处文本未变，可继续无需对象化，仅在本对象 `change_log` 中记一句版本漂移说明。
