## 研究问题

目标分解、任务到目标的可追溯、以及「完成了多少」的可见化，在需求工程、Agent 模式目录与 OKR 管理三个领域各自有哪些成熟做法、其判据与边界是什么

本调研的对象是三个领域的外部做法，不是 LDVH 自身实现；目的是为 25 号「计划区」缺口的重新设计判断提供依据。

## 输入与边界

- **输入来源**：Agent Pattern Catalog（Goal Decomposition 模式页）、pi-goal 扩展的包页与 README、Google re:Work OKR 指南、What Matters 的 OKR 评分说明、Jama Software 的需求追溯矩阵指南。
- **读取深度**：上述五处以页面原文逐段读取；Goal-oriented Requirements Engineering 的原始 PDF 因其托管站点维护中未能取得，仅由检索摘要间接引用，已登记为缺口。
- **不覆盖**：未做代码级核实（pi-goal 的实现细节只据其 README 陈述，未读其 `src/`）；未穷举同类项目，聚焦于形态最具代表性的五处；不评估这些做法在 LDVH 中的采纳代价（属方案收敛，非调研范围）。

## 关键发现

### Goal Decomposition 模式要求递归拆分目标直至每个叶子可直接执行，且必须在每层监控进度、把卡住的分支显式浮出

该模式（成熟度标注 `mature`）把「一个过大的目标」拆成目标树，叶子是可直接执行的动作（发邮件、跑查询、改一个文件）。它明确列出五项失败模式，其中第一项即「丢失卡住分支」——深处叶子停摆而监控未浮出，最终报告里没有这个缺口。

模式还给出两条与 LDVH 直接相关的护栏：**只在叶子目标上行动**（非叶子必须先继续拆分），以及**为每个叶子设步骤预算**，使单条卡住的分支不能耗尽全局预算。

溯源：https://agentpatternscatalog.github.io/patterns/patterns/goal-decomposition.html（§2 Problem、§8 Guardrails、§9 Failure Modes）

### pi-goal 把每个任务建模为带可检验验收条件的 spec，reviewer 对着真实来源（跑测试、读文件、查 spec）核验而非评判对话记录

这是该扩展与常见的「让另一个模型看看做得对不对」的关键差别：reviewer 的判据是**可执行的核验动作**，示例验收条件直接写成 shell 表达式。README 明写 reviewer「gates against the real source of truth (running tests, reading files, checking specs) rather than judging the transcript」。

这一条与 LDVH 25 §9 的三层分工（机械反查 → AI 汇总 → Human 终判）同构，差别在于它把机械层落成了「可执行命令」而非「存在性检查」。

溯源：https://pi.dev/packages/@peeraponw/pi-goal（README「How it works」与「pi-goal」引言段）

### pi-goal 把终态压成闭集 achieved/unmet/halted/budget_limited，过程进度另以 run 目录承载，两者分离

终态是四值闭集，不设百分比；过程进度另走 `goal-runs/<run-id>/` 可 tail 的痕迹。二者分离是本条最重要的一点——它说明「二值验收」与「连续进度」不是竞争关系，而是分处两个权限层。

边界如实登记：pi-goal 的目标是**单次运行**的生命周期（`/goal` 再次设定即替换），与 LDVH 的项目级常驻单例不同构。

溯源：https://pi.dev/packages/@peeraponw/pi-goal（README「Quick start」终态列表、「Commands」表与 `goal-runs/` 说明）

### OKR 评分的通行做法是逐条 KR 分别打分再取平均，而非自上而下拍一个总百分比

两处独立来源一致：先对每条 Key Result 单独打分（0.0–1.0），再聚合。What Matters 进一步指出 Andy Grove 原版是**纯 yes/no 判定**，现代 0.0–1.0 刻度是后来的演变，且 0.7 即视为成功。

对 LDVH 的直接含义：若引入完成度，其口径必须是**自下而上从各 SG 名下的可判定状态派生**，而不是允许自顶向下人工填写一个比例——后者可被注水且无法核对。

溯源：https://www.whatmatters.com/faqs/how-to-grade-okrs（「Grading is an unbiased activity」段与 FAQ）

### 需求追溯矩阵以「需求→任务→测试」三列对照把每个决策回指到来源需求

追溯矩阵的形态是把每一项需求沿生命周期连到实现它的任务与验证它的测试。这为 LDVH 的 `serves` 字段提供了外部定位：`serves` 就是该矩阵的第一列（工单→子目标），缺的是第二、三列的反查与呈现。

溯源：https://www.jamasoftware.com/requirements-management-guide/requirements-traceability/traceability-matrix/（Traceability Matrix 定义段）

## 未证实与缺口

- **未证实 1**：未找到把「目标树 + 二值终态 + 派生式进度」三者合一的开源实现。pi-goal 最接近，但其目标是单次运行型，与项目级常驻目标的级联、受控写入、Human Gate 语义不同构。故「组合形态无直接先例」这一判断仍成立。
- **缺口 1（medium）**：Goal-oriented Requirements Engineering 一手原文未取得（托管站点维护中），KAOS 的目标细化与障碍分析未逐条核实，仅有检索摘要间接支撑。
- **缺口 2（medium）**：pi-goal 的实现细节只据其 README 陈述，未读其 `src/`；其「可检验验收条件」的机械核验强度未经代码核实。

## 建议

以下建议均为调研结论，**不是决定**；采纳与否由 Human 裁决。

1. **以目标树形态重建 25 号移除的「计划区」**，并把「卡住分支必须显式浮出」写成设计要求（不是可选项）。依据 F1。创建判断：属 25 号受控修订，须 Human 决定，建议在确定形态后单独建单。
2. **把「二值验收」与「连续进度」分权，而非二选一**：完成度只用于显示、由各 SG 名下工单状态机械派生；「算不算完成」仍是二值且有证据、只能由 Human 宣布。依据 F3、F4。创建判断：可直接作为 30 号修订的设计输入。
3. **`serves` 改为必填，并补 SG→工单反查聚合**。依据 F5，且当前 6/36 工单未填 `serves` 是 F1 所述「丢失卡住分支」的现成实例。创建判断：实现改动，小范围，建议直接执行或建单由 Human 决定。
4. **把「可检验」落成可执行核验动作**（如子目标的达成材料给出可跑的检查），而非纯文字承诺。依据 F2。创建判断：属 30 号 §8.2 判据的强化，须 Human 决定是否加严。

## 后续分流

- 建议 2 作为设计输入保留在本对象，供 30 号下次修订引用。
