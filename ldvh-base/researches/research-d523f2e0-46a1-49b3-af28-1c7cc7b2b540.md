## 研究问题

dsh-mnemon、dsh-auto-memory、dsh-routed-subagent、dsh-custom-subagents 四个参考项目在「后台/闲时执行体的上下文供给」上的实现形态是什么——provider 选择（spawn/fork）、读取取舍落点（prompt 构造/seed 构造/surface 有界读取）、降级与防护——对 LDVH specs/04 §8.4 执行体上下文继承条款的修订提供哪些可回指证据？

背景展开：问题起源于 LDVH 自身机制的宿主实测故障——specs/04 §8.4 闲置摩擦发现的执行体经 fork 派生，继承主控会话全部历史；会话增长至约 1.1 万事件后执行体以 error/max-tokens 失败（pending-queue 两条 max-tokens 条目 6083188d/f644bb18 为在档证据），而机制判断实际只需约 6,000 字符的增量窗口材料。规范边界核查（04 §8.4）确认条款要求的是「输入侧继承」而非「全量复制」，故存在修订空间；修订方向需要参照系证据支撑，是为本调研。

## 输入与边界

- **观察对象与版本**：四个本地克隆，commit 钉死——dsh-mnemon@7bd96593、dsh-auto-memory@243dee1、dsh-routed-subagent@1838fca、dsh-custom-subagents@8725328；与各自 GitHub origin 对应，溯源锚点按钉死 commit 的 blob URL 给出。
- **方法**：四处关键实现源码精读（mnemon 的 reviewCheckpoint 与 review 决策层、auto-memory 的 runSubagent 与两处 prompt 构造、routed-subagent 的 makeProvider 与注册段、custom-subagents 的 delegate 开关），与既有事实库调研（research-fa0cff9c F19–F21、research-f8b248ce F6）交叉核对；宿主侧事实来自本会话对 DSH 0.2.0-rc.2 的实证回放。
- **对照基线（内部实证，非外部来源，不作发现单元）**：宿主 fork provider 的 seed 为原始日志前缀全量（completedTurnPrefix 取到最后一个 turn/end），SubagentStartRequest 无 seed 参数；子代理 Session 重建时重放 compaction 折叠（实测 24 次 replace 重放）；三个失败会话回放实测 10,742–11,336 事件 → 820–1,049 surface 节点 / 37.4–46.0 万字符（tool/result 占约 25–27 万）——折叠被继承但取舍粒度是主控视角，非执行体视角。
- **与既有调研的分工**：research-cf315013（闲时机制可吸收形态）覆盖触发/调度/写入边界/失败处置四面，不覆盖执行体上下文供给；research-fa0cff9c（mnemon）F20 已载 provider 可选 fork/spawn 之事实，但未展开 spawn 路径材料构造器与跨项目横切对照；research-f8b248ce（auto-memory）覆盖其记忆分层而非子代理上下文供给。本调研聚焦「执行体上下文供给形态」横切面，问题域相邻而不重复。
- **不覆盖**：参考项目的 Web 呈现层与记忆语义细节；mnemon fork 路径的生产运行数据（无公开来源）；LDVH 侧适配性原型验证（列入缺口）。

## 关键发现

### mnemon idle review 默认 spawn、fork 为显式可选项且启动前可回退，spawn 路径材料由专门有界构造器供给

观察：mnemon 的 DEFAULT_IDLE_REVIEW 配置为 `provider: 'spawn'`、`fallback: 'spawn'`、`maxContextChars: 24_000`、`minIntervalMs: 300_000`、`maxPerSession: 20`、`maxTokens: 4_096`；`review()` 决策层在用户显式配置 fork 时先尝试取 fork provider，不可用则按 fallback 回退 spawn 或直接 skip；prompt 按路径分叉——fork 路径仅一句话「Review the inherited completed checkpoint now.」，spawn 路径调用 reviewCheckpoint 构造有界材料，且 persona 文本同步把 inherited 替换为 supplied bounded，防止执行体对材料来源产生错误预期。其 v0.5.10 release note 把设计声明写成用户可见文本：「默认 spawn 路径限制上下文大小；fork 需要显式选择，可在子 Agent 启动前回退或跳过。」

价值判断：这是与 LDVH §8.4 机制最同构的参照（同为 idle 触发的后台审阅执行体），它证明「默认有界、继承可选、启动前可回退」是一个被生产采用且对用户明示的完整设计——§8.4 修订若转向有界交付，降级与回退语义有现成设计可参照，不必新造。

溯源：https://github.com/omdsh-dev/dsh-mnemon/blob/7bd96593/src/host/protocol.ts（200-211 DEFAULT_IDLE_REVIEW）；https://github.com/omdsh-dev/dsh-mnemon/blob/7bd96593/src/host/subagent.ts（1347-1363 review 决策层 fork/spawn 分叉与回退）

### mnemon 有界构造器读 session.surface.nodes 而非原始日志，24,000 字符预算整消息准入，折叠与回退痕迹进不了材料

观察：reviewCheckpoint 函数（全文 46 行）从 `session.surface.nodes` 取当前公开表面——代码注释明写理由「Use only the current public surface, so rewound or compacted evidence cannot reappear」；以最近一条 turn/end 定位检查点，倒序遍历最后 128 个 surface 节点，只取 user/message、assistant/message、tool/result 三类事件的文本，按 24,000 字符预算整条准入、预算不足整条跳过——注释明写「never fragments that could drop a user negation or present half a tool result as complete」。

价值判断：这条给出了「读取取舍」的最优实现点——取舍不在 fork/spawn 选择也不在 seed 构造，而在「读 surface 还是读 log」。LDVH 宿主实测表明 fork seed（原始日志）在子代理重建时重放折叠，殊途同归但代价是全量复制加全量重放；mnemon 一开始就只读折叠后表面，被 shadow 的历史物理上进不了材料。其 46 行构造器可直接作为 §8.4「机械交付窗口材料」构造器的实现模板，且天然满足「材料边界可判」（材料即 prompt 本身）。

溯源：https://github.com/omdsh-dev/dsh-mnemon/blob/7bd96593/src/host/review-checkpoint.ts（17-45 构造器全文与两条注释）

### dsh-auto-memory 后台执行体一律 spawn，取舍在 prompt 构造侧按字符截断，parent 仅承载路由与策略继承

观察：runSubagent 全文（110 行）默认 `providerName = 'spawn'`，仅当 spawn 未注册时才取已注册列表首项；prompt 由调用方构造精确材料——记忆沉淀任务只带本轮用户/助手文本各 3,000 字符切片加日志尾部，折叠任务 truncateTail 至 6,000 字符；parent 照常传入但仅供 captureDelegatedPolicyOverrides 读其 ctx/session 做路由与策略继承，上下文一概不带。配套生产防护：并发闸门（在飞 ≥3 拒绝新 spawn）、UNKNOWN_MODEL 等配置性错误熔断 30 分钟、结果 withTimeout 兜底、自有子代理 WeakSet 登记防套娃。

价值判断：这是 Human 此前在同构机制对照中指定过的参考项目（workcase-59b4899d 对照参考实现段），其水位概念与 LDVH §8.4 水位段同源；它证明「spawn + prompt 精确材料」形态在同构 idle 场景可持续生产运行，且其防护四件（闸门/熔断/超时/防套娃）是 LDVH 执行体侧可直接吸收的工程纪律——无论 §8.4 修订与否，防护件均适用。

溯源：https://github.com/Aik358/dsh-auto-memory/blob/243dee1/lib/index.js（4723-4832 runSubagent 全文含 4747 行 providerName='spawn'；5090-5100 沉淀材料 3000 字符切片；3341-3356 折叠 truncateTail 6000）

### dsh-routed-subagent 证明插件可注册自建 provider 并自决 seed，官方包经宿主解析无需自装

观察：该插件经 `ctx.subagents.registerProvider` 注册三个自建 provider（含 spawn 形态与 fork 形态各一），注册前以 `getProvider` 查重跳过（注册表是进程单例，防止第二挂载点抛 DUPLICATE_PROVIDER）；`start()` 内自决 seed——fork 形态取 completedTurnPrefix(parent)，spawn 形态 seed 为空；驱动层是文件头声明的「faithful re-implementation of startInProcessRun」，只改 child setup 挂载点，策略继承/descriptor/取消/结果读取语义全保留。其 package.json 的 dependencies 为空、@deepseek-ai/* 全部走 peerDependencies——文件头注释明写官方包「ARE resolvable from preset-local rows (the preset loader resolves bare specifiers against the harness install)」。

价值判断：这是路径 A（LDVH 插件自建收窄 seed 的 provider）的工作区内先例——registerProvider 用法、seed 自决位置、重复注册防护、依赖解析方式四件事全部有现成答案；此前评估中「driver 包不在 plugin/node_modules」的依赖风险被先例证伪（宿主解析裸导入，无需自装）。路径 A 的工程风险从「推断可行」升级为「已存在同形态工程」。

溯源：https://github.com/bpc-oss/dsh-routed-subagent/blob/1838fca/lib/index.js（15-25 重实现声明与宿主解析注释；260-346 makeProvider 与 seed 自决；357-366 查重注册）

### dsh-custom-subagents 把 fork 与 spawn 做成任务级配置开关，全量继承是显式可选项而非默认形态

观察：delegate.js 中按任务快照选择 provider——`snapshot.context === 'inherit' ? 'fork' : 'spawn'`；即「是否继承父会话全部上下文」是 per-task 显式配置项，默认不继承。

价值判断：加上 mnemon（fork 需显式 opt-in）与 auto-memory（无 fork 路径），四个参考项目中没有一个让后台执行体默认背负全量历史——「继承全文」在参照系中始终是按需选择的特例。LDVH §8.4 当前把 fork 硬性规定为唯一合法形态（selectContextInheritingProvider 拒绝 spawn），在参照系中是少数派；修订为「按任务语义选择供给形态」与生态惯例一致，且不会失去 fork 作为可选项的能力。

溯源：https://github.com/ktdhhc/dsh-custom-subagents/blob/8725328/lib/delegate.js（409-410 任务级 provider 开关）

## 未证实与缺口

**未证实**：

1. 参考项目均为记忆域（摘要/沉淀语义），其「有界材料」形态对摩擦发现「逐字引证机械核对」语义的适配性未验证——mnemon 的 review 是记忆写回（允许概括改写），LDVH §8.4 要求执行体逐字引证交付材料且落地侧机械核对（04 §8.4 水位段），材料必须含可逐字命中的原文片段；摘要式材料形态是否满足该要求，四个参考均未提供证据。此项为 Human 明确提出的保留点（「我们要做的是反思摩擦，之后还有沉淀经验，和记忆整理，他们 2 个项目都是和记忆相关的，是否适合我们的反思摩擦、沉淀经验还不知道」）。
2. spawn 路径下跨窗口上下文对「系统性阻碍」判断的充分性未实证——§8.4 要求判断「某现象是否构成系统性阻碍」，可能需超出单次窗口的历史脉络；mnemon 以 maxPerSession=20 的多次评审分摊该需求，LDVH 的候选账本（既有摩擦账目随材料交付）是否等价，未经任何运行验证。

**缺口**：

1. （medium）有界材料形态对摩擦发现语义的适配性原型验证未做：窗口材料+候选账本能否支撑执行体的系统性判断，需最小原型实证；阻塞「有界交付」具体形态的落地决策，不阻塞「是否修订」的方向判断。
2. （low）mnemon fork 路径的实际使用频率与失败率无公开数据，「fork 可选项」在生产中的真实权重未知。

## 建议

1. §8.4 修订方向获得参照系一致支持：四个参考项目无一让后台执行体默认背负全量历史（F1/F3/F5），「有界材料交付」是可成立的替代形态；fork 保留为显式可选项即可不损失能力。
2. 若修订为有界交付，材料构造器参照 mnemon reviewCheckpoint 的「读 surface.nodes + 字符预算 + 整消息准入」三件套（F2）；但修订文本须显式处理适配差异——摩擦发现的材料须含可逐字命中的原文片段以支持引证机械核对，记忆域摘要形态不直接满足（未证实项 1），条款应规定「材料含原文窗口」而非「材料为摘要」。
3. 路径 A（自建收窄 provider）作为规范不修订时的备选保留：工程可行性有 routed-subagent 先例（F4），但它是参照系中的少数路线，且 seed 收窄语义与「继承」条款的相容性仍需论证。
4. 落地任何形态前先做适配性最小原型（缺口 1）：以真实失败会话的窗口材料喂给 spawn 执行体，验证摩擦发现三态产出与逐字引证是否成立——这是把未证实项 1/2 转为实证的最小成本路径。
5. auto-memory 的执行体防护四件（并发闸门/熔断/超时/防套娃，F3）与 §8.4 修订方向无关、均建议吸收，可随修订一并列入或直接进实现层工单。
