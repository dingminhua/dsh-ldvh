## 研究问题

闲时处理机制（宿主在主控之外、回合结束或会话空闲时发起的辅助任务）在业界记忆系统中的实现形态与失效模式是什么，对 LDVH 记忆存取系统 §10 空闲维护与反思有哪些可吸收点？

## 输入与边界

- **边界一（Human 裁定，2026-11 会话）**：Letta 官方 `AGENTS.md:23-31` 明文禁止把已退役的 V1 server（archive 分支）用于跨系统比较。据此，`sleeptime` 机制的源码级分析（触发阈值 `turns_counter % frequency`、消息水位在发起前推进、失败仅记 Run 等）**全部排除在本研究之外**，不作为任何结论的依据。本研究只采信现行 `letta-ai/letta-code`（TypeScript harness）的可核验实现。
- **边界二**：dsh-mnemon 与 Hindsight 的闲时机制不重复调研——其结论已在既有调研对象中登记（`research-fa0cff9c` dsh-mnemon 三层记忆与工具信封；`research-4bb40d6b` Hindsight 银行隔离与归纳式信念）。本研究只提取其中与 LDVH 空闲维护直接相关、且原文可核的部分，并明确指回既有对象。
- **边界三**：不评价任何来源的产品优劣，只登记「对 LDVH 可吸收的机制」与「作为反例的失效模式」。

## 关键发现

### F1 记忆改动以 commit 为生效点，且「本轮不生效」被写进 agent 自身提示词

现行 Letta 的记忆是每个 agent 一个 git 仓库（`~/.letta/agents/{agentId}/memory/`，`src/agent/memory-git.ts:89-97`），系统提示词从 **git HEAD** 编译而非工作区（`src/backend/local/system-prompt-compilation.ts:90-110`）。其 agent 提示词逐字写道（`src/agent/prompts/letta_root_memfs.md:52-53,55`）：

> The MemFS is a git-backed projection of your memory. Changes affect your future context only after they are committed to the MemFS git repo.
> **Editing memory does NOT change your behavior in the current turn.** …… a memory edit is applied on a later recompile …… never instantly.

**对 LDVH 的价值**：这条同时解决两个问题。其一，agent 声称「我记住了」与系统提示词真的改变之间，隔着一个可审计的 commit，消除了不可验证性。其二，它用一句提示词声明取代了一整套审批交互，成本极低。LDVH 32 章 §8.5 规定「git 层写入须 Human 拍板」，其门位正是 commit；本发现提示该门位可以附带一条**声明式边界**（写入不在当前轮生效），而不必只依赖门本身。

溯源：https://github.com/letta-ai/letta-code（src/agent/prompts/letta_root_memfs.md 第 50-58 行；src/backend/local/system-prompt-compilation.ts 第 90-110 行）

### F2 跨 agent 记忆隔离的旧实现（字符串扫描）被官方承认可绕过并删除，改为 fail-closed 内核沙箱

`src/permissions/cross-agent-guard.ts:12` 的注释逐字自承：

> token/raw-command scanner is gone — it was bypassable by symlinks, command substitution, globbing, and subprocesses

取而代之的进程内 guard 声明其拒绝**不可被权限模式绕过**（同文件 `:22`：Its deny is unbypassable by modes and permission rules），而真正的执行边界是内核沙箱；沙箱不可用时启动器直接抛错而非降级（`src/permissions/memory-confinement-launcher.ts:64-70`：Memory confinement requires a non-empty launcher / requires MEMORY_DIR or LETTA_MEMORY_DIR）。

**对 LDVH 的价值**：这是对根方案「宿主闲置发起的辅助任务由机械校验保障」的一次真实校准。**路径或命令的字符串匹配不构成机械校验保障**——它可被 symlink、命令替换、glob、子进程绕过。真正的机械保障必须是执行边界（沙箱 / 真实路径判定 / 不可绕过的 guard），而不是输入文本的形状检查。LDVH 04 §8 与 32 §10.1 声称的机械校验应按此口径自检：凡依赖路径字符串比较的校验项，须确认其是否可被链接绕过。

溯源：https://github.com/letta-ai/letta-code（src/permissions/cross-agent-guard.ts 第 12 行与第 22 行；src/permissions/memory-confinement-launcher.ts 第 60-70 行）

### F3 后台记忆维护任务在私有 git worktree 中执行，完成后合并回主记忆仓

现行 Letta 的 memory-worker 使用私有 worktree 改动、完成后合并并重编译系统提示词（`src/agent/subagents/memory-worker.ts:1-14`，经 `createReflectionMemoryWorktree` / `integrateMemoryWorkerWorktree`）。同一机制在 compaction 事件与回合完成时均可能被触发。

**对 LDVH 的价值**：这是对 LDVH 规范的一个**具体缺口提示**。LDVH 32 §10 规定了三个空闲代理的职责与纪律，但**未规定并发写隔离**——若评审代理、容量维护代理在同一检查点被同时发起、且都可能写同一记忆条目，则冲突处置无规范依据。Letta 的私有 worktree + 合并是一条候选解法（另一条是串行化）。这是待查证的缺口，不是已定的方案。

溯源：https://github.com/letta-ai/letta-code（src/agent/subagents/memory-worker.ts 第 1-14 行）

### F4 记忆归属解析失败即跳过，宁可漏记不散布（Hindsight）

Hindsight 的 DSH 集成按工作区根解析记忆银行；身份推导三级顺序（显式配置 → 路径映射 → 默认模板）任一级失败时，插件**不退回兜底银行，而是直接跳过该会话的写回**（既有调研 `research-4bb40d6b` F10）。其设计理由是：把记忆写进一个不确定的银行，等于把内容散布到错误的作用域，而这种污染比漏记更难修复。同调研 F8：子代理会话被显式排除在写回之外，理由是子代理对话不是主会话的记忆。

**对 LDVH 的价值**：两条纪律——(a) **作用域不确定性优先于召回率**：归属不明就不写，不猜、不兜底；(b) **委派产生的对话不自动成为被委派方的记忆，记忆归属跟随责任归属**，后者与 00 §5「委派不转责」天然同构，且不依赖技术栈。这两条对 LDVH 记忆写入路径（32 章 §8.5 拍板门之前）都是可直接采纳的前置过滤。

溯源：https://github.com/vectorize-io/hindsight（F10 银行解析失败即跳过写回；F8 子代理会话排除写回——两条均已在既有调研 research-4bb40d6b 逐字溯源）

### F5 破坏性操作移出自动化链路，只留给显式 Human 意图（dsh-mnemon）

dsh-mnemon 的 worker 工具白名单按类型硬编码（读类 3、写类 9、评审 3、文档归档 4 等），且归档需 `documents.archive` 与 `memory-spaces.write` 双能力、子代理直接调用被拒（既有调研 `research-fa0cff9c` F12）。其做法是把 forget（删除）移出自主 worker 白名单——破坏性动作从自动化链路中剔除，只保留给显式 Human 意图。

**对 LDVH 的价值**：这是 04 §8.2「辅助机制不得产生需 Human 决定的结论」在**工具面**的落地样板。LDVH 现行以流程约束（不得做什么）表达，Letta/mnemon 的补充思路是从能力面收窄（不给它这个工具），两者叠加比任一单独更强。与 F2 一致：能力面限制是机械的，流程约束是语义的，后者可被误解而前者不可。

溯源：https://github.com/Aik358/dsh-mnemon（F12 封闭信封与按 worker 类型硬编码的工具白名单，forget 移出自主 worker 白名单——已在既有调研 research-fa0cff9c 逐字溯源）

## 未证实与缺口

1. **F1 与 LDVH 现有 32 §8.5「git 层写入须 Human 拍板」的相容性未验证**：Letta 的 commit 门由 agent 自己闭合，LDVH 的门由 Human 把关。若叠加声明式边界，是否会让 Human 复核时的「当前轮是否已受影响」判断变得模糊——未查证。
2. **F3 的并发缺口是否真实存在于 LDVH 运行时**：LDVH 32 §10.2 说三任务「共用触发点、按预算轮换」，这可能已隐含串行化。若「轮换」即串行，则 F3 不是缺口而是重复。须读运行时实现确认，本研究未读代码。
3. **Hindsight F10「宁可漏记」的代价未被量化**：漏记率与污染率的实际权衡没有一手数据，采纳时可能需要 LDVH 侧自定阈值。
4. **Letta 当前实现的 reflection 触发条件未完整核实**：本研究只核了 memory-worker 的执行形态，未穷举其触发源清单（如 compaction-event 之外是否还有别的锚点）。

## 建议

1. **可直接采纳（纪律层，成本低）**：F4 的两条（作用域不明不写、委派会话不自动落为被委派方记忆）可作为 32 章写入路径的前置过滤条款；F1 的「本轮不生效」声明可作为 §8.5 拍板门的附带说明。
2. **须先查证再动规范**：F3 的并发写缺口（缺口 2）应先读 LDVH 运行时确认，再决定是否需要新增隔离条款。
3. **须自检**：F2 对全项目机械校验项做一次排查——凡以路径字符串比较实现的安全判定，确认其是否可被 symlink 绕过。此项范围可能超出记忆系统，涉及 06 机械校验与插件能力面。
4. **登记为待查方向而非已定方案**：F3、F4(a) 的采纳应各自走 Spark 或工单，本研究不代行裁定。

## 后续分流

- F1 声明式边界 → 可作 Spark 候选（低成本纪律增强）。
- F2 机械校验口径自检 → 范围较大，宜作独立工单；**须先由 Human 判定是否纳入范围**（00 §4 根决定清单）。
- F3 并发写隔离 → Spark 候选（先查证运行时）。
- F4/F5 写入前置过滤 → Spark 候选（纪律明确，改动面小）。
