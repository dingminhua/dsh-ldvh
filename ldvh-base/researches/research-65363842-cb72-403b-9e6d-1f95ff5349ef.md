# DSH 0.1.2-rc.1 → 0.1.5-alpha.1 前瞻兼容性审计（LDVH 消费面）

## 研究问题

DSH 0.1.2-rc.1（运行版）→ 0.1.5-alpha.1（源码迁出 HEAD 5dda764ed3）的差量中，LDVH 消费面的 API 增删改与行为变化：现行插件依赖是否存续；第 0-1 波计划建造的入口（invariants/文件观察/会话存储/结构化问询/授权/子代理编排）在 0.1.5 的形态如何、有无移除或变形。

背景：LDVH 插件运行在 DSH 0.1.2-rc.1 上，上游已演进到 0.1.5-alpha.1（2026-09-08 release merge）。Human 2026-09-10 裁定：统一升级前不提前升级、但要先审计差异、避免建造未来已不支持的功能。

## 输入与边界

- 旧侧基准：git tag `dsh-v0.1.2-rc.1`（= 运行中的 DSH Desktop 版本，运行 App 内 @deepseek-ai/dsh 包版本号 0.1.2-rc.1 与之相同）
- 新侧基准：HEAD 5dda764ed3（0.1.5-alpha.1 release merge）
- 方法：三子代理并行差量审计（A 工具面+事件面；B 交互面+三入口；C 子代理+Web 连接面），主控对每份报告的关键判定做 file:line 级抽查；差量 1207 提交、按 LDVH 实际消费面切片
- 调研会话：rs-mttx5y18-h376ly（create + 3 轮 submit-round + check-delivery 通过 + converged round 4/4；finalize 因插件已知缺陷不可用，不影响证据闭环）
- 边界：0.1.5-alpha.1 仍在演进，结论钉死在该 commit；统一升级时以届时目标版本重跑对照法

## 关键发现

### F1 工具面与事件面零破坏

工具注册（ctx.tools.register/defineTool）、guard 单调守卫（tools/pre-execute 之后求值、只能拒不能放行）、restrict 作用域收敛在 0.1.5 签名与执行序不变。LDVH 监听的宿主事件（agent/created、agent/session-start、agent/pre-step、agent/turn-stopping、system-prompt/assemble、session/event）载荷与监听模式完全向后兼容。

对 LDVH 的价值判断：现行运行面无任何「今天在用、明天没了」的红灯——第 0 波回填 08 号时这五处「待核验」可直接转正。

溯源：https://github.com/deepseek-ai/deepseek-harness（packages/core/tools/src/index.ts@HEAD guard 定义；packages/core/agent-loop/src/agent.ts + packages/extensions/tool-cordis/src/api-catalog.ts 事件登记；对照 tag dsh-v0.1.2-rc.1）

### F2 tools/* 四标签是 LDVH 自家 ActivityLog 而非宿主事件

tools/registered、tools/registration-defect、tools/registration-failed、tools/unregistered 出自 plugin/lib/lifecycle.js 的 activity.record 调用，不在 Cordis 事件系统内，不受宿主版本影响。官方对应事件为 tools/change（两版签名相同，LDVH 未消费）。

对 LDVH 的价值判断：纠正了主控此前「十事件」的盘点口径——真实宿主事件面是六个；tools/* 四标签随 ActivityLog 自行稳定，且 tools/change 是未来挂载候选。

溯源：https://github.com/dingminhua/dsh-ldvh（plugin/lib/lifecycle.js#L77-L105）

### F3 问询授权面三包零变更

user-questions、user-approval、tool-ask-user 三包 src 在 0.1.2-rc.1→0.1.5 零 diff：ctx.userQuestions.ask(request) 签名、CALLER_NOT_LIVE/DELEGATED_CALLER 调用者限制、approval/policy 'ask'|'never' 原样。唯一交互面签名变是 commands 的 input.images→input.attachments 更名，LDVH commands 注册面为空占位，零触及。

对 LDVH 的价值判断：Human Gate 结构化问询（08 §5.5 交互面）可安全建造——第 0 波点 5 的核验结论落定。

溯源：https://github.com/deepseek-ai/deepseek-harness（packages/interaction/ 三包 src git diff --stat 为空，主控复验；commands/src/types.ts diff）

### F4 不变量入口字节级存续

ctx.invariants.register(packageName, installer) 的 src/index.ts 两版 SHA-256 完全一致（实测前缀 16c5dafe），官方 permission-presets 以 inject:['invariants'] 随 app 消费。

对 LDVH 的价值判断：第 0 波点 7（运行时不变量三时点断言：装载完成/受控写入前/交还前）可安全建造，且在两版间零兼容成本——超预期的稳定。

溯源：https://github.com/deepseek-ai/deepseek-harness（packages/runtime-diagnostics/invariants/src/index.ts 双版 shasum 实测）

### F5 文件观察/CAS 承载两版零变

宿主无文件 watch 服务（如实报告），但 LDVH CAS 所需承载全部稳定：writeText 的 FsWriteIntent.replaceIfVersion 版本守卫、editText version guard、fs/observed 观察、fs/write-intent 与 fs/edit-intent 瀑布——签名两版零变化。

对 LDVH 的价值判断：第 0 波点 8 的核验结论落定——宿主承载为守卫式写保护（非 watcher），LDVH 受控写入可安全挂载。

溯源：https://github.com/deepseek-ai/deepseek-harness（packages/fs/fs/src/types.ts#L119-L125 主控直读）

### F6 session-persistence 破坏性重构（最大预警）

0.1.2 服务直调式（append/load/inspect/borrowSession/readFrom/listSnapshots）在 0.1.5 整体移除，替换为 handle 所有权式（create(header)→SessionHandle、open(id,'read'|'write')、flush、stat、list；单写者）。任何基于旧会话写入 API 的第三方代码升级时编译级失效。

对 LDVH 的价值判断：LDVH 当前未直接调用 session-persistence（经宿主内部路径消费），但若第 0 波点 9 或后续波次需要写会话存储，绝不能按 0.1.2 API 建造——这正是本审计立项要抓的那类坑。

溯源：https://github.com/deepseek-ai/deepseek-harness（packages/session/session-persistence/src/index.ts#L130-L213@HEAD vs dsh-v0.1.2-rc.1:.../coordinator.ts 主控双版对照）

### F7 0.1.5 未知事件类型默认拒绝

validateStoredEvents 对 KNOWN_SESSION_EVENT_TYPES 之外的类型抛 SessionFormatUnsupportedError，唯一逃生口 ignorable:true（storage-contract.ts:59-78，注释原话 "Both newer vocabularies and retired pre-release shapes refuse here; this build ships no migration"）。

对 LDVH 的价值判断：Output Envelope 若以自定义事件写宿主事件流将撞此墙；推荐方案为 LDVH 自持久化、宿主侧只投影——与 02 §5.4「Envelope 载体属于实现层运行状态」的既有区分同构，把升级耦合面缩到最小。

溯源：https://github.com/deepseek-ai/deepseek-harness（packages/session/session-persistence/src/storage-contract.ts#L59-L78 主控直读）

### F8 WorkCase 编排依赖全部存续且多为增强

spawn/fork 双 provider、one-shot/continuable 二分、send_message 相邻通信、interrupt 任意深度祖先中断、子代理 approval 钉死 never、attempt/冷恢复全部在位；90 文件变更实质是 continuation 拆分为 activation+inbox 的健壮性重构，公开契约不变。新能力吸收候选：delivery 'steer'|'queue' 投递粒度——恰对位 WorkCase 编排「运行中转向 vs 排队新回合」控制需求。

对 LDVH 的价值判断：第 1 波 WorkCase 编排的宿主依赖面全绿，且 0.1.5 的 delivery 参数是原生新能力吸收候选。

溯源：https://github.com/deepseek-ai/deepseek-harness（packages/subagent/subagent/src/{index,continuation,child-agent}.ts + subagent-spawn-in-process/subagent-fork-in-process，主控抽查 deliverSubagentPrompt@255-278）

### F9 移除清单定案

registerContinuableSetup 已移除（dsh-sub-cli 三通道 fail-loud 已适配）；conversation.details.tool slot 移除（LDVH 仅占 settings.plugin.item 与 conversation.view，不受影响）；宿主内部变更（tool/code-dispatch→tool/ptc-dispatch、子调用 ID 格式、deployment:persona 拆分 prefix/suffix、session 格式 0→3）均不触及 LDVH 消费面。

对 LDVH 的价值判断：移除项逐一定案——除 registerContinuableSetup（已适配）外，对 LDVH 均无影响。

溯源：https://github.com/deepseek-ai/deepseek-harness（packages 全树 grep registerContinuableSetup 零命中；ui-chat slots diff）

### F10 插件测试面 393/393 全绿互证

LDVH 插件现行测试面 393/393 全绿（主控在 dsh-ldvh/plugin 实测 node --test，fail 0；396 个 test() 调用 − 3 个条件分支未满足 = 393 运行）。

对 LDVH 的价值判断：现行运行面在当前树无任何破坏，与三面审计「零红灯」结论互证。

溯源：https://github.com/dingminhua/dsh-ldvh（plugin/test/*.test.mjs，node --test 实测）
