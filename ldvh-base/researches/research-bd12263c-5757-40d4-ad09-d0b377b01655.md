## 关键发现

### F1 dsh-agency-agents 是社区维护的 DSH 专家召唤插件：321 名双语专家覆盖 22 个分类，含 5 个内置专家团，主插件 Apache-2.0、上游 persona MIT

观察事实：package.json 声明包名 @michengai/dsh-agency-agents v1.0.5，描述「DSH Agency Agents — 为 DeepSeek Harness 提供 321 名可召唤的专业智能体」；README.zh-CN.md 首部注明「社区维护的 DeepSeek Harness（DSH）插件，并非 DeepSeek AI 官方产品」。专家资产按语言分两个目录：assets/agency-agents（英文）与 assets/agency-agents-zh（中文）各 321 个 .md persona 文件（目录内另有 UPSTREAM.md/LICENSE 非专家文件），22 个分区目录（engineering 68、specialized 68、marketing 43、game-development 21、gis 13、security 12 等）。五个内置专家团定义在 src/team-contract.ts BUILTIN_TEAMS：产品方案评审团、技术方案评审团、内容选题策划团、数据分析诊断团、专题研究专家团，各 3 名成员分工并配交付物与任务示例。许可证双层：根目录 LICENSE 为 Apache-2.0（源码、构建脚本、文档），assets/agency-agents/LICENSE 为 MIT（上游 persona 继续沿用）。工具面六个：个人专家三件套 list_experts/summon_expert/summon_experts 加专家团三件套 list_expert_teams/get_expert_team/summon_expert_team。

对 LDVH 的价值判断：这是 dsh-ldvh 在 DSH 桌面生态中的直接邻居与同类（同为 DSH 插件、同把大量 md 文档作为一等资产随包发布）；其「persona 文件目录 = 插件一等资产」的形态与 LDVH 的「specs/ 与 ldvh-base/ 事实源」同构，而其双层许可（自研工程 Apache-2.0 + 上游内容保留原 MIT）正是引入外部内容资产时的授权边界样板。

溯源：https://github.com/MichengAI/dsh-agency-agents/blob/main/package.json（package.json name/description/files 节）

### F2 专家召唤走宿主 subagents 的 spawn/fork provider 加 persona capability：子代理只 shadow persona 段、保留普通 DSH 工具集，成员不得再召唤成员

观察事实：src/index.ts 模块头注释明确机制：「A summoned expert does NOT replace the parent's persona: the child shadows only its own deployment:persona section (the persona capability on the in-process spawn/fork providers), so it runs with the expert's identity plus the ordinary DSH tool set」；插件的 inject 列表为 ['tools', 'subagents', 'systemPrompt', 'settings', 'webServer']，即 subagent registry 及 spawn/fork 后端属宿主侧共享，本插件只消费。工程边界的两个防御：{{...}} 插值冲突在 persona 文本中插入零宽空格规避（保持视觉不变）；README 与 cordis.example.yml 均声明「专家不会继续召唤其他专家」。批量召唤上限 8 名、并发 4、单任务 8000 Unicode 码点（SUMMON_EXPERTS_MAX/SUMMON_TASK_MAX_CHARS 常量）。

对 LDVH 的价值判断：这是 LDVH「委派不转责」原则（00 §5）在插件层的对应物——子代理拿到完整 persona 身份但只是消费者，成员递归扩团被工具门禁机械拒绝（见 F4），责任保留在主会话；其常数化限额（8/4/8000）是把防滥用边界写进代码而非文档的做法，与 LDVH 机械锚点取向同源。

溯源：https://github.com/MichengAI/dsh-agency-agents/blob/main/src/index.ts（src/index.ts 模块头 docstring 与 export const inject 节）

### F3 上游 persona 以快照加同步基线治理：UPSTREAM.md 记录来源 commit、授权边界与更新方式三要素，更新基线后须跑 test/build/verify

### F4 专家团引擎对宿主能力做三态降级（unsupported/disabled/enabled），能力探测从宿主启动入口解析且显式 maxDepth 强制普通模式，原生队友被宿主工具门禁禁止再扩团

观察事实：src/team-engine.ts detectTeamEngine 的判定序：服务不存在且宿主未装 → unsupported（普通子代理，不提示开启不存在的能力）；服务不兼容或会话工具未就绪 → disabled（建议开启，仍可普通调用）；都就绪但配置了 maxDepth → 仍用普通模式以保留深度限制（原生 Agent Team 不支持该约束）；全部就绪 → native。能力探测 hostHasAgentTeam 从 process.argv[1] 宿主启动入口 resolveHostModule 解析并进程内只探测一次，「避免插件自身依赖版本冒充宿主能力」。递归防线 blocksNativeDelegation：以 delegationTools 集合加成员名正则（agency-*-[0-9a-f]{10}）识别本插件原生队友并拒绝其再调用召唤类工具，「由宿主工具门禁强制执行」。README.zh-CN.md「自动选择协作模式」表以宿主状态三行呈现同一逻辑（不支持/支持未启用/均可用），并注明「原生模式任务启动确认不等于专家已经完成；创建中途失败不会自动切换模式重复执行」「队友默认沿用主会话的模型选择」。

对 LDVH 的价值判断：这是消费宿主实验性能力（0.1.7-rc Agent Teams）的消费者侧诚实范式，四个取向均与 LDVH 制度同向：（一）能力不存在时 fail-closed 降级而非硬失败；（二）探测锚定宿主真实入口而非自身依赖树（LDVH 机械锚点精神）；（三）显式约束与宿主能力冲突时让用户配置优先（反自作主张）；（四）「dispatch 仅表示启动，必须等待实际结论」（与 LDVH 验收纪律同构）。若 dsh-ldvh 插件未来消费宿主原生机制（如 Agent Teams 承接复核），这是现成的降级与门禁参照。

溯源：https://github.com/MichengAI/dsh-agency-agents/blob/main/src/team-engine.ts（src/team-engine.ts detectTeamEngine/hostHasAgentTeam/blocksNativeDelegation）

### F5 插件接入走 Cordis 三件：patch 双顶层行（主插件加 remote 路由）、Typert face:host 严格描述符（避免启动期扫描缓存漏服务）、设置存宿主 agency-agents 命名空间并靠 revision 仲裁并发

观察事实：cordis.patch.yml 声明两个 insert 顶层行——id: agency-agents 与 id: agency-agents-remote（后者「供 api-gateway 从根服务表发现 agencyAgents Remote 路由」，即 npm 包 exports 的 ./remote 入口）。src/remote.ts 以 @deepseek-ai/dsh-typert-protocol 的 TypertContribution 声明 face: 'host' 的严格描述符 TYPERT（package/schemas/model/invocations），注释说明「Gateway 优先读取它，避免启动期间的 SRC 扫描缓存遗漏后加载的外部插件服务」。设置存储：src/expert-library.ts 以 AGENCY_SETTINGS_NAMESPACE（settingsNamespaceCompat('agency-agents')）把内容与启用状态「在同一 namespace 原子持久化」，读写依赖宿主 dsh-settings 的 mutate(ops, expectedRevision) 修订号仲裁与 ExpertSettingsStore 接口。peer 依赖方面 README「宿主依赖与兼容性」节声明：dsh.client.inject 决定浏览器模块加载顺序、宿主模块图中不存在的项会跳过、关闭 auto-install-peers 的 Profile 会出现 unmet peer 提示，「不能据 npm 包树缺失直接判定运行失败」。

对 LDVH 的价值判断：五组接入实践每一组都可直接对照 specs/08 的关切：patch 双行形态回答「插件如何被 api-gateway 发现」；严格描述符回答「宿主扫描缓存与后加载插件的服务发现竞争」这一 dsh-ldvh 插件同样会遇到的时序问题；宿主命名空间 + revision 仲裁回答多会话并发写设置（LDVH 插件设置面同样存在）；peer 诚实声明回答「required peer 表达运行时契约而非安装期硬约束」的表述纪律。这组事实使 08 号规范相关判断不必再从零试探。

## 建议

以下建议均为调研结论，**不是决定**；采纳与否由 Human 与讨论/决定通道裁决。每条给出目标对象类型、预期目标、验收条件与创建/更新判断。

**建议一：将「上游快照三要素治理」记为 dsh-ldvh 引入外部内容资产时的对照范本，暂不对象化。**
目标对象类型：暂无对象（形态知识）；触发后为 06 号规范修订提案或 ADR。预期目标：dsh-ldvh 未来引入外部资产（persona、技能集、术语表、外部规范）时，来源/同步基线/验证命令三要素成为最低记账标准。验收条件：出现一次真实的外部资产引入时，能按三要素完整记账且可审计。创建判断：当前 dsh-ldvh 无外部内容资产引入计划，无需对象化；本对象作为参照留存，引入需求出现时回读本对象再决定载体。

**建议二：将「宿主能力三态降级 + 宿主入口探测」列为 dsh-ldvh 插件消费宿主原生机制时的工程纪律候选，以 Spark 承接。**
目标对象类型：Spark（候选）。预期目标：dsh-ldvh 插件若消费宿主实验能力（Agent Teams、原生编排等），采用 unsupported/disabled/enabled 三态降级与「从宿主启动入口探测、防自身依赖冒充」的纪律，避免硬失败与能力误判。验收条件：dsh-ldvh 插件出现首个宿主原生机制消费点时，其实现包含三态降级与入口探测，且不被自身依赖树误导。创建判断：当前 dsh-ldvh 插件（specs/08 边界内）尚无宿主原生机制消费点，建议以 Spark 悬置，触发信号为 08 号实施扩展到原生机制接入时。

**建议三：将「Typert face:host 严格描述符 + patch 双顶层行」作为 dsh-ldvh 插件 web/remote 服务注册的形态参照，并入 specs/08 相关实施判断。**
目标对象类型：WorkCase 或直接实施（若 08 号已有对应实施）。预期目标：dsh-ldvh 插件暴露 web 服务（F1 卡片、面板等）时，服务发现不依赖宿主启动期 SRC 扫描缓存，patch 层声明 remote 路由行。验收条件：宿主重启或插件后加载场景下服务仍可被 gateway 发现。创建判断：需先核对 specs/08 与 dsh-ldvh/plugin 现有实现是否已覆盖该形态；已覆盖则本条降为「已验证一致」记录，未覆盖则按 21 §6.3 判定是否建工单。

**建议四：将该插件的支持矩阵变化纳入宿主升级监测的外部信号源，无需对象化。**
目标对象类型：无（流程信号）。预期目标：每次 DSH 宿主 rc 升级时，把「该插件是否更新支持矩阵」作为接口面实质变化的旁证之一，与既有变更对照 Research（如 research-6c81daa2 模式）互补。验收条件：下一次宿主升级调研中实际引用该信号并说明其证据地位（旁证而非权威）。创建判断：无需建对象；写法上注意它只是消费者侧信号，不替代源码级对照。

**建议五：明确不吸收专家名册与专家团业务语义进 LDVH 事实模型。**
目标对象类型：无（边界结论）。预期目标：防止后续把「专家 persona 库」「专家团分工」误当作 LDVH 应吸收的机制。理由：专家召唤是宿主 subagents/persona 能力的消费者实现，其权威在宿主；LDVH 已有自己的委派与复核制度（specs/32 工单执行复核、05 号 CLI 服务），引入第二套专家语义会制造双权威。验收条件：后续任何讨论中引用本对象时，F2/F4 的定位（宿主能力的消费者）不被改写为「LDVH 应自建」。创建判断：以本对象正文承载该边界结论即可，无需对象化。
