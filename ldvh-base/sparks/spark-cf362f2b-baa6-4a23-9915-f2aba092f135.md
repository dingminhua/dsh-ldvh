# 规范每回合注入的精简路径

## 当前理解

现状：规范目录行独立成行、每回合注入（约 725 字符/回合），保证「每回合在场」与「查阅时机判断材料」；代价是永久每回合开销与长会话累积。已知：压缩/rewind 无权威检测信号；「标题必在、摘录可降级」有先例可迁移到行粒度；两句定位有 27 §8 契约，压缩面限于是否每回合带摘录；把关请示块与引导层是比目录行更大的消费项，精简须先看全账。判据：压缩不得破两条保证且须带恢复条件。

**2026-11-21 认知层收敛（Human 主导，均未落实现/未改代码）**：

- **注入面盘点（不止四块）**：实际进上下文至少 7 类、走 3 条通道——systemPrompt 引导段（2153/4096 字符，有漂移检测）、systemPrompt 工具定义（20+ ldvh_* 工具、34 条长摘要约 9800 字符，最大块却未计入任何预算）、消息行（管辖判定 notice／双源召回候选／事实规范目录约 725 字符／把关请示开关块）、子代理会话（删引导段但继承工具集）。计量口径不统一：引导按 UTF-16 字符、recall 按 10–50KB 字节档、工具无计量（10 §5.3 已记宿主 token API 未提供）。代码锚点：index.js 的 `inject=["tools","systemPrompt"]`、guidance.js 的 createPreStepHandler、child.js、source-recall.js 的 INJECTION_BUDGET_TIERS。

- **缺失面（该在却没在）**：不只「能压到多少」，还有「该注入却没注入」致功能不完善与不稳——缺稳定的状态层（目标进度／未决火花／已作决定／待修摩擦／工作包当前阶段／授权边界）。specs/00 §2.6 承诺双源召回识别「什么必须遵守／可自主决定／必须暂停」这一状态结论，实际交付的是自称「候选、命中不等于适用」的召回行。证据：pitfall-8b3c5705（词法召回不保证相关条目靠前）、friction-768211b6（语料增长挤出正确答案，Human 2026-11-20 已否决改召回排序、不立项）——靠召回代替状态注入这条路被明确判为不稳且不修。

- **职责分离（本轮核心主张，Human 定）**：管辖判定就该只做判定；要注入元规范或事实规范属另一环节。当前实现相反——noticeTextFor 在判定块挂「管辖效果」四条副作用说明，GOVERNED_GUIDANCE 把 §1–§5 元规范摘要与把关请示／模型面提请／创建确认／失败留痕等操作纪律全挂在 governed 判定分支，且核心价值是过时口径（写「三大核心价值 §1.1–§1.3」，规范原文 §1 实为「对齐 Vibe／协调 Coding」两面、无 §1.1–§1.5 子节）。管辖判定是第一个被切出的模块。

- **Human 架构主张**：按模块注入上下文——每个模块负责自己要注入的，不挤压在一起；上下文预算共用、带优先级。判定块内「项目名／判定依据／登记指纹」是否算纯判定待定（AI 建议留，判定需可核对）。

- **注入结构收敛（Human 定）**：管辖判定只是很小的职能；元规范注入、事实规范、事实信息才是大头，三者分开注入而非合并。事实规范（norm-directory 常驻目录）与事实信息（召回候选）做法已对、不动；问题集中在元规范注入。提请（把关请示／联网调查／各 Human Gate）归元规范注入范畴。元规范注入按业务分两级：纯主动义务（把关请示三时机、主动积累经验、发现摩擦）与价值/据实声明必须常驻，其余业务（目标规划/火花/调研/规范确立）与元规范全体系导航仅给索引；维护 LDVH 自身的内容（发布/开发/上游跟进/代码注释）不注入（已在事实规范目录单列）。常驻的是「每回合判断」，内容按当次设置动态生成——开关开则注入具体自检问句、关则不注入（避免变成背景噪音）；对照 report-d84a1026 的量测：回合边界自检误伤 100%（3/3 合法回合）、真实问题 0 例，故不可做无条件义务复述。依据：帮助页（locales.ts help.*）承诺给用户的价值 + 设置卡（client.js LDVH_ZH）开关描述。

- **根本性反思（Human 2026-11-21 提出，待评估）**：一般插件仅靠「工具说明」注入即可实现价值，LDVH 却要通过「注入规则进上下文」来实现价值——这条路径本身对不对、好不好，尚未定论，须专门评估。这关系到注入设计的根本取向：是否/在多大程度上应回归工具说明承载，而非另建规则注入体系。记录为待评估问题，不下结论。
