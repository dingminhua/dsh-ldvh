# LDVH 体系结构性未完善

## 当前理解

LDVH 体系存在几处结构性未完善，共同性质是「规范或实现缺一块」而非「用起来硌手」，故均不属 Friction 类型（26 §5 账本层承载待修阻碍），需在悬置层以议题承接判明归属与处置。**缺口二已裁决出清（2026-10-05）**：Human 选定解法 C，结晶为 ADR `0b08523c`（关系目标的 open 约束为写入前置条件），20 §8/§9.1/§9.4/§11/§12/§14.1/§15/§17 已同步修订，实现侧 `spark-writer.js` 改为按本次写入引入的关系目标取差集校验，存量 6 条历史指向随即合法且父对象恢复更正能力；该条不再悬置。**缺口一已于 2026-11-04 落地处置**：八类有逐字内聚判据的 writer 在拒绝时交还 frontmatter 值与正文段两侧全文及条款依据，实质是「工具面能力补建」而非放松校验；载体 `workcase-5c0b8c2e` 已关闭。**缺口三已于 2026-11-04 落地处置**：新增只读工具 `ldvh_inspect_loaded_modules` 报告装载期陈旧模块，受检面由 2 个文件扩到 `plugin/lib` 全量；载体 `workcase-e487cdf4` 已关闭。三处缺口至此全部取得归属并已落地，本议题关闭。

各处缺口的展开与可复查证据：

**缺口一：载体内聚与载体结构校验的规范暴露顺序，构造阶段无同源提示。** 20 §14.1、23 §14.1、26 §14.1 均定义"载体内聚（逐字比对）"并规定"拒绝；补齐后重走"，同时要求正文自 H2 起（H1 由 Code 从 title 生成）、条件段与 `urls` 共现（无 `urls` 不写「证据」段）。这些规则完备、正确、机械校验强度恰当——**规则本身没有问题**。问题是同一组不变量散居各类型 §8 字段契约与 §14.1 验证表，按 01.Att.03 §4 属 L3/L4 披露层，而校验时机在写工具的提交阶段，构造对象时通常不在视野。2026-09-13 一次会话内该机制被命中 5 次（Spark 3 次、Pitfall 2 次），均发生在首次受控写入；2026-10-05 本对象自身写入时再次命中 1 次（换了 frontmatter 的 summary 却未同步正文），印证该规律不因已知而失效。**处置结论**：归入「工具面能力补建」——不放松任何校验，而是在拒绝时把不变量本身交还调用方（见下方 2026-11-04 闭环节）。

**缺口二（已裁决出清，2026-10-05）——保留经过以便追溯。** 原问题：20 §11 要求 split-into 目标必须 open、§13 无删除操作、§9.2 终态不可重开，三条并存使「子议题终态后父关系指向非 open」成为必然结果且无出路，而实现不巡检既有关系、使 §11 结尾的 Stop Condition 不可达。2026-10-05 全库核查确认存量已发生 6 条，且经 change_log 时序核准六条**全部**为「写入时目标仍 open、事后转终态」——故非越权写入，而是生命周期的合法演化。**Human 裁定采纳解法 C**：承认 `open` 为**写入前置条件**而非持久不变量，目标日后转终态不溯及既往地使既有关系失效，该关系转为历史指向；已在 §8/§9.1/§9.4/§11/§12/§14.1/§15/§17 依此修订，§17 停机闭集移除该不可达条目。**裁定中发现的连带死锁一并解决**：原实现对全部关系做无条件 open 复查，会使任何子议题已终态的父对象永久锁死（连无关的内容更正都被拒，与 §9.2 终态可更正冲突）；实现已改为按本次写入引入的关系目标取差集校验。**结晶去向**：ADR `0b08523c`（按 20 §6.4 宽进窄出，决定已进窄容器）。**价值验证**：新增三条回归用例（写入时拒绝非 open 新目标／子议题事后终态放行无关更正／混合情形取差集）覆盖 C 的两侧语义，`spark-writer.test.mjs` 64/64、插件全量 1036/1036 通过。**一致性**：与 21 §12 `routed-to`「写入时为 open」同口径。

**缺口三：运行中的进程与磁盘插件代码存在版本漂移，且无守卫可察觉。** 本次创建尝试中 `refs` 字段被机械拒绝（`spark/frontmatter_invalid: unexpected field "refs"`），但磁盘上的 `plugin/lib/spark-writer.js` 的 `VALID_FM_KEYS` 已包含 `refs`（由 `71c35b0` 于 2026-09-14 04:10 加入，已是 HEAD 祖先）；以 `node` 直接导入该模块验证 `validateSparkFrontmatter` 对含 `refs` 的载荷返回 `{"ok":true,"issues":[]}`。即：**运行中的 DSH 进程加载的是 `71c35b0` 之前的插件代码，其内存中的字段闭集早于仓库当前状态**。这使「工具面 schema 与 writer 闭集」的漂移多出一个维度——不只两份清单之间会漂移（b9601356），**运行进程与磁盘代码之间也会漂移**。与 Spark `5b0b380e`（工具参数校验层不生效）同源：因 DSH 参数校验对 LDVH 工具不生效，唯一防线是 writer 闭集，而 writer 代码的加载时机未纳入版本一致性保障。**处置结论**：归入「工具面能力补建」——提供「哪些模块比进程新」的确定性事实（见下方 2026-11-04 闭环节）。

**归属线索**：缺口一由 Friction 账目 `3048937d`（事实对象载体内聚校验后置）记录并被判为类型误置，该账目已关闭并指向本议题。

### 2026-11-02 重核（只读）：缺口一与缺口三都仍在，且两者的性质已辨明

> 本节给出**当前**证据；上文是记录时点叙述，未改写。

**缺口一（内聚规则的规范暴露顺序）——仍在，且本轮再次命中**。`plugin/lib/spark-tools.js` 的 `create` 路径先跑 `dryRun: true`（`:468`）再问 Human，`update` 路径同样（`:585`）——这个设计确实让机械错误在提问**之前**被拒（注释原文：「20 §16 requires an explicit Human confirmation; asking for a candidate the writer is already certain to refuse would spend the Human's attention on an action that can never land」）。**但 dryRun 拒绝时返回的是 `spark/coherence_invalid`，不是「怎么改」**——模型必须自己知道「summary 改了正文也要同步」这条不变量，而该不变量在 20 号里散居 §8 字段契约、§14.1 验证表与 §15 验证表三处（L3/L4 披露层）。本轮重核中，`spark-5eec3197` 与 `spark-5b0b380e` 两次 update 均因该规则被拒（一次改 summary 未同步正文、一次漏传 `frontmatter_after`），与上文所记「不因已知而失效」完全一致。**故缺口一的形态已可精确定义**：不是「没有校验」，也不是「校验后置」——校验时机正确（写入前），**缺的是拒绝时把不变量本身交还给调用方**。`spark-tools.js:516`／`:670` 的 `verification.checks` 数组列了 `carrier-coherence` 这个名字，但它只在**通过后**出现在返回里，不在拒绝时给出规则内容。

**缺口三（运行进程与磁盘插件代码漂移）——仍在，且现有守卫只覆盖 Hook 一侧**。`plugin/lib/commit-validation.js:66` 的 `SOURCE_FINGERPRINT` 是**该模块源码的 sha256**，`git-gate-runner.js:517` 在通过时把它打印出来；`plugin/lib/hook-manager.js:159` 的 `bundleVersion` 用于渲染 Hook 脚本并写入 marker，安装/检查事务比对 marker 与当前 `HOOK_BUNDLE_VERSION`。**两者都不是「运行中的宿主进程加载了哪个版本的 plugin/lib」**：前者证明「本次 Git Gate 跑的是哪份代码」，后者证明「磁盘上的 Hook 是哪版生成的」——而缺口三问的是**内存里的模块**。
