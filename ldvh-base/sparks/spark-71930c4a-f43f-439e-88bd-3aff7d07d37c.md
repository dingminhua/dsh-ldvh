# LDVH 体系结构性未完善

## 当前理解

LDVH 体系存在几处结构性未完善，共同性质是「规范或实现缺一块」而非「用起来硌手」，故均不属 Friction 类型（26 §5 账本层承载待修阻碍），需在悬置层以议题承接判明归属与处置。缺口一：20/23/26 各 §14.1 的载体内聚与载体结构规则完备正确，但同一组不变量散居 §8/§14.1 属 L3/L4 披露层，而校验时机在写工具提交阶段，构造时不在视野（2026-09-13 单次会话命中 5 次）。缺口二：writer 的 open 目标校验位于 updateSparkObject 内，只校验本次写入的关系而不巡检既有关系，故子议题合法走到终态后父对象 split-into 必然指向非 open 对象且无校验可发现（实例 2916e3d5 指向 3c20a739 与 bdb9623d）；20 §11 要求目标为 open、§13 无删除操作、§9.2 终态不可重开三者并存使该不合规为必然结果，§11 结尾「视为未完整关闭」因缺巡检而实际不可达。缺口三：本次创建尝试中 refs 被机械拒绝，但磁盘 spark-writer.js 的 VALID_FM_KEYS 已含 refs（71c35b0 已入 HEAD），直接导入验证对含 refs 载荷返回 ok — 运行进程加载了 71c35b0 之前的插件代码，运行期与磁盘代码漂移且无版本守卫可察觉，与 5b0b380e 同源。归属线索：缺口一由 Friction 账目 3048937d 记录并判为类型误置，该账目已关闭并指向本议题。

各处缺口的展开与可复查证据：

**缺口一：载体内聚与载体结构校验的规范暴露顺序，构造阶段无同源提示。** 20 §14.1、23 §14.1、26 §14.1 均定义"载体内聚（逐字比对）"并规定"拒绝；补齐后重走"，同时要求正文自 H2 起（H1 由 Code 从 title 生成）、条件段与 `urls` 共现（无 `urls` 不写「证据」段）。这些规则完备、正确、机械校验强度恰当——**规则本身没有问题**。问题是同一组不变量散居各类型 §8 字段契约与 §14.1 验证表，按 01.Att.03 §4 属 L3/L4 披露层，而校验时机在写工具的提交阶段，构造对象时通常不在视野。2026-09-13 一次会话内该机制被命中 5 次（Spark 3 次、Pitfall 2 次），均发生在首次受控写入。**待判明**：是否应通过在某处提供构造阶段的同源提示（创建提案模板或工具面声明）来改善，而非放松任何校验；它属规范体系的结构缺口、工具面能力缺口，还是可接受的学习成本。

**缺口二：既有 split-into/merged-into 关系无巡检，且「子议题终态后父关系如何呈现」无规则。** `plugin/lib/spark-writer.js` 的 open 目标校验位于 `updateSparkObject` 内，**只校验本次写入的关系，不巡检已存在的关系**。因此当被拆分出的子议题合法走到终态（20 §9.2 终态不可重开）后，父对象的 `split-into` 必然变成"指向非 open 对象"，而**没有任何机械校验会发现**。实例：`2916e3d5` 的 `split-into` 指向 `3c20a739`（implemented）与 `bdb9623d`（discarded），二者均已不在 open。规范内部张力在于：20 §11 要求 split-into 目标必须 open，§13 却规定"不存在删除操作"，§9.2 又规定终态不可重开——三条并存时，子议题终态后父关系不合规是**必然结果**，而规范未为这个必然发生的情形规定任何出路。§11 结尾称此情形"视为未完整关闭，进入 Stop Condition"，但缺少对应的既有关系巡检，该 Stop Condition 实际上不可达。**待判明**：该缺口应通过补充"子议题终态后父关系如何呈现"的规则、增加既有关系巡检能力，还是明确 split-into 的 open 约束仅为写入前置条件来消解——后者若成立，则 §11 结尾表述需相应修正。

**缺口三：运行中的进程与磁盘插件代码存在版本漂移，且无守卫可察觉。** 本次创建尝试中 `refs` 字段被机械拒绝（`spark/frontmatter_invalid: unexpected field "refs"`），但磁盘上的 `plugin/lib/spark-writer.js` 的 `VALID_FM_KEYS` 已包含 `refs`（由 `71c35b0` 于 2026-09-14 04:10 加入，已是 HEAD 祖先）；以 `node` 直接导入该模块验证 `validateSparkFrontmatter` 对含 `refs` 的载荷返回 `{"ok":true,"issues":[]}`。即：**运行中的 DSH 进程加载的是 `71c35b0` 之前的插件代码，其内存中的字段闭集早于仓库当前状态**。这使「工具面 schema 与 writer 闭集」的漂移多出一个维度——不只两份清单之间会漂移（b9601356），**运行进程与磁盘代码之间也会漂移**。与 Spark `5b0b380e`（工具参数校验层不生效）同源：因 DSH 参数校验对 LDVH 工具不生效，唯一防线是 writer 闭集，而 writer 代码的加载时机未纳入版本一致性保障。**归属线索**：可能与 `2074408b`（LDVH 写入未纳入版本守卫）相关，但本条特指插件代码加载版本的滞后，而非写入动作本身。

**归属线索**：缺口一由 Friction 账目 `3048937d`（事实对象载体内聚校验后置）记录并被判为类型误置——该账目已关闭并指向本议题。
