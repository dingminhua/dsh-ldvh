# 决策可见性与重审信号的落地缺口

## 当前理解

22 §12 已要求 Web 决策库呈现 active ADR 与谱系投影，但 07 号全文 0 次提及 ADR，呈现面无落点；状态闭集与 retirement_reason 五值、9 条中 8 条有 trigger_signal 都齐，缺的是 trigger_signal 的主动扫描、谱系形态定义与呈现归属。

22 §12 的消费点表末行已要求「Web 决策库呈现：active ADR 列表与决策谱系投影（细则见 `plugin/web/docs/10`）」，但 07 号全文 0 次提及 ADR——决策可见性的上游义务已存在，下游呈现面没有落点。用户所说「散落在文档里、之前看不到」在规范层是真的：现在能看决策的只有 22 §12 列出的四个文本消费点（方案收敛装配、遵守预检、审议上下文、故障调查），没有一个面向 Human 的常驻面。

「及时调整」这一半的机制基础是齐的：ADR 状态闭集只有 active/retired（22 §9），退休原因由 `retirement_reason` 五值承载（superseded / absorbed / outdated / out-of-scope / abolished），且 9 条 ADR 里 8 条写了 `trigger_signal`（重审信号）。22 §12 还规定遵守预检「声明了重审信号的 ADR 顺带核对前提是否已变化」。也就是说「何时该重审」有信号载体、「失效后如何标记」有状态与原因载体，缺的不是这两样。

真正的缺口有三个：① 呈现面缺失（07 号无 ADR 面）；② `trigger_signal` 只是被动核对——它写在那里等行动经过时才被读，没有任何机制主动扫描「某条信号是否已经成立」；③ 「决策谱系」的形态未定义——22 §12 说要投影，但 22 与 07 都没说谱系（谁替代了谁、谁被谁吸收）如何组织与呈现。

## 调查问题

决策的「可见」与「及时可调整」还差哪一环：呈现面、重审信号的主动扫描，还是谱系形态？
