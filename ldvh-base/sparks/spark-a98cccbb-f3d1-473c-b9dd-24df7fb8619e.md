# 召回候选的陈旧检测

## 当前理解

召回候选交付给模型后，事实对象若在交付之后被改动，旧候选仍可能以旧内容示人——当前没有任何失效检测。`source-recall.js` 与 `recall-injection.js` 内 `recordDigest`／`sourceVersion` 零命中；现有「不存在陈旧读」的保证只覆盖解析缓存（缓存键含内容指纹，`source-recall.js:495`／`:574`），不覆盖「已交付候选其载体此后被改动」这一面。参照做法：`dsh-auto-memory` 的 `memory-index.js` 用「UTF-8 半开字节区间 + recordDigest + sourceVersion」判定 stale。待答：失效判据取什么、检测发生在哪一侧、检出后如何处置。

### 与来源对象的分工

这是 `spark-7f5b8acc`（召回排序与决策依据的改进）三处缺陷里唯一未落地的一处；①② 已于 2026-10-27 落地（见该对象与其提交 `b6af935`／`e683437`），本条只承载 ③，来源对象据此收束。

**为什么值得单独承载**：它与①②不同族。①② 是「排序质量与决策依据」，改的是候选的**顺序**与**要不要注入**；本条改的是「候选**内容是否仍然有效**」，属正确性问题而非质量调优。二者混在一处会使前者的完成被后者的未完成拖住——本次正是如此（用户处置时只能把整条判为「部分完成」）。

### 现有保证覆盖了什么、没覆盖什么

「不存在陈旧读」这句在 `source-recall.js` 里出现两次（`:495` 的缓存键说明、`:574` 的旧版清理注释），两处指的都是**同进程内的解析缓存**：键含语料内容指纹，语料一改即换键，故不会复用旧解析结果。**但这条保证回答的不是本议题的问题**——它管「会不会用旧解析结果」，不管「已经注入到模型上下文里的候选，其载体此后被改动」。后者没有任何检测：注入一旦发生，那段文本就固定在上下文里，载体后续的受控写入不会回传任何信号。

### 参照做法（外部实现，仅作参照不作模板）

`dsh-auto-memory` 的 `memory-index.js` 用「UTF-8 半开字节区间 + recordDigest + sourceVersion」判定 stale——文件任一位置变化 ⇒ 该文件所有 locator stale；可在候选卡上复用同一思路：呈现层**标 stale**，而不是让候选消失。是否照搬须自行判断，不得以其为设计依据。

### 待回答的核心问题

1. 失效判据取什么（内容指纹／mtime／版本号）——本仓已有内容指纹机制，是复用还是另建？
2. 检测发生在哪一侧（召回时重算、注入时校验、还是呈现层按需）？
3. 检测到 stale 时如何处置——标 stale 而非撤回？撤回会不会造成「本来该看见的看不到了」？
4. 与 02 §9 确定性红线、与现有解析缓存指纹的关系。
