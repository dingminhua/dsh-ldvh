# 召回候选的陈旧检测

## 当前理解

经 Human 判定撤销（2026-11-04）：候选交付后的陈旧检测不属欠债，而是 02 §9.1 F2 行已明写的设计取舍——该层「不能单独证明」列即含「现时适用、结论当前」，规范在设计上就把「候选不是当前结论」交给读者按 F3 复核承担。故不做机械陈旧检测，本议题不再跟踪。

### 处置理由（2026-11-04，Human 确认）

**纵向核对先行**（按 `pitfall-a8f85076`）——核对结论是**规范源没有任何一条要求已交付候选的陈旧检测**；更关键的反面证据在 `02 §9.1` 的 F0–F4 分层表：F2 行的「不能单独证明」列逐字写着「语义相关、**现时适用、结论当前**、全文已读」。即规范在设计上已把「候选卡不保证是当前结论」作为**红线明示**，并把「是不是当前」的判断交给读者按 F3 精确读取复核。故本场景不构成缺陷，而是规范预设的形态。

**为何不按「影响小所以不做」关闭**——那个理由站不住。召回行确由每回合 step-1 重算（`guidance.js:323` 的 `payload.step !== 1` 门；digest 即渲染文本本身，`recall-injection.js:1522`），但**已注入的旧行不会被撤回**：载体在会话中途被改动后，同一对象的新旧两版并存于上下文。所以准确形态是「陈旧内容不再扩散，但也不会被清除」——真正的兜底是 `02 §9.1` 红线与 F3 复核能力，不是「影响只有一个回合」。

**核对中发现但未纳入本议题的事实**（登记以免日后重现）：候选卡上的 `source.contentFingerprint` 是 **FNV-1a 32 位**（`source-recall.js:1428` 起），而 F3 精确读取与 CAS 用的 `content_fingerprint` 是 **sha256**（`spec-registry.js:329`、`adr-writer.js:420`、`adr-enumeration.js:93`）。两者同名「内容指纹」但算法不同，不可互比。本议题既已撤销，此项不另立对象；若日后确需陈旧检测，须先统一这两套口径，不得直接比对。

### 原始判断（2026-11-01，照录不改）

召回候选交付给模型后，事实对象若在交付之后被改动，旧候选仍可能以旧内容示人——当时没有任何失效检测。`source-recall.js` 与 `recall-injection.js` 内 `recordDigest`／`sourceVersion` 零命中；现有「不存在陈旧读」的保证只覆盖解析缓存（缓存键含内容指纹，`source-recall.js:495`／`:574`），不覆盖「已交付候选其载体此后被改动」这一面。参照做法：`dsh-auto-memory` 的 `memory-index.js` 用「UTF-8 半开字节区间 + recordDigest + sourceVersion」判定 stale。

**与来源对象的分工**：这是 `spark-7f5b8acc`（召回排序与决策依据的改进）三处缺陷里唯一未落地的一处；①② 已于 2026-10-27 落地（见该对象与其提交 `b6af935`／`e683437`），本条只承载 ③，来源对象据此收束。

**现有保证覆盖了什么、没覆盖什么**：「不存在陈旧读」这句在 `source-recall.js` 里出现两次（`:495` 的缓存键说明、`:574` 的旧版清理注释），两处指的都是同进程内的解析缓存：键含语料内容指纹，语料一改即换键，故不会复用旧解析结果。但它管「会不会用旧解析结果」，不管「已经注入到模型上下文里的候选，其载体此后被改动」。

**待回答的核心问题**（现均不再需要回答）：① 失效判据取什么；② 检测发生在哪一侧；③ 检测到 stale 时如何处置；④ 与 02 §9 确定性红线、与现有解析缓存指纹的关系。
