# 总纲落点列的三层混装

## 当前理解

重建总纲第 8.1 节吸收总账为 18 项各设「落点」列，但该列混装三种性质不同的目标：规范条文层、实现层（落 plugin/lib/ 与 Git Gate，specs 检索必然为零）、以及被 §8.4 判据①「吸模式不吸功能」明确排除的本不该落项。经逐项核实，7 项标称「未落」中 3 项实为已落（K1 规则 ID 已在 commit-validation.js:49-58 有 10 条冻结注册表与 fail-loud 纪律；S4 覆盖映射、L2 同源投影同）、3 项本就不该落（S1 Complexity 表已由 00 §6.3 与 04 §13 以判据取代工件；L3 验证命令与 judge 闸门已被 04 §5.4 验证入口与 09 §102 覆盖）、1 项层次标注错误（K2 规模变体，§9 自述落「04 实现层」，§8.1 只写「04」读作规范号）。真缺口仅 S5 一项，另条承载。

三种混装性质如下：

1. **规范条文层**——落点应为某号规范正文，判据是正文可检索。误判例：S5 端点契约（确属此类，且确未落）。
2. **实现层**——落点应为 `plugin/lib/` 或 Git Gate 代码，判据是行为可观察，**在 specs 中检索必然为零**。误判最重的一类，例证：K1 规则 ID 稳定引用，实际已落在 `plugin/lib/commit-validation.js:49-58`——10 条规则的冻结注册表 `GATE_RULES`，`newFinding()` 产出 `{rule, severity, message, line}` 结构化 finding，未注册的 rule 直接抛错（fail-loud registry discipline）。**这是完整落地，却被记为「未落」**。同类的 S4 任务-需求覆盖映射落在同文件的双向覆盖检查（`staged_path_uncovered` + `EXEMPT_BASENAMES`，06 §6.2 具名）；L2 门与显示同源投影落在 `plugin/lib/web-preferences.js:9` 与 `plugin/web/shared/projectColors.ts` 的双闭集同步约束。
3. **本就不该落**——该吸收项被总纲 §8.4 吸收判据①「**吸模式不吸功能**——落既有机制实现层，**不新增独立机制**」明确排除，其「未落」恰是判据被正确执行的结果，而非缺口。例证：S1 Complexity Tracking 表（「违反原则须填表自证无更简方案」）——LDVH 已以 00 §6.3「答不出的不纳入」+ 01 §15 最小充分修改 + 04 §13 反过度设计红线九条 + 各类型规范自带反过度设计章**以判据取代了工件**，落它反属违反判据①；L3「声明式 bash 验证命令 + 有界 judge 成本闸门」——04 §5.4 的「验证入口」与 09 §102 测试基线（拒绝零测试实现）已是更强形态，且 judge 成本闸门对应外部 CLI 的计费约束，LDVH 无此约束。

K2 规模变体属第四种情形（**层次标注错误**）：总纲 §9 建设顺序自述其落点为「→ 04 **实现层**」（与 ① K1 的「纯机械增强，不动规范」并列），即自始指实现而非规范条文，但 §8.1 落点列只写「04」，读作规范号，两处自相矛盾。

**方法论后果**：该列未区分「规范 / 实现 / 不该落」三种目标，读者（含本次核实的上一轮）按「spec 里搜不到即未落」核对，会把已落项判成缺口（K1/S4/L2）、把正确的不落判成缺口（S1/L3）。这直接决定「读总纲的人会不会被误导」——属总纲自身可信度问题。

**附带发现（本条不作为主问题）**：Spark `c09b07bc` 正文在转述总纲时曾把「04 号反过度设计红线」转写为「§18」，而 04 号共 13 章、其反过度设计红线为 §13。转述层新增的章号错误与总纲原文的落点错误是两个不同层的问题，此处如实登记以备追溯，不在本条展开。
