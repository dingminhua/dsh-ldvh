# 事实对象随子目标变动的自动对应

## 当前理解

八类事实对象中只有 20/21/25/28/29 采用 `serves`（26 已因无消费方删除，22/23/24/27 从未有），故「随子目标变动自动对应」现状只覆盖一半类型；30 §8.5 的级联是「标记不是动作」且不存储下游状态，退役子目标名下对象无规定去向。缺口在哪、该怎么补尚未判定。

用户把核心价值一（项目可厘清）的痛点说成三问：当前目标是什么、围绕它需要哪些子目标、子目标经常变动时各类事实对象能否自动对应。前两问已有载体（25 号 Goal 单例、28 号 SubGoal 多例、30 号目标规划系统），第三问没有完整机制。

实测现状（按规范源原文核对）：

| 类型 | 是否有 `serves` | 依据 |
|---|---|---|
| 20 Spark | 有（条件字段） | 20 §8，轻量归属引用，不参与 goal 修订级联（25 §13 豁免） |
| 21 WorkCase | 有 | 21 §8，承载授权钉扎与达成证据链 |
| 25 Goal | 有（子目标指向目标） | 25 §8 |
| 26 Friction | 已删除 | 26 §18 第 1 条：四个消费点无一使用，归属已由 `attribution` 承载 |
| 28 SubGoal | 有 | 28 §12 |
| 29 DevLog | 有 | 29 §11 |
| 22 ADR / 23 Pitfall / 24 Research / 27 Norm | 无 | 全文无该字段 |

即：八类事实对象里只有五类能按子目标反查，且这五类的语义并不统一——Spark 的是「轻量归属」、WorkCase 的是「授权钉扎」、DevLog 的是「内容关联」，同一个字段名在不同类型下承担不同义务。

子目标变动侧：30 §8.5 规定级联「界定的对象是须核对，不是须一并修改」，且明确「级联是标记不是动作」「不存储下游状态」。这两条是对的（避免第二权威），但它只覆盖「在途工单」与「子目标的 `alignment`」，没有规定子目标 `retired` 后名下对象怎么办——已关闭工单显然保留，但开放状态的 Spark、DevLog、Friction 是否仍需重新归属、由谁判断、不判断会怎样，规范里读不出。

本议题直接关系到当前 4 条 active 子目标（项目可厘清、AI任务高效准确、召回保障当前工作、空闲积累与摩擦发现）名下对象的归属能否随其退役自动收敛。

## 调查问题

子目标频繁变动时，各类事实对象凭什么机制自动保持与当前子目标集的对应，而不是靠人工回填？

## 调查边界

当「哪些类型承载 serves／如何解析」与「子目标退役后名下对象怎么处置」两条判据都能从规范源原文读出，且至少覆盖全部八类事实对象时停止；不在本议题内决定子目标的分解粒度。
