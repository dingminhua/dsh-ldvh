# 检查关卡是否应设在回合边界

## 当前理解

本 Spark 的问题**已由实测回答**，答案是否定的，故转 discarded。

调研查明（读本机安装包 `~/.dsh2002/.dsh/profiles/desktop/node_modules/@changfenhuang/dsh-genui/src/plugin/`）：`@changfenhuang/dsh-genui` v0.16.0 提供了一种**检查不放在模型自觉环节、而由插件挂在宿主回合边界上机械触发**的形态——`ctx.on('agent/turn-stopping', …)`（fence-feedback.ts:662）每回合结束边界必然触发，对该回合正文里的每个 ```dsh-ui 围栏重跑判定（`fenceFailures`）；判定与渲染共用同一套守卫代码；不可渲染时走 `agent.steer()` 同回合纠偏，约束为每回合上限 2、每围栏 1 次（按正文指纹记账）、先记账后发送、有未决结果时竞态沉默、子代理不触发、判定只认正式事件不读 reasoning；诊断以计数差额（`declared=/rendered=/dropped=`）与字段级键值对（`node=/type=/error=/allowed=`）暴露静默丢弃。

**对照 LDVH 后的结论**：

- LDVH 的受控写入**已经**是强制通道内的机械关卡——校验在工具内部执行并零写入拒绝，模型在同一回合即收到拒绝理由并可当场改正；校验器与写入器共用同一实现（提交预检与 Git Gate 共用 `commit-validation.js`；各类型 precheck 与 writer 共用同一 validator）。因此「把检查从模型自觉的前置校验改设到回合边界」对 LDVH **不构成增量**（04 §6.3：既有规则已蕴含该类情形）。
- 候选判据「本回合存在受控写入硬失败 ∧ 同 `fact_type_key` 无 `completed`」在**132 个会话、7016 条工具结果**的语料上只触发 **3 个回合**，而这 3 例经逐回合查证**全部是模型向 Human 求证后改走合法替代路径**的合法回合（例一识别出 ADR 创建被 22 §16 拒绝是因为确认答复为空并如实说明；例二例三在 Human 选择「直接执行」后改建单为直接执行并完成工作）。**误伤率 3/3 = 100%，而它要拦的形态出现 0 次。**
