# 生命周期验证的 Windows 覆盖

## 当前理解

`governed-project-lifecycle-verification.md`（38 行）记录管辖项目生命周期的当前实现范围与验证。**当前实现范围**：设置页选择实际 Git 根目录；安装事务（登记、初始化 `ldvh-base/` 五类目录、安装或升级 Git common-dir `commit-msg` Hook）；检查（登记、Git 根、common-dir、事实源、Hook 所有权、正文 digest 与 bundle 版本）；卸载 Hook（只删 LDVH 托管 Hook，保留登记与 `ldvh-base/`）；取消管辖（先卸载 Hook，再移除登记，保留 `ldvh-base/`）；DSH Host 启动时自动检查全部登记项目一次，不自动修改。**macOS 已真实验证 10 项**：候选路径必须为实际 Git 根（仓库子目录被拒绝）；首次安装创建 `ldvh-base/{sparks,workcases,adrs,pitfalls,studies}`；首次安装创建登记文件并把首个项目设为默认；Hook 安装于 Git common-dir `hooks/commit-msg`；Hook marker 正文 digest 与 bundle 版本可回读为 `managed`；真实 `git commit` 中非法 message 被阻断；符合最小 Gate 契约的 message 被放行；卸载 Hook 后登记和 `ldvh-base/` 保留；再次安装可修复缺失 Hook 不重复登记；取消管辖移除登记并自动卸载 Hook、同时保留 `ldvh-base/`。**待补**：该文件含「## Windows 范围」章节但内容未完成——Windows 侧的范围与验证尚未补齐，而跨平台是 08 §5 声明的目标（路径须兼容 Windows 盘符、UNC、junction 与 linked worktree）。

### 2026-11-02 重核（只读）：Windows 侧已有**明确的 fail-closed 处置**，但仍未写进验证记录

> 本节给出**当前**证据；上文是 2026-09-12 记录，未改写。

**实现侧已有 Windows 分支，且是有意的 fail-closed 而非静默通过**。`plugin/lib/governed-projects.js:469` 起：

```js
if (process.platform === "win32") {
  // 07 §5.6 Windows clause: inherit the DSH user-config ACL, never fake POSIX
  // mode; when the ACL cannot be verified the high-risk write must
  // fail-closed. This implementation has no ACL verifier, so the honest
  // outcome is `registration_permission_unverified` — NOT a silent pass.
  return unavailable(REGISTRATION_UNAVAILABLE_CODES.PERMISSION_UNVERIFIED, ...);
}
```

该分支注释明确引「08 §6 forbids」——即它是有意识地对规范条文的执行，不是遗漏。`PERMISSION_UNVERIFIED` 在 `:29` 登记为 `registration_permission_unverified`，Unix 侧另有 `:489` 的 `0700` 宽权限拒绝，两侧同构。

**规范侧已有 Windows 条款，共四段**：`specs/08` 第 90 行（用户配置根须经宿主 API 解析，macOS/Windows/Linux 均消费实际根目录）、第 123 行（`path` 持久化语义，**Windows 盘符与 UNC 路径允许 `C:/...`、`//server/share/...`，比较须遵循实际文件系统语义并解析 junction/symlink，不得用简单 lowercase 冒充规范化**）、第 163 行（**Windows 继承 DSH 用户配置目录 ACL，不伪造 POSIX mode、不扩大到其它用户，ACL 无法核验时高风险写入 fail-closed**；另记「Windows 目标文件占用导致 replace 失败时明确返回失败」）、第 275 行（不在实现中硬编码三平台系统用户目录）。

**故 `scope_boundary` 的两个出口中，「明确声明不覆盖并记录理由」这一半其实已经以更严格的形式兑现了**：规范不是「不覆盖 Windows」，而是**对 Windows 写明了可执行要求（ACL 继承 + 不可核验即 fail-closed + 盘符/UNC/junction 语义），实现也照此执行**。这与上文所记「Windows 侧的范围与验证尚未补齐」已有实质差别——**范围已补齐（四段条文），缺的是验证**。

**仍未落的一半是「验证」**：`plugin/test/` 下没有任何 Windows 平台专属用例——`grep -rln "win32"` 命中的三个测试（`client-contract`／`closure-items`／`goal-writer`）都不是路径或权限语义的 Windows 覆盖；上文所记「macOS 已真实验证 10 项」的对应 Windows 清单**不存在**，也没有「在 Windows 上跑过这 10 项」的记录。且 `governed-projects.js:469` 的 win32 分支在 macOS 上**不可达**，故其行为在 macOS 上无法被任何测试证明——这是一个只在目标平台才可验证的分支。

**故本条完成度约 1.5/2**：范围已明确并写入规范（四段条文，含 fail-closed 处置），验证未做且**在 macOS 上不可能做**。要收束，须 Human 判定：① 在 Windows 真机补跑 10 项（需环境）；② 或明确声明「Windows 侧仅做条文级声明、不做真机验证」并记录理由（`scope_boundary` 允许此出口）。两者都需 Human 定，且第②条会把本条从「待补验证」转为「已明确不覆盖」，属可接受的终局。
