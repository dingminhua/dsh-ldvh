# 载体内聚构成二次事实

## 当前理解

载体内聚要求 frontmatter 字段在正文逐字重现，等于同一文字存两份；根因是一个字段同时承担内容摘要与召回索引两个语义。根因判断成立，但当初选的解法**已被推翻**：曾新增 `recall_digest` 拆出召回语义，该字段于 2026-11-11 整体退场（02 §7.1），召回改按各类型自己的召回判据字段取值。最终结局是取消逐字义务 + 不设跨类型关键词字段。

### 根因：一个字段承担了两个互相拉扯的语义（Human 2026-11-10 判定）

`summary` 同时被当作「当前语义快照」（内容摘要，给人和 AI 读）与「召回时的展示与匹配来源」（索引）。这两者的最优形态**不同**，强行合一必然一边将就：

- 内容摘要要通顺、讲清「这条结论是什么」，可以有主语谓语，可以长到三四百字；
- 召回摘要要**好命中**，读者是词法匹配器而非人——它需要高密度的关键词面（症状、机制、适用边界、同义表述），哪怕不成句。

实测证据：召回硬截断到 **120 字符**（`source-recall.js` 的 `EXCERPT_MAX_CHARS`），而 **94% 的 Spark `summary` 超过 120 字**（63 条中 59 条），DevLog 为 91%、WorkCase 为 38%。即现行 `summary` 对召回而言绝大多数被截断，却仍要为它维护一份正文副本。

规范自己已记录该病理：20 §166 写「`summary` 此前全库无长度规定，实测后果是**索引层与正文层塌缩成同一份文本**」。

### 独立核查（隔离子代理，只读）确认的事实

1. **不是公共契约**：01/02 号全历史 0 次出现「载体内聚」；它是 9 份类型规范各自的局部条款，字段集互不相同。
2. **正文副本零数据消费者**：召回、Web、诊断层、8 个 writer 校验点、36 处测试全部读 frontmatter。产品层反而在主动消重。
3. **损害已两次入档**：21 号 §478【承重声明】记正文「## 结果」节是「同一批残留文本的第二处呈现面」；摩擦账目 `friction-fef52f25` count 9。
4. **闸只在写入侧生效**：仅 DevLog 读时重算，其余类型读路径不检查——拦的是「不一致的写入」，不是「不一致的状态」。
5. **实测规模**：534 份日志、550 条受控写入（257 完成 / 293 失败），内聚拒绝 **50 次 = 失败数 17.1% = 全部写入 9.1%**；其中 45 次无其他阻塞原因、44 次下一次写入即成功，属纯返工。

### 当时的决定（已作废）：拆分语义

~~新增 `recall_digest`（≤ 200 汉字）专供召回；`summary` 退回内容职责；取消逐字义务；召回取值链 `recall_digest` → `summary` → 正文 → `title`。~~

**为何作废**（2026-11-11）：该字段的判据是「召回需要一套跨类型统一的词面」，而八个类型的召回判据表本就各自登记不同字段（02 §12.4 核心语义字段行）。增加第二套索引与该设计重复，且维护义务无机械保障。退场实测：13 条人工标注真实查询在删除前后逐条候选集完全一致；对象级整体不可达 0 个。

### 最终结局（2026-11-11）

1. **不设跨类型关键词字段**：`recall_digest` 已整体退场，召回按各类型自己的核心语义字段取值（02 §7.1）。
2. **取消载体内聚的逐字义务**：20/21/22/23/28/29 的「字段间不变量」均已改为「frontmatter 是索引与摘要、正文是展开，差异只报告不阻断」。
3. **写入侧不再按逐字判违规**：`devlog-writer.js` 的 `validateCarrierCoherence` 已改为只产 `warnings`、`ok` 恒为 true（此前仍按旧口径判 reject，属实现滞后于规范）。
4. **正文骨架注释同步**：8 处「← 字段逐字 + 展开」已改为「← 字段的展开……不要求逐字复现」，涉及 20（3 处）、21（2 处）、22（2 处）、23（1 处）。这是新写入仍在复制字段的直接原因——骨架注释与不变量自相矛盾。
5. **存量处置：决定不回改**（Human 2026-11-11）。实测二次事实存量 354/357 个对象，其中仍可写（open 期）198 个、已冻结 156 个。不回改的理由：正文里的「逐字副本」与「作者本来就这么写」**无法机械区分**，批量重写会误伤真实内容；且根因（一个字段两用）已随字段退场消失，剩余重复只是文本冗余，不再是二次权威载体的语义冲突。

### 本议题处理过程中的自我更正（三处）

1. 曾称「移出字段会破坏 L0–L4 渐进式阅读」——**错**。L0–L4 是 `specs/` 规范源的读取层级，02 §306 明文「F0–F4 不能与 L0–L4 混用」。
2. 曾称「删掉 summary 改从正文取首段」——**错**。方向反了：摘要是已收敛的理解、正文是展开，凝结物不该丢掉再从展开物里重猜。
3. 曾把 `friction-fef52f25` 的归因「specs/02 §7.2 载体内聚校验」当作事实——**该归因本身错误**，02 号从未有该条款，应归到 9 份类型规范。

## 调查问题

载体内聚要求同一段文字在 frontmatter 与正文各存一份，这是否构成 02 §7.2 第 1 条所禁止的第二权威载体；若是，应改由哪一侧承载该字段？

## 调查边界

当「该字段由 frontmatter 还是正文唯一承载」有明确结论、且 20–29 全部类型的统一形态与存量对象处置路径一并说清时停止；不在本议题内决定具体字段的书写格式。

三项均已达到：结论为「frontmatter 是索引、正文是展开，不要求逐字」；统一形态为 20–29 六份规范一致采用「差异只报告不阻断」、不设跨类型关键词字段；存量处置为不回改（理由见上）。
