### 方案甲的准确定义（存档，非提案）

| 项 | 方案甲的主张 |
|---|---|
| 附件位置 | `ldvh-base/attachments/<object_uid>/<NN>-<slug>.md`，只允许 `.md`；`<NN>` 至少两位、数值单调递增、不复用 |
| 索引字段 | frontmatter 增 `attachments`，每项 `{name, digest}`；`name` 为 `<NN>-<slug>`（不含 `.md`）；`digest` 由 Code 计算，AI 输入面只见 `{name, body_markdown}` |
| 甲语义 | 对象当前权威内容 = 主载体全文 ＋ 每件附件正文（这是「甲」与「乙」的分水岭：乙为附件独立载体、对象只记指针，代价小但附件进不了 F3 完整读取，等于换个地址的 docs/） |
| 载体组指纹 | sha256(主载体全文 ‖ 逐件 `"\0"+name+"\0"+附件实际字节`)，**对实际字节取哈希而非索引 digest**；件序按 `parseInt(NN,10)` 显式比较，不得依赖默认 `sort()` |
| F3 读取 | 返回载体组全文；超预算按 `02 §9.1` 末段既有三条处理，不新增第四种退路 |
| 受控写入 | 附件增删改只经受控写入，与主载体同一次写入；增/改：先写附件后写主载体；删：先写主载体后删文件——不变式是「失败残留一律是孤儿文件，不是悬空索引」 |
| 排除项 | Goal 不采纳（`specs/25:102-106` 单例、路径即身份、无 `object_uid`，`<object_uid>` 路径不可构造） |

### 为什么停在存档而不是继续改

方案甲要改的是 `02 §7.2` 第 1 条「每个对象只能有一个当前权威载体」、`02 §7.1` 的 `content_fingerprint` 绑定对象、`02 §9.1` F3 行「当前权威载体的完整对象内容」、`02 §10.2`「返回完整对象」、`02 §13`「当前文件完整读取」——这五处合起来就是「事实源承载形态」，属 `specs/00:171` 根决定事项。同条末句「单份规范的正文修改不因本条而升级为根决定」不能用来豁免：本条改的不是一份规范的正文，而是两类语义构成要素之一的承载定义。

连带面实测（全部逐行核对）：8 个 writer 的 `VALID_FM_KEYS` 闭集、`fileFingerprint`、`FRONTMATTER_FIELD_ORDER`、可删白名单；7 个 `*-tools.js` 的参数 schema 与 `enum`（如 `plugin/lib/friction-tools.js:601`）；`plugin/lib/governed-projects.js:17` 的 `FACT_DIRECTORIES` 与 `:375` 的回滚白名单；`plugin/lib/source-recall.js:1372` 的递归语料遍历（附件目录会变成伪类型 `attachment`，每个 md 变成伪候选）；`plugin/lib/git-gate-runner.js:250` 与 `plugin/lib/ldvh-tools.js:987` 的路径子串判定（附件路径含 uid 即判可引用，fail-open）；`specs/27:250` 的悬空引用「（02 §8.2）」须改指。

七版轨迹：v1 189 行 → v7 847 行；阻断 18 → 13 → 18 → 9 → 7。最后一轮终审明确写出「在候选自身不能自洽前，任何『9 条已全部处置』的声称都不能被采信」——处置表在同一主题上并存三种互斥的「已解决」。这个信号说明迭代方式本身失效，不是候选还差几条。

### 六条可复用的工程实测事实（与方案甲成败无关，可直接引用）

1. **`rename` 会覆盖，`link` 才排他**：8 个 writer 的 `atomicWriteFile`（`norm-writer.js:259`、`adr-writer.js:452`、`friction-writer.js:735`、`goal-writer.js:129`、`pitfall-writer.js:318`、`research-writer.js:663`、`spark-writer.js:626`、`workcase-writer.js:520`）全是「写 tmp → 校验 → `rename`」；`fs.renameSync(tmp, target)` 对已存在 target **成功覆盖、旧字节消失**。`{flag:"wx"}` 加在 tmp 上无效（tmp 名随机）。真正排他的是 `fs.linkSync(tmp, target)`——目标存在时抛 `EEXIST` 且目标内容不变，跨进程原子。
2. **默认 `sort()` 会打乱 NN 序**：`["02-b","01-a","10-j","100-x","99-y","9-z"]` 默认排序得 `01-a,02-b,10-j,100-x,9-z,99-y`；按 `parseInt(NN,10)` 得 `01-a,02-b,9-z,10-j,99-y,100-x`。任何以「件序」为指纹输入序列的设计都必须显式数值比较。
3. **`specs/02:177` 的算法承接方是空的**：该末句授权「算法、编码和共同响应字段由 05 与 06 另行承接」，但 `specs/05:102` 明写「LDVH CLI 只承载…指纹…的调用，**不自行定义 CAS**」，`specs/06` 全文 grep `fingerprint|sha|hash` **零命中**。单文件指纹今天只存在于 8 个 writer 各自的 `fileFingerprint`（sha256-of-utf8）。这是既有缺口，不是方案甲引入的。
4. **非法 UTF-8 会给出两个 CAS 基线**：同一字节序列 `61 ff 62`，按 Buffer 取 sha256 得 `01ce0241…`；utf8 读入再编码为 `61 efbfbd 62` 后取哈希得 `05087813…`，两者不等。任何「对实际字节取哈希」的条文都必须写明是否经过编码往返。
5. **「目录基数校验」是纸面承诺**：7 份类型规范写了 7 处「目录基数校验」（`20:112`、`21:124`、`22:104`、`23:109`、`26:130`、`27:125`，`25:104` 为豁免），实现里 grep `基数/dirCount/expectedCount/carrierCount` 全无。
6. **仓库基线是 2556 tests / 2552 pass / 2 fail**，两红为会话前既有（`plugin/test/source-recall.test.mjs:1929` 的注释计数、`plugin/test/recall-injection.test.mjs:870` 的事实卡行）。任何新工作开工前须先修这两条，否则无法区分新红与旧红。

### 与 docs/ 滞留问题的边界

方案甲解决的是「单个规范/对象太长」，**不解决**「有价值内容躺在 docs/ 里」。这一点在候选 §7 里已自认，但当时仍推了七版——把「让代理评估是否成立」执行成了「改到通过为止」，是本次的主要方法错误。docs/ 滞留问题的落点是 `spark-e92d4ebb`，其最小落法是 `specs/35-经验积累系统规范.md` §8.3 判据 6 补一段「『不承载』不等于『可滞留』」，不碰附件、不涉根决定。
