# 插件呈现层三处已定位缺陷

## 当前理解

三条既有 Spark 合并为一条聚焦议题，共同性质是「已定位到具体源码位置、判据可复现、但未修」的呈现层实现缺陷。① `parseWorkCaseResultDraft` 的 advice 段退出条件不严——advice 模式下遇到后续顶层 bullet 不退出，把本不属于该段的条目吞为建议条目，后果是投影失真（去向条目数少算/多算，直接影响关闭卡「去向分区」的呈现与条数口径）；有可复现失败信号：workcase-63700bd2 的正文改动可使 `workcase-projection-fidelity.test.ts` 的 L547 用例失败。② `FactCardAssociation` 对 `refs` 条目声明 `target?`（可选），而 `refs` 实际承载的是 `objectUid`——类型层面的可选性会被下游误当作「可能没有目标」，`ObjectList.tsx` 的去重逻辑已专门写注「不得依赖 refs 投影当前恰好没有 target 字段这一偶然事实」；2026-09-16 独立复核曾据此发现一处跨组去重静默丢弃 refs 条目的隐患。③ 六类阅读布局（ADR／Pitfall／Spark／Research／Friction／Norm）未普查是否存在同型守卫缺陷，本单只修过 WorkCase 呈现链；已知有利条件：`WORKCASE_SURFACES` 已参数化为 5 个 WorkCase 呈现面源码（`WorkCaseReadingLayout.tsx`／`ObjectList.tsx`／`WorkCaseCriteriaList.tsx`／`WorkCaseProgressFilter.tsx`／`WorkCaseCapabilityStatusBadge.tsx`，位于 `plugin/web/tests/api/workcase-design-language-contract.test.ts:31`），扩面成本低。

### 合并来源与各自的原始判据

三条来源的缺陷型别不同，但处置形态相同（同一子系统、同一回归面、同一批测试），这是合并的依据——不是议题变窄。**来源登记（2026-11-02，20 §9.3 情形二）**：本对象由三条既有 Spark 合并而来，`refs` 与下方逐条记载均为来源凭据，三条原对象各自转 `discarded` 并写入指向本对象的 `split-into` 关系：`spark-4a21bfda`（advice 段解析吞条目缺陷）、`spark-d56b0b76`（FactCardAssociation 建模松弛）、`spark-8d5437b7`（六类阅读布局同型守卫未扩面）。三条原对象**均未落地任何修复**，故合并时一律标 `discarded` 而非 `implemented`（20 §9.3 明文：被合并/拆分的原 Spark 一律 discarded，不因部分内容被承接而标记 implemented）。

- **来源一 · advice 段解析吞条目缺陷**（原 `4a21bfda`，出自 workcase-364df30e 的残留与去向）：载体原话是「修 `parseWorkCaseResultDraft` 的 advice 段退出条件——advice 模式下遇到后续顶层 bullet 应退出，不得吞为建议条目（2026-09-27 双基线复核发现，当前由 workcase-63700bd2 的未提交正文改动暴露为 fidelity L547 失败）」。两条要点：有可复现的失败信号；后果是投影失真，直接影响关闭卡的「去向分区」呈现与条数口径。
- **来源二 · FactCardAssociation 建模松弛**（原 `d56b0b76`，出自 workcase-18fcee2c 的残留与去向）：载体原话是「FactCardAssociation 对 refs 条目的建模松弛（声明 `target?` 而 refs 实为 objectUid）属既有问题，另立一单收敛类型」。该松弛已有先例记载：`ObjectList.tsx` 的去重逻辑专门写注说明「不得依赖 refs 投影当前恰好没有 target 字段这一偶然事实」，即类型层面的可选性会被下游误当作「可能没有目标」。
- **来源三 · 六类阅读布局同型守卫未扩面**（原 `8d5437b7`，出自 workcase-364df30e 与 workcase-99957f65 两份已关闭对象的残留）：前者的原话是「以同一手法普查其余六类阅读布局是否存在同类「按错误类型判定致字段静默丢弃」缺陷」；后者是「以同一守卫扩大扫描面（已参数化为 `WORKCASE_SURFACES` 列表，扩面成本低）」。两条看的是同一个面，只是判据的缺陷型别不同；守卫已参数化，故不必新造扫描器。**据实更正**：`WORKCASE_SURFACES` 是 5 个 **WorkCase 呈现面源码**的清单，不是按事实类型参数化的列表——「扩到六类」不是改数组成员，而是按另六类各自的阅读布局文件建对应面清单；扩面成本仍低，但原话的「依据」指错了对象。

### 三者为何合并而非各自推进

- 处置面同一：都在 `plugin/web/` 呈现层与其契约测试（`plugin/web/tests/api/workcase-design-language-contract.test.ts`、`workcase-projection-fidelity.test.ts`），一次改动可同批验证。
- 判据形态同一：三处都不是「设计未定」，而是「位置已知、型别已知、只差改」，不存在需要 Human 裁定的岔口。
- 分开推进的实际代价已出现：来源一与来源三出自同一批已关闭工单的残留，此前已各自被考古两次。

### 合并后的收敛要求

- 三处须逐条给出「改成什么、影响哪些存量正文、回归判据是什么」，不得只修其一而声称整族已收敛。
- 来源三的普查面须逐类给出结论（有／无／不适用），不得以「未发现」代替「已核对」。
- 类型收敛（来源二）若改动 `FactCardAssociation` 的形状，须同步核对全部消费点，不得只改声明。
