## 调查问题

Norm 事实类型的 writer、受控入口与唯一性三层防线应如何建成？

**当前状态：问题已全部回答，三层防线各自机械验证通过。** 原五个待决问题的落点：

1. writer 的模块边界——采独立 `norm-writer.js`（复刻既有 writer 形态），未抽共用管线：Norm 的闭集与四段固定 H2 与其他类型差异过大，强行抽象会引入条件分支而非减少重复。
2. `title ≤ 40 字` 的判定单位——照 `disposition` 先例按 UTF-16 码元（`.length`）实现，与 §9.1 保持判定单位一致。
3. 退役 `superseded` 的替代对象校验——Norm 确实不写 `relations`（27 §9）；实现按「另有一个可解析的 active Norm」判定，不为承载一个关系而扩容闭集。
4. 唯一性第二层是否纳入本轮——已纳入。理由：它正是唯一能覆盖「未经 writer、手工或 shell 直写载体」的那一层；不纳入则另两层对旁路写入完全无感。实施中该层暴露并修复了一个真实 fail-open（见上）。
5. 创建提案查重结论的留痕——frontmatter 是闭集，不留痕于载体；查重结论（27 §13.1）由 Human 确认提案与 tool 调用记录承载，不伪装为机械字段。

**原登记的两项遗留均已闭合**：

- 遗留①（27 §14 条件式声明限制）——**已闭合**。条款自身写明「依赖闭合后应相应调整或删除本节对应条款」；依赖既已闭合，规范已相应处置：§11 补回各层实际入口与验证方式、§8 与 §12 的对应声明限制句移除或改写、§14 的条件式条款删除并留处置说明、§13.1 验证表相应行更新。该条款明确要求「不得因依赖补齐而被改写为『已保障』」，故本轮采「按条件闭合后处置」而非「改写为已保障」，未违背其原意。
- 遗留②（缺真实全周期实例）——**已闭合**。`ldvh-base/norms/` 现有 2 份真实 active Norm（`local-dev-workflow`、`release-gate`），各自经受控创建路径出生，并已被 `ldvh_norm_list` 正常消费。真实「出生 → 消费」闭环成立。
