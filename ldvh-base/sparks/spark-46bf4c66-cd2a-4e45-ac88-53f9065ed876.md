# Spark 合并拆分次序实现缺口

## 当前理解

20 §9.4 由 Human 决定 **D-7**（2026-09-12，见 `audit/human-decisions-2026-09-12-segment.md`（原 docs 目录，已随 `ec19ba6` 清除、可自该提交回取））定义了合并/拆分的**三情形次序**——按目标构成分：**情形一**（既存目标）SOURCE-FIRST、**情形二**（新建目标）CREATE-FIRST、**情形三**（混合）先建后结。

**核实结果：规则齐备，缺的是实现。**

`plugin/lib/spark-writer.js` 的受控原语只有 `createSparkObject` 与 `updateSparkObject` 两个**单对象**操作，不承载跨对象的次序编排。实测：文件内 `CREATE-FIRST` / `先建后结` / `情形二` / `情形三` **零命中**（唯一的 `SOURCE-FIRST` 出现在注释里）。故**情形二与情形三尚未实装**，三种次序目前由调用方（主控 AI）按 §9.4 自行执行，无机械承载。

**一处注释失实已更正**（2026-09-27）：该文件原有一段 memo 写作「Human-ratified **deferral** … the safe order is **SOURCE-FIRST**」，两处不准——①「延期」不准确：延期的是**实现**不是**规则**（§9.4 已定义三情形）；② 把三情形之一说成了唯一次序。该段已改写为如实表述，并指向本对象作为缺口的正式承载。

**为什么这值得单独承载而非并入他处**：与 open Spark `71930c4a` 的三处缺口不同族——那三处（校验暴露顺序、既有关系巡检、版本漂移）都是「规范或实现少一块」的通用形态；本条的缺口有**明确的已定规则作为对照基准**（§9.4 三情形 + D-7 决定），差距是「规范已定义 N 种、实现只做了 1 种」，可逐情形核验完成度。与 draft 工单 `bb033829`（§11 open 约束改为写入前置）也不同——那件处理的是 §11 的约束性质，本条处理的是 §9.4 的**次序编排实现**。

**相关但不同**：`review-10d-03.md` 的 F2 曾指出 02 §10.6 与 20 合并/拆分流程存在张力；该张力已由 `084c311`（2026-09-12 23:22，晚于审核报告 21:09）以 §9.4 的三情形定义回应。故 F2 的**规则侧**已闭合，本条登记的是**实现侧**的剩余差距。

### 2026-11-02 重核（只读）：缺口仍在，但规范侧已把「无机械承载」写成明文

**实现侧**：`plugin/lib/spark-writer.js` 现导出 `readServableSubGoals:407`、`resolveRefsTargets:427`、`createSparkObject:670`、`readSparkObject:776`、`listSparkObjects:873`、`updateSparkObject:1072`，**全部是单对象原语**，无任何跨对象编排入口。`CREATE-FIRST` / `先建后结` / `情形二` / `情形三` 在文件内仍**零命中**；唯一命中 `SOURCE-FIRST` 的是 `:825-832` 那段已更正的注释，它自己写着「实现只覆盖三情形中的一种（情形一 SOURCE-FIRST）；情形二（CREATE-FIRST）与情形三（先建后结）尚未实装」。**缺口未变。**

**规范侧新增关键事实（本次首次读到，改变了本条的定性）**：`specs/20-Spark-火花.md` 第 389 行已明文登记——

> **§9.4 次序同样无组合级机械承载**：`§9.4` 的三情形次序是对执行者的义务，其各步骤均由单对象受控入口完成；在组合级载体具备之前，**不存在**能证明「整次合并/拆分已按序完成」的单一机械结论，故该次序的遵守情况须按 `§15` 的语义核对与 Human 判断取得，不得声称由机械保障。

同文件第 387 行另有相邻的「归属的义务方与承载限制」：合并/拆分的**整体确认**同样「尚无机械载体」，多出的逐步骤询问属**已知的实现限制**，须按 `00 §5.6` 如实披露。

**这两处使本条的性质变了**：缺口不再是「规范要求而实现没做」的落差，而是**规范自己已把「暂无机械承载」写成如实声明**。当前状态是规范许可的（§15 要求语义核对，不主张机械保障），本条登记的是「将来是否要补上组合级载体」。

**本次处置的实证（重要）**：2026-11-02 的 Spark 合并批次实际走了情形二（CREATE-FIRST）——先建 `spark-b0e805d1` 与 `spark-a98cccbb`，再关原对象，再补目标 change_log 的来源流水。**三步全部由主控按 §9.4 人工编排，无任何机械校验介入**；且规范第 387 行预言的「逐步骤各自触发确认」确实发生了（新建、每次终态转换各一次询问）。这为「缺口真实存在且可复现」提供了一条本仓内的执行样本，同时也证明 §15 的语义核对路径是可行的。

## 调查问题

20 §9.4 的合并/拆分三情形次序中，情形二（CREATE-FIRST）与情形三（先建后结）应如何实装，使次序获得机械承载而非依赖调用方遵守？

## 调查边界

三情形各自获得机械承载，或经 Human 判定「次序由调用方执行即可、不需要机械编排」并据此修正 §9.4 或本注释时停止；不要求实际完成实现改动。

**边界的含义与本次重核后的判断**：第一条路径（机械承载）未达成；第二条路径（Human 判定「不需要机械编排」）**已有规范侧的近似表述**——第 389 行已如实声明无组合级承载、并指明以语义核对与 Human 判断替代。但该声明是**「暂无」**的临时交代（「在组合级载体具备之前」），不是「不需要」的判定。二者差别是决定性的：前者把缺口留在待办，后者会关闭本条。故本条**不能据第 389 行自行结案**，须由 Human 明示择一。

**明确不包含**：`spark-5eec3197`（Spark 载体内聚的冗余与取舍）——同属 Spark 自身机制，但那是「规则是否恰当」的取舍问题，本条是「已定规则的实现缺口」，不合并。
