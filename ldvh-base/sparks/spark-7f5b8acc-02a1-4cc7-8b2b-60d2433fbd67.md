# 召回排序与决策依据的改进

## 当前理解

一条三分：① 稀有度加权排序**已落地**（`source-recall.js:2190` 按 Okapi idf 加权，提交 `b6af935`），但实现自述「不是标准 BM25、只是 idf 加权求和」——tf 恒为 1、k1/b 是死代码、`hits` 跨源不可比；② 排序分与注入决策**已分离**（`recall-injection.js` 的 `DECISION_KEYS` 冻结为 `candidateCount`+`baselinePresent`，配分数注入守卫用例，提交 `e683437`）；③ **候选无失效检测，仍未落地**——`recordDigest`／`sourceVersion` 在召回链零命中，现有「不存在陈旧读」只管解析缓存、不管已交付候选的内容漂移。故本条不具备整体转终态条件：分支①已被①②的实际落地回答，但③仍开放。

### 实施核实（2026-11-02，只读）

**缺陷①（稀有度加权排序）已落地**——`plugin/lib/source-recall.js:2190` 起按 Okapi idf 加权：`const idf = Math.log(1 + (corpusStats.total - df + 0.5) / (df + 0.5));` 并以 `sum += idf * sat` 累加；提交 `b6af935`（2026-10-27 17:20，「fix(recall): 中文切词放宽后降为弱证据，命中改按稀有度加权，条数与渲染上限由预算导出」）。**但实现自己声明了更强的边界，本议题若标「已实现 BM25」即是虚报**：同段注释（`source-recall.js:2160-2165`）写明 `tokenize()` 返回**去重后的集合**，故 `tf` 恒为 1、k1/b 的作用被抵消、`dl` 是词表大小而非文档长度——**「本式不是标准 Okapi BM25，只是 idf 加权求和」，tf 饱和与长度归一当前是死代码**。

**缺陷②（排序分与注入决策分离）已落地**——`plugin/lib/recall-injection.js` 的 `DECISION_KEYS` 冻结为两项（`candidateCount`、`baselinePresent`），并在同文件头声明「`hits`／BM25 加权分／tier／path **不在清单内**」；提交 `e683437`（2026-10-27 17:21，「fix(recall): 注入决策抽成纯函数只读条数与基线…」）。方法上比原设想的更强：不靠约定，而靠**闭集常量 + 守卫用例**（用分数注入验证「把排序分改到任意极端，决策结果不变」）。

**缺陷③（候选无失效检测）未落**——`source-recall.js` 与 `recall-injection.js` 内 `recordDigest`／`sourceVersion` 零命中；现有「不存在陈旧读」的保证只覆盖**解析缓存**（缓存键含内容指纹，见 `:495`／`:574`），不覆盖「已交付给模型的候选卡其内容已变」这一面。

**据实更正**：本条的 `question`（「能否在不引入外部依赖、不破坏 02 §9 确定性红线的前提下落地」）与 `scope_boundary` 分支①（「给出可落地的排序算法与决策分离方案，并说明各自的可判定验收判据」）**在缺陷①②上已被实际落地回答**，且落地方案确实零外部依赖、沿用 idf 这一「从语料统计推出的量」（注释自述满足 02 §9「确定性、可复算、无学习参数」红线）。故本条**不具备整体转终态的条件**：缺陷③仍开放，且①②的落地暴露了一个原议题未预见的形态问题（`hits` 已非计数而是 idf 加权厚度，但**跨源不可比**，这一点由实现侧 `ranking.note` 登记，属新信息而非本条原载）。

### 创建时点的判断（2026-10-26，照录不改）

下列各段是创建当时的记载，其中「尚未落地」「未修缺陷」等表述已被上节实施核实推翻，保留以备追溯。

召回的第二层改进尚未落地：排序仍用命中词计数而非词稀有度，且排序分与「是否注入」的决策依据未分离。

#### 一、本轮已修的部分（不属本 Spark 议题）

`source-recall.js` 的 tokenizer 原按「二元组含任一虚字即整组丢弃」过滤，把跨越虚字的实词对一并吞掉——实测 12 条真实查询里 4 条切不出任何 token，召回直接 `recall/no_tokens`。改为「两端皆虚才丢」，并把含单虚字的二元组（「为什」「里不」）标为弱证据（新增 `isWeakToken`，并入既有 `weakHit` 降权轴），再加一道「全为弱证据则不召回」的护栏。实测切空率 4/12 → 0/12，且「为什么这里不对」这类无主题句仍如实报 no_tokens。

#### 二、未修缺陷①：排序用命中词计数

现行排序键为 `weakHit → tier → hits → path`，其中 `hits` 是「命中的词有几个」，等权。于是「是一条」与「白屏」权重相同。本地 `dsh-auto-memory` 的 `shadow-retrieval.js` 已用 BM25（k1=1.2 / b=0.75，Okapi 经典参数：IDF 加权 + tf 饱和 + 文档长度归一），纯函数、零依赖。

#### 三、未修缺陷②：排序分与决策依据未分离

`dsh-auto-memory` 的 `recall-fusion.js` 文件头明确把两者分开：「融合分数只用于排序；『是否注入』的决策必须使用绝对分数与校准阈值比较，rank-space 分数本身仍是候选集内的相对量，不承担决策职责」。调研 R-f8b248ce 的 F4「回声陷阱」给出否证：单阈值策略精确率为 0（`denseTop=0.834` 时触发全是闲聊），语义相关性 precision 0.818 但 recall 仅 0.237，二者不可互相替代。**注意：我们的三态 gate（34 §6）比它稳，不该拆**——要拆的是「用排序结果当决策依据」这一点。

#### 四、未修缺陷③：候选无失效检测

事实对象改动后，旧候选仍可能以旧内容示人。`dsh-auto-memory` 的 `memory-index.js` 用「UTF-8 半开字节区间 + recordDigest + sourceVersion」判定 stale（文件任一位置变化 ⇒ 该文件所有 locator stale），可在候选卡上复用同一思路。

#### 五、另案处理（勿混入本议题）

① 渲染裁剪在 `limit=99` 时把全部事实行删空（`counts.factHits=132`、`factsReturned=18`、渲染事实行 0）——裁剪只从尾部删 `- ` 行，事实行排在规范行之后被整段删掉；② 插件多实例并存致钩子重复（已记 `pitfall-e2cfc7f9`）。

#### 六、边界判断

两调研（`0b3471af` F3、`f8b248ce`）一致结论是「零依赖启发式足够，向量非必需」，故不引入 embedding；本地三插件（`dsh-auto-memory` 22973 行、`dsh-coldread-cache` 1875 行）无一以向量为主力。
