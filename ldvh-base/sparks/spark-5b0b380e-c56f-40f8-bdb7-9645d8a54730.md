# 工具参数校验层不生效

## 当前理解

参数校验缺口已闭合：46 个 LDVH 工具经 defineTool 注册，参数层真实执行（实测非对象根、类型错、嵌套多余字段均抛 ToolArgsError）；e9fb0668 补上行为级守卫与 dsh-tools 的 peerDependencies 声明。参数根隐式开放致顶层通道外字段仍静默丢弃，属 specs/10 §5.2 已披露的既定差异。

（以上首段即 frontmatter `summary` 的逐字承载。）

本对象自 2026-09-13 记录`ctx.tools.register(裸描述符)`绕开 DSH 参数校验起，到 2026-11-11 缺口闭合，历时约两个月。首段以下为**过程证据**，记录时点值未逐一改写；当前状态以首段为准。

### 缺口是什么（2026-09-13 记）

LDVH 全部工具描述符由 toolDescriptorFor 返回裸对象、经 ctx.tools.register() 直接注册，从不经过 DSH 的 defineTool；而 DSH 的参数校验只存在于 defineTool 闭包内（ToolRuntime.register() 原样存、派发时不再校验）。实测：schema 明令禁止的属性仍能抵达 handler。因此 LDVH 工具的参数面约束不来自 DSH 运行时，writer 的闭集校验是实际生效的最后一道防线。此结论修正了 b9601356 的成因描述——它假定存在一个会 throw 的运行时 DSH 参数校验环节。

证据链（读自 `plugin/node_modules/@deepseek-ai/dsh-tools/lib/index.js`，0.2.x）：

1. `defineTool` 构造 `execute` 的方式是「先校验再执行」：`const violations = validate(args); if (violations.length > 0) throw new ToolArgsError(violations);` 之后才 `return userExecute(args, exec)`。参数校验在闭包内，不是运行时的公共环节。
2. `ToolRuntime.register(definition)` 只做 `output.schema`/`timeoutMs`/保留名的形状断言，然后 `layer.tools.insert(name, definition)` 原样存入，不包装、不注入校验。
3. `ToolRuntime` 派发时是 `const returned = await tool.execute(exec.arguments, exec)`，不再校验。

**2026-10-19 复现与承担面扩大**：在本仓活会话中向 ldvh_spark_read 传入 schema 未声明的属性 `__ldvh_probe_undeclared_field__`，调用仍正常完成、handler 照常返回——缺口自 2026-09-13 起未被修复。同时查明建立在该不存在环节上的规范文本不止 b9601356 一处：`specs/10` §5.2 规范性声明「参数经 JSON Schema 编译校验（违规抛 ToolArgsError）」，宿主缝表把 `ctx.tools.register` 的消费要求写作「经该入口注册操作并接受参数校验」，均与实现不符。三项候选路径（接入 defineTool／LDVH 侧等效校验／裁定 writer 闭集为唯一防线）的可行性已核对，归属裁定经 Human 于 2026-10-19 决定暂缓，本轮先固化证据。

**2026-11-02 只读重核（当时结论：缺口仍在，且比原记更彻底）**：`plugin/lib/` 内 `defineTool(` 零命中；`validateJsonSchemaValue` 与 `ToolArgsError` 同样零命中——即候选路径②也没有被部分采用。`@deepseek-ai/dsh-tools` 仍在 devDependencies，lib 内零 import。三项候选路径一条都未落地，不具备转终态条件。

### 2026-11-11 收尾（e9fb0668）

上一轮落地后仍有三处未闭合，本对象在此期间保持 `open`：

1. **无守卫防回退**——落地的只有代码，把任一层改回裸描述符时全部既有测试仍绿（`tool-descriptor-contract` 只检查 `output` 块，参数层是否执行不在其判据内）。已新增 `plugin/test/tool-parameter-validation.test.mjs`：以生产同款入口 `registerLdvhTools` 注册全部 46 个工具，逐个构造必被参数层拒绝的输入并要求 execute 抛 `ToolArgsError`；判据是「校验到底发不发生」，不是源码里有没有 `defineTool` 这个词。变异检验确认有效（退回裸描述符即转红并点名三个工具），并配有正控制用例防止判据恒真。
2. **依赖类别**——`plugin/lib` 已有 12 个文件在**运行时** import `@deepseek-ai/dsh-tools`（`defineTool`），却只列在 devDependencies，靠宿主 `node_modules` 逐级提升才解析。已补入 peerDependencies，下界取 `>=0.1.7-rc.1`（实测该版 `defineTool` 参数校验完备且能编译本适配器对真实工具的产出，无须抬高；抬高反而会与 README 已声明的宿主兼容范围冲突）。
3. **原对象未跟上**——本 Spark 正文停在 2026-11-02 的「一条未落地」，落后于代码 8 天。

### 仍存在的既定差异（不是缺口复发）

**参数根是隐式开放对象、不可关闭**，故顶层未声明字段不在此层被拒。本会话实测向 `ldvh_spark_read` 传未声明属性仍放行。这在 specs/10 §5.2 已据实写明：通道内字段的防护由各领域 writer 的字段闭集承担（02 §10.5）；且 `c7addfbe` 时已实测「顶层传 status 被静默丢弃」，属**已知且已披露**的行为，由 Human 裁定优先利用宿主能力、不在本层自建等价校验。
