# 工具参数校验层不生效

## 当前理解

LDVH 全部工具描述符由 toolDescriptorFor 返回裸对象、经 ctx.tools.register() 直接注册，从不经过 DSH 的 defineTool；而 DSH 的参数校验只存在于 defineTool 闭包内（ToolRuntime.register() 原样存、派发时不再校验）。实测：schema 明令禁止的属性仍能抵达 handler。因此 LDVH 工具的参数面约束不来自 DSH 运行时，writer 的闭集校验是实际生效的最后一道防线。此结论修正了 b9601356 的成因描述——它假定存在一个会 throw 的运行时 DSH 参数校验环节。

**2026-10-19 复现与承担面扩大**：在本仓活会话中向 ldvh_spark_read 传入 schema 未声明的属性 `__ldvh_probe_undeclared_field__`，调用仍正常完成、handler 照常返回——缺口自 2026-09-13 起未被修复。同时查明建立在该不存在环节上的规范文本不止 b9601356 一处：`specs/10-DSH 环境接入与插件发布规范.md` §5.2（第 99 行）规范性声明「`ctx.tools.register(defineTool({name, description, parameters, output, execute}))`……参数经 JSON Schema 编译校验（违规抛 ToolArgsError）」，同文件宿主缝表（第 159 行）把 `ctx.tools.register` 的消费要求写作「经该入口注册操作并接受参数校验」，均与实现不符。三项候选路径（接入 defineTool／LDVH 侧等效校验／裁定 writer 闭集为唯一防线）的可行性已核对，归属裁定经 Human 于 2026-10-19 决定暂缓，本对象先固化证据。

（以上首段即 frontmatter `summary` 的逐字承载。）

证据链（读自 `plugin/node_modules/@deepseek-ai/dsh-tools/lib/index.js`）：

1. `defineTool` 构造 `execute` 的方式是「先校验再执行」：`const violations = validate(args); if (violations.length > 0) throw new ToolArgsError(violations);` 之后才 `return userExecute(args, exec)`（约 863 行）。参数校验在闭包内，不是运行时的公共环节。
2. `ToolRuntime.register(definition)` 只做 `output.schema`/`timeoutMs`/保留名的形状断言，然后 `layer.tools.insert(name, definition)` 原样存入，不包装、不注入校验。
3. `ToolRuntime` 派发时是 `const returned = await tool.execute(exec.arguments, exec)`（约 3192 行），不再校验。

实测（本仓库内探针，非推断）：以 `toolDescriptorFor("spark-write-object", …)` 构造描述符，传入一个 schema 明令禁止的属性（`frontmatter_draft.bogus`），`d.execute(...)` 的返回值显示 handler 照常运行——参数校验没有拦截它。

**实测复现（2026-10-19，本仓活会话，非转述）**：直接向已注册的 `ldvh_spark_read` 传入一个 schema 从未声明的属性 `__ldvh_probe_undeclared_field__`（`additionalProperties: false` 下应被拒），调用**正常完成**并照常返回对象书面结果。即该缺口自 2026-09-13 记录至 2026-10-19 未被修复，且这一路径比仓库内探针更接近真实调用面——它经由宿主派发链本身。

**承担面扩大（2026-10-19 新查）**：建立在该不存在环节上的规范文本不止 b9601356 一处。`specs/10-DSH 环境接入与插件发布规范.md` §5.2（第 99 行）把接入形态**规范性**写作 `ctx.tools.register(defineTool({name, description, parameters, output, execute}))`，并声明「参数经 JSON Schema 编译校验（违规抛 ToolArgsError）」；同文件「宿主缝的消费义务」表（第 159 行）把 `ctx.tools.register` 的消费要求写作「经该入口注册操作并接受参数校验」。而实现是 `ctx.tools.register(toolDescriptorFor(...))` 裸描述符注册（`plugin/lib/spark-tools.js:855` 等八处同形）。故本缺口的规范承担面比本对象原记的范围更宽——本对象的 `scope_boundary` 只点名了 b9601356。

**三项候选路径的可行性（2026-10-19 核对，未落地）**：`defineTool` 确由 `@deepseek-ai/dsh-tools` 导出（同包导出清单含 `defineTool`/`validateArgs`/`validateJsonSchemaValue`），三条路均技术可行，约束不同——① 接入 defineTool：需把八个工具模块手写的 JSON Schema 改写成宿主参数 DSL（`defineTool` 以 `parameterSchemaSpecToJsonSchema` 编译 `options.parameters`，`output.schema` 亦须为 `valueSchemaSpec`），且该 API 的 tsdoc 自述为 first-party tool；该包当前仅列于 `devDependencies`，须升为运行时依赖；② LDVH 侧等效校验：在注册缝 `execute` 入口用宿主同一 `validateJsonSchemaValue(parameters, args, "")` 先行校验即可与 `defineTool` 内部同源，改动最小，同样须解决运行时依赖问题；③ 裁定 writer 闭集为唯一防线：无代码改动，但须修订上述 specs/10 两处声明与 b9601356 的表述，并接受错误只由 writer 抛出、报错更晚更弱。**本项未经 Human 裁定**——Human 于 2026-10-19 决定暂缓归属裁定，本轮只固化证据。

后果：模型侧之所以不会乱传，是因为 DSH 从描述符的 `parameters` 生成给模型的参数声明，模型按声明构造调用；一旦调用携带未声明字段，抵达的是 writer 而非校验层。writer 的闭集校验（如 `spark-writer.js` 的 `VALID_FM_KEYS`）因此不是「第二道防线」，而是实际生效的最后一道。

两项未被削减的能力：writer 闭集校验有效；`schema-writer-agreement` 守卫（2026-09-14 加固后）以 DSH 真实使用的 `validateJsonSchemaValue` 直测每个可选字段，能捕获字段漂移。

**核实边界（据实声明）**：宿主侧只读了插件 vendor 的 `@deepseek-ai/dsh-tools@0.2.0-rc.2` 副本（`plugin/node_modules/`）；DSH 检出路径是 `.asar` 归档、非目录，未直接读活宿主源码，故「宿主 tools 服务是否另有 define 缝」未经核实——该未核实项不影响三项候选路径的成立。

## 调查问题

LDVH 工具的参数面校验应由谁承担——接入 defineTool 使 DSH 校验真正生效，还是在 LDVH 侧建立等效的显式校验，抑或确认「writer 闭集即充分」并据此修正规范表述？

## 调查边界

当「LDVH 参数校验的责任归属」有定论并落地（无论接入 defineTool、自建等效校验、还是显式裁定 writer 闭集为唯一防线并据此修订相关规范表述）时停止。不含 writer 内部各字段的语义校验（属 20–27 号规范）、不含 b9601356 记的两份字段清单漂移（该问题已有守卫覆盖）、不含 Git Gate 对事实对象内容的校验（属 64754323 与 2074408b）。
