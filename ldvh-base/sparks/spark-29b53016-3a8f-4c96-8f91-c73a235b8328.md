## 当前理解

元规范（LDVH 框架规范，specs/ 单一权威、引导随插件分发）与管辖项目规范（项目自身约定）的区分经三视角对抗讨论确认成立；当前架构已隐含区分但未命名，07 §6 把 specs/ 写进每个管辖项目的工作对象定义、对非自举项目语义悬空。承载三候选：A 事实对象（效力同构 ADR，「不改 00」主张被自身修订清单证伪）、B 轻量规范源（唯一 Git Gate 机械通道，不动 00，双模型并存代价）、C 现有组合（六问三问答不出，YAGNI 适用）。已收敛四条设计不变量与重开评估清单。Human 裁夺（2026-09-09）：承载与 Layer 0 表述澄清一并推迟，先落 Spark 悬置，之后再研究。

概念区分的实质：LDVH 现行架构事实上有两类规范——元规范（specs/00–25 及 30–38 预留段，单一权威在 LDVH 仓库，最小引导硬编码于插件随插件分发）与管辖项目规范（项目自身的工程约定/业务边界/流程规范）。01 §9.1「候选只来自 LDVH 源码仓库」按元规范读法本来就正确；真正悬空的是 07 §6 把 specs/ 写进每个管辖项目的工作对象定义——非自举项目没有该目录。实现层（工具扫描管辖根 specs/）与 07 §6 一致，是规范语义债而非实现 bug。

三方向对抗结论（三隔离子代理，12 号 §8 纪律）：A 的最弱点是「00 §3.3 无需修订」被其自身修订清单证伪——项目约定若实质改变「行动是否允许」，事实身份下要么失强制力、要么违 00；B 的硬优势是唯一给项目级规则开 Git Gate 机械强制通道的方向（00 §3.4 机械保障只执行规范源定义内容），代价是元/项目两套规范模型并存与漂移防护（项目规范不得复制元规范可强制条款）；C 论证 03 §5.2 六问中独立身份必要性/无损承载不可/成本净值三问当前答不出（唯一管辖项目是自举仓库，其约定即元规范本身），且缺口为真时也各有非对象化解法（状态→命名约定/Git 分支；Web→直接渲染 md；机械检查→lint/test 工具），过早新建返工面（03/05/09/12 五部联动）大于推迟补建。C 自认让步：「Web 结构化呈现」是最强真实缺口（未验证）。

设计不变量（无论将来选哪条路都保留）：只收窄不放宽——项目规范只能比元规范更严（防 00 §3.6 稀释）；触顶回升——项目规范产生元规范级规则时审核强度回升十维对抗；基线锚定——framework_baseline 类字段锁定对应框架版本；评估先行——重开时先答四问再答六问。

重开评估清单（按序作答）：①状态流转需求是否真实（试行→正式→废弃）→真则指向 A；②机械强制需求是否真实（Git Gate 检查项）→真则指向 B；③Web 结构化呈现需求是否真实；④AGENTS.md/ADR 实测覆盖率。①②的答案分别指向 A/B，全否且 Web 无硬需求则维持 C。

未决与缺口：C 的「现有组合覆盖率 70–85%」是无据估计（其自报）；goal.md 存在两处日期缺陷（change_log 两条 2026-09-10 时间戳早于真实提交约 21 小时——e35efd9 实为 2026-09-09 03:58；SG-2「七类型（20–26）」过时为六类型），属 goal 修订范围（25 §13 Human Gate），不属本 Spark。

## 调查问题

管辖项目自身的工程约定应以什么形态承载——事实对象（同构 ADR 效力）、轻量规范源（Git Gate 机械通道），还是普通文件组合（AGENTS.md+装配/预检）已足够？

三个候选的真实分界是一道事实题：项目级约定是否需要（a）状态化承载与受控生命周期，还是（b）机械强制通道（Git Gate 直接执行项目级可机械检查项）——(a) 真则事实对象（A）成立，(b) 真则只有轻量规范源（B）能承接，两者皆否且 Web 呈现无硬需求时，现有普通文件组合（C）即为正解。该事实题在首个非自举管辖项目出现前无法据实回答。

## 调查边界

停止条件任一出现即进入裁定：SG-4 首个非自举项目完成管辖登记并做完承载评估；任一管辖项目普通文件承载出现实际失败（状态流转/机械强制/Web 呈现之一被证实）；自举项目自身出现框架外需状态化承载的约定；或 Human 直接裁定形态。

范围边界：本 Spark 只承载承载形态的悬置与评估输入，不预写类型规范草稿、不预改任何现行规范；答案落地时按 01 §11 规范新建判断顺序形成候选，A 路径需同步修订 00 §3.3（受保护文档，独立提交）。
