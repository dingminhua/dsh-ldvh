# 端点契约五契位与外部工件收割

## 当前理解

重建总纲第 7 节新增设计输入第 3 条提出端点契约五契位（specflow goal-complete 接缝 / keel AUDIT 三件套 / openspec 与 spec-loop archive 变更集 / spec-collab ReadyPackage+sha256），规定选型随 21 号实施定、收割产物挂靠对应 sub-goal，§5.5 流转图亦写明此路径，§11 开放问题第 7 条正式登记。核实结果（2026-09-14）：该设计输入在规范正文、代码与开放问题表之外承载面全部为零——「端点契约」「收割」「feature」在 21/26/04 三号零命中，代码亦零命中，且「feature = sub-goal 产品语义特例」的定义本身在 04/21/26 同样零命中，定义层与格式层双缺。本条经核验不属 §8.4 判据①「吸模式不吸功能」排除的类别（对比 S1/L3），因它要求的是为已有的 Gate 2 与 sub-goal 挂靠位确定契位与格式，落在既有机制而非新增机制，故确属应落未落。

**五契位原文与出处**：第 7 节第 3 条列 specflow goal-complete 接缝（评为「最干净」）、keel AUDIT 三件套（结果+证据+偏差+复盘 = Gate 2 关闭提案的证据结构）、openspec 与 spec-loop 的 archive 变更集、spec-collab ReadyPackage+sha256，共五处契位，并规定「选型随 21 号实施定；收割产物挂靠对应 **sub-goal**（§5.4 Feature 归宿）」。第 5.5 节流转图写「WC 关闭（Gate 2）→ 沉淀判断 → 蓝图投影刷新；外部流水线工件经端点契约收割挂 sub-goal」。

**核实细节**：检索「端点契约」「收割」「feature」三词，21 号、26 号、04 号均零命中；`plugin/lib/` 与 `plugin/web/` 代码中「端点契约」亦零命中（仅 `session-scopes.js` 有无关的 HTTP endpoint 用法）。总纲把「外部流水线工件挂靠 sub-goal」写在 Feature 归宿条目下，而「feature = sub-goal 产品语义特例」本身在 04 号、21 号、26 号同样零命中——即该接缝的**定义层**与**格式层**双双缺失。

**为何这是真缺口而非「不该落」**：本条经核实**不属于**总纲 §8.4 判据①「吸模式不吸功能、落既有机制实现层、不新增独立机制」所排除的那一类（对比 S1 Complexity 表、L3 judge 成本闸门——二者的「未落」是判据正确执行的结果）。理由是 S5 要求的不是新增独立机制，而是**为已有的外部工件接缝确定契位与格式**：LDVH 已有 Gate 2 关闭提案与 sub-goal 挂靠位（21 号与 25 号），所缺的是「外部产出的工件以何种契位被这两个既有位置接住」的选型与格式。它落在既有机制上，符合判据①，故确属应落未落。

**外部证据基础**：总纲 §3.2「端点空位五重印证」已对六个样本项目逐一核证——openspec（verify→sync→archive 全靠自觉，无 Gate 2、无事实沉淀）、specflow（goal complete + 逐条 AC 审计，**零沉淀**，端点完全空置故为最干净的接入缝）、keel（AUDIT 归档 + 复盘进下轮锚定，有沉淀萌芽但 agent 自述审计、无独立复核）、spec-loop（delta 机械并入主规格 + 全量归档，无筛选、无 Gate 2）、spec-collab（六门机械封口 + sha256 ReadyPackage，止于 Ready 明确不做下一跳）——结论「生成纪律各显神通，端点治理无人问津」。**该结论证明「端点治理」是真实的结构性空位**，但不证明 LDVH 应承接（判据①约束落既有机制；且总纲 §8.2 已把部分相邻形态列为「参考不吸收」）。

**待判断的核心**：五契位的选型（或以何种方式收敛到更少契位）、以及收割产物挂靠 sub-goal 的具体格式，需在 21 号实施时定案。本条不预设选型结论。
