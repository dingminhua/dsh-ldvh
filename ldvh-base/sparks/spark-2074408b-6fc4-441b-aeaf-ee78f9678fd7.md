# LDVH 写入未纳入版本守卫

## 当前理解

10 §6 关于 fs/observed 写半的描述与实现范围不一致的初判**未能证实**——2026-10-16 的 05/10/06 三处核对与实现比对推翻了该前提。仍然成立的部分：LDVH 自身写入（登记载体经 @deepseek-ai/dsh-atomic-write，8 个事实 writer 各自 import node:fs/promises 自造原子写）均不经宿主 fs 服务，故 fs/write-intent 与 fs/edit-intent 对 LDVH 写入永不触发——守卫本身确实挂载且可达（host-seams.js:351-352），但仅对 OBSERVED_VERSIONS 中有条目的目标生效，而 LDVH 只观察登记载体（index.js:394 单点）。三处一致结论：① 谁承载写入版本守卫——00 §3.5 把受控写入定义为「写前受控入口／写后精确回读／Git Gate 终闸」三层，版本守卫不在其中，00 §2「核对实际结果」对应层②（已实现）；08 §5.6 对登记载体写的是「使用版本守卫或锁」，withFileLock 已满足该析取；事实对象的陈旧覆盖由 02 §10.1 的对象级 content_fingerprint CAS 基线对治。② 宿主 fs 不可用时如何如实披露——10 §6 末段与 §8 已有机械承载：fs 缺失时置 consumed:false + partial:true，detail 如实写明「listeners mounted, but the fs service is unavailable…」，snapshot() 逐缝输出且不省略未消费缝。③ 描述是否过宽——10 §6 第 153 行「其存在不证明 LDVH 已受其保护」、第 162 行「只对已观察过的目标主张版本」、§8 表格「不证明相应防护已生效…或覆盖全部受影响操作」三句恰在防止把「挂了缝」读成「覆盖全部写入」，故非描述过宽，而是读者预期与条文范围错位。对原 summary 两处断言的更正：其一，「陈旧 unavailable 永久拒绝写操作」为过度陈述——Map 虽无 delete/clear，但 scope 每轮 assemble 无缓存重算（guidance.js:54 resolve → recordScope → syncTools → recordJudgementForGuard），且 assemble 先于该轮任何工具调用，陈旧窗口实际为空；其二，「并发保护由 withFileLock 与原子写入承担」仅对登记载体成立，8 个事实 writer 既无锁也不经宿主 fs。真正的缺口不在 10 §6，而在事实对象写入的并发语义无规范承接：02 §10.6 规定「并发、单调令牌和协调锁的具体语义须由具体类型来源或执行来源定义」并明写受控提交与机械守护规范「不承接本项」，09 §3.2 亦确认排除；02 §10.6 同时禁止在此之前以对象指纹或单对象 CAS 冒充并发控制。故「何时纳入」的答案是：待类型来源定义并发语义时；登记载体已由 08 §5.6 的「或锁」满足，不需版本守卫。

**核实方法（只读，未改动任何规范与实现）**：读取 00 §2／§3.5、02 §10.1／§10.6／§13、05 §3.2／§10／§12、06 §3.2／§6、08 §5.6、09 §3.2、10 §6／§8 原文；比对 plugin/lib/host-seams.js、governed-projects.js、guidance.js、lifecycle.js、index.js 与 8 个 `*-writer.js` 的实现；只读核对 node_modules/@deepseek-ai/dsh-atomic-write 的实现来源（其 index.js 直接 `import { lstat, mkdir, rename, rm, writeFile } from "node:fs/promises"`，不接受 ctx、不 emit 任何宿主缝事件）。

**尚未核实的范围（据实声明）**：本次核对未实跑宿主，故 `fs/write-intent` 在宿主侧由谁 emit、以及宿主 fs 服务的实际可用性，均按代码路径与既有测试判定，未取得活体证据；`ctx.on` 对 `fs/write-intent` 的挂载语义（监听 vs waterfall）亦按既有实现与测试注释理解。这些不影响本页结论（结论只依赖「LDVH 写入不经宿主 fs 服务」这一实现事实），但构成保证边界。

## 调查问题

LDVH 对事实源与登记载体的写入何时纳入宿主 fs 的版本守卫，而不是仅靠原子写入与文件锁？

**当前已答／未答**：已答——原设想的三个选项（补实现／修正描述／维持现状）中，前两项的前提均不成立：10 §6 无须修正，登记载体亦无须补版本守卫（08 §5.6 的「或锁」已满足）。「何时纳入」的答案亦已得：事实对象写入的并发语义按 02 §10.6 归具体类型来源或执行来源定义，在该来源定义之前不得以对象指纹或单对象 CAS 冒充。**本条不再承接**：该来源的具体定义属类型来源的工作，超出本条 scope_boundary（其末段明示「不扩大至：重新设计事实源写入协议、引入第二套并发控制、或改动 00 §2 根方案本身」）。
