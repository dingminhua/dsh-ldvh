# LDVH 写入未纳入版本守卫

## 当前理解

08 §6 关于 fs/observed 写半的描述与实现范围不一致：LDVH 自身写入走 @deepseek-ai/dsh-atomic-write（直接用 node:fs/promises），不经宿主 fs 服务，故 fs/write-intent 与 fs/edit-intent 对 LDVH 写入永不触发——实测已确认。当前写入的并发保护由 withFileLock 与原子写入承担，版本守卫在 LDVH 自身写入上缺位。描述过宽已确认为缺陷（00 §7.1）；实现是否补齐待定。原子写入防「写坏」与版本守卫防「陈旧覆盖」性质不同，不可互替，后者对应 00 §2「受控写入并核对实际结果」。关联未决：LATEST_JUDGEMENT 无失效路径，陈旧 unavailable 会以已不成立的理由永久拒绝写操作（仅错拒、不错误放行）。

**追根路径**：`00 §2` 根方案规定「以 LDVH CLI 确定性服务承载读与写」，且须「把已经明确去向的内容受控写入，并核对实际结果」。实测发现 `fs/observed` 的写半挂在 `fs/write-intent` / `fs/edit-intent` 上，而 LDVH 自己的写入走 `@deepseek-ai/dsh-atomic-write`（其实现直接 `import { lstat, mkdir, rename, rm, writeFile } from "node:fs/promises"`），不经过宿主 fs 服务，因此该 waterfall 永不触发。

**实测证据**：装载守卫后执行 LDVH 真实写入路径——宿主 `fs.writeText` 未被调用，`fs/write-intent` 未触发。

**性质区分**：原子写入防「写坏」，版本守卫防「基于陈旧认知覆盖并发修改」；根方案所称「受控写入并核对实际结果」对应后者，两者不可互相替代。

## 调查问题

LDVH 对事实源与登记载体的写入何时纳入宿主 fs 的版本守卫，而不是仅靠原子写入与文件锁？
