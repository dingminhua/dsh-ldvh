# ADR/Friction 终态更正被实现阻断

## 当前理解

核对 Spark 终态语义注释（②，已由 `b6c84e7` 修正）时，对**全部五类**逐一比对「规范允许终态内容更正」与「实现是否放行」，发现 **ADR 与 Friction 两类实现与规范不符**，且该缺陷**未被任何对象登记**。

**缺陷一：实现无条件拒绝终态更新，规范却要求可更正**

| 类型 | 规范原文 | 实现行为 | 判定 |
|---|---|---|---|
| Spark | §9.2「终态不可重开，但内容可更正」 | 仅禁状态回转，放行更正 | ✅ 一致 |
| Pitfall | §9.2 同上 | 仅禁状态回转，放行更正 | ✅ 一致 |
| **ADR** | 22:166「错误的终态记录按 05 的事实更正规则修正，不伪装成状态转换」 | `if (prevStatus === "retired") return failure(...)` ——**无条件拒绝** | ❌ **不符** |
| **Friction** | 26:157「`resolved` 终态不重开（销错的账按 05 事实更正修正…）」 | `if (prevStatus === "resolved") return failure(...)` ——**无条件拒绝** | ❌ **不符** |
| Norm | 27:177「`retired` 保留为只读历史档案」 | 拒绝（与规范一致） | ✅ 一致 |

**代码证据（三行之差）**：

- `plugin/lib/adr-writer.js:585`：`if (prevStatus === "retired")` → 无条件 `failure("adr/status_terminal", "...the object is read-only (22 §9.2)...")`
- `plugin/lib/friction-writer.js:545`：`if (prevStatus === "resolved")` → 无条件 `failure("friction/status_terminal", "...the object is read-only (26 §9.2)...")`
- 对照正确写法 `plugin/lib/pitfall-writer.js:480`：`if (requested !== undefined && requested !== prevStatus)` —— 仅当状态被改动时拒绝

**后果**：ADR 若写错一条终态决策记录、Friction 若销错一笔账，**无法就地改正**——而两类规范都明文要求可以改。这不是注释问题，是行为缺陷（拒绝规范允许的操作）。

**成因（可回指）**：`5277f7f`（Human 决定 2026-09-13）的提交信息明确列出其作用范围为 **Spark 与 Pitfall 两类**（specs/20、specs/23、spark-writer、pitfall-writer 及其测试）。ADR 与 Friction **当时未被纳入**；而它们各自的规范里**已存在**「按事实更正修正」的表述（22:166、26:157）。故非「规范漏了」，而是「实现未跟上规范」。

**缺陷二（核对中另发现，与本条相邻但独立）：两类规范引用的目标不存在**

22:166 与 26:157 均写「按 **05** 的事实更正规则修正」。实测：**`specs/05-LDVH CLI规范.md` 全文「更正」零命中**（`grep -c` 得 0），其 §1–§12 无任何事实更正相关节。该规则实际由 `03 §9.5`（CAS 更新与更正）承载；21 §258 的同类表述写作「按事实更正规则修正」（不带 05 前缀），形态更准确。故该引用疑似失效或误引，须核实其应指向何处。

**来源**：本议题于 2026-09-27 由核对 ②（Spark 终态注释更正）时的横向比对产出，Human 指示「建成 Spark 登记」。

## 调查问题

ADR 与 Friction 的实现拒绝规范允许的终态内容更正，应如何修复，并使两类规范中「按 05 的事实更正规则修正」的引用指向真实承载？

## 调查边界

两类实现改为「仅禁状态回转、放行内容更正」（对齐 Spark/Pitfall 既有形态），且该引用改指真实承载或确认无需改动时停止；不要求实际完成实现改动。
