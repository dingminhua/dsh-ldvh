# 工具面 schema 与 writer 字段漂移

## 当前理解

各 `*-tools.js` 的 `frontmatter_draft.properties` 与各 `*-writer.js` 的 `VALID_FM_KEYS` 是两份独立维护的字段清单，必须一致：schema 声明 `additionalProperties: false`，故 schema 缺字段即该字段**经工具面完全不可写**（在进入 writer 前即被 DSH 参数校验拦下），writer 侧已写的校验沦为不可达代码。已发生实证：`aa12604`（2026-09-13 增设 Spark `priority`）改动 34 个文件却漏改 `plugin/lib/spark-tools.js`，导致任何带 `priority` 的调用被拒；该缺陷潜伏至 2026-09-13 被发现，修于提交 `b3f2ff6`。未被发现的原因：**无任何测试跨越「工具面 → writer」边界**——schema 用例只测负例、writer 用例只测自身，两侧皆绿而中间有缝。全类型审计（修正后）显示 adr/pitfall/friction/research/spark 五类一致，无第二处同类缺陷（adr/research 无 `retired_at` 系合法排除——该字段由 writer 自赋值，属 Code 托管）。

**已发生的实证**（`aa12604`，2026-09-13，增设 Spark `priority` 字段）：该提交改动了 34 个文件（`spark-writer.js`、21 个对象回填、web 侧契约、`specs/20`），**唯独漏改 `plugin/lib/spark-tools.js`**。后果：任何携带 `priority` 的 create/update 调用都在**进入 writer 之前**被 DSH 参数校验拒绝，writer 侧已实现的闭集校验与「仅 `status=open` 允许出现」互斥校验成为不可达代码。该缺陷自 `aa12604` 起潜伏至 2026-09-13 被发现。

**暴露方式值得记录**：727 个测试全绿，是因为**没有任何测试跨越「工具面 → writer」这条边界**——`spark-tools.test.mjs` 的 schema 用例只断言负例形状（拒绝缺 title 的 draft），`spark-writer.test.mjs` 测 writer 自身校验，两侧都对，中间那道缝无人测。缺陷最终是在「真的去经工具面写一个带 priority 的对象」时暴露的。

**旁证**：现有 21 条 open Spark 的 `priority` 之所以是「回填」进去的，正是因为当时只能靠直接改文件绕过工具面——这本身是一次**绕过受控写入路径**的操作（与 `2074408b`、`64754323` 所记的守卫缺口相关）。

**已完成的即时处置**（提交 `b3f2ff6`）：spark 侧 schema 补 `priority` 属性，与 writer 的 `PRIORITY_VALUES` 闭集对齐。同时已做一次**全类型机械审计**（writer 闭集 − Code 托管字段 − schema properties），结论：adr / pitfall / friction / research / spark 五类型在修正后**全部一致**，无第二处同类缺陷。（审计初期误报 adr/research 缺 `retired_at`，核实后退回——该字段由 writer 自行赋值，属 Code 托管，schema 排除它是正确的。）

## 调查问题

工具面参数 Schema 与 writer 字段契约的一致性应如何获得机械保障，而非依赖人工同步？

**当前状态：部分未答**。已在执行中采用但尚未定案的措施与待决问题：

1. **跨类型一致性守卫测试**是否建立——断言 `∀ 类型：writer 的 VALID_FM_KEYS − Code 托管字段 − schema properties = ∅`，使任何一侧漏改立即测试失败。本次审计是一次性手工比对，未固化为测试。
2. **正例测试**是否补齐——现有 schema 用例只测负例，缺「经工具面成功 create 一个带可选字段的对象」这类正例，而**正是这个盲区**让 `aa12604` 的缺陷潜伏。
3. **Code 托管字段清单**如何在守卫中声明——`object_uid`/`fact_type_key`/`created_at`/`change_log`/`retired_at`/`goal_key` 等由 Code 赋值，schema 排除它们是正确的；守卫必须显式区分「合法排除」与「漏改」，否则会产生误报。
4. **是否引入字段扩展的同步清单或流程约束**——`aa12604` 的根因是字段扩展横跨 writer / tools / web / specs 四处而无清单驱动。是否值得引入工程纪律物件，取决于守卫测试能否充分覆盖（若能，则规范增条目的成本高于收益）。
5. **范围是否限于 frontmatter 字段**——工具面与 writer 之间还有其他契约面（如 update 的 CAS 参数、枚举值闭集、必填性），是否一并纳入守卫。

## 调查边界

工具面 Schema 与 writer 字段契约的一致性获得机械保障（守卫测试落地并覆盖全部事实类型）时停止。不含各类型字段本身的语义设计（属 20–27 号规范）、不含 Git Gate 对事实对象内容的校验（属 64754323 与 2074408b 所记的守卫缺口）。

边界说明：本对象聚焦的是**两份手工维护清单之间的漂移**，而非「字段该不该存在」。它的价值判据是可机械判定的：守卫测试存在与否是二值的。另需注意本缺陷与「Git Gate 不校验事实对象内容」是**两个不同的缺口**——即使守卫测试落地，直接改文件绕过工具面的路径仍然不被拦截。
