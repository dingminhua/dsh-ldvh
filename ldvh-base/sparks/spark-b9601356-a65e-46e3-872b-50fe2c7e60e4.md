# 工具面 schema 与 writer 字段漂移

## 当前理解

各 `*-tools.js` 的 `frontmatter_draft.properties` 与各 `*-writer.js` 的 `VALID_FM_KEYS` 是两份独立维护的字段清单，必须一致：schema 声明 `additionalProperties: false`，故 schema 缺字段即该字段**经工具面完全不可写**（在进入 writer 前即被 DSH 参数校验拦下），writer 侧已写的校验沦为不可达代码。已发生实证：`aa12604`（2026-09-13 增设 Spark `priority`）改动 34 个文件却漏改 `plugin/lib/spark-tools.js`，导致任何带 `priority` 的调用被拒；该缺陷潜伏至 2026-09-13 被发现，修于提交 `b3f2ff6`。未被发现的原因：**无任何测试跨越「工具面 → writer」边界**——schema 用例只测负例、writer 用例只测自身，两侧皆绿而中间有缝。全类型审计（修正后）显示 adr/pitfall/friction/research/spark 五类一致，无第二处同类缺陷（adr/research 无 `retired_at` 系合法排除——该字段由 writer 自赋值，属 Code 托管）。

**已发生的实证**（`aa12604`，2026-09-13，增设 Spark `priority` 字段）：该提交改动了 34 个文件（`spark-writer.js`、21 个对象回填、web 侧契约、`specs/20`），**唯独漏改 `plugin/lib/spark-tools.js`**。后果：任何携带 `priority` 的 create/update 调用都在**进入 writer 之前**被拒，writer 侧已实现的闭集校验与「仅 `status=open` 允许出现」互斥校验成为不可达代码。该缺陷自 `aa12604` 起潜伏至 2026-09-13 被发现。

**暴露方式值得记录**：727 个测试全绿，是因为**没有任何测试跨越「工具面 → writer」这条边界**——`spark-tools.test.mjs` 的 schema 用例只断言负例形状（拒绝缺 title 的 draft），`spark-writer.test.mjs` 测 writer 自身校验，两侧都对，中间那道缝无人测。缺陷最终是在「真的去经工具面写一个带 priority 的对象」时暴露的。

**旁证**：现有 21 条 open Spark 的 `priority` 之所以是「回填」进去的，正是因为当时只能靠直接改文件绕过工具面——这本身是一次**绕过受控写入路径**的操作（与 `2074408b`、`64754323` 所记的守卫缺口相关）。

**已完成的即时处置**（提交 `b3f2ff6`）：spark 侧 schema 补 `priority` 属性，与 writer 的 `PRIORITY_VALUES` 闭集对齐。同时已做一次**全类型机械审计**（writer 闭集 − Code 托管字段 − schema properties），结论：adr / pitfall / friction / research / spark 五类型在修正后**全部一致**，无第二处同类缺陷。（审计初期误报 adr/research 缺 `retired_at`，核实后退回——该字段由 writer 自行赋值，属 Code 托管，schema 排除它是正确的。）

## 调查问题

工具面参数 Schema 与 writer 字段契约的一致性应如何获得机械保障，而非依赖人工同步？

**已答毕**。原列五项待决的落地结果：

1. **跨类型一致性守卫测试**——已建立。`plugin/test/schema-writer-agreement.test.mjs`（随 `16d84f1` 进入）：对 spark / adr / pitfall / friction / norm / research 六类断言 `writer 闭集 − Code 托管字段 − schema properties = ∅`，并有元测试扫 `*-writer.js` 反查覆盖，新类型漏挂即失败。
2. **正例测试**——已补齐。`spark-tools.test.mjs` 新增「create: optional fields (priority/serves) succeed through the tool plane and land on disk」与一条直测声明 schema 的断言。
3. **Code 托管字段清单**——已在守卫中显式声明：`CODE_ASSIGNED` 列出 `object_uid`/`fact_type_key`/`created_at`/`change_log`/`retired_at`/`goal_key`，区分「合法排除」与「漏改」，误报来源已消除。
4. **是否引入字段扩展的同步清单或流程约束**——**裁定不引入**（Human，2026-09-14）。理由：守卫已能机械覆盖字段漂移，把手工比对固化为可重复断言；此时再增规范条目的成本高于收益。若未来出现守卫覆盖不到的漂移面（如 web 契约侧独立漂移），再重新评估。
5. **范围是否限于 frontmatter 字段**——**裁定不扩展**（Human，2026-09-14）。CAS 参数、枚举闭集、必填性在工具面与 writer 两侧本就由同一份 schema 声明驱动，不构成「两份手工清单」的漂移面，故不纳入本守卫。

**过程中的一处修正（2026-09-14）**：本对象原先把「在进入 writer 前即被 DSH 参数校验拦下」作为机制描述。后续实测发现 LDVH 的 `toolDescriptorFor` 返回裸描述符、从不经过 `defineTool`，而 DSH 的参数校验只存在于 `defineTool` 闭包内，`ToolRuntime` 注册与派发均不再校验——即该描述假定了一个并不存在的运行时校验环节。此项另立 `5b0b380e`（工具参数校验层不生效）跟踪，不在本对象内解决。

**守卫的加固（2026-09-14）**：原守卫只比对两份字段**清单**，能证明字段「被声明」，不能证明携带该字段的调用「真能通过校验」。加固后新增一条测试，对每个类型 × 每个 writer 声明的可选字段，直接调用 DSH `defineTool` 内部使用的 `validateJsonSchemaValue` 构造真实校验，字段名取自 writer 闭集而非 schema（故不依赖被测对象自身）；另加一条防退化自检测试，在内存中重建 `aa12604` 缺陷并断言守卫会捕获它。反向验证：三次注入真实缺陷，第三次确认报出与当年逐字相同的错误 `"frontmatter_draft.priority" is not a declared property (additionalProperties: false)`。

## 调查边界

工具面 Schema 与 writer 字段契约的一致性获得机械保障（守卫测试落地并覆盖全部事实类型）时停止。不含各类型字段本身的语义设计（属 20–27 号规范）、不含 Git Gate 对事实对象内容的校验（属 64754323 与 2074408b 所记的守卫缺口）。

边界说明：本对象聚焦的是**两份手工维护清单之间的漂移**，而非「字段该不该存在」。它的价值判据是可机械判定的：守卫测试存在与否是二值的。另需注意本缺陷与「Git Gate 不校验事实对象内容」是**两个不同的缺口**——即使守卫测试落地，直接改文件绕过工具面的路径仍然不被拦截。
