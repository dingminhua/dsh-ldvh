# 规则遵守系统的功能重定位与双源召回命名

## 当前理解

经多轮对齐，规则遵守系统的真实功能被重新定位为「在恰当时候召回当前规范源和事实源的相关信息」，而非我此前理解的「预检记录的事后质检」。依据有三：(一) 34 §7「输入来源」明写规则来源经 L0–L4 读取取得、事实来源经 F0–F4 召回取得——输入本身就是召回操作；(二) 34 §8.1 第 1 项「适用识别」定义为「从来源中找出与当次行动相关的规则、事实、决定与授权」，「找出」即召回；(三) 上一轮对话 session-a6a973c2 已得出「识别等同于同一个 recall」的结论。功能重定位的实践含义：事实类型的细分（Norm/ADR/Pitfall/Research/WorkCase/Friction/Spark 共七类 311 个对象）本身就是召回的索引维度，role+status+scope 即确定性过滤条件，故召回可走零依赖启发式而不必上向量——此点由仓内两份独立调研印证（0b3471af A3、fd133f0d A2，Mem0 实测图增益仅约 2%）。业界失败模式诊断与 LDVH 现状吻合：resonant 明言「记忆是工具、要 agent 自己想到去搜，没想到就不浮现」，而 Strands MemoryInjectionConfig 与 dsh-agent-memory 的 pre-step 动态召回均在模型调用前自动注入 top-N，不等 agent 自觉；LDVH 现在的 ldvh_read_specification_* 与 ldvh_*_list 全是工具，需我主动调用才有效，正是该失败模式。命名问题：「规则遵守」名实不符，三点理由——(一) 34 §1 末句明文「预检已完成、约束已识别或记录已生成，均不能单独证明约束已被遵守」，系统自称不能证明遵守而名取「遵守」；(二) 34 §7「适用条件」的对象是约束来源（规则、事实、决定或授权）四类，「规则」一词过窄；(三) 其余六个业务系统名均为动作词（规划/记录/执行/吸收/积累/销账），唯有「遵守」是状态词，而系统实际动作是召回。命名结论（2026-10-24 三改后定案）：定名「双源召回」。理由：(一) 「双」有根规范依据——00 §3.2 标题即「两类语义构成要素与规范源、事实源」，明文「规范与事实是 LDVH 组织语义的两类要素」且「Code、Web、工具输出和宿主能力不构成第三类语义构成要素」，故双源字面即规范源与事实源，不必硬编数字；(二) 经验（Pitfall）作为事实源七类之一自然在内，不必勉强归入「约束」；(三)「召回」是动作而非断言，不像「遵守」声称自己证明不了的状态；(四) 四字符合七系统「对象+动作」格式；(五) 事实源将来再加类型不用改名（仍只有两个源）。规范重写方向：34 号应以召回为主轴重写，把「识别」明确为召回动作本身，落实与记录退到检查层（04/05/09）；实现侧已建 source-recall.js 承接该召回（确定性分层布尔匹配、现读现解析、无持久索引、带字节预算），此前建成的 2072 行 precheck-record.js 退为召回结果的质量检查而非主体。

分层展开：

**功能重定位的规范依据**：34 §7「输入来源」把四类来源的取得方式写死了——规范源经 L0–L4 读取、事实源经 F0–F4 召回。也就是说，这个系统的工作从一开始就是「调召回」，不是「造记录」。34 §8.1 第 1 项对「适用识别」的定义（「从来源中找出……」）进一步印证：识别的本体就是找出，即召回。

**召回为何可低成本高效**：事实类型七分（Norm 规则/ADR 决定/Pitfall 教训/Research 调研/WorkCase 工单/Friction 摩擦/Spark 议题）本身就是索引维度。每类的 frontmatter 字段（title/status/scope/trigger_signal/decision/phenomenon/question/gist）即天然的匹配面。故确定性 token 匹配足够，不必上向量——这也是 0b3471af A3 与 fd133f0d A2 两份独立调研的共同结论。

**经验必须单独点名**（2026-10-24 补）：34 §7 的四类措辞「规则、事实、决定或授权」里没有「经验」。我起初把 Pitfall 塞进「事实」算覆盖，并据此建议「约束召回」；Human 指出「经验也要召回」，复核后确认：经验在行动时的用法与约束不同——约束（Norm/授权）说「必须/不得」，决定（ADR）说「已拍板」，经验（Pitfall）说「上次这么做踩了坑」。把经验/议题/工单都挤进「约束」是勉强的。

**「双」的规范依据**（2026-10-24 补）：00 §3.2 标题即「两类语义构成要素与规范源、事实源」，正文「规范与事实是 LDVH 组织语义的两类要素，职责分工、互不替代」，并明文「Code、Web、工具输出和宿主能力不构成第三类语义构成要素。要素分类以本节为准」。故「双源」不是实现侧硬编的数字，而是根规范定死的两类；即便事实源再加类型，仍是这两类之下的细分。

**业界同构做法**：Strands MemoryInjectionConfig「在模型调用前搜记忆、把 top 结果放进那次调用，不必等 agent 自己想到去搜」；dsh-agent-memory 0.8.4 的 pre-step 动态召回以用户消息作 query 注入 top-3，且明确替代「固定热集广播」（v0.1→v0.2 实测教训：多项目场景固定热集命中率低）；mem0 Proactive Memory 用环境信号（时间/项目/最近文件）定时机。注入侧必须带字节预算（fd133f0d A3，以 Anthropic 注意力预算为一手依据）。

**命名三点理由的原文回指**：34 §1 末句「不能单独证明……约束已被遵守」→ 名取「遵守」自相矛盾；34 §7「适用条件」的「约束来源（规则、事实、决定或授权）」→ 对象是四类，「规则」过窄；七个系统名的动作/状态词性对照 → 唯「遵守」是状态词。

**实现现状**：已建 plugin/lib/source-recall.js 承接召回（载入两源、确定性四层布尔匹配、按层排序不算分、现读现解析、带字节预算、如实标 truncated 与 coverage）。此前七轮建成的 precheck-record.js（2072 行/59 导出/234 用例）事后确认为错层——它做的是记录的事后质检，对「行动前召回」这一目的约 85% 无用；其 checkEntry（时机）、checkRiskRouting（深度）、detectRitualRecord（护栏）三项保留，余下退为召回结果的质量检查。

## 调查问题

规则遵守系统的实际功能是「在恰当时候召回规范源与事实源」而非「记录格式的事后质检」，这一重定位是否成立、该系统应改为何名、其规范应如何重写？
