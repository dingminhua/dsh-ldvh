# 关键变更路径覆盖的宽松匹配

## 当前理解

Git Gate 的 K1 双向路径覆盖校验中，反向半边（每个非豁免暂存路径须被某条「关键变更」项覆盖）的匹配函数对路径做目录段回退：只要消息项含路径的任一目录段（如 plugin、web），该路径即算被覆盖。源码注释自认此为 known limitation，测试固化其为有意设计（为兼容 diffstat 式区域命名）。代价是同一目录下的范围外污染——典型为并行会话的 git add 落入共享 Index——不被拦下，实际已发生一次（32 个 plugin/web 文件被随同提交）。已确认的判断：①该回退是有意设计而非缺陷，故处置不是修 bug，而是权衡「收紧规则」与「如实登记代价」；②收紧会破坏 diffstat 式区域命名的既有用法与对应测试，代价收益尚未计算；③防御侧经验（Pitfall 86d23c1a）已记「提交时显式 pathspec」为必需措施，但那只降低发生率，不能使校验本身可依赖。未决：收紧到何种粒度（精确路径级匹配，或目录段词须整段匹配并排除通用词）；是否须在 specs/06 §6.3 或 specs/08 §6 如实登记该已知边界与代价；是否与同门议题 64754323（precheck 与 Git Gate 检查覆盖不一致）合并处置。

**为什么保留**：这是防自欺锚点（「关键变更」逐路径对应）在反向半边上的可绕过口子，已导致一次范围外内容被静默提交；且该隐患于 2026-09-10 已被记录，却在归档时被误判为已由 Spark 承载，至今无人承接。后续方向：判定「收紧匹配」与「如实登记代价」何者成本相当，并决定是否与同门议题 64754323 合并处置。

**机制细节（供后续执行者判断，不进 frontmatter）**：

- 反向半边取未覆盖集：`plugin/lib/commit-validation.js:143-145`；匹配函数 `itemMatchesPath` 在 `:166-173`，三分支依次为全路径包含、basename/stem 包含、目录段回退（`const segments = path.split("/").filter((segment) => segment.length > 2 && !/\d/.test(segment)); return segments.some((segment) => item.includes(segment));`）。
- 源码注释 `:105-122` 自述该半边的用途（把并行会话 git add 造成的暂存污染转成响亮的拒绝）并紧接着自认 `known limitation: a same-directory pollution where some item happens to contain a shared directory word (e.g. "plugin") is not caught`。
- 测试 `plugin/test/commit-validation.test.mjs:432` 名为 `checkKeyChangesAgainstDiff passes when items cover every staged path (grouping via directory word)`，断言区域命名覆盖两文件时 `result.ok === true` ⇒ 回退是有意设计。
- 隔离实验（可复现）：消息项写「docs/mine.md 新增；实测该号位在 specs 与 plugin 中零引用」＋ diff 含两个 `plugin/web/src/**` 路径 ⇒ PASS；把该项改为不含 `plugin` 一词 ⇒ `FAIL -> validation/staged_path_uncovered`（两条）。
- 同门议题 `64754323` 的对象是**正向**覆盖不一致（precheck 查签名取值来源、Git Gate 不查），与本项的反向匹配宽松不是同一机制，但在「提交校验的检查覆盖不完整」这一层同源。

**既有登记（非事实对象，故只能作为依据引用而不能作为 refs）**：`docs/archive/restructure-decision-list-2026-09-10.md:106`（§5 第 5 项）已写明「「关键变更:」逐路径覆盖在宽松匹配下几乎不设防（目录词即算覆盖），摩擦却全部转嫁给第三方项目的人类贡献者；且 hook-manager 在项目无 commit-msg 时静默安装」。该清单按方案 B 归档时登记为「内容已由 dbffddd2 / 64754323 / 2e79939a 承载」（`docs/archive/README.md:51`）；经逐条核验，三者分别是执行系统立项、签名取值来源 fail-open、WorkCase 立项，对「宽松」/「目录词」/「pathspec」三词均零命中 ⇒ **归档覆盖判据对该第 5 项不成立，属一次反例**。本对象即为该悬置项的承接。（第 5 项提到的 hook-manager 静默安装一说尚未核实，不在本对象范围内。）

## 调查边界

**边界的含义**：停止条件是**处置路径之一被择定并落实**，不是「该漏洞被完全消除」。三条路径各自成立即可停止：

1. **收紧**——把匹配规则改为路径级判定（或保留目录段回退但限定为整段匹配并排除通用词），并相应更新测试与既有提交消息撰写惯例；
2. **登记**——不改正向行为，转而在规范侧（候选落点 `specs/06` §6.3 或 `specs/08` §6）如实登记该已知边界与代价，使「校验能覆盖什么、不能覆盖什么」不被过度主张；
3. **不适用**——经 Human 判定该类宽松匹配对本管辖区不构成须处置的问题，给出理由后停止。

**明确不包含**：同门议题 `64754323` 所涉的正向覆盖不一致（签名取值来源未查）本身，不在本对象边界内——只包含「是否与之合并处置」这一判定。
