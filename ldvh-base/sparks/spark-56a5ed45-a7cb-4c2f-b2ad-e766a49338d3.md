# 新事实类型候选准入

## 当前理解

**来源**：`technical-framework-mnemon-base.md` §2.4「终局目标：装了 LDVH 就不用装 mnemon」，§8「新事实对象讨论（已启动，2026-09-03）」自述「**未定案，按 02 §6.2 准入六问逐项判**」；§8.1「补充议题：事实源的『人能看』承诺与规范类文档（Human 提出 2026-09-03）」。

**议题 1 · mnemon 三层记忆的对应承载形态**（候选方向，未定案）：Runtime 热记忆（USER.md/MEMORY.md）→ 不一定是事实对象，可能只是插件自管的注入层或五类之外的轻量载体，关键问题＝与 DSH 宿主 runtime memory 的边界（重复还是增强？写入是否也受控？）；Documents（项目文档）→ 可能是新事实类型（「项目文档/笔记」）也可能归入 Research/Spark 扩展，关键问题＝与 Research 的边界（Research 是研究报告，项目文档是工作记录——分开还是合并？）；Memory Spaces（长期知识）→ 可能根本不需要对象化，关键问题＝LDVH 是否要「跨项目记忆」，与 08 单项目工作对象边界如何调和。

**议题 2 · 「人能看」承诺与规范类文档**：两类新内容冲击「事实源人能看」承诺——① code/web 设计文档（人不看，消费对象是 AI）；② 规范类文档（审计/测试/发布规范，人要看且「像规范又像 ADR」）。**建议（未定案，准入属 Human Gate）**：① 设计文档**不对象化**，保持 docs/ 现状，立纪律「**设计文档禁止藏规则**」，约束性内容必须上浮为 ADR 或规范（docs/ 是解释不是约束）；② **规范类文档立新类型（暂名 Practice/实践规范）**，与 ADR 按行业「决定与规则分离」共识分工——ADR 记「为什么」（决定+理由+适用范围，决策时刻快照，改决策=新 ADR 替代），Practice 记「怎么做」（检查清单/步骤/标准，长期演化，change_log 承载修订）；互引（ADR consequences 指向 Practice；Practice change_log 首条回指 ADR）。**行业对照**：ADR 运动决定/规则分离、IETF BCP 系列、Diátaxis 四象限、Policy-as-Code、开源根目录惯例。

**注意**：`specs/27-Norm-事实规范.md` 已存在（Norm 类型已立项并定稿），与本文档 2026-09-03 提出的 Practice 候选**是否同一物的不同命名或不同设计**，须核对——这是本 Spark 的首要查重点。**讨论原则（Human 定）**：以「满足什么问题」为准入唯一依据；mnemon 的形态是参照不是模板；任何新类型在 20–24 重建之后按同节奏起草规范（编号待分配，可能 25+）。

**号位注记（2026-10-14，批次 G 事实更正）**：本单创建时点（2026-09-12）所引「03 §5.2」（准入六问）为时点号位——该事实模型规范经 02–10 重构现为 `specs/02-事实源与事实模型基础规范.md`，其事实模型准入为 §6.2；「07 单项目工作对象边界」所指管辖范围规范现为 `specs/08`。摘要、意图、调查边界与正文内该两处引用已按现行号位更正；文内 20–24、27 号位未随重构变动。

### 2026-10-28 议题 2② 核对结论：Practice 候选已由 27 号 Norm 吸收，不另立类型

**本 Spark 原文的首要查重点**（「27 号 Norm 与 2026-09-03 的 Practice 候选是否同一物的不同命名或不同设计」）**已有确定答案**：是同一物，且设计与分工都已写在既有规范里，故**无需新类型**。逐条比对如下（Practice 候选的每一项设计主张，都能在 27 号找到对应条款）：

| Practice 候选的主张 | 27 号 Norm 的对应 | 出处 |
|---|---|---|
| 记「怎么做」：检查清单／步骤／标准 | 承载「一个完整工程方向的**成体系规则体系**」，三条判据之首为「多条可独立执行的规则」 | 27 §5 |
| 长期演化，由 change_log 承载修订 | 受控更新 + 每次恰好一条 change_log | 27 §13 |
| 与 ADR 按「决定／规则分离」分工 | ADR 的 `absorbed-into` 关系键**已把这个分工写成契约**：决策内容被某方向的 Norm 完整承接时，ADR 退出约束转历史依据 | 22 §11 |
| 「像规范又像 ADR」的边界困惑 | 已由主动作分离解决，不需要第三处权威 | 22 §11 / 27 §5 |
| 立新类型（暂名 Practice） | 方向键排他（一方向至多一个 active Norm）已覆盖「一个方向一份规则」的诉求 | 27 §11 |

**为什么不立**：29% 的核心理由不是「27 号已有」这件事本身（02 §6.2 明言「历史中曾有同名类型」不能单独证明准入），而是**02 §6.2 第 3 问的回答已经变了**——「普通文档、已有事实类型或其它稳定位置为什么不能无损承载」这一问，在 27 号建成之后已能答「能承载」。Practice 立项时（2026-09-03）27 号尚不存在，该问无从回答；现在答案是有。

**若仍要立 Practice，须先回答的反问**：它的消费者是谁、与 Norm 的边界如何机械区分、同一份「怎么做」出现两处权威时以谁为准。这三问在 27 号已答的前提下，新类型的举证责任在提议方（与 35 §8.3「判据 1/2 先于 5」的举证方向一致）。

**该结论的边界**：本条只覆盖议题 2②（规范类文档是否立新类型）。**议题 2①（设计文档不对象化 + 「禁止藏规则」纪律）未核**——它需读 `docs/` 现状并判断纪律落点，属纪律设立，须 Human 决定。**议题 1（mnemon 三层记忆如何承载）未核**——它牵涉 `specs/08` 的单项目工作对象边界与 DSH 宿主 runtime memory 的边界，是独立领域，建议单独立项而非在本条内推进。
