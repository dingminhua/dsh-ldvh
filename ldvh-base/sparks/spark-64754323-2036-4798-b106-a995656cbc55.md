# Git Gate 的 fail-open 通路

## 当前理解

已闭合（2026-11-05，workcase-608786b8，bf64380）：Git Gate 在受管提交内用 shell 权威路由校验取值来源，路由不可得即 validation/signature_source_unverifiable 阻断；09 §5.5 分派已实现，两入口共用 checkSignatureAgainstRoute。

Git Gate（commit-msg hook）与 precheck 的检查覆盖不一致，构成 fail-open 通路：`09 §5.1` 要求两入口都校验 trailer 的「存在、取值来源和候选一致性」，但 precheck 查取值来源，而 Git Gate 只查存在性（`validateMessage` 的 `commit-validation.js:150-154` 只管两行是否各恰好一行非空）——**取值是否属实，钩子里一字不查**。结构原因：钩子是 Git 在提交时新起的独立进程，其入参只有 `--workspace-root`／`--worktree`／`--message-file`／`--index-file`，拿不到当次权威路由，故「钩子也查」不是加一行调用而要补一条通道。并存的第二处不一致：`09 §5.5` 写普通提交「直接放行」（按内容分派），实现无分派、一律全套检查。两条方向：补通道使两入口同源，或收窄规范把取值来源校验明确落到 precheck——二者都要动规范，不存在纯实现路径。

### 核实明细（2026-11-02，只读）

- **precheck 一侧确实查取值来源**：`plugin/lib/ldvh-tools.js` 调 `currentRouteValues(deps.sessionPersistence?.(), exec?.agent)` 取当次权威路由，交 `checkSignatureAgainstRoute`；路由不可得时返回 `{ok:false, hardFail:false, issues:[]}`，即**三值语义的 unverifiable**，不硬判失败；取到而 trailer 不一致时发射 `validation/signature_provider_mismatch`／`validation/signature_model_mismatch`。
- **Git Gate 一侧当时只查存在性**：commit-msg 入口为 `const issues = [...validateMessage(message), ...shared.issues];` 再加 `checkKeyChangesAgainstDiff(...)`。`validateMessage` 对签名只做 `matches.length !== 1` 的存在性判定（rule 为 `validation/signature_trailer_missing`）。两个 mismatch rule 虽已在 `GATE_RULES` 冻结表注册，但**当时只有 precheck 侧那一处发射点**。
- **钩子侧补不齐的结构原因**：`hook-manager.js` 全文 `session` 零命中；`git-gate-runner.js` 无 `DSH_*`、无 `sessionPersistence` 引用。**故这不是漏调一个函数，而是缺一条把当次权威记录交给钩子的通道。**

### 核实更新（2026-11-04，只读）

- **行号位移，结论未变**：precheck 取权威路由与 mismatch 发射点在 `ldvh-tools.js`；Git Gate 的 commit-msg 入口为 `runCommitMsgChecks`（`git-gate-runner.js:576`），`validateMessage` 调用在其 `:591`；`commit-validation.js:150-154` 的存在性判定未变。两处不一致（取值来源未查、无内容分派）在 2026-11-04 的代码上仍成立。
- **方向 1 的成本判断须更正——通道的一半已经存在**：`plugin/lib/session-signature.js` 已有 shell 路径 `currentRouteValuesFromShellEnvironment()`／`shellAuthoritativeSignature()`（b1368f8，2026-09-12），按 `DSH_SESSION_JSONL` 或 `$DSH_HOME/sessions/<cwd>/<DSH_SESSION_ID>/session.v<N>.jsonl[.zstd]` 尾读当次权威路由。实测（本会话 DSH shell 子进程内）返回 `{provider:"dsh-opencode-go", model:"deepseek-v4.1-flash", eventType:"request/context"}`——**由 DSH shell 子进程发起的提交，其 git 进程继承 `DSH_*`，钩子据此能取到权威路由**，无须另建通道。
- **更正边界**：「钩子拿不到当次权威路由」在**由 DSH shell 子进程发起**的提交上已不成立；在**不由 DSH shell 发起**的提交（人工终端、IDE、GUI 客户端）上仍成立。故方向 1 的剩余成本是：① 钩子侧接线；② 路由不可得时的语义；③ 与 `09 §5.5` 内容分派的次序（若不先实现分派，闸门会对普通提交也因取不到路由而误拦）。此处只更正成本事实，择向由 Human 决定。

### 闭合记录（2026-11-05，workcase-608786b8 / commit bf64380）

- **择向为方向 1（补通道），落地形态**：`git-gate-runner.js` 的 commit-msg 入口在受控提交内调用 `currentRouteValuesFromShellEnvironment()` 取当次权威路由，与该入口共用 `commit-validation.js` 导出的 `checkSignatureAgainstRoute`；路由不可得时发射 `validation/signature_source_unverifiable` 并阻断（09 §5.5「非 passed 即阻断」）。precheck 的三值语义未改。
- **09 §5.5 分派同时实现**：`touchesGovernedContent`（`AGENTS.md`、`ldvh-base/**`、`specs/**`）在受控提交前先分派，普通提交直接放行；空 Index 仍进 `git/index_empty`。
- **两处已声明差异**（09 §5.1／§5.5 明写）：① 路由不可得时 precheck 返回 `unverifiable`、提交缝阻断；② 仓库根 `README.md` 在 §5.3 第 5 项的预检范围内、但不在分派触发面内（Human 2026-11-05 决定 B），README-only 提交在 Gate 放行、预检仍查。
- **保证边界**：主动伪造 `DSH_SESSION_ID`／`DSH_SESSION_JSONL` 指向自造日志挡不住——本机制闭合的是「取值未核对」的静默缺口，不是有意的环境伪造。
- **验证**：全量 `npm --prefix plugin test` 3055 项、3053 通过、0 失败；拆阻断与关分派两次变异均被对应用例检出并还原。

### 后果

`LDVH-Provider` / `LDVH-Model` 两行可以写任意值而通过真实提交路径。防自欺锚点（`09 §5.1`：「由 Code 从 DSH 当次权威会话或请求记录机械取得并写入，AI 不判断、选择或填写」）在实际提交上失效，只在 AI 自觉先跑 precheck 时才成立。这与 Human 决定 2026-09-02 拒绝设 Human-Gate 行的理由同源——自报文本无机械来源，无法防自欺；区别在于 trailer 的取值**本可以**有机械来源，只是钩子拿不到。上节记录的是该落差的闭合结果。

### 第二处不一致：内容分派

`09 §5.5` 原文「Git Gate 依据 staged 内容是否触及受管载体（`ldvh-base/` 事实对象）、规范源文件、规则源成员变更或仓库根 `AGENTS.md`，判定当次提交是否按受控提交契约检查；不含上述内容的普通提交在 hook 中直接放行」。实现侧当时 `runCommitMsgChecks` 无任何分派，对**所有**提交一律跑全套检查；唯一按路径过滤的是 `checkDocsReferences` 内部。方向是**收紧**（比规范更严），故不是安全漏洞，但与规范原文不符，属同一族「两入口/两文档不一致」——已按上节随分派一并收束。

### 两条可走的方向（2026-11-05 已择定方向 1）

1. **补通道**——使钩子能取得当次权威记录（环境变量注入／提交时把权威值随候选落盘／经 `LDVH CLI` 确定性服务查询），两入口真正同源。成本在通道，不在检查逻辑本身（`checkSignatureAgainstRoute` 已是现成函数）。
2. **如实收窄**——若通道成本高于收益，则改规范表述：把「Git Gate 机械校验取值来源」改为「precheck 校验取值来源，Git Gate 校验存在性」，并把「提交前必须过 precheck」写成可核对的义务。代价是真实提交路径上的取值来源**仍无机械保障**，须在规范里如实声明这一点，不得留下「已校验」的读法。

**关键判断**：两条都与 `09 §5.1`／`§5.5` 现有措辞冲突，**必有一处规范改动**，不存在「只改实现不动规范」的路径。这一点在择向时已先认下来。

## 调查问题

precheck 与 Git Gate 的检查覆盖不一致（签名取值来源未查）应如何闭合？

## 调查边界

实现与 `09 §5.1/§5.3` 契约一致、fail-open 通路闭合、有机械校验覆盖时停止。

**边界的含义**：停止条件是**两入口的覆盖关系被择定并落实**（补通道或收窄规范二者之一），不是「钩子也查了」。若择定收窄，则「取值来源」的校验责任须在规范中明确落到 precheck 一侧，且「提交前过 precheck」须有可核对形态；否则不构成闭合。**明确不包含**：同门议题 `spark-c48af9e6`（关键变更路径覆盖的宽松匹配）所涉的反向匹配机制本身，只包含「是否与之合并处置」这一判定——该判定已作出：**不合并**，见该对象。
