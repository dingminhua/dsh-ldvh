**Human 方向性主张：specs 是开发文档、交付应为提炼后的生产内容（2026-11-21，待共同研究，未裁决、未改任何规范/代码/打包）**：

Human 原话：「specs 只是一份开发文档，真正交付的不应该包括 specs，而是最后提炼出来用于生产的内容，这个写入到 spark，我们之后一起研究。」

主张要旨：把 specs/（元规范＋事实规范文档）定位为**开发期文档**，生产交付物应是**从 specs 提炼出来、用于生产的内容**，而非 specs 原文本身。这与本 Spark 已承载的根本性判断①（LDVH 靠注入规则进上下文兑现价值，路径对不对须评估）、②（无机械保障则注入未必兑现价值）同向——若 specs 是开发文档，则「把 specs 原文打进生产包并注入」这一当前形态正是须重新评估的对象。

**当前交付现状取证（本轮实测，供研究起点，非裁决）**：
- `plugin/package.json` 的 `files` 字段含 `"specs"`（与 lib/icons/web/dist 等并列）；`scripts.prepack = node scripts/specs-bundle.mjs copy && node scripts/require-web-dist.mjs`，`scripts.postpack = node scripts/specs-bundle.mjs clean`——即打包时把仓库根 specs/ 复制进包内副本、发布后清理。
- 发布规范 norm-80c95693 门禁 4「打包内容核对」清单含 `specs`；产物边界汇总明文「**发布产物须包含 specs**（核对见门禁 4）；不得包含 ldvh-base/ 下任何事实对象路径」。
- 即：**现状是 specs 原文入生产包**，与 Human 主张「交付不应包括 specs」直接相反。这是待研究的张力，不是已决定的变更。

**待共同研究的问题（记录，不预设答案）**：
- 「提炼出来用于生产的内容」具体指什么形态？候选方向（仅列举、未选定）：① 把 specs 规则编译/提炼为注入引导文本＋工具说明＋机械校验代码（harness），生产只交付提炼物、不交付 specs 原文；② specs 仍随包但仅作开发参考、不参与生产注入；③ 其它。需 Human 定方向。
- 与现行规则的冲突面：发布规范门禁 4/产物边界「须包含 specs」、00 §2.4 规范源承载、双源召回 L0–L4 读取面（ldvh_read_specification_content 读 specs 原文）都依赖 specs 在场；若生产不含 specs，这些消费面如何承接须一并设计。属受保护内容/下位规范实质修改，须独立审核＋Human Gate，不擅动。
- 与「规范无机械承载必漂移」的关系：若 specs 仅作开发文档、生产靠提炼物＋机械承载，恰是内部调研结论「可机械化者落 harness/schema」的落地形态；但提炼物本身也会漂移（guidance-text.js:45 口径漂移即实例），须配语义保障（G3）。

本主张已纳入本 Spark 作为「如何更好保障并实现 LDVH 价值」的又一输入，与注入精简、触发有效性、根本性判断①②并列；**之后共同研究**，本轮仅记录＋取证，不改实现、不改规范、不改打包。

**量化证据：用户实际工作需要用到的 specs 内容很少（2026-11-21，Human 追问「实际工作需要用到的内容、对用户来说需要用到的有多少」后按用途实测；支撑上述主张）**：

口径澄清：Human 问的不是「运行时注入多少字节」，而是「**用户实际干活需要用到 specs 的哪些内容**」——按用途切，不按注入切。主控先误按注入维度答（身份块 1.1%＋引导 0.36%），经 Human 纠正后改按用途三分。

按用途三分（全量 31 份 605,361 字符，UTF-16 口径；分类依据各份 positioning/scope 原文，属主控语义判断、非机械判定，Human 可推翻）：
- **A 纯开发/实现文档（12 份，142,329 字符，23.5%）**：01 规范源模型、05 CLI 契约、06 Code 实践、07 Web 呈现、08 管辖范围、10 环境接入＋6 份附件（双语术语表/身份字段表/关系层级表/事实召回分层表/管辖登记 Schema 表/Norm 方向清单）。造 LDVH 本身才用，用户干活不读。
- **B 类型契约＋共同模型（9 份，257,734 字符，42.6%）**：02 事实模型、03 业务系统共同结构、20–26 七个事实类型（Goal/SubGoal/Spark/Norm/Report/Pitfall/Friction）。字段/状态机/校验已编码进工具，用户经工具用、不读原文。
- **C 工作流/行为规则（10 份，205,298 字符，33.9%）**：00 理念、04 检查机制、09 受控提交、30–36 七个业务系统（目标规划/火花/把关/调研/召回/经验/摩擦）。这才是用户干活真要用的规则；且其中高频用的是判据/义务/骨架，论证/反模式/验证表是支撑材料。

结论：**A+B 共 21 份 400,063 字符（66.1%）用户干活基本不读原文**（纯开发文档或已编码进工具）；用户实际真要用的规则原文 ≈ C 类 33.9%，且其中高频仅判据骨架。即「把整包 605K specs 原文交付给用户，约三分之二备而不用」——为「交付应为提炼后的生产内容」提供量化依据。

**勘误（据实，主控上一轮口头数字错误）**：主控在对话里曾口述「A 34.2%／B 47.0%／C 18.8%、用户不读 81.2%」，该组数字错误（A 附件误计 5 份实为 6、C 漏算 09 等，份数与字符对不上）。写入前以脚本逐份重算纠正为上表（A 23.5%／B 42.6%／C 33.9%、A+B 66.1%）。结论方向不变（多数 specs 用户不读原文），量级以重算为准；此错本身即「凭印象数字充当实测」（friction-ae501078 同族）的又一实例，如实记。

边界（不夸大）：① 三分是语义判断、非机械可判；B 类「用户不读原文」前提是工具校验已正确编码契约，若工具与规范漂移（如已发现的 25 §13、guidance 口径），用户仍可能被迫读原文核对，该部分消费量会回升。② C 类 33.9% 是规则原文体量，非「用户每次都用全」，单次任务只用相关几份。③ 未统计真实会话里用户/AI 实际 L4 读了哪些份、多少频次（需会话日志，本轮未取）。④ 本量化是体量占比，非价值占比——不据此说 A/B 无价值，只说其不在用户干活的常驻消费面。

**专项分出（2026-11-21，Human 指示）**：本 Spark 承载的「Human 方向性主张：specs 是开发文档、交付应为提炼后的生产内容」及其关键拆解，已于同日分出为专项 Spark `spark-0251b588`（生产交付物形态：提炼物与 specs 的边界），该专项承载主张本身、生产消费面／权威归属／漂移防护的三问拆解、A/B/C 三个候选方向与「生产包内 specs 全文留否」的分歧；专项讨论与裁决在该对象进行，本 Spark 保留总体方向、根本性判断①②与本主张的取证记录，专项结论回并至此。
