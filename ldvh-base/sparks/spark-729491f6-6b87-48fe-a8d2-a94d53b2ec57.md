# 受控写入失败原因与减缓

## 当前理解

复测 738 会话：写入 593 次、失败 313（52.8%，剔除 D 类既定分支后 297 次 50.1%）。真因是更新路径校验首错即返：rejected 重试后仅 60.1% 成功、33.9% 再失败且二次失败是被掩盖的下一层。已在 spark writer 落地四类独立检查一次报全。六类原因的成本与对机械保障的影响已逐类判定，停止条件达成。

（以上首段即 frontmatter `summary` 的逐字承载。）

### 2026-11-11 复测：口径与结论

**扫描面**：`~/.dsh/sessions` 全部 738 个会话日志（`zstd` 解压后逐行解析 `tool/result`，以 `tool-call` 建 callId→工具名索引做关联）。口径：仅十类 `ldvh_*_write`，以返回文本首行 `LDVH <op>: <outcome>` 判定，`completed` 之外计失败。

**总量**：写入类调用 593 次、失败 313 次、失败率 **52.8%**。按工具：`ldvh_workcase_write` 319 次（失败 56.7%）、`ldvh_spark_write` 175 次（57.1%）、`ldvh_subgoal_write` 52 次（21.2%）、`ldvh_friction_write` 23 次（39.1%）。

**分母须说明**：本条原记的「537 会话 / 931 次」是时点累计的 `tool/result` 事件数；本轮同一批日志中 ldvh_* 全工具调用 2134 次，其中写入类 593。引用失败率时必须说明分母是「写入类调用」而非「全部工具调用」——后者会把基数放大 3.6 倍。

### 失败率的真实含义（度量更正）

按「同一工具连续失败直到首个成功」聚类（会话内）：首试即成功 132；失败簇 164，其中 148 簇（90.2%）后续最终成功；簇均失败 1.91 次。

即 313 次失败不是 313 次工作损失，而是 **164 次受阻尝试**。故减缓的正确目标是**把簇均重试从 1.91 压向 1.0**，而不是把失败率降到 0。这也解释了甲档（补 schema 必填表）为何可能无效：它减的是簇的**数量**，不是簇内的**重试次数**。

### 一次被推翻的判断（据实记录）

本轮曾判断「A 类（缺字段/格式）与 C 类（子代理转述）共 88 条拒绝的 `follow_up` 全为空，属信息缺失」，并据此建议「拒绝时返回可复制的合格片段」。**该判断经实测被证伪**：

- `gaps` 早已精确到字段级，例如 `refs[].object_uid: must be a canonical UUIDv4 object_uid, got "subgoal-01978a8b-..."`、`body: expected exactly 1 H1 heading, found 2`、`priority: may appear only while status=open, got status="discarded"`。
- 逐簇查看：模型**确实照着 `gaps` 改了**——`norm_write` 缺 `frontmatter_after`，下一轮补上即成功；`workcase_write` 缺 `change_summary` 同样。
- `writeRejected` 的 `follow_up` 一直有内容，真正为空的只有 `invalidRequest()` 一支，而那一支的 `gaps` 已够用。

故「补 `follow_up` 内容」收益接近零。该判断已按 00 §4.6 撤回。

### 真因：校验首错即返，重试像剥洋葱

查 `rejected` 类（168 次）：紧接同工具重试**成功仅 60.1%**，**再次失败 33.9%**。逐例查看再次失败的样本，第二次失败的原因**恰是第一次被掩盖的下一层错误**：

- 第 1 次报 `refs[].object_uid` 格式错 → 模型改成裸 uuid → 第 2 次才报这些 uuid 根本不可解析；
- 第 1 次报 `priority` 状态错 → 模型删掉 → 第 2 次才报 `serves` 指向已 retired 的子目标。

根因在 writer：校验是**分阶段 `return failure()`** 的。**每次拒绝只报当前这一层，掩盖了后续所有层。**

### 已落地的改动

`plugin/lib/spark-writer.js` 的 update 路径改为：**四类互不依赖的检查一次性求值并合并报出**——字段形状、关系闭集、serves 解析、refs 解析。判据一条未改，只改「一次能报出多少条」。CAS 与状态机迁移必须先于它们成立，故仍保持首错即返。

**实测验证**：历史真实场景复现（refs 带类型前缀短 id + priority 出现在终态 + refs 目标不存在）——一次拒绝报出三层。改动前需撞 2–3 轮。守卫经变异检验确认可检出回退。

### 六类原因：判断、成本与对机械保障的影响

分母为剔除 D 类后的 **297 次真实失败**。

| F 其他 | 24 | — | **已归因完毕**，无新类型 | — | 见下：全部可并入既有类别 |

**F 类归因明细（24 条，无一条构成新类别）**：`candidate_changed` 3 + `CN_fingerprint_invalidated` 3 + `goals_conflict` 5 → E（状态时序）；`action must be create|update` 4 → A（参数错）；`refs/serves_unresolvable` 8 → B（结构）；审核轮次上限、`review_required` 等 4 → C 或 D。

**一句话结论**：297 次真实失败里，**可消除的只有 A 类 80 次（26.9%）**，其中 spark 层已消除；B 类 114 次已另案处理；C/E 共 79 次的正确处置是「不改」或「只减缓」，因为削弱它们换来的失败率下降要以机械保障为代价。

### 仍在的证据边界（据实声明）

- **收益尚未经真实流量验证**：改动的效果只在夹具与历史场景复现中确认。「簇均重试是否真的从 1.91 下降」须等新的会话数据，本条不预先声称已降低。
- **分类器是本轮所写的文本匹配**，判据为 gap 文本特征，非领域权威分类；A/B 类边界存在判定歧义，误差未量化。
- **其余九个 writer 的同类收益未经实测**，表中所列只是改动量的估计，不是收益估计。
- **C 类的削弱风险未验证**：本轮只确认了「现行不给片段」，未评估「改为给片段」对 21 §8 防代述的具体影响——若要动，须另起议题先做那项评估。
