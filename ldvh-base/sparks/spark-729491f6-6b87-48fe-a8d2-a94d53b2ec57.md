# 受控写入失败原因与减缓

## 当前理解

复测 738 会话：写入 593 次、失败 313（52.8%）。三类失败 88 条拒绝的 follow_up 恒空是误判——gaps 已精确到字段级且模型照改。真因是更新路径首错即返：rejected 类重试后 60.1% 成功、33.9% 再失败，且二次失败恰是被掩盖的下一层错。已改为四类独立检查一次报全（spark），一次拒绝可报出三层。

（以上首段即 frontmatter `summary` 的逐字承载。）

### 2026-11-11 复测：口径与结论

**扫描面**：`~/.dsh/sessions` 全部 738 个会话日志（`zstd` 解压后逐行解析 `tool/result`，以 `tool-call` 建 callId→工具名索引做关联）。口径：仅十类 `ldvh_*_write`，以返回文本首行 `LDVH <op>: <outcome>` 判定，`completed` 之外计失败。

**总量**：写入类调用 593 次、失败 313 次、失败率 **52.8%**。与本条原记的 2026-11-10 复测（285/931，52.7%）同量级，**未自愈**。按工具：`ldvh_workcase_write` 319 次（失败 56.7%）、`ldvh_spark_write` 175 次（57.1%）、`ldvh_subgoal_write` 52 次（21.2%）、`ldvh_friction_write` 23 次（39.1%）。

**分母须说明**：本条原记的「537 会话 / 931 次」是时点累计的 `tool/result` 事件数；本轮同一批日志中 ldvh_* 全工具调用 2134 次，其中写入类 593。引用失败率时必须说明分母是「写入类调用」而非「全部工具调用」——后者会把基数放大 3.6 倍。

### 失败率的真实含义（度量更正）

按「同一工具连续失败直到首个成功」聚类（会话内）：首试即成功 132；失败簇 164，其中 148 簇（90.2%）后续最终成功；簇均失败 1.91 次。

即 313 次失败不是 313 次工作损失，而是 **164 次受阻尝试**。故减缓的正确目标是**把簇均重试从 1.91 压向 1.0**，而不是把失败率降到 0。这也解释了甲档（补 schema 必填表）为何可能无效：它减的是簇的**数量**，不是簇内的**重试次数**。

### 一次被推翻的判断（据实记录）

本轮曾判断「A 类（缺字段/格式）与 C 类（子代理转述）共 88 条拒绝的 `follow_up` 全为空，属信息缺失」，并据此建议「拒绝时返回可复制的合格片段」。**该判断经实测被证伪**：

- `gaps` 早已精确到字段级，例如 `refs[].object_uid: must be a canonical UUIDv4 object_uid, got "subgoal-01978a8b-..."`、`body: expected exactly 1 H1 heading, found 2`、`priority: may appear only while status=open, got status="discarded"`。
- 逐簇查看：模型**确实照着 `gaps` 改了**——`norm_write` 缺 `frontmatter_after`，下一轮补上即成功；`workcase_write` 缺 `change_summary` 同样。
- `writeRejected` 的 `follow_up` 一直有内容（「fix the reported mechanical issues and retry; zero write has occurred」），真正为空的只有 `invalidRequest()` 一支，而那一支的 `gaps` 已够用。

故「补 `follow_up` 内容」收益接近零。该判断已按 00 §4.6 撤回。

### 真因：校验首错即返，重试像剥洋葱

查 `rejected` 类（168 次）：紧接同工具重试**成功仅 60.1%**，**再次失败 33.9%**。逐例查看再次失败的样本，第二次失败的原因**恰是第一次被掩盖的下一层错误**：

- 第 1 次报 `refs[].object_uid` 格式错 → 模型改成裸 uuid → 第 2 次才报这些 uuid 根本不可解析；
- 第 1 次报 `priority` 状态错 → 模型删掉 → 第 2 次才报 `serves` 指向已 retired 的子目标。

根因在 writer：校验是**分阶段 `return failure()`** 的——字段校验不过就提前返回，修好后才进入 serves 解析，再之后才是 refs 解析。**每次拒绝只报当前这一层，掩盖了后续所有层。**

### 已落地的改动（本轮）

`plugin/lib/spark-writer.js` 的 update 路径改为：**四类互不依赖的检查一次性求值并合并报出**——字段形状、关系闭集、serves 解析、refs 解析。判据一条未改，只改「一次能报出多少条」。

- 合并的边界（不是所有检查都能合并）：CAS 与状态机迁移必须先于它们成立（否则后续校验跑在错误基线上），故仍保持首错即返。
- 合并后 `code` 取第一个失败的 code（调用方按 code 分类的既有行为不变），`details.issues` 汇总全部层，并新增 `details.failed_codes`。
- 单错时不合并，报错形态与改动前完全一致。

**实测验证**（历史真实场景复现）：refs 写成带类型前缀的短 id + priority 出现在终态 + refs 目标不存在——一次拒绝把三层全部报出（`spark/frontmatter_invalid` + `spark/refs_unresolvable`，issues 含 `refs[].object_uid`、`priority`、`refs target` 三条）。改动前需撞 2–3 轮。

**守卫**：新增 2 条用例锁住「一次报多少层」，并用变异检验确认——把实现退回首错即返，该用例立即转红；还原后 68 例全通过、文件 md5 与备份一致。

**范围**：本轮只改 spark。其余九个 writer 有同构的 `failure()` 与分阶段校验，**未改**——是否推广须先有它们各自的实测数据，不以「同构应当也一样」推定。

### 仍在的证据边界（据实声明）

- **收益尚未经真实流量验证**：改动的效果只在夹具与历史场景复现中确认。「簇均重试是否真的从 1.91 下降」须等新的会话数据，本轮不预先声称已降低。
- **after 期样本不足**：以参数校验接入（2026-11-10）为界，after 期仅 48 次写入调用，不足以判定任何趋势。
- **分类器是本轮所写的文本匹配**，判据为 gap 文本特征，非领域权威分类；A/B 类边界存在判定歧义，误差未量化。
- 其余九个 writer 的同类问题**未验证**，不主张它们也有同样收益。
