# Spark 创建后的合拢发现机制

## 当前理解

Spark 的查重只在创建时发生（20 §6.2），创建后无周期性回看，且 31:465 禁止合并自动执行；首次全量回看 73 条已发现 3 组真同题（其中两组已终态），而关键词粗筛 0 组——机械判同题不可行，缺的是发现者与终态重叠题面的处置规则。

Spark 已有「记录」与「同题判定＋合并」的判据（31 §8 出生地登记、§8.4 同答一问题方可合并、§15 合并须 Human 确认），但查重只发生在创建时（20 §6.2：创建前查重，命中则转向既有）。两次相隔很久创建的 Spark，在各自创建时都不会命中对方，而之后没有任何机制回过头发现它们应合拢——31:465 还明确禁止把合并自动执行。故现状是：记录不会丢，但会散；不会自动合拢，也不会有人被指派去发现该合拢的组。

首次全量回看（73 条）已证实「散」正在发生，至少有 3 组真同题：

- 「摩擦与经验的分诊边界与重复治理」（implemented）与「摩擦与经验的重复与边界」（implemented）——都在问 Friction 与 Pitfall 的边界与重复消除；
- 「Norm 类型实现侧空缺」（discarded）、「Norm 承载层补建」（implemented）、「Norm 与 WorkCase 承载层补建」（discarded）——三条都在问 Norm/WorkCase 的 writer、受控入口与唯一性防线怎么建；
- 「30–38 段编号与六业务系统承载」（discarded）、「上层规范体量与归属」（discarded）、「总纲落点失实与外部接入缺口」（discarded）——同属 00 重建总纲的收口问题。

同时验证到一条负面证据：关键词粗筛（共享 ≥4 个双字词）对 73 条输出 0 组，而肉眼能找出上述 3 组。这印证 02 §9.2 不建立相似度自动裁决的判断是对的，也说明「机械判同题」这条路走不通。

需要注意：上表前两组已全部进入终态（implemented/discarded），而 31 §8.4 要求合并只在 open 之间有意义；因此缺口不只是「发现」，还包括「终态对象已无法再合并时，其题面重叠如何处理」。

## 调查问题

散落的待办已能记录，但让它们按主题自动合拢还差什么：缺的是发现机制、触发者，还是终态对象的合拢规则？

## 调查边界

当「由谁在什么时机发现可合拢组」与「已进入终态的重叠题面如何处置」两条判据能从规范源原文读出时停止；不在本议题内设计相似度算法（02 §9.2 已否决机械裁决）。
