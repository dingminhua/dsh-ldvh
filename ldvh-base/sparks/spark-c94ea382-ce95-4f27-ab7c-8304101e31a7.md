# Norm 与 WorkCase 承载层补建

## 当前理解

**拆分去向**（依 `20 §9.4` 情形二，CREATE-FIRST）：本对象原判断「两支缺口性质完全相同，散成两条会掩盖这一唯一卡点」。复核后该判断**部分失实**——两支在「缺 writer/入口/断言」这一点上确实同型，但**剩余风险的性质不同**：

- **Norm 侧**：规范自洽、无外部依赖，缺口是**纯实现工作量**；且其核心约束是 27 §11 的唯一性三层防线，三层未具备前不得声称唯一性已获机械保障。
- **WorkCase 侧**：卡在 `attempt` 令牌的跨规范接缝——21 §9.1 把 `attempt` 定为 `open` 状态的必要条件，而 §10.4 第 4 项声明其宿主实现应由 08/09 承接、未落地前「依赖 attempt 的部分不成立」，§15.2 记替代保障为「无」。即它缺的不只是代码，还有**一个待定案的规范层前提**。

合并承载会把「规范间待定案」误呈现为「实现待补」。故拆为两条独立对象，各自承接：`4cb237fe`（Norm 承载层补建，P0）与 `27a9dbfc`（WorkCase 承载层与 attempt 接缝，P1）。

**本次同时更正两处失实转述**：原文（第 39 行表格）记 `ldvh-base/norms/` 与 `ldvh-base/workcases/` 为「已建、空」。经复核该表述**失实**——补建之前这两个目录**并不存在**（同批的 `frictions/` 亦然）。「不存在」与「空目录」在本系统不等价：`factSourceStatus()` 对前者判 `incomplete`、对后者判 `ready`，故原转述不能作为事实依据。三目录已于 2026-09-13 由 Human 裁定补建（本地建立，未纳入版本控制——空目录不进 Git，故 clone 后仍需安装事务补建）。同类更正此前已在 `6f5adc82`、`89df677f` 与四份 `docs/` 中执行（提交 `19fe610`），本对象当时被漏改，此处补正。

**实际终止路径**：未等到边界满足即收口——因该边界本身不可判定（它描述的是「要做的事」，不是「何时停止」，且两支的可达性不同：Norm 可达，WorkCase 受 attempt 接缝阻塞）。按 Human 确认（2026-09-13），拆为两条各自具备可判定停止条件的对象，本对象以 `split-into` 指向二者。依 `20 §9.3`，被拆分的原对象一律 `discarded`，不因部分内容被承接而标记 `implemented`。
