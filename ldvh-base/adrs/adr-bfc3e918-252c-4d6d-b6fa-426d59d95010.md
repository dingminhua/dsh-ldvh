# DevLog 增设内部来源锚点字段

## 决策背景

D1 已确定调研吸收系统的内部信息吸收结论由 DevLog 承载。随之而来的问题是：内部结论的证据锚点放在哪个字段。

现状两侧都被关死。29 号「字段契约」表中没有 `urls`，也没有任何 `evidence`／`anchor`／`source` 类字段；29 §10.1 明文写「**不采用**的公共字段及理由：`urls`——条目源自内部过程，不调查外部世界（外部调研归 24 号）」，§10 又写「本类型无 `urls`、无逐字外部摘录要求」。`refs` 也不能顶替：02 §7.1 规定 `refs` 承载「活动对象与其它事实对象之间的**内容关联**」，目标必须是事实对象 `object_uid`，并明文列举三种不得承载的内容，其中就有「**不承载**载体内部锚点」。故会话记录、文件路径、运行记录这类内部来源，进不了 `urls`（那是外部 HTTP(S) 专用，且明文禁止用本机路径、日志、会话或 Git 定位符替代），也进不了 `refs`（目标必须是事实对象）。

## 决定

29 号 DevLog 新增一个内部来源锚点字段，用于承载内部信息吸收结论的证据定位；该字段与 `urls` 并列而不混同，不改动 02 §7.1 对 `urls` 与 `refs` 的既有公共语义。

## 备选与理由

不选「复用并扩展 `refs` 语义」：`refs` 的采用面当前是 spark／workcase／devlog 三家，扩其语义等于改 02 §7.1 的公共字段语义，会波及三个类型的既有对象与实现，代价远高于新增一个类型专属字段。

不选「不要求锚点」：这与 00 §2.4.2「事实源为判断提供可定位、可回读、可追溯的依据」相抵；结论无法回查，等于放弃了事实源的核心作用。

选新增类型专属字段的理由：改动面限于 29 号字段契约与 devlog 写入器的字段闭集，不触及 02 号的公共字段语义，`refs` 与 `urls` 的既有采用面均不受影响；且 02 §7.1 允许类型来源在字段契约中登记自己的字段，此路径不需提升为公共模型变更。

## 后果

29 号须给出该字段的名称、格式、必填条件与机械校验；devlog 写入器的字段闭集与校验须同步实现（02 §7.1：单独改规范而不改实现，会使按规范创建的对象无法通过机械校验）。既有 16 条 DevLog 均为存量，新字段不得成为其失效原因——该字段须为条件字段，存量对象缺失时按 D3 的处置处理。

## 适用范围

适用于 29 号 DevLog 的字段契约与 devlog 写入器的字段闭集，以及 D1 所定的内部信息吸收结论的证据定位。
