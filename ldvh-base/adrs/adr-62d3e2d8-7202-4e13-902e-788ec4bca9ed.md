# 只推 dev，main 发布线不含事实对象

## 决策背景

**起点（实测）**：`main` 停在 `d8fdff3 Initial commit`，其树只有 `LICENSE` 一个文件；`dev` 领先它 1635 笔；`origin/HEAD` 指向 `origin/main`，即它是默认分支。`git ls-tree -r --name-only main` 只有 `LICENSE`。

**两支的内容差**：`ldvh-base/` 下 298 份跟踪文件全部是事实载体，目录名与文件名前缀一一对应、无第三种内容混入——`adrs` 7（`adr-`）、`frictions` 67（`friction-`）、`norms` 2（`norm-`）、`pitfalls` 70（`pitfall-`）、`researches` 47（`research-`）、`sparks` 62（`spark-`）、`subgoals` 4（`subgoal-`）、`workcases` 38（`workcase-`），另加单例 `goal.md`。

**产物侧早已是事实无涉，分支侧从来没有规定**：`npm pack` 实测 129 个条目中 `ldvh-base` 0 个、`specs/` 33 个——`plugin/package.json` 的 `files` 白名单只列 `lib`/`icons`/`specs`/`cordis.patch.yml`/`web/dist`/`LICENSE`/`README*`/`CHANGELOG`，`scripts/specs-bundle.mjs` 的 prepack 只复制仓库根的 `specs/`。也就是说「发布产物不含事实对象」今天已经成立，但从来没有被写成规则；而「main 该不该含事实对象」全库无任何规定——`specs/` 中「发布线」「main 分支」「主干分支」零命中，`RELEASING.md` 与 `specs/10 §7` 只讲版本双轨与发布门禁，不讲分支内容。

**要解决的问题**：「main 落后 1635 笔」与「main 故意只放 LICENSE」在现象上不可区分，无规定时每次都要重新判断，且误合入不会被任何检查发现。

**Human 裁定（2026-11-02）**：只推送 dev；发布与合并到 main 都必须不含事实对象。本 ADR 把这条裁定固定为可检查的决策，使其不必每轮重新讨论，也让误合入有一个可对照的判据。

### 为什么事实对象不该进 main

事实对象是**项目专属的当前判断依据**：它们的 `object_uid`、`occurred_at`、`change_log` 记录的是本项目这一刻的事实状态，不是产品能力。把它们随发布线分发的具体后果有二：① 它们会成为产品内容的一部分被外部读者当作 LDVH 的「示例事实」，而其中相当部分是对本次工作本身的自我检查记录；② 任何一份被后续受控更新改写，历史发布版本与当前事实源的内容就不可区分。

### 查重结论

对照既有 7 条 active ADR 的 `title`/`decision` 逐条比对（`关系目标的 open 约束为写入前置条件`、`注入交付按类型分节与次序`、`v4 存量零迁移`、`不为否定性规范结论新增机械门禁`、`提请弹窗 question 上限 200 字符`、`每次回复先称呼老丁`、`规划由 goal.md authored 区承载`），无同主题决策。`specs/` 中无任何分支内容的规定；`发布门槛` Norm（`norm-773cc0bc`）的门禁 4 约束的是「打包清单与 `files` 字段一致」，不含分支内容。故无既有规则承接，新建成立。

## 决定

日常推送只进 dev，main 仅由发布动作推进，且发布产物与 main 分支的载体一律不含事实对象。

展开为四条可独立检查的约束：

- **日常推送只进 `dev`**：开发提交只进 `dev` 并推 `origin/dev`；`main` 不接收来自日常开发的推送。
- **`main` 仅由发布动作推进**：`main` 的每一次前进都对应一次发布或一次发布准备，不是一次日常合并。
- **`main` 载体不含事实对象**：`main` 的树中不出现 `ldvh-base/` 整个目录。判定方式机械可判——`git ls-tree -r --name-only <ref> -- ldvh-base` 为空即成立。
- **发布产物不含事实对象**：`npm pack` 的文件清单中不出现 `ldvh-base/` 下任何路径。该条今天已成立（实测 0 条目），本决策把它固定为不得回退的约束。

## 备选与理由

- **把 dev 整体合入 main**——否决：等于把 298 份项目专属事实对象当产品内容发布，与「事实源是项目当前判断依据、随项目走」的定位冲突（`00 §3.2`），也与本次 Human 裁定直接冲突。
- **维持 main 空置现状、不写规定**——否决：`main` 是默认分支，源码安装与首次访问都落在它上面；「落后 1635 笔」与「故意只放 LICENSE」在现象上不可区分，无规定时每次重新判断，且误合入不会被任何检查发现。
- **只约束 npm 产物、不约束分支**——否决：产物侧今天已满足，约束它不改变分支状态；一旦 `main` 被合入事实源，从 `main` 源码安装得到的仍是带事实对象的树，产物白名单挡不住。
- **把这条规则写进 `发布门槛` Norm（`norm-773cc0bc`）而非 ADR**——否决：该 Norm 门禁 4 只约束打包清单与 `files` 字段一致；且把分支规则写进 Norm 会让规则载体本身也是事实对象，同样只存在于 `dev`、`main` 上读不到——载体形态改变不了这个处境。Norm 的「成体系方向」粒度（`27 §6.1`）也不适合承载单条分支规则。
- **删除 main、只留 dev**——否决：`origin/HEAD` 指向 `main`，删除会让默认分支悬空；Human 的裁定是「main 不含事实对象」，不是「不要 main」。
- **选定：dev 为唯一开发线且承载事实源；main 为发布线，其树不含 `ldvh-base/`。**

## 后果

**正面**：`main` 的角色从「默认分支的重力」变成被规定的发布线；误合入事实对象有一个机械可判的拒绝依据（`git ls-tree` 为空）；「main 落后多少」不再是需要每轮重新判断的问题；发布产物不含事实对象从「碰巧如此」变成不得回退的约束。

**负面与限制（如实登记，全部实测）**：

1. **不含事实对象的树无法通过现有全量测试。** 以 `git archive dev` 解出、仅移除 `ldvh-base/` 的树实测 `tests 2711 / pass 2677 / fail 31`；同一棵树补回 `ldvh-base/` 后 `2711 / pass 2708 / fail 0`（另有 `skipped 2`、`todo 1`）。31 条分布：`plugin/test/source-recall.test.mjs` 16、`plugin/test/recall-injection.test.mjs` 11、`plugin/test/goal-writer.test.mjs` 1、`plugin/test/recall-quality.test.mjs` 1、`plugin/test/recall-integration.test.mjs` 1、`plugin/test/source-recall.bench.test.mjs` 1。根因：这批用例以 `ROOT = join(import.meta.dirname, "..", "..")` 直接读仓库根的 `ldvh-base`，把「仓库自带的真实语料」当作被测对象。这不是本决策引入的缺陷，但它把这条决策的实现代价暴露出来。
2. **`.github/workflows/ci.yml` 在 `main` 上必然红。** 该工作流的触发是 `on.push.branches: [main, dev]`。除非另行处置，推一次事实无涉的 `main` 就会得到 31 条失败。**本决策不规定该处置**：可选路径有（a）让这批用例在语料缺失时如实 skip、（b）`main` 的 CI 只跑与语料无关的 job、（c）`main` 不触发 CI。三者的取舍涉及「守护是否被削弱」，须单独判断，不在本条内定。
3. **本决策的载体自身即事实对象**（`ldvh-base/adrs/adr-<uid>.md`），故它只存在于 `dev`，`main` 上不可见。从 `main` 单独取树工作的人读不到这条规则——这是本条如实登记的已知缺口，不以「反正没人从 main 开发」掩盖。
4. **本决策不提供任何自动化的分支构造**：把 `dev` 转成事实无涉的 `main` 需要树手术（`git read-tree` → `git rm -r --cached ldvh-base` → `git write-tree` → `commit-tree`），仓库里没有这样的脚本，也没有检查在推送时拒收带 `ldvh-base/` 的 `main` 提交。本决策只定规则，不建机制；下一次真发布时这条缺口会显现。
5. `main` 目前只有 `LICENSE`，故本决策不丢失任何已发布内容；但也意味着「发布线」在本次决策之前从未真正使用过，其首次使用即须面对第 1、2 项。

## 适用范围

适用于本仓库 dev 与 main 两条线各自允许承载的内容，以及 npm 发布产物的组成；不改变事实对象的受控写入通道与受控提交规则，不改变 `specs/` 规范源随包分发的方式。

**适用**：本仓库 `dev`、`main` 两条分支的树内容；`npm pack` 产物的文件清单；以及由这两者派生的源码安装与包安装所得内容。

**不适用**：不适用于其他仓库或其他项目的发布线；不改变事实对象的受控写入通道、受控提交规则与 Git Gate 的既有判定（`dev` 上事实源照常读写与提交）；不改变 `specs/` 随包分发——`specs/` 是规范源（元规范），不是事实源（`00 §3.2`），两者不得混为一类；不约束开发期工作树里 `ldvh-base/` 的存在。

**与相邻规则的分工**：`发布门槛` Norm（`norm-773cc0bc`）管发布点必须通过的门禁清单，本条管两条线的载体内容；两者不重叠、不互相替代。`specs/10 §7` 管发布门面（版本双轨、渠道、README/CHANGELOG），本条不改写其中任何一条。
