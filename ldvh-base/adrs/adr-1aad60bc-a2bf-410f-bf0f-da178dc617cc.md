# v4 存量零迁移

## 决策背景

LDVH v5 对事实对象做了载体与字段模型的全面重构：类型规范重写（20 Spark 的字段三分工重设计、24 Research 的薄索引+正文主体）、载体统一为 frontmatter+markdown 单文件、公共身份机械（object_uuid/created_at/change_log）与受控读写契约全链更换。v4 仓库的 103 个 Spark、152 个 WorkCase、2 个 ADR 及其余对象运行于旧模型之上，二者没有无损的机械转换路径。

v4 的实证价值（spark-0040 跨 17 天 5 个运行时接力的真实形态、workcase-0068 如实失败的 partial 关闭、重量病灶的量化证据）已在 v5 规范设计过程中被逐条吸收（重建锚点文档与三场调研承载），历史对象本身不再携带未被吸收的决策输入。

## 决定

v4 仓库的全部事实对象（103 Spark、152 WorkCase 等）不迁入 v5，v4 保留为只读历史归档。

## 备选与理由

- **分批受控迁移**（specs/20 §14.2 原案）：人工逐份映射字段、重建载体、补受控创建。成本为数百个对象的全量人工核对，而消费方为零——收益端不存在，被否。
- **写自动迁移器**：v4 的 backfill 历史教训（为旧对象补新字段曾造成批次性数据损伤）表明自动迁移在高语义密度对象上的错误成本远高于其收益，被否。
- **维持双读**（v5 消费入口兼容 v4 载体）：会让两代字段模型在同一消费面并存，违背单一权威原则，被否。

## 后果

无已知重大后果——历史对象失去消费方是本决策的预期结果而非损失；v4 仓库随 Git 历史永久可回查，回溯需要（如 v4 行为数据对照）经 Git 历史满足即可。

## 适用范围

适用于 v4→v5 的版本迁移决策记录：v4 事实对象、规范与仓库的处置边界；不适用于其他版本或跨项目迁移。不适用于 v5 内部的类型重构——那是新对象替代路径（勘误/替代两路），不属版本迁移。
