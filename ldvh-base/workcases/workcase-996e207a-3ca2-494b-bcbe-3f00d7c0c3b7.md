# 事实对象指称须带类型与标题

## 摘要

把「描述事实对象必须带有事实对象类型」落成规范要求，先固定现状口径与落点。候选口径：事实对象的**指称形态**——即在对话、正文、提交消息与派生输出中指称一个对象时的最小可读形式——最小形态为「类型短名 + 短标识」（如 `friction-abf557e1`）；需要读者据此辨认对象时，紧随其标题（如 `friction-abf557e1 局部改动时以记忆或截断输出为数据源`）。

### 现状核实（本轮机械核验）
- `specs/` 内共 8 处裸 8 位短标识（`04:166` 的 `82260dec`、`21:463–466` 的 `b57780cb`／`1a895068`／`e0bab773`、`26:203/204` 的 `bf73fad4`、`26:222` 的 `71930c4a`）；其中 `b57780cb`、`1a895068`、`e0bab773` 在事实源内无任何可解析载体，读者无从定位。
- `ldvh-base/` 正文中出现的 8 位裸串去重后 163 个：102 个可解析为某事实对象 uid 的前缀，61 个不可解析（引文片段或其它 hex）。
- 七类事实类型工具的列表与读取投影统一输出「裸 uuid + 标题」，不带 `fact_type_key`（`plugin/lib/*-tools.js` 各一处）。
- 提交消息主体普遍写裸短标识：近 60 条消息中 20 余处为裸 8 位串，仅少数带类型前缀。

### 落点建议（待 Human 决定）
唯一权威归 `02`——该规范已承接公共身份字段 `object_uid` 与 `fact_type_key`（含类型短名值域）、稳定引用原则与载体权威位置；形态条款拟落在 §7 之下。各消费面（09 提交消息、05/06 CLI 与 Code 输出、07/10 呈现与注入）以一行回指承接，不在各自复制展开。

### 待决范围
条款覆盖面（是否含提交消息与规范正文）、是否为其设机械门禁、既有裸引用的存量是否回改。
