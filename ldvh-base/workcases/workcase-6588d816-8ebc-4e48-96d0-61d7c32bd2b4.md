  ### 处置方向
  - **机械审核门**：新增运行侧 verifyRun，按 §18 逐行产出 `{id, verdict, evidence}`，verdict 取 pass / fail / not-checkable。landed 仅在无 fail 且不存在未声明的 not-checkable 行时成立。不可判行由模块内具名常量声明（每行附理由），id 派生规则同样固化为常量。
  - **无判定行必须有承载位**：「派发准入」既非可核对、也非语义判断，在 pass/fail/not-checkable 三值里最容易被顺手填成 pass——那正是本单要消除的「默认通过」。故该行以 not-checkable 声明，理由写死为「本行当前不产生判定（§18 条件式）」，并**由机械层反向拦截**：已声明不可判的行若被报 pass，按 fail 处置。

# 辅助任务完成门禁

## 摘要

本单为闲时辅助任务（specs/11）补一道机械审核门：完成判定不再只看「落地有没有被调用」，而要逐条核对规范已定义的确定性校验。本单由拆分而来——原候选把「完成门禁」与「摩擦补充路径三处缺口＋存量迁移」合成一单，建前独立审核判定该合并与实测相反（运行痕迹其实已带完整失败，真问题是读取侧无人消费），两者可独立授权与独立关闭，故拆为两单；本单只承担「完成门禁」，另一单为 workcase-feb5b7cf。

### 现状核实
- **完成语义过弱**：运行痕迹里 landed 的定义是「落地已调用」（`plugin/lib/idle-runlog.js:123` 注释原文），不是「校验通过」。§18 定义了验证对象与逐行成立条件（表头在 `specs/11:818`，数据行原 `:820-841` 共 22 行），但代码中没有对应的运行侧逐行核对面——全仓检索 verifyRun 的调用点为零，§18 只出现在注释引用里。
- **§18 的行须按「验证入口」列分类**（建前审核实测订正）：各行「验证入口」列写「回读与复算／是非核对／解析与比对」的属机械可核对（20 行），写「AI 语义审核」的属语义判断（1 行，「经验对象的查重已执行」），成立条件本身写明「**本行当前不产生判定**」的属无判定行（1 行，「派发准入」）。故「延迟的取消」「二次确认空闲」「路径约定落实」「无主控预检落实」四行**是可核对的**，不得登记为 not-checkable 以免掉这四道核对。
- **§18 无 id 列**：首列含 Markdown 粗体（7 行）、日期括注（仅「转写条目的合法性（2026-11-01）」）、全角斜线（仅「缓冲条目不可写／不可回读」），另有一处非日期括注「延迟的取消（回合开始即清掉计时）」。故 id 派生规则必须显式定义，不能假定首列天然唯一可作键。
- **三处 stage 派生点，但性质不同**：`lifecycle.js:700-702` 与 `:1028-1030` 是单任务三元式 `landed / skipped / else land-failed`——**这两处会在 partial 出现后误记为失败**；`:1445-1455` 是多任务的 IIFE，`:1453` 为 `landedN === 0 → land-failed` 而 **`:1454` 已经 `return "partial"`**，该处对 partial 是正确的。故本次是「两处置换语句 + 一处已正确者一并收敛为同一函数」。
- **前置依赖**：`experience-review-stage.js:678/842-843` 的 outcome 原本只有 landed / skipped，故 `:700/:1028` 的 partial 误记**当时不可达**，要等步骤 3 引入 partial 之后才生效。修法与引入已同批落地。
- **两处闭集声明**：`per_task.outcome` 的闭集在 `idle-runlog.js:135`（原 `landed|rejected|land-failed`，无 partial）；`stage` 的枚举在 `:121-123`。**`:131-132` 早已写明「部分失败而成功者已落地时整轮 stage 为 partial」**——故不是「stage 闭集无 partial」，而是枚举行未同步、且 per_task 侧确实缺 partial。

### 处置方向
- **机械审核门**：新增运行侧 verifyRun，按 §18 逐行产出 `{id, verdict, evidence}`，verdict 取 pass / fail / not-checkable。landed 仅在无 fail 且不存在未声明的 not-checkable 行时成立。不可判行由模块内具名常量声明（每行附理由），id 派生规则同样固化为常量。
- **无判定行必须有承载位**：「派发准入」既非可核对、也非语义判断，在 pass/fail/not-checkable 三值里最容易被顺手填成 pass——那正是本单要消除的「默认通过」。故该行以 not-checkable 声明，理由写死为「本行当前不产生判定（§18 条件式）」，并**由机械层反向拦截**：已声明不可判的行若被报 pass，按 fail 处置。
