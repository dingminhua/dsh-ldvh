  ### 现状核实
  - **完成语义过弱**：运行痕迹里 landed 的定义是「落地已调用」（`plugin/lib/idle-runlog.js:123` 注释原文），不是「校验通过」。§18 定义了验证对象与逐行成立条件（表头在 `specs/11:818`，数据行 `:820-841` 共 22 行），但代码中没有对应的运行侧逐行核对面——全仓检索 verifyRun 的调用点为零，§18 只出现在注释引用里。
  - **§18 的行须按「验证入口」列分类**（建前审核实测订正）：各行「验证入口」列写「回读与复算／是非核对／解析与比对」的属机械可核对（20 行），写「AI 语义审核」的属语义判断（1 行，「经验对象的查重已执行」），成立条件本身写明「**本行当前不产生判定**」的属无判定行（1 行，「派发准入」）。故「延迟的取消」「二次确认空闲」「路径约定落实」「无主控预检落实」四行**是可核对的**，不得登记为 not-checkable 以免掉这四道核对。
  - **§18 无 id 列**：首列含 Markdown 粗体（7 行）、日期括注（仅「转写条目的合法性（2026-11-01）」）、全角斜线（仅「缓冲条目不可写／不可回读」），另有一处非日期括注「延迟的取消（回合开始即清掉计时）」。故 id 派生规则必须显式定义，不能假定首列天然唯一可作键。

  ### 处置方向
  - **机械审核门**：新增运行侧 verifyRun，按 §18 逐行产出 `{id, verdict, evidence}`，verdict 取 pass / fail / not-checkable。landed 仅在无 fail 且不存在未声明的 not-checkable 行时成立。不可判行由模块内具名常量声明（每行附理由），id 派生规则同样固化为常量。
  - **无判定行必须有承载位（第 3 轮阻断）**：「派发准入」既非可核对、也非语义判断，在 pass/fail/not-checkable 三值里最容易被顺手填成 pass——那正是本单要消除的「默认通过」。故该行以 not-checkable 声明，理由写死为「本行当前不产生判定（§18 条件式）」，并**进入步骤 1 的测试场景**，不由读者自行推断。
  - **§18 增行与模块同步**：规范把「运行完成」一行加进 §18 后行数由 22 变 23，模块必须同批补上该行 id，否则「id 集合相等」测试会红。该同步义务写进计划。
  - **stage 与闭集**：把三处派生收敛为同一判定函数（避免第四处漏改），`per_task.outcome` 补 partial、`stage` 枚举行同步补 partial（`:132` 的说明文字已承认该值，属文档与枚举不一致）。
  - **modelApplied 的归入理由**：它与门禁不直接耦合，但门禁的 `verification[].evidence` 要能回指实际模型才能核对「署名与路由」类行，而它当前恒为 null，任何依赖它的核对必然落空。故本单收它，理由是「门禁的证据底座」。
