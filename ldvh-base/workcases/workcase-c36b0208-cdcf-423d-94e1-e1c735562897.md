summary: |-
  修正 7 个 writer 受控更新路径的「完整目标 after」形态，使 `02 §10.5` 已要求但未实现的字段保全成为机械保证，并消除同类静默丢字段。

  ### 现状核实
  `specs/02` :335 起规定写入入口在实际写前**必须**重新确认六项，含 :339「**after 保留全部未变更且仍有消费价值**的字段」；:344 规定「**after 不完整…零写入并报告拒绝**」；`02 §15.1` 第 4 项更把「after 不完整」列为 `00 §5.7` 必停情形。

  ### 违规位置
  7 个 writer 的 update 路径均以「从调用方 payload 整体构建 frontmatter」的形态实现——`const fm = { ...afterFields }`（adr-writer.js:591、friction-writer.js:634、goal-writer.js:466、pitfall-writer.js:495、research-writer.js:769、spark-writer.js:975）或 `const next = { ...frontmatterAfter }`（norm-writer.js:501），漏传字段即被静默删除，无任何完整性校验。**两种表达式同源同义**（均整体取自调用方），故一并纳入本单。

  ### 实测发生
  2026-10-16 销账 `ba4afa96` 时，`frontmatter_after` 漏抄 `attribution` 一行，该字段被静默删除（`friction-writer.js:633-634`）；经提交前人工 diff 比对发现并回填。**该防线是人工动作，不属 `00 §3.5` 的三层防线。**

  ### 规范要求的准确读法
  `specs/02` :329 的主语是**服务侧**：「LDVH CLI 确定性服务规范若提供补丁入口，**必须**…**在内存中形成完整目标 after**」。故「形成完整 after」是写入入口的义务；7 个 writer 的违规实质是**把该义务错误地推给调用方**（要求调用方手写全字段）。

  ### merge 禁令的边界
  `specs/02` :333 禁止的是**未定义的**差量 merge——「以磁盘为基线 + 只应用**显式声明**的变更」有明确定义的声明集，其产物即「完整目标 after」，不在禁止之列。

  ### 处置方向
  update 路径改为「磁盘基线 + 显式变更」四步形态（与 `correct` 路径同构，见 `friction-writer.js:842` 的 `const next = structuredClone(fm)`、`workcase-writer.js:3863` 的 `correctWorkcaseObject` 声明处；行号经建前独立审核实测校正）：① `structuredClone(current.value.frontmatter)` 磁盘基线、全字段先继承；② 应用调用方显式声明的字段变更；③ 按显式删除通道 `frontmatter_removals` 删除（仅限逐类型白名单）；④ Code 重设托管字段（`object_uid`/`fact_type_key`/`created_at`/`change_log`）。

  ### 声明集的机械判据
  「哪些键被有意赋值」以 `Object.hasOwn(frontmatterAfter, key)` 判定——调用方在 `frontmatter_after` 中**实际携带的键**即声明集。`after` 带该键即覆盖；不带且不在 `removals` 即**继承磁盘**；需要删除必须经 `removals` 声明，**不得靠「after 不带该键」表达**。误操作表现为显式失败而非静默错误（未声明删除而字段残留时，各类型既有状态互斥校验会拒绝该结果，如 `spark-writer.js:240-242`）。

  ### 逐类型可删白名单
  已经一轮独立核对，统一口径：白名单 = 该类型 §8 的**条件字段**中**非「终态伴随」**者。spark 为 `priority`/`refs`/`serves`；friction 为 `attribution`/`attribution_ref`；adr 为 `urls`/`trigger_signal`；pitfall 为 `urls`/`trigger_signal`；research 为 `uncertain`/`gaps`/`clarification_log`/`implications`；norm 与 goal 为空。

  ### 白名单的判定依据
  终态伴随字段（`disposition`/`relations`/`retirement_reason`/`retired_at`）在 update 路径不可达（终态对象只读），一律不列。据此**唯一真正需要的顶层删除能力是 `spark` 的 `priority`**（`open` 专属，`open → implemented/discarded` 时须清，`20 §8` :133）。

  ### 边界
  不改 `correct` 路径（已正确）；不改 workcase-writer；不改任何 `specs/` 规范正文（本次为实现对齐，不新增规范语义）；不批量切换后再补迁移。

  ### 陈旧交叉引用的实际分布（经三轮审核实测）
  `03 §9.5`/`03 §10.5` 类引用在 writer 中的分布为：`adr:550`、`friction:588`（update 路径内）与 `friction:805`（**位于 `correctFrictionObject`，:785–:1024，属本单禁区**）、`goal:437`、`norm:448/462/474/478`、`pitfall:449`、`research:724`、`spark:917`，以及 `workcase-writer.js` 9 处（多落在本单禁区路径）。故本单清理面**只覆盖非禁区的 update 路径引用**；`friction:805` 与 `workcase-writer` 的全部命中一并另行立项。

  ### 须一并处置的风险
  本方案把 update 语义从「**省略即删除**」反转为「**省略即保留**」。凡既有调用方依赖「不写某字段＝删掉它」者，行为将静默反转。测试套件内无一例暴露（所有有效指纹的 `after` 均为全展开；3 个残缺 after 在 CAS 阶段即失败），但真实调用面须逐处迁移，且工具 schema 描述必须改写为三向声明口径——其中 6 个 per-type 文件的描述串含「(all fields…)」（friction-tools.js:558、adr-tools.js:480、norm-tools.js:462、pitfall-tools.js:467、research-tools.js:749、spark-tools.js:749），`goal-tools.js:310` 的措辞为「(Code re-assigns goal_key/created_at and appends change_log)」而不含「all fields」，**同样须改**（经建前独立审核实测校正）。

# 受控更新 after 完整性：7 writer 形态修正

## 摘要
修正 7 个 writer 受控更新路径的「完整目标 after」形态，使 `02 §10.5` 已要求但未实现的字段保全成为机械保证，并消除同类静默丢字段。

### 现状核实
`specs/02` :335 起规定写入入口在实际写前**必须**重新确认六项，含 :339「**after 保留全部未变更且仍有消费价值**的字段」；:344 规定「**after 不完整…零写入并报告拒绝**」；`02 §15.1` 第 4 项更把「after 不完整」列为 `00 §5.7` 必停情形。

### 违规位置
7 个 writer 的 update 路径均以「从调用方 payload 整体构建 frontmatter」的形态实现——`const fm = { ...afterFields }`（adr-writer.js:591、friction-writer.js:634、goal-writer.js:466、pitfall-writer.js:495、research-writer.js:769、spark-writer.js:975）或 `const next = { ...frontmatterAfter }`（norm-writer.js:501），漏传字段即被静默删除，无任何完整性校验。**两种表达式同源同义**（均整体取自调用方），故一并纳入本单。

### 实测发生
2026-10-16 销账 `ba4afa96` 时，`frontmatter_after` 漏抄 `attribution` 一行，该字段被静默删除（`friction-writer.js:633-634`）；经提交前人工 diff 比对发现并回填。**该防线是人工动作，不属 `00 §3.5` 的三层防线。**

### 规范要求的准确读法
`specs/02` :329 的主语是**服务侧**：「LDVH CLI 确定性服务规范若提供补丁入口，**必须**…**在内存中形成完整目标 after**」。故「形成完整 after」是写入入口的义务；7 个 writer 的违规实质是**把该义务错误地推给调用方**（要求调用方手写全字段）。

### merge 禁令的边界
`specs/02` :333 禁止的是**未定义的**差量 merge——「以磁盘为基线 + 只应用**显式声明**的变更」有明确定义的声明集，其产物即「完整目标 after」，不在禁止之列。

### 处置方向
update 路径改为「磁盘基线 + 显式变更」四步形态（与 `correct` 路径同构，见 `friction-writer.js:842` 的 `const next = structuredClone(fm)`、`workcase-writer.js:3863` 的 `correctWorkcaseObject` 声明处；行号经建前独立审核实测校正）：① `structuredClone(current.value.frontmatter)` 磁盘基线、全字段先继承；② 应用调用方显式声明的字段变更；③ 按显式删除通道 `frontmatter_removals` 删除（仅限逐类型白名单）；④ Code 重设托管字段（`object_uid`/`fact_type_key`/`created_at`/`change_log`）。

### 声明集的机械判据
「哪些键被有意赋值」以 `Object.hasOwn(frontmatterAfter, key)` 判定——调用方在 `frontmatter_after` 中**实际携带的键**即声明集。`after` 带该键即覆盖；不带且不在 `removals` 即**继承磁盘**；需要删除必须经 `removals` 声明，**不得靠「after 不带该键」表达**。误操作表现为显式失败而非静默错误（未声明删除而字段残留时，各类型既有状态互斥校验会拒绝该结果，如 `spark-writer.js:240-242`）。

### 逐类型可删白名单
已经一轮独立核对，统一口径：白名单 = 该类型 §8 的**条件字段**中**非「终态伴随」**者。spark 为 `priority`/`refs`/`serves`；friction 为 `attribution`/`attribution_ref`；adr 为 `urls`/`trigger_signal`；pitfall 为 `urls`/`trigger_signal`；research 为 `uncertain`/`gaps`/`clarification_log`/`implications`；norm 与 goal 为空。

### 白名单的判定依据
终态伴随字段（`disposition`/`relations`/`retirement_reason`/`retired_at`）在 update 路径不可达（终态对象只读），一律不列。据此**唯一真正需要的顶层删除能力是 `spark` 的 `priority`**（`open` 专属，`open → implemented/discarded` 时须清，`20 §8` :133）。

### 边界
不改 `correct` 路径（已正确）；不改 workcase-writer；不改任何 `specs/` 规范正文（本次为实现对齐，不新增规范语义）；不批量切换后再补迁移。

### 陈旧交叉引用的实际分布（经三轮审核实测）
`03 §9.5`/`03 §10.5` 类引用在 writer 中的分布为：`adr:550`、`friction:588`（update 路径内）与 `friction:805`（**位于 `correctFrictionObject`，:785–:1024，属本单禁区**）、`goal:437`、`norm:448/462/474/478`、`pitfall:449`、`research:724`、`spark:917`，以及 `workcase-writer.js` 9 处（多落在本单禁区路径）。故本单清理面**只覆盖非禁区的 update 路径引用**；`friction:805` 与 `workcase-writer` 的全部命中一并另行立项。

### 须一并处置的风险
本方案把 update 语义从「**省略即删除**」反转为「**省略即保留**」。凡既有调用方依赖「不写某字段＝删掉它」者，行为将静默反转。测试套件内无一例暴露（所有有效指纹的 `after` 均为全展开；3 个残缺 after 在 CAS 阶段即失败），但真实调用面须逐处迁移，且工具 schema 描述必须改写为三向声明口径——其中 6 个 per-type 文件的描述串含「(all fields…)」（friction-tools.js:558、adr-tools.js:480、norm-tools.js:462、pitfall-tools.js:467、research-tools.js:749、spark-tools.js:749），`goal-tools.js:310` 的措辞为「(Code re-assigns goal_key/created_at and appends change_log)」而不含「all fields」，**同样须改**（经建前独立审核实测校正）。
