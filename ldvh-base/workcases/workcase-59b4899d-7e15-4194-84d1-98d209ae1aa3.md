  ### 边界

### 计划步骤 4 —— 实测 outputSchema 通道（已完成，本宿主实跑）

取证方式：**在本宿主真实派派生两个子代理**（非读文档、非据签名推断）。因 AI 直调的 `subagent` 工具参数面只有 `description`/`prompt`/`run_in_background`（无 schema 字段），而 `workflow` 的 `agent(prompt, {schema})` 钩子消费 `opts.schema` 并由宿主传 `structured`，故以该入口作为 AI 可及的实测通道；被验证的是**宿主的结构化提交层**（同一层，与 provider 无关）。

同一 schema（object root，`properties: {verdict: enum[same-obstacle|new-obstacle|no-discovery], target_uid: string, reason: string}`，`required: [verdict, reason]`，`additionalProperties: false`），分别派两个子代理：

- **合规子代理**要求报 `verdict="no-discovery"`、`reason="probe-conforming"`。实测返回：`{"reason":"probe-conforming","verdict":"no-discovery"}`——object 形状精确符合 schema，无文本包裹，直接可用。
- **故意违规子代理**被要求报 `verdict="definitely-not-in-the-enum"`、`target_uid=12345`（数值而非字符串）、外加 `unexpected_extra_field=999`。实测结果：**违规对象交不出来**——enum 越界值与多余字段均被提交层拦下，数值 `12345` 被规范化为字符串 `"12345"`；该子代理只能在同一 schema 内改交合规对象（`verdict="no-discovery"`），并在 `reason` 中说明原始请求为何无法提交。

**结论**：`outputSchema` 不是事后过滤器，而是子代理**唯一的交付出口**——不合规数据根本交不出来。这与仓库既有记录 `docs/experiment-outputschema-2026-10-03.md` 的预测一致，本步骤在本宿主上独立复现了它。

**本步骤不证明的事**：① 只证明**结构**可被机械强制（字段名、枚举、必填性、类型），**不证明判断内容正确**——「这条候选是否与本次观察同题」仍是语义判断，仍属 §8.4 第 1 项登记的 gap；② 实测经 `workflow` 的 `agent({schema})` 完成，**未**经 `subagents.start(name, request)` 实调——两者共用同一结构化提交层，但 `start` 路径的实际可调用性（须持 parent Agent 与 AbortSignal）仍未实跑，留待步骤 5/7 在插件内接通时观察。

### 计划步骤 5、6 —— 子代理契约、outputSchema 通道与水位（已完成）

**步骤 5（契约）**：新增 `plugin/lib/friction-subagent-contract.js`，承载三件东西——`discoveryOutputSchema()`（object root、只用具宿主支持的 JSON Schema 子集、`additionalProperties:false`、verdict 闭集与模块导出同源）、`buildDiscoveryPrompt()`（把阈值/候选清单/水位区间三项**机械前提**写成提示词，并写明三条约束：只判断区间内内容且不得默默扩大、禁止价值判断与 Human 决定项、不得自行数 count）、`validateDiscoveryVerdict()`（跨态必填字段的落地前校验）。
