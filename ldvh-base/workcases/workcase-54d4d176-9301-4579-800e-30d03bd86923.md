### 计划步骤 1：specs/26 类型列与 §11 形态定义
`specs/26-Friction-摩擦账本.md`：§8 字段表 `attribution_ref` 类型列由 `string` 改为 `object`，值语义一格补「出现时由 Code 机械核验 object_uid 可解析，不可解析即拒绝入账」；§11 新增「非 relations 字段的引用形态（锚点型）」一段，明写必须是对象形态 `{ object_uid }`、不得是裸字符串（2026-10 订正），且目标可指任意同项目事实对象（含 Friction 自身）。两处与上下文无矛盾。

### 计划步骤 2：契约登记与归一
`plugin/web/api/services/factFieldContract.ts` 的 `attribution_ref` 由 `field(...,'object',false)` 改为 `objectField('friction-attribution-ref', false, { requiredKeys:['object_uid'], nonEmptyKeys:['object_uid'] })`，并新增 `ObjectShape` 类型与 `objectField` 工厂；`plugin/web/api/services/localFactReader.ts` 新增 `matchesObjectShape`，`matchesExpectation` 增加第三参数 `shape`，调用处传 `contract.objectShape`。`plugin/web/tests/api/fact-field-contract.test.ts` 增一条登记断言。

### 计划步骤 3：CLI 两处投影
`plugin/lib/friction-writer.js` 的 `listFrictionObjects` 与 `plugin/lib/friction-tools.js` 的 `executeReadObject` 均改为经 `normalizeAttributionRef` 归一后投影。**复核发现 7 的收敛**：原先两处各自内联了一份逐字等价的归一器，现已改为 `friction-tools.js` 直接 import writer 侧导出的 `normalizeAttributionRef`，只保留一份权威实现。

### 计划步骤 4：形态校验与可解析性核验
`plugin/lib/friction-writer.js` 的 `validateFrictionFrontmatter` 补 `attribution_ref` 三态形态校验（对象形态 / 裸 uuid 串 / 其余非法，各给独立错误文案）；新增 `ATTRIBUTION_REF_DIRS`（7 类事实目录）与 `verifyAttributionRefResolves`，在 `create`／`update`／`correct` 三入口的 `validateFrictionRelations` 之后、落盘之前核验 `object_uid` 可解析，不可解析即零写拒绝，错误码 `friction/attribution_ref_unresolvable`；该码同时登记进 `plugin/lib/friction-tools.js` 的 `mechanicalCodes`（不登记会被判成 `unavailable` 而非 `rejected`）。
**复核发现 6 的收敛**：扫描正则改为行首锚定且不带 `\s*` 前缀（只认顶层 `object_uid` 声明行，避免把 relations 成员或正文里的缩进 uid 当成载体身份而 fail-open），命中值再走同一 `UUID_PATTERN` 复核（不让「可解析」与「合法 uid」分裂成两套判定）。新增测试钉住缩进 uid 不被误判为可解析。
**复核发现 4 的收敛**：该核验位于 `no-op` 判定之前，意味着已落盘悬空锚点的终态载体无法再经 `correct` 改正文。这是 fail-closed 的自洽结果，已在 `specs/26` §13 显式记为「悬空锚点的可达性约束」，并写明可行出路（`observing`／`open` 走 `update` 补正锚点；终态失效走状态流转），避免该约束下次以隐性回归面出现。

### 计划步骤 5：工具 schema 双形态与守卫
`plugin/lib/friction-tools.js` 的 `attribution_ref` 由 `type:"string"` 改为 `oneOf` 双分支（string 分支排第一——`valueSatisfying` 取 `oneOf[0]` 造样）。
**复核发现 5 的收敛**：`plugin/test/schema-writer-agreement.test.mjs` 原先只对 `oneOf[0]` 造样，对象分支零覆盖；新增 `valueVariantsSatisfying` 对每个 oneOf 分支各造一样各探一次，标签带 `[oneOf#N]`，守卫从此覆盖全部合法承载。

### 计划步骤 6：真实管道保真测试
新增 `plugin/web/tests/api/friction-attribution-ref-fidelity.test.ts`（两条：对象形态经 `showObject` 不被丢弃；裸串按 §11 被拒并报 `type_mismatch`，不再假装存在一条并不存在的兼容行为）与 `plugin/web/tests/api/friction-attribution-ref-shape.test.ts`（四条坏形态：缺 `object_uid`／空对象／`object_uid` 非字符串／空字符串，均须报 field issue 而不得原样投影）。
**复核发现 3 的收敛**：原 web 读取层对 `expected:'object'` 只做 `isRecord` 判定，`{}` 与 `{ garbage_key:1 }` 会被当作合法承载原样投影，而 CLI 侧对同样输入返回 `undefined`——同一载体两套读法。本次以新增的 `objectShape` 契约能力补上内容核验，web 与 CLI 读法一致。该四条测试是先写红测确认缺陷真实存在、再改实现转绿的。
