# 运行实例版本判据被自动重启推翻

## 现象

助手以「进程启动时刻早于源文件修改时间」断定服务端仍加载旧代码，同轮又发现该进程已被插件自动拉起替换（同 PID 已不存在），该判据随即被推翻。

（来源：22）
2. （2026-11-14T09:40:53.508Z，session-04bdf95b-a6a7-4e33-9d9a-17fbe414422a @ 48）早于我改 objects.ts 的时间，说明服务端是旧代码
（来源：48）
3. （2026-11-14T09:53:39.686Z，session-04bdf95b-a6a7-4e33-9d9a-17fbe414422a @ 52）进程在 17:39:22 启动，早于我改 `objects.ts` 的时间，说明**服务端是旧代码**
（来源：52）

## 入账依据

该判据只在「所观测进程未被外部替换」时成立，而本仓插件服务子进程会自行拉起/重启，故在同一部署形态下必然被推翻；改为对当前存活实例取版本回指（或以重启后重测为准），可避免把「旧代码」当结论并据此反复返工。

## 处置

**不可清偿去向（不在本项目可动范围，Human 2026-11-20 裁定）**：根因落在「运行实例版本取证层」与「宿主 plugin 服务子进程自动重启机制」之间缺绑定——判据只比对单个 PID 的启动时刻与源文件 mtime，既无「该进程是否已被替换/重启」的判据位，也无对当前存活实例的版本回指位。宿主会自行拉起/替换子进程（同 PID 消失、新实例接管），本仓作为受管辖项目无法让宿主在重启时提供存活实例的版本回指，消除途径不在本项目可动范围，按 36 §9.4 第 2 类接受，不再作为待修项计入。

**规避而非根治（如实登记）**：本仓能做的只是作业纪律规避——不把「PID 启动时刻早于源文件 mtime」当确定事实、以重启后重测为准、必要时取存活实例版本回指；这些都绕不开「宿主自动替换子进程且不吐回指」的根因，不构成解药，故不走 resolved。

**复审触发**（自觉约束，非机械检测）：当宿主 plugin 服务子进程的自动重启/版本回指机制改变（例如重启时在终态或健康探针中输出当前加载版本、或停止自动替换使 PID 启动时刻重新可信）时，由 Human 按 26 §10 Human 入口新建 open 账目并在正文接续本 uid。宿主版本升级、plugin 服务拉起流程变更是应关注的信号。

**配对复审**：`open → accepted` 不触发配对复审（36 §9.4）——本账目无 `paired-with` 边，债未清偿，规避经验仍按需要处理。
