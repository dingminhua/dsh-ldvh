# 短 ID 查询事实对象必然落空

## 现象
按工单短 ID 查询事实对象时查不到结果，实际标识是完整 UUID，该次查询落空

### 该阻碍的历次观察（3 次，逐字引证）
1. （2026-11-04T06:05:27.536Z，session-22dbafa4-e962-49cc-b69a-27e606271907 @ 3）另外两个文件都被丢弃了，连一条 invalid 记录都没有
（来源：3）
2. （2026-11-04T06:49:59.161Z，session-22dbafa4-e962-49cc-b69a-27e606271907 @ 5）WorkCase 的 list 存在同一缺陷：它把文件名当成身份，命名形态不符的载体仍会被静默丢掉
（来源：5）
3. （2026-11-05T13:39:14.882Z，session-ce3bdb87-5510-4b78-b491-5629c267682a @ turn 30..32）文件名是完整 UUID，我之前按短 ID 查所以没找到。
来源：主控会话 [turn 32] 的 assistant 正文（提交分组阶段，查看 10 个 closed 工单状态处）

## 入账依据
事实对象的身份是完整 UUID（02 §7.1），而查询入口只按完整 UUID 匹配，短名/短 ID 形态没有任何解析器把它归一到完整 UUID；于是同一对象存在「短 ID 查询 → 静默零结果」与「完整 UUID 查询 → 命中」两条路径，且前者没有「未命中，请用完整 UUID」的提示，把一次必然落空的查询表现成数据不存在。本条引证：「文件名是完整 UUID，我之前按短 ID 查所以没找到。」（主控会话 [turn 32] assistant 正文，提交分组阶段查看 10 个 closed 工单状态处）。它是可复现的（换任何以短 ID 为参数的查询都会落空），且落在「查询入口的标识归一层」这一系统性位置，故属应攒的摩擦观察而非一次性噪音。
