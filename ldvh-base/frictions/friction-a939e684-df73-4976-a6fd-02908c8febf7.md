# 短 ID 查询事实对象必然落空

## 现象
按工单短 ID 查询事实对象时查不到结果，实际标识是完整 UUID，该次查询落空

### 该阻碍的历次观察（3 次，逐字引证）
1. （2026-11-04T06:05:27.536Z，session-22dbafa4-e962-49cc-b69a-27e606271907 @ 3）另外两个文件都被丢弃了，连一条 invalid 记录都没有
（来源：3）
2. （2026-11-04T06:49:59.161Z，session-22dbafa4-e962-49cc-b69a-27e606271907 @ 5）WorkCase 的 list 存在同一缺陷：它把文件名当成身份，命名形态不符的载体仍会被静默丢掉
（来源：5）
3. （2026-11-05T13:39:14.882Z，session-ce3bdb87-5510-4b78-b491-5629c267682a @ turn 30..32）文件名是完整 UUID，我之前按短 ID 查所以没找到。
来源：主控会话 [turn 32] 的 assistant 正文（提交分组阶段，查看 10 个 closed 工单状态处）

## 入账依据
事实对象的身份是完整 UUID（02 §7.1），而查询入口只按完整 UUID 匹配，短名/短 ID 形态没有任何解析器把它归一到完整 UUID；于是同一对象存在「短 ID 查询 → 静默零结果」与「完整 UUID 查询 → 命中」两条路径，且前者没有「未命中，请用完整 UUID」的提示，把一次必然落空的查询表现成数据不存在。本条引证：「文件名是完整 UUID，我之前按短 ID 查所以没找到。」（主控会话 [turn 32] assistant 正文，提交分组阶段查看 10 个 closed 工单状态处）。它是可复现的（换任何以短 ID 为参数的查询都会落空），且落在「查询入口的标识归一层」这一系统性位置，故属应攒的摩擦观察而非一次性噪音。

补充观察（2026-11-13T18:35:19.825Z）：引证显示本轮实际发生一次「用短标识更新 Spark 被 spark/invalid_uid 拒绝」，且材料中把这一形态不对称列为仍「未做」的第一项抓手（「读面认五种写法，写面仍 assertValidUid 只认 canonical UUIDv4」），并在 24 小时失败分类中单列「指称形态 2 次」。归因落点是 LDVH 工具面对象标识形态的归一层：事实对象的唯一身份是完整 UUID，而各入口各自规定自己接受什么形态，入口侧没有任何把短标识翻译成完整 UUID 的共享解析器——写入口只认 canonical UUIDv4，读入口却认五种写法。与既有 open 账目 friction-a939e684（短 ID 查询事实对象必然落空）的归因「标识形态的归一职责在入口侧无人承担」落在同一子系统、同一机制模式上，且该账目本身已把 b733502f（复制端产物无解析方、消费端只接受裸 UUID）
逐字引证：第一次用 `spark-096c1e6d` 短标识更新，被 `spark/invalid_uid` 拒绝。
（来源：3）

补充观察（2026-11-14T09:13:27.966Z）：引证表明：写入入口的标识接受面只认 canonical UUIDv4 这件事在规范源里找不到任何依据——搜遍全仓只搜到 object_uid 字段值域的规定，没有一条规定写入入参只接受这一种形态，因此该限制是实现自选口径（adr-writer.js 的 assertValidUid），而读侧 object-reference.js 的五种形态解析器未被写入入口复用（材料给出「改实现：写接口接受与读接口相同的形态集」作为出路，并称这样「立刻消掉 3 次失败」）。这与既有 open 账目 friction-a939e684 的归因落点一致：该条归因为「标识形态的归一职责在入口侧无人承担」，并已把 b733502f（复制路径只接受裸 UUID）指为同一处缺口；本次材料补的是同一根源在写入路径上的表现（入口只认裸 UUID、短名/短标识形态被拒），机制模式相同（规范已给最小可读形态、入口侧无归一解
