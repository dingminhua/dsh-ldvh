# serves 归属缺少反查复核

## 现象

serves 归属只在写入时校验，无写入后的反查复核。

具体表现：`serves` 的机械校验仅发生在受控创建与更新两个时点（`spark-writer.js` `spark/serves_unresolvable`、`friction-writer.js` `friction/serves_unresolvable`），校验内容限于「形状匹配 `SG-[1-9]\d*`」与「锚点存在于 goal.md 子目标」。写入成功后，不存在任何机制按 `serves` 反查名下对象、复核其归属是否仍成立。20 §8 明示该字段为「轻量归属引用，不参与 goal 修订级联（25 §11 豁免）」——豁免的对象是 goal 修订级联，而级联之外亦无替代复核通路。

本账目有**两个**触发实例，且第二个比第一个更硬：

**实例一（依据失真）**：Spark `cdc8bf7d` 的正文「仍未决的两项与证据缺口」所用依据已部分失效（只检索 05 而未检索类型层，见下「入账依据」），该失真直至 2026-09-15 由 Human 主动点名该对象、AI 逐项复核才被发现。

**实例二（字段静默丢失，机械可证）**：同一对象在 2026-09-14 缩范围提交 `9e4f9d5` 中，`serves: SG-1` **被连同 `priority: P2` 一并删除**——该提交的信息只声明移除 `priority`（「同时更正触发时点并移除 priority（该字段在 open 态缺失合法）」），对 `serves` 的删除**只字未提**。实测：`af4e774`（导入时）与 `dd3be15` 均有 `serves: SG-1`，至 `HEAD` 时该行已不存在；`git show 9e4f9d5` 对该文件的 diff 同时含 `-serves: SG-1` 与 `-priority: P2` 两行。**该丢失自 2026-09-14 存续至 2026-09-15，全程无任何机械或人工机制报告**——写入时校验不会重跑（对象未被再次写入），反查复核不存在，Web/工具投影只是如实反映「没这个字段」，于是该对象在整个 Spark 集合中成为唯一一条无 `serves` 的记录，直到 Human 用肉眼在列表中发现它缺 `(SG-1)` 后缀。同类暴露面：当前 39 条 Spark 中 30 条声明 `serves: SG-1`、7 条 SG-3、2 条 SG-4，全部处于同一复核真空中；Friction 侧已有 1 条同样声明 `serves`。

## 入账依据

三条件逐项核对：

**重复出现**——本机制对每一条声明 `serves` 的对象都成立，不是单次卡顿。当前事实源内 40 个声明 `serves` 的对象（39 Spark + 1 Friction）全部只经过写入时校验、全部未经过任何反查复核。失真是否已实际发生属事后核对，但**复核通路的缺失对全体对象同等成立**，不因单个对象是否恰好失真而改变——这是结构性重复，不是偶发。上「实例二」已给出一次**已实际发生**的丢失：一个字段在受控更新中被静默删除并在事实源中存续一日，全靠 Human 目视发现。

**可归因**——归因到 `20 §8` 与 `25 §11` 共同确立的设计边界：`serves` 被定性为「轻量归属引用」并**显式豁免**于 goal 修订级联。该豁免在「目标锚点稳定、归属长期有效」的乐观前提下是合理的——`SG-n` 编号冻结、原位作废不换号（25 §6），故锚点本身不会失效。**但规范只保证了锚点的有效性，未保证归属判断的有效性**：对象当前工作实际服务哪条子目标，会随对象自身缩范围、修订、外部依赖消化而变化（`cdc8bf7d` 即典型——它从未改过 `serves`，改变的是它自己还剩多少内容真正属于 SG-1）。写入时校验能拦住「锚点不存在」，拦不住「锚点存在但归属已漂移」。25 §11 的豁免只考虑了「goal 变动向下传导」，未考虑「对象自身变动导致归属失真」这一反向情形。

**修了会更好**——若存在按 `serves` 分组的反查复核通路（F1 投影按 `serves` 聚合、或在对象更新时对其所属子目标给出一条待复核提示），上述漂移可在缩范围提交的当次暴露，而不必等 Human 点名。**本账目不预设修复形态**（反查投影、更新期提示、定期巡检均属候选），仅登记该通路缺失。修复不改变任何既有机械校验强度——写入时的 `serves_unresolvable` 拒绝保持不变，本账目要的是**写入之后**的复核，不是在写入时加严。

**未决事项与转化条件**（登记于此，非处置承诺）——修复形态与归属层级（20 类型层加反查提示 / 25 goal 层加按 SG 聚合投影 / 05 服务层加检索操作）须经 Human 定案，本账目不自行选定。与既有账目 `3048937d`（已转 deferred，理由是「LDVH 体系结构缺口而非实际工作流摩擦」）的区别必须说清：`3048937d` 记载的校验规则本身完备正确、仅暴露顺序错位，故不构成摩擦；**本账目记载的是一条复核通路根本不存在**，其后果已在真实对象上产生可观测的依据失真，且该失真对 39 条同组对象同等成立。若 Human 判定该缺失同样属「系统未完善」而非「实际工作流摩擦」（沿用 `3048937d` 的裁定口径），则应转 deferred 并由相应 Spark 承接——**该裁定权在 Human，不在 AI**。

**与本账目并列的一处实现事实**：`ldvh_spark_list` 工具的列表行当前输出 `title + status + serves`，与本条现象相关但**不是同一件事**——那是投影已实现但字段取舍与 20 §12 的 F1 规定（`title + status + priority + serves + refs`）不一致，属实现侧投影遗漏，已另行核实，不在本账目归因范围内。
