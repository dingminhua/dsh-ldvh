# Git Gate 大 diff 超 maxBuffer 阻断

## 现象
Git Gate 对提交 diff 取 stdout 的 maxBuffer 为 4MB，批量删除文件致 diff 超过该上限时 commit-msg 钩子以「unavailable: stdout maxBuffer length exceeded」阻断提交。

## 入账依据
本次提交 214 份 docs 删除时实测触发：git-gate-runner.js:17 的 `execFileAsync("git", [... "diff", "--cached", "--binary", "--no-ext-diff"], { maxBuffer: 4 * 1024 * 1024 })`，而该笔候选 Index 的 `git diff --cached --binary | wc -c` 为 4809443 字节（4.59MiB），超限 4MB，钩子以 unavailable 退出、提交被拒。可归因性：根因明确落在 `plugin/lib/git-gate-runner.js` 的 maxBuffer 常量，与提交内容语义无关。修了会更好的预期：该笔为合法提交（214 个纯删除、precheck 已判 passed），仅因承载量超限被拒；同一仓库中 `ldvh-tools.js:548` 的 precheck 侧 maxBuffer 已是 8MB——**同一校验的两个入口取不同上限**，正是 09 §5.1 双入口一致性要求所指的形态，提高 gate 侧上限即可使二者一致并消除该阻断类。另实测：8MB 时同一 diff 正常返回（2710540 字节，214 条 `diff --git` 行），故该上限有明确充分值。本笔为机械通道创建，仅陈述现象与实测证据，不评影响等级以外的结论。

## 处置
解药为提交 `a43883fe5768c480fd49c3f1dacdb06f27021a6b`（直提路径修复，无对应的 ADR/WorkCase 事实对象，故依 02 §8.1 commit 形态以 informs 承载）：`plugin/lib/git-gate-runner.js` 的 staged diff 上限由 4MB 改为 8MB，与 precheck 侧（`plugin/lib/ldvh-tools.js:548`、`:621`）一致，09 §5.1 的双入口一致性要求由此成立。

核验（2026-10-14，第 0 批-核验销账）：全仓 `maxBuffer` 共 5 处——两入口各 8MB 之外，`plugin/lib/hook-manager.js:69` 与 `:247` 的两处 1MB 分别用于 `rev-parse`/`hash-object`/`read-tree` 等小输出管道与钩子自身输出，**均不在 staged diff 路径上**，无残留较小上限落在被阻断的路径。

**未覆盖（如实声明）**：本次核验**未重跑**「>4MB staged diff 过 gate」的实测，结论依据为两个入口取值已一致 + 无残余小上限 + 修复提交自带的实测记载（4.59MiB 触发、8MB 正常）。8MB 仍是真实上界，超限仍会阻断——那属承载量约束，不是本账所指的「两入口不一致」形态；若将来实测出新的承载量性阻断，应按新阻碍另立账目，本账终态不重开（26 §9.2）。
