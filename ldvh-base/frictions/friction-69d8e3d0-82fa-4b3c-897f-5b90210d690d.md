# 环境检查对 complete 目标无路径

## 现象

执行期接手的环境检查只以 resume 恢复宿主推进目标，而宿主 resume 的可恢复相位闭集不含 complete，故相位为 complete 的目标使环境检查永久失效，且失败被静默降级为 action:none。

**实例（2026-10-18，workcase-996e207a）**：执行会话 session-afff56ac 的宿主目标于 07:08:47 被置 complete（revision 4），而工单至今 open。此后该会话历经 14 个回合（turn 5–18），每回合 step 1 都执行 rearmInFlightWorkcaseGoal：它读到目标文本仍承载 workcase-996e207a、工单 status 仍为 open，遂调用 resume；宿主 @deepseek-ai/dsh-goal 的 resume(agent, ref) 实现为 const resumable = ["active","paused","blocked"]; if (!resumable.includes(current.phase)) throw this.transitionError(...)，complete 不在其中，故抛 GOAL_INVALID_TRANSITION。rearm 的 catch 分支返回 {ok:true, action:"none", detail:{reason:"resume failed: …"}}——既不拒绝、不重试、也不上报。

**规格与实现的对照**：同一模块在设置点（approve／execute）对 complete 有正确处置——if (current.phase === "complete") { goals.create(agent, {objective}) }，即「已完成的目标可被替换」（宿主 create 的契约注释同此：A completed goal may be replaced; every other current phase must be cleared or resumed instead）。rearm 路径没有这个 create 分支，只有 resume。故同一障碍在设置点有解、在环境检查点无解。

**静默性（本条的加重情节）**：rearm 的设计原则是「不拒绝任何动作」（21 §14 接手侧不因检查失败拦住会话），其失败分支遂一律 ok:true 降级。但 lifecycle.js 的调用点 await rearmInFlightWorkcaseGoal({…}) 丢弃了返回值，既不看 action 也不看 detail，故「环境检查试过、被宿主拒绝、工单仍失位」这一事实在日志、对象与工具输出中零痕迹。实测：~/.dsh/logs/desktop-next.log 中 turn-start check failed 计数为 0（该文本是 onTurnStart 抛错时的兜底日志，而 rearm 从不抛错）。

## 入账依据

**重复出现**：条件为「目标相位 = complete」而「工单 status = open」，一旦成立，每一个回合都会重复触发同一失败，且永不自行恢复——这是结构性、逐回合重复的失效，不是一次性卡顿。本次 14 个回合即为 14 次重复。更广地说，任何使宿主目标到达 complete 而工单未关闭的路径（AI 直调 update_goal complete、Human 在界面完成的、其它会话完成的）都会落入该态；本条与 friction-98c0a43d 互为因果：那条记的是规范未规定收口受阻时目标应保持何态（目标为何会到 complete），本条记的是环境检查对 complete 相位无恢复路径且静默（到了 complete 之后为何救不回）。

**可归因**：归因到 plugin/lib/workcase-goals.js 的 rearmInFlightWorkcaseGoal 与宿主 goals 服务契约之间。宿主契约把 resume 的可恢复相位限定为 active／paused／blocked，把 complete 划给 create（替换）；rearm 只用 resume，故对 complete 无路径。生命周期调用点 plugin/lib/lifecycle.js:307 丢弃返回值，使该失效静默。

**修了会更好**：若 rearm 对 current.phase === "complete" 补上 create 分支（与设置点同构、复用宿主既有的「已完成目标可被替换」语义），则目标被误置 complete 后，工单仍 open 时环境检查可自行恢复；若 lifecycle 调用点改为读取并登记 rearm 的 action／reason，则该恢复与其失败都可被观察，符合 21 §14「要点是可观测」的自身要求。本账目不预设具体修复形态（补 create 分支／调用点登记／在 §14 明写 complete 的处置），只登记「环境检查对 complete 无路径」这一机制缺口。

**未指定解药（如实登记）**：解药属实现与规范的分工决定，且与 friction-98c0a43d 的处置同域（若那条的处置为「目标不得在对象未关闭时完成」，本条的暴露面会被收窄但不消失——目标仍可能因界面操作或其它会话到达 complete）。故本账目 relations 不出现，是否与 98c0a43d 合并处置由 Human 决定。

**放回留观说明**：本条 occurrence.count=1（<3，未达 04 §8.4 阈值 N），按 26 §9.2 保持 observing 留观态。

**首次观察来源**：2026-10-18 本会话（Human 提问「在执行的工单没有按照要求设置宿主的goal功能」），经会话日志 goal/change 事件序列（create→resume→resume→complete，此后 14 回合无任何 goal 事件）与宿主 dsh-goal 实现原文双向核对定位；rearm 的相位覆盖由四相位对照探针实测（active+disarmed／paused／blocked 三者 rearmed，complete 为 none）。

**与既有账目的区别（如实登记，避免重复入账）**：friction-98c0a43d 记规范未规定收口受阻时目标的应然态；本条记环境检查对 complete 相位的恢复路径缺失与失败静默。friction-09ff06a3／56a9f9a8 记「返回值被丢弃致登记静默失败」，其形态与本条的调用点丢弃返回值相邻，但对象不同（那两条是异步闭集登记，本条是环境检查的结果）；本账目不重复其主张。
