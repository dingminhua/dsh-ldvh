# 宿主 web 工具指向未注册 provider

## 现象

宿主注入的 web_search 与 web_fetch 工具把调用指向未注册的 provider 名，使规范外网取证通道整体不可用，同一时刻本机 shell 直取相同 URL 可达。

具体观察（2026-10-29 一次调研会话）：

- `web_search` 调用返回 `Error: configured web provider "ddg" is not registered`；
- `web_fetch` 对两个不同 URL 的调用均返回 `Error: configured web provider "fs-quality-fetch" is not registered`（同一工具、同一配置名，多次调用一致）；
- 同一时刻用 shell `curl` 直取本应经 web_fetch 取得的 URL：`https://sre.google/sre-book/postmortem-culture/` 返回 200（55,113 字节）、`https://docs.github.com/.../about-code-owners` 返回 200、`https://raw.githubusercontent.com/steveyegge/beads/main/README.md` 返回 200；
- 另两条路径返回 404，属 URL 本身失效（runbook 一类未取得来源，已记入 research-5c135fae 的 gaps），与本条机制无关，不计入本账。

即：**网络可达性正常，失败发生在宿主工具的 provider 解析层**。该失效不产生「取不到内容」的模糊信号，而是显式报未注册——这是它比一般网络故障更易诊断的一面；代价在下一节。

## 入账依据

1. **可归因**：根因落在宿主的网络工具 provider 配置面——配置的 provider 名（`ddg`、`fs-quality-fetch`）无已注册实现。归属层级不在本仓可改范围：本仓不定义也不注册宿主 web provider，宿主配置位于 `~/.dsh/` 下，属环境接入面。
2. **反复出现**：单次会话内 web_search 一次、web_fetch 三次，共四次独立调用全部命中同一失败；`occurrence.count=1` 按 26 §8 口径记本次入账时确认的观察组规模，不推定跨会话累计。它是「每次调用必失败」的配置态而非偶发时序问题，在配置修复前会以相同形态重现。
3. **修后更优**：修好后 33 §5.2 第 2 项所要求的「可访问来源」通道恢复，后续调研不再需要绕行取证，也不再需要把「取回路径经由实现层」写进报告的边界声明。
4. **查重结果**：全目录 57 条 Friction 逐条核对标题与现象，无同一失效形态。三条同族最近邻：
   - `906dae15`——插件 lib 改动只在宿主重启后进入运行实例（模块重载缺口），已 voided；
   - `fbd65401`——长驻进程按启动时缓存的旧模块执行 precheck，与 Git Gate 新进程口径不一致，已 resolved；
   - `6cb53179`——`.git/hooks/commit-msg` 裸 `exec node` 在 PATH 无 node 时把拒绝原因与校验不通过混同，已 resolved。
   三者共同特征是「宿主执行了与磁盘代码不一致的版本」或「环境路径依赖」；本条是「配置直接指向不存在的 provider」，调用在接缝层即被拒，不存在版本比对问题，归因对象与失效形态均不同，故新建而非并入。

**影响判级 medium 的依据**：本次由 shell 直取绕行后，调研得以完成全部取证并落为 `research-5c135fae`，未造成结论缺失或交付阻塞，故不判 heavy；代价有三处真实发生——（a）取证路径改道：来源文本仍一手，但取回方式经由实现层，须在报告「未证实与缺口」中如实声明；（b）本条中一条 URL 因无搜索结果辅助而无法定位（runbook 相关路径 404，最终未取证，记为 low 缺口）；（c）`ldvh_discover_capabilities` 查 `web-search` 返回 no public operation，无法用 LDVH 能力面确认该通道的声明状态。综合判 medium。
