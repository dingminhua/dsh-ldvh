# 受控写入时手工内联长正文被截断

## 现象
本轮助手再次以手工重抄长正文的方式向受控写入接口提交 Spark 正文，写入被截断在开头一节，须改用脚本从磁盘原文追加后重写。

## 入账依据
现象可归因于主控在同一会话中反复选择「手工重抄正文」而非「从磁盘原文读取后写入」的路径，且失败位置与原因一致；若写入面提供/强制从原文取数的路径或对内联长度设机械边界，该失败不会发生。

补充观察（2026-11-04T08:45:40.217Z）：受控写入接口在接收手工内联的长正文时把内容截断在开头一节。

来源：本会话 turn 3 助手回复「必须如实声明的边界」段 list 第 2 项（"期间还新冒出两个未跟踪载体：friction-4d4f0369（手工内联长正文被截断）与 web 侧改动 —— 都不是我的产出"）

补充观察（2026-11-04T09:22:29.236Z）：本次材料 turn 7 中，主控向受控写入接口提交 Spark 正文时，先因缺 frontmatter_after 被要求补参、再因「summary 必须逐字出现在『当前理解』节」被拒，最终把摘要写进正文才写入成功。这与既有 open 账目 friction-4d4f0369（受控写入时手工内联长正文被截断）的归因落点与机制模式相同：根源都在「主控经受控写入接口提交长正文时的取材路径（手工内联而非从磁盘原文读取）+ 写入接口未对内联正文长度与完整性/内容边界设机械边界」这一接缝缺口，同一种方式反复产生（一次被截断、一次被内容位置约束拒收后改走别的路径重写），故按 26 §6.2 归因+机制模式判为同一阻碍，而非按措辞判为新条目。本次未发现与之并列的其他系统性阻碍；Pitfall 侧交付仅 40/53，跨类型查重不完整。
