# 并发会话 reset 卷走未提交改动

## 现象
另一个会话在 dev 分支上执行 git reset: moving to HEAD，把本会话未提交的工作树改动全部卷入一条 stash，导致 stash 创建之后才写入的 F1 refs 修复与工单执行节无法从 stash 取回

## 入账依据
可归因性：材料直接给出卷走源头与时刻——并发会话 03:12 的 git reset 生成 stash@{0}，03:18–11:57 又有 6 个提交落在同一分支；丢失边界有实测判据（stash 里也不存在的 F1 refs 修复与工单执行节，工作树退回 210 行 draft 版）。可改善预期：只要未提交工作区与并发分支操作相互隔离（每会话独立 worktree，或对含未提交改动的工作树在 reset/stash 前置机械拦截并提示），此类静默丢失即可消除，代价仅是一道前置检查。

补充观察（2026-10-19T06:22:58.701Z）：材料逐字记载了并发会话提交清空共享暂存区、导致本会话改动被挤出并使预检失败的现象；既有账本中 4290b838「并发会话 reset 卷走未提交改动」记录的正是同一阻碍机制——并发会话操作作用于共享仓库状态把他方未提交改动卷走，本次的具体动作是提交而非 reset。
