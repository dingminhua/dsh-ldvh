# 局部改动时以记忆或截断输出为数据源

## 现象
主控在只改一条账目 title 时两次把该对象其它内容写坏：一次凭印象把两个真实时间戳换成编造的整点数并整段重写「入账依据」，另一次把经 cut 截断的终端输出当正文粘贴致正文由 1227 字截成 816 字

## 入账依据
两次写坏的逐项实况（归因于本次运行本身）：

- **第一次（数值伪造＋改写他处）**：我凭印象填 `occurrence`，把两个真实时间戳（`first_at: 2026-10-14T05:48:44.064Z`、`last_at: 2026-10-15T05:02:46.220Z`）换成了编造的整点数（`2026-10-11T00:00:00.000Z`／`2026-10-14T00:00:00.000Z`），同时整段重写了「入账依据」——原文中例①的机制位置（`spark-tools.js` 的 `sparkCreateReport`／`sparkTerminalReport` 用 `\n` 拼字段）与「两例的机制差异」分析被我的转述取代。
- **第二次（截断冒充全文）**：我把先前经 `cut -c1-130` 截断的终端输出当作正文粘贴，正文由 1227 字被截成 816 字，丢失 411 字（例②与「两例的机制差异」的实质部分）。
- **两次的发现与还原**：均在落盘前自查发现，以 `git checkout HEAD` 还原，第三次重做。

**根因与触发条件**：两次的数据源都不是载体——第一次是记忆，第二次是被截断的中间输出；而对象内容的权威来源只有载体本身。触发条件很窄但很常见：**改动范围极小（一行标题）而要求提交完整对象**，此时容易顺手「补全」未逐字核对的部分。

**与既有账目的关系（查重结论：非重复，同根）**：

- `5d5862c9`（回滚未取原文致以改写冒充恢复）——**同根而不同形**：两者都是「不以原文为准而以自拟或自记为准」，但那条发生在**回滚**整段内容时，本条发生在**局部改动**时顺带改写他处；且本条的失效含**数值伪造**，而那條是措辞改写。数值伪造更隐蔽：措辞不同一眼可辨，编造的整点时间戳看起来完全合理。
- `c58675c`（规范读取返回被截断致受控读取路径失效）——那条是**工具返回**被截断，本条是**主控自己把截断输出当数据源**：即使工具完整返回，若主控从经过 `cut`／`head` 的中间产物取数，同样会发生。

**后果的真实边界（如实声明）**：本次两次均**未造成落盘污染**——两次都在提交前自查发现并还原，故未产出错误结论。本条记的是**做法**；其潜在后果是事实对象被静默改写（对象看起来正常、`read_back: ok`，但内容已非原文）。

**已识别的防法（本次第三次做对所用）**：改动前把字段**逐字从载体取出**（不手打、不复制中间产物），落盘后用脚本比对「预期保留的部分是否与基线逐字相同」——本次即以该方法确认「正文 1227 字与 HEAD 相同、除标题两行与 change_log 外逐字相同」后才提交。

## 处置
**机制级对策已落地（workcase-c36b0208，修复提交 8b7b9b3）**：本条反复出现的触发条件——「改动范围极小、而要求提交**完整对象**」——其根源不在主控的记性，而在**受控更新入口的契约**：7 个 per-type writer 的 update 路径原以「从调用方 payload 整体构建 frontmatter」实现，要求调用方手写全字段；调用方漏抄一行，该字段即被静默删除。这使「以记忆补全未逐字核对的部分」成为**结构性诱因**，而非仅靠自律可避免的个人失误。

本次改动把该义务从调用方收回服务侧：写入入口改为「磁盘基线 + 显式声明变更 + 显式删除通道」——调用方**只声明要改的字段**，未携带的字段一律从磁盘基线继承。于是「漏抄一行」在机械上不再等于「删除该字段」：调用方不再需要回传完整对象，本条所述失效的主要触发面被消除。

**保证边界（如实声明，不得过度主张）**：
- 本对策消除的是「**漏抄导致字段丢失**」这一路径，**不消除**「声明集中某字段的值本身是凭记忆编造的」（如编造整点时间戳）——那是取值来源问题，须由逐字取载体与落盘后比对来防；
- 提交消息 trailer 照抄历史值一类属**提交侧**，不在本次改动覆盖范围内；
- 本改动对既有调用方的语义由「省略即删除」反转为「省略即保留」，已在提交消息中如实声明。

据此，本条所记的阻碍的**结构性成因**已由机械保证覆盖，销账。仍保留的取值来源类风险由上述自律手段与其后可能的独立立项承接。
