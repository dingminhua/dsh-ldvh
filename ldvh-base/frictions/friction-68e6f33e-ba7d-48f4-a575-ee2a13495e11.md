# 并行会话在途重写同一代码块致合并前提失效

## 现象
主仓 dev 工作树中另一会话的未提交改动已重写助手改动的同一排序块（compareFactHits），助手已提交的召回侧改动前提被推翻，合并无法进行、该部分需重做。

### 该阻碍的历次观察（3 次，逐字引证）
1. （2026-10-27T08:32:17.089Z，session-75bb2718-fe7a-4209-aff3-80f00eee8ff4 @ 16）这就是那个经典陷阱：**主检出因为带着未提交的 `source-recall.js` 而通过，而干净检出会失败**
（来源：16）
2. （2026-10-27T08:40:54.733Z，session-75bb2718-fe7a-4209-aff3-80f00eee8ff4 @ 17）这份未提交改动**自身就有一例测试失败**（召回精确率从 10.8% 退到 9.2%）。
（来源：17）
3. （2026-10-27T09:17:19.816Z，session-d44bfdfb-ded5-4f9f-a74c-e0c6f4591eb2 @ 14）如果我现在合并，要么产生冲突要我手工裁决，要么把我的改动覆盖掉——两种都不该由我擅自决定。
（来源：14）

## 入账依据
可归因：共享工作树上并行会话的在途未提交改动与本执行者改动直接重叠，落盘前无可见性/隔离手段；修了会更好：合并前即可发现前提已被推翻，避免已提交实现整体作废。
