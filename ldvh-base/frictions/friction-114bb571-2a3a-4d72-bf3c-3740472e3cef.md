# 断言与实现共用常量致变异未检出

## 现象
把上限常量 200 改成 5000 后，接缝层 10/10 用例仍全部通过，变异未被检出。

## 入账依据
可归因：空转由「断言与实现共用同一常量」这一具体写法直接造成，改断言为字面值 200 后同一变异立即转红、11/11 恢复全绿，可归因性明确；修好后会更好的预期：用例能真正固定被守护值，避免后续改动上限时保护用例静默失效。

补充观察（2026-11-13T19:39:03.047Z）：本次材料 turn 7 助手自陈：本轮落盘的 ask-text-guard 校验器里 ASK_TEXT_MAX_CHARS = 200 与 host-seams.js 的 ASK_QUESTION_MAX_CHARS = 200 是两份副本、须收敛成单点 re-export。这与既有 open 账目 friction-114bb571（断言与实现共用 ASK_QUESTION_MAX_CHARS 这一被守护上限、断言与实现同源致变异未检出）落在同一子系统（plugin/lib 内被守护量 200 的定义与使用）与同一机制模式（被守护值多来源、无单点/字面量绑定），本次是该常量在实现侧再次出现副本，故判 same-obstacle 并给出该 uid；本次观察对象落点由「测试断言↔实现」变为「两个实现模块↔常量定义」，故在 reason 中如实标明差异。

## 处置
已销账（2026-11-19）：commit `a6519832ed2ee4c166216bf118a05bac4f89a94c` 把两份 200 常量收敛为单点——`host-seams.js` 的 `ASK_QUESTION_MAX_CHARS` 改为从 `ask-text-guard.js` 的 `ASK_TEXT_MAX_CHARS` re-export；测试断言改用字面值 200/201/400，不再引用被守护常量本身。变异验证：在隔离副本中把常量改为 5000 后，4 条边界断言转红（原实现下 10/10 全绿），证明变异已能被检出。解药为该 commit 级代码修复、无对应事实对象，按 26 §9.2 commit 例外以 `informs.target.commit` 承载。销账后本账目现象不再复现。无 `paired-with`，无配对复审义务。
