# execute 漏带字段被静默清除

## 现象

工单 execute 写入的 payload 是克隆语义，调用方漏带的字段被静默清除而非拒绝，且写入成功后不返回任何警告。

ldvh_workcase_write 的 execute 路径把调用方传入的 frontmatter_after 作为目标内容的克隆来源（Code 托管字段除外）。这意味着：调用方若未携带某个应保留字段（如 refs、reviews、relations），该字段不会报错、也不会回落到既有值中的对应项，而是**在写出的文件里消失**——写入调用返回成功，回读显示字段已丢失，调用方直到下一次精确读取才会发现。

本轮 12 小时内的实测证据：

1. **已实际发生的一次字段丢失**：工单 ccc2b91c 的执行节 change_log 逐字记录「heartbeat 未携带 refs，refs 被静默丢弃」——该丢失是在后续精确读取时才发现的，写入调用本身返回成功。
2. **本轮两次因指纹过期导致的整轮重写**：工单 81c37ef0 补执行记账时，首次 execute 因 expected_fingerprint 已被前一次写入推高而失败，改用新指纹重试；同轮另一次 execute 因漏传 frontmatter_after 被拒后补齐重发。两次均是「构造完整 payload」这一要求带来的往返。
3. **写入侧的高昂准备成本**：调用方为满足 execute 的完整克隆要求，必须先精确读取对象、取出磁盘上的完整 frontmatter 逐字段复制（gate_1、attempt、reviews、plan、scope 等），再构造完整 body；本轮多个会话的推理记录显示该步骤占用了大量往返（如 turn 2 step 9-14、turn 3 step 26-29 连续多次重读与重发）。

**与「拒绝而重试」的对比**：指纹过期被拒绝至少是显式的（返回错误，调用方知道要换指纹）。本条的问题是**接受态下的静默丢失**——写入成功、结果错误、且无任何提示。

**放回留观说明（Human 2026-10-11 指示：观察次数小于 3 的摩擦移入留观）**：本条 occurrence.count=1（<3，未达 04 §8.4 阈值 N），由 Human 放回 observing 留观；本流转已写入 occurrence.human_return_at，机械通道不得据 count 回翻（26 §9.2）。

## 入账依据

**重复出现**：本机制对每一次未完整携带字段的 execute 调用成立，不是单次卡顿。本轮 12 小时内已实际发生字段丢失 1 次（ccc2b91c 的 refs）、整轮重写 2 次（81c37ef0），并导致多个会话反复执行「读全文 → 复制全部字段 → 组装完整 body」的高成本准备流程。该结构不依赖具体工单内容，只依赖调用方是否记得完整携带——而工具描述中「Code-managed fields are overwritten by the writer」的措辞只覆盖 Code 托管字段，未说明内容字段漏传时的实际行为，使用方只能在踩坑后从 writer 源码反推。

**可归因**：根因在 21 号规范与 workcase 写工具的 payload 语义之间。execute 采用 payload 克隆（而非按字段合并），是为了保证 plan/scope 的 C2 冻结检查能对「前后完整内容」做比对；但该设计未配套定义「调用方漏带内容字段」的处理方式——既没有 fail-closed，也没有回落既有值，而是直接清除。工具描述亦未声明这一行为。

**修了会改善什么**：若 execute 对「调用方未携带但既有 frontmatter 中存在」的字段回落既有值（而非清除），或至少在返回值中列出「本次未携带因而丢失/沿用了哪些字段」，则「漏带字段 ⇒ 静默数据丢失」这一失败模式被消除；调用方也无需为每次 execute 完整重建整个 frontmatter 与正文，准备成本从「逐字段抄写」降至「只写要改的部分」。本条不主张具体实现方式，只主张「克隆语义下的漏带必须是可感知的，不应是静默的」。

**未指定解药（如实登记）**：解药属工具侧改动（字段回落或写入后回执列出未携带字段），可能与 21 号规范对 execute 的字段契约表述相关。Human 决定项，本条不自行选定，故 status 保持 open、relations 不出现。

**与既有账目的关系**：无同题摩擦。与「direction 冲突拒绝零信息量」（cccb379f）同属「机械通道未把决策所需信息传给调用方」一族，但机理相反（一个是拒绝时信息不足，一个是接受时信息丢失），故分列两账，不合并。
