# 管辖判定块相邻轮次重复注入

## 现象
完全相同的管辖判定块在连续两轮（turn 2 / turn 3）重复出现，助手察觉异常并主动暂停其它事项去排查重复原因

## 入账依据
现象可归因于管辖判定块的注入/投递层重复投递同一内容，消除该重复会一并消解两轮相同的判定块与随之而来的排查停顿，修复后流程更可预期

（既有补充观察共 13 条，逐条记于 change_log，本处不重复展开。）

## 处置
根因（2026-10-19）：判定「本行是否已在会话中出现过」时，`plugin/lib/guidance.js` 的 pre-step 处理器只看 `decision.messages`——即本回合刚装配好的这一批消息，而不是会话历史。上一轮注入过的行永远不会出现在下一轮的批次里，于是「行已丢失」这一误判每轮都成立，loss-recovery 便每轮补注一次。旧的回归用例把上一轮的 `injected` 回灌进 `decision.messages`，恰好掩盖了这个误解。

修法（提交 2c476bd）：新增模块级 `noteOwnMessages` 维护 `state.injectedIds`——插件自己的消息 id 曾经出现在任一装配批次里即记入，与该批次是不是本回合无关；处理器改为依据「是否曾经注入过」而非「本批次里是否有」来判定。会话视图重置（startup/resume/clear/compact）经 `agent/created` 的 `payload.source` 识别并调用 `resetVisibility()`，重置后重新注入。回归用例改为使用真实宿主批次形状（下一轮批次只含它自己的消息）逐轮推进，断言 turn2/turn3 不再新增、通知变更时仍注入、重置后重新注入。

销账依据：原因已在代码层消除并有回归用例锁定；解药是一次受控提交、没有对象身份，按 26 §9.2 的 commit 例外以提交哈希登记（见 relations）。
