# 独立复核身份被盖戳为实施会话

## 现象

实施会话自录复核时 Code 盖戳其身份致关闭门禁判非独立，隔离子代理同步跑完后登记表回收致回传通道取回失败。

工单的独立复核若由实施会话自己调用 record_review 录入，Code 会把该实施会话身份盖戳进 reviews 条目的 session_id，而关闭门禁恰好要求至少一条 review 的 session_id 不等于实施者会话——于是自证独立的路径在机械上不可能成功，且工具侧无任何提示区分这两种情形。

本账目有两个互相独立的触发面，本轮均已实际发生。

**触发面一：实施会话自录被门禁判非独立**（工单 81c37ef0）。精确回读该对象的 reviews 与 attempt：唯一一条 review 的 session_id 与 implementer_session_id 完全相同（都是 session-b29e50eb），关闭门禁（workcase-writer.js 约 2940 行的 `session_id !== implementer_session_id`）判其非独立。该工单因此在 Gate 2 被机械拒绝，且其 change_log 中声称的「独立受管辖根会话 sb-046ae78c」与 Code 实际盖戳的 session-b29e50eb 相矛盾——即对象账面声称的复核来源与机械盖戳的复核来源不是同一个。

**触发面二：隔离子代理同步跑完后被清理，agent_id 取不到**（工单 1a34f9e4 的丙档追认复核）。规范为隔离子代理提供了 `reviewer_child_agent_id` 回传通道，使身份取自宿主登记表而非调用方自填。但当子代理以 `run_in_background: false` 同步跑完并返回后，调用方再查 `list_agents`（scope=descendants / children）时登记表已被清空，返回空列表——回传通道所需的 agent_id 已在回收中丢失。调用方只剩两条路：用自己（实施会话）的身份录一条会被门禁拒绝的 review，或伪造子代理身份（规范禁止且工具会校验）。实测发生于 turn 3 step 6–7，子代理跑完后登记表为空。

**并发只读的连带效应**（属另一笔账，此处仅记关联）：复核子代理在并发工作区中被强制全程只读，为验证判别力需在 /tmp 自建副本做变异实验，这使触发面二的失败代价进一步升高（已跑完的变异实验因无法回传身份而全部作废）。

**放回留观说明（Human 2026-10-11 指示：观察次数小于 3 的摩擦移入留观）**：本条 occurrence.count=1（<3，未达 04 §8.4 阈值 N），由 Human 放回 observing 留观；本流转已写入 occurrence.human_return_at，机械通道不得据 count 回翻（26 §9.2）。注：本条处置方向已由 Human 决定（见下），放回留观不影响该处置方向的后续执行。

## 入账依据

**重复出现**：本机制对每一次「由实施会话自己发起的独立复核」成立，不是单次卡顿。本轮 12 小时内已实际命中 2 次（81c37ef0 的自录被判非独立、1a34f9e4 的子代理身份取回失败），分属两个独立触发面——一次在写入端（盖戳即错），一次在回传端（身份已丢）。两者的共同根因相同：规范要求「复核者身份必须独立于实施者」，而唯一能机械保证该独立性的通道是 Code 盖戳；而盖戳的两个来源（调用方身份、隔离子代理登记表）恰好在最需要它们的时刻分别失效。

**可归因**：根因在 21 号规范与 workcase 写工具的实现配合上，具体是两处：(1) `record_review` 的 at／provider／model／session_id 由 Code 从**调用方**的会话记录托管，工具描述未声明「调用方即实施者时本通道必然产生非独立条目」这一后果，使用者只能靠试错发现；(2) 子代理登记表在同步完成后即回收，`reviewer_child_agent_id` 通道没有要求子代理必须后台运行、也没有在登记表回收时保留 agent_id 供事后回传。

**修了会改善什么**：若 record_review 在调用方 session_id 等于 implementer_session_id 时 fail-closed 并明确提示「须经 reviewer_child_agent_id 回传」，或若隔离通道要求子代理后台运行并在回收后保留可回传的 agent_id，则实施者不会做出一份注定被门禁拒绝、且账面声称与机械盖戳矛盾的 review，关闭环节的返工（重跑复核、补录 review）也随之避免。

**处置方向（Human 决定 2026-10-09；变更已落工作树，待审核与受控提交）**：两个触发面各采一条解法——工具侧与流程侧同时收紧。(1) 工具侧：`plugin/lib/workcase-tools.js` 的 `record_review` 现要求 `reviewer_child_agent_id`，省略即 fail-closed 并给出可操作停止提示（不再以调用方自身身份盖戳、杜绝主控自查冒充独立复核）。(2) 流程侧：`04 §7.3` 把独立复核的承载形式定为「受管辖隔离子代理（独立上下文）」唯一形式（取消另一受管辖根会话入口），`21 §14`／关闭前置条件二／`§15.1` 与 `34 §12` 同步；并明示**派生须后台**（同步派生返回即回收登记表，friction 82260dec 本条触发面二的确定解法），无法创建子代理或 id 不可回传时按 00 §5.7 停止并报告、保持 open。

**本账状态说明（如实登记）**：上述变更已落工作树但**尚未取得规则效力**——受保护规范源的修改须经 01 §12 独立审核、Human 决定与 09 受控提交（00 §4.3、01 §9.2）。故本条**不因变更已落盘而销账**：两个触发面的解药均未取得效力，且实施侧改动的机械覆盖仍有已知缺口（关闭门禁本身未改，故从对象上无法区分某条 review 来自子代理还是另一根会话，规则在关闭侧依赖录入侧把关）。待审核结论与受控提交完成后，按实际结果决定本条销账或保留。

**未指定解药（如实登记）**：解药方向已由 Human 于 2026-10-09 选定（见上「处置方向」条），故本条此前的「未指定解药」状态已被取代；但销账仍待审核与提交完成，以及关闭侧覆盖缺口的处置。
