# UI 表格 rows 结构错误致围栏反复渲染失败

## 现象
dsh-ui 围栏中 table 的 rows 被写成扁平字符串数组，宿主渲染器判 invalid_spec 并反复要求重发

## 入账依据
可归因于固定环节（dsh-ui 围栏里 table 的 rows 写成扁平字符串数组），本次窗口内至少 4 次被宿主判 invalid_spec/invalid_json 并要求重发；修掉（发起前机械校验 rows 为数组的每一行）能避免多轮返工与内容重发。

补充观察（2026-10-16T18:20:52.219Z）：材料 turn 22 开头的围栏修复回执显示 status=render_failed、error=invalid_spec，诊断为 items[0].rows[0] 至 rows[7] 全部「must be an array or object」，即表格 rows 元素被写成字符串而非数组/对象。这与既有账目 uid=ea104c6c「UI 表格 rows 结构错误致围栏反复渲染失败」描述的是同一机制（同一个 dsh-ui table 组件的 rows 结构校验失败），故判为 same-obstacle 而非新阻碍。另注材料因长度上限被截断（turn 22、turn 23 均在句中中断），判断仅就所见部分作出。

补充观察（2026-10-19T14:02:26.935Z）：材料 turn 8 记述助手写好的 dsh-ui 讨论稿在提交前因「第一张 table 的 rows 数组少一个闭合括号」被 JSON 校验拦下、该稿尚未发出，与既有账目 friction-ea104c6c「UI 表格 rows 结构错误致围栏反复渲染失败」是同一阻碍（同一失败机制、同一载体类型），故判 same-obstacle 而非新建。另说明：本次材料因长度上限被截断（turn 12 正文末尾中断），判断仅就所见部分作出。

补充观察（2026-10-20T06:23:29.969Z）：材料 turn 2 的 dsh-ui 围栏中，「内置提醒 vs 真正的自动化任务」表格的 columns 声明为 3 列，而各 rows 实际给出 4 个元素（多出一段空串），与「UI 表格 rows 结构错误致围栏反复渲染失败」这一既有账目的现象形态完全一致（同一机制、同一载体形态），故判为同一阻碍的又一次出现，而非新账目。材料在 turn 4 处被长度上限截断，故只就所见部分判断；turn 1 与 turn 2 其余表格的 rows 元素数与 columns 一致，未见其它形态的 rows 结构错误。

补充观察（2026-10-25T04:34:03.195Z）：引证出自 turn 9 助手正文：主控在交付收尾材料时自陈其 dsh-ui 围栏规格写错——`text` 节点须带 `content`、表格须用 `columns`+`rows`——并随即「重做」。这一现象的构成是「UI 规范节点字段名/结构写错 → 围栏渲染失败 → 须重做」，与既有账目 friction-ea104c6c「UI 表格 rows 结构错误致围栏反复渲染失败」指向同一阻碍（本次实例同时含表格结构项与 text 节点字段项，属同一条目的同一类缺陷），故判 same-obstacle 并指向其 uid，不另立新条目（避免同机制重复入账）。需要如实说明两点限制：其一，本次材料因长度上限在 turn 12 处被截断（末句「基线段无条件，而」中断），故只能就所见部分判断，未覆盖窗口以内容；其二，窗口内另有两处候选阻碍现象——注释内硬编码实测值被并发写入的宿主任务冲掉、致「数字漂移守卫」连续三次报警，以及新增基线段与 800 字节预算约束冲突致三条既有用例失败——本次未作入账判定，因其与既有账目的对应关系需另行比对，且不宜与本次结论混同。

## 处置
**为何废弃（属 Human 判定：非本仓可修的债，2026-10-28 由 Human 决定转投）**：本账现象
真实——dsh-ui 围栏的 table 节点因 `rows` 元素被写成字符串、行内元素数与 `columns` 不一致、
JSON 括号不闭合等形态被宿主判 `invalid_spec` 并要求重发，本账五次观察形态一致。但**解药
