# 工作对象与管辖范围规范


## 1. 价值判断

管辖登记制度解决“哪些项目受 LDVH 管辖”依赖 AI 记忆和环境猜测的问题，通过可回读登记与一致判定为受控操作提供共同边界，减少误入非管辖项目、重复确认和跨会话恢复负担。

工作对象与登记定位主要支撑 V1 快速定位；管辖判定和 fail-closed 边界主要支撑 V3 边界识别；可回读登记状态主要支撑 V6 工作接续；消费方机械门禁主要支撑 HV2 授权执行受控可续。

本规范只定义登记制度、管辖判定和工作对象边界；事实源、LDVH CLI、Git Gate、环境接入、实现和 Web 呈现由 05、06、08–10 与实际消费方承接。

登记载体存在、判定成功、路径解析、文件写入或消费方放行，只能证明当次机械范围，不能单独证明项目应受管辖、行动适用、授权成立、工作完成或价值兑现。

## 2. 规范依据

本文直接依据：

1. `ldvh-root`：00 §3.3 的规范源与事实源边界、§3.4 的 fail-closed 与机械保障、§4 的 Human 决定权、§7 的防自欺、Stop Conditions 与交还；
2. `specification-model-foundation`：01 §7 的共同章节结构、§9 的当前规则源条件、§10 的 L0–L4 读取层级、§12 的独立对抗审核；
3. `work-model-foundation`：02 §13 规则遵守（业务系统）、§8 编排（能力承载）与 §15 复核与校验（制度）对管辖判定作为执行前边界落实与复核的机制指向。

本文不依赖额外外部语法或行业标准定义管辖语义。

05、06、08–10 是协作来源和判定结果消费方，不是本文的规范依据；历史规范、开发备忘和实现只作为设计输入，不取得规范效力。本文不重新解释 00–02；发生冲突或权威关系无法确认时，按 00 §7.2 暂停受影响范围并完成对齐。

## 3. 职责边界

### 3.1 本文负责

1. 管辖登记制度：登记方向、登记载体语义、判定方式、登记入口与取消登记（§5）；
2. 工作对象边界：Git 根目录、事实源路径与规范路径的定位语义（§6）；
3. 管辖判定语义：只读登记载体的判定规则与前置条件（§5）；
4. 消费方消费管辖判定结果的语义接口（§7）。

### 3.2 本文不负责

1. 登记载体的宿主 user-data API、跨工作区权限、文件系统实现与 Web 交互细节——分别由 08–10 承接；
2. LDVH CLI 传输 envelope——归 05；受管载体与受控提交——归 06；
3. Git Hook 部署、插件装载与环境接入——归 08；Code 实现与测试——归 09；Web 交互细节——归 10；
4. AI 对当前行动是否适用管辖判定的语义判断，与 Human 的授权、验收决定。

### 3.3 相邻规范分工与唯一权威

01 是规范路径与当前规则源的唯一权威，06 是事实源与受管载体的唯一权威，05 是传输 envelope 的唯一权威，08 是环境权限与接入的唯一权威，09 是实现与测试的唯一权威，10 是 Web 交互的唯一权威；07 只定义登记制度、判定语义与工作对象边界，不另建第二登记权威。

## 4. 适用范围

### 4.1 适用对象

本规范适用于：

1. LDVH 管辖项目及其工作对象；
2. 管辖登记、取消登记和判定结果；
3. LDVH CLI、Git Gate、Skill 与 Web 对判定结果的消费边界。

### 4.2 适用场景

本规范用于项目登记、取消登记、管辖判定、Git 根与事实/规范路径定位，以及受控操作前的管辖门禁。

### 4.3 明确排除与证明边界

普通项目操作和非 LDVH 受控流程不因本规范存在而强制经过管辖判定；本规范不适用于登记文件的具体 Schema、LDVH CLI 传输、Git Hook 部署、Code 实现或 Web 交互细节。

项目已登记、判定成功或路径可解析，只证明当次判定的机械范围，不单独证明行动适用、授权成立、受控操作正确或价值兑现。

## 5. 管辖登记制度

### 5.1 用户目录登记方向

以下登记位置、Schema、路径语义、三态判定、写入与迁移规则已经 Human 对准确候选及作用范围明确确认，是 07 的管辖登记权威契约。

v5 管辖登记载体固定为 DSH 正式用户配置根下的 `ldvh/governed-projects.yaml`。该载体与普通插件设置同属 DSH 用户配置体系，但因管辖登记具有独立 Schema、原子写入、并发守卫与写后回读契约而使用独立文件，不并入通用 `settings.yaml`。用户不能修改登记文件位置；设置界面只说明配置由 LDVH 自动保存在 DSH 用户配置目录下的 `ldvh/governed-projects.yaml`，不展示实际绝对路径，也不提供路径输入、选择、复制或打开目录入口。用户配置根必须通过 DSH/Electron 正式 user-data/config API 解析，不硬编码 `~/.dsh`、`%APPDATA%` 或任何单一系统路径；macOS、Windows 与 Linux 均消费宿主返回的实际根目录。v5 不再使用项目内配置、项目外任意配置、向上遍历或多配置合并。

### 5.2 登记载体与 Schema

登记文件采用以下闭集结构，参考 v4 已验证字段并增加 `schema_version`：

```yaml
schema_version: 1
governance_instance_name: "DSH Project LDVH Governance"
product_description: |
  当前管理实例说明。
projects:
  - id: "dsh-ldvh"
    path: "C:/absolute/git/root"
    name: "DSH LDVH (v5)"
    description: |
      项目说明。
default_project_id: "dsh-ldvh"
```

`schema_version` 固定为整数 `1`；实例名称和用途说明必填非空；`projects` 必填、可为空；每项 `id` 与 `path` 必填且分别唯一，`name`、`description` 选填但出现时非空；`default_project_id` 始终存在，`projects: []` 时必须为空字符串，项目非空时必须为非空并精确匹配一个 `projects[].id`。不得加入 `status`、`enabled`、Git/branch/remote、初始化、审计、缓存或过程状态字段。

### 5.3 判定方式

判定先核对 DSH 用户配置根、登记载体、Schema 版本、访问权限和消费接入。任一前置条件不可取得、不可解析或未核验时，直接返回 `unavailable` 并报告精确缺口，不读取候选或旧载体，不进入列表判断。

前置条件全部成立后：

1. 每次判定只读已定案登记文件，不使用缓存补回；
2. 当前路径须解析为存在的真实 Git 根；路径不存在、不可访问或无法确定 Git 根时返回 `unavailable`；
3. 路径规范化后判断是否命中 `projects[].path`，命中返回 `governed`，未命中返回 `not_governed`；
4. 不做向上遍历，也不回退读取 v4 `LDVH-GOVERNED-PROJECTS.yaml`。

`path` 持久化为 realpath 后的绝对 Git 根，统一使用 `/` 分隔符，不保存 `~`、环境变量、相对路径或尾部分隔符。Windows 盘符与 UNC 路径允许使用 `C:/...`、`//server/share/...`，比较须遵循实际文件系统语义并解析 junction/symlink，不得用简单 lowercase 冒充规范化；linked worktree 通过 Git common-dir 确定性识别同一项目，不在配置中保存 branch、remote 或 worktree 列表。

### 5.4 登记入口

08 完成跨工作区权限核验与登记、且登记载体经 Human Gate 定案后，以下入口方可启用：

1. **AI 入口**：用户在项目目录内对 AI 表达把当前项目设为 LDVH 管辖的意图时，LDVH CLI 先只读登记文件确认当前项目不在列表中，再写入登记文件；写入应使用原子操作防并发竞态；**原子写入、冲突拒绝与回读要求由本文 §5.6 定义**，宿主是否满足该要求由 08 §6 核验、实现由 09 承接；
2. **Web 入口**：通过 Web 界面管理登记列表，交互细节归 10。

上述前提未满足时，两种入口均返回 `unavailable`，并按实际原因报告 `user_config_root_unavailable`、`registration_carrier_unavailable`、`registration_permission_unverified`、`registration_access_denied` 或 `registration_schema_invalid`，不得展示为可执行。

**入口的穷尽性与其 intent 载体**：登记载体的**写入路径只有本节所列入口**，不存在未归类的第三条。任何实现中可写登记载体的函数——包括 CLI 子命令、HTTP 路由、工具处理器与内部写入原语——都必须归入下列之一，不得自外于本文的意图要求：

| 路径类别 | 归入 | intent 载体 |
|---|---|---|
| AI 入口 | 本节第 1 项 | 一次**显式 Human 提请**（§5.6 机械形态）；提请未获肯定答复不得写入 |
| Web 入口 | 本节第 2 项 | Human 在界面上作出的**该次操作本身**；请求须显式携带该意图，不得因「路由被命中」而推定 |
| 安装事务内的登记步骤（`08 §5.2`） | **不属本节入口**，由 `08 §5.2` 定义 | Human 在设置页**点击「安装」**；该事务内的登记写入不再重复提请，因为它承载的是已经发生的意图 |
| 运维入口（CLI 子命令） | **不属本节入口**，属运维动作 | Human 运行该命令时**显式携带**的意图载体（如标志）；该载体强度为「弱」（§5.6 强度分级），只能阻断误触发与裸调用 |

**为何 CLI 单列而非并入 AI 入口**：本节第 1 项的入口是「用户在项目目录内对 AI 表达意图」后由 AI 代为写入；CLI 子命令则由**人类操作者直接执行**，没有 AI 作为中介，其意图载体、强度与可核对方式均不同。两者是不同的写入路径，不是同一入口的两种形态。单列的目的是使「写入路径只有本节所列入口」这一断言与其下的表**逐行对应**——表未枚举的路径即不存在。

**内部写入原语不是入口**：供安装事务复用的无门禁写入原语**不得**被任何 AI 发起的路径直接调用；代为 AI 执行的登记一律经本节第 1 项的入口。实现须使这一边界在代码中可辨认（原语的注释与命名须声明其非入口性质）。

**公开操作声明**（按 `05 §6.1` 的声明形状）：

| operation_key | summary | effect | arguments_contract | result_contract |
|---|---|---|---|---|
| `register-governed-project` | 把一个 Git 项目登记为 LDVH 管辖项目（AI 入口） | `may_change_state` | `07-工作对象与管辖范围规范::5. 管辖登记制度/5.4 登记入口` | `07-工作对象与管辖范围规范::8. 验证与证据边界` |
| `unregister-governed-project` | 取消一个已登记项目的管辖登记（AI 入口） | `may_change_state` | `07-工作对象与管辖范围规范::5. 管辖登记制度/5.7 取消登记` | `07-工作对象与管辖范围规范::8. 验证与证据边界` |

声明的输入章节与结果章节为本规范自身的 §5.4、§5.7 与 §8；本节不复制其字段与语义。两个操作在被调用前仍须逐项满足 §5.4 的前置条件，声明本身不证明任何项目已登记、权限已核验或载体已定案（`05 §6.1`：`operation_key` 不能从名称推导适用、授权、实现、验证或完成）。

### 5.5 前置条件

1. 登记对象必须是 Git 项目（存在 `.git` 目录）；
2. 非 Git 项目不允许登记。

### 5.6 创建、写入与迁移

登记或取消仅由 Human 明确意图触发。写入前读取并验证当前 Schema，使用版本守卫或锁；在目标同目录创建临时文件、flush 后执行原子 replace，再重新读取和解析。不得退化为先删除目标再写新文件；并发冲突返回 `rejected`/`conflict`，Windows 目标文件占用导致 replace 失败时明确返回失败。Unix 目录与文件权限目标分别为 `0700`、`0600`；Windows 继承 DSH 用户配置目录 ACL，不伪造 POSIX mode、不扩大到其它用户，ACL 无法核验时高风险写入 fail-closed。

**「仅由 Human 明确意图触发」的机械形态**：该要求不是可由调用方自述满足的语义条件，实现须使其**可机械核对**：

1. 登记与取消前置一次**显式 Human 提请**，经 `08 §6` 所列的 `ctx.userQuestions.ask` 承载（该缝的消费方式见 `08 §6`），并记录本次提请的结果；
2. 提请**未获肯定答复**时——包括答复为否定、答非所问、答问入口不可用或提请失败——**一律不得写入**，须返回 `rejected` 并说明原因。**沉默、缺省或调用方声称已获意图，都不构成 Human 意图**（fail-closed）；
3. 提请内容须包含被登记或取消的**项目标识与路径**，使答复对象明确可回查。

**intent 载体的强度分级（据实，不夸大）**：上述第 1 项要求的是**载体存在且结果被记录**，但各载体的**强度不同**，实现与声明都不得把弱载体说成强载体：

| 载体 | 强度 | 说明 |
|---|---|---|
| `ctx.userQuestions.ask` 的实际提请 | **强**：由宿主答问入口取得 Human 答复 | AI 入口须用此载体；未获肯定答复不得写入 |
| Human 在界面上作出的界面动作（Web 入口） | **中**：交互本身即意图，请求须显式携带该意图 | 不得因「路由被命中」或「字段有值」而推定有界面动作；无界面动作时该请求与凭据同源，**不构成 Human 意图** |
| 命令行显式标志（CLI） | **弱**：由执行者自述，与调用者同源 | 只能阻断**误触发与裸调用**，**不能**证明 Human 确实意图；故 CLI 登记属**运维动作**，其效力以 Human 实际操作为准，不得据标志存在主张已获 Human 意图 |

**该分级的强制要求**：任何据此主张「已满足 Human 意图」的声明，**必须同时披露所用载体的强度**；以弱载体主张强结论，或在无界面动作时以请求字段主张 Human 意图，均为本节所禁止。载体的强度不因实现方便而提升。

v4 配置只作为一次性迁移输入，保留实例名称、用途说明、项目 id/path/name/description 与默认项目。迁移前规范化路径并向 Human 展示完整 v5 候选；Human 确认后写入新载体，不自动删除旧文件、不双写。v5 载体成立后，v4 文件不再作为 v5 管辖权威。实际路径由 Web 和 AI 响应如实呈现。

### 5.7 取消登记

08 完成跨工作区权限核验与登记、且登记载体经 Human Gate 定案后，取消登记入口方可启用：

1. **AI 入口**：用户明确要求取消时，LDVH CLI 从登记文件中移除对应项目并回读确认；
2. **Web 入口**：通过 Web 界面操作移除。

前提未满足时返回 `unavailable`，不得尝试移除候选或默认载体中的项目。

## 6. 工作对象

工作对象成立的前提是项目已登记且为 Git 项目（§5.5）。

1. **定义**：工作对象 = 当前项目 Git 根目录 + 事实源路径（`ldvh-base/`）+ 规范路径（`specs/`）；
2. **登记载体边界**：用户目录登记载体位于项目 Git Working Tree 之外，不属于项目事实源、受管事实载体或 Git Gate 候选；它是项目外受控配置载体，语义由 07 定义，**写入权限与原子机制由本文 §5.6 定义**，其宿主满足性由 08 §6 的沙箱分层与文件观察策略核验——用户目录属跨工作区路径，其写入授权路径由 08 核验登记，核验与登记完成前 AI 登记入口不得声明可用；
3. **边界**：工作对象不跨越多个项目（单项目单 worktree）；多项目聚合归未来规范（v4 多项目聚合做法废弃）。

## 7. 管辖判定消费方

| 消费方 | 消费方式（语义接口，不描述具体 UI/传输细节） |
|---|---|
| LDVH CLI | 前置条件成立后，在执行 LDVH 操作前调用管辖判定；未管辖时拒绝操作 |
| Git Gate | 前置条件成立后，在 Git Hook 事件中检查管辖状态；未管辖时阻断提交 |
| Skill | 前置条件成立后，执行前检查当前项目是否在管辖列表；未管辖时不执行 |
| Web | 前置条件成立后，参照管辖判定结果决定功能呈现与隐藏 |

四类消费方使用同一前置状态契约：登记载体已经 Human Gate 定案，且 08 对相应权限与消费接入的核验已完成，状态才是 `available`；任一前置条件未满足时统一对外返回或呈现 `unavailable`，受控操作、Hook 提交和 Skill 执行均 fail-closed、不得继续，Web 不得把不可用伪装成“未管辖”。此时只允许来源定位、只读诊断和分流准备。

消费方按判定结果执行的承接义务仅在 `status=available` 且全部前置条件已核验时生效；`unavailable` 时不得执行、放行、隐藏为未管辖或宣称已检查。本表只定义语义接口，不证明任一消费方已经实现。

**消费方承接义务的条件式限定**：**在某一消费方的管辖检查实际具备之前**，不得据本文主张该消费方已履行承接义务，也不得把「提交通过」「调用成功」引为管辖检查已执行的证据；登记载体不可读或损坏时，受影响消费方须按本文 fail-closed 处理，不得放行。各消费方的实现可用性属实现现状，按 01 §7.2 由读取时的观察取得，本条不陈述其当前状态。

机械拒绝语义：非 Git 项目拒绝登记；项目未登记时拒绝受管操作；已登记时不重复写入。权限层的机械拒绝与停止层的暂停互不替代（00 §7.2）。

## 8. 验证与证据边界

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 登记载体与接入前置状态 | 管辖判定、登记或消费前 | 登记载体已经 Human Gate 定案，且 08 权限与消费接入核验已完成，定案载体存在并可唯一解析 | Human 定案记录、08 核验记录与文件系统 | 前置状态与载体定位检查 | `available` 状态及载体可解析；不证明项目清单语义正确或授权成立 | 统一返回或呈现 `unavailable` 并 fail-closed，报告精确缺口，只允许只读诊断与分流准备 |
| 登记内容有效性 | 登记或取消登记时 | 项目路径格式有效，登记项目实际存在且含 `.git` | 登记文件与项目目录观察 | 登记校验 | 当次登记条目的机械有效范围；不证明项目应否受管辖 | 格式无效时拒绝登记；发现孤立记录（幽灵登记）时标记并提示 Human |
| 判定结果一致性 | 每次管辖判定后 | 多次判定结果一致且可回指同一登记状态 | 判定响应与登记文件 | 判定结果核对 | 当次判定范围；不证明行动适用或授权 | 结果不一致时暂停受影响操作并重新判定 |
| 登记写入 | 登记或取消登记后 | 原子写入完成且回读一致 | 写入结果与回读 | 写后回读核对 | 当次实际登记变化；不证明管辖正当性或 Human 决定 | 回读不一致时暂停并修复，不宣称登记完成 |
| 登记入口前置条件 | 调用 AI 或 Web 登记入口前 | §5.4 各项前置条件逐项成立；任一不成立时入口返回 `unavailable` 并报告对应错误码 | 用户配置根、载体文件系统状态与 Human 定案记录 | 前置条件逐项判定（`user_config_root_unavailable`/`registration_carrier_unavailable`/`registration_permission_unverified`/`registration_access_denied`/`registration_schema_invalid`） | 当次入口是否可执行；不证明登记正当、授权成立或项目应受管辖 | 返回对应错误码且不得展示为可执行；不写入、不回退到候选载体 |
| linked worktree 身份一致 | 管辖判定时 | 当前路径的 Git 仓库与已登记项目由 Git common-dir 判定为同一仓库 | Git common-dir 实际取值 | 机械：逐路径求 common-dir 后比对 | 当次「同一仓库」的机械结论；不证明该 worktree 内的具体动作已获授权 | 无法取得 common-dir 时不据此判为 governed；维持 §5.3 的包含判定结果 |
| 消费方行为 | 消费方执行受控操作时 | 消费方按判定结果执行拒绝或放行 | 各消费方的执行记录 | 消费方规范域验证 | 当次消费执行；不证明判定语义或整体完成 | 未按判定执行时由消费方规范域暂停受影响操作 |

机械结果与语义判断互不替代。登记存在、判定成功或消费方放行只能证明各自机械范围；本章不能单独证明登记正当、行动适用、授权覆盖或 V/HV 价值成立，未执行和不可用范围保留为 gaps。

## 9. Human Gate

本文不新增 00 之外的 Human Gate。

### 9.1 领域增量事项

以下事项是 00 §4.2 在管辖范围领域的具体化：

1. 改变已经 Human 定案的登记载体逻辑位置、文件名、Schema、权限目标或迁移规则；
2. 改变登记方向、判定方式或工作对象边界（含恢复向上遍历或跨项目聚合）；
3. 是否移除幽灵登记。

受保护文档修改按 00 §4.3 执行，此处仅回指，不构成本文领域增量。

### 9.2 决定边界

Human 决定只证明决定及其作用范围，不替代登记校验、判定结果核对或写后回读。

## 10. Stop Conditions

本规范不新增根停止类型。

### 10.1 领域触发与影响范围

出现以下任一情况时，按 00 §7.2 暂停受影响的最小登记、判定或受控操作范围，并统一对外返回或呈现 `unavailable`、执行 fail-closed：

1. DSH 用户配置根无法取得，或 08 权限/消费接入尚未核验；
2. 登记载体损坏、不可唯一解析或无法受控读取；
3. 登记载体无法受控创建或权限不足；
4. 判定范围不清或多次判定结果不一致；
5. 准备在未登记或非 Git 项目上执行受管操作。

### 10.2 暂停期间允许动作

暂停期间只允许不越过停止边界的规则定位、只读核对、载体检查、修复与分流准备，不得继续受影响登记、判定或受管操作。

### 10.3 恢复与再次触发

恢复须与触发原因对应，且只覆盖当前依据支持的范围；同一停止条件恢复后再次触发时按 00 §7.3 进入 Human Gate。

## 11. 反过度设计红线

1. 不以任何形式向上遍历查找登记文件（废弃 v4 做法）；
2. 不把工作对象扩展到跨多个项目或多 worktree 聚合；
3. 不在实现中硬编码 macOS、Windows 或 Linux 的系统用户目录，也不绕过 DSH 正式 user-data/config API；
4. 不在登记或判定前省略 Git 根与路径规范化检查；
5. 不为管辖判定建立第二登记表、缓存权威或独立状态账本。
