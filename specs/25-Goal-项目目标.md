# Goal-项目目标

> 本规范按 01 §7 固定章节契约与 02 §12 事实类型规范共同结构组织：§1–§4 为固定前置四章；§15–§18 为固定收尾四章。02 §12.1 十项结构角色的落点：第 1 项→§1.1（并入固定章「价值判断」），第 2 项→§6，第 3 项→§7，第 4 项→§8，第 5 项→§9，第 6 项→§10，第 7 项→§11，第 8 项→§12，第 9 项→§13，第 10 项→§14；每项出现且仅以一项对应。十项必填结构的最小表达不得删除、合并或跳过。

## 1. 价值判断

Goal 解决项目目标缺少稳定承载的问题：项目「为什么存在、要实现什么、走到哪里算成」若只存在于 README、对话记忆或散落文档，则每次授权、每轮规划、每个会话都无法对照同一个锚——方向漂移无从暴露（00 §1 痛点 1「规划模糊、来去不可答」），演进脉络缺第一环（「长期意图」无载体）。Goal 以单例冻结锚承载项目目标：目标陈述表达为什么与要什么，为全部前向工作提供统一引用顶点；「走到哪里算成」由下级 SubGoal 对象承载（28 号），本类型不重复承载。普通文件或既有类型不能无损承载：README 是公共门面不是事实对象（无受控写入、无 change_log、无 Gate 1 引用契约）；Spark 是悬置层（目标已定，不是悬而未决）。本规范主要服务核心价值一（项目可厘清，00 §1.1）：Goal 为「项目为什么存在、要实现什么、走到哪里算成」提供唯一稳定锚点，使每次授权、每轮规划、每个会话都能对照同一个目标，方向漂移可被暴露而非事后追认；兼服务核心价值二（任务高效准确完成，00 §1.2）：Gate 1 授权提请必含目标锚定，说不清服务哪条子目标即暴露偏离，收官判定按证据分层核对。本文不以全量价值声明替代主要影响判断。

Goal 是单例类型：一个管辖项目在任一时点至多一个当前 Goal 对象。单例不使用多例身份机械（见 §7），这是本类型与 20–24、27 等其余事实类型最重要的形态差异。

Goal 对象存在、状态为 active 或 change_log 条目存在，均不能单独证明目标本身正确、适用或已兑现——目标的价值须在后续授权、规划与交付中按实际使用效果核对。

## 3. 职责边界

### 3.1 本文负责

1. Goal 类型的对象边界、单例约束与查重（存在性检查）；
2. Goal 的身份与载体（路径即身份、单例三免）；
3. Goal 的字段契约（frontmatter 闭集、正文两块固定 H2——目标陈述/子目标）；
4. 项目收官判定（全部子目标达成且 Human 决定）与 goal 修订的级联边界——子目标的锚点冻结与状态由 28 号承接；
5. Goal 的状态闭集（active/achieved）与翻转条件；
6. Goal 的消费点（Gate 1 / Web 呈现 / 方案收敛 / systemPrompt 注入）；
7. Goal 的受控操作（创建、更新、级联、翻转）与升级路径。

### 3.2 本文不负责

1. 行动授权模板（00 §3.4 承载）；
2. Web 投影格式（07 号承载，细则归 `plugin/web/docs/`）；
3. 项目初始化对话的执行流程（业务系统段承载，本文只定义产出契约）；
4. 多项目共享目标或跨项目聚合（08 §6 管辖范围边界）。

### 3.3 相邻规范分工与唯一权威

02 是公共字段语义的唯一权威；09 是受控提交契约与 Git Gate 的唯一权威；06 是 Code 实现的唯一权威；00 §3 是 Human 授权语义的唯一权威。本文只定义 Goal 类型自身的边界、字段、状态与消费点，不复制上述相邻规范的规则。

## 4. 适用范围

### 4.1 适用对象与场景

1. 管辖项目中的单例 Goal 对象（`ldvh-base/goal.md`）；
2. 项目收官判定与 goal 修订级联。

本规范用于 Goal 的创建（项目初始化对话）、更新（陈述精化）、级联（goal 修订引发的下游标记）、状态翻转（achieved 判定）与消费（Gate 1 / Web 呈现 / 讨论 / systemPrompt）。子目标的增改不在本规范适用面内（归 28 号）。

### 4.2 明确排除与证明边界

明确排除：项目价值约束（Charter 语义，归规范源项目级 spec）；使命宣言式永不可判定文本（子目标判据必须可判定，28 §8）；多项目共享目标。子目标的具体内容取决于「这个 goal 属于哪个项目」，归 28 号对象承载。Goal 对象存在或状态为 active，不能单独证明目标正确、子目标充分适用或授权工作已经开始。

## 5. 类型定位与价值（02 §12.1 第 1 项）

**类型解决什么持续问题**：项目长期意图缺少可回指、可核对的稳定承载，使「为什么做、做到哪里算成」随会话结束而散失（00 §1 痛点 1）。

**服务哪些消费方与核心价值**：消费方为 Human 授权链（00 §3）、Web 呈现（07 号）、方案收敛工作（主控本职，04 §6.1）与 systemPrompt 注入；主要兑现在「边界识别」与「据实判断」两面，并向 Human 提供决策提请与演进脉络追溯（见本章第一段）。

**为什么普通文件或既有类型不能无损承载**：普通 Markdown 无受控写入与 `change_log`，无 Human 决定的授权绑定，因而无法承担「一切下游锚定」的可回指义务；20 Spark 是悬置层（方向未定），22 ADR 是点状决定，均不承载项目级单一目标锚。Goal 以「路径即身份的单例冻结锚」承载该职责。

## 6. 对象边界（02 §12.1 第 2 项）

### 5.1 什么构成一个对象

一个 Goal 对象 = 一个管辖项目在当次时点的**项目目标冻结锚**：目标陈述（为什么存在、要实现什么）。对象粒度是**项目级单例**——不是每个方向、每轮规划或每条任务各一个 Goal。

**子目标不在本对象内**：子目标以 SubGoal 事实对象独立承载（28 号），Goal 与 SubGoal 之间是两层结构关系（Goal 在上、SubGoal 在下，即 `parent_goal` 指上来）。本类型不承载子目标的判据、状态与变更——Goal 侧只承载目标陈述这一条长期意图，以及「本项目已展开若干子目标」这一事实的**派生视图**（由 `parent_goal` 反查得到，不存储副本）。

### 5.2 查重

单例即查重：对象边界由「路径即身份」承载，`ldvh-base/goal.md` 至多一份。受控创建入口在 goal.md 已存在时必须拒绝，不得创建第二个 Goal（运行时兜底见 §17 必停情形第 1 项）。本类型不建立相似度自动裁决（02 §9.2），也不靠语义比对判断「是否同一目标」——单例约束由载体唯一性机械承担。

### 5.3 明确不属于本类型（入口拦截）

以下内容不形成 Goal：单个方向或有待调研的问题（归 20 Spark）；已定决策的表达（归 22 ADR）；外部对象深度调研（归 24 Research）；某轮执行计划与验收（由主控在当次行动中承接，不对象化）；项目价值约束（Charter 语义，归规范源项目级 spec）；使命宣言式永不可判定文本（子目标判据必须可判定，28 §8）；多项目共享目标。

## 7. 身份与载体

| 项 | 定案 |
|---|---|
| `fact_type_key` | 不采用（单例路径即身份——类型标记由 `goal_key` 固定值 `project-goal` 承担，机械校验见 §13 创建检查；同 `object_uid` 的单例豁免通道，02 §7.1「字段缺省遵循类型来源」） |
| 载体 | 平铺单文件：YAML frontmatter（机器权威）+ markdown 正文（家族统一约定，24 号同形态） |
| 权威位置 | `ldvh-base/goal.md`——路径即身份：不分配 `object_uid`、无类型子目录、无文件名编码 |
| 单例三免 | 免 `object_uid`（类型来源声明不采用，见下）、免 F0–F2 候选召回（消费点直读）、免目录基数校验（文件系统天然单例） |

正文结构的公共契约（H1 恰好一个且由 Code 从标题生成、正文自 H2 起）按 02 §7.3 承接；本节只定义本类型的 H2 骨架，不重述该层。

`object_uid` 不采用的类型来源声明：02 §7.1 将其定义为「事实对象唯一身份」，服务多例对象的引用消歧；Goal 无消歧需求（引用目标恒为该路径，路径即身份——同 specs/00 的单例先例）。本节即 02 §7.1「各事实类型规范分别登记本类型实际采用的公共字段」所允许的类型来源声明，依据 02 §7.1 单例类型字段豁免通道。公共字段实际采用：`title`、`status`、`created_at`、`change_log`（首修后必有）；不采用 `fact_type_key`（单例路径即身份，类型标记由 `goal_key` 固定值承担——本节首行定案，与 §7 闭集一致）、`object_uid`（路径即身份）、`urls`（目标陈述不依赖外部来源）、`relations`（Goal 是链顶，无上游可指；下游引用由 WC 的 `serves` 直接建立，方向不可逆）。

创建与变更权：创建与任何修改都必须经 Human 决定（修订属 00 §3.2 级根决定事项——项目目标的变更改变一切下游锚定）；AI 只能提议修订（C1 提案对象模式），无直接写入路径。

## 8. 字段契约

frontmatter 闭集（全部必填，除标注外创建时一次落定）：

| 字段 | 类型 | 语义 | 约束 |
|---|---|---|---|
| `goal_key` | string | 固定值 `project-goal` | 唯一合法值；机械校验 |
| `title` | string | 目标陈述收紧后的短标题 | ≤ 40 字；不承载子目标内容 |
| `status` | string | 闭集 `active` / `achieved` | 初态必为 `active`；`achieved`=项目收官判定，见 §9 |
| `created_at` | RFC3339 | Code 受控创建时填写 | AI 不得填写 |
| `change_log` | array | 每次实际修改恰好追加一条 | `at`/署名 Code 托管；AI 只提供一句话语义摘要；每条必含修订理由 |

正文一块固定 H2：

```
 # 项目目标
 ## 目标陈述        ← 为什么 + 要实现什么；一段话；≤ 200 字符；写给未来会话与新读者（冻结区）
```

**本类型只有一个内容字段：目标陈述**（Human 决定）。没有「概要」与「陈述」两个字段，也不存在任何摘要型字段——同一句话在聚焦页与详情页都按原文呈现，两处不承担不同长度的版本。理由是防第二事实源：一旦为同一意图并存「短版」与「长版」，两者必然分叉，而分叉时没有任何机械判据能说哪一版才是目标。这一条与其他类型分层承载摘要与正文的做法**方向相反**，不构成先例引用：分层承载摘要与正文的做法服务于不同读者且都只描述「要做什么」；Goal 只有一类读者，短版与长版之间没有读者差异，只有抄写差异。

**目标陈述 ≤ 200 字符（机械校验）**：判定单位为 UTF-16 码元计数（实现按 `.length` 判定，与各类型对摘要字段的判定单位一致）。上限是**意图上限**而非排版上限：它把「怎么做」「做到哪算成」「为什么这样拆」这些属于下游对象的内容挤出本载体——写不下时，作者只能把细节挪到它该在的地方（判据归 28 号 SubGoal，执行与验收由主控在当次行动中承接，尚未定形的方向归 20 号 Spark，已作出的决定归 22 号 ADR）。超限时**拒绝写入，不得截断后写入**（与各类型对摘要字段的拒绝纪律同形）。计数按去除首尾空白后的正文段计算，段内换行与空白照常计入。

**上限不替代可判定性**：200 字符是形态约束，不是内容判据。一条写满 200 字符的陈述仍可能不是可判定的目标陈述（30 §8.1 四项：能被证据判定、指向未来状态、不依赖当次会话、不绑定实现手段）。机械层只保证长度，内容是否达到「可判定」属语义判断，由 Human 确认承担（§15）。

**子目标节已移出本载体**（本次修订）：子目标改由 SubGoal 事实对象承载（28 号），goal.md 不再列子目标条目。该移除解除了一处长期存在的粒度冲突——单例载体同时承载「一条项目级意图」与「一组可增删的条目标签」，使子目标既无独立身份也不能被单独更新。

**方法与规划两区已移除**（Human 决定简化）：方法与规划后续重新设计，当前 goal.md 只承载目标陈述；原规划内容回归锚点文档建设顺序承载。

change_log 修订理由的最低形态：`summary` 必须能独立回答「改了什么 + 为什么改」；goal 修订属罕见事件（预期季度级零次至一次），每条理由都是演进脉络链的实体节点。

## 9. 状态与生命周期

状态闭集仅两值：`active`（项目存续期常态）→ `achieved`（全部子目标判定达成且 Human 决定收官）。无第三个状态——不设 `abandoned`：项目放弃 = 项目退役（管辖取消），goal.md 随 `ldvh-base/` 保留为历史档案（08 §5.7 取消登记语义），无需独立状态承载。

- `active → achieved`：Human Gate（终局判定是根决定）；前提是全部活跃子目标的达成判定成立（每条锚定其 `criterion` 所指材料，AI 汇总提议，Human 判定）；翻转后文件冻结为历史档案。
- 不存在的转换：goal 不退役、不 superseded、不重开。项目目标被根本推翻 = 受控修订（大改 change_log），不是状态转换。
- **更正/更新/处置/删除的差异**（02 §12.2 本角色必答项）：更正与更新的语义区分与共同纪律见 §13「更正与更新的区分」条；处置即项目退役（goal.md 随 `ldvh-base/` 保留为历史档案，见 08 §5.7）；删除不存在（同上）。本类型不设关闭、归档、合并、替代四类动作，故不另立对应入口。

子目标精化次序：创建时允许只落目标陈述（尚无子目标是合法中间态，28 §6 不要求每条目标都有子目标）；首次精化由 AI 在该项目的早期会话提议子目标候选、Human 逐条确认后经受控创建落入 SubGoal 载体（28 §13）——该路径不经过 Goal 的受控更新，goal.md 不因新增子目标而变更，故 goal 的 change_log 不记录子目标的增改。

## 10. 来源与证据

目标陈述是 Human 意图的结构化表达，来源是 Human 决定本身（初始化对话或修订对话中的确认记录），不适用外部证据锚定；本类型无 `urls`、无逐字摘录、无溯源锚点要求（与 24 号的最大差异——Goal 不调查外部世界，只承载内部意图）。

子目标的可判定性由 28 §10.2 的判据类型闭集与其语义审核共同保障；本类型不重复该判断，也不校验子目标的判据格式。

`achieved` 判定的证据形态与三层职责边界：逐条子目标（SubGoal 对象）→ 各条 `criterion` 所指材料链。三层分工：机械层反查 `parent_goal` 收集全部子目标、再反查 `serves` 收集各自名下对象的关闭记录，汇总为证据清单（只做存在性与格式校验，不判断材料是否真的满足该子目标的 `criterion`）；AI 层逐条语义审核证据是否覆盖判据，发现缺口时列出（不得补造证据或掩盖缺口）；Human 层终判（achieved 翻转是根决定）——三层互不替代，机械层的「记录存在」不等于语义层的「条件满足」。

**子目标为空时的处置**：全部子目标为零或全部 `retired` 时，目标不满足收官前提；该状态须在交还与呈现中显式标注为「未完成精化」，不得以「没有反对意见」推定为可收官（30 §8.3 末段同向）。

## 11. 关系契约

不使用 `relations` 字段（类型来源声明不采用，02 §8.2 允许）。理由：Goal 是引用链顶点，唯一合法边是「下游指上来」——SubGoal 的 `parent_goal` 与 WC 的 `serves`（`object_uid`）；Goal 自身无上游、无平级。反向投影（本项目有哪些子目标、某子目标名下有哪些 WC）由机械反查 `parent_goal` 与 `serves` 得到，不需要 Goal 侧存储。

## 12. 召回与消费

单例三免的第三免：不走 F0–F2 候选召回。消费点全部直读（消费方知道路径）：

| 消费点 | 时机 | 消费内容 |
|---|---|---|
| systemPrompt 注入（引导段 +1 项） | 每会话 | 目标陈述 + active WC 列表一行摘要；goal 缺失时注入「项目未初始化」提醒 |
| Gate 1 授权提请 | 每次 WC 授权 | 必含「本 WC 服务哪条子目标」（直引其 `object_uid` 与标题，须解析到 28 号对象） |
| Web「当前目标」区块 | 每次 Web 呈现 | 目标陈述投影 + 子目标派生概览（按 `parent_goal` 反查，含空集歧义提示 28 §8.1） |
| 方案收敛依据装配 | 每次方案收敛装配前 | 目标服务性检查（主控方案收敛本职 04 §6.1 已定义引用） |
| 子目标精化提议 | 早期会话 | 全文直读（子目标由 28 号承载，见该类型消费点） |

Enforcement：goal.md 缺失时 Gate 1 无法受理（授权无锚可引，架构性 fail-closed，无需额外规则）；一切读操作（调研/讨论/Spark/Research/事实源浏览）不拦——探索与调研正是形成目标的过程。goal.md 存在但子目标为空（零条或全 `retired`）时，WC 可正常走（Gate 1 引 goal 本体与 `serves` 所引子目标），注入段须提示「子目标待精化」，且该缺口在交还中可见（30 §8.3 末段）。

**召回判据表（02 §12.4 格式契约）**：

| 判据项（recall-criteria/v1） | 本类型规则 | 机械值 | 依据/理由 |
|---|---|---|---|
| 召回时机 | 不采用 | 不采用 | 单例三免第三免：Goal 不走 F0–F2 候选召回，消费点全部直读（本文本节） |
| 默认候选状态 | 不采用 | 不采用 | 同上——无候选概念，消费方知道路径直接读取 |
| 核心语义字段 | 不采用 | 不采用 | 同上——goal.md 全文直读，无候选投影与匹配面 |
| 类型词别名 | 不采用 | 不采用 | 同上——Goal 不在类型点名候选路径内；`goal` 单例身份由 goal_key 承载 |
| 关系展开 | 不采用 | 不采用 | 同上——Goal 无 `relations`；级联只到在途行动标记，不建关系边（本文 §13 goal 修订级联） |

## 13. 受控操作

- 创建：仅经「项目初始化对话」路径（触发句「帮我进行项目初始化」；Web 横幅指路）。机械校验：goal.md 不存在（否则拒绝——单例 fail-closed）、`goal_key=project-goal`、title 非空、status=active、目标陈述 H2 存在且非空且 ≤ 200 字符。创建后回读。安装表单不是创建路径。
- 更新（陈述精化）：02 §10.5 受控更新；CAS 以完整文件为单位，绑定 `content_fingerprint`；每次恰好一条 change_log（含理由）；必须先经 Human 确认（C1 模式）。**子目标的增改与作废不经本入口**——由 28 号受控操作承接，本类型不为子目标变更追加 change_log。
- **更正与更新的区分（02 §11）**：Goal 的任何修改均须经 Human 决定（§7 创建与变更权），故「事实更正」与「普通内容更新」二者彼此在**权限与纪律上相同**（比较对象是这两种动作，不是 AI 与 Human）——同走 C1 提案、Human 确认、02 §10.5 CAS 与恰好一条 change_log。二者区别在**语义**：更正只改错述（写错的陈述、错记的判据），不改判断结论；更新可改变判断结论，须按 §13 既有纪律提交 change_log 理由并经 Human 确认。**不得**以更正之名改变已作出的判断结论（那属更新）。
- goal 修订级联（C2 链式扩展）：修订落盘后先按 `parent_goal` 取出全部子目标，再机械扫描这些子目标的 `serves` 命中的 active WC，逐个标记 `goal-changed 待核对` 并生成待办；核对（调整/关闭/保持，各留各自 change_log），按局部重批语义处置。只到 active 对象；Spark 豁免；每跳是标记非动作；Goal 侧不为级联存储任何下游状态。**子目标本身的 `alignment` 是否仍成立**同属须核对项（28 §12.1），核对结论写入各子目标的 change_log。
- 状态翻转（achieved）：Human Gate；AI 按 `parent_goal` 取出全部子目标并逐条汇总证据链，Human 判定；翻转即冻结。
- 删除：不存在删除操作。项目退役时 goal.md 随 `ldvh-base/` 保留。

升级路径（存量管辖项目无 goal.md）：「更新修复」入口扩展 goal 检测；首次 AI 会话检测缺失时主动引导。Web 横幅持续显示直至补齐。

## 14. 类型特有验证与类型退出（02 §12.1 第 10 项）

### 13.1 类型特有验证

本类型在 02 §10 公共契约与 §15 通用验证表之外的特有验证：

- **单例 fail-closed**：受控创建入口在 `goal.md` 已存在时零写入拒绝；运行时兜底按 §17 必停情形第 1 项暂停（存在性检查为机械可判）。
- **子目标不落本载体**：goal.md 不得列子目标条目、不得存子目标状态副本；身份与状态全由 28 号类型核对（28 §14.1），本类型只核对「未被复制回本载体」。
- **载体内聚**：`title`、`scope`（若采用）等 frontmatter 权威字段与其正文对应段逐字一致（frontmatter 为唯一权威文本，正文只展开）。
- **目标陈述长度上限**（§8）：目标陈述去除首尾空白后 ≤ 200 字符（UTF-16 码元，实现按 `.length`），创建与每次更新都校验；超限即拒绝写入，不得截断后写入。**未验证范围**：本项只证明长度达标，不证明陈述可判定（30 §8.1 四项属语义判断），也不证明 200 字符已装下全部意图——被挤出的细节是否真的迁到了下游对象，无机械判据。
- **修订授权绑定**：每次更新恰好一条 `change_log`，且对应一次 Human 确认记录；无确认记录的变更不成立（§15 验证表第 3 行）。
- **achieved 证据链完整性**：翻转前每条 SubGoal 须有可回读的其 `criterion` 所指材料；证据缺口不得翻转（§17 必停情形第 4 项）。

### 13.2 类型退出

若 Human 决定取消 Goal 类型，须按 02 §11 处理：处理仍适用事实、入向/出向关系（`serves` 反查链）与稳定引用，登记变化按 01 §8.1 同步，走受控提交。退出属 00 §3.2 根决定。

## 15. 验证与证据边界

| 验证对象 | 成立条件 | 验证入口 | 未满足时的处理 |
|---|---|---|---|
| 单例存在性 | 消费点读取时核对（依据文件系统路径检查结果）：goal.md 至多一份；存在即解析成功。仅证明当次载体存在性与可解析性 | 机械（路径检查） | 报告 `unavailable`；不选择替代文件继续 |
| 子目标归属可解析 | 每次读取与达成判定前核对（依据子目标全集回读28 §14.1）：以 `parent_goal` 反查到的每条 SubGoal 均可读，且其 `parent_goal` 回指本目标。仅证明当次反查到的子目标集合；**不证明集合已穷尽或子目标充分** | 机械（`parent_goal` 反查） | 报告悬空子目标；不选择替身继续 |
| 修订授权 | 每次更新核对（依据change_log 条目 + 会话/Gate 载体中的确认记录）：change_log 对应一次 Human 确认记录。仅证明当次修订的授权事实 | AI 语义审核 | 撤回未授权变更；补走 Human 确认 |
| achieved 证据链 | 状态翻转前核对（依据`parent_goal` 反查的子目标全集 + 各条 `serves` 反查的关闭记录）：每条子目标有可回读的其 `criterion` 所指材料。仅证明各子目标达成判定的证据覆盖 | 机械（双层反查）+ AI 汇总 + Human 终判 | 保持 active；补齐证据或缩小声明范围 |
| 级联标记正确性 | 修订后核对（依据子目标全集的 `serves` 反查结果与标记清单对照）：受影响 active WC 全部被标记、无遗漏。仅证明当次扫描的引用链完整性 | 机械（`serves` 反查） | 补标遗漏项；重新生成待办 |
| 子目标不存储于本载体 | 每次更新与读取核对（依据更新前后完整文件对照）：goal.md 不含子目标条目、不含子目标状态副本。仅证明当次载体是否仍承担子目标承载；**不证明引用方向未被复制到别处** | 机械（正文结构比对） | 拒绝写入；把子目标相关改动转由 28 号受控操作承担 |
| 目标陈述长度 | 创建与每次更新核对（依据载体正文的 `## 目标陈述` 段长度）：目标陈述去除首尾空白后 ≤ 200 字符（UTF-16 码元）。仅证明当次陈述的字数达标；**不证明可判定、不证明细节已迁出** | 机械（`.length` 计数） | 拒绝写入；精炼陈述或把细节移到下游对象，不得截断 |

Goal 对象存在、状态为 active 或 change_log 条目存在，均不能单独证明目标正确、子目标充分适用、授权工作已经开始或项目价值成立。

类型退出：若 Human 决定取消 Goal 类型，须按 02 §11 处理。退出属 00 §3.2 根决定。

## 16. Human Gate

本文不新增 00 之外的 Human Gate。领域增量事项（00 §3.2 在 Goal 领域的具体化）：

1. Goal 的创建与任何修订（项目目标的变更改变一切下游锚定）；
2. `achieved` 状态翻转（终局判定）；
3. Goal 类型本身的取消或合并。

Human 的决定只证明其决定内容与作用范围，**不替代**本领域以下判断：目标陈述是否可判定、子目标是否可观测（28 §10.2）、达成证据是否完整、目标与结构或进展的偏离是否已被证据支持、以及目标本身是否正确。这些只能由规范原文与证据核对承担，不由 Gate 决定替代。

## 17. 必停情形

本文不新增必停的根触发（该共同规则见 00 §4.7）。领域触发与最小影响范围：

出现以下任一情况时，必须暂停受影响的 Goal 操作：

1. 准备创建第二个 Goal 对象（单例违例——受控创建入口应拒绝而非暂停，此处是运行时兜底）；
2. 准备在 goal.md 内重新承载子目标条目或状态副本（第二权威违例，28 §17 第 6 项同向）；
3. AI 未经 Human 确认直接执行 goal 修订（授权缺失）；
4. `achieved` 翻转提议存在子目标证据缺口（未达成却准备翻转）；
5. 级联扫描发现受影响 active WC 存在但标记遗漏（级联完整性违例）。

暂停期间只允许不越过停止边界的证据补取、引用修复、授权补走与条件核实。恢复须与触发原因逐项对应。同一停止条件恢复后再次触发的，按 00 §4.7 的恢复与再次触发进入 Human Gate。

## 18. 反过度设计红线

1. 不为单例建目录/编号/文件名编码——路径即身份，不另设 `object_uid`；
2. 不为 Goal 存储下游状态——级联是标记不是 Goal 侧的数据结构，反向投影由 `serves` 反查得到；
3. 不为 goal.md 建缓存/索引/投影副本——消费点直读，Web 投影不回写；
4. 不为「goal 缺失」建立独立的状态枚举——Gate 1 自然 fail-closed 即是全部 enforcement，无需额外规则；
5. 不为初始化对话设独立 Gate 形态——创建走正常受控创建，精化走普通受控更新。
