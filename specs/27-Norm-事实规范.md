# Norm-事实规范

## 1. 价值判断

Norm 解决管辖项目的成体系方向规范缺少事实对象承载的问题：「代码规范」「安全策略」「API 契约」这些方向的规则若散落在对话、散落文档或多份重叠文件中，每次方案工作都无法定位同一份权威依据，重复制定规则、无意间违背既有约束、或找不到某方向的完整约束集——与 00 §1 痛点 4「历史经验与教训，无法积累」同构。Norm 以事实对象承载成体系方向规范：一个 `direction_key` 标识一个方向，一份 active Norm 承载该方向的完整规则体系，为遵守预检、方案收敛、审计核对与 Web 呈现提供可回指的稳定来源。普通文件不能无损承载：无受控写入、无 active/retired 状态闭集（「这份规范还在生效吗」无从机械判定）、无方向键排他约束（「同方向是不是只有一份」无从核查）、无正文骨架结构保障（「是否成体系」无弱机械门槛）。ADR 是点状决定（单条、临时），Norm 是面状体系（长效、系统化）；Spark 是悬置层（方向未定），Norm 是方向已定的成体系承载。本规范主要服务核心价值一（项目可厘清，00 §1.1）：Norm 为「代码规范」「安全策略」「API 契约」这类成体系方向规范提供唯一权威事实载体，使每次方案工作定位到同一份依据，而不是在多份重叠文件或对话中猜测哪份有效；兼服务核心价值二（任务高效准确完成，00 §1.2）：遵守预检以 direction_key 为索引，违背当前 active Norm 即被拦截，规则引用可回指具体条目。本文不以全量价值声明替代主要影响判断。并支撑积累效用直观可见（方向清单与活跃规范是项目规则体系的全貌投影）。

Norm 对象存在、处于 active 或正文包含规则条目，均不能单独证明规则正确、适用、已被遵守或方向覆盖完整——规则的价值须在后续遵守预检、方案收敛装配与审计核对的真实消费中核对。Norm 与元规范层级不同：Norm 是项目侧事实规范，元规范是 LDVH 自身机制规范；事实规范不得放松元规范（00 §3.2），也不自授效力——效力来自规范源层级与 active 状态，不来自任何路径挂靠或来源字段。

## 3. 职责边界

### 3.1 本文负责

1. Norm 类型的目的、对象边界与「成体系」的定义判据；
2. Norm 的身份与载体（多例、平铺单文件、`ldvh-base/norms/norm-<uid>.md`）；
3. Norm 的字段契约（frontmatter 闭集、正文四段固定 H2 骨架、direction_key 专属字段）；
4. Norm 的状态与生命周期（active/retired 闭集、转换与终态处理）及来源与证据边界；
5. Norm 的方向清单与反重复机制（唯一性公式、三层设计契约及各层入口与验证方式）；
6. Norm 的关系契约（不使用 relations 字段）；
7. Norm 的召回与消费点（遵守预检、方案收敛、审计核对、Web 呈现）；
8. Norm 的受控操作（创建、受控更新、退役）。

### 3.2 本文不负责

1. 方案收敛的装配与分流流程（主控方案收敛本职承载，04 §6.1，本文只定义 Norm 作为装配依据来源的消费语义）；
2. 遵守预检的完整判定逻辑（34 号双源召回系统规范承载，本文只定义消费语义接口）；
3. 受控提交契约（09 承载）；
4. Human 作出或废除方向规范的过程（00 §3 承载——Norm 记录已确立的方向规范，不产生规范制定过程本身）；
5. Web 呈现的视觉与交互细节（10 号承载）；
6. ADR 终态流转的具体机制（22 号承载——ADR 被事实规范承接后的退役由 22 号 `retirement_reason=absorbed` + `absorbed-into` 关系表达，本类型不定义 ADR 的退役细节）。

### 3.3 相邻规范分工与唯一权威

02 是公共字段、关系与受控读写契约的唯一权威；09 是受控提交契约与 Git Gate 的唯一权威；06 是 Code 实现的唯一权威；22 是 ADR 类型语义的唯一权威；01 是元规范结构与身份契约的唯一权威。本文只定义 Norm 类型自身的边界、字段、方向清单、状态、关系与消费点，不复制相邻规范的规则。

## 4. 适用范围

### 4.1 适用对象与场景

1. 管辖项目中的多例 Norm 对象（`ldvh-base/norms/norm-*.md`）；
2. Norm 的方向键、状态、正文骨架与规则内容。

本规范用于 Norm 的创建（方向确立后起草成体系规范）、受控更新（active 状态下的规则修订）、退役（方向不再需要或被替代）与消费（遵守预检、方案收敛、审计核对、Web 项目规范看板呈现）。

### 4.2 明确排除与证明边界

明确排除：元规范（`specs/` 下的 LDVH 自身机制规范，不适用本类型）；单条决定（走 ADR）；执行计划与已批准行动（由主控在当次行动中承接，不对象化）；项目目标（走 Goal）；外部证据调查（走 Research）；教训与规避（走 Pitfall）；改进账本（走 Friction）；对话中的临时约定（重要性不足以对象化的留在会话记录）；方向内的子主题拆分文件（不升格为新方向，不建立新 Norm 对象）。Norm 对象存在或状态为 active，不能单独证明规则正确、适用、已被遵守或方向覆盖完整。

## 5. 类型定位与价值

Norm 是项目侧事实规范层的系统化类型：承载管辖项目中一个完整工程方向的成体系规则体系，供前瞻约束与回溯审查。它是事实规范的唯一事实类型定义——事实规范是一种事实对象，由本类型规范定义其对象边界、字段、状态与生命周期。

**层级边界（本类型的适用范围锚点）**：本文定义的 Norm 属于**项目层级** —— 它约束**单一受管辖项目**的内容、结构与工程纪律，随该项目 worktree 走，不随 LDVH 插件版本发布。**元层级**的规范（LDVH 自身的机制规范，位于 `specs/`，随插件版本锁定、对所有受管辖项目生效）**不属于本类型**，其结构、身份与读取契约由 01 与相应元规范定义。因此 §12 授权附件中的方向参考清单，其用途是**帮助该项目识别自身需要哪些方向的事实规范**，**不是**用于核查元规范是否遗漏或重复方向。两层可各自持有同名方向（如元层 `09` 管 Code 方向、项目层亦可有自己的 Code 方向 Norm），二者不构成重复，因为约束对象不同。

**「成体系」的定义判据（Human 定义的类型准入核心）**：

一个方向的规则是否构成「成体系」的规范，满足以下三条判据中的至少两条：

1. **多条可独立执行的规则**：不是单条决定或建议，而是形成规则集合——多个条目各自可被检查遵从性；
2. **明确的管辖边界**：有清晰的「管什么、不管什么」定位，不与其它方向的边界严重重叠；
3. **持续消费价值**：在后续方案工作、代码实现、审计核对中会被反复引用，不是一次性结论。

按 02 §6.2 准入六问：跨行动保留——方向规范必须跨会话稳定，否则每次方案工作重新制定规则；独立身份与状态——有 active/retired 与方向键排他约束，需要独立生命周期；普通文件不能无损承载——无受控写入、无状态闭集、无方向键排他校验、无正文骨架；消费价值服务 AI（遵守预检/装配）与 Human（Web 规范看板）双轨；维护成本——中等频率类型（每方向通常数月修订一次），净值为正；类型定义来源——本规范。

## 6. 对象边界

### 6.1 什么构成一个对象

一个 Norm 对象 = **一个完整工程方向的成体系规范体系**：方向键（direction_key）+ 方向定位与适用范围（正文）+ 核心规则体系（正文）+ 约束与反模式（正文）+ 验证与遵从性检查（正文）。判据：方向可独立召回、规则可独立检查遵从性、方向定位有清晰边界、正文具有成体系的规则内容。

**「方向」的判据**：一个方向是管辖项目中一个可独立成规范的关注面。两个候选方向是否为「同一方向」，满足以下任一条则应分设为不同方向：

1. **主语不同**——管的是「机制/能力」还是「职责/判定」？是「工程动作」还是「治理结论」？主语不同则方向不同；
2. **变更频率不同**——一个话题常随业务变、另一个随技术变，应分开；
3. **责任面不同**——违反它的后果由谁承担、向谁负责？责任面不同则方向不同。

三条都高度重合才考虑合并（参见 §11 方向清单的「可合并」说明）。

### 6.2 查重

创建前必须查重：对照既有 active Norm 的 `direction_key` 精确匹配（机械）与 title/正文定位语义比对（AI 语义判断）。同方向已存在 active Norm 时，不新建——走受控更新路径修订既有规范；方向实质变化时，退役旧 Norm 并建立新 Norm（新 direction_key），不改写既有 Norm 的方向语义。查重结论必须记录在创建提案中。

### 6.3 明确不属于本类型

单条决定或取舍记录（走 ADR——「临时的、单条的决定」）；执行计划与已批准行动（由主控在当次行动中承接，不对象化）；项目目标与子目标（走 Goal）；外部证据调查（走 Research）；教训与规避经验（走 Pitfall）；改进账本（走 Friction）；对话中的临时约定；方向内子主题的拆分文件（不升格新方向，不建立新 Norm）；元规范（`specs/` 下的 LDVH 自身机制规范，不适用本类型）；已被事实规范完整承载的 ADR 决策（规则由 Norm 承载，ADR 可作为决策来源被引用但不再承担约束——22 §6.3 第 9 项）。

## 7. 身份与载体

| 项 | 定案 |
|---|---|
| `fact_type_key` | `norm`（类型短名，02 §7.1 值域） |
| 载体 | 平铺单文件：YAML frontmatter（机器权威）+ markdown 正文；`ldvh-base/norms/norm-<uid>.md` |
| 权威位置 | `ldvh-base/norms/`；目录基数校验，文件名编码 UID |
| 公共字段 | `object_uid`（UUIDv4，Code 生成）、`fact_type_key`（`norm`）、`title`、`created_at`（Code 填写）、`status`（active/retired）、`change_log`（Code 托管流水） |
| 不采用字段 | `urls`（规则内容住正文，不依赖外部 HTTP 来源；02 §7.1「字段缺省遵循类型来源」）、`relations`（Norm 之间不建立结构化关系，跨方向约束以主规范承载 + 他处引用实现，参见 §9） |

正文结构的公共契约（H1 恰好一个且由 Code 从标题生成、正文自 H2 起）按 02 §7.3 承接；本节只定义本类型的 H2 骨架，不重述该层。

创建与变更权：创建必须经 Human 决定（方向规范的确立是项目规则架构决策，属 00 §3.2 级根决定事项）；active 状态下的受控更新走 02 §10.5（change_log 留痕）；退役必须经 Human 决定（方向不再需要或被替代是根决定）。AI 只能提议修订与创建提案，无直接写入路径。

**载体内聚（本类型的形态，与 22/23/26 不同）**：本类型正文四段是**规则散文**，不是任何 frontmatter 字段的投影——frontmatter 只承载机器索引（`direction_key`、状态、流水），规则内容整体住正文，二者不构成「同一文本在两处出现」的关系。故本类型**不要求**正文逐字复现任何 frontmatter 标量。机械校验只覆盖一条：正文若以文本声明 `direction_key`，其值必须与 frontmatter 一致（frontmatter 是唯一权威文本，正文不得声明与之矛盾的方向键）。

## 8. 字段契约

本章按 02 §12.1「允许合并相邻角色」的口径，合并承载「字段契约」「状态与生命周期」（§8.1）与「来源与证据」（§8.2）三个相邻结构角色。

frontmatter 闭集（全部必填，除标注外创建时一次落定）：

| 字段 | 类型 | 必填性 | 语义 | 约束 |
|---|---|---|---|---|
| `fact_type_key` | string | 必填 | `norm` | 唯一合法值（02 §7.1 值域） |
| `object_uid` | UUIDv4 | 必填 | Code 生成 | 创建时落定，永不改变 |
| `title` | string | 必填 | 方向规范短标题 | ≤ 40 字；供候选定位与 Human 扫读 |
| `status` | string | 必填 | `active` / `retired` | 初态必为 `active` |
| `direction_key` | string | 必填 | 方向键，标识本规范管辖的方向 | 小写 kebab-case：`^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`；同一 direction_key 至多一个 active Norm（§11 唯一性公式） |
| `created_at` | RFC3339 | 必填 | Code 受控创建时填写 | AI 不得填写 |
| `retirement_reason` | string | 条件 | 终态原因 | 闭集：`superseded` / `outdated` / `out-of-scope`；retired 必填、active 禁现 |
| `retired_at` | RFC3339 | 条件 | Code 填写 | retired 必填、active 禁现 |
| `change_log` | array | 条件 | 变更流水 | 首修后必有；每次恰好一条 |

`direction_key` 是本类型的专属字段（符合 02 §7.1「各事实类型规范分别登记专属字段增量」的既有惯例，对照 22 的 `decision`、24 的 `research_question`）。它是机器可验证的方向标识，与 `object_uid`（全局唯一标识）语义完全不同：`direction_key` 定义「这份规范管哪个方向」和「唯一性约束的作用域」，`object_uid` 定义「这份对象是谁」。

正文四段固定 H2 骨架（创建时必须全部存在且各段非空）：

```markdown
## 方向定位与适用范围  ← 首句为「**管什么**：…」（≤60 字，书写契约见下）；其余为不管什么/适用边界（必填）
## 核心规则体系        ← 该方向的核心规则条目，可包含 H3 子节（必填）
## 约束与反模式        ← 明确禁止项与违规后果（必填）
## 验证与遵从性检查    ← 定义如何检查是否遵守本规范（必填）
```

**「方向定位与适用范围」段的书写契约（本段的唯一权威形态）**：该段的职责是让读者（AI 或 Human）在不展开其余三段的前提下，判断「本规范是否可能在管当前事项」。为使其可被确定性摘取、且不夹带规则内容，该段**首句**须满足以下四条，其余内容（不管什么、适用/不适用、相邻分工、依据沿革等）另起段落、不受首句约束：

1. **以固定标签起首**：首句必须以 `**管什么**：` 逐字开头（粗体标记 + 中文冒号），其后紧跟定位陈述；
2. **是职责定位，不是规则或授权**：只陈述「本方向管什么」，不得含具体规则条目、触发条件、授权措辞（如「无须请示」「可直接」「免于」）、依据沿革或时间叙事；
3. **自足且可独立成立**：脱离本段其余文字仍能被读懂，不以「上文」「本条」「该规程」等指代开头；
4. **长度 ≤ 60 字**（含标点，按 UTF-16 码元计）：使 `ldvh_norm_list` 的 「方向定位摘录」无需截断即可完整外发，也让本段在注入面可读。

**首句边界与机械范围**：「首句」指 `**管什么**：` 之后到第一个 `。` 或 `；` 为止。机械层（`ldvh_norm_list` 的摘录提取）只判第 1 条标签形态、第 2 条点名的授权措辞、第 4 条长度；第 3 条「自足」与第 2 条的语义边界（是否夹带规则/触发条件）属 AI/Human 语义审核，不由机械层宣称已判定。不合契约时不外发摘录，而非截断后外发——截断会产生脱离上下文的半句。

**为什么限定首句**：`ldvh_norm_list` 对每份 Norm 投影一段「方向定位」摘录（`34 §8.1` 适用识别的消费面），其提取规则与本节第 1 条绑定——只取 `**管什么**：` 标签后的首句。首句若混入授权、触发条件或无法自足，摘录就会把一句脱离上下文的规则当成「本规范管什么」抛给 AI（本仓「上游更新跟进规程」的旧写法即为实证）。此契约把「可机械提取」与「内容质量」合并在一处，不构成第二规则源：摘录是正文首句的派生视图，正文仍是唯一权威文本（§7 载体内聚）。

`direction_key` 与 `title` 的区别：`direction_key` 是机器标识（唯一性校验、索引、跨规范检索），`title` 是人类可读短标题（扫读定位、Web 呈现）。`direction_key` 不随标题修改而改变（纯标题修正不改 direction_key，参见 §13.2 勘误边界）。

字段间不变量：`direction_key` 格式符合正则（机械校验）；同一 `direction_key` 在 active 集合中至多一个（§11 唯一性公式；其三层机械承载的具备前提见 §11 与 §14）；`retirement_reason`/`retired_at` 随 `status` 约束（§8.1）；正文四段固定 H2 全部存在且各段非空（机械校验）；未知字段不进入 canonical 对象。「方向定位与适用范围」首句的书写契约（见上）**当前不接入创建/更新拒绝**：不合契约者由 `ldvh_norm_list` 的「摘录可用性标注」显式报告不可用（此处借用 `34 §12` 的 unavailable 词表示「该份定位不可导出」，并非该节召回完整度三态的取值），并指引 `ldvh_norm_read` 读正文。是否启用机械拦截属独立 Human Gate 决定，本文不预设其时点。

### 8.1 状态与生命周期

**状态闭集与合法初态**：`status` 闭集为 `active` / `retired`（§8 字段表；§7 公共字段）。合法初态唯一：创建时必为 `active`，不存在以 `retired` 为初态的对象。状态值与终态字段只能经 02 §10 受控写入路径落定，AI 无直接写入路径（§7 创建与变更权）。

**转换（闭集内的全部合法转换及各自所需依据）**：

1. **创建 → `active`**：Human 确认（方向规范的确立属 00 §3.2 级根决定）后经受控创建入口落盘。依据：创建提案（含查重结论、direction_key 合法性与完整四段正文）＋机械校验（字段闭集合法、direction_key 符合正则、同一 direction_key 无 active 冲突、title ≤ 40 字、四段骨架非空）＋创建后精确回读（§11 创建）。
2. **`active` → `active`（受控更新）**：走 02 §10.5；CAS 以完整文件为单位，每次恰好一条 change_log。依据：change_log 注明修订内容与理由。direction_key 不得改变；方向定位与适用范围段的管辖边界不得实质变更——实质漂移走退役＋新建路径，不伪装为更新（§11 受控更新；勘误级更新见 §13.2）。
3. **`active` → `retired`（退役）**：唯一进入终态的转换，Human Gate。依据：`retirement_reason`（闭集 `superseded`/`outdated`/`out-of-scope`）＋ `retired_at`（Code 填写）＋ `superseded` 时替代 Norm 已存在且可解析；AI 先精确读取 F3 核对理由与证据，Code 检查闭集、字段与回读（§11 退役；§13.1 终态完整性）。

不存在 `retired` → `active` 转换：重启某方向不经由状态回转，而按创建路径建立新对象（新 `object_uid`；`direction_key` 可以复用）（§11 唯一性公式）。`retired` 是唯一终态；终态 Norm 保留为只读历史档案（§11），不进入普通候选，只在精确引用或历史追溯时展开（§10 召回分层）。

**更正/更新/处置/删除差异**（02 §11 要求类型来源区分普通内容更新、事实更正、状态转换、关闭、归档、合并、替代和删除等不同动作，本节为本类型的落地）：更正＝勘误级更新——错别字、引用路径修正、表述澄清，不改 direction_key 与管辖边界（§13.2）；更新＝`active` 状态下的规则修订（§11 受控更新）；处置＝退役＋终态字段齐备（§11）；删除＝不存在删除操作，终态保留即处置的完成形态（§11）。状态-字段不变量：`active` 禁现终态字段，`retired` 必填 `retirement_reason`/`retired_at`（§8 字段表；§13.1）。

### 8.2 来源与证据

**来源**：Norm 承载的规则内容，其确立与退役均是 Human 的方向规范决定（00 §3.2 根决定；§7 创建与变更权；§15 项 1/2）；AI 只能提议修订与产出创建提案（含查重结论，§6.2），不产生规范制定过程本身（§3.2 项 4）。既有设计文档与边界调研只作设计输入，不取得规范效力（§2）。ADR 可作为决策来源在正文自然语言中引用（§9）。事实规范的效力来自规范源层级与 `active` 状态，不来自任何路径挂靠或来源字段（§1；§17.4）。

**证据形态**：YAML frontmatter（机器权威）＋ markdown 正文（§7 载体）；创建提案中的查重结论记录（§6.2）；Human 确认记录（§14「规则内容质量」行）；`change_log` 变更流水（Code 托管，§7/§8）；受控操作后的精确回读与机械校验结果（§11、§13.1）。

**观察时间**：`created_at`（Code 受控创建时填写，AI 不得填写）、`retired_at`（Code 填写）与 `change_log` 流水时间均由 Code 托管（§8 字段表；02 §10/§7.1 公共契约——实际修改时同一事务追加 Code 托管时间的流水）。规则内容的确立与修订时点以这些受控时间戳为准（frontmatter 为机器权威，§7）。

**充分性判断**：本类型不另设第二套充分性标准，按 §14 验证表逐行判断——身份与方向键、方向键唯一性、正文骨架、查重已执行、终态完整性、规则内容质量（成立条件：规则可执行、边界清晰、验证可操作）、跨方向约束一致性；机械结果与语义判断互不替代（§14）。Norm 对象存在、处于 `active` 或正文包含规则条目，均不能单独证明规则正确、适用、已被遵守或方向覆盖完整（§1；§14）。

**机械校验与 AI 语义审核边界**：机械可校验者＝字段闭集、direction_key 正则、四段固定 H2 存在性与非空、终态字段完整性，以及 active 方向键唯一性（§13.1；§11 三层设计契约）。AI 语义审核承担＝创建前查重的语义比对（同义异名、上下位重叠机械无法识别——§11 判据的机械可实现性边界）、候选展开后的相关性判断（§10；02 §9.2）、规则内容质量初审（§14）。Human 终审＝创建、退役与规则内容质量（§15）。不得据本角色主张：规范效力可由任何来源字段、路径挂靠或对象存在本身证明。

## 9. 关系契约

不使用 `relations` 字段（类型来源声明不采用，02 §8.2 允许）。理由：方向规范之间不建立结构化对象关系。跨方向的规则约束（如「安全方向的规则适用于 API 方向的接口设计」）以「主规范承载 + 他处引用」实现——安全方向 Norm 正文承载完整安全规则，API 方向 Norm 正文中以自然语言引用安全方向的相关条目，不建立双向结构化关系。此设计禁止重复定义：同一规则只在一个方向的 Norm 中定义，它处只引用不重述。

方向规范与 ADR 的边界处理：当零散 ADR 决策沉淀为成体系的事实规范后，相关 ADR 应当按 22 号的退役路径处理（retired，`retirement_reason=absorbed`，并以 `absorbed-into` 关系指向承接它的 Norm，见 22 §9.2、§11）；ADR 的 change_log 中注明「规则已完整并入事实规范 `ldvh-base/norms/norm-<uid>.md`（方向：`<direction_key>`），退出约束，转为历史依据」。**该承接关系是单向的**：Norm 不建立指回 ADR 的结构化关系——ADR 可作为决策来源在正文自然语言中引用；「本方向承接了哪些 ADR」属于反向导航，由 Code/Web 从 ADR 侧 `absorbed-into` 边派生索引得到（02 §8.2 第 4 条），不在 Norm 对象上落字段、不构成第二权威。

## 10. 召回与消费

**义务召回原则（成体系规范的消费侧落地）**：相关方向的方案工作、代码实现、审计核对开始前，AI 必须召回并核对相关 active Norm——这是义务而非「需要时查阅」。方向规范未召回核对即开始工作，视同违背本规范。

| 消费点 | 时机 | 消费内容 |
|---|---|---|

## 11. 受控操作

- **创建**：AI 产出提案对象（含查重结论、direction_key 合法性与完整四段正文），Human 确认后经受控创建入口落盘。机械校验：字段闭集合法、direction_key 符合正则、同一 direction_key 无 active 冲突、title ≤ 40 字、正文四段固定 H2 全部存在且非空。创建后精确回读。
- **受控更新**：02 §10.5 受控更新；CAS 以完整文件为单位；每次恰好一条 change_log（注明修订内容与理由）。active 状态下可受控更新（方向规范是长效文档，需支持规则修订）。更新的 direction_key 不得改变（纯标题修正不改 direction_key，管辖范畴实质漂移则走退役+新建路径）。方向定位与适用范围段的实质变更（管辖范畴扩大或缩小）应视为新 Norm（新 direction_key 或旧 Norm 退役 + 新 Norm 建立），不走更新。
- **退役（retired）**：Human Gate；AI 先精确读取 F3，核对 retirement_reason 与证据；Code 检查闭集、字段与回读。理由闭集：`superseded`（被新 Norm 替代——新 Norm 已存在且可解析）、`outdated`（环境或前提变化使规范失效，无单一替代者）、`out-of-scope`（规范管辖范围整体不再属于本项目）。
- **删除**：不存在删除操作。retired Norm 随 `ldvh-base/norms/` 保留为历史档案。

**唯一性公式（反重复）**：

```
Count(direction_key = d ∧ status = "active") ≤ 1
```

同一 `direction_key` 在历史全集中可以有多份（1 份 active + N 份 retired）。退役的 Norm 保留为只读历史档案。若未来重启该方向，新 Norm 分配新的 `object_uid`，方向键可以复用。机械校验器在检查唯一性时，过滤条件是 `status === "active"`。

**唯一性的三层设计契约（写入前拒绝 / Git Gate 拦截 / 消费端 fail-closed）**：

本节定义唯一性在架构上由哪三层承载。三层现已全部具备，各层实际入口与验证方式回填如下（§14 原条件式条款据此闭合）：

1. **第一层：受控写入前**——受控写入入口在创建/更新前扫描 `ldvh-base/norms/` 全部现存 Norm 载体、解析 frontmatter，发现同 `direction_key` 的 active Norm 时拒绝写入（`ERR_DIRECTION_ALREADY_EXISTS`）。入口：`plugin/lib/norm-writer.js`；验证：`plugin/test/norm-writer.test.mjs`（同 key 拒绝、退役后复用放行）。
2. **第二层：提交前 Git Gate**——即使绕过受控写入工具（手工编辑或 shell 写入），提交时 Git Gate 遍历工作树与暂存区的 `ldvh-base/norms/norm-*.md`，提取 active Norm 的 `direction_key` 构建频次 Map，任何 key 出现次数 > 1 则拒绝提交。入口：`plugin/lib/commit-validation.js` 的 `checkNormDirectionUniqueness`（判定 `facts/norm_direction_collision`；载体不可解析时以 `facts/norm_carrier_unparseable` fail-closed）；验证：`plugin/test/commit-validation.test.mjs`（含 `\r\n` 换行回归）。
3. **第三层：消费/读取诊断**——主控通过 LDVH CLI 读取或 Web 投影 Norm 时，若发现 active 方向冲突，两份冲突规范均不得作为当前生效规则返回（fail-closed，对齐 01 §9.1「同一编号映射到多个候选时，全部受影响候选均不得进入成员读取」），报告 `gaps: [{ reason: "direction_collision", direction_key: "..." }]`。入口：`plugin/lib/norm-tools.js` 的 `ldvh_norm_list`（扣留全部冲突项并回报 `direction_collision`）；验证：`plugin/test/norm-writer.test.mjs`。

**反重复版的「一方向一规范」判据**：

- **反重复**：同一方向至多由一份 active 规范承载——由上述唯一性公式与三层设计契约机械承载；§6.2 查重与 Human Gate 承担其中机械不可实现的部分（同义异名、上下位重叠的语义判断）；
- **允许合并**：一份规范可聚合多个强相关方向（如 LDVH 元规范 09=Code 含代码+测试、10=Web 含呈现+交互）——合并判据见 §6.1「三条都高度重合才考虑合并」；
- **方向内子主题可拆文件但不得升格新方向**：方向规范正文中可按 H3 划分子主题；若需拆分为独立文件，该文件不建立新 Norm 对象、不分配新 direction_key，而是作为正文扩展或附件承载（02 §8.2）；
- **跨方向约束以主规范承载 + 他处引用实现，禁止重复定义**：同一规则只在一个方向的 Norm 中定义，它处只引用不重述（参见 §9）。

**判据的机械可实现性边界（条件式）**：本判据可机械化者**仅限于字面 `direction_key` 的互斥**。以下情形**机械层无法识别**，须由 §6.2 创建前查重（AI 语义比对）与 Human Gate 承担，**不得声称已由机械校验覆盖**：同义异名（如 `web` 与 `frontend` 指向同一方向）、上下位重叠（如 `backend` 与 `api`）。因此「一方向一规范」是**字面层可机械、语义层不可机械**的判据，**任何情形下均不得表述为已获完整机械保障**。

## 12. 授权附件

本节承担 27 号的授权附件结构角色。本规范授权以下附件，其内容由本文 §5（类型定位与价值）、§6.1（对象边界与消歧判据）、§11（受控操作与唯一性三层设计契约）已经定义并授权：

- `norm-direction-catalog`：Norm 可承载的**方向参考清单**（五层共 44 个方向）、各方向的必需性与 LDVH 元规范覆盖状态，以及清单的使用说明。位于 `specs/attachments/27.Att.01-Norm方向清单.md`。

**附件内容边界**：该附件只承载方向参考清单及其必要使用说明，不建立新的职责、义务、授权、Human Gate、必停情形或正文规则。附件与本文冲突时以本文为准；附件完整读取必须同时保留本文的授权上下文。

**方向参考清单的效力**：清单是**方向识别的参考**，不是强制枚举——项目按自身实际需要选择方向，不强制为清单中每个列出的方向建立 Norm；**超出清单建立 Norm 时，该方向必须给出足够理由**，说明它为何不能归入清单中任一既列方向（判据见 §6.1 的主语／变更频率／责任面三条），并经受控创建的查重与 Human Gate 核对。清单不穷举所有可能方向，也不证明任何方向已有规范承载或某份 Norm 内容正确。

## 13. 类型特有验证与类型退出

### 13.1 类型特有验证

- **查重结果记录**：创建提案必含查重结论（同 direction_key active 已存在 → 不新建，走更新或替代）；
- **direction_key 合法性**：符合 `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$` 正则（机械校验）。该正则的**唯一权威来源**是 [01.Att.02-规范身份字段表](attachments/01.Att.02-规范身份字段表.md) §2「共同值格式」的**职责标识符**闭集 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`（本文的全串匹配语义等价于 `plugin/lib/spec-registry.js` 的 `ID_PATTERN` 全串校验；此处不复制定义，只回指来源）。类型专属字段采用既有标识符格式，不建立第二套命名规则；
- **direction_key 唯一性**：active 集合内无冲突（由 §11 三层机械承载——写入前拒绝 / Git Gate 拦截 / 消费端 fail-closed）；
- **正文骨架完整**：四段固定 H2 全部存在且各段非空（机械校验——H2 标题与段落存在性）；
- **终态完整性**：retired 必有 `retirement_reason` + `retired_at`；superseded 时须确认替代 Norm 已存在可解析；
- **状态-字段不变量**：active 不得带终态字段（`retirement_reason`/`retired_at`）；非 superseded 的 retired 不得带替代关系。

### 13.2 勘误级更新

正文错别字、引用路径修正、表述澄清（不改变方向定位、核心规则语义与适用范围判断）走 02 §10.5 受控更新，change_log 留痕并注明勘误性质。判断标准：`direction_key` 不变、方向定位与适用范围段的管辖边界不变——若管辖边界实质变化，走退役+新建路径，不伪装为勘误。

### 13.3 存量对象迁移

无 v5 存量。管辖项目的现有方向规范（如散落文档中的代码规范、安全策略）若要成为 Norm 事实对象，须按本文创建路径新建，不自动迁移。

### 13.4 类型退出

若 Human 决定取消 Norm 类型，须按 02 §11 处理：处理仍适用方向规范的转移承接（转为普通文档或其他事实类型）、入向/出向关系与稳定引用，登记变化（01 §8.1）与受影响引用同步，走受控提交。退出属 00 §3.2 根决定。

## 14. 验证与证据边界

| 验证对象 | 成立条件 | 验证入口 | 未满足时的处理 |
|---|---|---|---|
| 身份与方向键 | 创建、更新或精确读取时核对（依据当前载体与本文 §8）：YAML 可解析；direction_key 符合正则；fact_type_key = "norm"；title ≤ 40 字。仅证明当次载体身份与 direction_key 合法性 | 机械解析与正则校验 | 拒绝创建/更新；修复后重走 |
| 方向键唯一性 | 创建时核对（依据全量扫描 ldvh-base/norms/ 全部 Norm 载体）：同一 direction_key 在 active 集合中至多一个。仅证明当次扫描的 active 集合范围 | 机械拦截由 §11 第一层承担（`norm-writer.js`）；§6.2 查重补充语义比对 | 拒绝创建（ERR_DIRECTION_ALREADY_EXISTS）；要求走更新或替代路径 |
| 正文骨架 | 创建、更新时核对（依据当前载体正文结构）：四段固定 H2 全部存在且各段非空。仅证明当次载体结构完整性 | 机械（H2 标题与段落存在性校验） | 拒绝创建/更新；补齐骨架后重走 |
| 方向定位首句 | 由 `ldvh_norm_list` 投影时核对（依据「方向定位与适用范围」段首句）：以 `**管什么**：` 起首、≤60 字、自足、不含授权措辞。仅证明首句可否机械导出摘录，不证明定位语义准确（后者属「规则内容质量」行） | 机械（`directionPositioningOf`）+ list 的 「摘录可用性标注」显式报告 | **不阻断**：不合契约时不外发摘录、标 unavailable 并指引 `ldvh_norm_read` 读正文；是否启用创建/更新拒绝属独立 Human Gate 决定 |
| 查重已执行 | 创建时核对（依据提案记录）：创建提案含查重结论（direction_key + title 语义比对）。仅证明当次查重范围 | AI 语义审核 | 补查重后重走创建 |
| 终态完整性 | 终态流转时核对（依据对象全文与目标读取结果）：retirement_reason/retired_at 齐备；superseded 时替代 Norm 可解析。仅证明当次终态机械范围 | 机械（字段+关系校验） | 拒绝流转；补齐后重走 |
| 规则内容质量 | 创建与更新时核对（依据Human 确认记录）：规则可执行、边界清晰、验证可操作。仅证明当次规则内容质量 | AI 语义审核 + Human 终审 | 拒绝或退回修订 |
| 跨方向约束一致性 | 更新时核对（依据引用目标读取结果）：引用他方向规则时指向的 Norm 存在且 active。仅证明当次引用的可解析范围 | AI 语义审核 | 保留未解析引用为 gap；不静默忽略 |

机械结果与语义判断互不替代。本章不能单独证明规则正确、适用、已被遵守——这些由消费点的真实使用核对；未实现与不可用范围保留为 gaps。**机械承载未覆盖时不得声称已受机械保障**，该要求按 `specification-model-foundation` §14.1 单点承载，本节不复述。

## 15. Human Gate

本文不新增 00 之外的 Human Gate。领域增量事项（00 §3.2 在 Norm 领域的具体化）：

1. Norm 的创建（新方向规范的确立——含 direction_key 新增确认）；
2. Norm 的终态决定（retired——方向不再需要或被替代）；
3. 方向清单的增减或重新分层（清单是本规范的一部分，修改属规范修改）；
4. Norm 类型本身的取消或合并。

### 15.1 决定边界

Human 决定只证明决定及其作用范围，不替代查重判断、direction_key 校验、正文骨架校验或终态机械校验。

### 15.2 确认的承载与呈报

**承载范围（条件式）**：第 1 项（创建）与第 2 项（终态决定）的确认，须由宿主询问入口（`10 §5.5`：`ctx.userQuestions.ask`）取得——无答题器、询问失败或未作选择时一律拒绝并如实报告。**第 3 项（方向清单的增减或重新分层）与第 4 项（Norm 类型本身的取消或合并）不为它们声明承载**：前者属对本文自身的修改、走规范修改程序，后者当前没有受控实现入口。该两项一旦提上日程，须先建立入口再谈承载，不得据本节主张其已获机械保障。

**呈报内容**：取得确认时须向 Human 呈报——创建：查重结论、`title`、`direction_key`、以及**正文「方向定位与适用范围」段的要点**；终态决定：拟转状态、`retirement_reason`，以及本次流转的 `change_log.summary` 据实说明。

**为什么创建侧不写 `scope`**：本类型没有 `scope` 字段（§8 闭集），且 §7 载体内聚明定规则整体住正文、frontmatter 只承载机器索引。ADR 的 `scope` 字段在 Norm 上的对应物是正文首段，故此处按本类型写；照抄 `22 §16.2` 的字段清单会造出一条本类型兑现不了的呈报要求。**缺少上述任一项时不得提请**——查重结论未记录即硬拒，与 `22 §14.1` 同一处置（语义查重不可机械判定，「有没有记录」可判定）。

**呈报内容的承载位置**（与 `22 §16.2` 同一口径，Human 2026-11-13 决定）：上列内容须由主控在**调用受控写入之前写进对话正文**，不得依赖提请弹窗携带——「所有经过 ldvh 业务的提请，都要求内容简洁，title 字数在 200 字内，没有其它细节信息」。故弹窗只承担「这是什么动作、点哪个键」。

**保证边界（如实声明）**：本项只证明「**经受控写入入口**时，写入前取得过一次明确的肯定答复、未取得即零写入」；**不证明**答复者理解了呈报内容、不证明方向取舍的质量，也不产生可事后核对「谁确认过」的凭据——答复由宿主记录在会话侧，本类型不新增确认凭据字段。**手工编辑载体绕开受控入口的路径不在本项承载范围内**：Git Gate 只校验 `direction_key` 唯一性、不校验确认来源，该面由 `§16` 必停情形与主控自律承担，本节不主张已覆盖。**工具侧呈报不承载规则内容**——本类型的核心规则住在正文「核心规则体系」等段，机械呈报只承载上面所列的判断材料；因此「Human 是否看到了规则本身」既不落机械层、也不进任何凭据，属主控在对话正文中的无凭据义务（`00 §4.6`）。**呈报是否真的在对话正文中给出，机械层同样判不了**，该缺口不得以「弹窗简化」为理由隐去。**在宿主询问入口对本类型实际具备之前，不得主张本项已获机械保障**，须按 `00 §4.6` 如实披露未兑现范围；该前提是否成立按 `01 §7.2` 由读取时的观察取得，本节不陈述其当前状态。

**已知代价**：承载须按工具声明，故同一工具的 `active → active` 勘误级与补充级更新同样失去执行期的墙钟上限——那些动作不提问，但与提问的动作共用一个描述符。二阶代价一并登记：不提问的更新路径也失去墙钟上限，若写入侧因文件系统等异常卡住，该调用将无限期挂起，唯一释放是调用方的取消信号。

## 16. 必停情形

本文不新增根停止类型。领域触发与最小影响范围：

1. 创建时发现同 direction_key 的 active Norm 已存在（方向键唯一性违例）——未完成冲突解决前不创建；
2. direction_key 格式不合法或为空；
3. 正文四段固定 H2 缺失或存在空段（骨架完整性违例）；
4. 准备在 active 状态下改写 direction_key 或方向定位与适用范围段的管辖边界（应走退役+新建路径）；
5. 准备退役但 retirement_reason/retired_at 缺失（终态完整性违例）；
6. AI 未经 Human 确认直接创建或退役（授权缺失）；
7. 遵守预检消费时发现方向冲突（两份 active Norm 共存——消费端 fail-closed）。

暂停期间只允许不越过停止边界的证据补取、引用修复、授权补走与条件核实。恢复须与触发原因逐项对应；同一停止条件恢复后再次触发的，按 00 §4.7 的恢复与再次触发进入 Human Gate。

## 17. 反过度设计红线

1. 不为每个小差异或低频场景单独建 Norm——方向粒度按 §6.1 判据判断，不在清单条目上机械对应；
2. 不把 44 个清单条目强制展开为 44 份 Norm——项目按需选择，不为「全量覆盖」制造空壳规范；
3. 不在 Norm 之间建立 `relations` 结构化关系——跨方向约束以正文引用实现，不建第二关系图；
4. 不设 `norm_source` 或类似的「指向元规范」字段——事实规范的效力来自规范源层级与 active 状态，不靠路径挂靠（Human 撤回该设计，理由见 00 §3.2）；
5. 不为「成体系」的语义完备性设立无法机械判定的强制质量门槛——4 段骨架是弱机械门槛（验形），语义质量由 AI 审核与 Human Gate 保障（验质）；
6. 不把 direction_key 扩展为层级键或树状结构——kebab-case 是扁平标识，方向层级以正文定位说明，不以字段编码；
7. 不为 Norm 建缓存/索引/投影副本——消费点经 LDVH CLI 或 Web 按需读取，不建第二权威。
