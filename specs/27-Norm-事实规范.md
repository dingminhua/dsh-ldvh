# Norm-事实规范

## 1. 价值判断

Norm 解决管辖项目的成体系方向规范缺少事实对象承载的问题：「代码规范」「安全策略」「API 契约」这些方向的规则若散落在对话、散落文档或多份重叠文件中，每次方案工作都无法定位同一份权威依据，重复制定规则、无意间违背既有约束、或找不到某方向的完整约束集——与 00 §1 痛点 4「历史经验与教训，无法积累」同构。Norm 以事实对象承载成体系方向规范：一个 `direction_key` 标识一个方向，一份 active Norm 承载该方向的完整规则体系，为遵守预检、讨论装配、审计核对与 Web 呈现提供可回指的稳定来源。普通文件不能无损承载：无受控写入、无 active/retired 状态闭集（「这份规范还在生效吗」无从机械判定）、无方向键排他约束（「同方向是不是只有一份」无从核查）、无正文骨架结构保障（「是否成体系」无弱机械门槛）。ADR 是点状决定（单条、临时），Norm 是面状体系（长效、系统化）；Spark 是悬置层（方向未定），Norm 是方向已定的成体系承载。

主要支撑 V3 边界识别（遵守预检以 direction_key 为索引——违背即拦截）、V4 稳定推进（受控更新使规范可在 active 状态下修订而保持权威）、V5 据实判断（规则引用可回指当前 active Norm 的具体条目）与 V8 持续积累（方向规范的 change_log 是规则演进的可回溯脉络）；HV3 入档闭环节点可验（创建与退役可回读）与 HV4 积累效用直观可见（方向清单与活跃规范是项目规则体系的全貌投影）。

Norm 对象存在、处于 active 或正文包含规则条目，均不能单独证明规则正确、适用、已被遵守或方向覆盖完整——规则的价值须在后续遵守预检、讨论装配与审计核对的真实消费中核对。Norm 与元规范层级不同：Norm 是项目侧事实规范，元规范是 LDVH 自身机制规范；事实规范不得放松元规范（00 §3.6），也不自授效力——效力来自规范源层级与 active 状态，不来自任何路径挂靠或来源字段。

## 2. 规范依据

本文直接依据（结构父规范 `fact-model-foundation` 的 03 全文自动适用——类型准入、公共身份字段、载体与权威位置、公共关系形状、召回分层、受控读写、生命周期与类型规范共同结构，不重复列出）：

1. `ldvh-root`：00 §3.3 规范源与事实源两级承载及元规范/事实规范层级定义、§3.6 下位承接与不构成第二套权威、§4.2 Human Gate 根决定清单、§7 防自欺与交还。
2. `source-of-truth-traceability`：06 §5 事实源与溯源、§6 受控提交契约。
3. `specification-model-foundation`：01 §6 身份块契约、§8 编号登记、§10.1 关系语义与 L0–L4 读取层级。

本文不依赖外部语法或行业标准定义 Norm 语义。既有设计文档（`docs/design-one-direction-one-norm.md`、`docs/survey-software-directions.md`）与边界调研（`docs/research-adr-to-norm-boundary.md`）只作设计输入，不取得规范效力。发生冲突或权威关系无法确认时，按 00 §7.2 暂停受影响范围并完成对齐。

## 3. 职责边界

### 3.1 本文负责

1. Norm 类型的目的、对象边界与「成体系」的定义判据；
2. Norm 的身份与载体（多例、平铺单文件、`ldvh-base/norms/norm-<uid>.md`）；
3. Norm 的字段契约（frontmatter 闭集、正文四段固定 H2 骨架、direction_key 专属字段）；
4. Norm 的状态闭集（active/retired）与终态处理；
5. Norm 的方向清单与反重复机制（唯一性公式、三道防线）；
6. Norm 的关系契约（不使用 relations 字段）；
7. Norm 的召回与消费点（遵守预检、讨论装配、审计核对、Web 呈现）；
8. Norm 的受控操作（创建、受控更新、退役）。

### 3.2 本文不负责

1. 讨论收敛的扩散、装配与分流流程（12 号承载，本文只定义 Norm 作为装配依据来源的消费语义）；
2. 遵守预检的完整判定逻辑（02 §13 承载，本文只定义消费语义接口）；
3. 受控提交契约（06 承载）；
4. Human 作出或废除方向规范的过程（00 §4 承载——Norm 记录已确立的方向规范，不产生规范制定过程本身）；
5. Web 呈现的视觉与交互细节（10 号承载）；
6. ADR 终态流转的具体机制（22 号承载——ADR 被事实规范承接后的退役由 22 号的 retirement_reason 闭集扩展或 change_log 注记处理，本类型不定义 ADR 的退役细节）。

### 3.3 相邻规范分工与唯一权威

03 是公共字段与受控读写契约的唯一权威；06 是事实源与受控提交的唯一权威；22 是 ADR 类型语义的唯一权威；01 是元规范结构与身份契约的唯一权威。本文只定义 Norm 类型自身的边界、字段、方向清单、状态、关系与消费点，不复制相邻规范的规则。

## 4. 适用范围

### 4.1 适用对象

1. 管辖项目中的多例 Norm 对象（`ldvh-base/norms/norm-*.md`）；
2. Norm 的方向键、状态、正文骨架与规则内容。

### 4.2 适用场景

本规范用于 Norm 的创建（方向确立后起草成体系规范）、受控更新（active 状态下的规则修订）、退役（方向不再需要或被替代）与消费（遵守预检、讨论装配、审计核对、Web 项目规范看板呈现）。

### 4.3 明确排除与证明边界

明确排除：元规范（`specs/` 下的 LDVH 自身机制规范，不适用本类型）；单条决定（走 ADR）；执行计划与已批准工作（走 WorkCase）；项目目标（走 Goal）；外部证据调查（走 Research）；教训与规避（走 Pitfall）；改进账本（走 Friction）；对话中的临时约定（重要性不足以对象化的留在会话记录）；方向内的子主题拆分文件（不升格为新方向，不建立新 Norm 对象）。Norm 对象存在或状态为 active，不能单独证明规则正确、适用、已被遵守或方向覆盖完整。

## 5. 类型定位与价值

Norm 是项目侧事实规范层的系统化类型：承载管辖项目中一个完整工程方向的成体系规则体系，供前瞻约束与回溯审查。它是事实规范的唯一事实类型定义——事实规范是一种事实对象，由本类型规范定义其对象边界、字段、状态与生命周期。

**「成体系」的定义判据（Human 定义的类型准入核心）**：

一个方向的规则是否构成「成体系」的规范，满足以下三条判据中的至少两条：

1. **多条可独立执行的规则**：不是单条决定或建议，而是形成规则集合——多个条目各自可被检查遵从性；
2. **明确的管辖边界**：有清晰的「管什么、不管什么」定位，不与其它方向的边界严重重叠；
3. **持续消费价值**：在后续方案工作、代码实现、审计核对中会被反复引用，不是一次性结论。

按 03 §5.2 准入六问：跨行动保留——方向规范必须跨会话稳定，否则每次方案工作重新制定规则；独立身份与状态——有 active/retired 与方向键排他约束，需要独立生命周期；普通文件不能无损承载——无受控写入、无状态闭集、无方向键排他校验、无正文骨架；消费价值服务 AI（遵守预检/装配）与 Human（Web 规范看板）双轨；维护成本——中等频率类型（每方向通常数月修订一次），净值为正；类型定义来源——本规范。

## 6. 对象边界

### 6.1 什么构成一个对象

一个 Norm 对象 = **一个完整工程方向的成体系规范体系**：方向键（direction_key）+ 方向定位与适用范围（正文）+ 核心规则体系（正文）+ 约束与反模式（正文）+ 验证与遵从性检查（正文）。判据：方向可独立召回、规则可独立检查遵从性、方向定位有清晰边界、正文具有成体系的规则内容。

**「方向」的判据**：一个方向是管辖项目中一个可独立成规范的关注面。两个候选方向是否为「同一方向」，满足以下任一条则应分设为不同方向：

1. **主语不同**——管的是「机制/能力」还是「职责/判定」？是「工程动作」还是「治理结论」？主语不同则方向不同；
2. **变更频率不同**——一个话题常随业务变、另一个随技术变，应分开；
3. **责任面不同**——违反它的后果由谁承担、向谁负责？责任面不同则方向不同。

三条都高度重合才考虑合并（参见 §11 方向清单的「可合并」说明）。

### 6.2 查重

创建前必须查重：对照既有 active Norm 的 `direction_key` 精确匹配（机械）与 title/正文定位语义比对（AI 语义判断）。同方向已存在 active Norm 时，不新建——走受控更新路径修订既有规范；方向实质变化时，退役旧 Norm 并建立新 Norm（新 direction_key），不改写既有 Norm 的方向语义。查重结论必须记录在创建提案中。

### 6.3 明确不属于本类型

单条决定或取舍记录（走 ADR——「临时的、单条的决定」）；执行计划与已批准工作（走 WorkCase）；项目目标与子目标（走 Goal）；外部证据调查（走 Research）；教训与规避经验（走 Pitfall）；改进账本（走 Friction）；对话中的临时约定；方向内子主题的拆分文件（不升格新方向，不建立新 Norm）；元规范（`specs/` 下的 LDVH 自身机制规范，不适用本类型）；已被事实规范完整承载的 ADR 决策（规则由 Norm 承载，ADR 可作为决策来源被引用但不再承担约束——22 §6.3 第 9 项）。

## 7. 身份与载体

| 项 | 定案 |
|---|---|
| `fact_type_key` | `norm`（类型短名，03 §6.1 值域） |
| 载体 | 平铺单文件：YAML frontmatter（机器权威）+ markdown 正文；`ldvh-base/norms/norm-<uid>.md` |
| 权威位置 | `ldvh-base/norms/`；目录基数校验，文件名编码 UID |
| 公共字段 | `object_uid`（UUIDv4，Code 生成）、`fact_type_key`（`norm`）、`title`、`created_at`（Code 填写）、`status`（active/retired）、`change_log`（Code 托管流水） |
| 不采用字段 | `urls`（规则内容住正文，不依赖外部 HTTP 来源；03 §6.1「字段缺省遵循类型来源」）、`relations`（Norm 之间不建立结构化关系，跨方向约束以主规范承载 + 他处引用实现，参见 §9） |

创建与变更权：创建必须经 Human 决定（方向规范的确立是项目规则架构决策，属 00 §4.2 级根决定事项）；active 状态下的受控更新走 03 §9.5（change_log 留痕）；退役必须经 Human 决定（方向不再需要或被替代是根决定）。AI 只能提议修订与创建提案，无直接写入路径。

## 8. 字段契约

frontmatter 闭集（全部必填，除标注外创建时一次落定）：

| 字段 | 类型 | 必填性 | 语义 | 约束 |
|---|---|---|---|---|
| `fact_type_key` | string | 必填 | `norm` | 唯一合法值（03 §6.1 值域） |
| `object_uid` | UUIDv4 | 必填 | Code 生成 | 创建时落定，永不改变 |
| `title` | string | 必填 | 方向规范短标题 | ≤ 40 字；供候选定位与 Human 扫读 |
| `status` | string | 必填 | `active` / `retired` | 初态必为 `active` |
| `direction_key` | string | 必填 | 方向键，标识本规范管辖的方向 | 小写 kebab-case：`^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`；同一 direction_key 至多一个 active Norm（§11 唯一性公式） |
| `created_at` | RFC3339 | 必填 | Code 受控创建时填写 | AI 不得填写 |
| `retirement_reason` | string | 条件 | 终态原因 | 闭集：`superseded` / `outdated` / `out-of-scope`；retired 必填、active 禁现 |
| `retired_at` | RFC3339 | 条件 | Code 填写 | retired 必填、active 禁现 |
| `change_log` | array | 条件 | 变更流水 | 首修后必有；每次恰好一条 |

`direction_key` 是本类型的专属字段（符合 03 §6.1「20–24 分别登记专属字段增量」的既有惯例，对照 22 的 `decision`、24 的 `research_question`）。它是机器可验证的方向标识，与 `object_uid`（全局唯一标识）语义完全不同：`direction_key` 定义「这份规范管哪个方向」和「唯一性约束的作用域」，`object_uid` 定义「这份对象是谁」。

正文四段固定 H2 骨架（创建时必须全部存在且各段非空）：

```markdown
## 方向定位与适用范围  ← 本规范管什么、不管什么、适用于哪些场景（必填）
## 核心规则体系        ← 该方向的核心规则条目，可包含 H3 子节（必填）
## 约束与反模式        ← 明确禁止项与违规后果（必填）
## 验证与遵从性检查    ← 定义如何检查是否遵守本规范（必填）
```

`direction_key` 与 `title` 的区别：`direction_key` 是机器标识（唯一性校验、索引、跨规范检索），`title` 是人类可读短标题（扫读定位、Web 呈现）。`direction_key` 不随标题修改而改变（纯标题修正不改 direction_key，参见 §13.2 勘误边界）。

字段间不变量：`direction_key` 格式符合正则（机械校验）；同一 `direction_key` 在 active 集合中至多一个（§11 唯一性公式，三道防线保障）；`retirement_reason`/`retired_at` 随 `status` 约束（§9）；正文四段固定 H2 全部存在且各段非空（机械校验）；未知字段不进入 canonical 对象。

## 9. 关系契约

不使用 `relations` 字段（类型来源声明不采用，03 §7.2 允许）。理由：方向规范之间不建立结构化对象关系。跨方向的规则约束（如「安全方向的规则适用于 API 方向的接口设计」）以「主规范承载 + 他处引用」实现——安全方向 Norm 正文承载完整安全规则，API 方向 Norm 正文中以自然语言引用安全方向的相关条目，不建立双向结构化关系。此设计禁止重复定义：同一规则只在一个方向的 Norm 中定义，它处只引用不重述。

方向规范与 ADR 的边界处理：当零散 ADR 决策沉淀为成体系的事实规范后，相关 ADR 应当按 22 号的退役路径处理（retired，retirement_reason 由 22 号闭集定义）；ADR 的 change_log 中注明「规则已完整并入事实规范 `ldvh-base/norms/norm-<uid>.md`（方向：`<direction_key>`），退出约束，转为历史依据」。Norm 不建立指回 ADR 的结构化关系——ADR 可作为决策来源在正文自然语言中引用。

## 10. 召回与消费

**义务召回原则（成体系规范的消费侧落地）**：相关方向的方案工作、代码实现、审计核对开始前，AI 必须召回并核对相关 active Norm——这是义务而非「需要时查阅」。方向规范未召回核对即开始工作，视同违背本规范。

| 消费点 | 时机 | 消费内容 |
|---|---|---|
| 遵守预检（义务） | 行动涉及某方向既有规则域时（02 §13） | `direction_key` + 正文「约束与反模式」+「验证与遵从性检查」——识别当前行动是否触及/违背方向规范 |
| 讨论系统依据装配 | 每次扩散前（12 §7.1） | 相关方向 active Norm 的「核心规则体系」——方案违背即淘汰，淘汰须记录违背的方向与条目 |
| 审计核对 | 事后追溯或独立复核时 | 方向 Norm 全文——核对实际工作与规则的一致性 |
| Web 项目规范看板 | 蓝图渲染与项目状态投影（10 号） | active Norm 列表与方向清单投影 |

召回分层（03 §8）：F1 枚举 active Norm 计数（direction_key + title + status）；F2 按 direction_key、title、命中词的候选卡；F3/F4 按需展开。默认候选只含 active——当前生效规范就是 active 集本身。retired 不进入普通候选，只在精确引用或历史追溯时展开。AI 展开候选后必须重新比较当前主题与方向状态——Norm 被召回不等于规则全部适用，遵守预检时的相关性判断是 AI 语义工作（03 §8.2）。

## 11. 受控操作

- **创建**：AI 产出提案对象（含查重结论、direction_key 合法性与完整四段正文），Human 确认后经受控创建入口落盘。机械校验：字段闭集合法、direction_key 符合正则、同一 direction_key 无 active 冲突、title ≤ 40 字、正文四段固定 H2 全部存在且非空。创建后精确回读。
- **受控更新**：03 §9.5 受控更新；CAS 以完整文件为单位；每次恰好一条 change_log（注明修订内容与理由）。active 状态下可受控更新（方向规范是长效文档，需支持规则修订）。更新的 direction_key 不得改变（纯标题修正不改 direction_key，管辖范畴实质漂移则走退役+新建路径）。方向定位与适用范围段的实质变更（管辖范畴扩大或缩小）应视为新 Norm（新 direction_key 或旧 Norm 退役 + 新 Norm 建立），不走更新。
- **退役（retired）**：Human Gate；AI 先精确读取 F3，核对 retirement_reason 与证据；Code 检查闭集、字段与回读。理由闭集：`superseded`（被新 Norm 替代——新 Norm 已存在且可解析）、`outdated`（环境或前提变化使规范失效，无单一替代者）、`out-of-scope`（规范管辖范围整体不再属于本项目）。
- **删除**：不存在删除操作。retired Norm 随 `ldvh-base/norms/` 保留为历史档案。

**唯一性公式（反重复）**：

```
Count(direction_key = d ∧ status = "active") ≤ 1
```

同一 `direction_key` 在历史全集中可以有多份（1 份 active + N 份 retired）。退役的 Norm 保留为只读历史档案。若未来重启该方向，新 Norm 分配新的 `object_uid`，方向键可以复用。机械校验器在检查唯一性时，过滤条件是 `status === "active"`。

**三道防线（写入前拒绝 / Git Gate 拦截 / 消费端 fail-closed）**：

1. **第一道：受控写入前**——受控写入入口在创建/更新前扫描 `ldvh-base/norms/` 全部现存 Norm 载体，解析 frontmatter；发现同 direction_key 的 active Norm 时直接拒绝写入（`ERR_DIRECTION_ALREADY_EXISTS`）。
2. **第二道：提交前 Git Gate**——即使绕过受控写入工具（手工编辑或 shell 写入），提交时 Git Gate 遍历暂存区与工作树的 `ldvh-base/norms/norm-*.md`，断言每个文件 direction_key 合法、提取所有 active Norm 的 direction_key 构建频次 Map，任何 key 出现次数 > 1 则拒绝提交。
3. **第三道：消费/读取诊断**——主控通过 Helper 读取或 Web 投影 Norm 时，若发现 active 方向冲突，两份冲突规范均不得作为当前生效规则返回（fail-closed，对齐 01 §9.1「同一编号映射到多个候选时，全部受影响候选均不得进入成员读取」），报告 `gaps: [{ reason: "direction_collision", direction_key: "..." }]`。

**反重复版的「一方向一规范」判据**：

- **反重复**：同一方向至多由一份规范承载——上述唯一性公式与三道防线保障；
- **允许合并**：一份规范可聚合多个强相关方向（如 LDVH 元规范 09=Code 含代码+测试、10=Web 含呈现+交互）——合并判据见 §6.1「三条都高度重合才考虑合并」；
- **方向内子主题可拆文件但不得升格新方向**：方向规范正文中可按 H3 划分子主题；若需拆分为独立文件，该文件不建立新 Norm 对象、不分配新 direction_key，而是作为正文扩展或附件承载（03 §7.2）；
- **跨方向约束以主规范承载 + 他处引用实现，禁止重复定义**：同一规则只在一个方向的 Norm 中定义，它处只引用不重述（参见 §9）。

### 12.6 方向清单的使用说明

1. **量级估计**：本清单罗列约 42 个方向。典型受管辖项目实际需要的 Norm 份数约 15–20 份（必需方向独立成规范 + 强相关方向合并成规范）。
2. **合并判据**：§6.1 的三条消歧判据（主语、变更频率、责任面）三条都高度重合时可合并为一份 Norm。典型合并：E1+E6（代码风格+测试）、E7+E8+E17（构建+发布+部署）、P2+P4（交互+信息架构）、G5+G8（文档+版本策略）。
3. **必须分开的典型情形**：E11（安全）与 G4（隐私）法规边界独立；G1（审计）与 G2（合规）审计是能力、合规是判定；E6（测试）与 Q1（验收）机制与结论不可混淆。
4. **同义异名防范**：`direction_key` 的精确排他（§11 三道防线）在机械层防止同名重复；语义重叠的防范依赖 AI 创建前查重与 Human Gate 最终裁定。

## 13. 类型特有验证与类型退出

### 13.1 类型特有验证

- **查重结果记录**：创建提案必含查重结论（同 direction_key active 已存在 → 不新建，走更新或替代）；
- **direction_key 合法性**：符合 `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$` 正则（机械校验）；
- **direction_key 唯一性**：active 集合内无冲突（三道防线中的第一道保障）；
- **正文骨架完整**：四段固定 H2 全部存在且各段非空（机械校验——H2 标题与段落存在性）；
- **终态完整性**：retired 必有 `retirement_reason` + `retired_at`；superseded 时须确认替代 Norm 已存在可解析；
- **状态-字段不变量**：active 不得带终态字段（`retirement_reason`/`retired_at`）；非 superseded 的 retired 不得带替代关系。

### 13.2 勘误级更新

正文错别字、引用路径修正、表述澄清（不改变方向定位、核心规则语义与适用范围判断）走 03 §9.5 受控更新，change_log 留痕并注明勘误性质。判断标准：`direction_key` 不变、方向定位与适用范围段的管辖边界不变——若管辖边界实质变化，走退役+新建路径，不伪装为勘误。

### 13.3 存量对象迁移

无 v5 存量。管辖项目的现有方向规范（如散落文档中的代码规范、安全策略）若要成为 Norm 事实对象，须按本文创建路径新建，不自动迁移。

### 13.4 类型退出

若 Human 决定取消 Norm 类型，须按 03 §10 处理：处理仍适用方向规范的转移承接（转为普通文档或其他事实类型）、入向/出向关系与稳定引用，登记变化（01 §8.2）与受影响引用同步，走受控提交。退出属 00 §4.2 根决定。

## 14. 验证与证据边界

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 身份与方向键 | 创建、更新或精确读取时 | YAML 可解析；direction_key 符合正则；fact_type_key = "norm"；title ≤ 40 字 | 当前载体与本文 §8 | 机械解析与正则校验 | 当次载体身份与 direction_key 合法性 | 拒绝创建/更新；修复后重走 |
| 方向键唯一性 | 创建时 | 同一 direction_key 在 active 集合中至多一个 | 全量扫描 ldvh-base/norms/ 全部 Norm 载体 | 写入前扫描（第一道防线） | 当次扫描的 active 集合范围 | 拒绝创建（ERR_DIRECTION_ALREADY_EXISTS）；要求走更新或替代路径 |
| 正文骨架 | 创建、更新时 | 四段固定 H2 全部存在且各段非空 | 当前载体正文结构 | 机械（H2 标题与段落存在性校验） | 当次载体结构完整性 | 拒绝创建/更新；补齐骨架后重走 |
| 查重已执行 | 创建时 | 创建提案含查重结论（direction_key + title 语义比对） | 提案记录 | AI 语义审核 | 当次查重范围 | 补查重后重走创建 |
| 终态完整性 | 终态流转时 | retirement_reason/retired_at 齐备；superseded 时替代 Norm 可解析 | 对象全文与目标读取结果 | 机械（字段+关系校验） | 当次终态机械范围 | 拒绝流转；补齐后重走 |
| 规则内容质量 | 创建与更新时 | 规则可执行、边界清晰、验证可操作 | Human 确认记录 | AI 语义审核 + Human 终审 | 当次规则内容质量 | 拒绝或退回修订 |
| 跨方向约束一致性 | 更新时 | 引用他方向规则时指向的 Norm 存在且 active | 引用目标读取结果 | AI 语义审核 | 当次引用的可解析范围 | 保留未解析引用为 gap；不静默忽略 |

机械结果与语义判断互不替代。本章不能单独证明规则正确、适用、已被遵守——这些由消费点的真实使用核对；未实现与不可用范围保留为 gaps。

## 15. Human Gate

本文不新增 00 之外的 Human Gate。领域增量事项（00 §4.2 在 Norm 领域的具体化）：

1. Norm 的创建（新方向规范的确立——含 direction_key 新增确认）；
2. Norm 的终态决定（retired——方向不再需要或被替代）；
3. 方向清单的增减或重新分层（清单是本规范的一部分，修改属规范修改）；
4. Norm 类型本身的取消或合并。

### 15.1 决定边界

Human 决定只证明决定及其作用范围，不替代查重判断、direction_key 校验、正文骨架校验或终态机械校验。

## 16. Stop Conditions

本文不新增根停止类型。领域触发与最小影响范围：

1. 创建时发现同 direction_key 的 active Norm 已存在（方向键唯一性违例）——未完成冲突解决前不创建；
2. direction_key 格式不合法或为空；
3. 正文四段固定 H2 缺失或存在空段（骨架完整性违例）；
4. 准备在 active 状态下改写 direction_key 或方向定位与适用范围段的管辖边界（应走退役+新建路径）；
5. 准备退役但 retirement_reason/retired_at 缺失（终态完整性违例）；
6. AI 未经 Human 确认直接创建或退役（授权缺失）；
7. 遵守预检消费时发现方向冲突（两份 active Norm 共存——消费端 fail-closed）。

暂停期间只允许不越过停止边界的证据补取、引用修复、授权补走与条件核实。恢复须与触发原因逐项对应；同一停止条件恢复后再次触发的，按 00 §7.3 进入 Human Gate。

## 17. 反过度设计红线

1. 不为每个小差异或低频场景单独建 Norm——方向粒度按 §6.1 判据判断，不在清单条目上机械对应；
2. 不把 42 个清单条目强制展开为 42 份 Norm——项目按需选择，不为「全量覆盖」制造空壳规范；
3. 不在 Norm 之间建立 `relations` 结构化关系——跨方向约束以正文引用实现，不建第二关系图；
4. 不设 `norm_source` 或类似的「指向元规范」字段——事实规范的效力来自规范源层级与 active 状态，不靠路径挂靠（Human 撤回该设计，理由见 00 §3.3）；
5. 不为「成体系」的语义完备性设立无法机械判定的强制质量门槛——4 段骨架是弱机械门槛（验形），语义质量由 AI 审核与 Human Gate 保障（验质）；
6. 不把 direction_key 扩展为层级键或树状结构——kebab-case 是扁平标识，方向层级以正文定位说明，不以字段编码；
7. 不为 Norm 建缓存/索引/投影副本——消费点经 Helper 或 Web 按需读取，不建第二权威。
