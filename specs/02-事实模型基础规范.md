## 1. 价值判断

事实模型的目标不是把所有信息都变成对象，而是在需要跨行动、跨会话或跨执行者接续时，提供一个有稳定身份、有当前权威位置、有明确关系和可回读验证边界的事实承载层。

本文主要承接 00 的以下价值：

- **V1 快速定位**：统一事实类型标识、对象引用、当前权威位置和 F0–F4 召回层级，使定位可以回到来源；“快速”仍需以后续实现和对照验证证明，本文不以字段存在宣称效率成立。
- **V2 充分理解**：把对象当前内容、类型来源、状态、来源、证据边界和关系放在可分层消费的同一事实模型中；对象被读取不等于语义适用已经成立。
- **V5 据实判断**：以当前 Working Tree、完整内容指纹、写后回读和机械完整性审计约束状态与声明范围；机械结果不替代 AI 语义判断或 Human 决定。
- **V6 工作接续**：使事实能够按稳定引用跨会话恢复、按当前指纹更新，并在失败或部分完成时保留实际范围。
- **V8 持续积累**：只准入具有持续消费价值的事实类型和对象，避免重复、无消费价值的字段和对象污染事实源。
- **HV3 入档闭环节点可验**：为受控创建、当前状态、更新、更正、处置和回读提供可核对的共同节点；不以对象存在、数量或工具成功单独证明价值成立。

关系字段、F0–F4 和受控写入的机制成立，不单独证明上述价值成立。价值验证须由 09 Code 与测试、10 Web 消费、真实对象闭环和后续效用核对共同形成。

## 4. 基础概念与准入

### 4.1 稳定事实、事实类型与事实对象

- **稳定事实**：在当前项目后续行动中仍需被定位、核对、复用、承接或追溯的内容。稳定事实可以由普通规则允许的 Markdown 或其它文件自然承载，不必自动对象化。
- **事实类型**：对一类具有相同语义和对象边界、需要按共同模型进行对象化、状态化或证据化管理的事实内容所作的分类。本文不定义具体类型语义；当前重建计划登记的五类为 ADR、Pitfall、Spark、WorkCase、Study。
- **事实对象**：在已准入事实类型下具有稳定身份和当前权威位置、可独立读取、验证、关联和更新的具体事实单位。

事实类型不是目录名、文件扩展名、Schema 名称、Code 类名或 Web 筛选项；事实对象不是缓存、索引、摘要、聊天记录、Git commit、Web DTO 或工具响应的替代副本。

### 4.2 事实模型准入

候选事实类型或对象只有在以下问题均能得到据实回答时，才进入后续起草或受控创建：

1. 为什么需要跨行动或会话保留，而普通当次上下文不能承担；
2. 为什么需要独立身份、对象边界、状态、关系或证据管理；
3. 普通文档、已有事实类型或其它稳定位置为什么不能无损承载；
4. 其独立消费价值服务 AI、Human 或两者中的哪一方，对应哪些 V/HV 判据；
5. 维护、查重、召回、迁移和实现成本不会抵消其净价值；
6. 类型定义、对象字段、合法初态、来源、关系和处置边界由哪个当前规则源承担。

“文件已存在”“历史中曾有同名类型”“已经有页面或解析器”“Human 希望保留”均不能单独证明准入或对象成立。

### 4.3 五类类型责任

02 只登记共同承载责任，不在正文预定五类类型的最终字段或关系闭集。20–24 起草时至少分别回答：类型目的、对象边界、字段与结构、合法初态、状态转换、来源/证据、关系 key、召回时机、消费边界、验证、Human Gate、Stop Conditions 和类型退出。

Human 已决定保留 `Spark` 类型。本文只回指该决定；20 起草时按 Human 已定决策核对 Spark 的类型定义和字段边界（见 `docs/dev-memo.md` 待定项 15），不把 `Intent` 作为类型改名方案。

## 5. 公共对象身份与载体

### 5.1 公共身份字段

所有允许使用结构化事实对象的类型，均按下表承接公共身份；本文草案只定义公共语义候选，不把本表当作已生效的机械字段登记表。正式统一登记、字段闭集和类型使用绑定须在本文定稿时通过经授权的结构化登记附件承接，Code 机械实现与测试由 09 承接；在附件尚未登记前，类型来源不得据本表单独创建对象。05 只承接 Helper 对这些字段的请求/响应与读取写入服务契约，不取得字段定义权。

| 字段 | 出现条件 | 公共语义与边界 |
|---|---|---|
| `object_uid` | v5 对象必填 | Code 生成的 canonical UUIDv7 文本，创建后不可变；它是事实对象唯一身份，AI 不得自造、填写或按标题推导。v4 `object_id` 只作为迁移输入，不进入 v5 canonical 对象。 |
| `fact_type_key` | 必填 | 小写 ASCII kebab-case 类型标识，必须回指唯一当前类型定义来源；不得由目录或调用方猜测。 |
| `title` | 必填 | 可供候选定位和 Human 扫读的短标题；不承载完整正文、状态结论或创建原因。 |
| `created_at` | 必填 | 对象形成时间；只由 Code 在受控创建时填写，AI 不得提供、覆盖或推导。 |
| `status` | 类型条件 | 只有具体类型定义状态时才出现；状态值、初态、转换和终态由类型来源定义。 |
| `urls` | 类型条件 | 只承载具有长期消费价值的外部 HTTP(S) 资料；不得用本机路径、日志、会话或 Git 定位符替代。 |
| `relations` | 类型条件；类型来源可声明不使用 | 只承载当前类型来源定义的事实对象业务关系；采用证据定位时按 §6.1–§6.2 的公共形状承载；不得把关系、目标标题、授权或责任流水混入其中。 |
| `change_log` | 对允许受控修改的对象：首次修改后必有；不可修改类型可不出现 | 每次实际 canonical 内容修改追加恰好一条流水；`at`、署名和对象身份由 Code 托管，AI 只提供一条简短语义摘要；不记录读取、拒绝、no-op、工具调用或完整 diff。 |

字段缺省必须遵循类型来源：不适用字段省略，不使用 `null`、空字符串、空列表或占位时间伪造条件字段。跨类型共享字段的统一身份、定义位置、适用类型、登记与提升规则，由本文定稿时授权的字段登记附件承接；附件只承载结构化登记，不替代本文或类型来源的语义。公共字段修改必须评估全部当前适用类型和消费者。

`created_at` 是由 Code 在受控创建时填写的对象形成时间；AI 不得填写、覆盖或从对话、文件 mtime、Git 或其它来源推导。02 不保留公共 `updated_at`：对允许受控修改的对象，每次实际 canonical 内容修改都由 Code 在同一写入事务中追加一条 `change_log` 流水并填写其变更时间；AI 只提供简短语义摘要，不能提供或覆盖时间、署名、对象身份。读取、拒绝、no-op 和未落盘的尝试不产生流水；Git commit 是更粗粒度的工作树快照，不替代对象级 `change_log`。

`content_fingerprint` 是受控读写使用的完整当前载体指纹：它绑定当次实际 Working Tree 中对象 canonical 载体的完整内容，由受控入口或其 Code 计算并在回读时重新观察。它用于 CAS 过期检测和快照绑定，不证明载体机械有效、自然语言语义正确、证据充分、Git 版本等价或产品价值成立；不得以对象重新序列化、缓存摘要或 AI 自述替代实际载体指纹。算法、编码和共同响应字段由 05/09 另行承接。

### 5.2 载体与权威位置

1. 每个对象只能有一个当前权威载体；索引、缓存、F2 卡、Web 视图和 Helper 响应均为派生结果；
2. 具体类型定义载体格式、目录、文件名和一文件一对象/多对象承载方式；02 不预定 YAML、Markdown 或统一后缀；
3. 新创建对象的身份和 `created_at` 由 Code 最终分配，创建入口不得接受调用方提供的 `object_uid`、`created_at` 或其它托管值；
4. 受控读写以唯一的实际 Git Working Tree 和当前事实源视图为前提；具体管辖项目、worktree/common-dir、路径安全、符号链接、HEAD/Index 排除和载体定位检查由 06/07 按各自来源承接，02 不建立第二套检查器；
5. v4 `object_id` 只作为迁移输入或历史外部资料，不进入 v5 canonical 对象、关系目标或 CAS 身份；v5 普通更新不得改变 `object_uid`；
6. 事实源目录缺失、载体重复、身份冲突或当前权威位置不唯一时，不得静默选择一份继续消费或写入；实际检查未完成时按 `unavailable` 或 `partial` 交还。

## 6. 来源、证据与关系共同边界

### 6.1 来源与证据

来源回指只回答“内容从哪里形成或观察”，不单独证明内容正确、证据充分、当前适用或已获授权。具体类型来源必须定义需要保留的来源、证据形态、版本/观察时间、可接受范围和可证明范围。

证据候选可以包括对象自有的观察说明、外部长期可复核资料、类型来源定义的结构化引用或其它被 Human 定义接受的形态。02 只要求起草时明确：

- 证据是否由对象自然语言表达、公共字段、类型字段或关系目标承担；
- 机械层检查的存在性/形状范围；
- AI 对证据语义、范围和当前性的复核范围；
- 无法验证、来源冲突或证据不足时的停止和缩小声明方式。

当具体关系需要结构化证据定位时，公共关系契约必须能够承载一个由类型来源定义的证据 locator 闭集；该 locator 的公共形状由本节承接，是否必须存在以及机械检查的具体范围由 20–24 类型来源、05 Helper 和 09 Code 按实际消费与风险定义。02 不预定证据字段名称、最低校验深度或领域证据充分性，但不得把证据环节完全留成各类型互不兼容的私有形状。

关系不得凭空猜测，也不得以关系存在、URL 存在、文件存在、命令成功、测试通过或 Human 回应冒充事实证据。关系声明本身只证明声明被记录，不证明证据充分、语义正确、当前适用、行动允许或工作完成。

### 6.2 公共关系形状

事实对象关系候选使用统一的最小形状：

```text
relations:
  - relation_key: "<由事实类型来源定义的 key>"
    target:
      object_uid: "<v5 唯一对象身份>"
    # v4 object_id 只作迁移输入，不作为 v5 关系目标
    # 仅当类型来源采用证据定位时，增加其定义的 evidence_locator
```

实际请求中的 `target` 只使用 `object_uid`；v4 legacy 三元组不进入 v5 canonical 关系目标。关系条目只保存：

- 类型来源定义的 `relation_key`；
- 可稳定解析的 v5 `object_uid` 目标引用；
- 类型来源采用时，按本节公共边界形成的证据定位闭集；
- 不复制目标标题、关系解释、授权、责任 ID、反向导航或 Web 投影。

共同不变量如下：

1. relation key 必须属于当前来源类型定义的闭集；未知 key fail closed；
2. target 必须可按当前事实源规则稳定解析，跨项目关系是否允许由 20–24 和 Human 定；当前草案默认不把跨项目关系视为已获允许；
3. 关系方向、目标类型、基数、自指、循环、同义重复和目标状态条件由定义该关系的类型来源定；02 不建立通用关系家族；
4. 反向关系索引、图导航和关系目标标题均为 Code/Web 派生，不写回对象，不建立第二权威；
5. 目标缺失、无效、不可读、退役或关系语义冲突必须保留实际边和失败范围，不得降格报告为“无关系”；
6. 关系存在只证明声明被记录，不证明语义正确、当前适用、行动允许、责任已承接或工作已完成；
7. 关系变更必须使用对象当前指纹绑定的完整更新入口，写后精确回读；实际关系变更随该次对象修改由 Code 追加一条对象级 `change_log` 流水，流水只保留简短语义摘要，不自动形成外部审计流水。

`routed-to`、`contributed-to`、`informs` 等关系家族只在 20–24 起草时按类型语义逐项决定；Spark 不因类型名保留而自动取得任何承接关系。作为待决输入，20–24 与 Human 至少需要比较：关系是否属于公共业务关系或正文/演变内容、证据是对象自有说明还是结构化定位、机械校验是否只做存在性/形状还是还有来源范围检查、目标失效如何报告，以及关系变更是否具有独立历史消费价值；本清单登记问题，不预定答案。

## 7. 事实发现、召回与语义消费

事实消费严格区分四个结论：

1. **发现**：在唯一实际管辖项目/Working Tree 中，按确定性条件枚举对象引用和最小卡片；
2. **召回**：按当前目标、类型来源和已知对象形成少量候选，并保留命中依据和未检查范围；
3. **展开**：对稳定引用读取当前权威对象全文并完成已实现机械检查；
4. **语义消费**：AI 结合当前目标、类型来源、对象内容、状态、来源、证据和环境，判断对象是否相关、适用、授权或影响行动。

候选返回、机械有效、文本命中、关系存在和对象状态均不能替代语义消费判断。Code 不得使用相似度、embedding、关键词权重或 AI 输出自动裁决相关性、适用性或事实结论。

### 7.1 F0–F4 分层

| 层级 | 内容 | 允许用途 | 不能单独证明 |
|---|---|---|---|
| F0 | 管辖项目、实际 worktree/common-dir、类型/状态计数、Schema/对象集指纹、当前工作对象、coverage、cursor、无效/不可用对象清单和未完成范围 | 恢复边界、过期检查、确认未检查范围 | 具体对象存在、相关、适用、未变化 |
| F1 | 类型来源要求的最小权威字段卡片；需要时为全部指定对象集合分页返回 | 建立恢复基线、当前决策/责任全貌 | 全文已读、适用、授权、完成 |
| F2 | 按类型、状态、稳定引用、关系、locator 或类型允许字段命中的候选卡、命中依据和有界确定性摘录 | 筛选少量候选并选择 F3 | 语义相关、现时适用、结论当前、全文已读 |
| F3 | 当前权威载体的完整对象内容与当次机械检查 | 语义、状态、边界和限制判断 | 来源真实、证据充分、行动授权或下游完成 |
| F4 | 仅展开影响当前适用、决定、验证或当前性的必要来源/证据 | 核对具体声明、版本、观察时间和范围 | 未展开引用已核对、全部声明当前 |

F0–F4 是事实召回分层，不能与 01 的 L0–L4 规范读取分层混用。分层结果的数量、排序、分页、截断、指纹和未完成范围必须可观察；超预算必须分页、继续缩小或返回 partial，不得静默截断后声称完整。

### 7.2 召回进入条件

规则引导先于事实消费。AI 已明确当前目标后，只有在项目事实对当次理解、判断、验证或行动确实必要，或当前输入精确引用稳定事实时，才进入事实消费分支。新会话、压缩、委派或生命周期事件本身不自动证明事实消费必要，也不自动证明事实不存在。

具体类型来源定义本类型的召回时机、默认候选状态、关系闭包和必须展开的 F3/F4 范围。02 不建立所有类型共用的触发词、相关性分数、默认数量或无条件全量注入。

事实预热可以由 08 环境接入与 05 Helper 在已满足事实消费进入条件时承载，但只交付带来源与指纹的候选、卡片或恢复入口；它不得写入事实源、改变关系、替代 F3/F4 精确读取、替代语义适用判断或把概率召回变成事实声明。预热容量、触发事件和宿主注入形式由 05/08 与具体类型来源共同承接；未完成、超预算或不可用范围必须按本规范的 partial/unavailable 边界交还。

## 8. 受控读取、创建与更新共同契约

### 8.1 共同前提

每次事实域读写必须形成：

1. 唯一管辖项目和实际 Git Working Tree；
2. 当前规则源和具体类型定义来源；
3. 事实对象当前稳定引用或无副作用草案依据；
4. 当次请求的作用范围、授权边界和未验证范围；
5. 写操作必须具备对象级当前 `content_fingerprint` 作为 CAS 基线；F0/候选发现或完整性审计可另具 Schema、对象集或 WorkTree 指纹；只读候选不因此被强制增加写入前 CAS；
6. 可回读的结果定位。

无法形成唯一范围、来源冲突、规则源或类型定义缺失、当前载体不可读、必要全集检查无法完成时，受影响范围 fail closed；不得用计划、缓存、候选 ID、路径猜测或工具成功替代实际范围。

### 8.2 只读路径

只读事实能力至少区分：

- **候选发现**：形成 F0/F1/F2，允许分页和确定性过滤；不修改事实源，不建立持久索引；
- **精确读取**：按稳定引用读取 F3 当前对象，返回完整对象、实际路径、content fingerprint、carrier、机械问题和来源回指；不做模糊搜索；
- **F4 展开**：按类型来源定义的必要来源/证据定位读取，不把来源内容自动写回对象；
- **完整性审计**：对单对象或当前 WorkTree 的事实集合执行独立机械检查，报告 complete/partial/unavailable 及具体未完成范围。

读取结果中的 `mechanically_valid` 只表示当次已实现机械规则通过，不证明自然语言语义、来源真实性、证据充分性、适用、授权或完成。

### 8.3 无副作用草案

草案准备只派生：

- 当前类型来源和 Schema/字段契约指纹；
- 当前项目、worktree/common-dir 和对象集范围；
- 允许字段、条件字段、托管字段和载体契约；
- 调用方仍需填写的语义字段和来源/证据输入边界。

草案准备不得创建对象、预留 UID、占用 counter、写缓存、写 Git ref 或修改事实源。草案绑定发生变化时必须失效，不得移植到其它项目、worktree 或 Schema。

### 8.4 受控创建

受控创建一次只形成一个新对象，且必须：

1. 消费当前有效草案依据；
2. 由 Code 生成并写入身份和托管字段；
3. 对 AI 提供的类型字段执行当前来源已定义的机械检查；
4. 以原子、不可覆盖的方式写入唯一当前载体；
5. 写后按精确读取边界回读当前文件；
6. 返回 `actual_ref`、content fingerprint、carrier、回读对象和写后机械结果；
7. 任何创建不确定、部分、回读失败或无法排除残留时，停止后续事实写入、提交和成功声明。

创建成功只证明一个对象在当次范围内实际创建并通过当次机械回读，不证明自然语言事实真实、证据充分、Human Gate 已完成、Git 已提交或上层工作完成。创建入口不得使用多个单对象创建拼接一个需要多对象共同成立的原子结果。

### 8.5 CAS 更新与更正

局部补丁可以是调用方降低表达摩擦的请求形态，但不改变事实域的发布不变量：05 若提供补丁入口，必须把它绑定当前对象指纹，在内存中形成完整目标 after，并以与整对象更新相同的类型校验、原子发布、写后回读和审计边界落盘；02 不授权静默 merge 或把局部补丁当作绕过完整 after 的发布路径。

若目标对象允许受控修改，发布事务必须同时完成内容变化与恰好一条 `change_log` 追加；Code 自动填写该条的 `at`、署名和对象身份，调用方只提交一条简短语义摘要。摘要可以由 05 在请求中承载为单一字段，或由类型入口从本次更新意图形成，但不得要求调用方另行调用日志操作。摘要缺失、为空或无法据实说明变化时，写入不成立；零变化、拒绝、失败或未落盘不追加流水。

对既有对象的内容、关系或类型允许的状态变化，必须使用完整目标 after 替换，不使用未定义的差量 merge 或静默 patch；目标请求绑定最近一次精确回读的 `content_fingerprint`。

写入入口必须在实际写前重新确认：

- 目标引用仍解析到同一权威对象；
- 当前指纹与 expected fingerprint 一致；
- after 保留全部未变更且仍有消费价值的字段；
- 托管字段由 Code 维护，调用方不得伪造；
- 类型来源允许该内容/关系/状态变化；
- 作用范围和授权覆盖实际变化。

指纹不匹配、目标消失、关系全集无法检查、after 不完整、类型条件不成立或授权/来源不成立时，零写入并报告拒绝或不可用范围。成功写入后必须精确回读新的对象和 content fingerprint；不得复用旧指纹继续下一步。

### 8.6 多对象边界

只有当前来源已经定义范围匹配的公开原子操作，且 Code 能证明全部目标、关系、基线、原子写入、失败回滚和回读时，才能声明多对象原子变化。并发、单调令牌和协调锁的具体语义由 06 与具体类型/执行来源定义；它们不能被对象指纹或单对象 CAS 自动冒充。否则：

- 不得先写孤立新对象，再补关系；
- 不得用多个单对象成功拼接整体成功；
- 不得用补偿更新制造伪原子性；
- 保持全部对象原状，并交还完整拟变更范围、能力缺口和零写入结果。

类型来源明示的非原子例外必须逐项定义；02 不自行增加例外。

### 8.7 写后回读与适用完整性审计

受控写入后，必须完成精确回读：

1. 从 Helper 响应的 `actual_ref` 或实际定位精确回读；v5 对象和关系一律使用其唯一 `object_uid` 稳定引用；
2. 检查外层结果、领域状态、coverage、gaps、diagnostics 和未验证范围；
3. 只有当前来源、类型规则或风险边界要求时，才对同一实际 WorkTree 追加单对象或全库完整性审计；审计触发范围和入口由 05/09/20–24 定义，不因每次低风险写入自动扩张。

精确回读与适用的完整性审计互不替代。已经触发的审计为 partial、unavailable、调用失败、事实集合/规则源/worktree 变化而失效，或写入残留无法排除时，不得继续事实写入、提交或扩大成功声明。失败后只可使用来源允许且范围匹配的回滚/更正入口，不得直接普通编辑 canonical 载体。

### 8.8 部分结果与交还

事实域操作的部分或不可用结果必须把已完成、未完成和未验证范围分开交还。共同响应字段由 05 定义；02 要求其语义至少能够表达：

```text
partial_scope:
  completed: ["<已实际完成的对象、边、页或检查范围>"]
  not_completed: ["<未完成、不可用或未检查的范围>"]
  residual_risks: ["<已观察或无法排除的残留风险>"]
  resume_from: "<可继续的精确引用、cursor 或验证入口；无入口时省略>"
```

该结构是交还语义示例，不是 02 对 05 共同 envelope 的字段登记。任何分页、关系边、对象集合、审计或写入范围只要未完成，就不得用空数组、工具成功或当前已完成子范围代表整体完成；已完成子范围可以继续消费，但不得越过未完成范围形成整体成功声明。

## 9. 事实变更、生命周期与关系失效

02 不规定通用 `active`、`closed`、`implemented`、`discarded` 等状态。类型来源必须定义：状态集合、合法初态、转换、字段出现/禁止条件、来源/证据、Human Gate、失败和终态保留。Spark 与 WorkCase 的查重、attempt/锁恢复、partial/cancelled/not-achieved 收口及快通道等生命周期改进候选，按 dev-memo 待定项 14 在 20/21 起草时逐项形成方案并呈 Human 定，02 不预判其字段或状态。

普通内容更新、事实更正、关系变更、状态转换、关闭、归档、合并、替代和删除是不同动作；类型来源必须区分。关闭或归档不等于删除；删除前必须处理仍适用事实、入向/出向关系和稳定引用。目标失效、退役、缺失或不可读时，关系声明不能静默删除或改写成无关系。

关系变更、目标失效和退役是否保留历史，只在该关系或类型确有独立消费价值时由类型来源定义。公共模型要求消费方能够区分：当前可解析关系、已声明但目标缺失、目标不可用、关系被过滤、关系来源未检查和未完成范围。

## 10. 价值验证与证据边界

| 验证对象 | 机制成立条件 | 可证明范围 | 不能单独证明 |
|---|---|---|---|
| 公共身份与载体 | 类型来源、路径、身份、字段闭集和托管字段检查通过 | 当次对象机械身份与载体 | 事实语义真实、价值成立 |
| F0–F2 候选 | 确定性过滤、投影、命中依据、分页和 coverage 完整 | 当次候选范围与未检查范围 | 语义相关、适用、全文已读 |
| F3 完整读取 | 稳定引用解析、当前文件完整读取、机械检查和指纹形成 | 当次对象完整快照 | 来源真实、证据充分、授权、完成 |
| F4 来源展开 | 类型来源要求的必要来源已实际读取 | 当次来源/证据读取范围 | 未展开范围已核对、结论正确 |
| 受控创建/更新 | CAS/授权/类型条件、原子写入、精确回读和适用审计均完成；发生实际修改时同一事务追加 Code 托管时间的 `change_log` 流水 | 当次事实源变化、流水追加和机械结果 | 自然语言语义、Human 决定、Git 提交、产品价值 |
| 关系导航 | 直接关系声明、目标状态和失败原因如实投影 | 当次一跳关系与目标读取范围 | 关系语义正确、适用、责任承接、完成 |

事实模型的机械结果只交还当次已证实、未证实、partial/unavailable 范围和残留风险，沿用 00 §6.2 的交还结构；02 不建立价值审计报告、外部证明材料或过程留痕工件。不得因为对象数量、工具成功、页面显示、commit 创建或测试通过而声称 V/HV 价值成立；真实使用效用和价值对照由 04/09/10 按各自职责另行核对。

## 11. Human Gate

本文不新增统一 Human Gate。以下事项按 00 §5.4 进入 Human Gate：

1. 新增、删除、改名或重排已登记事实模型或事实类型；
2. 改变公共字段语义、关系公共形状、事实源边界或 Helper/Code/Web 的效力边界；
3. 确定关系证据方案、跨项目关系、关系家族、重大状态/生命周期或删除/替代规则；
4. 事实类型准入、对象化与普通文件承载之间存在重大取舍；
5. 多对象共同成立但原子能力不足，或冲突关系、证据、方向和风险需要 Human 取舍；
6. 事实对象的高影响创建、更新、终态、删除、替代或迁移超出已明确授权。

Human 决定只证明决定及其作用范围，不替代类型条件、技术验证、对象回读、完整性审计或事实语义审核。事实域授权仍受 00 §5.3 授权包的对象、范围、边界和冻结语义约束；已明确的授权不得扩张到未列明的对象、关系、副作用或提交。

## 12. Stop Conditions

以下条目是 00 §5.5.1 在事实域的具体化，不新增停止触发类型；暂停期间和恢复条件仍分别受 00 §5.5.2–§5.5.4 约束，与 00 冲突时以 00 为准。出现以下任一情况，必须暂停受影响的事实对象、关系、类型或声明：

1. 管辖项目、实际 Working Tree、类型来源、对象权威位置或作用范围不唯一；
2. 事实类型未准入、类型定义来源缺失/冲突，或准备以目录、Schema、Code、Web、工具响应替代类型权威；
3. 普通文件或已有对象可以无损承载，却仅因对象模型存在而新建事实对象；
4. 公共字段未登记、条件字段未解析、after 不完整、身份/托管字段由调用方伪造；
5. 关系 key、目标形状、方向、基数、目标类型或关系证据边界未由当前类型来源定义；
6. 准备用标题、关键词、相似度、关系存在或 AI 候选自动判断语义相关、适用、证据充分、责任承接或完成；
7. F0–F4 与 L0–L4 混用，或分层结果静默截断、缺 coverage、未报告 cursor/partial/unavailable；
8. 写前没有当前指纹/范围，或准备复用过期草案、旧指纹、缓存、HEAD/Index/其它 worktree 内容；
9. 受控创建/更新后尚未精确回读，或尚未完成适用完整性审计却准备继续写入、提交或声明成功；
10. 多对象共同成立却准备使用多个单对象写入、补偿更新或后续补关系拼接成功；
11. 关系变更、目标失效、删除或退役将丢失仍适用事实、稳定引用或必要承接；
12. 准备把机械有效、工具成功、对象数量、页面呈现或 Human 回应写成自然语言事实、授权、完成或价值成立；
13. 发现本草案与 00/01、具体类型来源或 Human 已定决策冲突；
14. 受控写入失败、拒绝、部分成立、残留无法排除或结果不可观察，却准备继续后续事实写入或提交。

暂停期间可进行不越过边界的来源定位、事实回读、证据收集、验证、修复和分流准备；恢复条件必须与触发原因对应，按 00 §5.5 执行。

## 13. 起草验证清单

### 13.1 00 停止条件承接

本规范不替代 00 §5.5 的停止条件。事实域出现 00 §5.5.1 所列任一触发时，暂停受影响的最小事实对象、关系、声明或行动单元；恢复条件、暂停期间允许的规则定位/事实核对/验证/修复/分流准备和恢复后的范围限制，分别按 00 §5.5.2–§5.5.4 执行。本规范第 12 节只把这些上位停止边界投影到事实域，不新增更宽的停止效力。

### 13.2 本文起草验证清单

02 草案在进入 Human 审阅前至少应完成以下检查：

1. 00/01 交叉引用、身份块、编号和职责边界一致；
2. 五类事实公共字段与载体边界不抢占 20–24 类型语义；
3. `relations` 只定义公共最小形状，不提前决定具体关系 key；
4. F0–F4 与 L0–L4 明确分层，所有 partial/unavailable 范围可交还；
5. 创建、更新、CAS、回读、完整性审计和多对象边界不把工具成功写成语义成立；
6. Human Gate、Stop Conditions 与 00 一致，不新增第二套授权或状态机；
7. 每项公共机制均能说明对应的 V/HV 判据、机械证据、未验证范围和摩擦风险；
8. 真实最小纵向闭环应在 02 定稿后立即安排：一个对象的创建、精确回读、完整性审计和本地 Git Gate；该闭环结果不能回填为价值已成立。
