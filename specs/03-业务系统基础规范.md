# 业务系统基础规范


## 1. 价值判断

业务系统基础规范解决六大业务系统各自展开时缺少共同骨架与风险分流的问题，使每个业务系统都能在同一套进入与退出契约、停止分流、验证和交还结构中承接 00 §3.1 赋予它的职责，减少职责漂移、风险误判与结论声明失据的负担，同时避免把每个系统都写成独立仪式。

定位与理解机制主要支撑 V1–V3，系统声明、进入与退出契约、根职责回指和相邻系统边界用于定位系统并理解完整边界；执行与分流机制主要支撑 V4 与 V6，可复用骨架、快通道、降级路径与结论承载用于稳定推进并把结果交接到后续会话；接续与沟通机制主要支撑 V7 与 HV1，预检落实记录、已验证与未验证范围和交还承接用于保留关键结果和未完成范围；积累与节点可验机制主要支撑 V8 与 HV3，使系统更新、合并、退出和关键节点可回指来源与结果。

**新增的负担与风险（00 §6.3 第 4 问，如实登记）**：本规范不是无成本的。它为六大业务系统引入共同骨架，**新增以下负担**：(a) 每个业务系统规范都须逐项承载 §11.3 的十项结构与 `01 §7` 的固定八章，起草与修改成本高于各自自由展开；(b) 十项结构与准入条件须逐项可核对，核查成本随系统数线性增加；(c) 分工与边界须显式声明，避免重复即须在多处维护交叉引用。**新增以下风险**：(a) **形式合规替代实质**——结构齐全不等于职责真正承接，十项可被填空式满足；(b) **共同结构掩盖系统差异**——按同一骨架展开可能压抑各系统的领域特性（如过程型系统与结论型系统的差异）；(c) **骨架随实例增长而漂移**——各系统在扩展规则下自行增补，长期可能累积彼此不一致的变体。**核对方式**：以 `01 §12` 的独立审核检验「结构是否被填空式满足」，并在每次新系统建立时比较其与既有系统的偏差点。**若上述负担与风险在实践中被证明超过收益，应重审本节机制而非默认保留**（00 §6.3「答不出的不纳入」，反向亦成立）。

本规范只定义业务系统的公共机制和共同结构；V4 的具体复用效果由业务系统规范段中的实际规范使用证明，HV4–HV5 的系统效用与关系脉络由检查机制与辅助机制规范、受控提交与机械守护规范、DSH 环境接入与插件发布规范和实际工作承接，Human 决策与授权仍由 00 及相应领域来源承担。

系统存在、结构完整、流程执行或工具成功不能单独证明系统适用、行动获准、验证通过、工作完成或价值成立；价值须由具体业务系统的真实复用、验证、回读和后续效用核对共同支持。

## 2. 规范依据

本文直接依据：

1. `ldvh-root`：00 §3.1 的能力承载与业务系统根职责、§3.3 的检查机制与辅助机制、§3.5 的技术与机械保障、§4.2 的根决定清单、§5.6 的据实声明、§5.7 的必停情形与恢复、§5.8 的交还与撤回和 §6 的双轨价值标准；五机制由本文 §5 定义；
2. `specification-model-foundation`：01 §6 的身份块契约、§7 的共同章节结构与基础模型规范对下属规范的结构责任、§8 的编号登记、§9 的当前规则源条件、§10 的 L0–L4 读取层级与 F0–F4 不混用边界、§11.3 的修改与替代追溯、§12 的独立审核；
3. `check-auxiliary-mechanism-foundation`：检查机制与辅助机制规范 §5 的共同框架、§6 的检查机制三形态与 §10 的协同、接管与交还，以及 §10.3 的交还对预检、方案、完成门禁与风险路由的职责边界。

本文不依赖额外外部语法或行业标准定义业务系统语义。

历史规范、研究材料、事实对象、Code、测试和其它建设材料只作为设计输入，不取得规范效力。本文不重新解释 00/01；发生冲突或权威关系无法确认时，按 00 §5.7 暂停受影响范围并完成对齐。

## 3. 职责边界

### 3.1 本文负责

1. 业务系统的公共机制定义：进入与退出契约、系统停止条件、反逃避信号、结论门禁与分层交还；
2. 风险路由与快通道的层级数、判断标准与声明方式（00 §5.7 与 §5.9 要求）；
3. 预检落实记录的公共格式和承载边界（规则遵守系统的机械承载，00 §5.7 落点）；
4. 降级路径的公共契约：能力不足、验证失败、结果不可观察时的分流和交还要求；
5. 反过度设计红线：不复制状态机、不全局事务、不每步强制复核、不外部审计簿记；
6. 业务系统规范段（具体业务系统规范）的共同结构、必填内容、扩展规则与准入条件的完整定义；
7. 业务系统与工作模型职责、事实模型、能力承载、制度和事实源之间的协作边界。

### 3.2 本文不负责

1. 任何具体业务系统的 `system_key`、专属流程、领域条件、命令、字段、格式或当前效力，由业务系统规范段承接；00 §3.1 已定义的职责、判据与边界，本文只回指不改变；
2. 具体事实类型的字段定义、状态机、Human Gate 或完成条件，由事实源与事实模型基础规范与各事实类型规范承接；
3. LDVH CLI 的请求/响应 envelope、工具注册和宿主接入，由 LDVH CLI 确定性服务规范承接；
4. 事实源与 Git 提交、Git 提交候选机械预检（commit candidate precheck）、署名 trailer 和提交 message，由受控提交与机械守护规范承接；行动前事实预检与预检落实记录由本文承接；
5. 管辖判定、环境接入、Hook 部署、Code 测试纪律和 Web 视觉/交互，由管辖、环境、Code 与 Web 的相应规范承接；
6. AI 对某业务系统是否适用、条件是否满足、证据是否充分的语义判断，本文只定义判断框架；
7. 业务系统执行的一次性计划、临时顺序、负责人和运行进度，由当次行动单元承载；
8. 不重新定义检查机制与辅助机制规范的工作职责；不替代其关于"遵守成立不等于行动完成"的边界；不把编排或复核的全部职责收入本文；不定义事实字段、状态机、关系形状或事实域契约；业务系统执行中需要保留的事实写入回指事实源与事实模型基础规范、LDVH CLI 确定性服务规范与受控提交与机械守护规范，不建立第二套事实写入规则；`change_log` 是事实域机制，本文不要求业务系统流程产生 `change_log`。

### 3.3 相邻规范分工与唯一权威

00 是业务系统**根**职责的唯一权威，检查机制与辅助机制规范是检查与辅助机制的唯一权威；事实源与事实模型基础规范与事实类型规范定义业务系统所需事实的字段、状态、关系和受控写入；LDVH CLI 确定性服务规范是 LDVH CLI 服务入口的唯一权威；受控提交与机械守护规范是受控提交契约的唯一权威；管辖范围规范、环境接入规范、Code 实践与测试规范与 Web 呈现与交互规范分别承接管辖、环境、Code 与 Web。本规范只定义业务系统公共机制和共同结构，Code 不得由实现、测试、缓存或 Web 反向创造第二权威。

**业务系统定义的「当前唯一来源」与迁移路径（避免双权威）**：六大业务系统的**根职责**由 00 §3.1 定义、由本文 §9 展开。业务系统规范段的独立规范**应逐步承接各系统的专属流程与领域条件，并在承接完成时由本文保留指针、不再重复展开**（迁移由各系统规范建立时按其自身建立程序处理，本规范不预设强制时点）。**已有独立规范承接的系统**，其专属流程与领域条件的唯一定义来源为该独立规范，本文 §9 的对应展开保留为根职责指针；**尚无独立规范承接的系统**，本文 §9 的内联展开即该系统的唯一定义来源。判断某系统是否有独立规范承接，以 `specs/` 实际文件与 `01 §9.2` 的成立条件为准，本文不登记具体承接状态。任何消费方不得因「业务系统规范段是唯一权威」这一表述而认定本文 §9 的展开失效——§11.2 的 `definition_ref` 可选择指向业务系统规范段独立规范**或**本文 §9 中自然承接该系统责任的章节，两者不并存为两份权威：同一系统在任一时点只有一个 `definition_ref` 目标。

## 4. 适用范围

**术语**：本文中的「**业务系统规范段**」指 `01 §8.1` 为业务系统规范登记的编号区间。**该区间的具体起止编号由 `01 §8.1` 唯一登记，本文不复制其数字**——本文引用业务系统规范时统一使用「业务系统规范段」，需要确切编号时回指 `01 §8.1`。这样在业务系统数量经 Human 决定增减、区间随之调整时，本文无需逐处修改。

### 4.1 适用对象

本规范适用于：

1. 业务系统的公共机制与共同结构；
2. 业务系统规范段中的具体业务系统规范；
3. Human、AI 与 Code 对业务系统的共同消费。

### 4.2 适用场景

本规范用于业务系统的进入与退出判断、风险路由、快通道、预检落实、执行、验证、交还、更新、合并和退出，以及跨会话、跨行动单元按同一骨架承接业务职责。

### 4.3 明确排除与证明边界

本规范不适用于一次性临时顺序、未取得重复价值依据的计划，也不替代事实字段、LDVH CLI envelope、提交契约或实现规范。具体业务系统规范必须按本文 §11.3 的共同结构和 §11.1 的准入条件起草；预留编号不证明系统已成立、已登记或已进入当前规则源。

系统匹配、结构完整或执行发生只证明相应候选与过程范围，不单独证明系统适用、行动获准、验证通过、交还完成或价值成立。

## 5. 业务系统五机制

业务系统的技术骨架由五个机制构成，服务于工作包生命周期模式：

### 5.1 进入与退出契约

每个业务系统必须定义：

- **进入信号**：哪些当前目标、对象、事实或来源规则使其成为应被承接的系统；
- **适用条件**：哪些输入、前置事实、规则、授权、环境和能力必须成立；
- **排除条件**：哪些相近场景不应由本系统承接（反例）；
- **不确定处理**：哪些信息不足或冲突会阻止适用判断，以及需要补充什么；
- **作用范围**：当次判断覆盖哪些对象、行动、环境和时间范围；
- **退出条件**：当次职责在何种信号下视为完成收口、转交其它系统或进入暂停交还。

系统发现、结构校验通过或名称相似，只能说明它是候选，不能证明已经适用。适用条件无法确认时，不得按最相近系统猜测执行；应补充依据、改用普通求解、转交其它已成立的系统，或按风险路由降级。

### 5.2 系统停止条件

每个业务系统必须定义其专属流程的停止条件，同时承接 00 §5.7 的上位必停情形。系统的停止条件至少包括：

- 流程所需输入缺失或冲突；
- 流程依赖的前置条件不成立；
- 流程执行结果不可观察或部分失败；
- 流程发现的实际风险超出快通道假设；
- 流程触发了 Human Gate 但尚未取得回应。

停止条件是暂停的最小单位，不要求在流程内的每次工具调用前重复判断。暂停期间可进行不越过停止边界的来源定位、事实核对、证据收集、验证和分流准备。

### 5.3 反逃避信号

业务系统执行域把"以形式成功掩盖实质失败或越权"的行为聚合识别为**反逃避信号**。信号至少覆盖以下五类来源：绕过应承接的业务系统而走普通求解、用默认值/历史记忆/名称相似静默补齐缺失条件、流程失败后不按分流路径处理、用工具/命令/文件存在的形式成功代替实际验证、把超出当次验证范围的结果声明为完成。具体信号清单由业务系统规范段在其流程中按领域增删，但**本文不逐信号做流水记录**，只在当次预检落实记录或交还结构中**聚合记录触发原因、影响范围与已采取的停止/降级动作**。反逃避信号不新增独立审计记录或外部簿记，触发即进入 §14 停止序列或 §8 降级序列。

### 5.4 结论门禁

业务系统的结论（含以事实对象承载的结论）声明必须同时满足以下条件：

1. 系统的全部必要流程环节已执行（或按分流路径完成）；
2. 每一环节的结果在当次可观察范围内取得；
3. 系统定义的验证入口已通过；若验证未完成、失败或覆盖不足，只能形成 partial/unverified 交还，不得宣称系统结论成立；
4. 需要回写的事实已按事实源与事实模型基础规范与实际来源规则写入并精确回读；
5. 需要提请 Human Gate 的事项已取得作用范围清楚的回应；未取得回应时，只能暂停并交还，不得宣称系统结论成立；
6. 结论声明不超过当次依据、验证和完成条件实际支持的范围。

系统静态存在、环节全部打勾、工具返回成功、Human 已回应或 Git commit 已创建，都不单独替代上述成立条件。

### 5.5 系统执行分层交还

业务系统执行结果按以下三层分层交还，互不替代：

| 层级 | 内容 | 用途 |
|---|---|---|
| **流程完成层** | 系统流程按定义执行完毕，未触发停止条件 | 确认执行完整性 |
| **验证通过层** | 流程完成层成立，且系统定义的验证入口全部通过；验证未完成或覆盖不足时只能交还 partial/unverified | 确认验证覆盖 |
| **交还承接层** | 验证通过层成立，且结果、已验证/未验证范围、残留风险和需要回写或 Human 决定的事项已按来源要求交还或承接 | 确认后续行动可据实接续，不替代 00 的价值判断 |

流程完成层不等于验证通过层；验证通过层也不等于价值成立。交还承接层只表示当次结果已可据实接续，不要求每次系统执行都回指或审计 V/HV 效用。01 的 L0–L4 是规范读取分层，事实源与事实模型基础规范的 F0–F4 是事实召回分层；本文的三层是系统执行评测分层，三者不混用。

## 6. 风险路由与快通道

### 6.1 风险分层

00 §5.9 要求预检粒度与风险相称，00 §5.7 要求预检不得缺失或覆盖不足。业务系统承担该分层的具体定义。三个风险层**均为系统路径**，每个具体业务系统（业务系统规范段）必须按其重复场景的实际风险，**从下表三个风险层中选其一**作为自身默认风险层，不得在快通道、标准路径、加固路径之外另立第四层或排除快通道这一层：

| 风险层 | 适用场景 | 预检要求 | 系统路径 |
|---|---|---|---|
| **快通道** | 低风险、高度确定、已反复执行且满足排除条件的业务动作 | 完成最低预检覆盖（生效+适用+行动允许三段判断）；已成立的事实召回时机仍必须按相应来源完成所需召回 | 业务系统规范段中声明默认风险层为快通道的系统，或本文适用范围内的快通道骨架直接进入普通求解 |
| **标准路径** | 常规风险、需要完整预检和验证的业务动作 | 完成适用来源要求的行动前事实预检；召回时机成立时，按相应来源完成所需的 ADR/Pitfall 召回 | 业务系统规范段的标准系统 |
| **加固路径** | 高风险、影响重大、不确定性高的业务动作 | 在标准路径基础上增加来源要求的独立复核，并按风险提高对抗性与视角数量；Human Gate 仅在 00 §4.2 触发条件成立时前置 | 业务系统规范段的加固系统或特殊流程 |

快通道是业务系统预先定义的预检分层，不构成预检覆盖不完整。快通道不遍历未被当前目标和来源规则触发的全量规则或事实；一旦相应来源的召回时机成立，快通道不得豁免该来源要求的召回，只读取满足当前触发范围所需的内容。执行中发现实际风险超出快通道假设时，必须停止快通道，按 00 §5.7 补齐标准或加固路径的预检要求；满足对应恢复条件后，才能以新路径恢复。升级不绕过停止，也不自动取得 Human Gate 授权。业务系统规范段不得以"快通道不适配本系统"为由绕开快通道这一层；确有更高风险时按 §6.3 升级到标准或加固路径，而非另立层级。

### 6.2 快通道声明

快通道的声明必须包含：

1. **适用条件**：什么场景下可以使用快通道（与标准路径的边界）；
2. **排除条件**：什么场景下即使符合适用条件也不能使用快通道（反例）；
3. **最低预检覆盖**：快通道仍然必须完成的三段判断（生效、适用、行动允许）；
4. **升级触发**：执行中发现哪些信号时必须停止快通道，并按 00 §5.7 补齐标准路径或加固路径的预检后恢复；
5. **声明方式**：AI 在进入快通道时如何声明（如"本次使用 [快通道名称]"，附带适用依据）。

快通道的层级数、判断标准与声明方式由本文统一定义，业务系统规范段具体业务系统必须从 §6.1 三个风险层中选其一作为自身默认风险层，不得自行增设层级或降低本文 §6.2 定义的最低预检覆盖（其根边界见 00 §5.7），也不得声明"本系统不属于任何风险层"以绕开预检分层。

### 6.3 风险升级、停止与恢复

当执行中发现以下情况时，必须从快通道升级到标准路径或加固路径：

- 实际影响的文件或对象超出快通道假设的范围；
- **当前环节**需要写入受控事实对象（而非普通文件修改）；
- 需要修改规范或受保护文档；
- 涉及未经验证的技术能力或环境入口；
- 需要 Human Gate 决策；
- 已完成环节的结果与预期显著偏离。

**升级判定的粒度是本环节，不是整个系统（重要澄清）**：上列触发按**当前正在执行的环节**判定，而非按「该系统最终是否会落档」判定。因此**同一系统内不同环节可以处于不同风险层**：一个系统的默认风险层为快通道时，其**不落档的探索、求解、检索、草拟等环节**可继续走快通道；一旦某个环节需要写入受控事实对象，**该环节**须升为标准路径，**其前置的不落档环节不因此回溯失效**。这与 §6.1「每个系统从三个风险层中选其一作为自身默认风险层」不矛盾——**默认风险层是该系统的基线，本节规定的是基线上的环节级升级**；系统仍不得另立第四层，也不得整体排除快通道这一层。

**该澄清的适用边界**（防止被误用作规避）：(a) **不得**以「本环节不落档」为由，先在快通道下做出**只有标准路径才允许的结论**，再于落档环节追认——快通道允许的是**探索与求解**，不是**免预检的定论**。**此边的判定判据（避免主观滑移）**：**凡产出带明确取舍倾向的结论**——包括但不限于推荐方案、定案建议、可直接据以行动的草拟结果——**即属「定论」而非「探索」，即便该产出不落档、不转交受控事实，仍须按标准路径完成预检**；快通道只允许产出**并列选项、权衡材料与待决问题**，不得输出已收敛的单一主张；(b) 环节划分须**事先在系统规范中声明**（依 §6.2 的适用条件与排除条件），**不得在执行中为规避升级而临时切分环节**；**且划分不得宽到使标准路径仅剩写入动作**——若某系统的探索环节被划定为涵盖方案草拟与比较，则该划分本身须按标准路径预检，不得以「属探索」为由整体下沉；(c) 无法清晰界定环节边界时，**按整个系统取标准路径**（保守默认）。

升级后，已执行的快通道环节中符合升级后路径要求的部分可保留，不符合的部分必须重新执行。

## 7. 预检落实记录

本节是预检落实记录格式的唯一领域来源；00 只定义事实预检根触发，检查机制与辅助机制规范只定义检查与辅助机制，不另设字段。

### 7.1 定位

预检落实记录是规则遵守系统的机械承载（检查机制与辅助机制规范将其领域分工指向本文），用于记录 AI 在承接业务动作前已完成的预检结论，使规则遵守系统的结论可回指、可恢复、可验证。本文不以此替代检查机制与辅助机制规范关于「遵守成立不等于行动完成」的职责边界；预检落实记录完成不等于业务系统执行完成。

预检落实记录与《事实源与事实模型基础规范》事实对象中的 `partial_scope` 是不同语义：

- 预检落实记录是当次行动前已确认的**预检结论聚合**（生效/适用/行动允许、已召回、未验证范围、快通道声明、升级记录），是"预检的输出"；
- `partial_scope`（事实源与事实模型基础规范定义）是事实对象**部分成立时记录未覆盖范围**的字段，是"事实写入的输出"。

两者经常同时出现（一次写入若只覆盖部分范围，预检落实记录会与 `partial_scope` 一起被生成），但本文不替代事实源与事实模型基础规范对 `partial_scope` 的定义。两者按各自规范回读，互不替代。LDVH CLI 确定性服务规范可按统一 envelope 把预检落实记录与 `partial_scope` 等事实字段组合到一次交还中，但组合动作属于 LDVH CLI 确定性服务规范的服务边界，不改变两者的独立语义与各自验证入口。

### 7.2 公共格式

预检落实记录使用以下公共格式，在行动交还时一并呈现：

```text
[预检落实记录]

- 生效规则：<已确认生效的规范/事实来源列表>
- 适用规则：<已确认适用的具体规则和引用>
- 行动允许：<已确认的授权范围和边界>
- 已召回：
  - ADR：<按 ADR 类型来源定义的当前适用 ADR 及适用结论；若未触发则标记未触发>
  - Pitfall：<按 Pitfall 类型来源定义的当前适用 Pitfall 及规避结论；若未触发则标记未触发>
- 未验证范围：<明确未验证或无法验证的范围>
- 快通道声明：<如使用快通道，说明适用依据>
- 升级记录：<如从快通道升级，说明触发原因、停止范围、补齐的预检和恢复依据>

快通道时，"已召回"区只记录适用来源要求的召回；未要求的全量召回应明确标记"未遍历"，不得把未遍历写成已核对。标准或加固路径时，按适用来源要求列出实际完成的召回及其适用结论。
```

该格式是交还语义示例，不是对 LDVH CLI 或 Code 的字段登记。具体业务系统可以扩展该格式，但不得省略预检落实记录，也不得用"预检已完成"一句话替代实际内容。

### 7.3 复用条件

预检落实记录只可在以下低成本可观察条件全部满足时直接复用：

1. 同一会话的连续行动步骤中，Human 目标、工作对象和当前行动范围未发生实质变化或超出上次覆盖范围；
2. 上次记录后，当前 Working Tree 中作为预检依据的规则源和事实载体没有发生变更；
3. 未出现新的召回触发、风险升级、能力缺口或 Human Gate 信号。

不满足时，必须重新执行受影响部分的预检并形成新的预检落实记录。AI 不得以"无法证明没有变化"为由无差别重扫全部规则源或事实源；只核对当前行动所依赖的可观察范围。

## 8. 降级路径

### 8.1 降级原则

当业务系统执行中遇到能力不足、验证失败、结果不可观察或环境限制时，应按以下顺序降级，不得伪造成功或静默跳过：

1. **缩小范围**：把行动缩小到当前能力和验证可支持的范围，如实报告剩余范围；
2. **风险重分类**：只有重新评估确认风险已经降低且目标、授权、来源规则和最低预检覆盖仍满足，才可从加固路径切换到标准路径；不得把能力不足、验证失败或结果不可观察直接降为更轻路径；重分类依据必须进入预检落实记录；
3. **切换系统或技术**：转交另一个仍然适用且验证要求不被降低的业务系统，或改用已验证的宿主技术（按环境接入与 Code 的实现规范）；不得把技术清单写成固定仪式；
4. **暂停交还**：无法继续时，暂停受影响范围，形成完整的交还报告并提请 Human 决定。

能力不足分流不是风险降低证明。不得以"降级"为由跳过已经触发的验证入口、掩盖失败、产生超出授权范围的实际副作用，或把 partial/unverified 结果表达为完成。

### 8.2 降级声明

降级发生时必须：

1. 明确声明降级原因和触发条件；
2. 说明降级后的路径、范围和能力差异；
3. 说明因降级而跳过或简化的环节和验证；
4. 说明降级后的残留风险和未验证范围；
5. 如降级到暂停交还，完成完整交还结构。

### 8.3 降级禁止

以下情况不得降级：

- 降级后将违反来源规则的强制要求；
- 降级后无法完成本文 §6.2 定义的最低预检覆盖（其根边界见 00 §5.7）；
- 降级后的行动超出 Human 已明确授权范围；
- 不得**临时修改适用规则**（包括临时放宽规范、临时改写已冻结授权包、临时变更已登记的验证条件）以使降级显得"合法"或"满足条件"。这不禁止**另行按规范模型 与受控提交与机械守护规范的受控流程对规范、受保护文档或授权包做独立修改**——此类修改属于规范/授权变更流程，须相互独立地分别评估、审核、Human Gate 与提交，不得与当次降级动作打包；它只禁止把"为了能降级"作为修改规则的动机。

## 9. 六大业务系统的职责

本章承接 00 §3.4 的六项业务系统根定义，展开各系统的职责、判据、机制指向与边界。

**本章与业务系统规范段的关系**：本章定义各系统的**基础职责与边界**；业务系统规范段（编号落在业务系统号段内的独立规范）在同一职责与方向上承接各系统的**专属流程、步骤与领域机制**，不得改变本章的职责根边界。二者的分工与迁移路径见 §10。

### 9.1 目标规划

- **职责**：把 Human 的长期意图确立为可回指、可核对的项目目标；以 Goal 事实对象承载其结论。

- **判据**：目标陈述可判定且有明确引用顶点；子目标可观测；目标与结构、进展的偏离可识别并能回指依据。

- **机制指向**：目标确立与修订级联、子目标锚点；具体契约由 Goal 事实类型规范与环境接入规范承接。

- **边界**：目标不自动产生行动授权或完成结论；Goal 对象存在或状态为 active 不证明目标正确或子目标充分。

### 9.2 蓝图跟踪

- **职责**：校准项目蓝图使其与目标、结构和进展一致。

- **判据**：蓝图内容与目标、结构、进展的偏离可识别并能回指依据。

- **机制指向**：蓝图校准与空闲触发调度；具体契约由 Web 呈现与交互规范与环境接入规范承接。

- **边界**：蓝图不自动产生行动授权或完成结论；蓝图呈现不构成机械校验。

### 9.3 记忆存取

- **职责**：留存和取回项目的经验认识；从目标、判断、行动、结果、摩擦和反馈中形成候选认识，接收多入口候选并按其沉淀环节分流决定去留，空闲时自动维护记忆健康。沉淀环节承接对话中的灵感与经验，并以事实对象承载其产物，方向与未决问题归入 Spark；反思为本系统的一个机制，检查既有认识与经验是否仍然适用。
- **判据**：留存的内容有消费对象、适用边界和明确去向；候选认识可回指实际行动和证据；偶发现象与可复用模式可区分；反思产出的修订意见可回指其依据。
- **机制指向**：事实分层召回、事实类型准入、空闲自动维护与效用审计、沉淀分流路由与反思触发；具体契约分别由事实源与事实模型基础规范与事实类型规范、LDVH CLI 确定性服务规范与 Web 呈现与交互规范承接。
- **边界**：记忆留存不自动产生规则或授权；对象数量、页面呈现和单次复用不证明效用；反思结论不自动生效，须经相应规范或事实承载与 Human 决定。

### 9.4 调研吸收

- **职责**：围绕不掌握的问题搜集证据，直到不再产生新的确认认识，产出已证实、未证实与缺口三态证据。
- **判据**：调研问题明确；证据可回指来源；已证实、未证实与缺口范围可区分；停止条件可判定。
- **机制指向**：外部检索、事实证据链、三态证据结构与停止判据；具体契约由事实源与事实模型基础规范与事实类型规范、LDVH CLI 确定性服务规范与环境接入规范承接。
- **边界**：调研吸收产出事实证据，不自动产生行动授权或完成结论；调研结论进入事实源须满足 事实源与事实模型基础规范的准入。

### 9.5 工单执行

- **职责**：执行已批准的工单，以 WorkCase 承载其结论；工作包生命周期（批准→执行→复核→关闭→交还）在业务面上由本系统承接。
- **判据**：执行对象已获批准且授权边界清楚；实际进展、结果与残留范围可回读；中断后有恢复路径。
- **机制指向**：工作包生命周期、WorkCase 类型契约、attempt 令牌与冷恢复；具体契约由 WorkCase 事实类型规范、本文与具体业务系统规范、环境接入规范承接。
- **边界**：执行不自我授权，不以"已批准"扩张授权范围；子代理完成不等于主控完成；执行完成不自动等于复核通过或整体完成。

### 9.6 规则遵守

- **职责**：识别并落实当前适用的规则、事实、决定和授权，使约束实际改变行动。
- **判据**：适用条件、授权、禁止动作和未验证范围可回指；应暂停或缩小处实际执行。
- **机制指向**：规范源、事实来源、预检结论机械承载、既有行动结构、Human 决定与宿主权限；具体契约分别由规范模型、事实源与事实模型基础规范与事实类型规范、本文与具体业务系统规范、00 §4 与环境接入规范承接。
- **边界**：事实、经验和预检记录不成为规则源；低风险行动不自动全量召回或触发 Human Gate。遵守成立（含预检落实记录完成）不等于行动完成。

## 10. 能力承载

能力承载（两族）提供实际手段，**不独立产生业务结论**（00 §3.1）。本章定义其共同职责、判据、机制指向与边界；具体契约由相邻规范承接，见各节「机制指向」。

### 10.1 读

- **职责**：取得当前工作所需且来源明确的规范、事实、状态和能力信息，控制上下文负担。
- **判据**：实际使用的信息可回指来源；候选、片段、完整来源、已读和未读范围可区分。
- **机制指向**：规范分层读取、事实分层召回、LDVH CLI 读取、宿主引导与预算，以及 Web 呈现的 Human 阅读入口；具体契约分别由规范模型、事实源与事实模型基础规范、LDVH CLI 确定性服务规范、环境接入规范与 Web 呈现与交互规范承接。
- **边界**：读取成功不证明理解、适用、授权或完成。

### 10.2 写

- **职责**：把已经明确去向的内容通过来源允许的受控入口写入，并核对实际结果。
- **判据**：范围、身份、授权、当前基线、实际变化、回读和未验证范围可区分。
- **机制指向**：事实域受控写入与 CAS、LDVH CLI 受控操作、事实源与 Git 溯源、Code 实现与测试；具体契约分别由事实源与事实模型基础规范、LDVH CLI 确定性服务规范、受控提交与机械守护规范与 Code 实践与测试规范承接。
- **边界**：写不决定是否值得沉淀；工具成功和 commit 不证明事实语义或上层完成。

### 10.3 编排

- **职责**：调度子代理执行委派的工作，管理其通信、漂移防护、中断恢复、结果回收与成本控制；编排承载工作包运行，主控对工作包的业务结果承担整体责任。
- **判据**：委派有明确任务与验收边界；子代理产物被主控核对和整合；中断后有恢复路径；成本受闸门约束。
- **机制指向**：可续子代理、任务调度、通信信道、守护网关、成本控制与恢复机制；具体契约由环境接入规范承接，工作包生命周期模式由检查机制与辅助机制规范与工单执行系统规范承接。
- **边界**：编排是能力承载，不独立产生业务结论；子代理完成不等于主控完成。

### 10.4 注入

- **职责**：按来源定义的时机与预算，把来源明确且不复制规则正文的引导内容推入当前会话上下文，使主控在无须自行检索的前提下取得最小充分的方向约束；注入由宿主原生机制承载，与 §10.1 的读（由主控按需发起）分工不重叠。
- **判据**：每次注入的触发时机、范围与预算可回指其来源定义且可观察；注入内容与单一权威来源的一致性要求、以及不得构成第二规则源的要求，按环境接入规范承接，本节不重复其判据；未注入、注入不足或注入失败时可如实区分。
- **机制指向**：最小规则引导的内容锚点、注入顺序、预算与触发时机，以及宿主注入面（会话冷启动入口与行动前入口）与宿主承载；具体契约分别由规范模型的规则引导节与环境接入规范承接。
- **边界**：注入是能力承载，不独立产生业务结论；注入存在不证明主控已理解、已遵守或已应用所注入内容；注入不替代 §10.1 的读、事实召回或适用判断，也不因内容进入上下文而使被注入文本取得规范效力、事实或授权（00 §3.2）。注入以只读为限：不得写回事实源、不得改变对象状态。

## 11. 业务系统规范的公共结构约束

### 11.1 准入条件

候选业务系统同时满足以下条件时，才可进入业务系统规范段中的具体业务系统规范正式起草：

1. 其职责已在 00 §3.1 登记，或按 00 §4.2 取得 Human 决定后新增、删除或改名；本文不改变该系统在 00 中的名称与职责原文；
2. 有可回指的重复价值依据，说明相同或实质相近的业务场景会再次出现；
3. 移除领域规则、项目强制要求、具体事实语义和平台细节后，仍存在相对稳定的进入条件、流程关系、失败分流、验证入口或交还结构；
4. 能明确说明适用场景与不适用场景，以及与相邻业务系统、能力承载和制度的边界；
5. 已有正式来源承担该系统所引用的规则、授权、事实语义和验证成立条件；
6. 已比较普通说明、现有规范章节、事实对象、Code/tests 和一次性计划，确认独立业务系统规范是净负担最低的承载位置。

### 11.2 系统声明

每个具体业务系统必须在其唯一定义来源正文中使用唯一的 H3 标题 `业务系统声明`，以如下真实表头逐行声明：

| system_key | summary | activation_hint | definition_ref |
|---|---|---|---|
| `<小写 ASCII kebab-case，全局唯一>` | `<一句话摘要，不替代 00 §3.1 的正式职责>` | `<提示 AI 何时应继续读取该系统规范>` | `<回指同一来源的唯一定义章节>` |

`system_key` 只识别具体业务系统，不证明适用、授权、执行、验证或完成。`activation_hint` 只帮助 AI 选择是否继续读取候选系统，不是必要且充分的适用条件。`definition_ref` 必须回指同一来源正文中承担该系统完整职责展开的唯一 H2 或 H3 章节。具体业务系统的唯一定义来源可以是业务系统规范段中的独立规范，也可以是已有规范中自然承接该系统责任的章节。系统声明只作为机器读取入口，不替代正文中的完整定义。

### 11.3 共同结构（必填内容与扩展规则）

每个具体业务系统（业务系统规范段）必须使下列十项共同结构在正文中可定位，全部为**必填内容**，不得省略或用一句泛指替代。10 项之间不规定固定线性顺序，但**每一项都必须出现且只能以一项对应**。

**本十项与其它必填结构的关系（重要，避免遗漏）**：本节十项**不是**业务系统规范的全部必填结构，**满足十项不足以形成合规规范**。一份合规的业务系统规范还**同时**必须满足：

1. **`01 §7.1/§7.3` 的固定章节**——固定前置四章（`## 1. 价值判断`、`## 2. 规范依据`、`## 3. 职责边界`、`## 4. 适用范围`；其中 **§1、§2 按规定的段落顺序表达**，**§3、§4 各须使用规定的三个 H3**——依 `01 §7.1`）与固定收尾四章（`验证与证据边界`、`Human Gate`、`必停情形`、`反过度设计红线`），编号随领域正文连续顺延。**这八章由 `01` 强制，不属本节十项，也不属「系统扩展」**；本十项与它们的关系是**并列的必填集合**，二者共同构成完整骨架。**各固定章节的具体表达要求以 `01 §7.1`/`§7.3` 原文为准，本节只声明其为必填，不复制、不转述其细则。**
2. **本文 §11.2 的「业务系统声明」**——以**唯一 H3 标题 `业务系统声明`**（不是 H2）承载 `system_key`/`summary`/`activation_hint`/`definition_ref` 四列表头。**该声明在本十项之外，但同为强制**，强制力来自 **§11.2 本节自身**，并受 §11.1 准入条件约束（`01 §9.2` 是普通规范的一般成立条件，未提及本声明，故不构成其依据）。

**判定粒度说明**：上句「每一项都必须出现且只能以一项对应」的主语是**本节十项**，含义为「十项中的每一项在规范正文中有唯一落点」；它**不禁止**某一项的内容由多个相互衔接的章节共同展开（如「过程机制与分支」可由若干机制章构成）。以该方式承载时，应在其中**一个锚点章显式标注**该项与其余衔接章的归属关系，使落点可机械定位。

| 序号 | 必填结构 | 必须表达 |
|---|---|---|
| 1 | 系统定位与价值 | 稳定身份、`system_key` 与 00 §3.1 登记名的对应关系、解决的持续业务问题、服务哪些消费方与 V/HV |
| 2 | 职责根边界与回指 | 00 §3.1 职责原文回指、本文不改根定义的声明、本系统不产生授权或完成结论的边界 |
| 3 | 进入与退出契约 | 进入信号、适用条件、排除条件、不确定处理、当次作用范围、退出与转交条件 |
| 4 | 输入与前置条件 | 必需与可选输入、来源、缺失和冲突处理 |
| 5 | 过程机制与分支 | 关键机制、先后顺序或并行关系、失败分流、停止位置 |
| 6 | 结论承载与回写 | 本系统以何种事实对象或载体承载结论，是否必须写入、目标来源、回读要求；不承载结论的系统须显式说明 |
| 7 | 风险路由与预检要求 | 引用 §6 风险层与升级、§8 降级路径的对应条款，以及该系统的最低预检覆盖（快通道/标准/加固）；不得在 §9 内重复定义风险层名称、升级触发或降级顺序 |
| 8 | 验证 | 验证对象、入口、依据、可证明范围和未满足处理 |
| 9 | 交还 | 当次状态、结果与证据、已验证和未验证范围、残留风险和待决定事项 |
| 10 | 与相邻系统及能力的边界 | 与相邻业务系统、能力承载（读/写/编排）和制度（主控自查/独立复核/机械校验）的分工，以及与相近概念的区分 |

**扩展规则**：

1. 业务系统规范段可在每一项必填结构下增加子项、限定词、字段或示例，但不得删除、合并、跳过或降低任一项必填结构的最小表达；扩展内容不得与 业务系统基础规范§5–§8、§13 冲突；
2. 业务系统规范段可在十项必填结构之外增加该系统独有的补充结构（如专属错误码、专属回写目标、专属 Human Gate 触发条件），新增结构必须以单独 H3 列出并显式声明为"系统扩展"，不得挤占任一必填结构的位置；
3. 业务系统规范段不得自行增设 §6.1 风险层（不得新增介于快通道与标准路径之间或标准与加固之间的中间层级），不得修改 §5.5 三层评测的定义，不得修改 §7.2 预检落实记录的公共字段名；
4. 业务系统规范段可在本文 §11.2 系统声明四列表头之外补充系统级元数据（仅作发现入口增强，不替代四列表头）；
5. 业务系统规范段的流程编号、命令清单、字段命名等技术细节可由各系统按领域习惯自由选择。**澄清（避免歧义）**：`definition_ref`（§11.2）指向**同一来源正文中承担该系统完整职责展开的唯一 H2 或 H3 章节**，是**每份规范一个**的登记入口，作用域为**整份规范**；上句**不要求**技术细节逐项回指各自的章节。技术细节只需保证：(a) 本规范整体有唯一的 `definition_ref` 且其目标章节确实承担完整职责展开；(b) 技术细节不改变 00 §3.1 的职责，也不引入本节十项与 `01 §7` 之外的强制要求；
6. 业务系统规范段不得改变 00 §3.1 已登记的系统名称与职责，也不得以"便于实现"为由改写其它业务系统的职责边界。

### 11.4 更新、合并与退出

具体业务系统规范的修改、合并或退出，必须重新检查 §11.2 准入条件，并按 01 §11 与 §8 登记规则核对编号登记（仅在规范编号或规范承载发生变化时更新）。系统被替代或取消后，原 `system_key` 保留历史指向且不得重用。系统退出后，其业务职责仍可由普通求解或其它系统承接，不因规范退出而自动取消能力覆盖；系统数量的增减本身属 00 §4.2 Human 根决定事项。

历史口径处置（替代说明）：本规范**实质替代**了已退出的 `action-template-foundation`（旧称"行动模板基础规范"）——旧规范定义的是可复用行动结构的共同机制，本规范定义的是六大业务系统的共同结构与公共机制，二者不是同一职责的改名。旧规范名下的具体模板语义不再作为当前规则源成员消费；其可复用行动结构方面的既有内容，在相应业务系统规范（业务系统规范段）按本文 §9 承接之前，不取得规范效力。本文不追溯解释旧模板条目的逐项去向。

## 12. 验证与证据边界

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 进入与退出契约 | 系统规范起草、设计基线确认或执行前 | 进入信号、适用条件、排除条件、不确定处理、作用范围和退出条件均已定义 | 系统正文与本文 §5.1 | 结构检查与 AI 语义审核 | 当次系统候选的机械边界；不证明系统适用或行动允许 | 暂停适用判断，补齐契约或改用其它路径 |
| 系统停止条件 | 系统定义或流程执行中 | 每个系统的独有停止条件已定义并承接 00 §5.7 | 系统正文与本文 §5.2 | 结构检查与执行中识别 | 当次流程环节的暂停边界；不证明环节完成或验证通过 | 触发时按 00 §5.7 暂停最小受影响范围 |
| 反逃避信号 | 系统执行中 | 信号已定义，AI 能在执行中识别并触发停止或降级 | 本文 §5.3 与执行记录 | 聚合记录核对 | 当次逃避行为的识别；不证明逃避行为已纠正 | 触发即进入 §14 停止序列或 §8 降级序列 |
| 结论门禁 | 系统结论声明前 | 全部必要条件成立，声明不超过实际支持范围 | 本文 §5.4 与当次验证记录 | 结论门禁逐项核对 | 当次系统执行的结论状态；不证明价值成立或长期效用 | 只能形成 partial/unverified 交还，不得宣称结论成立 |
| 分层评测 | 每次系统执行交还时 | 流程完成层/验证通过层/交还承接层分别交还，不混用 | 本文 §5.5 与交还内容 | 分层交还核对 | 当次执行的分层结果；不证明下级评测自动成立 | 修正分层表达后重新交还 |
| 风险路由与快通道 | 系统起草或路径选择时 | 层级、判断标准和声明方式按本文 §6 统一定义，下位系统未自行增设层级 | 本文 §6 与系统声明 | 路由声明核对 | 当次风险路由选择；不证明快通道假设始终成立 | 按实际风险升级路径并补齐预检 |
| 预检落实记录 | 行动交还时 | 格式按本文 §7 定义，预检结论可回指、可恢复、可验证 | 预检落实记录与本文 §7.2 | AI 语义审核与记录回读核对（**字段无机器载体，仅人工核对**） | 当次预检的完成范围和结论；不证明预检结论长期有效 | 不满足复用条件时重新执行受影响预检 |
| 降级路径 | 降级发生时 | 降级顺序、声明要求和禁止条件按本文 §8 定义 | 降级声明与本文 §8.2 | 降级声明核对 | 当次降级的路径和范围；不证明降级后能力已覆盖 | 按禁止条件停止降级并交还 |
| 业务系统规范段共同结构 | 系统规范起草、修改或退出前 | **三类必填结构齐备**：① 本节 §11.3 十项共同结构可定位；② `01 §7.1/§7.3` 固定八章齐备且标题逐字（§3/§4 另须规定 H3）；③ §11.2 唯一 H3「业务系统声明」存在——**三者缺一即不合规，结构齐备不等于职责已承接**；另须准入条件重检通过、扩展未挤占必填结构 | 本文 §11 与系统规范正文 | 结构角色逐项核对；固定八章标题与声明 H3 的级别/唯一性可机械解析 | 当次规范的结构完备性；不证明领域语义正确、职责已被实质承接或已获 Human 确认 | 补齐缺失结构或移除越界扩展后重新进入确认 |
| 反过度设计红线 | 系统起草或修改时 | 每条红线含对象与禁止行为，起草和执行中可对照 | 本文 §15 与系统规范正文 | 红线逐条对照 | 当次系统的红线遵守情况；不证明系统整体无过度设计 | 移除越界内容后再进入确认 |

机械结果与语义判断互不替代。业务系统的机械结果只交还当次已证实、未证实、partial/unavailable 范围和残留风险，沿用 00 §5.8 的交还结构，并作为主控 Output Envelope 的输入，不替代主控交还；本章不能单独证明系统适用、行动允许或 V/HV 价值成立。本文不建立价值审计报告、外部证明材料或过程留痕工件。

**未验证范围的处置要求（条件式）**：本文 §11.3 的十项共同结构与 §11.2 的声明，其生效不依赖于业务系统规范段是否已建齐。**业务系统规范段尚未建齐期间**：援引本文时不得声称「业务系统规范段已完备」或「六系统均已按 §11.3 对齐」；未建立的系统编号不得被当作已存在、已登记或已进入当前规则源。**既有独立规范尚未承接某系统专属流程期间**：本文 §9 的内联展开即该系统的唯一定义来源，不得因业务系统规范段的存在而认定本文 §9 的展开失效。

本节只承载要求，不登记条件是否已兑现；兑现情况属实现现状，按 `01 §7.2` 由读取时的观察取得，规范不设状态登记载体。

## 13. Human Gate

本文不新增 00 之外的 Human Gate。

### 13.1 领域增量事项

以下事项是 00 §4.2 在业务系统领域的具体化：

1. 新增、删除、改名或重排业务系统或业务系统编号（00 §3.1 与 §4.2 已列为 Human 根决定事项，本文只登记其在业务系统规范段的具体落点）；
2. 改变业务系统五机制的定义、数量或效力边界；
3. 改变快通道的层级数、判断标准或声明方式；
4. 改变预检落实记录的公共格式；
5. 具体业务系统需要改变正式规范责任或载体，且按 01 完成承载比较后仍无法收敛；
6. 系统执行中涉及来源规则保留给 Human 的授权、方向选择、风险接受或验收决定。

### 13.2 决定边界

Human 决定只证明决定及其作用范围，不替代系统条件、技术验证、回读结果或事实语义审核。系统授权受 00 §4 的 Human 决定权和 00 §5.4 的 AI 实施边界约束；授权包结构与冻结语义待 WorkCase/授权承接规范定义。

## 14. 必停情形

本文不新增根停止类型。

### 14.1 领域触发与影响范围

以下条目是 00 §5.7 根停止条件在业务系统执行域的具体化。出现任一情况时，暂停受影响的最小系统选择、流程环节、执行或结论声明范围：

1. 适用条件、必需输入、授权、写入范围或对象范围无法确认，却准备按名称相似或默认值执行；
2. 必需能力未实现、未接入、被拒绝、部分可用或结果不可观察，却准备假定能力成功或跳过失败分流；
3. 系统选择、环节完成、工具成功、Human 回应或 commit 正在被直接声明为验证通过或行动完成；
4. 实际失败、拒绝、部分结果、未验证范围、副作用或残留风险没有进入交还，却准备结束当次系统执行；
5. 快通道执行中发现实际风险超出快通道假设，却未按 00 §5.7 停止、补齐预检和恢复；
6. 预检尚未完成或预检落实记录缺失，却准备进入受控执行；
7. 降级将违反来源规则强制要求、无法完成最低预检覆盖、超出授权范围，或需要修改规范/受保护文档；
8. 系统执行命中了 00 §5.7 或具体业务系统的独有停止条件，却准备继续推进或静默跳过；
9. 具体业务系统规范的正文与 00 §3.1 已登记的系统名称或职责冲突，却准备按系统规范正文继续消费。

候选准入阶段另须按 §11.1 检查根职责回指、重复价值、稳定结构、来源完整性和承载边界；系统规范定义与 00/01、具体系统来源或 Human 已定决策冲突时，按本节与 00 §5.7 停止起草或消费。上述静态治理检查不是每次运行时步骤前的重复检查。

### 14.2 暂停期间允许动作

暂停期间只允许不越过停止边界的来源定位、事实核对、证据收集、验证、修复和分流准备，不得继续受影响系统流程、写入或结论声明。

### 14.3 恢复与再次触发

恢复条件必须与触发原因对应，且只覆盖当前依据支持的范围；同一停止条件恢复后再次触发时按 00 §5.7 进入 Human Gate。根停止的全部边界以 00 §5.7 为唯一权威，风险匹配以 00 §5.9 为准，本节不重新展开。

## 15. 反过度设计红线

1. 不在本文与业务系统规范段定义通用状态机或预设系统执行状态闭集；执行进度属当次行动单元信息，事实类型状态机由事实源与事实模型基础规范与各事实类型规范定义，本文只回指。
2. 不建立全局事务机制；多对象原子操作由事实源与事实模型基础规范与受控提交与机械守护规范定义，普通流程环节按顺序执行、失败按分流路径处理，不要求全局回滚。
3. 不因系统结构对每一环节强制复核；复核只在涉及高风险操作（写入受控事实、修改规范、提交）、结果将作为后续关键输入且不可逆、或失败可能造成数据丢失或规则冲突的环节必要，其余由复核与校验制度自主判断。
4. 不为系统执行产生独立的过程日志、审计账本或外部簿记工件；防自欺锚点为预检落实记录与事实回读结果（对象级 `change_log` 由事实源与事实模型基础规范承担，见 §3.2），不需要额外留痕证明"执行过"。
5. 不把业务系统集合当作 AI 行动的许可白名单；未匹配系统不阻断普通求解、不要求先新增系统，也不把最相近系统强制套用到当前事项。
6. 不把系统流程中的工具成功、命令成功、文件存在、页面呈现或 Human 回应单独写成环节完成或验证通过；每环节完成由该环节的输出条件和验证入口共同支持。
7. 不在本文或业务系统规范段复制 LDVH CLI 确定性服务规范的 envelope、Code 实践与测试规范的实现细节、受控提交与机械守护规范的提交契约、事实源与事实模型基础规范的事实域契约、管辖范围规范的管辖解析、环境接入规范的接入协议或 Web 呈现规范的呈现细节；调用时只回指相应规范的对应章节，如发现复制或近似复制，相关条款无效，由该领域的唯一权威解释。
8. 不为编号整齐或未来可能扩展而新增业务系统；六个系统的数量、名称与职责以 00 §3.1 为唯一权威，本文不在业务系统规范段之外预留系统空位。
9. 不把业务系统写成必须依次经过的流程；系统可并行、回跳或按需跳过未触发职责，具体协同由检查机制与辅助机制规范 §10.1 与主控按风险选择。
