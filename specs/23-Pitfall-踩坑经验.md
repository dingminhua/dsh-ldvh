# Pitfall-踩坑经验

## 1. 价值判断

Pitfall 解决已验证的踩坑经验随对话消散的问题：一次失败实际发生、查明根因、解决并验证之后，它的症状识别信号、触发条件、根因判断、实际方案与规避方式——若只存在于会话记录或散落备忘，后续行动无法在事前预检时对照已知坑位，事后调查时找不到「以前踩过什么、怎么解的」，同一错误重复踩、同一调试反复做（00 §1 痛点 4）。Pitfall 以知识层对象承载已验证经验：回溯记录、前瞻消费——执行前预检与故障调查时被引用。普通文件不能无损承载：无受控写入、无状态闭集（active/discarded 无从机械判定）、无预检的匹配投影。Spark 是未定悬置；Research 是外部证据；ADR 是决策记录——Pitfall 是「什么会出错、怎么识别、怎么规避」。

主要支撑 V3 边界识别（行动落入已知坑位的影响范围时经预检暴露）、V5 据实判断（症状匹配可回指「哪条 Pitfall」）、V6 工作接续（跨会话恢复经验基线）与 V8 持续积累（相似场景直接复用规避经验，不再重复调试）；HV3 入档闭环节点可验（创建与终态可回读）与 HV5 项目演进脉络可循（项目踩过的坑与解法构成经验史）。

Pitfall 对象存在、处于 active 或形成经验积累，均不能单独证明经验仍然适用、被实际消费或真的避免了损失——经验的价值须在预检、故障调查的真实消费中核对；经验的积累规模也不证明积累效用（HV4 须由实际复用与可观察损耗避免核对）。Pitfall 是经验事实不是规则来源：avoidance 不取得 MUST 级规则权威，需要强制做法时由规范源另行定义（00 §3.3）。

## 3. 职责边界

### 3.1 本文负责

1. Pitfall 类型的对象边界（已验证失败机制的构成、查重、明确不属于本类型的内容）；
2. Pitfall 的身份与载体（多例、平铺单文件、`ldvh-base/pitfalls/pitfall-<uid>.md`）；
3. Pitfall 的字段契约（frontmatter 薄索引闭集、正文固定 H2、字段间不变量）；
4. Pitfall 的状态闭集（active/discarded）与终态处理；
5. Pitfall 的召回与消费点（执行前预检、故障调查、Web 知识库呈现）；
6. Pitfall 的受控操作（创建、勘误与补充级更新、终态流转）。

### 3.2 本文不负责

1. 遵守预检的完整判定逻辑（02 §13 承载，本文只定义消费语义接口）；
2. WorkCase 执行期的 Pitfall 发现与授权集成（预留编号 21 号承载——21 建成前创建入口只有 AI 提案与 Human 直接提出两路）；
3. 调研执行与 Research 类型语义（30 号、24 号承载）；
4. Human 确认经验有效性的过程（00 §4 承载——Pitfall 记录已验证经验，验证本身是创建前提）；
5. Web 呈现的视觉与交互细节（10 号承载）。

### 3.3 相邻规范分工与唯一权威

03 是公共字段与受控读写契约的唯一权威；06 是事实源与受控提交的唯一权威；02 §13 是遵守预检的唯一权威；21 是 WorkCase 集成的唯一权威；22/24 分别是 ADR/Research 类型语义的唯一权威。本文只定义 Pitfall 类型自身的边界、字段、状态与消费点，不复制相邻规范的规则。

## 4. 适用范围

### 4.1 适用对象

1. 管辖项目中的多例 Pitfall 对象（`ldvh-base/pitfalls/`）；
2. Pitfall 的症状、触发、根因、解决、规避、验证与影响范围记录。

### 4.2 适用场景

本规范用于 Pitfall 的创建（执行中发现经提案确认、Human 直接提出）、查重、勘误与补充级更新、终态流转（废弃）与消费（执行前预检、故障调查、Web 呈现）。

### 4.3 明确排除与证明边界

明确排除：未解决的问题（问题没查明/没解决/没验证时不该有 Pitfall——那是当次行动或 Spark）；未发生实际失败的假想风险（预防性记录不成立，必须有实际发生与验证）；已定决策（ADR）；外部证据（Research）；日志与自由标签。Pitfall 对象存在或状态为 active，不能单独证明经验适用、被消费或避免了损失——这些须由预检与故障调查的真实使用核对。

## 5. 类型定位与价值

Pitfall 是知识层的事实类型：承载已验证失败机制的回溯记录，供前瞻消费。与同层的 ADR/Research 分工——ADR 回答「为什么这么定」，Research 回答「外部世界是什么」，Pitfall 回答「什么会出错、怎么识别、怎么规避」。

按 03 §5.2 准入六问：跨行动保留——经验基线必须跨会话稳定，否则同一坑重复踩；独立身份与状态——经验有 active/discarded 与适用性衰减，需要独立生命周期；普通文件不能无损承载——无受控写入、无状态闭集、无预检投影；消费价值服务 AI（预检/调查）与 Human（Web 经验库）双轨；维护成本——低频类型（v4 实证数十量级），净值为正；类型定义来源——本规范。

## 6. 对象边界

### 6.1 什么构成一个对象

一个 Pitfall 对象 = 一项可独立引用的已验证失败机制：症状识别信号 + 触发条件 + 根因判断 + 实际采用的解决方案 + 规避方式 + 验证说明 + 影响与适用范围。机制必须可独立召回、可独立预检匹配（行动落入影响范围时能指向「哪条 Pitfall」）、可独立终态（不再适用时单独废弃）。

### 6.2 查重

创建前必须查重：对照既有 active Pitfall 的 title 与症状/根因语义比对（AI 语义判断，03 §8.2 不建立相似度自动裁决）。同一失败机制的新表现或新触发样例已存在时，不新建——走补充级更新并入既有对象；不同机制的相似症状（根因不同）各自成对象。查重结论必须记录在创建提案中。

### 6.3 明确不属于本类型

单次调试过程未收敛为经验的内容（留在会话记录）；预防性假设（未实际发生的风险不记录）；已由规范源吸收为强制规则的规避（规则由规范源承载，Pitfall 可作为经验来源被引用但不再独立承担约束）。

## 7. 身份与载体

| 项 | 定案 |
|---|---|
| `fact_type_key` | `pitfall`（类型短名，03 §6.1 值域） |
| 载体 | 平铺单文件：YAML frontmatter（机器权威）+ markdown 正文；`ldvh-base/pitfalls/pitfall-<uid>.md` |
| 权威位置 | `ldvh-base/pitfalls/`；目录基数校验，文件名编码 UID |
| 公共字段 | `object_uid`（UUIDv4，Code 生成）、`created_at`（Code 填写）、`change_log`（Code 托管流水） |

创建与变更权：创建与终态流转都必须经 Human 决定（经验的入档与废止是 00 §4.2 领域具体化）；勘误与补充级更新走受控更新（change_log 留痕），影响范围的实质变化走新对象。

## 8. 字段契约

frontmatter 闭集（分析性长文本一律住正文，frontmatter 只留薄索引）：

| 字段 | 类型 | 必填性 | 语义 | 约束 |
|---|---|---|---|---|
| `fact_type_key` | string | 必填 | `pitfall` | 唯一合法值 |
| `object_uid` | UUIDv4 | 必填 | Code 生成 | 创建时落定，永不改变 |
| `title` | string | 必填 | 失败机制短标题 | ≤ 30 字；简短识别机制，不复制症状全文；平台/环境专属时凸显平台 |
| `status` | string | 必填 | `active` / `discarded` | 初态必为 `active` |
| `scope` | string | 必填 | 影响与适用范围陈述 | 正文「影响与适用范围」段逐字包含；哪些活动/工具/交互可能落入 + 经验可信复用的边界 |
| `trigger_signal` | string | 条件 | 重新审视信号 | 存在真实重审前提时写（依赖版本变更、环境迁移等）；无则省略（03 §6.1） |
| `urls` | array | 条件 | 支撑经验的外部 HTTP(S) 证据 | 出现时非空；`urls` 非空 ⇒ 正文「证据」段必填 |
| `disposition` | string | 条件 | 终态去向与理由 | 仅 discarded 时必填；说明废弃依据（前提消失/机制不存在/经验失效）；**≤ 200 字符**（终态原因说明的阅读上限，§9.1） |
| `created_at` | RFC3339 | 必填 | Code 填写 | AI 不得填写 |
| `change_log` | array | 条件 | 变更流水 | 首修后必有；每次恰好一条 |

不设 `symptoms`/`trigger_conditions`/`root_cause`/`resolution`/`avoidance`/`validation` 等 frontmatter 字段——六要素是分析主体，住正文；`trigger_signal` 是短句信号例外（同 22 号先例）。

正文固定结构（H1「# 标题」由 Code 从 title 生成、位于围栏后首行，正文自 H2 起；此处不直书 H1 字面以免与身份 H1 重复）：

```
## 症状            ← 失败实际发生后的可观察表现与识别信号（必答：识别信号是什么）
## 触发条件        ← 会触发该机制的前置条件、组合与上下文（必答：什么条件下会触发）
## 根因            ← 当前经验范围内能解释症状与触发的机制判断（必答：机制判断+已观察/未知的区分）
## 解决            ← 已实际采用的处理方式与成功信号（必答：做了什么+成功信号+必要边界）
## 规避            ← 后续识别、预防或安全复用该经验的方式（必答：核对条件+动作+例外）
## 验证            ← 已观察结果、覆盖与未知范围（必答：已观察什么+未覆盖什么）
## 影响与适用范围  ← scope 逐字 + 展开：何时可能踩到、经验何时可信（必答：何时踩到+何时可信）
## 证据            ← 支撑经验的外部引用（可选；urls 非空时必填）
```

字段间不变量：`scope` 载体内聚（正文段逐字包含）；`disposition` 出现 ⇔ `status=discarded`（active 禁现、discarded 必填非空）；未知字段不进入 canonical 对象，不得以空字段或占位代替判断。

## 9. 状态与生命周期

状态闭集两值：`active`（经验可信可复用）→ `discarded`（经验不再适用）。无第三个状态——v4 的 draft（Human 确认前快照）由创建前置确认替代：AI 只产出完整提案，Human 确认后经受控创建入口落盘，创建即 active，不存在「已保存但未确认」的中间态（同 22 号先例）。

### 9.1 状态语义与成立条件

| `status` | 语义 | 必须成立 |
|---|---|---|
| `active` | 经验已验证且仍可信，参与预检与故障调查 | `disposition` 不得出现 |
| `discarded` | 经验不再适用；保留为历史基线 | `disposition` 必填非空（说明哪个前提消失了）；不进入普通候选 |

**`disposition` 的长度上限（机械校验）**：`disposition` 不超过 **200 字符**（判定单位与本规范 `title` 的同名上限一致，均为 UTF-16 码元计数；实现按 `.length` 判定）。终态原因说明是给后续读者与人扫读的定位信息，不是完整处置记录——完整理由属于正文、`change_log` 或承接对象。超限时拒绝写入（与 §13 的受控写入前置条件同为机械条件，按 03 §9 的公共契约执行），不得截断后写入。

**判定的是数量而非语义**：本上限只约束长度，不判断说明是否据实、充分或与 `status` 相符——后者仍由 §15 的语义核对与 Human 废止授权承担。长度合规不证明终态处置正确。

### 9.2 状态转换

正常转换只有 `active → discarded`（Human Gate：经验废止）。终态不重开；错误终态记录按 05 事实更正规则修正。经验的根因判断或解决方案实质变化（不是补充新观察）时创建新 Pitfall；旧对象视情况废弃（前提消失则 discarded+disposition，机制仍存在则保持 active 各自独立）。

### 9.3 勘误与补充级更新

正文错别字、引用修正、表述澄清（不改变机制语义）以及**同一机制的新表现、新触发样例补充**（症状/触发条件段的扩展性补充是明确允许项）走 03 §9.5 受控更新，change_log 留痕。机械边界：更新后的 `scope` 逐字段不变（变了就不是补充——影响范围实质变化走新对象）；机械比对只覆盖 scope，其余段的语义不变性（补充与实质变更的分界）是 AI 审核义务：根因、解决、规避三段的实质更换不得以补充名义放行，须走新对象路径。补充的判别锚点是**与既有根因判断相容**——新表现、新触发起码要能被当前根因解释；根因解释不了的新触发不是同一机制的样例，是新机制，走查重与新对象。

## 10. 来源与证据

经验来源是实际发生的失败与验证：当次行动的观察、调试与修复记录（会话留痕）是第一来源，Human 提出的历史经验是第二来源。Pitfall 的创建前提是失败已发生、根因已查明、解决已采用、验证已有观察——四项不齐时不创建。`urls` 的来源回指语义遵循 06 §5 公共边界；内部证据以自然语言在验证段交代。验证说明必须区分已观察结果与未覆盖范围——「验证过什么」与「没验证什么」同样必答，不得以验证摘要冒充全面覆盖。

## 11. 关系契约

不使用 `relations` 字段（类型来源声明不采用）。理由：Pitfall 的替代与关联无独立机械消费价值——经验废止的谱系（被什么取代）由 `disposition` 自然语言承载；与 WorkCase 的贡献关联（该经验来自哪次执行）由 21 号 WC 侧的 `contributed-to` 承载（03 §7.2 第 4 条：反向引用不复制）；与 ADR/Research 的关联由正文自然语言交代。确有公共消费价值时由 03 提升公共契约再议。

## 12. 召回与消费

| 消费点 | 时机 | 消费内容 |
|---|---|---|
| 讨论系统依据装配 | 每次扩散前（31 §7.1） | 相关 active Pitfall 的 scope + 触发条件——陷阱规避依据：方案不得重蹈已知陷阱（31 §7.2 违背淘汰须记录违背的具体条目） |
| 遵守预检 | 行动可能落入已知影响范围时（02 §13） | title + scope + 触发条件 + 规避——「当前行动是否可能踩到此坑、踩到怎么规避」 |
| 故障调查 | 出现失败症状时 | title + 症状——按表现匹配已知机制，回溯根因与方案 |
| Web 知识库 | 蓝图渲染（10 号） | active Pitfall 列表与经验呈现 |

召回分层（03 §8）：F1 枚举 active Pitfall 计数（title + status + scope）；F2 按类型、状态、命中词的候选卡；F3/F4 按需展开。默认候选只含 active；discarded 不进入普通候选，只在精确引用或历史追溯时展开。AI 展开候选后必须重新核对当前行动/症状与经验的 scope 相容性——Pitfall 被召回不等于当前适用，预检匹配是 AI 语义工作（03 §8.2）。

## 13. 受控操作

- **创建**：AI 产出提案对象（含查重结论与完整七要素），Human 确认后经受控创建入口落盘——入口两路：执行中发现（当次行动失败已查明验证后形成提案）与 Human 直接提出（历史经验口述，AI 整理成提案）。机械校验：字段闭集合法、title ≤ 30 字、urls 形状、载体结构（H2 固定序 + urls 非空时「证据」段必在）、载体内聚（scope 逐字）。创建后精确回读。
- **勘误与补充级更新**：03 §9.5 受控更新；CAS 以完整文件为单位；每次恰好一条 change_log；scope 逐字段不变（机械比对，变了拒绝——走新对象路径）。
- **终态流转（discarded）**：Human Gate；AI 先精确读取 F3 核对 disposition 依据；Code 检查闭集、字段、CAS 与回读。
- **删除**：不存在删除操作。discarded Pitfall 随 `ldvh-base/pitfalls/` 保留为历史基线。

## 14. 类型特有验证与类型退出

### 14.1 类型特有验证

- 查重结果记录：创建提案必含查重结论（同机制已存在 → 走补充更新）；
- 载体内聚：scope 在正文「影响与适用范围」段逐字出现；
- 补充边界：更新的 scope 与 CAS 基线逐字段一致（防影响范围实质变化伪装补充）；
- 终态完整性：discarded 必有非空 disposition；且 disposition 长度不超过 200 字符（§9.1）；
- 状态-终态不变量：active 不得带 disposition。

### 14.2 存量对象迁移

无 v5 存量。v4 仓库的 Pitfall 实例按「v4 存量不迁移」（ADR `adr-1aad60bc`）保留在 v4 历史归档；经验若仍适用，在 v5 以新 Pitfall 重新记录。

### 14.3 类型退出

若 Human 决定取消 Pitfall 类型，须按 03 §10 处理：处理仍适用经验的转移承接与稳定引用，登记变化（01 §8.2）与受影响引用同步，走受控提交。退出属 00 §4.2 根决定。

## 15. 验证与证据边界

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 载体结构 | 创建、更新或精确读取时 | H2 固定序完整、各段非空、H1 与 title 一致 | 当前载体与本文 §8 | 机械（结构解析） | 当次载体结构合法性 | 拒绝创建/更新；修复后重走 |
| 载体内聚 | 创建与更新时 | scope 在正文对应段逐字出现 | frontmatter 与正文对照 | 机械（逐字比对） | 索引与主体一致性 | 拒绝；补齐后重走 |
| 补充边界 | 更新时 | scope 与 CAS 基线逐字段一致 | 更新前后 frontmatter 对照 | 机械（字段比对） | 当次更新的补充性质 | 拒绝；范围变化走新对象 |
| 查重已执行 | 创建时 | 创建提案含查重结论 | 提案记录 | AI 语义审核 | 当次查重范围 | 补查重后重走创建 |
| 终态完整性 | 终态流转时 | disposition 非空且据实，长度不超过 200 字符 | 对象全文 | 机械（字段校验） | 当次终态机械范围 | 拒绝流转；补齐后重走 |
| 经验质量 | 创建与终态时 | 四前提齐（已发生/已查明/已解决/已验证）、验证段区分已观察与未覆盖；各必填段逐段回答 §8 行内注记的必答问题——一句话段落必须答全（句子数不是判别轴，必答问题是否答全才是），影响与适用范围仅逐字转写 scope 不构成展开 | Human 确认记录 | AI 语义审核 + Human 终审 | 当次经验记录质量 | 拒绝或退回修订 |

机械结果与语义判断互不替代。本章不能单独证明经验适用、被消费或避免损失——这些由消费点真实使用核对；未实现与不可用范围保留为 gaps。

## 16. Human Gate

本文不新增 00 之外的 Human Gate。领域增量事项（00 §4.2 在 Pitfall 领域的具体化）：

1. Pitfall 的创建（经验的入档成立——含执行发现与直接提出两入口的记录确认）；
2. Pitfall 的终态决定（discarded——经验废止）；
3. Pitfall 类型本身的取消或合并。

### 16.1 决定边界

Human 决定只证明决定及其作用范围，不替代查重判断、载体校验、预检匹配判断或终态机械校验。本文成为当前规则源成员时的 01 §8.1 登记与受影响引用同步，按 01 §8.2 的登记变化义务随本次规范新建一并执行。

## 17. Stop Conditions

本文不新增根停止类型。领域触发与最小影响范围：

1. 创建时发现同机制 active Pitfall 已存在（重复经验风险）——未完成查重结论前不创建；
2. 创建前提不齐（失败未发生/根因未查明/解决未采用/验证未观察）却准备创建；
3. scope 为空或不可读；
4. 准备以更新改写 scope 实质或更换根因/解决/规避的语义（补充边界违例）；
5. 终态流转 disposition 缺失；
6. AI 未经 Human 确认直接创建或流转（授权缺失）；
7. 预检消费时 Pitfall 状态与引用不一致（引用了 discarded 经验为现行依据）。

暂停期间只允许不越过停止边界的证据补取、引用修复、授权补走与条件核实。恢复须与触发原因逐项对应；同一停止条件恢复后再次触发的，按 00 §7.3 进入 Human Gate。

## 18. 反过度设计红线

1. 不设 `draft` 状态——创建前置确认（AI 提案 → Human 确认 → 受控创建）替代确认前快照，不存在「已保存未确认」中间态；
2. 不设 `symptoms`/`trigger_conditions`/`root_cause`/`resolution`/`avoidance`/`validation` frontmatter 字段——六要素分析主体住正文，frontmatter 只留 scope 薄索引；
3. 不设 `severity`/`priority`/`tags`/`repeatability` 类装饰字段——经验重要性由消费点引用体现；
4. 不建 `relations` 关系边——谱系由 disposition 承载、贡献关联由 WC 侧承载（03 §7.2 第 4 条）；
5. 不建症状相似度自动匹配——预检与故障调查的匹配是 AI 语义工作（03 §8.2）；
6. 不把 avoidance 提升为规则源——经验约束需强制时由规范源另行定义（00 §3.3）。
