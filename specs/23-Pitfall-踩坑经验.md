# Pitfall-踩坑经验

## 1. 价值判断

Pitfall 解决已验证的踩坑经验随对话消散的问题：一次失败实际发生、查明根因、解决并验证之后，它的症状识别信号、触发条件、根因判断、实际方案与规避方式——若只存在于会话记录或散落备忘，后续行动无法在事前预检时对照已知坑位，事后调查时找不到「以前踩过什么、怎么解的」，同一错误重复踩、同一调试反复做（00 §1 痛点 4）。Pitfall 以知识层对象承载已验证经验：回溯记录、前瞻消费——执行前预检与故障调查时被引用。普通文件不能无损承载：无受控写入、无状态闭集（draft/active/discarded 无从机械判定）、无预检的匹配投影。Spark 是未定悬置；Research 是外部证据；ADR 是决策记录——Pitfall 是「什么会出错、怎么识别、怎么规避」。

主要支撑 V3 边界识别（行动落入已知坑位的影响范围时经预检暴露）、V5 据实判断（症状匹配可回指「哪条 Pitfall」）、V6 工作接续（跨会话恢复经验基线）与 V8 持续积累（相似场景直接复用规避经验，不再重复调试）；HV3 入档闭环节点可验（创建与终态可回读）与 HV5 项目演进脉络可循（项目踩过的坑与解法构成经验史）。

Pitfall 对象存在、处于 active 或形成经验积累，均不能单独证明经验仍然适用、被实际消费或真的避免了损失——经验的价值须在预检、故障调查的真实消费中核对；经验的积累规模也不证明积累效用（HV4 须由实际复用与可观察损耗避免核对）。Pitfall 是经验事实不是规则来源：avoidance 不取得 MUST 级规则权威，需要强制做法时由规范源另行定义（00 §3.2）。

## 3. 职责边界

### 3.1 本文负责

1. Pitfall 类型的对象边界（已验证失败机制的构成、查重、明确不属于本类型的内容）；
2. Pitfall 的身份与载体（多例、平铺单文件、`ldvh-base/pitfalls/pitfall-<uid>.md`）；
3. Pitfall 的字段契约（frontmatter 薄索引闭集、正文固定 H2、字段间不变量）；
4. Pitfall 的状态闭集（draft/active/discarded）、入档前置与终态处理；
5. Pitfall 的召回与消费点（执行前预检、故障调查、Web 知识库呈现）；
6. Pitfall 的受控操作（创建、勘误与补充级更新、终态流转）。

### 3.2 本文不负责

1. 遵守预检的完整判定逻辑（03 §9.5 承载，本文只定义消费语义接口）；
2. WorkCase 执行期的 Pitfall 发现与授权集成（预留编号 21 号承载——21 建成前创建入口只有 AI 提案与 Human 直接提出两路）；
3. 调研执行与 Research 类型语义（33 号、24 号承载）；
4. Human 确认经验有效性的过程（00 §4 承载——Pitfall 记录已验证经验，验证本身是 **`draft → active` 入档的前置**，见 §16.1）；
5. Web 呈现的视觉与交互细节（10 号承载）。

### 3.3 相邻规范分工与唯一权威

02 是公共字段与受控读写契约的唯一权威；09 是受控提交的唯一权威；03 §9.5 是遵守预检的唯一权威；21 是 WorkCase 集成的唯一权威；22/24 分别是 ADR/Research 类型语义的唯一权威。本文只定义 Pitfall 类型自身的边界、字段、状态与消费点，不复制相邻规范的规则。

## 4. 适用范围

### 4.1 适用对象

1. 管辖项目中的多例 Pitfall 对象（`ldvh-base/pitfalls/`）；
2. Pitfall 的症状、触发、根因、解决、规避、验证与影响范围记录。

### 4.2 适用场景

本规范用于 Pitfall 的创建（执行中发现经提案确认、Human 直接提出）、查重、勘误与补充级更新、终态流转（废弃）与消费（执行前预检、故障调查、Web 呈现）。

### 4.3 明确排除与证明边界

明确排除：未解决的问题（问题没查明/没解决/没验证时不该有 Pitfall——那是当次行动或 Spark）；未发生实际失败的假想风险（预防性记录不成立，必须有实际发生与验证）；已定决策（ADR）；外部证据（Research）；日志与自由标签。Pitfall 对象存在或状态为 active，不能单独证明经验适用、被消费或避免了损失——这些须由预检与故障调查的真实使用核对。

## 5. 类型定位与价值

Pitfall 是知识层的事实类型：承载已验证失败机制的回溯记录，供前瞻消费。与同层的 ADR/Research 分工——ADR 回答「为什么这么定」，Research 回答「外部世界是什么」，Pitfall 回答「什么会出错、怎么识别、怎么规避」。

按 02 §6.2 准入六问：跨行动保留——经验基线必须跨会话稳定，否则同一坑重复踩；独立身份与状态——经验有 draft/active/discarded 与适用性衰减，需要独立生命周期；普通文件不能无损承载——无受控写入、无状态闭集、无预检投影；消费价值服务 AI（预检/调查）与 Human（Web 经验库）双轨；维护成本——低频类型（v4 实证数十量级），净值为正；类型定义来源——本规范。

## 6. 对象边界

### 6.1 什么构成一个对象

一个 Pitfall 对象 = 一项可独立引用的已验证失败机制：症状识别信号 + 触发条件 + 根因判断 + 实际采用的解决方案 + 规避方式 + 验证说明 + 影响与适用范围。机制必须可独立召回、可独立预检匹配（行动落入影响范围时能指向「哪条 Pitfall」）、可独立终态（不再适用时单独废弃）。

### 6.2 查重

创建前必须查重：对照既有 **`active` 与 `draft`** Pitfall 的 title 与症状/根因语义比对（AI 语义判断，02 §9.2 不建立相似度自动裁决）。**`draft` 必须纳入查重范围**——否则同一失败机制会在每个空闲周期被重复形成候选，把 Human 的待确认队列灌满；已存在 `draft` 时不新建，如实登记为已存在。同一失败机制的新表现或新触发样例已存在时，不新建——走补充级更新并入既有对象；不同机制的相似症状（根因不同）各自成对象。查重结论必须记录在创建提案中。

### 6.3 明确不属于本类型

单次调试过程未收敛为经验的内容（留在会话记录）；预防性假设（未实际发生的风险不记录）；已由规范源吸收为强制规则的规避（规则由规范源承载，Pitfall 可作为经验来源被引用但不再独立承担约束）。

## 8. 字段契约

frontmatter 闭集（分析性长文本一律住正文，frontmatter 只留薄索引）：

| 字段 | 类型 | 必填性 | 语义 | 约束 |
|---|---|---|---|---|
| `fact_type_key` | string | 必填 | `pitfall` | 唯一合法值 |
| `object_uid` | UUIDv4 | 必填 | Code 生成 | 创建时落定，永不改变 |
| `title` | string | 必填 | 失败机制短标题 | ≤ 30 字；简短识别机制，不复制症状全文；平台/环境专属时凸显平台 |
| `status` | string | 必填 | `draft` / `active` / `discarded` | 初态依通道而异：机械通道创建（11 §10）初态为 `draft`；Human 入口在确认入档时创建，初态为 `active`（§13） |
| `scope` | string | 必填 | 影响与适用范围陈述 | 正文「影响与适用范围」段逐字包含；哪些活动/工具/交互可能落入 + 经验可信复用的边界 |
| `trigger_signal` | string | 条件 | 重新审视信号 | 存在真实重审前提时写（依赖版本变更、环境迁移等）；无则省略（02 §7.1） |
| `urls` | array | 条件 | 支撑经验的外部 HTTP(S) 证据 | 出现时非空；`urls` 非空 ⇒ 正文「证据」段必填 |
| `disposition` | string | 条件 | 终态去向与理由 | 仅 discarded 时必填；说明废弃依据（前提消失/机制不存在/经验失效）；**≤ 200 字符**（终态原因说明的阅读上限，§9.1） |
| `created_at` | RFC3339 | 必填 | Code 填写 | AI 不得填写 |
| `change_log` | array | 条件 | 变更流水 | 首修后必有；每次恰好一条 |

不设 `symptoms`/`trigger_conditions`/`root_cause`/`resolution`/`avoidance`/`validation` 等 frontmatter 字段——六要素是分析主体，住正文；`trigger_signal` 是短句信号例外（同 22 号先例）。

正文固定结构（H1「# 标题」由 Code 从 title 生成、位于围栏后首行且恰好一个，正文自 H2 起；此处不直书 H1 字面以免与身份 H1 重复）：

```
## 症状            ← 失败实际发生后的可观察表现与识别信号（必答：识别信号是什么）
## 触发条件        ← 会触发该机制的前置条件、组合与上下文（必答：什么条件下会触发）
## 根因            ← 当前经验范围内能解释症状与触发的机制判断（必答：机制判断+已观察/未知的区分）
## 解决            ← 已实际采用的处理方式与成功信号（必答：做了什么+成功信号+必要边界）
## 规避            ← 后续识别、预防或安全复用该经验的方式（必答：核对条件+动作+例外）
## 验证            ← 已观察结果、覆盖与未知范围（必答：已观察什么+未覆盖什么）
## 影响与适用范围  ← scope 逐字 + 展开：何时可能踩到、经验何时可信（必答：何时踩到+何时可信）
## 证据            ← 支撑经验的外部引用（可选；urls 非空时必填）
```

字段间不变量：`scope` 载体内聚（正文段逐字包含）；`disposition` 出现 ⇔ `status=discarded`（`draft`/`active` 禁现、`discarded` 必填非空）；未知字段不进入 canonical 对象，不得以空字段或占位代替判断。

## 9. 状态与生命周期

状态闭集三值：`draft`（**待确认的候选**——经验已成文但尚未入档）→ `active`（经验可信可复用）→ `discarded`（经验不再适用）。

**`draft` 的存在理由与边界**：宿主辅助任务的经验积累（11 §10 捕获段与审核段）在闲置时把会话材料整理成「可按证据写全七段」的候选后，需要一个**可机械枚举、可排队等待确认**的承载——分散的提案文本无法被「待确认」这一状态查询命中，Human 也无从知道有多少候选在等。故 `draft` 是**候选的正式承载**，其语义是「经验已按证据完整写成，等待入档决定」，**不是**「尚未查明的半成品」：`draft` 必须满足与 `active` **相同的正文七段要求**（§8），不得以占位符或「待查明」标记冒充——不能据证据写出某一段者不构成候选，说明材料不足以支撑一次候选，可按 §17 第 2 项如实报告后停止（四前提的核对不在此时，见 §10）。

**`draft` 不是 v4 的 draft**（与 22 号先例的差异须写明）：v4 的 `draft` 是「Human 确认前的快照」，其存在使「已保存」与「已确认」在载体上不可区分，故本规范此前以「创建前置确认」取消之。现行 `draft` 与之相反——它**只由宿主辅助任务的机械通道创建**，而该通道**不含任何入档判断**：候选的入档（`draft → active`）是 §16 的 Human Gate，且以另一主体复现验证为前置（见 §9.2）。故「已保存」与「已确认」在状态上**始终可区分**：前者 `draft`，后者 `active`。

**不进入普通候选**：`draft` 不参与召回分层的默认候选（§12），也不参与预检与故障调查——它尚未入档，其经验可信度未经确认。

### 9.1 状态语义与成立条件

| `status` | 语义 | 必须成立 |
|---|---|---|
| `draft` | **待确认的候选**：经验已成文（七段齐备）但尚未入档；由宿主辅助任务的经验积累机械通道创建（11 §10） | `disposition` 不得出现；正文七段齐备且各段非空（同 `active` 的结构要求）；**不进入默认候选**（§12） |
| `active` | 经验已验证且仍可信，参与预检与故障调查 | `disposition` 不得出现；入档须经 §16 的 Human Gate，并以另一主体复现验证为前置 |
| `discarded` | 经验不再适用；保留为历史基线 | `disposition` 必填非空（说明哪个前提消失了）；不进入普通候选 |

**`disposition` 的长度上限（机械校验）**：`disposition` 不超过 **200 字符**（判定单位与本规范 `title` 的同名上限一致，均为 UTF-16 码元计数；实现按 `.length` 判定）。终态原因说明是给后续读者与人扫读的定位信息，不是完整处置记录——完整理由属于正文、`change_log` 或承接对象。超限时拒绝写入（与 §13 的受控写入前置条件同为机械条件，按 02 §10 的公共契约执行），不得截断后写入。

**判定的是数量而非语义**：本上限只约束长度，不判断说明是否据实、充分或与 `status` 相符——后者仍由 §15 的语义核对与 Human 废止授权承担。长度合规不证明终态处置正确。

### 9.2 状态转换

正常转换有三：`draft → active`（**Human Gate：入档**——该转换即 §16 第 1 项的「经验的入档成立」，其前置为另一主体复现验证，见 §16.1；**§10 的经验质量四前提即在此核对**，创建时不核对）；`active → discarded`（Human Gate：经验废止）；**`draft → discarded`**（Human Gate：候选未入档即被否决，其 `disposition` 记否决依据）。**`draft → active` 是入档的唯一起点**——不存在「创建即 active」的通道：`active` 只能由 `draft` 升格而来，或在 Human 直接提出历史经验时经受控创建入口**同时**形成候选并完成入档（此时创建与入档是同一决定的两面，见 §13）。**终态不可重开，但内容可更正**（Human 决定 2026-09-13）：`discarded` 后状态不得再变回 `active`；但终态对象的**内容仍可更正**，走 §9.3 的勘误与补充级更新（含 `disposition` 等字段的修正）——写错的、超限的、与事实不符的终态记录须就地改正，不得靠伪造一次状态转换来洗白，且**不得借更正改变 `status`**。经验的根因判断或解决方案实质变化（不是补充新观察）时创建新 Pitfall；旧对象视情况废弃（前提消失则 discarded+disposition，机制仍存在则保持 active 各自独立）。

### 9.3 勘误与补充级更新

正文错别字、引用修正、表述澄清（不改变机制语义）、**同一机制的新表现、新触发样例补充**（症状/触发条件段的扩展性补充是明确允许项），以及**独立复现验证结论的登记**（§16.1 第 3 项：把另一主体的复现结论记入「验证」段——该补充是对已声称结果的独立核对，不改机制语义、不动根因/解决/规避，属明确允许项）走 02 §10.5 受控更新，change_log 留痕。机械边界：更新后的 `scope` 逐字段不变（变了就不是补充——影响范围实质变化走新对象）；机械比对只覆盖 scope，其余段的语义不变性（补充与实质变更的分界）是 AI 审核义务：根因、解决、规避三段的实质更换不得以补充名义放行，须走新对象路径。补充的判别锚点是**与既有根因判断相容**——新表现、新触发起码要能被当前根因解释；根因解释不了的新触发不是同一机制的样例，是新机制，走查重与新对象。

## 10. 来源与证据

经验来源是实际发生的失败与验证：当次行动的观察、调试与修复记录（会话留痕）是第一来源，Human 提出的历史经验是第二来源。`urls` 的来源回指语义遵循 02 §8.1 公共边界；内部证据以自然语言在验证段交代。验证说明必须区分已观察结果与未覆盖范围——「验证过什么」与「没验证什么」同样必答，不得以验证摘要冒充全面覆盖。

**经验质量四前提与它的承担时点（2026-10-20 重定位）**：Pitfall 的准入前提是**失败已发生、根因已查明、解决已采用、验证已有观察**。这四项**不是创建时的闸门，而是 `draft → active` 的前置**——其完整展开在 §16.1，本节只作一手回指。

**为什么从创建时移到入档时**：创建时判四前提，等于要求形成者在落盘那一刻就自证「已解决、已验证」。现行两条创建通道都做不到如实自证——机械通道（11 §10 的审核段）只读留观缓冲里的材料，它看到的证据支持「把七段按材料写出来」，**不支持**形成者断言「这四项我核过了」；Human 入口（§13）的议案同样只有形成者的一面之词。把门槛留在创建时，实际效果是逼形成者用一句自证换落盘，而那恰恰是 §15「经验质量」一行要核对的内容。故四前提下沉到它真正能被第三方核对的位置：`draft → active` 时的另一主体复现验证（§16.1）。

**创建时改由什么约束（替代闸门，不是取消闸门）**：`draft` 必须能**据证据写出**七段（§8）、各段非空、不以占位符或「待查明」标记冒充；「验证」段须如实区分已观察与未覆盖，其依据是逐字引证的证据片段与来源标识，不得凭记忆补写。**不能据证据写出某段者不构成候选**——这不是四前提闸门，而是 §8 的正文要求本身：写不出症状、根因、解法中的任一段，说明材料不足，候选无从成立。

**四前提与七段不是同一件事**：七段是**载体结构**，任何状态都须满足；四前提是**准入质量**，只在 `draft → active` 时核对——「失败已发生」对应症状与触发条件可回指，「根因已查明」对应根因段，「解决已采用」对应解决与规避段，「验证已有观察」对应验证段。**七段写全不等于四前提已齐**：四段都能写出，根因仍可能只是猜测、解法仍可能只是当时凑巧有效；这正是入档须经独立复现的原因。

## 11. 关系契约

不使用 `relations` 字段（类型来源声明不采用）。理由：Pitfall 的替代与关联无独立机械消费价值——经验废止的谱系（被什么取代）由 `disposition` 自然语言承载；与 WorkCase 的贡献关联（该经验来自哪次执行）由 21 号 WC 侧的 `contributed-to` 承载（02 §8.2 第 4 条：反向引用不复制）；与 ADR/Research 的关联由正文自然语言交代。确有公共消费价值时由 03 提升公共契约再议。

## 13. 受控操作

- **创建（分两条通道）**：**机械通道**——宿主辅助任务的经验积累（11 §10）自动创建 `draft` 候选，**无须事前 Human 确认**并保留事后否决权；其入口由 11 §10 定义、记录机械依据，另按 11 §19.1 第 4 项经其领域增量 Gate。**Human 入口**——执行中发现（当次行动失败已查明验证后形成提案）与 Human 直接提出（历史经验口述，AI 整理成提案）两路，经 Human 确认后落盘。**两条通道的落点不同**：机械通道只产出 `draft`（**不含入档判断**）；Human 入口可由 Human 在确认时**同时**决定入档，此时落盘即 `active`（创建与入档是同一决定的两面）。机械校验（两通道共用）：字段闭集合法、title ≤ 30 字、urls 形状、载体结构（H2 固定序 + urls 非空时「证据」段必在）、**七段齐备且各段非空**、载体内聚（scope 逐字）。创建后精确回读。**创建时不核对四前提**（§10：四前提是 `draft → active` 的前置，由 §16.1 的独立复现核）；创建的质量约束是「七段据证据写出」（§10）。**机械通道的边界**：不得创建 `active`、不得升格、不得废止——三者均属 §16 的 Human Gate。
- **勘误与补充级更新**：02 §10.5 受控更新；CAS 以完整文件为单位；每次恰好一条 change_log；scope 逐字段不变（机械比对，变了拒绝——走新对象路径）。
- **状态流转（分两项）**：
  - **入档（`draft → active`）**：Human Gate（§16 第 1 项）；**前置为另一主体复现验证**（§16.1）——未经独立验证的候选不得提请入档。AI 先精确读取 F3 核对七段完整与验证段依据；Code 检查目标状态属当前闭集、字段（`disposition` 不得出现）、CAS 与回读。**机械通道不得执行本项**（§13 创建条末段）。
  - **终态流转（`active → discarded` 与 `draft → discarded`）**：Human Gate（§16 第 2 项）；AI 先精确读取 F3 核对 disposition 依据；Code 检查闭集、字段（`disposition` 必填非空且 ≤ 200 字符）、CAS 与回读。**`draft → discarded` 的 `disposition` 记否决依据**（§9.2）。
- **终态更正**（`discarded` 对象）：走 §9.3 勘误与补充级更新；**不得改变 `status`**（§9.2 终态不可重开但内容可更正），每次恰好一条 `change_log` 据实说明更正了什么。
- **删除**：不存在删除操作。discarded Pitfall 随 `ldvh-base/pitfalls/` 保留为历史基线。

## 14. 类型特有验证与类型退出

### 14.1 类型特有验证

- 查重结果记录：创建提案必含查重结论（同机制已存在 → 走补充更新）；
- 载体内聚：scope 在正文「影响与适用范围」段逐字出现；
- 补充边界：更新的 scope 与 CAS 基线逐字段一致（防影响范围实质变化伪装补充）；
- 终态完整性：discarded 必有非空 disposition；且 disposition 长度不超过 200 字符（§9.1）；
- 状态-终态不变量：`draft` 与 `active` 均不得带 disposition。

### 14.2 存量对象迁移

无 v5 存量。v4 仓库的 Pitfall 实例按「v4 存量不迁移」（ADR `adr-1aad60bc`）保留在 v4 历史归档；经验若仍适用，在 v5 以新 Pitfall 重新记录。

### 14.3 类型退出

若 Human 决定取消 Pitfall 类型，须按 02 §11 处理：处理仍适用经验的转移承接与稳定引用，登记变化（01 §8.1）与受影响引用同步，走受控提交。退出属 00 §4.2 根决定。

## 16. Human Gate

本文不新增 00 之外的 Human Gate。领域增量事项（00 §4.2 在 Pitfall 领域的具体化）：

1. Pitfall 的**入档成立**（`draft → active`）——含执行发现与直接提出两入口的记录确认；**机械通道创建 `draft` 候选除外**：该创建由 11 §10 定义、记录机械依据，另按 11 §19.1 第 4 项经其领域增量 Gate，**无须事前 Human 确认**并保留事后否决权。**机械通道只到 `draft` 为止**——升格仍属本项；
2. Pitfall 的**终态决定**（`discarded`）——含两路：**`active → discarded`（经验废止）**与**`draft → discarded`（候选未入档即被否决）**；
3. Pitfall 类型本身的取消或合并。

### 16.1 决定边界

Human 决定只证明决定及其作用范围，不替代查重判断、载体校验、预检匹配判断或终态机械校验。**入档决定（`draft → active`）的前置是另一主体复现验证**（本段是该前置的**完整展开的唯一处**；11 §10 只作一手回指）：

1. **验证对象**：独立复现并核对 §8 的「验证」段——所声称的已观察结果可重现、未覆盖范围如实。**不得**以「重新阅读候选正文并认为其合理」替代复现；复现指**实际重走该失败机制的可观察步骤**，或在其不可重走时核对原始证据链（会话留痕、提交、日志）是否支持「已观察」的声称。
2. **执行体类型与独立性判据**：按 01 §12.2 的独立性判据（**未参与形成当前候选的执行体**；同一上下文中形成候选的同一角色不得审核该候选）。**执行体范围由 `00 §3.3` 与 `00 §3.7` 固定**——由已登记的代理执行体承担，本类型不增列执行体类别；Human 的明确同意是与独立审核并列的另一要件，不以 Human 亲自审核替代独立审核。**采用同一模型时仍须保持上下文隔离，并在验证结论中披露独立性边界。****形成者与验证者不得为同一主体**——同一上下文中的同一角色不构成独立验证（独立性要求见 `01 §12.2`；`04 §7.3` 所定的是复核轴承载形式，与审核轴分属两轴，不得互相替代或借用）。
3. **结论载体（本项必须落盘，不得只以交还正文承载）**：验证结论**不新设事实类型、不新设字段**，按 §9.3 的补充级更新登记——**结论正文记入候选的「验证」段**（§9.3 已把「独立复现验证结论的登记」列为明确允许的补充项）：写明复现主体、独立性边界、复现做法与观察结果、以及未被覆盖的范围；`change_log` 只记**这次更新事件本身**（一条，按 §8 的 change_log 形态），**不在流水里另存正文级结论**。复现过程若涉及外部材料（如上游链接、开源项目行为），按 02 §8.1 的外部证据形态经 `urls` 回指；**纯内部产生的复现结论（会话留痕、提交、日志）不写 `urls`**——该字段的准据是外部 HTTP(S) 证据（§8）。**不得**只把结论写在会话交还正文里（那使它在跨会话时不可召回，与 §9 的候选承载理由同）。
4. **该结论的效力边界**：它是 Human 决定的**依据**，**不自动使候选生效**，也不使 Human 的确认免除 §15 的经验质量核对。
5. **无法安排独立验证时（防死锁）**：按 00 §5.7 停止该次升格提请并如实报告，**不得以同一主体自验冒充**。**同时须避免候选无限积压**：候选停在 `draft` 不构成失败，也不计入任何「未完成核查即不得消费」的范围（它本就不进默认候选，见 §12）；当同一候选连续未获验证时，**Human 可主动决定其处置**（降低复现强度并以「未独立复现」如实登记、或其否决为 `discarded`）——**该决定属 §16 第 2 项**，不由本规范或机械通道自行作出。**候选不得因无法验证而被静默删除或静默改判**。本文成为当前规则源成员时的 01 §8.1 登记与受影响引用同步，按 01 §8.1 的登记义务随本次规范新建一并执行。

## 17. 必停情形

本文不新增根停止类型。领域触发与最小影响范围：

1. 创建时发现同机制 Pitfall 已存在（`active` 或 `draft`，见 §6.2；重复经验风险）——未完成查重结论前不创建；
2. **候选不成立却准备创建**——即无法据证据写出七段中的某段（含以占位符或「待查明」标记冒充七段的情形；`draft` 与 `active` 的正文要求相同，见 §9）；四前提（失败已发生／根因已查明／解决已采用／验证已有观察）**不属本项**，它们是 `draft → active` 的前置，见 §10 与 §16.1；
3. scope 为空或不可读；
4. 准备以更新改写 scope 实质或更换根因/解决/规避的语义（补充边界违例）；
5. 终态流转 disposition 缺失；
6. **未经 Human 确认直接入档或流转**（授权缺失）——即未经 §16 第 1 项直接产生 `active`，或未经确认直接流转；**机械通道创建 `draft` 候选不属本项**（该通道由 11 §10 定义，见 §13）；
7. 预检消费时 Pitfall 状态与引用不一致（引用了 discarded 经验为现行依据）。

暂停期间只允许不越过停止边界的证据补取、引用修复、授权补走与条件核实。恢复须与触发原因逐项对应；同一停止条件恢复后再次触发的，按 00 §5.7 的恢复与再次触发进入 Human Gate。

## 18. 反过度设计红线

1. **`draft` 只承载候选，不承载半成品**——不设「待查明」「待补充」类中间态：`draft` 与 `active` 的正文要求相同（七段齐备），二者的唯一差别是**入档决定是否已作出**。故不得以 `draft` 为名保存未查明的失败机制（那属会话记录，不是候选），也不得增设第二个中间态（如「已入档待复核」）——入档即 `active`，其后的内容更正是勘误与补充级更新的职责（§9.3）；
2. 不设 `symptoms`/`trigger_conditions`/`root_cause`/`resolution`/`avoidance`/`validation` frontmatter 字段——六要素分析主体住正文，frontmatter 只留 scope 薄索引；
3. 不设 `severity`/`priority`/`tags`/`repeatability` 类装饰字段——经验重要性由消费点引用体现；
4. 不建 `relations` 关系边——谱系由 disposition 承载、贡献关联由 WC 侧承载（02 §8.2 第 4 条）；
5. 不建症状相似度自动匹配——预检与故障调查的匹配是 AI 语义工作（02 §9.2）；
6. 不把 avoidance 提升为规则源——经验约束需强制时由规范源另行定义（00 §3.2）。
