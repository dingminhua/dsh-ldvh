# Web 呈现与交互规范


## 1. 价值判断

Web 呈现与交互解决 Human 难以直接观察 LDVH 状态、依据、授权和积累的问题，通过统一阅读层级与交互入口，使信息可定位、可回应、可回读，减少黑盒感、误操作和跨页面理解负担。

结构化问询与计划审查主要支撑 HV1 决策提请清晰可决；授权流和执行状态呈现主要支撑 HV2 授权执行受控可续；节点回读主要支撑 HV3 入档闭环节点可验；卡片网格、语义详情与扩展阅读主要支撑 HV4 积累效用直观可见与 HV5 项目演进脉络可循。V 轨价值由 AI 侧规范承接，Web 只呈现其可观察结果。

本规范只定义 Human 呈现语义与交互契约；机械拒绝、领域数据、宿主接入和 Code 实现由 03、05–09 与实际运行环境承接。

页面呈现、工具成功、组件加载或 Human 操作，只能证明当次呈现与交互范围，不能单独证明事实成立、授权覆盖、技术验证、工作完成或价值兑现。

## 5. 四层阅读器

四层阅读器承载 Human 对 LDVH 项目信息的呈现消费。四层**互不替代、不互锁**：Human 可随时切换至任一或同时展开多层，不要求从低层向高层递进。

### 5.1 字段级直读

- 呈现事实对象的核心字段（名称、状态、指纹、时间戳、来源引用）
- 面向快速定位与核对：Human 可一眼确认某条记录是否存在、状态如何
- 不渲染关联关系或语义解释

### 5.2 卡片网格

- 以卡片形态呈现事实对象摘要（标题、状态标签、单行摘要、关联计数）
- 支持按类型、状态、维度、时间等条件筛选与排序
- 面向浏览与概览：Human 在卡片间扫描，定位感兴趣的对象

### 5.3 语义详情

- 完整呈现单条事实对象的所有字段与关联引用，含来源回指
- 显示该对象的变更历史（摘要形态，不要求完整 diff）
- 面向深度核查：Human 逐条审阅内容、判断适用性与完整性

### 5.4 扩展阅读

- 跨对象关联呈现：按话题、决策链、问题-方案-结果线索串联多条事实
- 呈现事实的积累效用与复用情况（HV4/HV5 的承载面）
- 面向脉络探索：Human 沿关联追踪项目演进路径

### 5.5 WorkCase 呈现契约

本节登记 WorkCase 在 Web 中的呈现接线。**类型语义与字段的唯一权威是 21 号**（§3.3）；本节不重定义状态机、字段或 Gate 语义，只登记「Web 读什么、由什么派生、筛选与待办如何接线」。21 号语义变更时本节随之复核，本节不得作为第二规则源。

**三态直读**：WorkCase 的呈现状态由 `status` 闭集三值（`draft` / `open` / `closed`）直接读取，不引入 v4 的 phase 或多值进度词汇。`closed` 配 `outcome` 四值（`completed` / `partial` / `not-achieved` / `cancelled`）呈现终态徽标。

**派生分组（呈现层派生，不写回对象）**：列表筛选与收件箱**共用同一派生函数**（防口径漂移）。四组及其派生判据：

| 派生组 | 判据 |
|---|---|
| 待批准执行（`pending_gate1`） | `status = draft`（含 C2 局部重批回退的对象——同在等 Gate 1） |
| 执行中（`executing`） | `status = open` ∧ 正文不含 H2「结果」节 |
| 待批准关闭（`awaiting_gate2`） | `status = open` ∧ 正文**含** H2「结果」节 |
| 已关闭（`closed`） | `status = closed` |

筛选提供五档：上述四组加「全部」。

**「待批准关闭」的判据说明**：以「正文含 H2 结果节」为派生依据，是因为该节是 21 §8 定义的**关闭提案正文承载**（关闭提案时必填）。**不得改用「Gate 2 已提请」一类运行期状态**——那不是事实源中可读的稳定内容。H2 识别须忽略代码围栏内的行，并容许 ≤3 空格缩进。

**交互入口接线**：`draft` 对象接入 21 §10.1 的 Gate 1 提请（对应 §6.2 计划审查）；`open` 且正文含结果节的对象接入 21 §10.2 的 Gate 2 提请（对应 §6.4 验收交还）。收件箱待办由上述派生组产生，不得由 v4 的进度字段或运行期标记产生。

**复核节点的呈现**：21 §8 的 `reviews`（复核节点概要流水）按 §5.3「显示该对象的变更历史（摘要形态）」呈现——列出每次复核的时间、署名与概要。**复核详情不入对象**，故详情面不承载其原文。

**执行期阶段（呈现层派生，不写回对象；不进筛选与收件箱）**：`executing` 组内部按下列判据派生四个阶段，供卡片与详情呈现。**本派生不对上表「派生分组」的闭集做任何扩张**——筛选仍为五档、收件箱待办仍由上述四组产生；阶段是同一组内部的呈现细节，不是状态词汇。

| 阶段 | 判据 |
|---|---|
| 执行中 | `reviews` 不存在，且 `change_log` 中无**复核条目** |
| 复核中 | `change_log` 中存在**复核条目**，且 `reviews` 不存在 |
| 修订中 | `reviews` 存在，且其后仍有**本对象**的 `change_log` 条目 |
| 结项中 | `reviews` 存在，且其后无本对象的 `change_log` 条目 |

**「复核条目」（21 §8 记账纪律）**：摘要**以「复核：」开头**者，或含 `[review recorded by session`（Code 盖戳）者。**为何用前缀而非关键词**：`change_log` 中「复核这件事」与「处置复核的发现」共用同一批词——实测「独立复核（两视角）的 12 条发现与处置」是复核报告、「复核 2 项必须处置全部落地」是修订动作、「复核与处置非计划步骤」是记账更正，三者都含「复核」而语义分属三类；按关键词识别必然误判（旧实现即因此把处置动作标成了复核）。该判据两侧的可靠性不同：**完成一侧是机械的**（`record_review` 由 Code 盖戳写入 `reviews` 并在 `change_log` 留 `[review recorded by session …]` 标记，不依赖作者）；**发起一侧依赖前缀**（21 §8 已声明该条非机械门禁）。故「复核中」是组合判据，不得据此声明复核过程已被完整机械记录。

**当前无呈现消费方（Human 2026-09-23 决定）**：本派生已实现且有测试守护（`deriveWorkCaseExecPhase`），但**卡片不呈现阶段标签**——对象头部的状态显示恒为 21 号状态机的真实值，不被阶段影响；执行进度改由卡片主体的「变更流水」及其标记表达（见下）。本判据留待后续需要时启用，**不得据下表在卡片上新增阶段标签**。

**变更流水（卡片主体的执行进度呈现）**：`executing` 组的卡片主体呈现 `change_log` 的流水——按日分组、每条给时刻、最多 8 条（更早折叠），关键行动以**文字标记**凸显：

| 标记 | 判据 |
|---|---|
| 复核 | 摘要**以「复核：」开头**（21 §8 记账纪律）**或**含 `[review recorded by session`（Code 盖戳，机械） |
| 修订 | **最后一条复核条目之后**的本对象条目（数组序；`reviews` 非空为前提） |
| （无标记） | 其余条目 |

标记与归属口径同样复用上述三条判定口径（数组序 / 他对象排除 / 格式治理排除），由 `shared/workcaseLifecycle` 单点给出（`markWorkCaseFlow`），组件不自行判断。**流水不改变对象状态，也不影响筛选与收件箱**。

**判定口径**：① 一律按 `change_log` 的**数组序**判定，**不得**使用 `reviews[].at` 或 `change_log[].at` 的相对先后——写入函数在一次写入中把同批条目刷成同一时刻，时间不承载相对先后（21 号实现已登记该边界）。②「本对象的条目」指摘要中**未**提及他对象 `workcase-XXXXXXXX` 的条目；提及他对象的条目（如替他单执行的迁移）不参与本对象的阶段判定。③ 摘要以「**格式治理：**」开头的条目（21 §8）不参与判定——它是跨对象的批量格式操作，语义逐字未变，不构成该对象的修订。

**与「待批准关闭」的区别**：「结项中」指已复核通过、尚未写出「## 结果」节的对象；一旦写出结果节，该对象即进入既有派生组「待批准关闭」（`awaiting_gate2`）。二者判据互斥，**不得合并**——「是否已提请 Gate 2」是真实差别。

**未验证范围**：本条只提供判据，不保证「复核：」前缀被实际遵守——写成其它形式（如「开始独立审核」）时「复核中」不可判（21 §8 已声明该纪律非机械门禁）。判据 ② 亦不排除「摘要未提及任何对象、实为他单工作」的条目。

**卡面与详情的字段分工（21 §8「`gist` 与 `summary` 的分工」的呈现落点）**：21 §8 把「要做什么」拆为两个字段服务不同读者，本节登记其呈现接线：

| 呈现面 | 渲染 `gist` | 渲染 `summary` |
|---|---|---|
| 列表卡（§5.2 卡片网格，三态全部） | 是——卡体首行 | 否 |
| 聚焦收件箱卡体（待决定事项 / 推进中事项） | 是——卡体首行 | 否 |
| 联邦对象卡（跨项目视图） | 是——卡体首行 | 否 |
| 语义详情（§5.3） | 是——独立阅读节点 | 是——Markdown 节点 |

**本表是卡面的完整清单**：凡渲染 WorkCase 卡体的呈现面都在表内，新增卡面须同步登记。「卡面不渲染 `summary`」是**按呈现面类型**（扫读窗口）成立的规则，不因卡片来自单项目视图还是联邦视图而改变——同一张卡在两种视图下读者与版式相同，字段分工不得随数据来源漂移。

**AI 侧召回不在本节范围内**：F1/F2 召回投影由 21 §13 定义（F1 = `title` + `status` + `serves`；F2 = `title`/`summary`/`scope` 的有界摘录 + 命中依据），本节不为其登记字段，也不因 `gist` 的引入而改动它——`gist` 是**呈现层**的 Human 扫读字段，召回投影的字段集以 21 §13 原文为准。若日后需让 AI 侧也消费 `gist`，须先修订 21 §13，不得由本节倒推。

**为何卡面不渲染 `summary`**：卡面是**扫读窗口**（§5.2：Human 在卡片间扫描以定位感兴趣的对象），而 `summary` 按 21 §8 是**给执行者的完整快照**——它可以长、可以含编号引用与对象标识、可以带 Markdown 标记。把后者放进前者，两个后果都已实测：卡面文字溢出扫读窗口；且卡体渲染路径若为纯文本插值，Markdown 标记会以字面形式（`**加粗**`、`` `uid` ``）暴露给 Human。

**呈现降级（条件出现，如实披露）**：`gist` 在 `status = closed` 时按 21 §8 缺失合法（终态只读，无受控入口可补写）。卡面遇缺失时**如实降级**——不得以 `summary` 首句静默替代（那会把两个读者的字段混为一谈，掩盖字段缺口），也不得留白使卡片看似无内容。具体形态由 §12 第 7 条（长文本须有折叠或分层入口）与第 8 条（状态不得只由颜色承载，须有可读文本与可区分形态）共同决定，本节只登记「必须可区分于有 `gist` 的卡片」。

**机械校验边界**：本节的派生规则只证明**呈现当次**的读取与派生结果；不证明对象语义正确、Gate 授权成立、执行推进或结果达成。派生结果不写回事实源（03 §6.2）。本节不校验 `gist` 的内容质量——21 §15.1 已声明机械层只校验存在性与长度，内容是否「Human 扫读自足」属 AI 语义审核与 Human 阅读。

**「已关闭」的卡体（Human 2026-09-24 定，方案 A）**：`closed` 组卡体呈现**四块**，均**无标题栏**（与「待批准关闭」同形态纪律）：

| 块 | 内容 | 来源 |
|---|---|---|
| 结论行 | `outcome` 徽标 + 核对达成计数（`核对 N/M 达成`）+ 残留条数（`残留 K 条`，无则「无残留」） | `outcome`、`result.criteria_checks`、`result.residual` |
| 逐条核对 | `[达成／未达成／未记录] plan[N].step`——**只给标题，不给证据** | `result.criteria_checks[].satisfied` × `plan[N].step` |
| 残留 | `[残留] <正文>` 逐条；超过 2 条经「更早 N 条」展开 | `result.residual` |
| 去向 | 建议段逐条（去向标记 + 正文 + 「出自「…」」） | 正文「## 结果」节 `- advice:` 段 |

**「待批准关闭」的卡体（Human 2026-09-24 定）**：`awaiting_gate2` 组卡体与「已关闭」**同构**，差别只在**各自取当期的权威来源**，以及已关闭多一行结论（`outcome` 此时尚未判定，无结论可给）。四块无标题栏：

| 块 | 内容 | 来源 |
|---|---|---|
| 逐条核对 | `[达成／部分达成／未达成／未记录] plan[N].step` | 正文「## 结果」节（无 `result` 字段可读） |
| 残留 | `[残留] <正文>` 逐条；超过 2 条经「更早 N 条」展开 | 正文 `- residual:` 段 |
| 去向 | 建议段逐条（同一处正文承载，与已关闭**读的是同一条**） | 同上 |

**两块卡为何一分为二、又为何同构（数据源不对称，如实登记）**：`21 §9.1` 规定 **`result` 出现 ⇔ `status = closed`**，故「待批准关闭」期 `result` 字段**尚不存在**，核对／去向／残留**只在正文**；「已关闭」期 `result` 已落盘并成为**权威**。于是**内容项相同、权威来源不同**——这正是两块卡同构的理由：它们是**同一个结果块的先后两期**，不是两种展示。**去向尤须注意**：`result` 字段闭集只有 `criteria_checks`／`achieved_scope`／`residual` 三样，**不含 advice**，故去向在**关闭前后读的都是同一处正文承载**（`close` 不删正文），不另存一份（`21 §10.2`）。残留相反：两期各取当期权威（open 读正文、closed 读字段），**互不顶替**。

**块序与逐条标记（Human 裁定 2026-09-24）**：两块卡的块序一律为**核对 → 残留 → 去向**——**残留排在去向之上**，因为残留是「还剩什么」（事实）、去向是「打算怎么办」（拟议）；先陈述事实再给去向，读者才不必回头。残留条目**逐条**带「残留」标记（而非块首标一次），使三块的行结构统一为「`[标记] 正文`」：核对是状态三词、去向是去向四词、残留是固定词「残留」。**为什么残留用固定词而非分类词**：残留条目无闭集可归（`21 §8` 未给 `residual` 登记词表），条目自身常带 `**标题**` 前缀，故标记只回答「这属于哪一块」，不重复条目内容。**标记色与块底色同源**（均琥珀）——颜色只表达「这是残留」一件事，不引入第二个语义色。

**同构纪律**：上述两块共用**同一套类名与折叠阈值**（`workcaseCheckState` 的 `WORKCASE_RESIDUAL_BLOCK_CLASS`／`WORKCASE_RESIDUAL_ROW_CLASS` 与 `COLLAPSED_RESIDUAL = 2`），不得各写一份——分写必然漂移（本仓已有先例：同一状态曾出现「徽标紫、卡内提示琥珀」的分歧）。琥珀底表达「未解决/待处置」，与核对（三词各自的语义色）、去向（四色分类）区分开。

**「待批准执行」的卡体（Human 2026-09-24 定，方案 ③）**：`pending_gate1` 组卡体呈现**两块**，均无标题栏：

| 块 | 内容 | 来源 |
|---|---|---|
| 目标 | `gist`（首行，恒有；见本节开头） | `gist` |
| 计划清单 | `plan[N].step` 逐条，蓝点项目符号 | `plan[].step` |

**计划清单的容器（Human 裁定 2026-09-24，附「表现有点弱」的实测观察）**：计划清单此前**无容器**（只有蓝点 + 蓝字），是四组卡体里**唯一的无框块**——「执行中」的变更流水有框，「待批准关闭／已关闭」的核对/去向/残留三块也都有框。现包一层 `WORKCASE_CRITERIA_SURFACE_CLASS`（**与详情页判据面板同源**）：两处渲染的是**同一份 `plan` 数据**，形态因此呼应（§1.10 要求列表卡与详情共用同一套设计语言）；蓝点本就是该面板的标记，加蓝底后不再是「悬浮的点」。**容器类单列于 `WorkCaseCriteriaList`**，列表卡、收件箱、详情页**三处共用同一个常量**，不得各写一份。选蓝色而非中性灰/琥珀的理由：① 有同源先例（详情页）；② 不与 `gist` 的琥珀框争色（同卡两个琥珀框会分不清主次）；③ 不引入新语义色（琥珀已用于 `gist` 框、「部分达成」与「残留」）。

**「执行中」的卡体（Human 2026-09-23 定）**：`executing` 组卡体呈现**两块**，均无标题栏：

| 块 | 内容 | 来源 |
|---|---|---|
| 目标 | `gist`（首行，恒有） | `gist` |
| 变更流水 | 「复核」「修订」二字标记的关键行动；无标记者为普通推进 | `change_log` × `reviews`（经 `shared/workcaseLifecycle`） |

**四组卡体登记完整性（如实登记）**：本节此前只登记了「已关闭」与「待批准关闭」两组卡体，`pending_gate1` 与 `executing` 两组**无卡体契约**——实现先于登记。2026-09-24 一并补登记（两组各两块，见上）。**本表的形态来源是当时实现，不是重新设计**：补登记的作用是让「改动前须比对契约」有依据，而非追认任何未经裁定的加法。

**为什么核对只给标题（实测理由）**：`21 §8` 的 `result.criteria_checks[]` 只有 `{satisfied, evidence}`，**不含判据文本**；此前卡面显示的是「已满足 · <整段证据>」，实测 4 份 closed 对象的证据最长 **258 字**，一张卡被撑到十几行，扫读窗口（§5.2）失效。**证据与 `gate_1` 明细归详情面**（§5.3）。判据文本只能由 `plan[i].step` 给出，故 **`closed` 期列表卡投影须包含 `plan`**——此前该分支不投影 `plan`，卡上因此无法显示步骤标题（详情面不受影响：`showObject` 直接展开对象字段）。

**结论行的必要性（实测理由）**：此前 `outcome` 是一个孤立徽标、核对是另一串「已满足」行，读者须自行数数才能把两者对上；且**残留完全不上卡**——那是「关闭后还剩什么」，属关闭终态最需扫读的信息之一。

**核对状态词与「待批准关闭」统一**：`closed` 卡同样使用 `21 §8` 登记的三词映射（**达成** ⇔ `satisfied: true`；**未达成** ⇔ `false`；缺失 ⇒ **未记录**），复用 `@/utils/workcaseCheckState` 的单一实现。此前 `closed` 卡另用一套「已满足／未满足」，同一状态在两个派生组显示为不同词，跨组不可比。

**卡面纯文本**：本组卡体按**纯文本**渲染 `result.residual` 与 `achieved_scope`——不解析 Markdown 标记。写作侧纪律见 `21 §8`（建议段同纪律）。存量已带标记的对象**不自动追溯改写**（`03 §6.1`）；确需清理时须由 Human 单独授权，按事实更正处理（2026-09-24 已如此处置 1 例：`workcase-18fcee2c` 的残留条目去标记、文字逐字未改）。

**「不解析」不等于「不显示标记」——卡面渲染前须剥标记**（2026-09-24 补充，实测依据）：上述原文只写了「不解析」，而**纯文本插值恰恰会把 `**加粗**`、`` `标识符` `` 的标记本身显示给读者**。实测正文「## 结果」节的残留（「待批准关闭」期与关闭后的数据源）27 条中 **19 条含标记**，若原样插值，扫读窗口里会布满星号与反引号。故卡面渲染 `result.residual`、正文解析出的 `residual` 与建议段正文前，**须先剥离 Markdown 标记**；剥离函数为**单一实现**（`@/utils/cardText` 的 `stripCardMarkdown`），`ObjectList` 的既有同类处理亦已收敛到该处。**剥的是显示、不是数据**——详情面仍用 Markdown 渲染（语义保留），数据层不改：同一源文本在两面形态不同是有意的（卡面是扫读窗口、详情是阅读面）。**未验证范围**：该函数只去标记，不证明剥离后文本「准确」或「可读」；且它不处理代码围栏、链接与表格——卡面不承载这些，出现即应暴露而非静默吞掉。

**机械校验边界**：本组只证明**呈现当次**的读取与派生结果；不证明 `outcome` 判定正确、核对结论成立或残留已穷尽。计数与条数均为对字段的机械聚合。

## 6. 交互入口

交互入口承载 Human Gate 与交还流程。每个入口定义触发条件与 Human 响应契约，并在 Web 中呈现对应面板。

### 6.1 结构化问询

- **触发条件**：AI 需要 Human 判断、选择或补充信息，问题已组织为带选项、影响与风险的结构化形式
- **Human 响应契约**：呈现代选项与自由输入，响应须含对象、范围与处理结论

### 6.2 计划审查

- **触发条件**：AI 呈交候选计划，等待 Human 审查或批准；Gate 1 / Gate 2 的授权语义以 21 的定稿为准（21 已定稿，该语义不再为 provisional），34 号不定义 Gate 语义，故本节的触发依据以 21 现行文本为准
- **Human 响应契约**：呈现计划依据、范围、步骤与风险，Human 批准/拒绝/要求修改

### 6.3 授权流

- **触发条件**：AI 需要 Human 授权才能执行或继续某项受控操作
- **Human 响应契约**：呈现授权对象、范围、边界与执行状态，Human 授予/拒绝/限制，越权动作被机械拒绝

### 6.4 验收交还

- **触发条件**：AI 完成当前工作，呈交验收结果
- **Human 响应契约**：呈现 00 §7.4 Output Envelope 的 Human 可读视图与验证证据，Human 验收/退回/要求补充；Web 不重新定义 Envelope，也不把呈现或验收写成技术验证

### 6.5 登记管理

- **触发条件**：Human 在 Web 中发起项目登记或取消登记（对应 07 §5.4/§5.7 的 Web 入口）
- **Human 响应契约**：呈现登记对象、项目路径、综合就绪状态与分项诊断。**安装事务的步骤、状态闭集与失败处置由 08 §6 定义，本文不复述**；本文只定义其**呈现与交互约束**：(a) 用户选择的目录由 Host 确认为实际 Git 根后方可提交安装；(b) 未就绪项须分项呈现原因而非合并为单一结论；(c) 可修复与不可修复状态须在交互上可区分，前者提供修复入口、后者只呈现原因；(d) 写入与移除经 07 §5.4/§5.7 和 08 §6 定义的受控流程并分项回读确认，**Web 不自行解析或直写**登记载体、事实源或 Hook

## 7. 管辖登记与项目切换

07 §5 登记的管辖项目在 Web 中可切换呈现，规则如下：

- Web 通过 07 定义的唯一管辖判定职责读取 Human 已定案的登记载体，列出管辖项目；Web 不自行解析候选路径或 Schema；
- Human 在 Web 中切换当前呈现的管辖项目，切换后四层阅读器与交互入口均指向目标项目的事实源；
- 切换只作用于 Web 呈现层，不改变当前会话工作目录，不触发 LDVH CLI 或 Git 操作；
- 管辖判定消费方式沿用 07 §7 消费方表。

## 8. Web 边缘条件处理

以下条件处理仅影响 Web UI 呈现行为，本身不新增 Human Gate 触发条件或 Stop Conditions；Human Gate 以 00 §4.2 为准，Stop Conditions 以 00 §7.2、恢复以 §7.3 为准，本文领域增量见 §10–§11。

| 条件类型 | 具体条件 | 处理方式 |
|----------|----------|----------|
| 登记文件缺失 | 07 登记文件尚未创建 | 显示“尚未初始化”并提供受控安装入口；不可读、权限不足或 Schema 无效时显示 `unavailable`，不得伪装为“未管辖” |
| 项目未管辖 | 当前项目不在登记列表 | 隐藏 LDVH 功能，提示登记入口 |
| 授权范围不清 | 授权对象/范围/边界不明确 | 显示授权不可用状态，提示 Human 补充范围 |
| 交还未通过 | 验收交还条件不满足 | 退回至 AI 补充或修正 |
| 切换失败 | 目标项目登记文件损坏 | 保留当前项目呈现，提示问题 |

登记载体损坏、不可唯一解析等触及 07 §10 停止边界的条件，其暂停语义以 07 §10 与 00 §7.2 为准；Web 层仅按本节表格呈现对应状态（“尚未初始化”、`unavailable`、保留当前呈现并提示），不自行处置，也不把呈现写成暂停已执行。

## 9. 验证与证据边界

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 四层阅读器呈现 | 每次呈现或层间切换时 | 各层按 §5 语义呈现，层间切换不丢失已加载数据 | 各层渲染结果 | 呈现核对 | 当次呈现范围；不证明内容正确、事实成立或价值兑现 | 呈现异常时暂停受影响视图并修复 |
| 交互入口触发 | 交互面板出现时 | 面板出现时机与 §6 触发条件一致 | 各交互面板观察（含 §6.1–§6.5） | 触发条件核对 | 当次触发一致性；不证明提请内容正确或 Human 已回应 | 时机不一致时修正触发，不伪造面板 |

| 关键节点可回读 | Human 核对节点时 | 受控创建、状态变更、关闭节点在语义详情或扩展阅读可核对 | 语义详情与扩展阅读 | 节点回读核对 | 当次可回读范围；不证明节点语义正确 | 不可回读时如实披露缺口 |
| 价值声明可观察 | 声称 HV4/HV5 时 | 页面可呈现相应复用与演进依据 | 卡片网格与扩展阅读 | 呈现依据核对 | 只证明页面可呈现相应依据；不单独证明 HV4/HV5 已成立 | 无依据时降低声明并记录缺口 |

## 10. Human Gate

本文不新增 00 之外的 Human Gate。

### 10.1 领域增量事项

以下事项是 00 §4.2 在 Web 呈现与交互领域的具体化：

1. 改变四层阅读器的层级定义、切换契约或交互入口的触发条件与响应契约；
2. 改变管辖项目切换或 Web 边缘条件的处理语义。

受保护文档修改按 00 §4.3 执行，此处仅回指，不构成本文领域增量。

### 10.2 决定边界

Human 决定只证明决定及其作用范围，不替代呈现一致性核对、触发条件核对或节点回读核对。

## 11. Stop Conditions

本规范不新增根停止类型。

### 11.1 领域触发与影响范围

出现以下任一情况时，按 00 §7.2 暂停受影响的最小呈现、交互或完成声明范围：

1. 呈现所依据的来源（登记载体、事实源、Output Envelope）缺失、不可读或相互不一致；
2. 准备把页面呈现、组件加载或 Human 操作写成技术验证、授权成立或整体完成；
3. 交互入口的触发条件或响应契约无法确认。

### 11.2 暂停期间允许动作

暂停期间只允许不越过停止边界的规则定位、只读核对、呈现比对、修复与分流准备，不得继续受影响交互或完成声明。

### 11.3 恢复与再次触发

恢复须与触发原因对应，且只覆盖当前依据支持的范围；同一停止条件恢复后再次触发时按 00 §7.3 进入 Human Gate。

## 12. 反过度设计红线

1. 不要求四层阅读器互锁或从低层向高层递进；
2. 不指定 UI 框架、组件库或预设组件形态——只定义呈现语义与交互契约；
3. 不绕过 07 登记制度在 Web 侧自行解析管辖项目列表或候选路径；
4. 不在 Web 中直接改写规范或写入事实——均经 06 受控提交与 05 LDVH CLI 流程；
5. 不在已授权范围内重复提请 Human Gate 或把已授权操作再次转为问询；
6. 不为状态切换、加载或列表更新加入装饰性动画、过场或音效；必要的加载与进行中反馈只用于表明实际进行中的操作，不用于营造效果；
7. 不在单一视图中堆积与当前判断无关的信息，不以信息密度代替可用性；长列表与长文本须有分页、折叠或分层入口，不一次铺满；
8. 不用颜色、图标或动效单独承载状态语义；状态须有可读文本与可区分形态，使色觉差异或静音环境下仍可判断。
