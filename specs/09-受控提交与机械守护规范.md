# 受控提交与机械守护规范


## 1. 价值判断

本规范解决受控提交证据与规则源成员变化缺少统一边界的问题，通过提交契约、机械预检与 Git Gate，使提交候选的变更与授权来源可定位、可回读、可追溯，减少来源混淆、声明与差异不一致及未授权提交的风险。**事实源载体的定位与 Git 溯源由事实源与事实模型基础规范承接**，本文不重复展开，只在提交步骤中消费其结果。

事实源定位与提交历史主要支撑 V1 快速定位、V6 工作接续和 V8 持续积累；message 与 diff 对应、precheck 与 Git Gate 主要支撑 V5 据实判断；受控提交终闸和授权签名主要支撑 HV2 授权执行受控可续。本文不以全量价值声明替代主要影响判断。

本规范只提供受控提交与机械守护边界；事实源载体与溯源、事实对象语义、行动步骤、环境部署、Code 实现和 Web 呈现由事实源与事实模型基础规范 及相邻规范与实际工作承接。

载体存在、Git 命令成功、文件写入、precheck 通过或 Git Gate 放行，只能证明当次机械范围，不能单独证明事实语义真实、授权成立、工作完成或价值兑现。

**新增的负担与风险（00 §6.3 第 4 问，如实登记）**：本文不是无成本的。**新增以下负担**：(a) 每次受控提交都须满足 message 契约并逐条对应 diff，编写与核对成本高于自由提交；(b) 提交前须走 precheck、提交时须过 Git Gate，构成两次机械校验，增加单次提交的时延；(c) 受影响来源须维护 trailer 的权威取值链路，实现与联调成本高于无签名提交。**新增以下风险**：(a) **形式合规替代实质**——message 列举与 diff 逐条对应只能证明「列举完整、机械可匹配」，不证明变更语义正确、授权成立或工作完成；(b) **双入口不一致**——precheck 与 Git Gate 若作用于不同快照，会造成「预检通过但终闸拦下」或反之，须以 `snapshot_identity` 比对处置；(c) **受控范围被绕过**——普通编辑若不触及受管载体即可直接放行，判定规则的实现错误会使受控范围静默漏检。**核对方式**：以 §7 验证表逐项核对，交还按 §5 的失败处置如实分层声明。**若上述负担与风险在实践中被证明超过收益，应重审本文机制而非默认保留**（00 §6.3「答不出的不纳入」，反向亦成立）。

## 3. 职责边界

### 3.1 本文负责

1. 受控提交契约的成立条件、机械预检与 Git Gate 的效力边界；
2. 受控提交契约：message 格式、trailer 规则、message 与 diff 逐条对应（§5）；
3. `precheck-git-commit` 公开操作的机械校验语义与三值结果（§5.2）；
4. Git Gate（commit-msg）事件检查的同一 validator 与双入口要求（§5.5）；
5. 受保护文档 Merge 的治理边界（§5.6）；
6. 规则源成员的生效条件与退出方式（§6）。

### 3.2 本文不负责

1. 事实对象的字段、关系形状、CRUD、CAS、content_fingerprint、change_log——归事实源与事实模型基础规范；事实类型语义归各事实类型规范；
2. precheck 的请求/响应 envelope 字段闭集、能力发现、传输细节——归 LDVH CLI 确定性服务规范；
3. commit 的动作步骤（暂存、创建、回读）——归本文（见 §5.7）；
4. 写入或更新事实源规则的受控写入契约——归事实源与事实模型基础规范；
5. Git Hook 部署、插件装载、环境接入——归环境接入规范；Code 实现与测试——归 Code 实践与测试规范；Web 呈现——归 Web 呈现与交互规范；
6. AI 对适用、授权、语义正确的判断，与 Human 的授权、验收决定。

### 3.3 相邻规范分工与唯一权威

事实源与事实模型基础规范是事实源载体、事实对象公共模型与受控写入契约的唯一权威；LDVH CLI 确定性服务规范是传输 envelope 的唯一权威；规范模型是编号登记与成员资格的唯一权威；环境接入规范是 Git Hook 部署的唯一权威；Code 实践与测试规范是实现与测试的唯一权威。本文定义受控提交契约（含提交动作步骤，§5.7）与规则源成员的提交承接，不另建第二权威。

## 4. 适用范围

### 4.1 适用对象

本规范适用于：

1. 按来源规则须经受控流程的提交候选；
2. 规则源成员成立与退出中的提交承接。

### 4.2 适用场景

本规范用于提交消息与差异核对、机械预检、Git Gate、提交回读和提交链溯源。受控提交候选包括受管事实对象、规范源文件和规则源成员变更。

### 4.3 明确排除与证明边界

普通求解、普通编辑和非受管文件修改不因本规范存在而强制经过 precheck 或 Git Gate；本规范不适用于事实对象字段与状态、LDVH CLI envelope、Git Hook 部署、Code 实现或 Web 呈现。

载体存在、precheck 通过、Git Gate 放行或 commit 创建，只证明当次机械校验与 Git 结果范围，不单独证明事实语义、授权成立、工作完成或价值兑现。

## 5. 受控提交契约

### 5.1 message 契约

每个受控提交的 message 必须满足以下格式：

**Header**（一行）：`<type>: <简短描述>`。`type` 为小写 ASCII 单词，**不设 scope**（决策 #15，Human 决定 2026-08-25）。**过渡期兼容**：`type(scope): <描述>` 双段格式在过渡期内同样被接受。**过渡期的终止条件**：当（且仅当）**存量对象的提交历史不再需要与新格式共存**，即 (a) 本仓库不再有以 `type(scope)` 形式提交的待追溯记录，或 (b) Human 指定终止时点——满足其一即终止。**终止后**：`type(scope)` 形式须被机械校验拒绝，本节不再兼容；**终止时点及其依据须有 Human 决定记录**。过渡期内不得以「兼容」为由新增 `type(scope)` 提交。

**Body**（空一行后开始）：必须包含恰好一个唯一 `关键变更:` 小标题，其下以 `- ` 列表逐项列出每次实际变更。**每个 `- ` 列表项必须与本次提交的 diff 逐条对应**——不得列出 diff 中不存在的变更项，也不得遗漏 diff 中实际存在的变更项（防自欺核心规则，v4 教训 #10）。

**Trailer**（空一行后开始，两行，逐行写入）：

```
LDVH-Provider: <当次实际 provider>
LDVH-Model: <当次实际 model>
```

`LDVH-Provider` 与 `LDVH-Model` 由 Code 从 DSH 当次权威会话或请求记录机械取得并写入，AI 不判断、选择或填写；不得用部署默认值代替实际调用值。precheck 与 Git Gate 机械校验两行 trailer 的存在、取值来源和候选一致性。受控提交的 Human 授权不由 trailer 行承载（Human 决定 2026-09-02：不设 Human-Gate 行——自报文本无机械来源、无法防自欺）；授权事实存在于会话记录，机械校验由未来授权包承接（结构待 WorkCase/授权承接规范定义）。空白会话、历史会话和会话内模型切换的取值规则由环境接入规范与 Code 实践与测试规范实现并验证。

### 5.2 precheck-git-commit 公开操作

`precheck-git-commit` 是 LDVH CLI 公开操作：**语义归本文、传输归 LDVH CLI 确定性服务规范**。其公开操作声明按 LDVH CLI 确定性服务规范 §6.1 形状登记如下，输入与结果分别回指本文独立 H3（§5.3 与 §5.4）：

| operation_key | summary | effect | arguments_contract | result_contract |
|---|---|---|---|---|
| `precheck-git-commit` | 对受控提交候选执行只读机械预检，不声明提交已获授权 | read | `source-of-truth-traceability::5. 受控提交契约/5.3 precheck-git-commit 输入契约` | `source-of-truth-traceability::5. 受控提交契约/5.4 precheck-git-commit 结果契约` |

### 5.3 precheck-git-commit 输入契约

**性质**：只读机械校验。操作以受控提交候选的 message 文本与当前 Index diff 为输入，执行以下确定性检查：

1. Header 格式合规（按 §5.1 或过渡期规则）；
2. Body 含唯一 `关键变更:` 小标题；
3. 每个 `- ` 列表项与 diff 逐条对应（机械可判定部分：列表项与 diff 变更可匹配，无空列表项，无 diff 不存在的变更项，且 diff 的每个非豁免变更路径被至少一项机械覆盖——本反向半边落实 §5.1「不得遗漏」的可判定切片，2026-09-10 Human 批准；机械生成物豁免清单首批为 `package-lock.json` 与 `pnpm-lock.yaml`（独立审核发现本仓实存后者），由实现层登记维护，扩展清单不改变本条语义边界）；
4. Trailer 两行完整（LDVH-Provider / LDVH-Model），且 provider/model 可回指当次 DSH 权威记录。

### 5.4 precheck-git-commit 结果契约

**三值结果**（承载于 `mechanical_outcome` 字段，取值闭集如下）：

| 结果 | 含义 |
|---|---|
| `passed` | 全部机械校验通过；通过时返回 `snapshot_identity`（当前 Index diff 与候选的确定性指纹，如 `git diff --cached` 归一化后哈希，算法由 Code 实践与测试规范实现时确定，用于与 Git Gate 双入口一致性比对） |
| `failed` | 至少一项未通过，返回具体未通过项 |
| `unverifiable` | 输入不足以完成检查（如 Index 为空、message 不可解析），返回具体缺口 |

precheck 只执行来源已封闭定义的机械规则，不判断语义适用、授权范围或 Human 是否应同意；precheck 不替代 Git Gate 事件检查。

### 5.5 Git Gate（commit-msg）事件检查

Git Gate 是 00 §3.4 定义的机械守护终闸，在真实 Git 提交事件（commit-msg hook）中触发，提交前不可绕过。

- **同一 validator**：precheck 与 Git Gate 使用同一算法逻辑，只允许入口输入、响应形式与实际作用不同——precheck 返回结构化结果供 AI 消费，Git Gate 在提交时阻断或放行；
- **非 passed 即阻断**：阻断后不得使用 `--no-verify` 绕过，须修正后重新提交；
- **快照一致性**：Git Gate 通过时 stderr 输出 `LDVH Git Gate (commit-msg) passed` 与 `snapshot_identity`；AI 提交后核对 `snapshot_identity` 与 precheck 返回一致，确认双入口作用于同一提交候选。

Git Gate 依据 staged 内容是否触及受管载体（`ldvh-base/` 事实对象）、规范源文件或规则源成员变更，判定当次提交是否按受控提交契约检查；不含上述内容的普通提交在 hook 中直接放行。该判定规则由环境接入规范与 Code 实践与测试规范实现并验证。Git Gate 在 Hook 事件中的管辖状态检查按 管辖范围规范 §7 消费方表执行。

### 5.6 受保护文档 Merge 承接

受保护文档的 Merge 处理承接 00 §4.3，不由普通提交契约简化或替代。本节定义边界；**在实现与验证实际完成之前**，触及受保护文档的 Merge 必须暂停，不得声称 Merge 闭环成立。相关 Code、Hook 与 LDVH CLI 能力的实际可用性属实现现状，按 01 §7.2 由读取时的观察取得，本节不陈述其当前状态。

1. Merge 触及 00、README、插件 AI 面向语义文本、LICENSE 或已登记版本声明点时，不得静默选择一侧、直接拼接或以普通提交流程掩盖冲突。
2. 必须逐段形成合并结果，展示冲突处理后的现有内容与拟保留内容、差异及原因，并取得 Human 对准确合并结果的明确同意；该同意只覆盖明确列明的文档、段落和合并结果。
3. Merge 提交必须以 `Merge-Touched` 声明逐项申报所触及的受保护文档；声明缺失、文档清单不完整或作用范围不清楚时，不能进入受控 Merge。
4. 机械校验至少应识别冲突标记残留、`Merge-Touched` 声明缺失，以及登记的版本声明点发生漂移；任一检查不可用或未通过时必须阻断。
5. Merge 提交仍须经过真实 Git 事件中的 Git Gate；普通 commit-msg 检查不能替代受保护文档的逐段 Human 同意，也不能把 Merge 自动变成已授权、已验证或已完成。
6. 当前 v5 不定义 push、PR、远端 ref 或 pre-push；本节只覆盖本地 Merge 及其受保护文档治理。

### 5.7 提交的动作步骤

受控提交的**动作步骤**由本节定义。步骤只规定**顺序与每步的可核对结果**；具体命令、参数与实现属 Code 实践与测试规范，本节不预设。

1. **暂存（stage）**：把**当次授权范围内的变更**放进暂存区，使暂存内容与拟提交范围一致。
   - **可核对结果**：暂存内容能逐项对应到当次授权范围；**范围外的改动不得混入暂存**（含未授权的文件、他人改动与生成产物）。
   - **失败处置**：发现混入时须先移出暂存再继续；不得以「稍后修正」的方式带着范围外内容提交（00 §5.7）。
2. **创建（commit）**：以 §5.1 的 message 契约创建提交，使提交实际包含的内容与暂存内容一致。
   - **可核对结果**：提交的 message 段落与 trailer 符合 §5.1；**提交实际包含的变更与 message 中「关键变更」逐条对应**。
   - **失败处置**：message 与内容不符时不得靠修改 message 追认，须重新组织内容或修正 message 后重建提交。
3. **回读（read-back）**：提交完成后回读实际结果并核对，不得以「命令返回成功」代替核对。
   - **可核对结果**：回读到本次提交的标识与其实际包含的变更；回读结果与第 1、2 步的预期一致。
   - **失败处置**：回读不可用、结果不符或无法确认时，**不得声称提交已完成**，按 00 §5.7 暂停并如实披露未兑现范围（与 §7 的未满足处理一致）。

**三步的顺序不可跳过或合并**：未暂存不得创建、未回读不得声明完成。**本节只定义步骤与可核对结果**；这些步骤不能单独证明提交已获授权、已验证或工作已完成。


## 6. 规则源成员

1. **生效** = 文件存在（`specs/` 下、路径符合 01 §9.1 候选模式）+ 编号落在 01 §8.1 规定的号段内且按该段用途归属正确 + 提交经 Human 同意（创建或修改经 Human Gate 授权且 Git Gate 通过）。完整成立条件以 01 §9.2 为准；本条只列事实源域可见的必要条件，不豁免其余条件。规范不设生命周期 `status`（01 §6.3）。
2. **退出** = 该文件不再满足 01 §9.1 的候选模式或不满足 01 §9.2 的成立条件，记录退出原因、时间与取代来源（如有）；文件可保留，但已退出的不再作为当前规则源成员生效。退出的完整要求以 01 §9.3 为准。
3. **成员身份的权威来源是机械扫描结果**，不是任何人工登记表：一份规范是否在册，由 `specs/` 实际文件（01 §9.1 的候选发现）与 01 §9.2 各项条件分别核对得出。01 §8.1 只规定**号段与用途**及区段边界，**不登记段内成员**；本文只承接其生效与退出语义，不另建第二登记表，也不要求任何人工维护的成员清单存在。

**导出的判定（条件式）**：成员身份的机械扫描当前由 01 §9.1 定义的候选发现提供（其实现见 Code 实践与测试规范承接的 Code）。在扫描入口尚不可用的范围内，成员判定须以人工逐项核对替代，且不得声称已完成机械核对；无论以何种方式判定，结论都必须可回指到具体文件与 01 §9.2 的具体条件，不得以「在某个清单上」本身作为成员资格的证据。

## 7. 验证与证据边界

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 提交候选定位 | 读取提交候选或形成提交前 | 提交候选位于实际 Working Tree 且满足来源规则 | 当前 Working Tree 与路径规则 | 候选定位检查 | 候选定位范围与未检查范围；不证明载体存在、路径稳定或 Git 可跟踪，亦不证明内容正确、授权成立或完成 | 暂停受影响的提交候选定位并交还缺口 |
| message 机械合规 | 受控提交候选形成或 precheck 调用时 | §5.1 格式检查全部通过 | message 文本与本文 §5.1 | precheck 机械校验 | header/body/trailer 机械格式正确；不证明变更语义准确或 Human 授权 | 按返回的未通过项修复 message，不进入提交 |
| message 与 diff 对应 | precheck 调用时 | 每个 `- ` 列表项与 Index diff 逐条对应（机械可判定部分） | message 列表项与当前 Index diff | precheck 机械核对 | 机械可判定的对应范围；不证明变更语义、价值或授权 | 无法确认时按 00 §5.7 暂停提交并交还缺口 |
| precheck 结果 | 每次 precheck 调用后 | 检查依输入执行并返回三值结果 | precheck 响应 | 结果核对 | 当次候选的机械校验范围与结果；不证明适用、授权或 Human 同意 | `failed`/`unverifiable` 时修复输入后重试，不跳过检查 |
| Git Gate 阻断 | 真实提交事件中 | 事件检查非 passed 且提交被实际拒绝 | Git 事件输出与提交回读 | 事件检查与提交回读核对 | 当次提交被真实拦截；不证明修正已满足或绕过不存在 | 修正后重新提交，不得使用 `--no-verify` 绕过 |
| 双入口快照一致性 | 受控提交后 | `snapshot_identity` 与 precheck 返回一致 | precheck 响应与 Git Gate stderr 输出 | 提交后核对 | 双入口作用于同一提交候选；不证明提交语义或授权 | 不一致时暂停受影响的提交声明并按 00 §5.7 处置 |
| 成员生效与退出 | 宣称规则源成员变化时 | §6 条件与 01 §9.2/§9.3 相应条件分别有证据 | Working Tree、01 §9.1 候选发现结果、01 §9.2 条件核对、Human 决定与提交记录 | 资格条件逐项核对 | 规范在规则源中的成员身份；不证明内容正确、适用或价值成立 | 未证明项进入 gaps，不宣称成员生效 |

机械结果与语义判断互不替代。提交创建、precheck 通过、Git Gate 放行或登记一致只能证明各自机械范围；本章不能单独证明变更语义准确、Human 授权覆盖、事实成立或 V/HV 价值成立，未执行和不可用范围保留为 gaps。

## 8. Human Gate

本文不新增 00 之外的 Human Gate。

### 8.1 领域增量事项

以下事项是 00 §4.2 在事实源与受控提交领域的具体化：

1. 改变事实源载体定义（Working Tree 之外的承载形态）；
2. 改变受控提交契约的 message 格式、trailer 字段、precheck 机械校验规则或 Git Gate 事件检查语义；
3. 改变规则源成员的生效条件或退出方式；
4. 受保护文档 Merge 逐段合并结果的明确同意（00 §4.3 与本文 §5.6）。

受保护文档修改按 00 §4.3 执行，此处仅回指，不构成本文领域增量。

### 8.2 决定边界

Human 决定只证明决定及其作用范围，不替代 message 与 diff 对应核对、precheck 机械校验、Git Gate 事件检查或成员资格逐项核对。

## 9. 必停情形

本规范不新增根停止类型。

### 9.1 领域触发与影响范围

出现以下任一情况时，按 00 §5.7 暂停受影响的最小提交、成员声明或结果声明范围：

1. precheck 返回 `failed` 或 `unverifiable` 且未修正；
2. Git Gate 阻断后准备使用 `--no-verify` 或其它方式绕过；
3. message 与 diff 逐条对应无法确认；
4. 提交后 `snapshot_identity` 与预检不一致；
5. 机械扫描所得成员集合与 01 §9.2 条件的核对结论不一致（或该结论不可回指到具体文件与具体条件）；
6. 准备以普通提交替代受控提交流程。

### 9.2 暂停期间允许动作

暂停期间只允许不越过停止边界的规则定位、message 修复、Index 核对与预检重试，不得继续受影响提交或成员资格声明。

### 9.3 恢复与再次触发

恢复须与触发原因对应，且只覆盖当前依据支持的范围；同一停止条件恢复后再次触发时按 00 §5.7 进入 Human Gate。

## 10. 反过度设计红线

1. 不要求每次普通求解、普通编辑或非受管文件修改先经过 precheck 或 Git Gate；
2. 不以本文建立全局事务、全量审计日志或外部证明链；Git 历史即溯源记录；
3. 不重复定义事实校验层；提交链调用事实源与事实模型基础规范已定义实现的同一实现；
4. 不写入版本发布契约、时间表示（时间由 Code 托管填 RFC 3339）或来源枚举（归 LDVH CLI 确定性服务规范 `sources` 响应字段）；
5. 不复制事实对象身份清单（UUID 形态与版本等，归事实源与事实模型基础规范）；
6. 不在本清单重复 commit 的创建、暂存、回读步骤的操作细节（归本文 §5.7）。
