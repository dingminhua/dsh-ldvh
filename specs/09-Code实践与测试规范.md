## 1. 价值判断

本规范的目标是让 specs/ 下规范定义的机械规则有与规范一致、可测试、可回读的单一 Code 实现，减少实现与规范的漂移、副本逻辑与无证据的完成声明。本文主要承接 00 的以下价值：

- **V4 稳定推进**：工程纪律确保既有行动模板的 Code 实现可被复用，复用依据由语义显式对应（§6）。
- **V5 据实判断**：声明中已证实与未证实范围分层清晰——验证表（§7）逐行对应已证明与待证明边界。
- **V8 持续积累**：单一实现原则（§6）使相似事项的代码实现可复用既有经验与结论，不重复造轮子。
- **HV3 入档闭环节点可验**：测试基线确保每个机械规则有对应测试文件，可回读核对。

代码文件存在、测试通过、Lint 无错误或编译成功，均不单独证明以上价值成立；价值由实际使用、回读核对与后续验证共同核对。

上述机制对治 00 §1 的根缺陷：工程纪律与测试基线对治“概率性输出”（AI 声称实现但无机械可查证据），单一实现原则对治“上下文依赖”（多份副本逻辑漂移导致判断不一致），验证表对治“无连续状态”（把当次结果偷换为长期结论）。v4 同类问题——无统一工程纪律导致测试缺失、实现与规范漂移——通过 §5 测试基线与 §6 单一实现原则系统性承接，不再依赖逐案修补。

## 3. 职责边界

### 3.1 本文负责

1. LDVH 插件代码结构：目录规范、代码与测试文件命名约定、打包构建工具链与 lint 基准（§5）；
2. 测试基线：机械规则覆盖测试的要求，包括正反向用例、边界值及模拟数据（§5）；
3. 契约实现纪律：统一 Helper、precheck、管辖读取与 Git Gate 的单点实现与调用链，禁止副本逻辑（§6）；
4. 实现并测试 01 定义的规范身份块、L0–L4 读取与根级 Code 消费入口解析，不改变其语义（§6）；
5. Output Envelope 的单一生成与一致性实现职责（§6）。

### 3.2 本文不负责

1. Helper 服务契约、公开操作声明、传输 envelope——归 05；
2. 事实字段、状态机、CRUD、CAS——归 03；行动模板步骤、触发条件、完成门禁——归 04；
3. 事实源定义、受控提交契约、precheck 语义——归 06；
4. 管辖登记 Schema、判定逻辑——归 07；
5. DSH 插件接入、部署、发布与公共门面——归 08；Web 呈现——归 10；
6. AI 对实现是否满足语义要求的判断，与 Human 的授权、验收决定。

01–08 各自是其领域语义的唯一权威；09 只定义实现与测试纪律，不改变任何规范的语义，不成为第二规则源。

## 4. 适用范围

本规范适用于 specs/ 下规范定义的机械规则的 Code 实现与测试，包括插件代码结构、契约实现纪律、测试基线与 Output Envelope 生成职责。规范起草、语义讨论与 Human 决定不因本规范存在而自动取得实现效力；本规范不适用于事实类型语义、行动模板语义、Web 呈现或环境接入的领域定义。代码存在、测试通过或构建成功，只证明当次实现的机械范围，不单独证明规范语义已满足、行动允许或价值兑现。

## 5. 工程纪律

**目录结构**：规范实现位于 `src/rules/`（按规范 ID 分文件夹），测试文件位于 `tests/` 或与实现同目录，工具配置位于 `tools/`。

**命名约定**：文件与子目录小写 kebab-case，测试以 `.test.ts` 结尾，函数 camelCase，类 PascalCase。

**测试基线**：每个机械规则必须有对应单元或集成测试，覆盖正反向用例、边界条件、异常处理，拒绝零测试实现。代码实现与其验证测试须由不同代理或不同 AI 分任，避免同源自证；具体分任方式由主控按风险组织，不写死为单一宿主机制。

**Lint 与格式化**：ESLint + Prettier 统一配置，提交前必须通过静态分析，`git diff --check` 无空白错误。

**工具链**：TypeScript（Strict 模式），pnpm 管理依赖，Vitest 测试运行器，Vite/Rollup/ESBuild 构建工具。

## 6. 契约实现纪律

**单一实现原则**：下述职责分别由 01、03、05、06、07、08、10 定义唯一领域语义，09 只规定实现纪律，不替它们定义接口或行为。对应 Code 必须通过单一职责入口实现，严禁复制副本逻辑。

**规范解析实现**：01 §6 的身份块契约与 §10.3 的读取入口（`read-specification-candidates` / `read-specification-content`）由单一解析入口实现并测试，实现不得改变 01 语义；领域语义由 01 定义，09 只登记实现与测试纪律。

**Helper 操作契约**：Helper 仅负责共同请求/响应的解析与异常拦截，具体领域逻辑通过调用规范独立实现完成，不得在 Helper 中直接实现领域逻辑。

**Git Gate 共享**：Git commit-msg 与 Helper precheck 必须调用 06 定义的同一校验职责入口；具体路径由实现登记，不由 09 替 06 预定。`pre-push` 不纳入当前 v5 核心范围，不实现、不要求、不部署。

**管辖登记共享**：所有消费方必须调用 07 定义的唯一管辖判定职责入口，拒绝在各处独立解析；具体实现路径由 07/09 在实现时登记。

**机械签名**：提交（06 §6.1）、事实 `change_log`（03 公共字段署名要求）及其它来源后续定义的回报结构所需的 provider/model 必须由 Code 从 DSH 权威会话或请求记录取得，不允许 AI 自填、用部署默认值替代或由调用方覆盖；来源尚未定义所需签名的回报结构不在此列。空白会话、历史会话和模型切换场景必须有确定性取值与不可用结果。

**Output Envelope**：09 只定义并验证主控 Output Envelope 的单一生成职责；08 定义 DSH 宿主承载、写入时机、消费方和验收流映射，10 定义 Human 呈现。Human 可读正文由同一结构派生或经一致性检查，二者不得矛盾；Helper 共同响应只是输入，不得冒充主控交还。

## 7. 验证与证据边界

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 静态分析 | 提交前或 CI 检查时 | 文件命名、目录结构与 Lint 完全合规 | lint 输出与目录观察 | 静态分析检查 | 当次静态合规范围；不证明逻辑无缺陷或功能实现完整 | 修复后重跑，未通过不提交 |
| 测试基线 | 实现新增或修改后 | 每一机械规则均关联对应测试文件且运行通过，正反向用例与边界覆盖 | 测试文件与测试运行结果 | 测试运行核对 | 当次已运行规则的通过范围；不证明用例完备或无边缘遗漏 | 缺测试时补齐，未通过时修复，不宣称实现完成 |
| 单一实现 | 实现新增或修改后 | 同一规则只存在唯一职责入口实现，无副本逻辑 | 代码库扫描与调用链观察 | 副本扫描核对 | 当次扫描范围内唯一；不证明依赖方调用无绕过或调用语义无漂移 | 发现副本时合并到单一入口，未修复前不发布 |
| 规范一致性 | 实现或对应规范变化后 | 实现行为与对应规范条文一致，无漂移 | 规范条文与实现行为对照 | 一致性对照审核 | 当次对照范围；不证明规范本身正确或适用 | 漂移时暂停受影响功能声明并修复 |
| Output Envelope 一致性 | 每次交还生成后 | 机器可读 Envelope 与 Human 可读正文表达同一结果 | 生成结果与一致性检查记录 | 一致性检查 | 当次生成一致性；不证明交还内容正确或价值成立 | 不一致时修正，不得交付矛盾交还 |

机械结果与语义判断互不替代。编译、测试、Lint 或构建成功只能证明各自机械范围；本章不能单独证明规范语义满足、授权覆盖或 V/HV 价值成立，未执行和不可用范围保留为 gaps。

## 8. Human Gate

本文不新增 00 之外的 Human Gate。以下事项按 00 §4.2 提请 Human 对准确候选及作用范围作出明确决定：

1. 变更工具链配置、目录结构或命名约定；
2. 放宽测试覆盖要求，或改变验证边界与证据定义；
3. 新增或修改契约实现纪律。

受保护文档修改按 00 §4.3 执行，此处仅回指，不构成本文领域增量。

Human 决定只证明决定及其作用范围，不替代静态分析、测试运行、副本扫描或规范一致性对照。

## 9. Stop Conditions

本规范不新增根停止类型。出现以下任一情况时，按 00 §7.2 暂停受影响的实现、提交或完成声明：

1. 编译失败或 Lint 检查未通过；
2. 机械规则缺少对应测试；
3. 代码中存在针对同一规则的多份副本实现；
4. 管辖判定或校验器逻辑与对应规范发生漂移；
5. 准备实现未由生效规范确立的机械规则或属性。

恢复条件：修复对应代码使之与规范一致，且通过全部测试。同一停止条件恢复后再次触发时按 00 §7.3 进入 Human Gate。

## 10. 反过度设计红线

1. 不为非 LDVH 规范需求编写跨平台、多宿主的通用 Hook 或中间件适配层；
2. 不实现未在 specs/ 当前规则源成员规范（00–08 及 10）中确立为生效的机械规则与属性；
3. 不因懒于重构而复制已有的校验器、管辖判定或 Helper 封包逻辑。
