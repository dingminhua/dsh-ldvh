## 1. 价值判断

- **V4 稳定推进**：工程纪律确保既有行动模板的 Code 实现可被复用，复用依据由语义显式对应（§5）；
- **V5 据实判断**：声明中已证实与未证实范围分层清晰——验证表（§6）的三列对应已证明/待证明边界；
- **V8 持续积累**：单一实现原则（§5）使相似事项的代码实现可复用既有经验与结论，不重复造轮子；
- **HV3 闭环节点可验**：测试基线确保每个机械规则有对应测试文件，可回读核对。

代码文件存在、测试通过、Lint 无错误或编译成功，均不单独证明以上价值成立；价值由实际使用、回读核对与后续验证共同核对。

上述机制对治 00 §1 的根缺陷：工程纪律与测试基线对治"概率性输出"（AI 声称实现但无机械可查证据），单一实现原则对治"上下文依赖"（多份副本逻辑漂移导致判断不一致），验证表对治"无连续状态"（把当次结果偷换为长期结论）。v4 同类问题——无统一工程纪律导致测试缺失、实现与规范漂移——通过 §4 测试基线与 §5 单一实现原则系统性承接，不再依赖逐案修补。

## 4. 工程纪律

**目录结构**：规范实现位于 `src/rules/`（按规范 ID 分文件夹），测试文件位于 `tests/` 或与实现同目录，工具配置位于 `tools/`。

**命名约定**：文件与子目录小写 kebab-case，测试以 `.test.ts` 结尾，函数 camelCase，类 PascalCase。

**测试基线**：每个机械规则必须有对应单元或集成测试，覆盖正反向用例、边界条件、异常处理，拒绝零测试实现。代码实现与其验证测试须由不同代理或不同 AI 分任，避免同源自证；具体分任方式由主控按风险组织，不写死为单一宿主机制。

**Lint 与格式化**：ESLint + Prettier 统一配置，提交前必须通过静态分析，`git diff --check` 无空白错误。

**工具链**：TypeScript（Strict 模式），pnpm 管理依赖，Vitest 测试运行器，Vite/Rollup/ESBuild 构建工具。

## 5. 契约实现纪律

**单一实现原则**：下述职责分别由 05、06、07、08 定义唯一领域语义，09 只规定实现纪律，不替它们定义接口或行为。对应 Code 必须通过单一职责入口实现，严禁复制副本逻辑。

**Helper 操作契约**：Helper 仅负责共同请求/响应的解析与异常拦截，具体领域逻辑通过调用规范独立实现完成，不得在 Helper 中直接实现领域逻辑。

**Git Gate 共享**：Git commit-msg 与 Helper precheck 必须调用 06 定义的同一校验职责入口；具体路径由实现登记，不由 09 替 06 预定。`pre-push` 不纳入当前 v5 核心范围，不实现、不要求、不部署。

**管辖登记共享**：所有消费方必须调用 07 定义的唯一管辖判定职责入口，拒绝在各处独立解析；具体实现路径由 07/09 在实现时登记。

**机械签名**：提交、事实 `change_log` 和协同回报所需的 provider/model 必须由 Code 从 DSH 权威会话或请求记录取得，不允许 AI 自填、用部署默认值替代或由调用方覆盖。空白会话、历史会话和模型切换场景必须有确定性取值与不可用结果。

**Output Envelope**：09 只定义并验证主控 Output Envelope 的单一生成职责；08 定义 DSH 宿主承载、写入时机、消费方和验收流映射，10 定义 Human 呈现。Human 可读正文由同一结构派生或经一致性检查，二者不得矛盾；Helper 共同响应只是输入，不得冒充主控交还。

## 6. 验证与证据边界

| 验证对象 | 可证明范围 | 不能单独证明 |
|----------|------------|--------------|
| 静态分析 | 文件命名、目录结构与 Lint 完全合规 | 逻辑无缺陷、功能实现完整 |
| 测试基线 | 每一机械规则均关联对应测试文件且运行通过 | 测试用例完备、无边缘幻觉遗漏 |
| 单一实现 | 仅存在唯一的管辖判定与 Gate 校验逻辑实现 | 依赖方调用无绕过、调用语义无漂移 |

## 7. Human Gate / Stop Conditions

**Human Gate**：变更工具链配置、目录结构或命名约定；放宽测试覆盖要求；修改验证边界与证据定义；新增或修改契约实现纪律。

**Stop Conditions**：编译失败或 Lint 检查未过；机械规则缺少对应测试；在代码中发现针对同一规则的多份副本实现；管辖判定或校验器逻辑与规范发生漂移。

恢复条件：修复对应代码使之与规范一致，且通过全部测试。

## 8. 反过度设计红线

1. 不写通用抽象层：不得为非 LDVH 规范需求编写任何跨平台、多宿主的通用 Hook 或中间件适配层；
2. 不写超前实现：严禁实现未在 00–08 规范中被确立为生效（或 active）的机械规则与属性；
3. 不写重复逻辑：严禁因懒于重构而复制已有的校验器、管辖判定或 Helper 封包逻辑。
