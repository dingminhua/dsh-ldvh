# 规范源与规范模型基础规范


## 1. 价值判断

本规范的机械解析与提交完成只证明相应机械范围，不能单独证明规范内容正确、规则适用、Human 已授权、行动完成或长期价值成立；该证明边界的共同规则见 00 §4.6、§7.4 C-6。

## 2. 规范依据

本规范直接依据：

1. `ldvh-root`：00 §1 的核心价值、00 §2 的方法与构成（含 00 §2.4 的规范源与事实源）、00 §3 的 Human 权利、00 §4 的 AI 责任与义务（含 00 §4.6 据实声明、00 §4.7 必停情形与恢复、00 §4.8 交还与撤回、00 §4.9 流程轻重与后果相称）和 00 §5 的价值纪律。

GFM 与 YAML 1.2.2 Core Schema 只提供外部语法定义，不取得 LDVH 领域语义权威。历史版本、开发备忘、审计材料、聊天、Code、tests 与工具输出只作设计输入或证据，不是本规范的规范依据，也不因此进入当前规则源。下位来源不得改变、稀释 00 的根定义（`00 §2.9`）；冲突或权威不明时按 `00 §4.7` 暂停对齐。

## 3. 职责边界

### 3.1 本文负责

本规范负责：

1. 根规范、普通规范和授权附件的角色及 YAML 身份契约；
2. 职责标识符、编号、登记、规范关系和附件授权；
3. 普通规范的共同章节结构与基础模型规范对下属规范的结构责任；
4. 当前规则源成员的成立、退出、视图与失败边界；
5. L0–L4 规范读取层级、来源回指与安全展开边界；
6. 最小规则引导中必须提供的 00 锚点；
7. 规范新建、修改、拆分、合并、取消与旧规则处置判断；
8. 风险匹配的独立审核、修复和复审。

身份字段闭集见 §6 与 [01.Att.02-规范身份字段表](attachments/01.Att.02-规范身份字段表.md)。

### 3.2 本文不负责

本规范不定义事实源与事实模型、事实类型、业务系统规范共同结构、检查机制、能力承载与 LDVH CLI 共同 envelope、受控提交契约与机械守护、管辖解析、宿主接入、Code 实现或 Web 呈现的领域规则。

### 3.3 相邻规范分工与唯一权威

00 是根定义的唯一权威；02 定义事实公共模型、事实源载体与事实类型共同结构；03 定义业务系统规范共同结构；04 定义检查机制；05 定义共同请求与响应 envelope、06 承接规范解析的实现与测试、09 定义受控提交契约与机械守护、10 定义宿主接入。本规范只定义规范源与规范模型，不复制这些相邻规范的领域语义、协议或实现细节。

## 4. 适用范围

### 4.1 适用对象与场景

本规范适用于：

1. `specs/` 根目录下的 LDVH 规范；
2. `specs/attachments/` 下由唯一父规范明确授权的附件；
3. Human、AI 与 Code 对上述文件的共同消费——用于上述文件的建立、识别、定位、分层读取、登记、审核、修改和一致性检查。

### 4.2 明确排除与证明边界

00 是根规范，不适用普通规范固定章节结构，但仍须以自身结构承担根职责。本规范的适用范围只表示实质涉及的工作面，不限定本文对系统或检查机制的名称、根职责、协同模型或操作流程的定义权。本规范不把 `docs/`、`archive/`、Code、tests、缓存、索引、聊天、评审结论或工具输出转化为规范源。

## 5. 基础术语与文件角色

1. **规范文档**：位于 `specs/` 根目录、承担明确且稳定规范职责的 Markdown 文件；
2. **根规范**：00，职责标识符固定为 `ldvh-root`，定义 LDVH Human 根契约；
3. **普通规范**：根规范之外、依据 00 建立并承担稳定规范职责的规范；
4. **授权附件**：由唯一父规范登记，只承载父规范已经定义并授权的字段表、登记表、清单、矩阵或术语等结构化内容及必要使用说明；不得建立新的独立规则、Human Gate 或必停情形；
5. **身份块**：文件头 `---` 围栏包裹的 YAML frontmatter，围栏闭合后空一行、再出现唯一 H1；
6. **职责标识符**：由 `spec_key` 或 `attachment_key` 承载，不随标题、编号或路径变化，不得改派；
7. **定义来源**：对某概念的含义、边界和相邻概念差异承担唯一定义责任的当前规范章节；
8. **设计草案**：尚未取得 Human 对准确候选及作用范围确认的规范候选；
9. **设计基线**：经 Human 明确确认，可用于继续建立和审核规范，但尚不等于当前规则源成员；
10. **当前规则源成员**：满足 §9 全部成立条件并进入当前来源视图的规范或授权附件；
11. **渐进式披露**：其含义、边界与对两个来源的作用见 `00 §2.4`，本规范不重复；本规范侧的增量是分层读取的层级口径——规范读取的 L0–L4 层级语义、各层承载内容与用途在 §10.2 与 `01.Att.03` §4 承担，消费方可直接请求任何足够层级、不强制逐层仪式；
12. **独立复核**与**独立审核**：两条互不替代的审查轴——**独立复核**对已发生的实际工作与结果对照核对（对应 00 §2.5 的代理复核），**独立审核**对尚未取得效力的候选主动找错（触发与执行见 §12）。二者对象、时点不同，任一轴不构成另一轴的履行；本规范及受辖规范统一使用这两个词形，形态展开见 `04`。「多视角」是 `04` 所定视角维度之一、不是机制名；
13. **反稀释**：下位来源和实现不得借细化、默认值、自动化、兼容处理或其它方式改变、绕过或使 00 的根定义形同虚设；
14. **基础模型规范**：为某一类规范定义共同结构、必填内容与扩展规则的普通规范；其覆盖范围按职责所服务的那类规范（见 §7.2）与 §8.1 号段判定。本规范指定 02 服务于事实类型规范（`20–29` 段）、03 服务于业务系统规范（`30–39` 段）。结构父与基础模型规范可分离，义务归属见 §7.2。

## 6. YAML 身份块契约

### 6.1 位置、语法与解析边界

文件第一行是 `---`，与下一个 `---` 共同包裹唯一身份块（YAML frontmatter）；围栏闭合后空一行，紧随唯一 H1。Markdown 使用 GFM，身份块使用 YAML 1.2.2 Core Schema。顶层只允许 `ldvh_spec` 或 `ldvh_attachment` 一个映射。

实现与本节不一致时，按 `00 §4.7` 暂停受影响范围并按 §12 独立审核后对齐，不得静默选边。

不允许重复 key、未知字段、多个 YAML 文档、自定义标签、锚点、别名或合并键。字符串与字符串列表成员使用双引号。字段类型、必填性、空值、格式、闭集、列表规则及根规范 profile 由 [01.Att.02-规范身份字段表](attachments/01.Att.02-规范身份字段表.md) 承载；附件只展开本节已经授权的契约，不得自行增加字段语义。

### 6.2 职责标识符与一致性

`spec_key` 与 `attachment_key` 匹配 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`，在当前规则源及可回查历史中唯一且不改派。编号、标题和路径可经 Human 决定变化，但职责标识符保持不变；职责实质改变到不再是同一责任时应建立新 key。

`title`、编号字段和 `canonical_path` 分别镜像实际 H1、文件名前缀和当前 worktree 相对路径。身份块、正文和实际载体冲突时必须修复，不得选择较方便的一方继续。

**根级 Code 消费入口的解析**：根规范 `code_consumption` 的成员（字段形状、必填性与「不证明实现存在」的边界见 `01.Att.02`）各自解析到的契约按本条对应关系确定，本条是该对应关系的唯一权威：

- `spec-identity-block`：§6.1 的身份块位置、语法与解析边界，与 §6.2 的职责标识符与一致性；
- `spec-read-contract`：§9.1 的来源视图与同快照要求、§10.2 的读取层级语义（层级结构化表见 `01.Att.03` §4）与 §10.3 的读取入口边界；
- `minimal-guidance-profile`：§10.4 的最小规则引导；
- `ldvh-cli-boundary`：05 §7 的最小共同请求语义与 §8 的最小共同响应语义（接入面不得改写共同响应字段语义见 05 §5.2）。

入口名的增删或改名须同步根规范 `code_consumption` 声明与本对应关系（`00 §3.2`、`00 §3.3`）。不得据登记主张入口已实现；声明与本对应关系不一致时按 `00 §4.7` 暂停并披露。

### 6.3 规范建设阶段与效力条件

规范建设区分设计草案、设计基线和当前规则源成员（三者定义见 §5 第 8–10 项），但普通规范和附件不设置生命周期 `status` 字段。设计基线必须有 Human 对准确候选及作用范围的明确确认；成为当前规则源成员还必须满足 §9。文件存在、登记、审核、Human 决定或提交任一单项都不自动产生完整规则效力。

**建设阶段是读取与判断时的结论，不是载体内容**：载体不得陈述自身或他者的当前阶段或完备度（该判断由读取方按 §9.2 核对），附件亦不得以专设列、取值闭集或标记承载此类登记（按 §7.2 状态禁令与 §8.3 处置）。三个阶段概念可在规则中引用，用于「某阶段之前不得如何」类义务。

**来源占位允许**：「待定义」类占位是义务的条件而非状态登记，须在既有登记栏内以条件句或括注给出，不得做成专设列或与 `defined`／`provisional` 一类取值闭集并列；其条件含义与恢复条件按 §7.2 的回查锚承载。

**越界内容的处置**：以专设列、取值闭集或标记承载的完备度登记，若改为条件式要求且不再以这些形态承载，则不属本节禁止、可予保留；其保留、改写或删除按 §8.3 与 §11 处理，本节不一次性授权。此为 §9.2 所引「按 §8.3 与本规范 §11 另行处理」通道。

## 7. 普通规范共同章节契约

除 00 外，普通规范前四个 H2 与末尾四个 H2 的编号和标题固定，中间领域正文按 §7.2 约束自由定义。

**共同规则单点承载与回指优先**。对各普通规范统一适用的共同规则由 §7.4 单点承载。固定章节要求某条共同规则出现时：

- 无领域增量——以一行回指 §7.4 对应条款或相应上位章节呈现，不得自陈复制其文本；
- 有领域增量——自陈增量内容，共同部分以一行回指补足（验证表对规则的投影除外，§7.2）。

**领域增量**指受辖规范就某共同规则在本领域实际出现的对象、环节或动作上所作的具体化；共同条款与 00 上位内容本身不构成增量。以回指呈现即断言该元素无增量；有增量而仅回指，与无增量而自陈复制，同样不满足本条。无增量而自陈复制共同条款或 00 内容的，属为满足共同章节结构制造重复（§16 红线 2；存量成员的核对时点按本章末段过渡条款执行）。

**回指的形态**。最小形态是含被指章节号或条款号的正文引用（如 §7.4 C-2、00 §4.7）；与 02 §7.1 所称「来源回指」（事实对象对其来源的引用）不同义。自陈与回指向读者承载同一义务，两式并存不构成重复权威；回指与本章各章末「一句明确回指」同义。

**固定章节的最小要求**。本章规定各固定章节的最小必填语义元素，元素必须可辨认——读者和审核者能据实指出其在正文中的位置；领域规则单元的内容按 §7.2 按需书写，不设必填元素清单。固定章节须包含相同语义元素、遵循本章规定的信息顺序、使用相近的段落结构与清单粒度，使同类信息在不同规范中位于可预期位置；但不要求逐字相同、篇幅相同或统一文体（本章明确规定的 H3 分组、验证表格与红线编号清单除外）。全部八个固定章节的标题可增加不改变结构角色的领域限定词，但固定标题文字必须逐字保留，使机械规则能唯一识别其结构角色。

### 7.1 固定前置章节

1. `## 1. 价值判断` 以一句承载本规范**不能单独证明的范围**；不承载 00 §2.4.4 第 2 项所称立项论证（含价值对齐、代价与证据取舍）。无领域增量时以一句回指 00 §4.6，不制造空段或套话。定位类的价值内容按基础模型规范（02、03）在领域正文承载，不并入本章。

   `00 §5.1` 的准入说明（落实哪项根方案、服务核心价值哪一面、新增什么负担与风险、以什么证据核对）在新建或修改机制的提请与独立审核中逐项说明，答不出的不纳入，不写入正文；其记录的稳定承载形式由下位规范承接，本节不指定。
2. `## 2. 规范依据` 固定按以下顺序表达：先以编号清单列出直接且必要的上位规范及所依据章节；清单每项必须对应身份块 `basis` 的一个成员，使用 `` `spec_key`：规范编号 + 精确章节`` 的形式，顺序与 `basis` 一致，不得把同一 basis 的不同章节拆成多个编号项；再用独立段落排除非规范输入；确实依赖外部语法或标准时，在非规范输入之前增加独立段落，说明它只提供外部定义、不取得 LDVH 领域语义权威。上位来源冲突或权威关系无法确认时的处置由 §7.4 C-1 单点承载。
3. `## 3. 职责边界` 固定依次使用 `### 3.1 本文负责`、`### 3.2 本文不负责`、`### 3.3 相邻规范分工与唯一权威` 三个 H3；各节使用直接段落或编号清单，不把三类信息混写在同一段。
4. `## 4. 适用范围` 固定依次使用 `### 4.1 适用对象与场景`、`### 4.2 明确排除与证明边界` 两个 H3；适用对象多于一项时使用编号清单，适用场景紧随其后。第二节说明明确排除，并在存在“范围成立被误当作生效、许可或完成”的混淆风险时说明范围成立不能单独证明什么；通用边界由 00 §2.4 与本文 §9–§10 承载，不逐份复制。

### 7.2 领域正文与规则单元

第 5 章起由各规范按职责和最小充分原则自由定义。同一语义元素的**完整展开**——以定义、规则或不变量的完整表述形态出现——在同一规范内（含固定章节与领域正文）只出现一次；其余位置以指向该唯一展开处的引用承载，不得重复展开；验证表对规则的投影不属重复展开。领域正文不得复制 00 根定义、相邻规范的唯一职责或实现细节。`00 §2.9` 载有根规范对其自身书写的约束；本规范不重复其内容，本规范自身的共同章节与领域规则按第 7 章执行。基础模型规范还必须定义其下属规范共同结构、必填内容和扩展规则：**02 定义事实类型规范（`20–29` 段）的共同结构**；**03 定义业务系统规范（`30–39` 段）的共同结构**。

**规范不承载状态（作用域覆盖 `specs/` 内一切载体）**：状态禁令不以「规范正文」为限——其主体是**规范**，覆盖 `specs/` 内的任何载体：普通规范正文与固定章节、授权附件的表格、列头与取值，以及其它任何承载形态。载体形态不构成豁免：状态写进正文、表格、列名还是取值，同样受本款禁止。以下各段是本禁令的适用方式与判据。

**本禁令作用域的扩张属 `00 §3.2` 的根决定事项**（依 `00 §3.2` 与 `00 §2.4`：本禁令作用域的扩张属根决定事项；Human 决定按其作用范围生效但不因此成为常设规范，不在规范正文重复记载）。

**判据（断言 vs 规定，载体无关）**：`specs/` 内的任一承载单元——无论一句正文、一个**标题**（含 H1／H2／H3）、一个表格列头，还是一列取值——**断言某对象或载体「当前是什么」者，是状态，不得承载**；**规定「应当做／不得做」者（无论是否附条件），是规则，应当承载**。**可改写性测试**：把该单元改写成「在 X 成立时，应当／不得……」并**不损失其内容**的，落入规则侧（允许）；**一经改写即失真、或其内容就是某个现状的描述**的，落入状态侧（禁止）。**三项附带操作检查（补充上句，缺一即不得据改写测试判为规则）**：

1. **对象无关性**——规则的条件 `X` **不得指向某个既定的外部事实**（「待 21 定义」这类来源占位是**尚未确定**的条件，可以；「X＝该模块已实现」指向既定事实，**不可以**）；
2. **实测值不进规则**——改写后若仍须保留具体计数、日期、文件名或函数名（如 `1024/1024`、「落盘」），则该内容仍是状态，**不得以「在 X 成立时应当…」的句式保留**；
3. **两类须与状态区分的边界形态**（改写测试对此二者给不出答案，故单列）：① **契约 vs 现状观察**——「该入口的注册结果以装载后检查为准」「该服务不是授权通道、不得作为授权入口消费」是**规定该依赖应如何被使用与校验**（契约，规则）；而「该入口当前为只读」「该服务现已接入」是**观察其现状**（状态，禁止）。分界：**规定它必须如何**者为契约，**报告它现在如何**者为状态。② **无条件的范畴式规则**——「不得把已实现但未执行的校验返回为通过」这类**不含条件 `X`** 的普遍禁止／普遍义务，**本身就是规则**（改写测试无 X 可套，不等于落入状态侧）；判定看其是否**规定一类行为在任何情形下的对待方式**。

**本判据是 `specs/` 内判定「状态」的唯一判据**，其它规范或附件不得另行表述等价判据，只能回指本节。判定按承载单元逐处进行（复合句拆到最小成分），规则性部分保留、状态性部分删除或改写为条件式要求，不按段落整体豁免或废弃。

据此，三类内容**禁止**（最常见的违规形态）：

1. **实现状态**：某项机制、校验、接口或能力「已实现／尚未实现／未接入／已由某提交落地」，以及实现所在的文件、函数或批次说明；
2. **下位文档的存在状态**：某编号是否已有规范、某段内已建立几份规范、某份规范处于何种生命周期阶段；
3. **过程与进度**：当前处理到哪一步、待办事项、已完成的轮次或批次。

以下为规则、不受禁：条件式要求与反例、对读者的处置指引；规范对其依赖的外部接口或宿主机制所要求的契约；事实对象的状态机与状态取值（规范为对象设定的分类与转移规则）。**规范自身的登记项**（依 §8、§9、§13 建立、受 §9.2 第 10 项约束的编号／号位／关系／附件授权）准确性正是规范成立条件，不受禁；但表内夹带的现状陈述、或在登记项外另行陈述「某编号当前是否已建、某规范现处何种阶段」者仍是状态。

**来源占位判别**：条件式占位（「待定义」一类）适用 §6.3；占位所在列若同时承载字段的封闭取值集合（如 `defined`／`provisional`）即属并列、受禁，若承载逐条各异的实质内容则允许。占位的条件含义与恢复条件须载于同单元格括注、同表紧前说明段或同一次级标题说明段之一。

**状态的去向**：现状信息由观察取得，不由规范承载；确需提示时以条件式要求表达。本节不建立状态登记载体，也不授权他人建立（§9.3、§16 第 3 条）。「建设状态」「规范状态」及等价词形不得作为 `specs/` 承载名目，附件表格亦不得以任何名目登记规范载体的存续状况。

**基础模型规范覆盖范围**（定义见 §5 第 14 项、号段见 §8.1）：`20–29` 段受 02 约束、`30–39` 段受 03 约束，与 `parent_spec` 指向无关（`parent_spec` 只表结构归属，依 `01.Att.03`）。已进入规则源的段内规范受该段基础模型规范约束，空号不产生义务。结构父与基础模型规范分离时，共同结构定义义务属基础模型规范、结构父只承担结构归属（依 `01.Att.03`）；基础模型规范须声明其覆盖范围、结构父须声明共同结构的权威去向、下属规范须能被前两者之一明确覆盖，三者一致可查，悬空按 `00 §4.7` 暂停补齐。

领域正文以规则单元为消费粒度。规则单元是完整包含在单一 L3 标题路径返回范围内的最小正文单元，通常为 H2/H3 小节，或同一小节内共同表达一项规则且边界明确的一组条目；规则单元不得跨标题拆分。仅用于聚合多个可独立消费 H3 的容器 H2 本身不是规则单元，该容器小节的正文只承担全部子单元共享的定位与边界。规则单元的内容按其规则本身的需要书写：定位、规则或不变量、边界（不能单独证明什么、何时不适用或与相近概念的差异）、成立条件、反例、相邻规范分工、独立验证或失败处理等元素**按需出现**，无增量时省略，不得用空句或固定标签占位。

具体规则使用直接、词义一致的陈述，并在本规范适用范围内说明对象与场景。示例、说明和建议不因出现在规范中自动取得强制效力。需要 Code 稳定引用的规则，应位于具有明确标题、表头或结构说明的段落、列表、表格或授权附件中。多行同构且有机器消费方的契约使用表格；单条机器消费契约可以按稳定定位需要使用带表头的表格；单条自然语言规则使用陈述句或列表，不为形式统一拆表或增加固定小标题。

### 7.3 固定收尾章节

每份普通规范末尾依次包含下列四个 H2，编号随领域正文连续顺延：

1. `验证与证据边界`：存在领域验证对象时，必须使用以下四列表头，表头文字与顺序固定：

   | 验证对象 | 成立条件 | 验证入口 | 未满足时的处理 |
   |---|---|---|---|

   每行必须绑定本规范自身的对象、契约、边界或失败场景；已由 00 或其它来源完整定义的共同验证只作必要回指，不另起重复行；没有真实的成立条件时，不得以空泛的“AI 审核”“后续检查”或同义占位填充行。验证时机、可接受依据与可证明范围按需写入「成立条件」或「未满足时的处理」单元格，不另设列。章节末尾说明机械结果与语义判断互不替代（按 §7 回指优先，对应 §7.4 C-6），以及本章不能单独证明的范围。无领域验证增量时用一句回指 00 §4.6，不制造空表格。
2. `Human Gate` 固定按以下顺序表达：第一段声明是否新增 00 之外的 Human Gate（按 §7 回指优先，对应 §7.4 C-3）；有领域增量时，随后使用编号清单登记本领域的 Human 决定增量事项——包括 00 §3.2 根清单的领域具体化与上位未完整定义的本领域决定事项；末段说明 Human 决定只证明决定及其作用范围，不替代本领域哪些验证或判断。无增量时只保留第一段并一句回指 00 §3，不制造空清单。
3. `必停情形` 固定按以下顺序表达：第一段声明不新增必停的根触发（按 §7 回指优先，对应 §7.4 C-4）；有领域增量时，随后使用编号清单登记领域触发及其最小影响范围；再用独立段落说明暂停期间允许动作（确有增量时按 §7 回指优先，对应 §7.4 C-5）、恢复条件和同一条件再次触发进入 Human Gate（按 §7 回指优先，对应 §7.4 C-2）。无增量时只保留第一段并一句回指 00 §4.7，不制造空清单。
4. `反过度设计红线` **按需承载**：本规范存在真实的领域过度设计风险时，用编号清单登记，每条一句指明对象与禁止行为，理由或边界仅在不自明时附注，不登记无对象或无禁止行为的口号句；无领域风险时以一句回指 `00 §4.9`（流程轻重与后果相称）与 `00 §2.9`（不得新增语义构成要素、不得建立第二套权威）承载，不制造口号清单。

无领域增量时用一句明确回指，不制造空规则、空表格或重复清单。设计草案可临时附带起草核对材料，但在 Human 确认设计基线前应删除，或吸收到正式结构角色中。

### 7.4 共同条款

本节对各普通规范统一适用的共同规则**单点承载**，各款本身即完整规则，受辖规范不必逐份复制，按 §7 回指优先呈现；各款修改只在本节发生一次，不构成对受辖规范的实质修改。

受辖规范可就各款作**本领域具体化**（列举本领域实际对象、环节、动作，并在本款允许范围内收窄），共同部分仍以回指补足。以下三种越出区间构成冲突：扩大本款允许范围、削减或删去本款禁止事项、遗漏本款要求事项。

**C-1（上位冲突与对齐）**：普通规范与上位来源发生冲突，或权威关系无法确认时，不静默选边，按 `00 §4.7` 暂停受影响范围并完成对齐。

**C-2（恢复与再次触发）**：恢复须与触发原因逐项对应，且只覆盖当前依据支持的范围；同一必停情形恢复后再次触发的，不得再次自行恢复，必须按 `00 §4.7` 进入 Human Gate。**本款是 `00 §4.7` 在规范域的实体；受辖规范的领域增量是「本领域有哪些触发、其恢复对应什么」**，而非重复本款。故受辖规范按其领域列出触发与恢复对应关系即满足；无领域增量时以回指本款满足。

**C-3（不新增根 Human Gate）**：普通规范不新增 00 之外的根 Human Gate；存在领域增量时，按 §7.3 第 2 项以编号清单登记 00 §3.2 根清单的领域具体化事项与上位未完整定义的本领域决定事项。Human 决定只证明决定及其作用范围。

**C-4（不新增必停的根触发）**：普通规范不新增必停的根触发；存在领域增量时，按 §7.3 第 3 项以编号清单登记领域触发及其最小影响范围。**本款不要求受辖规范复述根触发的清单内容**——其领域义务是列出本领域触发，或回指本款；§7.3 第 3 项要求的声明段仍须有。

**C-5（暂停期间允许动作）**：暂停期间允许的动作限于不越过必停边界者；各规范按其领域说明本领域允许的具体动作（§7.3 第 3 项），不得以本领域的列举缩减 C-2 所要求的恢复与再次触发处置，也不得据此继续消费受影响规范、扩大规则效力声明或创建提交。

**C-6（机械结果与语义判断互不替代）**：机械结果与语义判断互不替代；机械解析、测试通过、工具返回 `ok`、文件存在、Human 确认、登记一致或提交成功，均只能证明各自范围，不得扩大为规范正确、规则适用、授权成立、行动完成或价值成立。

受辖规范自陈领域增量时，本节各款为该内容的权威表述。较本节简略、用词不同、按领域列举更具体或未在边界外增列禁止事项，只要未改变义务内容均不构成冲突（简略不等于可遗漏本节要求事项）；仅当落入上述三种越出区间情形方按 C-1 处置。本节不因收拢共同规则而收窄受辖规范原有领域列举。

【承重声明】本章契约的变化不追溯取消既有成员已经取得的资格证据，也不使既有成员仅因本章变化而视为不满足 §9.2 第 5 项；过渡期内，该项按成员取得资格时点有效的本章契约核对。既有成员在下一次实质修改或 Human 指定的迁移时点，按当时有效契约核对并修复；该过渡不允许既有成员在实质修改时继续沿用已经不符合当前契约的结构。Human 指定迁移时点时，按 00 §3.4 形成作用范围清楚、可回查的回应记录。**恢复条件**：既有成员已按「下一次实质修改或 Human 指定迁移时点」完成按当时有效契约的核对与修复。

**承重声明的撤除条件**：本节末段过渡所需的缺口声明（含 §7.2 状态禁令的过渡），以及其它以「不得声称」类禁止为要件、以恢复条件为解除要件的承载单元（以下合称**承重声明**），其删除或弱化**须以独立复核（§5 第 12 项）就「该声明所指范围已按判据在全载体上穷尽核对且无残留」给出的结论为前提**。该结论取得之前，**不得**删除或弱化该声明，其恢复条件继续适用；期间对声明所指载体的任何审核与核对，**须**把「该范围是否仍有未声明的残留」作为一等检查项。承重声明**须**以固定标记 `【承重声明】` 标识，并以固定标签的恢复条件子件 `**恢复条件**：…` 承载其解除要件；该标记与子件由受控提交契约（`source-of-truth-traceability` §5）机械校验。

【承重声明】**该过渡同样适用于 §7.2 的状态禁令**：§7.2 的作用域宽化（如从「规范正文」扩至 `specs/` 内一切载体）**不使既有成员仅因该宽化而即时失格**；既有成员在本规范宽化生效日**之后**的**下一次实质修改**时，须按当时有效的 §7.2 核对并修复其全部受影响范围（该次实质修改所触及的正文、表格、列头与取值一并核对，不得只清点本次改动处）。**未在该次实质修改中完成核对的，须以条件式要求如实声明该范围为未对齐缺口，并按 §13「正文不含状态」行的处置进入后续处理**；不得因宽化而主张既有成员即时失格，也不得因过渡而主张其在本轮修改后可继续保留已不符合当前 §7.2 的内容。**恢复条件**：全部受影响范围已按当时有效的 §7.2 核对并修复（未完成核对者，其按本条如实声明的未对齐缺口已按 §13 对应行处置完毕）。

## 9. 当前规则源成立与来源视图

### 9.0 元规范与事实规范的两级归属判断

本节承接 `00 §2.4`「具体归属判断由下位规范定义」的指派。**元规范**承载 LDVH 自身规则（位于本仓库 `specs/`，对全部受管辖项目生效）；**事实规范**承载管辖项目规则（以事实对象形态位于该项目事实源 `ldvh-base/`）。

**归属判据**（首要判据为约束对象，可机械或半机械判定）：

| 维度 | 元规范 | 事实规范 |
|---|---|---|
| **D1 约束对象（首要）** | 约束 LDVH 机制／跨项目运作 | 约束**单一项目**的内容、结构、工程纪律 |
| D2 适用项目数 | 全部受管辖项目 | 仅该项目 |
| D3 载体位置 | `specs/`（本仓库） | 该项目的事实源 `ldvh-base/` |
| D4 效力来源 | 效力来自规范源；成立条件为规范源成员的受控建立程序（`§9.1`/`§9.2`）。承载位置与效力来源分属两问（`00 §2.4`） | 效力来自规范源；成立条件为相应事实类型的类型与状态规则（由该类型规范定义），不靠路径挂靠。承载位置与效力来源分属两问（`00 §2.4`） |
| D5 建立程序 | 本规范 §11、§12 | **复用同一套受控建立程序**（`00 §2.9`），不得另设一套 |

「进入规则集、适用于当前事项、获得允许」三问分别判断（`00 §2.4`）；本节只回答「该内容作为元规范还是事实规范承载」，不回答适用与授权。

**边界纪律**（依 `00 §2.9`）：

1. 两级**共用同一套受控建立程序**，故不构成第二套权威；
2. **事实规范不得放松元规范、不得自授效力**；事实对象不因存放位置而取得规范效力（`00 §2.4`）；
3. 同一事项**不得**同时由一份元规范与一份事实规范重复定义；出现重复时按 `00 §4.7` 暂停受影响范围并完成对齐；
4. 归属存在争议、或本判据无法确定归属时，**进入 Human Gate**（`00 §3.2`：改变规范模型、事实模型属根决定事项），不得由 AI 自行认定；
5. **改变本节的归属判据本身**属 `00 §3.2` 的根决定事项。

**两级不互为对方的成员**：事实规范是**事实源中的事实对象**，不进入 `specs/` 的候选路径，不占用本规范的编号命名空间（`§9.1`、`§8.1`）；元规范亦不进入事实源。二者各自按本规范与相应事实类型规范成立。

### 9.1 候选路径与唯一视图

候选只来自已确认 LDVH 源码仓库当前实际 Git worktree 中的普通 Markdown 当前文件，不跟随符号链接：

1. `specs/<至少两位数字>-<规范标题>.md`；
2. `specs/attachments/<父规范编号>.Att.<至少两位序号>-<附件标题>.md`。

候选发现与成员资格分层：文件名匹配只产生待解析候选，不产生规则资格；含 `.draft`／`.tmp`／备份后缀或不合完整模式者不进入候选，未满足 §9.2 者只能以 `non_member_candidate` 及原因进入诊断范围，不进 L0–L4 结果。路径按 UTF-8 字节逐字比较（不折叠大小写、不归一化 Unicode），但 NFC 或大小写折叠后冲突的近似路径按跨平台歧义拒绝；同一编号、key、`canonical_path` 或规范化名称映射到多个候选时，全部受影响候选不得进入成员读取，直到冲突解除。

唯一当前来源视图是该 worktree 的 Working Tree，一次读取或资格检查以**同一次调用**返回的来源标识为准；契约不承载来源标识时不得声称已确认来源视图，须按 §10.3 披露并进入 `gaps`。跨调用取得父规范与附件时，只有能从各次返回的来源标识判定同快照才成立；无从判定（内容变化、指纹不一致、标识不足以比较）即「同一快照未证实」，须如实披露并进入 `gaps`，不得声称同快照。此类情况该范围**不得返回 `completed`**，且不因是否跨调用而免除。工作树可含未提交变化，但不复用旧候选的决定、审核与提交证据；Index 与 HEAD 只用于提交前检查与历史溯源；安装包、缓存等副本不得覆盖或与当前来源混合。本条读取契约只约束 LDVH CLI 规范读取入口（§10.3），非 CLI 的宿主／Web 读取入口不产生受控回执、不满足同快照要求，不得单独作为资格判断或受控行动依据，须按 §10.3 降级披露。

### 9.2 规范成立条件

规范进入当前规则源必须同时满足：

1. 位于 §9.1 候选路径，且不是符号链接；
2. H1、身份块和 Markdown/YAML 可以按 §6 解析；
3. `spec_key` 与 `attachment_key` 共享一个职责标识符命名空间并全局唯一且未被改派；`spec_id` 在规范编号命名空间唯一，`attachment_id` 在附件编号命名空间唯一，二者不作跨类型相等比较；所有载体的 `canonical_path` 在候选全集中全局唯一；

5. 普通规范符合 §7 的共同章节结构（其中对应 §7.4 共同条款的语义元素，按 §7 回指优先呈现）；00 符合其自身根结构；附件**不适用 §7 的共同章节结构**，只须符合 §6、§8.3 及 Att.02 的附件身份与内容边界，**并须符合 §7.2 的状态禁令**（该禁令的作用域覆盖 `specs/` 内一切载体，附件不因其不适用 §7 的共同章节结构而豁免）；既有成员的过渡核对按 §7 末段执行；**其中已按 §6.3 末句进入「按 §8.3 与本规范 §11 另行处理」通道的越界内容，按 §8.3 中「待修复而非已失效」的但书处理**，在处置完成前不因该内容径行认定附件不满足本项；
6. 对规范身份 profile，`basis`、`authorized_attachments` 及已声明的 `supersedes`、`related_specs` 符合 §10 与 Att.03，`parent_spec` 与 `relation` 在无结构父规范时按 Att.02 成对为空字符串，有父规范时目标、方向、基数和正文说明成立；对附件身份 profile，只检查 Att.02 §5 允许的字段、唯一父规范授权及本节附件附加条件，不要求附件声明规范专属关系字段；
7. 没有另一份当前规范重复承担同一职责；
8. 新建或实质修改已经完成 §12 的独立审核、修复与必要复审；
9. 已取得 Human 对准确候选及作用范围的明确决定；
10. §8 登记及所有受影响引用与实际文件一致；
11. 已按 09 的受控提交契约形成可回查提交；
12. 当前来源视图的内容指纹仍与 Human 决定、审核和提交所绑定的准确候选一致。

第 11 项提交契约由 09 定义，本文不复述其格式与 validator，只保留不可省略的不变量：Human 对准确候选与作用范围明确同意、提交含可回查受控签名、预检与真实 Git Gate 作用于同一候选、提交后回读与候选一致、不得绕过 Git Gate。**草案不得反向授予自身或其它规范资格。**

12 项按可核验方式分两类，互不替代：

- **机械可核验项**（第 1–4、10 项，第 5 项中章节顺序、标题角色与表头等结构化部分，以及第 6 项中字段形状、目标存在、基数与方向等结构化部分）：候选路径与符号链接、身份块解析、编号与 `canonical_path` 唯一性、H1 与文件名一致、固定章节的结构化部分、`basis`/`attachments` 的引用可解析、§8 号段与登记一致。这些项在机械入口可用时**须由机械校验直接给出结论**。
- **语义与证据项**（第 5 项中「按 §7 回指优先呈现」所涉领域增量有无与回指、自陈形态的判定、第 6 项中「正文说明成立」的判定、第 7 项的职责重复判断，以及第 8、9、11、12 项）：这些项**不能仅由代码判定**——其**可机械核对的子部分**须由机械校验给出结论（§13.1），其**语义判定的子部分**须以人工逐项核对执行，且**不得声称成员资格已通过机械校验**；任何未实际证实的项必须进入 gaps 并如实披露（`00 §4.7`），不得以「条件已列出」代替「条件已满足」。

**第 8、9、11、12 项的机械化细分**：这四项各自的机械部分与语义部分必须**分别交还**，不得合并为单一结论：

| 项 | 机械可核对（须由机械给出结论） | 不可机械判定（留给语义核对与 Human） |
|---|---|---|
| 8 独立审核 | 审核记录**是否存在**，且是否指向该候选 | 该审核是否真实、充分、独立，是否攻击了真实风险（§12.2） |
| 9 Human 决定 | 决定记录**是否存在**，且是否指向该候选 | 该决定是否准确、充分、仍覆盖当前候选 |
| 11 受控提交 | 是否存在触及该载体的提交；受控签名 trailer 是否存在 | 该提交是否经过授权、审核与 Human 同意（签名存在**不等于**授权） |
| 12 指纹绑定 | 载体当前内容指纹是否与记录时的绑定一致 | 被绑定的决定是否仍然适用 |

产出这四项机械结论时**必须同时交还语义余项**，不得给出「成员资格已成立」结论（机械部分全满足不构成资格证据）；无记录可核对者计入 gaps，不得因「无期望值可比」默认通过。

附件还须有唯一有效父规范、被登记授权、授权列表每个 key 精确对应一个实际附件、内容不扩张父规范规则。孤儿／悬挂／多父授权及授权声明缺失或歧义属**结构性缺陷**，无宽限、授权读取不成立；内容扩张属**边界越界**，已进入 §6.3 末句另行处理通道者按「待修复而非已失效」宽限，二者不得互换适用。

第 9、12 项的 Human 决定只针对建立与实质修改（§12.1），不含非实质性修正：后者只涉身份镜像、引用、格式或中文语义，不改变职责、边界、据实声明边界（00 §4.6）或判断结论，故不重新开启 Human 决定、不因指纹变化使成员资格失效，仅须完成 §8 登记同步（若涉及）与第 11 项受控提交并如实说明（红线 5）。实质修改须重走第 8、9 项，第 12 项指纹绑定重新成立前成员资格证据不完整、受影响范围按 `00 §4.7` 暂停；实质与非实质有争议时按 §12.1 末段从高风险。

### 9.3 退出与失败边界

退出须经 Human 对准确退出候选决定、完成 §8 登记变更与受影响引用关系处理、受控提交，并说明职责去向；四项共同构成，任一项不能替代。文件可为追溯保留于候选路径，但登记移除且退出提交成立后只能作为非成员候选，不进 L0–L4 消费结果，读取入口须披露非成员原因；仅删文件、改名、改字段或改 Git 状态不构成完整退出。

无法证明成立条件者记入 `gaps`，不得伪装通过；已实现但未执行／未通过／不可信的机械校验不得返回通过，未实现的检查不得用人工猜测冒充。来源不一致时暂停受影响行动，不静默回退 Index／HEAD 或副本。

资格证据至少绑定候选集合与内容指纹、逐项条件及证据、审核对象与范围、Human 决定对象与范围、提交引用和当前来源视图；任一绑定变化、决定撤回或范围不匹配时旧证据失效。证据载体与传输结构由 05、09、10 承接，不在 01 建立第二账本。

## 10. 规范关系、读取与规则引导

### 10.1 关系语义

`basis`、`parent_spec` + `relation`、`authorized_attachments`、`supersedes` 与 `related_specs` 的方向、基数、允许目标和禁止用途由 [01.Att.03-规范关系与层级表](attachments/01.Att.03-规范关系与层级表.md) 承载。本规范正文定义其边界：

- `basis` 只列理解、判断或维护当前规范所必需的直接上位规范；目标必须是当前成立的规范，依赖图不得成环；
- `parent_spec` 与 `relation` 是必填成对字段：无结构父规范时都为空字符串；有结构父规范时都为非空，只表达唯一直接结构归属；关系闭集当前仅 `refines`；同一目标不得同时作为 `basis` 和结构父规范；父规范正文必须能定位被具体化的职责边界，子规范不得越出该边界；
- `authorized_attachments` 只从父规范指向附件；父规范必须在 §8.3 或等价授权小节逐项说明附件承载对象与边界；
- `supersedes` 只表示新职责对旧职责的实质替代，不用于同一职责改名、改号或移动；替代图不得成环，旧职责不得与替代者同时作为当前规则源成员；**其成员的可追溯性以历史提交为唯一口径**——每个成员须曾在某次提交中作为某规范的 `spec_key` 存在过（可由 `git log` 追溯），本规范不另设人工登记表；两者皆不成立时，该成员不成立，不得以「字段格式合法」代替「目标可追溯」（§9.2 第 6 项、`01.Att.03` §替代处置）；
- `related_specs` 只表达非结构关联，不产生继承、效力或替代关系。

**正文引用其它规范时的负载／路由二分纪律**（适用于全部普通规范）：

规范正文**引用另一份规范**时，须按**引用是否承载规范内容**分为两类，分别处理：

| 类别 | 判据 | 处理 |
|---|---|---|
| **规范负载型引用** | 本规范的规则**消费**被引规范的**内容**——即读者必须按被引规范的定义来理解、填写或执行本规范的某条规则（如照其表头登记、按其闭集取值、依其形状声明、受其暂停规则约束） | **须把被引规范列入 `basis`**，并在 §2 依据清单中附**精确章节**。**不得**仅以正文引用代替依据声明 |
| **路由型引用** | 只**指向职责归属**，不消费其内容——如「X 归某规范承接」「本节不定义 X」「X 由某规范定义」等划界句式 | **可保留为正文引用**，**不强制**列入 `basis`，也**不强制**登记 `related_specs` |

**判定粒度是逐处引用，不是逐份规范**：同一规范可同时有负载型（须入 `basis`）与路由型（可留引用）两种引用。

**`related_specs` 的使用边界**：它**不用于**替代 `basis`。仅当存在**需要向读者提示、但不产生内容消费**的关联时使用；**不得**以登记 `related_specs` 的方式规避规范负载型引用应有的 `basis` 声明。两者皆不属于的引用应删去或改写为明确的划界表述。

**依据方向不因引用方向而变**：若 A 的规则约束 B（B 须遵守 A），则 B 的 `basis` 须含 A；**A 不因约束 B 而须把 B 列入 `basis`**——依赖边只从被约束方指向约束方，据此保证依赖图无环。

### 10.2 L0–L4 读取层级

L0–L4 的名称、累积内容、用途和不能单独证明的范围以 01.Att.03 §4 为唯一结构化表。L0–L2 不证明相关、适用或完整约束；L3 不证明已经包含全部语义依赖；L4 不证明实现、验证或授权成立。消费方可直接请求任何足够层级，不强制逐层仪式。01 定义层级语义，05 定义共同请求/响应 envelope，06 实现并测试解析。

### 10.3 读取入口边界

**入口与层级**：`read-specification-candidates` 按职责标识符或全部候选读取 L0–L2；`read-specification-content` 按精确 `responsibility_key` 与 `heading_path` 读取 L3，或不提供标题路径读取 L4。`responsibility_key` 的取值就是目标 `spec_key` 或 `attachment_key`，不接受编号、标题、路径或模糊回退。L3 的 H2/H3 路径必须在同一载体中精确唯一，重复或歧义标题不选择首个匹配而应拒绝；行号为 1-based。

**披露义务**：每次结果必须披露来源视图、候选集合指纹与各载体内容指纹；读取契约不承载某项时，须如实披露该项缺失并使其进入 `gaps`，不得以「已披露」或省略代替；还须披露完成与未完成范围及资格 gaps。返回候选或内容不等于载体已满足 §9.2，也不得把不合格候选当作可执行规则。规范读取 L0–L4 与事实召回 F0–F4 不混用。

规范语料来源按三级回退解析：受辖项目根 `specs/` → 插件开发布局的源仓库根 `specs/`（link／开发安装指向源目录，以根规范载体的实际存在辨认）→ 插件包内 `specs/`（发布打包时自源仓库复制的语料副本）。三级按序探测，首个实际存在的目录即该次读取的唯一来源视图，同一次结果不得跨级混读；来源披露必须如实标注实际应答方，不得把回退来源表述为项目自著语料。语料由回退来源应答时，`§9.2` 的机械核对子项对该受辖项目按「不适用」报告并说明缘由——语料自身的成员条件核对属于其源仓库，不由消费方会话代行，也不得以消费方项目内 Git 查无载体充当核对结论。项目自著语料与包内副本的内容差异不属于读取入口的核对义务，由发布打包流程约束。

LDVH CLI 读取不可用时，不得伪造受控回执。只读核对可据实降级到宿主公开文件读取，但必须披露入口、未取得的 LDVH CLI 回执和未验证范围；来源要求受控回执而无法取得时，按 00 §4.7 暂停受影响行动。

### 10.4 最小规则引导

会话启动时，插件 AI 工作引导至少提供下列 00 锚点：身份块、00 §1 核心价值（对齐 Vibe、协调 Coding）、00 §2 方法与构成、00 §3 Human 权利、00 §4 AI 责任与义务（含 00 §4.6 据实声明、00 §4.7 必停情形与恢复、00 §4.8 交还与撤回）、00 §5 价值纪律。具体注入顺序、预算、触发时机与宿主承载由 10 定义；最小引导不替代完整规范读取、事实召回或适用判断。

## 11. 规范新建、修改与重构判断

### 11.1 判断顺序

按以下顺序形成候选，不得先决定技术形态再补理由：

1. 明确要解决的问题、现有来源、消费方和缺口；
2. 判断是否只需更正表达、引用、格式或身份镜像；
3. 判断现有规范能否通过最小充分修改无损承载；
4. 比较现有正文、授权附件、新建规范、拆分、合并或取消的职责清晰度、重复风险、读取成本、维护成本与净价值；
5. 形成包含旧规则处置和来源影响的准确候选；
6. 按 §12 独立审核并修复；
7. 取得适用 Human 决定，更新登记与引用，再受控提交。

### 11.2 独立规范成立条件

新建或保留独立规范必须同时具有：稳定且可独立说明的职责、明确消费方、足够持续的规则内容、现有承载无法无损吸收，以及相对新增搜索和维护成本为正的净价值。只因篇幅较长、概念名称不同、未来可能扩展或希望编号整齐，不足以成立独立规范。

授权附件只在父规范已经定义规则、结构化内容稳定且正文内维护明显降低可读性时使用；它不是规避独立规范成立条件或隐藏新规则的途径。

### 11.3 修改、拆分、合并与取消

最小充分修改优先：能改一处不改一章，能改一章不改整份，能改一份不牵动多份，但不得以“最小改动”为由保留错误结构或重复权威。

拆分应证明原职责包含可独立消费且稳定的多个责任；合并应证明多个来源实质承担同一责任或分离成本超过价值；取消应证明职责不再需要或已由其它当前来源完整承接。每种变化都必须说明旧规则逐项保留、转移、改写或退出的去向，处理身份、编号、关系、附件、引用、实现与历史回指。

同一职责改名、改号或移动时保留原 key，不使用 `supersedes`。实质新职责替代旧职责时使用新 key，并通过 `supersedes` 与正文处置说明建立可追溯关系。拆分时可以由一个保留原 key 的幸存职责继续承载未改变部分，其余实质新职责使用新 key；合并进既有幸存规范时，幸存 key 保持不变，并可用 `supersedes` 指向被并入且退出的旧职责。纯取消没有替代者时不虚构 `supersedes`，由退出决定、登记变化和正文处置记录共同追溯。

### 11.4 来源先行闭环

规范先定义语义、字段和成立条件，再由 Code 与 Web 实现或呈现。不得因现有实现方便而反向改变规范语义，也不得在规范尚未成立时由 Code、测试、索引或页面先行制造事实上的第二规则源。实现缺口进入 gaps 和后续工作，不冒充规范已被机械保障。

## 12. 规范独立审核

### 12.1 触发与风险匹配

规范新建、删除、改名、重排、实质修改，或产生、改变可强制执行规则时，必须在 Human 决定前完成风险匹配的独立审核并修复真实发现。风险分级可以调整审核范围和深度，但不能取消审核触发（相称性与不得以「风险低」减免已适用边界的实体见 `00 §4.9`）。

非实质性修正只涉及身份镜像、引用、格式或中文语义，且不改变职责、边界、可实现性、据实声明边界（00 §4.6）或判断结论；触及其中任一项即为实质修改。无法确定是否产生或改变可强制执行规则时，按较高风险审核。01 自身同样适用。

本节（何时启动审核）与 §13（各项何时、依何条件、由何入口核对）互不替代；各项核对时机以 §13 对应行「成立条件」为准，本节不复制其清单，也不另设核对义务。风险分级可调审核范围与深度，但不使 §13 各行「成立条件」失效——例如「正文不含状态」行时机为建立／实质修改／提交前，按 §7.2 判据引入状态陈述即触及据实声明边界（00 §4.6），不属非实质性修正，不得据「非实质性」免核对。

### 12.2 独立与对抗

独立审核由未参与形成当前候选的执行体完成；同一上下文中形成候选的同一角色不得审核该候选。**执行体范围由 `00 §2.5` 与 `00 §2.9` 固定**——独立审核由已登记的代理执行体承担；下位只承接审核的深度、职责、技术、流程与协同，不改变执行体，也不增列执行体类别。

审核须以独立上下文执行，执行体不得与候选形成者共享上下文，也不得以「会话身份不同」充当独立性证据；采用同一模型时仍须隔离并披露独立性边界。承载形式依本轴自身章节（不借用 `04 §7.3` 的复核轴形式）。Human 明确同意（`00 §3.3`、`00 §3.4`）是并列要件，不替代也不被视为独立审核。

审核须说明对象、准确候选、范围、依据、攻击方向、发现、未覆盖范围与保证边界，不得只报「已审核」或「无问题」。

### 12.3 审核维度

产生或改变可强制执行规则时覆盖下列七维：

1. 价值对齐；
2. 职责边界、单一权威与反过度设计——该规则是否属本规范职责、有无第二权威、是否超出最小充分；
3. 技术可实现性与能力真实性；
4. 载体形式——身份、编号、引用、格式、中文语义清晰、术语一致与机器表示对应；
5. 据实声明与不能单独证明的边界（00 §4.6）；
6. 规范内部一致性与反例检验；
7. 闭环与相称——草案、修复、Human 决定和提交闭环，以及审核自身是否与风险匹配。

**第 1 维「价值对齐」判据**：只回答候选规则与其声称落实的根方案、服务的核心价值面、所增负担与证据是否同一指向、互不相悖。查 `00 §5.1` 四项（落实哪条根方案、服务哪面、负担风险、核对证据）有无指向矛盾，及所声称核心价值是否与 `00 §1` 两面定义同一指向；**只判指向一致、不判价值成立**（后者按 `00 §5.2`、`00 §4.6` 保留），声明服务两面时须逐面说明；报「一致」须指出同向具体内容，报「矛盾」须指出相反条文，举证不能时报「未完成核对」并计入未证实范围，不得默认判向任一侧。

报告须说明实际覆盖与跳过的维度、跳过依据、信息不足项与保证边界；风险档位由审核执行体反向核对，不由候选形成者单方认定。

### 12.4 修复与复审

主控核对审核发现并修复真实问题。未修复项必须说明原因、影响与残留风险，不得静默忽略。修复改变根语义、职责、可强制规则或审核结论时，由独立审核执行体复审全部受影响维度。审核完成不证明规范正确，也不自动使其进入当前规则源。

| 身份与路径 | 建立、修改、读取或提交前核对：YAML 可解析；字段闭集、类型、格式、H1、编号与实际路径一致（依据当前文件与 Att.02）。仅证明当次身份和载体一致性 | 机械解析与路径检查 | 记录精确问题并暂停受影响载体 |
| 根级 Code 消费入口 | 00 或 §6.2 修改后、读取该入口前核对：00 `code_consumption` 的成员与 §6.2 对应关系逐一相符；无未登记成员，无已登记而声明已删除的成员（依据 00 身份块与本规范 §6.2）。仅证明当次入口名与其对应关系 | 机械解析比对该字段与对应关系 | 按 `00 §4.7` 暂停受影响解析并如实披露，不得择一继续 |
| 编号与职责 | 登记变化或全量检查时核对：key、编号唯一且未改派；登记与实际文件一致；业务系统号位约定与 `00 §2.6` 现行名录的成员与名称一致（§8.2 条件式要求）（依据 §8、`00 §2.6`、当前候选集、可回查历史）。仅证明已扫描范围内的唯一性与号位一致性 | 全量扫描、名录对照与历史核对 | 未覆盖历史进入 gaps，不声明全局通过；号位不一致时按 §8.2 暂停受影响号位约定并提请重排 |
| 关系与附件 | 读取、修改或提交前核对：目标存在；方向、基数、授权和正文边界一致（依据当前规范、Att.03 与附件全文）。仅证明当次关系与授权范围 | 关系图检查及语义审核 | 停止消费不一致范围并修复 |
| 共同章节结构 | 设计基线确认和提交前核对：前四章、连续领域正文、后四章及结构角色唯一；固定章节的最小必填语义元素可辨认（对应 §7.4 共同条款者，按 §7 回指优先呈现，回指处承载「该元素无领域增量」的可核断言——有领域增量而仅回指，与无领域增量而自陈复制，均不满足 §7）；同一语义元素的完整展开唯一（§7.2）；验证章节使用标准四列表头；基础模型规范（02、03）定义其**职责所服务范围内**规范的共同结构（依据 §7、02/03 与当前全文）。仅证明章节顺序、标题角色、表头及已审核语义元素与受辖结构符合性，以及回指处无增量断言与完整展开唯一（§7.2）的已审核范围 | Markdown 标题与验证表头机械解析；固定章节要素由 AI 语义审核 | 缺少结构、表头、必填语义元素或受辖规范不符合时暂停相关规范确认并修复 |
| 正文不含状态 | 建立、实质修改或提交前核对：**本规范全部正文与受辖附件**均不含 §7.2 禁止的状态（实现状态、下位文档状态与过程进度；§7.2 作用域覆盖 `specs/` 内一切载体，含附件表格、列头与取值）（依据本文 §7.2 与当前全文，含附件）。仅证明当次文本不含状态陈述，不证明该规范的全部规则已被实现 | AI 语义审核逐处判断（判据：该处是断言某对象或载体「当前是什么」，还是规定「在某条件下应当／不得」——后者为规则，不受限） | 将状态陈述改写为条件式要求，或移出 `specs/` 后重新进入确认 |

| 证据项机械子部分 | 需要核对 §9.2 第 8/9/11/12 项时：四项各自的机械子部分（记录存在、提交与签名、指纹一致）由机械给出结论；语义余项如实交还；无记录可核对者计入 gaps（依据审核与决定记录、Git 历史、记录时的内容指纹）。仅证明各项的机械子部分；**不证明**记录真实充分、提交获授权或决定仍适用，不构成成员资格证据 | 逐项机械核对（记录引用、`git log`、内容指纹比对） | 机械子部分不成立或无法核对时计入 gaps，保持「成员资格未证成」，不得以部分通过代替整体 |

机械解析与 AI 语义审核互不替代（见 §7.4 C-6）；缺失的实现和检查进入 gaps。

### 13.1 机械入口可用性

本规范要求机械校验给出结论之处（含 §8.3 三项校验、§9.2 机械可核验子部分），核对义务不因是否已有实现而改变，按下表处理：

| 机械入口状态 | 该范围的核对方式 | 禁止事项 |
|---|---|---|
| 入口可用 | 须以机械结果为准 | 不得以人工核对冒充机械证明 |
| 入口不可用 | 须以人工核对执行，并如实披露该范围未经机械核对 | 不得声称该范围已通过机械校验，也不得引入口缺失为免于核对或降低核对标准的理由，亦不得用人工猜测冒充机械证明 |

**机械入口的实际可用性与覆盖状态属实现现状**（§7.2）：按读取或审核时的观察**逐项**取得，在**当次读取或审核的交还与说明中**逐项如实披露，不写进规范正文，也不写进授权附件。未覆盖、未执行或不可信的机械校验，不得使受影响载体返回为通过。

## 14. Human Gate

本规范不新增 00 之外的根 Human Gate（该共同规则见 §7.4 C-3）。

### 14.1 领域增量事项

以下事项是 00 §3.2 在规范模型领域的具体化：

1. 新建、删除、改名、重排、拆分或合并规范模型；拆分与合并均导致模型或其成员发生增删或重排，故适用同一 Human Gate——其是否属 `00 §3.2` 所称「重排」，以该条对「四类对象的存续」与「各成员的增删、改名与重排」的表述为准；
2. 改变当前规则源成立条件或来源视图；
3. 改变身份字段闭集、共同章节结构或关系语义；
4. 改变附件授权、审核义务，或本领域其它可强制执行规则（`00 §3.2` 根清单已列者不属本项，仍按根决定处理）；
5. 处理 00 §3.3 受保护内容的修改或合并。

受保护内容修改必须经 Human Gate（第 5 项）；本规范不登记受保护文件清单、不实现其机械校验（避免第二登记权威），消费时读取：
- **路径登记**由 `dsh-environment-integration` §7.6 载明（`00 §3.3` 五类到 DSH 位置的映射，清单变更须经 Human Gate）；
- **机械校验**由 `source-of-truth-traceability` §5.6 承接，限其 Merge 场景，不覆盖普通提交路径。

未被定义为机械校验项的范围不得声称已受机械保障，交还中如实披露未覆盖（`00 §4.6`、`00 §4.8`）。

提请内容、作用范围和回应效力按 00 §3.4 执行。

### 14.2 决定边界

Human 决定只证明决定及其作用范围，不替代本规范 §13 的验证与语义审核、§9 的成员资格核对或受控提交检查。

## 15. 必停情形

本规范不新增必停的根触发（该共同规则见 §7.4 C-4）。

### 15.1 领域触发与影响范围

出现以下任一情况时，按 00 §4.7 暂停最小受影响范围：

1. 规范身份、编号、职责或来源视图不唯一；
2. H1、身份块、登记、路径或正文相互矛盾；
3. 依据、结构关系、附件父权或旧规则去向无法确认；
4. 当前规则源成立条件缺失，却准备宣称成员有效或据其执行；
5. 应完成的独立审核未完成，或真实问题未修复却准备进入 Human 决定；
6. Human 决定、候选、Index 或准备提交的范围不一致；
7. 应改变当前行动的适用约束未实际落实。

### 15.2 暂停期间允许动作

暂停期间的允许动作见 §7.4 C-5；本规范不另作增量规定。

### 15.3 恢复与再次触发

恢复与再次触发的实体规则见 §7.4 C-2，本规范不另作增量规定。

## 16. 反过度设计红线

1. 不为每个概念、字段、小差异或低频场景建立独立规范或附件；
2. 不为满足共同章节结构制造空规则、重复清单、无消费方表格或无领域增量的共同条款自陈复制；
3. 不建立独立于当前规范源的第二索引、状态账本、规则数据库或发行快照；
4. 不恢复普通规范生命周期 `status`，也不以其它字段改名重建同类机制；
5. 不要求每次普通编辑都执行全量规范召回、最高风险审核或 Human Gate；
6. 不为未来可能需要的迁移、批量改号、关系类型或协议提前扩展字段；
7. 不把 Code 可解析性、测试便利或 Web 呈现反向提升为规范语义；
8. 不在 01 复制 05 的完整 envelope、06 的解析实现或其它领域规范的细节；
9. 不为统一章节内部写法制造固定句式、固定小标题、逐项仪式或无消费方表格；**§7 明确规定者除外**——固定章节标题、§3／§4 的固定 H3、验证表头、§7.4 共同条款与 §7 回指优先，是结构契约而非写法统一，不受本条禁止；
10. “保障措施”“待补齐事项”“版本历史”和起草清单不是固定章节，只有本规范职责确有独立消费需要时才进入领域正文。
