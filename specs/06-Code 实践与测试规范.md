# Code 实践与测试规范


## 1. 价值判断

本规范解决规范机械规则缺少一致、可测试、可回读单一实现的问题，通过工程纪律、测试基线和单一实现原则，减少实现漂移、副本逻辑、重复造轮子和无证据完成声明的负担。

工程纪律与契约实现主要支撑 V4 稳定推进；验证证据与声明边界主要支撑 V5 据实判断；单一实现与可复用测试主要支撑 V8 持续积累；测试文件、运行结果与实现回读主要支撑 HV3 入档闭环节点可验。

本规范只定义 Code 实现与测试纪律；规范语义、事实与业务系统规范规则、提交契约、环境接入和 Web 呈现由 01–05、07–10 及实际实现消费方承接。工程纪律和测试只提供机械证据，不替代领域语义与 Human 决定。

代码文件存在、测试通过、Lint 无错误、编译或构建成功，只能证明各自机械范围，不能单独证明规范语义满足、授权覆盖、功能完整、行动完成或价值成立。

**新增的负担与风险（00 §6.3 第 4 问，如实登记）**：本文不是无成本的。

**本条（§5「断言须以被测面的真实形状为准」）新增的负担**：(a) 编写涉及读取面返回结构的断言前须读该面实现，单条断言的编写成本高于按直觉直写；(b) 每条**否定式**断言须按两类形状补判据——「字段应在另一位置」补该位置的正向断言，「字段/容器必须整体缺席」补同级在场断言与缺席位置集合，逐条递增；(c) 形状判据须按读取面分别取得，同一对象跨面时须重复确认，成本随读取面数增长；(d) 证明形状断言的检测力须做一次变异（改回错误形状并确认转红），每次新增此类断言都多一轮改动与还原。

**本条新增的风险**：(a) **以实现为准钉漂移**——读取实现偏离其权威契约时，照实现写断言会把漂移固化成绿测（出口：§7「规范一致性」行的漂移处置）；(b) **否定式断言误作防护**——`in` 的否定形式在字段整体缺席时恒真，若被当作「字段不该在这里」的守卫，它对该形态没有检测力（出口：本条要求按两类形状分别补判据）；(c) **变异未做而声称已证**——未做单项变异就宣称该断言已覆盖该形状，属超出依据的声明（出口：§7「形状断言有效性」行的第 ④ 项）。

**本条（§6「删除唯一生产者须同轮清理下游」）新增的负担**：(a) 删除类改动须在同一轮内按名检索下游五类消费形态，并在检索发现残留时清理（含当轮写范围之外的载体），实际改动面可能超出原计划；(a2) 残留是否归零须落到载体内容，可能持有该值的载体要逐个读，并对每个声称覆盖的键形各取样本自证——比跑一次检索多出成倍的阅读与核对工作；(b) 须把核查结论写进交还，未核查的载体逐项登记为未覆盖。**本条新增的风险**：(a) **删了生产者却留消费形态**——形参恒收空值、派生字段恒记 0，无测试失败、无运行时报错，只在人工核查或下游效果异常时暴露（出口：本条的五类逐点核查 + §7 该行）；(b) **以「不在当轮范围」为由跳过**——范围外载体因此从核查中消失（出口：本条要求其中至少完成一次按名检索并登记结论）；(c) **检索未命中被读作不存在**——模式未覆盖键形时，「搜过且没有」与「确实没有」在结论上不可区分，清理完成会被提前声明（出口：本条要求归零判断落到载体内容；检索只可用来缩小需读的范围，且每个据以下结论的键形须有样本自证）。

**本条（§6「依赖边界须与提交边界对齐」）新增的负担**：(a) 触及跨文件 import 的改动须在提交后额外做一次纯净导出加载，单次提交的验收成本上升；(b) 当次判据未覆盖的载体形态须逐个人工确认，并把确认记录写进交还，逐次增加核对工作。**本条新增的风险**：(a) **以本地可运行结案**——工作树里文件齐全，验收因此通过，缺陷推迟到他人检出或 CI 才暴露（出口：本条要求以纯净导出加载为判据）；(b) **把覆盖范围读成全部**——判据存在时只覆盖某类说明符，其余载体的悬空引用不被发现（出口：本条要求按读取时取得的实际覆盖面核对，并人工确认未覆盖的载体）。

**本条（§6「结构校验须按集合性质判定，不得以首行比较替代集合判定」）新增的负担**：(a) 结构类校验须按计数或枚举实现，等价形态与结构性字面须按 GFM 的 ATX 规则处理，实现与夹具成本高于一行字符串比较；存量载体（仍为首行比较者）迁移到计数式属额外的实现改动，其工作量不在本文规定之内；(b) 每处结构校验须按 §5 变异三向备反向用例（真实写法可被捕获、等价变体不被误伤），用例数随之增加。**本条新增的风险**：(a) **单点比较被当作结构校验**——首行比较看起来也在检查结构，实际漏检与误报并存，且两个方向都不会被既有测试自动发现（出口：本条要求改为计数并按 §5 变异三向补反向用例）；(b) **只测一个方向**——只测「多出即拒」会把误报固化，只测「变体仍过」会把漏检固化（出口：本条要求按 §5 变异三向补齐反向用例）。

**本条（§5「「没有输出」与「输出为零」是两个结果」）新增的负担**：(a) 批量判定脚本须为「取不到计数」单独设计终态与退出码，并做一次对照运行（人为让测试不运行）证明该终态真的触发；(b) 判定前须取得与本次运行结果无关的证据（运行器报告或计数行是否存在），并另须保证被判定对象的定位与判定逻辑读取的路径一致；脚本的定位与输出设计随之受限。**本条新增的风险**：(a) **零值歧义**——「没跑」被并入「零失败」，整批结论反向（出口：本条要求独立终态并使其影响退出码）；(b) **残留副本冒充本次结果**——上一轮的副本仍在路径上，判定读到的是旧内容（出口：本条要求以本次运行自身的证据判断运行是否发生）。

**本条（§6「源码注释是待验证线索，不是事实来源」）新增的负担**：(a) 把注释用作结论背景前，凡涉及当前状态的断言须对当前事实重测并标明来源（不限于全量断言，弱化措辞同样须重测），单条背景的成本高于直接引用；(b) 注释与判据不一致时须先确认二者前提是否相同，确认前提相同后还要回到数据面确定二者之中哪一个已不成立，该确认往往需要读实现与数据，成本高于单方采信。**本条新增的风险**：(a) **照抄旧注释致结论反向**——涉及当前状态的断言与现状不符时，据其推导的整条结论会反向，且既有测试通常不会因此失败（出口：本条要求此类断言当场重测并标明来源）；(b) **不一致时单方采信**——注释与判据不一致时若只采信任一方，会把其中一个的失效状态固化进结论（出口：本条要求先确认前提是否相同，同一前提下再回到数据面确认）；(c) **弱化措辞逃过核对**——「通常」「大多数情况」看起来不像断言，因而不被当作现状断言重测，实际比全量断言更容易被直接采信（出口：本条的判据取「是否在陈述当前状态」，不取措辞强弱）。

**本条（§5「源码文本断言会把当次实现钉成契约」）新增的负担**：(a) 每条源码文本断言都须有据：正向断言回指契约位置、反向断言回指该形态已被淘汰的记载；并对正向断言逐一确认不指向待淘汰形态，编写成本高于照抄当前实现；(b) 每条此类断言须回指到具体契约位置或淘汰依据，并确认匹配窗口所在单位，编写与核对成本高于照抄当前实现。**本条新增的风险**：(a) **把 bug 钉成契约**——正向断言指向旧名、旧键或旧路径时，修正会先让测试变红，于是否定修正（出口：本条要求正向断言只指向契约形态，防复活改用反向断言）；(b) **宽匹配窗口掩盖残留或误伤正确实现**（出口：本条要求窗口限定在被测单位内）。

**本条（§5「断言的检测力须可证，零检测力断言不得保留」）新增的负担**：(a) 新增或实质修改的**每条断言**须说明「哪种实现改变会让它转红」；**含多条断言的用例须为每条断言各指明一种使其单独转红的改变**，并实做对应的变异运行——一次让整条用例转红的变异不足以证明其中每条断言都有检测力（逐用例取证会让「一条真断言＋一条恒真断言」过关）；(b) 删除存量零检测力断言须逐条写明理由与承接用例，并使该行为另有守护；(c) 以事实对象为答案的评测项须改为稳定契约对象或自造夹具，或按本条形态 5 的处置条件、豁免段处置，改写成本随语料规模增长。**本条新增的风险**：(a) **删除过头**——把「答案随活语料漂移」的防漂移断言误当零检测力删除，使语料漂移不再报警（出口：本条形态 5 的豁免段，处置回指 §7「基线归因的比对锚点」第 ③ 项）；(b) **文本标记误判**——以注释短语而非「用例内有无断言」识别形态 3，会把合法守护误删（出口：形态 3 的判据取语义属性，不取注释文本）；(c) **检测力未证而声称已守护**——只说明改变而不实做变异（出口：§7「断言检测力」行的成立条件与未满足处理）。

**核对方式**（§1 各负担条款的聚合索引；**不含下一条「断言检测力」负担，其核对方式另列于下**）：以 §7 验证表逐行核对，其中与各条直接相关者分别为「形状断言有效性」「删除后的下游清理」「依赖边界的加载闭合」「结构校验的判定对象」「批量判定的零值歧义」「注释断言的可采性」「源码文本断言的方向」「测试基线」「基线归因的比对锚点」；未执行变异或未完成核查时，按 06 §7 末段的 gaps 纪律如实登记为未覆盖。

**核对方式**（§5「断言的检测力须可证，零检测力断言不得保留」）：以 §7 验证表逐行核对，其中与之直接相关者为「形状断言有效性」「源码文本断言的方向」「测试基线」「基线归因的比对锚点」「断言检测力」。

**若上述负担与风险在实践中被证明超过收益，应重审本文机制而非默认保留**（00 §6.3「答不出的不纳入」，反向亦成立）。

## 2. 规范依据

本文直接依据：

1. `ldvh-root`：00 §3.5 的技术与机械保障、§5.6 的据实声明、§5.7 的必停情形与恢复、§5.8 的 Output Envelope 与交还；
2. `specification-model-foundation`：01 §6 的身份块契约（含 `01.Att.02` 的字段形状与 §6.2 登记的根级 Code 消费入口解析）、§7 的共同章节结构、§10 的 L0–L4 读取层级、§12 的独立审核；
3. `check-auxiliary-mechanism-foundation`：检查机制规范 §6 的检查机制三形态、§7 的视角纪律与 §8 的检查结果与声明边界（本文 §6 的机械实现与 §7 的验证边界受其约束）；
4. `fact-model-foundation`：事实源与事实模型基础规范 §6.1 的公共字段署名要求（事实 `change_log` 的 provider/model 由 Code 从权威记录取得，本文 §6 的机械签名实现受其约束）；
5. `source-of-truth-traceability`：受控提交与机械守护规范 §5.1 的 message 契约（提交署名 trailer 的格式与来源要求，本文 §6 的机械签名实现受其约束）与 §5.7 的提交动作步骤（暂存、创建、回读三步及各步的可核对结果；本文 §6 对依赖边界的验收以该三步为处置入口，不另立步骤，也不裁减其中的任何一步）；
6. `work-object-governance-scope`：管辖范围规范 §5 的管辖登记制度契约（Schema、路径语义、三态判定、写入与迁移规则；本文 §6 的登记共享实现与 §10 的测试基线依其派生）。

JavaScript 运行时、包管理器、测试运行器与构建工具只提供工程语法和执行能力，不取得 LDVH 领域语义权威。

GFM 只提供外部语法定义，不取得 LDVH 领域语义权威（01 §2 已登记）。本文 §6 的结构校验纪律以它的 ATX 标题规则作为形态判定依据；载体结构本身是什么，仍由 01 §7、02 §12 与各类型规范定义。

业务系统基础规范、LDVH CLI 确定性服务规范、DSH 环境接入与插件发布规范、Web 呈现与交互规范是协作来源，不是本文的规范依据；历史规范、开发备忘和既有实现只作为设计输入，不取得规范效力。

本文不重新解释 00–01 与检查机制规范；发生冲突或权威关系无法确认时，按 00 §5.7 暂停受影响范围并完成对齐。

## 3. 职责边界

### 3.1 本文负责

1. LDVH 插件代码结构：目录规范、代码与测试文件命名约定、打包构建工具链与 lint 基准（§5）；
2. 测试基线：机械规则覆盖测试的要求，包括正反向用例、边界值及模拟数据（§5）；
3. 契约实现纪律：统一 LDVH CLI、precheck、管辖读取与 Git Gate 的单点实现与调用链，禁止副本逻辑（§6）；
4. 实现并测试 01 定义的规范身份块、L0–L4 读取与根级 Code 消费入口解析，不改变其语义（§6）；
5. Output Envelope 的单一生成与一致性实现职责（§6）。

### 3.2 本文不负责

1. LDVH CLI 服务契约、公开操作声明、传输 envelope——归 LDVH CLI 确定性服务规范；
2. 事实对象的公共字段语义、CRUD、CAS 公共契约——归事实源与事实模型基础规范；**具体类型的字段、状态与状态机**——归各事实类型规范（事实源与事实模型基础规范 §6.1 明确「状态值、初态、转换和终态由类型来源定义」）；业务系统规范步骤、触发条件、完成门禁——归业务系统基础规范；
3. 事实源定义、受控提交契约、precheck 语义——归受控提交与机械守护规范；
4. 管辖登记 Schema、判定逻辑——归管辖范围规范；
5. DSH 插件接入、部署、发布与公共门面——归 DSH 环境接入与插件发布规范；Web 呈现——归 Web 呈现与交互规范；
6. AI 对实现是否满足语义要求的判断，与 Human 的授权、验收决定。

### 3.3 相邻规范分工与唯一权威

01–05、07–10 各自是其领域语义的唯一权威；06 只定义实现、工程和测试纪律，不改变任何规范的语义，不成为第二规则源。领域契约变化先进入对应规范，再由 06 实现和测试；Code、测试、构建配置与运行结果不得反向创造规则。

## 4. 适用范围

### 4.1 适用对象

本规范适用于：

1. specs 当前规则定义的机械规则实现；
2. 插件代码结构、构建配置和测试；
3. Output Envelope 的单一生成与一致性实现。

### 4.2 适用场景

本规范用于新增、修改、复核和发布 LDVH Code，实现规范解析、LDVH CLI、事实读写、提交检查、管辖判定、宿主接入和交还生成等已定义机械职责。

### 4.3 明确排除与证明边界

规范起草、语义讨论与 Human 决定不因本规范存在而自动取得实现效力；本规范不定义事实类型、业务系统规范、Web 呈现或环境接入的领域语义。

代码存在、测试通过或构建成功，只证明当次实现的机械范围，不单独证明规范语义已满足、行动允许、功能完整或价值兑现。

## 5. 工程纪律

**目录结构**：宿主插件实现位于 `plugin/lib/`（平铺，按职责分文件）；测试文件位于 `plugin/test/`，命名 `<主题>.test.mjs`；Web 面实现位于 `plugin/web/`，构建产物为 `plugin/web/dist/`；插件与 Web 的依赖清单分别为 `plugin/package.json` 与 `plugin/web/package.json`。本节描述**当前实际结构**；结构迁移须先改本节并同步实现，不得在实现未到位时以目标结构代替现状。

**命名约定**：文件与子目录小写 kebab-case，测试以 `.test.mjs` 结尾，函数 camelCase，类 PascalCase。

**测试基线**：每个机械规则必须有对应单元或集成测试，覆盖正反向用例、边界条件、异常处理，拒绝零测试实现。代码实现与其验证测试须由不同代理或不同 AI 分任，避免同源自证；具体分任方式由主控按风险组织，不写死为单一宿主机制。测试运行入口为 `node --test test/*.test.mjs`。

**断言的检测力须可证，零检测力断言不得保留**（2026-10-30 新增，2026-10-30 审核后修订、同日复审后再修订）：断言必须**存在一种与被守护行为的质量相关的实现改变能让它转红**；不存在这样的改变时，该断言不构成守护，须删除而不是保留——留着会让「测试通过」冒充「行为已守」，并使后续改动误判为安全。此处「实现改变」指**被测实现（Code）及其源码文本**的改变；**事实对象、语料与载体的存废或改名不属之**——它们可以使其转红，但这种红不反映质量（这正是形态 5 要排除的）。以下五类是**典型形态**，清单**不构成闭集**；判定以本句为准，形态 5 的豁免段是唯一例外。

1. **恒真式**：`assert.ok(x || true)`、`assert.ok(n >= 0)`（对 `.length` 恒成立）、`assert.equal(true, true)`。`|| true` 与对非负量取 `>= 0` 是同一类问题——把断言写成永远为真的表达式。
2. **恒不可达式**：循环体内以「本应由循环自己的条件排除」为唯一条件的 `assert.fail`（退出条件为假时循环根本不进入）。
3. **无断言的用例**：该用例内**不存在任何断言**——只调用不抛异常属 smoke test，与守护某条规则不是一回事；需要 smoke 覆盖时单独写一个命名明确的用例，不得挂在规则用例名下。**判据取「用例内有无断言」这个语义属性，不取注释文本**（注释可解释意图，不得据此判定用例有无断言）；§5「守卫测试的证据边界」要求的文件内边界声明不属本项。**「用例内」指该用例的执行范围，含其所调用的辅助函数**（断言写在 `assertVerbatim(...)` 这类辅助函数里，仍属有断言）；**以失败即抛出的步骤代替 `assert` 的，同样构成断言**（失败会使用例转红）。
4. **期望值与被测值同源**：期望值由被断言的同一个函数/同一套归一化导出，使比较恒成立（如用 `join()` 的结果去断言 `join()` 的输出）。
5. **答案指向可被废止或改名之事实对象的评测项**：以某个**可被废止或改名的事实对象**为「应得答案」的评测用例，其目标被废止或改名后转红——此时红不代表质量下降，绿也不代表质量上升。这类用例的答案须指向**稳定的契约对象**（如规范标题、类型闭集），或改用自造夹具；确需钉具体事实对象时，须在用例内写明并执行该对象的处置条件（据该条件跳过或改判，不因对象被废止而红）。**该对象的状态与状态机由事实源与事实模型基础规范及相应类型规范定义，本条不另行判定何为废止、亦不复制其状态语义。**
   - **豁免**：以活语料规模为期望值、**刻意以漂移为报警**的防漂移断言**不适用本条首句的判定，亦不属本类**（这句同时说明它的两种身份：既不受首句判据约束，也不算形态 5 的成员——避免「不属本类」被读成「只是分类排除、首句仍适用、结论仍是须删除」）。其处置按 §7「基线归因的比对锚点」第 ③ 项同步期望值并按该项的归因口径处理，不因本条改写为自造夹具。本类针对的是**答案本身指向某个可被废止或改名的事实对象**的评测项。**主张本豁免者须在用例名或断言处写明「防漂移／漂移报警」，并注明期望值所据的基线提交**——**不接受只写日期**：「实测日期」在文本上与任何日期无法区分、无可核对对象，只有基线提交可用 `git` 回查。否则「刻意」只是一句自述，无法回查。

**与「拒绝零测试实现」的关系**：本条不减损测试基线，而是其反面补充——基线管「每条规则必须有测试」，本条管「每条测试必须真能测」。二者同时成立时，测试通过才具有「该规则的**某一种破坏**能够被检出」这一较弱结论；仍不证明该规则的全部形态已被覆盖（§7「测试基线」行），也不证明未被任何用例守护的形态不存在。

**与本节既有断言纪律的分工**：按断言对象分界的三段（「本项与本节其他断言纪律的分工」「与『形状断言有效性』的分界」及本段）在此**回指前两段，不重复其内容**；本段只新增一件事——本条管**检测力是否存在**，不改变前两段的取分结论。「形状断言有效性」行管运行期数据断言的形状判据与其单项变异，「源码文本断言的方向」行管源码文本断言的依据与方向。对源码文本断言，本条所说的「实现改变」指**该守卫所针对的形态被改回或消失**（即变异第 1 向），其转红只证明该形态当前不在或已被改回，**不证明语义成立**（§5「守卫测试的证据边界」）；对语义独立于字形的源码文本守卫，本条不要求其证明语义级的破坏可检出，该条不构成对其证据上限的扩张，也不减免其按前提声明边界的义务。

**存量口径**：本条自生效起适用于**新增或实质修改**的用例，适用范围限于 §4.1 所列对象（LDVH 自身 Code 与测试）；管辖项目的工程纪律归其事实规范，不受本条约束。既有的零检测力断言于普查后分批清理，不因本条生效而立即不合规（与本节目录结构段、「守卫测试的证据边界」的存量口径同构）。清理时须逐条写明删除理由与「该行为现由哪条用例承接」，不得以「删了一条恒真断言」结案；**形态 3（无断言的用例）不适用「删除理由＋承接用例」的写法**——其存量处置为**拆分并改名**：须把其中的 smoke 覆盖拆为命名明确的独立用例，并为其余行为补上可转红的断言。

**断言须以被测面的真实形状为准**：为读取侧、投影或宿主接口编写断言时，**先读该面的实现确认真实返回结构**（是否展平、嵌套键名、可选字段在什么条件下存在），再决定断言的取值路径；不得按「它应该长什么样」编写。

- **路径取值会抛错，否定式断言不会**。在 `node:assert/strict` 下，对不存在的路径取值（`payload.a.b`）会抛 `TypeError`，深比较会抛 `AssertionError`——这两类会**显式失败**。会静默通过的是**否定式写法**：`assert.equal('k' in payload, false)` 在「字段被移到别处」与「字段整体缺席」两种形态下都成立，因而不能区分形状不同与什么都没返回。（`assert.equal(payload.k, undefined)` 属正向等值断言：字段真的不存在时它同样通过，但它不主张"形状该如何"，故不在此列。）

- **否定式断言须能区分「不在这一层」与「哪儿都没有」，判据按两类形状分别取**：
  - **字段按契约应在另一位置**（合法的形状变换）：在**它应在的位置**断言存在，与「不在原位置」的否定断言并存。今 `payload.result` 下有 `k`、顶层无 `k` 时，`assert.ok('k' in payload.result)` 与 `assert.ok(!('k' in payload))` 是不同对象上的断言，可同时成立。
  - **字段或容器按契约必须整体缺席**（闭集、展平、不得泄漏）：**不给它配正向存在断言**——为「必须不存在的东西」断言存在，与契约本身相反。可满足的判据是**断言同级仍该在的东西在场，并钉住缺席的位置集合**。写法示例：设被测返回对象为 `result`，对其断言 `assert.equal('<不该有的容器名>' in result, false)`，并另对其**同级仍在的锚点字段**断言 `assert.ok('<锚点名>' in result)`——同一对象、不同字段，前者否定不该有的嵌套容器，后者钉住被平坦化后仍在的锚点。该组合的检测力须按本节下一项（形状断言的单项变异）证明：把读取面改回嵌套形状后必须转红。

- **形状断言的有效性靠单项变异判定，不靠首跑是否失败**。做法：把读取面改回错误形状，该断言必须转红（改回后仍绿，说明它对该形状没有检测力）。**本项不适用本节「变异三向」的第 2、3 向**——第 2 向（合法等价变体不被误伤）与第 3 向（被守卫实现改名改措辞但语义不变后仍被捕获）针对的是**校验逻辑的匹配形式**，而形状断言检验的是**返回结构的键位**；对结构键位做「改名改措辞」没有对应物，故不设此两向。首跑是否失败不构成判据：回归用例在缺陷已修后补写时首跑必绿，这不说明它没有检测力。

- **形状判据须取自该面的实现**，不得从另一面（列表项、二次读取、派生投影）的形状推得——同一对象在不同读取面上可以有合法的不同形状。**但读取实现偏离其权威契约时，须同时报告该漂移**：按实现写断言会把漂移固化成绿测，故该情形按 §7「规范一致性」行处置（该行成立条件即「实现行为与对应规范条文一致，无漂移」），不得只改断言。

本条的保证边界如实声明：它规定**编写断言前的核对顺序与写法要求**，不提供「形状是否正确」的机械判据——真实形状仍须由读取实现确认，检测力仍须由单项变异证明。

**守卫测试的证据边界**：以源码文本（读取文件与模式匹配）为断言对象的守卫测试，其证明力**按被断言对象取分**——**当该对象承载的语义独立于其字形而存在时**（如「某拒绝门禁不得复活」「某纪律已获强制」），源码文本断言只能证明该形态当前存在，不能证明该语义成立，因为形态可被改名、改措辞而语义不变；**当形态本身即语义目标时**（如死代码文件不得存在、特定错误命名不得出现），源码文本断言是充分的，不存在改名逃逸的余地。前一类守卫须在文件内声明该边界，且不得据其通过声称某规则已获机械保障。

新增校验前须以变异验证其三向有效性：目标错误的**真实写法**可被捕获、合法写法的等价变体不被误伤、把被守卫实现**改名改措辞但保留语义**后仍被捕获。三项任一不成立时，不得以收紧匹配或增加文本断言加以掩盖——须先判断被区分对象在形式上是否可分。被区分对象在形式上不可分时（同一字形承载不同语义），不得以机械校验强制执行；此时改用弱约束：由规范给出唯一合法写法，其判断依据的提供方式见 §6。弱约束不具强制力，同样不得据其声称已获保障。

本条判据是**「被区分对象在形式上是否可分」，不是「结构化字段还是自然语言正文」**。按前者判断而非按载体形态判断，有两处必须分清：

- **结构化字段**（枚举、类型、必填性、闭集、形状与长度上限）：形式与语义一一对应，机械校验有效且应当使用。
- **引用完整性类约束**（某字段值必须存在于另一集合，如引用编号不得超过目标集合长度）：**其形式（数值比较）完全可机械判定，但被比较的数值在正文上下文中可能指代不明**——同一数字既可能指目标集合的元素，也可能指叙述者自身的序号，两种指代在字形上无别。此类约束是否可强制，取决于**该字段出现在何处**：出现在结构化字段中（如 `parent_index: 7`）则可强制；出现在自然语言正文中且与其它编号体系可能同形时则不可强制，须按本条前段的变异三向验证逐例判定。

不得把这两类笼统归为「正文相关一律不设校验」，也不得仅凭「形式上是一个数字比较」就认为可强制——本条的失效案例正属后者：其形式完全可判定，失效源于指代不可分。

本项**不减免既有测试义务**：既有源码文本断言仍须保留其防止已知形态被误删、被随手复原的作用，只是不得据其声称语义级保障；「拒绝零测试实现」的既有要求不因本项而放宽。

**源码文本断言会把当次实现钉成契约**：以源码文本为断言对象的守卫（读取文件内容后做匹配、计数或比对，如 `assert.match(source, …)` / `assert.doesNotMatch` 类），断言的是「代码里现在写着什么」。当它断言的具体字形正是**待淘汰的旧形态**时，该守卫不再防止回归，而是**把回归钉成契约要求**——此后每次试图修正都会让测试变红，修正者只能改测试或保留缺陷，两者都错。

故编写或修改**以源码文本为断言对象的守卫测试**时：

1. **正反两个方向都要有据**：正向断言（`match`）须能回指到权威契约（某类型规范的字段表、某节规定的形态或命名）；反向断言（`doesNotMatch`）须能回指到**该形态已被淘汰**这一事实。**两侧都不得以「当前实现就是这么写的」为据**——实现是断言的对象，不是它的依据。⚠️ **注意第三种情形**：断言的依据可能落在两侧之外——正向断言钉住的字形在契约里查不到（而实现里恰好写着，故测试是绿的），反向断言针对的旧形态既无淘汰依据、也无任何规范记载。二者**任一**即属**无依据断言**：须先判定它该断言什么，不得以「反正现在测试是绿的」保留。
2. **正向断言只允许指向契约规定的形态**，不得指向待淘汰的旧名、旧键、旧路径。需要防止旧形态复活时，用**反向断言**表达，并写明它针对的是哪个已淘汰形态。
3. **反向断言的匹配窗口须限定在被测单位内**：跨文件或跨函数的宽窗口会把无关处的同名字形一并算作命中，使断言在正确实现上也失败，或掩盖真正的残留。**「被测单位」指该断言所守护的那个单位**——函数、模块或文件；若该断言的对象本身是全仓库或某目录的闭集（如已跟踪文件清单、引用图），则该闭集就是它的被测单位。该单位须在断言处可读出。
4. **断言须注明它所依据的位置**：正向断言注明**契约位置**（哪份规范的哪一节或哪个字段表），反向断言注明**该形态已被淘汰的依据**（规范条款或事实载体）。**标注依据位置**是该项要求唯一可核对的形态；**所注位置须确实包含被断言的那个字形或命名**（回指一个通篇不含该字形的章节，等于没有给出依据）。本规范不要求、也不承认「字段／接口版本」这类标注：若某类对象没有既定的版本载体，凭空引入版本号只会造出一个无法核对的证据位，而「写对了版本号」本身不构成任何判据。

**本项与本节其他断言纪律的分工（各自管一层，不互相替代）**：

- **「守卫测试的证据边界」**管此类断言的**证明力上限**（其取分规则见该条，本项不重述）；本项管**方向**：它可能反过来把现状钉成契约。二者是同一种断言的两个不同问题，**本项不改变该条的取分结论**。
- **「断言须以被测面的真实形状为准」**管**数据与形状层**：读取面的键位、层级、可选字段该怎么断言。本项管**源码文本层**：断言的字符串该指向哪种字形。
- **读取实现偏离其权威契约时须同时报告该漂移**（见本节「形状判据须取自该面的实现」一段）同样适用于本项：本项不提供「只改断言」的出口。
- **变异验证的要求不因本项而变**：本项不新立变异方向，按本节「变异三向」执行；反向断言的有效性按第 1 向（把旧形态放回去，该断言必须转红）证明。

**与「形状断言有效性」的分界**：两条验证行按**断言对象**分界，同一个断言只会落在其中一行。断言对象是**源码文本**（对读取文件内容的匹配、计数或比对）→ 适用「源码文本断言的方向」；断言对象是**运行期取回的数据**（某个返回值的键位、层级、可选字段）→ 适用「形状断言有效性」。一个断言若两侧都涉及（既读源码又读数据），它实际上是两条断言，须各自满足各自那一行，不得以其中一行成立顶替另一行。

**存量生效口径**：本节所述要求自本段生效起适用于**新增或实质修改**的守卫测试；既有守卫测试于普查后分批补齐边界声明，不因本段生效而立即不合规（与本节目录结构段「本节描述当前实际结构」同构）。

**「没有输出」与「输出为零」是两个结果**：以脚本批量判定测试或验证结果时，判据若从输出里取某个计数（失败数、命中数、通过数），**取不到该计数**与**取到了零**必须输出为两个不同的终态。把前者并入后者会让「根本没运行」以「结果为零」的形式呈现，且不报任何错误。

故批量判定须满足：

1. **判断运行是否真的发生，证据须与本次运行的结果无关**：可用的证据是「运行器是否产出了它的报告」（报告头、计数行、本轮独占的标记，**满足其一即可**）——**报告存在**说明运行发生过，与报告里的数值无关；但该报告须属于本次运行，不以路径上驻留的旧报告充当。**不以「路径上有东西」代替**——副本目标已存在时，「复制成功」可能只是复制进了其下的一层，被测内容并不在判定逻辑引用的位置；上一轮的残留也会在路径上。
   **进程退出状态不能单独充当该证据**：非零退出至少有两种成因——「跑了且失败」与「根本没启动」；把「退出码非零／为零」当作「是否跑过」的判据，会把正常的失败运行判成未运行，本条要防的失效反而被制造出来。退出状态只用于区分「未启动」，且须与报告是否存在并读。
2. **取不到计数时输出独立终态，不得并入零计数**。该终态须如实反映第 1 项的结论：确已启动而计数不可得时，名称不得写成「未能运行」那样否定运行本身；该终态须在输出中与该计数并列可见，不因取值为空而被省略。
3. **该终态须使整批结论不可用**：出现该终态时不得以「全部存活／全部通过」收尾，须按 §7 末段的 gaps 纪律如实披露未执行与不可用范围，并使该批结果不可用于后续结论。
4. **被判定对象的定位方式须与判定逻辑一致**：判定读的是哪个路径、被测内容实际落在哪个路径，两者须是同一处；不以「上一次」的副本充当本次。

**生效口径**：本条适用于新增或实质修改的批量判定脚本；既有脚本于迁移时按本条改造，改造完成之前据其结论作出的判断须如实披露该缺口，不得据其声称「已排除未运行」。

**本条不主张「零失败」没有信息量**：运行已被确证时，零失败说明「本次运行没有失败」，可作为「该行为可能由别处承担、或缺守护」的依据并要求人工判断；本条禁止的只是把它读作「测试没接住」或「守护无效」——那需要先确证运行真的发生。二者的区别：**缺守护**指本次运行没有任何测试对该行为转红（它可能由别处承担，未必是缺陷）；**守护无效**指存在针对该行为的守卫而它未转红——后者需要先确认该守卫存在。「零命中」方向的依据见 §6「检索不能证明「没有」」，本条不重复。

**Lint 与格式化**：ESLint 统一配置，提交前必须通过静态分析，`git diff --check` 无空白错误。格式化不设独立工具链。

**工具链**：JavaScript（ESM，`"type": "module"`），npm 管理依赖（`package-lock.json`），`node --test` 为测试运行器，Web 面使用 Vite 构建。本节所述工具链为**当前实际使用**的工具链；引入 TypeScript、pnpm、Vitest 或其它替代工具链属实现升级，须先改本节并完成相应迁移，不得以计划中的工具链作为当前工程纪律的依据。

## 6. 契约实现纪律

**单一实现原则**：下述职责分别由 01、02、05、07、08、09、10 定义唯一领域语义，06 只规定实现纪律，不替它们定义接口或行为。对应 Code 必须通过单一职责入口实现，严禁复制副本逻辑。

**删除唯一生产者须同轮清理下游**：当某个值的**唯一生产者**被删除（采集段取消、上游字段下线、唯一写入点移除），该值在下游的**每一处消费形态**都成为「恒空来源」——形参仍收、调用点仍传空值、派生字段仍记 0、注释仍在解释一个已不存在的前提。它们不会让任何测试失败，因为「参数无人传」不是错误，只是空。

故删除唯一生产者时，须在**同一轮改动**内沿五类消费形态逐点核查并清理：

1. **形参**——签名里仍在接收该值的参数；
2. **调用点**——仍向该形参传值的调用（常见形态：`existing: x ?? []`）；
3. **派生字段**——由该值算出的计数、痕迹或摘要（常见形态：`existing_pitfalls: x?.length ?? 0`，恒为 0 而不报错）；
4. **注释与文档**——仍在解释该值的前提或语义的说明；
5. **闭集登记与消费点**——该值曾参与的字段闭集条目、错误码或消费点注册（删除后仍登记会让「已删除」与「仍可用」并存）。

**不在当轮写范围内的载体也须核查**：删除发生在 A 文件而消费在 B 文件时，B 不在本次改动范围内**不构成豁免**——须至少完成一次按名检索（形参名 → 调用方是否仍传值 → 派生是否恒空/恒零），并把核查结论写进交还。**检索发现残留时同样须清理**，范围外不使清理义务消失；**未完成核查的载体如实登记为未覆盖，且在该登记存在时不得声称「删除已完成」**。按名检索须逐处判定命中是否指向**被删除的那个值**——同名不同值的活生产者不属残留，不得据命中即改。

**检索不能证明「没有」**：残留往往落在检索模式的形式之外——同一语义在不同载体上可有不同键形（大小写差异、键名含载体前缀、复数与缩写）。**「模式未命中」不等于「不存在」**：它可能确实没有，也可能只是这个模式没覆盖到；二者用检索结果不可区分。反过来，**「模式有命中」也不能证明覆盖了全部形态**——同一文件里可以既有被命中的键形、又有被漏掉的另一种键形（本条的来源经验正是如此：模式在同一文件命中数十行，同一文件的另一批键形却零命中）。

故按本条删除某值的生产者后，要判断其下游残留是否归零：

1. **检索只能给出候选，不能单独作为「已清空」的依据**。把未命中读作「不存在」、或把某次命中读作「覆盖了该文件」，都是把检索结果用到了它答不了的题上。
2. **归零判断须落到载体内容**：对可能持有该值的每个载体（含本次改动之外的载体）读取其内容，确认该键形确已不在。这是唯一能回答「还有没有」的动作；检索的作用是帮你找到该读哪些地方。
3. **检索不能替代内容核对**。对**每一个**你要依据其检索结果下结论的键形，各取一个已知存在的样本（可从删除前的版本取），该模式必须命中该样本——未取样本的键形不构成任何结论依据。但**样本自证只说明「该模式认识这一种写法」，不说明「你已想到全部写法」**：键形的枚举由你的认知决定，想不到的写法既不会取样本、也不会出现在未覆盖登记里。故自证通过后仍须回到第 2 项读载体内容；自证的作用是**缩小**需要读的范围，不是**替代**读。
4. **未完成的核对不得由「已登记未覆盖形态」顶替**：把某键形记为「未覆盖」是如实披露，不是完成条件——在该披露仍然存在时，不得声明「已一并删除」（00 §5.6）。

**可机械判定的范围（条件式限定）**：上述五类消费形态中，**派生字段的闭集**与**调用点的传参形态**属原理上可机械判定的对象（二者都是可断言的代码形态）；**形参是否仍有实参传入**与**注释是否仍在解释已不存在的前提**不属同一判定面——前者在参数形态下不构成错误，后者须语义判断。**在针对派生字段与调用点的守卫实际建成之前，不得据本条主张这类残留已获机械拦截**；实现是否已建成属实现现状，按 01 §7.2 由读取时的观察取得，本款不陈述其当前状态。该守卫建成后，其有效性按 §5 变异三向的第 1 向验证（把被删值对应的派生字段或调用点传参恢复后，该守卫必须转红）。

**例外**：某值仍有生产者时，下游保留消费形态是正常接线，不属残留。但**值的多条生产路径中只删除其中一条**时，本条适用于**被删那条路径**对应的消费边与其前提解释——其余路径仍在，不使被删路径的残留变为正常接线。

**依赖边界须与提交边界对齐**：**触及跨文件 import 的改动**（新增引用、改写说明符、搬移被引用文件）中，**两条边界必须同时推进**——import 关系进入 HEAD，被引用文件也须进入同一次提交。二者不同步时，本地工作树一切正常（文件就在盘上），缺陷只在**纯净检出**（干净 worktree、归档导出、他人克隆、CI）上暴露，表现为模块加载即失败；本地能运行不构成通过依据。

- **验收判据是「纯净检出可加载」，不是「本地可运行」**。触及跨文件 import 的改动，提交前须确认新建文件已进入暂存区（即落在受控提交与机械守护规范 §5.7 第 1 步「暂存内容能逐项对应到当次授权范围」之内；被引用文件不在当次授权范围时，须先取得范围再提交，不得靠遗漏暂存来缩小范围），提交后须在**从 HEAD 导出的版本**上加载一次**受影响模块**（导出物只含已入提交的内容；工作区里暂存但未提交、或被忽略的文件不在其中）——即该 import 所涉的直接依赖方，以及本次改动中一并触及的其它模块（不要求对整个依赖闭包逐一加载，但不得只挑一个「看起来能跑」的入口）。
- **机械判定的范围（条件式限定）**：已跟踪源文件的相对 import 目标是否出现在版本控制索引中，属原理上可机械判定的对象。**在针对依赖边界的该守卫实际建成之前，不得据本条主张加载边界已获机械拦截；实现是否已建成、其实际覆盖面有多大，均属实现现状，按 01 §7.2 由读取时的观察取得，本款不陈述其当前状态。** 当次判据覆盖不到的一切载体形态（说明符种类、脚本扩展名、加载方式）均须按上一项的验收判据人工确认，并把确认记录写进交还——**不得把「判据存在」读作「全部载体已被覆盖」**。该守卫建成后，其有效性按 §5 变异三向的第 1 向验证（注入一条指向未纳入版本的文件的 import 后，该守卫必须转红）。
- **不得以「本机能跑」结案**：本地通过只证明当前盘上文件齐全，不证明这些文件属于同一个提交。
- **提交后加载失败时，须处置已产生的提交**：补齐被引用文件不是全部——**已产生的提交本身**也须处置。该处置是提交动作，须按受控提交与机械守护规范 §5.7 **全部三步**重新走一遍（重新暂存 → 按 §5.1 契约形成提交 → 回读核对），**三步不得跳过或合并**；回读同样适用于该处置产生的提交。**在补齐内容已进入 HEAD、且上述三步与本次加载核对均完成之前，不得声称本次改动已完成。** 加载核对本身是**本条的验收动作**，不在 §5.7 三步的既定内容之内——它发现的是提交内容与加载事实不符，处置入口仍是 §5.7。

**与 §6「删除唯一生产者须同轮清理下游」成对**：本条管**依赖关系两端未同步落地**（新增时引用方先进、被引用方未进；改写或搬移时路径已变、被引用位置未变），上条管**删除依赖**（生产者已删、消费形态未清）。两者的共同失效形态相同——**改动边界与依赖边界不重叠**，且都在本地不可见。核查时须同时走两侧：新增了什么引用、删除了什么生产者。

**结构校验须按集合性质判定，不得以首行比较替代集合判定**：当规则说的是「某级标题恰好一个」「某节序列固定」「某元素不得重复」这类**集合性质**时，校验的**判定对象是该集合本身**（计数或枚举）。**以「首个匹配行是否等于标题」的单点比较来替代集合判定，即属本条禁止的形态**——单点比较可保留，但它不承担集合性质，不能独自充当结构校验。本条约束**校验的写法**，不新增结构规则——结构是什么仍由 01 §7、02 §12 与各类型规范定义。

单点比较会同时产生两个方向的错误，且**两个方向都不会被既有测试自动发现**：

- **漏检**：多出一个同名元素时仍然通过——单点比较天生看不见「后面还有没有第二个」。首行之后、小节中间、文件末尾三种位置都会被放行。
- **误报**：合法但写法略有差异的单个元素反被拒绝——单点比较隐含「合法输入只有一种字面写法」这一假设。

**等价形态的判定基准是已登记的外部语法，不是本文列举**：标题的识别与计数以 01 §2 已登记的 **GFM**（其 ATX 标题规则）为准——该登记属外部语法定义，不取得 LDVH 领域语义权威（01 §2）。代码中统一承担结构解析的那个共用入口是该语法的消费点；**该实现与该语法不一致时以该语法为准**，不得反向据实现定义等价形态。判断某写法是否等价，查 GFM 的 ATX 规则，不从本文的示例清单里找。本文给出的等价形态（前导空格、`\t` 或空格分隔、闭合序列、尾随空格、CRLF 与裸 `\r` 行尾）**只作示例**。同理，结构性字面不止出现在围栏内：**代码围栏、行内代码、HTML 块内的 `#` 行都不计入结构**（`#标题` 井号后无空格不是标题，`startsWith("# ")` 恰好排除它属碰巧正确，不能据此认为该写法可用）。

**写法要求**：

1. **判定对象取该规则实际约束的集合**（标题层级 → 该级标题的出现次数；小节序列 → **各节的存在与顺序**），不从「第一行长什么样」推。
2. **等价形态按已登记的 GFM ATX 规则认定为同一元素**，不得因字面差异判为不符。
3. **结构性字面须按该语法规则排除**：围栏、行内代码、HTML 块内的同类字面不计入。
4. **计数与内容比较职责不同，须并存而非相互替代**：计数保证集合性质（恰好一个／序列固定），内容比较保证**可对应到具体期望值的那些位置**与期望一致——标题类即「首个标题与 `title` 一致」，序列类即「各节标题与规定序列一致」。**不得只留内容比较**（会漏掉多出的元素），**也不得以计数删去内容比较**（会失去「与期望值一致」这一约束）。该处存在可对应期望值时二者缺一即属本条不满足；无对应期望值时只有计数一种判定，不要求虚构一个内容比较。
5. **反向用例按 §5「变异三向」验证**（多出一个即被拒、等价变体不被误伤），本条不另立方向集；只测前者会把误报固化，只测后者会把漏检固化。

**本条的适用对象（两类，处置不同）**：① **已采用计数式校验的载体**——不得降级回首行比较，这是一个**反回归**要求，其验证按 §5 变异三向的第 1 向进行（把该处改回首行比较后，锁住「多出的标题被拒」的用例必须转红）；② **仍为首行比较的载体**——在改为计数式之前，**不得据本条主张该处结构已获机械校验**（该处状态属实现现状，按 01 §7.2 由读取时的观察取得，本款不陈述其当前状态）。存量载体的迁移属实现变更，其排期不在本文规定。

**源码注释是待验证线索，不是事实来源**：注释记录的是**某一时刻的观察或当时作者的读法**，它不随代码与数据演进自动失效，也不承担与实现保持一致性的义务。把注释里的断言当作背景事实、据此推导 Code 结论，等于继承他人当次的取样与判断。

- **涉及当前状态的断言，一律按待验证处理**，不论措辞强弱。「全部为 `null`」「均为」「从不」「本宿主没有」这类**全量断言**一旦不符，据其推导的结论会整体反向；而「通常」「大多数情况」「目前看」这类**弱化措辞并不更安全**——它同样是关于现状的断言，却因为看起来不像断言而不被当作断言核对，反而更容易被直接采信。判据不是措辞的强弱，而是**该句是否在陈述当前状态**。用于支撑 Code 结论前，须对当前事实重测，并在结论里标明该背景的来源是注释而非实测。
- **注释与现行判据不一致时，它的作用是「指出这里需要核对」，不是「判定谁错」**。**不一致本身不足以指认任何一方失效**：既不得据注释推翻判据，也不得据判据直接否定注释。须先确认二者是否指向**同一对象、同一版本、同一适用范围**——
  - **同一前提之下不可同真**：二者至少有一个已不成立，须回到数据面与实现确认是哪一个，并记录该结论。
  - **前提不同**：不能据该不一致判定任何一方失效（例如某判据按设计保留以兼容不同环境，而注释记录的是其中一种环境下的观察），**不构成失效信号**，也不做「谁过期」的判断；但注释所述的当前状态仍须按上一条重测后方可作结论依据。
- **注释可以说明「为什么」，不能证明「现在是什么」**：解释设计取舍、历史原因的注释有阅读价值；涉及当前状态、当前覆盖、当前取值的断言，一律按待验证处理。

**本条不否认注释的正当用途**：注释是定位与理解的入口，也是排查「该不该继续这么写」的线索；本条限制的是**把它当作结论的依据**。本条也不减免「删除唯一生产者须同轮清理下游」对注释的清理义务。

**规范解析实现**：01 §6 的身份块契约、§6.2 登记的根级 Code 消费入口解析与 §10.3 的读取入口（`read-specification-candidates` / `read-specification-content`）由单一解析入口实现并测试，实现不得改变 01 语义；领域语义由 01 定义，06 只登记实现与测试纪律。

**弱约束的判断依据由实现提供**：当某纪律按 §5「守卫测试的证据边界」判定为形式不可分、因而不得以机械校验强制执行时，实现侧须在**该纪律所约束操作的时点**向调用方提供判断所需的权威依据（如当前有效值的完整清单），使遵守无须自行推断或回查权威载体。该义务只要求**提供依据**，不要求也不允许实现代为判定对错——弱约束不具强制力，实现不得以「已提供依据」声称该纪律已获保障。

**机械签名**：提交（受控提交与机械守护规范 §5.1）、事实 `change_log`（事实源与事实模型基础规范公共字段署名要求）及其它来源后续定义的回报结构所需的 provider/model 必须由 Code 从 DSH 权威会话或请求记录取得，不允许 AI 自填、用部署默认值替代或由调用方覆盖；来源尚未定义所需签名的回报结构不在此列。空白会话、历史会话和模型切换场景必须有确定性取值与不可用结果。

**署名不可用时必须拒绝并报告，不得静默省略**（Human 要求 2026-09-12：「changelog 和提交都要机械署名，不能署名的要报告 human」）：上款所称「不可用结果」是**拒绝**，不是「照写一条无署名的记录」：

1. **提交侧**：提交消息缺少 `LDVH-Provider`／`LDVH-Model` 时，Git Gate 必须**阻断**（`受控提交与机械守护规范 §5.1`），不得放行。
2. **对象侧**：`change_log` 流水无法取得权威署名时，受控写入**不成立**——不得落盘、不得以空值或占位代替、不得先写入再补。
3. **报告义务**：拒绝时须交还**精确原因**并明确标示**需 Human 处理**（署名来源不可用属 Human 可处置的范围）；不得只返回成功形状的 partial，也不得只记录「无署名」而不报告。
4. **禁止降级为静默**：任何实现不得以「降级为无署名流水」的方式绕过本条；非品牌载体（含普通对象、伪造形态、调用方自造值）与缺失签名同样处理。

**依据**：事实源与事实模型基础规范 §6.1 规定 `change_log` 的署名**由 Code 托管**，从未允许省略；本款把该义务的失败路径成文化，使「未署名写入」在机械上不可达，而非事后由人工发现。

**Output Envelope**：06 只规定并验证主控 Output Envelope 的**单一生成职责**（Envelope 的最低语义由 00 §5.8 定义，06 不定义其形状）；DSH 环境接入与插件发布规范定义 DSH 宿主承载、写入时机、消费方和验收流映射，Web 呈现与交互规范定义 Human 呈现。Human 可读正文由同一结构派生或经一致性检查，二者不得矛盾；LDVH CLI 共同响应只是输入，不得冒充主控交还。

**生成职责的条件式限定**：**在 Envelope 的生成与一致性检查实际建成之前**，不得据本文主张 Envelope 已生成、已校验或交还已完成；仅有 Human 可读正文时，须按检查机制规范 §9.3 暂停交还完成声明并披露未兑现范围，不得以本款的规定性表述代替实现证据。实现是否已建成属实现现状，按 01 §7.2 由读取时的观察取得，本款不陈述其当前状态。

| 测试基线 | 实现新增或修改后 | 每一机械规则均关联对应测试文件且运行通过，正反向用例与边界覆盖 | 测试文件与测试运行结果 | 测试运行核对 | 当次已运行规则的通过范围；不证明用例完备或无边缘遗漏；源码文本断言按其前提只证明形态当前存在，不证明语义成立（§5 守卫测试的证据边界） | 缺测试时补齐，未通过时修复，不宣称实现完成 |
| 依赖边界的加载闭合 | 触及跨文件 import 的改动（新增引用、改写说明符、搬移被引用文件）时 | 正常路径：被引用文件与 import 关系在同一次提交内；处置路径：补齐内容已进入 HEAD 且 §5.7 三步均已完成。两种路径均须在**从 HEAD 导出**的某版本上加载该 import 所涉的直接依赖方（及其在本次改动中一并触及的模块）成功；当次判据未覆盖的载体形态已人工确认，确认记录写进交还 | 暂存内容与实际提交、从 HEAD 导出的加载结果、未覆盖载体的确认记录（写进交还） | 暂存核对与 HEAD 导出口加载 | 当次提交对加载闭合的范围；不证明判据覆盖全部载体形态，也不证明运行期行为正确 | 加载失败或未确认覆盖时不得声称本次改动已完成；处置路径须走完 §5.7 三步（含第 3 步回读）后再声明完成 |
| 删除后的下游清理 | 删除某个值的唯一生产者（含多生产路径中删其一）时 | 同一轮内已核查形参、调用点、派生字段、注释与文档、闭集登记与消费点五类形态；当轮范围外的载体已做按名检索、逐处判定命中是否指向被删的值，并把结论写进交还；**残留是否归零已落到载体内容**——可能持有该值的载体已逐个读取内容确认；用检索缩小阅读范围时，每个据以下结论的键形均已取已知样本自证，且自证未被当作内容核对的替代；存在未覆盖键形时已读内容结案，未以「已登记未覆盖」顶替；发现残留者已清理 | 删除改动、按名检索结果及逐处命中判定、内容核对记录（读了哪些载体、结果如何）、各键形的样本—命中对照记录、未覆盖形态登记（均写进交还） | 载体内容核对与键形样本对照 | 当次核对所读过的载体；不证明仓库内不存在其它同类残留——未读的载体与未想到的键形均不在此列（未普查范围须如实登记），自证样本也不代表全部键形 | 未落到载体内容核对时，检索结果不构成证据，不得声明清理完成；仍有未覆盖键形时须读内容结案，不得以登记未覆盖顶替；残留存在时先清理再声明删除完成 |
| 源码文本断言的方向 | 编写或修改以源码文本为断言对象的守卫时 | 正向断言的依据是可回指的契约位置**且该位置确含被断言的字形**，反向断言的依据是该形态已被淘汰的记载（规范条款或事实载体），二者均不以当前实现为据；正向断言不指向待淘汰的旧形态；反向断言的匹配窗口限定在被测单位内且该单位可读出；发现读取侧仍在用旧键时已同时报告该漂移 | 断言文本、所注契约位置与该字形的对应关系、淘汰该形态的依据（规范或事实载体）、断言所处的被测单位 | 实现与契约对照、断言运行、变异第 1 向 | 当次断言所指向的字形与依据之间的对应；不证明该断言覆盖了全部旧形态，也不证明所引契约条款的其它内容成立 | 正向断言指向旧形态或无依据时先判定该断言应断言什么；所注位置不含该字形时视为未给出依据；窗口跨单位时收敛后再声明完成；发现实现漂移时须报告，不得只改断言 |
| 结构校验的判定对象 | 新增或实质修改结构类校验时；存量载体改回首行比较时 | 判定对象是该规则约束的集合（计数/枚举），非以「首个匹配行等于标题」的单点比较替代集合判定；小节序列须覆盖**各节的存在与顺序**；等价形态按 GFM 的 ATX 规则认定；结构性字面按该规则排除（围栏、行内代码、HTML 块）；计数与首行文本比较并存且互不替代；反向用例按 §5 变异三向验证 | 校验实现、GFM ATX 规则（01 §2 已登记）、按 §5 变异三向的反向用例、围栏与等价形态的测试夹具、顺序类夹具 | 用例运行与实现对照 | 当次覆盖的层级与形态；不证明其它层级、其它形态同样被正确计数，也不证明该结构规则本身正确 | 仅以首行比较替代集合判定时，不得据本条主张该处已获机械校验；已采用计数者降级回首行比较时按回归处置，先改回再声明完成；等价形态或结构性字面未被正确识别时，先修该处的识别再声明完成（不得以「只测了围栏」结案） |
| 注释断言的可采性 | 把源码注释中的断言用作 Code 结论的背景时 | 涉及当前状态的断言已对当前事实重测，结论中标明该背景来源为注释；注释与判据不一致时未择一采信，已先确认是否同一对象／版本／适用范围；确认属同一前提时，已记录回到数据面得出的结论 | 注释原文、重测所依据的当前实现与数据、前提同异的确认、同一前提下的核对结论 | 实现对照与事实重测 | 当次重测覆盖的断言；不证明其它注释的断言当前仍成立，也不证明重测取样代表了全部情形 | 未重测的现状类断言不得作为结论依据；注释与判据不一致时任何一方都不得被单方采信 |
| 单一实现 | 实现新增或修改后 | 同一规则只存在唯一职责入口实现，无副本逻辑 | 代码库扫描与调用链观察 | 副本扫描核对 | 当次扫描范围内唯一；不证明依赖方调用无绕过或调用语义无漂移 | 发现副本时合并到单一入口，未修复前不发布 |
| 规范一致性 | 实现或对应规范变化后 | 实现行为与对应规范条文一致，无漂移 | 规范条文与实现行为对照 | 一致性对照审核 | 当次对照范围；不证明规范本身正确或适用 | 漂移时暂停受影响功能声明并修复 |
| Output Envelope 一致性 | 每次交还生成后 | 机器可读 Envelope 与 Human 可读正文表达同一结果 | 生成结果与一致性检查记录 | 一致性检查 | 当次生成一致性；不证明交还内容正确或价值成立 | 不一致时修正，不得交付矛盾交还 |

机械结果与语义判断互不替代。编译、测试、Lint 或构建成功只能证明各自机械范围；本章不能单独证明规范语义满足、授权覆盖或 V/HV 价值成立，未执行和不可用范围保留为 gaps。

## 8. Human Gate

本文不新增 00 之外的 Human Gate。

### 8.1 领域增量事项

以下事项是 00 §4.2 在 Code 实现与测试领域的具体化：

1. 变更工具链配置、目录结构或命名约定；
2. 放宽测试覆盖要求，或改变验证边界与证据定义；
3. 新增或修改契约实现纪律。

受保护文档修改按 00 §4.3 执行，此处仅回指，不构成本文领域增量。

### 8.2 决定边界

Human 决定只证明决定及其作用范围，不替代静态分析、测试运行、副本扫描或规范一致性对照。

## 9. 必停情形

本规范不新增根停止类型。

### 9.1 领域触发与影响范围

出现以下任一情况时，按 00 §5.7 暂停受影响的最小实现、提交或完成声明范围：

1. 编译失败或 Lint 检查未通过；
2. 机械规则缺少对应测试；
3. 代码中存在针对同一规则的多份副本实现；
4. 管辖判定或校验器逻辑与对应规范发生漂移；
5. 准备实现未由生效规范确立的机械规则或属性。

### 9.2 暂停期间允许动作

暂停期间只允许不越过停止边界的规范定位、代码检查、测试补充、修复与验证，不得继续受影响实现发布、提交或完成声明。

### 9.3 恢复与再次触发

恢复须修复对应代码使其与规范一致，并通过实际受影响测试；恢复只覆盖当前验证支持的范围。同一停止条件恢复后再次触发时按 00 §5.7 进入 Human Gate。

## 10. 反过度设计红线

1. 不为非 LDVH 规范需求编写跨平台、多宿主的通用 Hook 或中间件适配层；
2. 不实现未在 specs/ 当前规则源成员规范（基础规范段、事实类型规范段与业务系统规范段内的规范，见 01 §8.1）中确立为生效的机械规则与属性；
3. 不因懒于重构而复制已有的校验器、管辖判定或 LDVH CLI 封包逻辑。
