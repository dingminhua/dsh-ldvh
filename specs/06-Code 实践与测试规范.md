# Code 实践与测试规范


## 1. 价值判断

本规范解决规范机械规则缺少一致、可测试、可回读单一实现的问题，通过工程纪律、测试基线和单一实现原则，减少实现漂移、副本逻辑、重复造轮子和无证据完成声明的负担。

工程纪律与契约实现主要支撑 V4 稳定推进；验证证据与声明边界主要支撑 V5 据实判断；单一实现与可复用测试主要支撑 V8 持续积累；测试文件、运行结果与实现回读主要支撑 HV3 入档闭环节点可验。

本规范只定义 Code 实现与测试纪律；规范语义、事实与业务系统规范规则、提交契约、环境接入和 Web 呈现由 01–05、07–10 及实际实现消费方承接。工程纪律和测试只提供机械证据，不替代领域语义与 Human 决定。

代码文件存在、测试通过、Lint 无错误、编译或构建成功，只能证明各自机械范围，不能单独证明规范语义满足、授权覆盖、功能完整、行动完成或价值成立。

**新增的负担与风险（00 §6.3 第 4 问，如实登记）**：本文不是无成本的。

**本条（§5「断言须以被测面的真实形状为准」）新增的负担**：(a) 编写涉及读取面返回结构的断言前须读该面实现，单条断言的编写成本高于按直觉直写；(b) 每条**否定式**断言须按两类形状补判据——「字段应在另一位置」补该位置的正向断言，「字段/容器必须整体缺席」补同级在场断言与缺席位置集合，逐条递增；(c) 形状判据须按读取面分别取得，同一对象跨面时须重复确认，成本随读取面数增长；(d) 证明形状断言的检测力须做一次变异（改回错误形状并确认转红），每次新增此类断言都多一轮改动与还原。

**本条新增的风险**：(a) **以实现为准钉漂移**——读取实现偏离其权威契约时，照实现写断言会把漂移固化成绿测（出口：§7「规范一致性」行的漂移处置）；(b) **否定式断言误作防护**——`in` 的否定形式在字段整体缺席时恒真，若被当作「字段不该在这里」的守卫，它对该形态没有检测力（出口：本条要求按两类形状分别补判据）；(c) **变异未做而声称已证**——未做单项变异就宣称该断言已覆盖该形状，属超出依据的声明（出口：§7「形状断言有效性」行的第 ④ 项）。

**本条（§6「删除唯一生产者须同轮清理下游」）新增的负担**：(a) 删除类改动须在同一轮内按名检索下游五类消费形态，并在检索发现残留时清理（含当轮写范围之外的载体），实际改动面可能超出原计划；(b) 须把核查结论写进交还，未核查的载体逐项登记为未覆盖。**本条新增的风险**：(a) **删了生产者却留消费形态**——形参恒收空值、派生字段恒记 0，无测试失败、无运行时报错，只在人工核查或下游效果异常时暴露（出口：本条的五类逐点核查 + §7 该行）；(b) **以「不在当轮范围」为由跳过**——范围外载体因此从核查中消失（出口：本条要求其中至少完成一次按名检索并登记结论）。

**核对方式**：以 §7 验证表「形状断言有效性」「删除后的下游清理」「测试基线」三行逐项核对；未执行变异或未完成核查时，按 06 §7 末段的 gaps 纪律如实登记为未覆盖。

**若上述负担与风险在实践中被证明超过收益，应重审本文机制而非默认保留**（00 §6.3「答不出的不纳入」，反向亦成立）。

## 5. 工程纪律

**目录结构**：宿主插件实现位于 `plugin/lib/`（平铺，按职责分文件）；测试文件位于 `plugin/test/`，命名 `<主题>.test.mjs`；Web 面实现位于 `plugin/web/`，构建产物为 `plugin/web/dist/`；插件与 Web 的依赖清单分别为 `plugin/package.json` 与 `plugin/web/package.json`。本节描述**当前实际结构**；结构迁移须先改本节并同步实现，不得在实现未到位时以目标结构代替现状。

**命名约定**：文件与子目录小写 kebab-case，测试以 `.test.mjs` 结尾，函数 camelCase，类 PascalCase。

**测试基线**：每个机械规则必须有对应单元或集成测试，覆盖正反向用例、边界条件、异常处理，拒绝零测试实现。代码实现与其验证测试须由不同代理或不同 AI 分任，避免同源自证；具体分任方式由主控按风险组织，不写死为单一宿主机制。测试运行入口为 `node --test test/*.test.mjs`。

**断言须以被测面的真实形状为准**：为读取侧、投影或宿主接口编写断言时，**先读该面的实现确认真实返回结构**（是否展平、嵌套键名、可选字段在什么条件下存在），再决定断言的取值路径；不得按「它应该长什么样」编写。

- **路径取值会抛错，否定式断言不会**。在 `node:assert/strict` 下，对不存在的路径取值（`payload.a.b`）会抛 `TypeError`，深比较会抛 `AssertionError`——这两类会**显式失败**。会静默通过的是**否定式写法**：`assert.equal('k' in payload, false)` 在「字段被移到别处」与「字段整体缺席」两种形态下都成立，因而不能区分形状不同与什么都没返回。（`assert.equal(payload.k, undefined)` 属正向等值断言：字段真的不存在时它同样通过，但它不主张"形状该如何"，故不在此列。）

- **否定式断言须能区分「不在这一层」与「哪儿都没有」，判据按两类形状分别取**：
  - **字段按契约应在另一位置**（合法的形状变换）：在**它应在的位置**断言存在，与「不在原位置」的否定断言并存。今 `payload.result` 下有 `k`、顶层无 `k` 时，`assert.ok('k' in payload.result)` 与 `assert.ok(!('k' in payload))` 是不同对象上的断言，可同时成立。
  - **字段或容器按契约必须整体缺席**（闭集、展平、不得泄漏）：**不给它配正向存在断言**——为「必须不存在的东西」断言存在，与契约本身相反。可满足的判据是**断言同级仍该在的东西在场，并钉住缺席的位置集合**。仓库实例（`friction-attribution-ref-fidelity.test.ts:77-78`）：`assert.equal('fact_object' in data, false)` 配 `assert.ok('attribution_ref' in data)`——同一对象、不同字段，前者否定不该有的嵌套容器，后者钉住被平坦化后仍在的锚点；该组合已做破坏性反证（把读取面改回嵌套后转红）。

- **形状断言的有效性靠单项变异判定，不靠首跑是否失败**。做法：把读取面改回错误形状，该断言必须转红（改回后仍绿，说明它对该形状没有检测力）。**本项不适用本节「变异三向」的第 2、3 向**——第 2 向（合法等价变体不被误伤）与第 3 向（被守卫实现改名改措辞但语义不变后仍被捕获）针对的是**校验逻辑的匹配形式**，而形状断言检验的是**返回结构的键位**；对结构键位做「改名改措辞」没有对应物，故不设此两向。首跑是否失败不构成判据：回归用例在缺陷已修后补写时首跑必绿，这不说明它没有检测力。

- **形状判据须取自该面的实现**，不得从另一面（列表项、二次读取、派生投影）的形状推得——同一对象在不同读取面上可以有合法的不同形状。**但读取实现偏离其权威契约时，须同时报告该漂移**：按实现写断言会把漂移固化成绿测，故该情形按 §7「规范一致性」行处置（该行成立条件即「实现行为与对应规范条文一致，无漂移」），不得只改断言。

本条的保证边界如实声明：它规定**编写断言前的核对顺序与写法要求**，不提供「形状是否正确」的机械判据——真实形状仍须由读取实现确认，检测力仍须由单项变异证明。

**守卫测试的证据边界**：以源码文本（读取文件与模式匹配）为断言对象的守卫测试，其证明力**按被断言对象取分**——**当该对象承载的语义独立于其字形而存在时**（如「某拒绝门禁不得复活」「某纪律已获强制」），源码文本断言只能证明该形态当前存在，不能证明该语义成立，因为形态可被改名、改措辞而语义不变；**当形态本身即语义目标时**（如死代码文件不得存在、特定错误命名不得出现），源码文本断言是充分的，不存在改名逃逸的余地。前一类守卫须在文件内声明该边界，且不得据其通过声称某规则已获机械保障。

新增校验前须以变异验证其三向有效性：目标错误的**真实写法**可被捕获、合法写法的等价变体不被误伤、把被守卫实现**改名改措辞但保留语义**后仍被捕获。三项任一不成立时，不得以收紧匹配或增加文本断言加以掩盖——须先判断被区分对象在形式上是否可分。被区分对象在形式上不可分时（同一字形承载不同语义），不得以机械校验强制执行；此时改用弱约束：由规范给出唯一合法写法，其判断依据的提供方式见 §6。弱约束不具强制力，同样不得据其声称已获保障。

本条判据是**「被区分对象在形式上是否可分」，不是「结构化字段还是自然语言正文」**。按前者判断而非按载体形态判断，有两处必须分清：

- **结构化字段**（枚举、类型、必填性、闭集、形状与长度上限）：形式与语义一一对应，机械校验有效且应当使用。
- **引用完整性类约束**（某字段值必须存在于另一集合，如引用编号不得超过目标集合长度）：**其形式（数值比较）完全可机械判定，但被比较的数值在正文上下文中可能指代不明**——同一数字既可能指目标集合的元素，也可能指叙述者自身的序号，两种指代在字形上无别。此类约束是否可强制，取决于**该字段出现在何处**：出现在结构化字段中（如 `parent_index: 7`）则可强制；出现在自然语言正文中且与其它编号体系可能同形时则不可强制，须按本条前段的变异三向验证逐例判定。

不得把这两类笼统归为「正文相关一律不设校验」，也不得仅凭「形式上是一个数字比较」就认为可强制——本条的失效案例正属后者：其形式完全可判定，失效源于指代不可分。

本项**不减免既有测试义务**：既有源码文本断言仍须保留其防止已知形态被误删、被随手复原的作用，只是不得据其声称语义级保障；「拒绝零测试实现」的既有要求不因本项而放宽。

**存量生效口径**：本节所述要求自本段生效起适用于**新增或实质修改**的守卫测试；既有守卫测试于普查后分批补齐边界声明，不因本段生效而立即不合规（与本节目录结构段「本节描述当前实际结构」同构）。

**Lint 与格式化**：ESLint 统一配置，提交前必须通过静态分析，`git diff --check` 无空白错误。格式化不设独立工具链。

**工具链**：JavaScript（ESM，`"type": "module"`），npm 管理依赖（`package-lock.json`），`node --test` 为测试运行器，Web 面使用 Vite 构建。本节所述工具链为**当前实际使用**的工具链；引入 TypeScript、pnpm、Vitest 或其它替代工具链属实现升级，须先改本节并完成相应迁移，不得以计划中的工具链作为当前工程纪律的依据。

## 6. 契约实现纪律

**单一实现原则**：下述职责分别由 01、02、05、07、08、09、10 定义唯一领域语义，06 只规定实现纪律，不替它们定义接口或行为。对应 Code 必须通过单一职责入口实现，严禁复制副本逻辑。

**删除唯一生产者须同轮清理下游**：当某个值的**唯一生产者**被删除（采集段取消、上游字段下线、唯一写入点移除），该值在下游的**每一处消费形态**都成为「恒空来源」——形参仍收、调用点仍传空值、派生字段仍记 0、注释仍在解释一个已不存在的前提。它们不会让任何测试失败，因为「参数无人传」不是错误，只是空。

故删除唯一生产者时，须在**同一轮改动**内沿五类消费形态逐点核查并清理：

1. **形参**——签名里仍在接收该值的参数；
2. **调用点**——仍向该形参传值的调用（常见形态：`existing: x ?? []`）；
3. **派生字段**——由该值算出的计数、痕迹或摘要（常见形态：`existing_pitfalls: x?.length ?? 0`，恒为 0 而不报错）；
4. **注释与文档**——仍在解释该值的前提或语义的说明；
5. **闭集登记与消费点**——该值曾参与的字段闭集条目、错误码或消费点注册（删除后仍登记会让「已删除」与「仍可用」并存）。

**不在当轮写范围内的载体也须核查**：删除发生在 A 文件而消费在 B 文件时，B 不在本次改动范围内**不构成豁免**——须至少完成一次按名检索（形参名 → 调用方是否仍传值 → 派生是否恒空/恒零），并把核查结论写进交还。**检索发现残留时同样须清理**，范围外不使清理义务消失；**未完成核查的载体如实登记为未覆盖，且在该登记存在时不得声称「删除已完成」**。按名检索须逐处判定命中是否指向**被删除的那个值**——同名不同值的活生产者不属残留，不得据命中即改。

**可机械判定的范围（条件式限定）**：上述五类消费形态中，**派生字段的闭集**与**调用点的传参形态**属原理上可机械判定的对象（二者都是可断言的代码形态）；**形参是否仍有实参传入**与**注释是否仍在解释已不存在的前提**不属同一判定面——前者在参数形态下不构成错误，后者须语义判断。**在针对派生字段与调用点的守卫实际建成之前，不得据本条主张这类残留已获机械拦截**；实现是否已建成属实现现状，按 01 §7.2 由读取时的观察取得，本款不陈述其当前状态。该守卫建成后，其有效性按 §5 变异三向的第 1 向验证（把已删除的派生字段或调用点传参恢复后，该守卫必须转红）。

**例外**：某值仍有生产者时，下游保留消费形态是正常接线，不属残留。但**值的多条生产路径中只删除其中一条**时，本条适用于**被删那条路径**对应的消费边与其前提解释——其余路径仍在，不使被删路径的残留变为正常接线。

**规范解析实现**：01 §6 的身份块契约、§6.2 登记的根级 Code 消费入口解析与 §10.3 的读取入口（`read-specification-candidates` / `read-specification-content`）由单一解析入口实现并测试，实现不得改变 01 语义；领域语义由 01 定义，06 只登记实现与测试纪律。

**LDVH CLI 操作契约**：LDVH CLI 仅负责共同请求/响应的解析与异常拦截，具体领域逻辑通过调用规范独立实现完成，不得在 LDVH CLI 中直接实现领域逻辑。

**Git Gate 共享**：Git commit-msg 与 LDVH CLI precheck 必须调用受控提交与机械守护规范定义的同一校验职责入口；具体路径由实现登记，不由 06 替受控提交与机械守护规范预定。`pre-push` 不纳入当前 v5 核心范围，不实现、不要求、不部署。

**管辖登记共享**：管辖范围规范是登记 Schema、路径语义、三态判定、写入与迁移规则的唯一权威；06 只实现并测试这些规则，所有消费方调用同一判定入口，不独立解析、维护权威缓存或回退向上遍历。测试应从管辖范围规范当前契约派生，覆盖三态/fail-closed、字段闭集与条件、路径和 linked worktree、跨平台权限与文件系统、并发/原子写入/回读及 v4 迁移；具体用例清单随管辖范围规范契约和 DSH 环境接入与插件发布规范实际宿主能力维护，不在 06 建立第二份字段或算法定义。

**留观缓冲与经验候选的单一权威**：宿主辅助任务规范（11 号）是留观缓冲的载体契约（§12bis：字段闭集、容量上限、保留期、状态闭集、写入与读取纪律、证据复制要求）与经验候选形成路径（§10.1／§10.2：两段自动动作闭集与机械通道边界）的唯一权威；06 只实现并测试这些规则，所有消费方调用同一缓冲读写入口与同一候选创建入口，不独立解析、不维护副本载体，不得把「不可写」降级为内存或日志承载。测试应从 11 号当前契约派生，覆盖：字段闭集与越界拒绝、载体不存在为合法空集合、容量上限与最旧优先淘汰、保留期状态转换、写入后精确回读、不可写或不可回读时的 fail-closed、`status` 闭集内的状态转换与 `consumed_by` 指向、**逐字引证与来源已复制进 `draft` 正文**（不得只写 `buffer:<id>`）、审核段「只读缓冲不读实时对话」的可观察边界、以及「一次派发交出的每一条都必须有判定、缺判定即整轮 fail-closed 且零写入」的判定完备性（2026-10-27 修订：原「一次运行至多形成 1 条候选」的产出配额已废止）；具体用例清单随 11 号当前契约与实际宿主能力维护，不在 06 建立第二份字段或算法定义。

**弱约束的判断依据由实现提供**：当某纪律按 §5「守卫测试的证据边界」判定为形式不可分、因而不得以机械校验强制执行时，实现侧须在**该纪律所约束操作的时点**向调用方提供判断所需的权威依据（如当前有效值的完整清单），使遵守无须自行推断或回查权威载体。该义务只要求**提供依据**，不要求也不允许实现代为判定对错——弱约束不具强制力，实现不得以「已提供依据」声称该纪律已获保障。

**机械签名**：提交（受控提交与机械守护规范 §5.1）、事实 `change_log`（事实源与事实模型基础规范公共字段署名要求）及其它来源后续定义的回报结构所需的 provider/model 必须由 Code 从 DSH 权威会话或请求记录取得，不允许 AI 自填、用部署默认值替代或由调用方覆盖；来源尚未定义所需签名的回报结构不在此列。空白会话、历史会话和模型切换场景必须有确定性取值与不可用结果。

**署名不可用时必须拒绝并报告，不得静默省略**（Human 要求 2026-09-12：「changelog 和提交都要机械署名，不能署名的要报告 human」）：上款所称「不可用结果」是**拒绝**，不是「照写一条无署名的记录」：

1. **提交侧**：提交消息缺少 `LDVH-Provider`／`LDVH-Model` 时，Git Gate 必须**阻断**（`受控提交与机械守护规范 §5.1`），不得放行。
2. **对象侧**：`change_log` 流水无法取得权威署名时，受控写入**不成立**——不得落盘、不得以空值或占位代替、不得先写入再补。
3. **报告义务**：拒绝时须交还**精确原因**并明确标示**需 Human 处理**（署名来源不可用属 Human 可处置的范围）；不得只返回成功形状的 partial，也不得只记录「无署名」而不报告。
4. **禁止降级为静默**：任何实现不得以「降级为无署名流水」的方式绕过本条；非品牌载体（含普通对象、伪造形态、调用方自造值）与缺失签名同样处理。

**依据**：事实源与事实模型基础规范 §6.1 规定 `change_log` 的署名**由 Code 托管**，从未允许省略；本款把该义务的失败路径成文化，使「未署名写入」在机械上不可达，而非事后由人工发现。

**Output Envelope**：06 只规定并验证主控 Output Envelope 的**单一生成职责**（Envelope 的最低语义由 00 §5.8 定义，06 不定义其形状）；DSH 环境接入与插件发布规范定义 DSH 宿主承载、写入时机、消费方和验收流映射，Web 呈现与交互规范定义 Human 呈现。Human 可读正文由同一结构派生或经一致性检查，二者不得矛盾；LDVH CLI 共同响应只是输入，不得冒充主控交还。

**生成职责的条件式限定**：**在 Envelope 的生成与一致性检查实际建成之前**，不得据本文主张 Envelope 已生成、已校验或交还已完成；仅有 Human 可读正文时，须按检查机制规范 §9.3 暂停交还完成声明并披露未兑现范围，不得以本款的规定性表述代替实现证据。实现是否已建成属实现现状，按 01 §7.2 由读取时的观察取得，本款不陈述其当前状态。

## 8. Human Gate

本文不新增 00 之外的 Human Gate。

### 8.1 领域增量事项

以下事项是 00 §4.2 在 Code 实现与测试领域的具体化：

1. 变更工具链配置、目录结构或命名约定；
2. 放宽测试覆盖要求，或改变验证边界与证据定义；
3. 新增或修改契约实现纪律。

受保护文档修改按 00 §4.3 执行，此处仅回指，不构成本文领域增量。

### 8.2 决定边界

Human 决定只证明决定及其作用范围，不替代静态分析、测试运行、副本扫描或规范一致性对照。

## 9. 必停情形

本规范不新增根停止类型。

### 9.1 领域触发与影响范围

出现以下任一情况时，按 00 §5.7 暂停受影响的最小实现、提交或完成声明范围：

1. 编译失败或 Lint 检查未通过；
2. 机械规则缺少对应测试；
3. 代码中存在针对同一规则的多份副本实现；
4. 管辖判定或校验器逻辑与对应规范发生漂移；
5. 准备实现未由生效规范确立的机械规则或属性。

### 9.2 暂停期间允许动作

暂停期间只允许不越过停止边界的规范定位、代码检查、测试补充、修复与验证，不得继续受影响实现发布、提交或完成声明。

### 9.3 恢复与再次触发

恢复须修复对应代码使其与规范一致，并通过实际受影响测试；恢复只覆盖当前验证支持的范围。同一停止条件恢复后再次触发时按 00 §5.7 进入 Human Gate。
