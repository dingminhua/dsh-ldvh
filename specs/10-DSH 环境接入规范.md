# DSH 环境接入规范


## 1. 价值判断

manifest 存在、工具注册成功、钩子安装或页面加载，只能证明相应接入范围，不能单独证明能力可用、授权成立、行动完成或价值兑现；该证明边界的共同规则见 00 §4.6（按 00 §2.4.4，立项论证不在正文承载）

## 2. 规范依据

本文直接依据：

1. `ldvh-root`：00 §2.7 的技术与机械保障、00 §2.8 的四种价值交付方式、00 §3.3 的受保护内容、00 §3.4 的回应效力、00 §4.6 的据实声明、00 §4.7 的必停情形与恢复、00 §4.8 的交还与撤回；
2. `specification-model-foundation`：01 §7 的共同章节结构、§9 的当前规则源条件、§10.4 的最小规则引导、§12 的独立审核；
3. `check-auxiliary-mechanism-foundation`：检查与辅助机制规范 §9.3 交还（含 Output Envelope）对宿主承载的边界、§6 的检查机制四类；
4. `source-of-truth-traceability`：受控提交与机械守护规范 §5.5 的 Git Gate 事件检查（本文 §6 的 Hook 部署使用其定义的同一 validator）与 §5.1 的 message 契约（本文 §6 的 Git Gate 检查与其对齐）。

DSH 插件规范只提供宿主接口，不取得 LDVH 领域语义权威。

业务系统基础规范、LDVH CLI 确定性服务规范、管辖范围规范、Code 实践与测试规范、Web 呈现与交互规范是协作来源，不是本文的规范依据；历史规范、平台调研、决策材料和实现只作为设计输入或授权证据，不取得规范效力。本文不重新解释 00–01 与检查与辅助机制规范；发生冲突或权威关系无法确认时，按 00 §4.7 暂停受影响范围并完成对齐。

## 3. 职责边界

### 3.1 本文负责

1. manifest 字段声明（名称/版本/入口/权限声明/市场字段）与插件身份入口（§5.1）；
2. 工具注册缝的接入语义：领域操作的输入语义约束由 LDVH CLI 确定性服务规范及各领域来源定义，DSH 工具层实际工具名称、输入 schema 形态、注册时机与权限配置由 10 按当前 DSH 版本核验并定义（§5.2）；
3. 引导面注入形式与预算、turn/end 事件时机接入（turn/end 为会话事件类型，经 `session/event` 载荷分发）、`ctx.userQuestions` 问询面与审批通道授权承载接入（§5.3–§5.5）；
4. 08 管辖范围规范登记制度在 LDVH CLI/Git Gate/Skill/Web 侧的 DSH 宿主接入点（呈现细节归 08 与 Web 呈现与交互规范）（§5.6）；
5. 机械守护部署：运行时不变量、文件观察策略、Git Gate 安装形态、沙箱分层（§6）；
6. 00 §3.3 五类受保护文档在 DSH 域的路径登记与 Output Envelope 宿主承载（§7）；发布流程规则由本项目事实规范「dsh-ldvh 发布规范」承载，本规范只提供其核对所依据的登记位。
7. 编排接入点的宿主接入语义：委派、工作流扇出、通信与中断回收、结果回收所依赖的宿主接入点（其消费义务按 §6 的同一形态适用）——其业务面纪律由业务系统基础规范与 32/33（及主控方案收敛工作，04 §6.1）定义。

### 3.2 本文不负责

1. LDVH CLI 服务契约、公开操作声明、传输 envelope——归 LDVH CLI 确定性服务规范；
2. 事实字段、状态机、CRUD、CAS、content_fingerprint——归事实源与事实模型基础规范；业务系统规范步骤、触发条件、完成门禁——归业务系统基础规范；
3. 事实源定义、受控提交契约、precheck 语义——归受控提交与机械守护规范；管辖登记 Schema、判定逻辑——归管辖范围规范；
4. 代码实现、构建、测试、CI/CD——归 Code 实践与测试规范；Web 呈现、四层阅读器、UI 组件——归 Web 呈现与交互规范；
5. 通用 Hook 抽象、跨平台适配、非 DSH 环境接入、MCP 网关——本文红线禁止（§11）；
6. 编排的业务面纪律——归业务系统基础规范与 32/33（及主控方案收敛工作）；检查点、复核执行与独立复核的组织方式——归检查与辅助机制规范 §6 与 01 §12；子代理的 Code 实现——归 Code 实践与测试规范。

### 3.3 相邻规范分工与唯一权威

LDVH CLI 确定性服务规范是 LDVH CLI 服务契约与领域操作输入语义的唯一权威，受控提交与机械守护规范是 Git Gate 与提交检查语义的唯一权威，管辖范围规范是管辖判定语义的唯一权威，Code 实践与测试规范是 Code 实现与测试的唯一权威，Web 呈现与交互规范是 Web 呈现与交互的唯一权威；10 只定义 DSH 宿主接入点、部署形态、受保护文档登记位与 Output Envelope 承载，不另建第二权威。33 是调研吸收系统内部机制的唯一权威；10 是子代理编排接入与宿主的唯一权威，不回授编排的业务面纪律。

## 4. 适用范围

### 4.1 适用对象与场景

本规范适用于：

1. DSH 宿主下的 LDVH 插件；
2. 插件 manifest、工具、引导、事件、交互、管辖登记与编排接入点接入；
3. 机械守护部署、受保护文档路径登记与 Output Envelope 承载。

本规范用于插件装载、工具注册、规则引导、事件接入、授权交互、编排接入点的接入与消费、Git Gate 部署、沙箱权限、受保护文档路径登记与 Output Envelope 宿主承载。

### 4.2 明确排除与证明边界

非 DSH 宿主、跨平台移植与非 LDVH 插件不在本文适用范围；本规范不定义 LDVH CLI 确定性服务、事实模型、业务系统规范、Web 呈现或 Code 实现细节。

manifest 存在、工具注册成功或钩子安装，只证明当次接入的机械范围，不单独证明能力可用、授权成立、工作完成或价值兑现。

## 5. DSH 插件身份与接入

### 5.1 插件 manifest

manifest（`package.json` 或 DSH 市场规定的文件）为插件身份入口，至少声明：名称、版本、入口路径、权限声明、DSH 插件市场字段（描述/分类/图标/作者）。manifest 是身份与权限的机械来源；AI 不得修改权限声明字段，修改须经 Human Gate。

### 5.2 工具注册缝

LDVH CLI 确定性服务规范定义的 LDVH CLI 操作经 DSH 正式工具注册入口 `ctx.tools.register(defineTool({name, description, parameters, output, execute}))` 接入，返回 disposer；`parameters` 为宿主 schema DSL（非裸 JSON Schema：`required` 是逐属性注解而非兄弟数组，每个 object 节点须显式 `additionalProperties`），在 `defineTool` 的 execute 闭包内编译校验，违规抛 `ToolArgsError`——**校验只在 defineTool 内发生**，裸描述符直接交给 `ctx.tools.register` 时该入口只断言 `output`/`timeoutMs`/保留名，参数一律不校验。校验覆盖类型、枚举与嵌套对象字段封闭；**参数根是隐式开放对象、不可关闭**，故顶层未声明字段不在此层被拒——通道内字段的防护由各领域 writer 的字段闭集承担（事实源与事实模型基础规范 §10.5）；「顶层出现与 frontmatter 同名的字段」这一形态**不得据本层声明已获机械拦截**：该形态不进入领域 writer，由工具 handler 只消费已知通道参数，故须按静默丢弃（而非拒绝）对待；其防护由领域 writer 的字段闭集承担，是否已在某入口拦截按 `01 §7.2` 由读取时的观察取得，本节不陈述其当前状态。该层校验只覆盖**嵌套必填与形状**；**顶层 `required` 不在此层强制**，缺顶层必填参数仍进入 handler 并返回带 `gaps`/`follow_up` 的 `invalid_request` 信封。该层校验先于 `execute` 执行，故进入该层判定的违规**以宿主 `ToolArgsError` 形态返回，不承载共同 envelope**（LDVH CLI 确定性服务规范 §8 的 `operation_key`/`outcome`/`gaps`/`follow_up` 均不出现）——这是宿主能力带来的既定差异：优先利用宿主的参数校验，而不在本文再自建一层等价校验；受影响的是「请求形状错误」这一类，其修正依据由工具参数表本身承载；守卫通道 `ctx.tools.guard(guard)` 注册单调守卫（任何 guard 可拒不可放行，guard 在 tools/pre-execute 之后求值），执行链全序为 pre-policy → guards → around-dispatch → post-policy → 内容终结 → 通知；实际注册以装载后注册状态检查为准。领域操作的输入语义约束由 LDVH CLI 确定性服务规范及各领域来源定义（承接 LDVH CLI 确定性服务规范 §5.1 分派），权限配置遵循 §5.1 manifest 权限声明，Code 实践与测试规范实现并测试；注册成功不证明操作可调用、授权成立或实际可用。

### 5.3 引导面

最小规则引导（内容锚点由 01 §10.4 定义）经两种机制注入：

- 会话冷启动引导入口：经 `system-prompt/assemble` waterfall（(assembly, context, next) 三参、返回组装权威）注入 01 §10.4 定义的最小规则引导 00 锚点；注入以 agent 身份为前提，无 agent 上下文不注入。**在宿主提供注入预算计量 API 之前**，预算控制由 LDVH 侧承担——引导文本单一权威源，体量以固定常量承载，变更走受控提交；
- 行动前引导入口：经 `agent/pre-step` waterfall 事件（载荷 {agent, messages, turn, step, signal}）在来源定义的触发时机提供事实候选与既有行动结构路由。

注入内容由 01 定义、注入形式与预算由 10 定义；内容须单一权威来源、逐字节一致、不复制规则正文、不成为第二规则源。

**预算的承载形态**（Human 决定）：上述两个入口的体量预算**各自独立承载、互不扣减**——冷启动引导入口是系统固定内容（管辖判定与最小规则引导），不随业务变化，其体量由固定常量给出；行动前引导入口的召回候选随语料增长，其体量可由**已登记的量化档位**承载。档位制须同时满足两项要求：

1. **档位集合本身是受控常量**——集合成员与其对应字节数写入实现并由受控提交变更，不得在运行期接受任意数值；运行期只能在已登记档位中选择（可核对性：审计可确定当时生效的是哪一版）；
2. **选择权属 Human**——生效档位由 Human 在插件配置中指定，该选择落在 profile 配置而非受控提交；故「档位集合的变更」走受控提交，「生效档位的变化」由 Human 决定，二者不混同。

未登记档位不得静默回落默认值，须如实报错（`02 §9.1` 不得静默截断的精神）。提高档位上限属本节 §9.1 第 2 项事项，须 Human 决定。

**分节次序、名额归属与裁剪（注入候选的形式规则）**：行动前引导入口交付的召回候选按**分节次序**分节呈现，各类型有名额上限。分节次序属注入形式：其具体次序以实现具名常量承载、单一来源、变更走受控提交，改动属 §9.1 第 2 项「改变引导面注入形式或预算边界」的 Human Gate 事项；本文不写次序值。各类型名额的归属与裁剪规则由各类型规范的召回判据表给出（`02 §12.4`）；名额数值的承载形态与归属由 `34 §11` 承接，本文不重复其规则。**裁剪规则**：各类型名额之和超注入预算或条数上限时，按分节次序从后往前裁剪；截断来源与被裁类型的披露由 `34 §12` 承接。

**注入与卡面中指称事实对象时的书写形态**：按 `02 §9.3` 的指称形态呈现。本条只承接「宿主注入与卡片呈现须使用该形态」这一要求，**不复制**该节的形态定义与机械承接边界；该节第 6 条已如实声明其在工具响应投影面与契约测试面的承接状态与保证边界，本文不重复声称该面已获机械拦截。注入侧的**名额与预算**仍归本条上文与 `34 §11`／`34 §12` 承接，与指称形态是两件事：形态不改变注入体量的计量口径。

**索引段与候选段的分属**：行动前引导入口交付的内容含两类，计量口径不同，不得混同——**候选段**是按当次动作取得的、带命中依据与稳定引用的少量条目，受条数上限与字节预算约束；**索引段**是事实源中事实规范（Norm）一类对象的 F1 标识**常驻枚举**，不受条数上限约束、不占候选的名额。事实规范（Norm）的常驻目录以独立一行注入（自己的行、自己的标签、自己的措辞；**不进召回块、不占召回预算、不在系统提示段内**；每回合注入一行，内容稳定也照注——「每回合在场」是本机制的目的；只保留同批次内去重，防插件多实例重复注入）；代价是每回合多一行进对话记录，靠宿主的上下文压缩兜底。目录是按类型枚举的，不是候选，故不沿用候选区的「命中不等于适用」，且须自证「未判定适用」（分层归属、依据与四项强制约束见 `34 §8.4`；F0–F4 与 L0–L4 不能混用，见 `02 §9.1`，此处一律称 F1）。**目录自带体量上限**（实现具名常量），放不下时截断并披露条数与全量入口，不得静默丢弃。召回侧不并列同一份目录（避免第二权威）。各类型交付的字段以其类型来源为准：Norm 带标题、方向键与**两句定位摘录**（`23 §10`，摘录是正文两句的派生视图、不构成第二规则源；所有规范均须将这些内容注入上下文）。摘录不改变索引段的计量口径——它仍不是候选语汇（不带命中依据、排序权重，见 `34 §8.4` 第 1 项），但增加索引段的字节占用，故 Norm 条目分两个部件计量与装填：标题行必出、摘录可降级；降级与「机械导不出」须分别如实披露，不得静默（细则与不变量见 `34 §8.4` 预算段，本文不复制）。**经验（Pitfall）不属常驻索引段**，改为一行按需入口（active 总数 + `ldvh_pitfall_list`），属索引语汇、同样不占候选名额，三项强制要求见 `34 §8.4`。**开发规范（`specs/`）不属本索引段**——其载体发现与读取由 `01 §10` 的 L0–L4 通道与 `ldvh_read_specification_candidates` 承担，引导面已按 `01 §10.4` 注入规范锚点，不在注入面另发一份标题清单。**预算次序**：同一字节预算内按「事实规范 → 其余词法候选」分配（经验不占索引份额）；该次序确定谁先被满足，不产生新的预算边界，总额仍由上文档位承载。份额分母只保证索引不越份额，不保证候选区不被索引增长挤压（该代价如实登记，档位选择权仍在 Human，上文档位制第 2 项）。**索引段让位须留痕迹**——预算不足时逐段让位并写明未展开的类型与条数，不得静默消失（`02 §9.1` 不得静默截断）；让位次序与注入次序相反（经验先让、事实规范后让）。索引段的段头、段尾、让位阈值与份额分母以实现具名常量承载、单一来源、变更走受控提交；**改动本条属 §9.1 第 2 项**。本条只界定承载形态与计量口径，各类型的召回时机与默认候选状态由 `02 §9.2` 与 20–29 各类型规范承接，本文不重复。

### 5.4 事件面

行动与结束事件接入下列事件，用于承载既有行动结构路由、执行状态更新、交还处理和资源清理：`agent/created`（serial，载荷 `{agent, source, signal?}`；`source` 承载会话创建入口语义）、`agent/pre-step`（waterfall）、`agent/turn-stopping`（serial，载荷 `{agent, turn, signal}`）、`system-prompt/assemble`（waterfall）、`session/event`（emit，`(session, event)`；`turn/end` 为会话事件类型、经其载荷分发）。工具生命周期观察可经官方 `tools/change`（emit）挂载；该接入点是否已被消费，按 `01 §7.2` 由读取时的观察取得，**本节不陈述其当前状态**。中断恢复共同语义由检查与辅助机制规范定义，10 只承接宿主接入时机。

### 5.5 交互面

DSH 结构化问询入口为 `ctx.userQuestions.ask(request)`（validation + scoped answerer waterfall；调用者限制 CALLER_NOT_LIVE/DELEGATED_CALLER——子代理直接问人被拒），承载 Human Gate 决策提请、计划审查与验收交还。行动授权不设独立宿主 API：由 DSH 审批通道（user-approval，ApprovalPolicy 'ask'|'never'，与沙箱三档固化联动）与 00 §3 Human 决定权组合承载。语义区分：宿主存在 `ctx.authorization` 服务，但它是凭证获取流程注册表（credential-obtaining flows），不是行动授权通道，本规范不将其作为授权入口消费。**在授权承接规范定义授权包结构之前，不得主张授权包结构已定稿。**

### 5.6 管辖登记接入

管辖范围规范是登记位置、Schema、路径、权限目标、三态判定、写入与迁移规则的唯一权威；LDVH CLI、Git Gate、Skill 与 Web 统一消费其结果。10 只承接宿主接入：接入点为宿主提供的 `ctx.get('dshHomePath')` 服务，即 08 §5.1 所要求的「DSH 正式用户配置根解析接口」在 DSH 侧的具体形态——该接口由宿主解析用户配置根并经 DSH_HOME 环境变量与 `~/.dsh` 默认根确定实际目录，**不得由插件硬编码 `~/.dsh`、`%APPDATA%` 或任何单一系统路径**（本节行文中的 `~/.dsh` 仅为说明默认根来源，不是插件的解析方式；08 §5.1 的禁令针对插件侧实现，宿主自身以该默认根兜底不属违反）。配置根为该解析结果下的 `ldvh/governed-projects.yaml`，跨工作区读写经该路径；宿主 ACL/沙箱结果映射为管辖范围规范的 `available` 或 `unavailable`。10 不复制管辖范围规范的 Schema 或写入规程；**本规范不以 Electron userData 级 API 作为接入点**。

## 6. 机械守护部署

- **运行时不变量**：经 DSH 正式不变量注册器 `ctx.invariants.register(packageName, installer)` 在装载完成、受控写入前和会话交还前执行来源已定义的断言（InvariantInstaller = (ctx, fail) => void|Promise，fail 抛 InvariantError code='INVARIANT' 带 packageName 归因；官方包 permission-presets 以 inject: ['invariants'] 同法消费）；不替代 00 §2.7 三层防线。
- **文件观察策略**：经 DSH 守卫式写保护承载：读观察经 `fs/observed` 事件；写守卫经 `writeText(target, content, {kind:'replaceIfVersion', version})` 与 `editText(..., {version})` 版本守卫，配合 `fs/write-intent` 与 `fs/edit-intent` waterfall 挂载 LDVH 策略；`fs-observation-policy` 提供 FS_NOT_OBSERVED / FS_STALE_VERSION 拒绝语义，版本或指纹不一致时拒绝写入。对管辖范围规范的登记载体，10 只核验宿主满足管辖范围规范已定义的跨平台原子写入、冲突拒绝与回读要求并向实现暴露结果，不复制其写入算法。
- **Git Gate 部署**：commit-msg 钩子安装到由项目 Git 根解析所得的 Git common-dir `hooks/commit-msg`，不得简单假设 `<worktree>/.git/hooks/`；主 worktree 与 linked worktree 共享同一 common-dir，独立 clone 分别部署。安装前检查既有钩子，非 LDVH 资产一律 `conflict` 且零写入，不覆盖 Human 自建钩子；部署后须确认 `managed` 状态（归属、路径、内容与版本一致，且文件带执行位——git 对无执行位的钩子直接忽略），未确认不得声称已就绪；事件检查用受控提交与机械守护规范定义的同一 validator。
- **管辖项目安装事务**：Human 在设置页选择的目录必须是实际 Git 根。点击“安装”后，登记项目、创建或校验项目内 `ldvh-base/`、安装或更新当前版本 Git Hook 均为必需步骤而非选项；任一步失败都不得报告管辖已就绪。设置页不提供单独的“卸载”操作；“取消管辖”自动卸载 LDVH 托管 Hook并移除登记，但永久保留 `ldvh-base/` 与其中事实对象。每次 DSH 启动对全部登记项目执行一次只读状态检查；检查或巡检发现 Hook 过时或事实源缺失时，安装事务须能修复可修复状态（Hook `absent/outdated` 或事实源 `absent/incomplete`）；`conflict` 或 `unavailable` 属不可修复状态，事务不得对其执行写入。**上述状态的呈现形态与交互区分由 Web 呈现与交互规范 §6.5 定义，本文不复述**；10 只定义事务的步骤、状态闭集与失败处置。版本不一致只报告并等待 Human 点击安装/更新，不静默修改。
- **设置页写入与权限降级**：**设置页写入不得以 `ctx.approval.request()` 或模型工具的 `sandbox_permissions` 作为一次性升权来源**；普通插件 Host 自动安装**不得假设存在**插件安装专用的授权通道，其权限边界以宿主实际提供的 OS 文件权限为准。安装先完成只读预检，确认所有目标、Hook 所有权和回滚边界后再写入；OS 拒绝写入时 fail-closed、回滚本次可安全回滚的变化，不使用 `sudo` 或管理员 PowerShell。此时可提供同一 LDVH CLI 语义的精确平台命令和 DSH Desktop 正式“打开终端”入口作为降级，macOS/Windows 仅在路径引用和终端载体上不同；用户执行后必须回到设置页重新“检查”，终端退出码不单独证明就绪。
- **权限预设与沙箱分层**：`workspace-write`（默认，工作区路径内读写与执行，无需 Human 授权）/ `danger-full-access`（跨工作区与系统级，需 Human 授权）只约束 Agent 工具调用；分层语义归 00 §2.7 的 fail-closed 授权边界与 00 §3.1 的 Human 授权决定，10 只定义宿主接入方式，AI 不得把聊天工具授权转移给设置页按钮，也不得自行扩权。

**宿主缝的消费义务（条件式）**：上列宿主缝是**可用手段**，其存在**不证明 LDVH 已受其保护**。对每一道宿主缝：**在 LDVH 实际消费该缝之前**，不得据本文主张相应防护已部署、已生效或已 fail-closed；不得把「宿主提供该缝」「提交通过」「工具调用成功」引为守卫、不变量或版本屏障已执行的证据；也不得以「宿主已有该机制」代替 LDVH 自身的消费与验证。

**逐缝的消费要求与证明边界**：

| 宿主缝 | LDVH 须做什么才算消费 | 未消费时不得主张什么 |
|---|---|---|
| `ctx.tools.register` | 经该入口注册操作并接受参数校验 | 不得主张操作已注册可用 |
| `ctx.tools.guard` | 经该入口注册单调守卫；守卫**只能拒绝、不得放行**，拒绝以返回原因表达 | 不得主张执行链对 LDVH 操作有守卫约束 |
| `ctx.invariants.register` | 经该入口部署运行时不变量断言；违规经其 `fail` 通道报告，而非返回值 | 不得主张本节所述检查时机对 LDVH 操作生效 |
| `fs/observed` 读观察 | **两半都要**：读一侧把实际读到的观察**记录并发出**（不得凭空构造版本）；写一侧经 `fs/write-intent`／`fs/edit-intent` 挂载版本守卫，且**只对已观察过的目标**主张版本 | 不得主张版本或指纹屏障已生效；仅挂一个不记录内容的监听器不算消费 |
| `ctx.userQuestions.ask` | 经该入口承载 Human Gate 决策提请；须存在**实际调用点**（提请经该入口发出），未获肯定答复时 fail-closed | 不得主张问询已经该入口；仅取到可调用引用而无人调用不算消费 |

各缝的**实际消费现状**按 01 §7.2 由读取时的观察与实现核对取得，本节不陈述其当前状态。消费补齐后须纳入 §8 的验证对象；**未纳入验证对象的防护不得被声称为已部署**。

**逐缝消费的可报告要求**：消费不是一次性声明，而是**可被读取时观察到的注册结果**。对每一道缝，实现须使「是否已消费」可由装载期诊断或等价的可读结果判定，且**未消费的缝必须与已消费的缝一同如实报告**——只报告已消费项、静默省略未消费项，等同于主张该缝已生效，为本节所禁止。判定结果只证明「该缝已注册」，不证明防护有效（见 §8「宿主缝消费」行的可证明范围）。

| 引导面注入 | 会话冷启动或行动前触发时核对（依据注入内容观察与来源比对）：注入内容与 01 §10.4 单一权威来源一致且未超 LDVH 侧常量预算。仅证明当次注入范围；不证明内容正确或 AI 已遵守 | 注入核对 | 超预算或漂移时暂停受影响注入并修复 |
| Git Gate 部署 | 部署后或宣称就绪前核对（依据`.git/hooks` 观察与 managed 确认记录）：钩子存在、`managed` 状态已确认（已安装、路径正确、版本匹配、文件带执行位）。仅证明部署状态成立；不证明实际阻断有效或绕过不存在 | 部署状态检查 | 未确认时不得声称就绪，暂停受控提交声明 |
| 权限预设 | 装载或扩权请求时核对（依据manifest 权限声明与宿主沙箱观察）：权限边界已声明且沙箱分层与声明一致。仅证明当次声明与分层一致；不证明越权被实际拒绝 | 权限一致性检查 | 不一致时拒绝执行并按 00 §4.7 交还 |
| 编排接入点消费 | 装载后或宣称编排能力生效前核对（依据注册调用结果、监听器挂载结果与装载期诊断）：§5.7 所列接入点中，被声称已消费的每一个均已按该接入点的形态被消费（注册型：经入口注册并取得 disposer；观察型：监听器已挂载且其事件可被观察）；未消费项如实报告为未消费。仅证明当次该接入点已被消费；**不证明**相应编排环节有效、结果正确或主控责任已履行 | 逐接入点消费状态检查（§5.7） | 未消费的接入点不得主张其能力；如实报告并保留为缺口 |
| 宿主缝消费 | 装载后或宣称某缝防护生效前核对（依据注册调用结果与装载期诊断）：§6 所列缝中，被声称已消费的每一道均已**经该缝入口实际注册**并取得 disposer；未消费的缝如实报告为未消费。仅证明当次该缝已被消费；**不证明**相应防护已生效、已 fail-closed 或覆盖全部受影响操作 | 逐缝注册状态检查（§6 逐缝消费要求表） | 未消费的缝不得主张其防护；按 §6 报告未消费并保留为缺口 |

机械结果与语义判断互不替代。manifest 合规、注册成功或部署确认只能证明各自机械范围；本章不能单独证明能力可用、授权覆盖、行动允许或核心价值成立，未执行和不可用范围保留为 gaps。发布动作的验证由本项目事实规范「dsh-ldvh 发布规范」承载。

## 9. Human Gate

本文不新增 00 之外的 Human Gate。

### 9.1 领域增量事项

以下事项是 00 §3.2 在 DSH 接入与受保护文档登记领域的具体化：

1. 改变插件身份定位、权限声明范围；
2. 改变引导面注入形式或预算边界；
3. 改变 Git Gate 部署形态或沙箱分层接入方式；
4. 新增、删除或修改受保护文档及其登记位置（00 §3.3 与本文 §7.6）。

分发渠道、版本号双轨制与版本声明点定义的变更，其 Human Gate 由本项目事实规范「dsh-ldvh 发布规范」承载；本规范 §7.6 路径登记的变更仍按第 4 项执行。

### 9.2 决定边界

Human 决定只证明决定及其作用范围，不替代 manifest 检查、注册核对或部署确认。

## 10. 必停情形

本规范不新增根停止类型。

### 10.1 领域触发与影响范围

出现以下任一情况时，按 00 §4.7 暂停受影响的最小接入或部署声明范围：

1. 工具注册失败且无来源允许的分流；
2. Git Gate `managed` 状态无法确认；
3. 引导面注入超出预算或与单一权威来源不一致；
4. 受保护文档的版本声明点出现不一致（漂移）——发布侧按本项目事实规范「dsh-ldvh 发布规范」的发布门禁处理；本规范 §7.6 的登记项漂移时按 §7.6 的 Human Gate 处置；
5. 准备声明环境接入完成，但 manifest、工具注册、Git Gate 或引导面未全部确认。

### 10.2 暂停期间允许动作

暂停期间只允许不越过停止边界的规则定位、只读核对、能力验证、修复与分流准备，不得继续受影响接入或部署声明。

### 10.3 恢复与再次触发

恢复须与触发原因对应，且只覆盖当前依据支持的范围；同一停止条件恢复后再次触发时按 00 §4.7 进入 Human Gate。

## 11. 反过度设计红线

1. 不写通用 Hook 抽象——只针对 DSH 一个宿主；
2. 不写跨平台适配——DSH 之外的平台移植由社区完成；
3. 不写非 DSH 环境接入（Human 决定）；
4. 不写 MCP 网关（Human 决定）；
5. 工具注册仅经 DSH 正式注册入口一个缝接入，不建独立注册表；
6. 权限与沙箱直接使用 DSH 宿主机制，不建独立权限系统。
