# Friction-摩擦账本

## 1. 价值判断

Friction 解决「应该修但还没修」的系统性阻碍无账可查的问题：CI 每次要 8 分钟、某个流程每次都要手动绕一步、某类提示总是重复打断——这些摩擦单次可忍、累积伤效率，若只存在于会话抱怨或个人记忆，就没有「攒到什么程度该修」的判断依据，也没有「修完之后效率真的改善了吗」的度量基础（00 §1 痛点 4 的效率维度）。Friction 以改进账本承载：open 是待修的账，resolved 是已销的账，deferred 是缓议的账；消费端是迭代决策输入（攒够触发修订）与 dogfood 度量（摩擦数与解决率）。普通文件不能无损承载：无受控写入、无状态闭集、无度量投影。Pitfall 是规避导向（踩过的坑怎么避开），Friction 是改进导向（躲不掉的阻碍怎么修掉）——「CI 慢」不是教训，是待修的账；Spark 是未定问题的悬置（Friction 入账时归因与修益已判，不是悬而未决）。

主要支撑 V3 边界识别（入账三条件是 Friction 与闲聊抱怨的边界）、V5 据实判断（度量与迭代决策以账本为据）、V6 工作接续（跨会话累积摩擦证据）与 V8 持续积累（解决率随时间可查）；HV3 入档闭环节点可验（创建与销账可回读）与 HV4 积累效用直观可见（摩擦解决曲线是「越做越顺」的直接证据）。

Friction 对象存在、处于 open 或形成账本积累，均不能单独证明阻碍真实、值得修或修复有效——账目的价值须在迭代决策与度量的真实消费中核对。Friction 是账本不是规则来源：入账不产生修订义务，何时修、修不修始终是迭代决策。

2. `work-model-foundation`：02 §9 「摩擦」入口用词（本类型命名依据）与工作模型中摩擦记录的职责位置。

本文不依赖外部语法或行业标准定义 Friction 语义；行业 friction log 实践与 v4 problem-ledger（`docs/v4-problem-ledger.md`）只作设计输入，不取得规范效力。设计定稿依据记忆系统设计文档 §5.13（Human 批准 2026-09-10）。发生冲突或权威关系无法确认时，按 00 §7.2 暂停受影响范围并完成对齐。

## 3. 职责边界

### 3.1 本文负责

1. Friction 类型的对象边界（改进账本的构成、入账三条件、查重、明确不属于本类型的内容）；
2. Friction 的身份与载体（多例、平铺单文件、`ldvh-base/frictions/friction-<uid>.md`）；
3. Friction 的字段契约（frontmatter 薄索引闭集、正文段与必答问题、字段间不变量）；
4. Friction 的状态闭集（open/resolved/deferred）与转换；
5. Friction 的关系契约（informs 指向解药）；
6. Friction 的召回与消费点（迭代决策输入、度量、Web 呈现）；
7. Friction 的受控操作（创建、补充级更新、状态流转）。

### 3.2 本文不负责

1. 空闲评审代理、摩擦检测阈值与本地 buffer 的宿主机制（记忆系统与编排接入承载——本类型只定义账本本身的契约，出生路径的触发器不在本文范围）；
2. 归因判据的仓库路由执行（框架摩擦进 LDVH 仓库、项目摩擦进项目事实源——这是管辖登记与使用纪律，不是类型契约）；
3. 度量的计算与呈现口径（10 号 Web 与 SG-3 度量消费方承载，本文只保证 open/resolved 状态可机械统计）；
4. Pitfall/Spark/ADR/WorkCase 类型语义与讨论系统的分流流程。

### 3.3 相邻规范分工与唯一权威

03 是公共字段与受控读写契约的唯一权威；06 是事实源与受控提交的唯一权威；20/21/22/23/24/25 分别是既有六类型的唯一权威；12 是讨论系统（Friction 攒够触发议题时走讨论）的唯一权威。本文只定义 Friction 类型自身的边界、字段、状态、关系与消费点，不复制相邻规范的规则。

## 4. 适用范围

### 4.1 适用对象

1. 管辖项目与 LDVH 仓库中的多例 Friction 对象（各自事实源的 `ldvh-base/frictions/`——按归因判据落仓库，见 §7）；
2. Friction 的现象、入账依据与处置记录。

### 4.2 适用场景

本规范用于 Friction 的创建（空闲评审捕捉或即时检测经提议确认）、查重与攒账、补充级更新（重复出现计数、现象补充）、状态流转（销账/缓议/重新激活）与消费（迭代决策、度量、Web 呈现）。

### 4.3 明确排除与证明边界

明确排除：业务上的坑（走 Pitfall——规避导向）；未定问题（走 Spark——入账时归因与修益已判是 Friction 的前提，悬而未决不满足）；已定决策（走 ADR）；一次性卡顿与情绪化抱怨（入账三条件不过——可重新发现的偶发、无归因、修了无感的都不记）。

与 Pitfall 的操作性判别锚：**看消除途径**——途径是「改系统本身」（改 API、改流程、改工具配置）记 Friction；途径是「系统不变时避免损失」（防御写法、绕开、检查清单）记 Pitfall。同一根源可以两者并存不互斥：阻碍本身入 Friction 账（等修），过程中的防御经验入 Pitfall（立即可用）——三层闭环（账本→决定→教训）本就是并存分工，不是择一而入。判例：「某 API 设计导致每次调用都要写防御代码」——API 该改是 Friction 账，防御写法是 Pitfall，两者同根各自入账。Friction 对象存在或状态为 open，不能单独证明阻碍真实、值得修或修复有效——这些须由迭代决策与度量的真实消费核对。

## 5. 类型定位与价值

Friction 是改进通道的账本层，与三层闭环分工：账本层（Friction：待修阻碍的记录与度量）→ 决定层（攒够触发 Spark 议题或直接 ADR，走讨论系统）→ 教训层（修复过程中踩的新坑走 Pitfall）。它不替代任何既有类型，是独立的框架/项目改进通道。

按 03 §5.2 准入六问：跨行动保留——摩擦证据必须跨会话累积（重复出现是入账条件本身）；独立身份与状态——账目有 open/resolved/deferred 与销账追溯，需要独立生命周期；普通文件不能无损承载——无受控写入、无状态闭集、无度量投影（解决率统计需要状态可机械枚举）；消费价值服务迭代决策（AI+Human）与度量双轨；维护成本——入账摩擦必须低于摩擦本身（轻字段+轻正文是本类型的形态约束，见 §18 红线）；类型定义来源——本规范。v4 实证：open Spark 中的 10 条 P1/P2 摩擦项证明该类内容真实存在且寄居悬置层是错位（v4 problem-ledger §1 各主题的 open 项）。

## 6. 对象边界

### 6.1 什么构成一个对象

一个 Friction 对象 = 一笔可独立处置的待修阻碍账：现象（phenomenon）+ 入账依据（三条件核对）+ 影响评级（impact）+ 归因（attribution，可后补）+ 处置（条件出现）。账目必须可独立销账（修复后单独 resolved）、可独立统计（度量聚合的单位）、可独立缓议（deferred 单独挂起）。

### 6.2 查重与攒账

同一摩擦重复出现是**攒账不是重复入账**：创建前查重（对照 open 与 deferred 的 title/phenomenon 语义比对，AI 语义判断），已存在的同题摩擦走补充级更新（重复出现计数与证据补充并入既有账目）。入账三条件中的「重复出现」本身吸收了查重义务——查重结论必须记录在创建提案中。

### 6.3 明确不属于本类型

修了会更好的判断不成立的内容（纯偏好、审美之争）；已由规范源吸收为规则的改进（规则由规范源承载，Friction 可作为触发证据但销账后不承担规则）；单次调试卡顿（未收敛为系统性阻碍）。

## 7. 身份与载体

| 项 | 定案 |
|---|---|
| `fact_type_key` | `friction`（类型短名，03 §6.1 值域） |
| 载体 | 平铺单文件：YAML frontmatter（机器权威）+ markdown 正文；**两类摩擦都进各自事实源的 `ldvh-base/frictions/friction-<uid>.md`**——框架摩擦记 LDVH 仓库的 `ldvh-base/frictions/`（LDVH 自身是被管辖项目，其事实源就是 ldvh-base），项目摩擦记该项目 `ldvh-base/frictions/`；不存在事实源外的 frictions 目录（03 §6.2 唯一权威载体、06 §5 事实源边界） |
| 权威位置 | 每个事实源内的 `frictions/`；目录基数校验，文件名编码 UID |
| 公共字段 | `object_uid`（UUIDv4，Code 生成）、`created_at`（Code 填写）、`change_log`（Code 托管流水） |

归因判据的判别锚：**按根源归属而非发生地**——摩擦的根源在 LDVH 的规范/工具/流程（无论在哪个项目遇到，含 SG-4 项目里遇到的框架摩擦）记框架账；根源在该项目自身的 CI/构建/依赖/流程记项目账。「归因定仓库」指账目落在哪个仓库的事实源，不是在事实源外另建目录。

创建与变更权：创建与状态流转（销账/缓议/重新激活）都必须经 Human 决定（账目的入册与处置是迭代决定）；补充级更新走受控更新（change_log 留痕）。

## 8. 字段契约

frontmatter 闭集（账本类型必须轻——入账摩擦高于摩擦本身时没人记账；分析性长文本住正文）：

| 字段 | 类型 | 必填性 | 语义 | 约束 |
|---|---|---|---|---|
| `fact_type_key` | string | 必填 | `friction` | 唯一合法值 |
| `object_uid` | UUIDv4 | 必填 | Code 生成 | 创建时落定，永不改变 |
| `title` | string | 必填 | 摩擦短标题 | ≤ 30 字；识别阻碍，不复制现象全文 |
| `status` | string | 必填 | `open` / `resolved` / `deferred` | 初态必为 `open` |
| `phenomenon` | string | 必填 | 现象单句陈述 | 非结论（「CI 平均 8 分钟」不是「CI 太慢」）；正文「现象」段逐字包含 |
| `attribution` | string | 条件 | 归因陈述 | 指向哪个子系统/规范/流程；入账时归因未定可省略，后补走补充级更新；出现时非空 |
| `impact` | string | 必填 | 影响评级 | 闭集 `light` / `medium` / `heavy`——机械消费方在本文 §12 定义（F1 投影含 impact、度量按状态×影响聚合）与设计定稿的出生路径「重大即显」通道（heavy 跳过攒熟直接提议）；非装饰字段 |
| `serves` | string | 条件 | 服务的 SG-n | 框架摩擦挂 SG-3；项目摩擦按所属项目目标；goal.md 无该锚点时省略 |
| `relations` | array | 条件 | `informs` 指向解药（见 §9） | 仅 resolved 时出现 |
| `created_at` | RFC3339 | 必填 | Code 填写 | AI 不得填写 |
| `change_log` | array | 条件 | 变更流水 | 首修后必有；每次恰好一条 |

正文固定结构（H1「# 标题」由 Code 从 title 生成、位于围栏后首行且恰好一个，正文自 H2 起；此处不直书 H1 字面以免与身份 H1 重复）：

```
## 现象            ← 摩擦的具体表现与重复出现证据（必答：摩擦是什么+重复出现的频次/证据）
## 入账依据        ← 三条件逐项核对（必答：为何算重复、归因到哪、修了会改善什么）
## 处置            ← 解药记录或推迟理由（条件出现——resolved/deferred 时；必答：怎么解的+解药指引，或为何暂缓+重启条件）
```

字段间不变量：`phenomenon` 载体内聚（正文现象段逐字包含）；`relations` 出现 ⇔ `status=resolved`；`attribution`/`serves` 出现时非空；未知字段不进入 canonical 对象，不得以空字段或占位代替判断。

## 9. 状态与生命周期

状态闭集三值：`open`（待修的账）→ `resolved`（已销的账——修复完成，informs 指向解药）/ `deferred`（缓议的账——明确暂缓但保留账面）。

### 9.1 状态语义与成立条件

| `status` | 语义 | 必须成立 |
|---|---|---|
| `open` | 阻碍待修，参与攒账与度量 | `relations` 不得出现 |
| `resolved` | 已修复销账；informs 指向解药对象 | `relations` 必含至少一条 `informs`（1..n）；正文「处置」段必在 |
| `deferred` | 明确暂缓；保留账面，可重新激活 | 正文「处置」段必在（推迟理由+重启条件）；`relations` 不得出现 |

### 9.2 状态转换

- `open → resolved`（Human Gate：销账）：必须带 `informs` 关系指向解药对象（ADR/WorkCase 的 object_uid——**关系目标限事实对象**；commit 级修复记录在处置段以自然语言+commit hash 承载，不进结构化关系，因 03 §7.2 关系目标为 object_uid）；
- `open → deferred`（Human Gate：缓议）：推迟理由与重启条件记处置段；
- `deferred → open`（可逆：重新激活——同一笔账，无须新对象；激活时**不带关系**）；
- `deferred → resolved`（事后解决——**informs 关系在该次销账流转中写入**，与从 open 直达 resolved 相同）；
- `resolved` 终态不重开（销错的账按 05 事实更正修正；阻碍复现时创建新账目并在正文接续前账 uid）。

`informs` 关系伴随 resolved 状态存在：只在销账流转的那次受控更新中写入（无论从 open 还是 deferred 直达），resolved 是终态故关系一经写入即稳定；缓议与激活的中间流转不带关系。处置段内容随状态流转**可重写**——deferred 期的推迟理由在后续销账时被解药记录替换（处置段是状态伴随段，change_log 留痕其演变）；关系目标后续退役（如 ADR 被 superseded）不删除边——按 03 §7.2 第 5 条保留边并如实报告（解药曾是该对象是历史事实）。

所有状态转换经 Human 决定；补充级更新（计数/现象/归因补充）不改变状态。

### 9.3 补充级更新

重复出现计数与证据补充（现象段扩展）、归因补充（`attribution` 后补）、表述澄清走 03 §9.5 受控更新，change_log 留痕。机械边界：更新后的 `status` 不变（状态变化走流转）；`phenomenon` 的更新是现象陈述的精化（载体内聚保持），现象语义的实质变化（不同阻碍）走新账目。其余段的语义不变性是 AI 审核义务。

## 10. 来源与证据

摩擦来源是实际工作流中的重复体验：空闲评审代理的捕捉、即时检测、或 Human 直接提出——三路都只产出提案，Human 确认后入账。入账三条件（全中才记，防膨胀红线）：**重复出现**（≥3 次或证据等价的重复性）+ **可归因**（能指向具体子系统/规范/流程——暂未归因清楚可入账后补）+ **修了会更好**（修复有可感知的改善预期）。单次卡顿与情绪化抱怨过门即拒。证据以自然语言与频次记录承载于正文现象段；无 urls 字段（摩擦是内部体验，不依赖外部证据——与 24/22 的外部调研/决策证据形态不同）。

## 11. 关系契约

`relations` 只使用 03 §7.2 公共形状。本类型关系闭集：

| `relation_key` | 方向 | 目标类型 | 基数 | 语义 | 约束 |
|---|---|---|---|---|---|
| `informs` | 本 Friction → 解药对象 | ADR / WorkCase | 1..n | 本摩擦由目标的修复/决策解决 | 仅 `resolved` 时出现；目标必须存在且可解析（ADR 任状态；WorkCase 建议已关闭——机械只查可解析，关闭状态是审核义务） |

不建反向边（解药侧不复制账目引用）；不建 Friction 间的关联（同一摩擦的重复走补充级更新并入同一账，不建 F-F 关系）；commit 级解药不进关系（见 §9.2）。关系变更必须使用对象当前指纹绑定的完整更新入口，写后精确回读。

## 12. 召回与消费

| 消费点 | 时机 | 消费内容 |
|---|---|---|
| 迭代决策输入 | 规范/工具修订判断时（01 §11） | open 账目聚合——攒到什么程度触发修订（按归因/impact 聚合），有账可依；**聚合规则与「攒够」判据是消费方义务**（迭代决策的判断方法），本文只保证 open 账目可按归因与 impact 机械枚举（F1/F2 投影） |
| dogfood 度量 | SG-3 度量周期 | open/resolved/deferred 计数与解决率——摩擦解决曲线是 HV4 的直接证据 |
| 空闲评审攒账 | 摩擦检测周期 | open+deferred 账本查重——新捕捉对既有账目 |
| Web 账本呈现 | 蓝图渲染（10 号） | open 账目列表与解决曲线投影 |

召回分层（03 §8）：F1 枚举（title + status + impact + attribution）；F2 按状态/归因/影响级别的候选卡；F3/F4 按需展开。默认候选含 open 与 deferred（deferred 是活账——重新激活的候选源）；resolved 仅精确引用或历史追溯时展开。账目被召回不等于值得修——迭代优先级判断是消费方语义工作。

## 13. 受控操作

- **创建**：AI 产出提案对象（含查重结论+三条件核对+完整字段），Human 确认后经受控创建入口落盘——入口两路：空闲评审提议（buffer 攒熟或重大即显）与即时检测/直接提出。机械校验：字段闭集合法、title ≤ 30 字、phenomenon 单句、impact 闭集、载体结构（H2 固定序 + resolved/deferred 时「处置」段必在——创建即终态不允许，初态强制 open）、载体内聚（phenomenon 逐字）。创建后精确回读。
- **补充级更新**：03 §9.5 受控更新；CAS 以完整文件为单位；每次恰好一条 change_log；status 不变（机械比对，变了拒绝——走流转）。
- **状态流转**：Human Gate；AI 先精确读取 F3 核对流转依据；resolved 校验 informs 目标可解析；Code 检查闭集、字段、关系、CAS 与回读。
- **删除**：不存在删除操作。三类状态的账目都随 `frictions/` 保留。

## 14. 类型特有验证与类型退出

### 14.1 类型特有验证

- 查重结果记录：创建提案必含查重结论（同题已存在 → 走补充级更新攒账）；
- 载体内聚：phenomenon 在正文现象段逐字出现；
- 状态-关系不变量：open/deferred 不得带关系；resolved 必有 1..n 条 informs 且目标可解析；
- 处置段条件：resolved/deferred 必有非空处置段（必答问题见 §8）；
- 补充边界：更新的 status 与 CAS 基线一致（防状态变化伪装补充）。

### 14.2 存量对象迁移

无存量。v4 problem-ledger 的 open P1/P2 项（10 条）若仍适用，作为框架摩擦在新账本重新入账（v4 存量零迁移，ADR `adr-1aad60bc`）。

### 14.3 类型退出

若 Human 决定取消 Friction 类型，须按 03 §10 处理：处理 open/deferred 账目的转移承接、入向/出向关系与稳定引用，登记变化（01 §8.2）与受影响引用同步，走受控提交。退出属 00 §4.2 根决定。

## 15. 验证与证据边界

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 载体结构 | 创建、更新或精确读取时 | H1 恰好一个且与 title 一致、正文自 H2 起、H2 固定序完整、各段非空；resolved/deferred 时处置段必在 | 当前载体与本文 §8 | 机械（结构解析） | 当次载体结构合法性 | 拒绝创建/更新；修复后重走 |

| 补充边界 | 更新时 | status 与 CAS 基线逐字段一致 | 更新前后 frontmatter 对照 | 机械（字段比对） | 当次更新的补充性质 | 拒绝；状态变化走流转 |

机械结果与语义判断互不替代。本章不能单独证明阻碍值得修或修复有效——这些由迭代决策与度量的真实消费核对；未实现与不可用范围保留为 gaps。

## 16. Human Gate

本文不新增 00 之外的 Human Gate。领域增量事项（00 §4.2 在 Friction 领域的具体化）：

1. Friction 的创建（账目入册——含空闲评审与即时/直接两入口的记录确认）；
2. Friction 的状态流转（销账/缓议/重新激活——迭代决定）；
3. Friction 类型本身的取消或合并。

### 16.1 决定边界

Human 决定只证明决定及其作用范围，不替代查重判断、载体校验、度量计算或流转机械校验。本文成为当前规则源成员时的 01 §8.1 登记与受影响引用同步，按 01 §8.2 的登记变化义务随本次规范新建一并执行。

## 17. Stop Conditions

本文不新增根停止类型。领域触发与最小影响范围：

1. 创建时发现同题 open/deferred 账目已存在（重复入账风险）——未完成查重结论前不创建；
2. 三条件核对不齐（重复性无证据/归因全无/修益判断为空）却准备创建；
3. phenomenon 为空或不可读、impact 闭集外值；
4. 准备以补充级更新改变 status 或现象语义（补充边界违例）；
5. resolved 流转缺 informs 关系或目标不可解析；deferred 流转缺处置段；
6. AI 未经 Human 确认直接创建或流转（授权缺失）；
7. 度量消费时状态与账本不一致（把 deferred 计入待修或 resolved 计入 open）。

暂停期间只允许不越过停止边界的证据补取、引用修复、授权补走与条件核实。恢复须与触发原因逐项对应；同一停止条件恢复后再次触发的，按 00 §7.3 进入 Human Gate。

## 18. 反过度设计红线

1. 不设 severity/priority/tags 类无消费方装饰字段——`impact` 例外的消费方全部在规范内有锚：本文 §12 的 F1 投影与度量聚合、设计定稿出生路径的「重大即显」通道；宿主层的攒账阈值是**额外**消费者而非字段存在的前提（阈值规则不由本文定义，也不因阈值未定义而反证字段冗余）。此区分不构成其他类型放松同类红线的先例；
2. 正文只设三段——账本类型必须轻，入账摩擦高于摩擦本身时没人记账；分析深度由入账依据段的三条件核对承载，不扩张段数；
3. 不设 urls 字段——摩擦是内部体验，不依赖外部证据（与 Research/ADR 的证据形态不同）；
4. 不建 Friction 间关联边——同一摩擦的重复走补充级更新并入同一账，不建 F-F 关系网络；
5. 不为 deferred 建独立阈值或期限机制——重启条件由处置段自然语言承载，检测时机归空闲评审的宿主机制；
6. 不把入账变成修订义务——账本是证据不是工单系统，「修不修」永远是迭代决策，Friction 不自动触发任何行动。
