# Friction-摩擦账本

## 1. 价值判断

Friction 解决「应该修但还没修」的系统性阻碍无账可查的问题：CI 每次要 8 分钟、某个流程每次都要手动绕一步、某类提示总是重复打断——这些摩擦单次可忍、累积伤效率，若只存在于会话抱怨或个人记忆，就没有「攒到什么程度该修」的判断依据，也没有「修完之后效率真的改善了吗」的度量基础（00 §1「历史经验与教训，无法积累」与「无连续状态」）。Friction 以改进账本承载：open 是待修的账，resolved 是已销的账，voided 是记错了的账（**2026-10 修订：观察材料不在账本里**——「已看见但还没攒够」由 11 §12bis.1 的摩擦观察缓冲承载，攒够 N 次才晋升为一条 `open` 账；原 `observing` 状态已退出闭集）；消费端是迭代决策输入（攒够触发修订）与 dogfood 度量（摩擦数与解决率）。普通文件不能无损承载：无受控写入、无状态闭集、无度量投影。Pitfall 是规避导向（踩过的坑怎么避开），Friction 是改进导向（躲不掉的阻碍怎么修掉）——「CI 慢」不是教训，是待修的账；Spark 是未定问题的悬置（Friction 入账时归因与修益已判，不是悬而未决）。

主要支撑 V3 边界识别（入账三条件是 Friction 与闲聊抱怨的边界）、V5 据实判断（度量与迭代决策以账本为据）、V6 工作接续（跨会话累积摩擦证据）与 V8 持续积累（解决率随时间可查）；HV3 入档闭环节点可验（创建与销账可回读）与 HV4 积累效用直观可见（摩擦解决曲线是「越做越顺」的直接证据）。

Friction 对象存在、处于 open 或形成账本积累，均不能单独证明阻碍真实、值得修或修复有效——账目的价值须在迭代决策与度量的真实消费中核对。Friction 是账本不是规则来源：入账不产生修订义务，何时修、修不修始终是迭代决策。

## 3. 职责边界

### 3.1 本文负责

1. Friction 类型的对象边界（改进账本的构成、入账三条件、查重、明确不属于本类型的内容）；
2. Friction 的身份与载体（多例、平铺单文件、`ldvh-base/frictions/friction-<uid>.md`）；
3. Friction 的字段契约（frontmatter 薄索引闭集、正文段与必答问题、字段间不变量）；
4. Friction 的状态闭集（open/resolved/voided）与转换；
5. Friction 的关系契约（informs 指向解药）；
6. Friction 的召回与消费点（迭代决策输入、度量、Web 呈现）；
7. Friction 的受控操作（创建、补充级更新、状态流转）。

### 3.2 本文不负责

1. 摩擦发现的宿主机制——触发锚、子代理派生与上下文供给、自动动作边界、阈值承载、fail-closed 与待处置登记（**11 号宿主辅助任务规范 §9 摩擦发现承载**——本类型只定义账本本身的契约，出生路径的机制不在本文范围）。**阈值 N 由 11 §9 固定为 3，本文不内嵌也不定义**（见 §18 第 1 项）；
2. 归因判据的仓库路由执行（框架摩擦进 LDVH 仓库、项目摩擦进项目事实源——这是管辖登记与使用纪律，不是类型契约）；
3. 度量的计算与呈现口径（10 号 Web 与 SG-3 度量消费方承载，本文只保证 open/resolved/voided 三状态可机械统计，并保证 voided 可与其余二值区分以单独计入废弃率）；
4. Pitfall/Spark/ADR/WorkCase 类型语义与主控方案收敛的分流流程（04 §6.1）。

### 3.3 相邻规范分工与唯一权威

02 是公共字段与受控读写契约的唯一权威；09 是受控提交的唯一权威；20/21/22/23/24/25 分别是既有六类型的唯一权威；方案收敛已归主控本职（04 §6.1——Friction 攒够触发议题时由主控方案收敛分流）。本文只定义 Friction 类型自身的边界、字段、状态、关系与消费点，不复制相邻规范的规则。

## 4. 适用范围

### 4.1 适用对象

1. 管辖项目与 LDVH 仓库中的多例 Friction 对象（各自事实源的 `ldvh-base/frictions/`——按归因判据落仓库，见 §7）；
2. Friction 的现象、入账依据与处置记录。

### 4.2 适用场景

本规范用于 Friction 的创建（反思摩擦捕捉、即时检测或摩擦发现机械通道）、查重与攒账、补充级更新（重复出现计数、现象补充）、状态流转（销账、废弃、留观与激活）与消费（迭代决策、度量、Web 呈现）。

### 4.3 明确排除与证明边界

明确排除：业务上的坑（走 Pitfall——规避导向）；未定问题（走 Spark——入账时归因与修益已判是 Friction 的前提，悬而未决不满足）；已定决策（走 ADR）；一次性卡顿与情绪化抱怨（入账三条件不过——可重新发现的偶发、无归因、修了无感的都不记）。

与 Pitfall 的操作性判别锚：**看消除途径**——途径是「改系统本身」（改 API、改流程、改工具配置）记 Friction；途径是「系统不变时避免损失」（防御写法、绕开、检查清单）记 Pitfall。同一根源可以两者并存不互斥：阻碍本身入 Friction 账（等修），过程中的防御经验入 Pitfall（立即可用）——三层闭环（账本→决定→教训）本就是并存分工，不是择一而入。判例：「某 API 设计导致每次调用都要写防御代码」——API 该改是 Friction 账，防御写法是 Pitfall，两者同根各自入账。Friction 对象存在或状态为 open，不能单独证明阻碍真实、值得修或修复有效——这些须由迭代决策与度量的真实消费核对。

## 5. 类型定位与价值

Friction 是改进通道的账本层，与三层闭环分工：账本层（Friction：待修阻碍的记录与度量）→ 决定层（攒够触发 Spark 议题或直接 ADR，走主控方案收敛）→ 教训层（修复过程中踩的新坑走 Pitfall）。它不替代任何既有类型，是独立的框架/项目改进通道。

按 02 §6.2 准入六问：跨行动保留——摩擦证据必须跨会话累积（重复出现是入账条件本身）；独立身份与状态——账目有 open/resolved/voided 与销账追溯，需要独立生命周期；普通文件不能无损承载——无受控写入、无状态闭集、无度量投影（解决率统计需要状态可机械枚举）；消费价值服务迭代决策（AI+Human）与度量双轨；维护成本——入账摩擦必须低于摩擦本身（轻字段+轻正文是本类型的形态约束，见 §18 红线）；类型定义来源——本规范。v4 实证：open Spark 中的 10 条 P1/P2 摩擦项证明该类内容真实存在且寄居悬置层是错位（v4 problem-ledger §1 各主题的 open 项）。

## 6. 对象边界

### 6.1 什么构成一个对象

一个 Friction 对象 = 一笔可独立处置的待修阻碍账：现象（phenomenon）+ 入账依据（三条件核对）+ 影响评级（impact）+ 归因（attribution，可后补）+ 处置（条件出现）。账目必须可独立销账（修复后单独 resolved）、可独立统计（度量聚合的单位）。

**观察不在本类型的对象边界内（2026-10 修订，Human 决定）**：单次或少量观察既不是「待修阻碍账」，也不需要独立身份、状态与关系——它在满足三条件之前只是**观察材料**，由 11 §12bis 的摩擦观察缓冲承载（非事实对象，按管辖项目分载体、有容量与保留期）。本类型只承载**已达阈值、构成为待修阻碍**的账目。故本类型的**初态是 `open`**，不存在「观察态」。

### 6.2 查重与攒账

同一摩擦重复出现是**攒账不是重复入账**：创建前查重（对照既有 open 账目的 title/phenomenon 语义比对，AI 语义判断），已存在的同题摩擦走补充级更新（重复出现计数与证据补充并入既有账目）。入账三条件中的「重复出现」本身吸收了查重义务——查重结论必须记录在创建提案中。

**观察阶段的攒账不在本类型**：同一阻碍第 1、2 次出现时，其累积由摩擦观察缓冲按「同源条目」聚合（11 §12bis）；达阈值后**一次性**把全部观察证据写入新建的 `open` 账目正文。故本类型**没有**「跨状态累积」的语义——`occurrence` 记录的是该账目成立时**已确认的观察次数**，此后仅作补充级更新。

### 6.3 明确不属于本类型

修了会更好的判断不成立的内容（纯偏好、审美之争）；已由规范源吸收为规则的改进（规则由规范源承载，Friction 可作为触发证据但销账后不承担规则）；单次调试卡顿（未收敛为系统性阻碍）。

## 7. 身份与载体

| 项 | 定案 |
|---|---|
| `fact_type_key` | `friction`（类型短名，02 §7.1 值域） |
| 载体 | 平铺单文件：YAML frontmatter（机器权威）+ markdown 正文；**两类摩擦都进各自事实源的 `ldvh-base/frictions/friction-<uid>.md`**——框架摩擦记 LDVH 仓库的 `ldvh-base/frictions/`（LDVH 自身是被管辖项目，其事实源就是 ldvh-base），项目摩擦记该项目 `ldvh-base/frictions/`；不存在事实源外的 frictions 目录（02 §7.2 唯一权威载体、02 §5 事实源边界） |
| 权威位置 | 每个事实源内的 `frictions/`；目录基数校验，文件名编码 UID |
| 公共字段 | `object_uid`（UUIDv4，Code 生成）、`created_at`（Code 填写）、`change_log`（Code 托管流水） |

归因判据的判别锚：**按根源归属而非发生地**——摩擦的根源在 LDVH 的规范/工具/流程（无论在哪个项目遇到，含 SG-4 项目里遇到的框架摩擦）记框架账；根源在该项目自身的 CI/构建/依赖/流程记项目账。「归因定仓库」指账目落在哪个仓库的事实源，不是在事实源外另建目录。

创建与变更权（2026-10 修订，Human 决定：观察不进事实源）：分三条通道——

- **机械通道**（11 §9）：**只作用于观察缓冲，不写本类型**——识别到的观察写入摩擦观察缓冲条目（非事实对象，§3.2 第 1 项归 11 §12bis）；缓冲中**同源条目达阈值 N=3** 时，机械通道**晋升**为一条新的 `open` 账目（把全部同源观察证据一次性写入正文）。
- **Human Gate**：是否值得修与立项修复、销账、废弃、影响评级变更。
- **补充级更新**（走受控更新，change_log 留痕，不改变状态）。

机械通道**仅限「写观察条目」与「阈值晋升为 open」两类，不得扩张**（11 §9）。**创建 `observing` 与 `observing → open` 两条旧路径已随观察态退出闭集而删除**。

## 8. 字段契约

frontmatter 闭集（账本类型必须轻——入账摩擦高于摩擦本身时没人记账；分析性长文本住正文）：

| 字段 | 类型 | 必填性 | 语义 | 约束 |
|---|---|---|---|---|
| `fact_type_key` | string | 必填 | `friction` | 唯一合法值 |
| `object_uid` | UUIDv4 | 必填 | Code 生成 | 创建时落定，永不改变 |
| `title` | string | 必填 | 摩擦短标题 | ≤ 30 字；识别阻碍，不复制现象全文 |
| `status` | string | 必填 | `open` / `resolved` / `voided` | **初态必为 `open`**（2026-10 修订：观察态退出闭集，初态即待修态） |
| `phenomenon` | string | 必填 | 现象单句陈述 | 非结论（「CI 平均 8 分钟」不是「CI 太慢」）；正文「现象」段逐字包含 |
| `attribution` | string | 条件 | 归因陈述 | 指向哪个子系统/规范/流程；归因未定可省略，后补走补充级更新；出现时非空。**摩擦的根源常是「规范/工具/流程」本身而无对象身份**（如「CI 每次 8 分钟」的根源是构建流程），故本字段保留自由文本形态，不强制指向事实对象 |
| `attribution_ref` | object | 条件 | 归因对象的精确引用 | 值为 `{ object_uid: "<同项目某已存在事实对象的 object_uid>" }`（**对象形态**，与 02 §8.2 公共形状的引用承载一致；§11 relations 的 target 用同一承载形态）；出现时由 Code 机械核验 `object_uid` 可解析，不可解析即拒绝入账；**出现不强制**——未出现时归因的真实性属 AI 审核义务。消费方：§12 迭代决策输入的按归因机械聚合 |
| `occurrence` | object | 必填 | 重复出现的证据载体 | `{ count: integer ≥1, first_at: RFC3339, last_at: RFC3339 }`；创建时必带（初值为该账目成立时**已确认的观察次数**，`first_at`/`last_at` 取最早与最近一次观察时间）。**`count` 的语义（2026-10 修订）**：它记录「该阻碍被独立观察到的次数」，在晋升为 `open` 时由同源观察条目数写入，此后仅经受控更新作补充级递增；**它不再是跨状态阈值的输入源**（阈值判定已移到观察缓冲，11 §12bis）。**机械权威源**——正文现象段的频次叙述是人类可读投影，二者不一致时以本字段为准。**必填的例外**：`voided` 状态且来源为闭集收缩改判者可缺（见 §14.2） |
| `impact` | string | 必填 | 影响评级 | 闭集 `light` / `medium` / `heavy`——机械消费方在本文 §12 定义（F1 投影含 impact、度量按状态×影响聚合）与设计定稿的出生路径「重大即显」通道（heavy 跳过攒熟直接提议）；非装饰字段 |
| `disposition` | string | 条件 | **终态去向说明**（该账为何废弃） | **条件必填：`voided` 时必有**（`open`/`resolved` 时不得出现——`resolved` 的去向已由 `informs` 机械承载，另设字段会造出第二个来源）。与 SPARK 的 `disposition`（20 §8：终态去向）同名同义——跨类型扫读一致。**消费方**：列表卡的终态呈现（`TerminalFactPanel` 形态，与 Spark/Pitfall/Norm 的终态卡同款），使 Human 在列表页即可读到去向而不必进详情页。**与「处置」段的分工**：本字段是**薄索引**（一句话去向），处置段是**正文承载**（解药指引或废弃理由的完整展开）——二者不重复：前者供机械枚举与卡面直读，后者供阅读与追溯。**非装饰字段**（§18 第 1 条） |
| `relations` | array | 条件 | `informs` 指向解药（见 §9） | 仅 resolved 时出现 |
| `created_at` | RFC3339 | 必填 | Code 填写 | AI 不得填写 |
| `change_log` | array | 条件 | 变更流水 | 首修后必有；每次恰好一条 |

正文固定结构（H1「# 标题」由 Code 从 title 生成、位于围栏后首行且恰好一个，正文自 H2 起；此处不直书 H1 字面以免与身份 H1 重复）：

```
## 现象            ← 摩擦的具体表现与重复出现证据（必答：摩擦是什么+重复出现的频次/证据+首次观察来源）
## 入账依据        ← 三条件逐项核对（必答：为何算重复、归因到哪、修了会改善什么）
## 处置            ← 解药记录或废弃理由（条件出现——resolved/voided 时；必答：怎么解的+解药指引，或为何废弃）。open 时本段必不在
```

字段间不变量：`phenomenon` 载体内聚（正文现象段逐字包含）；`relations` 出现 ⇔ `status=resolved`；`disposition` 出现 ⇔ `status=voided`（废弃的去向说明，与 `relations` 互斥：一个说「为何废弃」、一个说「如何修复」）；`attribution` 出现时非空；`occurrence` 载体内聚（正文现象段须含首次观察来源）。**阈值相关性（2026-10 修订）**：本类型**不再存在**以 `count` 为输入的阈值判定——`count ≥ N` 的晋升判定发生在观察缓冲（11 §12bis），晋升时一次写入；故不存在「`count ≥ 3` 但状态未推进」的可疑态，**`human_return_at` 字段随放回留观流转一并删除**。**不设基于 `change_log` 的静态判据**——`change_log` 只有 Code 托管的时间与自由文本摘要，无决定来源的结构化标记（02 §7.1）。`resolved`/`voided` 时 `occurrence` 逐字冻结、停止计数；未知字段不进入 canonical 对象，不得以空字段或占位代替判断。

（2026-10 修订：删除 `serves` 字段。理由：§12 四个消费点无一使用它，§18 第 1 条禁止无消费方装饰字段；归属信息已由 `attribution` 承载，且归属判断主观、无后果产出。与 WorkCase 的 `serves` 不同——后者承载授权钉扎、goal 修订级联与达成证据链，不可类比。）

## 9. 状态与生命周期

状态闭集三值：`open`（待修的账）/ `resolved`（已销的账——修复完成，informs 指向解药）/ `voided`（**已废弃的账——记错了的账目**）。

**（2026-10 修订，Human 决定：观察不进事实源）** 原第四值 `observing`（留观）**已退出本类型的状态闭集**——「已看见但尚未够格」的观察不再作为事实对象存在，改由 **11 §12bis 的摩擦观察缓冲**承载（非事实对象、按管辖项目分载体、有容量上限与保留期、有唯一消费者）。本类型只承载**已达阈值**的待修阻碍账，故其**初态即 `open`**。这次收缩不是「换名字」：缓冲条目没有 `object_uid`、不进事实源、不参与 F0–F4 召回、不承载关系、不取得任何授权或结论效力（02 §6.1 中间产物三条边界）。

### 9.1 状态语义与成立条件

| `status` | 语义 | 必须成立 |
|---|---|---|
| `open` | 阻碍待修，参与攒账与度量 | `relations` 不得出现；正文「处置」段必**不**在 |
| `resolved` | 已修复销账；informs 指向解药对象 | `relations` 必含至少一条 `informs`（1..n）；正文「处置」段必在 |
| `voided` | **已废弃**；载体保留可追溯，但自此不参与查重范围、不参与度量、不参与迭代决策输入 | `disposition` 必填（一句话废弃去向，非空）；正文「处置」段必在，须写废弃理由（归因错误／现象描述失真／根本不是系统性阻碍三者之一——该分类属 Human 判断，非机械闭集）；`relations` 不得出现 |

### 9.2 状态转换

- `open → resolved`（Human Gate：销账）：必须带 `informs` 关系指向解药对象（ADR/WorkCase 的 object_uid——**关系目标限事实对象**，02 §8.2）。**commit 例外（Human 裁定 2026-10-09；同日二次修订）**：解药为 commit 级修复且**该修复没有任何对象身份**时，`informs` 的 `target` 直接取 `{commit: "<40 位 hex>"}`（形状依 02 §8.1），使这类账**可销**——否则「销账必带 informs」与「`target` 只使用 object_uid」两句互斥，使直提路径修复的摩擦永久无法销账。该例外**不放松**「有事实对象时必须指向对象」：只在无对象可指时启用，不得用于回避本可指向的对象（该判断属审核义务，机械层只核 hash 真实可解析）；
- `open → voided`（Human Gate：废弃）：正文处置段须写废弃理由。

**（2026-10 修订，Human 决定）以下四条流转随观察态退出闭集而删除**：
- ~~`observing → open`~~（阈值流转）——改为「观察缓冲达阈值 → 晋升为新的 `open` 账目」，由 11 §12bis 定义，**不经本类型的状态流转入口**；
- ~~`open → observing`~~（放回留观）——Human 决定：**不存在放回**。`open` 的账要么修（→ `resolved`），要么判为记错（→ `voided`）；「暂时不值得修」不是本类型的状态，它只意味着**不去动它**，账目保持 `open` 并在人工判断时继续留着。原先该流转靠 `human_return_at` 保护「Human 的决定不被机械翻回」，**该保护已无必要**——机械通道不再按 `count` 翻状态（阈值判定移到缓冲，且晋升只发生在缓冲侧，不作用于既有 `open` 账目）；
- ~~`observing → resolved`~~（事后解决）——观察材料不构成账目，无从销账；
- ~~`observing → voided`~~——同上。

- `resolved` 终态不重开（销错的账按 05 事实更正修正；阻碍复现时创建新账目并在正文接续前账 uid）。

`informs` 关系伴随 resolved 状态存在：只在销账流转的那次受控更新中写入，resolved 是终态故关系一经写入即稳定。处置段内容随状态流转**可重写**（处置段是状态伴随段，change_log 留痕其演变）；关系目标后续退役（如 ADR 被 superseded）不删除边——按 02 §8.2 第 5 条保留边并如实报告（解药曾是该对象是历史事实）。

状态转换分两类（2026-10 修订后）：**机械通道只作用于观察缓冲与「缓冲晋升为 open」**（11 §12bis），**不作用于任何已存在的账目状态**——既有账目的状态变更全部属 **Human Gate**（销账 `open → resolved`、废弃 `→ voided`）。机械通道的边界不得扩张；超出即按 §17 必停处理。补充级更新（计数/现象/归因补充）不改变状态，非终态时执行。

### 9.3 补充级更新

重复出现计数（`occurrence.count` 递增 1、`last_at` 更新为本次观察时间）与证据补充（现象段扩展）、归因补充（`attribution`/`attribution_ref` 后补）、表述澄清走 02 §10.5 受控更新，change_log 留痕。**计数的递增与现象段扩展须在同一次更新内完成**——二者是同一事实（本次观察）的两个承载面，`count` 是机械权威源（§8）。**2026-10 修订后的语义**：补充级更新作用于**已成立的 `open` 账目**，记录的是「该账目成立之后又观察到同一阻碍」；它**不再驱动任何状态流转**（阈值判定在观察缓冲侧）。**仅非终态（`open`）时执行**；`resolved`/`voided` 为终态，计数冻结。机械边界：更新后的 `status` 不变（状态变化走流转）；`phenomenon` 的更新是现象陈述的精化（载体内聚保持），现象语义的实质变化（不同阻碍）走新账目。其余段的语义不变性是 AI 审核义务。

## 10. 来源与证据

摩擦来源是实际工作流中的重复体验：反思摩擦代理的捕捉、即时检测、或 Human 直接提出。**（2026-10 修订，Human 决定）观察与账目分两层**：

- **观察层**（反思摩擦代理的机械通道，11 §9）：查重后把本次观察**写入摩擦观察缓冲占条目**（11 §12bis，非事实对象），无须事前确认并保留事后否决权。缓冲按管辖项目分载体、按「同源」聚合；**同源条目达阈值 N=3 时晋升为一条 `open` 账目**。
- **账目层**：Human 直接提出与即时检测两路产出提案，经 Human 确认后入账；缓冲晋升是机械通道在本类型的**唯一写入路径**。

**「创建不要求已达阈值」这条已随观察态退出闭集而失效**——现在**恰恰相反**：`open` 账目的成立**以达阈值为前提**（缓冲中同源条目 ≥ 3），未达阈值的观察留在缓冲，不进事实源。机械通道仅限「写观察条目」与「阈值晋升」两类，不得据此扩张出第三类触发。入账三条件（全中才记，防膨胀红线）：**重复出现**（≥3 次或证据等价的重复性）+ **可归因**（能指向具体子系统/规范/流程——归因未定可入账后补，但须在入账依据段显式声明「归因暂缺，原因 X」，不得默默省略）+ **修了会更好**（修复有可感知的改善预期）。**三条件的第一项对账本层是硬前置（2026-10 修订，方向反转）**：`open` 账目的成立**以达阈值为前提**（同一阻碍的同源观察条目 ≥ N）。原「第一项仅适用于 open 及以上、observing 的创建不受 ≥3 次约束」的表述**已作废**——观察态退出闭集后，未达阈值的观察留在缓冲，根本不进事实源。单次卡顿与情绪化抱怨过门即拒。频次的**机械权威源为 `occurrence` 字段**，正文现象段是其人类可读投影（含首次观察来源）；二者不一致时以 `occurrence` 为准。无 urls 字段（摩擦是内部体验，不依赖外部证据——与 24/22 的外部调研/决策证据形态不同）。

## 11. 关系契约

`relations` 只使用 02 §8.2 公共形状。本类型关系闭集：

| `relation_key` | 方向 | 目标类型 | 基数 | 语义 | 约束 |
|---|---|---|---|---|---|
| `informs` | 本 Friction → 解药对象 | ADR / WorkCase（走 `target.object_uid`）**＋ `target.commit` 形态（例外，见右）** | 1..n | 本摩擦由目标的修复/决策解决 | 仅 `resolved` 时出现；目标必须存在且可解析（ADR 任状态；WorkCase 建议已关闭——机械只查可解析，关闭状态是审核义务）。**commit 例外（Human 裁定 2026-10-09）**：解药是 commit 级修复且**无对应 ADR/WorkCase 事实对象**时（修复当时走的直提路径、未对象化），`informs` 的 `target` 直接取 `{commit: "<40 位 hex>"}` 承载该修复载体——**形状依 02 §8.1「`commit` 形态」**（公共形状由 02 承接，本表只声明本类型采用它），本类型不自设 target 形态。**仅在解药本身没有对象身份时**用（解药是 ADR/WorkCase 时必须指向那个对象），不得用 commit 替代可指的对象（该判断属审核义务；机械层只核 hash 真实可解析）。**语义**：一笔摩擦若只是**消费**了某次修复（如某工单在缺陷修好后正常走完流程），那是**证据**而非**解药**——记在处置段，不得指向那个消费者对象当解药 |

不建反向边（解药侧不复制账目引用）；不建 Friction 间的关联（同一摩擦的重复走补充级更新并入同一账，不建 F-F 关系）；commit 级解药**一般**不进 `target`——**唯一例外**是「解药本身没有对象身份」时的销账，届时 `target` 直接取 `{commit: hash}`（02 §8.1 commit 形态；见 §9.2 与本表 informs 行），**不与 `evidence_locator` 混用**（后者附加在 object_uid target 上）。关系变更必须使用对象当前指纹绑定的完整更新入口，写后精确回读。

**本类型 `informs` 的特指语义（与 24 号同名不同义）**：本类型的 `informs` 是**回溯性销账声明**——「该账已由目标对象的修复或决策解决」，属已发生事实的登记。`24` 号 Research 亦使用 `informs` 键，两表同为「源→目标」同形边，但**因果流向与时态**不同：本条的因果是「目标（解药）→ 已解决该账」，24 的因果是「调研 → 影响目标」，本条指已经发生的解决，24 指尚未发生的影响。两者不得互相替代或互相推断；按 02 §8.2 第 3 项，关系 key 的闭集与语义由各类型来源分别定义，02 不建立通用关系家族。

**非 relations 字段的引用形态（锚点型）**：`attribution_ref`（§8）不走 relations，其引用形态与本类型 relations 的 target 采用同一承载——**必须是对象形态** `{ object_uid: "<uuid>" }`，不得是裸字符串（2026-10 订正：字段表原写 string 且「形态依 §11」悬空，致载体与契约分歧、读取层静默丢弃——按对象形态定案）；该对象可指任意同项目事实对象（含 Friction 自身）。

## 12. 召回与消费

| 消费点 | 时机 | 消费内容 |
|---|---|---|
| 迭代决策输入 | 规范/工具修订判断时（01 §11） | open 账目聚合——攒到什么程度触发修订（按归因/impact 聚合），有账可依；**聚合规则与「攒够」判据是消费方义务**（迭代决策的判断方法），本文只保证 open 账目可按归因与 impact 机械枚举（F1/F2 投影） |
| dogfood 度量 | SG-3 度量周期 | open/resolved 计数与解决率——摩擦解决曲线是 HV4 的直接证据；**`voided` 单独计废弃率**（自动入账门是否过松的观测量），不进解决率分母。**观察缓冲不进账目度量**（其条目不构成账目，11 §12bis）：缓冲可另计「待晋升条目数」作为入账门松紧的旁证，但**不得与账目计数相加或混报** |
| 反思摩擦攒账 | 摩擦检测周期 | 查重对象有两层（2026-10 修订）：**① open 账目**（防同一阻碍已成立为账目后重复入账）；**② 观察缓冲的同源条目**（防同一阻碍在缓冲里被拆成互不相干的多条，使聚合永远到不了 N）。两层都要查，**只查其一均构成漏查重**（11 §9 第 1 项、§12bis） |
| Web 账本呈现 | Web 呈现（07 号；细则见 `plugin/web/docs/10`） | open 账目列表与解决曲线投影 |

召回分层（02 §9.1）：F1 枚举（title + status + impact + attribution）；F2 按状态/归因/影响级别的候选卡；F3/F4 按需展开。**默认候选只含 `open`**（2026-10 修订：观察态已退出闭集，账本里不再有「攒够待修的候选源」这一状态）；resolved 仅精确引用或历史追溯时展开，`voided` 不进默认候选。**观察缓冲不在任何召回层里**（02 §6.1：中间产物不进 F0–F4）——需要读它的执行体由 11 §12bis 指名，不经本节的召回路径。账目被召回不等于值得修——迭代优先级判断是消费方语义工作。

## 13. 受控操作

- **创建**：AI 产出提案对象（含查重结论+三条件核对+完整字段），经受控创建入口落盘——**两个创建入口**（与 §7 的「三条通道」是两个口径：通道描述授权来源，入口描述写入路径）：**机械通道入口**（11 §9 摩擦发现机制自动创建，记录确认转为「机械依据留痕」）与 **Human 入口**（反思摩擦提议或重大即显、即时检测、Human 直接提出，经 Human 确认后落盘）。机械校验：字段闭集合法、title ≤ 30 字、phenomenon 单句、impact 闭集、`occurrence` 必带、不得带 `disposition`、载体结构（H2 固定序 + resolved/voided 时「处置」段必在——**创建不得进入 resolved 或 voided，初态强制 `open`**）、载体内聚（phenomenon 逐字）。创建后精确回读。
- **补充级更新**：02 §10.5 受控更新；CAS 以完整文件为单位；每次恰好一条 change_log；status 不变（机械比对，变了拒绝——走流转）。
- **状态流转**：Human Gate；AI 先精确读取 F3 核对流转依据；resolved 校验 informs 目标可解析；Code 检查**目标状态**属当前闭集、字段、关系、CAS 与回读。**源状态可属已收缩的历史取值**——闭集收缩后的存量处置（如 §14.2 的 `deferred` → `voided`）由本节承载：闭集校验只施加于目标状态，历史源状态不因不在现闭集内而被拒绝；该放宽**仅适用于闭集收缩的存量处置**，不适用于新产生的流转。
- **终态事实更正**（`correct`；Human 决定 2026-10-09 建立）：**适用于 `resolved` 与 `voided` 两个终态**——`open` 的内容修正走补充级更新或状态流转，本入口不得承载（否则等于把更正伪装成状态转换，02 §10.5）。**存在理由**：§9.2 要求「销错的账按 05 事实更正修正」，而本类型此前只有补充级更新（机械拒绝改 status）与状态流转（终态不重开）两个通道——**销错的终态账无路可改**，该要求形同虚设。可改范围：**正文（含处置段）与 `relations`**，外加**已退出类型闭集的 frontmatter 字段的显式删除**——恰是销账时写错的两处（02:386 事实更正与关系变更是不同动作，本入口覆盖两者，校验中分别核对）。**删除动作（2026-10，Human 裁定；因删除 `serves` 而建立；2026-11 与 2026-10 两次扩围）**：`frontmatter_removals` 只允许**删除**三类字段——① 已从 §8 闭集移除的字段（首个用例 `serves`）；② **其存在违反 §8 条件约束的字段**（2026-11 扩围，首个用例：§14.2 豁免 `occurrence` 的 `voided` 对象被误加该字段——豁免的意思是「本不该有」，故其存在即违规，须有受控清除途径）；③ **其目标对象已退役或即将退役的锚点字段**（2026-10 扩围，首个用例：`attribution_ref` 指向 `observing` 载体，而该状态随闭集收缩退出、其载体经 Human 决定删除——见下段）。**不得删除其它字段**，不得新增或改值——新增/改值等于把终态更正变成受控更新。删除是**显式声明**而非隐式克隆：不声明则该字段逐字继承，声明「删除一个本就不存在的字段」计入 no-op。首个用例是 `serves`（§8 于 2026-10 删除）；当时的存量中，除 1 份 `resolved` 终态外其余均为非终态，经受控更新删除即可，**该 `resolved` 终态无法经受控更新触及**，本入口是其唯一受控清除途径——若无此通道，闭集收缩会在终态对象上留下不可清除的残留字段（本次实测：bf73fad4 的 `serves: SG-3` 即是）。**第三类删除的存在理由（2026-10；因果链须一并读）**：本条上方「悬空锚点的可达性约束」已登记该死结——`attribution_ref` 的核验在**任何写入之前**触发，故一旦指向的目标对象消失，该载体**此后无法经 `correct` 作任何正文更正**，而 `correct` 本身按本款不得改值。原文给出的两条出路（「由 `update` 补正」「走状态流转」）在**终态载体**上都不成立：`update` 对终态只读（§9.3），状态流转在 `resolved` 上不重开（§9.2）。于是「目标将退役」这一情形没有任何受控清除途径——闭集收缩会在终态对象上留下**必然悬空**的锚点（本次实测：`abf557e1` 的 `attribution_ref` 指向的 `5d5862c9` 即随观察态退出闭集而删除）。

故本款补上该途径，且**只补这一个缺口**：允许删除的是「**指向已退役或将退役目标的锚点字段**」，不是「任意不想要的锚点」。**机械判据**：该字段是锚点型（§8 的 `attribution_ref`），且其目标 `object_uid` **在写入选定时刻不可解析**——即目标确实已不存在；**「将退役」由 Human 在授权记录中言明**，机械层只核「此刻不可解析」与「该字段确为锚点型」两项。**不得据此删除目标仍可解析的锚点**（那会使「归因缺失」被伪装成「目标已退役」，是数据伪造）。**边界**：与前两类同一纪律——可删的是「字段之无」，不是「字段的值」；**不设「改指向到另一个对象」的通道**（那是改值，属受控更新，终态不受理）。

**边界**：本动作不构成「correct 可改 frontmatter」的先例——可改的是「已不在闭集里的字段之无」，不是「字段的值」。**逐字不变**：`status`、`title`、`phenomenon`、`impact`、`attribution`、`attribution_ref`、`occurrence`、`created_at`（`change_log` 由 Code 追加一条新条目）。**必填**：`human_authorization`（Human 的授权记录：谁／何时／覆盖什么）——与 21 号 WorkCase 的 `correct` 同规格，缺之 fail-closed。**机械校验分两支**：**`resolved` 支**——`resolved` 状态前置；`informs` 条数 **≥ 1（无例外**——`informs` 是 resolved 的必备关系，commit locator 只是该条目**附加**的证据定位，不替代 `informs` 本身）且每条 `target.object_uid` 可解析（ADR/WorkCase）；**`voided` 支**——`voided` 状态前置；`relations` 必须为空（`informs` 校验不适用，因已废弃的账目无解药）；若某条带 `evidence_locator.commit`，该 hash 另须在仓中真实可解析（02 §8.1）；CAS 与回读同其它动作；**no-op 拒绝**（正文、relations 与 `frontmatter_removals` 均无实际变更即拒绝，不追加声称更正过的 change_log，02 §10.5）。**边界**：更正的**正当性**属 Human 判断与独立审核（**是否**该改）；机械层只保证「只改了正文与 relations、终态判定逐字未变、目标真实可解析」。本动作**不使 `resolved` 可重开**——改完仍是 resolved，且须以本条 `change_log` 留痕。**与 21 号 WorkCase `correct` 的形态差异（勿读作同规格）**：21 的 correct **不接收任何 frontmatter 字段**（`next` 是落盘对象的克隆、调用方无法触及），只改正文——因为 WorkCase 的 `result`／`reviews` 等字段由关闭动作写入、更正不得触碰；本动作**接收 `relations_after`**，因为 Friction 的 `relations`（`informs`）恰是销账动作写入的产物，销账写错时若不能改，则 §9.2「销错的账可改」对本类型仍是空话；本动作亦**接收 `frontmatter_removals`**（仅限已退出闭集的字段），而 21 号不接收——WorkCase 无闭集收缩发生，且其字段由 Gate 1/关闭动作写入。
**对称的补填动作（`frontmatter_additions`；2026-11 建立）**：闭集**扩张**时（新必填字段进入 §8，如 `occurrence`），既有终态对象无法经受控更新触及（§9.2 终态只读），`correct` 是其唯一受控补填途径——与 `frontmatter_removals` 恰成对称：删除处理「字段已不在闭集」，补填处理「字段新进入闭集」。**约束**：① 只允许补填**新进入闭集的字段**，不得用于改已有字段的值或补填本就在闭集里的字段（后者属受控更新）；② 补填的值**必须可由既有载体据实推得**，不得编造——不可据实推得时不得补填，该对象缺字段的事实如实保留；③ 每次补填须带 Human 授权记录并逐字入 `change_log` 摘要；④ 该动作**不构成「correct 可改 frontmatter 值」的先例**——可补的是「字段之无」，不是「字段的值」，与 `frontmatter_removals` 同一纪律。**首个用例**：`occurrence`（§8 于 2026-11 新增必填）；当时的存量中，除 1 份 `resolved` 终态（`bf73fad4`）外其余均可经受控更新补填，该终态无法触及，本通道是其唯一受控补填途径（该对象 2026-10 亦曾因 `serves` 删除成为 `frontmatter_removals` 的首个用例——同一对象两次撞上同一缺口，是该通道存在的实证）。**共同点**：均须 Human 授权记录（且逐字写入 `change_log` 摘要）、均不使终态可重开、均逐字继承终态判定、均做写后回读、均拒绝 no-op。**悬空锚点的可达性约束（2026-10 复核发现 4）**：`attribution_ref` 出现时由 Code 机械核验「`object_uid` 可解析为同项目某已存在事实对象」，核验在**任何写入之前**，对 `create`／`update`／`correct` 三入口一视同仁（§14.1）。由此有一个必须明写的后果：**若某载体已落盘的 `attribution_ref` 指向了一个不再存在的对象（目标被更正文删改或项目迁移），该载体此后无法经 `correct` 作任何正文更正**——核验在 `no-op` 判定之前触发，于是「改正文」与「修锚点」两个动作都被同一条核验拦下，而 `correct` 本身按上款**不得改值**。这是 fail-closed 的自洽结果（宁可拒绝一次合法更正，也不让悬空归因混入机械聚合，§12），不是可用性缺口：可走的路是 ① 由 `update` 补正 `attribution_ref`（`observing`／`open` 适用——它是补充级更新，不是终态更正）；② 终态载体确认归因确已失效时走状态流转而非正文更正。**此处如实记录该约束，是为了不让它在下次成为隐性回归面**：读者若发现「一条终态账改不动正文」，答案在这里，而不必从插桩点位置反推。
**授权记录的自报边界（同 21 §14 的免责，不得省写）**：`human_authorization` 是**自报文本**——它被机械写入 `change_log` 摘要，但**其存在与内容不证明 Human 真的作过该授权**；机械层只保证「授权记录被提供并逐字留痕」。与 21 号一致，不因本类型而放宽。
- **删除**：不存在删除操作。三类状态的账目都随 `frictions/` 保留（`voided` 亦保留载体以可追溯）。

**唯一的删除例外（2026-10，Human 决定）**：观察材料不在本类型，故 `observing` 载体**不属于本类型的账目**。闭集收缩时已存在的 `observing` 载体（本次实测 78 份）经 Human 决定**全部删除**、观察重新收集——这是**闭集收缩的存量处置**（§14.2 承载），不是「删除账目」通道的开放；`open`/`resolved`/`voided` 三类账目仍无删除操作。

## 14. 类型特有验证与类型退出

### 14.1 类型特有验证

## 17. 必停情形

本文不新增根停止类型。领域触发与最小影响范围：

1. 创建时发现同题 open 账目已存在（重复入账风险）——未完成查重结论前不创建（**本项同样约束机械通道**；观察缓冲侧的查重是同题条目归属判定，见 11 §12bis）；
2. 三条件核对不齐（重复性无证据／**无 `attribution` 且无 `attribution_ref` 且入账依据段未说明归因为何暂缺**／修益判断为空）却准备创建；
3. phenomenon 为空或不可读、impact 闭集外值；
4. 准备以补充级更新改变 status 或现象语义（补充边界违例）；
5. resolved 流转缺 informs 关系或目标不可解析；voided 流转缺处置段或带非空 relations；
6. 机械通道的语义查重被判定为误判（把不同阻碍当作同题而错误递增 `occurrence.count`），却准备据该 `count` 继续阈值判定或流转——**须先按原 `count` 复核并更正**（误判的递增须撤销，该次观察的处置如实登记）。**披露**：「被判定为误判」的判定本身无受控载体（与下项同属自觉约束，非机械约束）；其后果仅为**禁止性主张**（不得据该 `count` 主张阈值判定可靠），不制造能力假象；
7. AI 未经 Human 决定、亦不属 §7 机械通道授权范围，而直接创建或流转（授权缺失）。**机械通道内的创建与阈值触发流转不构成本项**——其授权来自 11 §9，但每次写入必须在受控入口留下可回读的机械依据（`occurrence` 计数、查重结论、归因解析结果）；**可机械判定的机械依据只有 `occurrence` 字段**；「查重结论」与「归因解析结果」当前无受控载体（§10 只要求创建提案含查重结论，而提案不在受控载体上），故本项的后半句在当前载体下属**自觉约束而非机械约束**，如实登记为缺口。
8. 度量消费时状态与账本不一致（把 resolved、voided 计入 open；或把观察缓冲条目当作账目计入待修累计——**缓冲条目不是账目，不进任何账目度量**，见 11 §12bis）；

暂停期间只允许不越过停止边界的证据补取、引用修复、授权补走与条件核实。恢复须与触发原因逐项对应；同一停止条件恢复后再次触发的，按 00 §5.7 的恢复与再次触发进入 Human Gate。

## 18. 反过度设计红线

1. 不设 severity/priority/tags 类无消费方装饰字段——`impact` 例外的消费方全部在规范内有锚：本文 §12 的 F1 投影与度量聚合、设计定稿出生路径的「重大即显」通道；攒账阈值是**额外**消费者而非字段存在的前提（阈值规则不由本文定义，也不因阈值在本文未定义而反证字段冗余；阈值 N 由 11 §9 固定为 3，本文只作消费者）。此区分不构成其他类型放松同类红线的先例；
2. 正文只设三段——账本类型必须轻，入账摩擦高于摩擦本身时没人记账；分析深度由入账依据段的三条件核对承载，不扩张段数；
3. 不设 urls 字段——摩擦是内部体验，不依赖外部证据（与 Research/ADR 的证据形态不同）；
4. 不建 Friction 间关联边——同一摩擦的重复走补充级更新并入同一账，不建 F-F 关系网络；
5. 不为观察缓冲建期限机制或基于日历的门槛——不得出现「到某日自动该修」这类隐性承诺。检测时机归摩擦发现的宿主机制（11 §9），**阈值规则不由本文定义**（见第 1 条）。**证据累积计数只作入账与召回的依据**：缓冲中同源条目达 N=3 时晋升为 `open`，该晋升是账面分类推进，**不得据此产生排期、优先级或立项**；是否修订仍由第 6 条与 §12 迭代决策判断。
6. 不把入账变成修订义务——账本是证据不是工单系统，「修不修」永远是迭代决策，Friction 不自动触发任何行动。
