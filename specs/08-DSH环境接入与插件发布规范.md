## 1. 价值判断

本文只服务"DSH 插件接入"这一个目标：

- **V1 快速定位**：以插件 manifest 为入口定位身份、能力、版本与权限。
- **V3 边界识别**：经工具注册缝、权限声明与沙箱分层明确操作边界与授权边界。
- **V4 稳定推进**：引导面与事件面为插件提供稳定的宿主注入时机与执行时机。
- **V5 据实判断**：版本号/README/CHANGELOG 使版本声明与变更据实可查，不作超前宣传。
- **HV2 授权执行受控可续**：授权流与文件观察策略使越权可机械拒绝，运行时不变量使状态可核查。
- **HV3 入档闭环节点可验**：CHANGELOG 版本条目、manifest 版本字段与 README 版本行三者构成版本声明点（§6.5），发布节点可回读核对。

manifest 存在、工具注册成功、页面加载或发布完成，均不单独证明以上价值成立。

## 4. DSH 插件身份与接入

### 4.1 插件 manifest

manifest（`package.json` 或 DSH 市场规定的文件）为插件身份入口，至少声明：名称、版本、入口路径、权限声明、DSH 插件市场字段（描述/分类/图标/作者）。manifest 是身份与权限的机械来源；AI 不得修改权限声明字段，修改须经 Human Gate。

### 4.2 工具注册缝

05 定义的 Helper 操作经 `ctx.tools.register` 注册为 DSH 原生工具，在插件装载期（`activate`）完成，早于 Human 首次交互。schema 约束由 05 定义；08 只定义注册时机与装载语义。注册成功不证明操作可调用、授权成立或实际可用。

### 4.3 引导面

最小规则引导 profile（01 §8 定义内容）经两种机制注入：

- `systemPrompt.section`：会话冷启动注入公共必读层（active ADR 摘要、open WorkCase 状态、Gate/Stop 边界），容量受 `ctx.tokenMeter` 与 L0 预算约束；
- pre-step 事件：会话启动与行动单元开始前注入类型触发层（Pitfall 分发、事实卡候选）与模板路由。

注入内容由 01 定义、注入形式与预算由 08 定义；内容须单一权威来源、逐字节一致、不复制规则正文、不成为第二规则源。

### 4.4 事件面

turn 事件承载模板路由与执行状态更新，end 事件承载交还处理与资源清理；中断恢复语义由 02 定义（单调令牌/冷恢复/中断锁恢复），08 只定义其在 turn/end 中的接入时机。终止时机在 DSH 无原生事件，属未验证缺口，暂不接入。

### 4.5 交互面

`ctx.userQuestions` 承载结构化问询（00 §3.1 交互面），用于 Human Gate 决策提请、计划审查与验收交还；`ctx.authorization` 承载授权流（00 §5.3 授权包），Human 对行动范围、作用边界与后续方向作出明确允许。

### 4.6 管辖登记接入

07 登记制度由 Helper（操作前管辖判定）、Git Gate（Hook 事件检查）、Skill（如保留）与 Web（显示/隐藏）消费；08 只定义消费接入方式，不定义登记 Schema 或判定逻辑。

## 5. 机械守护部署

- **运行时不变量**：经 `ctx.invariants` 注册，在装载完成、每次受控写入前、会话交还前触发断言；不替代 00 §3.3 三层防线，只作辅助机械检查。
- **文件观察策略**：`ctx.fs` observation policy——read-before-edit（修改前必须读取当前内容，不以默认值覆盖）与 version-guarded write（预期版本/指纹与当前文件一致，否则拒绝写入）。
- **Git Gate 部署**：commit-msg 钩子安装到管辖项目 `.git/hooks/`，安装前检查既有钩子避免覆盖 Human 自建钩子；部署后须确认 `managed` 状态（已安装、路径正确、版本匹配），未确认不得声称已就绪；事件检查用 06 定义的同一 validator。
- **权限预设与沙箱分层**：`workspace-write`（默认，工作区路径内读写与执行，无需 Human 授权）/ `danger-full-access`（跨工作区与系统级，需 Human 授权）；分层语义归 00 §5.3，08 只定义宿主接入方式，AI 不得自行扩权。

## 6. 发布与公共门面

### 6.1 版本号双轨制

对外发布版本 `MAJOR.MINOR.PATCH`（纯 SemVer，仅正式发布递增）；开发迭代版本同主版本 + `-dev.N`（每次开发迭代递增）。二者共享主版本、互不污染（决策 #7）；发布时封存干净版本，之后 dev 进入下一轮。

### 6.2 分发渠道

DSH 插件市场（主要渠道，接受开源公共契约）/ 本地 asar 加载（开发测试与离线使用）/ 源码安装（社区贡献与自定义构建）。

### 6.3 README

README 是 DSH 插件市场的用户第一眼界面，遵循行业通用格式：项目名称与一句话定位、安装说明（市场/本地/源码）、使用指引、配置项、开源协议（MIT，与 DSH 本体同协议）、版本号。内容必须与当前版本实际能力一致，不得超前宣传未实现的功能。README 是 00 §5.4.2 受保护文档。

### 6.4 CHANGELOG

遵循 Keep a Changelog：条目 `## [版本] - YYYY-MM-DD`，分区 Added/Changed/Fixed/Removed/Known。每次发布对应一条；条目内容必须由实际已提交变更支撑，不得为未提交内容做记录；与 06 提交契约对齐（message 与 diff 共同支撑条目）。

### 6.5 版本声明点

CHANGELOG 版本条目、插件 manifest 版本字段、README 版本行三者共同构成 00 §5.4.2 的"版本声明点"受保护文档。三者版本号必须一致，漂移按停止条件处理。

### 6.6 受保护文档承接

00 §5.4.2 五类在 DSH 域的映射：00（`specs/00-理念与构成.md`）、README（`README.md`）、插件 AI 面向语义文本（systemPrompt.section 与模板路由文本）、LICENSE（`LICENSE`）、版本声明点（CHANGELOG + manifest 版本 + README 版本行）。五类修改均须 Human 逐段同意 + 独立审核 + 只含该文档的独立 commit。08 不削弱其保护地位；受保护文件清单的变更须经 Human Gate。

## 7. 验证与证据边界

| 验证对象 | 可证明范围 | 不能单独证明 |
|----------|------------|--------------|
| 插件 manifest | 字段完整、格式合规 | 能力可用、授权成立 |
| 工具注册 | 工具已注册到宿主 | 操作可调用、Human 授权 |
| 引导面注入 | 注入内容在宿主中可观察 | 内容正确、AI 已遵守 |
| Git Gate 部署 | 钩子存在、managed 已确认 | 实际阻断有效、绕过不存在 |
| 权限预设 | 权限边界已声明 | 越权被实际拒绝 |
| README 一致性 | 版本声明对齐 | 功能完整、价值成立 |
| CHANGELOG 条目 | 变更记录存在 | 变更语义正确、Human 授权 |

## 8. Human Gate / Stop Conditions

本文不新增统一 Human Gate。以下事项按 00 §5.4 提请：改变插件身份定位、权限声明范围或分发渠道；改变引导面注入形式；改变 Git Gate 部署形态；改变版本号双轨制或版本声明点定义；修改受保护文档或新增受保护文件位置。

以下条目是 00 §5.5.1 在 DSH 接入域的具体化，**不新增停止触发类型**：工具注册失败且无来源分流；Git Gate `managed` 状态无法确认；引导面注入超出预算；版本声明点不一致；受保护文档修改未按 00 §5.4.2 流程执行；准备声明环境接入完成但 manifest/工具注册/Git Gate/引导面未全部确认。暂停期间可做规则定位、只读核对与修复准备；恢复条件须对应触发原因。

## 9. 反过度设计红线

1. 不写通用 Hook 抽象——只针对 DSH 一个宿主；
2. 不写跨平台适配——DSH 之外的平台移植由社区完成；
3. 不写非 DSH 环境接入（决策 #11）；
4. 不写 MCP 网关（决策 #11）；
5. 工具注册仅经 `ctx.tools.register` 一个入口，不建独立注册表；
6. 权限与沙箱直接使用 DSH 宿主机制，不建独立权限系统。
