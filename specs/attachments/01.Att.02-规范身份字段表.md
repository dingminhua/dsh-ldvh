# 规范身份字段表

```yaml
ldvh_attachment:
  attachment_key: "specification-identity-fields"
  attachment_id: "01.Att.02"
  title: "规范身份字段表"
  canonical_path: "specs/attachments/01.Att.02-规范身份字段表.md"
  positioning: "承载根规范、普通规范与授权附件的 YAML 身份字段、类型、必填性、空值、格式和列表契约"
```

本附件由 `specification-model-foundation` §6 与 §8.3 授权，只展开父规范已经定义的身份结构，不建立独立规则、Human Gate 或 Stop Conditions。附件与父规范正文冲突时必须修复；不得选择较方便的一方继续。

## 1. 共同解析契约

| 项目 | 要求 | 拒绝条件 |
|---|---|---|
| Markdown 位置 | 文件第一行是唯一 H1；空一行后立即出现唯一 `yaml` 代码围栏 | H1 缺失或重复、身份块不在固定位置、存在多个身份块 |
| YAML 版本 | YAML 1.2.2 Core Schema；单文档 | 多文档、自定义 schema 或依赖实现私有扩展 |
| 顶层 | 仅有 `ldvh_spec` 或 `ldvh_attachment` 一个 mapping | 两者并存、缺失或存在其它顶层 key |
| mapping key | 字段名为本附件相应 profile 的闭集 | 未知 key、重复 key、非 string key |
| YAML 构造 | 只使用普通 mapping、sequence 与 scalar | 自定义 tag、anchor、alias、merge key `<<` |
| string | 必须为 YAML string；身份块中的 string 使用双引号 | null、boolean、number 或其它隐式类型；空字符串不被对应字段允许 |
| string list | YAML sequence；成员均为双引号非空 string；保持声明顺序 | null、非 sequence、重复成员、空成员或混合类型 |
| 可选字段 | 无值时省略 | 用 null、空字符串或空对象占位；明确允许空列表的字段除外 |
| 路径 | 使用 `/` 分隔的仓库相对 POSIX 路径；不得以 `/` 开头 | `.`、`..` 路径段，反斜杠，绝对路径，尾随 `/`，与实际路径不一致 |
| Unicode | 文件和字段值使用 UTF-8；标题与文件名按实际字符逐字一致 | 解析时静默改写大小写、空白、Unicode 或路径字符 |

解析器必须检测重复 key，不得采用“最后一个覆盖前一个”的宽松行为。未知字段不得被静默忽略。格式拒绝只证明身份块不满足契约，不证明正文语义错误；反之，身份块通过也不证明正文、授权或当前规则源资格成立。

## 2. 共同值格式

| 名称 | 机器类型 | 格式与闭集 |
|---|---|---|
| 职责标识符 | string | `[a-z][a-z0-9]*(?:-[a-z0-9]+)*` |
| 规范编号 | string | `[0-9]{2,}`；保留前导零 |
| 附件编号 | string | `[0-9]{2,}\.Att\.[0-9]{2,}`；父编号与父规范当前 `spec_id` 一致 |
| 规范路径 | string | `specs/<spec_id>-<title>.md` |
| 附件路径 | string | `specs/attachments/<attachment_id>-<title>.md` |
| 标题 | string | 非空；与 H1 逐字一致；不得含 `/`、`\\`、控制字符或首尾空白 |
| 简述 | string | 非空单段；不得只有空白；不替代正文 |
| 关系 | string | 当前非空闭集仅 `refines`；根规范与无结构父规范的普通规范都使用空字符串，并与 `parent_spec` 成对 |
| 维度 | string | `read`、`write`、`orchestrate`、`memory`、`research`、`discussion`、`comply` |
| 根权威 | string | 当前只允许 `active`；只表示 00 的根权威地位，不是生命周期状态 |

路径中的 `<title>` 必须等于 H1 与身份块 `title`，文件名不得包含路径分隔符。正则是完整字符串匹配，不做大小写修正、Unicode 归一化或自动补零。

## 3. 根规范身份 profile

| 字段 | 类型 | 必填与空值 | 值与边界 |
|---|---|---|---|
| `spec_key` | string | 必填、非空 | 固定 `ldvh-root` |
| `spec_id` | string | 必填、非空 | 固定 `00` |
| `spec_kind` | string | 必填、非空 | 固定 `spec` |
| `title` | string | 必填、非空 | 固定 `理念与构成`，与 H1 一致 |
| `authority` | string | 必填、非空 | 固定 `active`；不是普通规范字段或生命周期状态 |
| `canonical_path` | string | 必填、非空 | 固定 `specs/00-理念与构成.md` |
| `parent_spec` | string | 必填；允许空字符串 | 固定 `""` |
| `relation` | string | 必填；允许空字符串 | 固定 `""` |
| `positioning` | string | 必填、非空 | 根规范简要定位 |
| `scope` | string | 必填、非空 | 根规范概括范围 |
| `basis` | array[string] | 必填；允许空列表 | 固定 `[]` |
| `related_specs` | array[string] | 必填；允许空列表 | 非结构关联的普通规范 `spec_key`；成员唯一 |
| `dimensions` | array[string] | 必填、非空 | 七维全集，各值恰出现一次；顺序为 read、write、orchestrate、memory、research、discussion、comply |
| `code_consumption` | array[string] | 必填、非空 | 根规范声明的稳定 Code 消费入口；成员使用职责标识符格式且唯一；不证明实现存在 |

根规范不声明 `authorized_attachments`、`supersedes` 或普通规范建设状态。根 profile 是 00 的一等身份契约，不是普通规范解析失败后的兼容 fallback。

## 4. 普通规范身份 profile

| 字段 | 类型 | 必填与空值 | 值与边界 |
|---|---|---|---|
| `spec_key` | string | 必填、非空 | 规范职责标识符；全局唯一且不改派 |
| `spec_id` | string | 必填、非空 | 规范编号格式；与文件名前缀一致 |
| `spec_kind` | string | 必填、非空 | 固定 `spec` |
| `title` | string | 必填、非空 | 与 H1 和文件名标题一致 |
| `canonical_path` | string | 必填、非空 | 规范路径格式；与实际 worktree 相对路径一致 |
| `parent_spec` | string | 必填；允许空字符串 | 唯一直接结构父规范 `spec_key`；无父规范时为 `""` |
| `relation` | string | 必填；允许空字符串 | 与 `parent_spec` 成对；有父规范时取关系闭集，无父规范时为 `""` |
| `positioning` | string | 必填、非空 | 唯一职责定位；不复制目录 |
| `scope` | string | 必填、非空 | 概括适用对象与场景；不替代正文适用范围 |
| `basis` | array[string] | 必填；允许空列表 | 直接且必要的上位规范 `spec_key`；成员唯一 |
| `authorized_attachments` | array[string] | 必填；允许空列表 | 当前父规范授权的 `attachment_key`；成员唯一 |
| `dimensions` | array[string] | 可选；若出现必须非空 | 仅取七维闭集；成员唯一；正文实质承担的维度必须声明 |
| `supersedes` | array[string] | 可选；若出现必须非空 | 被实质替代的旧 `spec_key`；成员唯一；不用于同一职责改名、改号或移动 |
| `related_specs` | array[string] | 可选；若出现必须非空 | 非结构关联 `spec_key`；成员唯一；不产生依据、归属、授权或替代关系 |

普通规范不允许 `status`、`authority` 或 `code_consumption`。`parent_spec` 与 `relation` 必须同时为空字符串或同时非空。`basis` 不得包含自身，不得与非空 `parent_spec` 指向同一 key；所有关系列表不得包含自身 key。

## 5. 授权附件身份 profile

| 字段 | 类型 | 必填与空值 | 值与边界 |
|---|---|---|---|
| `attachment_key` | string | 必填、非空 | 附件职责标识符；全局唯一且不改派 |
| `attachment_id` | string | 必填、非空 | 附件编号格式；与文件名前缀一致 |
| `title` | string | 必填、非空 | 与 H1 和文件名标题一致 |
| `canonical_path` | string | 必填、非空 | 附件路径格式；与实际 worktree 相对路径一致 |
| `positioning` | string | 必填、非空 | 只说明附件承载的结构化内容 |
| `supersedes` | array[string] | 可选；若出现必须非空 | 被实质替代的旧 `attachment_key`；成员唯一 |

附件不声明 `status`、`basis`、`parent_spec`、`relation`、`scope`、`dimensions`、`authorized_attachments` 或 `related_specs`。附件的唯一父规范与授权边界只从父规范 `authorized_attachments` 及正文反向确定，不由附件自我声明。

## 6. 列表与关系一致性

1. 所有列表保持作者声明顺序；解析器不得排序后冒充原始顺序。
2. 列表成员以逐字相等判断重复，不做大小写或 Unicode 修正。
3. 空列表只允许用于表中明确标注“允许空列表”的必填字段；可选列表无成员时省略。
4. `dimensions` 的顺序不改变维度语义，但根规范必须使用规定顺序以形成稳定镜像。
5. 关系目标必须在同一当前来源视图中精确解析；字段格式通过不证明目标存在或关系适当。
6. `canonical_path`、编号、标题和实际载体的一致性是跨字段及文件检查，不能只靠单字段 schema 证明。
