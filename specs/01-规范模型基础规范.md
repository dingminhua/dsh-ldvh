# 规范模型基础规范

```yaml
ldvh_spec:
  spec_key: "specification-model-foundation"
  spec_id: "01"
  spec_kind: "spec"
  title: "规范模型基础规范"
  canonical_path: "specs/01-规范模型基础规范.md"
  parent_spec: ""
  relation: ""
  positioning: "定义 LDVH 规范与授权附件的身份、职责标识符、编号登记、读取契约、最小规则引导和独立对抗审核；是规范被定位、解析、审核、引用和消费的基础"
  scope: "适用于 specs/ 下全部规范与 specs/attachments/ 下全部授权附件；不定义八维工作模型、事实模型、行动模板、事实类型与具体实现"
  basis: ["ldvh-root"]
  authorized_attachments:
    - "ldvh-bilingual-terminology"
  dimensions: ["read", "write", "comply", "deliberate", "review", "execute", "reflect", "consolidate"]
  supersedes: []
```

> 本规范依据 00 起草，只承接、不重新解释 00 的根语义；当前处于 v5 规范建设期，作为规范身份、登记、读取与审核的设计基线使用。后续修改经 Human 明确决定和受控提交后进入相应效力范围。

## 1. 价值判断

本规范主要支持 V1 快速定位、V2 充分理解、V3 边界识别、V6 工作接续和 HV5 项目演进脉络可循。身份、登记、读取与审核机制只提供规范定位、关系和治理依据，不因文件存在、格式通过或审核完成就证明规范内容正确、适用或已生效。

## 2. 规范依据

本规范直接依据 00 §2 的根方案、§3.2 的规范模型、§3.3 的规范源、§4 的 Human 决定权、§5 的 AI 责任、§6 的双轨价值标准和 §7 的防自欺、停止与交还边界。下位规范不得改变、重新解释或稀释 00 的定义。

## 3. 职责边界

本规范负责：

- 规范与授权附件的身份块契约；
- 职责标识符的命名、唯一性和不改派规则；
- 规范编号、登记和关系；
- 规范读取的 L0–L4 分层与来源定位；
- 最小规则引导所需的 00 锚点；
- 规范建立和实质修改的独立对抗审核、修复和复审；
- 规范修改的最小充分判断与 Human Gate 承接。

本规范不定义八维工作模型、事实对象、行动模板、Helper 服务、Git 契约、管辖、插件接入、Code 或 Web 的领域规则。

## 4. 基础术语

1. **根规范**：00，职责标识符固定为 `ldvh-root`；
2. **普通规范**：根规范之外、依据 00 建立的规范；
3. **授权附件**：由父规范登记，只承载字段表、登记表、清单或术语等结构化内容及其使用说明；不得在附件中建立对 AI 或 Human 的新可强制执行义务；
4. **身份块**：H1 后立即跟随的唯一 `yaml` 代码围栏；
5. **职责标识符**：由 `spec_key` 或 `attachment_key` 承载，不随标题、编号或路径变化，不改派给其它职责；
6. **维度**：规范对八维工作模型的职责声明，取值闭集为 `read`、`write`、`comply`、`deliberate`、`review`、`execute`、`reflect`、`consolidate`；
7. **设计草案**：用于迁移、讨论、审计和 Human 决策的候选，不直接作为实现基线；
8. **设计基线**：经 Human 确认，用于继续建立和审核规范的当前依据；
9. **当前规则源成员**：满足本规范登记、审核和 Human 决定要求后，正式进入当前规则源的规范；
10. **独立对抗审核**：由未参与形成候选的审查执行体主动寻找错误、遗漏、越权、反例和候选依据缺口的审核；
11. **反稀释**：下位规范和实现不得借细化、默认值、自动化、兼容处理或其它方式改变、绕过或使 00 的根定义形同虚设。

## 5. 身份块契约

### 5.1 位置与格式

H1 标题后立即跟随、全文唯一的 `yaml` 代码围栏；Markdown 使用 GitHub Flavored Markdown，YAML 使用 1.2.2 Core Schema。顶层只允许 `ldvh_spec` 或 `ldvh_attachment` 一个映射。

### 5.2 规范建设状态

规范建设期区分设计草案、设计基线和当前规则源成员。设计草案是尚未取得 Human 基线确认的候选；设计基线必须有 Human 对准确候选及作用范围的明确确认；当前规则源成员还必须完成适用的独立对抗审核与修复、Human 明确决定纳入规则源、登记变更和受控提交。退出或退回同样需要 Human 明确决定、登记变更及原因可回读。不新增生命周期 `status` 字段；登记、Human 决定或提交任一单项都不自动产生规则效力。

### 5.3 根规范身份字段

根规范身份块字段：`spec_key`、`spec_id`、`spec_kind`、`title`、`authority`、`canonical_path`、`parent_spec`、`relation`、`positioning`、`scope`、`basis`、`related_specs`、`dimensions`、`code_consumption`。其中 `authority` 固定为 `active`，只表示根权威地位；`dimensions` 必须声明八维全集。

### 5.4 普通规范身份字段

普通规范身份块字段：`spec_key`、`spec_id`、`spec_kind`、`title`、`canonical_path`、`parent_spec`、`relation`、`positioning`、`scope`、`basis`、`authorized_attachments`，以及可选的 `dimensions`、`supersedes`、`related_specs`。`code_consumption` 仅用于根规范；普通规范的 Code 消费入口由其正文和实现登记承接。

- `spec_key` 匹配 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`，唯一且不改派；
- `spec_id` 至少两位数字，与文件名前缀一致；
- `parent_spec` 与 `relation` 成对，结构关系闭集仅 `refines`；
- `basis` 只列直接且必要的上位规范；
- `dimensions` 只从八维闭集取值；普通规范可按实际职责声明子集，正文实质承担某维职责时必须声明对应键；省略表示未声明任何维度职责，不得借省略逃避一致性审核；
- `supersedes` 只用于实质替代，不用于改名或移动。

### 5.5 附件身份字段

附件身份字段：`attachment_key`、`attachment_id`、`title`、`canonical_path`、`positioning`，以及可选的 `supersedes`。附件路径为 `specs/attachments/<父编号>.Att.<至少两位序号>-<标题>.md`；标题部分使用 UTF-8 规范标题，可包含中文、ASCII 字母、数字与连字符，不含路径分隔符。

## 6. 编号与登记

### 6.1 编号段

| 编号 | 规范 | 说明 |
|---|---|---|
| 01 | 规范模型基础规范 | 身份、读取、登记、审核 |
| 02 | 八维工作模型基础规范 | 八维职责、技术/流程支撑、协同与恢复 |
| 03 | 事实模型基础规范 | 事实公共模型、受控读写与关系 |
| 04 | 行动模板基础规范 | 模板共同机制、预检与风险路由 |
| 05 | Helper 服务规范 | Helper 确定性执行契约 |
| 06 | 事实源与信息溯源规范 | 事实载体、溯源、提交与 Git Gate |
| 07 | 工作对象与管辖范围规范 | 工作对象与受辖判定 |
| 08 | DSH 环境接入与插件发布规范 | 插件接入、引导、事件、发布与受保护路径 |
| 09 | Code 实践与测试规范 | Code 实现与测试 |
| 10 | Web 呈现与交互规范 | Web 信息呈现与交互 |

- `20–24`：依据 00 §3.2 事实模型建立的事实类型规范预留段；
- `30–38`：依据 00 §3.2 行动模板建立的行动模板规范预留段；
- 附件编号：`<父规范编号>.Att.<至少两位序号>`。

编号预留不等于规范已存在或已进入当前规则源；每份文件仍分别按设计草案、设计基线或当前规则源成员判断。

### 6.2 登记规则

编号、标题和职责标识符的对应关系以 §6.1 为唯一登记权威。新建、删除、改名或重排规范模型属于 00 §4.2 的 Human 根决定事项。登记变更必须同步身份块、文件名、路径、关系、引用和术语附件，并说明当前对应关系、候选对应关系、受影响规范与附件、引用和实现范围。`canonical_path` 与实际文件路径、`spec_id` 与文件名前缀必须经机械检查一致，不一致时拒绝进入规则源。

## 7. 读取契约

规范读取由 Helper 确定性执行提供，L0–L4 各层语义如下：

| 层级 | 返回内容 | 可用于 |
|---|---|---|
| L0 | 在册职责标识符、编号、标题与路径 | 发现有哪些规范或附件 |
| L1 | L0 + positioning、scope、authority/建设状态 | 判断候选职责与效力范围 |
| L2 | L1 + basis、结构关系、维度、附件授权和章节目录 | 选择需要深入读取的来源与章节 |
| L3 | 由精确 `heading_path` 定位的完整章节片段及行号 | 读取当前问题所需的局部规则 |
| L4 | 目标文件从身份块到正文结尾的完整当前内容 | 完整审计、冲突处理或无法局部裁剪时读取 |

1. `read-specification-candidates`：按职责标识符或全部在册候选读取 L0–L2；
2. `read-specification-content`：按 `responsibility_key` 读取 L3 章节片段或 L4 完整来源。

`responsibility_key` 等于目标 `spec_key` 或 `attachment_key`。L3 必须提供精确 H2 或 H2/H3 `heading_path`；L4 不提供 `heading_path`，返回完整当前文件。`start_line`/`end_line` 使用 1-based 行号。具体请求/结果形状由 05 回指本节定义，01 不复制 Helper envelope。规范读取 L0–L4 与事实召回 F0–F4 不混用；F0–F4 的具体定义归 03；候选、片段和完整来源不互相冒充。

Helper 读取入口不可用时，不得伪造受控读取结果；主控可使用宿主公开文件读取继续只读核对，但必须披露降级入口、未取得 Helper 回执和未验证范围。来源规则要求受控回执而当前无法取得时，按 00 §7.2 暂停受影响行动。

## 8. 最小规则引导

会话启动时，插件 AI 工作引导至少提供下列 00 锚点：

1. 00 文件头部身份块；
2. 00 §2 八项根方案；
3. 00 §3.1 八维工作模型；
4. 00 §4.2 Human Gate 与根决定清单；
5. 00 §5.1 单一主控最终负责；
6. 00 §7.1 防自欺锚点；
7. 00 §7.2 Stop Conditions；
8. 00 §7.4 交还与 Output Envelope。

具体注入顺序、预算、触发时机和宿主承载由 08 定义；最小引导不替代完整规范读取、事实召回或适用判断。

## 9. 规范关系与授权附件

### 9.1 关系语义

- `basis`：直接必要的上位依据，方向为下位到上位；
- `parent_spec` + `relation`：结构父子关系，`refines` 表示子规范具体化父规范的部分职责而不替代父规范；同一目标不得同时作为 `basis` 和结构父规范；
- `supersedes`：新规范承接旧规范全部或主要职责且旧规范退出当前规则源的实质替代；改名或移动不构成替代；
- `related_specs`：不产生继承、效力或替代关系的非结构关联。

附件必须由唯一父规范的 `authorized_attachments` 登记；附件只承载结构化内容，不承载正文规则。附件冲突时以父规范正文为准。各领域操作、模板和字段声明的唯一权威以本规范登记与各自领域来源为限，领域之间不得互相声称同一语义的唯一权威。

### 9.2 双语术语附件

本规范授权 `ldvh-bilingual-terminology` 承载跨规范核心术语的中文名称、英文名称、缩写、机器表示、唯一定义来源和建设状态。附件只提供定位；标记为 `provisional` 的条目不证明相应规则、字段、授权或实现成立。

### 9.3 根级 Code 消费入口

根规范 `code_consumption` 当前登记四个根级入口：`spec_identity_block`、`spec_read_contract`、`minimal_guidance_profile`、`helper_service_boundary`。四个键分别承接身份解析、规范读取、最小引导和 Helper 确定性执行边界；授权、Stop、验证和交还等具体机械入口由相应下位规范登记，不在根身份块复制。

01 定义键的语义和来源；05 定义 Helper 读取与响应契约；08 定义插件消费与宿主承载；09 实现并测试解析。键被登记、实现或调用成功，只证明对应入口存在，不证明规则适用、授权或整体完成。

## 10. 规范修改判断

规范修改遵循最小充分原则；能改一处不改一章，能改一份不牵动多份。新建、删除、改名、重排或改变可强制执行规则时，按 00 §4.2 进入 Human Gate。

## 11. Human Gate 与 Stop Conditions

本规范不新设 Human Gate 或 Stop Conditions：

- 规范模型根决定事项按 00 §4.2 提请；
- 受保护内容按 00 §4.3 执行；
- 提请内容与回应效力按 00 §4.4；
- Stop 根触发与恢复按 00 §7.2、§7.3；
- 交还与 Output Envelope 按 00 §7.4。

本规范只能具体化规范域中的拒绝、暂停与恢复条件，不得新增 00 未定义的根停止类型。§12 的审核义务是规范生效前置门控：审核未完成或真实问题未修复时不得进入 Human 决定；它不另设 00 §7.2 之外的恢复路径。

## 12. 规范独立对抗审核

### 12.1 触发与风险分层

规范新建、删除、改名、重排、实质修改，或产生、改变可强制执行规则时，必须在进入 Human 决定前完成独立对抗审核并修复真实发现。风险分级只能调整审核范围和深度，不能取消审核触发。

- 非实质性修正：检查身份、引用、格式和中文语义；
- 实质修改但不改变可强制执行规则：检查价值、职责、边界、可实现性和防自欺；
- 产生或改变可强制执行规则：执行完整审核，并核对 Human 根决定与反稀释边界。

非实质性修正仅涉及身份、引用、格式或中文语义，且不改变职责、边界、可实现性、防自欺或判断结论；触及其中任一项即为实质修改。无法确定是否产生或改变可强制执行规则时，按最高一档审核。01 自身同样适用本节。

### 12.2 独立与对抗

独立审核由未参与形成候选的审查执行体完成；同一会话中形成候选的同一角色不得审核该候选。可由隔离会话中的 AI、独立代理或 Human 执行；采用同一模型时仍须保持候选形成上下文隔离，并披露独立性边界。对抗审核必须主动寻找错误、遗漏、越权、反例和候选依据缺口。审核必须说明对象、范围、所用依据、实际攻击方向、发现、未覆盖范围和保证边界，不得只报告“已审核”或“无问题”。

### 12.3 审核维度

审核按风险选择以下维度，产生或改变可强制执行规则时全部覆盖：

1. 价值判据对齐；
2. 职责边界与单一权威；
3. 反过度设计；
4. 技术可实现性与能力真实性；
5. 身份、编号、引用和格式；
6. 防自欺与不能单独证明的边界；
7. 已知病灶与反例；
8. 草案、修复、Human 决定和提交闭环；
9. 审核自身是否与风险匹配；
10. 中文语义清晰与术语一致。

审核报告必须说明实际覆盖和跳过的维度、跳过依据、信息不足项及保证边界；分档结论由独立审核执行体反向核对，不由候选形成者单方认定。

### 12.4 修复与复审

主控核对审核发现，修复真实问题；未修复问题必须明确说明原因、影响和残留风险，不得静默忽略。修复改变被审对象的根语义、职责、可强制规则或结论时，须由独立审核执行体复审全部受影响维度。审核完成不证明规范正确，也不自动使规范生效。

## 13. 验证与交还

规范身份、登记、关系和引用采用机械解析与回读验证；价值、职责、语义和可实现性采用 AI 审核。两者互不替代。验证结果只证明实际检查范围，不证明规范适用或整体价值成立。

每次交还按 00 §7.4 同时提供 Human 可读正文与机器可读 Output Envelope，说明当前状态、依据、已证实与未证实范围、残留风险、待 Human 决定事项和继续入口。Output Envelope 的具体结构与承载由相应下位规范定义。
