# 规范模型基础规范


## 1. 价值判断

本规范解决规范身份、结构、关系、读取和修改边界缺少统一来源的问题，使 Human、AI 与 Code 能以同一套稳定契约定位、理解和维护规范，减少搜索、猜测、遗漏、重复权威和跨会话接续负担。

本规范主要支持 V1 快速定位、V2 充分理解、V3 边界识别、V6 工作接续、V8 持续积累，以及 HV1 决策提请清晰可决、HV3 入档闭环节点可验、HV4 积累效用直观可见和 HV5 项目演进脉络可循。

本规范只提供规范定位、结构、关系和治理基础；具体领域价值、执行结果、Human 授权和长期效用由相邻规范与实际工作承接。共同格式只有在减少实际负担时才有价值。

身份可解析、文件存在、检查通过或提交完成，只能证明相应机械范围，不能单独证明规范内容正确、规则适用、Human 已授权、行动完成或长期价值成立。

## 2. 规范依据

本规范直接依据：

1. `ldvh-root`：00 §2 的根方案、§3.2 的规范模型、§3.3 的规范源、§4 的 Human 决定权、§5 的 AI 责任、§6 的双轨价值标准和 §7 的防自欺、Stop Conditions 与交还边界。

GFM 与 YAML 1.2.2 Core Schema 只提供外部语法定义，不取得 LDVH 领域语义权威。

历史版本、开发备忘、审计材料、聊天、Code、tests 和工具输出可作为设计输入或证据，但不是本规范的规范依据，也不因此进入当前规则源。下位规范、附件、Code 与 Web 不得改变、重新解释或稀释 00 的根定义；发生冲突或权威关系无法确认时，按 00 §7.2 暂停受影响范围并完成对齐。

## 3. 职责边界

### 3.1 本文负责

本规范负责：

1. 根规范、普通规范和授权附件的角色及 YAML 身份契约；
2. 职责标识符、编号、登记、规范关系和附件授权；
3. 普通规范的共同章节结构与基础模型规范对下属规范的结构责任；
4. 当前规则源成员的成立、退出、视图与失败边界；
5. L0–L4 规范读取层级、来源回指与安全展开边界；
6. 最小规则引导中必须提供的 00 锚点；
7. 规范新建、修改、拆分、合并、取消与旧规则处置判断；
8. 风险匹配的独立对抗审核、修复和复审。

本规范自身的建立与治理会涉及全部系统与制度，因此身份块声明七维全集；该声明只表示本文实质涉及的工作范围，不定义系统或制度的名称、根职责、协同模型或操作流程。

### 3.2 本文不负责

本规范不定义工作模型语义、事实公共模型、事实类型、业务系统规范、Helper 共同 envelope、Git 提交契约、管辖解析、插件接入、Code 实现或 Web 呈现的领域规则。

### 3.3 相邻规范分工与唯一权威

00 是根定义的唯一权威；02 定义工作模型；03 定义事实公共模型与事实类型共同结构；04 定义业务系统规范共同结构；05 定义共同请求与响应 envelope；09 实现并测试规范解析。本规范只定义规范模型，不复制这些相邻规范的领域语义、协议或实现细节。

## 4. 适用范围

### 4.1 适用对象

本规范适用于：

1. `specs/` 根目录下的 LDVH 规范；
2. `specs/attachments/` 下由唯一父规范明确授权的附件；
3. Human、AI 与 Code 对上述文件的共同消费。

### 4.2 适用场景

本规范用于上述文件的建立、识别、定位、分层读取、登记、审核、修改和一致性检查。

### 4.3 明确排除与证明边界

00 是根规范，不适用普通规范固定章节标题和顺序，但仍必须由自身结构承担价值、职责、验证、Human Gate、Stop Conditions 与反过度设计等根职责。本规范不把 `docs/`、`archive/`、Code、tests、缓存、索引、聊天、评审结论或工具输出转化为规范源。

规范位于候选路径且身份可解析，只证明候选被发现和相应机械范围成立，不单独证明其满足 §9 的当前规则源条件。

## 5. 基础术语与文件角色

1. **规范文档**：位于 `specs/` 根目录、承担明确且稳定规范职责的 Markdown 文件；
2. **根规范**：00，职责标识符固定为 `ldvh-root`，定义 LDVH Human 根契约；
3. **普通规范**：根规范之外、依据 00 建立并承担稳定规范职责的规范；
4. **授权附件**：由唯一父规范登记，只承载父规范已经定义并授权的字段表、登记表、清单、矩阵或术语等结构化内容及必要使用说明；不得建立新的独立规则、Human Gate 或 Stop Conditions；
5. **身份块**：文件头 `---` 围栏包裹的 YAML frontmatter，围栏闭合后空一行、再出现唯一 H1；
6. **职责标识符**：由 `spec_key` 或 `attachment_key` 承载，不随标题、编号或路径变化，不得改派；
7. **定义来源**：对某概念的含义、边界和相邻概念差异承担唯一定义责任的当前规范章节；
8. **设计草案**：尚未取得 Human 对准确候选及作用范围确认的规范候选；
9. **设计基线**：经 Human 明确确认，可用于继续建立和审核规范，但尚不等于当前规则源成员；
10. **当前规则源成员**：满足 §9 全部成立条件并进入当前来源视图的规范或授权附件；
11. **渐进式披露**：按当前需要提供最小且足够的可回指信息，并在不足、风险上升或消费方要求时展开更完整来源；它不是新的规则源或授权机制；
12. **独立对抗审核**：由未参与形成当前候选的审查执行体主动寻找错误、遗漏、越权、反例和依据缺口的审核；
13. **反稀释**：下位来源和实现不得借细化、默认值、自动化、兼容处理或其它方式改变、绕过或使 00 的根定义形同虚设。

## 6. YAML 身份块契约

### 6.1 位置、语法与解析边界

文件第一行是 `---`，与下一个 `---` 共同包裹唯一身份块（YAML frontmatter）；围栏闭合后空一行，紧随唯一 H1。Markdown 使用 GFM，身份块使用 YAML 1.2.2 Core Schema。顶层只允许 `ldvh_spec` 或 `ldvh_attachment` 一个映射。

**形态来源与效力**：身份块采用文件头 frontmatter 而非「H1 后的 `yaml` 代码围栏」，系依 **Human 裁定（2026-09-08）**——「所有文件都是 md，md 里包含一段 yaml（frontmatter）」，使 `specs/` 规范与事实对象（`ldvh-base/` 下对象）的处理方法统一；两者对预览器一致隐藏 YAML、对机器消费一致经 frontmatter 解析。该迁移由 `2cb26b3` 实施（含 `plugin/lib/spec-registry.js` 的 `splitIdentityBlock` 重写与全部夹具更新）。本节条文为该形态的规范表述；实现与本节不一致时，按 `00 §7.2` 暂停受影响范围并按 `01 §12` 独立审核后对齐，不得静默选边。

不允许重复 key、未知字段、多个 YAML 文档、自定义标签、锚点、别名或合并键。字符串与字符串列表成员使用双引号。字段类型、必填性、空值、格式、闭集、列表规则及根规范 profile 由 [01.Att.02-规范身份字段表](attachments/01.Att.02-规范身份字段表.md) 承载；附件只展开本节已经授权的契约，不得自行增加字段语义。

### 6.2 职责标识符与一致性

`spec_key` 与 `attachment_key` 匹配 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`，在当前规则源及可回查历史中唯一且不改派。编号、标题和路径可经 Human 决定变化，但职责标识符保持不变；职责实质改变到不再是同一责任时应建立新 key。

`title`、编号字段和 `canonical_path` 分别镜像实际 H1、文件名前缀和当前 worktree 相对路径。身份块、正文和实际载体冲突时必须修复，不得选择较方便的一方继续。

### 6.3 规范建设状态

规范建设区分设计草案、设计基线和当前规则源成员，但普通规范和附件不设置生命周期 `status` 字段。设计基线必须有 Human 对准确候选及作用范围的明确确认；成为当前规则源成员还必须满足 §9。文件存在、登记、审核、Human 决定或提交任一单项都不自动产生完整规则效力。

## 7. 普通规范共同章节契约

除 00 外，普通规范前四个 H2 与末尾四个 H2 的编号和标题固定，中间领域正文按 §7.2 约束自由定义。本章规定各固定章节与领域规则单元的最小必填语义元素；元素必须可辨认，即读者和审核者能够据实指出其在正文中的位置。固定章节不仅必须包含相同语义元素，还必须遵循本章规定的信息顺序，并使用相近的段落结构与清单粒度，使同类信息在不同规范中位于可预期位置。除本章明确规定的 H3 分组、验证表格与反过度设计红线编号清单外，不要求逐字相同、篇幅相同或领域正文采用统一文体。全部八个固定章节的标题可以增加不改变结构角色的领域限定词，但固定标题文字必须逐字保留在标题中，使机械规则能够唯一识别其结构角色。

### 7.1 固定前置章节

1. `## 1. 价值判断` 固定按以下段落顺序表达：第一段说明目标与净价值，即本规范解决什么持续问题、减少什么负担；第二段使用一个连续普通段落，逐项或以分号分组说明主要影响的 V/HV，不得用列表、表格、子标题或多个段落拆分该映射块；逐项引用使用 00 §6 的编号与名称原文，分组引用只使用编号或编号区间，不得以无差别的 V1–V8 或 HV1–HV5 全区间声明，或全量逐项罗列全部 V/HV，替代主要影响判断；第三段按需说明依赖相邻规范承接的独立价值边界，无增量时省略；末段说明不能单独证明的范围。不得把目标、映射和证明边界压缩为一个不可分辨的长段。
2. `## 2. 规范依据` 固定按以下顺序表达：先以编号清单列出直接且必要的上位规范及所依据章节；清单每项必须对应身份块 `basis` 的一个成员，使用 `` `spec_key`：规范编号 + 精确章节`` 的形式，顺序与 `basis` 一致，不得把同一 basis 的不同章节拆成多个编号项；再用独立段落排除非规范输入；确实依赖外部语法或标准时，在非规范输入之前增加独立段落，说明它只提供外部定义、不取得 LDVH 领域语义权威。普通规范与上位来源发生冲突或权威关系无法确认时，不静默选边，按 00 §7.2 暂停受影响范围并完成对齐；各规范不逐份复制该共同规则。
3. `## 3. 职责边界` 固定依次使用 `### 3.1 本文负责`、`### 3.2 本文不负责`、`### 3.3 相邻规范分工与唯一权威` 三个 H3；各节使用直接段落或编号清单，不把三类信息混写在同一段。
4. `## 4. 适用范围` 固定依次使用 `### 4.1 适用对象`、`### 4.2 适用场景`、`### 4.3 明确排除与证明边界` 三个 H3；适用对象多于一项时使用编号清单。第三节说明明确排除，并在存在“范围成立被误当作生效、许可或完成”的混淆风险时说明范围成立不能单独证明什么；通用边界由 00 §3.3 与本文 §9–§10 承载，不逐份复制。

### 7.2 领域正文与规则单元

第 5 章起由各规范按职责和最小充分原则自由定义。领域正文不得复制 00 根定义、相邻规范的唯一职责或实现细节。基础模型规范还必须定义其下属规范共同结构、必填内容和扩展规则：**03 定义事实类型规范（`20–29` 段）的共同结构**；**04 定义业务系统规范（`30–35` 段）的共同结构**。

**「下属规范」以身份块 `parent_spec` 为准，不以段号推定**：一份规范是否属某基础模型规范的下属规范，由该规范身份块的 `parent_spec` 指向决定（`01.Att.03`）。**基础模型规范定义共同结构时，必须覆盖其全部 `parent_spec` 指向自身的下属规范**；段号相同但 `parent_spec` 未指向者不受其约束，`parent_spec` 指向但段号不同者仍受其约束。**该覆盖义务不因下属规范的编号落在预留段之外而免除。**

领域正文以规则单元为消费粒度。规则单元是完整包含在单一 L3 标题路径返回范围内的最小正文单元，通常为 H2/H3 小节，或同一小节内共同表达一项规则且边界明确的一组条目；规则单元不得跨标题拆分。仅用于聚合多个可独立消费 H3 的容器 H2 本身不是规则单元，该容器小节的正文只承担全部子单元共享的定位与边界。每个规则单元至少使下列内容在语义上可辨认，但不要求固定标签：

1. **定位**：该单元定义什么、解决什么；
2. **规则或不变量**：直接陈述的规则、义务或不变量；
3. **边界**：不能单独证明什么、何时不适用或与相近概念的差异，至少一项。

下列元素按需出现，无增量时省略，不得用空句占位：成立条件，仅在规则具有独立前提时说明；反例，仅在存在易混淆场景时说明；相邻规范分工，仅在需要比 §3 更细的边界时说明；独立验证或失败处理，仅在固定尾章无法覆盖该单元的独立验证需求时说明。

具体规则使用直接、词义一致的陈述，并在本规范适用范围内说明对象与场景。示例、说明和建议不因出现在规范中自动取得强制效力。需要 Code 稳定引用的规则，应位于具有明确标题、表头或结构说明的段落、列表、表格或授权附件中。多行同构且有机器消费方的契约使用表格；单条机器消费契约可以按稳定定位需要使用带表头的表格；单条自然语言规则使用陈述句或列表，不为形式统一拆表或增加固定小标题。

### 7.3 固定收尾章节

每份普通规范末尾依次包含下列四个 H2，编号随领域正文连续顺延：

1. `验证与证据边界`：存在领域验证对象时，必须使用以下七列表头，表头文字与顺序固定：

   | 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
   |---|---|---|---|---|---|---|

   每行必须绑定本规范自身的对象、契约、边界或失败场景；已由 00 或其它来源完整定义的共同验证只作必要回指，不另起重复行；没有真实的成立条件和可接受依据时，不得以空泛的“AI 审核”“后续检查”或同义占位填充行。章节末尾说明机械结果与语义判断互不替代，以及本章不能单独证明的范围。无领域验证增量时用一句回指 00 §7，不制造空表格。
2. `Human Gate` 固定按以下顺序表达：第一段声明是否新增 00 之外的 Human Gate；有领域增量时，随后使用编号清单登记本领域的 Human 决定增量事项——包括 00 §4.2 根清单的领域具体化与上位未完整定义的本领域决定事项；末段说明 Human 决定只证明决定及其作用范围，不替代本领域哪些验证或判断。无增量时只保留第一段并一句回指 00 §4，不制造空清单。
3. `Stop Conditions` 固定按以下顺序表达：第一段声明不新增根停止类型；有领域增量时，随后使用编号清单登记领域触发及其最小影响范围；再用独立段落说明暂停期间允许动作（确有增量时）、恢复条件和同一条件再次触发进入 Human Gate。无增量时只保留第一段并一句回指 00 §7，不制造空清单。
4. `反过度设计红线` 使用编号清单；每条红线用一句指明对象与禁止行为，理由或边界仅在不自明时附注，不登记无对象或无禁止行为的口号句。

无领域增量时用一句明确回指，不制造空规则、空表格或重复清单。设计草案可临时附带起草核对材料，但在 Human 确认设计基线前应删除，或吸收到正式结构角色中。

本章契约的变化不追溯取消既有成员已经取得的资格证据，也不使既有成员仅因本章变化而视为不满足 §9.2 第 5 项；过渡期内，该项按成员取得资格时点有效的本章契约核对。既有成员在下一次实质修改或 Human 指定的迁移时点，按当时有效契约核对并修复；该过渡不允许既有成员在实质修改时继续沿用已经不符合当前契约的结构。Human 指定迁移时点时，按 00 §4.4 形成作用范围清楚、可回查的回应记录。

## 9. 当前规则源成立与来源视图

### 9.0 元规范与事实规范的两级归属判断

本节承接 `00 §3.3` 的指派：「元规范不替项目定规则，事实规范不替 LDVH 定机制；**具体归属判断由规范模型定义**」。以下为该项归属判断。

**两级定义**（依 `00 §3.3`）：

- **元规范**：承载 **LDVH 自身**的规则，约束 LDVH 自身及其机制对项目的运作；位于本仓库 `specs/`，随插件版本锁定，对全部受管辖项目生效。
- **事实规范**：承载**管辖项目**的规则，即项目的内容、结构与工程纪律；位于该项目的**事实源**（`ldvh-base/`），以**事实对象形态**承载，随项目 worktree 走。

**归属判据**（首要判据为约束对象，可机械或半机械判定）：

| 维度 | 元规范 | 事实规范 |
|---|---|---|
| **D1 约束对象（首要）** | 约束 LDVH 机制／跨项目运作 | 约束**单一项目**的内容、结构、工程纪律 |
| D2 适用项目数 | 全部受管辖项目 | 仅该项目 |
| D3 载体位置 | `specs/`（本仓库） | 该项目的事实源 `ldvh-base/` |
| D4 效力来源 | 路径与编号登记（`§9.1`/`§9.2`） | 类型与状态（由相应事实类型规范定义），不靠路径挂靠 |
| D5 建立程序 | 本规范 §11、§12 | **复用同一套受控建立程序**（`00 §3.6`），不得另设一套 |

**判定的三个必须分别判断的问题**（依 `00 §3.3`，互不替代）：规范内容**进入当前规则源**、具体规则**适用于当前事项**、当前行动**获得允许**。本节的归属判断只回答第一个问题的一小部分——「该内容应作为元规范还是事实规范承载」，不回答适用与授权。

**边界纪律**（依 `00 §3.6`）：

1. 两级**共用同一套受控建立程序**，故不构成第二套权威；
2. **事实规范不得放松元规范、不得自授效力**；事实对象不因存放位置而取得规范效力（`00 §3.3`）；
3. 同一事项**不得**同时由一份元规范与一份事实规范重复定义；出现重复时按 `00 §7.2` 暂停受影响范围并完成对齐；
4. 归属存在争议、或本判据无法确定归属时，**进入 Human Gate**（`00 §4.2`：改变规范模型、事实模型属根决定事项），不得由 AI 自行认定；
5. **改变本节的归属判据本身**属 `00 §4.2` 的根决定事项。

**两级不互为对方的成员**：事实规范是**事实源中的事实对象**，不进入 `specs/` 的候选路径，不占用本规范的编号命名空间（`§9.1`、`§8.1`）；元规范亦不进入事实源。二者各自按本规范与相应事实类型规范成立。

### 9.1 候选路径与唯一视图

候选只来自已确认 LDVH 源码仓库当前实际 Git worktree 中的普通 Markdown 当前文件，不跟随符号链接：

1. `specs/<至少两位数字>-<规范标题>.md`；
2. `specs/attachments/<父规范编号>.Att.<至少两位序号>-<附件标题>.md`。

候选发现与成员资格严格分层。文件名匹配只产生待解析候选，不产生规则资格。文件名含 `.draft`、`.tmp`、备份后缀或其它不符合上述完整模式的载体不进入候选；设计草案、退出后历史保留文件和其它未满足 §9.2 的匹配载体，只能以 `non_member_candidate` 及精确原因出现在诊断范围，不进入 L0–L4 当前规则结果。Git 路径按仓库记录的 UTF-8 字节序列逐字比较，不做大小写折叠或 Unicode 归一化；但经 NFC 或大小写折叠后发生冲突的近似路径必须作为跨平台歧义拒绝，不选择任一文件。同一编号、职责标识符、`canonical_path` 或规范化名称映射到多个候选时，全部受影响候选均不得进入成员读取，直到冲突解除。

唯一当前来源视图是该 worktree 的 Working Tree。一次读取或资格检查必须绑定同一轮扫描取得的 worktree 身份、候选集合指纹和各载体内容指纹；父规范与附件必须来自同一快照。检查期间任一相关内容变化、指纹不一致或无法形成同一快照时，该范围不得返回为完成。工作树可以包含未提交变化，但这些变化不会复用旧候选的 Human 决定、审核或提交证据。Index 与 HEAD 只用于提交前检查和历史溯源；安装包、缓存或其它来源副本不得覆盖、补回或与当前来源混合。

### 9.2 规范成立条件

规范进入当前规则源必须同时满足：

1. 位于 §9.1 候选路径，且不是符号链接；
2. H1、身份块和 Markdown/YAML 可以按 §6 解析；
3. `spec_key` 与 `attachment_key` 共享一个职责标识符命名空间并全局唯一且未被改派；`spec_id` 在规范编号命名空间唯一，`attachment_id` 在附件编号命名空间唯一，二者不作跨类型相等比较；所有载体的 `canonical_path` 在候选全集中全局唯一；

8. 新建或实质修改已经完成 §12 的独立审核、修复与必要复审；

12. 当前来源视图的内容指纹仍与 Human 决定、审核和提交所绑定的准确候选一致。

### 9.3 退出与失败边界

规范退出当前规则源必须经 Human 对准确退出候选明确决定、完成 §8 登记变化、受影响引用与关系处理和受控提交，并说明职责去向与仍适用规则的保留、转移或退出；四项共同构成退出，不得由任一单项替代。文件可为历史追溯保留在候选路径，但登记移除且退出提交成立后只能作为非成员候选被发现，不得进入 L0–L4 当前规则消费结果；读取入口必须披露其非成员原因并拒绝把正文作为当前规则返回。仅删除文件、改名、修改字段或改变 Git 状态不构成完整退出。

无法证明某项成立条件时，应把该项和受影响范围记录为 `gaps`，不得伪装为通过。存在已实现但未执行、未通过或不可信的机械校验时，不得把受影响载体返回为通过；尚未实现的检查不得用人工猜测冒充机械证明。当前来源不一致时暂停依赖受影响内容的行动，不得静默回退 Index、HEAD 或其它副本。

资格证据至少绑定：候选集合与载体内容指纹、逐项成立条件及证据引用、独立审核对象与范围、Human 决定对象与作用范围、提交引用和观察到的当前来源视图。任一绑定内容变化、决定被撤回、审核对象不再一致或提交范围不匹配时，旧证据不能继续证明当前候选。具体证据载体与传输结构由 05、06、08 在各自职责内承接，不在 01 建立第二账本。

## 10. 规范关系、读取与规则引导

### 10.1 关系语义

`basis`、`parent_spec` + `relation`、`authorized_attachments`、`supersedes` 与 `related_specs` 的方向、基数、允许目标和禁止用途由 [01.Att.03-规范关系与层级表](attachments/01.Att.03-规范关系与层级表.md) 承载。本规范正文定义其边界：

- `basis` 只列理解、判断或维护当前规范所必需的直接上位规范；目标必须是当前成立的规范，依赖图不得成环；
- `parent_spec` 与 `relation` 是必填成对字段：无结构父规范时都为空字符串；有结构父规范时都为非空，只表达唯一直接结构归属；关系闭集当前仅 `refines`；同一目标不得同时作为 `basis` 和结构父规范；父规范正文必须能定位被具体化的职责边界，子规范不得越出该边界；
- `authorized_attachments` 只从父规范指向附件；父规范必须在 §8.3 或等价授权小节逐项说明附件承载对象与边界；
- `supersedes` 只表示新职责对旧职责的实质替代，不用于同一职责改名、改号或移动；替代图不得成环，旧职责不得与替代者同时作为当前规则源成员；
- `related_specs` 只表达非结构关联，不产生继承、效力或替代关系。

### 10.2 L0–L4 读取层级

L0–L4 的名称、累积内容、用途和不能单独证明的范围以 01.Att.03 §4 为唯一结构化表。L0–L2 不证明相关、适用或完整约束；L3 不证明已经包含全部语义依赖；L4 不证明实现、验证或授权成立。消费方可直接请求任何足够层级，不强制逐层仪式。01 定义层级语义，05 定义共同请求/响应 envelope，09 实现并测试解析。

### 10.3 读取入口边界

`read-specification-candidates` 按职责标识符或全部候选读取 L0–L2；`read-specification-content` 按精确 `responsibility_key` 与 `heading_path` 读取 L3，或不提供标题路径读取 L4。`responsibility_key` 的取值就是目标 `spec_key` 或 `attachment_key`，不接受编号、标题、路径或模糊回退。L3 的 H2/H3 路径必须在同一载体中精确唯一，重复或歧义标题不选择首个匹配而应拒绝；行号为 1-based。每次结果必须披露来源视图、候选集合或内容指纹、完成与未完成范围及资格 gaps；返回候选或内容不等于载体已满足 §9.2，也不得把不合格候选当作可执行规则。规范读取 L0–L4 与事实召回 F0–F4 不混用。

Helper 读取不可用时，不得伪造受控回执。只读核对可据实降级到宿主公开文件读取，但必须披露入口、未取得的 Helper 回执和未验证范围；来源要求受控回执而无法取得时，按 00 §7.2 暂停受影响行动。

### 10.4 最小规则引导

会话启动时，插件 AI 工作引导至少提供下列 00 锚点：身份块、§2 根方案、§3.1 工作模型、§4 Human 决定权、§5 AI 责任、§6 双轨价值、§7 防自欺/Stop/交还。具体注入顺序、预算、触发时机与宿主承载由 08 定义；最小引导不替代完整规范读取、事实召回或适用判断。

## 11. 规范新建、修改与重构判断

### 11.1 判断顺序

按以下顺序形成候选，不得先决定技术形态再补理由：

1. 明确要解决的问题、现有来源、消费方和缺口；
2. 判断是否只需更正表达、引用、格式或身份镜像；
3. 判断现有规范能否通过最小充分修改无损承载；
4. 比较现有正文、授权附件、新建规范、拆分、合并或取消的职责清晰度、重复风险、读取成本、维护成本与净价值；
5. 形成包含旧规则处置和来源影响的准确候选；
6. 按 §12 独立审核并修复；
7. 取得适用 Human 决定，更新登记与引用，再受控提交。

### 11.2 独立规范成立条件

新建或保留独立规范必须同时具有：稳定且可独立说明的职责、明确消费方、足够持续的规则内容、现有承载无法无损吸收，以及相对新增搜索和维护成本为正的净价值。只因篇幅较长、概念名称不同、未来可能扩展或希望编号整齐，不足以成立独立规范。

授权附件只在父规范已经定义规则、结构化内容稳定且正文内维护明显降低可读性时使用；它不是规避独立规范成立条件或隐藏新规则的途径。

### 11.3 修改、拆分、合并与取消

最小充分修改优先：能改一处不改一章，能改一章不改整份，能改一份不牵动多份，但不得以“最小改动”为由保留错误结构或重复权威。

拆分应证明原职责包含可独立消费且稳定的多个责任；合并应证明多个来源实质承担同一责任或分离成本超过价值；取消应证明职责不再需要或已由其它当前来源完整承接。每种变化都必须说明旧规则逐项保留、转移、改写或退出的去向，处理身份、编号、关系、附件、引用、实现与历史回指。

同一职责改名、改号或移动时保留原 key，不使用 `supersedes`。实质新职责替代旧职责时使用新 key，并通过 `supersedes` 与正文处置说明建立可追溯关系。拆分时可以由一个保留原 key 的幸存职责继续承载未改变部分，其余实质新职责使用新 key；合并进既有幸存规范时，幸存 key 保持不变，并可用 `supersedes` 指向被并入且退出的旧职责。纯取消没有替代者时不虚构 `supersedes`，由退出决定、登记变化和正文处置记录共同追溯。

### 11.4 来源先行闭环

规范先定义语义、字段和成立条件，再由 Code 与 Web 实现或呈现。不得因现有实现方便而反向改变规范语义，也不得在规范尚未成立时由 Code、测试、索引或页面先行制造事实上的第二规则源。实现缺口进入 gaps 和后续工作，不冒充规范已被机械保障。

## 12. 规范独立对抗审核

### 12.1 触发与风险匹配

规范新建、删除、改名、重排、实质修改，或产生、改变可强制执行规则时，必须在 Human 决定前完成风险匹配的独立对抗审核并修复真实发现。风险分级可以调整审核范围和深度，但不能取消审核触发。

非实质性修正只涉及身份镜像、引用、格式或中文语义，且不改变职责、边界、可实现性、防自欺或判断结论；触及其中任一项即为实质修改。无法确定是否产生或改变可强制执行规则时，按较高风险审核。01 自身同样适用。

### 12.2 独立与对抗

独立审核由未参与形成当前候选的执行体完成；同一上下文中形成候选的同一角色不得审核该候选。可由隔离会话 AI、独立代理或 Human 执行；采用同一模型时仍须保持候选形成上下文隔离，并披露独立性边界。

审核必须说明对象、准确候选、范围、依据、实际攻击方向、发现、未覆盖范围和保证边界，不得只报告“已审核”或“无问题”。

### 12.3 十维审核

产生或改变可强制执行规则时覆盖全部十维：

1. 价值判据对齐；
2. 职责边界与单一权威；
3. 反过度设计；
4. 技术可实现性与能力真实性；
5. 身份、编号、引用和格式；
6. 防自欺与不能单独证明的边界；
7. 规范内部一致性与反例检验；
8. 草案、修复、Human 决定和提交闭环；
9. 审核自身是否与风险匹配；
10. 中文语义清晰、术语一致与机器表示对应。

审核报告必须说明实际覆盖和跳过的维度、跳过依据、信息不足项与保证边界；风险档位由独立审核执行体反向核对，不由候选形成者单方认定。

### 12.4 修复与复审

主控核对审核发现并修复真实问题。未修复项必须说明原因、影响与残留风险，不得静默忽略。修复改变根语义、职责、可强制规则或审核结论时，由独立审核执行体复审全部受影响维度。审核完成不证明规范正确，也不自动使其进入当前规则源。

## 13. 验证与证据边界

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 身份与路径 | 建立、修改、读取或提交前 | YAML 可解析；字段闭集、类型、格式、H1、编号与实际路径一致 | 当前文件与 Att.02 | 机械解析与路径检查 | 当次身份和载体一致性 | 记录精确问题并暂停受影响载体 |
| 编号与职责 | 登记变化或全量检查时 | key、编号唯一且未改派；登记与实际文件一致 | §8、当前候选集、可回查历史 | 全量扫描与历史核对 | 已扫描范围内的唯一性 | 未覆盖历史进入 gaps，不声明全局通过 |
| 关系与附件 | 读取、修改或提交前 | 目标存在；方向、基数、授权和正文边界一致 | 当前规范、Att.03 与附件全文 | 关系图检查及语义审核 | 当次关系与授权范围 | 停止消费不一致范围并修复 |
| 共同章节结构 | 设计基线确认和提交前 | 前四章、连续领域正文、后四章及结构角色唯一；固定章节的最小必填语义元素可辨认；验证章节使用标准七列表头；03/04 已分别定义其下属编号段的共同结构，存在相应下属规范时也符合对应基础模型 | §7、03/04 与当前全文 | Markdown 标题与验证表头机械解析；固定章节和规则单元要素由 AI 语义审核 | 章节顺序、标题角色、表头及已审核语义元素与下属结构符合性 | 缺少结构、表头、必填语义元素或下属规范不符合时暂停相关规范确认并修复 |

| 规范变更闭环 | Human 决定和提交前 | §11 判断、§12 审核修复、准确候选、授权与受控提交范围一致 | 审核记录、Human 回应、Index、提交回读 | AI 语义核对与 Git Gate | 当次候选与授权范围 | 不进入提交或生效声明 |
| 读取结果 | 每次 L0–L4 读取后 | 层级、原文、行号、来源视图和未展开范围如实 | 当前工作树和读取响应 | Helper 或披露的降级读取 | 当次实际返回范围 | 不扩大为适用、授权或完整性结论 |

机械解析与 AI 语义审核互不替代。测试通过、工具返回 `ok`、文件存在、Human 确认、登记一致或 commit 成功，均只能证明各自范围；缺失的实现和检查明确进入 gaps。

## 14. Human Gate

本规范不新增 00 之外的根 Human Gate。

### 14.1 领域增量事项

以下事项是 00 §4.2 在规范模型领域的具体化：

1. 新建、删除、改名或重排规范模型；
2. 改变当前规则源成立条件或来源视图；
3. 改变身份字段闭集、共同章节结构或关系语义；
4. 改变附件授权、审核义务或其它可强制执行规则；
5. 处理 00 §4.3 受保护内容的修改或合并。

**受保护内容的登记与机械校验归属**（承接 `00 §4.3` 末句「具体登记与机械校验由下位规范承接」）：本规范只规定受保护内容修改**必须经 Human Gate**（上列第 5 项），**不在本规范内登记受保护文件清单，也不在本规范内实现其机械校验**。该登记与机械校验由 `08 §7.6` 承接——它把 `00 §4.3` 的五类映射到 DSH 域的具体位置，并载明「受保护文件清单的变更须经 Human Gate」。**本规范不复制该清单，避免形成第二处登记权威**；消费受保护内容清单时应读取 `08 §7.6`。

提请内容、作用范围和回应效力按 00 §4.4 执行。

### 14.2 决定边界

Human 决定只证明决定及其作用范围，不替代本规范 §13 的验证与语义审核、§9 的成员资格核对或受控提交检查。

## 15. Stop Conditions

本规范不新增根停止类型。

### 15.1 领域触发与影响范围

出现以下任一情况时，按 00 §7.2 暂停最小受影响范围：

1. 规范身份、编号、职责或来源视图不唯一；
2. H1、身份块、登记、路径或正文相互矛盾；
3. 依据、结构关系、附件父权或旧规则去向无法确认；
4. 当前规则源成立条件缺失，却准备宣称成员有效或据其执行；
5. 应完成的独立审核未完成，或真实问题未修复却准备进入 Human 决定；
6. Human 决定、候选、Index 或准备提交的范围不一致；
7. 应改变当前行动的适用约束未实际落实。

### 15.2 暂停期间允许动作

暂停期间只允许不越过停止边界的来源定位、规范回读、差异核对、证据补充、候选修复和分流准备，不得继续消费受影响规范、扩大规则效力声明或创建提交。

### 15.3 恢复与再次触发

恢复条件必须逐项对应触发原因；恢复只覆盖当前依据支持的范围。同一条件恢复后再次触发，按 00 §7.3 进入 Human Gate。

## 16. 反过度设计红线

1. 不为每个概念、字段、小差异或低频场景建立独立规范或附件；
2. 不为满足共同章节结构制造空规则、重复清单或无消费方表格；
3. 不建立独立于当前规范源的第二索引、状态账本、规则数据库或发行快照；
4. 不恢复普通规范生命周期 `status`，也不以其它字段改名重建同类机制；
5. 不要求每次普通编辑都执行全量规范召回、最高风险审核或 Human Gate；
6. 不为未来可能需要的迁移、批量改号、关系类型或协议提前扩展字段；
7. 不把 Code 可解析性、测试便利或 Web 呈现反向提升为规范语义；
8. 不在 01 复制 05 的完整 envelope、09 的解析实现或其它领域规范的细节；
9. 不为统一章节内部写法制造固定句式、固定小标题、逐项仪式或无消费方表格；
10. “保障措施”“待补齐事项”“版本历史”和起草清单不是固定章节，只有本规范职责确有独立消费需要时才进入领域正文。
