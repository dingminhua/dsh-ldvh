# 插件规范载体规范

## 1. 价值判断

运行时机制的文件存在、YAML 可解析、校验器通过，只证明当次载体的机械范围，不能单独证明其中的要求正确、完整、适用或已被遵守，也不能单独证明该载体的效力已经成立。共同规则见 00 §4.6。

## 2. 规范依据

本文直接依据：

1. `ldvh-root`：00 §2.4.1 的两级承载、两个载体形态、运行时机制非规范源成员与准入，00 §2.4.3 的归属指派，00 §2.4.4 的规范内容纪律与「运行时机制面的替代关系形态」之委托，00 §2.5 的检查机制四类，00 §2.9 的下位承接与两级不构成第二套权威，00 §3.2 的根决定清单，00 §3.3 的受保护内容，00 §4.6 的据实声明、00 §4.7 的必停情形与恢复、00 §4.8 的交还与撤回；
2. `specification-model-foundation`：01 §6.1–§6.2 的身份块与解析边界，§7.1–§7.3 的共同章节结构与语义元素的唯一展开，§8.1 的编号登记，§9.0 的归属判断，§9.2 的成立条件，§9.3 的退出与失败边界，§10.1 的依据与引用二分、§10.3 的读取入口边界，§11.3 的修改与取消，§12.1 的实质与非实质修正、§12 的独立审核，§13.1 的机械入口不可用降级，§16 的反过度设计红线；
3. `source-of-truth-traceability`：受控提交与机械守护规范 §5.3 第 5、6 项的检查项与检查范围、§5.5 的 Git Gate 分派与检查范围、§5.7 的提交动作步骤；
4. `check-auxiliary-mechanism-foundation`：检查与辅助机制规范 §6.3 的机械校验能力边界与「判据形态须逐环如实列出」的声明纪律；
5. `dsh-environment-integration`：DSH 环境接入规范 §7.6 的受保护文档路径登记与清单变更的 Human Gate。

YAML 只提供文档语法与承载能力，不取得 LDVH 领域语义权威；它定义一份运行时机制如何被解析为字段与条目，不定义任何要求的含义、效力或适用。

以下不是本文的规范输入：历史版本、已被取代的草稿、本文自身的讨论记录、Code 与测试的输出、工具返回值、对话中的临时表述。

## 3. 职责边界

### 3.1 本文负责

1. 运行时机制是什么、放在哪、身份字段有哪几个、条目容器是什么（§5.1–§5.3）；
2. 承接的登记形态：载体级 `carries` 声明与可寻址锚点的判定口径（§6.2）；
3. 写法要求，以及禁止项中哪些可确定性检查、哪些必须语义审核，并与各自的匹配口径与扫描范围（§5.4、§5.5）；
4. 体量上限、计量口径与拆分规则，含唯一允许的场景路由表（§5.6、§5.7）；
5. 标识与命名空间纪律、载体准入的两层、优先关系、替代关系的形态（§6.1、§6.3–§6.5）；
6. 变更流程、来源缺失与不合格的分界、门禁面与受保护路径边界（§6.6、§6.7）；
7. 校验与验证口径（§7）。

### 3.2 本文不负责

1. 各领域有哪些要求、要求怎么判、违规怎么办——归各份运行时机制本身；
2. 事实对象的公共字段语义、读写契约与关系——归事实源与事实模型基础规范；各事实类型的具体要求——归各事实类型对应的运行时机制；
3. 业务系统的步骤、触发与完成门禁——归各业务系统对应的运行时机制；
4. 受控提交、precheck 与 Git Gate 的机制语义、检查项实现与检查范围——归受控提交与机械守护规范（本文只按 §6.7 陈述运行时机制落在其中的哪一面，不复制其检查逻辑）；
5. 工具的公开操作声明形状——归 LDVH CLI 确定性服务规范；运行时机制不承载该声明，出现声明表即不合格（§5.4 第 3 项、§5.5 乙类第 6 项）；
6. 受保护文档路径清单的具体条目与变更程序——归 DSH 环境接入规范与 00 §3.3（本文只按 §6.7 给出运行时机制面不得违反的三条边界）；
7. 运行时机制读取入口与来源视图的实现形态——本文只规定该入口须满足的条件（§6.1、§6.3），不规定其结构与呈现；
8. AI 对某次行动是否满足某条要求的判断，与 Human 的授权与验收决定。

### 3.3 相邻规范分工与唯一权威

本文是**运行时机制的形态与写法**的唯一权威，不定义任何领域语义。00 的两处指派各有唯一落点：00 §2.4.1 把运行时机制的载体准入、形态与校验指派给开发规范侧的载体契约，由本文承接；00 §2.4.3 把「具体归属判断」指派给下位规范，其中开发规范与事实规范之间的归属由 01 §9.0 承接，运行时机制与开发规范两个载体形态之间的分属由本文承接（§6.3–§6.5）。承接关系由下位侧以其依据声明建立（00 §2.9），本文不据此对 00 的书写施加约束，也不要求 00 指明本文。

分工如下：

- 载体形态、写法、结构、校验口径：以本文为准；
- 领域要求内容：以对应的那份运行时机制为准；
- 同一要求不在两份运行时机制里各写一遍，也不对同一要求给出两种口径（§5.4 第 5 项）；
- **两份运行时机制对同一要求给出不同口径时**：按 00 §4.7 暂停受影响的最小范围，把口径分歧作为 Human 决定候选交还（§8.1（二）第 9 项），不得以任一方的领域边界自行压倒另一方，也不得择一继续；
- 运行时机制与开发规范之间：按 §6.2 的承接登记与 §6.4 的优先关系处置。

## 4. 适用范围

### 4.1 适用对象与场景

本规范适用于：

1. 编写、修改、复核任何一份运行时机制；
2. 实现与测试运行时机制的解析器、校验器与读取入口；
3. 判断某条开发规范条文是否已被某份运行时机制承接，以及该承接是否已产生运行期效果。

本规范用于新增、改写、拆分或废弃一份运行时机制，以及判断某份载体是否形态合格、是否已取得效力。

### 4.2 明确排除与证明边界

明确排除以下内容不由本文承载：各领域要求的具体内容；工具的公开操作声明的具体形状；受控提交与 Git Gate 的检查实现；受保护文档路径清单的具体条目；运行时机制读取入口的实现形态；立项论证与价值论证。

本文不能单独证明的范围见 §1，载体形态与效力成立的分界见 §6.3，本处不复述。

领域要求写成什么样由该领域的规则决定，不由本文决定；本文只决定它被允许以什么形态存在。

## 5. 载体契约

### 5.1 一份运行时机制是什么

一份运行时机制是仓库根 `plugin-specs/` 目录下的一个 YAML 文件，其仓库相对路径即该载体身份字段 `canonical_path` 的值。随包发布时该文件的副本位置属发布与接入面，不由本契约规定；本契约不以任何未在其自身路径上存在的副本为前提，也不以某个假定的载体名为依据。

它由两部分组成：

1. **身份字段**：说明这份文件是什么、归哪一类、什么时候该看它；
2. **要求条目**：一串条目，每条讲清这个领域的一条要求。

它只回答一个问题：**在这个领域，行动要满足什么。**

它是约束**运行期行动**的运行期读物（00 §2.4.1）：只约束开发过程（提交、审核、协作步骤）的要求归开发规范承载，不写进运行时机制（§5.5 乙类第 12 项）。运行期要求与开发过程要求在同一条文里交织、无法按标题路径分开时，须由开发规范侧先写成其自身的边界再承接（§6.2）。

它不回答：这些要求为什么这样定、别的领域怎么定、历史上怎么演变的、代码怎么实现。

### 5.2 身份字段与顶层结构

运行时机制**不参与规范模型的编号登记**：它没有编号，唯一标识是 `spec_key`，该标识在运行时机制的标识命名空间内成立（§6.1）。它的身份字段自成一套，不适用开发规范的身份块 profile。

顶层只有一个映射，取 `ldvh_spec`；不得出现第二个映射，也不得出现 `ldvh_attachment`——本文不设附件载体形态，也不得以任何字段重建该形态。该映射下的字段如下：

| 字段 | 要求 |
|---|---|
| `spec_key` | 必填；运行时机制命名空间内唯一；小写 kebab-case；首次经受控提交落盘后不改派，改派与否以该次提交之后的 git 历史为基线比对 |
| `spec_kind` | 必填；固定取值 `spec`；不设其它取值 |
| `title` | 必填；一句话标题；不含路径分隔符、控制字符与首尾空白 |
| `canonical_path` | 必填；逐字等于 `plugin-specs/<spec_key>.yaml`，且与该文件相对仓库根的实际路径逐字相等 |
| `positioning` | 必填；一句话：这份文件管什么 |
| `scope` | 必填；一句话：什么时候该查阅它 |
| `carries` | 可选；载体级承接声明，锚点列表（形态与判定见 §6.2） |
| `role` | 可选；出现时取值闭集只有 `router`，表示该载体是场景路由表（§5.7）；不写 `router` 以外的值 |
| `requirements` | 必填；要求条目的唯一容器 |

六项身份字段（`spec_key`、`spec_kind`、`title`、`canonical_path`、`positioning`、`scope`）任一缺失或取值不符即判载体不合格；`carries`、`role` 不属身份字段，出现时按各自条款判定。上表之外的顶层字段一律不允许：不得出现 `spec_id`，也不得出现关系、替代、继承、父级一类指向别的载体的字段（替代关系的形态见 §6.5）。无值的可选字段整项省略——不写空列表、不写空字符串、不写占位值。

**`title` 与文件名的关系分两层判**：`canonical_path` 与文件名的对应是可机械判定的（上表第 4 行，文件名因此只能是 `<spec_key>.yaml`）；`title` 是否与文件名所指的领域同一，属语义判定，按 §5.5 乙类第 11 项由独立审核判断，不写成机械不合格。

**要求条目的唯一容器是该映射下的 `requirements` 列表**，不得另设容器；`carries` 承载承接声明，不是条目容器。

### 5.3 要求条目

每条条目由下列三项组成，缺一即判不合格：

| 字段 | 要求 |
|---|---|
| `id` | 本文件内唯一；小写 kebab-case；首次经受控提交落盘后不改派（基线同 §5.2 第 1 行） |
| `title` | 一句可读的标题，说清这条要求管什么 |
| `text` | 条目正文，用自己的话把要求写全 |

条目**不带 `source` 字段**：承接由载体级 `carries` 声明承担（§6.2），不在条目上逐条登记。条目出现 `source` 或其它闭集外字段，按甲类第 7 项（§5.5）判不合格。

条目的排列按**读者什么时候需要它**：先说清这个领域的对象是什么，再说怎么判断，最后说怎么动手；根载体一类不定义对象，直接从跨领域的底线开始。排列不按任何外部编号，不按历史顺序。

一条只讲一件事。**可操作的拆分判据**：一条里出现两个不同的动作对象、或两个不同的触发条件、或一个动作加一条判据，即拆成两条。列出多个并列条件（同一个动作的多个前提）不算拆分。

### 5.4 写法要求

1. **自足**：任何一条都不引用别的运行时机制的章节、编号、文件名或 `spec_key`，也不引用开发规范。需要别处的东西时，在本条目里用自己的话把要什么写出来——写「要一个可解析的子目标」，不写「见某号规范某节」。`carries` 锚点是登记字段而非正文引用，不受本项限制；`role: router` 的条目按 §5.7 第 3 项指向目标路径，是唯一的另一例外。
2. **自己的话**：不写指引语，不用「按某某规范」「见某规范」一类表述替代自足写法。指代本文件内的另一条目时，把要点重述一遍。
3. **只写要求**：可以用散文写「什么算它」「它有哪些状态」「每个状态意味着什么」「要满足哪些条件」；**条目正文不使用 GFM 表格**——字段契约、状态转换、取值闭集与公开操作声明一律不写。提到某个字段名时，只在说明该要求本身必需时出现，不复制写入口 schema 的字段清单。
4. **可判定**：每一条都能回答「某次具体行动是否满足它」。写不出这个问句的条目不成立。
5. **不重复规则**：同一条要求只在一份运行时机制里出现。领域边界不同、且两份条目各自可独立判定时，可以各自规定**不同**的要求，但不得对同一要求给出两种口径；口径分歧按 §3.3 处置，不得择一继续。
6. **不留历史**：不写「以前叫」「迁移前是」「原来没有」「被谁取代」。沿革与替代过程由 git 提交与 Human 决定承载（§6.5）。
7. **不写元规则**：不写「不得自行新增规则」「以本文件为准」这类自指表述；效力边界由上位规范与本文承担。
8. **措辞**：用「须」「不得」「可以」，不用「应当」「应该」「建议」「尽量」。不写「AI 应当审慎判断」这类无法判定的表述。
9. **不留溯源**：运行时机制的字段值不写指向开发期材料的路径或文件名。
10. **文本类别要说清**：提到别的文本类别时写明是「开发规范」还是「运行时机制」，不单独用「规范」指代其中一类（本类文本自称「运行时机制」或直接说「本文件」）。

### 5.5 禁止项

分两类，处置方式不同。

**共同口径（甲类）**：甲类逐条判定，命中即不合格并报出字段路径与命中片段。

- **判定次序**：先整份判定第 7、8 项（结构闭集与体量），再逐字段值判定第 1–6 项；同一字段值命中多项时全部报出，不择一，也不因某项命中而略过其余项。
- **扫描范围**：`ldvh_spec` 下**除 `spec_key`、`canonical_path`、`carries` 之外的全部标量字段值**，含 `title`、`positioning`、`scope`、`role` 与条目的 `title`、`text` 及其它业务字段；**不含注释**——注释不是字段值，不进扫描。`spec_key` 与 `canonical_path` 属自指标识与自指路径，由 §5.2 单独校验；`carries` 是登记字段，其锚点由 §6.2 单独校验；条目 `id` 是标识，由 §5.3 单独校验——这四项不参与甲类 1–6 项扫描。
- **注释不承载要求**：注释内容不进入规则判定；要求只写在条目的 `title` 与 `text` 里。
- **路径匹配**：按路径段边界匹配，不按子串（`plugin-specs/` 目录前缀不构成 `specs/` 路径段）；匹配前先排除载体自身的 `canonical_path`（§5.7 第 5 项的豁免另计）。
- **标识匹配**：按标识符边界匹配，标识前后不得紧邻 `[a-z0-9-]`——`goal-fact-type` 是 `subgoal-fact-type` 的子串，命中后者时不得报作前者。
- **文件名匹配**：以完整文件名为匹配单位（含扩展名）——文件名须逐字出现在被扫描文本中，其前后不得紧邻 `[A-Za-z0-9._-]`。运行时机制的文件名标识部分是其 `spec_key`（`goal-fact-type.yaml` 是 `subgoal-fact-type.yaml` 的子串，命中后者时不得报作前者）；开发规范的文件名形如 `<编号>-<中文标题>.md`，其中文标题部分不作标识切分，整体按完整文件名匹配。甲类第 1 项与第 2 项共用本边界。

**甲类：可确定性检查**

1. 指向别的运行时机制的引用：出现别的载体的文件名、别的载体的 `spec_key`、或指向其 `canonical_path` 的路径；§5.7 第 5 项的豁免是唯一例外；
2. 指向开发规范的引用：出现 `specs/` 路径段、`specs/` 下开发规范的文件名、开发规范的 `spec_key`；本载体自身的 `spec_key` 不属本项（该标识由 §5.2 判定）；
3. 章节号或条款指称：出现 `§` 字符，或「第」加数字加「章」「条」「节」任一形态；
4. GFM 表格语法：字段值中出现以 `|` 起头且含两个以上 `|` 的行；本项只判语法，不判该表的用途；
5. 弱约束措辞：「应当」「应该」「建议」「尽量」；
6. 指引语（闭集）：`见上`、`见前`、`见下`、`如前所述`、`如上所述`、`参照前文`、`上面那几条`、`参见前文`、`另见`、`详见`、`参见`、`见《`；
7. 结构闭集与关系字段（结构检查，不是字段值扫描）：顶层映射唯一且为 `ldvh_spec`；其下字段限于 §5.2 所列；`role` 出现时取值须为 `router`，且全语料 `role: router` 的载体至多一份；条目字段限于 `id`、`title`、`text`。含 `spec_id` 与 `supersedes`、`parent_spec`、`relation`、`related_specs` 一类关系、替代、继承、父级字段；
8. 体量（§5.6）：条目数不在 1–30、单条 `text` 超 600 个 Unicode 码点、整份超 20480 字节（按 §5.6 的字节计量口径），或 `carries` 条目超过 10 条；

**误伤量测**：每新增或修改一条甲类匹配口径，须在当次有效的运行时机制语料上运行并报出**误伤数**——命中但经独立审核判定不属该项情形的条数。误伤数不为零时，须修正口径，或把该项降为乙类交由语义审核判定；不得以「误伤可接受」结案，也不得据未量测的扫描结果声明该项已守护对应形态。依据是 04 §6.3：机械校验只执行规范已定义且可确定校验的内容，判据形态须逐环如实列出。

**乙类：必须语义审核**（由独立审核逐条判定，不声称机械可检）

1. 示例、沿革、「迁移前」「原来叫」「被谁取代」一类表述；
2. 元话语（「本章承接…」「如实登记…」）；
3. 自指元规则（§5.4 第 7 项）；
4. 「每条只讲一件事」是否成立；
5. 「可判定」是否成立；
6. 「只写要求」是否成立：是否夹带了字段契约、状态转换或取值闭集，或是否以条目式声明写出公开操作的操作标识、作用、输入与结果契约（非表格形态的公开操作声明）；
7. 承接的语义相符：`carries` 锚点所列条文，与条目实际陈述的要求是否同一指向。本项是独立审核的必查项，不由锚点解析代替——解析只证明条文被指向，不证明条目真的承接了它；
8. **是否作出承重声明类主张**：即以固定标记 `【承重声明】` 或恢复条件子件 `**恢复条件**：` 承载、并以解除条件为前提的声明（§6.7 第 3 项）。本项不得按字符串命中判不合格：机械只把这两个固定串的出现报为**提示**，供独立审核判断该处是作出主张还是在描述该标记；
9. 是否以「按某某规范」「见某规范」一类指引代替自足表述（甲类第 6 项的语义余项）；
10. 跨载体同题或口径分歧：两份运行时机制是否对同一要求给出两种口径（§5.4 第 5 项、§3.3）；
11. `title` 与文件名所指的领域是否同一（§5.2）；
12. 条目是否属开发过程类要求——只约束提交、审核、协作步骤而不约束运行期行动（§5.1）。

### 5.6 体量上限与计量口径

一份运行时机制：条目数不少于 1 且不超过 30；单条 `text` 不超过 600 个 Unicode 码点（不含 YAML 缩进与注释）；整份不超过 20480 字节。

**字节计量口径**：以该载体文件在仓库中的 UTF-8 字节数为准，含文件头注释、缩进与结尾换行；**顶层 `carries` 登记块不计入**——该块按 YAML 节点边界切出：从 `carries` 键所在行的行首起（不含该行之前的空白），到该键的值节点最后一行的行尾止（含该行的换行符）；该区间内的注释行与空行计入该块、不计入文件总字节，该区间之后、下一个顶层键之前的注释行与空行计入文件总字节。

**承接登记的条数上限**：一份运行时机制的 `carries` 条目不超过 10 条。该上限与字节上限各自独立成立。承接登记条数超限时，按领域边界拆分该载体；不得为压条数而删掉真实承接的条文。

超限即判不合格。超限的处置是按**领域边界拆分**成多份，各自有边界，**不压措辞**。

拆分后不得新建索引类载体；唯一例外是 §5.7 的场景路由表。其余载体不建索引、目录或二级结构。拆分后须仍可被读者按 `positioning` 与 `scope` 发现：每一份的 `positioning` 须写出它接管的领域边界，使读者不依赖索引即可判断该读哪一份。

### 5.7 场景路由表

至多一份运行时机制可作「场景→读哪一份」的路由表。它是拆分之后唯一被允许的导航载体，形态受下列约束：

1. **它自身仍是一份运行时机制**，受 §5.2–§5.6 全部约束，六项身份字段齐备，条目放在 `requirements` 里，受同一体量与禁止项口径；
2. **以 `role: router` 标识**：校验器按该顶层字段判定，全语料 `role: router` 的载体至多一份（「至多一份」由此字段判定，不靠文件名或人工记忆）；
3. **条目的 `text` 只写两件事**：一个读者可辨认的场景，与承载该场景要求的那一份载体的 `canonical_path`——每个条目恰给出一个目标路径。不写要求内容，不写标识解析方式，不写第三层定位；
4. **按路径定位**：路由给出的是路径，不是标识；读取方据路径取载体，不据标识解析（§6.1）；
5. **甲类第 1 项的唯一豁免**：`role: router` 的条目 `text` 中那个唯一的目标路径值，在逐字等于某份现有载体的 `canonical_path` 时不参与甲类第 1 项判定——**该路径值内部的 basename 与 `spec_key` 不计入甲类第 1 项**；该 `text` 出现第二个路径值、或在目标路径值**之外**出现任何载体的文件名、`spec_key`、章节号时，豁免不成立，全部按甲类第 1 项判定；
6. **路径须可解析，且不成二级索引**：目标路径须逐字等于另一份现有载体的 `canonical_path`（形态为 `plugin-specs/<spec_key>.yaml`）；不得指向自身、另一份路由表、目录或章节；不满足即判不合格；
7. **不作要求的唯一来源**：读者仍须读被指向的载体正文；路由表的存在不使该场景的要求成立；
8. **不作承接登记**：路由条目不描述要求，其载体没有 `carries` 不构成来源缺失（§6.2）；
9. **不逃避体量**：路由表自身超限时取消该路由表，或把场景判断改由各载体自身的 `positioning` 与 `scope` 承载；不得以「它只是导航」为由豁免，也不得拆成第二份路由表。

## 6. 承接、准入与变更

### 6.1 标识与命名空间

运行时机制使用**独立的标识命名空间**：`spec_key` 在该命名空间内唯一。

与开发规范的同名标识（例如两份命名空间各自都有一个 `ldvh-root`）**不构成冲突**：两个命名空间各自成立，不做跨命名空间的唯一性判定，也不因同名而要求任一侧改名，也不要求标识全局唯一。

**禁令的准确表述**：禁止**视图同时覆盖两个命名空间的解析与召回入口按标识解析**——这类入口只给标识、不给命名空间限定时，不得返回任一侧的内容：不得择一返回，不得按「先到先得」返回，也不得据同名推定两处是同一份文本；该请求须被拒绝，或要求请求方给出命名空间限定。**下列两类入口不受本项约束**：开发规范的读取入口（视图仅 `specs/`，按 `responsibility_key` 解析且不接受路径，01 §10.3）；`carries` 锚点的登记校验解析（§6.2，锚点以自己的目标 `spec_key` 限定命名空间）。

校验器须有一项检查守住这条：构造一个同时覆盖两个命名空间的视图，仅给标识的解析请求须被拒绝，给命名空间限定或路径的解析须定位到唯一一侧。该检查以用例断言；运行期读取入口未落地时，按 01 §13.1 以人工核对执行并如实披露，不得声称已守护。

### 6.2 承接登记与来源缺失

每份运行时机制在顶层 `carries` 登记它承接的开发规范条文；数量由它实际承担的范围决定，不要求承接整份开发规范，且须在 §5.6 的条数上限内。承接登记是**载体级**的，不逐条登记到条目上。**`carries` 是承接的唯一登记处**：不另立承接清单、来源对照表或第二本账；取证材料不参与运行期判定（§6.4）。

**承接单位是一个标题路径**：一条锚点对应开发规范的一个 H2 或 H3 标题路径（含其整节正文）。某条条文只有一部分面向运行期时，须由开发规范侧把该部分写成它自己的 H2 或 H3 边界后再承接——本文不承认「节内部分承接」的锚点。

**锚点形态**（标题路径形）：

```
<目标 spec_key>::<H2 标题>[/<H3 标题>]
```

1. 前缀是**被承接条文所在开发规范的 `spec_key`**——承接登记跨载体，故前缀写目标而非声明方；
2. 标题逐字一致；写 H3 时须带 H2 祖先，只写 H3 而省略其 H2 祖先，不构成可寻址锚点；`::` 之后的整串**不含 `/`** 时，整串须逐字等于目标载体唯一一个 H2 标题，且该 H2 下有自身正文；**含 `/`** 时，分隔点按目标载体的实际标题集合确定：把整串按各个 `/` 切分点尝试，只有**唯一一个**切分点使前段逐字等于该载体某个 H2 标题、且后段逐字等于该 H2 下的某个 H3 标题时，该锚点才构成可寻址锚点；不存在这样的切分点、或存在多个这样的切分点时，按形态不合格处理；
3. 锚点须解析到目标载体中**唯一既有**的标题路径，且该路径下有本条条文自己的正文；标题按 Markdown 结构识别——代码围栏（``` 或 ~~~）内的 `##`／`###` 行不构成标题，不作为锚点解析目标；
4. 同一份载体的 `carries` 里不得出现重复锚点。

该形态与 LDVH CLI 确定性服务规范 §6.1 的公开操作声明使用同一标题路径形；那处要求锚点前缀为声明方自身，**该前缀约束不适用于本形态**——本形态的前缀是被承接条文所在的开发规范。标题是否带编号前缀按其目标载体自身的结构契约，本文不另设要求（编号前缀只是常规形态，不进入锚点解析判定）。

**形态硬失败**：锚点格式不符（不匹配上述形态）、目标 `spec_key` 不在开发规范语料、标题路径在目标载体中不存在或不唯一、该路径只有子标题而无自身正文（定位为空），任一成立即判**形态不合格**：该载体不得声明生效，按 §9.1 暂停。此类失败不降为提示。

**复验**：被承接的开发规范发生实质修改（01 §12.1）时，其被承接锚点须重跑解析；实质修改后锚点悬空而继续据以主张承接，按形态不合格处理。

**来源缺失**：一份运行时机制没有 `carries` 字段。其严重性为**提示**：不阻断该载体的使用，进入独立审核范围，并在交还中声明；不得在交还中把提示级缺口写成已核实。`carries` 以空列表出现时同时违反 §5.2 的省略规则，按形态不合格判定，不按来源缺失处理。

不得据「条目已写完」推定某条开发规范条文已被承接；未被任何载体承接的面向运行期条文，仍在开发规范面成立并生效（00 §2.4.1）。承接成立是 §6.4 优先关系的共同前提。

### 6.3 载体准入：两层

**（a）形态合格**＝校验器判定通过：§5 的全部形态要求（含 §5.2 的身份与顶层结构、§5.3 的条目三项、§5.5 的甲类各项、§5.6 的体量）与 §6.1 的解析纪律，以及 §6.2 的锚点格式与可解析性，逐项通过。

**（b）效力成立**＝Human 决定 ＋ 建设期独立审核：00 §2.9 规定运行时机制的载体建立须经 Human 决定，并在其进入决定前完成建设期独立审核。00 §2.4.1 称运行时机制「在该载体取得准入后成立」，本节（b）层即该准入。

**与 00 §2.4.1 用词的读法**：00 §2.4.1 把运行时机制的载体准入、形态与校验「规定」给开发规范侧的载体契约与代码校验器；本文把该「规定」读作**规定判据与校验形态**，不读作作出准入决定——判据由本文规定、由校验器执行（（a）层），准入决定本身按 00 §2.9 由 Human 作出（（b）层）。

两层的关系：

1. **校验通过不等于效力成立**：形态合格只证明载体形态（§1），不得以校验通过声明某份载体已生效；
2. **反向亦然**：Human 决定不使形态不合格的载体取得准入；
3. **生效声明的前置**：运行期读取入口与门禁面未落地前，运行时机制不得声明生效。所称落地指该份载体能被读取入口按其命名空间定位并回读，且其改动即按受控提交契约检查（§6.7）。该条件不因校验通过或 Human 决定而视为满足；未落地时以人工核对执行并如实披露（01 §13.1），且「人工核对 + 披露」不构成生效声明。

### 6.4 优先关系

同一主题在两个载体形态各自成文时，**运行期以运行时机制的表述为准**（00 §2.4.1）。

该优先关系**只在下列两项条件同时成立时**成立：该条文已被 `carries` 锚点承接（§6.2），且该运行时机制已取得载体准入（§6.3）。**开发规范侧是否已完成该条文的修订或退出，不是本优先关系的成立条件**——00 §2.4.1 只设上述两项；该侧的条文级处置是 §6.6 第 4 项的义务与交还事项，不改变运行期的取用。

**共存窗口**：开发规范侧仅修订而不退出、两侧仍同题时，本优先关系照常成立；§6.6 第 4 项与 §6.7 的任何处置都不使优先关系在运行期失效。

**可判定方式**：判定依据是 `carries` 锚点集合与锚点解析结果，不是两份文本的措辞比较。锚点所指开发规范条文存在，且该条文的主题与运行时条目同一时，运行期取运行时机制那份；机械只判锚点集合与解析结果，语义同一性由独立审核判（§5.5 乙类第 7 项）。未被任何载体承接的条文，运行期仍取开发规范那份。

本优先关系不延伸到开发过程——开发过程仍由开发规范约束；也不使运行时机制成为规范源成员（00 §2.4.1）。

### 6.5 替代关系的形态

00 §2.4.4 第 4 项把「运行时机制面的替代关系形态」委托给载体契约。本契约给出的形态是：**载体面不设替代关系字段，替代关系由 git 提交与 Human 决定承载**。

1. 身份字段与顶层字段的闭集里没有关系类字段（§5.2）；
2. 一份运行时机制被替代时，替代关系随 Human 决定记录与提交留存，旧载体不再作为生效载体；载体正文不记替代叙述；
3. **判据**：`ldvh_spec` 出现 `supersedes`、`parent_spec`、`relation`、`related_specs` 一类关系、替代、继承、父级字段，按甲类第 7 项判不合格（§5.5）；正文出现「以前叫」「被谁取代」一类叙述，按乙类第 1 项判（§5.5）。

### 6.6 变更流程

1. 一份运行时机制的改动，按受控提交与机械守护规范 §5.7 的三步（暂存、创建、回读）落盘；`关键变更:` 逐条对应改动。本节在上述三步之外另加下列要求，不替代那三步。
2. 改动前须有可展示的候选内容（改后全文或逐条前后对照）。
3. **要求内容**（条目的文字、边界、门禁）与**形态**（身份字段、条目增删、顺序、措辞、`carries` 锚点）两类改动，均须先取得 Human 的明确回应，并在 Human 决定前完成建设期独立审核（01 §12）；新建一份运行时机制同样适用。此即 §6.3 第（b）层。**非实质性修正**（只涉身份镜像、引用、格式或中文语义，不改变职责、边界、据实声明边界或判断结论，依 01 §12.1）不重新开启本款首句对要求内容与形态两类改动的 Human 决定程序；无法确定属实质还是非实质时按实质处理（01 §12.1 末段）。运行时机制属受保护内容（登记见 `10 §7.6`），其任何内容修改按 `00 §3.3` 执行——展示现有内容与准确候选、说明差异与原因、经过独立审核并取得 Human 明确同意，且形成只包含相应受保护文档的独立提交；该程序不因改动属非实质性修正而减免。
4. **承接后的开发规范侧处置**：一条开发规范条文被 `carries` 锚点承接后，该侧的条文级修订或退出按该侧自身的修改与取消程序执行（01 §11.3），不由本契约判定，本契约也不据此建立来源登记表；整份规范不再需要时按该侧的退出程序处置。该侧未完成处置期间：该条文的运行期效果由运行时机制承担（§6.4），开发规范面保留的文本仅在其自身适用面（开发过程与未被承接的部分）成立，不构成运行期的第二口径；**不得**据运行期优先关系推定该侧已修订或已退出，该未处置范围须在交还中如实声明（00 §4.8）。
5. **不合格与提示的分界**：甲类命中（含体量超限）、坏锚点属**不合格**，该次改动不得声明通过或生效；来源缺失属**提示**（§6.2）。该分界与 §7 的验证口径、§9.1 的必停触发一致。
6. 校验不通过时不得声明该份运行时机制已生效。

### 6.7 门禁面与受保护路径

1. **受保护路径清单与运行时机制**：运行时机制路径的登记形态、清单变更程序与受保护内容的修改程序，以 DSH 环境接入规范 §7.6 与 00 §3.3 为准；本文不另立登记形态。该目录下每份载体的存在性与 `canonical_path` 仍按 §5.2 校验。
2. **门禁面**：运行时机制的改动落在 precheck 第 5 项的检查范围内，并触发 Git Gate 分派中的「规范源文件」面——该面含 `specs/**` 与 `plugin-specs/**`（受控提交与机械守护规范 §5.3 第 5 项、§5.5）。运行时机制不是规则源成员（00 §2.4.1），故不落在以 `specs/**` 为承载的「规则源成员变更」面。不得声称运行时机制的改动可按普通提交放行。
3. **承重声明类主张（禁止）**：运行时机制不得作出承重声明类主张——该形态的界定见 §5.5 乙类第 8 项。运行时机制也不得把开发规范侧的检查要求改写成自己的条目（§5.1：开发过程类要求归开发规范）：此类改写会把主张挂在一条不覆盖自身的检查上，形成看起来被机械守护、实际没有的假保障（00 §4.6）。受控提交与机械守护规范 §5.3 第 6 项的检查范围限于 `specs/**`；运行时机制不作承重声明类主张，故该范围不扩到 `plugin-specs/**`。

## 7. 验证与证据边界

| 验证对象 | 成立条件 | 验证入口 | 未满足时的处理 |
|---|---|---|---|
| 载体形态 | 编写或修改任一运行时机制后核对（依据校验器输出与载体回读）：顶层唯一映射 `ldvh_spec`、六项身份字段齐备且取值符合、无闭集外字段与 `spec_id`、`canonical_path` 等于 `plugin-specs/<spec_key>.yaml` 与实际路径、`requirements` 为唯一容器、条目三项齐备、`id` 文件内唯一、体量三项在限内。仅证明当次载体的形态范围；不证明其中要求正确、完整或被遵守 | 校验器运行与载体回读 | 修正后重跑，不得声明已生效 |
| 承接声明的解析 | 建立或修改 `carries` 时核对（依据锚点解析）：每个锚点按 §6.2 的形态解析到目标载体中唯一的既有标题路径，且该路径下有自身正文；无重复锚点；被承接的开发规范实质修改后重跑解析。仅证明锚点可寻址，不证明条目内容真的承接了该条文 | 锚点解析器与开发规范语料比对 | 坏锚点按形态不合格处理并暂停；来源缺失按 §6.2 的提示口径处置 |
| 甲类禁止项的检测力 | 新增或修改甲类匹配口径后核对（依据逐项变异运行）：把载体逐项改成含跨载体引用、含指向开发规范的引用、含 `§` 或条款指称、含 GFM 表格、含弱约束措辞、含指引语、含闭集外字段或关系字段、体量越界（含条目数为零、含 `carries` 条目超过 10 条）、含按 §5.6 计量口径的字节超限的形态时，相应校验项须单独转红。仅证明该形态在该项上的可转红性；不证明其它形态 | 逐条断言的变异运行 | 未证明检测力时不得声称该项已守护对应形态；补用例 |
| 甲类扫描的误伤量测 | 新增或修改甲类匹配口径后核对（依据当次有效语料上的扫描结果与独立审核判定）：已报出误伤数，且误伤已修正或该项已降为乙类。仅证明当次语料上的误伤量；不证明其它语料无误伤 | 语料扫描与审核判定 | 未量测时不得声明该项可用；误伤未处置时不得以其命中结果判定不合格 |
| 乙类语义项与承接语义 | 独立审核时逐条判定（依据载体原文与审核记录）：§5.5 乙类各项逐条给出结论，含承重声明类主张的判断与跨载体口径分歧。仅证明当次审核覆盖的条目；不证明其余条目 | 独立审核记录 | 命中即回退该条目并重审；未审核条目如实登记为未审 |
| 体量与拆分 | 编写、修改或拆分一份运行时机制时核对（依据校验器输出与读者可发现性）：条目数与单条码点在限内；整份字节按 §5.6 的计量口径在限内（`carries` 登记块不计入）；`carries` 条目不超过 10 条；拆分后每份的 `positioning` 写出其接管的领域边界，不依赖索引即可判断该读哪一份。仅证明当次体量与边界声明，不证明拆分后的领域边界划分正确 | 校验器运行与 `positioning`/`scope` 复核 | 超限即不合格；接近上限时先判断是否须按领域边界拆分，不得压措辞，也不得为守住上限删掉判定所需的边界与条件 |
| 标识解析与命名空间 | 建立或修改标识解析入口或校验器时核对（依据用例运行）：两个命名空间并存时，仅给标识的请求被拒绝；给命名空间限定或路径的请求定位到唯一一侧；单命名空间内按 `responsibility_key` 解析与 `carries` 锚点解析不受影响。仅证明当次用例上的判定；不证明所有调用方都按命名空间限定解析 | 用例断言 | 未过时暂停该入口的生效声明并修复 |
| 载体准入与效力成立 | 声明某份运行时机制生效前核对（依据 Human 决定记录、独立审核记录、校验器输出与读取回读）：形态合格；Human 决定与独立审核均已完成且审核在决定之前；读取入口能按其命名空间回读。两层关系与「校验通过不等于效力成立」见 §6.3，本行不复述其展开；仅证明当次两层准入的留痕与形态 | 决定与审核记录核对、校验器运行、读取回读 | 任一层缺失时不得声明生效；已声明者撤回声明并如实披露 |
| 场景路由表形态 | 建立或修改一份路由表时核对（依据校验器输出与路径解析）：`role: router` 在全语料至多一份、受 §5.2–§5.6 全部约束、条目只写场景与一个目标路径、所引路径能解析到另一份实际载体、不指向自身或目录或章节。仅证明当次路由表形态；不证明其中的场景判断正确 | 校验器运行与路径解析 | 不满足者按不合格处理，不得以路由表名义保留要求内容 |
| 规范一致性 | 校验器或本文变化后核对（依据本文条文与校验器行为对照）：校验器的判定与本文 §5、§6 一致，无漂移。仅证明当次对照范围 | 一致性对照复核 | 漂移时暂停该项的「已守护」声明并修复 |

机械结果与语义判断互不替代（01 §7.4 C-6）。校验通过只能证明当次载体的机械范围；本章不能单独证明要求内容正确、效力成立或被遵守，未执行和不可用范围保留为 gaps（降级口径见 01 §13.1）。

## 8. Human Gate

本规范不新增 00 之外的根 Human Gate（01 §7.4 C-3）。

### 8.1 领域增量事项

下列事项是 00 §3.2 根清单在本领域的具体化，以及上位未完整定义的本领域决定事项。

（一）根决定的具体化：

1. 建立或改变运行时机制这一类文本，或改变其标识命名空间与解析纪律（§6.1）——「运行时机制」是 00 §2.4.1 所称两个载体形态之一；
2. 本规范在 01 §8.1 的编号登记行的列入（新建规范属 00 §3.2 根决定）；该登记行列入前，不得据本规范主张其编号登记已成立；
3. 放宽或收紧 §5.5 的甲类匹配口径、乙类项目集合、§5.6 的体量上下限；
4. 改动 §5.4 的写法要求或 §5.7 的路由表例外；
5. 改动 §6.2 的承接登记形态、§6.3 的准入两层、§6.4 的优先关系或 §6.5 的替代关系形态。

（二）上位未完整定义的本领域决定事项：

6. 变更受保护文档路径清单中的运行时机制路径（DSH 环境接入规范 §7.6）；
7. 放弃 §6.7 第 3 项的承重声明禁令，或把受控提交与机械守护规范 §5.3 第 6 项的检查范围扩到 `plugin-specs/**`；
8. 设立运行时机制的附件载体形态（§5.2）——设立前不得设，也不得以其它字段重建该形态；
9. 两份运行时机制对同一要求给出不同口径时的取舍（§3.3、§5.4 第 5 项）；
10. 改变 00 §2.4.1 所称「规定载体准入」的读法（§6.3）；
11. 新增、删除、合并、拆分一份运行时机制，或改动其身份字段（含 `spec_key`）；

### 8.2 决定边界

Human 决定只证明决定及其作用范围，不替代载体形态校验、甲类扫描与误伤量测、乙类语义审核、承接锚点解析或规范一致性对照。

## 9. 必停情形

本规范不新增必停的根触发（01 §7.4 C-4）。

### 9.1 领域触发与影响范围

出现以下任一情况时，按 00 §4.7 暂停受影响的最小运行时机制范围：

1. 载体形态不合格（坏锚点或甲类命中），却准备声明其生效或据其执行；
2. 准备声明某份运行时机制生效，而 §6.3 的两层准入缺其一，或运行期读取入口与门禁面未落地；
3. 某份载体来源缺失（§6.2）却被据以声明该部分已取得运行期效力，或把提示级缺口写成已核实；
4. 准备把同一要求作为要求写进两份运行时机制，或两份运行时机制对同一行动判定不同而准备择一继续（§3.3）；
5. 准备在运行时机制里写入跨载体引用、指向开发规范的引用、GFM 表格、字段契约表、状态转换表、取值闭集表、承重声明类主张、沿革或示例；
6. 要求内容或形态的改动已落盘，而 Human 回应或独立审核尚未取得；
7. 校验器行为与本文条文发生漂移，或同时覆盖两个命名空间的视图按标识择一返回；
8. 场景路由表出现第二份 `role: router`，或路由条目指向自身、另一份路由表、目录、章节或不存在的路径。

### 9.2 暂停期间允许动作

暂停期间只允许不越过停止边界的载体定位、校验器检查、锚点解析、误伤量测、来源核对、修复与验证，不得继续受影响载体的落盘、发布或生效声明。

### 9.3 恢复与再次触发

恢复须修复载体或校验器使其与本文一致，并通过实际受影响的校验、解析、量测与准入留痕；恢复只覆盖当前验证支持的范围。同一停止条件恢复后再次触发时按 00 §4.7 进入 Human Gate。

## 10. 反过度设计红线

1. 不为单份运行时机制建立专用的格式、模板或生成器——载体形态由本文统一规定，各份只填内容；
2. 不在运行时机制里建立索引、目录或二级结构——读者按 `positioning` 与 `scope` 判断该看哪一份；唯一例外是 §5.7 的场景路由表，且不得据它扩张为目录体系；
3. 不为「将来可能有别的形态」预留多套写法或附件分支——本文只承认本文规定的一种；
4. 不因个别载体不合形态或个别误伤而放宽甲类口径——放宽属 Human 决定（§8.1（一）第 3 项），须有 Human 决定与独立审核；
5. 不以拆分替代取舍：拆分按领域边界，不按体量凑数，不得为守住上限而删掉判定所需的边界与条件；
6. 不为来源缺失另立登记表、状态字段或清理队列——提示级缺口由独立审核与交还承载；
7. 不为承接登记另立清单文件或第二本账——载体级 `carries` 是唯一登记处。
