# 插件规范载体规范

## 1. 价值判断

运行时机制的文件存在、YAML 可解析、校验器通过，只证明当次载体的机械范围，不能单独证明其中的要求正确、完整、适用或已被遵守，也不能单独证明该载体的效力已经成立。共同规则见 00 §4.6。

## 2. 规范依据

本文直接依据：

1. `ldvh-root`：00 §2.4.1 的两级承载、两个载体形态、运行时机制不参与开发规范的编号登记与准入，00 §2.4.3 的归属指派，00 §2.4.4 的规范内容纪律与「运行时机制面的替代关系形态」之委托，00 §2.5 的检查机制四类，00 §2.9 的下位承接与两级不构成第二套权威，00 §3.2 的根决定清单，00 §3.3 的受保护内容，00 §4.6 的据实声明、00 §4.7 的必停情形与恢复、00 §4.8 的交还与撤回；
2. `specification-model-foundation`：01 §6.1–§6.2 的身份块与解析边界，§7.1–§7.3 的共同章节结构与语义元素的唯一展开，§8.1 的编号登记，§9.0 的归属判断，§9.2 的成立条件，§9.3 的退出与失败边界，§10.1 的依据与引用二分、§10.3 的读取入口边界，§11.3 的修改与取消，§12.1 的实质与非实质修正、§12 的独立审核，§13.1 的机械入口不可用降级，§16 的反过度设计红线；
3. `source-of-truth-traceability`：受控提交与机械守护规范 §5.3 第 5 项的检查项与检查范围、§5.5 的 Git Gate 分派与检查范围、§5.7 的提交动作步骤；
4. `check-auxiliary-mechanism-foundation`：检查与辅助机制规范 §6.3 的机械校验能力边界与「判据形态须逐环如实列出」的声明纪律；
5. `dsh-environment-integration`：DSH 环境接入规范 §7.6 的受保护文档路径登记与清单变更的 Human Gate。

YAML 只提供文档语法与承载能力，不取得 LDVH 领域语义权威；它定义一份运行时机制如何被解析为字段与条目，不定义任何要求的含义、效力或适用。

以下不是本文的规范输入：历史版本、已被取代的草稿、本文自身的讨论记录、Code 与测试的输出、工具返回值、对话中的临时表述。

## 3. 职责边界

### 3.1 本文负责

1. 运行时机制是什么、放在哪、身份字段有哪几个、条目容器是什么（§5.1–§5.3）；
2. 写法要求，以及禁止项中哪些可确定性检查、哪些必须语义审核，并与各自的匹配口径与扫描范围（§5.4、§5.5）；
3. 体量上限、计量口径与拆分规则，含唯一允许的场景路由表（§5.6、§5.7）；
4. 标识与命名空间纪律、载体准入的两层、替代关系的形态（§6.1–§6.3）；
5. 变更流程与不合格的分界、门禁面与受保护路径边界（§6.4、§6.5）；
6. 校验与验证口径（§7）。

### 3.2 本文不负责

1. 各领域有哪些要求、要求怎么判、违规怎么办——归各份运行时机制本身；
2. 事实对象的公共字段语义、读写契约与关系——归事实源与事实模型基础规范；各事实类型的具体要求——归各事实类型对应的运行时机制；
3. 业务系统的步骤、触发与完成门禁——归各业务系统对应的运行时机制；
4. 受控提交、precheck 与 Git Gate 的机制语义、检查项实现与检查范围——归受控提交与机械守护规范（本文只按 §6.5 陈述运行时机制落在其中的哪一面，不复制其检查逻辑）；
5. 工具的公开操作声明形状——归 LDVH CLI 确定性服务规范；运行时机制不承载该声明，出现声明表即不合格（§5.4 第 3 项、§5.5 乙类第 6 项）；
6. 受保护文档路径清单的具体条目与变更程序——归 DSH 环境接入规范与 00 §3.3（本文只按 §6.5 给出运行时机制面不得违反的三条边界）；
7. 运行时机制读取入口与来源视图的实现形态——本文只规定该入口须满足的条件（§6.1、§6.2），不规定其结构与呈现；
8. AI 对某次行动是否满足某条要求的判断，与 Human 的授权与验收决定。

### 3.3 相邻规范分工与唯一权威

本文是**运行时机制的形态与写法**的唯一权威，不定义任何领域语义。00 的两处指派各有唯一落点：00 §2.4.1 把运行时机制的载体准入、形态与校验指派给开发规范侧的载体契约，本文即该契约；00 §2.4.3 把「具体归属判断」指派给下位规范，其中开发规范与事实规范之间的归属由 01 §9.0 规定。下位承接关系由下位侧以其依据声明建立（00 §2.9），本文不据此对 00 的书写施加约束，也不要求 00 指明本文。

分工如下：

- 载体形态、写法、结构、校验口径：以本文为准；
- 领域要求内容：以对应的那份运行时机制为准；
- 同一要求不在两份运行时机制里各写一遍，也不对同一要求给出两种口径（§5.4 第 5 项）；
- **两份运行时机制对同一要求给出不同口径时**：按 00 §4.7 暂停受影响的最小范围，把口径分歧作为 Human 决定候选交还（§8.1（二）第 9 项），不得以任一方的领域边界自行压倒另一方，也不得择一继续。

## 4. 适用范围

### 4.1 适用对象与场景

本规范适用于：

1. 编写、修改、复核任何一份运行时机制；
2. 实现与测试运行时机制的解析器、校验器与读取入口。

本规范用于新增、改写、拆分或废弃一份运行时机制，以及判断某份载体是否形态合格、是否已取得效力。

### 4.2 明确排除与证明边界

明确排除以下内容不由本文承载：各领域要求的具体内容；工具的公开操作声明的具体形状；受控提交与 Git Gate 的检查实现；受保护文档路径清单的具体条目；运行时机制读取入口的实现形态；立项论证与价值论证。

本文不能单独证明的范围见 §1，载体形态与效力成立的分界见 §6.2，本处不复述。

领域要求写成什么样由该领域的规则决定，不由本文决定；本文只决定它被允许以什么形态存在。

## 5. 载体契约

### 5.1 一份运行时机制是什么

一份运行时机制是仓库根 `plugin-specs/` 目录下的一个 YAML 文件，其仓库相对路径即该载体身份字段 `canonical_path` 的值。随包发布时该文件的副本位置属发布与接入面，不由本契约规定；本契约不以任何未在其自身路径上存在的副本为前提，也不以某个假定的载体名为依据。

它由两部分组成：

1. **身份字段**：说明这份文件是什么、归哪一类、什么时候该看它；
2. **要求条目**：一串条目，每条讲清这个领域的一条要求。

它只回答一个问题：**在这个领域，行动要满足什么。**

它是**行动要求**的读物：条目约束的是行动，运行期行动与开发过程（提交、审核、协作步骤）中的行动同属其适用面，写法上不作区分（00 §2.4.1 的「运行期读物」是该类文本的名称，不收窄其适用面）。同一主题下两类要求交织时，在同一份载体里各自写成可独立判定的条目。

它不回答：这些要求为什么这样定、别的领域怎么定、历史上怎么演变的、代码怎么实现。

### 5.2 身份字段与顶层结构

运行时机制**不参与规范模型的编号登记**：它没有编号，唯一标识是 `spec_key`，该标识在运行时机制的标识命名空间内成立（§6.1）。它的身份字段自成一套，不适用开发规范的身份块 profile。

顶层只有一个映射，取 `ldvh_spec`；不得出现第二个映射，也不得出现 `ldvh_attachment`——本文不设附件载体形态，也不得以任何字段重建该形态。该映射下的字段如下：

| 字段 | 要求 |
|---|---|
| `spec_key` | 必填；运行时机制命名空间内唯一；小写 kebab-case；首次经受控提交落盘后不改派，改派与否以该次提交之后的 git 历史为基线比对 |
| `spec_kind` | 必填；固定取值 `spec`；不设其它取值 |
| `title` | 必填；一句话标题；不含路径分隔符、控制字符与首尾空白 |
| `canonical_path` | 必填；逐字等于 `plugin-specs/<spec_key>.yaml`，且与该文件相对仓库根的实际路径逐字相等 |
| `positioning` | 必填；一句话：这份文件管什么 |
| `scope` | 必填；一句话：什么时候该查阅它 |
| `role` | 可选；出现时取值闭集只有 `router`，表示该载体是场景路由表（§5.7）；不写 `router` 以外的值 |
| `requirements` | 必填；要求条目的唯一容器 |

六项身份字段（`spec_key`、`spec_kind`、`title`、`canonical_path`、`positioning`、`scope`）任一缺失或取值不符即判载体不合格；`role` 不属身份字段，出现时按该行条款判定。上表之外的顶层字段一律不允许：不得出现 `spec_id`，也不得出现关系、替代、继承、父级一类指向别的载体的字段（替代关系的形态见 §6.3）。无值的可选字段整项省略——不写空列表、不写空字符串、不写占位值。

**`title` 与文件名的关系分两层判**：`canonical_path` 与文件名的对应是可机械判定的（上表第 4 行，文件名因此只能是 `<spec_key>.yaml`）；`title` 是否与文件名所指的领域同一，属语义判定，按 §5.5 乙类第 13 项由独立审核判断，不写成机械不合格。

**要求条目的唯一容器是该映射下的 `requirements` 列表**，不得另设容器。

### 5.3 要求条目

每条条目由下列三项组成，缺一即判不合格：

| 字段 | 要求 |
|---|---|
| `id` | 本文件内唯一；小写 kebab-case；首次经受控提交落盘后不改派（基线同 §5.2 第 1 行） |
| `title` | 一句可读的标题，说清这条要求管什么 |
| `text` | 条目正文，用自己的话把要求写全 |

条目**不带 `source` 字段**：载体不登记来源出处，也不在条目上逐条登记依据或出处。条目出现 `source` 或其它闭集外字段，按甲类第 7 项（§5.5）判不合格。

条目的排列按**读者什么时候需要它**：先说清这个领域的对象是什么，再说怎么判断，最后说怎么动手；根载体一类不定义对象，直接从跨领域的底线开始。排列不按任何外部编号，不按历史顺序。

一条只讲一件事。**可操作的拆分判据**：一条里出现两个不同的动作对象、或两个不同的触发条件、或一个动作加一条判据，即拆成两条。列出多个并列条件（同一个动作的多个前提）不算拆分。

### 5.4 写法要求

1. **自足**：任何一条都不引用别的运行时机制的章节号、条款号、文件名或 `spec_key`，也不引用开发规范。需要别处的东西时，在本条目里用自己的话把要什么写出来——写「要一个可解析的子目标」，不写「见某号规范某节」。`role: router` 的条目按 §5.7 第 3 项指向目标路径，是唯一例外。
2. **自己的话**：不写指引语，不用「按某某规范」「见某规范」一类表述替代自足写法。指代本文件内的另一条目时，须在该处把被指条目的判定内容重述出来，使读者不读原条目也能判定——重述至少含被指条目的**判定对象**与**判定结果**（写「同一要求不得在两份运行时机制里各写一遍」，不写「同第 5 项」）。
3. **只写要求**：可以用散文写「什么算它」「它有哪些状态」「每个状态意味着什么」「要满足哪些条件」；**任何字段值都不使用 GFM 表格**——字段契约、状态转换、取值闭集与公开操作声明一律不写（甲类第 4 项按 §5.5 的扫描范围覆盖全部标量字段值，含 `title`、`positioning`、`scope` 与 `role`）。提到某个字段名时，只在说明该要求本身必需时出现，不复制写入口 schema 的字段清单。
4. **可判定**：每一条都能回答「某次具体行动是否满足它」。写不出这个问句的条目不成立。
5. **不重复规则**：同一条要求只在一份运行时机制里出现。**载体不得把开发规范侧或工具侧的检查清单整条复制为自己的条目**——外部检查项的名称、编号与逐项条件不是本领域的行动要求；要求只能按本领域自己的话说出。领域边界不同、且两份条目各自可独立判定时，可以各自规定**不同**的要求，但不得对同一要求给出两种口径；口径分歧按 §3.3 处置，不得择一继续。
6. **不留历史、不举例**：不写「以前叫」「迁移前是」「原来没有」「被谁取代」；也不写示例、样例或演示性段落——要求用陈述句直接给出，实例留在提交说明与审核记录里。沿革与替代过程由 git 提交与 Human 决定承载（§6.3）。
7. **不写元规则、不写元话语**：不写「不得自行新增规则」「以本文件为准」这类自指表述；也不写「本章承接」「本节特此规定」一类描述本文件自身的元话语。要求对行动结果据实披露（如实说明、如实登记为未履行）不属本项。效力边界由上位规范与本文承担。
8. **措辞**：用「须」「不得」「可以」，不用「应当」「应该」「建议」「尽量」。不写「AI 应当审慎判断」这类无法判定的表述。
9. **不留溯源**：字段值不写指向开发期材料的路径或文件名——评审记录、计划、草稿、代码与测试文件的路径都不进载体；需要材料就在条目里把要什么写出来（本项由乙类第 11 项判定）。
10. **文本类别要说清**：提到别的文本类别时写明是「开发规范」还是「运行时机制」，不单独用「规范」指代其中一类（本类文本自称「运行时机制」或直接说「本文件」；本项由乙类第 10 项判定）。
11. **注释只写说明**：YAML 注释可以解释字段含义、说明取值约定、记录编辑提醒，或复述本契约对这一形态的写法要求（例如身份字段有哪几项、`canonical_path` 怎么拼、某字段的取值闭集），但不得承载本领域的要求——把要求写进注释不使它成为一条要求（读取方不执行它、判定也不把它算作要求），而这样写本身构成乙类第 16 项的命中，须按该条处置。两类注释分界：**复述本契约写法要求的说明性注释不属承载要求**（例如「本文件不引用任何其它载体」「身份字段六项必填」「某字段取 `a`／`b` 之一」），那是对本文件写法的说明；载体头部**对本契约写法的**说明性注释属这一类，不构成乙类第 16 项的命中；**把本领域的行动要求写进注释的才属承载要求**，按乙类第 16 项判。按此分界，现有载体的注释只作文件身份说明、复述本契约写法要求与编辑提醒，不承载本领域的行动要求，不属该项命中。要提的要求写进条目的 `title` 与 `text`。

### 5.5 禁止项

分两类，处置方式不同。

**共同口径（甲类）**：甲类逐条判定，命中即不合格并报出字段路径与命中片段。

- **判定次序**：先整份判定第 7、8 项（结构闭集与体量），再逐字段值判定第 1–6 项；同一字段值命中多项时全部报出，不择一，也不因某项命中而略过其余项。
- **扫描范围**：`ldvh_spec` 下**除 `spec_key`、`canonical_path` 之外的全部标量字段值**，含 `title`、`positioning`、`scope`、`role` 与条目的 `title`、`text` 及其它业务字段；**不含注释**——注释不是字段值，不进扫描。`spec_key` 与 `canonical_path` 属自指标识与自指路径，由 §5.2 单独校验；条目 `id` 是标识，由 §5.3 单独校验——这三项不参与甲类 1–6 项扫描。
- **注释不承载要求**：注释内容不进入规则判定——这是一条机械事实（扫描范围不含注释）；但「注释里写了本领域的要求」这件事由乙类第 16 项判，命中按乙类通例处置（不得声明通过、回退并重审；注释情形的回退对象是该注释段，见乙类第 16 项），不得读作「无效所以不判」。一份载体的要求集合是它 `requirements` 中条目的 `title` 与 `text`（写法要求见 §5.4 第 11 项）。
- **路径匹配**：按路径段边界匹配，不按子串（`plugin-specs/` 目录前缀不构成 `specs/` 路径段）；匹配前先排除载体自身的 `canonical_path`（§5.7 第 5 项的豁免另计）。
- **标识匹配**：按标识符边界匹配，标识前后不得紧邻 `[a-z0-9-]`——`goal-fact-type` 是 `subgoal-fact-type` 的子串，命中后者时不得报作前者。
- **文件名匹配**：以完整文件名为匹配单位（含扩展名）——文件名须逐字出现在被扫描文本中，其前一字不得是 `[A-Za-z0-9._-]`，其后一字不得是 `[A-Za-z0-9_-]`；文件名之后紧接的 `.` 在其后一位为空白、行尾或非 ASCII 字符时不算标识延续，那是行文句号，须照常命中。运行时机制的文件名标识部分是其 `spec_key`（`goal-fact-type.yaml` 是 `subgoal-fact-type.yaml` 的子串，命中后者时不得报作前者）；开发规范的文件名形如 `<编号>-<中文标题>.md`，其中文标题部分不作标识切分，整体按完整文件名匹配。甲类第 1 项与第 2 项共用本边界。

**甲类：可确定性检查**

1. 指向别的运行时机制的引用：出现别的载体的文件名、别的载体的 `spec_key`、或指向其 `canonical_path` 的路径；§5.7 第 5 项的豁免是唯一例外；
2. 指向开发规范的引用：出现 `specs/` 路径段、`specs/` 下开发规范的文件名、开发规范的 `spec_key`；本载体自身的 `spec_key` 不属本项（该标识由 §5.2 判定）；
3. 章节号或条款指称：出现 `§` 字符；或出现「第」加一个或多个阿拉伯数字、再加「章」「条」「节」任一形态——数字可以多位，「第」与数字之间、数字与「章」「条」「节」之间可以有空白；构成章节号或条款指称而不属上述形态的写法，按乙类第 14 项判定——该条按**例示**读，不构成穷举，本项不因乙类未列举某形态而把该形态收进本项；
4. GFM 表格语法：任何标量字段值中出现以 `|` 起头、且含两个及以上 `|` 的行（`|a|b|` 即命中）；本项只判语法，不判该表的用途；
5. 弱约束措辞：「应当」「应该」「建议」「尽量」；
6. 指引语（闭集）：`见上`、`见前`、`见下`、`如前所述`、`如上所述`、`参照前文`、`上面那几条`、`参见前文`、`另见`、`详见`、`参见`、`见《`；
7. 结构闭集与关系字段（结构检查，不是字段值扫描）：顶层映射唯一且为 `ldvh_spec`；其下字段限于 §5.2 所列；`role` 出现时取值须为 `router`，且全语料 `role: router` 的载体至多一份；条目字段限于 `id`、`title`、`text`。含 `spec_id` 与 `supersedes`、`parent_spec`、`relation`、`related_specs` 一类关系、替代、继承、父级字段；
8. 体量（§5.6）：条目数不在 1–30、单条 `text` 超 600 个 Unicode 码点，或整份超 20480 字节（按 §5.6 的字节计量口径）；

**误伤量测**：每新增或修改一条甲类匹配口径，须在当次有效的运行时机制语料上运行并报出**误伤数**——命中但经独立审核判定不属该项情形的条数；同时报出语料规模（份数与条目数）。误伤数不为零时，须修正口径，或把该项降为乙类交由语义审核判定；不得以「误伤可接受」结案，也不得据未量测的扫描结果声明该项已守护对应形态。依据是 04 §6.3：机械校验只执行规范已定义且可确定校验的内容，判据形态须逐环如实列出。

**留痕责任**：该留痕由执行当次改动的一方在提交前产生并写出——误伤数与语料规模写进当次交还；留痕须落在可跨会话查阅处：当次改动的独立审核记录，或当次提交说明（`关键变更:` 之外的说明段）；只写在对话交还里不构成留痕。当次改动同时触及校验器时，同一处写进该次改动说明。独立审核可复算并以其结果覆盖。未留痕的，按 §7「甲类扫描的误伤量测」行：不得声明该项可用，也不得据其命中结果判不合格。

**乙类：必须语义审核**（由独立审核逐条判定，不声称机械可检；命中不作不合格，但该次改动不得声明通过，须回退命中条目或该注释段并重审，见 §6.4 第 5 项）

**判定次序**：逐项判定，同一字段值或同一条目同时命中多项时全部报出，不择一，也不因某项命中而略过其余项；乙类第 1 项与第 7 项、第 7 项与第 8 项存在重叠面，重叠时两项都记。

1. 示例、沿革、「迁移前」「原来叫」「被谁取代」一类表述（§5.4 第 6 项）；
2. 元话语（「本章承接…」「本节特此规定…」，§5.4 第 7 项）；要求对行动结果据实披露（如实说明、如实登记为未履行）的表述不属本项；
3. 自指元规则（§5.4 第 7 项）；
4. 「每条只讲一件事」是否成立（§5.3）；
5. 「可判定」是否成立（§5.4 第 4 项）；
6. 「只写要求」是否成立：是否夹带了字段契约、状态转换或取值闭集，是否以条目式声明写出公开操作的操作标识、作用、输入与结果契约（非表格形态的公开操作声明），或整条复制外部检查清单（§5.4 第 3、5 项）；
7. **承重声明类主张**：以「解除某个条件后本要求即成立或不再适用」为前提的声明。`【承重声明】` 或 `**恢复条件**：` 是它的常见承载形态，不是唯一形态——不以标记承载而正文作出同一主张的，本项同样成立（§6.5 第 3 项）。机械只把这两个固定串的出现报为**提示**，是否构成主张由独立审核判断；
8. **覆盖断言**：是否以自身条目的存在声明某项开发期检查已覆盖本载体（例如「本要求已由 precheck 保证」「本载体已被机械守护」「提交门禁会拦住此类改动」）。只写一条开发过程类要求本身不属本项；本项只判是否存在「某检查覆盖本载体」的断言（§6.5 第 3 项）；
9. 是否以「按某某规范」「见某某规范」一类指引代替自足表述，或指代本文件内其它条目而未重述其判定内容（§5.4 第 2 项、甲类第 6 项的语义余项）；本项另收甲类 1–3 收不到的指称：以别的载体的条目 `id`（如「照 `stable-fact-not-auto-object` 做」）、开发规范的中文标题（如「按理念与构成的读法」）或文件名标题部分指代而不把要求写出来，同样按本项判（§5.4 第 1 项）；
10. 是否单独用「规范」指代两类文本之一，未写明是「开发规范」还是「运行时机制」（§5.4 第 10 项）；
11. 是否写入指向开发期材料的路径或文件名，或指向它们的位置（§5.4 第 9 项）；
12. 跨载体同题或口径分歧：两份运行时机制是否对同一要求给出两种口径（§5.4 第 5 项、§3.3）；
13. `title` 与文件名所指的领域是否同一（§5.2）；
14. 章节号或条款指称的非上述形态：以中文数字（「第三条」「第三章」）、全角数字（「第３条」）、带小数点的编号（「第3.2节」）、非「第」字头的编号（「见 3.2 节」「（三）」）或外文编号（`Section 3`）指称某份文本的章节或条款。判定：该写法被用来定位读者要满足的要求即命中；仅作为被引文本的示例出现、不用于定位要求时不命中。此类形态不属甲类第 3 项，须由独立审核判断（§5.4 第 1 项）。**上述形态为例示**：凡构成对某份文本章节或条款的指称、**且被用来定位读者要满足的要求**、而按甲类第 3 项不判的写法（如「见第 3 项」「第 3 款」），均按本项判定；仅作示例或普通叙述、不用于定位要求的不命中（以本项首句的用途判据为准）；
15. 场景路由表的条目是否只写一个读者可辨认的场景与一个目标路径，是否夹带要求内容、标识解析方式或第三层定位（§5.7 第 3 项）。
16. **注释是否承载要求**：注释里是否写了本领域的行动要求（如「每条观察须记全来处与出处」「同一阻碍出现三次以上才入账」）。判定分两步：**先按 §5.4 第 11 项的分界排除**复述本契约写法要求的说明性注释（例如「本文件不引用任何其它载体」「身份字段六项必填」「某字段只能取闭集中的一个」、记录编辑提醒之类）——这类注释不属承载要求，不命中；**再对剩余注释**，把该段单独取出，若它能作为一条**本领域的**行动要求被执行与验收，即命中；仅解释字段含义或取值约定时不命中（§5.4 第 11 项）。命中后的处置：把该注释改为只作说明（改注释即可，载体其余条目不因此回退），该次改动不得声明通过、须重审（§6.4 第 5 项）。

### 5.6 体量上限与计量口径

一份运行时机制：条目数不少于 1 且不超过 30；单条 `text` 不超过 600 个 Unicode 码点（不含 YAML 缩进、注释与块标量结尾的一个换行）；整份不超过 20480 字节。

**字节计量口径**：以该载体文件在仓库中的 UTF-8 字节数为准，含文件头注释、缩进与结尾换行。

**测不出时的处置**：字节数或码点数无法测量（文件不可读、编码不可解析）时，结果是**未判定**——它是与「不合格」并列的第三种结果：不按甲类判不合格，也不得读作通过（不进入 §6.2 的形态层）；实现侧以 `gap` 级结果报出并把判定置为 `undetermined`，该项如实登记为未验证。仅在写作期量不出、未准备声明其生效的，登记未验证即可，不触发必停；**准备声明其生效时**按 §9.1 第 2 项停（两层准入的形态层因此缺项）。

超限即判不合格。超限的处置是按**领域边界拆分**成多份，各自有边界，**不压措辞**。

拆分后不得新建索引类载体；唯一例外是 §5.7 的场景路由表。其余载体不建索引、目录或二级结构。拆分后须仍可被读者按 `positioning` 与 `scope` 发现：每一份的 `positioning` 须写出它接管的领域边界，使读者不依赖索引即可判断该读哪一份。

### 5.7 场景路由表

至多一份运行时机制可作「场景→读哪一份」的路由表。它是拆分之后唯一被允许的导航载体，形态受下列约束：

1. **它自身仍是一份运行时机制**，受 §5.2–§5.6 全部约束，六项身份字段齐备，条目放在 `requirements` 里，受同一体量与禁止项口径；
2. **以 `role: router` 标识**：校验器按该顶层字段判定，全语料 `role: router` 的载体至多一份（「至多一份」由此字段判定，不靠文件名或人工记忆）；
3. **条目的 `text` 只写两件事**：一个读者可辨认的场景，与承载该场景要求的那一份载体的 `canonical_path`——每个条目恰给出一个目标路径。不写要求内容，不写标识解析方式，不写第三层定位；
4. **按路径定位**：路由给出的是路径，不是标识；读取方据路径取载体，不据标识解析（§6.1）；
5. **甲类第 1 项的唯一豁免**：`role: router` 的条目 `text` 中那个唯一的目标路径值，在逐字等于某份现有载体的 `canonical_path` 时不参与甲类第 1 项判定——**该路径值内部的 basename 与 `spec_key` 不计入甲类第 1 项**；该 `text` 出现第二个路径值（同一目标路径出现两次与出现第二个路径值同等处理）、或在目标路径值**之外**出现任何载体的文件名或 `spec_key` 时，豁免不成立，那些出现按甲类第 1 项判；在目标路径值之外出现章节号或条款指称时，豁免同样不成立，按甲类第 3 项判；
6. **路径须可解析，且不成二级索引**：目标路径须逐字等于另一份现有载体的 `canonical_path`（形态为 `plugin-specs/<spec_key>.yaml`）；不得指向自身、另一份路由表、目录或章节；不满足即判不合格；
7. **不作要求的唯一来源**：读者仍须读被指向的载体正文；路由表的存在不使该场景的要求成立；
8. **不逃避体量**：路由表自身超限时取消该路由表，或把场景判断改由各载体自身的 `positioning` 与 `scope` 承载；不得以「它只是导航」为由豁免，也不得拆成第二份路由表。

## 6. 标识、准入与变更

### 6.1 标识与命名空间

运行时机制使用**独立的标识命名空间**：`spec_key` 在该命名空间内唯一。

与开发规范的同名标识（例如两份命名空间各自都有一个 `ldvh-root`）**不构成冲突**：两个命名空间各自成立，不做跨命名空间的唯一性判定，也不因同名而要求任一侧改名，也不要求标识全局唯一。

**禁令的准确表述**：禁止**视图同时覆盖两个命名空间的解析与召回入口按标识解析**——这类入口只给标识、不给命名空间限定时，不得返回任一侧的内容：不得择一返回，不得按「先到先得」返回，也不得据同名推定两处是同一份文本；该请求须被拒绝，或要求请求方给出命名空间限定。**开发规范的读取入口不受本项约束**：视图仅 `specs/`，按 `responsibility_key` 解析且不接受路径（01 §10.3）。

校验器须有一项检查守住这条：构造一个同时覆盖两个命名空间的视图，仅给标识的解析请求须被拒绝，给命名空间限定或路径的解析须定位到唯一一侧。该检查以用例断言；运行期读取入口未落地时，按 01 §13.1 以人工核对执行并如实披露，不得声称已守护。

### 6.2 载体准入：两层

**（a）形态合格**＝校验器判定通过：§5 的全部形态要求（含 §5.2 的身份与顶层结构、§5.3 的条目三项、§5.5 的甲类各项、§5.6 的体量）逐项通过。§6.1 的解析纪律不针对单份载体的形态，按该节单独核对（§7「标识解析与命名空间」行）。

**（b）效力成立**＝Human 决定 ＋ 建设期独立审核：00 §2.9 规定运行时机制的载体建立须经 Human 决定，并在其进入决定前完成建设期独立审核。00 §2.4.1 称运行时机制「在该载体取得准入后成立」，本节（b）层即该准入。

**与 00 §2.4.1 用词的读法**：00 §2.4.1 把运行时机制的载体准入、形态与校验「规定」给开发规范侧的载体契约与代码校验器；本文把该「规定」读作**规定判据与校验形态**，不读作作出准入决定——判据由本文规定、由校验器执行（（a）层），准入决定本身按 00 §2.9 由 Human 作出（（b）层）。

两层的关系：

1. **校验通过不等于效力成立**：形态合格只证明载体形态（§1），不得以校验通过声明某份载体已生效；
2. **反向亦然**：Human 决定不使形态不合格的载体取得准入；
3. **生效声明的前置**：运行期读取入口与门禁面未落地前，运行时机制不得声明生效。所称落地指该份载体能被读取入口按其命名空间定位并回读，且其改动即按受控提交契约检查（§6.5）。该条件不因校验通过或 Human 决定而视为满足；未落地时以人工核对执行并如实披露（01 §13.1），且「人工核对 + 披露」不构成生效声明。

### 6.3 替代关系的形态

00 §2.4.4 第 4 项把「运行时机制面的替代关系形态」委托给载体契约。本契约给出的形态是：**载体面不设替代关系字段，替代关系由 git 提交与 Human 决定承载**。

1. 身份字段与顶层字段的闭集里没有关系类字段（§5.2）；
2. 一份运行时机制被替代时，替代关系随 Human 决定记录与提交留存，旧载体不再作为生效载体；载体正文不记替代叙述；
3. **判据**：`ldvh_spec` 出现 `supersedes`、`parent_spec`、`relation`、`related_specs` 一类关系、替代、继承、父级字段，按甲类第 7 项判不合格（§5.5）；正文出现「以前叫」「被谁取代」一类叙述，按乙类第 1 项判（§5.5）。

### 6.4 变更流程

1. 一份运行时机制的改动，按受控提交与机械守护规范 §5.7 的三步落盘：先**暂存**（第 1 步）；**暂存之后、创建（第 2 步）之前**调用一次 `precheck-git-commit` 并取得 `passed`——该操作的输入是当前 Index diff 与提交 message 文本，`passed` 时返回的 `snapshot_identity` 须与提交后 Git Gate 的同一快照一致；其检查项与判定由该规范 §5.3–§5.5 规定，本文不复制（受控提交与机械守护规范 §5.3 的输入契约、§5.4 的结果契约、§5.5 的快照一致性）。再**创建**与**回读**（第 3 步）。本节在该三步与预检之外另加下列要求，不替代它们。
2. 改动前须有可展示的候选内容（改后全文或逐条前后对照）。
3. **要求内容**（条目的文字、边界、门禁）与**形态**（身份字段、条目增删、顺序、措辞）两类改动，均须先取得 Human 的明确回应，并在 Human 决定前完成建设期独立审核（01 §12）；新建一份运行时机制同样适用。此即 §6.2 第（b）层。**非实质性修正**（只涉身份镜像、引用、格式或中文语义，不改变职责、边界、据实声明边界、可实现性或判断结论，依 01 §12.1）不重新开启本款首句对要求内容与形态两类改动的 Human 决定程序；无法确定属实质还是非实质时按实质处理（01 §12.1 末段）。运行时机制属受保护内容（登记见 `10 §7.6`），其任何内容修改按 `00 §3.3` 执行——展示现有内容与准确候选、说明差异与原因、经过独立审核并取得 Human 明确同意，且形成只包含相应受保护文档的独立提交；该程序不因改动属非实质性修正而减免。
4. **与开发规范面不联动**：载体改动不构成开发规范面条文处置的触发条件，也不在该面建立镜像、来源登记或对照表；开发规范面是需求记录，其条文的取舍与变更按该面自身程序执行。
5. **不合格与不得声明通过的分界**：甲类命中（含体量超限）属**不合格**；乙类命中不作不合格判定，但该次改动同样不得声明通过，须回退命中条目（注释命中时回退该注释段）并重审（§7）。乙类未审或未出结论的范围如实登记为未审。本节与 §7 的验证口径、§9.1 的必停触发一致。
6. 校验或审核未通过时不得声明该份运行时机制已生效。

### 6.5 门禁面与受保护路径

1. **受保护路径清单与运行时机制**：运行时机制路径的登记形态、清单变更程序与受保护内容的修改程序，以 DSH 环境接入规范 §7.6 与 00 §3.3 为准；本文不另立登记形态。该目录下每份载体的存在性与 `canonical_path` 仍按 §5.2 校验。
2. **门禁面**：运行时机制的改动落在 precheck 第 5 项的检查范围内，并触发 Git Gate 分派中的「开发规范与运行时机制文件」面——该面含 `specs/**` 与 `plugin-specs/**`（受控提交与机械守护规范 §5.5）。运行时机制是规范源的承载之一（00 §2.4.1），故不落在以 `specs/**` 为承载的「规则源成员变更」面。不得声称运行时机制的改动可按普通提交放行。
3. **承重声明与覆盖断言（禁止）**：运行时机制不得作出承重声明类主张（形态见 §5.5 乙类第 7 项），也不得以自身条目的存在声明某项开发期检查已覆盖本载体（§5.5 乙类第 8 项）；只写一条开发过程类要求本身不属本项禁止范围。受控提交与机械守护规范 §5.3 第 5 项的 `docs/` 引用检查覆盖运行时机制载体；运行时机制不得作出承重声明类主张，本就不依赖任何针对该类主张的检查。

## 8. Human Gate

本规范不新增 00 之外的根 Human Gate（01 §7.4 C-3）。

### 8.1 领域增量事项

下列事项是 00 §3.2 根清单在本领域的具体化，以及上位未完整定义的本领域决定事项。

（一）根决定的具体化：

1. 建立或改变运行时机制这一类文本，或改变其标识命名空间与解析纪律（§6.1）——「运行时机制」是 00 §2.4.1 所称两个载体形态之一；
2. 本规范在 01 §8.1 的编号登记行的列入（新建规范属 00 §3.2 根决定）；该登记行列入前，不得据本规范主张其编号登记已成立；
3. 放宽或收紧 §5.5 的甲类匹配口径、乙类项目集合、§5.6 的体量上下限；
4. 改动 §5.4 的写法要求或 §5.7 的路由表例外；
5. 改动 §6.2 的准入两层或 §6.3 的替代关系形态。

（二）上位未完整定义的本领域决定事项：

6. 变更受保护文档路径清单中的运行时机制路径（DSH 环境接入规范 §7.6）；
7. 放弃 §6.5 第 3 项的承重声明与覆盖断言禁令；
8. 设立运行时机制的附件载体形态（§5.2）——设立前不得设，也不得以其它字段重建该形态；
9. 两份运行时机制对同一要求给出不同口径时的取舍（§3.3、§5.4 第 5 项）；
10. 改变 00 §2.4.1 所称「规定载体准入」的读法（§6.2）；
11. 新增、删除、合并、拆分一份运行时机制，或改动其身份字段（含 `spec_key`）；
12. 改变 00 §2.4.1 所称「运行期读物」的适用面读法（§5.1）。

### 8.2 决定边界

Human 决定只证明决定及其作用范围，不替代载体形态校验、甲类扫描与误伤量测、乙类语义审核或规范一致性对照。

## 9. 必停情形

本规范不新增必停的根触发（01 §7.4 C-4）。

### 9.1 领域触发与影响范围

出现以下任一情况时，按 00 §4.7 暂停受影响的最小运行时机制范围：

1. 载体形态不合格（甲类命中），或乙类命中而未回退重审，却准备声明其生效或据其执行；
2. 准备声明某份运行时机制生效，而 §6.2 的两层准入缺其一，或运行期读取入口与门禁面未落地；
3. 准备把同一要求作为要求写进两份运行时机制，或两份运行时机制对同一行动判定不同而准备择一继续（§3.3）；
4. 准备在运行时机制里写入跨载体引用、指向开发规范的引用、GFM 表格、字段契约表、状态转换表、取值闭集表、承重声明类主张、覆盖断言、沿革或示例；
5. 要求内容或形态的改动已落盘，而 Human 回应或独立审核尚未取得；
6. 校验器行为与本文条文发生漂移，或同时覆盖两个命名空间的视图按标识择一返回；
7. 场景路由表出现第二份 `role: router`，或路由条目指向自身、另一份路由表、目录、章节或不存在的路径。

### 9.2 暂停期间允许动作

暂停期间只允许不越过停止边界的载体定位、校验器检查、误伤量测、路径解析、修复与验证，不得继续受影响载体的落盘、发布或生效声明。

### 9.3 恢复与再次触发

恢复须修复载体或校验器使其与本文一致，并通过实际受影响的校验、量测与准入留痕；恢复只覆盖当前验证支持的范围。同一停止条件恢复后再次触发时按 00 §4.7 进入 Human Gate。

## 10. 反过度设计红线

1. 不为单份运行时机制建立专用的格式、模板或生成器——载体形态由本文统一规定，各份只填内容；
2. 不在运行时机制里建立索引、目录或二级结构——读者按 `positioning` 与 `scope` 判断该看哪一份；唯一例外是 §5.7 的场景路由表，且不得据它扩张为目录体系；
3. 不为「将来可能有别的形态」预留多套写法或附件分支——本文只承认本文规定的一种；
4. 不因个别载体不合形态或个别误伤而放宽甲类口径——放宽属 Human 决定（§8.1（一）第 3 项），须有 Human 决定与独立审核；
5. 不以拆分替代取舍：拆分按领域边界，不按体量凑数，不得为守住上限而删掉判定所需的边界与条件。
