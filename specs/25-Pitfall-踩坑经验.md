# Pitfall-踩坑经验

## 1. 价值判断

Pitfall 对象存在、处于 active 或形成经验积累，均不能单独证明经验仍然适用、被实际消费或真的避免了损失——经验的价值须在预检、故障调查的真实消费中核对；经验的积累规模也不证明积累效用（积累效用须由实际复用与可观察损耗避免核对）。Pitfall 是经验事实不是规则来源：avoidance 不取得 MUST 级规则权威，需要强制做法时由规范源另行定义（00 §3.2）；该证明边界的共同规则见 00 §4.6（按 00 §2.4.4，立项论证不在正文承载）。

## 3. 职责边界

### 3.1 本文负责

1. Pitfall 类型的对象边界（已验证失败机制的构成、查重、明确不属于本类型的内容）；
2. Pitfall 的身份与载体（多例、平铺单文件、`ldvh-base/pitfalls/pitfall-<uid>.md`）；
3. Pitfall 的字段契约（frontmatter 薄索引闭集、正文固定 H2、字段间不变量）；
4. Pitfall 的状态闭集（active/discarded）与终态处理；
5. Pitfall 的召回与消费点（执行前预检、故障调查、Web 知识库呈现）；
6. Pitfall 的受控操作（创建、勘误与补充级更新、终态流转）。

### 3.2 本文不负责

1. 遵守预检的完整判定逻辑（34 号双源召回系统规范承载，本文只定义消费语义接口）；
2. 行动期的 Pitfall 发现与授权集成（由 00 §3 与本规范共同承接——创建入口有三条：机械通道、主控主动记录通道、Human 直接提出，见 §13；此前「只有 AI 提案与 Human 直接提出两路」的表述已随主控主动记录通道的建立作废）；
3. 调研执行与 Research 类型语义（33 号、24 号承载）；
4. Human 确认经验有效性的过程（00 §3 承载——Pitfall 记录已验证经验，验证本身**不再是入档的前置**：本类型不设入档动作，创建即 `active`，见 §9.2）；
5. Web 呈现的视觉与交互细节（10 号承载）。

### 3.3 相邻规范分工与唯一权威

02 是公共字段与受控读写契约的唯一权威；09 是受控提交的唯一权威；34 号双源召回系统规范是遵守预检判据的唯一权威；24 是 Report 类型语义的唯一权威。本文只定义 Pitfall 类型自身的边界、字段、状态与消费点，不复制相邻规范的规则。

## 4. 适用范围

### 4.1 适用对象与场景

1. 管辖项目中的多例 Pitfall 对象（`ldvh-base/pitfalls/`）；
2. Pitfall 的症状、触发、根因、解决、规避、验证与影响范围记录。

本规范用于 Pitfall 的创建（机械通道自动创建、主控主动记录通道、Human 直接提出）、查重、勘误与补充级更新、终态流转（废弃）与消费（执行前预检、故障调查、Web 呈现）。

### 4.2 明确排除与证明边界

明确排除：未解决的问题（问题没查明/没解决/没验证时不该有 Pitfall——那是当次行动或 Spark）；未发生实际失败的假想风险（预防性记录不成立，必须有实际发生与验证）；已定决策（归 Human 决定与规范源）；已收敛认识（Report）；日志与自由标签。Pitfall 对象存在或状态为 active，不能单独证明经验适用、被消费或避免了损失——这些须由预检与故障调查的真实使用核对。

## 5. 类型定位与价值

Pitfall 是知识层的事实类型：承载已验证失败机制的回溯记录，供前瞻消费。与同层的报告类型分工——报告回答「已收敛的认识是什么」，Pitfall 回答「什么会出错、怎么识别、怎么规避」。

按 02 §6.2 准入六问：跨行动保留——经验基线必须跨会话稳定，否则同一坑重复踩；独立身份与状态——经验有 active/discarded 与适用性衰减，需要独立生命周期；普通文件不能无损承载——无受控写入、无状态闭集、无预检投影；消费价值服务 AI（预检/调查）与 Human（Web 经验库）双轨；维护成本——低频类型，净值为正；类型定义来源——本规范。

## 6. 对象边界

### 6.1 什么构成一个对象

一个 Pitfall 对象 = 一项可独立引用的已验证失败机制：症状识别信号 + 触发条件 + 根因判断 + 实际采用的解决方案 + 规避方式 + 验证说明 + 影响与适用范围。机制必须可独立召回、可独立预检匹配（行动落入影响范围时能指向「哪条 Pitfall」）、可独立终态（不再适用时单独废弃）。

### 6.2 查重

创建前必须查重：对照既有 **`active`** Pitfall 的**归因落点与机制模式**语义比对（锚为「归因落点 + 机制模式」，与 26 §6.2 同口径；§9.3「与既有根因判断相容」即此意）。**查重对象是全部 `active` Pitfall**（**修订**：此前要求把 `draft` 一并纳入查重，理由是防止同一机制每个空闲周期重复形成候选、灌满待确认队列；`draft` 取消后该理由随之消失，而「同一机制不重复成对象」的义务不变——见 §9.2）。同一失败机制的新表现或新触发样例已存在时，不新建——走补充级更新并入既有对象；不同机制的相似症状（根因不同）各自成对象。查重结论必须记录在创建提案中。

**跨类型同源：不并入，但必须留边**。同源的另一条记录若属 Friction，**不得**并入本类型（类型边界不因同源消失），也**不得**因此拒绝本类型的创建——由 **Friction 侧**建立 `paired-with`（26 §11：单侧存储，本侧不写反向边），两侧义务见 26 §9.4 与本规范 §9.4。

**跨类型对照的可执行范围（须写清，避免造出不可执行的义务）**：本条的对照集在**三个入口**上不同——
① **Human 入口**（§13）：可读 Friction 账本，故**必须**对照 `open` 账目（26 §6.2 的对照集）；
② **原机械通道的审核段（已取消）**：该段与经验留观缓冲一并删除。**现存两条创建通道**（主控主动记录通道、Human 直接提出）**均须读 Friction 账本**做跨类型配对核对——原先「审核段被限定为只读缓冲、故不要求读账本」的豁免随该段消失而失效。这是**收紧**：跨类型配对不再有已知缺口。
③ **主控主动记录通道**（§13）：其输入是**主控在当次行动中整理并交出的上下文材料**（由「继承本对话上下文」改为「主控给上下文」——代理不再继承主控的完整上下文，只收到主控挑选的材料），可读 Friction 账本，故按 ① 对照 `open` 账目（26 §6.2）；不得引用与本通道无关的缓冲条目。对照成立时可主张跨类型重复已排除；未对照或未命中者须如实登记。**本通道只写 Pitfall，同源跨角色的 `paired-with` 边由 Friction 侧单侧建立（26 §11、25 §11），本通道不得在 Pitfall 侧写反向边**。

### 6.3 明确不属于本类型

单次调试过程未收敛为经验的内容（留在会话记录）；预防性假设（未实际发生的风险不记录）；已由规范源吸收为强制规则的规避（规则由规范源承载，Pitfall 可作为经验来源被引用但不再独立承担约束）。

## 7. 身份与载体

| 项 | 定案 |
|---|---|
| `fact_type_key` | `pitfall`（类型短名，02 §7.1 值域） |
| 载体 | 平铺单文件：YAML frontmatter（机器权威）+ markdown 正文；`ldvh-base/pitfalls/pitfall-<uid>.md` |
| 权威位置 | `ldvh-base/pitfalls/`；目录基数校验，文件名编码 UID |
| 公共字段 | `object_uid`（UUIDv4，Code 生成）、`created_at`（Code 填写）、`change_log`（Code 托管流水） |

创建与变更权：**终态流转必须经 Human 决定**（经验的废止是 00 §3.2 的领域具体化）；**创建不必**——主控主动记录通道（§13）直接创建 `active` Pitfall，无须事前 Human 确认并保留事后否决权（§16 第 1 项与第 3 项），Human 入口则在确认时落盘为 `active`。勘误与补充级更新走受控更新（change_log 留痕），影响范围的实质变化走新对象。

## 8. 字段契约

frontmatter 闭集（分析性长文本一律住正文，frontmatter 只留薄索引）：

| 字段 | 类型 | 必填性 | 语义 | 约束 |
|---|---|---|---|---|
| `fact_type_key` | string | 必填 | `pitfall` | 唯一合法值 |
| `object_uid` | UUIDv4 | 必填 | Code 生成 | 创建时落定，永不改变 |
| `title` | string | 必填 | 失败机制短标题 | ≤ 30 字；简短识别机制，不复制症状全文；平台/环境专属时凸显平台 |
| `status` | string | 必填 | `active` / `discarded` | 三条通道初态均为 `active`（§13；**取消 `draft`**，见 §9.2） |
| `scope` | string | 必填 | 影响与适用范围陈述 | 与正文字段分工见 §8 字段契约的字段间不变量（差异只报告不阻断）；哪些活动/工具/交互可能落入 + 经验可信复用的边界 |
| `trigger_signal` | string | 条件 | 重新审视信号 | 存在真实重审前提时写（依赖版本变更、环境迁移等）；无则省略（02 §7.1） |
| `urls` | array | 条件 | 支撑经验的外部 HTTP(S) 证据 | 出现时非空；`urls` 非空 ⇒ 正文「证据」段必填 |
| `disposition` | string | 条件 | 终态去向与理由 | 仅 discarded 时必填；说明废弃依据（前提消失/机制不存在/经验失效）；**≤ 200 字符**（终态原因说明的阅读上限，§9.1） |
| `created_at` | RFC3339 | 必填 | Code 填写 | AI 不得填写 |
| `change_log` | array | 条件 | 变更流水 | 首修后必有；每次恰好一条 |

不设 `symptoms`/`trigger_conditions`/`root_cause`/`resolution`/`avoidance`/`validation` 等 frontmatter 字段——六要素是分析主体，住正文；`trigger_signal` 是短句信号例外。

正文固定结构（H1「# 标题」由 Code 从 title 生成、位于围栏后首行且恰好一个，正文自 H2 起；此处不直书 H1 字面以免与身份 H1 重复）：

```
## 症状            ← 失败实际发生后的可观察表现与识别信号（必答：识别信号是什么）
## 触发条件        ← 会触发该机制的前置条件、组合与上下文（必答：什么条件下会触发）
## 根因            ← 当前经验范围内能解释症状与触发的机制判断（必答：机制判断+已观察/未知的区分）
## 解决            ← 已实际采用的处理方式与成功信号（必答：做了什么+成功信号+必要边界）
## 规避            ← 后续识别、预防或安全复用该经验的方式（必答：核对条件+动作+例外）
## 验证            ← 已观察结果、覆盖与未知范围（必答：已观察什么+未覆盖什么）
## 影响与适用范围  ← scope 的展开：何时可能踩到、经验何时可信（必答：何时踩到+何时可信；不要求逐字复现 `scope`，02 §7.1）
## 证据            ← 支撑经验的外部引用（可选；urls 非空时必填）
```

字段间不变量：**正文与字段分工（不再是「载体内聚」）**：frontmatter 字段是索引与摘要，正文是展开，二者**不需逐字一致**（02 §7.1、Human 决定）；差异由读回与诊断层如实报告，不阻断写入。；`disposition` 出现 ⇔ `status=discarded`（`active` 禁现、`discarded` 必填非空）；未知字段不进入 canonical 对象，不得以空字段或占位代替判断。

## 9. 状态与生命周期

状态闭集两值：`active`（经验可信可复用）→ `discarded`（经验不再适用）。

**为什么创建即 `active`（Human 决定，取消 `draft` 待确认态）**：此前 `draft` 是「经验已成文但尚未入档」的候选承载，入档（`draft → active`）是 Human Gate 且以另一主体复现验证为前置。取消它的理由有二：①**经验这一侧的成文与吸收都是 AI 判断**——现由主控派生代理按证据写全七段（原审核段已取消），再吸收时仍是 AI 在核对材料，Human 逐份确认在此不产生额外判断；②**确认形态早已是批次裁定**，而非逐份审读。**摩擦不同**：一笔账的销账牵涉「修不修、怎么修、谁来修」的多次决策，只能由 Human 逐步推进——故 Friction 侧的状态机不受本修订影响。

**取消的代价如实登记**（不得读作「无代价」）：取消独立复现验证这一前置后，复现才能拦下的实质缺陷**直接进入默认候选**，纠正点从「落盘前」挪到「落盘后」，由 Human 走 `active → discarded` 承担（§16 第 1 项）。因此本类型对创建的质量要求**不降**：七段据证据写全、逐字引证、查重、写后精确回读全部保留（§10、§13）。

**不设第二个中间态**：`discarded` 是终态，「已入档待复核」类状态不设（§18 第 1 项）。`discarded` 不进入普通候选（§12）。

### 9.1 状态语义与成立条件

| `status` | 语义 | 必须成立 |
|---|---|---|
| `active` | 经验已验证且仍可信，参与预检与故障调查；创建即为此态（§9.2） | `disposition` 不得出现；正文七段齐备且各段非空；创建的质量闸门见 §10 与 §13 |
| `discarded` | 经验不再适用；保留为历史基线 | `disposition` 必填非空（说明哪个前提消失了）；不进入普通候选 |

**`disposition` 的长度上限（机械校验）**：`disposition` 不超过 **200 字符**（判定单位与本规范 `title` 的同名上限一致，均为 UTF-16 码元计数；实现按 `.length` 判定）。终态原因说明是给后续读者与人扫读的定位信息，不是完整处置记录——完整理由属于正文、`change_log` 或承接对象。超限时拒绝写入（与 §13 的受控写入前置条件同为机械条件，按 02 §10 的公共契约执行），不得截断后写入。

**判定的是数量而非语义**：本上限只约束长度，不判断说明是否据实、充分或与 `status` 相符——后者仍由 §15 的语义核对与 Human 废止授权承担。长度合规不证明终态处置正确。

### 9.2 状态转换

正常转换只有一条：`active → discarded`（**Human Gate：经验废止**，§16 第 1 项；其 `disposition` 记废止依据）。**创建即 `active`**（§13：三条通道的落点相同）——不存在「先落候选、再升格」的两拍，也不存在任何中间态。**终态不可重开，但内容可更正**（Human 决定）：`discarded` 后状态不得再变回 `active`；但终态对象的**内容仍可更正**，走 §9.3 的勘误与补充级更新（含 `disposition` 等字段的修正）——写错的、超限的、与事实不符的终态记录须就地改正，不得靠伪造一次状态转换来洗白，且**不得借更正改变 `status`**。经验的根因判断或解决方案实质变化（不是补充新观察）时创建新 Pitfall；旧对象视情况废弃（前提消失则 discarded+disposition，机制仍存在则保持 active 各自独立）。

### 9.3 勘误与补充级更新

正文错别字、引用修正、表述澄清（不改变机制语义）、**同一机制的新表现、新触发样例补充**（症状/触发条件段的扩展性补充是明确允许项）、**配对复审结论的登记**（§9.4：把「本经验与哪笔债同源、该债消长后本经验的去向」的判定记入正文——配对边不在本侧（§11 单侧存储），故此处只登记判定，不写边），以及**独立复现验证结论的登记**（后该项不再是入档前置，但事后复核仍可产生结论——把另一主体的复现结论记入「验证」段：该补充是对已声称结果的独立核对，不改机制语义、不动根因/解决/规避，属明确允许项）走 02 §10.5 受控更新，change_log 留痕。机械边界：更新后的 `scope` 逐字段不变（变了就不是补充——影响范围实质变化走新对象）；机械比对只覆盖 scope，其余段的语义不变性（补充与实质变更的分界）是 AI 审核义务：根因、解决、规避三段的实质更换不得以补充名义放行，须走新对象路径。补充的判别锚点是**与既有根因判断相容**——新表现、新触发起码要能被当前根因解释；根因解释不了的新触发不是同一机制的样例，是新机制，走查重与新对象。

### 9.4 配对的复审义务

**与 26 §9.4 互补定义，须两侧一起读**。§9.4 只定义 Pitfall 侧的两条义务；Friction 侧的三条在 26 §9.4。**术语**：两侧是**互补**而非「对称」——触发点集合不同，任一单侧都镜像不出另一侧（26 §9.4 同此口径）。

**载体前提（须先读）**：配对边**只在 Friction 侧存储**（§11），本侧不写反向边。「本经验对应哪笔债」由机械反查得到（26 §12 配对反查）。故下列义务的**第一步都是取回**，取不到时按「无配对」处理但须在交还中如实说明反查范围。

| 触发事件 | 本侧义务 | 履行时机与载体 |
|---|---|---|
| 本经验 `active → discarded`（退休） | 先反查配对，再对每条作**去向判定**：**债仍成立**（机制仍存在，只是不再用这套规避）／**债已不成立**（机制前提消失，对应账应收窄范围或走 26 §9.2 废弃）／**待核**（本侧无法判定，移交 Human） | 在退休的**同一次交还**中给出判定与理由；判定可回读于「处置」段或 `disposition`（≤ 200 字符，超长部分写处置段） |

**删去一行**：原表第二行「本经验 `draft → active`（入档）→ 若反查到配对且其账目处于 `resolved`／`voided`，须核对『本经验是否仍与其同源』」随 `draft` 取消而失去触发事件——现在不存在「入档」这一刻。该行的**实质关切**（债已清或记错时配对可能过时）已由下方两行的接收方覆盖：账目被 `resolved`／`voided` 时的本侧复审义务不依赖入档动作，见下。

**两条硬边界（与 26 §9.4 同义）**：① **不产生期限、优先级或排期**——义务只在「本经验被处理时」生效；② **义务不等于决定**——是否退休仍是 §16 的 Human Gate，§9.4 只要求**作出并登记判定**。

**本侧必须有的接收行：账目被 resolved／voided → 本经验复审（复核后补回）**。26 §9.4 第 2 行（本账目 `open → voided`）明写「如原账是误记，则配对可能也错了——**须移交 Pitfall 侧（25 号）复审**」。那半句若在本侧没有接收方，就是一条**悬空义务**：两侧都指向对方，而「原账记错了 → 本经验的根因判断可能同错」这个 §9.4 设立时的核心情形无人负责。故本侧明确设立对应行：

| 触发事件 | 本侧义务 | 履行时机与载体 |
|---|---|---|
| 反查发现配对账目已被 `resolved` | 复审**规避的消费价值**：阻碍已修，本经验的「怎么绕开」是否还需要？**不再需要绕开就该退休**（§16）；仍需绕开（回归、他处复用、同类 API）则保留并注明触发条件已变 | 在下次触及本经验时（§9.3 补充级更新或 §16 流转）复审并留痕；**不自动改状态** |
| 反查发现配对账目已被 `voided`（记错了） | 复审**根因判断是否同错**——原配对基于该账的归因，若该归因被否定，本经验的「根因」可能建立在同一错误前提上；判定同错时按 §9.3 或新对象路径处置 | 同上；**这是 26 §9.4 废弃行「须移交 Pitfall 侧（25 号）复审」的接收方** |

**方向说明（第一版引反了，此处更正）**：26 §9.4 表里的「配对目标被 `discarded`」指的是**本侧的 Pitfall 被废弃**（因为 26 侧的关系目标就是 Pitfall），那正是本节的第 1 行（本经验退休）；而「账目被 resolved/voided」须由本侧接收，即是上面两行。两者**不是同一件事**，不得互相代替。

**为什么不建反向边（须与 §11 一并读）**：若两侧各写一条，同一事实便有两处载体，而任一侧都无法机械判断「另一侧应不该有」，副本可静默分叉且无任何机械信号；单侧存储使「谁记录了这条配对」成为唯一权威。代价是单条读取不自带配对目标（须反查），该代价如实登记。

## 10. 来源与证据

经验来源是实际发生的失败与验证：当次行动的观察、调试与修复记录（会话留痕）是第一来源，Human 提出的历史经验是第二来源。`urls` 的来源回指语义遵循 02 §8.1 公共边界；内部证据以自然语言在验证段交代。验证说明必须区分已观察结果与未覆盖范围——「验证过什么」与「没验证什么」同样必答，不得以验证摘要冒充全面覆盖。

**经验质量四前提与它的承担时点（重定位）**：Pitfall 的准入前提是**失败已发生、根因已查明、解决已采用、验证已有观察**。这四项**不是机械闸门**——`draft` 取消后不存在「入档」这一刻，也就没有任何一个可机械判定的核对时点。它们现在由两处承担：①**创建时**的语义核对（§15「经验质量（创建段）」：七段须据证据写全，逐段回指引证，四前提是这些段落**要回答的内容**）；②**创建后**的 Human 事后判断（Human 若认为某条经验不成立，走 §16 第 1 项的废止）。

**为什么四前提不能机械化（如实登记）**：此前把它下沉到 `draft → active` 的另一主体复现验证，理由是「那是四前提真正能被第三方核对的位置」。取消 `draft` 后这个位置不存在了，而**没有任何替代位置能在不引入新动作的前提下成立**——这是本次修订**真实的代价**，不是「闸门换个地方」。代价的承担方式已写在 §9：纠正点从落盘前移到落盘后，靠 Human 事后 `active → discarded`。

**创建时由什么约束（须逐条成立，不是取消约束）**：`active` 必须能**据证据写出**七段（§8）、各段非空、不以占位符或「待查明」标记冒充；「验证」段须如实区分已观察与未覆盖，其依据是逐字引证的证据片段与来源标识，不得凭记忆补写。**不能据证据写出某段者不构成对象**——这不是四前提闸门，而是 §8 的正文要求本身：写不出症状、根因、解法中的任一段，说明材料不足，对象无从成立。

**四前提与七段不是同一件事**：七段是**载体结构**（任何状态都须满足）；四前提是**准入质量**（现在由 §15 的创建段语义核对与 Human 事后判断承担）。**七段写全不等于四前提已齐**：四段都能写出，根因仍可能只是猜测、解法仍可能只是当时凑巧有效——这正是 §15 把「创建段的经验质量」标为「**不证明**四前提已齐」的原因，也是 Human 事后废止权限存在的理由。

## 11. 关系契约

不使用 `relations` 字段（类型来源声明不采用）。理由：Pitfall 的替代与关联无独立机械消费价值——经验废止的谱系（被什么取代）由 `disposition` 自然语言承载；与某次行动的贡献关联（该经验来自哪次执行）由本规范侧的 `contributed-to` 承载（02 §8.2 第 4 条：反向引用不复制）；与报告类型的关联由正文自然语言交代。确有公共消费价值时由 03 提升公共契约再议。

**同源跨角色的配对不在本侧承载**：一笔阻碍与它的规避经验常同源，配对由 **Friction 侧的 `paired-with`** 记录（26 §11），**Pitfall 侧不写反向边**——02 §8.2 不变量 4 规定反向索引与图导航由 Code/Web 派生、不写回对象；本条若在此存一份副本，同一事实便有两处载体而任一侧都无法机械核对另一侧，副本会静默分叉。

**本侧的义务与取回路径**：「这笔经验对应哪笔债」由机械反查 Friction 侧的 `paired-with` 得到（26 §12 配对反查消费点）；本类型的 §9.4 定义退休时的配对复审义务（须读该反查结果）。**该设计的代价如实登记**：反查须扫 Friction 载体，Pitfall 单条读取不直接携带配对目标——这是「不建第二权威」的必然代价，不是可用性缺失。

## 13. 受控操作

- **创建（分两条通道，落点相同）**：**Human 入口**——Human 直接提出（历史经验口述，AI 整理成提案），经 Human 确认后落盘。**注**：原「执行中发现（当次行动失败已查明验证后形成提案）」一路已改由**主控主动记录通道**承接（Human 决定），不再经本入口——同一触发不得同时走两条通道。**主控主动记录通道**——主控在当次行动中发现一条已查明验证的失败机制时，**整理该次发现所需的上下文材料并交出**，派生一个**以该材料为输入**的代理起草发现记录（修订：原「继承本对话上下文」的供给形态已改为「主控给上下文」——代理零上下文派生，输入全部由主控交付，见 §13「上下文供给」段）（含归属核对结论、查重结论与七段逐段可回指的逐字引证，草稿须先落盘再交出），由主控经本类型的受控创建入口在同一动作内完成写入与写后精确回读，落盘为 `active`。子代理只起草，不写入事实源、不取得授权或完成效力（00 §4.3、02 §6.4）；**主控以落盘草稿为准，不以交付消息为准**——落盘草稿缺失即判无结论，不得以交付消息内容起草或写入。**两条通道的落点相同**：均为 `active`（创建即 `active`，见 §9.2）。机械校验（三通道共用）：字段闭集合法、title ≤ 30 字、urls 形状、载体结构（H2 固定序 + urls 非空时「证据」段必在）、**七段齐备且各段非空**、正文与字段一致性的差异报告（scope 与「影响与适用范围」段的差异**只报告不阻断**，02 §7.1、Human 决定取消逐字义务）。创建后精确回读。**创建时不核对四前提**（§10：四前提不是机械闸门，由 §15 的创建段语义核对与 Human 事后废止承担）。创建的质量约束是「七段据证据写出」（§10）。**创建通道的边界**：不得废止（`active → discarded` 属 §16 第 1 项）。

  **主控主动记录通道的授权、边界与失败处置**（授权与归属结论见 §16 第 3 项，本文不重复展开）：

  **边界**：不得废止——本通道创建的对象其 `active → discarded` 仍属 §16 第 1 项 Human Gate，主控不得自行废止（§17 第 6 项）；不得改写本通道之外的既有对象；不写任何缓冲（经验留观缓冲已取消；摩擦观察缓冲的写入者另有其规定）。

  **归属核对（前置）**：草稿落盘前须已完成事实类型归属核对（02 §6.4 公共次序 / 35 §8.3 领域展开），判定非 Pitfall 归属即不写入、按该去向转交；不得借本通道绕开分流判据。

  **证据基准**：会话留痕为第一来源（§10），七段据证据写全、逐段可回指、逐字引证片段与来源标识复制进正文；不借用缓冲条目（本通道无缓冲）。

  **查重**：按 §6.2 ③ 对照既有 `active` Pitfall 与 Friction `open` 账目；同机制已存在时不新建、如实登记为已存在。

  **失败路径**：起草不合规、归属不符、受控写入失败或写后回读不完整时，**不创建对象**；按 00 §4.7 暂停受影响范围，按 00 §4.8 在同一次交还中如实登记未完成范围与残留风险，交由下一个主控或 Human 处置。**本通道不向任何跨会话失败队列登记**（00 §4.7 不设待处置队列）；失败留痕由当次交还与运行痕迹承载。「无需主控后续跟进」仅指本动作内完成写入与回读，不含跨回合遗留。
  **上下文供给（由「继承」改为「主控给上下文」）**：代理**零上下文派生**，其判断所需输入**全部由主控交付**——主控从当次行动中挑选与该失败机制相关的材料（现象、触发条件、根因判断、已采用的解决、验证方式、影响范围各自对应的原始片段），连同既有 `active` Pitfall 与 Friction `open` 账目的候选投影一并交出。**代理不得自行读取主控的完整上下文**——继承不是本通道的可选供给形态。

  - **为什么不继承**：继承使代理看到主控看到的一切，其中绝大部分与本条失败机制无关；判断质量并不因「看得更多」而提高，反而因材料未经挑选而下降。同时继承把「哪些材料支撑了这条记录」这一信息抹掉了——而 §10 要求七段**逐段可回指**，可回指的前提是材料本身是可枚举的。
  - **不做切分不降低证据要求**：材料仍须**逐字引证**、可回指（§10、§14）；主控交付的材料即本通道的「交付材料」，引证片段必须确实落在其中。**这一条是机械可核对的**——代理引用的片段不在主控交出的材料内时，该次判断不成立。
  - **代价如实登记**：① 主控挑选材料的能力直接决定记录质量——挑漏了关键片段，代理无法补看；② 主控可能交出与本机制无关的材料，此时代理须按 §6.2 查重与归属核对拒绝成文，**不得**为凑满七段而援引无关材料；③ 无水位载体，故「同一机制是否已被记录过」只能靠 §6.2 的查重承担，不存在按区间去重的第二道保险。


  **代价登记（如实）**：本通道的误判面比机械通道更大——由主控在当次行动中自评「已查明验证」，无独立第二主体、无跨运行观察区间；误判对象直接进入默认候选，纠正点仍是 Human 事后 `active → discarded`（§9、§16 第 1 项）。本通道「做到了」的可核对证据仅为受控写入链（字段／结构／原子写／回读）；七段是否据证据、查重是否真做、归属是否正确只能靠 AI 自述 + 事后 Human 废止，按 00 §4.6 在交还时披露未兑现范围。
- **勘误与补充级更新**：02 §10.5 受控更新；CAS 以完整文件为单位；每次恰好一条 change_log；scope 逐字段不变（机械比对，变了拒绝——走新对象路径）。
- **状态流转（一项）**：
  - **终态流转（`active → discarded`）**：Human Gate（§16 第 1 项）；AI 先精确读取 F3 核对 disposition 依据；Code 检查闭集、字段（`disposition` 必填非空且 ≤ 200 字符）、CAS 与回读。**机械通道不得执行本项**。
- **终态更正**（`discarded` 对象）：走 §9.3 勘误与补充级更新；**不得改变 `status`**（§9.2 终态不可重开但内容可更正），每次恰好一条 `change_log` 据实说明更正了什么。
- **删除**：不存在删除操作。discarded Pitfall 随 `ldvh-base/pitfalls/` 保留为历史基线。

## 14. 类型特有验证与类型退出

### 14.1 类型特有验证

- 查重结果记录：创建提案必含查重结论（同机制已存在 → 走补充更新）；
- **正文与字段分工**：frontmatter 字段是索引与摘要、正文是展开，**不要求逐字一致**（02 §7.1、Human 决定取消「载体内聚」义务）；差异由读回与诊断层如实报告，不阻断写入。
- 补充边界：更新的 scope 与 CAS 基线逐字段一致（防影响范围实质变化伪装补充）；
- 终态完整性：discarded 必有非空 disposition；且 disposition 长度不超过 200 字符（§9.1）；
- 状态-终态不变量：`active` 不得带 disposition。

### 14.2 存量对象迁移

v4 仓库的 Pitfall 实例按「v4 存量不迁移」（Human 决定）保留在 v4 历史归档；经验若仍适用，在 v5 以新 Pitfall 重新记录。

### 14.3 类型退出

若 Human 决定取消 Pitfall 类型，须按 02 §11 处理：处理仍适用经验的转移承接与稳定引用，登记变化（01 §8.1）与受影响引用同步，走受控提交。退出属 00 §3.2 根决定。

## 15. 验证与证据边界

| 验证对象 | 成立条件 | 验证入口 | 未满足时的处理 |
|---|---|---|---|
| 载体结构 | 创建、更新或精确读取时核对（依据当前载体与本文 §8）：H1 恰好一个且与 title 一致、正文自 H2 起、H2 固定序完整、各段非空。仅证明当次载体结构合法性 | 机械（结构解析） | 拒绝创建/更新；修复后重走 |
| 正文与字段一致性 | 创建与更新时对照 frontmatter 与正文：**仅报告差异、不阻断写入**（02 §7.1、Human 决定取消逐字义务）。仅证明当次可对照观察，不证明内容正确 | 机械（差异报告） | 如实呈现差异；不拒绝 |
| 补充边界 | 更新时核对（依据更新前后 frontmatter 对照）：scope 与 CAS 基线逐字段一致。仅证明当次更新的补充性质 | 机械（字段比对） | 拒绝；范围变化走新对象 |
| 查重已执行 | 创建时核对（依据提案记录）：创建提案含查重结论。仅证明当次查重范围 | AI 语义审核 | 补查重后重走创建 |
| 终态完整性 | 终态流转时核对（依据对象全文）：disposition 非空且据实，长度不超过 200 字符。仅证明当次终态机械范围 | 机械（字段校验） | 拒绝流转；补齐后重走 |
| 经验质量（创建段） | 创建 `active` 时核对（依据载体与**各通道的证据载体**与逐字引证：Human 入口与主控主动记录通道均为会话留痕逐字引证）：七段**据证据**写出且各段非空、不以占位符或「待查明」冒充；验证段如实区分已观察与未覆盖，依据为逐字引证片段与来源标识；**四前提不在此时机械核对**（见 §10重定位）。仅证明当次对象的据实性与结构合法；**不证明**四前提已齐、根因判断正确 | AI 语义审核（材料可回指性） | 拒绝创建（材料不足以写出某段）；不构成对象者按 §15 如实报告 |

机械结果与语义判断互不替代。本章不能单独证明经验适用、被消费或避免损失——这些由消费点真实使用核对；未实现与不可用范围保留为 gaps。

**删去「经验质量（入档段：四前提）」一行**：该行原以 `draft → active` 提请前为验证时机、以独立复现验证结论为可接受依据。`draft` 与入档动作一并取消后该时机不存在；其核对内容（四前提齐否）改由「创建段」的语义核对与 Human 事后废止承担，代价见 §9。

## 16. Human Gate

本文不新增 00 之外的 Human Gate。领域增量事项（00 §3.2 在 Pitfall 领域的具体化）：

1. Pitfall 的**终态决定**（`discarded`）——`active → discarded`（经验废止）。**创建不在本项**：由 Human 入口或主控主动记录通道（§13）直接创建 `active`，**无须事前 Human 确认**并保留事后否决权；
2. Pitfall 类型本身的取消或合并。
3. **主控主动记录通道的免事前确认与归属裁定**：该通道（§13）与机械通道同样「创建不在本项」，其依据是本节第 1 项既有裁定（创建即 `active`、保留 Human 事后否决权）在该通道上的适用。**Human 裁定**：新增该通道不属 `00 §3.2` 根决定，Human 与 AI 的服务定位与责任关系不变，Human 保留事后废止权；该归属结论按 `00 §3.2` 第二段说明（00 §3.2「单份规范的正文修改不因本条升级为根决定」）由 Human 作出，不由本文自证。代价：无独立第二主体、无跨运行观察区间，误判面大于机械通道，纠正点仍为事后废止（§9、§13）。

**入档动作不存在**：本类型创建即 `active`，不存在「入档成立」这一刻。**该决定属 Human 裁定**（「取消吧，人也不看的，反正之后如果觉得不成立，人是可以取消的」），其代价登记在 §9。

### 16.1 决定边界

Human 决定只证明决定及其作用范围，不替代查重判断、载体校验、预检匹配判断或终态机械校验。

**复现本身没有被禁止**：任何主体仍可在事后对某条 `active` 经验做独立复现，并按 §9.3 把结论登记进「验证」段（那是补充级更新，明确允许）；复现不构成任何创建或流转的阻断条件。

本文成为当前规则源成员时的 01 §8.1 登记与受影响引用同步，按 01 §8.1 的登记义务随本次规范新建一并执行；**25 号的状态闭集修订须同步该登记行**（见 01 §8.1 的 25 号条目）。

## 17. 必停情形

本文不新增根停止类型。领域触发与最小影响范围：

1. 创建时发现同机制 Pitfall 已存在（`active`，见 §6.2；重复经验风险）——未完成查重结论前不创建；
2. **对象不成立却准备创建**——即无法据证据写出七段中的某段（含以占位符或「待查明」标记冒充七段的情形，见 §8）；四前提（失败已发生／根因已查明／解决已采用／验证已有观察）**不属本项**——它们不是机械闸门，见 §10；
3. scope 为空或不可读；
4. 准备以更新改写 scope 实质或更换根因/解决/规避的语义（补充边界违例）；
5. 终态流转 disposition 缺失；
6. **未经 Human 确认直接废止**（授权缺失）——即未经 §16 第 1 项直接把 `active` 流转为 `discarded`；**Human 入口与主控主动记录通道创建 `active` 不属本项**（主控主动记录通道见 §13）；
7. 预检消费时 Pitfall 状态与引用不一致（引用了 discarded 经验为现行依据）。

暂停期间只允许不越过停止边界的证据补取、引用修复、授权补走与条件核实。恢复须与触发原因逐项对应；同一停止条件恢复后再次触发的，按 00 §4.7 的恢复与再次触发进入 Human Gate。

## 18. 反过度设计红线

1. **不设中间态**——Pitfall 一经创建即 `active`，其正文七段必须据证据写全、各段非空、不以占位符或「待查明」标记冒充（§8、§10）。不得增设「待确认」「待复核」类中间态，也不得以任何状态为名保存未查明的失败机制（那属会话记录，不是 Pitfall）——其后的内容更正是勘误与补充级更新的职责（§9.3）；
2. 不设 `symptoms`/`trigger_conditions`/`root_cause`/`resolution`/`avoidance`/`validation` frontmatter 字段——六要素分析主体住正文，frontmatter 只留 scope 薄索引；
3. 不设 `severity`/`priority`/`tags`/`repeatability` 类装饰字段——经验重要性由消费点引用体现；
4. 不建 `relations` 关系边——谱系由 disposition 承载、贡献关联由对象侧承载（02 §8.2 第 4 条）；
5. 不建症状相似度自动匹配——预检与故障调查的匹配是 AI 语义工作（02 §9.2）；
6. 不把 avoidance 提升为规则源——经验约束需强制时由规范源另行定义（00 §3.2）。
