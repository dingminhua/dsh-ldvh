# LDVH CLI规范


## 1. 价值判断

LDVH CLI 解决 LDVH 确定性读取、机械校验和受控操作缺少统一工具入口的问题，使 AI 能经可回指的 DSH 工具取得当次结果、范围、来源与缺口，减少重复封装、传输歧义和工具成功被误当作语义成立的负担。

公开操作声明与能力发现主要支撑 V1 快速定位；共同响应保留来源、范围和缺口，主要支撑 V2 充分理解、V3 边界识别与 V5 据实判断；稳定工具入口与继续入口主要支撑 V4 稳定推进、V6 工作接续和 V7 清晰沟通；结构化范围、来源、缺口与继续入口为 HV1 决策提请清晰可决提供机械输入；受控变更与回读主要支撑 HV2 授权执行受控可续和 HV3 入档闭环节点可验；高保真读取与来源标记间接支撑 V8 持续积累、HV4 积累效用直观可见和 HV5 项目演进脉络可循。

本规范只定义 LDVH CLI 服务入口与共同传输边界；既有行动结构复用、事实语义、Git 溯源、长期效用和 Human 决定由 02、03、04、06、10 与实际工作承接。普通求解、语义判断和 Human 决定不会因 LDVH CLI 存在而变成服务调用。

LDVH CLI 存在、工具注册成功、操作被发现、请求返回或载体被写入，只能证明相应服务与机械范围，不能单独证明领域适用、事实真实、授权成立、验证通过、工作完成或价值产生。

## 2. 规范依据

本文直接依据：

1. `ldvh-root`：00 §3.4 的机械保障、§3.5 的 LDVH CLI 确定性执行、§4–§5 的授权与责任、§7 的防自欺、Stop Conditions 与交还；
2. `specification-model-foundation`：01 §6 的身份块契约、§7 的共同章节结构、§9 的当前规则源条件、§10 的读取层级与最小规则引导、§12 的独立对抗审核；
3. `work-model-foundation`：02 §6–§8 的读/写/编排三能力承载对 LDVH CLI 确定性执行的机制指向，及 §5.1 的非默认仪式边界；
4. `fact-model-foundation`：03 §8.2 的事实消费进入条件与召回分层（本文 §9 的交付前提）、§9.8 的 `partial_scope` 交还形状（本文 §8 的划界对象）。

本文不依赖额外外部语法或行业标准定义 LDVH CLI 服务语义。

04、06–10 是协作来源，不是本文的规范依据；历史规范、平台研究、实现和测试只作为设计输入，不取得规范效力。本规范无结构父规范，`parent_spec` 与 `relation` 均为空字符串且成对保留。发生冲突或权威关系无法确认时，按 00 §7.2 暂停受影响范围并完成对齐。

## 3. 职责边界

### 3.1 本文负责

1. LDVH CLI 作为确定性服务的规范形态与契约唯一实现的共同定位（形态见 §5）；
2. LDVH CLI 自治范围内领域公开操作的稳定身份、声明形状、may_change_state 标记与发现语义；
3. 最小共同请求和响应的语义、响应状态分类（completed/partial/unavailable/rejected/invalid_request/execution_error）、来源与范围保留和缺口交还；
4. LDVH CLI 承载规范读取 L0–L4、事实召回 F0–F4 和事实预热时的共同传输与 envelope 契约；
5. 受控状态变更调用的共同传输边界：来源规则、当前范围、授权、实际变化与回读不可互相省略；
6. 共同反过度设计红线、验证边界、Human Gate 与 Stop Conditions 的承接。

### 3.2 本文不负责

1. 规范、附件、事实类型、事实字段、关系、状态、召回时机、证据充分性或领域操作的参数/结果 Schema；这些由 01、03、各事实类型规范和各自来源承担；
2. 业务系统规范的触发、适用、风险路由、预检落实记录、步骤、完成门禁或降级；这些由 04 与业务系统规范段承担；
3. Git 提交候选机械预检、Git Gate、事实载体、提交消息或 trailer；这些由 06 承担；
4. 工作对象的管辖判定、插件装载、工具的实际注册、引导注入、Host 事件或 Hook 部署；这些由 07/08 承担；
5. Code 模块、工具 schema、缓存、索引、并发、日志、测试、错误栈或 Web 呈现；这些由 09/10 承担；
6. AI 对相关、适用、证据充分、行动允许或完成的语义判断，以及 Human 的取舍、授权、验收决定。

### 3.3 相邻规范分工与唯一权威

领域来源是操作参数、结果与语义的唯一权威；05 是 LDVH CLI 服务入口、能力发现与共同 envelope 的唯一权威；06 是提交预检与 Git Gate 的唯一权威；07 是管辖判定的唯一权威；08 是 DSH 接入的唯一权威；09 只能执行来源已封闭定义的机械规则；10 只负责呈现。实现、缓存、工具描述、测试与 Web 不得反向创造第二规则源。

## 4. 适用范围

### 4.1 适用对象

本规范适用于：

1. AI 经 DSH 原生工具接入面调用的 LDVH CLI 确定性服务；
2. 公开操作声明、能力发现、请求、响应与受控状态变更的共同传输；
3. LDVH CLI 承载规范与事实领域能力时的共同边界。

### 4.2 适用场景

本规范用于 LDVH CLI 操作发现、调用、输入输出传输、范围与来源保留、缺口交还、受控副作用报告和回读定位。

### 4.3 明确排除与证明边界

普通求解、不依赖 LDVH 能力的文件读写和宿主原生工具操作不因本规范存在而强制经过 LDVH CLI；本规范不适用于领域操作参数与结果 Schema、插件装载实现或 Web 呈现。

服务被调用、操作被发现或传输成立，只证明当次服务范围，不单独证明领域适用、行动允许、事实真实、验证通过或操作完成。

## 5. CLI 契约与接入面

### 5.1 规范形态与接入面

LDVH CLI 是 LDVH 确定性服务的规范形态与契约的唯一实现形态。会话内的读写经 DSH 原生工具接入面调用；Git 事件、终端与外部消费方经 CLI 接入；Human 呈现经 Web API 接入面。三个接入面调用同一契约实现，只允许入口输入、响应形式与实际作用不同；任何接入面不得私改契约，接入面之间的一致性由契约测试机械保证（该测试的建立情况按 09 核验并登记；未建立前，不得据本句主张一致性已经成立）。

**三个接入面的实现状态必须分别判断**：本节规定的是规范形态与一致性要求，不等于三个接入面当前均已实现、已接入、当前可用或已通过验证。各接入面的实际实现、装载、可用范围与一致性测试的建立情况，按 08/09 分别核验并登记；核验完成前，不得据本节声明三接入面的一致性已经成立。接入面存在、工具注册成功或命令可用，只证明相应接入口可被发现，不证明任何 LDVH 操作已经实现、装载、可用或通过验证。DSH 已可观察的 `ctx.tools.register` 是工具注册缝；实际工具名称、输入 schema、注册时机、权限/沙箱配置、呈现和错误映射由 08/09 根据 DSH 当前版本核验并定义。

### 5.2 契约边界

1. 每个公开领域操作必须有唯一、稳定的 `operation_key`，但 `operation_key` 不等于 DSH 工具名称、文件路径、模块名、路由 URL 或权限；
2. 操作可以是只读或可能改变状态；“可能改变状态”只描述副作用风险，不证明请求已获授权或实际发生变化；
3. LDVH CLI 只承载来源已封闭定义的解析、定位、过滤、指纹、机械校验等确定性机制的调用，不自行定义 CAS、原子发布或提交语义（这些归 03/06）；不得自行推断领域语义、补造输入、扩张授权或替 Human 作决定；
4. 普通只读检查、普通求解和不依赖 LDVH 能力的业务编辑不因 05 存在而强制调用 LDVH CLI；具体来源将某操作列为不可替代前置条件时，其局部效力来自该来源；
5. 各接入面不得改变共同响应的字段语义、`outcome` 分类与 `scope` 边界；接入面之间的字段集差异必须在 05 授权附件登记，未登记不得据"接入面实现如此"主张契约已满足。

### 5.3 授权附件

本文当前不授权任何授权附件（身份块 `authorized_attachments` 为空）。接入面之间的字段集差异、共同 envelope 的字段闭集与分页、编码或诊断档位等结构化内容，在本文建立授权附件之前，必须按 01 §8.3 走规范修改程序，不得以附件登记替代；未登记前，各接入面不得据"接入面实现如此"主张契约已满足。

已观察到的接入面差异（首个待登记项）：Web API 接入面当前按 `outcome === "ok"` 判定成功，而本文 §8 的结果分类闭集为 completed／partial／unavailable／rejected／invalid_request／`execution_error`，不含 `ok`；该差异在建立授权附件或经 09 登记之前，不得被引为本契约已满足该接入面的证据。

## 6. 公开操作声明与能力发现

### 6.1 领域操作声明

05 定义公开操作的声明形状（本表）；承担某项领域操作语义的当前来源按此形状声明其公开操作，供能力发现定位。同一来源没有公开操作时不创建空表，声明的格式位置由该来源自行安排，05 只约束本表的字段与取值闭集，不强制其它规范的文件结构。

| operation_key | summary | effect | arguments_contract | result_contract |
|---|---|---|---|---|
| `<小写 ASCII kebab-case，全局唯一>` | `<操作提供什么服务，不声明可用或完成>` | `<read 或 may_change_state>` | `<本来源或其授权附件的唯一输入章节>` | `<本来源或其授权附件的唯一结果章节>` |

`operation_key` 只稳定识别服务行为，不能从名称推导适用、授权、实现、验证或完成。`arguments_contract` 和 `result_contract` 必须以 `<spec_key 或 attachment_key>::<精确标题文本>` 回指同一当前来源或其已授权附件中的唯一章节。**标题文本须采用可机械寻址的层级路径形**（`<H2 标题>` 或 `<H2 标题>/<H3 标题>`，各级标题均含其编号前缀、逐字一致）；只写 H3 或更深标题而省略其 H2 祖先不构成可寻址锚点，等于未声明。解析失败、重复 key、来源未生效、输入/结果章节缺失或与声明不符时，必须暂停发现并按 00 §7.2 暂停调用。

**发现的机械义务**：能力发现入口必须**实际解析**来源声明并据其结果填充分类，不得以常量或假设值代替解析结果。无法解析来源声明时，该操作只能出现在诊断范围并附带精确原因，不得作为已声明操作返回；发现入口若以固定值声明某操作「已声明」而不解析其来源，即属本规范未满足的声明。故本款为**条件式要求**：在发现入口实际解析来源声明之前，不得据本规范主张任何接入面的 `已声明` 分类已契约成立；该前提是否成立按 `01 §7.2` 由读取时的观察取得，本款不陈述其当前状态。

05 只定义声明形状，不登记 01、03、04、06 或其它来源具体操作的字段。领域来源中的示例、内部函数、工具注册、测试、缓存或草案表格都不是公开声明。

### 6.2 能力发现

LDVH CLI 必须提供一个只读的能力发现入口，返回当前规则源可定位的公开操作及其来源、effect、所需输入类别、实现观察和未完成范围。发现至少区分：

- **已声明**：当前来源存在符合 §6.1 的操作声明；
- **已实现**：当前实际环境可定位对应实现；
- **当次可调用**：声明、实现、必要输入、工作对象、能力、来源要求与来源要求的授权范围均在当前请求范围内成立；
- **部分可调用**：独立子范围中可调用与不可调用范围可区分；
- **不可用**：没有实现、必要输入/能力/来源/授权前提缺失或零个请求子范围可调用。

以上是能力发现的 `availability` 描述，不是调用结果分类；发现入口可枚举全体操作或针对单一操作检查。每次调用的 `outcome` 仅使用 §8 的 `completed`、`partial`、`unavailable`、`rejected`、`invalid_request` 或 `execution_error` 分类，两者不得混用。

未提供完整领域输入时，能力发现只能报告已声明/已实现与需要补充的输入，不能把未知写成不可用或可调用。当次可调用只证明 LDVH CLI 可以尝试按服务契约处理请求，不证明领域适用、Human 授权、技术验证或上层完成。

操作目录不是行动许可白名单：操作不存在、未实现、不可用或请求无效，只说明 LDVH CLI 无法按该操作承接请求；不自动禁止适用规则允许的普通求解或其它能力。反之，来源明确要求某操作且它不可用时，按该来源暂停、缩小或分流。

## 7. 最小共同请求语义

每次 LDVH CLI 调用都应由 DSH 工具输入承载以下最小语义；实际工具 schema 只登记当次操作确有需要的字段，不为对齐表格填充无关字段：

| 内容 | 用途与边界 |
|---|---|
| `operation_key` | 识别已声明的领域操作；服务级能力发现可不针对单一领域操作。 |
| `work_object_locators` | 需要项目或对象专属信息时提供原始定位符；不得由 LDVH CLI 以缓存、同名路径或默认工作区猜测未提供的对象。 |
| `arguments` | 由领域来源定义的结构化输入；自由文本不得绕过领域 Schema、来源条件或授权边界。 |
| `observed_context` | 操作确有需要的当次可观察环境、能力或签名输入；必须说明来源，不能成为稳定事实或替代回读。 |
| `authorization_reference` | 仅在领域来源要求授权时引用已存在的 Human 决定及其作用范围；不证明技术结果或自动扩权。 |

`responsibility_key` 是规范/附件读取操作的领域 `arguments` 字段，取值即目标 `spec_key` 或 `attachment_key`，与 01 §10.3 的定义同义。01 定义 L0–L4 的读取层级、标题/行号定位与具体读取参数；05 只保证请求和响应不会改写该语义，不新增或重定义读取参数。

共同请求字段是否裁剪、响应聚合或诊断档位是否需要，由 08/09 按各接入面（DSH 工具、CLI、Web API）的实际承载与实际消费定义，05 只定义其共同语义。

请求缺少必需输入、范围无法唯一定位、来源冲突或输入无法按操作契约解析时，LDVH CLI 必须在执行任何领域副作用前返回具体缺口或无效请求；不得静默从历史会话、缓存、猜测、环境变量或未声明的默认值补齐。

## 8. 最小共同响应语义

每次 LDVH CLI 响应必须同时提供机器可读结果和可供交还的摘要；两者不得矛盾。下表定义共同语义要求，最小字段闭集只在有实际实现与独立消费需要时由 05 授权附件或 09 登记。共同响应至少表达：

| 内容 | 要求与边界 |
|---|---|
| `operation_key` 与服务结果 | 回显服务发现或实际调用的标识和结果分类；无效标识的回显不使其成为公开操作。 |
| `result` | 仅由领域来源定义的结果；没有领域结果时明确为空，不在共同层伪造领域字段。 |
| `scope` | 明确请求、已完成和未完成的对象、页、检查或动作范围；“已完成”只表示本次服务处理范围，不表示上层任务完成。 |
| `sources` | 保留实际使用的规则、事实、Human 决定、配置、观察或实现依据及其可定位信息；不由 05 建立权威优先级。 |
| `gaps` 与未验证范围 | 明确缺失的输入、能力、来源、覆盖、实现或验证，而不是用空数组、工具成功或已完成子范围代表整体完成或验证通过。 |
| `changes` 与回读定位 | 可能变更状态的操作只报告实际发生的变化、实际定位与来源要求的回读；零写入、拒绝或失败不得伪称变化。 |
| `verification` | 只报告当次实际执行的机械校验、范围和结果；不把检查存在或通过写成领域语义、Human 决定、价值或整体完成。 |
| `follow_up` | 给出可继续读取、分页、回读、修复、分流或 Human 决定入口；没有可信入口时如实为空。 |

`completed`、`partial`、`unavailable`、`rejected`、`invalid_request` 与 `execution_error` 必须可区分：

- `completed`：请求范围已全部完成，且无未完成或未验证范围；仅当 `scope` 的未完成项与 `gaps` 均为空时方可使用，不得以工具调用返回、进程正常退出或子范围完成冒充；
- `partial`：已实际完成独立子范围，但仍有明确未完成或未验证范围；
- `unavailable`：当前来源、实现、能力、环境、输入或授权前提不足，未能按请求范围提供服务；
- `rejected`：已形成足够输入，但来源已定义的机械条件、CAS、范围或权限检查拒绝操作；
- `invalid_request`：请求形状或共同/领域输入不能解析或不符合契约，领域副作用为零；
- `execution_error`：服务开始后发生未由领域契约吸收的错误，必须报告实际已发生副作用与残留范围，不得暗示可无条件重试。

上述分类是 LDVH CLI 服务响应状态，区别于 03 §9.8 事实域的 `partial_scope` 交还形状；后者是否进入共同 envelope 字段闭集由 05 授权附件按 01 §8.3 登记，服务状态与领域结果不互相替代。

具体响应字段闭集、枚举、分页 cursor、编码与 DSH 工具 schema 只在有实际实现和独立消费需要时，通过 05 授权附件或 09 定义；在此之前不得用虚构的全局 DTO、日志、版本协议或错误码表填充本文。

## 9. 读取、预热与事实操作协作

### 9.1 规范读取

LDVH CLI 在承载由 01 定义的规范读取领域操作（`read-specification-candidates` 与 `read-specification-content`）时，不改变其 L0–L2 与 L3/L4 分工，保留 01 定义的 `responsibility_key`、`heading_path`、`start_line`、`end_line` 与未展开范围，不让工具自动展开全部依据或把候选写成适用。

### 9.2 事实召回和预热

LDVH CLI 仅承载由 03 定义的 F0–F4 事实读取、草案、创建、更新、回读和完整性审计等领域操作的传输，不在 05 中自行定义或扩张其领域契约。F0–F2 候选、预热卡、分页结果或概率提示不得被写成 F3/F4 已读、事实适用、行动允许或事实声明。

在 03 的事实消费进入条件、具体类型来源的召回时机和 08 的宿主注入边界均成立时，LDVH CLI 可以交付带来源与指纹的候选、卡片或恢复入口。预热在传输与注入时的实质行为约束严格遵守 03 §8.2 的限制，LDVH CLI 仅提供传输载体；超预算、分页、不可用和未展开范围必须据实返回 partial/unavailable。

### 9.3 受控状态变更

可能变更状态的操作只能在领域来源已定义操作、实际范围、机械条件与授权要求均满足时执行。05 不自行定义事实创建、更新、删除或提交语义；这些语义分别由 03 和 06 定义，05 仅提供 `may_change_state` 标记和共同传输支持。

状态变更响应中的成功只证明实际服务结果和来源要求的回读/检查范围。若写后精确回读、已触发的完整性审计或其它来源要求未完成、partial、unavailable 或残留无法排除，必须停止受影响的后续写入、提交和成功声明，按 00 §7.2 暂停受影响范围，并按 00 §7.4 与领域来源交还。

## 10. 验证与证据边界

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 操作声明 | 声明形成或能力发现调用时 | `operation_key`、effect 与输入/结果章节可唯一回指当前来源 | 声明表与目标来源正文 | 声明解析与回指检查 | 公开服务身份与领域契约定位；不证明已实现、当次可调用、适用或授权 | 解析失败时暂停发现并按 00 §7.2 暂停调用 |
| 工具注册 | 插件装载后 | DSH 当前环境已实际注册目标工具 | 宿主注册观察（承载能力由 08/09 核验；验证权威与入口归 08 §8 工具注册行，此处只验证 LDVH CLI 服务工具面语义） | 注册状态检查 | 当前宿主工具面可发现；不证明操作领域语义、能力有效或完成 | 未注册时按不可用交还，不伪造回执 |
| 能力发现 | 每次发现调用后 | 来源、实现和当次前提按实际观察报告 | 发现响应 | 发现结果核对 | 当次发现范围与缺口；不证明领域适用、Human 授权或技术验证 | 如实报告缺口，不把未知写成不可用或可调用 |
| 只读响应 | 每次只读调用后 | 读取范围、来源和未完成范围如实返回 | 响应与来源回指 | 响应核对 | 当次读取/候选/披露范围；不证明语义相关、适用或全文已读 | 未完成范围按 partial/unavailable 交还 |
| 状态变更响应 | 状态变更调用后 | 来源定义的前提、实际变化、回读与已触发检查均已完成 | 写入结果、回读与检查记录 | 写后回读核对 | 当次实际变化和机械结果；不证明自然语言事实、Git 提交、Human 决定或上层完成 | 停止后续写入、提交与成功声明 |
| partial/unavailable 交还 | 结果非完整成功时 | 已完成、未完成、未验证和残留范围可区分 | 响应的 scope 与 gaps | 交还结构核对 | 当次服务所及与不及的明确边界；不证明不存在风险或可无条件恢复 | 保留缺口并给出可继续入口，无入口时如实为空 |

上表“成立条件”是机制的设计意图，其中“工具注册”“能力发现”的机械可判定性依赖 08/09 按 DSH 当前版本核验 DSH 工具 schema（具体协议名称由 08 核验登记）后成立；核验通过前，对应“成立条件”只代表来源要求，不当作已实现事实。每项机制必须能回答“防的是 AI 用哪种具体方式骗过自己”，答不出的不引入：

| 机制 | 对治根缺陷 | 防 AI 骗过自己的具体方式 |
|---|---|---|
| 能力发现与当次可用性 | 上下文依赖 | 防止 AI 在输入不全、实现缺失或环境未接入时，把“操作存在”脑补成“可调用可用”，或用缺失输入/能力去盲调用 |
| 共同请求/响应 envelope 与 gaps | 概率性输出 | 防止 AI 用空数组、局部成功、`{ok:true}` 或已完成子范围冒充整体完成或验证通过 |
| 受控状态变更与写后回读 | 概率性输出 | 防止 AI 把“写入接口返回成功”当成“载体已正确落盘且当前”，绕过精确回读与来源要求的完整性审计 |
| partial/unavailable 交还 | 无连续状态 | 防止 AI 把“没做完/没查到”吞成“已覆盖”或“无风险”，掩盖残留与未验证范围 |

机械结果与语义判断互不替代。05 不建立价值审计报告或外部过程证明。LDVH CLI 共同响应是单次服务调用的机器可读结果，只交还当次已证实、未证实与残留风险；它是主控形成 00 §7.4 Output Envelope 的输入之一，不替代主控交还。共同响应附带的人类可读摘要必须与机器结果一致；本章不能单独证明领域适用、授权成立或 V/HV 价值成立。

## 11. Human Gate

本文不新增 00 之外的 Human Gate。

### 11.1 领域增量事项

以下事项是 00 §4.2 在 LDVH CLI 服务领域的具体化：

1. 新增、删除、改名或重排 LDVH CLI 服务规范、公共服务形态或领域公开操作的编号/职责边界；
2. 改变 LDVH CLI 契约的效力边界、共同 envelope 的语义边界，或把新传输形态纳入当前范围；
3. 改变受控状态变更的授权、回读、机械拒绝或实际变化表达边界；
4. 领域来源与 05/08/09 的职责冲突且无法以来源回指收敛。

受保护文档修改按 00 §4.3 执行，此处仅回指，不构成本文领域增量。

### 11.2 决定边界

Human 决定只证明决定及其作用范围，不替代操作契约核对、机械校验、写后回读或传输一致性验证。

## 12. Stop Conditions

本规范不新增根停止类型。

### 12.1 领域触发与影响范围

出现以下任一情况时，按 00 §7.2 暂停受影响的最小服务调用、状态变更或结果声明范围：

1. 操作来源缺失、冲突或无法唯一定位；
2. 请求范围、必需输入、实际能力或授权无法确认；
3. 准备把候选、注册、工具成功或部分结果写成适用、授权、完成或价值；
4. 已触发的回读、审计、验证或 Human Gate 未完成；
5. 当次请求实际超出来源已声明的操作前提或机械条件。

### 12.2 暂停期间允许动作

暂停期间只允许不越过停止边界的来源定位、只读核对、验证、修复与分流准备，不得继续受影响调用、副作用或成功声明。

### 12.3 恢复与再次触发

恢复须与触发原因对应，且只覆盖当前依据支持的范围；同一停止条件恢复后再次触发时按 00 §7.3 进入 Human Gate。

## 13. 反过度设计红线

1. 不要求每次普通求解、读文件、编辑或工具调用先经过能力发现、完整 envelope、事实召回、授权匹配或 Human Gate；只在实际来源和风险要求时调用相应机制。
2. 不以 LDVH CLI 建立全局事务、统一状态机、全量审计日志、跨环境消息总线、固定错误码宇宙或外部 API 网关。
3. 不把共同请求/响应字段扩张成领域字段仓库；具体字段只留在实际领域来源的 `arguments`/`result`。
4. 不把 DSH 工具注册、实现文件存在、schema 校验、返回成功、缓存命中或页面呈现当作规则适用、授权、验证、完成或价值成立。
5. 不把能力发现、公开操作目录或工具权限当作 AI 行动的许可白名单，也不以未匹配操作阻断普通求解。
6. 不要求 LDVH CLI 自动保存会话轨迹、推理过程或逐动作簿记；防自欺只保留来源要求的实际范围、变化、回读和机械校验锚点。
