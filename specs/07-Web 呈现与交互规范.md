# Web 呈现与交互规范


## 1. 价值判断

Web 呈现与交互解决 Human 难以直接观察 LDVH 状态、依据、授权和积累的问题，通过统一阅读层级与交互入口，使信息可定位、可回应、可回读，减少黑盒感、误操作和跨页面理解负担。

结构化问询与计划审查主要支撑 HV1 决策提请清晰可决；授权流和执行状态呈现主要支撑 HV2 授权执行受控可续；节点回读主要支撑 HV3 入档闭环节点可验；卡片网格、语义详情与扩展阅读主要支撑 HV4 积累效用直观可见与 HV5 项目演进脉络可循。V 轨价值由 AI 侧规范承接，Web 只呈现其可观察结果。

本规范只定义 Human 呈现语义与交互契约；机械拒绝、领域数据、宿主接入和 Code 实现由事实源与事实模型基础规范、业务系统基础规范、检查机制与辅助机制规范、LDVH CLI 确定性服务规范、管辖范围规范、DSH 环境接入与插件发布规范、Code 实践与测试规范与实际运行环境承接。

页面呈现、工具成功、组件加载或 Human 操作，只能证明当次呈现与交互范围，不能单独证明事实成立、授权覆盖、技术验证、工作完成或价值兑现。

**关系显示规则的价值登记（2026-09-28）**：§5.5 新增的「认知中心热力图的关系显示规则」一表按下述五项交还（`00 §6.3`）。**回应第 1 章的哪个问题**：Human 四项短板中的「长期规划与演进逐渐模糊」——派生视图若把「已终结的目标」过滤掉，Human 看到的是一片干净但**不完整**的图，等于把「这条残留交出去之后怎么样了」这一问从视野里删掉；而不完整比不呈现更危险，因为它不像缺失。**落实第 2 章的哪项根方案**：`00 §2` 的「宿主原生机制承载编排与注入」＋「元规范承载规则」——显示判据此前只存在于实现，本表把它落成可回查的规则，并指明唯一权威仍是定义该关系的规范（`21 §12`），显示层不得自行放宽或收紧形态。**预期影响哪些 V/HV**：主要支撑 HV5 项目演进脉络可循（演进脉络里「已终结的去向」也是脉络的一部分，不得静默消失）、HV4 积累效用直观可见；V 轨不直接承接（Web 只呈现可观察结果，V 轨由 AI 侧规范承接——与本节同口径）。**新增什么负担与风险**：① 每新增一个关系键即须在本表补一行——未登记即意味着该键的显示判定没有可回查的规范源，在其补入本表之前不得主张该键的显示形态成立（已登记的缺口见 §5.5）；② 显示期与写入期两个判据并存于同一关系键，读者可能误读为两处权威——本表以「唯一权威仍是 `21 §12`、显示层只选择呈现范围」显式拆分。**准备以什么证据核对**：① 机械侧——在本表的每一行都具备可重跑的关系显示用例覆盖之前，不得声称该行已获机械保障；② 对应侧——本表每行须与实现中的唯一对应点逐行相符，行与实现不一致时以本表与 `21 §12` 为准并须修正实现，不得反过来据实现放宽本表；③ 制度侧——该收窄的决策依据（原判定允许指向 WorkCase 且状态不限，与 `21 §12` 互斥）已登记在本表「为什么目标接受终态而写入期只接受 `open`」段。**尚无充分证据支撑的部分保留为缺口**：其余七个关系键的显示条件仍未获规范登记；本表的效用（Human 是否真能据此更新演进认知）在取得实际使用证据前不作推定。

## 3. 职责边界

### 3.1 本文负责

1. 四层阅读器的呈现语义与切换契约（字段级直读 / 卡片网格 / 语义详情 / 扩展阅读）（§5），含 WorkCase 的呈现接线登记（§5.5）；
2. 交互入口的触发条件与 Human 响应契约（结构化问询 / 计划审查 / 授权流 / 验收交还）（§6）；
3. 管辖项目登记与取消登记的 Web 交互契约（经管辖范围规范 §5.4/§5.7 受控登记流程承载，Web 不自行解析或直写登记载体）（§6.5）；
4. 管辖项目在 Web 中的切换呈现规则（§7）；
5. Web 呈现边缘条件的识别与处理方式（登记文件缺失、项目未管辖、授权范围不清、交还未通过等场景下的 UI 行为）（§8）。

### 3.2 本文不负责

2. 事实字段、状态机、CRUD、CAS、content_fingerprint——归事实源与事实模型基础规范；业务系统规范步骤、触发条件、完成门禁——归业务系统基础规范；

4. 管辖登记 Schema、判定逻辑——归管辖范围规范；
5. 插件 manifest、工具注册缝、引导面注入、事件时机——归 DSH 环境接入与插件发布规范；
6. 代码实现、组件库、构建、测试、CI/CD——归 Code 实践与测试规范；

### 3.3 相邻规范分工与唯一权威

事实源与事实模型基础规范是事实与状态语义的唯一权威，LDVH CLI 确定性服务规范是 LDVH CLI 响应的唯一权威，受控提交与机械守护规范是提交与溯源语义的唯一权威，管辖范围规范是管辖判定的唯一权威，DSH 环境接入与插件发布规范是宿主接入的唯一权威，Code 实践与测试规范是 Code 实现的唯一权威；07 只定义呈现语义与交互契约，不改变任何领域语义，不成为第二规则源。

### 3.4 本文只承载要求，不承载实现状态

本文正文只承载**要求**——在某条件成立时应当或不应当做什么，以及呈现语义与交互契约（呈现什么、何时呈现、如何派生、状态如何表达）。**不得承载任何「当前如何」的事实陈述**：实现状态（某项机制是否已实现、已由何提交落地、实现所在的文件、组件、函数、常量或测试）、下位文档的存在状态与过程进度。

**判据**：一句正文如果**随实现或其它载体的现状变化而需要修改**，它是状态，不得留在正文；如果它在现状变化后**仍然成立**（义务、条件、边界、禁止项），它是规则，应当留在正文。

**状态的去向**：**实现与状态由下位设计文档（`plugin/web/docs/`）承载**，不由本文承载。具体的呈现接线——由哪个组件、哪处常量、哪份测试钉住——属实现接线，其登记与维护归下位设计文档；本文只定义可被验收的呈现要求。

确需向读者提示现状时，以**条件式要求**表达（「在 X 具备之前，不得主张 Y 已生效／已完成，并须如实披露未兑现范围」），把事实判断的责任交还给读取时的观察。

**相邻形态（不受本款禁止）**：条件式要求、假设与反例、对读者的处置指引——这三类是义务而非事实陈述，应当保留。

**本款与 §3.3 的分工**：§3.3 约束**职责**边界（07 不越权定义领域语义，不成为第二规则源）；本款约束**内容形态**（07 不承载实现状态）。二者互不替代——缺前者会使 07 变成第二规则源，缺后者会使 07 变成实现台账。

## 5. 四层阅读器

四层阅读器承载 Human 对 LDVH 项目信息的呈现消费。四层**互不替代、不互锁**：Human 可随时切换至任一或同时展开多层，不要求从低层向高层递进。

### 5.1 字段级直读

- 呈现事实对象的核心字段（名称、状态、指纹、时间戳、来源引用）
- 面向快速定位与核对：Human 可一眼确认某条记录是否存在、状态如何
- 不渲染关联关系或语义解释

### 5.2 卡片网格

- 以卡片形态呈现事实对象摘要（标题、状态标签、单行摘要、关联计数）
- 支持按类型、状态、维度、时间等条件筛选与排序
- 面向浏览与概览：Human 在卡片间扫描，定位感兴趣的对象

### 5.3 语义详情

- 完整呈现单条事实对象的所有字段与关联引用，含来源回指
- 显示该对象的变更历史（摘要形态，不要求完整 diff）
- 面向深度核查：Human 逐条审阅内容、判断适用性与完整性

**已登记的窄例外（Human 授权 2026-09-28）**：WorkCase 终态（`status = closed`）对象的 `result.residual` 不上屏——见 §5.5「「已关闭」为何不再呈现残留」。这是本条首句「完整呈现所有字段」的**一处明确例外**，由 Human 直接授权（原话：「在关闭页面就不应该有残留信息了，要删除掉，规范里也要明确一下」；追问后答「1，要删」，确认详情页同）。**该例外不扩张**：只作用于 WorkCase 终态对象的 `result.residual` 这**一个字段**与这**一种状态**，不得据以将其它类型、其它字段或其它状态下的呈现收窄解释为合法。**该例外的适用范围（2026-09-29 修订）**：条件豁免段已于该日删除（见 §5.5），故**全部** WorkCase 终态对象**一律**适用本例外——不再区分形态或去向正文是否自足（此前「不满足前提者如实保留」那一侧已随该段一并取消）。

### 5.4 扩展阅读

- 跨对象关联呈现：按话题、决策链、问题-方案-结果线索串联多条事实
- 呈现事实的积累效用与复用情况（HV4/HV5 的承载面）
- 面向脉络探索：Human 沿关联追踪项目演进路径

### 5.5 WorkCase 呈现契约

本节定义 WorkCase 在 Web 中的**呈现语义与交互契约**——读什么、由什么派生、如何呈现、何时呈现。**类型语义与字段的唯一权威是 21 号**（§3.3）；本节不重定义状态机、字段或 Gate 语义，不登记实现接线（归下位设计文档），也不得作为第二规则源。21 号语义变更时本节随之复核。

**三态直读**：WorkCase 的呈现状态由 `status` 闭集三值（`draft` / `open` / `closed`）直接读取，不引入多值进度词汇。`closed` 配 `outcome` 四值（`completed` / `partial` / `not-achieved` / `cancelled`）呈现终态徽标。

**派生分组（呈现层派生，不写回对象）**：列表筛选与收件箱**共用同一派生判据**（防口径漂移）。四组及其派生判据：

| 派生组 | 判据 |
|---|---|
| 待批准执行（`pending_gate1`） | `status = draft`（含 C2 局部重批回退的对象——同在等 Gate 1） |
| 执行中（`executing`） | `status = open` ∧ 正文不含 H2「结果」节 |
| 待批准关闭（`awaiting_gate2`） | `status = open` ∧ 正文**含** H2「结果」节 |
| 已关闭（`closed`） | `status = closed` |

筛选提供五档：上述四组加「全部」。**四组与五档是闭集**，不得增设第五个派生组或新增状态词汇。

**「待批准关闭」的判据说明**：以「正文含 H2 结果节」为派生依据，是因为该节是 `21 §8` 定义的**关闭提案正文承载**（关闭提案时必填）。**不得改用「Gate 2 已提请」一类运行期状态**——那不是事实源中可读的稳定内容。H2 识别须忽略代码围栏内的行，并容许 ≤3 空格缩进。

**交互入口接线**：`draft` 对象接入 `21 §10.1` 的 Gate 1 提请（对应 §6.2 计划审查）；`open` 且正文含结果节的对象接入 `21 §10.2` 的 Gate 2 提请（对应 §6.4 验收交还）。收件箱待办由上述派生组产生，不得由进度字段或运行期标记产生。

**执行期「增量审批」待批项的呈现**：`open` 对象存在**待批的增量申请**时，呈现层须让 Human 看得见「这一单在等他批」。呈现**只在一处：卡片与语义详情**——**不设收件箱待办**（网页只呈现、不接收指令）。**判据单一来源**：待批 ＝ `gate_1.amendments` 的末项无 `decision`，卡面与详情取同一值，不得两处各写一套。**不新增派生组、不新增状态词汇**——该对象仍归其所属的既有派生组（`executing`／`awaiting_gate2`），本项只是组内多一块。**决定的入口不在网页**。

**判据的机械可读性**：待批状态取自 `gate_1.amendments` 的末项是否已有 `decision`（该流水的形态与校验见 `21 §8`／§14）。这是**机械可读**的字段判据：不需事务性运行期标记，也不接受「AI 自称已提请」。

**复核节点的呈现**：`21 §8` 的 `reviews`（复核节点概要流水）按 §5.3「显示该对象的变更历史（摘要形态）」呈现——列出每次复核的时间、署名与概要。**复核详情不入对象**，故详情面不承载其原文。

**执行期阶段（呈现层派生，不写回对象；不进筛选与收件箱）**：`executing` 组内部按下列判据派生四个阶段，供卡片与详情呈现。**本派生不对「派生分组」的闭集做任何扩张**——筛选仍为五档、收件箱待办仍由上述四组产生；阶段是同一组内部的呈现细节，不是状态词汇。

| 阶段 | 判据 |
|---|---|
| 执行中 | `reviews` 不存在，且 `change_log` 中无**复核条目** |
| 复核中 | `change_log` 中存在**复核条目**，且 `reviews` 不存在 |
| 修订中 | `reviews` 存在，且其后仍有**本对象**的 `change_log` 条目 |
| 结项中 | `reviews` 存在，且其后无本对象的 `change_log` 条目 |

**「复核条目」（`21 §8` 记账纪律）**：摘要**以「复核：」开头**者，或含 `[review recorded by session`（Code 盖戳）者。**为何用前缀而非关键词**：`change_log` 中「复核这件事」与「处置复核的发现」共用同一批词——按关键词识别必然误判（旧实现即因此把处置动作标成了复核）。该判据两侧的可靠性不同：**完成一侧是机械的**（由受控动作盖戳写入，不依赖作者）；**发起一侧依赖前缀**（`21 §8` 已声明该条非机械门禁）。故「复核中」是组合判据，**不得据此声明复核过程已被完整机械记录**。

**阶段标签的当前纪律**：卡片**不得**呈现阶段标签——对象头部的状态显示恒为 `21` 号状态机的真实值，不被阶段影响；执行进度由卡片主体的「变更流水」及其标记表达（见下）。本判据留待后续需要时启用，**不得据上表在卡片上新增阶段标签**。

**变更流水（卡片主体的执行进度呈现）**：`executing` 组的卡片主体呈现 `change_log` 的流水——按日分组、每条给时刻、最多 8 条（更早折叠），关键行动以**文字标记**凸显：

| 标记 | 判据 |
|---|---|
| 复核 | 摘要**以「复核：」开头**（`21 §8` 记账纪律）**或**含 `[review recorded by session`（Code 盖戳，机械） |
| 修订 | **最后一条复核条目之后**的本对象条目（数组序；`reviews` 非空为前提） |
| 已批准（增量） | 摘要含 `[adjustment approved by`（机械方括号，`21 §14` 的批准支） |
| 已拒绝（增量） | 摘要含 `[adjustment rejected by`（同上，拒绝支） |
| （无标记） | 其余条目 |

标记与归属口径共用同一套判定规则（数组序／他对象排除／格式治理排除），须**单一来源**，组件不自行判断。**流水不改变对象状态，也不影响筛选与收件箱**。

**「待批调整」不是流水标记，而是卡体顶部的一块**：`open` 对象存在**待批的增量申请**时，卡体在流水**之上**呈现一块——判据是 `gate_1.amendments` 的**末项无 `decision`**（**不新增派生组、不新增状态词汇、不经收件箱**），块内给出「已申请追加 N 项」＋首条的 `step`，并注明「等 Human 决定」。**为什么与两种决定标记分开**：待批是「当下在等的事」（应当先被看到，且它尚未进 `change_log` 的语义序列），而两种决定标记是「发生过的授权事件」（属流水的一部分）。

**两种增量标记的优先级**：增量审批的决定是**授权事件**，比「复核之后又改了什么」（修订）更具体，故**优先于「修订」**；它不改变「复核」的判定（复核标记仍以其自身判据优先）。**不得**据此声称增量审批影响了对象的阶段或状态。

**判定口径**：① 一律按 `change_log` 的**数组序**判定，**不得**使用 `reviews[].at` 或 `change_log[].at` 的相对先后——同批条目可能被刷成同一时刻，时间不承载相对先后。②「本对象的条目」指摘要中**未**提及他对象 `workcase-XXXXXXXX` 的条目；提及他对象的条目不参与本对象的阶段判定。③ 摘要以「**格式治理：**」开头的条目（`21 §8`）不参与判定——它是跨对象的批量格式操作，语义逐字未变，不构成该对象的修订。

**与「待批准关闭」的区别**：「结项中」指已复核通过、尚未写出「## 结果」节的对象；一旦写出结果节，该对象即进入既有派生组「待批准关闭」（`awaiting_gate2`）。二者判据互斥，**不得合并**。

**未验证范围**：本条只提供判据，不保证「复核：」前缀被实际遵守——写成其它形式时「复核中」不可判（`21 §8` 已声明该纪律非机械门禁）。判据 ② 亦不排除「摘要未提及任何对象、实为他单工作」的条目。

**卡面与详情的字段分工（`21 §8`「`gist` 与 `summary` 的分工」的呈现落点）**：

| 呈现面 | 渲染 `gist` | 渲染 `summary` |
|---|---|---|
| 列表卡（§5.2 卡片网格，三态全部） | 是——卡体首行 | 否 |
| 聚焦收件箱卡体（待决定事项 / 推进中事项） | 是——卡体首行 | 否 |
| 联邦对象卡（跨项目视图） | 是——卡体首行 | 否 |
| 语义详情（§5.3） | 是——独立阅读节点 | 是——Markdown 节点 |

**本表是卡面的完整清单**：凡渲染 WorkCase 卡体的呈现面都在表内，新增卡面须同步登记。「卡面不渲染 `summary`」是**按呈现面类型**（扫读窗口）成立的规则，不因卡片来自单项目视图还是联邦视图而改变——同一张卡在两种视图下读者与版式相同，字段分工不得随数据来源漂移。

**AI 侧召回不在本节范围内**：F1/F2 召回投影由 `21 §13` 定义，本节不为其登记字段——`gist` 是**呈现层**的 Human 扫读字段，召回投影的字段集以 `21 §13` 原文为准。若日后需让 AI 侧也消费 `gist`，须先修订 `21 §13`，不得由本节倒推。

**为何卡面不渲染 `summary`**：卡面是**扫读窗口**（§5.2：Human 在卡片间扫描以定位感兴趣的对象），而 `summary` 按 `21 §8` 是**给执行者的完整快照**——它可以长、可以含编号引用与对象标识、可以带 Markdown 标记。把后者放进前者，会溢出扫读窗口，且纯文本插值路径会把 Markdown 标记以字面形式暴露给 Human。

**呈现降级（条件出现，如实披露）**：`gist` 在 `status = closed` 时按 `21 §8` 缺失合法（终态只读，无受控入口可补写）。卡面遇缺失时**如实降级**——不得以 `summary` 首句静默替代（那会把两个读者的字段混为一谈，掩盖字段缺口），也不得留白使卡片看似无内容。具体形态由 §12 第 7 条（长文本须有折叠或分层入口）与第 8 条（状态不得只由颜色承载）共同决定，本节只登记「必须可区分于有 `gist` 的卡片」。

**机械校验边界**：本节的派生规则只证明**呈现当次**的读取与派生结果；不证明对象语义正确、Gate 授权成立、执行推进或结果达成。派生结果不写回事实源。本节不校验 `gist` 的内容质量——`21 §15.1` 已声明机械层只校验存在性与长度，内容是否「Human 扫读自足」属 AI 语义审核与 Human 阅读。

**四组卡体（块构成与次序）**：四组的卡体均为**无标题栏**的块构成，次序不得调换：

| 派生组 | 块构成与次序 |
|---|---|
| 待批准执行（`pending_gate1`） | 目标（`gist`）→ 计划清单（`plan[].step` 逐条） |
| 执行中（`executing`） | 目标（`gist`）→ 变更流水（关键行动文字标记）；存在待批增量申请时，流水**之上**多一块「待批调整」 |
| 待批准关闭（`awaiting_gate2`） | 逐条核对 → 残留（含流向） |
| 已关闭（`closed`） | 去向（按去向词分区）；`outcome = cancelled` 时另加取消理由块 |

**「逐条核对」块去掉不等于核对未发生（须合读）**：`result.criteria_checks[]` 仍是关闭时的机械证据、仍在详情面完整呈现，`outcome` 徽标正是它的汇总结论；`closed` 卡面去掉的只是**同一批信息的第二次呈现**。不得据本条声称「核对已被取消」或「关闭无须逐条核对」。

**「已关闭」卡不呈现独立残留块**：已关闭意味着每条残留都已被去向**消化**（`21 §8` 合并式——去向子项长在每条残留之下，闭集二词二选一），故卡面无须再单列残留。**删除的是呈现、不是字段**：`result.residual` 仍在载体与投影中，其文本在语义详情（§5.3）与正文「## 结果」节仍完整可读，**丢失的只有卡面可见性**；判据仍由**详情面**消费（**同源不得被破坏**）。

**去向分区**：去向项的呈现**按去向词分区**——

- **分区标题**：去向词从**每条重复的行内标记**提为**块首标题**，标题**沿用该去向词标记的样式**（不新造标题样式）。同一去向词在一屏上因此**只出现一次**。
- **一个去向词一个区域**：各分区是**独立的块**（各有边框与底色，上下排列），不是同一块内的相邻分节。块底色取该去向词标记的**同族色**；**无现行去向语义色的词不着色**（为已停用语义新增色源属越界），回落中性只留边框。
- **组内条目**：只留正文，行首缀一颗**装饰性项目符号**（不承载语义；须与正文正确对齐，不得因行距叠加而与正文分离）。
- **不报条数**：分区标题**不写**「N 条」——块内条目读者一眼可数，逐块申报属冗余。
- **「转入 Spark」的目标关联行**仍**就地渲染**于该分区各条正文之下（行式见下）。按序配对为**写法约定**、非机械可核验事实（`21 §15.1`）。
- **信息未增未减（本项的边界）**：条目数、顺序、正文与逐条呈现时**逐字相同**——去掉的只是重复的词。这是**去重与分区**，不是对去向内容的加工：**不合并、不排序、不丢弃**判不出词的条目。分区按去向词的**首次出现顺序**排列，不按闭集顺序重排——条目顺序是作者写下的、载体里的既有信息。

**「待批准关闭」期为何不写去向正文**：该期**残留正文就在上一行**，去向正文在此重写一遍是同一信息的重复陈述。故呈现层在该期**只画去向标记**；**去向正文只在「已关闭」期呈现**（那时残留一侧不再上屏，去向正文是读者唯一读到的内容，`21 §8` 的**自足**要求正为该期而设）。**载体中仍写去向正文**——本项收窄的只是**待批准关闭期卡面的呈现**，不减损载体与门禁（`21 §15.1` 门禁⑤「接受现状」正文非空**仍在**）。**残留与其流向之间不加分割线**：流向行紧贴其所属残留，读作一个单元；单元与单元之间才有分割线。

**「已关闭」为何不再呈现残留（决定 A）**：去向不是独立的一段，而是**长在每条残留里面**（`21 §8` 的合并式形态）——「还剩什么」与「打算怎么办」是同一个不可分离的单元。关闭后该单元的去向一侧已按 `21 §8` 要求**自足**（离开残留也能读懂），故呈现层只画读者需要执行的那一半，残留不再重复出现。**这不是删除信息**：残留与其去向在**载体**中仍是同一个单元（合并式），收窄只发生在**呈现**层。

**决定 A 适用于全部关闭对象**：不设「不满足前提者如实保留残留块」的例外——已关闭卡体不含残留块，该例外无事可做，保留它只会制造第二套相互冲突的块构成。**既知后果（如实登记，不掩盖）**：存量分离式对象中，**无去向的那部分残留不再出现于卡面**；这些残留的文本**仍在载体正文「## 结果」节内**（`21 §8` 载体内聚），故**可读性未丢失**，丢失的是**卡面可见性**。

**详情面的同一收窄（决定 A 的一部分）**：A 不仅适用于卡片网格（§5.2），也适用于**语义详情**（§5.3）——关闭对象的详情阅读布局**同样不再呈现残留一侧**，只呈现去向。**与 §5.3「完整呈现所有字段」的关系以「已登记的窄例外」处理**（见 §5.3），该例外只作用于 WorkCase 终态对象的 `result.residual` 一个字段、**不得扩张**。该收窄现**一律适用**于全部关闭对象；判据由投影层单点给出，卡面与详情**同源**，不得两处各写一套。

**两期卡的关系（数据源不对称，如实登记）**：`21 §9.1` 规定 **`result` 出现 ⇔ `status = closed`**，故「待批准关闭」期 `result` 字段**尚不存在**，核对与残留（含去向子项）**只在正文**；「已关闭」期 `result` 已落盘并成为**权威**。两期的内容项分岔：待批准关闭期读**残留（正文）＋其下的去向标记**（不读去向正文）；已关闭期读**去向（标记＋正文）**（不读残留）。**去向的承载**：`result` 字段闭集不含去向，故去向的**去向词与正文**在关闭前后读的都是同一处正文承载，不另存一份——差别只在**哪一期呈现它**。**「转入 Spark」的指向**由 `relations.routed-to` 承载；**该指向只在已关闭期呈现**（渲染为去向条下方的目标关联行）——待批准关闭期**不呈现**目标关联行。**残留一侧相反**：开放期从正文读、关闭期按 A 不呈现；`result.residual` 字段仍落盘（`21 §8` 要求），只是不再上卡——字段存在与是否呈现是两件事。

**两期呈现所依据的正文形态**：`21 §8` 的新写入一律为**合并式**（残留 ＋ 去向子项）；存量仍有**分离式**（`- residual:` 段 ＋ 独立的 `- advice:` 段）。呈现层**两种都要能解析**——这是不溯及在消费侧的必要条件，不是双权威：同一对象在其载体中只有一种形态，解析器按实际出现的形态读取。**事后补记声明**（`21 §8`）须**随去向子项一同呈现在卡面**——该期由去向块首行承载；其用途正是让读者知道这些去向不是关闭时的提请输入。

**块序与逐条标记**：**待批准关闭**的块序为**逐条核对 → 残留（含流向）**——残留是「还剩什么」（事实），其下的去向标记是「打算怎么办」（拟议）；先陈述事实再给去向，读者才不必回头。**逐条标记**：残留条目带固定词「残留」标记，去向条目带**闭集二词**标记；使行的结构统一为「`[标记] 正文`」。**为什么残留用固定词而非分类词**：残留条目无闭集可归（`21 §8` 未给 `residual` 登记词表），条目自身常带 `**标题**` 前缀，故标记只回答「这属于哪一块」，不重复条目内容。**去向条的呈现按期分岔**：**待批准关闭**期去向**只给标记**、缩进一行紧贴其所属残留，且**该行与其残留之间不加分割线**；**已关闭**期去向为**平级行且带正文**（那时残留一侧不再上屏，去向正文是读者唯一读到的内容，`21 §8` 的**自足**要求正为该期而设）。**标记色与块底色同源**——颜色只表达「这是残留」一件事，不引入第二个语义色。

**单一来源纪律**：两期卡虽不再同构（开放期读完整单元、关闭期只读去向一侧），但**去向条目与残留条目的类名、标记与折叠阈值仍须只有一处来源**，消费方从该处取得、不得各自重写——分写必然漂移。两期在**标记与语义色**上一致，只在**块构成**（是否呈现残留一侧）与**密度**上分岔。

**语义块四边同为 1px 细线**：语义块的边框**四边同宽（1px）、同色**；**不得**用粗左线或独立的左线色。块的身份由**背景色**与**标记**表达，不由边框粗细表达。**代价（如实登记）**：移除左侧加粗竖线后，左边框的视觉强度降至与其余三边相同、**看起来会变淡**——这是「四边同为 1px」的必然结果，属已明确选择的效果，**不得再以「左边框太淡」为由回改**。该形态适用于所有同类语义块（判据面板、计划清单等），不得只改一处而致两处形态分岔。

**卡体条目行的分割线**：卡体内**所有**条目行——核对、去向、残留、计划清单——**统一**用带分割线的行样式；**条间距由该行的 padding 提供**，不再另用 `gap`。**首条不加顶线**，否则与块顶边框叠成双线。**为什么必须单一来源**：该样式曾被多处各自复制，导致同卡各块形态不一致；**单一来源**是唯一可靠做法。**卡面与详情的密度差异显式化为参数**：卡面用带分割线的紧凑行（扫读窗口），详情面用宽松行（阅读面）；两面**共享同色、同标记、同结构**，只在密度上分岔。

**计划清单的容器**：计划清单**必须有容器**，且**与详情页判据面板同源**——两处渲染的是**同一份 `plan` 数据**，形态因此呼应。**容器形态只有一处来源**：列表卡、收件箱、详情页**三处共用**，不得各写一份。**选蓝色而非中性灰／琥珀的理由**：① 有同源先例（详情页）；② 不与 `gist` 的琥珀框争色（同卡两个琥珀框会分不清主次）；③ 不引入新语义色。

**为什么核对只给步骤标题**：`21 §8` 的 `result.criteria_checks[]` 只有 `{satisfied, evidence}`，**不含判据文本**；若卡面显示整段证据，实测证据最长可达 258 字，一张卡被撑到十几行，扫读窗口（§5.2）失效。**证据与 `gate_1` 明细归详情面**（§5.3）。判据文本只能由 `plan[i].step` 给出，故 **`closed` 期列表卡投影须包含 `plan`**——否则卡上无法显示步骤标题。

**核对状态词跨组统一**：`closed` 卡**同样使用 `21 §8` 登记的三词映射**（词表以 `21 §8` 为唯一展开处，本处不重复列出）——**同一状态在两个派生组必须显示为同一词**，跨组可比。映射判定**只有一处实现**，各消费方从该处取得，不得各写一套。

**卡面纯文本**：卡体按**纯文本**渲染其条目正文（去向条的去向正文、取消理由块的一行理由）——不解析 Markdown 标记。写作侧纪律见 `21 §8`。存量已带标记的对象**不自动追溯改写**；确需清理时须由 Human 单独授权，按事实更正处理。

**「不解析」不等于「不显示标记」——卡面渲染前须剥标记**：纯文本插值会把 `**加粗**`、`` `标识符` `` 的标记本身显示给读者（实测正文残留与去向条目中含标记者接近七成）。故卡面渲染**去向正文**与**正文解析出的残留**之前，**须先剥离 Markdown 标记**；剥离为**单一实现**，各呈现面从该处取得。**剥的是显示、不是数据**——详情面仍用 Markdown 渲染（语义保留），数据层不改：同一源文本在两面形态不同是有意的（卡面是扫读窗口、详情是阅读面）。**未验证范围**：剥离只去标记，不证明剥离后文本「准确」或「可读」；且它不处理代码围栏、链接与表格——卡面不承载这些，出现即应**暴露**而非静默吞掉。

**卡头的合并徽标：状态词 · 结论词**：「已关闭」**且仅限 WorkCase** 的卡头**只画一枚**徽标，位于**右侧状态位**，文本为 `状态词 + 中心圆点 + 结论词`（`已关闭 · 完成`／`已关闭 · 部分完成`／`已关闭 · 未完成`／`已关闭 · 取消`），**配色由结论决定**。

- **只此一处**——`outcome` 在卡面**只在卡头这一枚里出现**，卡体不再有任何 outcome 元素。
- **不得回归为两枚并列或分置两处**：分开两处时读者要把「已关闭」与「完成／取消」自行拼起来，而它们本是**同一件事的两半**（怎么关的 ＋ 关得如何）。
- **只作用于 WorkCase 的「已关闭」卡**：其余**类型**与其余**状态**（无 `outcome` 可合并）**一律仍走默认状态徽标**，本形态**不得扩张**。判据须三条件齐备：类型是 `workcase`、状态是 `closed`、`outcome` 值存在；**缺 `outcome` 时回落默认状态徽标**。
- **四值各显其真**：**不得**把 `partial`／`not-achieved` 显示为「完成」——`21 §9.3` 明确 `partial` ＝ 部分判据达成、其余有明确未达成范围，写成「完成」即让卡头说一句**载体否认的话**。合并徽标用**短式**结论词（完成／部分完成／未完成／取消），而**独立出现**的结论词仍用原词表（已完成／部分达成／未达成／已取消）——两套词表的分工即「是否与状态词并排」。
- **不做展开**：该徽标不承载展开体；`result.achieved_scope`、逐条判据的**证据**、`result.residual` **均不上卡**——前两者归语义详情（§5.3），后者是 §5.3 已登记的例外。
- **不恢复核对计数**：徽标只给结论词，不带「核对 N/M 达成」。
- **不算状态词汇**：合并徽标仍承载状态机语义，但不参与派生分组、不进筛选五档、不进收件箱。
- **样式与既有卡头徽标一致**：尺寸、圆角、字号与内距**一律由共享 chip 形态给出**，组件不得自定——避免并排时高低不一。
- **状态徽标与合并徽标互斥**（只替换、不叠加）：命中合并徽标时不得并排画状态徽标（并排会把同一件事说两遍）；状态词须由调用方取得后**传入**合并徽标，组件内不得另取一份（两处各取一次即同一信息的两处来源）。

**取消理由块**：`outcome = cancelled` 的已关闭卡上，取消一事由**一块**承载——**形态与去向分区逐项相同**（同圆角/内距/块首标记/组内项目符号/字号），**只换一个颜色**，且**只留一行**。

- **只留一行**：标记词为「**取消理由**」（它是块首标题，须自足说明「这是取消的理由」）；**「未发生的范围」不再上卡**。
- **删除的只是呈现，不是字段**：「未发生的范围」是 `21 §8` 对取消记录的**必填项**；故该字段**仍在载体与投影中**、其文本在正文「## 结果」节与语义详情（§5.3）仍完整可读；本次收窄的只是**卡面可见性**。
- **换玫瑰色**：取消是「这单停掉了」，玫瑰是最直接的读法；且它与去向闭集二词的色源都不撞。**已知风险与抵偿（如实登记）**：红系可能被读成「失败」，而 `21 §9.3` 明写 cancelled 不是失败——故以**标记词「取消理由」先行**抵掉该读法；**此风险不声称已消除**。
- **复用而非另写**：块底／标题行／标题／条目行／项目符号／容器留白**一律取去向分区那组形态**；本块**只新增颜色**，尺度与去向分区一致。**形态类两处各写一份即本仓反复出现的「两处各写一套」病，故禁止**。

**目标关联行的行式**：「转入 Spark」去向条的**下一行**就地渲染目标 Spark 的关联行，形态为**单独一行**：`[目标类型图标（类型色）] 标题（撑满，单行不换行、超长省略号截断） [行末状态图标]`；状态**不写文字、只给图标**（可读文本由 `title` 属性承载，供 hover 与读屏）。状态取值与色相取**通用关联行**的口径：目标 spark `open` ⇒ `pending`「待处理」、`implemented` ⇒ `closed`「已关闭」、`discarded` ⇒ `discarded`「已废弃」。本条形态**不是本处特有写法，而是统一关联行的一个实例**（一般规则见下）。

**反向引用块的形态：无标题、无块边框**：「已关闭」卡呈现反向引用区（谁声明引用了本单），其**行式必须复用卡片的统一关联行**，**不得自建第二套行式**；且该区**没有标题、没有块边框、没有底色**——区域形态＝**顶部分割线 ＋ 行间分割线**。

1. **为什么去掉标题**：**行本身自描述**——类型图标说出这是什么类型的对象，行末状态图标说出它的状态；旧标题是一句规范腔长句，**不增加行所没有的信息**，却制造**命名难题**：任何概括词要么过长、要么**冒领方向语义**。
2. **冒领风险的具体形态（本条最有价值的登记）**：曾考虑把该区改名为去向闭集词「转入 Spark」——**该方向错误，且被否决**。理由三者皆不成立：① **方向相反**——`转入 Spark` 是**本单的**去向（承载在**本单的** `relations.routed-to`），而本区是**别人**的 `refs` 指向本单（**反向**）；同一份对象上二者可并存且含义无关。② **会宣称载体里不存在的边**——实测某对象的去向全部是「接受现状」、其 `relations` 内**没有任何 `routed-to`**；而该区列出的对象只是**声明引用了本单**（它自己的工作才是主题）。改名即等于宣称「本单残留转入了该对象」——**该边在载体里不存在**。③ **内容不由本单控制**——本区是**实时反查**（任何对象声明 `refs` 指向本单即入选），**不保证类型**；标题若写死某个去向词，一旦换类型即当场变假。**故本区不写标题即无冒领面**。
3. **两类引用不是同一批数据、也不互相替代**：外向引用（本单引用了谁）与反向引用（谁声明引用了本单）是两批数据——故反向区**不与外向关联合并**，只是**行式**与**区域形态**共用。
4. **理由（防漂移）**：同一类信息若两处各写一套行式，任何一处改样式都会让另一处不一致。**区域形态同理收敛到单一来源**，不各自抄类名。
5. **本区只显示「谁声明引用了本单」，不暗示建议已履行或已闭环**（`21 §13`）。
6. **未覆盖的边界（如实登记）**：本区与卡片的外向关联区在同时出现时会是**两组相邻的无标题行**，读者无法从形态区分方向——当前该情形结构上不可达（实测无对象同时具备两类引用），但这是**数据现状而非结构保证**，属须在出现真实样例时再定的缺口。

**事实对象关联一律以引用行呈现**：卡面凡牵涉**可解析事实对象**的关联（含「本单事项已由另一对象承接」「该缺口另立单处置」这类去向），一律以**统一关联行**呈现——类型图标 ＋ 标题 ＋ 行末状态，可点开；**不得**只在散文里写对象号/对象名充数（那不是可反查的承载，也点不开）。承载由该对象一侧的 `refs` 声明（`21 §12`），呈现在**反向引用区**。**边界（勿过度声明）**：引用行只证明「声明关联」，**不证明**承接已被批准、去向已被履行、语义已被覆盖或本单已闭环（`21 §13`）。

**同类信息只有一处行式（一般规则）**：**凡呈现「引用／关联某个事实对象」的行**，其行式**一律复用统一关联行**，**不得自建第二套**。

1. **适用**：卡片与详情面的**任何**「指向另一个对象」的行——外向引用、反向引用、正式关系、去向目标行皆在其列。
2. **理由**：同一类信息两处各写一套行式时，改一处另一处必然漂移；且读者会看到两种「指向对象」的形态而不知其别。
3. **可扩展的例外**：若某处确需不同行式（例如需要承载统一行**给不出的字段／动作**），**须先在本规范登记该处与理由**，不得以「就地实现」绕过；**未登记的差异视为缺陷**。
4. **不适用场景（免误套，按能力而非按文件登记）**：① 承载**关系键 chip、外部链接目标、复制路径、文档预览**的关联行——属关联行的**详情面扩展**；② 呈现**字段值里的引用**（带原文标识、类型 chip、复制）——属 §5.1 的**字段级直读**层，与「关联块行」不是同一层（四层互不替代）。
5. **判据**：一条行若承载统一行给不出的字段／动作，属合法差异；若只是「指向另一个对象」而无额外承载，**必须**复用统一行。

**认知中心热力图的关系显示规则**：派生视图（认知中心热力图）**只显示本仓已登记的关系键**，每个键的显示条件以**定义该关系的规范为唯一权威**——显示层不得自行放宽或收紧出规范不承认的形态。当前已登记的显示规则：

| 关系键 | 定义权威 | 显示条件（显示层，与写入期判定不同） |
|---|---|---|
| `routed-to` | `21 §12` | 源对象 `status = closed`；目标**只接受 spark**；目标状态接受 `open`／`implemented`／`discarded` 三者 |

**为什么目标接受终态而写入期只接受 `open`**——这不是两处权威，而是**两个不同的判据**：写入期判据是「该边此刻能否成立」（`21 §12` 要求目标写入时为 `open`，因为只有仍在承载议题的 Spark 才配作残留去向）；显示期判据是「该边此刻是否应当呈现」（`21 §13` 规定目标其后转终态**不使该边失效**，且消费方**必须**标注目标已终结——故终态目标必须画出来，由节点自己的状态徽标承载其终结态，而不是过滤掉；过滤会让「已终结的目标」静默消失，反而违反 §13）。**唯一权威仍是 `21 §12`**：显示层不判定该边是否有效、不新增或放宽可接受的边形态，只选择呈现范围。

**已知收窄（如实登记）**：该显示只画源对象 `closed` 的边。对象在 `open` 期已落盘 `routed-to`、尚未关闭的窗口内该边**不显示**（`21 §14` 的 CREATE-FIRST 次序会先把边写下来）。这是**显示选择**，不主张该边无效，也不构成对 `21` 的重述或修正。**未验证范围**：本行只登记 `routed-to` 一条——其余关系键（`serves`／`refs`／`contributed-to`／`related-to`／`depends-on`／`inspired-by`／`informs`）的显示条件**尚未按此形态登记**；此为**已登记的缺口**，在它们各自按此形态登记之前，不得据显示已在运行而推定其形态成立（`00 §6.3`）。

## 6. 交互入口

交互入口承载 Human Gate 与交还流程。每个入口定义触发条件与 Human 响应契约，并在 Web 中呈现对应面板。

### 6.1 结构化问询

- **触发条件**：AI 需要 Human 判断、选择或补充信息，问题已组织为带选项、影响与风险的结构化形式
- **Human 响应契约**：呈现代选项与自由输入，响应须含对象、范围与处理结论

### 6.2 计划审查

- **触发条件**：AI 呈交候选计划，等待 Human 审查或批准；Gate 1 / Gate 2 的授权语义以 21 的定稿为准（21 已定稿，该语义不再为 provisional）；该语义属 WorkCase 类型语义（21 §3.3），不属目标规划与蓝图跟踪业务系统（30/31 号位）的职责，故本节的触发依据以 21 现行文本为准
- **Human 响应契约**：呈现计划依据、范围、步骤与风险，Human 批准/拒绝/要求修改

### 6.3 授权流

- **触发条件**：AI 需要 Human 授权才能执行或继续某项受控操作
- **Human 响应契约**：呈现授权对象、范围、边界与执行状态，Human 授予/拒绝/限制，越权动作被机械拒绝

### 6.4 验收交还

- **触发条件**：AI 完成当前工作，呈交验收结果
- **Human 响应契约**：呈现 00 §5.8 Output Envelope 的 Human 可读视图与验证证据，Human 验收/退回/要求补充；Web 不重新定义 Envelope，也不把呈现或验收写成技术验证

### 6.5 登记管理

- **触发条件**：Human 在 Web 中发起项目登记或取消登记（对应管辖范围规范 §5.4/§5.7 的 Web 入口）
- **Human 响应契约**：呈现登记对象、项目路径、综合就绪状态与分项诊断。**安装事务的步骤、状态闭集与失败处置由 DSH 环境接入与插件发布规范 §6 定义，本文不复述**；本文只定义其**呈现与交互约束**：(a) 用户选择的目录由 Host 确认为实际 Git 根后方可提交安装；(b) 未就绪项须分项呈现原因而非合并为单一结论；(c) 可修复与不可修复状态须在交互上可区分，前者提供修复入口、后者只呈现原因；(d) 写入与移除经管辖范围规范 §5.4/§5.7 和 DSH 环境接入与插件发布规范 §6 定义的受控流程并分项回读确认，**Web 不自行解析或直写**登记载体、事实源或 Hook

## 7. 管辖登记与项目切换

管辖范围规范 §5 登记的管辖项目在 Web 中可切换呈现，规则如下：

- Web 通过管辖范围规范定义的唯一管辖判定职责读取 Human 已定案的登记载体，列出管辖项目；Web 不自行解析候选路径或 Schema；
- Human 在 Web 中切换当前呈现的管辖项目，切换后四层阅读器与交互入口均指向目标项目的事实源；
- 切换只作用于 Web 呈现层，不改变当前会话工作目录，不触发 LDVH CLI 或 Git 操作；
- 管辖判定消费方式沿用管辖范围规范 §7 消费方表。

## 8. Web 边缘条件处理

以下条件处理仅影响 Web UI 呈现行为，本身不新增 Human Gate 触发条件或必停情形；Human Gate 以 `00 §4.2` 为准，必停情形以 `00 §5.7` 为准，本文领域增量见 §10–§11。

| 条件类型 | 具体条件 | 处理方式 |
|----------|----------|----------|
| 登记文件缺失 | 管辖范围规范登记文件尚未创建 | 显示“尚未初始化”并提供受控安装入口；不可读、权限不足或 Schema 无效时显示 `unavailable`，不得伪装为“未管辖” |
| 项目未管辖 | 当前项目不在登记列表 | 隐藏 LDVH 功能，提示登记入口 |
| 授权范围不清 | 授权对象/范围/边界不明确 | 显示授权不可用状态，提示 Human 补充范围 |
| 交还未通过 | 验收交还条件不满足 | 退回至 AI 补充或修正 |
| 切换失败 | 目标项目登记文件损坏 | 保留当前项目呈现，提示问题 |

登记载体损坏、不可唯一解析等触及管辖范围规范 §10 停止边界的条件，其暂停语义以管辖范围规范 §10 与 00 §5.7 为准；Web 层仅按本节表格呈现对应状态（“尚未初始化”、`unavailable`、保留当前呈现并提示），不自行处置，也不把呈现写成暂停已执行。

## 9. 验证与证据边界

| 验证对象 | 验证时机 | 成立条件 | 可接受依据 | 验证入口 | 可证明范围 | 未满足时的处理 |
|---|---|---|---|---|---|---|
| 四层阅读器呈现 | 每次呈现或层间切换时 | 各层按 §5 语义呈现，层间切换不丢失已加载数据 | 各层渲染结果 | 呈现核对 | 当次呈现范围；不证明内容正确、事实成立或价值兑现 | 呈现异常时暂停受影响视图并修复 |
| 交互入口触发 | 交互面板出现时 | 面板出现时机与 §6 触发条件一致 | 各交互面板观察（含 §6.1–§6.5） | 触发条件核对 | 当次触发一致性；不证明提请内容正确或 Human 已回应 | 时机不一致时修正触发，不伪造面板 |
| 管辖项目切换 | 每次切换后 | 呈现目标项目的事实源，切换不改变会话工作目录 | 管辖范围规范登记载体与目标项目观察 | 切换结果核对 | 当次呈现指向；不证明目标项目状态正确 | 切换失败时保留当前呈现并提示 |
| 授权范围可追溯 | 授权流面板呈现时 | 授权边界与实际执行范围一致呈现 | 授权流面板与执行状态 | 授权呈现核对 | 当次呈现一致性；不证明授权成立或越权被拒 | 范围不清时显示授权不可用并提示补充 |
| 关键节点可回读 | Human 核对节点时 | 受控创建、状态变更、关闭节点在语义详情或扩展阅读可核对 | 语义详情与扩展阅读 | 节点回读核对 | 当次可回读范围；不证明节点语义正确 | 不可回读时如实披露缺口 |
| 价值声明可观察 | 声称 HV4/HV5 时 | 页面可呈现相应复用与演进依据 | 卡片网格与扩展阅读 | 呈现依据核对 | 只证明页面可呈现相应依据；不单独证明 HV4/HV5 已成立 | 无依据时降低声明并记录缺口 |
| Output Envelope 呈现 | 每次验收交还时 | 机器可读结果与 Human 可读视图两层表达一致 | 00 §5.8 结果与 Human 可读视图 | 一致性核对 | 当次呈现一致性；不证明技术完成 | 不一致时退回修正，不交付矛盾呈现 |

机械结果与语义判断互不替代。页面呈现、组件加载或 Human 操作只能证明各自呈现范围；本章不能单独证明事实成立、授权覆盖、技术验证或 V/HV 价值成立，未执行和不可用范围保留为 gaps。

## 10. Human Gate

本文不新增 00 之外的 Human Gate。

### 10.1 领域增量事项

以下事项是 00 §4.2 在 Web 呈现与交互领域的具体化：

1. 改变四层阅读器的层级定义、切换契约或交互入口的触发条件与响应契约；
2. 改变管辖项目切换或 Web 边缘条件的处理语义。

受保护文档修改按 00 §4.3 执行，此处仅回指，不构成本文领域增量。

### 10.2 决定边界

Human 决定只证明决定及其作用范围，不替代呈现一致性核对、触发条件核对或节点回读核对。

## 11. 必停情形

本规范不新增根停止类型。

### 11.1 领域触发与影响范围

出现以下任一情况时，按 00 §5.7 暂停受影响的最小呈现、交互或完成声明范围：

1. 呈现所依据的来源（登记载体、事实源、Output Envelope）缺失、不可读或相互不一致；
2. 准备把页面呈现、组件加载或 Human 操作写成技术验证、授权成立或整体完成；
3. 交互入口的触发条件或响应契约无法确认。

### 11.2 暂停期间允许动作

暂停期间只允许不越过停止边界的规则定位、只读核对、呈现比对、修复与分流准备，不得继续受影响交互或完成声明。

### 11.3 恢复与再次触发

恢复须与触发原因对应，且只覆盖当前依据支持的范围；同一停止条件恢复后再次触发时按 00 §5.7 进入 Human Gate。

## 12. 反过度设计红线

1. 不要求四层阅读器互锁或从低层向高层递进；
2. 不指定 UI 框架、组件库或预设组件形态——只定义呈现语义与交互契约；
3. 不绕过管辖范围规范的登记制度在 Web 侧自行解析管辖项目列表或候选路径；
4. 不在 Web 中直接改写规范或写入事实——均经受控提交与机械守护规范的机械预检与 Git Gate 流程、以及 LDVH CLI 确定性服务规范流程；
5. 不在已授权范围内重复提请 Human Gate 或把已授权操作再次转为问询；
6. 不为状态切换、加载或列表更新加入装饰性动画、过场或音效；必要的加载与进行中反馈只用于表明实际进行中的操作，不用于营造效果；
7. 不在单一视图中堆积与当前判断无关的信息，不以信息密度代替可用性；长列表与长文本须有分页、折叠或分层入口，不一次铺满；
8. 不用颜色、图标或动效单独承载状态语义；状态须有可读文本与可区分形态，使色觉差异或静音环境下仍可判断。
