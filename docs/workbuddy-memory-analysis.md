# WorkBuddy 记忆系统实证分析（LDVH 记忆系统设计参考）

> 取证来源：用户提供的 WorkBuddy 记忆导出（工作背景/个人背景/当前关注/近期动态四段式单文档，反映另一条工作线——Windows 环境 + WorkBuddy 宿主 + LDVH V4 时代）。本文档为 `docs/memory-system-design-prompt.md` 的配套实证，与 `docs/trae-memory-analysis.md` 并列为"外部记忆系统实证"系列。**第八个样本**，也是唯一反映"同一用户、另一条工作线、另一个历史版本（V4）"的样本。

---

## 一、结构解剖：四段式单文档

| 段 | 内容 | 对应 LDVH 设计 | 判定 |
|---|---|---|---|
| 工作背景 | 六七条并行主线全景（LDVH V4 审计 + 多个工具项目 + 文件管理线） | fact（多项目混合，**无 scope 分区**） | ❌ 所有项目塞一段，检索无法按项目过滤 |
| 个人背景 | 协作风格画像（简短指令习惯、授权短语、工作闭环、验证习惯、meta 反思） | **preference + pattern（global scope）——黄金内容样本** | ✓ 准确、丰富、长期沉淀 |
| 当前关注 | 活跃焦点（P0/P1 缺口、workcase 验证状态） | 运行状态（LDVH 选 C 不记的那类） | ❌ 状态腐坏快于任何 TTL |
| 近期动态 | 时间线流水（30+ 条事项记录） | 会话历史压缩 | ❌ 大半可从会话历史重建（门 0 应拦） |

组织方式为单文档四段式（对比 Trae 的三级文件层次）——"当前关注 + 近期动态"近似 Trae 的 session/topics 层的浓缩，但全部持久化在一个无分区文档里。

## 二、五个关键发现

### 2.1 过时记忆的活体（比镜像问题严重一级）

记忆描述的是 **LDVH V4 架构**：编号体系（00 根 / 01-03 横切面 / 04-08 五大元素 / 30+ 模板）、六类事实对象含 **FileAsset 与 Study**（v5 已废弃，分别由既有六类的新组合与 Research 替代）、35 个 WorkCase 的 V4 状态。当前仓库已是 v5——**编号体系全变、类型系统全变**。

这段记忆如果今天被召回，AI 会拿到完全过时的 LDVH 架构描述。这是 Trae 镜像问题（复述规范）的恶化版：**复述的是已经演进掉的规范版本，且没有任何机制察觉**——记忆侧与规范侧零同步。

**LDVH 设计的三道对照防线**：受众判据门 0（规范内容不记为记忆，规范去 specs/ 读——防复述）+ TTL 衰减（过时内容自然出局）+ 晋升时验证（进入 git 层前过受控写入的版本与结构校验）。

### 2.2 隐私与工作记忆完全混杂（两层分界的刚性需求实证）

记忆中私人内容（个人文件管理细节）与工程记忆（LDVH 架构、workcase 状态）同层共存，无脱敏、无分层。该样本证明受众判据的存在意义：**私人内容天然属于本地层（scope: global 的私人事实）**，一旦记忆体被同步、共享或误进公共层即是事故。LDVH 的"什么进 git、什么不进"分界在此是最刚性的需求，不是优化项。

### 2.3 "个人背景"段是 preference 类的黄金内容样本

该段几乎可逐条拆为本地层 preference/pattern 条目（内容质量高——长期协作的真实沉淀）：

```
type: preference, scope: global
  "沟通语言简体中文，偏好简短直接回复，接受结构化输出（表格/优先级/证据链）"
type: preference
  "批量操作（重命名/裁剪类）必须先输出 before/after 预览，确认后执行"
type: pattern
  "任务流程遵循只读审计→确认→执行→报告四步闭环"
type: preference
  "常中断长时间命令，要求从断点续做并先做状态回顾"
type: preference
  "任务完成后习惯 meta 反思，追问 AI 从该任务获得的学习价值"
type: pattern
  "会用项目缩写做探测式提问，考验 AI 对项目知识的深度"
```

这是 LDVH 本地层的 **preference 类初始数据范本**——真实用户画像的形态、粒度、措辞密度可直接参考。

### 2.4 "当前关注/近期动态"是状态持久化的腐坏实证

"当前关注"记录的是某时刻的活跃焦点（workcase 验证、未推送提交审计、P0/P1 缺口清单）——数天内即失真；"近期动态"为流水账，回忆价值密度低且大半可从会话历史重建。**这正是 LDVH 选 C（状态不记忆、靠 DSH 会话历史 + Output Envelope 交还结构承载）的实证**：进行中状态的腐坏速度快于任何记忆维护周期。

### 2.5 无 scope 分区的跨项目混合

六七条主线（框架审计、多个工具项目、文件管理线）挤在同一"工作背景"段，无法按项目过滤检索——对照 LDVH 本地层 scope 字段（当前项目条目 + global 兜底）的分区价值一目了然。

## 三、对照结论

WorkBuddy 样本的三宗罪——**架构过时、隐私混杂、无分区**——恰好构成 LDVH 三层设计的答辩证据链：

| 样本问题 | LDVH 设计的解法 |
|---|---|
| 规范复述且随架构演进过时（V4→V5 漂移无察觉） | 门 0：可从 git 重新发现的不记 + TTL + 晋升校验 |
| 隐私与工程记忆同层混杂 | 两层架构：受众判据把私人内容锁在本地层 |
| 跨项目内容混一段 | scope 字段过滤（project + global 兜底） |

反向馈赠一条：**"个人背景"段是 preference 类初始数据的最佳内容范本**（LDVH 本地层冷启动素材）。

## 四、两样本（Trae + WorkBuddy）合并结论

两个外部记忆系统的实证形成互补证据对：**Trae 证明了"复述当前规范"的镜像问题，WorkBuddy 证明了"复述已演进规范"的漂移问题**——两者共同指向同一解法：记忆不承载可从规范源（specs/，git 层）读取的任何内容；记忆的疆域是"规范里没有的东西"（个人偏好、环境事实、未成熟观察）。这正是受众判据门 0 与完整性承诺（LDVH 独占记忆职责、不与规范重复）的实证根基。
