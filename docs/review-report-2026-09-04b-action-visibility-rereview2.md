## 2. 实际攻击方向

1. **A2 真修复还是文字游戏**：把“子代理与主代理表现一致”拆成能力事实、规则义务和缺口状态三层，检查条件式是否真的提供 Human 方便核对，还是只禁止当前作出已呈现声明。
2. **宿主能力链核验**：追踪 `conversation.chat.turnTail` 的注册、匹配和渲染范围；区分“主对话流内显示子代理委派条目”与“子代理自身有可注入、可访问的 Chat UI Conversation”。
3. **子代理实际事件链攻击**：核对子代理是否注册 LDVH 工具、是否产生 `ldvh-scope-claim`、是否能取得状态查询面；检查候选所要求的注入/管辖标记是否有实现入口。
4. **缺口期间的反例**：子代理承载面未提供、状态查询面未提供、两者判断失败或判断未发生时，Human 能否方便核对；检查默认态是否 fail-closed。
5. **父子管辖迁移反例**：父会话从 `governed` 迁移到 `unavailable` 或 `not_governed` 后，已安装子代理的继承状态是否同步。
6. **八处 A2 文本单一权威攻击**：逐处比较候选 §2、§3.2、§3.3、§4.3、§4.6、§6.2、§6.3、§7 的表述、义务强度和 gaps 语义。
7. **编号与引用攻击**：逐条核对候选 §4.3 拟写入 10 §7.1 的 bullet 唯一性、顺序和与 §7.2 的拆分；检查候选自身修复记录是否仍存在悬空引用。

## 3. DSH 宿主事实核验

### 3.1 `turnTail` 确实是 Chat UI Conversation 的通用定义，但证据不等于 A2 已成立

DSH Chat UI 的 `dsh-client-ui-chat/lib/client.js`：

- 第 3232–3242 行，`TurnTailNodeView` 对每个 turn 调用 `renderSlotChain("conversation.chat.turnTail", { turn, seq, openFile })`；
- 第 6287–6333 行定义 `turn-tail`，匹配 `turn/start`、`turn/end`、工具事件和带 turn 坐标的事件，并通过 `buildLocationData(..., "turn")` 建立 turn 尾节点；
- 第 6338–6339 行在传入的 `ctx.uiConversation` 上注册该定义；
- 第 3013、3022 行以及第 5896–5901 行识别子代理委派工具并计数，主对话流会显示子代理数量/属性；这证明的是**父会话 turn 的委派条目呈现**，不是子代理事件已经被注入该父 turn 的 `turnTail`。

进一步核对 `@deepseek-ai/dsh-client-ui-conversation/lib/client.js`：

- 第 1517–1556 行，`UiConversation` 通过 `binding(sessionId)` 为具体 session 建立 `BoundConversation`；
- 第 15723–15734 行存在按 session scope 取得 conversation 的路径；
- 第 14310–14369 行处理 `summary.origin === "subagent"`、面包屑和子代理 session header；
- 第 13180、13324 行仍明确写有子代理会话暂不支持图片，但这不是 turnTail 不存在的证据。

结论是：宿主代码提供了“对某个可进入 Chat UI 的 session 绑定 Conversation 时，Chat 定义可用于该 session”的结构性能力线索；同时，现有源码没有证明 LDVH 子代理已取得可用的 Human-facing session 页面、事件注入权限、子代理 session 的标记消费路径，或该页面在当前 GUI 中对 Human 可达。父 turn 上 `subagentCount` 的渲染不能偷换成子代理侧承载面已经交付。

### 3.2 LDVH 当前实现明确没有完成 A2 所需的子代理标记链

- `plugin/lib/lifecycle.js` 第 82–86 行对子代理转入 `installChild`，不创建 `AgentLifecycle` 根记录；第 189–195 行 `snapshots()` 只遍历 `agents` Map。
- `plugin/lib/child.js` 第 18–21 行明确写明子代理“no tools registration, no sessionScopes publication ... mark belongs to the human-facing root conversation”；第 59–73 行只挂 `system-prompt/assemble`，第 74–81 行只挂空的 pre-step 与 session-start 刷新。
- `plugin/lib/child.js` 第 45–48 行只复制父当时的 `scopeState`；第 78–81 行仅在**子代理自己的 session-start** 时重新读取父状态，没有父状态变更监听。
- `plugin/lib/client.js` 第 910–946 行的 `ldvh-scope-claim` 只在匹配到 `ldvh_resolve_governance_scope` 的 `tool/call` 时 claim；第 950–964 行的 `conversation.chat.turnTail` 注入只有 claim 成立才渲染标记。子代理未注册 LDVH 工具，不能按现有链路产生该 claim。
- `plugin/lib/agent-lifecycle.js` 第 68–82 行的 snapshot 只返回当前治理态、工具注册布尔值、pre-step、turn 计数、activityCount 等，不含事件历史或事件指纹。
- `plugin/lib/rpc.js` 第 20 行注册 `ldvh/lifecycle-snapshots`，`plugin/lib/lifecycle.js` 第 189–195 行只输出根 `agents`；子代理 `children` 不在查询输出内。

因此，A2 是未来实现义务，不是当前能力事实；候选若保持条件式，必须把上述事实作为当前 gaps 的明确边界，而不能只写“未提供时不声明已呈现”。

## 4. 发现列表

### R2b（high）——条件式 A2 只修复“过度声明”，没有消除 R2 指出的方便核对缺口

- **精确定位**：
  - 候选 §2 A2，**第 23 行**：“子代理与主代理表现一致……承载面由 DSH 宿主提供，未提供时，不声明已呈现，按 gaps 登记并保留机械记录”；
  - 候选 §3.2，**第 47 行**：“子代理侧承载面由 DSH 宿主提供，未提供时不声明已呈现”；
  - 候选 §3.3，**第 57 行**：“子代理会话……同形态呈现标记……承载面由 DSH 宿主提供，未提供时不声明已呈现，按 gaps 登记并保留机械记录”；
  - 候选 §4.3，**第 124 行**：“委派子代理的对话流承载面同形态呈现……未提供时不声明已呈现，按 gaps 登记并保留机械记录”；
  - 候选 §6.2，**第 154 行**：“子代理在主对话流中被渲染为委派条目……子代理会话是否暴露等价可注入的承载面仍待……核验”；
  - 候选 §6.3，**第 155–157 行**：把“子代理承载面核验”与查询面覆盖列为后续实现负担，并承认子代理不在当前查询面；
  - 候选 §7，**第 166 行**：同样把 A2 核验结果分成“通过则同形态呈现，未通过则 gaps”。

- **事实与反例**：当前实现中，子代理不注册工具（`child.js` 第 18–21、59–73 行），因此 `client.js` 第 910–964 行的现有 turnTail 标记链无法在子代理侧成立；子代理也不进入 `lifecycle.snapshots()`（`lifecycle.js` 第 189–195 行）。反例：父会话委派一个子代理，子代理获得 system-prompt 引导但没有 LDVH tool call；其注入发生而子代理侧没有 `ldvh-scope-claim`，查询面也没有子代理记录。Human 仍只能读 JSONL/activity（若 activity 可达），这正是第一次复审 R2 判为“不方便”的通道。

- **问题说明**：条件式写法确实消除了一个较窄的错误：它不再把“尚未核验”写成“已经可呈现”，并承认可能存在 gaps。但它**没有提供任何新的方便核对面**，也没有使 A2 的“与主代理表现一致”原则在 gaps 期间成立。把未满足的能力登记为 gaps 是诚实披露/停止声明的修复，不是对 Human 可核对性的功能修复。因候选 §1 第 8 行仍把“只能依赖解压会话 JSONL”定性为不满足“方便”标准，而 A2 gaps 的实际回退仍是机械记录，候选对“当前子代理是否满足该标准”没有作出明确否定披露，故 R2 的实质缺口仍在。

- **核心问题正面结论**：**条件式 A2 不是对 R2 的实质修复，主要是换成较诚实的文字来限制过度声明；就“方便核对缺口”而言属于文字游戏/语义降级，而非能力修复。** 它只有在以下条件全部满足后才可称为实质修复：宿主实际提供可进入的子代理 Conversation；LDVH 在该 session 上注册/记录注入和管辖事件；Human 能通过该承载面及可回指的查询/机械记录核对；缺失或判断失败时有明确定义的 fail-closed 状态。候选目前没有交付或验证这些条件。

- **建议修复**：保留“核验前不得声明已呈现”，但在 §1、§2 A2、§3.3、§4.3、§6.2、§7 统一写明：**当前子代理方便核对面尚未建立，A2 属已知 gaps，不满足 §1 所述方便核对目标；当前仅保留机械记录，且子代理不在 `ldvh/lifecycle-snapshots` 输出内。** 将“子代理与主代理表现一致”改成未来成立条件/目标，不要作为当前分类的无条件原则。待实现批次完成宿主 session 承载、事件标记、查询面和可回指核验后，再由独立执行体复审。

### R2c（high）——“未提供承载面”没有定义判定者、判定时机和失败默认态

- **精确定位**：候选 §3.2 第 47 行、§3.3 第 57 行、§4.3 第 124 行、§6.2 第 154 行、§7 第 166 行，均使用“DSH 宿主提供/未提供/待核验”，但没有定义检测入口、证据、判定主体、判定时点或判断失败处理。

- **反例**：实现批次没有能力枚举接口，只能看到父 turn 有 `subagentCount`；开发者据此把“存在委派条目”当作“子代理承载面存在”，错误进入“通过则同形态呈现”。另一反例是能力检查请求超时：若没有默认态，渲染器可能继续展示主代理同形态标记，形成 fail-open；若直接静默不展示，也没有登记 gaps 的机械入口和影响范围。

- **问题说明**：`未提供`（能力确定不存在）、`未核验`（尚无证据）、`判断失败`（检查出错）是三个不同状态。候选把它们合并为一个条件，没有规定默认 fail-closed，也没有规定谁有权将其登记为 gaps。该缺口会让实现自行选择，并可能把“未判断”当“已提供”。这直接触及 00 §3.4 的能力状态分层与 §7.2 的依据不足暂停要求。

- **建议修复**：增加确定性规则：由指定的宿主能力核验入口产生 `available/unavailable/unknown/error`；`unknown/error` 默认 fail-closed，禁止声明已呈现，自动登记 gaps（含对象、版本、证据、影响范围）；只有 `available` 且子代理 session 实际可绑定并渲染时，才允许声称 A2 已呈现。明确该判断属于实现验证/09 承接，规则层只规定状态与声明边界。

### R2d（high）——A2“表现一致”与 gaps 期间“子代理侧零可见性”自相矛盾，候选未限定一致性的时间/范围

- **精确定位**：候选 §2 第 23 行“子代理与主代理表现一致”；§3.3 第 57 行“同形态呈现标记”；§4.3 第 124 行同文；对照同一行“未提供时……按 gaps 登记并保留机械记录”，以及候选 §6.3 第 157 行“状态查询面亦不能作为子代理事件的替代核对面”。

- **反例**：承载面未提供的期间，父会话有迁移/注入标记，子代理只有 system-prompt 注入和机械记录；Human 在父流能看到父事件，在子代理不能看到对应事件。若“表现一致”是强制原则，则已违反；若 gaps 允许例外，则 A2 不是“子代理与主代理表现一致”，而是“目标一致、当前不一致”。

- **问题说明**：候选没有说明 A2 一致性是当前规范义务、宿主能力存在时的条件义务，还是未来目标。结果是实现者可选取有利解释：一方面以 A2 宣传覆盖子代理，另一方面以 gaps 免除所有子代理呈现责任。这延后而不是解决 R2 的矛盾。

- **建议修复**：把条文改成二态：`available` 时“必须同形态呈现”；`unknown/unavailable/error` 时“不得声明已呈现，子代理方便核对目标未满足，按 gaps 登记，受影响的子代理可见性/完成声明范围暂停”。删除或明确限定不带条件的“子代理与主代理表现一致”。

### R2e（high）——子代理管辖态不会随父会话中途迁移同步，违反候选的迁移可见性与委派不转责原则

- **精确定位**：候选 §4.3 第 121 行要求会话中途管辖态迁移在检测回合追加迁移标记；第 124 行要求子代理同形态呈现；候选 §6.3 第 155 行把“中途迁移追加标记、子代理承载面核验”列为实现负担，但没有父子同步条款。

- **源码证据**：`plugin/lib/child.js` 第 42–48 行安装时只复制父记录的 `scopeState`；第 78–81 行仅在子代理自己的 `agent/session-start` 时重新读取父记录。`plugin/lib/lifecycle.js` 第 50–76 行父侧 `syncTools()` 会更新父 `AgentLifecycle`，但没有通知 `children`；第 111–147 行父侧 assemble/session-start 也没有更新已安装 child 的 `record.scopeState`。`child.js` 第 64–73 行的 child assemble 读取自己的 record，而不是实时读取父生命周期。

- **反例**：父在 turn 1 为 `governed`，随后登记文件变化，在 turn 4 迁移到 `unavailable`；turn 2 已安装子代理且其 session-start 已结束。之后子代理继续使用 `governed` 的旧引导，父流显示迁移标记，子代理流不显示迁移或仍显示旧态。若子代理已有待执行操作，这会造成授权/工具边界与 Human 看到的父状态不一致。

- **问题说明**：条件式 A2 只讨论承载面是否存在，没有覆盖继承状态的一致性生命周期；“委派不转责”不等于允许父子状态永久脱钩。该反例是实际实现已能构造的，不是未来假设。

- **建议修复**：规则层规定父状态每次确定变化必须向所有活动子代理传播，传播事件带父事件序号/指纹和子代理 sessionId；传播失败时子代理进入 `unknown/unavailable` 的 fail-closed gaps。实现层在父生命周期变更点遍历 children 更新 record 或通过受控事件通知，不得只依赖 child session-start。

### R3b（medium）——八处 A2 表述并非完全一致，存在“规则义务/实现待核验/记录兜底”三种强度漂移

- **逐处核对**：
  1. §2 第 23 行：Human 决定写成“子代理与主代理表现一致”，并含“未提供”条件；
  2. §3.2 第 47 行：只写“注入事件可见性按 §5.7”，再补“未提供时不声明”；未明确 gaps、机械记录；
  3. §3.3 第 57 行：同形态呈现 + gaps + 机械记录；
  4. §4.3 第 124 行：同形态呈现 + gaps + 机械记录；
  5. §4.6 第 138 行：只规定标记不得承载正文，未说明子代理例外或缺口；
  6. §6.2 第 154 行：承载位置存在，但“等价可注入承载面”待核验；
  7. §6.3 第 155–157 行：实现负担，承认子代理不在当前查询面；
  8. §7 第 166 行：核验通过/未通过的二分结果。

- **问题说明**：§2 的“表现一致”像已定原则；§6.2/§6.3/§7 又把能力放在未来核验；§3.2 没有声明当前 gaps 的可见性后果；§4.6 的“标记只承载……”适用于有标记的路径，却没有定义子代理无标记时如何对 Human 呈现缺口。八处不是字面完全一致，且没有一个唯一的 A2 定义单元承担状态机、声明边界和记录后果。

- **建议修复**：把 A2 的唯一规则放在 `10 §7.1`，08 §5.3/§5.7 只回指事件类别和能力核验边界；其它位置只写指针。统一使用 `available / unknown / unavailable / error` 和对应声明、gaps、暂停后果，避免“表现一致”在 §2 取得比正文更强的权威。

### R4b（medium）——候选 §4.3 的第 7.1 bullet 列表未发生重复，但 A2 位于第 5 条且顺序合理性仍依赖未写明的事件优先级

- **逐条核对**：候选 §4.3 第 116–127 行共有 7 个 bullet，顺序为：
  1. 首回合锚标与三态；
  2. 中途迁移；
  3. 注入/注册附注与同回合合并；
  4. `unknown`；
  5. 子代理；
  6. 正文/状态查询面；
  7. 耗时辅助呈现。

- **结论**：本轮未发现重复 bullet、编号缺失或明显错序；该点攻击未攻破。子代理放在 `unknown` 之后、正文承载约束之前，在文档结构上可接受。

- **残余问题**：A2 bullet 没有说明当“子代理状态 unknown”与“父会话有迁移”同时发生时，适用哪个标记/缺口规则；这属于 R2c/R2e 的语义缺口，不是编号错误。

### R5b（medium）——§8 修复记录仍含对规范章节不成立的“§6.2/§6.3 同步”悬空引用

- **精确定位**：候选 §8 第 175 行：“同步点为候选 §2 A2 行、§3.2、§3.3、§4.3、§4.6、§6.2 与 §6.3（实现影响）”；对照 §8 第 179 行及第一次复审报告的 R5。

- **问题说明**：候选自身 §6.2/§6.3 是“旧规则处置与实现影响”下的段落，不是目标 `specs/08` 或 `specs/10` 的章节；目标规范也没有对应 §6.2/§6.3 的 A2 条款。该引用虽然现在可理解为候选内部定位，但“同步点”一词与前面的规范条款混列，仍无法让读者判断是候选落点、规范落点还是实现任务落点。它削弱 §8 “F2 已完整修复”的可回查性。

- **建议修复**：改成分组明确的定位，例如“候选文本落点：§2、§3.2、§3.3、§4.3、§4.6；事实/实现影响记录：§6.2、§6.3；后续实现核验：§7”，不要把候选章节号写成规范章节同步点。

### R6b（medium）——“按 gaps 登记并保留机械记录”未定义 gaps 的记录载体、最小字段和影响声明

- **精确定位**：候选 §2 第 23 行、§3.3 第 57 行、§4.3 第 124 行、§7 第 166 行；对照候选 §3.3 第 71 行“标记缺失或与机械记录不一致时按 00 §7.2 暂停”。

- **问题说明**：候选把 gaps 当作处理结果，但没有说明登记在哪里、由谁登记、何时更新、如何与具体子代理 session/事件关联，也没有规定 gaps 期间是否禁止“子代理与主代理表现一致”的完成声明。`child.js` 的 `children` Map 和 activity 并不等于已存在的 Human 可回读 gaps 载体；`lifecycle-snapshots` 也不输出 children。若没有这些字段，gaps 只是报告中的口头标签，不是可核对的机械状态。

- **建议修复**：最小定义 gaps 记录：父/子 sessionId、宿主版本、能力状态、核验时间、证据来源、受影响事件范围、当前可见性状态、恢复条件和声明禁区；明确它进入哪个现有机械记录/状态查询面，若查询面尚未实现则只能写“待实现，不得声明已登记”。

### R7b（low）——§5.7 对“当回合具体承载与注入时机待核验”的保留，与 §6.2 对 turnTail 事实的说明不够分层

- **精确定位**：候选 §3.3 第 55 行“具体承载与注入时机待按当前 DSH 版本核验”；候选 §6.2 第 154 行“DSH Chat UI 注册 conversation.chat.turnTail 槽位……子代理在主对话流中被渲染为委派条目”；候选 §7 第 163 行“当回合在多步回合中的精确锚定……待核验”。

- **问题说明**：宿主核验已经足以证明 Chat UI 存在 turnTail 定义和父流委派条目，但不能证明 LDVH 所需的“事件发生时注入标记”及“子代理 session 等价承载面”。候选虽然总体写了待核验，却把“承载位置存在”与“等价可注入承载面未证实”放在同一段，容易被读成能力已基本成立。

- **建议修复**：明确三层事实：①宿主有通用 turnTail 定义；②父会话委派条目可呈现；③子代理自身 Conversation 是否可被 LDVH 注入以及 Human 是否可访问，当前未证实。只有第 ③ 层通过，A2 才能从目标规则转为已实现能力。

## 7. 是否可以进入 Human 终审

**不可以进入 Human 终审。**

核心判断不是“DSH 宿主一定没有子代理承载面”，而是：宿主源码只证明了通用 Conversation/turnTail 机制和父流委派条目呈现；它没有证明当前 LDVH 子代理能获得等价标记承载面，更没有证明 Human 能方便核对子代理事件。LDVH 当前实现明确不向 child 注册工具、不发布 sessionScopes，现有 `turnTail` 标记依赖子代理无法产生的 scope-claim；子代理也不进入生命周期查询面。

因此，条件式 A2 的积极部分是**停止错误宣传**，不是**填平方便核对缺口**。候选必须至少修复 R2b、R2c、R2d、R2e、R3b、R5b、R6b；其中 R2b/R2c/R2d/R2e 为 high，涉及 A2 是否满足 §1 的核心目标、缺口期间的默认安全态和父子管辖一致性。修复改变规则语义或审核结论后，应再次由未参与形成与修复的独立执行体复审受影响维度，再由 Human 作终审决定。

本报告不修改候选文件，不修改 `specs/` 下任何文件；只提供报告与建议修复，候选是否修复及其后续提交由主控和 Human 按 01 §12.4 处理。
