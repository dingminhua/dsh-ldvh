## 1. 变更一：撤回 N1，按「声明是产出物」重写

### 1.1 Human 裁定（2026-11-22，主控转述）

> **工具的公开操作声明是「产出物」，不是规则**。它不该出现在插件规范（载体）里；**保持只有一个地方有**。

### 1.2 r2 的三项处置，撤回其中两项

| r2 位置 | r2 写法 | r3 处置 |
|---|---|---|
| r2 §8-8（裁定清单第 8 项） | 给出 R1／R2／R3 三条路（放开载体承载声明／承认第三处承载／宣布操作契约非规则） | **整项撤回**。裁定已作出，且不属三选项中的任何一条：声明**不是规则面**，故既不必放开载体（R1），也不必增加承载处（R2），且与「操作契约不是规则」不同——R3 说的是「不是规则」，裁定说的是「是产出物」，二者不是同一命题（见 §7 判断） |
| r2 §9-N1（新发现） | 「工具操作声明与『规则只来自载体』硬冲突」，判为最重 | **结清**：冲突是 r2 的误判——它把「声明的形状受开发规范约束」当成「声明是规则」。按裁定，声明是接口事实（代码执行出来的形状与可用性），不进入规则面，故 `00 §2.4.1` 的「两处承载」自洽 |
| r2 §4-HB15（硬断点） | 把 `TOOL_LAYER_CATALOG` 的 `source_path` 改指**载体** `canonical_path` | **改为指向随包声明文件**（见 §3、§4）；「改指载体」的写法撤销 |

### 1.3 `specs/11` 的禁令：保持不动（并说明它本来就对）

`specs/11` 现有三条与声明有关，**全部保留原文，不做任何修改**：

1. §3.2 第 5 项：「工具的公开操作声明形状——归 LDVH CLI 确定性服务规范；运行时机制不承载该声明，出现声明表即不合格」；
2. §5.4 第 3 项（甲类禁止项之一）：载体条目 `text` 只写场景与目标载体路径，不写操作声明形状；
3. §5.5 乙类第 6 项：载体出现声明表即不合格。

**理由（写进候选，供审核核对）**：声明是产出物，不是要求；载体只承载要求。故「载体不得出现声明表」不是对载体能力的限制，而是对**文本类别**的判别——把一份形状说明写进载体，等于把产出物冒充要求。r2 的 N1 把这条读成「载体能力不足」，方向错了。

### 1.4 `specs/05` 的地位重述（生成源 ＋ 开发约定，不再被运行期直接读）

`specs/05`（`spec_key: helper-service-contract`）的公开操作声明表 §6.1 **仍是声明的生成源**，同时它作为开发规范承载「声明程序」的开发约定（谁在什么时候改、改完怎么重建）。但**运行期不再读 `specs/05`**：能力发现与工具层只读随包的那份声明文件（§3）。

## 2. 变更二：`00` 的「两处承载」保持两处（不改）

`specs/00 §2.4.1` 按 **r2 §2.3 的文本原样采用**，不因本次裁定作任何修改。理由写进候选供审核核对：

- 规范源承载的是**要求**（运行期行动该满足什么）；声明承载的是**接口事实**（有哪些操作、形状如何、本次可用性），二者类别不同，声明不进入规范源，故「两处承载」仍成立；
- 声明不因「代码执行出来的形状」而取得规范效力，也**不能**依它推出「这个操作允许做/必须做」——这一点由载体新增条目的末段承担（§4）；
- `00 §2.4.1` L73 第 ③ 项已有的「不构成第二套规则来源者」清单里含「Code、Web、工具输出」；**随包声明文件属工具输出的同类**，不再单列。

**可选项（须 Human 定，本候选不推荐擅自改）**：在 L73 第 ③ 项清单末尾追加「、随包生成的声明文件与其它构建产物」四字级改动，使该边界对读者更显式。**默认不做**——r2 已定「其余保持现状」，且 L73 的「工具输出」已能覆盖。若 Human 要求显式化，逐字文本为：

> 改后（③）：③ 不构成第二套规则来源者——对话临时表述、事实对象、Code、Web、工具输出、随包生成的声明文件与其它构建产物、环境入口、已退出或未受控的机制文本、开发备忘（含随手写下、未受控建立者）、未取得载体准入的运行时机制。

## 3. 变更三：声明的运行期唯一副本随包走

### 3.1 形式（照判据表的随包数据文件模式）

在 `plugin/scripts/specs-bundle.mjs` 的 `BUNDLE_DEFINITIONS` 追加第三项（前两项为 `runtime-carriers` 的 copy 与 `recall-criteria` 的 generate）。

```js

  name: "operation-declarations",
  kind: "generate",

  stampName: ".operation-declarations-bundle-stamp",
}),
```

## 4. 变更四：载体新增一条要求（不是声明本身）

### 4.1 落点

**载体**：`plugin-specs/service-contract.yaml`（`spec_key: service-contract`，`title: 回执语义`）。
**条目 `id` 建议**：`declaration-file-authority`（备选：`supported-operations`）。

**为什么是它**：该载体现有的 `positioning` 是「管工具回执长什么样、三个完成状态各意味着什么、什么算部分完成、什么算不可用」，`scope` 是「拿到一个工具回执…查阅本文件」——「哪些操作算受支持」属于同一读者场景（判断某次调用/某操作是否成立）。备选落点为 `controlled-commit`（不适合，属提交面）或新建一份「操作面」载体（会多一份载体，且 `11` 要求自足，成本高于收益）。**不选 `ldvh-root`**：那是全部行动的底线，不承载工具面细节。

### 4.2 身份字段的连带改动（同一份载体修改，须一并取得同意）

- `positioning` 改后：`管工具回执长什么样、三个完成状态各意味着什么、什么算部分完成、什么算不可用，以及哪些操作算受支持`
- `scope` 改后：`拿到一个工具回执、不确定某个状态代表什么、要判断某次调用是否真的做成、或要判断某个操作是否受支持时，查阅本文件`

### 4.3 新条目正文（可直接采用，已按 `11 §5.4`／§5.5 自足与禁项自查）

```yaml
    - id: declaration-file-authority
      title: 能调用哪些操作，只认随包的那份声明
      text: |
        能调用哪些操作的清单，以随插件发布的那份声明文件为准。

        声明文件里有的操作才算受支持；没有的，一律不得当作可调用或受支持来用，也不得凭工具名、代码里的注册表、代码注释或口头说明推定某个操作存在。实现存在但未声明的操作，至多只能作为诊断信息出现，不得据它主张能力可用。

        声明文件是构建产物，不是规则文本：它只说明接口的形状与可用性，不产生行动许可，也不证明某次调用做成。

        某次调用返回的回执怎么读，按已有的回执规定；声明文件不规定回执语义，也不得据声明文件改写回执的读法。
```

## 7. 判断：「声明作为产出物、其效力来源仍是载体」是否自洽

**结论：自洽，但有一处措辞必须避免。** 理由与边界如下。

1. **可自洽的链条**：载体新增条目（`service-contract::declaration-file-authority`）才是**要求**——它规定「以随包声明为准、未声明不得当受支持、不得据声明改写回执读法」。声明文件本身只是被该要求指向的**事实载体**（有哪些操作、形状如何）。于是「效力来自载体」成立：不是「声明生效因为它是声明」，而是「这条要求生效，因为它写在已准入的载体里」；声明文件是这条要求**适用时所需的事实**，与「事实源的事实不创设义务」同构。
2. **必须避免的措辞**：不能说「声明文件是规则的一部分／声明文件具有规范效力／读声明文件即取得规则」。若这样写，就会把产出物抬成规则面，并与裁定本身冲突。
3. **一处潜在张力（如实报）**：载体条目说「以随包声明文件为准」，而声明文件由 `specs/05`（开发规范）生成 → 运行期行为的实际内容仍受开发文档的文字支配（`05 §6.1` 的字段闭集与锚点规则）。**这不是规则效力问题**（那是生成器的输入），但它意味着：**改 `specs/05` 会改变运行期「哪些操作算已声明」的判定结果**，而 `specs/05` 的修改只需开发规范程序（不需 Human 四步）。后果：一个有权限改 `specs/05` 的人可以间接改变运行期能力面。→ 建议在 `specs/05` §6 头部的说明里补一句「改变本节声明表的字段闭集或锚点规则，属改变运行期能力面，须按 `00 §3.2` 提请 Human」；否则这是**绕过根决定清单的旁路**。我把它列入 §8 待确认项，不擅自写进候选正文。
4. **另一处张力**：`05 §6.2` 允许「实现存在但未声明」被报告为 `已实现`（诊断）。载体条目禁止把未声明操作「当作可调用或受支持」，二者不冲突（诊断 ≠ 主张可用）；但若未来有人把 `已实现` 读成能力可用，就会出现「声明文件外的操作仍在工具面上」。这一指向应在 `05 §6.2` 保留其现有措辞（r3 不改），并在测试里锁住「未声明 → 只出现在诊断，不出现在已声明」。
5. **与 r2 §8-8 的关系**：r2 的问题「操作契约是规则吗」在裁定下被重新定性——**契约的形状是产出物**，但「以声明为准、未声明不受支持」这条**是要求**，落在载体。故「两处承载」与「11 的禁令」同时成立，不需要任何一方向另一方妥协。
