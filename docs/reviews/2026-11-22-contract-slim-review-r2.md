### 2.2 乙类 7（承重声明）与乙类 8（覆盖断言）是否可判、是否互相吞并 —— **可判，不吞并**，但缺「多命中」次序

- 判据不同：乙类 7 要求「以『解除某个条件后本要求即成立或不再适用』为前提」；乙类 8 要求「以自身条目的存在声明某项开发期检查已覆盖本载体」。前者看**解除条件**，后者看**覆盖对象**。
- 单纯覆盖断言（「本要求已由 precheck 保证」）无解除条件 → 不入 7；单纯承重声明（「若 X 撤下，本要求另由 Y 承担」）未断言某项检查覆盖**本载体** → 不入 8。二者互为必要条件不成立，**不吞并**。
- 一句同时满足两者（「本条已由 precheck 保证；precheck 下线时退回人工」）时两项同时成立。§5.5 甲类有「同一字段值命中多项时全部报出，不择一」（`:168`），**乙类没有对应规则**。乙类扩到 14 项、且 1／7、7／8 存在重叠面之后，缺这条会让审核者误以为只能择一入账（S3）。
- 机械面：实现只对 `RUNTIME_CARRIER_LOAD_BEARING_MARKERS`（`【承重声明】`、`**恢复条件**：`）报 `hint/load_bearing_claim`（item 标记 `5.5-乙类7`），覆盖断言无机械项——与 `:196`「机械只把这两个固定串的出现报为提示」、乙类 8「由独立审核判定」一致（探针：含「本载体已被 precheck 机械守护」的载体 0 finding）。

### 2.3 §6.5 第 3 项与乙类 7／8 互指后是否仍自洽 —— **自洽**，但第二句理由对象错位（S4）

问题在末句：「受控提交与机械守护规范 §5.3 第 6 项的检查范围限于 `specs/**`，运行时机制**不作覆盖断言**，故该范围不扩到 `plugin-specs/**`」。`09 §5.3` 第 6 项的对象是**承重声明**（`【承重声明】` 撤除须携带复核引用），不是覆盖断言；用它来论证「范围不扩」时引错了承载位。结论（不扩）与 `09` 现文一致，故只作建议改，不动判定。

### 2.6 §6.4 第 1 项 precheck 前置的顺序与 `09` 冲突 —— **必须改（M1）**

`:264`：「先形成受控提交候选并调用 `precheck-git-commit` 取得 `passed`，再按受控提交与机械守护规范 §5.7 的三步（暂存、创建、回读）落盘」。两种读法都坏：

- 读法甲（候选＝工作树内容）：precheck 在**暂存之前**调用。但 `09 §5.3`（`:118`）的输入是「候选的 message 文本与**当前 Index diff**」，`09 §5.4`（`:148`）的返回值是 Index diff 的 `snapshot_identity`；`09 §5.5`（`:160`）要求提交后 `snapshot_identity` 与 precheck 返回一致。暂存前索引为空，`09 §5.5` 明写「候选 Index 为空时仍进入检查（`git/index_empty`），不得按普通提交放行」→ 只能得到 `unverifiable`，`09 §5.3` 又规定 `unverifiable` 不得当作通过。
- 读法乙（候选＝已暂存的候选）：那么「再……暂存」是把暂存做了两次，同一句自相矛盾。
- `09` 的实际次序是：暂存（§5.7 第 1 步）→ precheck（§5.3 触发时机「候选形成之后、真实创建提交之前」）→ 创建 → 回读。

上一轮 O1 的建议写作「三步之前须取得 `passed`」，本轮照办，于是把 `09` 的「创建之前」误写成「三步之前」。修法：改为「在暂存之后、创建之前取得 `passed`（`09` §5.3 的输入是 Index diff，`09` §5.5 要求与 Git Gate 同一快照）」。这一条是机械门禁的顺序，读者照做会拿到 `unverifiable` 或让预检与 Git Gate 的快照不一致，故定必须改而非建议。
