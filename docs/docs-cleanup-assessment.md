## 一、docs/ 的法律地位（先定性质，再谈清理）

**结论：`docs/` 不在规范源内，无规范效力。**

依据：

1. `specs/01-规范模型基础规范.md` §9.1「候选路径」**只列两条**：`specs/<NN>-<标题>.md` 与 `specs/attachments/<NN>.Att.<NN>-<标题>.md`。**`docs/` 不在其中** → 不进入「当前规则源」，不产生规则资格。

3. 既有文档本身也自述为非规范（如 `docs/spec-sync-plan-2026-09-11.md:3`：「**性质**：**计划**，非候选」）。

**→ 因此清理 `docs/` 不触犯「受保护内容」或「规范退出」程序**（那是 `specs/` 的事）。但仍须注意：**`docs/` 是 git 跟踪内容（77 份中 70 份已跟踪），删除会进入历史，可回溯**——这降低了删除风险，但不消除「唯一记录」的风险。

## 六、风险与注意事项

1. **删除是有 git 历史的**：`git rm` 后仍可 `git log`/`git show` 找回 → 风险低于「永久丢失」
2. **但「不知道要找回什么」才是真风险**：若某决定只在某候选稿里记录了「为什么没选另一方案」，删除后**无从知晓其存在**
3. **本轮 9 份未跟踪文档**：它们**未入库**，若清理会**真正丢失**（无 git 历史）
4. **我不建议一次性大批量删除**：候选稿的「决策过程」价值需 Human 判断，不宜由 AI 单方定

## 七、我的建议（供裁定）

**分层处置，先归档后清理**：

1. **第一步（低风险）**：建立 `docs/archive/`，把 21 份候选稿 + v4/v5 遗留**移入**（而非删除）——保留 git 历史与可查性，同时让 `docs/` 根目录清爽
2. **第二步（需你判断）**：观察一段时间后，若确无引用，再决定是否删除
3. **保留不动**：P0/事故、执行记录、评审报告、dev-memo、概念澄清底稿、本轮 9 份新产出

**依据**：00 §6.3 价值纪律要求「新增或修改机制必须说明……以什么证据核对」——**删除也是一种机制变更**，应对称地要求说明收益与风险。而在**没有消费方申报**的情况下，删除收益仅是「目录整洁」，风险却是「可能丢失决策溯源」。**收益与风险不对称，故倾向归档而非删除。**
