## 3. 拟裁定事项的核心权衡：item 状态属于「事实」还是「活动态」

这是本提案要求裁定的**根本问题**，其余都是它的推论。

底座草案 §0.2 已对信息分层（该草案经 Human 终审，但其中「状态两层归属」是否延及 item 级未定）：

| 层 | 权威位置 | 底座定性 |
|---|---|---|
| 事实 | 事实源 YAML（Git 工作树） | 唯一权威，经受控写入 |
| 事实对象内嵌状态机 | 事实源 `status` 字段 | 跃迁 = 受控写入 |
| **活动态** | **运行时** | 事件流 = 审计投影，**绝不作事实来源** |
| 交付物 | 通信内容 | 「像事实」者只能作候选 |

**Human 在本会话已给出判据**（原话）：

> 「进度事件流，当然不需要进git，关键是当item有了结果物或者改变了某些需要提交的内容，那么这个item的状态就要被记录，也就是item在wc中需要被记录的状态是和有无改变需要提交的内容有关的」

该判据的要点：

1. **细粒度进度**（跑第几个测试、覆盖率）→ 事件流，**不进 Git**；
2. **item 状态被记录的条件** = 该 item **产生了结果物或改变了需提交的内容**；
3. 即：**item 状态的记录时机绑定于「有无受管写入」**。

**本判据优于草案判据**，理由如下：

| | 草案遗留 9 判据 | Human 本会话判据 |
|---|---|---|
| 表述 | 「凡改变『下一步该做什么』的信息落盘；只改变『现在做到哪了』的观感信息走呈现」 | 「有结果物/改变了需提交的内容 → 状态被记录」 |
| 判断方式 | 语义判断（须人答「这改变了下一步吗」） | **机械事实**（工作树是否变更） |
| 可机械校验 | ❌ | ✅ **LDVH 已有锚点** |

机械锚点已存在：LDVH 事实源即 Git 工作树（06 号），「需提交的内容」有现成判据——工作树变更 / staged diff（`plugin/lib/commit-validation.js:103` 的 `snapshotIdentity(diff, message)` 已把 staged diff 纳入指纹）。

**且该判据与底座已终审的「写入权三分区」同构**（`team-control-foundation-draft.md:81-84`）：

| 底座分区 | 内容 | 判据下是否记录 item 状态 |
|---|---|---|
| 受管写入（单点在主控） | LDVH 工作树 / 事实源 / Git、受保护路径 | ✅ **记录** |
| 瞬态工作产物 | 测试输出 / coverage / 构建产物 / 日志 | ❌ 不记录（归 L3 副作用） |
| 成员私有区 | `scratch/`（gitignore） | ❌ 不记录 |

### 4.2 粒度（本提案请求 Human 在甲之下选定）

| 选项 | 状态闭集 | 优点 | 代价 |
|---|---|---|---|
| **甲-1** | 六态：`pending`/`running`/`completed`/`failed`/`cancelled`/`skipped` | 对齐 `dsh_workflow` 成熟模型（`src/types.ts:289`）；可表达失败与跳过 | 字段值最多 |

| **甲-3** | 记录「哪个 item 产生了哪个提交」的映射 | 直接贴合 Human 判据原文 | 丢失时序与失败信息；无法支撑「复核不可跳过」的前置判定 |

### 4.3 字段形态（若选甲-1）

候选（**设计草案，须 Human 批准后方可定稿**）：

```
| `items` | array | 条件 | item 级执行状态 | 每项 `{item_id, status, evidence_ref?}`；
  仅在 status 发生变化且该变化**伴随受管写入**时更新（Human 判据）；
  `status` 闭集见下；不置于 `plan` 内（故不触发 C2，同 `reviews` 先例） |
```

> **已删除 `updated_at`（据独立审核更正）**：21:119 逐字「**不设 `updated_at`，变更走 `change_log`**」，起草稿的字段形状曾含之，违反该条。时序改由变更流承载——每次写入恰好追加一条 `change_log`（21 §14 / 03 §9.5），其 `at` 即该状态变化的**事件时间**，无须在 item 内重复记录修改时间。
>
> **节 `{item_id, status, evidence_ref?}` 三项的取舍**：`item_id` 语义见 §7.1（未定）；`status` 见下方闭集（但 §5.3.1(b)(c) 指出 `running`/`failed` 与 Human 判据存在冲突，未解决前不得定稿）；`evidence_ref` 使 32 §13「收货以证据、不轻信声明」可机械核对。

`status` 闭集（甲-1）：`pending`（未开始）/ `running`（进行中）/ `completed`（已产出并收货）/ `failed`（执行失败）/ `cancelled`（取消）/ `skipped`（跳过）。

> **该闭集的两条未解决张力**（见 §5.3.1）：`running` 与 `failed` 在 Human 判据（「伴随受管写入才记录」）下几乎/常常不可写。三选一须 Human 定：①放宽为「进入执行即记一次」；②承认二者只在事件流可见、对象中不出现；③把失败设为判据例外。**在选定前，本节闭集不构成可用设计。**

`evidence_ref` 指向该 item 的产物（提交 sha / 文件锚点），使「收货以证据、不轻信声明」（32 §13）可机械核对。

## 5. 各自影响（00 §4.4 第 4 项）

### 5.1 C2 授权钉扎的影响（决定性）

`plugin/lib/workcase-writer.js:234`：

```javascript
export function computeAuthorizationFingerprint(plan, scope) {
  const canonical = stableStringify({ plan, scope });
  return createHash("sha256").update(canonical, "utf8").digest("hex");
}
```

**指纹只哈希 `plan` 与 `scope`**。故：

- **选项甲**（独立字段）→ 指纹不变 → 不触发 C2 → 授权持续有效；
- **选项乙**（写入 `plan` 内）→ 每次 item 跃迁改变 `plan` 内容 → 指纹失配 → 按 21 §10.3 **授权自动失效、回到 draft 局部重批** → 每次进度更新都触发重批，**不可用**。

**先例**：`specs/21-WorkCase-工单.md:178` 对 `reviews` 的原文——「录入 **不改变** `plan` 或 `scope`，故**不触发 C2**」。选项甲与该先例同构。

| 诉求 | 甲（新增 `items` 承载） | 丙（不承载） | **戊（最小承载，独立审核提出）** |

#### 5.2.1 「戊」方案的必要披露（据独立审核更正）

起草稿曾写「§5.2 丙→四项诉求全部无法满足」，**该断言不成立**，现更正并补出一个更简方案：

**(1) 复核档可零新字段派生。** `reviews` 字段已存在（21 §8），10:138 已登记其呈现。据此可派生：
- `复核已完成`（`reviews` 非空）——**可机械判**；
- 但 `复核进行中`（已提请、未完成）**缺机械信号**——`reviews` 只在复核**完成后**追加。故此方案能表达「有/无复核记录」，**不能**表达「正在复核」。

**(2) 「判据收齐」可用单一 checkpoint 标记承载**，不必用六态数组。尤其 §5.3.1(b)(c) 指出的 `running`/`failed` 不可写问题，在窄方案下自然消失。

**(3) 正文「## 执行」节是既定承载位。** 21:151 逐字：「`## 执行` ← attempt 与执行进展的正文承载；跨会话接力」。起草稿**未与该位作比较**——这是范围论证的缺口。

**(4) 据 01 §11.1 第 3 步（「现有规范能否通过最小充分修改无损承载」），至少应比较**：①纯 `reviews` 派生复核档；②checkpoint 单标记；③正文承载；④本提案的 `items` 六态。起草稿只比较了甲/乙/丙，**比较空间不完整**。

> **这不否定本提案**，但要求 Human 在裁定 `items` 之前先排除更简方案。若诉求仅为「复核可见 + 不可跳过 + 进度可见」，则 (1)+(3) 的组合可能已足够——**`items` 的增量价值主要在「逐 item 的可核执行状态」**，那是否必要属 Human 判断。

#### 5.3.1 红线 4 的三处未解决冲突（起草稿未披露）

**(a) `items.updated_at` 与 21:119 直接冲突，须删除或改设计。**
`specs/21-WorkCase-工单.md:119` 逐字规定：

> 「`created_at` 由 Code 在受控创建时填写，AI 不得填写或推导；**不设 `updated_at`，变更走 `change_log`**」

起草稿 §4.3 的候选字段形状含 `updated_at`——**违反该条**。注意区分：`reviews.at` 是**事件时间**（那次复核何时发生），`updated_at` 是**修改时间**（记录何时被改），后者恰是 21:119 所禁的形态。**修正方向**：删去 `updated_at`；若需时序，改用「事件时间」语义（如该 item 状态变化所伴随的那次 change_log 条目时间）或干脆不记时间（change_log 已有）。

**(b) `running` 态在 Human 判据下几乎不可写。**
Human 判据为「item 有结果物或改变了需提交的内容 → 状态被记录」。而「开始执行」通常**不伴随**该 item 的受管写入——于是 `running` 这个最直观的进度信号反而落不进对象。**须裁定**：是放宽为「进入执行即记一次」，还是承认 `running` 只在事件流可见、对象中不出现。

**(c) `failed` 态同理，且后果更重。**
失败常常**没有**受管写入（正因失败而没产出）。于是按 Human 判据，「最需要回读的失败信息」反而不可记录——这与本提案主张的 V6（工作接续）直接相悖。**须裁定**：失败是否作为判据的例外（不受「伴随受管写入」约束）。

> 起草稿把红线 4 判为「否」，理由写的是「本提案恰是**拒绝**完整日志」。该理由**只在 (a)(b)(c) 均被解决后才成立**；在三者未定时，`items` 的六态数组确实构成对执行过程的持续状态追踪，与红线 4 的立法方向（v4→v5 重建砍掉 2753 行过程承载）存在实质张力。据此更正为「须 Human 裁定」。
