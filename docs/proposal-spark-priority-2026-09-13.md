## 4. 字段设计（照抄 20 §8 既有「条件」型字段形态）

`priority` 采用与 `disposition` / `relations` / `evolution` 相同的**条件型**形态：

```markdown
| `priority` | string | 条件 | 悬置排序档位 | 闭集 `P0`/`P1`/`P2`/`P3`；**AI 综合判断初值，Human 可按情况调整**；`open` 时出现，终态省略（为悬置中的排序依据，非对象价值声明） |
```

**字段间不变量**（新增）：
- `priority` 出现 ⇔ `status = open`
- 与既有 `disposition` 出现 ⇔ `status ∈ {implemented, discarded}` **正好互补**，不重叠

**取值闭集**：`P0` / `P1` / `P2` / `P3`（沿用 v4，无需重新定义语义）

## 5. 为什么这不构成「装饰字段」

既有红线（22 §271 / 23 §252 / 26 §258）的原话是：「**重要性由消费点引用体现**」，判为装饰字段。

**本字段与该红线的关系须说清，不可含糊**：

- 该红线反对的是「**对象自我声明价值**」——标注"我很重要"却无人消费
- 本字段声明的是「**这堆悬置里先看哪个**」——它描述**悬置状态的处置次序**，且**终态即消失**
- 关键区别：它是**过程状态**，不是**价值属性**

**但这不等于豁免。** 03 §11.3-4 要求字段扩展「必须说明**消费方**」——本提案的消费方见 §6，**若 Human 不认可该消费方，本字段仍不成立**。

## 6. 消费方（03 §11.3-4 要求，须 Human 确认）

**须评估的冲突**：20 §262 声明「Spark 被召回不表示……提高其优先级」；21 §252 声明 WorkCase「被召回……也不表示可以提高优先级」。本提案不改变该语义——**召回不自动提级**与**列表可按 priority 排序**是两回事，但**措辞需调整以免读作冲突**。

## 7. AI 判断的合法性边界（03 §8 相关）

03 §8 原文：

> Code 不得使用相似度、embedding、关键词权重或 **AI 输出自动裁决**相关性、适用性或事实结论。

**本字段不受该条禁止**，理由：该条禁止的是"**AI 输出自动裁决**"，而本设计中 AI 仅提供**初值**，**Human 保有调整权**。这与既有先例同型：

> `specs/20` §14.1：「question 可读性｜创建时｜……｜Human 确认记录｜**AI 初审+Human 终审**｜……」

**故 priority 的验证入口应登记为「AI 综合判断 + Human 可调整」，而非机械校验。**
