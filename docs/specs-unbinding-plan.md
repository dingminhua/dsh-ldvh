# specs 解绑方案（草案）

> **地位**：方案类内容，依 `specs/02` §6.4 判据 9 落 `docs/`；依 `specs/09` §5.3 第 5 项**不得作权威依据**；依 `specs/24` §6.7 不对象化为报告对象。
> **状态**：草案。本文件**未修改任何规范、载体或代码**。文中「改前」一律指当前工作树或 HEAD 的实际文本，「改后」是候选表述，尚未取得任何审核或 Human 决定。
> **来源**：Human 2026-11-22 指示——「原来的 specs 过于形式主义导致无法推进正常的工作，所以原来的 specs 需要先解绑；对于插件规范，需要严格的审核与检查，但对于 specs 不再需要格式上的检查」。

## 0. 这份方案要解决什么

> **独立审核结论：不通过**（`docs/reviews/2026-11-22-unbinding-plan-review.md`：12 必须改／8 建议改／17 处方案未提到的依赖机制／1 处本方案数字不成立）。
>
> **本节数字已更正**：初稿写「五轮共 51 条必须改（13／6／7／9／4）」——**该数字不成立**。仓库内可查的复现数为 **26 条**（6／7／9／4；第一轮的 13 条在仓库内无记录，13＋6＋7＋9＋4＝39 亦非 51）。更严重的是**收益论证**：26 条中只有 **6 条完全随承接机制消失、3 条部分消失、17 条与承接无关**（外推全量约 12 消失／6 部分／约 33 仍需处置）。**「承接机制是五轮审核成本的主要来源」只对约四分之一成立**，本方案 §0 的原判断已作废。
>
> 审核同时指出本方案**三处把未查证的事写成了已成立的事实**，且它们正是收益论证与"不设中间态"承诺的承重点：① **运行期根本没有载体读取入口**，召回与注入今天仍指向 `specs/`（`source-recall.js` 读 `specs/*.md`，`recall-injection.js` 注入「规范源：」）；② **事实召回判据表在运行期解析 `specs/20–29` 的表格**（`recall-criteria.js` 的 `parseRecallCriteriaTable`），`specs/` 的表格形态在运行期事实上仍是硬要求；③ **两份 README 是受保护内容且现文把 `specs/` 称为规范源与权威**，本方案完全未列。
>
> 结论：**方向成立，但本方案不是可执行版本**——它缺一个前置（运行期载体读取入口）与一批下游影响清单（17 处）。按审核给的修正顺序，本方案应作为**第二批**（先做读取入口与承接覆盖率核对），不能直接落地。

载体契约 `specs/11` 从一轮到五轮共出 26 条可复现的必须改（6／7／9／4），每一轮都在同一类地方翻车：条文自身互斥、判据不可执行、口径缺失、边界情形无穷。**根因不是某一条写错，是 `specs/11` 被要求承担一件它承担不了的事**——把 `specs/` 里的规则搬进载体，同时保持"每条都能机械判定、每条都承接得清、每条都有来源可查"。

解绑的思路是**取消搬迁的前提**：如果 `specs/` 不再是运行期规则源，那么载体不必"承接"它的条文，承接登记、优先关系、语义相符审核这一整套机制失去对象，契约随之瘦身到它该有的规模。

## 1. 解绑前后对照

| 维度 | 解绑前 | 解绑后（候选） |
|---|---|---|
| `specs/` 的角色 | 规范源成员，可强制执行规则的来源 | 开发期需求与开发约定；只约束开发过程 |
| 运行期规则的来源 | 开发规范中面向运行期的条文 ＋ 运行时机制；前者按 00 §2.4.1 过渡句在未被逐条承接时**仍然生效** | **只有运行时机制**（`plugin-specs/`） |
| `specs/` 的形式要求 | 身份块、共同章节结构、编号登记、当前规则源成立条件，机械校验 | 降为开发期约定，**不再有机械强制面** |
| 载体与 `specs/` 的关系 | 载体逐条承接 `specs/` 的条文并登记锚点（`carries`，127 条） | **无承接关系**；载体自足，不再声明承接 |
| 同题两份文本的取用 | 按 `specs/11` §6.4 优先关系（须已承接 ＋ 已准入） | 不再可能出现"同题两面"；载体是运行期唯一规则源 |
| 严格性的落点 | 分散在两边（`specs/` 的形式检查 ＋ 载体的形态与语义审核） | **集中在载体一侧**：形态、条目可判定、体量、误伤量测、逐条变异取证 |
| 载体效力成立的要件 | 形态合格（校验器）＋ Human 决定 ＋ 建设期独立审核 ＋ 读取入口与门禁面落地 | 同前（不因解绑而放宽） |

## 2. 解绑动作清单

标注：**[根]**＝触及 `00 §3.2` 根决定清单；**[受保护]**＝触及 `00 §3.3` 受保护内容程序；**[需裁]**＝须 Human 决定。

### 2.1 `specs/00`（根规范）

**[根][受保护] ① §2.4.1 两类载体形态与过渡句**

- 改前：「插件内规范规则是随插件承载的规范要求，由两个载体形态承载：**开发规范**（……其条文可含面向运行期的部分）与**运行时机制**（约束运行期行动的运行期读物）。」「**尚未被运行时机制逐条承接的面向运行期条文，仍按开发规范面成立并生效**；运行时机制逐条承接相应条文后，该部分改由运行时机制承担。」
- 改后（候选）：两个载体形态改为**按约束对象分工**——开发规范约束开发过程（提交、审核、协作、构建、发布），运行时机制约束运行期行动；开发规范的条文**不再对运行期行动生效**；运行期规则只来自运行时机制。
- 删除「尚未被逐条承接的面向运行期条文仍按开发规范面成立并生效」这一过渡句。

**[根][受保护] ② §2.4.1 优先关系**

- 改前：「同一主题在两个载体形态各自成文时，运行期以运行时机制的表述为准——该优先关系自运行时机制逐条承接相应运行期条文、并取得载体准入后成立。」
- 改后（候选）：删除该句；若仍需兜底，改为「运行期只适用运行时机制；开发规范的条文不进入运行期判断」这一句陈述，不再设优先关系与成立条件。

**[根][受保护] ③ §2.9 建立程序**

- 改前：「插件内规范规则的两个载体形态共用同一套建立程序：运行时机制的载体建立须经 Human 决定，并在其进入决定前完成建设期独立审核；该载体取得准入后，所载运行期条文依 §2.4.1 取得效力。」
- 改后（候选）：两种载体形态**分用两套程序**——运行时机制：受控写入 ＋ Human 决定 ＋ 建设期独立审核 ＋ 载体准入 ＋ 读取入口与门禁面落地（承载体契约）；开发规范：受控提交 ＋ 独立审核 ＋ 必要的 Human 同意（承载于 `specs/01` 与各下位规范），**不再有"准入"这一层**。

**[根] ④ §3.2 根决定清单**

- 改前：「改变两类语义构成要素及其承载（规范源、事实源）」属根决定。
- 改后（候选）：**不动**。解绑本身即属该条列举的事项——「改变……及其承载」——故必须走根决定程序（本项是 Human 的决定，不是主控的处置）。

**[受保护] ⑤ §2.4.4 内容纪律**

- 改前／改后：**不动**。它管的是"规范正文只叙述当前有效规则"，与解绑无冲突；解绑后它同样适用于载体条目正文（载体契约 §5.4 已引用其精神）。

## 3. 保留不动的东西

- `00 §3.3` 受保护内容的修改程序（展示候选、独立审核、Human 明确同意、独立提交）——**与解绑无关**；
- `specs/09` 的受控提交契约本身（消息格式、关键变更逐条对应、precheck 三值、Git Gate 终闸、三步动作、必停）；
- 事实源那整套（`specs/02`、`specs/20`–`specs/26`）——事实对象与摩擦／经验的机制与解绑无关；
- 载体侧的严格性：形态、条目可判定、体量、误伤量测、逐条变异取证、路由表、命名空间；
- 载体作为**受保护内容**的地位（`10 §7.6`）。

## 4. 风险与代价（如实列）

1. **`specs/` 失去机械保障**：身份块写错、章节结构错、引用悬空、条文互相矛盾，不再有机械拦截。代价由"人＋独立审核"承担。这正是解绑要接受的交换，但须由 Human 明知。
2. **载体成为运行期唯一规则源，单点风险上升**：载体写错＝运行期行为错，无第二来源兜底。缓解手段是载体侧的严格审核与机械校验（已在做），以及 §5.5 乙类的语义把关。
3. **需求与规则的追溯链变弱**：载体条目不再声明承接哪条开发规范，"这条要求从哪来"只能靠 git 历史与开发期文档。缓解：开发期材料保留、载体建立时的 Human 决定与独立审核记录留存。
4. **解绑是根决定**：触及 `00 §2.4`／`§2.9`，须走 `00 §3.2` 根决定 ＋ `00 §3.3` 受保护内容程序（展示候选、独立审核、Human 明确同意、独立提交）。
5. **半解绑是最大的坑**：只撤机械检查、却让 `specs/` 继续承担运行期规则，会留下一批"有规则效力、无形式保障、无机械校验"的条文——比现状更难判断。故本方案按"**全面退为需求文档**"设计，不设中间态。

## 5. 分批落地顺序（候选）

## 6. 需 Human 裁定的点

1. **解绑范围**：全面退为需求文档（动 `00`，根决定）vs 只解除格式检查（不动 `00`，但留下半解绑）——本方案按前者设计（§4 第 5 条）。
2. **`specs/09` §5.3 第 1–4 项（提交消息格式）是否保留**——本方案按"保留"设计（属提交纪律，不属 `specs/` 格式）。
3. **载体是否保留任何来源声明**：完全不留（§2.5 删除 `carries`）vs 降为非判定的溯源信息（不进载体校验、不参与准入，仅供人查）。本方案按**完全删除**设计；若要留溯源，须另行定义其形态与承载位（不进载体＝不进运行期语料，则应落开发期材料）。
4. **引导面分流**（§2.7）：运行期会话是否另有一套"按场景指向载体"的引导。
5. **载体删除 `controlled-commit.yaml` 与 `specs/09` 补写**（已裁定、已过覆盖核对与独立审核）是否与解绑同批落地——本方案建议**同批**（它在两种读法下都要做）。
