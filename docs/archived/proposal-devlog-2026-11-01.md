# 开发日志事实类型（候选）与 doc 43 试点（2026-11-01）

> 状态：**候选，未落规范源、未创建任何事实对象**。本文只回答三件事——
> 这个类型长什么样、生命周期怎么收、拿真材料试一遍是否可用。
>
> 依据：用户 2026-11-01 指示「小范围尝试一下」+「应该也有生命周期吧，或者可以清理的
> 有些过时的内容可以转换为不要」。试点材料取 ld-rl-poker `docs/43-history-performance-
> and-runtime.md`（27 KB / 7 节，主题单一、每节都有落地 commit，是最干净的试点对象）。
>
> **本文不主张已成立**（`00 §5.6`）。它要 Human 定的只有一处，见 §末。

## 一、为什么是「开发日志」而不是「新的事实类型」

先排除一条走不通的路：**现有 7 类都装不下过程记录**，这是逐条核过的，不是没找。

| 类型 | 排除依据（逐字） |
|---|---|
| Spark | `20:98`「以下内容不形成 Spark：…过程日志、逐条聊天、工具输出」 |
| ADR | `22:72`「对话中的临时取舍（重要性不足以对象化的留在会话记录）」；ADR 是点状决定 |
| Pitfall | `23:§16.1` 入档前置 = **另一主体复现验证**；且只要「已验证失败机制」，不要过程 |
| Research | `24:120`「运行日志与一次性笔记」不得形成 Research；`urls` 必填且须 HTTP(S) |
| WorkCase | 只在**有工单**时才有执行节；ld-rl-poker 实测 3 个工单执行节合计 7,381 B（7.2 KB），而 docs 有 491,945 B（480 KB） |
| Friction | 只收「应当修但尚未修的系统性阻碍」 |
| Norm | 只收「必须被遵守的约束」 |

`35 §8.3` 路由表第 6 条正是为此而设：「以上皆不成立 → 不承载」。所以现状不是
「大家忘了归类」，而是**规范明确要求这类内容不承载**——而它实际上在 `docs/` 里
长到了 480 KB（19 份 / 491,945 B 实测）。这是规范与实际的差距，不是使用者的疏忽。

## 二、类型骨架（草案）

### 2.1 身份与载体

| 项 | 提案 |
|---|---|
| `fact_type_key` | `devlog`（号位待定：`28` 为空） |
| 载体 | 平铺单文件 `ldvh-base/devlogs/devlog-<uid>.md`，沿用其余 7 类 |
| 正文骨架 | H2：`## 背景` / `## 做法` / `## 实测` / `## 结论与边界` / `## 去向` |

正文骨架**故意只有五段**，且每段都能被机械核：`实测` 段必须含至少一个
「指标 + 前后数值 + 测量方式」，`去向` 段必须含 commit / ADR uid / 「未落地」三者之一。

### 2.2 frontmatter 闭集

| 字段 | 必填 | 语义 | 约束 |
|---|---|---|---|
| `object_uid` / `fact_type_key` / `created_at` / `change_log` | 必填 | 公共 | 同其余类型 |
| `title` | 必填 | ≤ 30 字 | 供扫读 |
| `status` | 必填 | `active` / `absorbed` / `superseded` / `dropped` | 见 §三 |
| `serves` | 条件 | 主题锚点 `SG-n` | **直接复用 goal.md 的 SG 锚点，不新建主题对象** |
| `topic` | 必填 | 主题短名（如「训练性能」） | ≤ 20 字；用于 `list` 分组与主题内排序，**不是**跨对象引用 |
| `occurred_at` | 必填 | 事件发生日期 | RFC3339；**与 `created_at` 区分**（补录的旧日志二者不同） |
| `evidence_refs` | 条件 | 外部证据 | 形如 `[{kind:"commit", ref:"8559e5c..."}, {kind:"file", ref:"tools/..."}]` |
| `retirement_reason` | 条件 | 终态原因 | 闭集，见 §三；终态必填、active 禁现 |

**为什么不新设「主题」对象**：`serves` 指向 goal.md 的 SG-n 已经是「主题」，
且已有机械级联（`25 §12`）。实测 ld-rl-poker 的 14 个 SG 与 6 个 docs 主题是
自然的一一对应（训练性能→SG-5、规则验证→SG-6、界面配置台→SG-9/10、推进方法→SG-14）。
新设主题对象要改 8 个 writer 的字段闭集、要加 `refs` 过滤面，而收益只是「主题能有一份
自己的结论」——那份结论更适合放进 goal.md 的 SG 判据里。

**`topic` 是文本不是引用**：它是给人分组用的标签，写错了不会悬空、也不需要级联。
这是刻意降级——把跨对象引用做成字符串，就是为了让「主题」这个东西不进引用图。

## 三、生命周期（用户新增要求的正面回答）

四个状态，其中三个是终态（`active` 是唯一在管态）：

| 状态 | 含义 | 谁进入 |
|---|---|---|
| `active` | 结论仍承重：要么在被后续工作依赖，要么是「勿重试」的否定结论 | 创建即此态 |
| `absorbed` | **结论已被代码/规范完整承接**，日志只剩过程价值 | 落地 commit 合并后 |
| `superseded` | 被后来的日志推翻或修正 | 新条目建立时，旧条目指向新条目 |
| `dropped` | **不再承重，且不属于以上两种**——过时、范围消失、事实性错误且无保留价值 | Human 决定 |

三条关系（各 1 条，写进 `relations`）：`absorbed-into`（→ commit 或 ADR）、
`superseded-by`（→ devlog）、无关系（`dropped`）。

### 3.1 关键设计：`absorbed` 是「压缩」不是「删除」

这是对用户「可以清理的」的直接回答。**清理不等于删除文件**：

| 状态 | 载体处理 | 保留什么 |
|---|---|---|
| `active` | 全文保留 | 全正文 |
| `absorbed` | **正文压缩为一条 ≤ 200 字符的结论行 + 指向 commit 的引用**，过程段清空 | 结论、证据指针、发生时间 |
| `superseded` | 全文保留 | 全正文（推翻过程本身是教训，见 §3.2） |
| `dropped` | 正文压缩为「处置说明」一段 | 为什么丢、谁决定的 |

实测依据（ld-rl-poker 全库）：终态对象占语料 **4%**（113 KB / 2,571 KB，实测 `status` 逐文件统计）。
也就是说「全部对象都退休」也只省 4% 字节——**清理的价值不在省空间，在于把
「现在还要读的东西」和「只在追溯时要读的东西」分开**。真正省的是 F3 单次读取量：
51 号现在一次读 158.6 KB（162,438 B），压缩后典型条目 4–7 KB。

### 3.2 `superseded` 不删的理由（一手来源）

Google SRE postmortem 的原文：「**An unreviewed postmortem might as well never
have existed.**」被推翻的结论本身是资产——它记的是「这条路为什么走不通」。

ld-rl-poker 的 51 号里，标题即否定结论的有 **15 节 / 58 KB（37%）**，包括
「一次被自己推翻的优化」「两个候选证伪」「72.8% 算力花在已完成的手上 —— 但七条
绕开路径全部不可行」。这些是**最不该被清理的那部分**：删了就会有人重试。

所以清理规则必须按「结论是否还承重」分档，而不是按「是不是旧」。§三 的四态就是
这个分档。

## 四、试点：doc 43 → 4 条日志

doc 43 有 7 个 H3 节。按「已收敛 + 有一条可陈述结论 + 跨会话要回查」判据归并后是 4 条
（不是 7 条，也不是 1 条）。以下是**按新骨架真写出来的候选**，不是示意。

### 条目 1（active）

```yaml
title: 动作菜单向量化与按状态缓存
topic: 训练性能
serves: SG-5
occurred_at: 2026-10-23
status: active
evidence_refs: [{kind: commit, ref: 7964f0b}, {kind: file, ref: tools/gpu_hu_menu.py}]
```

- **背景**：无树环境 `env.step` 每步约 40 个算子，5 档循环逐槽写回。
- **做法**：整表向量化（约 8 算子/步），去重改 (K,K) 成对距离矩阵 + 下三角掩码；
  同一引擎状态的 `(mask, amt, kinds)` 挂 `DynamicHUState` 按状态缓存。
- **实测**：`env.step` 14.29 → 11.55 ms（−19%）；决策吞吐 286,562 → 354,618/秒（+24%）；
  训练端到端 1,048 → 1,376 手/秒（+31%）；GPU 利用率 19.1% → 22.8%。
  测量方式：`tools/probe_training_throughput.py`，HU 100bb / batch 4096 / 200 步。
- **结论与边界**：向量化对所有档数生效；缓存只对克隆前的同状态有效，克隆不带缓存。
- **去向**：已落地 `7964f0b`；顺带修掉查看台金额单位（筹码当 bb）。

### 条目 2（active，否定结论）

```yaml
title: 逐轮爬升 batch 会导致吞吐塌陷
topic: 训练性能
serves: SG-5
occurred_at: 2026-10-23
status: active
evidence_refs: [{kind: commit, ref: 3881e64}]
```

- **背景**：自动批次最初按「每轮 ×1.25 逼近上限」实现。
- **做法**：改为首轮按预算定档、之后不再爬升；只有显存被挤占时才下调。
- **实测**：逐轮爬升时峰值顶到 32.1 GB 满卡，吞吐从 3,426 塌到 **354–598 手/秒**；
  改为首轮定档后 2,000 → 4,019 手/秒，GPU 利用率 19.1% → 32.1%。
- **结论与边界**：**逐轮改张量尺寸会让分配器无法复用缓存**，这是塌陷的根因，
  不是「batch 太大」。另一个已排除的做法：不能用「当前空闲显存」做预算
  （`mem_get_info()` 会随本进程缓存增长而缩水）。
- **去向**：已落地 `3881e64`；此条属**否定结论**，永不退休——它防的是有人重新引入爬升。

### 条目 4（superseded）

```yaml
title: 一万里手长跑下 GPU 均值 25.1%
topic: 训练性能
serves: SG-5
occurred_at: 2026-10-23
status: superseded
relations: [{superseded-by: {kind: devlog, ref: <条目3 的 uid>}}]
```

- **原文结论**：HU 100bb 长跑 992,321 手，GPU 利用率均值 25.1% / 非零均值 34.5%。
- **被推翻的方式**：51 号 `36.1` 用干净口径（CUDA event + 逐步计时）实测一轮
  131.8 ms 与 GPU 内核 105.9 ms，得**占用 41.4%**，并明写「此前用 iterate 单步
  95% 论证『GPU 已饱和』，那是局部不是全局」。
- **保留理由**：两个数字**测量口径不同**（`nvidia-smi` 采样 vs 干净计时），
  不是谁错了。这条日志的价值恰在于它记下了「采样口径会低报」，防止后人拿
  `nvidia-smi` 的 19.1% 去论证「还有 80% 空间」。

**这四条合起来是 4 条而不是 7 条**。43 号的 7 节实测如下（`###` 计数，按出现次序）：

| 节 | 体量 | 去向 | 理由 |
|---|---:|---|---|
| §1 无树环境提速：动作菜单向量化 + 按状态缓存 | 2.1 K | **条目 1** | 一条独立结论 |
| §2 自弈采集早停 + 首轮后重定档 | 2.1 K | **条目 2** 的一半 | 与 §4 同属「batch / 吞吐」同一件事 |
| §3 稳态性能与 GPU 利用率（~100 万手） | 1.1 K | **条目 4** | 被 51 号干净计时改写为 41.4% |
| §4 自动批次：首轮定档、整卡预算、实测校准 | 2.3 K | **条目 2** | 含「逐轮爬升塌陷」这条否定结论 |
| §5 性能基线：GPU 只忙 ~20% | 1.4 K | **条目 3** | 判断已被两轮优化承接 |
| §6 显存预检按起始手数与真实维度判 | 2.0 K | **条目 2** 的另一半 | 属同一「batch 与显存」族 |
| §7 并行与耗时（`check_all` 并行与 `--fast`） | 16.0 K | **拆出，不在本试点** | 主题不同（检查基础设施，非训练性能）；16 K 占全文 59%，单独成条 |

即 7 节 → 4 条（条目 1/2/3/4），§7 留给「检查基础设施」主题另立条目。
**归并后的字节**：条目 1–4 覆盖 §1+§2+§3+§4+§5+§6 = 11.0 K，加 §7 另立一条 16.0 K，合计仍 27.0 K——**总量不变，
变的是「一次 F3 只读一条」**。

## 五、代价与未解决

### 5.1 我核过的代价

| 项 | 实测 | 判断 |
|---|---|---|
| 新类型挂接点 | 8 个 writer 各 6–14 处常量 + `object-reference.js` 类型表 + `source-recall.js` 的 `DEFAULT_STATUSES_BY_TYPE` | 与现有类型同量级，非新增负担 |
| 一条日志的固定开销 | frontmatter 骨架 700–1200 B；ld-rl-poker 全库均 13.5 KB / 中位 3.9 KB | 相对 51 号的 157 KB，可接受 |
| 召回面 | `DEFAULT_STATUSES_BY_TYPE` 需加 `devlog: ["active"]`，否则默认只认 `active`（回退值，碰巧对） | 一处显式声明，不写会静默潜行 |
| `topic` 分组 | `list` 工具当前只支持 status/keyword/serves/limit | 需加 `topic` 参数，或用 `serves` 过滤后前端分组 |

### 5.2 未解决（据实登记）

1. **归并本身是语义判断，会错**。51 号 40 个 H2 归成 17 条是我的判断，不是机械结果。
   归错了要重做——这是本方案最大的不确定成本。
2. **`absorbed` 的触发时机没有机械判据**。「commit 合并后就可以压缩」不等于「结论已
   被完整承接」——代码可能半年后被人改回去。现有类型里 `ADR absorbed` 要求
   「决策内容已被某方向的 Norm 完整承接」，那是对象指对象、可机械核；这里是
   对象指 commit，只能人工判断。
3. **`dropped` 与 `absorbed` 容易混**。都省字节，但前者不可回溯、后者可。我倾向
   把 `dropped` 的门槛设成 Human 决定（与 `26` 的 `voided` 同规格），但这会让人
   不敢用，导致 `absorbed` 被滥用。这个平衡我没把握。
4. **主题间的关系没处理**。SG-5 与 SG-12 的日志会互相引用（训练性能 ↔ 暴击训练），
   本方案只有「条目指主题」，没有「主题指主题」。
