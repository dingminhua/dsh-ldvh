## 2. 当前阶段目标：八维真实行动展开

在建立 20–24 和 30–38 前，先验证八维如何在真实工作中组合。候选设计基线位于：

- `docs/eight-dimension-action-baseline.md`

该基线必须覆盖：

1. 每维输入、触发、输出和转交；
2. Stop Conditions 与 Human Gate 产生点；
3. 机械入口与不能单独证明；
4. 事实候选由反思产生、由沉淀准入、由写维落位的链路；
5. 规范修订、故障修复、架构决策、普通代码改动、跨会话恢复五个场景；
6. 八维不得被固化成顺序流程。

完成条件：独立审核通过、Human 确认该基线足以作为 20–24/30–38 起草输入，但它仍不取得规范效力。

## 3. 后续顺序

### 阶段 A：八维基线确认

1. 审核八维矩阵是否与 00/02 一致；
2. 反例攻击事实过度对象化、模板仪式化、Human/AI 职责错位；
3. 用五个场景核对转交和停止；
4. Human 确认。

### 阶段 B：20–24 事实类型规范

顺序：20 Spark → 21 WorkCase → 22 ADR → 23 Pitfall → 24 Study。

每份必须从八维场景回答：候选在哪一维产生、沉淀如何准入、写维如何落位、读维何时召回、复核如何验证、何时合并/替代/退出。不得为记录八维过程增加流水字段。

### 阶段 C：30–38 行动模板规范

具体模板须从真实场景提炼维度组合、触发/排除、停止/分流、验证、回写与交还；不得把八维固定为八个步骤，也不得让模板匹配产生授权。

### 阶段 D：DSH 能力核验

逐项核验当前 DSH 版本的：插件激活、工具注册、systemPrompt/pre-step、事件面、结构化问询、授权、user-data 根、文件观察、沙箱、Git Hook、Web 路由与 Output Envelope 宿主承载。结果区分已定义、已实现、已接入、当次可用、已验证、不可用/未知。

### 阶段 E：实现与验证

依据 05–09 实现单一职责入口；代码与测试由不同代理/模型分任。实现后建立“规范章节 → 唯一实现 → 测试 → 消费方 → 可证明范围”矩阵，再进行全链路反例攻击与发布候选验证。

## 4. 执行纪律

1. 规范、事实、Code、Web 不互相取得第二权威。
2. docs 仅记录计划和设计输入，不替代当前规则源。
3. 任何能力未实测前不得写成已实现或可用。
4. 事实候选未经过沉淀、准入、查重、受控写入和回读，不进入事实源。
5. 每次规范或受控提交须经独立审核、Human 确认、precheck 与 Git Gate；不得 `--no-verify`。
6. 不 push，除非 Human 单独授权。
7. **v4 吸收优先**：实现任何 Helper、读取、事实、Git Gate、管辖、插件或 Web 能力前，必须先定位 v4 对应规范、Code、tests、事实样例、已知问题和相关提交；不得未读 v4 对应实现就从零设计同类能力。
8. 实现选择优先级固定为：直接复用 → 提取并适配 → 保留算法、重写边界 → 明确废弃 → 最后才从零重写。从零重写必须说明 v4 位置、不能复用原因、与 v5 规范的冲突、净价值和保留的历史反例。
9. 不因吸收 v4 而恢复其当前规则源地位；不得复制已废弃流程、过度合规机制、向上遍历、旧字段/状态机/生命周期或重复实现。优先吸收已验证的解析、Git/Index 检查、Gate、指纹/CAS、UUID、原子写入、事实解析、关系校验、边界用例和错误处理经验。
10. 每项实现开始前形成最小吸收判断：v5 能力、v4 规范位置、v4 Code、v4 tests、已知问题、复用/适配/重写/废弃决定、理由和验证方式。该判断可放在实施计划或提交说明中，不建立新的审计账本或事实类型。
11. 迁移实现必须回跑有价值的 v4 测试和反例，并增加 v5 新边界测试；复用成功不证明 v5 语义成立，仍须对照当前规范和实际 DSH 能力验证。
