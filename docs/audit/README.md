# `docs/audit/` —— 审计与状态记录（无规范效力）

> **本目录不承载规范，不具备规范效力。**
> `01 §9.1` 的当前规则源候选路径仅为 `specs/` 与 `specs/attachments/`；本目录不在其中。任何读取、引用或消费规范时，均不得以本目录内容替代规范源。

---

## 一、本目录的定位（Human 决定 2026-09-12）

**规范正文只承载要求（「当 X 时应做 Y」），不承载状态与过程（「现状是 X」「本轮审了什么」）。**

据此，以下内容从 `specs/` 移入本目录：

| 移入内容 | 原因 |
|---|---|
| **审计过程记录**（审了什么、发现了什么、结论如何、是否撤回） | 读者照之无事可做；它是历史，不是要求 |
| **实现状态**（某机制是否已实现、校验是否已覆盖） | 同上；由状态派生的**要求**已改写为条件式保留在规范中 |
| **更正记录**（原文写错、何时更正） | 同上 |

**由状态派生的要求仍留在规范中**，例如「机械校验覆盖本表之前须人工核对，不得声称已通过机械校验」——这类条件式表述**是要求**，故保留。

## 二、为什么不建「审计事实对象」（Human 决定 2026-09-12）

**结论：不需要。审计是过程性、阶段性内容，放在本目录即可。**

理由：

1. **审计内容不具备事实对象的稳定性** —— 事实对象承载「跨行动或会话稳定定位」的项目信息；审计记录是**一次性的过程产物**，随审计结束即不再变化，且会被后续审计超越。
2. **审计约束的是 LDVH 机制，不是项目内容** —— 按 `01 §9.0` 的 D1 判据（约束对象为首要判据），对 LDVH 自身规范的审计属**元规范侧**，本就不宜以项目事实对象承载。
3. **净负担** —— 建类型需定义身份、载体、字段契约、状态生命周期、受控写入与召回（`03 §11` 十项共同结构），而其消费场景仅为「回看某次审计做了什么」，**成本高于收益**。
4. **现有载体已足够** —— 本目录 + git 历史已完整承载该信息。

**若未来出现「审计结论需要被机器消费、跨项目复用或参与关系网络」的真实需求**，应重新论证本决定，而非默认沿用。
