## 1. 两类文本

| | 运行时机制（`plugin-specs/`） | 开发规范（`specs/`） |
|---|---|---|
| 装什么 | 25 份 YAML ＋ 6 份附件，每份 ＝ 身份字段 ＋ 一串要求条目 | 31 份 Markdown，含**载体契约 `specs/11`** |
| 约束谁 | 运行期 AI 的行动 | 开发过程（人 ＋ 开发中的 AI） |
| 标识 | **只有 `spec_key`，没有编号**，不参与规范模型的编号登记 | 规范身份块（`spec_key`＋`spec_id`） |
| 写法由谁规定 | 载体契约（`specs/11`）＋ 代码校验器 | 自身的共同结构契约 |
| 能否引用对方 | **不能**（禁止项） | 能（开发规范可规定运行时机制怎么写） |

**运行时机制自足**：需要别处的东西时用自己的话写出要求本身（写「要一个可解析的子目标」，不写「见 21 §13」）。因此没有跨载体引用、没有悬空引用、没有章节号互引、不需要全局 node id 体系。

**载体契约**（`specs/11`）＝ 防止各份运行时机制各自乱写的那把锁：身份 6 项、条目 3 项、写法 9 条、禁止项（甲类 7 项可机械查 ＋ 乙类 6 项须语义审）、体量上限（30 条／600 码点／12 KB）、校验口径、变更流程。

## 2. 已定事项

1. 运行时机制自足，用自己的话写要求；
2. 条目 = `id`（文件内唯一）＋ `title` ＋ `text`；无章节号、无 node id 全局体系；
3. 身份字段 6 项必填：`spec_key`／`spec_kind`／`title`／`canonical_path`／`positioning`／`scope`；**不得出现 `spec_id`**；
4. 禁止项分甲类（可确定性检查 7 项）与乙类（须语义审核 6 项）；校验器未建立时按 `01 §13.1` 人工核对并披露"未经机械核对"；
5. 工具的公开操作声明归 **Code** 承载，运行时机制里不写声明表；
6. 每条要求在进入运行期前，须能在开发期材料里找到来源；来源对照表放在开发期材料里，不随包携带；
7. 格式规则由校验器执行，不以文本形式进入运行期。

## 3. 剩下的问题（四个，都与引用无关）

| # | 问题 | 早期信号 | 处置方向 |
|---|---|---|---|
| P1 | 运行时机制的**读取入口**另立后，与开发规范的读取如何分开 | 两类文本被同一入口读到 | 另立入口：按载体格式分派，不跨来源视图混读 |

| P3 | **打包静默跳过**：`files` 里不存在的目录 npm 不报错，`npm pack --dry-run` 不会红 | 包内无语料但发布全绿 | 独立机械检查（目录存在 ＋ 数量相等 ＋ 根载体可解析）＋ CI tar 断言 ＋ 冒烟 |
