# 读维认知小结（设计输入）

> 性质：八维讨论的读维收束小结，基于 `docs/eight-dimension-work-model-discussion.md` §6.1–6.15 的讨论记录整理而成。
> 用途：作为将来起草 `20–24` 事实类型规范、`30–38` 行动模板规范，以及 Helper 读取（`05`）能力实现的**设计输入**；非规范、非事实对象，不取得规范效力或行动授权。
> 收束日期：2026-09-15。凡未单独注明者，均为讨论达成的认知候选；与 `specs/00`–`specs/10` 冲突时以规范为准，差异须回讨论解决。

## 0. 第零道闸门：管辖判定（读任何内容之前先回答"该不该读"）

读的第零步不是「读什么」，而是「**该不该读**」——管辖判定在一切 L0–L4 / F0–F4 / Helper 读取之前发生。

### 0.1 必须区分的两个概念

| | **管辖项目判定** | **管辖范围（工作对象）** |
|---|---|---|
| 问的是 | 这个项目在不在登记列表里 | LDVH 在这个项目里管什么、管到哪 |
| 判定结果 | `governed` / `not_governed` / `unavailable`（`07 §5.3`） | Git 根 + `ldvh-base/`（事实源）+ `specs/`（规范源）（`07 §6`） |
| 类比 | 「这个人是会员吗」 | 「会员能享受什么服务」 |

模糊感来源：操作名 `resolve-governance-scope` 用 "scope"（范围）命名，但实际判定的是「项目是否在列表」（项目资格）。语义上应明确：**scope 判定 = 项目资格判定，范围定义 = 工作对象边界**；命名可考虑更清晰表述。

### 0.2 非管辖项目：LDVH 零干预（关键边界）

- **`not_governed`** → LDVH 对该项目**零读取、零动作、零痕迹**：不读规范源/事实源、不召回事实、不加载 Helper 受控操作、不套模板、不写事实对象、不做 Git Gate、不触发 Human Gate/Stop。
- **`unavailable`** → 前置条件不可得，**fail-closed 暂停**（不是「不管」，而是「无法判定所以停」）。
- 二者差别关键：`not_governed` 是正常退出，`unavailable` 是异常暂停；都不是「管」。

LDVH 不是常驻监视器，只在登记过的项目里活动；对非管辖项目完全透明——这是防止 LDVH 越界侵入普通项目、不打扰非 LDVH 工作流的关键设计。

## 1. 读维的作用域

- LDVH 的「读」只覆盖两类受控信息：**管辖项目的事实对象**与 **LDVH 自己的规范源**（规则源）。
- 不读全量对话历史、运行痕迹或非受控内容；「读」的范围不等于「信息都在哪」的范围。
- 读维解决的是「AI 要读对、读可信、读有边界」，而非「低成本想起一切」（后者是 Hindsight 类外部记忆的定位）。

## 2. 内容的二分与各自的读取路径

| | 确定性集中的内容 | 散落的闲聊内容 |
|---|---|---|
| 典型形态 | 规范源、事实对象（受控格式） | 聊天中的零散观点、想法、经验 |
| 信息属性 | 有权威、可回指、结构化 | 无归属、碎片化、不负责 |
| 定位 | 判断依据 | 可找回的历史记录（档案） |
| 读取/处理 | 确定性读取（L0–L4 / F0–F4 / Helper 回指） | 宿主会话轨迹 FTS5 检索 |
| 生命周期 | 受控落位、退出管理 | 随聊随存、原文留档 |

- 闲聊内容**不需要验证价值、不要求结构化、不进入事实源/沉淀判定**；其唯一意义是「及时找到过去聊过的内容」。
- 「**找到**」≠「**作为依据**」：检索到过去闲聊只说明「当时说过」，要作判断依据必须再经受控转化。
- 有价值闲聊的受控承接位是 **Spark（20）**：Human 判定价值并安排 AI 记录；AI 在对话中已有完整上下文，整理成本趋近于零。判定权在 Human，整理由 AI 做且已做过。

## 3. 双通道读取骨架

| 通道 | 项目机制 | 读的是什么 | 主要服务维度 |
|---|---|---|---|
| 规则源（规范源） | L0–L4 规范读取层级（`01 §10` / `01.Att.03 §4`） | 「应该怎么做」——边界、义务、流程 | 遵守维 |
| 事实源 | F0–F4 事实召回分层（`03 §8`） | 「现在是什么、过去决定/踩过什么」——依据、状态、经验 | 判断/复核维 |
| （第三类）行动模板 | `template_key` / `definition_ref`（`04`） | 「该场景怎么做」的可复用方法 | 执行维（可归入规则性一侧，亦可单列，由 Human 定） |

- `01 §10` 明确：**L0–L4 与 F0–F4 不混用**——读规则读义务边界，读事实读判断依据，不可拿错证据。
- 广义「读」还有宿主能力/运行状态（08，能力发现），不属于 LDVH 管辖内容读取，不在内容分类内。

## 4. 「如何读」的核心机制（四要素）

1. **分层渐进**：不一次读全量；L0–L4 / F0–F4 按需展开，控制上下文负担。
2. **可回指**：每段信息可回指来源、行号、指纹；区分 `completed / not_completed / gaps`。
3. **机械确定性入口**：Helper 读取操作（`read-specification-candidates` / `read-specification-content` 与事实读取），AI 不靠猜路径。
4. **AI 语义判断收尾**：机械命中不自动裁决；相关/适用/授权/完成由主控判断。

## 5. 必须读 vs 选择性读

### 5.1 必须读（最小集合，防 AI 裸奔）

1. **00 根锚点（最小引导）**：身份块、§2 根方案、§3.1 八维、§4 Human 决定权、§5 AI 责任、§6 双轨价值、§7 防自欺/Stop/交还——会话/行动启动即注入；
2. **管辖判定**：`resolve-governance-scope`，进入受控执行前；
3. **适用行动模板**：候选 → 内容，动手前（受控执行单元）；
4. **条件性必须读**：召回时机成立时，全部 active ADR F1（长期决策/架构）、全部 active Pitfall F2（已知失败症状）——会话级预检。

必须读 ≠ 全文，而是「最小引导 + 条件触发」；普通聊天、纯查询不触发事实召回，只取得规则引导。

### 5.2 AI 选择性读（按目标/风险的最小充分展开，防上下文爆炸）

- 规范 L3/L4（规则切片/全文）：局部判断需要精确规则时按需展开；
- 事实 F1–F4（卡片/候选/全文/来源展开）：项目事实对当次判断必要、或精确引用稳定事实时；
- 行动模板全文/细节、更深来源证据。

选择依据：目标与风险实际需要哪一层；不需要就不展开。八维是职责不是流程，读也不被固化为固定步骤。

## 6. Helper 在读取中的角色

- Helper 是**确定性读取服务**，不是「确定性搜索器」：它不帮你「找」（该读哪段是 AI 的语义判断），而是「按精确坐标取到权威载体的当前内容，并保证取到的是权威内容」。
  - `read-specification-candidates`：按 `spec_key`/`attachment_key` 列候选（L0–L2），只产生待解析候选，不产生规则资格；
  - `read-specification-content`：按精确 `responsibility_key` + `heading_path` 返回规则原文（L3 切片/L4 全文），重复/歧义标题拒绝，带 1-based 行号。
- **确定性与阻碍**：`05 §13` 与 `05 §4.3` 明确不要求普通求解/读文件/编辑先过 Helper；只有读受控内容（规范/事实/模板）且要以其为判断依据时才走 Helper。因此 Helper 不制造阻碍。
- **比 AI 自查询更好**：读受控内容当依据时，Helper 更好（防猜路径、防拿错载体、防「以为查到了」、披露 gaps）；读普通文件时 AI 直接用宿主工具更好；「该读哪个、读了有没有用」必须 AI 判断。
- 核心区分（防自欺）：**AI 自己查询 → 可能「以为查到了」；Helper → 「确定取到了，且告诉没取到什么」。**

### 6.1 示例：做某件事要遵守什么规范

1. 规则引导（00 根锚点已注入，确定受管动作）；
2. 管辖判定 `resolve-governance-scope` 确认受辖；
3. `read-specification-candidates` 列出相关 `spec_key` 的 L0–L2（身份/定位/范围/关系）——只答「有哪些可能相关」；
4. **AI 判断适用性**（Helper 不替做）；
5. 对命中规范 `read-specification-content` 取 L3 切片 + 行号，需要时取 L4 全文；
6. 若为受控执行单元，再取行动模板（`read-action-template-candidates` → `read-action-template-content`）；
7. 遵守维把规则落成预检落实记录，使约束实际改变行动。

## 7. 与外部记忆服务（Hindsight 类）的关系

- Hindsight 解决「AI 会忘」（低成本想起、自动摄取、概率召回）；LDVH 读维解决「AI 要读对、读可信、读有边界」（受控、可回指、有权威）。**两者解决的问题不同，可互补但不等价。**
- 若并行，须「分层定位」：Hindsight 在候选/线索层，LDVH 事实源在权威/依据层，并守住三条红线：
  1. 候选不自动进入判断结论（影响判断的信息须回 LDVH 事实源做 F3/F4 精确读取）；
  2. 外部记忆不得反向写入事实源（事实只经受控入口落位）；
  3. 冲突时以事实源为准，记忆只提示「去核对事实源」。
- 当前阶段**不引入**：事实源规模尚小，读文件 + 分层 + 回指成本足够低；并行会引入双源漂移、上下文预算与第二权威投影风险。

## 8. 成本认知（无限 AI 前提下的读维）

- 无限 AI 只免掉「生成/提炼」成本，免不掉「保证正确、保持可信」的成本；成本从生产端推向筛选与验证端。
- 读维相关的真正成本：筛选（哪些值得沉淀、进哪里）、防自欺（提炼结果可能「很有条理但偏离原意」，必须可回指原文并经复核）、确认（每个候选须确认确实成立）、沉淀位置判断（进规范/事实对象/普通文档还是不留）。
- 原则：AI 提炼输出永远是「候选 + 原文回指」，绝不直接当事实/决定用。

## 9. 对后续规范与实现的设计输入

### 9.1 对 `20–24` 事实类型规范

- 每类事实须说明：候选在哪一维产生、沉淀如何准入、写维如何落位、**读维何时召回（F0–F4 哪个层级、什么时机）**、复核如何验证、何时合并/替代/退出。
- **20 Spark** 承接「有价值闲聊」：必须低摩擦/快通道（v4 教训：创建穿越 7 份规范、23 条 Stop），并在开 Spark 前查重（v4 教训：同一问题多次开 Spark）。
- 召回时机、默认候选状态、关系闭包由类型来源定义（`03 §8.2`），不得全类型共用触发词或无条件全量注入。

### 9.2 对 `30–38` 行动模板规范

- 模板须说明场景需要哪些维度组合、哪些维可最小化、转交对象、停止条件、Human Gate、验证与交还。
- 模板读取（`template_key` / `definition_ref`）与规范 L0–L4 不混用；模板不得把八维固化为顺序步骤，也不得以模板匹配产生行动授权。

### 9.3 对 Helper 读取能力（`05`/`09`）实现

- 读取操作须保留：分层（L0–L2/L3/L4、F0–F4）、来源视图、内容指纹、行号、`completed/not_completed/gaps`、分页/coverage/cursor；禁止静默截断后声称完整。
- 只读响应须如实交还 partial/unavailable；机械有效不证明语义相关、适用或全文已读。
- 读取入口不产生行动授权；概率候选、预热卡不得被写成 F3/F4 已读或事实声明。

## 10. 未验证范围与待定项

1. 事实源规模增长后，F0–F2 定位与索引（分页/coverage/cursor）的机械实现仍待实测。
2. 本地全文/语义检索作为 F2 候选辅助是否引入，如何与 `03 §8`「Code 不得用相似度/embedding 自动裁决」协调。
3. 行动模板归入「规则性一侧」还是单列为第三读取通道，由 Human 定。
4. 闲聊检索的宿主承载细节（DSH 轨迹 FTS5 的接入与权限）属 08 核验范围。
5. 读维的完整输入/触发/输出/转交，建议在起草 20–24/30–38 前用一个真实行动场景做一次端到端走查。

## 11. 一句话认知

**LDVH 的读 = 双通道（规则源 L0–L4 + 事实源 F0–F4）× 四要素（分层渐进、可回指、Helper 确定性入口、AI 语义判断）× 三种定位（必须读给底线、选择性读给效率、Helper 给确定性）；闲聊是可检索不负责的档案，有价值部分由 Human 判定经 Spark 承接；读的最终目标是让 AI 读对、读可信、读有边界，而不是记得多。**
