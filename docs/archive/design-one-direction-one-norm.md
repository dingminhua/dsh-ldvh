# 「一个方向只能一个规范」机械落地机制设计

## 0. 背景与已裁定事项

Human 为「事实规范」给出权威定义：
> 「事实规范我的定义就是**成体系的规范**」  
> 「**成体系就是一个方向只能一个规范**」

### 已裁定事实（Human 裁定，本设计直接继承，不再重新论证）：
1. **存放位置**：管辖项目事实源根目录下的规范子目录，即 `ldvh-base/norms/`（`specs/00:132`，`docs/design-fact-norm-in-fact-source.md:5-9`）。
2. **状态机闭集**：`active` / `retired`，无第三态（对齐 `specs/22-ADR-决策.md:121`）。
3. **核心判据**：**一个方向 = 一份规范**，同一方向在同一时点不得有第二份处于生效状态的规范。
4. **参照基准**：元规范（`specs/`）已按此结构组织（如 `09` 独占 Code 方向、`10` 独占 Web 方向）。

## 2. 六问逐条深入设计

### 问题 1：「方向」如何标识与定义取值域

#### 1.1 字段方案比选

为了在机器层面识别一个事实规范属于哪个「方向」，需要一个明确的元数据标识。存在以下四个候选方案：

| 方案 | 机制说明 | 优缺点分析 | 合规性判定（03/01） | 结论 |
|:---|:---|:---|:---|:---|
| **方案 A：复用 `fact_type_key`** | 令每个方向为一个独立的事实类型（如 `fact_type_key: "code-spec"`） | ❌ 破坏类型抽象：每增一个业务方向就要改 03、扩充 Web `FACT_TYPES`、增加 Schema，产生巨大侵入 | 违反 03 §5.2 准入原则（方向不是类型）；违背 03 §6.1 闭集定义 | **坚决否决** |
| **方案 B：用 `title` 识别方向** | 通过文本标题解析方向（如从 `# Web 规范` 提取） | ❌ 自然语言标题具有表述随意性、多词、易微调；标点或空格变化会导致机器无法精准判重 | 违反 03 §6.1（`title` 不承载状态结论、定位或机器键） | **坚决否决** |
| **方案 C：用文件名/路径即身份** | 文件名固定为 `<direction_key>.md`（如 `ldvh-base/norms/web.md`） | ⚠️ 路径天然互斥，但与状态机 `active/retired` 冲突：规范退役保留历史时，若同名文件存在则新规范无法落盘 | 虽有 25 号先例，但 25 是绝对单例；规范存在历史演进与退役档案 | **不作为唯一标识**，可作为辅助规则 |
| **方案 D：新增专属字段 `direction_key`**（推荐） | 事实规范作为一种事实类型（如 `factnorm`），在 frontmatter 中声明类型专属字段 `direction_key` | ✅ 语义精准，小写 kebab-case，专门承载方向机器键；与对象 UID、生命周期完全解耦 | **完全合规**：遵循 03 §6.1「20–24 分别登记专属字段增量」的既有规则，**无需修改 03 公共字段表** | **采纳为标准方案** |

#### 1.2 对照现有规范字段惯例与合规性论证
- **是否需要修改 `specs/03` 正文？**  
  **不需要**。`specs/03` §6.1 定义的是**跨所有事实类型共享的公共身份字段**（`object_uid`, `fact_type_key`, `title`, `created_at`, `status`, `urls`, `relations`, `change_log`）。03 §6.1 明文规定：“20–24 分别登记本类型实际采用的公共字段和专属字段……20–24 只声明采用范围与类型专属增量，不替代本文的公共语义。”例如：
  - 22 ADR 的 `decision`, `scope`, `trigger_signal`（`specs/22:117-131`）；
  - 24 Research 的 `research_question`, `research_purpose`（`specs/24:170`）；
  - 20 Spark 的 `question`, `scope_boundary`, `intent`（`specs/20:83`）。  
  因此，事实规范类型规范（候选编号 27）在自身契约中定义 `direction_key` 属于标准且合法的「类型专属字段」，**无需对 `specs/03` 作实质修改**。
- **与 `specs/attachments/01.Att.02` 的关系**：  
  `01.Att.02` 仅管辖元规范（`specs/` 及 `specs/attachments/`）的代码块身份契约，未知字段会被严格拦截（E5）。事实规范存放于 `ldvh-base/norms/`，是事实源中的事实对象，其解析遵循事实对象的 frontmatter 契约，不走 `01.Att.02`，因此不会破坏元规范身份闭集。

#### 1.3 方向的取值域：开放 vs 封闭？如何防止「同义异名」？

- **取值域定案：语法受限的「项目级开放集合」**。
  - **为什么不能封闭？** LDVH 元规范无法预测所有被管辖项目的具体业务与技术边界。电商项目需要 `order-fulfillment` 方向，系统项目需要 `memory-safety` 方向，编译器项目需要 `ir-lowering` 方向。如果设为封闭列表，项目每次增加领域规范都必须修改 LDVH 核心元规范，违背 `specs/00:136`（“元规范不替项目定规则，事实规范不替 LDVH 定机制”）。
  - **语法格式约束（机械可验）**：必须符合标识符闭集正则：`^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`（小写 kebab-case，与 01.Att.02 §2 职责标识符格式完全一致）。
- **核心风险：同义异名（Synonymy Problem）**  
  开放取值必然带来风险：同一个方向被不同人员/会话命名为不同的 key（例如一人建了 `web`，另一人建了 `frontend` 或 `client-ui`；或者 `api-spec` 与 `backend-api`）。
- **防范机制（机器 + 制度双轨）**：
  1. **机械层（精确排他）**：严格保证同一 `direction_key` 在 `active` 集合中全局唯一（100% 机械兜底）。
  2. **项目级登记簿（词表收敛）**：在 `ldvh-base/norms/` 设立项目级规范登记清单（或自包含在项目蓝图中），声明已确立的方向 key 清单与职责定义。
  3. **AI 创建前强制查重**：在提请创建事实规范时，AI 必须检索已有 active 规范的 `direction_key`、`title` 及正文 `定位与适用范围`，做语义相似性比对；若发现与既有方向高度重叠，禁止自动生成新 key。
  4. **Human Gate 最终裁定**：新增一个 `direction_key` 属于定义项目级规则领域，必须经 Human 确认（见 00 §4.2）。

### 问题 2：唯一性如何强制（机械检查点与冲突策略）

「同方向只能一份」属于**跨对象（跨文件）全局一致性约束**。

#### 2.1 现有跨对象唯一性先例比对

LDVH 现有代码与规范中已有三类跨对象唯一性检查实现：

| 先例来源 | 检查对象 | 检查机制与位置 | 机制启示 |
|:---|:---|:---|:---|
| **先例 1：`specs/25-Goal`** | 项目级目标单例 | 物理固定路径 `ldvh-base/goal.md`。文件系统层面天然互斥（`specs/25:80`） | 适用于全项目仅此一份的对象；不适合存在多方向的事实规范 |
| **先例 2：`spec-registry.js`** | 元规范 `canonical_path`、`spec_key` 全局唯一 | `plugin/lib/ldvh-tools.js:100-114` 在扫描时构建集合全量核对，发现重复抛出 gap/冲突 | 规范扫描器的全量汇总核验是标准做法 |
| **先例 3：`governed-projects.js`** | 项目登记 `id` 与 `path` 唯一 | `plugin/lib/governed-projects.js:48-57` 遍历验证，Set 查重：`if (ids.has(entry.id)) throw ...` | 内存中 Set 收集判重，违规立即中断并拒绝执行 |
| **先例 4：`adr-writer.js`** | ADR 状态转移与 CAS | `plugin/lib/adr-writer.js:16` 基于当前指纹与单文件内容做状态校验与排他更新 | 受控写入入口（Writer）是写前校验的最佳宿主 |

#### 2.2 三道机械检查点设计

为了保证「同方向只能一份 active」在任何路径下都不被突破，设立**三层机械防御网**：

```
[行动发起/更新提请]
       │
       ▼
【第 1 道：写入前受控防线】──> factnorm-writer (create/update)
       │                        └─ 扫描 ldvh-base/norms/，查验 active direction_key 是否冲突
       │                           (冲突则直接拦截拒绝写入，返回 DIRECTION_COLLISION)
       ▼
【第 2 道：提交前终闸防线】──> Git Gate (commit-msg & pre-commit hook)
       │                        └─ 离线无状态扫描 working tree 中全部 ldvh-base/norms/*.md
       │                           (发现重名 active direction_key 则 exit 1 终止提交)
       ▼
【第 3 道：消费/读取诊断防线】─> Helper (read-fact-norms) & Web (localFactReader)
                                └─ 运行时如检测到重复，触发 fail-closed，全部涉事文件降级为
                                   unusable_collision_gap，拒绝作为当前有效规则输出
```

1. **第一道防线：受控写入前（`plugin/lib/factnorm-writer.js`）**
   - 任何事实规范的创建必须经由受控写入入口。
   - `createFactNorm(worktree, input)` 执行时，首先枚举 `ldvh-base/norms/` 下所有现存 `.md` 载体，解析 frontmatter。
   - 若发现已存在 `status === "active"` 且 `direction_key === input.direction_key` 的对象：
     - **直接拒绝写入**，返回错误码 `ERR_DIRECTION_ALREADY_EXISTS`。
     - 提示必须走「替代/修订既有规范」路径，或由 Human 批准方向拆分。
2. **第二道防线：提交前 Git 终闸（Git Gate / `hook-manager.js`）**
   - 即使绕过了受控写入工具（如手工编辑或 shell 写入），在提交时必经 Git Gate 校验。
   - Git Gate 遍历暂存区与工作树的 `ldvh-base/norms/*.md`，执行两项断言：
     1. 每个文件必须具备合法的 `direction_key`。
     2. 提取所有 `status === "active"` 规范的 `direction_key`，构建频次 Map。若有任何 key 出现次数 > 1，**立即拒绝提交，打印冲突文件列表**。
3. **第三道防线：读取与运行时诊断（`ldvh-tools.js` / `localFactReader.ts`）**
   - 在主控通过 Helper 读取规范、或 Web 端投影事实规范时，若发现目录中存在 active 方向冲突：
     - **Fail-closed 隔离原则**：两份冲突规范**均不得作为当前生效规则返回**（对齐 `specs/01:216`：“同一编号、职责标识符……映射到多个候选时，全部受影响候选均不得进入成员读取，直到冲突解除”）。
     - 将冲突事实报告为 `gaps: [{ reason: "direction_collision", direction_key: "web", carriers: [...] }]`。

#### 2.3 冲突处置策略
- 唯一合法策略：**Fail-Closed（默认拒绝）**。
- 不得猜测哪一份更新；不得静默按更新时间（mtime）选择最新的一份；不得降级忽略。必须通过报错停止受影响行动，要求主控或 Human 处理冲突。

### 问题 3：与「成体系」判据的关系及与 ADR 的边界

#### 3.1 「成体系」是否需要独立判据？能否机械判定？
- **现实矛盾**：「一个方向一份规范」只解决了**非重复性（排他性）**，并不能从逻辑上推导出**成体系性**。一个开发者可以在 `ldvh-base/norms/web.md` 里面只写一句话：“所有按钮必须是蓝色的”，它满足方向唯一，但绝不是“成体系”。
- **能否机械判定？诚实结论：只能进行「弱结构机械判定」，无法进行「语义完备性机械判定」**。
  - **能做到的弱机械判定（结构骨架强制）**：  
    借鉴元规范（01 §7）与 ADR（22 §8）的做法，在事实规范类型中定义**必填 H2 共同章节结构**（缺失即拒绝写入）：
    ```markdown
    # <title>
    ## 1. 方向定位与适用范围   (明确本规范管什么、不管什么)
    ## 2. 核心架构与模式       (定义该方向的核心规则体系)
    ## 3. 约束与反模式         (明确禁止项与违规代价)
    ## 4. 验证与遵从性检查     (定义如何检查是否合规)
    ```
    同时可施加简单的结构指标（如：核心规则段至少包含可量化的条款条目）。
  - **机械无法判定的部分（语义与质量边界）**：  
    规范是否覆盖了该方向的主干脉络？规则之间是否存在矛盾？深度是否足够指导长程开发？这些**没有任何确定性代码可以机械证明**。
  - **建议处理方案**：
    - 弱机械负责「验形」：不符合 4 大固定章节骨架者，直接打回；
    - AI 对抗审核与 Human Gate 负责「验质」：事实规范的初次建立和重大重构，必须通过独立对抗审核与 Human 审查（对齐 00 §4.2），由 Human 判断其是否真正“成体系”。

#### 3.2 ADR（单条决定）与事实规范（成体系）的边界判据

根据 `specs/22-ADR-决策.md` 与调研文档 `docs/research-adr-to-norm-boundary.md`，两者的本质分工与边界如下：

| 维度 | ADR（决策事实，22 号） | 事实规范（成体系规范，27 候选） |
|:---|:---|:---|
| **本质定位** | **点状**决策历史快照与约束 | **面状**系统化工程规程与规则集合 |
| **颗粒度判据** | **单条可独立贯彻的法定效力决定**（22 §6.1）：“一条决定 + 理由 + 备选 + 接受的后果” | **一个完整专业方向的规则全集**：“定位 + 模式 + 约束 + 验证” |
| **生命周期特征** | 一经批准，不可修改其决策语义（仅勘误）；变更必须新立并 `retired` 旧条目 | 作为方向的长效主干，支持在 `active` 状态下受控追加与修订（带 `change_log`） |
| **典型示例** | “前端状态管理选型采用 Zustand 放弃 Redux” | “Web 前端工程与状态管理规范”（内含状态管理、路由、组件分层、CSS 等全套体系） |

#### 3.3 承接与转向机制（ADR → 事实规范）
背景：`specs/22:99` 规定「已被完整承接进规范源的可强制执行规则的决策，ADR 不再承担约束」。
- **当前机制缺口**：`specs/22:127` 的 `retirement_reason` 闭集仅有 `superseded` / `outdated` / `out-of-scope`，且 `superseded-by` 强约束只能指向另一个 ADR（`docs/research-adr-to-norm-boundary.md:41-50`）。
- **打通方案（需在后续 22 号修订或 27 号配套中明确）**：
  1. 当零散 ADR 沉淀为成体系的事实规范后，既有 ADR 应当流转为 `status: "retired"`。
  2. 理由声明为 `retirement_reason: "superseded"`。
  3. 在 ADR 的 `change_log` 中注明：“规则已完整并入事实规范 `ldvh-base/norms/<norm>.md`（方向：`<direction_key>`），ADR 退出约束，转为历史依据。”
  4. 约束责任平滑移交给事实规范，消灭“ADR 与规范双重权威”。

### 问题 4：方向的演进动力学（拆分、退役与改名）

#### 4.1 内容膨胀后的「方向拆分」怎么办？
- **问题**：一个方向规范（如 `backend`）膨胀到极大，需要拆分为 `backend-api` 与 `backend-db`，这是否违反“一个方向只能一个规范”？
- **判据**：**不违反，因为方向的粒度发生了裂变（Refinement）**。
- **拆分规则与程序**：
  1. **禁止重叠存活**：严禁出现宽方向 `backend` 仍然 active，同时并存窄方向 `backend-api` active 且两者都管 API。
  2. **拆分路径（二选一）**：
     - *路径 A（彻底继承）*：旧规范 `backend` 标记为 `retired`；新设立两个独立规范 `backend-api` 与 `backend-db`，各持独立 `direction_key`。
     - *路径 B（剥离分支）*：旧规范保留 `backend` 键，但在正文与 scope 中明确将数据库职责剥离，新建立 `backend-db`。
  3. **Human Gate**：方向的裂变属于调整项目规则架构，必须由 Human 批准。

#### 4.2 方向退役（retired）后，该方向能否被新规范复用？
- **判据**：**允许新规范复用该 `direction_key`，但 `object_uid` 必须重新生成**。
- **状态空间不变量**：
  $$\forall d \in \text{DirectionKeys}, \quad \text{Count}(\text{Norms}(direction\_key = d \land status = \text{"active"})) \le 1$$
- **逻辑释义**：
  - 同一 `direction_key` 在历史全集中可以有多份（1 份 `active` + N 份 `retired`）。
  - 退役的规范保留在 `ldvh-base/norms/` 中作为只读历史审计档案（`status: "retired"`, `retired_at: "..."`）。
  - 若未来重启该方向，新规范分配新的 `object_uid`，状态为 `active`。机械校验器在检查唯一性时，**过滤条件是 `status === "active"`**。

#### 4.3 方向的改名与原 Key 保留
- **对照元规范原则（`specs/01:301`）**：
  > “同一职责改名、改号或移动时保留原 key，不使用 supersedes。实质新职责替代旧职责时使用新 key……”
- **事实规范侧落地规则**：
  1. **纯标题/措辞修改**：若仅是规范标题更新（例如从《网页开发规范》改为《Web 前端开发规范》），管辖方向不变：**严禁更改 `direction_key`**（依然为 `web`）。只更新 `title`并在 `change_log` 中记录改名理由。
  2. **管辖范畴实质漂移**：若管辖范畴从单纯的 `frontend-web` 扩大为 `client-crossplatform`：这属于实质新方向，必须启用新键 `client-crossplatform`，并将原 `frontend-web` 规范退役，建立演进回溯说明。

### 问题 5：与元规范的对称性核查与分析

#### 5.1 元规范 01–12 实际执行情况的机械核查

逐条核对元规范登记表（`specs/01:170-182`）与实际文件：

```
specs/01-规范模型基础规范.md  ── 身份、结构、读取、登记与审核 [独占规范模型]
specs/02-工作模型基础规范.md  ── 能力承载、业务系统、制度职责 [独占工作模型]
specs/03-事实模型基础规范.md  ── 事实公共模型、受控读写与关系 [独占事实公共模型]
specs/04-业务系统基础规范.md  ── 业务系统规范共同结构与扩展 [独占业务系统基础]
specs/05-LDVH CLI规范.md      ── CLI 确定性服务共同契约     [独占 CLI 契约]
specs/06-事实源与信息溯源规范.md ── 事实载体、溯源、提交与 Git Gate [独占提交与溯源]
specs/07-工作对象与管辖范围规范.md ── 工作对象与受辖判定    [独占管辖范围]
specs/08-DSH环境接入与插件发布规范.md ── 插件接入、引导、发布 [独占宿主与发布]
specs/09-Code实践与测试规范.md ── Code 实现与测试           [独占 Code 方向]
specs/10-Web呈现与交互规范.md ── Web 信息呈现与交互        [独占 Web 方向]
specs/11-调研系统规范.md      ── 调研入口、三层收敛与三态   [独占调研业务系统]
specs/12-讨论系统规范.md      ── 方案扩散、收敛与四路分流   [独占讨论业务系统]
```

**核查结论**：
1. **完全无重叠**：01–12 之间没有任何两个规范承担同一方向职责。例如 Code 只有 09，Web 只有 10，不存在第二个 Code 规范。
2. **20–26 事实类型段亦无重叠**：每个事实类型仅有一份专属定义规范（20 Spark, 21 WorkCase, 22 ADR, 23 Pitfall, 24 Research, 25 Goal, 26 Friction）。

#### 5.2 元规范侧是「惯例」还是「机械强制」？两者差异何在？
- **机械核查事实**：
  - `plugin/lib/spec-registry.js` 中存在的是对 `spec_id` 格式、`spec_key` 格式与 `canonical_path` 路径格式的校验；
  - `specs/01:230`（成立条件第 7 项）虽然写着“没有另一份当前规范重复承担同一职责”，但在验证表（`specs/01:347`）中明文规定：**职责唯一性是通过全量扫描 + AI 语义审核 + 编号表登记（Human 根决定）来保障的**。
  - 代码中**并不存在**自动分析规范正文来判定“两份规范是否方向重复”的机械断言。
- **差异剖析**：
  - 元规范侧实质是**「编号登记簿 + Human Gate 强控制」**。因为元规范常驻仓库、数量极少（十余个）、每次改动都是 00 §4.2 的重大事件，依靠 Human 的全局视野和登记表（01 §8.1）即可做到绝对不重复。

#### 5.3 事实规范侧应采用哪种？
- **结论：事实规范侧必须采用「强机械排他 + Human Gate 审核」双轨制，不能照搬元规范的纯登记惯例**。
- **理由**：
  1. **执行主体不同**：元规范由架构师级别的 Human 深度把关维护；事实规范在日常长程开发中，由不同会话的主控 AI 高频读取、提议、修改甚至自动化处置。
  2. **漂移概率不同**：AI 执行者极易在不知情或记忆丢失时，为某个具体任务顺手新建一份局部规则文件（例如写了 `database-rules.md`，过几天又写了 `sql-guidelines.md`）。
  3. **必须依赖机械锁死**：必须在 `factnorm-writer` 和 Git Gate 中把 `direction_key` 冲突作为物理硬错误拦截，逼迫 AI 在试图新建时被机械驳回，转而去维护或替代既有规范。

                                     │
