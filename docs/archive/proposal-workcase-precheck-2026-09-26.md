## 2. 触发依据

### 2.1 缺陷：提请与机械校验的次序在原文中未定，实现按「先提请、后校验」执行

**规范侧现状**（`21 §14` 创建条原文）：

> **创建（draft）**：C1 提案对象模式（AI 只产出提案对象，含查重结果；Human 确认后经受控创建入口落盘）。创建前必须查重。机械校验：字段闭集合法、`gist` 非空且 ≤ 200 字符、……

原文规定了两件事：**创建前必须查重**，以及**受控创建入口执行哪些机械校验**。它**没有规定**机械校验相对于「向 Human 提请」的**位置**——「Human 确认后经受控创建入口落盘」只约束确认与落盘的前后，不约束校验与确认的前后。

**实现侧现状**（实测）：受控创建入口先取 Human 的路由答复，之后才执行机械校验与落盘。故一个机械上站不住的候选同样会被呈到 Human 面前，Human 的答复可能落在一个从未成立的提案上。

**为什么这不是「多一层礼貌」**：提请与其审查针对的是**那份**候选内容。候选在机械上不成立时，提问者与答问者围绕的不是同一件事——Human 被要求对一份不可能被接受的内容作出判断，其答复既不能成立，也无法据以实现。这与 `00 §4.4`（提请须让 Human 形成范围清楚的决定）正面相关。

**同类先例（本仓已有）**：`06 §6.2` 的 `precheck-git-commit` 与 `06 §6.5` 的 Git Gate 是**同一 validator 的两个入口**——预检返回结构化结果供 AI 消费，Git Gate 在真实提交时再执行一次，并通过 `snapshot_identity` 核对两入口作用于同一候选。本提案把同一形状用于 WorkCase 的创建。

### 2.2 为什么必须要求「两处同一组校验」而不是只写「先检查」

若只要求「提请前检查」而不要求两处同组，则存在两套规则各自演化的通路：预检说可以、写入说不行（或反之），而两边都自称合规。此时「先检查」不但没有保护，反而把**分歧**伪装成**通过**——Human 看到的是「已预检」，落盘时遇到的却是另一套判据。

同理，只写「先检查」而不写内容一致性，则预检的结论可以被**沿用到另一份内容**上：Human 审查的是候选甲，落盘的是候选乙，二者都「过了预检」。

## 3. 候选文本（逐字）

### 3.1 A —— `§14` 创建条（在「创建前必须查重。」之后插入）

> **提请前机械预检**：把候选提请 Human 作出创建决定之前，须先对该候选执行本节所列机械校验；未通过者不得提请，须先修复或如实报告缺口。该预检**只读**（不落盘、不生成对象标识、不写 `change_log`），且**与受控创建执行同一组机械校验**——两处各设一套规则时，同一候选可得两种结论，而两侧都自称合规（双入口一致性，同 `06 §6.5` 对预检与 Git Gate 的要求形态）。**提请与写入之间候选内容发生变化时，写入一律拒绝**：提请与其审查针对的是**那份**内容，不得把针对另一份内容的结论沿用于本次写入。**候选内容的范围由「是否由调用方提供且会进入对象」界定，不由字段是否为类型字段界定**——由调用方提供、且会写入对象的每一项（含流入变更记录的摘要）都在其内。该预检**不构成授权**，也不替代 Human 的创建决定（§17）。

### 3.2 B —— `§15.1` 类型特有验证（新增一条）

> - 提请前机械预检（§14 创建条）：把候选提请 Human 决策前，对候选执行与受控创建**同一组**机械校验，交还机械结论与候选内容指纹。**该预检只读**：不落盘、不生成对象标识（`object_uid`）、不写 `change_log`；为完成校验所必需的中性字段赋值（如时间戳与类型键）不落盘、不返回，不构成「生成标识」。**双入口一致性**：预检与受控创建须由**同一组校验函数**给出结论，不得为两处各设规则；两侧结论不一致即属实现缺陷，须修复而非择一采信。**候选指纹的覆盖范围**：覆盖调用方提供的候选内容——凡由调用方提供、且会写入对象的项（含流入 `change_log` 的变更摘要）均在其内；不覆盖由 Code 独有生成的 `object_uid` 与署名等项。故指纹比对证明的是「两次调用提交的是同一份候选内容」，**不证明**对象其后未被改动，也不证明内容恰当、范围合适或 Human 会同意——内容是否可决属 `§10.1` Gate 1 与 Human 判断；本项不构成授权凭据。**该一致性比对由受控创建入口承载**：越过受控入口直调写入实现（不提供预检结论者）不在本条的机械保证范围内——同 `§14` 复核独立性条对机械保证范围的声明形态（越界行为的防护归 09 代码评审与 06 受控提交）。**边界**：候选内容尾部空白差异可能产生「指纹不同而落盘相同」的误拒；该方向为 fail-closed（多拒不放过），处置是重新预检，不影响写入正确性。

### 3.3 C —— `§16` 验证与证据边界（新增一行，七列）

> | 提请前机械预检 | 把候选提请 Human 决策前 | 候选通过 §14 创建条所列全部机械校验；预检与受控创建由同一组校验函数同判；提请与写入之间候选内容（含流入变更记录的摘要）一致 | 预检结论与候选内容指纹 | 机械（预检与写入同判 + 内容指纹比对） | 当次候选的机械可写入性；**不证明**内容恰当、范围合适或 Human 会同意 | 未通过不得提请；修复或如实报告缺口后重走 |

### 3.4 不修改项（明确排除）

- 不改 `§14` 其余六项受控操作（Gate 1/执行期/关闭/重批/取消/复核记录）；
- 不改 `§10.1` Gate 1 的提请必含项与 `§10.2` Gate 2 的提请必含项；
- 不改 `§9` 状态机与四值 `outcome`；
- 不改 `§6.3` 的对象边界与路由判定；
- 不新增对象字段（候选指纹**不入对象**，只在本次调用内比对）。

### 3.5 公开操作声明的登记去向（如实说明，本候选不处理）

`05 §6.1` 要求承担领域操作语义的来源按声明形状登记其公开操作，能力发现据以定位契约。经核查：**事实类型规范（20–27）现均无操作声明表**，即 `workcase-read-object`/`workcase-list-objects`/`workcase-write-object` 三个既有操作与本次新增的 `workcase-precheck-create` 一样，都处于「已实现、未声明」状态。

这是**既有的系统性问题**，不是本次改动引入的：新增操作只是使该状态的条目数加一。能力发现会把未声明操作报为「不可用」并附精确原因（`05 §6.1` 的机械义务），故该状态**不会伪装成已声明**。

本候选**不处理**该问题，理由：它跨越八个类型规范，属独立范围；若塞入本候选，会把「一条创建次序规则」扩成「类型规范操作声明体系」，与 `01` 反过度设计相悖。故如实登记在此，供 Human 决定是否另行处置。

## 4. 实现对应（先行落地，供审核核对文本与实现是否两致）

| 候选条款 | 实现位置 |
|---|---|
| 只读预检入口、返回机械结论与候选指纹 | `plugin/lib/workcase-writer.js` `precheckWorkcaseCreate`；`plugin/lib/workcase-tools.js` 操作 `workcase-precheck-create` |
| 预检与写入执行同一组机械校验 | `plugin/lib/workcase-writer.js` `runMechanicalChecks`（预检与 `writeValidated` 唯一汇聚的编排）；`validateCreateCandidate` 为其薄包装 |
| 先预检、后提请 | `plugin/lib/workcase-tools.js` create 分支（预检在 `requestWorkcaseRouting` 之前） |
| 内容变化即拒绝 | `plugin/lib/workcase-writer.js` `computeCreateCandidateFingerprint`（覆盖调用方提供的全部候选内容，含流入 `change_log` 的变更摘要）+ `createWorkcaseObject` 的 `expectedCandidateFingerprint` 比对 |
| 只读性（不生成对象标识） | `evaluateCreateCandidate`：`object_uid` 仅在 `signature !== null`（写入路径）生成 |

守卫与变异验证：`plugin/test/workcase-precheck-create.test.mjs`（13 条用例）；五个变异体均被用例杀死——① 预检后置；② 移除指纹比对；③ 忽略调用方指纹；④ 禁用指纹格式校验；⑤ 指纹改回剥离变更摘要。全量 `npm test` 971 通过 0 失败（截至 2026-09-26）。

**独立对抗审核已发现的真实缺陷（已修复并转为守卫）**：

- **F1（高）**：指纹原先剥离 `change_summary`，而该值由调用方提供且逐字落盘到 `change_log[0].summary`。实测反例：预检候选甲取指纹后，把该值换成乙并携带同一指纹写入 → 写入被接受、落盘为乙；即候选文本「内容变化一律拒绝」当时**不成立**。修复取**收敛实现**（该值会落盘即属候选内容，纳入指纹），非放宽文本。
- **F2（中）**：「唯一汇聚点」原为夸大——`writeValidated` 内联复写同一三件套。已抽出 `runMechanicalChecks` 单一编排，预检与全部写入路径委托它；文本相应从「同一实现」改为「同一组机械校验/同一组校验函数」。
- **F3（中）**：指纹格式校验无守卫（禁用该校验后用例仍全过）。已补用例，变异体被杀死。

## 5. 未验证范围与风险（如实登记，供 Human 判断）

1. **实现先行**：本提案的实现已落地，存在「以既成事实换取同意」的形态风险。缓解：本提案明确声明实现先行不使提案取得规范效力，也不构成同意；若 Human 决定不采纳，实现须回退，回退范围见 §3.4 的对应项。
2. **候选指纹的覆盖边界**：只覆盖调用方提供的内容，不覆盖 Code 生成字段——已写入 §3.2 明示，不得据指纹声称「对象未被改动」。
3. **「两处同一组校验」的可验证性**：本候选要求预检与写入由同一组校验函数给出结论，但**规范本身不提供**机械手段证明二者确为同一组；该证明由 `09 §5` 守卫测试（两侧同判用例）与变异验证承担。规范层只登记义务，不声称已验证。
4. **未覆盖的对象类型**：本候选只针对 WorkCase 创建。其余六类的创建路径是否同形态，**本提案不主张、不推定**，须各自按其类型规范与 `01 §12.1` 处置。
5. **规范正文不含状态的核对**：本候选正文以条件式要求书写，未写入实现状态；§4 的实现对应只存在于本提案文档，不进入规范正文（`01 §7.2`）。
6. **受控工具面之外的路径不受本条保护**：经 §3.2 的边界声明已如实登记——越过受控创建入口直调写入实现者，本条不提供机械保证。该保证范围与 `21 §14` 复核独立性条同形，故本条不得被读作「任意路径下内容漂移均被拦下」。
