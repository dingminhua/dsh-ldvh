## 二、方向之间的边界

### 2.1 容易混淆的方向对

| 混淆对 | 混淆原因 | 消歧判据（如何判为同一/不同） |
|--------|---------|------------------------------|
| 测试（E6）vs 验收标准（Q1） | 都关乎「质量是否够」 | 测试=**自动化验证手段/基线**；验收=**业务意图是否被满足的判据**。前者是机制，后者是结论门槛。不同方向。 |
| 安全（E11）vs 隐私（G4） | 都处理「数据与风险」 | 安全=**对抗外部/内部威胁的防护**；隐私=**个人数据处理的合法性与最小化**。隐私是安全的子集但法规独立，通常分设。 |
| 审计（G1）vs 合规（G2） | 都涉及「留痕与满足外部要求」 | 审计=**内部可追溯性与证据留存机制**；合规=**对照具体法规/标准的符合性判定**。审计是合规的输入之一，但方向不同。 |
| 发布（E8）vs 发布门槛（Q2） | 都含「上线」 | 发布=**上线动作与流程**；发布门槛=**允许上线的硬性条件**。动作 vs 门禁，不同方向。 |
| 配置管理（E10）vs 部署（E17） | 都碰「环境」 | 配置=**环境差异数据的外部化与来源**；部署=**把产物送到环境的动作**。不同方向。 |
| 可观测性（E13）vs 运维（E18） | 都管「运行态」 | 可观测性=**产生/采集信号的能力**；运维=**基于信号做值守与处置的人机流程**。前者是能力，后者是职责。 |
| 分支策略（G10）vs 评审（G6） | 都属协作治理 | 分支=**代码集成的拓扑约定**；评审=**变更前的质量把关动作**。可独立存在。 |
| 文档（G5）vs 知识管理（T3） | 都关乎「写下来」 | 文档=**面向交付物/上手的结构化产出**；知识管理=**组织记忆的沉淀检索体系**。文档是知识管理的输入之一。 |
| 架构（E21）vs 技术选型 | 常被混为一谈 | 架构=**系统结构与关键约束的方向性规范**；技术选型=**具体组件的决策记录**（由 ADR 事实类型承载）。决策是架构的支撑，非同一方向。 |
| 需求（P1）vs 验收标准（Q1） | 常写在同一处 | 需求=**要做什么（意图）**；验收=**怎么算做完了（判据）**。需求可派生验收，但规范层面应分设。 |

### 2.2 可能合并 vs 必须分开

**可合并（一份规范覆盖多方向）的情形** `[判]`：
- E1 代码风格 + E6 测试基线 + E21 部分架构约束，可并入「Code 工程纪律」一份（LDVH 09 即此模式：代码风格+测试基线合一）。
- E7 构建 + E8 发布 + E17 部署，小项目可合并为「构建与交付」一份。
- G5 文档 + G8 版本策略，可在「发布与门面」一份内（LDVH 08 接近此模式）。
- P2 交互 + P4 信息架构，UI 项目可并入 Web 规范（LDVH 10 即此模式：呈现+交互合一）。

**必须分开的情形** `[判]`：
- 安全（E11）与隐私（G4）：法规边界独立，合并会模糊责任面。
- 审计（G1）与合规（G2）：审计是能力、合规是判定，合并会导致「有日志即合规」的误判。
- 测试（E6）与验收（Q1）：机制与结论混淆会让「测试过了」替代「业务满足了」。
- 任何「能力方向」与「治理方向」跨层合并（如可观测性 E13 与运维 E18）：前者是工程能力，后者是组织职责，合并会使规范既不像技术文档也不像流程文档。

### 2.3 消歧总判据（我的提炼）`[判]`

> 两个候选方向是否为「同一方向」，看三件事：
> 1. **主语不同**——管的是「机制/能力」还是「职责/判定」？是「工程动作」还是「治理结论」？主语不同则方向不同。
> 2. **变更频率不同**——一份规范的修订频率应大致一致；若一个话题常随业务变、另一个随技术变，应分开。
> 3. **责任面不同**——违反它的后果由谁承担、向谁负责？责任面不同则方向不同。
> 满足任一条「不同」即应分设；三条都高度重合才考虑合并。

3. API 契约 — 常见（暴露 API 时）
4. 数据库 — 常见（有状态存储时）
5. 依赖与供应链 — 必需
6. 配置与安全基线 — 必需（安全至少基线，配置必需）
7. 错误处理与日志/可观测性 — 常见
8. 构建/发布/部署 — 常见（可由 08 派生项目级交付规范）

**产品层（建议 1–2 份）**
9. 需求与验收 — 必需（需求 P1 + 验收 Q1 合并为「需求与验收」一份，避免意图与判据割裂）

### 3.2 量级估计 `[判]`

- **候选方向总数**：本调研罗列约 **42 个**方向（工程 21 + 产品 5 + 治理 10 + 团队 4 + 质量 4）。
- **典型项目实际需要的「事实规范」份数**：**约 15–25 份**（必需约 10–12 份 + 常见约 5–10 份 + 可选按场景）。
  - 必需性分布：必需 ~14、常见 ~20、可选 ~8（见 1.1–1.5 表格）。
  - 小项目（工具/库）：**8–12 份**；中大型产品：**18–25 份**；受监管/多团队：**25+ 份**。
- **与 LDVH 现状的落差**：当前元规范中，作为「被管辖项目的工程方向」**完整覆盖的仅 09（Code）、10（Web）两份**；05/06/08/02 在局部（契约/提交/发布门面/评审制度）部分覆盖；其余约 **35+ 个方向完全未被任何元规范作为方向承载**。

### 3.3 这个量级对 LDVH 机制的意味 `[判]`（据实评估）

1. **召回成本**：事实规范份数 ~15–25 时，Human 在 Web 呈现中定位某一方向规范的认知负担显著上升。LDVH 10 的四层阅读器（字段级直读/卡片网格/语义详情/扩展阅读）需要承担「多规范导航」压力；若规范数达 25+，必须依赖 07 的管辖登记 + 高效检索，否则 Human 会迷失。
2. **维护成本**：每份事实规范都是受控提交的治理对象（06 提交契约 + 08 发布门面）。15–25 份意味着每次跨规范改动都要走 Git Gate；规范漂移（spec drift）风险随份数线性上升，需要 01 的独立对抗审核与机械校验常态化。
3. **Web 呈现压力**：10 的四层阅读器需为每份规范渲染四层；25 份 × 四层 = 100 个呈现面。若规范正文冗长，前端渲染与 Human 滚动成本都成问题——这反过来要求每份事实规范保持「最小规则引导」式精简（呼应 01 的最小规则引导）。
4. **「一个方向只能一个规范」的执行成本**：该判据在 ~42 候选方向面前，意味着要么（a）严格一方向一规范 → 规范数爆炸至 40+，维护/呈现不可持续；要么（b）允许「一份规范覆盖多方向」的合并模式（如 09、10 已做的那样）→ 此时「一个方向一个规范」需重新表述为「**一个方向至多被一份规范承载，但一份规范可承载多个方向**」，否则与现有 09/10 自相矛盾。
5. **结论**：对典型受管辖项目，推荐以 **~15–20 份事实规范**为健康上限，采用「必需方向独立成规范、强相关方向合并成规范」的务实策略，而非机械的一方向一文件。

**残留不确定（如实指出）** `[判]`：
1. **「方向」的粒度未由 Human 给定上限**：本调研按「可独立成规范的关注面」切分，得到 ~42 个；若按更粗粒度（如仅「工程/产品/治理/团队/质量」五大方向），则只有 5 个。判据「一个方向只能一个规范」在两种粒度下结论完全不同——**这是判据本身的最大模糊点**（见 4.3）。
2. **LDVH 元规范的「方向」是元层级（LDVH 自身架构），还是项目层级（被管辖项目的工程方向）？** 本调研按任务字面理解为后者（软件开发方向），但 Human 给定实例（09/10/01–08/11–12）实为前者（LDVH 自身）。两层混谈会导致清单用途不清。
3. **部分「方向」是否应升格为事实类型而非事实规范**：如 审计（G1）、缺陷（Q3）、复盘（Q4）在 LDVH 中已由事实类型（ADR/Pitfall/Friction/WorkCase）提供能力，未必需要独立「规范方向」。此边界需 Human 裁定。

### 4.3 对 Human「一个方向只能一个规范」判据的边界问题（如实指出，不迎合）

1. **粒度缺失导致判据不可执行**：判据未定义「方向」的粒度。粗粒度 5 个方向 ↔ 细粒度 42 个方向，结果天差地别。若无粒度锚点，「一个方向一个规范」无法落地。
2. **单方向内容溢出必须拆分，与判据冲突**：一个方向（如「安全」）内容可能多到单文件不可维护，必然要拆（如拆为「应用安全/基础设施安全/数据安全」）。拆后仍是「同一方向多份规范」，直接违反判据。需补充「方向内可分子主题但不升格为新方向」的规则。
3. **跨方向内容归属困境**：安全（E11）的内容天然渗透代码（E1）、API（E5）、配置（E10）、部署（E17）。判据要求「一个方向一份规范」，那「API 的安全规则」写进 API 规范还是安全规范？若两边都写，则重复（违反「成体系」）；若只写一处，则另一规范缺失该约束。需要「主规范承载 + 他处引用」的引用纪律，而判据本身未提供。
4. **与现有 09/10 的实践自相矛盾**：09 把「代码风格 + 测试」合并、10 把「呈现 + 交互」合并，已事实上是「一份规范承载多方向」。若严格按判据字面，应拆为 4 份。说明 Human 的实际意图更可能是「**一个方向不被多份规范重复承载**」（即反重复），而非「一份规范只承载一个方向」（反合并）。两者方向相反，需 Human 澄清用词。
5. **可选方向是否计入「规范」**：小项目不需要灾备/供应商/隐私等方向。若判据隐含「全量方向都要有规范」，则与「按需」冲突；若允许缺省，则「一个方向一个规范」只对「存在的方向」成立，需显式声明。
6. **元层级 vs 项目层级的判据适用范围**：若判据只约束 `specs/` 元规范（每个文件一方向），则本调研的 42 个项目方向不在此列，调研价值转为「帮助识别元规范是否漏方向/重复方向」；若判据也约束被管辖项目的事实规范，则面临上述 15–25 份量级的维护压力。适用范围须明确。

> 综上：Human 的判据抓住了「反重复、成体系」的核心直觉，但在**粒度锚点、方向内拆分、跨方向引用、与 09/10 既成事实的一致性、可选方向处理、元/项目层级适用范围**六处存在边界空白。建议 Human 将判据精炼为：「**任一规范方向在管辖域内至多由一份规范承载（反重复）；一份规范可聚合强相关方向（允许合并）；方向内子主题可拆文件但不得升格为新方向；跨方向约束以主规范承载 + 他处引用实现，禁止重复定义。**」
