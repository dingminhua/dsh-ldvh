# 结构重排 · 代理审议输入材料（2026-09-10）

> 性质：过程文档，不是规范源、不是事实对象，不取得规范效力。
> 用途：作为代理审议（隔离视角独立作业）的统一输入材料。审议产出为「结构决定清单」，
> 后续分别进入 00 修订的受保护内容流程与下位规范修订。

## 一、背景

v5 根方案经 Human 逐点讨论，形成三项实质重排。本材料把**已定项**与**待审议议题**分开：
已定项是 Human 的决定，审议不得推翻，但**必须指出与已定项的内部矛盾**；待审议议题由审议定稿。

## 二、已定项（Human 已决定）

### A. 能力承载两族（原「三大技术支撑」重构）
- **LDVH CLI 确定性服务**承载读与写；**宿主原生机制**承载编排与注入。
- CLI 是确定性服务的**规范形态与契约唯一实现**；接入面可有多个：DSH 工具（会话内，进程内调同一核心，薄适配）、CLI（Git Hook / 终端 / 外部消费方）、Web API（Human 呈现）。任何接入面不得私改契约，parity 由契约测试机械保证。
- 05 改名（暂定「LDVH CLI 规范」）；四价值交付第 2 项相应改名（暂定「LDVH CLI 确定性执行」）。
- 现状佐证：`plugin/package.json` 已有 `bin: dsh-ldvh → lib/bin.js`；`commit-validation.js` 已被 `git-gate-runner.js`（CLI 面）与 `ldvh-tools.js`（工具面）共同 import；08 §125 已使用「LDVH CLI 语义」表述；05 §5.1/§7 现行「不要求另建 CLI / 不设 CLI 投影档位」与上述现实矛盾。

### B. 行动模板取消与执行系统新增
- 04 行动模板基础规范整体退出；三类语义构成要素 → **两类**（规范模型 + 事实模型）；30–38 模板编号作废。
- 模板中属「领域流程判断」的内容由各业务系统收敛；属「00 §7 机械落点」的横切内容进 02 或执行系统（逐块归属见议题 1）。
- **新增执行系统**（暂名「单元执行」），参照调研系统三件套模式：系统规范（流程层）+ WorkCase 事实类型（结构层，21 号已预留）+ CLI 服务与宿主机制（承载层）。
- 依据：30–38 从未起草；v5 全部真实工作零模板参与；v4 问题账 095（过度合规）教训；工作模型重构后业务系统+制度已覆盖流程职责。
- 护栏：执行系统只收「被批准工作」（00 §3.1 原文「各业务系统被批准工作的共同收口模式」），低风险普通求解不进 WorkCase。

### C. 两级规范与规范事实对象
- **元规范**（LDVH 仓库 `specs/`）+ **项目规范对象**（新事实类型，暂名 Norm，27 号；承载于管辖项目 `ldvh-base/norms/`，路径暂定）。
- 两者**核心机制同**（受控写入、状态机、Human Gate、Git Gate、回读、F0–F4 召回），**仪式按风险缩放**（低于元规范、高于 ADR）。
- 权威关系：项目规范不得放松或改变元规范对治理机制的约束；可在项目范围内加码；对与本项目无关的元规范条款无权触碰。
- 07 §6 工作对象定义中的「规范路径（specs/）」相应调整，`specs/` 成为元规范专属。
- 意义：00 §3.3「AI 不得自行新增、改写或扩张可强制执行规则」的完整机制化。

### D. 00 去枚举（根稳定性）
- 00 不再列举具体业务系统（记忆/调研/讨论/执行/遵守），只保留**类别契约**（业务系统=直接产生决策、行动或结论的职责层）；名录下沉至 30+ 业务系统区块登记。
- 增删业务系统由此从「00 修正案」降为规范生命周期事件（仍走 01 §8.2 Human Gate）。
- 「稳定后回填」：这是冻结名录，不是删除概念。
- 连带：AGENTS.md、`plugin/lib/guidance-text.js`（受保护内容）中列举业务系统的句子需同步。

### E. 元规范与管辖项目的边界原则
> 元规范约束 LDVH 自身及其机制对项目的运作；项目的内容、结构与工程纪律归项目规范对象。元规范不替项目定规则，项目规范不替 LDVH 定机制。

判定问句：任何一条元规范要落到项目里，必须能回答「它管的是 LDVH 自己产生或承载的东西吗？」——答不出的即越界。

### F. 提交层属 LDVH 管辖
- 管辖项目内**全部提交**均由 LDVH 管理（提交在 Web 呈现、是溯源载体），与提交内容无关，**只与项目是否受管辖有关**。
- 连带：06 §4.2「受控提交候选包括受管事实对象、规范源文件和规则源成员变更」应改为「管辖项目内的全部提交均为受控提交候选」；06 §4.3「普通求解、普通编辑和非受管文件修改不因本规范存在而强制经过 precheck 或 Git Gate」需改写（普通编辑不经 precheck，但提交仍受 Git Gate 消息契约约束）。
  （注：此处原为「规范限定范围、实现未分派」的不一致，Human 决定以实现为准，规范追上实现。）
- 项目自己的提交约定可作为项目规范对象声明的检查共存（加码方向），LDVH 契约为底线。

### G. 元规范准入判据
不随 LDVH 发布、不约束辖区工作进行的规范，不进元规范（迁往 dsh-ldvh 项目的事实源规范对象）。

### H. 效力层级
- **外边界**：元规范不可放松（要放松只能退出管辖）。
- **内层级**：Goal → ADR → Norm → 行动 / WorkCase；**边由下游声明**（25 §129 既成设计：Goal 是引用链顶点，唯一合法边是「下游指上来」）。
- 违反的处理是**暂停 + 提请**（00 §7.2「规则的适用、效力或权威关系无法确认」），不并存。
- 效力来源澄清：ADR 约束 Norm 不是因为事实创造规则，而因 ADR 是 **Human 决定的记录**（00 §3.3），Goal 是 **Human 意图的结构化表达**（25 §121）。此边界在 00 重写时必须写死。

### I. 锚点设计（方向已定）
- ADR 增 `serves_sg`（**强锚**，参与 goal 修订级联）——现状 22 号关系闭集仅 `superseded-by`，与 Goal 无机械连接。
- Norm 增 `derives-from → ADR`（0..n），无 ADR 时挂 `serves_sg`；退役用 `superseded-by → Norm`。
- 对照：Spark/Friction 的 `serves_sg` 是**轻锚**，明确豁免级联（20 §128 / 25 §11）。
- 机械可查：锚点存在性、被引对象存在与状态、悬空引用、级联枚举；语义一致性（「是否违反」）由 AI 判断 + Human Gate，**不得包装成机械检查**（00 §3.4）。

### J. 编号区块
- **30+ = 业务系统区块**（原 30–38 模板区块，开放不封顶）；01–19 基础设施；20–29 事实类型。
- 改号不改键：`research-system-foundation`、`discussion-system-foundation` 等 spec_key 存活，父子关系（refines 02）存活。

## 四、审议纪律（所有视角共同遵守）

1. **只读**：不得写入、修改任何文件，不得执行提交。
2. **依据可回指**：每条结论必须回指规范条款（`spec_key` + 章节号）或文件路径 + 行号。
3. **不得推翻已定项**，但必须指出其内部矛盾、与 00 根契约的冲突、或未预见的后果。
4. **机械与语义分层**：不得把语义判断包装成机械检查（00 §3.4）。
5. **反过度设计**：不为「更保险」无条件扩大流程（00 §7.3）；警惕 v4 问题账 095 过度合规的重演。
6. **输出格式**：每个议题给出「定论 / 理由 / 依据 / 未决点（需 Human 决定者单列）」四段。
