## 4. 反例清单（维度 7）

**R1：「测试通过只能证明各自机械范围」是否过于绝对？**——反例不成立。即使某测试恰覆盖完整语义（极端如穷尽性形式验证），它证明的仍是「当次运行的断言通过」；「不能**单独**证明语义满足」的真正理由（测试可能错译规范、实现与测试同源自证、环境代表性）在 §5 L102「实现与其验证测试须由不同代理或不同 AI 分任，避免同源自证」中已被 09 自己承认。且该措辞朝保守方向（宁可低估证明力），不产生自欺风险，反而服务防自欺。维持原文。

**R2：「严禁复制副本逻辑」——两个领域需要同一算法（如同一 hash）怎么办？**——反例不成立但暴露判据缺口。09 禁的是「复制副本」（平行复制的第二份实现），两领域共享同一 util 模块恰是「单一职责入口」鼓励的解，不违反。但 09 未显式定义「副本」判据（复制粘贴 vs 巧合相似 vs 语义不同而代码相同），§7 L130 的验证入口「副本扫描核对」无法机械判定语义副本——需人工调用链观察补充。09 如实将该项归入扫描+观察，可接受；判据缺口记为已知限制。

**R3：§3.2 状态机归 20–27 是否与 03 §6.1 一致？**——一致，反例不成立。03 §6.1 `status` 行原文「状态值、初态、转换和终态由类型来源定义」；同节表下原文「各事实类型规范（当前登记 20–27）」。「类型来源」= 20–27 有 03 双处原文背书。0a1b2d3 的更正准确，且消除了 review-09.md P3 的旧冲突。

**R4：09↔10 边界——Web 需要 Code 侧提供数据怎么办？**——边界可辩护但未显式声明。实现中 web 前端（plugin/lib/client.js）调用 host API（web-mount.js/host-api.js/web-preferences.js 提供，数据经 governed-projects.js 等实现取得）：数据通道的机械实现落在 09 §3.1.1「LDVH 插件代码结构」的工程纪律内，呈现语义归 10。09 未显式写出「Web 数据通道实现」这一跨界面，靠 §3.1.1 的宽覆盖成立。低危，建议未来在 §3 增一句划界。
