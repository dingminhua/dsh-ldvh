## 一、十维逐维结论

### 1. 价值判据对齐
- **结论：基本对齐，存疑一处。**
- 27 §1 引用 00 §1 痛点 4，价值叙事与 V3/V4/V5/V8、HV3/HV4 对应，符合 §6.3「价值纪律」。
- **存疑**：§1 第三段「Norm 与元规范层级不同……效力来自规范源层级与 active 状态，不来自任何路径挂靠或来源字段」——这一句本身是好的，但本节把「普通文件不能无损承载」列了四条理由（受控写入/状态闭集/方向键排他/正文骨架），其中「方向键排他」与「正文骨架」的**机械保障实际不存在**（见维度 4），价值判据是否被事实支撑存疑。属价值判据的「依据缺口」，非硬性缺陷。

### 2. 职责边界与单一权威
- **结论：与 03、22、01、04 边界总体清晰，但与 04 的潜在重叠未排除（见重点方向 C）。**
- 27 §3.1/§3.3 明确 03 是公共字段与受控读写唯一权威、22 是 ADR 唯一权威、01 是元规范结构唯一权威；不复制相邻规则。✅
- 与 02/06/12 的「不负责」分工声明完整。✅
- **缺陷（存疑）**：27 §5 自称「事实规范的唯一事实类型定义」，但 03 §5.1 已定义五类事实类型（ADR/Pitfall/Spark/WorkCase/Research），且 20–24、25、26 各占编号；27 以「事实类型」身份插入 27 位，属 03 §5.2 准入六问的「类型定义来源」由本规范承担——这一条在 01 §8.1 已登记，形式上通过。但与 04（业务系统规范 30–35）的「项目侧规范」职责是否重叠，未在本节澄清（见方向 C）。

### 3. 反过度设计
- **结论：红线设计良好，但第 4 条与维度 4 的三道防线声称存在张力。**
- 27 §17 七条红线逐条合理（不强制 42 份、不设 norm_source、不建 relations、不升层级键、不建缓存）。✅
- §17.4 明确「不设 norm_source 或类似的『指向元规范』字段」——撤回历史设计，符合 Human 判据。✅
- **存疑**：红线 5「不为『成体系』设立无法机械判定的强制质量门槛」与 §8「四段骨架是弱机械门槛」自洽；但 §11「三道防线」把未实现的写入前扫描/Git Gate/消费端 fail-closed 写成规范强制要求，**超出反过度设计的「不声称未实现能力」边界**（见维度 4 / 00 §7.1）。

### 4. 技术可实现性与能力真实性（重点）
- **结论：已证实缺陷——「三道防线」声称已保障而实际未实现。**
- 27 §11 第三段明确写成规范强制要求：

- **复现**：

  - `cat plugin/lib/git-gate-runner.js`（确认无 norms 扫描）

- **严重程度：高（已证实缺陷 D1）。**

### 5. 身份、编号、引用和格式
- **结论：身份块合规；但 `direction_key` 正则与既有「职责标识符」格式逐字不同（已证实 D2）；附件反向引用待核（D3）。**
- 身份块：27 与附件的 `spec_key`/`attachment_key`、编号、标题、canonical_path 一致，符合 §6/Att.02。✅
- 27 §8 `direction_key` 正则：`^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`（**带 `^` `$` 锚**）。
- Att.02 §2「职责标识符」格式：`[a-z][a-z0-9]*(?:-[a-z0-9]+)*`（**无锚**）。
- **差异**：27 引入了第二套带锚正则，而既有的「职责标识符」闭集无锚。27 §8 自注「符合 03 §6.1『20–24 分别登记专属字段增量』的既有惯例」——但 03 §6.1 并未定义 `direction_key` 的专属正则格式；03 §6.1 只说 `fact_type_key` 值域由各类型「身份与载体」逐一登记。27 的正则**实际是 kebab-case**，与 Att.02 职责标识符字符类相同但多了锚点。
- **判据**：01 §8.3 要求附件/字段「key 双向对应、身份与路径一致」；但更关键的是——`direction_key` 是**事实对象字段**，不是规范职责标识符，其正则无需与 Att.02 职责标识符逐字相同。然而 27 未说明「为何在既有的 kebab-case 之外新增带锚变体」，且未回指任何已登记的类型字段正则作为来源。**属引入了未经登记、与既有闭集形式不同的第二套标识符规则（存疑→倾向已证实 D2）**。
- **复现**：`grep -n 'direction_key' specs/27-Norm-事实规范.md`（行 142、225）；`grep -n '职责标识符' specs/attachments/01.Att.02-规范身份字段表.md`（行 36）。
- **D3（存疑）**：附件 §6「使用说明」第 4 条引用「27 号 §11 三道防线」「27 号 §6.1 三条消歧判据」；27 §6.1 确实含三条消歧判据（主语/变更频率/责任面），§11 含三道防线——引用存在且指向正确。✅ 但附件 §6.2 引用「27 号 §6.1 的三条消歧判据」与正文 §6.1 一致；附件未引用不存在的章节。**附件引用一致，D3 排除。**

### 6. 防自欺边界
- **结论：正文多处主动声明「不能单独证明」，但 §11 三道防线声称抵消了部分防自欺（与 D1 同源）。**
- 27 §1、§14、§15 反复声明「对象存在/active 不能单独证明规则正确、适用、已被遵守」。✅
- §14 验证表末行「未实现与不可用范围保留为 gaps」✅——但 §11 的三道防线文字与之矛盾：§11 把它们写成「保障」，§14 又承认「未实现进入 gaps」。**同一文件内部，§11 声称已保障、§14 承认未实现——内部不一致（见维度 7 / D4）。**

### 7. 内部一致性与反例检验
- **结论：已证实内部不一致（D4）；反例可击倒「成体系」弱门槛（D5）。**
- **D4（已证实）**：§11「三道防线保障唯一性」 vs §14「未实现与不可用范围保留为 gaps」+ 机械核验三道均未实现。规范自己承认能力未实现，却在前文称其「保障」。属 01 §9.3「不得把受影响载体返回为通过」的同质问题。
- **D5（已证实，反例）**：§5/§8 用「正文四段固定 H2 骨架且各段非空」作为「成体系」的弱机械门槛。构造反例：
  ```
  ## 方向定位与适用范围
  管代码风格。
  ## 核心规则体系
  写清楚点。
  ## 约束与反模式
  别乱写。
  ## 验证与遵从性检查
  自己看。
  ```
  该对象满足四段非空、direction_key 合法、status=active，**全部机械校验通过**，但显然是空壳规范。27 §17.5 自认「不设立法质量门槛」，故「成体系」判据在机械层为空——与 22 ADR 的「正文固定 H2 + decision/scope 逐字包含 frontmatter（§8 §14 真校验）」相比，**27 的四段骨架无逐字/字段对应强度，是弱于 ADR 的纯存在性校验**（见重点方向 D）。这不构成硬缺陷（27 自认弱门槛），但**价值叙事中「无正文骨架结构保障（『是否成体系』无弱机械门槛）」作为普通文件不能无损承载的理由之一，被该弱门槛自身证伪为「门槛过弱以至于近似不存在」**——属价值判据依据缺口。
- **反例（同义异名，已证实）**：27 §11 自认「`web` vs `frontend` 机械无法识别」。构造：方向 A `direction_key: web`、方向 B `direction_key: frontend`，二者语义重叠但机械层视为不同 direction_key，均可通过唯一性校验 → 「一方向一规范」判据在语义层无法机械保证。27 把查重语义判断推给 AI/Human（§6.2），故「一方向一规范」的**机械唯一性只覆盖字面 key，不覆盖语义方向**——规范把不可机械保证的判据写成「反重复版的『一方向一规范』判据」（§11 末段），但该判据的「反重复」仅由字面 key 实现，**语义重复（同义异名）仍可发生**。属「判据根本无法机械保证却写成规范要求」的边界问题，与 D1 同源（声称保障 vs 实际仅字面保障）。

## 二、缺陷清单（分级 + 依据 + 复现）

### 已证实缺陷

**D1（高）：§11「三道防线」声称已机械保障，但实现不存在 —— 违反 00 §7.1 防自欺锚点、01 §11.4。**
- 依据：27 §11 第三段将写入前扫描、`ERR_DIRECTION_ALREADY_EXISTS`、Git Gate 方向键频次校验、消费端 `direction_collision` fail-closed 写成规范强制「保障」。
- 复现：
  - `grep -rn 'ERR_DIRECTION_ALREADY_EXISTS\|direction_collision' plugin/` → 0 命中
  - `cat plugin/lib/git-gate-runner.js` → 仅 commit-message/identity 校验，无 `ldvh-base/norms/` 扫描
  - `grep -n 'norms' plugin/lib/governed-projects.js` → 仅目录常量，无唯一性逻辑
  - `ls specs/3*.md` → 30–35 未成立，Norm writer 未见
- 影响：规范把未实现能力写成「保障」，读者/Code/Web 可能误信方向键唯一性已被三层防线守住；实际仅字面 key 可由未来实现保障，当前无任何防线。
- 建议：将 §11 三道防线改为「设计意图 / 待实现契约」，明确标注未实现项进入 gaps；或等实现落地后再写「保障」。

**D2（中）：`direction_key` 正则引入带锚变体，与既有「职责标识符」闭集（`[a-z][a-z0-9]*(?:-[a-z0-9]+)*`）逐字不同，且未回指任何已登记类型字段正则作为来源。**
- 依据：27 §8 行 142、§13.1 行 225 用 `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`；Att.02 §2 行 36 职责标识符格式无 `^$` 锚。
- 复现：`grep -n 'direction_key' specs/27-Norm-事实规范.md`；`grep -n '职责标识符' specs/attachments/01.Att.02-规范身份字段表.md`
- 影响：事实对象字段正则与规范身份闭集形式分裂；若未来 Code 用无锚版解析 direction_key，边界不一致。27 未说明为何偏离既有 kebab-case 闭集。
- 建议：统一为 Att.02 既有 kebab-case 字符类（去锚或说明锚点为字段级完整匹配要求），并回指 03 §6.1 已登记值域。

**D4（高，内部不一致）：§11 称「三道防线保障唯一性」与 §14「未实现范围保留为 gaps」自相矛盾。**
- 依据：同 D1 + 27 §14 末行「未实现与不可用范围保留为 gaps」。
- 影响：同一规范既声称保障又承认未实现，削弱防自欺可信度。
- 建议：与 D1 一并修复，使 §11 与 §14 表述一致（均标注待实现）。

**D5（中，反例已证实）：「成体系」弱机械门槛（四段非空 H2）可被空壳规范通过，且 27 自认不设立法质量门槛 —— 价值叙事中「无正文骨架结构保障（是否成体系无弱机械门槛）」作为普通文件不能无损承载的理由被自身证伪。**
- 依据：27 §8 四段骨架仅要求存在且非空；§17.5 自认弱门槛；对照 22 §8/§14 decision/scope 逐字包含 frontmatter 为真校验。
- 复现：构造四段非空空壳 Norm，全部机械校验通过。
- 影响：价值判据中「成体系」的机器表示近乎为空，与 ADR 的正文真校验强度不对等。
- 建议：明确承认四段骨架仅为「结构存在性」门槛、不证明成体系；或将「成体系」三条判据（§5）中至少可机械化的部分（如「多条可独立执行规则」≥ N 条）纳入校验，否则在价值叙事中下调该理由权重。

### 存疑（需 Human/主控裁定）

**S1（方向 C）：27 的 Norm 与 04 的「业务系统规范 30–35」职责是否重叠。**
- 27 管「项目层成体系方向规范」，04 管「30–35 业务系统规范共同结构」。一个项目的「安全规范」应走 Norm 还是 30–35？04 §3.2 明确「具体业务系统规范（30–35）是其专属流程、领域条件和结论承载的唯一权威」，但 30–35 尚未成立（存疑：未来成立时是否含「项目安全规范」？）。当前 27 与 04 各自定义「规范」，存在**两套并行规范体系**风险，需 00 §3.6「不构成第二套权威」裁定。
- 依据：00 §3.6；04 §3.3；27 §5。
- 建议：在 27 §3 或 §5 显式说明「Norm 与 30–35 业务系统规范的分工：Norm 是项目侧方向规则承载，30–35 是 LDVH 业务系统机制规范，二者对象不同（项目事实规范 vs 元规范业务系统）」，消除并行权威疑云。

**S2（方向 A）：附件「超出清单建立 Norm 须给足够理由」是否构成附件建立新规则。**
- 依据：01 §8.3「新的职责、义务、授权、Human Gate、Stop Conditions 或正文规则不得放入附件」；27 §12 末段「超出清单建立 Norm 时，该方向必须给出足够理由……并经受控创建的查重与 Human Gate 核对」。
- 分析：该「必须给理由」是对创建提案的**内容要求**，其执行落地在 27 §11 受控创建（查重 + Human Gate），附件仅复述。但 01 §8.3 禁止附件「建立新规则」——若「超清单须理由」在附件中被读作**独立可强制义务**，则越界；若仅为对正文已定义规则的引用说明，则合规。
- **本审核倾向：该句位于附件 §6「使用说明」且 27 §12 已授权「清单的使用说明」，且执行绑定正文 Human Gate，属「解释使用说明」而非「新规则」——倾向合规，但表述应明确「本要求由 27 §11 受控创建承载，附件不新增义务」以避免歧义。**
- 复现：`specs/attachments/27.Att.01-Norm方向清单.md` 行 22；`specs/27-Norm-事实规范.md` §12 行 218。

**S3（方向 B）：`direction_key` 语义唯一性不可机械保证（同义异名），规范将不可机械保证的判据写成「一方向一规范」反重复判据。**
- 依据：27 §11 自认 `web` vs `frontend` 机械无法识别；唯一性公式仅约束字面 key。
- 影响：规范声称「反重复版的『一方向一规范』」，但语义重复仍可发生；实际保障仅字面 key 唯一。
- 建议：在 §11 明确「反重复保障范围为字面 direction_key；语义重复由 §6.2 查重（AI/Human）兜底，不进入机械唯一性」，避免读者误以为三道防线已防同义异名。

**S4（方向 E）：「两层各持同名方向不构成重复」是否导致同一方向两套规则同时约束。**
- 依据：27 §5「层级边界」段。
- 分析：元层 09=Code 与项目层 Code 方向 Norm 同名，约束对象不同（LDVH 机制 vs 本项目），不冲突。但需确认项目层 Norm 不得引用/覆盖元规范——27 §1 已声明「事实规范不得放松元规范」，基本覆盖。
- 建议：在 §5 补充「项目层 Norm 与元规范同名方向时，项目层只约束本项目、不得改写或放松元规范对应方向」。

### 已排除

- **附件 §6 反向引用正确性**：附件引用「27 号 §6.1」「27 号 §11」均存在且指向正确 → 排除 D3。
- **身份块格式**：27 与附件 identity block 字段闭集、key、编号、路径一致，符合 §6/Att.02 → 排除身份块缺陷。

## 三、重点方向 A–F 结论

### A. 授权附件合规性（最关键）
- **§12 满足「唯一授权附件结构角色」**：27 §12 是单一 H2 承担授权附件角色，无竞争结构角色（01 §8.3 要求满足）。✅
- **方向清单（42 个）是否在正文「已经定义」**：27 §5/§6.1 定义了「方向」判据与「成体系」判据，但**42 个具体方向条目（E1–Q4）是附件新内容**，正文未逐一定义。27 §12 称「其内容由本文 §5/§6.1/§11 已经定义并授权」——严格说，正文定义了**方向判据**，未定义**42 个方向清单本身**。属「把新内容搬到附件、声称已由正文授权」的边界情形。
- **「超出清单须给理由」是否新规则**：见 S2，倾向合规但表述待澄清。
- **结论：A 基本合规，但「42 方向清单已由正文定义」的声称偏弱（正文只定义判据不定义清单），且附件「超清单须理由」句宜显式回指正文受控创建以避免越界嫌疑。**

### B. `direction_key` 机械可强制性与软边界
- 写入前扫描在无 writer 实现时不成立（D1）。
- 同义异名机械无法识别（S3）→ 「一方向一规范」判据根本无法机械保证语义层，规范写成强制要求属超出可实现范围（与 D1 同源）。
- 正则与 Att.02 职责标识符闭集逐字不同（D2）。
- **结论：B 三项均指向同一根因——把未实现/仅字面/形式分裂的标识保障写成规范强制要求。**

### C. 与 04 的潜在冲突
- 见 S1。27 与 04 各自定义「规范」，30–35 未成立，当前无直接冲突但存在并行权威风险。
- **结论：C 存疑，需显式分工声明；未构成已证实冲突。**

### D. 「成体系」判据可执行性
- 四段骨架为纯存在性校验，可被空壳通过（D5）；弱于 22 ADR 的逐字校验。
- **结论：D 已证实「成体系」机械判据近似为空；27 自认弱门槛，但价值叙事将「无骨架门槛」列为普通文件不能无损承载的理由，自相矛盾。**

### E. 层级边界自洽性
- 与 00 §3.3 两级承载一致（✅）；与 00 §3.6 精神一致但「同名方向两套规则」未论证（S4）。
- **结论：E 基本自洽，补一句「项目层不放松元规范」即闭环。**

### F. 附件与正文一致性
- 附件 §6 量与 27 §12 一致（约 42 方向）；交叉引用 §6.1/§11 指向正确。
- **结论：F 一致，排除 D3。**
