## 4. 三个真实缺陷（全部由本轮发现，含实测）

### 4.1 经验缓冲不按项目分区

**规范依据**（`dev` 的 §12bis 载体段，2026-10 修订）：

> 载体须按管辖项目分文件（或等价的分区），**不得使多个管辖项目的观察材料混在同一个无项目维度的载体里**。
> **诊断记号**：本项目此前的实现把两个项目的材料混在一个全局载体里（实测 47 条中混有他项目材料，并已入账为 friction `11f4eb8f`），属**已知缺陷**。

即：这已是**规范要求、实现欠账**，不是我的提议。

**实现**：`ldvh/experience-buffers/<projectId>.jsonl`（与摩擦侧 `friction-observations/` 并列而分立，
02 §6.1 第 2 条要求每个中间载体有唯一消费者）。

**一处与摩擦侧的关键差异，我特意没照抄**：摩擦条目**自带 `project` 字段**（§12bis.1 闭集 10 项）；
经验条目**没有**（§12bis 闭集 9 项）。若照抄加 `project` 即**越出字段闭集**（§20.1 第 3 项）。
故经验侧的项目区分**只由载体路径承担** —— 这正是 §12bis「或等价的分区」允许的形态。

**防漏传**：`projectId` 在各入口必填，缺则明确拒绝（`capture/project_missing`、
`observation_review/project_missing`），**不静默落到旧全局载体**。另加源码级护栏扫描 `lib/` 全部缓冲调用点。

### 4.2 载体并发写丢失更新（**实测**，不是推理）

**Human 提问**：「摩擦发现 + 经验捕获，在不同的对话里，会不会出现并发的问题呢，如果都是写入同一个大文件，这样的设计肯定有问题」。

**实测（改前）**：

```
场景A 并发 append 40 条 → 读出 40 条  ✅ 无丢失
场景B 并发 settle 20 条 → 仍有 19 条没被结算 ❌ 丢失更新 19 条
```

**根因**：`settle` 走「读全文 → 改目标行 → 临时文件 + rename」。两个会话同时结算**不同**条目时，
各自读到同一份旧内容、各写一份「只有自己那条被改」的新文件，后一个 rename **整个覆盖**前一个。
`append` 之所以安全，是因为 `appendFile` 的 `O_APPEND` 由内核保证单次追加原子。

**修法**（Human 选 C：追加事件日志）：

```
{"kind":"entry",  "record":{…§12bis 九字段…}}
{"kind":"settle", "id":"…","status":"consumed","consumed_by":"…","settled_at":"…"}
{"kind":"remove", "id":"…","at":"…"}
```

读时按序折叠成当前状态。**物理上不存在改写别人那一条的代码路径** —— 故不需要跨进程锁。

**实测（改后）**：

```
并发 append 40 条        → ✅ 40/40
并发 settle 20 条        → ✅ 0 丢失
20 settle + 20 append 混合 → ✅ 总数 50、状态全对、invalid=0
```

**为什么必须常驻测试**：这是**非功能性质**（并发下保持正确），单线程顺序测试永远发现不了。
已加 4 条并发测试；否则将来任何一次「读-改-写更方便」的重构都会把缺陷带回来而测试仍全绿。

**顺带让一条纪律成为结构事实**：§12bis「内容字段一经写入不得就地修改」原来是纪律，
现在是**结构事实**——代码里没有就地修改的路径。

**90 天「整条移除」的落地**：折叠层用 `remove` 事件让条目从视图彻底消失；磁盘字节由
`compactBuffer` 回收。**压缩是尽力而为**：失败只推迟字节回收，不影响任何读写正确性。
且明确登记：压缩**不应与写入并发**（那会丢事件），当前只在诊断侧显式触发。

### 4.3 我自己造成的假绿（诊断页测试）

**症状**：改完载体格式后 web 测试**仍全绿**，但真实生产格式**读不出来**：

```
entries: 1 | recent[0]: {"at":null,"anchor":null,"phenomenon":null,"status":null}
```

条目数正确、字段全 null。原因：**测试夹具还在写旧格式**，而生产代码已改成折叠事件。
测试守的不是它以为在守的东西。

**修法**：夹具改为生产格式，并新增一条**「夹具与生产同格式」**的测试专门守这一环。

**同类教训（上一轮也犯过）**：删除 `idleSilenceOk` 后留下的未使用函数让 `eslint` 报错，
而该报错进入 Git Gate 的 preflight，使**整个仓库 19 条 hook 测试同时失败**。
故记下：**若出现「hook 测试成批失败」，先查 `npx eslint .`**。

## 7. 一次未能复现的失败（如实登记）

全量运行中曾出现 `web-mount.test.mjs` 的
`unexpected child exit re-warms without any incoming request` 失败一次，随后复跑全绿。

**已做的排查**：

| 排查项 | 结论 |
|---|---|
| 是否我改的 | **不是**。`web-mount.test.mjs` 与 `lib/web-mount.js` 与 `dev` **逐字相同**（`git diff dev --stat` 为空） |
| 该测试性质 | 会**真的**启动子进程、SIGKILL、再要求自动拉起、并 `fetch` health —— 对机器状态与负载敏感 |
| 单跑该测试 | 单独跑会挂起超过 5 分钟（等待型测试），故无法用单跑来定位 |

**结论**：**一个观察过一次、复跑即绿、未能归因**的不稳定因素。本次**不排除**它，
也不把它当作「重跑就绿了」打发过去。若再出现，须保留完整逐例输出再判断。
