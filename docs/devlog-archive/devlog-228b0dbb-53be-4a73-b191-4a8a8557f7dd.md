# 调研吸收双职能与目标锚定的规范候选

## 背景

调研吸收系统（specs/33）需要同时支持**外部调查**与**内部信息吸收**两职能，且两者都锚定当前目标与子目标。原载体是一份 WorkCase（`workcase-0179a73e`，open，serves 子目标「项目可厘清」），止于四份规范候选与其成立要件，不含 Code 与 Web 实现。

WorkCase 载体即将随类型删除而退役（2026-11-13 Human 根决定：WorkCase 正式从 LDVH 删除）。本条目承接该单已产出的结论与待裁事项。

## 做法

清点 33 号的取证面与承载面条款，界定内部信息吸收在两处的增量边界；取得 Human 对四项设计分叉与结论承载走向的裁定；按裁定结果产出 33 号两职能与锚定判据的规范候选（取证面分流、共同契约、目标锚定准入、必停情形与结论承载五段），产出 24 号「Research 增设 serves 字段」候选、29 号「内部信息吸收的结论准入与证据锚点形态」候选、28 号「Research 登记为 serves 采用面成员」候选；把与 34 号、04 号的边界写进对应候选，并在 33 号中回指 02 §6.4 既有判据而不改该判据。

## 实测

**取证面清点结果**：33 号的来源面在系统层并不只有外部 HTTP(S)——「适用条件」第 2 项、§6.1 必需输入 2、§9.1 已证实条件 1 允许「已确认存在的文档」，§10.1 逐字摘录第 1 项允许「文档路径」。但 §11.1「每项事实性声明须附稳定来源引用」与 §11.2「S1/S2 编号在对象创建时写入 Research 对象 frontmatter 的 `urls[].ref`」把引用闭环绑回 24 的 `urls`，而 24 §10 与 02 §7.1 更把 `urls` 限为外部 HTTP(S)。

**承载侧不止一条约束**：§12.1 承载载体与 §12.3 目标来源把结论承载绑在 Research；§13.2 约束证据形态；§14.2 已把调研结论的后续去向交由 02 §6.4 公共判据判定次序；§15.2 要求每项 confirmed 证据附逐字摘录、来源 URL 与锚点。

**目标锚定接法**：链条是 Goal（单例）→ SubGoal（多例）→ `serves`。`serves` 已由 Spark、WorkCase、DevLog 三家采用，解析口径在 28 §12.3；Research 加同一字段即接入。目标级不需要新字段，反向投影由 `parent_goal` 与 `serves` 反查派生（25 §11、28 §8.1）。

**交付**：33、24、29、28 四份规范候选及与 34 号、04 号的边界衔接，另附五项裁定记录（设计分叉四项 + 结论承载走向一项）。

## 结论与边界

调研吸收的外部调查与内部信息吸收两职能的规范候选已产出（33/24/29/28 四份候选＋五项裁定记录），但结论承载走向仍待 Human 裁定：33 §12.1 把承载绑在 Research、29 §6.3/§8/§10.1 载明 DevLog 源自内部过程不调查外部世界，两者直接冲突。候选已产出、承载冲突未裁前不改 33 号承载条款，也不预设任何一侧。

**边界**：本条目止于规范候选，**不含** Code 与 Web 实现；未改 00 号根定义与 02 §6.4 归属判据表；未新建事实类型。结论承载走向（扩 33 号承载条款为按 02 §6.4 分流，或维持承载单一）属 Human 裁定事项，未裁前两条路都未铺。
