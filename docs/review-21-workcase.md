## 二、缺陷清单（分级 + 依据 + 复现）

### D1 【已证实缺陷 · 高】attempt 令牌与冷恢复的宿主实装为悬空委派
- **依据**：21 §10.4 行 219 声明「attempt 的宿主实现、锁语义与接入由 08/09 承接，本文只定义对象上必须存在的字段、不变量与恢复判据」，并称这是「最大跨规范接缝风险」。但实测 08/09 **完全无 attempt/锁/冷恢复内容**：
  - `grep -rn 'attempt' specs/08-*.md specs/09-*.md` → 零命中。
  - `grep -rni '令牌\|冷恢复\|锁\|lock\|heartbeat\|token' specs/08/09` → 仅 08 行 102/164 的「冷启动引导/注入」（system-prompt 注入，非 attempt 冷恢复）。
  - 02 §18 行 190 仅说「attempt、锁、冷恢复和宿主事件所需的术语、接入与实现由 08/09 按各自来源另行定义，02 不预设其语义」——这是**待定义**声明，不是实装。
  - 04 行 360 仍声明「授权包结构与冻结语义待 WorkCase/授权承接规范定义」。
- **问题**：21 把类型侧字段（`attempt` 对象、`attempt_id` 单调分配、至多一个活跃 attempt、孤立 attempt、heartbeat）定义为契约，却把「谁分配 attempt_id、锁如何防并发、冷恢复如何核对副作用」全部推给尚无任何内容的 08/09。按 03 §5.3 / 03 §11.2 扩展规则第 4 条「字段、状态或关系扩展必须说明消费方、迁移影响、旧对象兼容、机械实现与未验证范围，不因 Code 已存在而反向取得规范效力」——此处**连「Code 已存在」都没有**，是纯悬空委派。
- **后果**：21 定义的 `attempt` 字段契约（如「至多一个活跃 attempt」「孤立 attempt 核对副作用前不续跑」）在当前宿主中**无可执行的机械保障**，其声称的 V6「工作接续」与 HV2「返回后从当前状态继续」依赖的锁/冷恢复能力**未落地**。
- **复现**：

  ```
  grep -rni '令牌\|冷恢复\|锁\|lock\|heartbeat' specs/08-*.md specs/09-*.md
  ```
- **建议**：要么在 08/09 实际定义 attempt/锁/冷恢复契约（并登记 Human Gate），要么在 21 中把 §10.4 降级为「类型侧字段已定义，宿主实装待 08/09 立项，当前 V6/HV2 的接续能力未兑现、须如实披露为 gaps」，不得把悬空委派写成已分工完成的接缝。

### D2 【已证实缺陷 · 中】`open → draft` 状态倒退是家族中唯一的反向转换，与「终态不直接重开」纪律相悖
- **依据**：21 §9.2 行 175 定义 `open → draft`（C2 局部重批）为合法转换，且 §9.2 行 177 仅约束「closed 后不得回到 draft/open」，即 open 可回退到 draft。对照兄弟类型状态机：
  - 20 Spark：闭集 open→implemented/discarded，行 166「终态不直接重开」。
  - 22 ADR：active→retired，行 166「终态不重开」。
  - 25 Goal：active→achieved，行 115「不存在的转换：不退役、不 superseded、不重开」。
  - 26 Friction / 23 Pitfall：均为严格正向终态。
  21 是唯一允许**非终态回退**（open 倒退到 draft）的类型。
- **问题**：21 辩称这是「授权失效局部重批」而非整单重走（行 175、210），逻辑上可理解（授权指纹失配须重新批准）。但：
  1. 这与 03 §10 行 338「类型来源必须定义状态集合、合法初态、转换、终态」及全家族「终态不重开」的强纪律形成**可见例外**，应在 §9.2 显式论证「为何本类型允许非终态反向转换而兄弟类型不允许」，目前仅在行 175 一句带过。
  2. `open → draft` 后 `attempt` 作废（行 175），但已发生的执行副作用如何与「回到 draft（待批准）」协调——draft 语义是「计划待批准、不得有 attempt/result」（行 166），而局部重批要求「保留已取得的结果证据为历史记录」（行 175）。**draft 状态定义（行 166：result/attempt 不得出现）与局部重批保留 result 证据（行 175）存在内部张力**：回到 draft 后到底能否携带历史 result？字段不变量（行 156 `result` 出现 ⇔ `status=closed`）在 open→draft 路径下如何处置已取得的 result 证据，21 未给出明确字段级规则。
- **后果**：状态机自洽性存疑；机械实现时 `result` 字段在 draft 态的出现/禁止条件与「保留历史证据」诉求冲突。
- **复现**：
  ```
  sed -n '160,177p' specs/21-WorkCase-工作项.md
  grep -n '终态不重开\|不重开\|不直接重开' specs/20-Spark-火花.md specs/22-ADR-决策.md specs/25-Goal-项目目标.md
  ```
- **建议**：明确 `open → draft` 后历史 result 证据的承载位置（如独立 `history` 字段或留在正文），并修正 §9.1 draft 语义与 §8 字段不变量的措辞，使「draft 禁 result」仅约束新建 draft、不约束重批回退 draft；或在 §9.2 增加与兄弟类型纪律差异的论证。
