## 3. 论证

### 3.1 为什么这不是「为 Web 呈现方便」

§19 第 9 条的立法意图（由条款自身措辞可读）是禁止**为了显示效果**而扩展数据模型。本提案的动因不同：

- `specs/02` §15 把独立复核列为**制度**，其判据原文为「对象、基线、方法、覆盖、未覆盖、发现和**保证边界**清楚；**发现得到处置**」；
- `specs/01` §12.2 规定复核「必须说明对象、准确候选、范围、依据、实际攻击方向、发现、未覆盖范围和保证边界，**不得只报告「已审核」或「无问题」**」；
- 但 `specs/03` §6.1 规定「不记录读取、拒绝、no-op…」——**复核是只读动作，因此当前在对象上完全无痕**；
- 结果是：02 §15 的判据**没有机械锚点**（视角 C 独立核实结论：「Q5『发现得到处置』无机械锚点」）。

因此本提案的动因是**让制度判据可获得承载**，而非呈现便利。它带来 Web 可见性是**结果**，不是**目的**。

### 3.2 为什么不是被红线所禁的「完整日志字段」

三处红线中，**只有两处**以「完整」为限定语，且限定范围不同：

| 红线条文 | 「完整」修饰什么 | 本提案形态 | 判定 |
|---|---|---|---|
| 21 §19.4 / 32 §16.3 | **完整「日志字段」** | 有界概要数组 | 「有界数组是否算日志字段」——**须裁定** |
| 02 §23.3 | **完整「消息」**（「思考链、运行日志、第二状态账本」为**不受限定的独立并列项**） | 按次累积、带署名的第二本账本 | **触「第二状态账本」——须裁定**（见 §2 更正说明） |

**原提案的错误论证（已撤回）**：初稿称「三处红线均以『完整』为限定语」，据此把 02 §23.3 判为不冲突。**该论断断章取义**——「完整」在 02 §23.3 中只修饰「消息」。撤回理由与影响见 §2 更正说明。

**原提案援引的 `evolution` 先例（已降级，不再作为证明）**：初稿称 `specs/20` §8 的 `evolution` 是「决定性同类先例」。经独立对抗审核回读，**该类比不成立**，三处不可比：

1. **红线不同（决定性）**：`specs/20` §18 的八条红线中，**没有**「不为执行过程建完整日志字段」，也**没有**「不因 Web 呈现方便增加字段」——而这两条恰是本提案的障碍。**Spark 从未受这两条约束，其 `evolution` 的合法性对 WorkCase 无证明力。**
2. **类型定位不同**：Spark 是「方向主线/悬置层」，WorkCase 是「授权执行层」（21 §5）；「有界性」在两类红线语境下权重不同。
3. **语义目的不同**：`evolution` 记「关键语义转折」（方向变化），`reviews` 记「复核结论」（工作审查）——同构的是**数组形态**，不是**规范上的可类比性**。

**保留的有限价值**：`evolution` 仅可作为「**LDVH 此前已接受过有界摘要数组这一数据形态**」的存在性例证（precedent of form），**不得**作为「不触红线的证明」（proof of permissibility）。**「判定分界在于有界性与粒度」是起草者的理论，规范原文无此分界**——不得冒充规范结论（00 §7.1）。

**反例（原提案援引错误，已撤回）**：初稿曾援引 `specs/21` §9.2 的 C2 重批作为「结论可入对象」的先例。**该援引方向完全相反，已撤回**：§9.2 原文是「已取得的核对证据**不留在对象字段中**，而是写入当次 `change_log` 条目的语义摘要」——它论证的正是**结论不进对象字段**，与新建字段的路径**相反**。

**由此暴露的真正问题（必须正面回答，不得回避）**：既然 §9.2 已经把「记录 `criteria_checks` 快照结论」的机制安排在 `change_log` 的语义摘要中，本提案就必须回答：**为什么不能继续用 `change_log` 承载复核结论，而必须新建字段？**

Human 的裁定给出了答案（§1 R5–R7；此处指「专门的复核字段」）：`change_log` 回答「**发生过一次写入**」，而复核结论的问题是「**这次复核的结论是什么**」，二者**基数与语义都不同**——三次复核会产生三条 `change_log`（若各引发写入）或零条（若复核是只读，按 03 §6.1「不记录读取…不产生流水」），而 `reviews` 必须**精确对应三次复核**。

**这一点是分立的核心理由，也是本提案的命门**：`change_log` 的条目数是「写入次数」的函数，而复核次数与写入次数**不存在一一对应**（复核可以只读、可以一次写入含多次复核）。**故 `change_log` 在结构上无法承载「第 N 次复核」这一语义**。这不是偏好问题，是基数不匹配。

**该论证的两个薄弱点（起草者自查，如实登记）**：

1. **若每次写入 `reviews` 也恰好产生一条 `change_log`，则二者基数相同，论证削弱。** 反驳依赖「一次写入可同时追加多项复核」这一情形；但该情形**规范未规定**——若实现约定「每次复核独立写入」，则一目了然的一一对应成立，`change_log` 摘要即可承载，**本提案的分立理由即不成立**。
2. **「复核可以为只读」这一前提须确认。** 03 §6.1 只说「不记录读取…不产生流水」，但复核是否可以**完全不引发任何写入**（即纯只读复核），取决于实现，**规范未明确**。若复核在实现上总是伴随某种写入（如更新 `attempt.heartbeat_at`），则「零 change_log 的复核」不存在，论证同样削弱。

**结论**：基数不匹配论证**成立与否取决于实现约定**，而非规范原文。**故本项须 Human 裁定（§5 未决项 3），本提案不声称该理由已自足。**

**若该理由不被接受**，则本提案不应成立——应改为「把复核结论并入 `change_log` 摘要」，但那会触 `specs/03` §15 第 6 条（不把 change_log 扩张为责任流水），且无法表达多次复核，故本提案认为该退路不可行。**此判断须 Human 确认。**

### 3.3 防作弊的强度与边界（不得夸大）

Human 要求「机械式获得复核代理的供应商与模型进行签名，防止 ai 作弊」。经核实，该机制**部分已存在**（`plugin/lib/signature-channel.js`），但**「复核子代理能自签」这一关键前提尚未证实**——本节如实区分已证实与未证实。

**已证实（机械可查）**：

- 签名**不由 AI 提供**，由 Code 从会话记录取得（`currentRouteValues(sessionPersistence, agent)`，`session-signature.js` 第 104–107 行，经 `agent.session.header` 定位 jsonl）；
- 载体带**模块私有 Symbol 品牌**，手工构造的 `{provider, model}` 一律解析为 `null`（`resolveAuthoritativeSignature`）；
- 取不到签名时**拒绝写入**（`requireAuthoritativeSignature` 返回 `signature_unavailable`），而非静默落无署名记录；
- 故对**主控自身**的写入：主控无法自填、无法用部署默认值替代。

**未证实（不得当作已成立，00 §7.1 / 21 §15.2 同款纪律）**：

- **子代理调用 LDVH 工具时，`exec.agent.session.header` 解析到的是子代理自己的会话，还是主控的会话？** 该行为取决于 DSH 宿主运行时的 `exec` 注入，**不在本仓库代码内**。本仓库代码（`signature-channel.js`、`session-signature.js`、`ldvh-tools.js` 的 `exec` 参数）**不足以支持**「子代理必然自签」这一断言。
- 独立对抗审核明确指出：提案初稿把该断言作为**已成立事实**陈述，同时又在 §5 未决项把「是否允许子代理直调写入」列为**待裁**——**自相矛盾**。已更正：本项**降级为待验项**，与 §5 未决项 6 合并（第二轮复审发现初稿此处误写为「未决项 4」，编号已更正）。

**若子代理不能自签**（即署名回落为主控）：签名的防作弊价值**大幅下降**，仅剩「记录主控自身模型」；且若「独立复核执行体」与主控**为同一模型**，署名与自评**不可区分**，防作弊价值**趋零**。

**必须显式声明的能力边界（防止超范围声明，00 §7.1）**：

即使签名完全成立，它证明的也只是「**某个 provider/model 写入了这条记录**」，**不证明**：
1. 复核确实独立（独立性由 `specs/02` §15 的「独立、继承、新鲜、对抗执行体」与子代理上下文隔离承接）；
2. 复核确实审阅了全部证据（内容质量受纪律约束，见下）；
3. 复核结论正确、或整体工作完成（`specs/02` §15 边界：「复核或校验通过不自动等于整体完成或授权扩张」）。

**Human 原始意图的稀释必须显式声明**：Human 说「防止 ai 作弊」。本机制实际能防的是「**冒名**」（伪造 provider/model），**不能防「走过场」**（写一句空泛「无问题」）。见 §3.4。

**完整防线是三层**：独立性（隔离执行体）→ 内容质量（见 §3.4，**不是** 01 §12.2 的八要素）→ 签名封条（防冒名）。签名是**最后一道封条，不是全部防线**。

### 3.4 内容质量约束（原提案范畴错位，已更正）

**原提案错误**：初稿称「内容质量由 `specs/01` §12.2 的八要素承接」。**该援引属范畴错位**——01 §12.2 的八要素（对象、准确候选、范围、依据、**实际攻击方向**、发现、未覆盖范围、保证边界）是**规范独立对抗审核**的要求，对象是**规范文档**；WorkCase 上的复核是**工作复核**，制度归属是 `specs/02` §15，其判据是**七要素**（对象、基线、方法、覆盖、未覆盖、发现和保证边界）——**两套要素集不同**（前者含「准确候选/依据/实际攻击方向」的规范审核语义）。

**因此本提案的 `reviews.summary` 内容约束应锚定 `specs/02` §15 的七要素，而非 01 §12.2 的八要素。**

**由此产生一个必须解决的粒度矛盾（见 §5 未决项 9）**：七要素（尤其「覆盖/未覆盖/保证边界」）**无法压缩进一句话**。若 `summary` 只写一句话，则它无法承载 02 §15 判据，§3.1 的「机械锚点」动因落空；若它要承载七要素，则**不再是「概要」**，与 Human 裁定「只留概要」冲突。**本提案不回避该矛盾**，将其列为须 Human 裁定的未决项。

## 4. 字段设计（候选）

拟插入 `specs/21` §8 字段表，位置在 `attempt` 之后、`result` 之前（按生命周期时序）：

```
| `reviews` | array | 条件 | 复核结论摘要流水 | 每次独立复核后追加一项：`{at, provider, model, summary}`；`at`/署名由 Code 托管；`summary` 的**最小要素集待裁定**（见 §5 未决项 9——「一句话」与「承载 02 §15 七要素」存在粒度矛盾，本提案不预设结论）；**详细复核内容不入对象**（归会话 transcript，21 §19.4）；上限 N 项（待定，见 §5 未决项 4）；仅记录**实际执行**的复核，未执行不得伪造；达到上限后的行为见 §5 未决项 10 |
```

> **该字段定义目前不是可实施的最终形态。** Human 已裁定「**复核概要是节点要记录，复核详情…不用记录**」（§5.2），故字段粒度方向已定：**只存概要**。但 `summary` 的最小要素集（未决项 9）与三条红线的适用性（未决项 1/2）仍未终局，此处给出的是**待终局裁定的候选形态**，不得据以实施。

> **粒度边界（据 Human 裁定，须写进规范正文）**：入对象的是**节点概要**（发生了什么复核、由谁做、结论为何）；**复核详情不入对象**（归会话 transcript，与 21 §19.4、32 §9「过程在 transcript 与 Git」一致）。这条边界是 HV3「关键节点可回读核对／不要求保存节点之间的完整过程日志」的直接落地。

**与 `change_log` 的分工**（Human 明确要求区分，须写进规范正文）：

| 维度 | `change_log` | `reviews`（本提案） |
|---|---|---|
| 记什么 | 「**发生过一次写入**」+ 本次修改的一句话语义摘要 | 「**第 N 次复核的结论是什么**」 |
| 触发 | 每次实际 canonical 修改，恰好一条 | 每次实际执行复核，恰好一条 |
| **基数来源** | **写入次数**的函数 | **复核次数**的函数 |
| 二者是否一一对应 | **否**——复核可只读（按 03 §6.1「不记录读取…不产生流水」，此时零条 change_log）；也可一次写入含多次复核 | — |
| 内容 | 本次修改的语义摘要 | 复核结论摘要（发现 + 处置 + 未覆盖 + 保证边界） |
| 署名 | Code 托管（已有） | Code 托管（同机制，但见 §3.3 未证实项） |
| 是否可多次 | 是 | 是 |
| 关系 | 写入 `reviews` 时**同时**产生一条 change_log（两维度并存，不互替） | — |

**该分工的根据是基数不匹配**（§3.2）：`change_log` 条目数是「写入次数」的函数，而复核次数与写入次数**不存在一一对应**，故 `change_log` **在结构上无法表达「第 N 次复核」**。这是本提案分立的核心理由。

**须注意的既有反例**：`specs/21` §9.2 的 C2 重批**确实**让 `change_log` 承载了「`criteria_checks` 快照结论」——即 `change_log` **并非完全不能承载结论**。本表因此**不主张**「change_log 只记事件、绝不记结论」，只主张「**change_log 的条目基数由写入驱动，无法表达独立于写入的复核次数**」。原提案初稿的绝对化表述已更正。

**正文承载**：本提案**不新增 H2 节**。`reviews` 为 frontmatter 字段，其详情页呈现归 `specs/10` §5.3「显示该对象的变更历史（摘要形态）」（注意：是 §5.3 语义详情，**不是** §5.4 扩展阅读——§5.4 管跨对象脉络）。
