## 2. 当前项目理解

### 2.1 项目定位

LDVH v5 是面向长程 Vibe Coding 的治理与协作系统，目标是让工作更稳定、更可控、更高效。项目以 DSH 原生插件为统一交付形态，并由四种方式交付价值：AI 工作引导、Helper 确定性执行、Web 信息呈现、Git 机械守护。

项目要共同对治三类根问题：

- AI 的概率性、不稳定、漂移与遗忘；
- Human 的规划模糊、灵感流失、进展断续与经验离散；
- Human 与 AI 之间的意图、授权、判断和结果交付错位。

### 2.2 权威与承接关系

- `specs/00-理念与构成.md` 是 Human 根契约，也是八维数量、名称、顺序和根职责的唯一权威。
- `specs/02-八维工作模型基础规范.md` 承接八维的职责、判据、机制指向、协同、暂停、接管、恢复与交还边界。
- `specs/03`、`specs/04` 分别承接事实公共模型和行动模板公共结构；它们不能重新定义八维。
- Helper、事实源/Git、管辖、DSH 接入、Code、Web 由 `specs/05–10` 分工承接。
- `docs/eight-dimension-action-baseline.md` 是八维真实行动的候选设计基线，当前性质仍是开发输入，非规范、非事实对象。
- 本讨论文档与其他 `docs/` 内容一样，仅承载讨论和设计输入，不建立第二权威。

### 2.3 当前建设阶段

当前基础规范 `00–10` 已建立；事实类型规范 `20–24`、行动模板规范 `30–38` 及 Helper/Code/Web 等实现尚未完成。当前阶段原计划是先确认八维真实行动展开基线，再据此推导事实类型和行动模板，避免先造 Schema 或把八维仪式化。

## 3. 当前八维基线

| 维度 | 根职责 | 当前关键判据 | 主要防误用边界 |
|---|---|---|---|
| 读 | 取得当前工作所需且来源明确的信息 | 已用信息可回指来源；候选、片段、全文、已读与未读可区分 | 读取成功不证明理解、适用、授权或完成 |
| 写 | 把已经明确去向的内容受控写入，并核对实际结果 | 范围、授权、基线、实际变化、回读与未验证范围可区分 | 写不决定是否值得沉淀；工具成功或 commit 不证明上层完成 |
| 遵守 | 识别并落实适用的规则、事实、决定和授权 | 约束真实改变行动；适用条件、授权和禁止动作可回指 | 事实和经验不成为规则源；遵守成立不等于行动完成 |
| 审议 | 把 Human 意图经扩散和约束收敛为方案 | 问题、反例、替代方案、排除范围和未决取舍清楚 | 审议不自动产生授权，也不以扩散扩大目标 |
| 复核 | 依据既定目标、方案和成功标准检查实际工作和结果 | 对象、基线、方法、覆盖、发现与保证边界清楚 | 复核通过不自动等于整体完成或授权扩张 |
| 执行 | 由主控组织行动并形成实际结果 | 行动与目标、方案、授权一致；局部结果被主控整合 | 工具、测试、任务或 commit 完成不证明整体完成 |
| 反思 | 从目标、判断、行动、结果、摩擦和反馈中形成候选认识 | 候选可回指实际证据；偶发现象与可复用模式可区分 | 反思不自动产生规则、事实、授权或长期效用 |
| 沉淀 | 判断哪些认识和结果值得跨行动保留及其稳定位置 | 有消费对象、适用边界和明确去向；进入事实源须满足准入 | 对象数量、页面呈现或单次复用不证明效用 |

## 4. 八维共同原则

1. 八维是同一行动中的八类职责，不是八套流程，也不是必须依次通过的八个步骤。
2. 一个行动可以同时触及多个维度，可以并行、回跳，也可以跳过未触发的维度。
3. 主控按目标、风险和缺口选择最小充分组合，并对委派、工具结果、整合和最终声明承担不可转移的责任。
4. 相关、适用、授权覆盖和完成是需要分别核对的四层判断，不能互相替代。
5. 运行状态不自动成为稳定事实；跨行动保留的内容须先经反思形成候选，再由沉淀判断去向，最后由写维受控落位。
6. Human Gate 只承接 Human 决定，不替代技术验证、语义复核或整体完成判断。
7. Git Gate、权限、沙箱、宿主事件等属于横向机械保障，不归属于某一单独维度，也不替代主控判断。
8. 任何能力都必须区分设计意图、实现存在、环境接入、当前可用和实际验证；未经核验不得宣称已经成立。

## 5. 当前讨论焦点

以下内容作为首轮讨论议程，不代表已经决定：

### 5.1 模型本身

- 八维的职责边界是否足够清晰，是否仍存在重叠、空缺或命名歧义？
- “写”与“沉淀”、“审议”与“复核”、“反思”与“沉淀”的分界是否能在真实行动中稳定判断？
- “遵守”是否应只承接规则落实，还是继续同时承接事实、Human 决定和授权的适用落实？
- “执行”是否过宽，是否需要更明确地表达组织、委派、异常处置、验证和交还之间的关系？

### 5.2 组合与触发

- 如何定义“最小充分”的维度组合，而不重新制造复杂流程或审核仪式？
- 哪些场景需要强制触发特定维度，哪些只应由主控按风险判断？
- 八维之间转交时，哪些信息是不变量，哪些应保持轻量？
- 如何让低风险普通改动不被八维拖成重流程，同时让高风险工作不漏掉必要职责？

### 5.3 Human 与 AI 协作

- 哪些讨论点必须进入 Human Gate，哪些属于主控可自行实施的技术选择？
- Web 应如何让 Human 看见目标、依据、风险、未决事项和进展，而不把八维术语负担转嫁给 Human？
- 主控如何把多视角、子代理、AgentTeams 或外部 CLI 的局部结果收敛为一个一致交还？

### 5.4 反思、沉淀与长期价值

- 反思应在何时触发，怎样避免每次行动都强制复盘？
- 如何判断候选认识值得长期保留，并明确消费者、适用边界和退出条件？
- 如何观测事实库的净效用，而不以对象数量、页面展示或单次复用冒充 HV4？
- 如何建立查重、合并、替代、退役与日落机制，避免经验库只增不减？

### 5.5 规范、事实与行动模板的承接

- `20–24` 应如何从真实八维场景推导类型准入、状态、关系、召回、验证和退出？
- `30–38` 应如何描述维度组合、停止、分流、验证与交还，又不把八维写成固定步骤？
- 哪些八维机制需要 Helper 的确定性入口，哪些必须保留为主控的语义判断？
- 哪些内容适合 Web 呈现，哪些只应存在于规范、事实对象或运行状态中？

### 5.6 读维的信息范围与读取方案

- LDVH 的读只覆盖两类信息：管辖项目的事实对象 + LDVH 自己的规范源；不读全量对话历史或运行痕迹。
- 事实源以规范格式（Markdown 正文 + YAML 结构化字段）存储，信息源、人读界面与 AI 读界面是同一份载体。
- 读取方案候选：分层渐进读取（L0–L4 / F0–F4）+ Helper 确定性回指入口 + AI 语义消费判断；不以概率召回或向量检索自动裁决相关、适用或事实结论。
- 待深入：事实源增长后的定位与索引、本地全文/语义候选与 03 §8 边界的协调、Web 人机共读呈现、预热注入的宿主承载。

### 6.2 2026-09-15：读维的信息范围与读取方案

**Human 原始观点（关键信息）**

> LDVH 要管的只是管辖项目的事实对象以及 LDVH 自己的规范源；这些信息的读取有什么比较合适的方案？我们在讨论 LDVH 的读。这些事实源又是以规范的格式进行存储管理，方便人和 AI 共同阅读——这就是 LDVH 的核心了。

**主控理解与提炼**

- LDVH 的「读」范围被明确收敛为两类受控信息：① 管辖项目的事实对象；② LDVH 自己的规范源。它不读全量对话历史、运行痕迹或非受控内容——这是 LDVH 与 Hindsight（全量对话记忆 + 向量召回）在读取层面上的本质分界。
- 由于事实源与规范源都以规范格式存储，**信息源、人读界面与 AI 读界面是同一份载体**，不需要为 AI 建立第二套隐藏索引或投影：Markdown 正文给人读，YAML 结构化字段给 AI/机械确定性解析，载体即 Git 仓库内普通文件（可 diff、可溯源、可回退）。
- 因此「读」的合适方案不是概率召回/向量检索主导，而是：**分层渐进读取 + Helper 确定性回指入口 + AI 语义消费判断**。项目现有基线已为此提供骨架：
  - 规范读取 L0–L4（发现→概览→关系→规则切片→全文），来源 `01 §10` 与 `01.Att.03 §4`；
  - 事实召回 F0–F4（发现→卡片→候选→全文→来源展开），来源 `03 §8`；
  - Helper 确定性读取入口（`read-specification-candidates` / `read-specification-content` 与事实读取操作），来源 `05 §9`；
  - 机械结果（候选命中、机械有效、文本命中）不自动裁决相关性、适用性或事实结论，语义消费判断保留给 AI（`03 §8`）。

**讨论形成的边界与共识候选**

1. LDVH 的读只管理「事实对象 + 规范源」两类受控信息，这是读维的作用域。
2. 规范格式（Markdown + YAML）是 LDVH 人机共读的核心：同一载体同时服务 Human 与 AI，不建第二权威投影。
3. 读取方案以「分层渐进 + 确定性回指 + AI 语义判断」为主，不以向量/概率召回自动裁决。
4. 基于此边界，当前并不需要引入 Hindsight 类外部记忆服务；LDVH 已把信息收敛到人机共读的规范格式，「读」就是读文件 + 分层 + 回指。

### 6.3 2026-09-15：Hindsight 的价值及其与 LDVH 读维的边界对照

**Human 问题**

> Hindsight 本身的价值是什么？

**主控分析（结合调研与当次会话中实际接触到的 Hindsight 工具形态）**

Hindsight（Vectorize，[GitHub: Agent Memory That Learns](https://github.com/vectorize-io/hindsight)）解决的是**编码代理的「无记忆」缺陷**——把「项目过去知道的东西」在每次全新会话里自动带回来，且不是靠人记，而是靠系统自己学。价值拆成四点：

1. **跨会话连续性（最核心）**：编码代理每次会话都是全新上下文窗口；Hindsight 把决策、约定、踩过的坑从「会消失的窗口」搬到持久存储，新会话自动召回。直接对治「AI 会遗忘」。
2. **从痕迹自动提炼成知识**：gitlog seed（读 git 历史）+ 自动摄取会话 + 持续整理/更新/淘汰的知识页（curated pages），即「会学习」的含义；[DSH 集成博客](https://hindsight.vectorize.io/blog/2026/08/14/deepseek-harness-persistent-memory) 即面向 DSH 的持久记忆形态。
3. **降低「重新发现」成本**：压缩、换会话、换成员后不必从头读代码、重推决策；[混合检索（全文+语义）](https://hindsight.vectorize.io/blog/2026/07/28/migrate-agent-memory-off-vector-database) 让「过去知道的」快速回到「现在需要的」。
4. **记忆的分层时效**：git 决策史、会话经验、持久知识页三层各归其位。

**价值边界（对本项目最有意义的部分）**

Hindsight 是**记忆服务，不是治理系统**：它擅长「让 AI 想起」，但不解决「该做什么、边界在哪、谁决定、如何验证」（授权与职责问题）、「想起 ≠ 遵守」（候选可能噪声、过时、概率性，仍需判断）、以及「受控写入与可信」（它低门槛摄取一切，而非受控写、可回指、有权威）。

**对照结论**

- Hindsight 解决「AI 会忘」；LDVH 读维解决「AI 要读对、读可信、读有边界」——前者是低成本想起，后者是受控读取 + 遵守。
- 印证 6.2 的边界：LDVH 信息已收敛到人机共读的规范格式，读 = 读文件 + 分层 + 回指；Hindsight 的「自动摄取一切 + 自动提炼」恰是 LDVH 刻意不依赖的能力。两者可互补但不等价：LDVH 不引入 Hindsight 式服务，不等于否定其「持久记忆」价值，而是选择以受控、可回指、有权威的方式达成同类目标。

### 6.4 2026-09-15：Hindsight 与 LDVH 读维是否可以并行

**Human 问题**

> 两者可以并行吗？

**主控分析**

可以并行，但**不是「并列的两套权威」，而是「分层定位、各管一段」**：把 Hindsight 严格放在「候选/线索层」，LDVH 事实源放在「权威/依据层」。

1. **为什么能并行：职责不重叠**。Hindsight 补 LDVH 刻意不做的部分（全量对话、灵感线索、低成本想起）；LDVH 补 Hindsight 不做的部分（受控、可回指、权威、遵守）。一个解决「AI 会忘」，一个解决「读对、读可信、读有边界」。

2. **并行必须守的三条红线**（不守则违背 LDVH 核心）：
   - **候选不自动进入判断结论**：Hindsight 输出只是候选/提示；影响判断、授权、验证、交还的信息必须回到 LDVH 事实源做 F3/F4 精确读取 + 受控验证（与 `03 §8` 一致）。
   - **不得反向写入事实源**：事实只能经受控入口（写维）落位，外部记忆的「顺手记录」不能绕过受控写入成为事实对象。
   - **事实源为准，记忆为线索**：冲突时以事实源为准（`00 §3.3`/`03 §7` 单一权威载体），记忆只提示「去核对事实源」，不做漂移仲裁。

3. **并行的形态对应 LDVH 已预留的「事实预热」槽位**（`03 §8.2`：预热只交付带来源与指纹的候选/卡片/恢复入口，不替代 F3/F4 精确读取）。但注意对接差异：LDVH 预热要求候选带来源与指纹，而 Hindsight 记忆指向 git commit/会话轨迹而非事实对象稳定引用，需补一层映射。

4. **现实建议：当前阶段不引入**。事实源规模尚小，读 = 读文件 + 分层 + 回指成本足够低，没有「想不起来」的实际痛点；并行会引入双源漂移、上下文预算、维护成本和「第二权威投影」风险。等到事实源增长、跨会话找回成为真实痛点时，再按「预热候选层 + 事实源权威层」分层方式评估引入，并守住三条红线。

### 6.5 2026-09-15：无限 AI 前提下本地构建 Hindsight 式技术还剩什么成本

**Human 问题**

> 假设我有一个无限量的 AI 可以用，本地构建这样的 Hindsight 这样的技术还有什么成本？

**主控分析**

无限 AI 只免掉「生成」成本，免不掉「保证正确、保持可信」的成本；且会把成本从生产端推向筛选与验证端。剩余成本清单：

1. **机械性基础设施**：向量存储/索引/元数据、摄取管道（git log 解析、会话捕获、去重、分块）的持续维护——写一次容易，跟 DSH 升级长期维护才是成本。
2. **召回质量与评估**：精确率/召回率调优、相关性校准、回归测试；AI 能生成候选，但不能替主控做质量评估。
3. **知识页治理（只增不减是陷阱）**：无限 AI 使生成近乎零成本 → 海量积累、只增不减、迅速陈旧；合并/拆分/退役/日落、查重、矛盾检测成为主要成本。对应 LDVH 沉淀维与 HV4：产出越便宜，筛选与淘汰越贵。
4. **信任与防自欺（核心，AI 无法自我免除）**：无限 AI 只会更快、更自信地犯错；记忆漂移、自动写入的错误内容、同源自证必须靠外部机械机制（来源、指纹、回读、矛盾检测、单一权威）约束——即 00 §1 第一句「AI 不可靠，只能依靠外部的制度、机械检查和多视角复核」。
5. **上下文预算与注入工程**：token 免费但上下文窗口仍是有限物理资源；决定注入什么、何时、多细是持续工程成本。
6. **集成布线 + 迁移**：与 DSH 执行循环的 hook/pre-step/Helper 布线随宿主升级；embedding 模型演进触发全量重嵌入。
7. **人的验证成本**：系统越自动，Human 越难信任；要么机制可验证（额外设计），要么人永远要再核（隐性成本转移给 Human）。

**结论**

无限 AI 让「生成」免费，于是真正的成本集中在「维护正确性、防止漂移、防止自欺、筛选净效用」——这几项恰好全部落在 LDVH 八维职责内（写=受控落位、遵守=约束生效、复核=验证、反思/沉淀=筛选与退役）。即便 AI 无限量，本地构建 Hindsight 式技术也只剩一个真正成本：把「AI 不可靠」制度化地兜住；而该制度化兜底正是 LDVH 的存在理由，不是可省成本。

### 6.6 2026-09-15：用 AI 自动处理散落在聊天里的内容（方法澄清与链路）

**Human 澄清（关键信息）**

> 我的意思是用这个方法（无限 AI 自动处理）来处理散落在聊天里的内容。

**主控理解修正**

- 上一轮（6.5）理解偏差：用户不是要「本地再造一个 Hindsight 系统」，而是**用 AI 自动提炼散落在聊天里的内容**——把对话中零散的决策、想法、经验、共识从聊天记录中收拢、提炼、沉淀为可用内容。
- 按 LDVH 边界（00 §3.3、03 §8）：聊天/运行状态/过程数据不自动成为事实源。因此该方法本质是：**聊天 = 原始素材 → AI 提炼 → 输出候选认识（反思维产物），而非事实、规则或决定。**

**该方法与八维的链路**

1. 聊天原始记录（过程数据，非事实源）；
2. AI 自动提炼候选（反思）：聚拢散落观点，**必须带原文回指**（哪个会话、哪段话）；
3. 主控/人复核（复核）：检验提炼是否误读、漏读、过度概括、夹带幻觉；
4. 判断去向（沉淀）：值得留吗？进哪里？——事实对象（Spark/ADR/Pitfall/Study）、普通文档或不保留；
5. 受控写入（写）：经受控入口落位 + 回读；
6. 消费（读）：后续跨会话召回复用。

**无限 AI 下该方法的真实成本**

1. **筛选成本上移（核心）**：聊天大多为噪音，AI 提炼后仍须判断「哪些值得沉淀、进哪里」；提炼变便宜、筛选变贵。
2. **防自欺未消失**：最大风险不是提不出来，而是「提炼得很有条理但悄悄偏离原意」；提炼结果必须可回指原文并经复核。
3. **确认成本**：每个候选须确认「确实是当时说的、确实成立」，AI 免费也替不了该语义判断。
4. **沉淀位置判断**：进规范/事实对象/普通文档还是不留，属沉淀维语义判断，AI 提炼不自动产生去向结论。

**关键原则**

AI 负责把聊天「收拢成候选」（便宜、可无限做）；「值不值得留、进哪里、是否被曲解」仍是主控语义判断 + 受控落位（AI 免费也省不掉）。提炼输出永远是「候选 + 原文回指」，绝不直接当事实/决定用。

**实践佐证**：本讨论文档即该方法的 LDVH 最小实践——每轮保留 Human 原话、主控理解、共识、分歧与未验证范围，持续从聊天中提炼沉淀。

### 6.7 2026-09-15：内容二分——确定性集中的内容 与 散落的闲聊内容

**Human 观点（关键信息）**

> 一部分是确定性集中的内容，一部分是散落的闲聊的内容。

**主控理解与分类**

信息在 LDVH 中分为两类，分别对应两种不同的处理机制：

| | 确定性集中的内容 | 散落的闲聊内容 |
|---|---|---|
| 典型形态 | 规范源、事实对象（受控格式） | 聊天中的零散观点、想法、决策火花、经验 |
| 信息属性 | 有权威、可回指、结构化 | 无归属、碎片化、可能重复/矛盾/过时 |
| 处理方式 | 确定性读取（L0–L4 / F0–F4 / Helper 回指） | AI 提炼（收拢成候选 → 复核 → 沉淀） |
| 进入读维方式 | 直接读，来源明确 | 先经反思/沉淀转化为候选，再考虑落位 |
| 状态 | 事实源/规范源（稳定） | 运行状态/过程素材（不稳定） |

**关键：转化关系（单向管道）**

散落闲聊经过「AI 提炼 → 主控复核 → 沉淀判断 → 受控写入」后，可升级为确定性集中的内容（进入事实源）；一旦进入即脱离闲聊状态，改用确定性读取。因此：

- 闲聊是**输入端**，确定性内容是**稳定端**；
- 读维需两层机制：对确定性内容「读文件 + 分层 + 回指」（可靠、可验证）；对散落闲聊「先收拢再判断」（AI 提炼只是候选，绝不直接当事实）；
- 两者不冲突，因为**确定性内容的权威性恰好来源于"曾经过受控转化"**；未经过转化管道的闲聊内容，永远只能当线索、不能当依据。

**对读维的推论**

该二分进一步说明 LDVH 读维的第一输入通道（确定性内容）与第二输入通道（闲聊→候选）的分工：前者保证判断有权威依据，后者保证有价值的灵感/经验不流失；中间的分界线就是受控转化（沉淀→写→可回指）。

### 6.8 2026-09-15：闲聊内容的定位修正——可检索档案而非待沉淀候选

**Human 观点（关键信息）**

> 散落的闲聊内容，不需要验证价值，只是方便及时可以找到过去曾经聊过的内容。

**主控理解修正**

- 这是对 6.6/6.7 中「闲聊 → 提炼 → 沉淀 → 事实对象」转化推论的**收口修正**：散落闲聊内容不需要验证价值，不进入沉淀判定，其唯一意义是**可检索的聊天档案**——当需要时能及时发现「过去聊过什么」。
- 修正后的二分：
  - **确定性集中的内容**：判断依据，需受控写入/复核/回读，生命周期受管；
  - **散落的闲聊内容**：可找回的历史记录，不要求价值、不要求结构化、不进入事实源；随聊随存、原文留档、按时间/关键词/主题检索。
- 核心边界：「**找到**」≠「**作为依据**」。检索到一段过去闲聊只说明「当时说过这些」，不自动成为当前判断依据；要作依据必须再经受控转化（非闲聊本职）。

**承载方式（关键推论）**

按 LDVH「深度绑定 DSH 原生机制」原则，闲聊检索**不由 LDVH 自建**，而由宿主承载：DSH 已有会话轨迹能力（zstd JSONL + SQLite FTS5 全文检索、43 种事件类型，`docs/dev-memo.md` #18 已验证；轨迹是过程数据，不是事实源，只读聚合、不写事实对象）。

**最终图景**

- 确定性内容 → LDVH 受控读取（L0–L4 / F0–F4 / Helper 回指）→ 判断依据（LDVH 管）；
- 闲聊内容 → 宿主轨迹/FTS5 检索 → 找回「聊过什么」（DSH 管，LDVH 只管边界：检索结果不自动升级为依据）。

### 6.9 2026-09-15：闲聊定位的最终判断——"笔记而不负责"，以及该想法是否有价值

**Human 观点（关键信息）**

> 散落的聊天内容，也不需要沉淀什么的，就是聊过，就像笔记一样，不需要负责，只是需要方便快速找到。但我也不确定这个想法是否有价值，因为有价值的内容都变成了事实对象。

**主控分析：这个"不确定"是正确的直觉，分两个层面看**

1. **作为「要建的东西」——几乎没价值**。因为有价值的内容已变成事实对象，聊天存档里剩下的多是落选内容（被否备选、半成品、死胡同、一时闲聊）；为找回这些建一套系统，边际价值很低。且 DSH 已有会话轨迹 + FTS5 全文检索，宿主已免费提供「检索过去聊过什么」，LDVH 再建即重复造轮子（违反深度绑定宿主、不建第二机制）。
2. **作为「一条边界」——有真正的价值**。价值不在检索本身，而在给聊天一个明确身份：**聊天 = 可找到、不负责、非权威的记录；事实对象 = 负责、受控、权威的结论**。该边界双向保护：
   - 保护事实源不被污染：聊天中的半成品、矛盾想法、被否方案允许随便记、不要求负责，不会被迫格式化或被误当结论；有价值的才走受控转化，事实源保持干净；
   - 保护聊天不被滥用：「找到」永远不等于「作为依据」，防止把「当时聊过」当成「已经决定」。

**结论**

- 「有价值的内容都变成了事实对象」→ 对，所以聊天存档**不该**被当作有价值内容来源；
- 「就是聊过，像笔记，不需要负责」→ 对，这就是它的正确定位；
- 「只需要方便快速找到」→ 对，但该「方便」由宿主的 FTS5 轨迹检索承担，LDVH 无需建任何东西。

LDVH 不需要为实现「闲聊可检索」做任何实现，只需在边界声明「聊天记录可找但不负责、非权威」。该想法的真正价值是**没有功能价值**——它是无负担的暗影区，让权威区保持干净；这本身即回答了「是否有价值」的疑问。

### 6.10 2026-09-15：洞察——Spark 就是「记录有价值闲聊」的机制，AI 已做过整理

**Human 观点（关键信息）**

> 我其实想明白了，LDVH 的 v4 版本的 Spark 就是记录有价值的闲聊。当对话有价值，我就可以安排 AI 记录到 Spark 里，AI 本身就已经做过整理了。

**主控核对与确认（对项目既有基线的印证）**

- Spark 官方定位（`docs/dev-memo.md` #15，Human 已决定保留）：**「尚未形成确定承接位置的单一信息需求、发现、问题或缺口」**——正是「有价值的闲聊」的定义：聊出了新发现、新问题、新需求，但还没想好去向，先开 Spark 兜住。
- v4 实证（`docs/v4-problem-ledger.md`）：103 个 Spark，implemented 73 / discarded 20 / open 10，24 天 ≈4.3 个/天——Spark 正是对话价值的日常出口。
- v5 承接（迁移矩阵）：`20-Spark-火花` = 「候选议题的低摩擦承载」。

**闭环打通（收拢前几轮线索）**

```
闲聊（不负责、宿主 FTS5 可检索）
   │  Human 识别出「这段有价值」
   ▼
安排 AI 记录到 Spark（AI 本就有对话上下文，整理近乎零成本）
   ▼
20 Spark（事实对象，受控落位，低摩擦承载）
```

三个关键点：

1. **判定权在 Human**：闲聊→Spark 的触发是 Human「安排」，不是 AI 自动沉淀——守住「筛选成本归 Human/主控」（呼应 6.6）。
2. **整理由 AI 做且已做过**：AI 在对话中已有完整上下文，「记录到 Spark」只是把已理解的结论落成受控格式，整理成本趋近于零——「无限 AI 后唯一省不掉的是筛选，而筛选由 Human 一句话完成」的最佳形态。
3. **它就是 20 Spark 的本职**：不需要新系统——闲聊可检索靠宿主、有价值闲聊承接靠 Spark，两个现成机制一拼即是完整答案。

**对 v5 20 的直接设计输入（v4 两大病灶须修复）**

- **开前查重缺失**：同一问题多次开 Spark（价值审计 3 次、Hook 架构 3 次、署名字段 5 次）→ 20 需要开 Spark 前查重机制；
- **创建摩擦高**：穿越 7 份规范、23 条 Stop → 20 必须是快通道/低摩擦；否则「Human 一句话 + AI 已整理」无法立刻落位，违背 Spark 存在意义。

### 6.11 2026-09-15：读的骨架确认——规则源通道 + 事实源通道

**Human 观点（关键信息）**

> 那关键的还是在于如何读取上，读取分两部分：一部分是事实源，一部分是规则源，对不对？

**主控核对（与项目已定义机制一一对应）**

用户判断正确，且与项目已定义机制精确对应：

| 用户说法 | 项目机制 | 读的是什么 |
|---|---|---|
| 规则源（规范源） | L0–L4 规范读取层级（`01 §10` / `01.Att.03 §4`） | 「应该怎么做」——边界、义务、流程 |
| 事实源 | F0–F4 事实召回分层（`03 §8`） | 「现在是什么、过去决定/踩过什么」——依据、状态、经验 |

并且 `01 §10` 明确「规范读取 L0–L4 与事实召回 F0–F4 不混用」：读规则时读义务边界，读事实时读判断依据，两通道必须分开、不可拿错证据。

**两点精确化（不完全是两部分）**

1. **第三类：行动模板**（`04` / 30–38）——读「该场景怎么做」的可复用方法，介于规则与事实之间，读取入口独立（`template_key` / `definition_ref`）；可归入规则性一侧，也可单列为第三通道，由 Human 定。
2. **广义读还有宿主能力/运行状态**（08，能力发现）——非 LDVH 管辖内容读取，先排除在内容读取分类之外。

**「如何读」的核心机制（比「分几个源」更关键）**

1. **分层渐进**：不一次读全量，L0–L4 / F0–F4 按需展开，控制上下文爆炸；
2. **可回指**：每段信息可回指来源、行号、指纹（`completed/not_completed/gaps`）；
3. **机械确定性入口**：Helper `read-specification-*` / 事实读取操作，AI 不靠猜路径；
4. **AI 语义判断收尾**：机械命中不自动裁决，相关/适用/授权由主控判断。

**维度对应**：规则源喂给遵守维（边界与义务），事实源喂给判断维/复核维（依据与状态）；两通道最终汇入主控的语义消费，构成读维完整骨架。

### 6.12 2026-09-15：必须读 vs 选择性读；Helper 提供什么确定性、有 Helper 是否更好

**Human 问题（关键信息）**

> 哪些是必须读，哪些是 AI 选择性读？选择性读 Helper 又能提供什么确定性的内容呢？有 Helper 是不是比没有要好呢？

**一、必须读（最小集合，`01 §263` 最小引导 + Skill 路由卡）**

1. **00 根锚点（最小引导）**：身份块、§2 根方案、§3.1 八维、§4 Human 决定权、§5 AI 责任、§6 双轨价值、§7 防自欺/Stop/交还——会话/行动启动即注入；
2. **管辖判定**：`resolve-governance-scope`，进入受控执行前；
3. **适用行动模板**：候选 → 内容，动手前（受控执行单元）；
4. **条件性必须读**：召回时机成立时，全部 active ADR F1（长期决策/架构）、全部 active Pitfall F2（已知失败症状）——会话级预检。

关键：必须读 ≠ 全文，而是「最小引导 + 条件触发」；普通聊天、纯查询不触发事实召回，只取得规则引导（`03 §8.2`）。

**二、AI 选择性读（`02 §5.1` 最小充分机制）**

- 规范 L3/L4（规则切片/全文）：局部判断需要精确规则时按需展开；
- 事实 F1–F4（卡片/候选/全文/来源展开）：项目事实对当次判断必要、或精确引用稳定事实时；
- 行动模板全文/细节、更深来源证据。

选择依据：该行动的目标与风险实际需要哪一层；不需要就不展开。

**三、选择性读时 Helper 提供什么确定性**

1. **确定性定位**：不靠 AI 猜路径/文件名；`read-specification-content` 按精确 `responsibility_key` + `heading_path` 读取，重复/歧义标题拒绝而非选首匹配；
2. **确定性范围披露**：每次返回 `completed / not_completed / gaps`、来源视图、内容指纹、1-based 行号、分页/coverage/cursor——AI 始终知道自己读到什么、没读到什么；
3. **确定性分层**：L0–L2 候选、L3 切片、L4 全文，机制固定不混用；
4. **机械检查**：结构/语法等确定性校验；
5. **不替代语义判断**：Helper 返回「读到的」，不返回「该读的/读懂的」；相关/适用/授权仍由主控判断。

**四、有 Helper 是否更好**

- **是**（LDVH 立足点之一）：无 Helper 时 AI 用通用文件读取+猜路径，读到什么不可审计、不可回指，易拿错载体（把索引/缓存/Web 视图误当权威载体）；有 Helper 后读取变为确定性、可验证、可回指的机械动作——「AI 不可靠靠外部机械补偿」的核心落地。
- **守边界**（`05 §261` 反过度设计红线）：不要求每次普通求解/读文件/编辑都先过能力发现、完整 envelope、事实召回、Human Gate——只在来源和风险实际要求时调用。结论：**有 Helper 比没有好，但按需用，不仪式化**。

**一句话总结**：必须读 = 最小规则引导（防 AI 裸奔）；选择性读 = 按目标/风险的最小充分展开（防上下文爆炸）；Helper = 让选择性读变得确定、可回指、可审计（防拿错证据）；有 Helper 好，但按需用。

### 6.13 2026-09-15：Helper 是否只是"确定性搜索器"、是否阻碍、是否比 AI 自查询更好、如何读"要遵守什么规范"

**Human 问题（关键信息）**

> 在读取方面 Helper 变成了一个确定性搜索器，是这个意思吗？会产生阻碍吗？会比 AI 自己去查询更好吗？比如做某件事要遵守什么规范，Helper 怎么去进行读取？

**一、修正："确定性搜索器"方向对，但更准确是"确定性读取服务"**

`05` 定义两个不同确定性操作，均非模糊搜索：

1. `read-specification-candidates`：按 `spec_key`/`attachment_key` 列出候选（L0–L2 发现/概览/关系），只产生待解析候选，不产生规则资格（`01 §9.2`）；
2. `read-specification-content`：按精确 `responsibility_key` + `heading_path` 返回规则原文（L3 切片 / L4 全文），重复/歧义标题拒绝而非选首匹配，带 1-based 行号。

结论：Helper 不帮你「找」（搜索是 AI 语义判断），它帮你「按精确坐标取到你指名要的权威载体当前内容，并保证取到的是权威内容」。定位与取件是 Helper，该读哪段是 AI。

**二、会不会阻碍？——设计上明确不会，且刻意保证**

`05 §13` 红线第 1 条 + `05 §4.3` 双重排除：不要求每次普通求解、读文件、编辑或工具调用先经过能力发现/完整 envelope/事实召回/授权匹配/Human Gate；普通求解与不依赖 LDVH 能力的文件读写不因 05 存在而强制经过 Helper。**只有当内容属受控内容（规范/事实/模板）且 AI 要以其为判断依据时才走 Helper**；普通文件照旧用宿主原生工具，Helper 不挡路。

**三、是否比 AI 自己查询更好——分场景**

| 场景 | 谁更好 | 原因 |
|---|---|---|
| 读受控内容（规范/事实/模板）当依据 | Helper | AI 自读会猜路径、可能拿错载体（索引/缓存/Web 视图误当权威）、读不全不知情、无 gaps；Helper 保证取到权威当前内容、披露 completed/not_completed/gaps、可回指 |
| 读普通文件/代码 | AI 直接用宿主工具 | 无需 Helper 开销，05 不强制 |
| 判断该读哪个、读了有没有用 | 必须 AI | Helper 不替代语义判断；返回「读到的」，不返回「该读的/读懂的」 |

一句话：AI 自己查询 → 可能「以为查到了」；Helper → 「确定取到了，且告诉没取到什么」——这正是 LDVH 防自欺核心：把「读了、读全、读的是权威」变成可机械验证的事实。

**四、具体场景："做某件事要遵守什么规范"，Helper 读取链路**

1. 规则引导（00 根锚点已注入，确定受管动作）；
2. 管辖判定 `resolve-governance-scope` 确认受辖；
3. `read-specification-candidates` 列出相关 `spec_key` 的 L0–L2（身份/定位/范围/关系）——只答「有哪些可能相关」；
4. **AI 判断适用性**（Helper 不替做）：据定位/范围声明判断哪些真正相关；
5. 对命中规范 `read-specification-content`（`responsibility_key` + `heading_path`）取 L3 切片 + 行号，需要时取 L4 全文；
6. 若为受控执行单元，再 `read-action-template-candidates` → `read-action-template-content` 取模板步骤；
7. 遵守维把规则落成预检落实记录，使约束实际改变行动。

链路中 Helper 只做 3/5/6 的确定性取件，其余是 AI 与规范的语义工作。

### 6.15 2026-09-15：管辖判定是读的第零道闸门——管辖项目 vs 管辖范围，非管辖项目零干预

**Human 观点（关键信息）**

> 这里读取还有一个点，就是管辖范围判断，这个有点模糊。首先是要有个区别：管辖范围和管辖项目要区分开。非管辖项目的，LDVH 是什么都不做的。

**主控核对与分析**

读维此前讨论的是「怎么读」，用户补充的是更前面的「该不该读」——管辖判定是读的第零道闸门，任何 L0–L4 / F0–F4 / Helper 读取之前先过它。核对 `specs/07` 后确认两个模糊点：

1. **必须区分的两个概念**：
   - **管辖项目判定**：这个项目在不在登记列表 → `governed` / `not_governed` / `unavailable`（`07 §5.3`）；
   - **管辖范围（工作对象）**：LDVH 在这个项目里管什么 → Git 根 + `ldvh-base/`（事实源）+ `specs/`（规范源）（`07 §6`）。
   - 模糊感来源：操作名 `resolve-governance-scope` 用 "scope"（范围）命名，但实际判定的是「项目是否在列表」（项目资格）。建议后续明确：scope 判定 = 项目资格判定，范围定义 = 工作对象边界；命名可考虑更清晰表述。

2. **非管辖项目零干预（用户核心观点，`07` 语义完全支持）**：
   - `not_governed` → LDVH 对该项目零读取、零动作、零痕迹：不读规范源/事实源、不召回事实、不加载 Helper 受控操作、不套模板、不写事实对象、不做 Git Gate、不触发 Human Gate/Stop；
   - `unavailable` → 前置条件不可得，fail-closed 暂停（不是「不管」，而是「无法判定所以停」）。
   - 二者差别关键：`not_governed` 是正常退出，`unavailable` 是异常暂停；都不是「管」。
   - 一句话：LDVH 不是常驻监视器，只在登记过的项目里活动；对非管辖项目完全透明——防止 LDVH 越界侵入普通项目、不打扰非 LDVH 工作流的关键设计。

**对读维的推论**

读维小结应在「作用域」之前增加「第零道闸门：管辖判定」——先判 `governed/not_governed/unavailable`，再谈读什么、怎么读；非管辖项目直接零干预退出。

## 7. 共识、分歧与待定项

### 7.1 已有规范共识

- 八维是职责模型而不是八步流程。
- 单一主控 AI 对整体结果最终负责，委派和机械检查不转移责任。
- 稳定事实、运行状态、规范、行动模板和工具输出必须保持边界，不能相互冒充。
- 反思只形成候选认识，沉淀决定长期去向，写维负责受控落位。
- Human 决定权、Stop Conditions、验证与交还不能被技术实现稀释。

### 7.2 本次讨论新增共识

- LDVH 的读维作用域 = 管辖项目的事实对象 + LDVH 自己的规范源；不读全量对话/运行痕迹。
- 规范格式（Markdown 正文 + YAML 字段）是 LDVH 人机共读核心；信息源、人读界面与 AI 读界面是同一载体，不建第二权威投影。
- 读取方案以「分层渐进（L0–L4 / F0–F4）+ Helper 确定性回指 + AI 语义消费判断」为主，概率/向量召回不自动裁决。
- 基于读维边界，LDVH 当前不需要引入 Hindsight 类外部记忆服务。
- 闲聊内容定位：可检索、不负责、非权威；「找到」≠「作为依据」；检索由宿主 FTS5 承担，LDVH 不实现。
- 有价值的闲聊由 Human 判定并安排 AI 记录到 Spark（20）；AI 本就有对话上下文，整理近乎零成本；Spark 即「有价值闲聊」的受控承接位。
- 读维讨论已收束为独立设计输入文档 `docs/read-dimension-understanding.md`（覆盖作用域、双通道、四要素、必须读/选择性读、Helper 角色、Hindsight 关系、成本与设计输入）。
- 管辖判定是读的第零道闸门：先判 `governed/not_governed/unavailable` 再谈读什么；管辖项目（项目资格）与管辖范围（工作对象边界）须区分；非管辖项目 LDVH 零干预。
