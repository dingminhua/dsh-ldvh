## 三、三个**真实的**结构问题（按价值排序）

### 3.1 `01 §10` 与 `01.Att.03` 内容重叠

- `01 §10`（25 行）定义规范关系、读取层级与规则引导
- `01.Att.03`（63 行）承载「规范关系与层级表」——**关系与层级**正是 §10 的主题

**性质**：附件是 §10 的**授权展开**（可能合规），但两者**边界未在正文显式划定**，读者无法判断「关系定义看 §10 还是看 Att.03」。

**判断**：属**边界不清**，非重复。**修法**：在 §10 加一句「关系的完整字段表与层级定义见 `Att.03`，本节只定义其语义角色」——**一句话级**。

### 3.2 `03 §9`（106 行）与 05/06 的边界（**最值得看的一处**）

`03 §9` 是**全集最大单章之一**，含 8 个子节：共同前提／只读路径／无副作用草案／受控创建／CAS 更新／多对象边界／写后回读审计／部分结果与交还。

**而 `03 §3.2` 已明确声明**：第 2 项「LDVH CLI 的共同请求/响应 envelope……由 05 承接」、第 4 项「事实源与 Git 提交、署名 trailer 和提交 message，由 06 承接」。

**我机械核了概念分布**：

| 概念 | `03` | `05` | `06` |
|---|---:|---:|---:|
| `content_fingerprint` | 3 | 0 | 1 |
| `CAS` | 9 | 2 | 1 |
| `回读` | **27** | 14 | 7 |
| `fail-closed` | 2 | 0 | 0 |

**判断**：`03 §9` 的**语义层**（什么条件下读写成立、何时 fail-closed）**确属 03 职责**——它是"事实域的成立条件"。**但它有相当篇幅在描述操作程序**（如 §9.4 受控创建的步骤、§9.5 CAS 更新的流程），**与 05/06 的契约存在操作性重叠**。

**这**不是**「内容放错规范」，而是**「同一操作在语义层与契约层各写了一遍」**。**风险**：两处可能漂移（03 说 fail-closed，05/06 却说别的处置）。

**修法方向**（需进一步论证）：
- **A**：`03 §9` 保留**语义不变量**（成立条件、失败边界、授权边界），把**操作步骤**改为对 05/06 的**回指**
- **B**：维持现状，但在 `03 §9` 显式声明「操作程序以 05/06 为准，本节只定义其成立条件」

**我倾向 A**，但**必须先验证**：05/06 是否**真的**已完整定义那些操作步骤。**本次未验证**（见 §五）。

### 3.3 `04 §7` 预检落实记录（46 行）—— **唯一的真附件候选**

`04 §7` 定义「预检落实记录」的**公共字段名**。`04 §9.3` 扩展规则 3 明确**禁止**业务系统规范修改这些字段名。

**为什么它是附件候选**：它**本质是字段表**（字段名 + 类型 + 必填性 + 语义），符合 `01 §8.3` 的允许类型。**且** §9.3 已把它定为**不可改的公共契约**——正是附件适合承载的形态（纯结构化、机械可校验）。

**但**：46 行里**只有一部分是字段表**，其余是**使用规则**（何时填、谁填、不填的后果）——**规则部分不能转**。

**判断**：**可能可以拆**（字段表→附件 `04.Att.01`，使用规则留 §7），但**拆出后 §7 仍留大部分内容**，收益有限。**属"可做但不必做"**。

## 四、**附件路径的结论（回答原始问题）**

**`01 §8.3` 的允许清单指向"结构化契约"，而 01–04 的表格几乎都是"规则的表格式表达"**：

| 表 | 承载的是 | 能否转 |
|---|---|---|
| `01 §8.1` 编号登记表 | 编号分配规则的**结果** | ❌ 正文规则抽不走 |
| `01 §8.2` 已退出 key 表 | 1 行数据 + 核对规则 | ❌ 得不偿失 |
| `03 §6.1` 公共字段表 | **字段语义（规则）** | ❌ 违反 §8.3 |
| `04 §6.1` 风险层表 | 预检要求（规则） | ❌ 仅 3 行 |
| `04 §9.3` 十项结构表 | **义务内容** | ❌ §8.3 明文禁止 |
| **`04 §7` 预检落实记录** | **字段表 + 使用规则** | ⚠️ **部分可拆，收益有限** |

**结论：`04 §7` 是唯一符合"字段表"形态者，但拆分收益不大。** 原始判断得到验证：**上位规范偏大不是"该转附件"的问题**。

## 五、真正的空间：**三处结构同构**（这才是重点）

我发现**上位规范的主体是三份「共同结构契约」**，它们**高度同构**：

| | 管什么 | 行数 |
|---|---|---:|
| `01 §7` 普通规范共同章节契约 | **所有**普通规范的固定八章 + 领域正文 | 46 |
| `03 §11` 事实类型规范共同结构 | `20–29` 事实类型规范的十项角色 | 56 |
| `04 §9` 业务系统规范的公共结构约束 | `30–35` 业务系统规范的十项结构 | 61 |
| **合计** | | **163** |

**同构之处**：三者都在做同一件事——**「为某类规范定义共同结构、必填内容与扩展规则」**。

**差异之处**：
- `01 §7` 定义的是**所有规范的共同骨架**（元层级）
- `03 §11`/`04 §9` 定义的是**各自领域的十项结构**（领域层级）

**这里的真实问题是**：`03 §11` 与 `04 §9` 的十项**各自独立定义**，**没有共同的元规则说明"如何定义一类规范的共同结构"**。若未来 32–35 或新类型出现，**会继续复制第三、第四份同构契约**。

**潜在修法**（**仅供后续论证**）：
- 在 `01 §7.2` 定义**「领域共同结构契约」的元规则**（必须含：结构角色表、必填内容、扩展规则、锚点标注要求），`03 §11`/`04 §9` 成为其**两个实例**而非各自发明结构。
- **收益**：新增类型时不必重新发明；三处不会漂移。
- **代价**：这是**实质重构**，触及三份规范，须经 `01 §12` 独立审核。

**我未推进此项** —— 它超出「体积与归属」的调查范围，属**规则设计变更**，须你先决定是否值得走。
