> 更新：2026-09-17（§4.2 WorkCase 阅读视角更新为 v5 语义；两个 Gate 待办组配色区分）
> 范围：`web/` 当前参考实现、页面开发文档和后续 Web 修改入口

## 1. 文档定位

本文用于把 Web 当前开发现状、页面文档职责和已经稳定的设计语言收敛到一个入口。后续修改 Web 页面时，应先按本文判断目标页面属于哪一类，再回到对应页面文档和源码实现。

本文不替代 `specs/07-Web 呈现与交互规范.md`、`specs/06-Code 实践与测试规范.md` 中适用于 Web 的测试规则、事实模型规范或 Git 文件事实源。本文只说明当前 `web/` 参考实现如何把这些规则呈现给 Human。

当前字段级读取器读取 WorkCase、ADR、Pitfall、Spark 和 Study 的当前正式载体；不读取 V2/V3 资产。WorkCase 不根据对象年代、缺失字段或实现版本切换结构。详情、对象预览、源路径复制和正文阅读必须先取得字段级直读，并把 `canonical_path`、`carrier`、`read_status`、读取问题、字段问题与未解析结构传到消费面。Study 定位为“外部内容调研报告”，不提供兼容双读。

## 1.1 已确认与待确认边界

当前 Web 设计沉淀采用“已确认先固化、待确认不写死”的原则。最前面第一入口已确认可见名为“聚焦 / Focus”，内部概念和源码仍使用 Cognition Center；其余入口 / tab 的最终名称、顺序和信息架构仍未完全确定，因此本文只沉淀它们必须遵守的视觉、i18n、复制、阅读面板和事实源边界，不把其余临时入口文案写成最终产品结构。

已确认并可进入实现收敛的内容：

1. App Shell 采用左侧主导航、中间主内容和右侧扩展阅读区；移动端右侧扩展阅读切换为底部阅读抽屉。
2. 对象列表使用卡片网格和统一状态筛选 tab，不回退到表格或顶部对象类型 tab。
3. 对象详情是语义阅读器，不是载体文件查看器；YAML 数据由精确读取后的事实对象字段重建，不显示源码兜底，Markdown Study 的完整阅读只进入同一份正文的扩展阅读。
5. ObjectDetail 和 ReadingPanel 必须复用同一套身份头部、节点顺序、折叠行为、关联行和复制语义。
6. 所有用户可见 UI 文案必须走 i18n；事实正文、Git message、Markdown 正文、路径、命令、ID 和 hash 不翻译。
7. 复制入口必须按对象路径、文档路径、链接、引用、提交上下文和提交 hash 区分，不使用泛化“复制完整路径”覆盖所有场景。
8. Web 只做 Human-facing 派生展示和受控轻写入，不成为第二事实源。
9. 聚焦页五个只读模块已经完成：待决定事项、推进中事项、近期动态、Spark 健康度和近期提交热点关系；详细派生规则以 02 为准。

待确认且不得写死为最终设计的内容：

1. 聚焦之后其余前置入口 / tab 的最终名称、顺序和信息架构。
2. 这些未确认入口是否最终对应当前工作、项目文件或其他更准确的产品入口。
3. 未确认入口不得反向影响已确认的聚焦页、对象页、提交页、ProjectFiles、扩展阅读、复制语义和 i18n 规则。

## 1.2 YAML 解析能力

`web/package.json` 已提供 `js-yaml`。当 Web 的 Node API 或前端确实需要解析 YAML 文本时，统一使用该依赖，不新增手写 YAML 解析器或第二个 YAML 库。

它只负责把已取得的 YAML 文本转换为程序数据；事实对象的读取边界、字段契约、可读状态和写入校验仍以现有受控读取与服务端契约为准。不得因为可以解析 YAML，就在页面侧把源码、导航路径或解析失败补造成事实字段，也不得直接改写事实载体。

## 2. 五个基准模块

当前 Web 的设计语言以五个已经完善的阅读模块为中心：

## 4. 统一设计语言

五个基准模块共享以下语言：

1. 顶部切换区使用 `ldvh-tab-list` / `ldvh-tab-button`，滚动时固定在主滚动容器顶部。
2. 列表主体使用 `ldvh-section-grid`；卡片宽度不足时换行，不用表格或营销式大留白替代。
3. 精确可读详情、预览和已解析引用的右上可放复制入口；候选卡不复制源路径。状态、类型和标题各在自己的层级，不互相挤占。
4. 标题带使用弱背景、内圈边框、左侧语义短线、对象类型图标或提交图标和完整标题。
5. 更新时间统一在卡片底部右侧，使用 `formatDateTime()`。
6. 详情页和右侧扩展阅读复用同一身份头部、节点顺序、折叠行为和关联行。
7. 正文节点使用小圆点标题、整行点击折叠、`ChevronDown` / `ChevronUp` 和统一 Markdown 阅读样式。
8. 已精确读取且有来源路径的关联行使用左侧语义图标和标题，右侧提供复制入口与扩展阅读入口；其余关联行保留扩展阅读入口但不伪造路径。操作图标必须垂直居中。
9. 复制入口必须按内容语义命名和复制：对象复制对象路径，文档复制文档路径，URL 复制链接，普通引用复制引用，提交卡片复制提交定位上下文，提交详情复制 hash。

### 4.1 四类事实对象的共同阅读基线

Study、ADR、Spark 与 Pitfall 已经形成 WorkCase 必须继承的阅读秩序。它们不是字段数相同的模板，而是在不同事实任务下共同遵守以下分层：

1. **先身份，后判断。** 统一身份头部先说明类型、状态、稳定 ID、标题、更新时间、可用时的更新流水署名与可用复制动作；不把状态、时间或复制混入正文节点。
2. **详情按阅读问题组织。** 每个对象以少量固定语义节点承接当前最需要理解的事实，而不是逐字段铺开。节点默认展开，使用同一圆点、整行折叠和 Markdown 正文。
3. **终态是处置，不是另一套时间线。** 只有终态对象才出现 `disposition_summary`；它与对象的 `updated_at` 共同构成最后一次有效记录，不新增关闭、退出或分流时间字段，也不把处置做成强警报模块。
4. **列表只帮助定位。** 卡片保留身份、状态、标题、必要优先级和更新时间；ADR retired、Pitfall discarded、Spark terminal 才补一段弱处置正文，Study 不在列表复述报告摘要。
5. **关联在主阅读之后。** 关联区只呈现来源已有的正式关系或外部资料。可读对象先解析标题、状态与可复制路径；未解析或跨项目引用如实保留其稳定身份，不把导航信息写成新的事实判断。
6. **详情与扩展阅读同源。** ReadingPanel 复用同一身份头部和阅读布局；Study 正文是同一 Markdown carrier 的进入入口，不在主详情复制第二份全文。

WorkCase 已经形成进展分组 Card 与状态无关详情的专属信息契约，但仍必须落在这六项共同秩序中：专属派生信息只回答 Human 当前扫读问题，不能替代身份、事实正文、当前复核与处置、Human 确认或批准、终态处置或关系来源。

### 4.2 WorkCase 人的阅读视角

WorkCase / 工作责任是工作主线对象，可以拥有不同于研究、决策、火花、经验和提交的专用阅读形态；但它仍必须继承同一套身份头部、卡片框架、复制语义、右侧阅读和弱装饰语言。WorkCase 的设计语言必须先继承五个成熟模块的基线，新的专用表达只能围绕“WorkCase 对象更复杂”来增加，不能另起一套视觉和信息秩序。专用形态只服务人的阅读任务，不允许把内部执行细节提升为一级对象或另起一套状态事实。

**v5 权威语义**：WorkCase 的类型语义、字段闭集与 Gate 授权语义的唯一权威是 `specs/21-WorkCase-工单.md`。呈现契约的层级（2026-10-09 起）：`specs/07` 只保留**最上层约定**（§5.1–§5.4 四层阅读器、§6 交互入口、§12 反过度设计红线）；**具体呈现规则整体移入本文 §5「WorkCase 呈现契约」**，§4.2 诸小节是其阅读视角的**说明性摘要**——两者不一致时以 §5 为准。本节与 §5 都**不重定义**状态机、字段或 Gate 语义，也不得作为规范源。

**本节承载实现与状态（2026-10-09 起）**：按 `specs/07` §3.4「本文只承载要求，不承载实现状态」，07 不再承载实现接线与落地状态；**实现与状态由本节与 §5 承载**。故记录：具体由哪个组件、哪处常量、哪份测试钉住，以及各形态的落地状态与实测口径。**形态判据以本文 §5 为准；与 `specs/07` §12 红线冲突时以 07 为准。**

#### 4.2.1 三态直读与派生分组

WorkCase 的呈现状态由 `status` 闭集三值（`draft` / `open` / `closed`）直接读取，不引入 v4 的 `phase` 或任何多值进度词汇。`closed` 配 `outcome` 四值（`completed` / `partial` / `not-achieved` / `cancelled`）呈现终态徽标。

列表筛选与收件箱**共用同一派生函数**（`web/shared/workcaseLifecycle.ts`，防口径漂移）。四个派生组与“全部”构成五档筛选：

| 派生组 | 派生判据 | 词条 |
|---|---|---|
| `pending_gate1` | `status = draft`（含 C2 局部重批回退的对象——同在等 Gate 1） | 待批准执行 |
| `executing` | `status = open` ∧ 正文不含 H2「结果」节 | 执行中 |
| `awaiting_gate2` | `status = open` ∧ 正文**含** H2「结果」节 | 待批准关闭 |
| `closed` | `status = closed` | 已关闭 |

派生组是**呈现层派生值，不写回对象**。它必须经语义映射本地化呈现（`getObjectStatusLocale` / `getObjectStatusHint`），不得裸露 `pending_gate1` 一类 raw snake_case。

四个派生组的语义色按 `docs/01` §1.10.2 的精确映射，且**两个 Human Gate 待办组必须显著不同色**（Human 指令 2026-09-17）——二者语义相反，同色会使 Human 无法一眼分辨「尚未开始」与「已完工待验收」：

| 派生组 | 语义 | 配色 |
|---|---|---|
| `pending_gate1` | 工单尚未开始，等 Gate 1 放行 | 琥珀（与 `draft`/`pending` 待办族同源） |
| `executing` | 正在执行 | 天蓝 |
| `awaiting_gate2` | 工单已做完，等 Gate 2 验收 | 紫（Human 待确认紫系） |
| `closed` | 已关闭 | 低饱和蓝灰 |

**着色必须单一来源**：徽标经 `StatusBadge → getStatusColor`（`utils/statusColors.ts`），卡内状态提示行经 `WorkCaseGroupHint` 调用**同一个**函数——不得在业务组件里硬编码 `text-amber-*` / `text-violet-*` 一类颜色类。两条平行路径必然分歧：曾出现 `pending_gate1` 的徽标是紫、而它自己的卡内提示是琥珀的矛盾，即同一张卡片里两种颜色说同一件事。

徽标的 tooltip 必须说明「这是派生分组、不是来源 status 取值」，避免 Human 把派生值误读为对象字段。

「待批准关闭」以「正文含 H2 结果节」为派生依据，因为该节是 `specs/21` §8 定义的**关闭提案正文承载**（关闭提案时必填）；**不得改用「Gate 2 已提请」一类运行期状态**——那不是事实源中可读的稳定内容。H2 识别须忽略代码围栏内的行，并容许 ≤3 空格缩进。

#### 4.2.2 列表卡片

WorkCase 列表优先回答 Human 的四个问题：

1. 我现在最该看哪个 WorkCase；
2. 这项工作责任是否需要我处理或确认；
3. 这项工作责任当前卡在哪里；
4. 这项工作责任是否已经形成可供关闭判断的报告与分流建议。

卡片头部的标签序固定为**类型 → 优先级 → SG → 修改次数**（2026-09-13 Human 定案），不设关联 chip——关联对象由卡体关联段承载。卡体随派生组呈现当前最需要扫读的事实：

```text
WorkCase 身份 / 优先级 / SG / 修改次数 / 派生分组
待批准执行：gist / 计划步骤 / 待 Gate 1 批准标识
执行中：gist / 变更流水（复核·修订·已批准(增量)·已拒绝(增量) 文字标记）；有待批增量申请时，流水之上多一块「待批调整」
待批准关闭：逐条核对 / 残留（含流向标记）
已关闭：去向（按去向词分区）；outcome = cancelled 时另加取消理由块
更新时间
```

**卡体块构成的权威与最近三次变更（2026-10-09 校正）**：上列块构成已按 `specs/07` §5.5「四组卡体（块构成与次序）」校正。本节此前记录的是**旧形态**，三处已失效，如实登记以免回退：

1. **「执行中」**：原记「attempt 执行者与心跳 / 计划步骤」，现为**目标（`gist`）＋ 变更流水**（含四类文字标记）。
2. **「待批准关闭」**：原记「待 Gate 2 关闭标识 / 计划步骤 / 结果草稿存在标识」，现为**逐条核对 → 残留（含流向）**。
3. **「已关闭」**：原记「outcome 四值徽标 / result.criteria_checks 逐条核对 / Gate 1 授权行」——这三个块**均已删除**。现为**去向一块**（按去向词分区），`outcome` 由**卡头合并徽标**（状态词 · 结论词）承载，核对结果与证据归详情面。

`result.criteria_checks` 的每条核对在列表卡与收件箱只呈现一段紧凑文本；该文本的**状态词必须是可读文本**（**达成 / 部分达成 / 未达成 / 未记录**），不得把布尔直接插值（不得出现裸 `true` / `false`），三态词条与详情共用 `web/src/utils/workcaseCheckState.ts` 的单一映射。三态中「未记录」与「未达成」语义不同，必须可区分。

> **2026-10-09 校正**：本段原记「已满足 / 未满足 / 未记录」，与 `specs/07` §5.5「核对状态词跨组统一」及 `specs/21` §8 的三词映射（达成／部分达成／未达成）不符——`closed` 卡曾另用一套词，导致同一状态在两个派生组显示为不同词、跨组不可比；该分歧已由规范收敛为单一词表，本段随之订正。

卡片排版固定为“16px/500 对象标题 → 13px/600 判断区标题 → 12px/20px 事实正文 → 11–12px 元信息”。对象标题与决策、经验、火花、研究卡片使用同一 `ldvh-card-title`，不以 WorkCase 类型单独放大；标题、判断项标题、判断项正文和元信息必须分别使用共享语义类，不在业务组件内临时指定字号。判断项正文即使在卡片里使用紧凑字号，也仍属于事实正文，不能使用弱色、mono 或辅助标签语义。

**对象标题为 16px/24px（Human 2026-10-05 复核定）**：该档原为 14px/20px，导致卡片上 chip 盒高（18px）与标题行高（20px）之比达 **0.90**——一排彩色状态胶囊与标题行几乎齐平，标题压不住标签；详情页因标题行高 28px、比值 0.64 而层级分明。回到 24px 行高后比值降至 **0.75**，层级恢复。该值的完整沿革见 `docs/01 §1.4` 的卡面标题行与 `index.css` 同期注释（含 2026-09-08 当天三次改口的记录）。`ldvh-object-title-tray-compact` 的 `min-h-9`（36px）本就等于 16px/24px + `py-1.5`（12px），故标题带无需另行调整。

五种派生分组保持同一中性外层 Card；状态徽章、标题短线和内部语义块已经足够表达分组，不再用整卡染色叠加强调。语义色的标题和正文必须与背景同色相并通过明度区分，普通语义标题不借用等宽元信息字体。

计划步骤以**有序列表**呈现（来源已定义步骤顺序）；判据与残留责任等并列集合统一使用圆点。只有来源已明确表达步骤、优先级、排名或依赖顺序时才使用数字序号，不得把数组位置或稳定 ID 视觉化为先后关系。

#### 4.2.3 详情阅读面

WorkCase 详情用于完整理解同一项当前责任。它**不自行渲染对象身份块**——类型标签、状态徽标、标题、更新时间与复制入口由共享 `ObjectIdentityHeader` 统一承载（`docs/01` §1.8.1）；详情页与右侧扩展阅读同源，不得出现两套头部。

正文段按 `specs/21` §8 的三态语义组织，四个派生组各有面向当前判断的主体；但**字段在场性不随分组变化**：条件字段可以随事实是否形成而省略，已存在字段不能因对象处于某个派生分组而消失。`summary` / `serves` / `scope` 三个身份与授权字段在四个主体中一律呈现（有值即显示），分组只改变**强调**，不改变**在场字段集**。

```text
身份头部（共享，不在此布局内重复）
摘要 / 服务子目标 / 授权范围（四组共有，有值即显示）
待批准执行：计划与完成判据 / 复核记录 / 待 Gate 1 批准标识
执行中：执行现场 / 计划与完成判据 / 复核记录
待批准关闭：待 Gate 2 关闭标识 / 正文「## 结果」节 / 计划与完成判据 / 复核记录
已关闭：终态判定 / 判据逐条核对 / 已证实范围 / 去向 / 计划与完成判据 / 复核记录 / Gate 1 授权
关联对象（共享）
变更历史（共享，默认折叠）
YAML 数据、未解析结构与字段问题汇总（共享，默认折叠）
```

> **2026-10-09 校正（决定 A 的详情面收窄）**：`closed` 行的节点清单原含「残留责任」，与 `specs/07` §5.5「已关闭卡不呈现独立残留块」及「详情面的同一收窄」不符——决定 A 之下已关闭对象的详情面**同样不再呈现残留一侧**，只呈现**去向**。本节改为「去向」。`result.residual` 字段**仍在载体与投影中**（`specs/21` §8 要求），其文本在正文「## 结果」节仍完整可读，收窄只作用于**字段侧的呈现**。

> **未覆盖的呈现面（如实登记；本条完整登记见下方正文）**：同一批残留文本还有**第二处呈现面**——正文「## 结果」节原文经 Markdown 全量渲染。故字段侧按 A 收窄后，**同一批文本仍会从正文节上屏**。该冲突**属须 Human 裁决的事项**，完整登记（含两条路径、实测证据与暂停消费依据）见本章「未覆盖的呈现面：正文「## 结果」节」。

**节点名的口径（2026-10-03 同步）**：上列名称为**详情面实际渲染的节点标题**（`locales.ts` 的 `objectDetail.workcase*` 键）。此前本清单有 4 处与实渲染逐字不一致——`计划与判据`、`复核节点`、`attempt 执行现场`、`结果逐条核对`——系历次改名未回灌文档所致，现已按实值订正为 `计划与完成判据` / `复核记录` / `执行现场` / `判据逐条核对`。改动 `locales.ts` 中这些键时必须同批更新本清单；本期即有一次遗漏（提交 `d58baeb` 改了 `objectDetail.workcasePlan` 而未同步本文）。

本清单中**未在详情面渲染为同名节点**的 3 个条目——`待 Gate 1 批准标识`、`待 Gate 2 关闭标识`、`结果草稿正文`——是**派生分组的语义描述**（该分组存在、载有何物），不是节点标题；实际呈现方式见下文及 `docs/01` §1.6，本节不以其名称断言存在同名节点。

**「结果草稿标识」只属于 `awaiting_gate2`，不属于 `executing`**：派生规则里 `has_result_draft` 为真 ⇔ 正文已含「## 结果」节 ⇔ `group = awaiting_gate2`（`shared/workcaseLifecycle.ts` 同一次派生同时给出 group 与该标记），故 `executing` 组内该标记恒为假。任何在 `executing` 分支渲染「关闭准备窗口」的写法都是不可达代码，且会让一条提示的着色入参与所在分组不一致——不得恢复。

详情正文段一律使用**详情阅读层级**（`ReadingNodeSection` + `ResearchTextNodeContent`，14px 阅读基准），与其余六类阅读布局同款。`docs/01` §1.4 第 4 条明确：卡片判断项正文只用于 Card 的有限行数扫描窗口，详情页和阅读面板仍使用各自正文层级，**不得随之缩小**——详情不得复用 `ldvh-card-decision-body`（12px 卡片扫描层级）承载事实正文。

**该禁令的实现覆盖（2026-10-05 收敛）**：`WorkCaseCriteriaList` 的 `density` 参数此前只切换行距与分割线，正文两档同为 `ldvh-card-decision-body`（12px）——`ProseNode` 已按本条修过（缺陷 D10），但本组件漏改，详情页的「计划与完成判据」「残留责任」两处正文因此仍停在卡面扫描档。现 `density` 成为**正文层级**的唯一分岔点：`card` → `ldvh-card-decision-body`（12px），`detail` → `ldvh-body`（14px）。实测详情页 `ldvh-card-decision-body` 归零、判据正文回到 14px/24px，与其余六类阅读布局一致。

**回归验证口径**：`WorkCaseCriteriaList` 的 `detail` 档正文必须落在 14px 阅读基准；在其两处详情调用点（`WorkCaseReadingLayout` 的 PlanNode / ResidualNode）渲染后，页面内不应存在任何 `ldvh-card-decision-body` 实例。卡面两处调用（`ObjectList`、`CognitionCenter`）的 12px 扫描档不受影响。

`result.criteria_checks` 的每条核对在详情呈现为：三态 chip（可读文本 + 可区分形态）+ 依据正文。10 §12.8 禁止只用颜色或图标单独承载状态，故颜色仅作辅助，文字必须独立可判读。`result.residual` 是字符串数组；**按决定 A 与 `specs/07` §5.5「详情面的同一收窄」，已关闭对象的详情面不呈现该字段侧**（其文本仍在正文「## 结果」节可读）。空数组（合法：`outcome = completed` 时可为空）表示「无残留责任」，与「未记录残留」必须可区分。

`reviews`（复核节点概要流水，`specs/21` §8）按 `specs/07` §5.3「变更历史（摘要形态）」呈现——列出每次复核的时间、署名与概要。**复核详情不入对象**，故详情面不承载其原文。

YAML 数据、未解析结构和字段问题汇总作为来源数据与技术诊断默认折叠，由 Human 主动打开；字段问题仍在对应语义节点就地显示。折叠只属于 Web 阅读状态，不影响 API 返回，也不成为 AI 取得事实的入口或权限边界。

#### 4.2.4 数据面与证明边界

WorkCase 列表与详情在 Helper 已确认的管辖 worktree 内由 Web 直接读取当前正式载体；它不启动 Web machine 或完整机械校验。字段级读取与 list/detail 投影归属 `web/api/services/localFactReader.ts` 和 `facts.ts`：读取层按 `specs/02` §7.1 归一顶层时间字段（公共身份字段的时间语义由 `created_at` 与 `change_log[].at` 承担），投影层必须按**各字段在规范中的真实类型**判定（`satisfied` 是布尔、`residual` 是字符串数组；`gate_1.approved_at`、`attempt.started_at`/`heartbeat_at` 经 js-yaml 解析后是 `Date`，须归一为 RFC 3339 文本）——按 `typeof === 'string'` 一类假定判定会把合规字段静默丢弃，使详情退化为「未记录」。

列表把可解析字段投影为 Card，并把字段问题、未解析结构和集合问题如实保留；只有载体 I/O 或 YAML 无法解析时才是读取失败。页面不设置列表级“观察时间”或“重新读取”控件；筛选或导航触发新的直读请求，不能复用旧 payload、对象更新时间或浏览器渲染时刻冒充新观察。定向回归命令为 `cd web && npm run test:web:api && npm run check`。

本节的派生规则只证明**呈现当次**的读取与派生结果；不证明对象语义正确、Gate 授权成立、执行推进或结果达成。派生结果不写回事实源。

> **来源与性质（2026-10-09 移入）**：本章原为 `specs/07-Web 呈现与交互规范.md` §5.5，经 Human 指示「web 应该只保留最上层的约定，具体规则实现都应该放到 web 专属的设计文档里」整体移出。
> **效力边界**：本章**不构成规范源**（`specs/00` §3.2、`specs/01` §4.3）。其约束力来自实现约定与契约测试，不来自规范。
> **与规范的关系**：`specs/07` §5.1–§5.4（四层阅读器）、§6（交互入口）、§12（反过度设计红线）仍是规范级要求；本章的形态**不得违反**它们，两者不一致时**以 `specs/07` 为准**。
> **上位指引**：WorkCase 的类型语义与字段唯一权威仍是 `specs/21-WorkCase-工单.md`；本章只定义呈现，不重定义状态机、字段或 Gate 语义。

本章定义 WorkCase 在 Web 中的**呈现契约**——读什么、由什么派生、如何呈现、何时呈现。**类型语义与字段的唯一权威是 `specs/21-WorkCase-工单.md`**；本章不重定义状态机、字段或 Gate 语义，也不得作为规范源。`21` 号语义变更时本章随之复核；实现接线见 §4.2.5。

**三态直读**：WorkCase 的呈现状态由 `status` 闭集三值（`draft` / `open` / `closed`）直接读取，不引入多值进度词汇。`closed` 配 `outcome` 四值（`completed` / `partial` / `not-achieved` / `cancelled`）呈现终态徽标。

**派生分组（呈现层派生，不写回对象）**：列表筛选与收件箱**共用同一派生判据**（防口径漂移）。四组及其派生判据：

| 派生组 | 判据 |
|---|---|
| 待批准执行（`pending_gate1`） | `status = draft`（含 C2 局部重批回退的对象——同在等 Gate 1） |
| 执行中（`executing`） | `status = open` ∧ 正文不含 H2「结果」节 |
| 待批准关闭（`awaiting_gate2`） | `status = open` ∧ 正文**含** H2「结果」节 |
| 已关闭（`closed`） | `status = closed` |

筛选提供五档：上述四组加「全部」。**四组与五档是闭集**，不得增设第五个派生组或新增状态词汇。

**「待批准关闭」的判据说明**：以「正文含 H2 结果节」为派生依据，是因为该节是 `21 §8` 定义的**关闭提案正文承载**（关闭提案时必填）。**不得改用「Gate 2 已提请」一类运行期状态**——那不是事实源中可读的稳定内容。H2 识别须忽略代码围栏内的行，并容许 ≤3 空格缩进。

**交互入口接线**：`draft` 对象接入 `21 §10.1` 的 Gate 1 提请（对应 §6.2 计划审查）；`open` 且正文含结果节的对象接入 `21 §10.2` 的 Gate 2 提请（对应 §6.4 验收交还）。收件箱待办由上述派生组产生，不得由进度字段或运行期标记产生。

**执行期「增量审批」待批项的呈现**：`open` 对象存在**待批的增量申请**时，呈现层须让 Human 看得见「这一单在等他批」。呈现**只在一处：卡片与语义详情**——**不设收件箱待办**（网页只呈现、不接收指令）。**判据单一来源**：待批 ＝ `gate_1.amendments` 的末项无 `decision`，卡面与详情取同一值，不得两处各写一套。**不新增派生组、不新增状态词汇**——该对象仍归其所属的既有派生组（`executing`／`awaiting_gate2`），本项只是组内多一块。**决定的入口不在网页**。

**判据的机械可读性**：待批状态取自 `gate_1.amendments` 的末项是否已有 `decision`（该流水的形态与校验见 `21 §8`／§14）。这是**机械可读**的字段判据：不需事务性运行期标记，也不接受「AI 自称已提请」。

**复核节点的呈现**：`21 §8` 的 `reviews`（复核节点概要流水）按 §5.3「显示该对象的变更历史（摘要形态）」呈现——列出每次复核的时间、署名与概要。**复核详情不入对象**，故详情面不承载其原文。

**执行期阶段（呈现层派生，不写回对象；不进筛选与收件箱）**：`executing` 组内部按下列判据派生四个阶段，供卡片与详情呈现。**本派生不对「派生分组」的闭集做任何扩张**——筛选仍为五档、收件箱待办仍由上述四组产生；阶段是同一组内部的呈现细节，不是状态词汇。

| 阶段 | 判据 |
|---|---|
| 执行中 | `reviews` 不存在，且 `change_log` 中无**复核条目** |
| 复核中 | `change_log` 中存在**复核条目**，且 `reviews` 不存在 |
| 修订中 | `reviews` 存在，且其后仍有**本对象**的 `change_log` 条目 |
| 结项中 | `reviews` 存在，且其后无本对象的 `change_log` 条目 |

**「复核条目」（`21 §8` 记账纪律）**：摘要**以「复核：」开头**者，或含 `[review recorded by session`（Code 盖戳）者。**为何用前缀而非关键词**：`change_log` 中「复核这件事」与「处置复核的发现」共用同一批词——按关键词识别必然误判（旧实现即因此把处置动作标成了复核）。该判据两侧的可靠性不同：**完成一侧是机械的**（由受控动作盖戳写入，不依赖作者）；**发起一侧依赖前缀**（`21 §8` 已声明该条非机械门禁）。故「复核中」是组合判据，**不得据此声明复核过程已被完整机械记录**。

**阶段标签的当前纪律**：卡片**不得**呈现阶段标签——对象头部的状态显示恒为 `21` 号状态机的真实值，不被阶段影响；执行进度由卡片主体的「变更流水」及其标记表达（见下）。本判据留待后续需要时启用，**不得据上表在卡片上新增阶段标签**。

**变更流水（卡片主体的执行进度呈现）**：`executing` 组的卡片主体呈现 `change_log` 的流水——按日分组、每条给时刻、最多 8 条（更早折叠），关键行动以**文字标记**凸显：

| 标记 | 判据 |
|---|---|
| 复核 | 摘要**以「复核：」开头**（`21 §8` 记账纪律）**或**含 `[review recorded by session`（Code 盖戳，机械） |
| 修订 | **最后一条复核条目之后**的本对象条目（数组序；`reviews` 非空为前提） |
| 已批准（增量） | 摘要含 `[adjustment approved by`（机械方括号，`21 §14` 的批准支） |
| 已拒绝（增量） | 摘要含 `[adjustment rejected by`（同上，拒绝支） |
| （无标记） | 其余条目 |

标记与归属口径共用同一套判定规则（数组序／他对象排除／格式治理排除），须**单一来源**，组件不自行判断。**流水不改变对象状态，也不影响筛选与收件箱**。

**「待批调整」不是流水标记，而是卡体顶部的一块**：`open` 对象存在**待批的增量申请**时，卡体在流水**之上**呈现一块——判据是 `gate_1.amendments` 的**末项无 `decision`**（**不新增派生组、不新增状态词汇、不经收件箱**），块内给出「已申请追加 N 项」＋首条的 `step`，并注明「等 Human 决定」。**为什么与两种决定标记分开**：待批是「当下在等的事」（应当先被看到，且它尚未进 `change_log` 的语义序列），而两种决定标记是「发生过的授权事件」（属流水的一部分）。

**两种增量标记的优先级**：增量审批的决定是**授权事件**，比「复核之后又改了什么」（修订）更具体，故**优先于「修订」**；它不改变「复核」的判定（复核标记仍以其自身判据优先）。**不得**据此声称增量审批影响了对象的阶段或状态。

**判定口径**：① 一律按 `change_log` 的**数组序**判定，**不得**使用 `reviews[].at` 或 `change_log[].at` 的相对先后——同批条目可能被刷成同一时刻，时间不承载相对先后。②「本对象的条目」指摘要中**未**提及他对象 `workcase-XXXXXXXX` 的条目；提及他对象的条目不参与本对象的阶段判定。③ 摘要以「**格式治理：**」开头的条目（`21 §8`）不参与判定——它是跨对象的批量格式操作，语义逐字未变，不构成该对象的修订。

**与「待批准关闭」的区别**：「结项中」指已复核通过、尚未写出「## 结果」节的对象；一旦写出结果节，该对象即进入既有派生组「待批准关闭」（`awaiting_gate2`）。二者判据互斥，**不得合并**。

**未验证范围**：本条只提供判据，不保证「复核：」前缀被实际遵守——写成其它形式时「复核中」不可判（`21 §8` 已声明该纪律非机械门禁）。判据 ② 亦不排除「摘要未提及任何对象、实为他单工作」的条目。

**卡面与详情的字段分工（`21 §8`「`gist` 与 `summary` 的分工」的呈现落点）**：

| 呈现面 | 渲染 `gist` | 渲染 `summary` |
|---|---|---|
| 列表卡（§5.2 卡片网格，三态全部） | 是——卡体首行 | 否 |
| 聚焦收件箱卡体（待决定事项 / 推进中事项） | 是——卡体首行 | 否 |
| 联邦对象卡（跨项目视图） | 是——卡体首行 | 否 |
| 语义详情（§5.3） | 是——独立阅读节点 | 是——Markdown 节点 |

**本表是卡面的完整清单**：凡渲染 WorkCase 卡体的呈现面都在表内，新增卡面须同步登记。「卡面不渲染 `summary`」是**按呈现面类型**（扫读窗口）成立的规则，不因卡片来自单项目视图还是联邦视图而改变——同一张卡在两种视图下读者与版式相同，字段分工不得随数据来源漂移。

**AI 侧召回不在本节范围内**：F1/F2 召回投影由 `21 §13` 定义，本节不为其登记字段——`gist` 是**呈现层**的 Human 扫读字段，召回投影的字段集以 `21 §13` 原文为准。若日后需让 AI 侧也消费 `gist`，须先修订 `21 §13`，不得由本节倒推。

**为何卡面不渲染 `summary`**：卡面是**扫读窗口**（§5.2：Human 在卡片间扫描以定位感兴趣的对象），而 `summary` 按 `21 §8` 是**给执行者的完整快照**——它可以长、可以含编号引用与对象标识、可以带 Markdown 标记。把后者放进前者，会溢出扫读窗口，且纯文本插值路径会把 Markdown 标记以字面形式暴露给 Human。

**呈现降级（条件出现，如实披露）**：`gist` 在 `status = closed` 时按 `21 §8` 缺失合法（终态只读，无受控入口可补写）。卡面遇缺失时**如实降级**——不得以 `summary` 首句静默替代（那会把两个读者的字段混为一谈，掩盖字段缺口），也不得留白使卡片看似无内容。具体形态由 §12 第 7 条（长文本须有折叠或分层入口）与第 8 条（状态不得只由颜色承载）共同决定，本节只登记「必须可区分于有 `gist` 的卡片」。

**机械校验边界**：本节的派生规则只证明**呈现当次**的读取与派生结果；不证明对象语义正确、Gate 授权成立、执行推进或结果达成。派生结果不写回事实源。本节不校验 `gist` 的内容质量——`21 §15.1` 已声明机械层只校验存在性与长度，内容是否「Human 扫读自足」属 AI 语义审核与 Human 阅读。

**四组卡体（块构成与次序）**：四组的卡体均为**无标题栏**的块构成，次序不得调换：

| 派生组 | 块构成与次序 |
|---|---|
| 待批准执行（`pending_gate1`） | 目标（`gist`）→ 计划清单（`plan[].step` 逐条） |
| 执行中（`executing`） | 目标（`gist`）→ 变更流水（关键行动文字标记）；存在待批增量申请时，流水**之上**多一块「待批调整」 |
| 待批准关闭（`awaiting_gate2`） | 逐条核对 → 残留（含流向） |
| 已关闭（`closed`） | 去向（按去向词分区）；`outcome = cancelled` 时另加取消理由块 |

**「逐条核对」块去掉不等于核对未发生（须合读）**：`result.criteria_checks[]` 仍是关闭时的机械证据、仍在详情面完整呈现，`outcome` 徽标正是它的汇总结论；`closed` 卡面去掉的只是**同一批信息的第二次呈现**。不得据本条声称「核对已被取消」或「关闭无须逐条核对」。

**「已关闭」卡不呈现独立残留块**：已关闭意味着每条残留都已被去向**消化**（`21 §8` 合并式——去向子项长在每条残留之下，闭集二词二选一），故卡面无须再单列残留。**删除的是呈现、不是字段**：`result.residual` 仍在载体与投影中，其文本在语义详情（§5.3）与正文「## 结果」节仍完整可读，**丢失的只有卡面可见性**；判据仍由**详情面**消费（**同源不得被破坏**）。

**去向分区**：去向项的呈现**按去向词分区**——

- **分区标题**：去向词从**每条重复的行内标记**提为**块首标题**，标题**沿用该去向词标记的样式**（不新造标题样式）。同一去向词在一屏上因此**只出现一次**。
- **一个去向词一个区域**：各分区是**独立的块**（各有边框与底色，上下排列），不是同一块内的相邻分节。块底色取该去向词标记的**同族色**；**无现行去向语义色的词不着色**（为已停用语义新增色源属越界），回落中性只留边框。
- **组内条目**：只留正文，行首缀一颗**装饰性项目符号**（不承载语义；须与正文正确对齐，不得因行距叠加而与正文分离）。
- **不报条数**：分区标题**不写**「N 条」——块内条目读者一眼可数，逐块申报属冗余。
- **「转入 Spark」的目标关联行**仍**就地渲染**于该分区各条正文之下（行式见下）。按序配对为**写法约定**、非机械可核验事实（`21 §15.1`）。
- **信息未增未减（本项的边界）**：条目数、顺序、正文与逐条呈现时**逐字相同**——去掉的只是重复的词。这是**去重与分区**，不是对去向内容的加工：**不合并、不排序、不丢弃**判不出词的条目。分区按去向词的**首次出现顺序**排列，不按闭集顺序重排——条目顺序是作者写下的、载体里的既有信息。

**「待批准关闭」期为何不写去向正文**：该期**残留正文就在上一行**，去向正文在此重写一遍是同一信息的重复陈述。故呈现层在该期**只画去向标记**；**去向正文只在「已关闭」期呈现**（那时残留一侧不再上屏，去向正文是读者唯一读到的内容，`21 §8` 的**自足**要求正为该期而设）。**载体中仍写去向正文**——本项收窄的只是**待批准关闭期卡面的呈现**，不减损载体与门禁（`21 §15.1` 门禁⑤「接受现状」正文非空**仍在**）。**残留与其流向之间不加分割线**：流向行紧贴其所属残留，读作一个单元；单元与单元之间才有分割线。

**本表对既有承载的覆盖（如实登记，2026-09-29）**：上表以「残留段**及其去向子项**」为来源，另有两种既有承载不在该列之内、但仍须在该期呈现——① **存量分离式**正文（`- residual:` 段 + 独立的 `- advice:` 段）：该形态下去向不挂在残留之下（`21 §15.3` 要求呈现层**两种都要能解析**），故其去向**以独立块呈现且含去向正文**（不受「只给标记」约束）——这是**存量特例**，不是新写入形态的第二个口径；② **事后补记声明**（`21 §8`）：补写的去向段前须有声明行，且该声明**必须随去向子项一同呈现在卡面**——该期由去向块首行承载。**实测影响面**：当前 `ldvh-base/workcases/` 无处于待批准关闭期且为分离式的对象（本轮实测 23 份载体：18 closed、5 draft、0 open；5 份 draft 均无「## 结果」节），故本项为**潜在缺口**而非现行错误，如实登记以备将来。

**「已关闭」为何不再呈现残留（决定 A）**：去向不是独立的一段，而是**长在每条残留里面**（`21 §8` 的合并式形态）——「还剩什么」与「打算怎么办」是同一个不可分离的单元。关闭后该单元的去向一侧已按 `21 §8` 要求**自足**（离开残留也能读懂），故呈现层只画读者需要执行的那一半，残留不再重复出现。**这不是删除信息**：残留与其去向在**载体**中仍是同一个单元（合并式），收窄只发生在**呈现**层。

**决定 A 适用于全部关闭对象**：不设「不满足前提者如实保留残留块」的例外——已关闭卡体不含残留块，该例外无事可做，保留它只会制造第二套相互冲突的块构成。**既知后果（如实登记，不掩盖）**：存量分离式对象中，**无去向的那部分残留不再出现于卡面**；这些残留的文本**仍在载体正文「## 结果」节内**（`21 §8` 载体内聚），故**可读性未丢失**，丢失的是**卡面可见性**。

**详情面的同一收窄（决定 A 的一部分）**：A 不仅适用于卡片网格（§5.2），也适用于**语义详情**（§5.3）——关闭对象的详情阅读布局**同样不再呈现残留一侧**，只呈现去向。**与 §5.3「完整呈现所有字段」的关系以「已登记的窄例外」处理**（见 §5.3），该例外只作用于 WorkCase 终态对象的 `result.residual` 一个字段、**不得扩张**。该收窄现**一律适用**于全部关闭对象；判据由投影层单点给出，卡面与详情**同源**，不得两处各写一套。

**未覆盖的呈现面：正文「## 结果」节（如实登记为缺口，2026-09-28 独立审核发现）**：本条与下条登记的收窄只覆盖**字段侧**（`result.residual` 的上屏与否）。但同一批残留文本还有**第二处呈现面**——详情阅读布局的 `BodySectionNode` 会取正文「## 结果」节**原文**交 Markdown 全量渲染，而该节**正是** `result.residual` 与去向子项的正文承载（`21 §8` 载体内聚：字段值在正文逐字出现）。故按 A 收窄字段后，**同一批残留文本仍会从正文节原样上屏**——实测：一份合并式对象的 `closure_narrows_residual` 为 `true`（字段侧已收窄），而「## 结果」节原文仍返回并含全部残留文本；真实载体同型（`2be11478` 4/4 条、`63700bd2` 5/5 条仍在节内）。**本规范此前完全没有登记「正文节节点是否随 A 收窄」**（全文检索「正文节」「BodySection」为 0），故该缺口同时是**登记缺口**与**实现缺口**。**不得自行择一处理**：收窄正文节会与 `plugin/web/docs/01` §1.10 内容结构第 2、5 条（稳定阅读顺序「只按字段是否实际存在省略节点」；「多行内容按来源已有 Markdown 结构忠实渲染」）相冲，不收窄则 A 在详情面**事实上未达成**（Human 原话「在关闭页面就不应该有残留信息了，要删除掉」）。**故本项属须 Human 裁决的规范冲突**：路径 ① 为正文节开同款窄例外并写明边界（须同时处理 `docs/01` 的呈现纪律）；路径 ② 维持正文节完整渲染，明确 A 的适用范围**仅限字段侧**（则详情面仍会看到残留，须向 Human 说明该期待未被满足）。**在裁决前，受影响范围按 `00 §5.7` 暂停消费**——实现侧暂按路径 ② 保持现状（正文节照常渲染），并须登记暂停依据与恢复条件；**不得**声称 A 已在详情面完整达成。

**两期卡的关系（数据源不对称，如实登记；2026-09-28 二次修订；2026-09-29 三次修订）**：`21 §9.1` 规定 **`result` 出现 ⇔ `status = closed`**，故「待批准关闭」期 `result` 字段**尚不存在**，核对与残留（含去向子项）**只在正文**；「已关闭」期 `result` 已落盘并成为**权威**。两期的**内容项按 2026-09-29 定案分岔**：待批准关闭期读**残留（正文）＋其下的去向标记**（不读去向正文，理由见上）；已关闭期读**去向（标记＋正文）**（不读残留）。**去向的承载**：`result` 字段闭集只有 `criteria_checks`／`achieved_scope`／`residual` 三样，**不含去向**，故去向的**去向词与正文**在**关闭前后读的都是同一处正文承载**（`close` 不删正文），不另存一份（`21 §10.2`）——差别只在**哪一期呈现它**。**「转入 Spark」的指向**（2026-09-28 起，`21 §12`／`§10.2`）：指向哪个 Spark 属对象标识，由 `relations.routed-to` 承载；**该指向只在已关闭期呈现**（渲染为去向条下方的目标关联行，行式见上）——待批准关闭期**不呈现**目标关联行（该期卡只给去向标记）。**残留一侧相反**：开放期从正文读、关闭期按 A 不呈现（而非改读字段）；`result.residual` 字段仍落盘（`21 §8` 要求），只是不再上卡——字段存在与是否呈现是两件事。

**两期呈现所依据的正文形态**：`21 §8` 的新写入一律为**合并式**（残留 ＋ 去向子项）；存量仍有**分离式**（`- residual:` 段 ＋ 独立的 `- advice:` 段）。呈现层**两种都要能解析**——这是不溯及在消费侧的必要条件，不是双权威：同一对象在其载体中只有一种形态，解析器按实际出现的形态读取。**事后补记声明**（`21 §8`）须**随去向子项一同呈现在卡面**——该期由去向块首行承载；其用途正是让读者知道这些去向不是关闭时的提请输入。

**块序与逐条标记**：**待批准关闭**的块序为**逐条核对 → 残留（含流向）**——残留是「还剩什么」（事实），其下的去向标记是「打算怎么办」（拟议）；先陈述事实再给去向，读者才不必回头。**逐条标记**：残留条目带固定词「残留」标记，去向条目带**闭集二词**标记；使行的结构统一为「`[标记] 正文`」。**为什么残留用固定词而非分类词**：残留条目无闭集可归（`21 §8` 未给 `residual` 登记词表），条目自身常带 `**标题**` 前缀，故标记只回答「这属于哪一块」，不重复条目内容。**去向条的呈现按期分岔**：**待批准关闭**期去向**只给标记**、缩进一行紧贴其所属残留，且**该行与其残留之间不加分割线**；**已关闭**期去向为**平级行且带正文**（那时残留一侧不再上屏，去向正文是读者唯一读到的内容，`21 §8` 的**自足**要求正为该期而设）。**标记色与块底色同源**——颜色只表达「这是残留」一件事，不引入第二个语义色。

**单一来源纪律**：两期卡虽不再同构（开放期读完整单元、关闭期只读去向一侧），但**去向条目与残留条目的类名、标记与折叠阈值仍须只有一处来源**，消费方从该处取得、不得各自重写——分写必然漂移。两期在**标记与语义色**上一致，只在**块构成**（是否呈现残留一侧）与**密度**上分岔。

**语义块四边同为 1px 细线**：语义块的边框**四边同宽（1px）、同色**；**不得**用粗左线或独立的左线色。块的身份由**背景色**与**标记**表达，不由边框粗细表达。**代价（如实登记）**：移除左侧加粗竖线后，左边框的视觉强度降至与其余三边相同、**看起来会变淡**——这是「四边同为 1px」的必然结果，属已明确选择的效果，**不得再以「左边框太淡」为由回改**。该形态适用于所有同类语义块（判据面板、计划清单等），不得只改一处而致两处形态分岔。

**卡体条目行的分割线**：卡体内**所有**条目行——核对、去向、残留、计划清单——**统一**用带分割线的行样式；**条间距由该行的 padding 提供**，不再另用 `gap`。**首条不加顶线**，否则与块顶边框叠成双线。**为什么必须单一来源**：该样式曾被多处各自复制，导致同卡各块形态不一致；**单一来源**是唯一可靠做法。**卡面与详情的密度差异显式化为参数**：卡面用带分割线的紧凑行（扫读窗口），详情面用宽松行（阅读面）；两面**共享同色、同标记、同结构**，只在密度上分岔。

**计划清单的容器**：计划清单**必须有容器**，且**与详情页判据面板同源**——两处渲染的是**同一份 `plan` 数据**，形态因此呼应。**容器形态只有一处来源**：列表卡、收件箱、详情页**三处共用**，不得各写一份。**选蓝色而非中性灰／琥珀的理由**：① 有同源先例（详情页）；② 不与 `gist` 的琥珀框争色（同卡两个琥珀框会分不清主次）；③ 不引入新语义色。

**为什么核对只给步骤标题**：`21 §8` 的 `result.criteria_checks[]` 只有 `{satisfied, evidence}`，**不含判据文本**；若卡面显示整段证据，实测证据最长可达 258 字，一张卡被撑到十几行，扫读窗口（§5.2）失效。**证据与 `gate_1` 明细归详情面**（§5.3）。判据文本只能由 `plan[i].step` 给出，故 **`closed` 期列表卡投影须包含 `plan`**——否则卡上无法显示步骤标题。

**核对状态词跨组统一**：`closed` 卡**同样使用 `21 §8` 登记的三词映射**（词表以 `21 §8` 为唯一展开处，本处不重复列出）——**同一状态在两个派生组必须显示为同一词**，跨组可比。映射判定**只有一处实现**，各消费方从该处取得，不得各写一套。

**卡面纯文本**：卡体按**纯文本**渲染其条目正文（去向条的去向正文、取消理由块的一行理由）——不解析 Markdown 标记。写作侧纪律见 `21 §8`。存量已带标记的对象**不自动追溯改写**；确需清理时须由 Human 单独授权，按事实更正处理。

**「不解析」不等于「不显示标记」——卡面渲染前须剥标记**：纯文本插值会把 `**加粗**`、`` `标识符` `` 的标记本身显示给读者（实测正文残留与去向条目中含标记者接近七成）。故卡面渲染**去向正文**与**正文解析出的残留**之前，**须先剥离 Markdown 标记**；剥离为**单一实现**，各呈现面从该处取得。**剥的是显示、不是数据**——详情面仍用 Markdown 渲染（语义保留），数据层不改：同一源文本在两面形态不同是有意的（卡面是扫读窗口、详情是阅读面）。**未验证范围**：剥离只去标记，不证明剥离后文本「准确」或「可读」；且它不处理代码围栏、链接与表格——卡面不承载这些，出现即应**暴露**而非静默吞掉。

**卡头的合并徽标：状态词 · 结论词**：「已关闭」**且仅限 WorkCase** 的卡头**只画一枚**徽标，位于**右侧状态位**，文本为 `状态词 + 中心圆点 + 结论词`（`已关闭 · 完成`／`已关闭 · 部分完成`／`已关闭 · 未完成`／`已关闭 · 取消`），**配色由结论决定**。

- **只此一处**——`outcome` 在卡面**只在卡头这一枚里出现**，卡体不再有任何 outcome 元素。
- **不得回归为两枚并列或分置两处**：分开两处时读者要把「已关闭」与「完成／取消」自行拼起来，而它们本是**同一件事的两半**（怎么关的 ＋ 关得如何）。
- **只作用于 WorkCase 的「已关闭」卡**：其余**类型**与其余**状态**（无 `outcome` 可合并）**一律仍走默认状态徽标**，本形态**不得扩张**。判据须三条件齐备：类型是 `workcase`、状态是 `closed`、`outcome` 值存在；**缺 `outcome` 时回落默认状态徽标**。
- **四值各显其真**：**不得**把 `partial`／`not-achieved` 显示为「完成」——`21 §9.3` 明确 `partial` ＝ 部分判据达成、其余有明确未达成范围，写成「完成」即让卡头说一句**载体否认的话**。合并徽标用**短式**结论词（完成／部分完成／未完成／取消），而**独立出现**的结论词仍用原词表（已完成／部分达成／未达成／已取消）——两套词表的分工即「是否与状态词并排」。
- **不做展开**：该徽标不承载展开体；`result.achieved_scope`、逐条判据的**证据**、`result.residual` **均不上卡**——前两者归语义详情（§5.3），后者是 §5.3 已登记的例外。
- **不恢复核对计数**：徽标只给结论词，不带「核对 N/M 达成」。
- **不算状态词汇**：合并徽标仍承载状态机语义，但不参与派生分组、不进筛选五档、不进收件箱。
- **样式与既有卡头徽标一致**：尺寸、圆角、字号与内距**一律由共享 chip 形态给出**，组件不得自定——避免并排时高低不一。
- **状态徽标与合并徽标互斥**（只替换、不叠加）：命中合并徽标时不得并排画状态徽标（并排会把同一件事说两遍）；状态词须由调用方取得后**传入**合并徽标，组件内不得另取一份（两处各取一次即同一信息的两处来源）。

**取消理由块**：`outcome = cancelled` 的已关闭卡上，取消一事由**一块**承载——**形态与去向分区逐项相同**（同圆角/内距/块首标记/组内项目符号/字号），**只换一个颜色**，且**只留一行**。

- **只留一行**：标记词为「**取消理由**」（它是块首标题，须自足说明「这是取消的理由」）；**「未发生的范围」不再上卡**。
- **删除的只是呈现，不是字段**：「未发生的范围」是 `21 §8` 对取消记录的**必填项**；故该字段**仍在载体与投影中**、其文本在正文「## 结果」节与语义详情（§5.3）仍完整可读；本次收窄的只是**卡面可见性**。
- **换玫瑰色**：取消是「这单停掉了」，玫瑰是最直接的读法；且它与去向闭集二词的色源都不撞。**已知风险与抵偿（如实登记）**：红系可能被读成「失败」，而 `21 §9.3` 明写 cancelled 不是失败——故以**标记词「取消理由」先行**抵掉该读法；**此风险不声称已消除**。
- **复用而非另写**：块底／标题行／标题／条目行／项目符号／容器留白**一律取去向分区那组形态**；本块**只新增颜色**，尺度与去向分区一致。**形态类两处各写一份即本仓反复出现的「两处各写一套」病，故禁止**。

**目标关联行的行式**：「转入 Spark」去向条的**下一行**就地渲染目标 Spark 的关联行，形态为**单独一行**：`[目标类型图标（类型色）] 标题（撑满，单行不换行、超长省略号截断） [行末状态图标]`；状态**不写文字、只给图标**（可读文本由 `title` 属性承载，供 hover 与读屏）。状态取值与色相取**通用关联行**的口径：目标 spark `open` ⇒ `pending`「待处理」、`implemented` ⇒ `closed`「已关闭」、`discarded` ⇒ `discarded`「已废弃」。本条形态**不是本处特有写法，而是统一关联行的一个实例**（一般规则见下）。

**反向引用块的形态：无标题、无块边框**：「已关闭」卡呈现反向引用区（谁声明引用了本单），其**行式必须复用卡片的统一关联行**，**不得自建第二套行式**；且该区**没有标题、没有块边框、没有底色**——区域形态＝**顶部分割线 ＋ 行间分割线**。

1. **为什么去掉标题**：**行本身自描述**——类型图标说出这是什么类型的对象，行末状态图标说出它的状态；旧标题是一句规范腔长句，**不增加行所没有的信息**，却制造**命名难题**：任何概括词要么过长、要么**冒领方向语义**。
2. **冒领风险的具体形态（本条最有价值的登记）**：曾考虑把该区改名为去向闭集词「转入 Spark」——**该方向错误，且被否决**。理由三者皆不成立：① **方向相反**——`转入 Spark` 是**本单的**去向（承载在**本单的** `relations.routed-to`），而本区是**别人**的 `refs` 指向本单（**反向**）；同一份对象上二者可并存且含义无关。② **会宣称载体里不存在的边**——实测某对象的去向全部是「接受现状」、其 `relations` 内**没有任何 `routed-to`**；而该区列出的对象只是**声明引用了本单**（它自己的工作才是主题）。改名即等于宣称「本单残留转入了该对象」——**该边在载体里不存在**。③ **内容不由本单控制**——本区是**实时反查**（任何对象声明 `refs` 指向本单即入选），**不保证类型**；标题若写死某个去向词，一旦换类型即当场变假。**故本区不写标题即无冒领面**。
3. **两类引用不是同一批数据、也不互相替代**：外向引用（本单引用了谁）与反向引用（谁声明引用了本单）是两批数据——故反向区**不与外向关联合并**，只是**行式**与**区域形态**共用。
4. **理由（防漂移）**：同一类信息若两处各写一套行式，任何一处改样式都会让另一处不一致。**区域形态同理收敛到单一来源**，不各自抄类名。
5. **本区只显示「谁声明引用了本单」，不暗示建议已履行或已闭环**（`21 §13`）。
6. **未覆盖的边界（如实登记）**：本区与卡片的外向关联区在同时出现时会是**两组相邻的无标题行**，读者无法从形态区分方向——当前该情形结构上不可达（实测无对象同时具备两类引用），但这是**数据现状而非结构保证**，属须在出现真实样例时再定的缺口。

**事实对象关联一律以引用行呈现**：卡面凡牵涉**可解析事实对象**的关联（含「本单事项已由另一对象承接」「该缺口另立单处置」这类去向），一律以**统一关联行**呈现——类型图标 ＋ 标题 ＋ 行末状态，可点开；**不得**只在散文里写对象号/对象名充数（那不是可反查的承载，也点不开）。承载由该对象一侧的 `refs` 声明（`21 §12`），呈现在**反向引用区**。**边界（勿过度声明）**：引用行只证明「声明关联」，**不证明**承接已被批准、去向已被履行、语义已被覆盖或本单已闭环（`21 §13`）。

**同类信息只有一处行式（一般规则）**：**凡呈现「引用／关联某个事实对象」的行**，其行式**一律复用统一关联行**，**不得自建第二套**。

1. **适用**：卡片与详情面的**任何**「指向另一个对象」的行——外向引用、反向引用、正式关系、去向目标行皆在其列。
2. **理由**：同一类信息两处各写一套行式时，改一处另一处必然漂移；且读者会看到两种「指向对象」的形态而不知其别。
3. **可扩展的例外**：若某处确需不同行式（例如需要承载统一行**给不出的字段／动作**），**须先在本规范登记该处与理由**，不得以「就地实现」绕过；**未登记的差异视为缺陷**。
4. **不适用场景（免误套，按能力而非按文件登记）**：① 承载**关系键 chip、外部链接目标、复制路径、文档预览**的关联行——属关联行的**详情面扩展**；② 呈现**字段值里的引用**（带原文标识、类型 chip、复制）——属 §5.1 的**字段级直读**层，与「关联块行」不是同一层（四层互不替代）。
5. **判据**：一条行若承载统一行给不出的字段／动作，属合法差异；若只是「指向另一个对象」而无额外承载，**必须**复用统一行。

**认知中心热力图的关系显示规则**：派生视图（认知中心热力图）**只显示本仓已登记的关系键**，每个键的显示条件以**定义该关系的规范为唯一权威**——显示层不得自行放宽或收紧出规范不承认的形态。当前已登记的显示规则：

| 关系键 | 定义权威 | 显示条件（显示层，与写入期判定不同） |
|---|---|---|
| `routed-to` | `21 §12` | 源对象 `status = closed`；目标**只接受 spark**；目标状态接受 `open`／`implemented`／`discarded` 三者 |

**为什么目标接受终态而写入期只接受 `open`**——这不是两处权威，而是**两个不同的判据**：写入期判据是「该边此刻能否成立」（`21 §12` 要求目标写入时为 `open`，因为只有仍在承载议题的 Spark 才配作残留去向）；显示期判据是「该边此刻是否应当呈现」（`21 §13` 规定目标其后转终态**不使该边失效**，且消费方**必须**标注目标已终结——故终态目标必须画出来，由节点自己的状态徽标承载其终结态，而不是过滤掉；过滤会让「已终结的目标」静默消失，反而违反 §13）。**唯一权威仍是 `21 §12`**：显示层不判定该边是否有效、不新增或放宽可接受的边形态，只选择呈现范围。

**已知收窄（如实登记）**：该显示只画源对象 `closed` 的边。对象在 `open` 期已落盘 `routed-to`、尚未关闭的窗口内该边**不显示**（`21 §14` 的 CREATE-FIRST 次序会先把边写下来）。这是**显示选择**，不主张该边无效，也不构成对 `21` 的重述或修正。**未验证范围**：本行只登记 `routed-to` 一条——其余关系键（`serves`／`refs`／`contributed-to`／`related-to`／`depends-on`／`inspired-by`／`informs`）的显示条件**尚未按此形态登记**；此为**已登记的缺口**，在它们各自按此形态登记之前，不得据显示已在运行而推定其形态成立（`00 §6.3`）。

## 6. 复制语义

复制按钮不是泛化“复制”动作，必须让 Human 和 AI 都知道复制结果是什么。

| 场景 | Tooltip | 复制内容来源 |
|---|---|---|
| 精确可读的对象详情头部、对象引用、右侧对象预览 | 复制对象路径 | 精确读取返回的 `canonical_path`；缺失、无效或候选列表时不显示复制入口 |
| 本地 Markdown 文档、Study 正文入口 | 复制文档路径 | 文档绝对路径或规范化后的 Markdown 文件路径 |
| 外部 URL | 复制链接 | URL `ref` |
| 非对象、非文档、非 URL 的普通引用 | 复制引用 | 原始引用文本 |
| 提交卡片 | 复制提交上下文 | 面向 AI 定位的稳定多行提交上下文 |
| 提交详情 | 复制提交 hash | 完整 commit hash |
| ProjectFiles 工具页 | 复制路径 | 项目路径、文件路径或 diff 文件路径 |
| 聚焦页模块标题带 | 复制模块摘要 | 面向 AI 对话的多行文本：模块名、所选时间窗口（仅适用模块）、关键计数与条目稳定 ID；不显示或复制页面“观察时间” |

对象路径复制不得依赖可能只是对象 ID 的 `target`、列表 `path` 或导航键作为来源。`canonical_path` 只是预期位置，仍须与字段级直读的 `read_status: readable` 一起成立；否则页面显示实际读取状态、字段问题和未读取范围，而不复制路径。

## 7. 后续开发顺序

后续继续推进 Web 时，推荐按以下顺序做判断：

1. 目标是否影响五个基准模块；如果影响，先保证五个模块一起变化。
2. 目标是否影响详情页和右侧扩展阅读；如果影响，两处必须复用同一布局或同一字段组件。
3. 目标是否影响列表卡片；如果影响，先对齐调研、决策、火花、经验对象卡片和提交卡片。
4. 目标是否新增复制、图标、状态、时间或 tab；如果新增，先检查全局设计、图标语义和 i18n。
5. 目标是否改变 API、事实源读取或状态派生；如果改变，补充或说明对应测试验证。
6. 目标是否读取 Git commit records；如果读取，必须复用 `web/api/services/git.ts` 的 commit message 拆分和 Conventional Commits 解析，不在页面 API 中维护第二套 parser。
7. 目标是否改变 App Shell 高度或滚动；如果改变，必须保持根节点不滚动、主内容/侧栏导航/阅读正文各自拥有滚动，并验证侧栏滚轮不会推动文档或产生横向滚动条。

## 8. 不再采用的方向

1. 不把对象详情退回 YAML 字段平铺。
2. 不让每个对象类型各自发明卡片、节点标题、复制按钮、关联行或时间位置。
3. 不把提交页当成独立视觉系统；提交是五个基准模块之一。
4. 不在右侧扩展阅读区维护第二套对象摘要。
5. 不用“复制完整路径”作为通用文案覆盖对象、文档、链接、引用和提交这些不同动作。
