# Web 开发现状与设计语言基线

> 更新：2026-08-13
> 范围：`web/` 当前参考实现、页面开发文档和后续 Web 修改入口
> 上位文档：[`01-全局设计约束.md`](./01-全局设计约束.md)

## 1. 文档定位

本文用于把 Web 当前开发现状、页面文档职责和已经稳定的设计语言收敛到一个入口。后续修改 Web 页面时，应先按本文判断目标页面属于哪一类，再回到对应页面文档和源码实现。

本文不替代 `specs/08-Web 呈现与交互规范.md`、`specs/07-Code 实践与测试规范.md` 中适用于 Web 的测试规则、事实模型规范或 Git 文件事实源。本文只说明当前 `web/` 参考实现如何把这些规则呈现给 Human。

当前字段级读取器读取 WorkCase、ADR、Pitfall、Spark 和 Study 的当前正式载体；不读取 V2/V3 资产。WorkCase 不根据对象年代、缺失字段或实现版本切换结构。详情、对象预览、源路径复制和正文阅读必须先取得字段级直读，并把 `canonical_path`、`carrier`、`read_status`、读取问题、字段问题与未解析结构传到消费面。Study 定位为“外部内容调研报告”，不提供兼容双读。

## 1.1 已确认与待确认边界

当前 Web 设计沉淀采用“已确认先固化、待确认不写死”的原则。最前面第一入口已确认可见名为“聚焦 / Focus”，内部概念和源码仍使用 Cognition Center；其余入口 / tab 的最终名称、顺序和信息架构仍未完全确定，因此本文只沉淀它们必须遵守的视觉、i18n、复制、阅读面板和事实源边界，不把其余临时入口文案写成最终产品结构。

已确认并可进入实现收敛的内容：

1. App Shell 采用左侧主导航、中间主内容和右侧扩展阅读区；移动端右侧扩展阅读切换为底部阅读抽屉。
2. 对象列表使用卡片网格和统一状态筛选 tab，不回退到表格或顶部对象类型 tab。
3. 对象详情是语义阅读器，不是载体文件查看器；YAML 数据由精确读取后的事实对象字段重建，不显示源码兜底，Markdown Study 的完整阅读只进入同一份正文的扩展阅读。
5. ObjectDetail 和 ReadingPanel 必须复用同一套身份头部、节点顺序、折叠行为、关联行和复制语义。
6. 所有用户可见 UI 文案必须走 i18n；事实正文、Git message、Markdown 正文、路径、命令、ID 和 hash 不翻译。
7. 复制入口必须按对象路径、文档路径、链接、引用、提交上下文和提交 hash 区分，不使用泛化“复制完整路径”覆盖所有场景。
8. Web 只做 Human-facing 派生展示和受控轻写入，不成为第二事实源。
9. 聚焦页五个只读模块已经完成：待决定事项、推进中事项、近期动态、Spark 健康度和近期提交热点关系；详细派生规则以 02 为准。

待确认且不得写死为最终设计的内容：

1. 聚焦之后其余前置入口 / tab 的最终名称、顺序和信息架构。
2. 这些未确认入口是否最终对应当前工作、项目文件或其他更准确的产品入口。
3. 未确认入口不得反向影响已确认的聚焦页、对象页、提交页、ProjectFiles、扩展阅读、复制语义和 i18n 规则。

## 1.2 YAML 解析能力

`web/package.json` 已提供 `js-yaml`。当 Web 的 Node API 或前端确实需要解析 YAML 文本时，统一使用该依赖，不新增手写 YAML 解析器或第二个 YAML 库。

它只负责把已取得的 YAML 文本转换为程序数据；事实对象的读取边界、字段契约、可读状态和写入校验仍以现有受控读取与服务端契约为准。不得因为可以解析 YAML，就在页面侧把源码、导航路径或解析失败补造成事实字段，也不得直接改写事实载体。

## 2. 五个基准模块

当前 Web 的设计语言以五个已经完善的阅读模块为中心：

| 模块 | 路由 | 当前定位 | 作为基线的内容 |
|---|---|---|---|
| 提交 | `/changelog`、`/changelog/:hash` | Git commit records 证据追溯 | 筛选 tab、提交卡片、提交详情、复制提交上下文、右侧快速阅读 |
| 外部调研 | `/objects/study`、`/objects/study/:id` | 外部调研报告阅读界面 | 研究意图、摘要、建议、唯一 Markdown 正文入口和关联资料；终态只在事实存在时显示处置 |
| 决策 | `/objects/adr`、`/objects/adr/:id` | 决策阅读页 | 对象卡片、标准身份头部、问题/决策/范围/理由/影响节点；retired 以处置收束 |
| 火花 | `/objects/spark`、`/objects/spark/:id` | 待处理信息阅读页 | 对象卡片、标准身份头部、意图/摘要/演变节点；implemented、discarded 才显示对应终态处置；历史 routed 仅只读兼容 |
| 经验 | `/objects/pitfall`、`/objects/pitfall/:id` | 可复用经验阅读页 | 对象卡片、标准身份头部、现象/触发/范围/验证/根因/方案/规避节点；discarded 以处置收束 |

这五个模块不是孤立样板，而是后续 Web 页面继续收敛的中心。新页面或旧页面改造如涉及列表、详情、右侧扩展阅读、复制入口、关联行、节点折叠或提交证据，应优先复用这五个模块已经形成的语言。

## 4. 统一设计语言

五个基准模块共享以下语言：

1. 顶部切换区使用 `ldvh-tab-list` / `ldvh-tab-button`，滚动时固定在主滚动容器顶部。
2. 列表主体使用 `ldvh-section-grid`；卡片宽度不足时换行，不用表格或营销式大留白替代。
3. 精确可读详情、预览和已解析引用的右上可放复制入口；候选卡不复制源路径。状态、类型和标题各在自己的层级，不互相挤占。
4. 标题带使用弱背景、内圈边框、左侧语义短线、对象类型图标或提交图标和完整标题。
5. 更新时间统一在卡片底部右侧，使用 `formatDateTime()`。
6. 详情页和右侧扩展阅读复用同一身份头部、节点顺序、折叠行为和关联行。
7. 正文节点使用小圆点标题、整行点击折叠、`ChevronDown` / `ChevronUp` 和统一 Markdown 阅读样式。
8. 已精确读取且有来源路径的关联行使用左侧语义图标和标题，右侧提供复制入口与扩展阅读入口；其余关联行保留扩展阅读入口但不伪造路径。操作图标必须垂直居中。
9. 复制入口必须按内容语义命名和复制：对象复制对象路径，文档复制文档路径，URL 复制链接，普通引用复制引用，提交卡片复制提交定位上下文，提交详情复制 hash。

### 4.1 四类事实对象的共同阅读基线

Study、ADR、Spark 与 Pitfall 已经形成 WorkCase 必须继承的阅读秩序。它们不是字段数相同的模板，而是在不同事实任务下共同遵守以下分层：

1. **先身份，后判断。** 统一身份头部先说明类型、状态、稳定 ID、标题、更新时间、可用时的更新流水署名与可用复制动作；不把状态、时间或复制混入正文节点。
2. **详情按阅读问题组织。** 每个对象以少量固定语义节点承接当前最需要理解的事实，而不是逐字段铺开。节点默认展开，使用同一圆点、整行折叠和 Markdown 正文。
3. **终态是处置，不是另一套时间线。** 只有终态对象才出现 `disposition_summary`；它与对象的 `updated_at` 共同构成最后一次有效记录，不新增关闭、退出或分流时间字段，也不把处置做成强警报模块。
4. **列表只帮助定位。** 卡片保留身份、状态、标题、必要优先级和更新时间；ADR retired、Pitfall discarded、Spark terminal 才补一段弱处置正文，Study 不在列表复述报告摘要。
5. **关联在主阅读之后。** 关联区只呈现来源已有的正式关系或外部资料。可读对象先解析标题、状态与可复制路径；未解析或跨项目引用如实保留其稳定身份，不把导航信息写成新的事实判断。
6. **详情与扩展阅读同源。** ReadingPanel 复用同一身份头部和阅读布局；Study 正文是同一 Markdown carrier 的进入入口，不在主详情复制第二份全文。

WorkCase 已经形成进展分组 Card 与状态无关详情的专属信息契约，但仍必须落在这六项共同秩序中：专属派生信息只回答 Human 当前扫读问题，不能替代身份、事实正文、当前复核与处置、Human 确认或批准、终态处置或关系来源。

### 4.2 WorkCase 人的阅读视角

WorkCase / 工作责任是工作主线对象，可以拥有不同于研究、决策、火花、经验和提交的专用阅读形态；但它仍必须继承同一套身份头部、卡片框架、复制语义、右侧阅读和弱装饰语言。WorkCase 的设计语言必须先继承五个成熟模块的基线，新的专用表达只能围绕“WorkCase 对象更复杂”来增加，不能另起一套视觉和信息秩序。专用形态只服务人的阅读任务，不允许把内部工作项提升为一级对象或另起一套状态事实。

WorkCase 列表优先回答 Human 的四个问题：

1. 我现在最该看哪个 WorkCase；
2. 这项工作责任是否需要我处理或确认；
3. 这项工作责任当前卡在哪里；
4. 这项工作责任是否已经形成可供关闭判断的报告与分流建议。

在呈现这四个问题以前，WorkCase 卡片先按“方案待确认 / 推进中 / 终止善后中 / 关闭待确认 / 已关闭”五个进展分组帮助 Human 定位。该分类轴只叫“进展分组”，不是 WorkCase 生命周期或正式状态。“推进中”的结果推进主链显示工作项执行、主控自检、结果复核、主控收敛四个推进环节；稳定键 `independent_review` 不证明实际方法为 subagent 或执行环境独立，实际方法与保证边界由 review 字段另行据实呈现。`plan_revising` 同样归入“推进中”，但显示为轨迹外内部位置“方案修订中”；`termination_cleanup` 使用独立 Card 和下一控制动作，不进入普通四步轨迹。创建前计划复核时尚无 WorkCase，不形成 Card 或分组。推进中可以以轻微且尊重减弱动态偏好的动效提示当前位置；终止善后和其它非推进分组不得借动效或推进轨迹暗示仍在执行原计划。

“方案待确认”Card 是 Gate 1 的紧凑入口：只显示 `goal`、成功标准和执行授权边界，并固定使用“目标”“成功标准”“执行授权边界”标题；成功标准用与详情相同的蓝色圆点列表。`scope`、完整工作项与方法、当前方案复核、执行批准及其基线指纹与来源引用全部留在同源详情页。项目认知中心复用这张紧凑 Card，标题在页内打开同源次级阅读；不额外叠加聚焦页专属条目操作。缺失或 malformed 时明确降级，不拼装伪完整材料。若该 WorkCase 同时为 `status=blocked`，Card 在紧凑入口之外完整显示独立的 `blocking_summary` 状态提示；它不改变“方案待确认”进展分组。

“推进中”Card 延续同一两区结构，但第二个区域从“成功标准”切换为与详情同名的“当前情况”：目标继续完整显示；结果推进主链显示四个固定推进环节并只高亮当前 `progress_step`，`plan_revising` 则显示“方案修订中”且不高亮四步。四个环节因来源已定义顺序而使用 1–4 编号，但编号不构成完成历史，前序环节不得因当前位置后移就显示完成。处于 `item_execution` 时，当前情况完整显示工作项的 ID、目标与状态：已完成项在前使用勾选，进行中项以当前样式突出，未执行项在后弱化，阻塞和取消项也如实保留；其它环节只显示 active 项。状态分组不表示执行顺序。work item 结构、身份、状态条件或依赖不成立时，相应工作项区整组显示不可判定，不使用数组位置、title、ID 或已退出字段补造线性执行信息。实际存在 `waiting_on` 或顶层 `blocking_summary` 时完整显示，二者都不替换当前推进位置；其标题分别与详情统一为“等待对象”和“阻塞说明”，并沿用详情琥珀/玫红语义色，Card 字号比详情小一级。成功标准、scope、依赖、方法、完整工作项计划、Reviewer 复核、Controller 处置、Human 批准、验证说明和关闭报告与分流建议留在详情页。

该 Card 的排版固定为“14px/500 对象标题 → 13px/600 判断区标题 → 12px/20px 事实正文 → 11–12px 元信息”。对象标题与决策、经验、火花、研究卡片使用同一 `ldvh-card-title`，不以 WorkCase 类型单独放大；标题、判断项标题、判断项正文和元信息必须分别使用共享语义类，不在业务组件内临时指定字号。成功标准陈述即使使用紧凑字号也仍属于事实正文，不能使用弱色、mono 或辅助标签语义。

WorkCase 的五种进展分组保持同一中性外层 Card；状态徽章、标题短线和内部语义块已经足够表达分组，不再用整卡染色叠加强调。内部主次随 Human 当前判断任务变化：方案待确认突出目标与成功标准，推进中突出当前情况，终止善后中突出 Human 中止来源与善后边界，关闭待确认与已关闭突出关闭结论及责任处置；不处于当前判断中心的目标仅保留低饱和支持层。语义色的标题和正文必须与背景同色相并通过明度区分，普通语义标题不借用等宽元信息字体。

成功标准是并列集合，统一使用圆点；只有来源已明确表达步骤、优先级、排名或依赖顺序时才使用数字序号。不得把数组位置、criterion ID 或显示排序视觉化为先后关系。

`current_snapshot_projection.lifecycle_position=closure_preparing` 表示“推进中 / 主控收敛”；只有同一投影的 `handoff_narrative_key=gate2_waiting` 才显示“关闭待确认”。`gate2_position_blocked` 必须显示“关闭位置受阻”并突出阻塞，不得在 Human Gate 尚未成立或仍有阻塞时提前提示 Human 处理。

因此 WorkCase 列表卡片的信息层级应为：

```text
WorkCase 身份 / 优先级 / 进展分组
目标
方案待确认：成功标准
方案待确认且阻塞：在计划判断输入区之外追加独立阻塞状态提示
推进中：四环节当前位置 / 执行时完整工作项清单或其它环节 active 项 / 实际等待与阻塞
推进中方案返修：轨迹外“方案修订中” / active 项 / 实际等待与阻塞
关闭待确认：关闭判断输入区（目标 / 关闭结论提议 / 处置摘要 / 遗留事项处置建议）/ 后续贡献
已关闭：通用身份与分组；专属正文待后续定义
更新时间
```

“关闭待确认”Card 的关闭判断输入区直读 `goal` 与完整 `closure_proposal`，显示 route_existing、suggest_spark、accept_stop 三类处置及 Spark suggestions；“后续贡献”只列 `contributed-to` Pitfall 的当前标题与待确认/活跃/已废弃状态，不提供审核控件。“已关闭”Card 从终态 `goal`、outcome、disposition、`routed-to`、顶层 suggestions 和 residuals 使用同一扫读结构；`related-to` 只在详情呈现。closed 不保存关闭 approval 或关闭时间，Web 不得把这些已移除的过程字段当作缺失。

WorkCase 列表在 Helper 已确认的管辖 worktree 内由 Web 直接读取当前正式载体；它不启动 Web machine 或完整机械校验。列表把可解析字段投影为 Card，并把字段问题、未解析结构和集合问题如实保留；只有载体 I/O 或 YAML 无法解析时才是读取失败。页面不设置列表级“观察时间”或“重新读取”控件；筛选或导航触发新的直读请求，不能复用旧 payload、对象 `updated_at` 或浏览器渲染时刻冒充新观察。

字段级读取与 list/detail 投影归属 `web/api/services/localFactReader.ts` 和 `facts.ts`。Node 仅通过 `resolve-governance-scope` Helper 调用取得受管辖 worktree，随后直接读取载体；不得恢复 Web Python machine、并行双路径或全量机械校验。定向回归命令为 `cd web && npm run test:web:api && npm run check`。

WorkCase 详情页用于完整理解同一项当前责任。它在所有状态和 phase 下使用同一信息结构，不根据 Card 进展分组或推进环节切换、隐藏或重排内容。稳定阅读顺序为：

WorkCase 身份头部、列表 Card、聚焦页、阅读面板、共享轨道与详情“当前情况”消费各自当前载体形成的同一 `current_snapshot_projection`；raw `status / phase` 仍作为来源字段可读，但不再由 downstream 自行映射。投影分别回答浏览分组、内部位置、Gate handoff、阻塞覆盖与结构上的下一必经控制步骤；unresolved 统一不可判定，不得回退或写回来源状态。详情对 `next_required_control_step` 只显示闭集本地化文字，未知值不泄漏原始 key，也不提供按钮、自动动作或授权/完成判断。

```text
身份头部
当前情况：phase / summary / 实际等待、阻塞与恢复入口
目标：goal / scope
成功标准：定义及已经形成的三值结果
当前计划与工作项
独立方案复核
执行批准
结果与验证
主控自检
独立结果复核
关闭提案
终态处置
关联与外部网址
```

当前实现把这套顺序收敛为固定阅读节点：当前情况、目标、成功标准、当前计划与工作项、独立方案复核、执行授权边界、执行批准、结果与验证、主控自检、独立结果复核、关闭提案、终态处置、关联、外部网址。条件字段可以随事实是否形成而省略，但已存在字段不能因对象处于某个进展分组而消失；类型来源必填字段缺失或类型不符时，API 返回逐字段问题，页面在对应区段显示“缺失”或“类型不符”空态。WorkCase 的关联节点直接复用其它事实对象的标题、类型分组和目标行，不增加专属关系芯片；关系 kind 仍保留在来源、详情 API 与折叠 YAML 中。详情与右侧扩展阅读直接复用 `WorkCaseReadingLayout`，不读取列表摘要、计数或 active 项作为第二快照。

WorkCase 详情的 Human 语义阅读节点默认展开，并与 Card 对同一字段共享图标、标题、正文和语义色：`goal` 固定为“目标”，成功标准固定为“成功标准”，执行授权固定为“执行授权边界”。Card 只将授权边界表现为允许动作、禁止项与实际存在前置条件的数量摘要，不提供展开控件；详情将这三类内容表现为同级、默认收起的数量区块。已授权行动展开后的单项行动也默认收起，仅以“摘要＋稳定 ID”作为入口；目标/影响范围在打开单项后显示，风险、回滚和规则引用仍是次级展开内容，其中规则引用使用标签而非项目符号。行动上限、允许调整、验证回滚和越界处置作为同一“已授权行动”展开区末尾的二级分区。详情只扩展信息量，不改变同一事实的表达含义；其 `scope` 作为“目标”节点内的次级字段，而不是把共享标题改写为“目标与边界”。YAML 数据、未解析结构和字段问题汇总作为来源数据与技术诊断默认折叠，由 Human 主动打开；字段问题仍在对应语义节点就地显示。折叠只属于 Web 阅读状态，不影响 API 返回，也不成为 AI 取得事实的入口或权限边界。

成功标准在 Card 与详情中统一为一个蓝色语义区内的圆点并列列表。详情不为每条标准增加第二层 Card，也不把 `criterion_id` 提升为 Human 阅读标题；已有结果只在对应标准下追加状态和结果摘要。

详情节点采用一致的信息层级：稳定 ID、版本、事件时间和结论在标题或弱元信息层；工作内容、总体结果、复核范围和处置说明是主正文；预期结果、方法边界、验证说明、复核反馈、主控处置、剩余责任及恢复条件使用与职责匹配的次级语义块。职责说明使用轻量提示，不用单边分隔线或第二张同权卡片。语义颜色仅帮助 Human 区分信息角色，不重写来源枚举，也不把 Reviewer、Controller 或 Human 的判断合并。

工作项只表达 WorkCase 内部的阶段目标、预期结果、依赖、当前恢复、阻塞和阶段结果。current work item 状态闭集是 `pending / in_progress / blocked / completed / cancelled`，UI 文案对应“待处理 / 进行中 / 已阻塞 / 已完成 / 已取消”。Web 只消费这套当前状态闭集；其它状态值不进入当前 WorkCase 呈现合同，也不建立适配分支。

### 4.3 组件契约沉淀

以下组件契约属于已确认的跨页面设计语言。其余入口 / tab 的信息架构未定时，仍必须遵守这些组件契约，但不得把临时入口名称写入最终结构。

| 组件族 | 统一契约 | 不得出现 |
|---|---|---|
| Tab / 筛选 | 使用 `ldvh-tab-list`、`ldvh-tab-button`、`ldvh-tab-button-active`、`ldvh-tab-button-idle`、`ldvh-tab-count`；同层 tab 数字与文字同字体、同字号、同字重；所有宽度使用同一紧凑高度 | 单页自定义胶囊、加粗数字、营销式分段控件、顶部对象类型 tab 替代左侧导航；不得按窄屏单独放大或增高 |
| Card | 使用 `ldvh-section-grid` 和 `ldvh-panel`；标题完整换行；候选卡右上只放状态，不复制未精确读取的来源路径；更新时间固定在底部右侧；所有宽度使用同一标题入口高度 | 表格化对象列表、标题截断、候选卡伪造来源路径、右上堆叠多个强按钮、卡片内大面积装饰色；不得建立窄屏专属 Card |
| Identity Header | 顺序固定为 `类型标签 + 状态标签 + object-id`、标题、标签、更新时间（最新完整更新流水署名可紧随其后）、右上复制对象路径；详情页和右侧预览同源 | 状态漂移到右上操作区、对象详情和 ReadingPanel 两套头部、ID 做大号标题 |
| Reading Node | 小圆点标题、整行点击、`ChevronDown` / `ChevronUp`、Markdown 内容区、默认展开 | 每个对象类型自定义折叠样式、正文节点内放额外“展开/收起”文字按钮 |
| Reference Row | 左侧语义图标 + 标题/路径/URL，右侧复制入口 + 扩展阅读入口；整行打开扩展阅读，复制不触发展开 | 对象、文档、URL 各自使用不同卡片、文字按钮或操作尺寸 |
| ReadingPanel / 移动抽屉 | 顶部控制区固定，正文独立滚动；桌面右侧面板保留拖动宽度、前后导航和关闭控件，对象标题由滚动正文中的同源身份头部呈现；Compact 只切换为底部抽屉，抽屉标题区同时承担当前对象识别和高度拖动 | 右侧对象列表导航、只开不关的单向入口、移动端另做独立站或底部主导航、桌面和抽屉分别维护对象摘要 |

## 5. 复制语义

复制按钮不是泛化“复制”动作，必须让 Human 和 AI 都知道复制结果是什么。

| 场景 | Tooltip | 复制内容来源 |
|---|---|---|
| 精确可读的对象详情头部、对象引用、右侧对象预览 | 复制对象路径 | 精确读取返回的 `canonical_path`；缺失、无效或候选列表时不显示复制入口 |
| 本地 Markdown 文档、Study 正文入口 | 复制文档路径 | 文档绝对路径或规范化后的 Markdown 文件路径 |
| 外部 URL | 复制链接 | URL `ref` |
| 非对象、非文档、非 URL 的普通引用 | 复制引用 | 原始引用文本 |
| 提交卡片 | 复制提交上下文 | 面向 AI 定位的稳定多行提交上下文 |
| 提交详情 | 复制提交 hash | 完整 commit hash |
| ProjectFiles 工具页 | 复制路径 | 项目路径、文件路径或 diff 文件路径 |
| 聚焦页模块标题带 | 复制模块摘要 | 面向 AI 对话的多行文本：模块名、所选时间窗口（仅适用模块）、关键计数与条目稳定 ID；不显示或复制页面“观察时间” |

对象路径复制不得依赖可能只是对象 ID 的 `target`、列表 `path` 或导航键作为来源。`canonical_path` 只是预期位置，仍须与字段级直读的 `read_status: readable` 一起成立；否则页面显示实际读取状态、字段问题和未读取范围，而不复制路径。

## 6. 后续开发顺序

后续继续推进 Web 时，推荐按以下顺序做判断：

1. 目标是否影响五个基准模块；如果影响，先保证五个模块一起变化。
2. 目标是否影响详情页和右侧扩展阅读；如果影响，两处必须复用同一布局或同一字段组件。
3. 目标是否影响列表卡片；如果影响，先对齐研究、决策、火花、经验对象卡片和提交卡片。
4. 目标是否新增复制、图标、状态、时间或 tab；如果新增，先检查全局设计、图标语义和 i18n。
5. 目标是否改变 API、事实源读取或状态派生；如果改变，补充或说明对应测试验证。
6. 目标是否读取 Git commit records；如果读取，必须复用 `web/api/services/git.ts` 的 commit message 拆分和 Conventional Commits 解析，不在页面 API 中维护第二套 parser。
7. 目标是否改变 App Shell 高度或滚动；如果改变，必须保持根节点不滚动、主内容/侧栏导航/阅读正文各自拥有滚动，并验证侧栏滚轮不会推动文档或产生横向滚动条。

## 7. 不再采用的方向

1. 不把对象详情退回 YAML 字段平铺。
2. 不让每个对象类型各自发明卡片、节点标题、复制按钮、关联行或时间位置。
3. 不把提交页当成独立视觉系统；提交是五个基准模块之一。
4. 不在右侧扩展阅读区维护第二套对象摘要。
5. 不用“复制完整路径”作为通用文案覆盖对象、文档、链接、引用和提交这些不同动作。
